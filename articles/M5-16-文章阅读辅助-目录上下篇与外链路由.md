# 成为全栈·Taro 小程序篇·文章阅读辅助：目录、上下篇与外链路由

> 一篇长文读到一半，读者想回到某个章节；读完一篇，想顺着系列往下看。这些小入口，决定了他会不会留下来。

{{IMG:M5-16-封面}}

## 前言：正文打开以后，产品才开始接受考验

目录、上下篇、作者、分类、外链，每一个入口都很小，组合起来却决定了阅读是否顺手。它们还有一条共同约束：辅助请求失败，不应该阻断已经能读的正文。

当前文章页因此独立组织正文、分类树、上下篇和相关文章。目录由正文解析，链接交给统一路由，阅读记录则结合可见时间处理。我们逐项看它们如何协作。

## 目录和正文必须对得上

标题 ID 不从标题字符串拼接，而是由 parseMarkdown 按出现顺序生成。中文标题、重复标题都拥有各自节点 ID。正文和目录读的是同一次解析结果的 `headings`：

```ts
// src/pages/article/index.tsx：目录直接复用正文解析出的标题清单。
const toc = useMemo(() => parseMarkdown(article?.content || "").headings, [article?.content]);
```

目录面板是一个浮层：底部弹出、限制高度、可纵向滚动，点遮罩关闭、点面板内部阻止冒泡。点击某一条时先关面板，再滚到目标。缩进不靠嵌套 DOM，而是由标题层级直接换算：

```tsx
// src/pages/article/index.tsx：目录浮层与滚动定位。
{tocOpen && (
  <View className="overlay" onClick={() => setTocOpen(false)}>
    <View className="toc-panel" onClick={(e) => e.stopPropagation()}>
      <ScrollView scrollY style={{ maxHeight: "60vh" }}>
        {toc.map((h) => (
          <View
            key={h.id}
            className="menu-item"
            style={{ paddingLeft: `${(h.level - 1) * 10}px` }}
            onClick={() => {
              setTocOpen(false);
              Taro.pageScrollTo({ selector: `#${h.id}`, offsetTop: -12, duration: 250 });
            }}
          >
            {h.title}
          </View>
        ))}
      </ScrollView>
    </View>
  </View>
)}
```

`offsetTop: -12` 给标题留一点顶部余量，避免文字贴着屏幕边缘。`stopPropagation` 是必需的——没有它，点面板内部也会冒泡到遮罩层，手一碰面板就关掉。`maxHeight: 60vh` 保证长目录滚动而不遮住关闭动作。这些细节让目录是一个临时阅读工具，而不是把读者困在另一层页面。

当前正文和目录分别调用同一算法，结果能保持对应；并没有把它们说成只解析一次。如果以后增加标题过滤或插件，必须同时验证两边的 ID 顺序，不能一边加编号另一边仍沿用旧规则。

### 为什么目录不用标题文字当选择器

中文、空格、括号和重复标题都可能使文本选择器复杂化。标题文本还可能在内容编辑后变化。顺序 ID 让当前解析内的唯一性更简单，目录只需对准当前节点。

代价是标题顺序变化后 ID 也会变化，所以它不是可以永久引用的跨版本锚点。若以后需要“分享某一章节”，应设计稳定锚点策略与版本兼容，而不是直接把 heading-3 当成长期公开标识。

这次目录只服务当前页面内部跳转，顺序方案足够直接。选择 ID 方法时，要先问它要活多久，而不是只看生成字符串是否好看。

## 一个只在真机上出现的目录 bug

目录浮层做完那天，测试同学在小屏设备上点了"收起" —— **面板没关掉，反而往上跳了一段。**

我第一反应是 `stopPropagation` 没写。查了代码，`onClick={(e) => e.stopPropagation()}` 明明白白在。

**真正的原因在 `paddingLeft` 那行**：`${(h.level - 1) * 10}px`。在小屏上，三级标题的缩进把文字挤到了很窄的位置，**而点击区域只有文字那么大** —— 我一直以为整行都可点，实际只有那几个字可点。

修法是给每一条加 `padding` 撑出足够的点击区域：

```tsx
// src/pages/article/index.tsx（节选）：点击区域要撑满整行。
<View
  key={h.id}
  className="menu-item"
  style={{ paddingLeft: `${12 + (h.level - 1) * 10}px` }}
  onClick={() => {
    setTocOpen(false);
    Taro.pageScrollTo({ selector: `#${h.id}`, offsetTop: -12, duration: 250 });
  }}
>
```

而这个 bug 在开发工具里看不出来 —— **因为模拟器是我按的默认尺寸，而我按的恰好是文字还够宽的那个尺寸。**

这和 M5-10 那个 Tab 图标是同一类问题：**只在一个配置下正确**。区别是那个丢的是图标，这个丢的是点击区域。**而点击区域的缺失比图标更难发现，因为"点不动"和"点得动但要点准"在视觉上很像。**


## 上下篇使用服务端关系，不从当前列表猜

文章列表的排序可能是最新、最多阅读，也可能来自搜索。拿列表数组里的前后项当“上一篇／下一篇”，会把查询上下文误当成文章关系。

当前调用 `/articles/{id}/adjacent`，由服务器返回 prev 和 next。相关文章也有独立端点。两者只在公开阅读模式请求，未发布本人预览不展示这些公开阅读入口——传空路径等于不发请求：

```ts
// src/pages/article/index.tsx：预览态下路径为空，请求根本不发出。
const adjacent = useResource<{ prev: Article | null; next: Article | null }>(
  article && !preview ? `/articles/${article.id}/adjacent` : "",
);
const related = useResource<Article[]>(
  article && !preview ? `/articles/${article.id}/related` : "",
);
```

渲染层也只按“有没有数据”决定显示，不为空关系编造占位。prev 和 next 各自独立判断，任一为空就整块不渲染：

```tsx
// src/pages/article/index.tsx：两个方向互不牵连，页面不会出现空的“上一篇”。
{adjacent.data?.prev && (
  <View className="menu-item" onClick={() => openArticle(adjacent.data!.prev!.id)}>
    <Text>上一篇：{adjacent.data.prev.title}</Text>
  </View>
)}
{adjacent.data?.next && (
  <View className="menu-item" onClick={() => openArticle(adjacent.data!.next!.id)}>
    <Text>下一篇：{adjacent.data.next.title}</Text>
  </View>
)}
```

| 阅读辅助 | 数据来源 | 无结果时怎么理解 |
|---|---|---|
| 目录 | 当前正文标题 | 没有标题就不显示目录入口 |
| 上下篇 | adjacent 端点 | 某一方向可能没有文章 |
| 继续阅读 | related 端点 | 空数组不等于正文失败 |
| 分类入口 | 分类树查 ID 对应 slug | 不应拿 ID 误充 slug |
| 作者主页 | 公开会员端点 | 与私人资料页分开 |

辅助结果可以为空，也可能请求失败。当前 UI 没有把它们提升为整页致命错误，避免“正文已经到了，却因为推荐挂了而不让读”。

### “继续阅读”也需要克制

技术教程的正文已经信息密集。上下篇与相关推荐应在正文后出现，不要因为接口可用就插入正文中段，打断论证。目录则是用户主动打开的辅助层，平时留给阅读空间。

这套布局来自确认过的原型。平台迁移保留阅读优先级，再根据平台能力调整外链行为，才能让三个客户端仍然像同一个内容产品。

## 站内链接需要识别，外链需要解释

`openLink` 识别当前站点 `/articles/` 路径，提取文章标识并安全解码，再进入原生文章页面。HTTP(S) 外站地址则弹窗确认复制，其他协议提示不支持。三种出口在同一个函数里分流：

```ts
// src/core/navigation.ts：站内走原生页，外站复制，其他协议明确拒绝。
export async function openLink(href: string) {
  if (/^(https:\/\/befull\.kao9\.com)?\/articles\//.test(href)) {
    const id = href.split("/articles/")[1].split(/[?#]/)[0];
    if (id) {
      try {
        openArticle(decodeURIComponent(id));
      } catch {
        Taro.showToast({ title: "链接地址无效", icon: "none" });
      }
      return;
    }
  }
  if (!/^https?:\/\//i.test(href)) {
    Taro.showToast({ title: "不支持此链接类型", icon: "none" });
    return;
  }
  const r = await Taro.showModal({ title: "打开外部链接", content: href, confirmText: "复制地址" });
  if (r.confirm) await Taro.setClipboardData({ data: href });
}
```

站内文章走原生页，读者继续使用目录、互动和评论；外站复制地址，用户知道接下来需要另行打开。这是两种不同能力，不应该统一给一个“打开成功”的提示。`openLink` 的三条分支，各自对应一种用户能理解的结果：

| 链接形态 | 处理 | 用户预期 |
|---|---|---|
| 站内 `/articles/{id}` | 进入原生文章页 | 继续用目录、互动和评论 |
| HTTP(S) 外站地址 | 弹窗确认后复制 | 需自行到浏览器打开 |
| 其他协议 | 提示不支持 | 明确拒绝，不假装成功 |
| 百分号编码非法 | 提示地址无效 | 不静默吞掉点击 |

站内跳转最终落到统一的 `go()`：它拼好 `/pages/<page>/index?<query>` 再 `navigateTo`，失败时给一句可读提示，而不是静默失败：

```ts
// src/core/navigation.ts：所有页面跳转共用一个入口。
export function go(page: string, params: Record<string, string | number> = {}) {
  const query = Object.entries(params)
    .map(([k, v]) => `${k}=${encodeURIComponent(v)}`)
    .join("&");
  return Taro.navigateTo({ url: `/pages/${page}/index${query ? "?" + query : ""}` }).catch(() =>
    Taro.showToast({ title: "页面打开失败，请返回重试", icon: "none" }),
  );
}
```

参数统一走 `encodeURIComponent`，所以分类名里的中文、空格不会把 URL 拼坏；失败也只提示一句，不会让读者卡在一个没响应的点击上。

解码也是一种边界：错误百分号编码可能让 `decodeURIComponent` 抛异常。当前捕获后显示“链接地址无效”，不给用户一个无响应点击。

站内匹配只覆盖当前实现接受的路径形式。它不是完整 URL 路由器，也不会自动把任意其他主机的 `/articles/` 解释为本站内容。新增域名与路由要补充测试，不能随意放宽匹配。

## APP 的 WebView 为什么没有搬过来

APP 已经拥有内部网页容器。小程序却受平台能力和环境配置约束，本轮选择复制降级，没有承诺任意外链在内部浏览。

这不影响文章接口复用，却改变了产品体验。更合适的文案是“复制地址”，而不是“在应用内打开”。若未来增加 web-view，要明确目标域名和平台条件，再给出真实验收；仅关闭开发工具校验不能作为正式能力依据。

这种取舍在 [小程序与 APP 的能力取舍]({{LINK:M5-07}}) 里继续讨论。跨端一致性首先是意图清楚，不是每个端都画出相同按钮。

## 阅读计数与个人历史是两件事

文章页可见约五秒后，调用公开 `/view`；有会员会话时，再写入个人 history。两条上报共用一个计时，却分属两套归属：

| 维度 | 公开计数 `/view` | 私人历史 `/me/history` |
|---|---|---|
| 前置条件 | 无，游客也计 | 需要会员会话 |
| 触发时机 | 可见满五秒 | 可见满五秒且已登录 |
| 携带数据 | 仅文章 ID | 文章 ID 与当前进度 |
| 失败处理 | 静默，不打断正文 | 静默，不弹错 |
| 预览态 | 不触发 | 不触发 |
| 数据归属 | 文章 | 当前会员 |

隐藏时取消尚未到期的计时，已记录阅读则可以补充当前进度。

发送前后还受会话边界影响。计时建立时捕获 epoch，如果期间换了账号，旧计时整支作废：

```ts
// src/pages/article/index.tsx：五秒计时里，epoch 变了就什么都不写。
const epoch = sessionEpoch();
timer.current = setTimeout(() => {
  if (epoch !== sessionEpoch()) return;
  recorded.current = true;
  void api(`/articles/${article.id}/view`, "POST", undefined, false).catch(() => {});
  if (session())
    void api("/me/history", "POST", { articleId: article.id, progress: progress.current }).catch(() => {});
}, 5000);
```

进度不是一个数字，而是一组引用在协作。进入页面先测一次正文高度，滚动时按比例算百分比，隐藏时把已记录进度补报一次：

```ts
// src/pages/article/index.tsx：测高、算进度、隐藏补报三者配合。
const measure = setTimeout(() => {
  Taro.createSelectorQuery().select("#article-content")
    .boundingClientRect((r) => { if (!Array.isArray(r) && r) height.current = r.height; }).exec();
}, 500);

usePageScroll(({ scrollTop }) => {
  progress.current = height.current
    ? Math.max(0, Math.min(100, Math.round((scrollTop / height.current) * 100))) : 0;
});

useDidHide(() => {
  clearTimeout(timer.current);
  if (recorded.current && article && session() && !preview)
    void api("/me/history", "POST", { articleId: article.id, progress: progress.current }).catch(() => {});
});
```

延迟 500ms 才测高，是因为正文刚渲染、图片还没撑开，立刻量会偏小，进度自然算虚高。`Math.min(100, ...)` 把结果钳在 100 以内，避免滚过底部时溢出。

当前 progress 由页面 scrollTop 与正文高度估算，并限制在 0～100。它不是精确阅读时长，也不是证明用户逐字读完。测量高度与真实可视区域不同，产品若要精细阅读统计，需要重新定义指标。

公开计数上报失败不阻断正文，私人历史失败也不自动弹出打断阅读的错误。这是低优先级副作用的处理选择，不代表后台收到每一次访问。未发布预览不触发公开阅读行为。

### 阅读记录不要制造隐形写入承诺

计时和隐藏补报采用尽力而为方式，失败不会打断用户。因而会员历史是可用的辅助记录，不是每一次页面访问的审计账本。

如果产品以后要求准确统计，需要明确匿名访问、重复访问、后台切换、重试和服务端去重规则。当前五秒阈值与 scrollTop 比值不能承担这种完整指标定义。

记录会受身份变化影响，但已记录标志也有自己的文章与用户依赖。后续修改时，要防止同一页切换内容后沿用上一篇的计时与高度。把这些引用变量的重置条件写进回归清单，比只检查接口是否成功更稳妥。

同样的身份边界也落在评论组件上。`Comments` 的 key 拼进了文章 ID 和当前用户 ID，账号一变，React 就重建整棵评论子树，不会把上一个账号的评论状态留在屏幕上：

```tsx
// src/pages/article/index.tsx：key 带 articleId 与 userId，切号即重建。
<Comments key={`${article.id}:${auth?.user.id || "guest"}`} articleId={article.id} />
```

对游客用 `guest` 占位，是为了让“未登录”也拥有一个稳定 key，不至于每次渲染都换一个值把评论区打散。


## 两个失效场景，比成功点击更值得检查

第一种是文章仍能读取，相关文章请求失败。正文应该保持可读，推荐区域不能让整个页面换成错误状态。当前独立 useResource 为这种拆分提供基础，但辅助区域是否显示足够清楚的局部反馈，仍要按 UI 实际观察。

第二种是分享或收藏中的文章已经下线。用户进入的是曾经有效的入口，详情请求现在拒绝。页面需要展示可理解错误，而不是继续靠缓存永久显示内容。当前短 TTL 与强制重试提供读取边界，并非永久保存授权。

这两个场景也提醒我们，不要把“没有上下篇”解释成请求出错。prev 和 next 都可以是 null；服务端成功返回空关系是一种正常结果。请求失败和关系缺失应从响应层区分。

## 验证先看用户能否回到正确位置

开发工具实际执行过目录跳到“复用成功的部分”，并阅读了真实线上文章。这能证明具体标题节点与滚动路径。上下篇和外链的全部边界组合仍需对应样本，不能因为目录成功就顺带宣布完成。

建议后续检查重复中文标题、没有上下篇、推荐失败、坏编码链接、外链取消复制，以及读到一半切换页面的计时。这些场景各自守住一种阅读意图。
