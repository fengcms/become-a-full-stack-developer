# 成为全栈·Flutter App 篇·服务端目录与文章辅助阅读：锚点、上下篇、浏览量和阅读历史

我最初也把文章目录当成标题列表：扫一遍 Markdown，为标题拼 slug，再滚到对应位置。遇到重复中文标题和代码围栏后，这种“看起来能用”的办法就开始跳错段落。

这篇以项目里的 `ServerHeadingSyntax` 为主线，逐行解释服务端 TOC 如何和正文标题按顺序配对、异步目录如何触发重解析，以及为什么无法匹配时应该禁用跳转。

{{IMG:M4-14-封面}}

## 为什么不自行生成 slug

同一篇文章中可能出现重复标题、中文标点、行内格式、围栏代码中的井号，甚至 Setext 标题。服务端已经返回目录层级、文本与 anchor，是导航唯一事实源。客户端若自行根据标题生成 slug，稍有规则差异就会错位。

项目做法是按层级和原始标题文本核对正文 ATX 标题，再把服务端 anchor 绑定到对应 Widget key；代码围栏不参与匹配，Setext 标题正常渲染但不消耗目录项。无法配对的目录项禁用跳转，不猜一个“差不多”的位置。

{{IMG:M4-14-目录绑定}}

## TOC 异步返回时需要再次完成解析

正文可能先显示，目录稍后才抵达。如果解析只在 Markdown 初次构建时运行，异步数据回来后并不会自动重算匹配关系，正文可读而 TOC 不能跳。文章内容组件需把正文版本和 TOC 作为解析输入，任一变化都触发重新绑定。

目录接口失败不应阻断正文阅读；可隐藏目录或呈现不可用状态。预览用户私有草稿时不请求公开目录和上下篇，避免把尚未发布内容当作公开文章处理。

## 上下篇和面包屑是辅助模块

相邻文章、面包屑与作者模块可增强阅读路径，但失败不能拖垮正文。登录态/私有预览则需要不同请求边界。文章页面可把正文作为核心资源、这些辅助模块分别加载并允许降级。

## 浏览量不等于个人阅读历史

浏览量是服务端聚合指标，个人阅读历史属于账号私有数据。页面显示一次访问不代表历史记录已经成功写入，阅读历史也不应用来假造流量统计。项目针对匿名/会员场景使用不同请求语义，私有记录需认证并遵循会话隔离。

## 标题匹配要保留位置和重复语义

不能只建立 `Map<title, anchor>`，因为重复标题会覆盖前一项。更安全的思路是按服务端顺序维护游标，正文解析也按出现顺序输出标题节点：

```text
toc = [ (level, text, anchor), ... ]
headings = parseAtxHeadings(markdown, skipFencedCode=true)
for heading in headings:
  查找下一个 level 与原始 text 均匹配的 toc 项
  命中 → 给该 Widget 绑定服务端 anchor
  未命中 → 普通标题，不消费后续项
剩余未匹配 toc 项 → 显示为不可跳转
```

项目采用原始文本和层级核对，避免把 `## **标题**` 的行内标记或代码围栏内容错误地当成目录标题。异步 TOC 到达后，解析输入发生变化，正文组件必须重建绑定结果。

## TOC 失败不应让主内容变成错误页

正文与目录虽然成组缓存，但 UI 仍应将目录视为阅读辅助功能。文章详情首屏若正文已成功，TOC 匹配失败可以保留正文并禁用目录跳转；接口请求 404 则要移除已缓存正文，不能继续向用户显示已不可见内容。私有投稿预览完全绕开公共 bundle，避免公开目录、上下篇和历史行为混入草稿。

阅读记录属于成员私有写操作，文章浏览量则是 API 统计操作，测试中分别检验阅读进度和浏览量不会互相替代。网络失败时是否记录阅读应遵循接口行为，不应通过本地历史列表推断服务器计数已增加。

## 绑定失败时如何定位

测试样例应包含同名二级标题、Markdown 行内加粗标题、标题尾部 `#`、Setext 标题和围栏代码。对每篇文章可把服务端 TOC 和实际匹配的 anchor 记录成可读断言；错误定位不应通过截图人工猜。

服务端 anchor 绑定到 `GlobalKey` 后，点目录时滚动到对应标题 Widget，而不是通过字符串查找正文。若该 key 未建立或 anchor 为空，目录项不可点击。自定义 markdown syntax 在同一个 document 中保留 cursor 顺序，文档改变时重置 cursor，避免重复渲染沿用上次解析位置。


## 贴着工程代码读实现

下面这段节选自 `flutter-app/lib/features/data/article_reader.dart 第 30–103 行`（保留原始实现；为突出主线省略了文件其余部分）。读代码时可以顺着调用链确认：分别检查正文缓存、阅读历史写入和相邻文章请求的路径。我会继续追踪它的返回值和副作用，直到页面状态稳定下来。

```dart
  Future<Map<String, dynamic>> read(String id, {bool force = false}) async {
    var canonical = aliases[id] ?? id;
    if (!aliases.containsKey(id) && !force) {
      final persisted = await cache.disk.findKey(
        (key, meta) => matchesAlias(key, meta, id),
      );
      if (persisted != null) {
        canonical = CacheKey.tryParse(persisted)!.path
            .substring(CacheKeys.articlePrefix.length);
      }
    }
    final k = key(CacheKeys.article(canonical), const {});
    trackKey(k);
    final data = jsonMap(
      await cache.get(
        k,
        const CachePolicy(
          Duration(minutes: 10),
          Duration(hours: 24),
          disk: true,
        ),
        () => fetchBundle(canonical),
        force: force,
        tags: {'article:$canonical', 'articleBodies'},
        forbidden: forbidden,
      ),
    );
    final a = jsonMap(data['article']);
    if (aliases.length > CacheLimits.articleAliases) aliases.clear();
    aliases['${a['id']}'] = canonical;
    if (a['slug'] is String) aliases[a['slug']] = canonical;
    return data;
  }

  // 别名只能指向同一 API 环境的公开正文，损坏索引按未命中处理。
  bool matchesAlias(String key, Map<String, dynamic> meta, String id) {
    final parsed = CacheKey.tryParse(key);
    return (meta['aliases'] as List? ?? []).contains(id) &&
        parsed?.baseUrl == baseUrl &&
        parsed?.scope == 'public' &&
        (parsed?.path.startsWith(CacheKeys.articlePrefix) ?? false);
  }

  // 公开正文始终匿名获取，不能把作者预览权限带入可落盘内容。
  Future<CacheReply> fetchBundle(String canonical) async {
    final response = await fetch(Endpoints.article(canonical), anonymous: true);
    final a = jsonMap(response.value);
    if (a['status'] != 'published') {
      throw const ApiFailure('内容不存在或暂不可见', code: 3001, status: 404);
    }
    // TOC and content are installed together. Never attach a previous TOC to new content.
    final toc = await fetch(Endpoints.toc(a['id']), anonymous: true);
    if (toc.value is! List || a['id'] is! int || a['content'] is! String) {
      throw const FormatException('文章或目录响应格式不正确');
    }
    // When a version is available, verify that publication did not change while fetching the TOC.
    if (a['updatedAt'] != null) {
      final check = jsonMap(
        (await fetch(Endpoints.article(a['id']), anonymous: true)).value,
      );
      if (check['updatedAt'] != a['updatedAt'] ||
          check['content'] != a['content'] ||
          check['status'] != 'published') {
        throw const ApiFailure('文章刚刚发生更新，请刷新后继续阅读', code: 3003);
      }
    }
    // 正文和目录共同遵守较严格的响应限制，不能独立续期其中一份。
    final control = '${response.control},${toc.control}';
    return CacheReply(
      {'article': a, 'toc': toc.value},
      control: control,
      age: response.age,
    );
  }
```

## 把容易出错的路径走一遍

我会用这个场景做一次可复现排查：**把阅读计数和缓存命中混为一谈导致读者看到旧辅助信息**。先分别检查正文缓存、阅读历史写入和相邻文章请求的路径；如果把问题定位在“一个大响应缓存”，修正方向是“按资源定义读策略，只有正文可复用时才命中，辅助信息独立刷新”。最后再验证正常路径没有退化，并把边界条件留在自动化检查里。

| 方案比较 | 简化做法 | 当前实现/推荐做法 |
|---|---|---|
| 本文核心选择 | 一个大响应缓存 | 按资源拆分策略 |
| 错误处理 | 失败后清空或静默忽略 | 保留可恢复状态，给出明确反馈 |
| 验证方式 | 只检查成功结果 | 注入边界条件并检查回归 |

| 排错步骤 | 要观察什么 | 通过条件 |
|---|---|---|
| 复现 | 把阅读计数和缓存命中混为一谈导致读者看到旧辅助信息 | 可以稳定触发或明确构造该输入 |
| 定位 | 分别检查正文缓存、阅读历史写入和相邻文章请求的路径 | 找到责任层和状态归属 |
| 修正 | 按资源定义读策略，只有正文可复用时才命中，辅助信息独立刷新 | 失败不污染后续页面或账号 |

## 小结

服务端 TOC anchor 是客户端跳转协议。准确匹配、处理异步到达、对无法匹配项禁用跳转，能避免读者落在错误段落。正文、相邻文章和私有阅读历史的所有权不同，应独立失败和验证。
