# 成为全栈·Taro 小程序篇·Taro 一套代码多端：这次究竟复用了什么

> 接口已经有了，APP 也已经有了，小程序还需要开发什么？把复用的边界说清楚，才不会对“一套代码”抱错期待。

{{IMG:M5-01-封面}}

## 前言：功能相同，为什么不能直接搬？

开发小程序之前，我们已经完成 Node 后端、React 管理后台、Next.js 网站和 Flutter APP。文章、分类、搜索、会员、投稿都不是新需求。按直觉，把 APP 的布局缩一缩，接上同一组接口，应该很快。

真正动手时，我发现这个说法省略了最重要的一半：功能可以相同，功能依赖的环境却不同。Flutter 的 Widget 不能交给 Taro 编译，网页里的 DOM 编辑器也不能直接塞进小程序。外链、登录、分享、键盘和页面返回，各有各的运行规则。

所以，第五批的第一篇，我先回答一个容易被宣传语带偏的问题：**这次到底复用了什么，哪些东西仍然需要重新实现？**

## 一、先画资产地图，再讨论技术选型

我把现有成果分成四层。这个分类决定了开发顺序，也决定了哪些“搬代码”的尝试根本不值得开始。

| 现有资产 | 小程序如何复用 | 有没有重新开发 |
|---|---|---|
| OpenAPI 与 Node 服务 | 继续使用统一信封、文章和会员端点 | 新登录能力由后端兼容增补 |
| 产品状态与流程 | 草稿、待审核、已发布等含义沿用 | 按小程序页面与生命周期实现 |
| APP 原型与图标 | 继承色彩、层级、图标路径和阅读布局 | 转换图标资源、实现原生组件 |
| Flutter 页面代码 | 参考行为与问题修复经验 | 不直接复用 Dart 与 Widget |

这里的“接口复用”也不是一句空话。公开文章仍然使用既有文章接口，收藏仍属于当前会员，投稿仍进入后台审核。我们没有为小程序复制一个独立内容库，也没有另建一套只认微信的文章作者体系。

微信登录创建的是系统会员。这个会员之后设置用户名密码，网站和 APP 就能通过现有密码登录进入同一个 userId。涉及后端变化的部分，已经放在 [契约兼容增补]({{LINK:M1-32}}) 和 [微信登录与首次账号设置]({{LINK:M1-33}}) 中。

## 二、为什么选择 Taro，而不是再写一种原生语言

这次的目标是教学项目：把已经完成的内容产品带到微信开发者工具里，展示真实阅读、互动和投稿流程。我们没有同时承诺支付宝、抖音等目标，也没有把正式上架列为本轮验收要求。

选择 Taro，是为了继续使用 React 和 TypeScript 的开发经验，同时生成微信小程序产物。已有后台的表单分层、异步竞态处理、纯逻辑测试经验都能迁移，尽管具体组件需要重写。

直接原生开发当然可以。它少了一层框架转换，却需要另一套组件组织和工程习惯。对于这个系列，继续深化已经使用过的 React，比为了展示技术种类再换一遍语言更合适。

但请留意：**选择多端框架，不等于已经完成多端交付。** 当前工程构建并验收的是 `weapp`。代码中实际调用了微信相关平台能力，其他目标要有自己的能力适配与测试，不能靠配置项存在就算支持。

## 三、接口复用，落到一个明确的服务入口

工程的 `config/index.ts` 将 API 基址注入构建：

```ts
// 关键表达式节选；不是完整配置文件。
process.env.TARO_APP_API_BASE ||
  'https://api-befull.kao9.com/api/v1'
```

请求层消费 `__API_BASE__`，页面只传相对路径。这样，真实线上阅读和临时本地集成测试能共用页面逻辑，不需要逐页改 URL。

但环境切换还牵涉会话与本机草稿。一个本地用户的编号可能恰好与线上会员相同，光用 userId 做存储键会串数据。于是，会话键带 API，草稿键也带 API。这不是部署之后才处理的小细节，而是复用接口时必须补齐的环境边界。

开发中用过临时本地测试后端，交付构建已恢复线上基址。临时测试账号与数据不应被写进生产数据库，更不能随着源码提交出去。

## 四、代码没有通吃，工程能力可以迁移

项目现在有 14 个注册页面、4 个原生 Tab。页面之下，按职责分成几块：

```text
src/core        请求、会话、缓存、Markdown、评论与草稿纯逻辑
src/hooks       资源读取和分页列表生命周期
src/components  页面骨架、图标、卡片、私有内容门禁
src/features    阅读、互动、评论、编辑等可组合能力
src/pages       页面参数、数据组合与平台事件
```

这套组织与 Web 的组件思想接近，却不是把一个通用目录复制过来便完事。Markdown 输出的是受控原生组件，评论输入要处理小程序键盘事件，图片上传要经过媒体选择和 `uploadFile`，返回刷新要看 `useDidShow`。

我更愿意把这些叫作“经验复用”。比如，会话代次保护旧请求、保存后立即保留稿件 ID、失败不盲目重试写入，这些判断来自前面几个客户端的真实问题。它们不依赖某种 UI 框架，值得带到下一端。

反过来，浏览器的 HttpOnly Cookie、Flutter 的安全存储，也不能因为理念相同就写成小程序已经拥有。当前小程序使用平台本地存储保存会话，存储安全边界需要单独说明。

## 五、怎样证明复用成功，而不是只证明页面画出来

这次交付留下了三类证据：纯逻辑测试、真实本地后端集成记录、开发者工具交互记录。它们分别回答不同问题。

纯逻辑测试能检查缓存隔离与 Markdown 解析；真实后端测试能检查保存、提交、撤回、评论关系和权限；开发工具能看到原生组件是否可操作、页面如何返回以及深色主题是否落实。

已有构建证据记录：Taro 4.3.0、14 页面、4 Tab、产物文件总量 758869 字节。这个数是文件系统求和，不是平台上传包体，也不是启动耗时。我不拿它证明“性能优秀”，只拿它核对交付范围与产物组成。

微信快捷登录还进行了线上真实链路验证。首次成功后，会员中心显示了微信会员与首次凭据设置入口。至于真机审核、上传交互的完整人工矩阵，并没有因为这一次登录成功就自动完成。


## 一个完整需求，怎样沿着三端分解

拿“收藏文章”做例子，更容易看清复用。服务端拥有收藏关系和权限判断；产品规定游客先登录、成功后可在私人列表找回；设计规定选中图标与操作反馈。这三层可以保持共同含义。

接下来才轮到客户端实现。网站需要处理浏览器会话与服务端渲染，APP 使用自己的路由和网络库，小程序处理原生页面栈与平台存储。我们共享的是“收藏属于当前会员”，而不是三端必须调用同一个 Hook。

如果反过来，为了共享一个前端函数，要求服务器适应三个客户端的内部状态，接口就容易变成平台细节的垃圾桶。契约应该表达业务对象与动作，平台负责把用户意图翻译成它。

还有一个反例：把 Flutter 的文章 HTML 输出存到后端，让小程序直接消费，看起来省了渲染开发，却把一种客户端的表示形式变成全端负担。Markdown 原文继续作为内容，客户端各自解析，才给目录、代码和交互留下空间。

### 复用收益该怎样验收

我会从两个方向检查：新增小程序有没有逼迫旧客户端改调用；同一会员的数据能否继续由同一套后端管理。前者检查兼容性，后者检查业务共享。它们都比“共享代码占比”更接近这次项目目标。

再补一张工作量清单：接口本身是否已存在，客户端展示是否已存在于参考原型，平台动作是否需要新实现，验收能否复用已有样本。一个需求如果四项都写清楚，估计工作量时就不会只剩“应该差不多”。

也别忘记，共享会放大错误传播范围。统一请求层修对了，多页受益；修错了，也会多页受影响。因此底层模块要保留针对性的逻辑测试，而不是因为复用成功就减少验证。

这个项目没有测量跨端代码共享比例，也没有据此计算开发效率百分比。我能给出的事实，是已有契约和流程减少了重新定义需求的工作，平台展示与交互仍进行了独立实现和验收。

## 六、给“一套代码”一个能兑现的解释

这次真正共享的是后端契约、产品规则和设计资产；Taro 内部则共享页面之外的请求、会话、解析、缓存等模块。网站、Flutter 和小程序各自承担自己的渲染与平台交互。

如果你准备给已有产品增加一端，我建议先列出“可直接调用、可翻译迁移、必须重写”三张清单，再决定框架。否则，你很可能为了复用一个不适合的组件，花掉比重写还多的时间。
