# 成为全栈·Taro 小程序篇·Taro 一套代码多端：这次究竟复用了什么

> 接口已经有了，APP 也已经有了，小程序还需要开发什么？把复用的边界说清楚，才不会对"一套代码"抱错期待。

{{IMG:M5-01-封面}}

## 前言：写完这句话当天，我就卡住了

做第五批之前，我在文档里给自己写了一句判断："接口已经有了，APP 也已经有了，小程序还需要开发什么？"

写完当天我就在开发工具里卡住了。

不是接口不通用 —— 恰恰相反，文章、分类、搜索、会员、投稿这些端点全都是现成的，生成的 `Article`、`Page<T>` 模型直接能用。**卡住的是另一件事：小程序的页面栈不像 Flutter 那样可以随便推，Tab 切换不会新建页面，`useDidShow` 触发的时机又和 `useEffect` 完全不同。**

所以这篇要回答的不是"能不能做出来"，而是那个更朴素的问题：**做完之后，我们究竟省下了什么，又不得不重新写了一遍什么。**

这句话看起来像总结陈词，但我发现只有把它拆到具体文件、具体行号，才能回答得诚实。

## 先画资产地图，再讨论技术选型

动手之前我先做了一件看起来很"项目管理"的事：把已经完成的四端成果分成四层。

| 现有资产 | 小程序如何复用 | 有没有重新开发 |
|---|---|---|
| OpenAPI 与 Node 服务 | 继续使用统一信封、文章和会员端点 | 新登录能力由后端兼容增补 |
| 产品状态与流程 | 草稿、待审核、已发布等含义沿用 | 按小程序页面与生命周期实现 |
| APP 原型与图标 | 继承色彩、层级、图标路径和阅读布局 | 转换图标资源、实现原生组件 |
| Flutter 页面代码 | 参考行为与问题修复经验 | 不直接复用 Dart 与 Widget |

这里的"接口复用"不是一句空话。公开文章仍然走既有端点，收藏仍属于当前会员，投稿仍进后台审核。**我们没有为小程序复制一个独立内容库，也没有另建一套只认微信的文章作者体系** —— 这两条是判断"复用了多少"的底线。

相关决策的具体来龙去脉，[契约先行](https://blog.csdn.net/fungleo/article/details/164140515) 里讲过设计原则；微信登录的兼容处理留到登录篇展开，这里不重复。

但真正让我学到东西的是环境边界。

## 存储键必须带上 API，否则本地测试会污染线上会员

开发中途我用过一个临时本地测试后端。联调时一切正常，直到我把构建切回线上基址，才发现**草稿串了**。

原因在存储键：

```ts
// src/core/session.ts：存储键随 API 基址变化。
export const API = __API_BASE__;
const key = `befull:session:${API}`;
```

`API` 来自构建期注入：

```ts
// config/index.ts（节选）
export default defineConfig({
  projectName: "befull-miniprogram",
  defineConstants: {
    __API_BASE__: JSON.stringify(
      process.env.TARO_APP_API_BASE || "https://api-befull.kao9.com/api/v1",
    ),
  },
  // …其余尺寸与输出配置
});
```

如果键里只有 `userId`，那么本地测试环境的 1 号会员和线上 1 号会员就是同一个键。**而本地库里那个 1 号会员是我自己随便造的测试数据。**

我一开始想的是"环境不同，缓存总会隔离吧"。后来才明白：**缓存隔离的前提是键里包含能区分环境的部分**，而我最初只写了 `befull:session`。

草稿键后来也补上了同样的东西：

```ts
// src/core/drafts.ts
export const draftKey = (userId: number, id: string) =>
  `befull:draft:${API}:${userId}:${id}`;
```

**一个字符串的差异，换来的是"本地测试永远不会污染线上数据"这条硬保证。** 这不是部署之后才处理的小细节，而是复用接口时必须补齐的环境边界。

顺带说，临时测试账号与数据更不该进生产库 —— 联调结束我第一件事就是确认构建产物里的基址已经指回线上。

## 为什么选 Taro，而不是再写一种原生语言

这次的目标是教学项目：把已有的内容产品带进微信开发者工具，展示真实的阅读、互动和投稿流程。支付宝、抖音这些目标本轮不承诺，正式上架也不在验收范围里。

选 Taro 是为了继续用 React 和 TypeScript 的经验。已有后台的表单分层、异步竞态处理、纯逻辑测试经验都能迁移，尽管具体组件要重写。依赖锁定与可复现构建的具体做法，后面单独讲。

直接原生当然可以 —— 它少一层框架转换，但需要另一套组件组织和工程习惯。对于这个系列，**继续深化已经用过的 React，比为了展示技术种类再换一遍语言更合适**。

但这里有个我在文档里专门加粗的判断：

> **选择多端框架，不等于已经完成多端交付。**

当前工程构建并验收的是 `weapp`。代码里确实调用了微信专属能力（`Taro.chooseMedia`、`Taro.showModal`、`Taro.setTabBarStyle`），这些在 H5 上没有对应物。**所以"配置里有 platform-weapp 插件"这件事，不能当成"多端已完成"的证据。**

## 接口复用的落点，是一个明确的常量

请求层消费 `__API_BASE__`，页面只传相对路径：

```tsx
// src/pages/index/index.tsx（节选）：页面只传相对路径。
const feed = useFeed("/articles");
const popular = useResource<Page<Article>>("/articles?sort=-viewCount&pageSize=3");
const settings = useResource<{ copyright: string; siteDescription: string }>(
  "/site/settings",
);
// …渲染时只用数据，不拼 URL、不管缓存
```

**页面不出现任何绝对 URL**，这是我想守住的一条线。一旦某个页面开始自己拼 `https://api-...`，切换环境时就会漏掉一处，而漏掉的那处只会在联调时暴露。

## 代码没有通吃，工程能力可以迁移

工程现在有 14 个注册页面、4 个原生 Tab。四个主入口在 `app.config.ts` 里声明（节选）：

```ts
// src/app.config.ts（节选）
tabBar: {
  list: [
    {
      pagePath: "pages/index/index",
      text: "首页",
      iconPath: "assets/icons/home-light.png",
      selectedIconPath: "assets/icons/home-active.png",
    },
    {
      pagePath: "pages/categories/index",
      text: "分类",
      iconPath: "assets/icons/layers-light.png",
      selectedIconPath: "assets/icons/layers-active.png",
    },
  ],
}
```

四个入口共用同一套页面路径，切换 Tab 只是换当前页，**不会新建页面栈**。小程序还有一批"以前写着没问题、现在必须改"的前端习惯，后面会逐条列一张限制清单，这一点讲生命周期时还要再提。

代码按职责分层：

```text
src/core        请求、会话、缓存、Markdown、评论与草稿纯逻辑
src/hooks       资源读取和分页列表生命周期
src/components  页面骨架、图标、卡片、私有内容门禁
src/features    阅读、互动、评论、编辑等可组合能力
src/pages       页面参数、数据组合与平台事件
```

这套组织跟 Web 的组件思想接近，但不是复制目录就完事。Markdown 输出的是受控原生组件，评论输入要处理小程序键盘事件，图片上传要过媒体选择和 `uploadFile`，返回刷新要看 `useDidShow`。

我更愿意把这些叫作**"经验复用"**。会话代次保护旧请求、保存后立刻保留稿件 ID、失败不盲目重试写入 —— 这些判断来自前面几个客户端的真实问题，**它们不依赖某种 UI 框架**。

反过来，浏览器的 HttpOnly Cookie、Flutter 的安全存储，也不能因为理念相同就写成小程序已经拥有。当前小程序用的是平台本地存储，**安全边界需要单独说明**。

## 怎么证明复用成功，而不是只证明页面画出来

这次留下了三类证据，它们分别回答不同问题：纯逻辑测试、真实后端集成记录、开发者工具交互记录。

纯逻辑测试检查缓存隔离与 Markdown 解析，不需要渲染页面。以缓存为例，它验证并发读取会合并成一次请求：

```ts
// test/core.test.ts：并发读同一键，只发一次请求。
test("缓存复用、强刷与并发请求合并", async () => {
  const c = new DataCache(),
    wait = deferred<number>();
  let calls = 0;
  const fetcher = () => {
    calls++;
    return wait.promise;
  };
  const a = c.read("key", fetcher),
    b = c.read("key", fetcher);
  wait.resolve(3);
  assert.deepEqual(await Promise.all([a, b]), [3, 3]);
  assert.equal(calls, 1);
});
```

**这条断言跨端通用** —— 它检查的是缓存契约，与最终渲染成网页还是原生组件无关。这就是"可翻译迁移"的典型：逻辑留下，表示重做。

已有构建证据：Taro 4.3.0、14 页面、4 Tab、产物总量 758869 字节。**这个数是文件系统求和，不是平台上传包体，也不是启动耗时。** 我不拿它证明"性能优秀"，只拿它核对交付范围与产物组成。

微信快捷登录做了线上真实链路验证。首次成功后会员中心显示了微信会员与首次凭据设置入口。**至于真机审核、上传交互的完整人工矩阵，并没有因为这一次登录成功就自动完成。**

## 一个完整需求，怎么沿三端分解

拿"收藏文章"举例：服务端拥有收藏关系和权限判断；产品规定游客先登录、成功后可在私人列表找回；设计规定选中图标与操作反馈。这三层可以保持共同含义。

接下来才轮到客户端实现。网站要处理浏览器会话与服务端渲染，APP 用自己的路由和网络库，小程序处理原生页面栈与平台存储。**我们共享的是"收藏属于当前会员"，而不是三端必须调用同一个 Hook。**

如果反过来，为了共享一个前端函数要求服务器适应三个客户端的内部状态，接口就容易变成平台细节的垃圾桶。

还有一个反例值得留着：**把 Flutter 的文章 HTML 输出存到后端，让小程序直接消费**，看起来省了渲染开发，却把一种客户端的表示形式变成了全端负担。Markdown 原文继续作为内容，客户端各自解析，才给目录、代码和交互留下空间。

### 复用收益该怎么验收

我会从两个方向检查：新增小程序有没有逼迫旧客户端改调用；同一会员的数据能否继续由同一套后端管理。**前者检查兼容性，后者检查业务共享** —— 它们都比"共享代码占比"更接近这次的目标。

再补一张工作量清单：

| 检查项 | 问什么 | 结论怎么用 |
|---|---|---|
| 接口 | 契约里是否已存在？ | 不存在则先改契约 |
| 展示 | 参考原型里是否已有？ | 有则只需平台化实现 |
| 平台动作 | 是否需要新实现？ | 需要则单独排期 |
| 验收 | 能否复用已有样本？ | 能则沿用同一口径 |

这四项都写清楚，估计工作量时就不会只剩"应该差不多"。

最后一句提醒：**共享会放大错误传播范围。** 统一请求层修对了多页受益，修错了也多页受影响。所以底层模块要保留针对性的逻辑测试 —— 不能因为复用成功就减少验证。

## 我第一次统计复用率，得出的是一个错误结论

这一批开始之前，我想给自己一个客观数字，于是统计"小程序有多少代码是从别的端搬过来的"。

我按文件对比 `src/core` 里的同名文件，结果是：**几乎为零。** 缓存、请求、会话、Markdown，四个核心模块和 Flutter 端没有一行相同。

那个数字让我一度很不舒服 —— 感觉第四端做下来什么都没剩下。

后来我把这个统计口径拆开看，才发现问题出在**我数错了东西**。真实情况是这样：

| 我数的 | 实际情况 |
|---|---|
| 逐行相同的代码 | 几乎没有，因为平台 API 名字就不同 |
| 契约与错误码复用 | 54 个端点、68 个操作全部共用 |
| 状态机含义复用 | draft/pending/published 三态含义一致 |
| 缓存键规则复用 | "键要含环境与账号"这条规则三端同源 |
| 决策复用 | 单飞刷新、代次保护、失败不重试写入 |

**我把"可复制"当成了"有价值"，而这两件事在这个项目里几乎不重合。**

真正被复用的东西大多不是代码，是**决策**。比如 Flutter 那轮我们定下"凡是 401 都刷新是错的"，这一轮做单飞刷新时几乎是直接照搬：

```ts
// src/core/api.ts（节选）：并发 401 合并成一次刷新。
let refreshFlight: Promise<void> | null = null;
export async function refreshSession() {
  if (refreshFlight) return refreshFlight;
  // …
  .finally(() => {
    if (refreshFlight === flight) refreshFlight = null;
  });
  refreshFlight = flight;
  return flight;
}
```

**这段逻辑在 Flutter 里是 Dart，在小程序里是 TypeScript，语法一个字都不通用，但"并发刷新必须合并"这个判断完全通用。** 而这个判断恰恰是踩过坑才有的 —— 没有那次并发 401 把用户踢下线，我不会写下这行。

所以现在我评估复用的方式是两个问题：**新增小程序有没有逼迫旧客户端改调用？同一个会员的数据能不能继续由同一套后端管理？**

前者检查兼容性，后者检查业务共享。**它们都比"共享代码占比"更接近这个项目的目标** —— 因为这个专栏要证明的是"契约能撑起多端"，不是"代码能复制粘贴"。


## 给"一套代码"一个能兑现的解释

这一轮做完，我对"一套代码多端"这句话的理解变了一点。

它不是"写一次到处跑"，而是**"一次决定哪些东西必须统一"**。我们统一了契约、错误码、状态机含义、缓存键规则、失效条件；我们没有统一渲染、导航、存储这些依赖平台的部分。

而这次最值得记住的两件事，一件是技术性的，一件是习惯性的：

技术上，**存储键必须包含环境标识**，否则本地测试会静默污染线上数据。
习惯上，**"多端框架已配置"和"多端已交付"之间隔着一整套平台行为的验证**，前者一分钟完成，后者要一个个撞。

下一步我会先撞最硬的那块：登录。它牵扯平台 code 换会话、首次凭据设置、以及"登录成功后回到用户原来的任务"这三件事，比页面布局更容易出错。
