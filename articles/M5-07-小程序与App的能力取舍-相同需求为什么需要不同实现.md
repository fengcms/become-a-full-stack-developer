# 成为全栈·Taro 小程序篇·小程序与 App 的能力取舍：相同需求为什么需要不同实现

> 跨端一致性应该保护用户的目标。为了一张功能表全部打勾，把不适合的平台行为硬塞进去，反而会破坏体验。

## 前言：既然参考 APP，为什么外链不能一样打开

小程序参考 Flutter APP 的功能，阅读、会员、投稿都相近。但文章外链在 APP 里进内部 WebView，在小程序里却提示复制。缓存、编辑器、登录也各有不同。

如果只比功能数量，小程序似乎少了一项。

有一次我想"补齐"这个差异 —— 反正 `web-view` 组件是有的，画个容器不过十几行。我写完就删了，因为**我不知道目标站点是否在业务域名白名单里，也不知道这个 AppID 有没有对应资质。**

**画一个加载不出来的空容器，比明确说"请复制地址"更糟** —— 前者让用户以为坏了，后者让用户知道下一步做什么。

把平台条件和本期目标加入比较之后，这些差异就有了明确理由。本轮只要求开发工具教学演示，没有承诺任意网页容器。

这篇不再盘点各页，而是讨论三个真实取舍：外链、缓存、编辑与登录。**如何让用户意图保持一致，同时接受不同实现与不同能力上限。**

## 先写共同目标，再写平台动作

共同目标是"读到文章引用的资料"，不是"必须出现同一个浏览器控件"；共同目标是"返回时少等待"，不是"两端必须使用同一缓存算法"；共同目标是"完成投稿"，不是"工具条按钮完全一样"。

| 需求 | Flutter APP 当前方向 | 小程序当前方向 |
|---|---|---|
| 外部网页 | 内部 WebView，返回来源与菜单 | HTTP(S) 地址提示复制 |
| 内容读取复用 | 更细策略，部分公开数据允许磁盘 | 60 秒有界内存分区 |
| Markdown 投稿 | 移动编辑表单与工具条 | 原生 Textarea 加文本插入 |
| 平台登录 | 继续用户名密码 | 增加微信 code 入口 |
| 分享 | 平台各自实现 | 原生分享 path |

这张表不是永久能力排名。**范围与条件改变时，每个选择都可能重评估，但不能靠"APP 有"就省略小程序的前提。**

把目标和动作分开写还有个直接好处：**某一端能力变化时，我们改的是那一行实现说明，而不是把整段产品目标重新讨论一遍。**

## 外链：容器不是一个可以随便复制的页面

APP 的 `web_page` 用 WebViewController，标题栏返回回到来源页面，菜单可以关闭或在系统浏览器打开。容器内跳转不改变左侧按钮的返回语义。

小程序没照搬。当前 `openLink` 把站内文章转原生详情，外站复制地址，其他协议拒绝：

```ts
// src/core/navigation.ts（节选）：三条路，最后一条是明确拒绝。
if (!/^https?:\/\//i.test(href)) {
  Taro.showToast({ title: "不支持此链接类型", icon: "none" });
  return;
}
const r = await Taro.showModal({
  title: "打开外部链接",
  content: href,
  confirmText: "复制地址",
});
if (r.confirm) await Taro.setClipboardData({ data: href });
```

**复制没有内部浏览方便，这是代价。** 但它不假装满足未经核对的业务域名与平台能力条件。

若以后新增 `web-view`，应先明确目标站点、账号条件与失败场景，**再**安排真机验收 —— 不是反过来。

更深一层的原因是平台条件本来就不同。APP 的容器运行在原生进程里，返回来源与菜单由自己决定；小程序的网页容器受业务域名白名单与账号资质约束，**开发工具关闭校验也改变不了正式环境的规则**。

把两件事当成同一个功能，最后写出来的往往是一句没有条件的功能对照，而不是一份可执行的实现说明。

## 缓存：复用判断，不复制全部复杂度

APP 缓存有 fresh、maxAge、disk 等策略：

```dart
// flutter-app/lib/core/cache/data_cache.dart（节选）
class CachePolicy {
  const CachePolicy(this.fresh, this.maxAge, {this.disk = false});
  final Duration fresh, maxAge;
  final bool disk;
}
```

小程序的 `DataCache` 没有这张策略表，也不宣称离线冷启动读正文：

```ts
// src/core/cache.ts（节选）：只做有界内存 + 版本栅栏。
export class DataCache {
  private entries = new Map<string, { value: unknown; until: number }>();
  constructor(private limit = 80) {}
}
```

它共享了**身份隔离、失效栅栏与合并请求**的判断，省掉了本轮没有验收资源支持的磁盘内容库。

理由不是"小程序不能存数据"。平台有 storage，本机草稿就在用；只是持久化公开文章还需要容量、旧版本、资源授权与清理策略。**把全部缓存一夜搬过去，会同时增加实现和验证范围。**

代价也明确：**关闭后正文缓存不在，弱网需要重新读取。**

这里的分寸在于：**共享的是判断，不是复杂度。** 身份隔离、请求合并和失效栅栏属于业务正确性，两端必须一致；磁盘容量、旧版本迁移和资源授权属于平台工程，可以各自决定。

把两类东西一起搬，等于替小程序提前承担了它还没有验收场景的维护成本。

### 那 80 和 60 两个数字是怎么定的

有人可能会问：公共缓存 80 条、私有缓存 60 条，这个数字有依据吗？

老实说，**第一个版本是随手写的 100**。后来发现两个问题。

第一个问题是内存。小程序运行在微信的 WebView 里，**可用内存比原生 App 少得多**（而且 iOS 侧的余量更紧）。100 条文章按每条几 KB 算不算多，但列表页、详情页、作者页各自的 key 又不完全重合，实际驻留条目会超过 100 —— 因为**没有淘汰时它是只增不减的**。

所以我加了硬上限：

```ts
// src/core/cache.ts（节选）：超出上限按插入顺序淘汰最旧的。
while (this.entries.size > this.limit)
  this.entries.delete(this.entries.keys().next().value!);
```

`Map` 的插入顺序即写入顺序，所以 `keys().next().value` 拿到的是**最早写入的那条**。这不是真正的 LRU（最近用过的不会被提前保护），但它是一个**有界的、可预测的**行为 —— 而在缓存这件事上，可预测比聪明重要。

第二个问题是私有缓存为什么更小。私有数据（收藏、历史、我的文章）的访问频率明显低于公开列表，**给它 60 条已经覆盖了绝大多数场景**，而省下来的内存留给公开内容。

**而更重要的是：私有缓存一登出就要清空。** 这意味着它的实际驻留量通常远小于 60 —— 容量上限只是兜底，不是预期。

所以这两个数字现在有了明确含义：**它们不是"能存多少"的答案，而是"在内存紧张的小程序环境里，我愿意为缓存花多少"的答案。** 换个环境（比如改成原生 App）这个数字就该重新算。

## 编辑：共享内容格式，尊重输入控件

三端继续使用 Markdown 原文，标题、摘要、分类、标签和封面含义一致。小程序用 Textarea 光标事件插入文本，不使用浏览器 Selection，也不等同 Flutter 编辑组件。

它提供常见语法、插图与预览，但不支持完整选区包裹和桌面快捷键。**用户仍可完成文章，更多精细编辑可以选择网站或 APP，账号与内容归属保持相同。**

这里不应该把"简化"当成忽视输入保护的理由。本机恢复、离开提醒与投稿 ID 固定仍然要做 —— **缩小格式能力可以，丢作者内容不可以。**

而共享内容格式不代表共享全部呈现：

```ts
// src/core/drafts.ts（节选）：草稿键按环境+会员+稿件隔离。
export const draftKey = (userId: number, id: string) =>
  `befull:draft:${API}:${userId}:${id}`;
```

**这个键里三个要素缺一不可。** 少 `API` 会让本地测试污染线上草稿（这在 M5-01 里真发生过）；少 `userId` 会让两个账号在同一台设备上互相看到对方的草稿；少 `id` 则新建文章的草稿会互相覆盖。

作者在两端看到的内容结构是同一份原文，输入手感按各自平台决定。**这种分工让"格式一致"和"体验一致"不再互相绑架。**

## 登录：一个账号可以有不同入口

小程序微信登录创建系统会员，之后设置用户名密码，同一个 userId 可以在网站与 APP 用旧密码登录。**APP 和网站没有新增微信快捷按钮。**

所以三端账号打通的依据是**后端身份与数据关系**，不是每一端提供所有登录方式。

存储也不一样：小程序 Auth 存入平台本地 storage，APP 的凭据处理有自己的实现。**理念相同不能推导安全等级相同**；文章要分别说明它们。

退出行为消费同一个后端契约。当前小程序文案提示**撤销该账号所有设备刷新令牌**，而不说"只删除本机文件"。跨端入口不同，服务器事实仍统一。

这也解释了一个常见误解：**某一端多出一种登录方式，不等于其他端需要补齐同一种按钮。** 账号是否打通取决于后端身份关系，而不是各端按钮数量对齐。

## 用意图和失败体验检查差异

一个可接受的差异应回答四个问题：用户原本要做什么，现在能得到什么，额外成本是什么，不能完成时怎样提示。

| 检查项 | 外链复制 | 内存缓存 | 原生文本编辑 |
|---|---|---|---|
| 用户原本要做什么 | 读到引用的网页 | 返回时少等待 | 完成一次投稿 |
| 现在能得到什么 | 复制地址，自行打开 | 短时间内的快速返回 | 文本输入与预览 |
| 额外成本 | 需要离开小程序 | 关闭后缓存不在 | 没有选区包裹与快捷键 |
| 不能完成时怎样提示 | 弹窗说明并复制地址 | 重新请求并显示加载 | 校验失败指出具体字段 |

**如果只点图标没反应，就不算合理降级。** 内存缓存缩小了关闭后能力，若文案还宣传离线阅读，就不算诚实取舍。

比较时也要区分核心路径与平台增强。读文章、本人数据、保存投稿属于共同产品核心；任意网页、更多分享渠道与长期离线属于需要独立条件的增强。**功能列表只统计数量，会掩盖这个区别。**

## 验收不是"看起来像 APP"

工具里观察过小程序真实文章、目录、登录、投稿与主题，真实微信入口又有专项证据。**APP 相同功能的既有验收不会自动覆盖小程序原生组件。**

未来扩展某个差异，应增加对应测试，而不是只改功能表：

- 加磁盘缓存 → 测试清理后旧磁盘回填
- 增加上传重放 → 检查身份和不确定写入
- 加网页容器 → 检查返回来源

**当前没有测量跨端共享比例，也没有以功能数量计算复用收益。** 能说清楚的事实是：共同接口与设计减少了重新定义，平台层仍付出了独立开发和验证成本。

### 给取舍设置重新评估的触发点

复制外链的升级触发点，可以是用户确实频繁需要站内浏览**并且**目标域名条件具备；内存缓存的触发点，可以是冷启动弱网阅读成为明确需求；编辑器增强，则应来自实际输入任务，**而不是只因别的工具按钮多**。

每个触发点还应该有衡量方式。外链看任务完成路径，缓存看请求和恢复数据，编辑器看输入丢失与格式操作成本。**没有证据时，就不要用"更完整"替代需求论证。**

### 平台增强不该污染共同契约

假如 APP 需要网页标题，优先在客户端容器获取，不必为小程序复制外链接口；假如小程序需要分享 path，也不该把它作为文章通用字段强加给所有消费者。

**服务器表达文章与会员事实，客户端表达平台入口。** 只有真正共同的业务规则变化才值得增补契约。

### UI 近似也不能代替语义一致

两端都画收藏图标，若一个失败回滚、另一个一直显示已收藏，**语义就不一致**；两端编辑页不同，只要保存位置、状态推进和恢复路径清楚，反而可以有可靠共同体验。

所以比较应覆盖成功、失败、返回和身份变化，**不只是首屏截图**。

## 把差异留成可维护的决策

每个端有明确目标、实现与限制，协作就能沿着边界推进。以后需要升级小程序，不必重新争论它为什么没照抄 APP，**而可以直接检查条件是否变化。**

这份取舍表是当前快照。后续改变某一项时，更新它的理由、实现与验收，再决定其他端是否需要同步。

最后读 [第五批复盘]({{LINK:M5-08}})。这次跨端开发的成果，既是一个能演示的小程序，也是对"复用什么、承担什么"更具体的认识。
