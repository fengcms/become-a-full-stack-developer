# 成为全栈·基础补充·Node.js 运行时：事件循环与异步

> Node.js 可以同时处理许多网络请求，不代表一段 JavaScript 会自动在多个 CPU 核心并行运行。理解事件循环、异步 I/O 和阻塞操作，才能解释它擅长什么、又会在哪里卡住。

## 前言：单线程为什么还能处理很多连接

Node.js 常用于 API 服务和工具链。许多前端开发者知道它“异步、非阻塞”，但容易把这句话理解成所有任务都会自动在后台并行。实际上，JavaScript 回调通常在一个主执行线程上运行；异步 I/O 让程序在等待网络或磁盘时先处理其他事件，事件循环再在操作完成后安排回调。

这个模型适合大量等待 I/O 的工作，但如果在主线程执行很长的 CPU 计算，事件循环就无法及时处理其他请求。

## 一、同步代码会占住当前执行线程

    console.log("A");
    const value = expensiveCalculation();
    console.log("B", value);

如果 expensiveCalculation 需要一秒，后续 JavaScript 回调也要等待这段工作完成。CPU 密集型循环、同步文件读写、大型 JSON 解析和正则表达式灾难性回溯，都可能阻塞事件循环。

服务端表现可能是多个用户同时觉得接口变慢。不是每个请求都独立拿到一颗线程；主线程被一个同步任务占满时，其他回调会排队等待。

## 二、异步 I/O 把等待交给运行时

    console.log("开始请求");
    fetch("https://example.test/data")
      .then((response) => response.json())
      .then((data) => console.log(data));
    console.log("继续执行");

启动 fetch 后，JavaScript 不需要同步等待网络响应，因此能继续执行后面的代码。网络完成后，运行时安排相应回调。async/await 让异步流程读起来像顺序代码，但它不会把等待变成同步阻塞：

    const response = await fetch(url);
    const data = await response.json();

这段函数会在等待期间挂起自己的后续步骤，让事件循环可以处理别的工作。若在等待前后执行大量同步计算，仍然会阻塞。

## 三、事件循环在合适时机执行回调

可以把事件循环概括为：执行当前 JavaScript；处理已经准备好的微任务和回调；等待或接收新的 I/O 事件；再继续处理。Node 还包含 libuv 事件循环阶段以及线程池等实现细节。Promise 回调属于微任务；定时器表示“至少等待一段时间后具备执行资格”，不保证到点立即运行。

具体阶段顺序会受 Node 版本、执行上下文和 API 影响。初学者不必先背一张复杂的阶段表，先理解三条规则更有用：

1. 当前同步调用栈执行完之前，其他 JavaScript 回调不能插进来。
2. I/O 等待期间，主线程可以处理其他已就绪任务。
3. 回调执行本身若很耗 CPU，仍会占住主线程。

运行时也可能把某些文件系统、加密等工作交给 libuv 线程池；网络 I/O 的实现路径不同。不能把“异步 API”统一解释为“开了一个工作线程”。

## 四、并发不等于 CPU 并行

并发表示多个任务在时间上交错推进；并行表示多个任务在不同核心上同时执行。Node 主线程可以通过异步 I/O 并发等待许多网络操作，但一段普通 JavaScript 计算通常仍在一个线程上顺序运行。

需要 CPU 并行时，可以评估 Worker Threads、子进程或把计算交给其他服务。它们会带来消息传递、数据复制、进程生命周期和资源限制，不能为了“多线程”而盲目引入。数据库也有自己的并发与锁模型，服务有多个请求同时到达不代表事务天然安全，见 [B-20]({{LINK:B-20}})。

## 五、错误处理属于异步流程的一部分

Promise 拒绝需要被捕获；await 可能抛出异常；事件回调可能在当前函数返回后才发生。若只在同步调用处 try/catch，却没有处理异步拒绝，错误可能成为未处理拒绝或造成请求永不返回。

    try {
      const response = await fetch(url);
      if (!response.ok) throw new Error("HTTP request failed");
      return await response.json();
    } catch (error) {
      // 记录脱敏上下文，并转换为上层可理解的失败
      throw new Error("读取数据失败");
    }

服务端还要设置数据库和外部 HTTP 请求超时，避免一项依赖无限等待。取消请求时把 AbortSignal 等取消上下文传给支持取消的操作；取消一个 HTTP 请求，并不一定能撤回已经提交的数据库事务。

## 六、怎样发现事件循环阻塞

先观察请求延迟、CPU 使用和事件循环延迟，再检查热点函数与同步调用。日志里“请求变慢”只是线索；可以使用 Node 提供的诊断工具、CPU profile 和火焰图找到耗时位置。性能实验要使用固定输入、代表性并发和足够样本，避免把启动时间或单次偶然波动当成结论。

若瓶颈在数据库，增加 Node Worker 未必有帮助；若瓶颈是 CPU 密集计算，优化算法或隔离计算可能有效；若瓶颈是网络慢，合理并发与超时比提高线程数更直接。

## 七、从 Node 事件循环对照 Go goroutine

Node 与 Go 都可以同时管理很多 I/O 请求，但并发调度模型不同。Node 的 JavaScript 回调主要由事件循环执行；Go 的 goroutine 由运行时调度到多个操作系统线程，可以在多核上并行运行。Go 更容易让多个执行流同时访问共享内存，因此需要同步原语或通过消息传递保护数据。

不管语言如何调度，数据库唯一约束、事务和业务不变量仍然需要设计。换成 goroutine 不会自动解决重复点赞、刷新 token 竞争或文件与数据库的跨资源一致性；这些问题见 [M6-06]({{LINK:M6-06}})。

## 小结：知道等待和计算分别在哪里

异步 I/O 让 Node 在等待网络和文件操作时处理其他事件；主线程上的同步 CPU 工作仍会阻塞事件循环。用 async/await 可以改善代码结构，但不会自动并行。先测量瓶颈，再选择算法优化、Worker、子进程或数据库方案，并为异步失败、超时和取消定义行为。
