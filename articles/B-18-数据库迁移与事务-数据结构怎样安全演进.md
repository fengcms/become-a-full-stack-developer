# 成为全栈·基础补充·数据库迁移与事务：数据结构怎样安全演进

> 修改一张表很容易，安全地升级已有数据却是一项发布工程。数据库迁移处理结构版本，事务处理一组操作的原子性；二者相关，但不能互相替代。

## 前言：为什么不能让服务启动时顺手改表

开发初期，给数据表加个字段，删掉本地数据库再重建，似乎就完成了功能。上线后，数据库里已经有用户、文章和关系数据，表结构变更必须面对旧版本、正在运行的服务、备份和失败恢复。一次随意的 `ALTER TABLE` 可能阻塞写入，也可能让旧程序无法工作；一次不完整的回滚可能让字段和数据处于互相不兼容的状态。

数据库迁移是“把数据库从一个已知结构版本推进到另一个版本”的过程。事务则是“把一组相关数据库操作作为一个整体提交或撤销”。项目里用版本化 SQL 管理 PostgreSQL、MySQL、SQLite 的结构演进，并让迁移由独立命令执行，而不是服务启动时自动改生产表。

## 一、迁移要有历史，不要只有当前 schema

如果仓库只保存一份最新建表 SQL，读者无法知道已有数据库如何从上一版升级。版本迁移通常按顺序编号：

```text
00001_initial_schema
00002_add_article_indexes
00003_add_member_setting
```

数据库会记录已执行到哪个版本；下一次部署只运行缺少的迁移。一个合格的迁移应能通过代码审阅，说明前置结构、变更内容和数据影响，并在开发、测试、部署环境使用同一份版本历史。

迁移命令与服务进程最好分开：部署流程先备份，执行迁移，再部署兼容的新程序；或者在经过验证后按明确顺序切换。这样可以控制数据库权限，也能在迁移失败时停止后续发布。项目 Go 服务提供独立 `migrate` 命令，不在 HTTP server 启动过程中隐式执行 DDL。

## 二、结构迁移也要考虑正在运行的旧代码

假设要把 `display_name` 改名为 `nickname`。如果先删旧列再部署新代码，仍在运行的旧版本会立即报错。更稳妥的 expand/contract 思路分阶段进行：

1. **扩展**：新增 `nickname`，旧字段暂时保留。
2. **双读或回填**：新代码能处理旧数据，按受控批次填充新列。
3. **切换写入**：确认新列完整且新版本稳定后，停止依赖旧列。
4. **收缩**：经过观察窗口再删除旧列和兼容逻辑。

单实例、停机窗口明确的小项目可以采用更简单的维护窗口，但也要有备份和恢复路径。不要为了背术语而给小项目加不必要的双写；要根据部署拓扑、数据量和可接受停机时间选迁移策略。

## 三、跨数据库时，迁移脚本不能只换连接字符串

同一 ORM 并不保证多种数据库有相同语义。PostgreSQL 有独立序列；MySQL 的字段类型、排序规则、DDL 和受影响行数行为不同；SQLite 外键、并发写入和表结构变更限制也各有特点。即便数据库接受同一条 SQL，索引行为、大小写比较、空值排序和冲突错误也可能不同。

M6 对 PostgreSQL 17、MySQL 8.4、SQLite 分别维护方言迁移，并针对每种数据库执行空库迁移、重复运行和版本升级。真实验证还暴露了 MySQL 索引列需要有界 `VARCHAR`、SQLite 导入时生成键可能回写输入 map、PostgreSQL 序列重置等问题。抽象层能减少重复代码，但真实数据库测试才能确认方言行为。

因此，迁移验收至少覆盖：

| 检查 | 要回答的问题 |
|---|---|
| 空库安装 | 全部迁移能否从零开始 |
| 已有版本升级 | 旧数据是否保留，索引和约束是否建立 |
| 重复执行 | 工具是否知道迁移已完成，避免重复破坏 |
| 失败恢复 | 失败发生在哪一步，是否有备份或可重试策略 |
| 真实方言 | PostgreSQL、MySQL、SQLite 是否分别验证 |

## 四、事务保证数据库内部的一致性

例如发布文章要同时更新文章状态并写入通知。如果状态更新成功、通知写入失败，用户看到的结果就与产品规则不一致。把两条 SQL 放在同一个数据库事务中，可以确保它们都提交或一起回滚：

```sql
BEGIN;
UPDATE articles SET status = 'published' WHERE id = ?;
INSERT INTO notifications (user_id, type, ...) VALUES (?, 'article_published', ...);
COMMIT;
```

需要注意，事务只覆盖同一个数据库连接里的数据库操作。它无法自动回滚已经发送的微信 HTTP 请求，也不会撤销已经上传到 R2 的对象。若业务同时改数据库和对象存储，需要设计补偿流程、临时对象或可重试清理，而不能假设 SQL `ROLLBACK` 会让外部世界倒带。

事务边界也不能过大。网络请求、慢速 bcrypt、文件上传放在持有数据库锁的事务里，会让连接和锁被长时间占用。先完成必要的校验和外部准备，再在短事务中确认业务状态；若外部步骤失败，按设计清理或记录待处理状态。

## 五、数据迁移和结构迁移是两类任务

结构迁移创建表、添加索引、改变约束；数据迁移把旧系统里的业务行转移到新数据库。后者还要核对 ID、父子关系、外键、用户凭据、附件对象和派生计数。把 JSON 导入成功当作迁移完成，会漏掉大量问题。

Go 项目提供独立离线快照工具，保留 13 张业务表，排除刷新会话和阅读去重记录，并在空目标库中执行关系校验。dry-run 会真实插入后再回滚；实际导入要求目标为空并使用整体事务。Node SQLite 副本导入 PostgreSQL 后，13 张表逐字段核对一致。附件字节不在 SQL 快照中，必须单独复制并核对对象 key、大小和哈希；旧登录会话也不能假装无缝迁移。

这类限制应在迁移方案里明确写出：哪些数据保留、哪些重建、哪些需要用户重新登录、对象存储怎么处理、停写时间多长、回退时如何处理新系统已经写入的数据。

## 六、回滚不是万能的撤销按钮

给每个迁移写 down 脚本很有帮助，但并不意味着线上恢复总能向后执行。删列后新代码写入的数据可能无法还原；MySQL DDL 不一定能像普通 DML 一样整体回滚；PostgreSQL 序列本身也可能在事务失败后留下间隙。数据回滚的代价有时比前向修复更高。

发布前至少要准备：已验证的备份、迁移耗时估计、失败停止条件、恢复演练、应用版本兼容策略和数据核对清单。不能只在 README 中写“如有问题执行 down”。对于不可逆或有损迁移，更安全的方案通常是先加字段、双版本兼容、备份后逐步清理，而非立刻删除旧数据。

## 小结：迁移要能解释，事务要有边界

用版本化迁移记录结构历史，用事务保护同一数据库内必须一起成功的变更，用真实方言测试验证多数据库行为。遇到文件、微信或其他外部系统时，把它们当作独立资源设计补偿。最后，先在隔离副本演练数据搬迁与恢复，再讨论生产切换；迁移安全来自证据和步骤，不来自 ORM 的自动化标签。
