# 成为全栈·React 管理后台篇·异步交互的一致性：上传、批量操作与部分失败

> 异步交互不能只有 loading。界面必须准确表达还有多少任务、哪些成功、哪些失败，以及用户此刻能不能安全离开。

## 前言

管理后台里最难复现的错误，常发生在“事情还没做完”的几秒钟里。图片仍在上传，用户已经点击保存；批量删除十篇文章，前六篇成功，第七篇失败，页面却把全部勾选清空并提示“操作完成”；快速双击按钮，同一个创建请求发出两次。

这些问题不是接口不会调用，而是 UI 用一个 boolean 把多个真实任务压成了“忙或不忙”。本篇沿着图片上传和批量操作，讨论怎样让界面状态忠实反映后台任务。

## 一个 boolean 为什么不够

假设封面和正文图片同时上传。两个任务都把 `uploading` 设为 true；封面先结束并写回 false，此时正文仍在上传，保存按钮却已经恢复。

当前项目使用计数器：

```ts
const begin = useCallback(() => {
  setCount((n) => n + 1)
  let finished = false
  return () => {
    if (finished) return
    finished = true
    setCount((n) => Math.max(0, n - 1))
  }
}, [])
```

每项任务开始时取得自己的 finish，且只能释放一次。`count > 0` 才是整个表单仍有上传活动的真实含义。`UploadScope` 把正文、封面和头像等组件汇总到同一表单边界，页面不必知道每个上传控件的内部实现。

## busy 必须同时约束保存与离开

文章页的 busy 包含创建、更新和上传：

```ts
const busy = create.isPending || update.isPending || count > 0
```

busy 时禁用保存，离开保护也进入“操作尚未完成”状态。普通 dirty 可以允许用户确认放弃，但上传或保存仍在运行时，应用内导航不提供强制离开按钮。否则附件可能已经上传，正文却没有保存 URL；或者请求实际成功，用户却以为失败并重复操作。

浏览器始终可能被强制关闭，前端无法承诺取消服务端请求。因此这里保证的是应用不会主动制造歧义，而不是实现分布式事务。

## 防重入需要同步锁

React 的 pending 状态要等下一次渲染才反映到按钮。快速双击发生在这个间隙里，仅靠 `disabled={isPending}` 仍可能进入两次处理函数。

```ts
if (running.current || !ids.length) return
running.current = true
try {
  await runTask()
} finally {
  running.current = false
}
```

ref 提供同步互斥，state 负责把忙碌状态显示给用户。创建文章、发布和批量删除都值得这层保护，尤其当接口并非天然幂等时。

## 批量操作不是一个请求的放大版

批量审核十条记录时，可能出现六条成功、两条已被别人处理、两条网络失败。只有“成功/失败”两个总状态无法表达现实。

当前 hook 顺序执行每个 id，降低瞬间并发和限流压力，并独立捕获错误：

```ts
for (const id of ids) {
  try {
    await action(id)
  } catch (error) {
    failed.push(id)
    messages.push(`#${id}：${toMessage(error)}`)
  }
}
```

顺序执行速度较慢，却让当前规模下的结果与提示更稳定。如果一次要处理上百项，应由后端提供原子或异步批量端点，而不是让浏览器维持上百次串行请求。

## 成功项清除，失败项保留

任务结束后，页面只保留 failed id：

```ts
setSelected(failed)
setFailures(messages)
await refresh()
```

用户可以看到刷新后的真实列表，并直接重试失败项。全部清空会丢失处理线索；全部保留又可能重复操作已经成功的数据。

失败详情不能只放在几秒后消失的 toast 中。`BatchFailures` 用默认展开的 details 持久展示每条 id 与原因，toast 只负责汇总：“已删除 8 项，2 项失败，已保留选中”。

查询范围变化时，选择和失败信息必须清空。否则从待审核页切到已发布页，隐藏的旧 id 仍可能被操作。选择状态与序列化后的 listQuery 绑定，始终只属于当前页和当前筛选范围。

## 刷新失败也是结果的一部分

逐项操作完成后还要重新获取列表。如果写操作成功而刷新失败，服务器事实已经改变，界面却暂时无法确认。此时不能宣称列表已经同步；应保留内联查询错误和手动重试入口。

更严格的实现可以分别记录 action 结果与 refresh 结果。当前项目通过 Query 的错误态承接刷新失败，但这仍是需要在浏览器验收中主动制造的场景。

## 乐观更新要服从可预测性

批量审核、评论回复和文章状态迁移都不适合随意乐观更新，因为后端可能返回不同状态或部分失败。等待响应会慢一点，却避免界面先展示一个从未成立的事实。

适合乐观更新的动作需要三个条件：结果可预测、失败可回滚、并发冲突影响小。仅仅因为“感觉更快”，不足以承担错误状态的成本。

## 进度、取消和完成是三件不同的事

页面显示“处理中”只证明任务已经开始，并不告诉用户完成了多少。串行处理十项时，可以进一步暴露 `completed / total`；文件上传若底层支持进度事件，也可以显示百分比。但没有真实进度来源时，不要用自动增长到 90% 的假进度条，它只是在网络慢时制造新的不确定感。

取消也必须由底层能力支持。关闭弹窗不能自动等于取消请求；fetch 需要 AbortController，服务端批量任务还需要取消端点或幂等标识。当前批量操作没有中途取消能力，所以进行中禁用离开，并明确等待完成。诚实地没有取消，比提供一个只隐藏界面的“取消”可靠。

任务完成则至少包含两层：写请求已经返回，界面已经重新确认最新数据。前者成功而 refetch 失败时，应告诉用户“操作可能已完成，请重试加载”，避免再次提交相同动作。

## 错误信息要保留可定位标识

批量失败明细使用记录 id，而不是只列十条“操作失败”。id 能帮助管理员重新查找对象，也能与后端日志和 requestId 对照。若业务对象有稳定标题，可以同时显示 `#42 · 文章标题`，但不能只显示可能重复或被修改的名称。

错误展示还要区分可重试与确定失败。网络断开适合重试；权限不足、状态已变化或仍有引用，需要先修改条件。把所有失败都提供“再次尝试”按钮，只会重复制造同一个错误。当前版本保留失败项与原始消息，后续可以根据 ApiError code 给出更精确动作。

## 卸载后的状态更新也要考虑

组件被强制卸载后，异步任务仍可能返回。React Query 能管理查询订阅，但编辑器内部 Promise 队列和自建上传逻辑仍应避免在已经离开的组件上恢复焦点或调用过期回调。当前应用通过 busy 离开保护减少正常路径中的卸载，并在 effect 中清理事件监听。

如果以后允许后台上传，应把任务状态提升到持久任务中心，而不是继续依附编辑器组件。生命周期改变后，状态所有权也必须随之改变。

## 小结

可靠的异步 UI 要回答四个问题：有多少任务仍在运行，是否允许再次触发，哪些项目成功或失败，离开页面会不会丢失结果。计数器、同步锁、作用域选择、失败保留和最终刷新，分别解决这些问题。

各位看官，测试异步交互时，请主动放慢网络、连续点击、制造一半成功一半失败，再尝试离开页面。界面始终说实话，才算完成。
