# 成为全栈·Taro 小程序篇·小程序限制清单：哪些前端习惯要改掉

> 最难的限制，往往不是某个 API 不存在，而是它让原来顺手的产品行为需要重新解释。

{{IMG:M5-02-封面}}

## 前言：我最花时间的一晚，耗在一个"应该没问题"上

写小程序页面时，我仍然可以拆组件、写 Hook、用 TypeScript 检查类型。那种熟悉感很容易让我忘了一件事：**最后运行的不是网页。**

有一晚我卡在评论输入框上。代码在开发者工具里跑得好好的，聚焦、显示页面都没问题，真机上一试——**键盘把输入框顶到屏幕外面，点发送按钮却什么都没发生。**

那天晚上我才明白：这不是 bug，是我把"在浏览器里的行为"当成了默认。

内容站恰好能把这个差别集中放大。文章有外链、代码、表格和图片；会员要登录；投稿要选图、恢复草稿；评论会拉起键盘。**哪一项处理得含糊，用户都会直接撞到。**

这篇不列一百条平台知识。我把本项目实际遇到、会影响实现判断的限制整理出来——它们不是劝退清单，而是开发之前应该改掉的几种习惯。

## 别把 DOM 当作默认服务

网页里 Markdown 常常变成 HTML 交给容器显示，编辑器通过 DOM Selection 操作光标。这条路径在当前小程序不能照搬。

项目用 `markdown-it` 解析成 AST，再把节点映射到 `View`、`Text`、`Image`、`ScrollView`。**原始 HTML 是关掉的**：

```ts
// src/core/markdown.ts（节选）：html: false 让原始 HTML 不被解析。
const md = new MarkdownIt({ html: false, linkify: true, breaks: true });
```

节点按类型映射到组件，而不是拼成一段 HTML：

```tsx
// src/features/markdown.tsx（节选）
if (n.type === "code_inline")
  return (
    <Text className="inline-code" userSelect>
      {n.content}
    </Text>
  );
if (n.type === "link_open")
  return (
    <Button className="link inline-link" onClick={() => void openLink(n.attrs.href)}>
      {children}
    </Button>
  );
if (n.type === "strong_open") return <Text className="bold">{children}</Text>;
if (n.type === "em_open") return <Text className="italic">{children}</Text>;
```

这里有一个很容易走进去的错误结论：**"既然 RichText 能显示富文本，那就把整篇 Markdown 转成 HTML。"**

我确实这么干过一次。页面确实省了代码，也确实看起来没问题——**直到我需要给代码块加横向滚动、给外链加拦截、给目录加锚点。** 每一项都要进那段"不透明输出"里去改，改不动也测不了。

最后全部推翻重来，换成 AST 映射。代价是每类节点都要处理一遍，收益是**每一类的行为都可单独测试**。

| 网页里的习惯 | 本项目的替代 | 需要接受的代价 |
|---|---|---|
| HTML 容器承接整篇正文 | AST 映射受控组件 | 逐类处理 Markdown 节点 |
| DOM 光标插入格式 | Textarea 光标事件与文本拼接 | 不是所见即所得编辑器 |
| 任意 CSS 与浏览器布局 | 平台组件配合 SCSS | 需在开发工具检查实际输出 |
| 点击任意标签当按钮 | 关键操作使用原生 Button | 统一清理原生默认样式 |

编辑器那一条尤其要紧。网页里可以用 `contenteditable` 或富文本库直接拿光标位置再插入标记；小程序的 `Textarea` 只给文本值和光标事件，**格式插入只能靠字符串拼接**。所以项目把编辑器收敛成「文本域 + 预览」两块，草稿按会员隔离存在本机。

还有一项来自真机交互经验：**看起来可点的文本，未必能在所有交互路径里被稳定识别为操作控件。** 所以关键动作必须有明确的按钮语义。

## 外链不能沿用 APP 的内部浏览器方案

Flutter 那边我实现了内部 WebView：顶部返回、标题、菜单，正文显示网页。小程序没照搬。

当前 `openLink` 有三条路：站内文章转原生文章页，HTTP(S) 外链弹窗后复制地址，其他协议提示不支持。

```ts
// src/core/navigation.ts（节选）：先白名单校验，再决定降级方式。
if (!/^https?:\/\//i.test(href)) {
  Taro.showToast({ title: "不支持此链接类型", icon: "none" });
  return;
}
const r = await Taro.showModal({
  title: "打开外部链接",
  content: href,
  confirmText: "复制地址",
});
if (r.confirm) await Taro.setClipboardData({ data: href });
```

**这是一次明确降级** —— 用户知道拿到的是地址，不会把"复制成功"理解成"网页已经打开"。这个区别很重要：我最初把提示写成"打开失败"，用户点复制之后回来投诉说"明明复制成功了怎么还报错"。

站内链接还有一层 URL 解码保护：

```ts
// src/core/navigation.ts（节选）：站内文章转原生页，解码失败不抛未捕获异常。
if (/^(https:\/\/befull\.kao9\.com)?\/articles\//.test(href)) {
  const id = href.split("/articles/")[1].split(/[?#]/)[0];
  if (id) {
    try {
      openArticle(decodeURIComponent(id));
    } catch {
      Taro.showToast({ title: "链接地址无效", icon: "none" });
    }
    return;
  }
}
```

**这个 `try` 不是防御性冗余。** 小程序里 URL 从分享卡片、二维码、站内跳转三方进来，其中任意一方给出一个畸形编码就会走到这里。

### 导航栏与胶囊区域，不按网页 Header 照搬

当前工程用原生导航栏和 Tab，页面标题区放在内容范围内，没有把网站 Header 整块搬到屏幕顶部。**右上平台胶囊有自己的空间**，不能按普通网页固定栏去覆盖它。

图片资源也有明确路径 —— 配置会复制 `src/assets` 到 `dist/assets`：

```ts
// config/index.ts（节选）：源码目录必须显式复制到产物。
copy: { patterns: [{ from: "src/assets", to: "dist/assets" }] },
```

**源码目录存在，不意味着运行时地址天然有效。** 我第一次以为图标不用管，直到 Tab 全是空白——图标在 `src/assets` 里，产物里根本没有。

## 页面没有卸载，不代表数据还有效

四个原生 Tab 用 `switchTab`，文章、编辑器等二级页面用 `navigateTo`。**从文章返回首页，首页可能还保留着，而不是重新执行一次完整初始化。**

我一开始的写法是"页面一显示就重新请求"，结果用户每从文章返回一次，首页就闪一次加载。

于是改成：页面显示事件结合**缓存版本**和 **60 秒时间条件**决定是否补读，下拉刷新才强制联网。

```ts
// src/hooks/data.ts（节选）：显示事件只做条件补读，不无条件重来。
const serial = useRef(0);
const id = ++serial.current,
  epoch = sessionEpoch();
if (id === serial.current && (!privateData || epoch === sessionEpoch())) {
  setData(result);
}
useDidShow(() => {
  void load();
});
```

而"是否需要补读"的判断落在数据层，不在页面里：

```ts
// src/hooks/data.ts（节选）：缓存版本变了说明被清过，必须重读。
if (
  !lock.current &&
  loadedAt.current &&
  (Date.now() - loadedAt.current > 60000 ||
    revision.current !== (privateData ? privateCache : cache).revision())
)
  void latest.current(true);
```

**`revision()` 这一条是我被坑过之后加的。** 场景是：用户在会员页改了昵称，触发私有缓存清空，回到收藏页 —— **页面显示事件触发了，但数据层认为"60 秒内刚读过"，于是留着旧昵称。**

而 `revision` 是单调递增的版本号，缓存一清就变了。于是判断变成："要么超了 60 秒，要么缓存被人清过 —— 两种情况都重读。"

这个限制反而帮我们拆清了两个概念：**页面是否存在是平台生命周期，数据是否可用是缓存规则。** 把两者绑成"页面一出现就请求"，只会让返回操作不断闪加载。

分页锁和请求序号也不能省。切换分类后旧分类的慢响应仍可能回来—— 组件还活着，**这个响应却未必还属于当前列表**。

```ts
// src/hooks/data.ts（节选）：序号不在最新位就丢弃结果。
if (id !== serial.current || (privateData && epoch !== sessionEpoch())) return;
```

## 平台登录提供 code，不提供我们的会员会话

`Taro.login()` 返回的 code 不能直接当文章接口的 Bearer。它要送到后端，由后端向微信换身份，再返回自己的 `AuthResult`。

```ts
// src/pages/auth/index.tsx（节选）：code 只是换会话的原料，不是令牌。
if (wechat) {
  const { code } = await Taro.login();
  if (!code) throw new Error("未取得微信登录凭证，请重试");
  result = await api<Auth>("/auth/wechat/callback", "POST", { code }, false);
}
setSession(result);
```

`setSession` 保存的是后端 `AuthResult`，不是微信 code。文章、收藏、评论、投稿继续用系统 accessToken，刷新继续用系统 refreshToken。

AppID 是项目身份配置，AppSecret 是后端凭据。**它不能成为 Taro 构建变量，更不能写进小程序 JS。** 用户可以检查包内代码，所以"藏在前端配置里"从来不是秘密管理。

另一个容易误会的地方：微信登录成功**不代表**已经拿到头像、昵称或手机号。当前自动建号不依赖这些资料授权，会员可以在资料页自己改。**我们没实现的授权能力，不该通过文案暗示存在。**

本地会话用微信存储 API。它方便恢复登录，但**不是 Flutter 安全存储的同义词**。登录退出、账号隔离和日志脱敏仍要认真做，不能因为"这是小程序"跳过风险判断。

登录成功后还要回到用户原来的位置：

```ts
// src/pages/auth/index.tsx（节选）：来源页优先，否则进会员 Tab。
setSession(result);
if (Taro.getCurrentPages().length > 1) await Taro.navigateBack();
else await tab("member");
```

## 网络和上传，是两条不同的执行路径

普通 JSON 请求走 `Taro.request`，统一信封、错误转换和并发 401 都在请求层处理。图片走媒体选择加 `Taro.uploadFile`，**返回体还需要解析字符串**。

所以，普通 API 自动刷新会话，**上传没有同样的重放机制**。我把这个差别明确写出来，免得读者把两种 API 都叫"请求"后推导出一致行为。

选择取消也不是上传失败：

```ts
// src/core/api.ts（节选）：选择、校验、上传是三件事，取消不是错误。
const choice = await Taro.chooseMedia({
  count: 1,
  mediaType: ["image"],
  sizeType: ["compressed"],
});
const file = choice.tempFiles[0];
if (!file) throw new Error("未选择图片");
if (file.size > 10 * 1024 * 1024) throw new Error("图片不能超过 10MB");
```

**把"用户关掉了相册"报成红色错误，是我改掉的一个毛病。** 现在的做法是：`chooseMedia` 返回空 `tempFiles` 时静默返回，只有真正选了文件才校验大小。

## 把"支持"拆成四种可以检查的说法

做平台迁移时，最危险的词往往是"支持"。源码能调用、框架能编译、开发工具能执行、正式环境允许执行 —— **是四件不同的事。**

| 说法 | 含义 | 需要的证据 |
|---|---|---|
| 源码能调用 | 存在这条实现分支 | 代码与单元测试 |
| 框架能编译 | 构建产出包含它 | 构建产物 |
| 工具能执行 | 模拟器里跑通 | 开发工具记录 |
| 正式环境允许 | 平台放行 | 真机与发布条件 |

分享功能就是个例子。按钮有 `openType`，这只证明"源码能调用"；**跨账号真机接收验证是另一件事**，而后者才是用户真正遇到的场景。

开发工具里有个"关闭域名校验"的开关，它让本地开发很方便 —— 但**它不会让一个不满足条件的外站获得真实运行资格**。我见过太多"开发工具好好的，上真机就白屏"，根因都在这里。

### 键盘是一份很好的迁移检查表

用户点评论框会有焦点、键盘和页面滚动；点外部区域应该收起键盘；点回复要把回复对象和输入位置一起带到可见区域。**这些都要额外实现，`Textarea` 绑定 `value` 不会自动带来它们。**

```tsx
// src/components/ui.tsx（节选）：点击屏幕根节点即收起键盘。
<View className={`screen ${theme}`} onClick={() => Taro.hideKeyboard().catch(() => {})}>
  {children}
</View>
```

表单内部阻止冒泡。**但这意味着"空白处"本身也有区域差异** —— 把"点任何地方必定失焦"当绝对结论并不稳妥。真机键盘高度、原生输入遮挡和滚动仍应按设备观察。

这也是我开头那个"卡了一晚"的根源：**开发者工具的模拟器不弹键盘，而真机会弹。** 组件在模拟器里"跑得好好的"这句话，在涉及平台 UI 的地方基本无效。

### 限制不是永久的禁止清单

外链目前降级，不代表永远不能加网页容器；上传没有自动刷新，也不代表重放一定不能做。关键是补齐对应条件：平台资格、目标域名、写入幂等与返回值检查。

**如果只为消除一条清单就匆忙加功能，很可能引入新的含糊状态。** 更好的顺序是：先说明当前用户能得到什么，再为新增能力准备明确入口、失败反馈和验收场景。

## 把限制翻译成验收动作

我们记录了构建与类型检查，也实际在开发工具里看过阅读、目录、登录、投稿和主题切换。**这些能证明当前演示路径。**

但移动设备的键盘遮挡、长文滚动、弱网上传以及权限分支，需要对应人工场景才能下结论。**没有验证过的项目不应该写成"兼容完成"。** 限制清单的价值，正是告诉我们缺哪份证据。
