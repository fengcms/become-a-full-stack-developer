# 成为全栈·Taro 小程序篇·小程序限制清单：哪些前端习惯要改掉

> 最难的限制，往往不是某个 API 不存在，而是它让原来顺手的产品行为需要重新解释。

{{IMG:M5-02-封面}}

## 前言：熟悉 React，不等于熟悉运行环境

写小程序页面时，我仍然可以拆组件、写 Hook、用 TypeScript 检查类型。这种熟悉感很容易让我忘记：最后运行的不是网页。

内容站恰好能把这个差别集中暴露出来。文章有外链、代码、表格和图片；会员要登录；投稿要选图、恢复草稿；评论会拉起键盘。哪一项处理得含糊，用户都会直接撞到。

各位看官，这篇不列一百条平台知识。我把本项目实际遇到、会影响实现判断的限制整理出来。它们不是劝退清单，而是开发之前应该改掉的几种习惯。

## 一、别把 DOM 当作默认服务

在网页里，Markdown 经常变成 HTML，然后交给容器显示。编辑器也可以通过 DOM Selection 操作光标。到了当前小程序，我们不能照搬这条实现路径。

项目使用 `markdown-it` 解析内容，再将节点交给 `View`、`Text`、`Image`、`ScrollView` 等组件。原始 HTML 被关闭，链接由显式按钮处理，代码高亮生成的受控片段才交给 `RichText`。

这里很容易出现一个错误结论：“既然 RichText 能显示富文本，那就把整篇 Markdown 转成 HTML。”这会把点击、目录、横向滚动以及样式控制重新塞进一段不透明输出。页面看似省了代码，能力边界却更难测试。

| 网页里的习惯 | 本项目小程序的替代 | 需要接受的代价 |
|---|---|---|
| HTML 容器承接整篇正文 | AST 映射受控组件 | 逐类处理 Markdown 节点 |
| DOM 光标插入格式 | Textarea 光标事件与文本拼接 | 不是所见即所得编辑器 |
| 任意 CSS 与浏览器布局 | 平台组件配合 SCSS | 需在开发工具检查实际输出 |
| 点击任意标签当按钮 | 关键操作使用原生 Button | 统一清理原生默认样式 |

最后一项来自开发工具交互经验：看起来可点的文本，并不等于所有工具与交互路径都能稳定识别为操作控件。关键动作应该拥有明确的按钮语义。

## 二、外链不能沿用 APP 的内部浏览器方案

Flutter APP 已经实现了内部 WebView：顶部返回、标题、菜单，正文显示网页。但小程序本次没有照搬。

当前 `openLink` 有三条路：站内文章转原生文章页，HTTP(S) 外链弹窗后复制地址，其他协议提示不支持。精简后的判断是：

```ts
// 来自 src/core/navigation.ts 的关键分支。
if (!/^https?:\/\//i.test(href)) {
  Taro.showToast({ title: '不支持此链接类型', icon: 'none' });
  return;
}
const r = await Taro.showModal({
  title: '打开外部链接', content: href, confirmText: '复制地址'
});
if (r.confirm) await Taro.setClipboardData({ data: href });
```

这是一种明确降级：用户知道拿到的是地址，不会把复制成功理解成网页已经打开。站内链接还有 URL 解码异常保护，非法地址不应把页面点击变成未捕获异常。

以后若增加 `web-view`，要重新核对账号类型、业务域名配置和目标站点条件。开发工具关闭域名校验，不会自动让所有外站具备真实运行资格。本文只解释当前实现，不承诺一个未经验证的容器方案。

### 导航栏与胶囊区域，不按网页 Header 照搬

当前工程使用原生导航栏和 Tab，页面标题区放在内容范围内，没有把网站 Header 整块搬到屏幕顶部。右上平台胶囊有自己的空间，不能按普通网页固定栏去覆盖它。若以后改自定义导航，应重新处理安全区与胶囊位置，并在设备上检查触控区域。

图片资源也有明确路径：配置会复制 `src/assets` 到 `dist/assets`，组件与 Tab 指向产物中的图片。源码目录存在，不意味着运行时地址天然有效。包内资源与网络图片还对应不同的加载和发布条件，应分别检查。

## 三、页面没有卸载，不代表数据还有效

四个原生 Tab 用 `switchTab`；文章、编辑器等二级页面用 `navigateTo`。从文章返回首页，首页可能仍然保留着，而不是重新执行一次完整初始化。

于是，不能只在 React 挂载时读数据，也不能一看到 `useDidShow` 就无脑重新请求。项目让页面显示事件结合缓存版本与 60 秒时间条件决定是否补读，主动下拉刷新再强制联网。

这个限制反而帮我们拆清了两个概念：页面是否存在，是平台生命周期；数据是否可用，是缓存规则。把两者绑成“页面一出现就请求”，只会让返回操作不断闪加载状态。

分页锁和请求序号也不能省。切换分类后，旧分类的慢响应仍可能回来。组件活着，并不意味着这个响应仍然属于当前列表。

## 四、平台登录提供 code，不提供我们的会员会话

`Taro.login()` 返回的 code 不能直接当作文章接口的 Bearer。它要送到后端，由后端向微信换取身份，再返回自己的 `AuthResult`。

AppID 是项目身份配置，AppSecret 是后端凭据。它不能成为 Taro 构建变量，更不能写进小程序 JS。用户可以检查包内代码，因此“藏在前端配置里”从来不是秘密管理。

另一个容易误会的地方：微信登录成功，不代表已经获取用户头像、昵称或手机号。当前自动建号不依赖这些资料授权，会员可以在自己的资料页面修改信息。我们没有实现的授权能力，不应通过文案暗示存在。

本地会话则使用微信存储 API。它方便恢复登录，但不是 Flutter 安全存储的同义词。登录退出、账号隔离和日志脱敏仍要认真做；不能靠“这是小程序”跳过风险判断。

## 五、网络和上传，是两条不同的执行路径

普通 JSON 请求通过 `Taro.request`，统一信封、错误转换和并发 401 都在请求层处理。图片通过媒体选择加 `Taro.uploadFile`，返回体还需要解析字符串。

所以，普通 API 自动刷新会话，并不意味着上传已经拥有同样的重放机制。当前上传没有自动刷新后重试。我在文章中明确保留这个差别，避免读者把两种 API 都叫“请求”后，错误地推导出一致行为。

选择取消也不是上传失败。用户只是关掉了相册，不应该收到红色错误提示；真正选定文件后，再检查大小、上传响应和账号是否切换。平台 API 的交互语义，必须传到页面状态里。


## 把“支持”拆成四种可以检查的说法

做平台迁移时，最危险的词往往是“支持”。源码能调用、框架能编译、开发工具能执行、正式环境允许执行，是四件不同的事。

比如 HTTP 图片，阅读器接受它的地址，只能证明我们有渲染分支。网络实际可达、域名条件满足、真机显示与平台发布条件，还要有另外的证据。再比如分享，按钮有 openType，也不等于已经完成跨账号真机接收验证。

我在项目里倾向于使用更精确的描述：已实现哪段逻辑，已观察哪个工具场景，哪个正式条件本轮不验证。这样协作者不需要靠猜测补全“支持”的含义。

### 键盘是一份很好的迁移检查表

用户点击评论框，会有焦点、键盘和页面滚动；点击外部区域，应该收起键盘；点击回复，要把回复对象与输入位置一起带到可见区域。这些并不是 Textarea 绑定 value 后自动完成的产品行为。

当前 Screen 捕获外部点击并调用 hideKeyboard，表单内部阻止冒泡；评论框用 onFocus、onBlur 协调 focus，回复时滚动到 composer。这样的实现能解释动作来源，也让后续回归知道该点哪里。

但表单内部阻止冒泡意味着“空白处”也有区域差异，不应把一句“点击任何地方必定失焦”写成绝对结论。真机键盘高度、原生输入遮挡和滚动仍应按设备观察。

### 限制不是永久的禁止清单

外链目前降级，不代表永远不能增加网页容器；上传没有自动刷新，也不代表重放一定不能做。关键是补齐对应条件：平台资格、目标域名、写入幂等与返回值检查。

如果只为消除一条清单就匆忙加功能，很可能引入新的含糊状态。更好的推进顺序，是说明当前用户能得到什么，再为新增能力准备明确入口、失败反馈和验收场景。

教学项目尤其需要保留这些判断。读者学到的不该是“某 API 不能用”的碎知识，而是面对运行环境变化时，怎样先缩小承诺、再通过证据逐步扩展能力。

## 六、把限制翻译成验收动作

我们记录了构建与类型检查，也实际看过开发工具中的阅读、目录、登录、投稿和主题切换。它们能证明当前演示路径。

但移动设备的键盘遮挡、长文滚动、弱网上传以及权限分支，需要对应人工场景才能下结论。没有验证过的项目不应该写成“兼容完成”。限制清单的价值，正是告诉我们缺哪份证据。
