# 成为全栈·Go 后端篇·第六批复盘：从换一种语言到证明系统等价

> 把服务从 Node 重写到 Go，最难的不是翻译 handler，而是在旧客户端、冻结契约、真实数据库和历史数据面前重新实现一整套可观察行为，并准确说明哪些已经验证、哪些仍未部署。

{{IMG:M6-10-封面}}

> 本文代码快照：Go 业务实现 ceac4e0；契约 1.12.0；Node 对照版本 v1.0.4。生产后端和线上数据未切换。

## 前言：结束开发不等于系统已经上线

M6 最初看起来像一次技术栈替换：用 Go + PostgreSQL 重写 Node 后端，继续支持 MySQL 与 SQLite，并保持前端 API 不变。真正推进后，工作变成一串相互约束的问题：冻结版本怎么定？旧 Node 中偏离契约的行为要不要复制？GORM 的零值如何保留？三种数据库的唯一冲突和锁有什么差异？对象存储故障能不能回滚 SQL？四个客户端实际请求代码如何验证？迁移工具是否能安全拒绝目标数据？

Go 服务最终实现 68 个冻结 operation，具备独立 server/migrate/seed/data 命令，采用领域包和显式事务，运行 PostgreSQL、MySQL、SQLite 的真实门禁，建立差分 trace 与离线数据快照。三轮代码审阅也促成工程边界和证据门禁改进。

它仍不是生产切换：本轮没有执行线上数据库写入、真实 R2/微信账号联调或完整 Linux 容器部署，客户端 smoke 也不等于所有页面重新验收。这些边界是最终复盘的组成部分。

## 一、为什么先做 G0 基线，而不是马上写代码

项目先固定 OpenAPI 1.12.0 的 54 路径/68 操作、Node v1.0.4 commit 和数据版本，再建立行为对照表。这个步骤揭露文档、契约和源码之间的差异：例如某些默认分页、评论限制、阅读窗口和通知行为并不完全一致。

如果没有这张基线，写 Go 时会把“新实现预期”误当“旧系统事实”。发生冲突时，我们按契约、产品材料、Node 源码和客户端消费证据逐项判断，记录决定而不借重写私自升级 OpenAPI。这个做法让重写更慢，却避免把接口变化伪装成内部实现替换。

真实经验是：跨语言项目前面的证据整理，往往比第一批 Go 文件更能降低后续返工。

## 二、工程结构围绕领域和事务组织

Go 工程以 cmd 作为程序入口，以 bootstrap 作为唯一装配根；httpapi 承担协议边界；article、auth、comment、taxonomy、member、administration 和 attachment 表达各自领域；platform/database、storage 与 model 承担基础设施和持久化映射。API DTO 与 ORM row 分开，Service 在有业务事务时直接使用 GORM，不叠加一个覆盖不全的 Repository<T> DSL。

这套设计有明确成本：Service 可见 GORM，未来更换 ORM 可能需要改动领域代码；显式映射增加了一些重复赋值。但 transaction owner、查询与业务边界都能从代码中追踪，少量 interface 仅用于 WechatClient、Provider 和 Identity 这类真实可替换边界。

测试中曾遇到的核心风险不是目录名字，而是事务是否被 helper 绕开。把 tx 显式传递，让通知、标签、文章状态共用一个提交边界，能减少“主表成功、关系失败”的半完成状态。

## 三、跨语言差异逼出了隐含语义

Go 的零值不记录 key 是否存在；GORM struct update 默认可能忽略 false、0 和空字符串。JavaScript 侧的字符串长度、时间、数字解码和数据库默认行为也不完全一样。M6 通过 Fields presence、明确白名单 map、UTF-16 长度 helper、毫秒整数时间和固定排序表，把这些边界显式化。

刷新令牌旋转展示了事务思维的重要性：重放时业务请求应被拒绝，但会话家族撤销必须提交，所以业务决策和数据库执行错误分开；文章审核与通知则要求同事务提交或回滚；对象和 SQL 没有共同事务，只能补偿与对账。

这些不是 Go 专属问题。语言重写只是把原来依赖运行时或 ORM 默认行为的规则暴露出来，迫使我们说清楚零值、权限和失败到底意味着什么。

## 四、多数据库支持必须是实际运行的事实

数据库.Open 使用 GORM dialector，数据库结构则按 PostgreSQL、MySQL、SQLite 各自维护两版 goose migration。SQLite 配置外键、WAL、busy timeout 和单写连接；项目没有依赖 AutoMigrate 自动改表。测试在 PostgreSQL 17、MySQL 8.4 容器及 SQLite 文件库上跑迁移、升级、完整业务、并发、权限与文件补偿。

三库都通过报告所列用例，不等于所有操作系统、数据库版本、数据规模和多实例拓扑全覆盖。特别是 SQLite 单写方案、进程内分类 mutex 和附件 key 锁，都不能宣称为多写副本协调方案。

多数据库的实现成本是实实在在的：每次 DDL 都要跨方言维护，冲突与 RowsAffected 要单独验证，性能也不能用 SQLite 代替 PostgreSQL。支持范围越宽，必须维护的证据矩阵越大。

## 五、差分测试找到相同和不同

同一中立请求 trace 在隔离数据上对照 Node 与 Go：74 次成功工作流请求覆盖 68 个 operation，其中 71 项比较一致、3 项是明确记录差异；111 次鉴权失败请求覆盖 47 个受保护 operation，全部比较一致。

差异不是通过放宽脚本消失。搜索默认页数按冻结契约设为 10，而 Node 通用默认是 20；文章发布通知在产品行为里存在，Node 源码缺少生成，Go 补齐后通知列表和未读数有相应差异。通知类型、内容、链接和计数都逐项检查。

这组结果提升了可解释性，但没有穷尽所有参数、权限和数据库状态。测试报告还要结合 schema、事务后置断言和客户端请求 smoke，不能把 185 次比较写成整个系统数学意义上的等价证明。

## 六、离线迁移和部署准备也有明确限制

data 工具采用只读导出与版本化快照，仅迁移 13 张业务表，不含活跃 refresh token、阅读去重和对象字节；导入要求已迁移空目标，规范化旧字段，父子关系按拓扑排列，并检查作者、分类、评论、附件、点赞计数。dry-run 写完整事务后回滚。

这证明迁移路径在隔离环境可运行，不代表线上数据已经切换。生产切换还要停写、备份、对象复制、真实写入、检查序列、启动服务、观察与回退。真实微信/R2 账户也没有在本轮做写入联调；Dockerfile 不是已部署容器的证据。

不复制 refresh token 意味用户重新登录；上线时间窗口若不冻结写入，快照会漏增量；附件元数据迁移不代表对象字节已经到位。这些限制必须写在迁移文档和发布计划里。

## 七、三轮代码审阅改变了什么

三轮审阅覆盖了正确性、代码可读性、工程约定和证据。整改包括领域文件职责调整、事务辅助命名、中文包说明、Provider/WechatClient/Identity 方法说明、AST doccheck 和缺陷注入自检。回应中也纠正了报告对 go/doc 聚合说明及 GOPROXY=off 离线边界的论证，同时接受相关工程改进。

审阅工具不是裁判。每条意见都需要回到具体代码和可复现行为；项目自己的自定义门禁也应检查缺陷注入、说明误报边界。生产工艺门禁通过不代表含测试代码的所有文档/行长告警也为零，结果必须如实分别报告。

这次过程让我们认识到，回复评审和修复代码是同一个工程活动：修复必须对应提交，回复必须绑定快照，未复跑的检查要明确标注。

## 八、Node 与 Go 的选择要回到团队和部署约束

本机 SQLite 小样本观察中，Go 的多数读取和登录场景延迟较低，Node 的点赞/取消 p50 较低；Node 运行 tsx、Go 使用原生二进制，RSS和数据库统计口径不同，样本量有限。本结果不足以决定生产选型。

若团队熟悉 TypeScript，服务对 Cloudflare Workers/D1/R2 的集成已经可靠，继续 Node 很可能比重写更划算。若团队需要 Go 服务、能承担新语言和 PostgreSQL 运维、迁移收益清楚并有时间建立兼容证据，Go 是合理实现。选择由业务边界和团队能力决定，不是 benchmark 排名。

## 九、这批工作留下的可复用方法

- 重写前固定代码、契约、客户端和数据版本；
- 让差异先进入清单，再决定修复还是兼容；
- 用真实数据后置状态测试事务，而非只断言 error；
- 用真实数据库验证数据库支持声明；
- 让第三方替身与真实服务验收分开；
- 为跨资源写入定义补偿，而不是声称它们原子；
- 将本地构建、容器构建、部署、迁移和切流分为不同证据；
- 记录每轮审阅的提交、命令、报告和未执行项；
- 性能数据连同样本、硬件、工具和限制一起发布。

这些方法可以应用于框架升级、数据库替换、服务拆分或 API 版本迁移，不限于 Node → Go。

## 结尾：重写完成了一份新实现，后续仍有发布工作

M6 完成了 Go 工程、三数据库验证、差分与客户端请求层 smoke、离线迁移工具、三轮代码审阅和相关教学材料。冻结契约及四端客户端没有因重写改动。它让项目拥有第二套可检查实现，也清晰暴露仍需完成的线上平台验收和生产切换步骤。

项目最终应以证据驱动下一步：目标 Linux 镜像构建与运行、真实微信/R2 联调、生产数据迁移演练、客户端 UI 全路径和正式切换。完成代码是阶段结果；完成部署需要另一组被验证的操作。
