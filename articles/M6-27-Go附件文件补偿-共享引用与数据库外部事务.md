# 成为全栈·Go 后端篇·文件与数据库没有共同事务：共享附件怎样补偿

> SQL transaction 不能回滚一次 R2 PutObject。上传先成功、数据库后失败时，工程必须决定对象如何清理；删除也一样，不能把两个系统伪装成一个原子操作。

> 本文代码快照：提交 ceac4e0。对象与元数据跨资源补偿限于本进程协调，清理失败需告警与对账。

## 前言：两种资源不会一起提交

上传附件需要把字节写到 local/R2，再创建数据库 Attachment 记录。删除时需要移除元数据，最后一个引用消失后删除对象。数据库事务可以回滚 SQL，却无法撤销已完成的文件系统 rename 或云存储 PUT；对象存储也不知道关系表的事务状态。

因此，文件操作天然存在部分成功窗口。M6 选择清晰的操作顺序、内容摘要 key、共享引用检查和保守补偿，不宣称“原子上传”。失败时要保护仍被引用的对象，并记录需要人工或后续作业清理的孤儿。

本文分别追踪新增和删除，并说明进程内锁的边界、取消时的清理语义以及为什么可靠队列/outbox 是后续规模化方案。

## 一、同一份内容可能被多个附件记录引用

附件对象 key 由 SHA-256 内容摘要加扩展名组成。两个相同字节、相同扩展名的文件可能落到相同 key；元数据记录则仍可分别属于不同用户或文章。对象因此可被共享引用。

这提供内容去重，但也增加删除规则：删除一条 Attachment 不代表可以马上删除对象。只有相同 storage + storage_key 的元数据引用数归零，才允许移除对象。计数必须查询数据库真实关系，不能从客户端传入“我觉得没人用了”。

key 经过安全白名单验证，不将原始文件名直接作为路径或云对象 key。扩展名仍参与 key，因此相同内容但不同扩展名可能形成不同对象；MIME 和扩展名处理需遵守上传契约。

两种资源的职责边界可以并排看：

| 维度 | 对象（Object） | 元数据（Attachment 行） |
|---|---|---|
| 存放位置 | local 磁盘或 R2 | 数据库 |
| 标识 | `storage_key`（内容摘要 + 扩展名） | 主键 `id` |
| 归属 | 无归属，可被多条记录共享 | 属于某用户，可关联文章 |
| 删除条件 | 同一 key 的引用数归零 | 权限校验通过且记录存在 |

这张表解释了为什么删除逻辑不能对称处理。删除元数据是一行 SQL，能否删由权限决定；删除对象要先回答“还有没有别的记录指向它”。前者是数据库问题，后者是跨资源的引用计数问题，两者的判据不在同一层。

## 二、上传顺序：先对象，后元数据

Create 首先验证可选 articleId 对应文章存在，再生成内容哈希 key，获取该 key 对应的本进程锁。然后调用 Provider.Put；对象成功后创建 Attachment 行。客户端只有在数据库行返回成功后才获得附件响应。

~~~go
// internal/attachment/service.go（Create，节选）
// Create 保存内容对象和元数据；数据库失败时仅补偿没有其他引用的对象。
func (s *Service) Create(ctx context.Context, user int64, articleID *int64, data []byte, ext, mime string) (any, error) {
	if articleID != nil {
		if _, err := article.Get(s.DB.WithContext(ctx), fmt.Sprint(*articleID)); err != nil {
			return nil, err
		}
	}
	hash := sha256.Sum256(data)
	key := fmt.Sprintf("%x%s", hash, ext)
	if !storage.SafeKey.MatchString(key) {
		return nil, fault.Field("file", "文件扩展名不合法")
	}
	lock := s.lock(key)
	lock.Lock()
	defer lock.Unlock()
	provider := s.Providers[s.Driver]
	if provider == nil {
		return nil, fault.New(fault.Internal)
	}
	if err := provider.Put(ctx, key, data, mime); err != nil {
		return nil, err
	}
	a := model.Attachment{
		UserID:     user,
		ArticleID:  articleID,
		StorageKey: key,
		URL:        "/files/" + key,
		Storage:    s.Driver,
		MimeType:   mime,
		Size:       int64(len(data)),
		CreatedAt:  s.Now().UnixMilli(),
	}
	if err := s.DB.WithContext(ctx).
		Create(&a).Error; err != nil { // Conservative compensation: never remove an object referenced by another row.
		cleanupCtx, cancel := context.WithTimeout(context.WithoutCancel(ctx), 5*time.Second)
		defer cancel()
		var n int64
		if countErr := s.DB.WithContext(cleanupCtx).
			Model(&model.Attachment{}).
			Where("storage_key = ? AND storage = ?", key, s.Driver).
			Count(&n).Error; countErr == nil && n == 0 {
			if cleanupErr := provider.Delete(cleanupCtx, key); cleanupErr != nil {
				slog.Warn("orphan upload cleanup required", "key", key, "storage", s.Driver)
			}
		} else if countErr != nil {
			slog.Warn("upload compensation inspection failed", "key", key, "storage", s.Driver)
		}
		return nil, err
	}
	return View(a), nil
}
~~~

顺序可以逐段读出来。`articleID` 非空时先确认文章存在，避免上传一个挂到不存在文章上的附件。`sha256.Sum256(data)` 加 `fmt.Sprintf("%x%s", hash, ext)` 生成 key——摘要决定主体，扩展名只做后缀。紧接着 `storage.SafeKey.MatchString(key)` 兜住扩展名里的非法字符，所以“文件扩展名不合法”这个错误来自 key 白名单，而不是单独写的扩展名检查。

`s.lock(key)` 取到该 key 对应的互斥锁并 `defer` 解锁，让同一对象的写入在本进程内串行。`provider.Put(ctx, key, data, mime)` 是第一个可能改变外部状态的动作，用的是调用方传入的 `ctx`。

数据库插入失败时的补偿分支有三个要点。`context.WithoutCancel(ctx)` 剥掉父 context 的取消信号，再套 `WithTimeout(..., 5*time.Second)`，所以即使客户端已经断开，清理仍有最多 5 秒可用时间。清理前先 `Count` 一次引用数，只有 `countErr == nil && n == 0` 才真正 `Delete`——查询失败时不删，保留对象并记 `slog.Warn`。这两处保守判断合起来确保：宁可留下一个孤儿对象，也不会删掉别人正在引用的内容。

若数据库插入失败，服务用 WithoutCancel 从请求 context 创建最多 5 秒清理 context。它重新查询数据库，看是否已有相同 storage_key/storage 的引用；只有查询成功且引用数为零，才调用 Provider.Delete。若其他记录已引用对象，则保留；若引用检查失败，也保守地不删，记录告警供清理。

这一顺序优先保护现有引用。代价是数据库不可用时可能留下 orphan object，需要后续对账。反过来先写数据库再上传，会产生“附件元数据存在但对象不存在”的窗口，用户拿到 URL 却读不到内容。不存在免费原子性，只能选择较安全的顺序并定义补偿。

| 顺序 | 失败后留下的中间态 | 后果 |
|---|---|---|
| 先对象、后元数据（当前） | 对象在，元数据缺失 | 上传报错，可能留下孤儿对象 |
| 先元数据、后对象 | 元数据在，对象缺失 | 用户拿到 URL 却读不到内容 |

选前者是因为两种中间态的可观测性和代价不同。孤儿对象不对外暴露，用户可以重传，运维对账能找出来；而“元数据在、对象缺失”会直接体现在用户侧——页面显示一张失败的图，重试上传还可能因为元数据已存在而失败。换句话说，这两行不是“哪个更优雅”的选择，而是“失败时你更愿意面对哪一种症状”。

## 三、删除顺序：先删元数据，再看剩余引用

Delete 先读取记录并检查本人或管理角色权限，按 storage key 加本进程锁，再开启数据库事务。事务里重读附件、删除元数据，并查询同一对象 key 还剩多少记录引用。事务提交后，如果计数为零才调用 Provider.Delete。

~~~go
// internal/attachment/service.go（Delete，节选）
// Delete 检查权限并移除元数据，最后一个引用消失后才删除对象。
func (s *Service) Delete(ctx context.Context, id int64, actor values.Actor) error {
	db := s.DB.WithContext(ctx)
	var a model.Attachment
	if err := db.First(&a, id).Error; err != nil {
		return err
	}
	if !actor.Allows("editor", a.UserID) {
		return fault.New(fault.Forbidden)
	}
	lock := s.lock(a.StorageKey)
	lock.Lock()
	defer lock.Unlock()
	var refs int64
	txErr := db.Transaction(func(tx *gorm.DB) error {
		if err := tx.First(&a, id).Error; err != nil {
			return err
		}
		if err := tx.Delete(&a).Error; err != nil {
			return err
		}
		return tx.Model(&model.Attachment{}).
			Where("storage_key = ? AND storage = ?", a.StorageKey, a.Storage).
			Count(&refs).Error
	})
	if txErr != nil {
		return txErr
	}
	if refs == 0 {
		if p := s.Providers[a.Storage]; p != nil {
			if err := p.Delete(ctx, a.StorageKey); err != nil {
				slog.Warn("object cleanup required", "key", a.StorageKey, "storage", a.Storage)
			}
		}
	}
	return nil
}
~~~

权限检查在加锁之前：`actor.Allows("editor", a.UserID)` 不允许就越权，此时还没有影响任何状态，直接返回。锁按 `a.StorageKey` 取，所以同一对象的删除和上传会排进同一个队列。

事务里的动作顺序是“重读、删元数据、数引用”。重读是为了在锁内拿到最新行，避免锁外读到的记录已被改动。计数用的是 `Where("storage_key = ? AND storage = ?", ...)`——同一 key 加同一存储驱动才算同对象，换成另一个 provider 上恰好同名的 key 不算。

对象删除放在 `Transaction` 外层，也就是提交之后。这一步若失败，只记 `slog.Warn("object cleanup required", ...)` 然后返回 `nil`——元数据确实已经删掉且已提交，向客户端报告失败会诱导它重试删除一条不存在的记录，所以这里选择如实返回成功，把对象层面的问题留给清理告警。

若 SQL 事务失败，元数据删除回滚，不会删对象。若 SQL 成功而对象删除失败，数据库记录已经消失，对象会成为孤儿；当前实现记录告警并返回元数据删除成功，避免让客户端重试删除已经不存在的附件记录。之后需要人工清理或运维对账找到遗留对象。

删除对象放在 SQL commit 之后有意避免误删：若先删对象、数据库回滚，其他附件引用会指向丢失对象。commit 后删除失败虽然产生孤儿，但服务仍保留安全优先策略。未来可以增加清理任务和待删除 outbox，让失败可重试且可观测。

## 四、本进程 key lock 保护共享对象的局部竞态

附件服务用固定数量的 striped mutex 根据 key 哈希选择锁，上传与删除相同 key 时串行执行，防止同一进程里“计数为零后删除”和“新引用刚上传”交错。

~~~go
// internal/attachment/service.go（节选）
// Service 协调元数据与对象存储，共享对象按内容 key 在本进程串行修改。
type Service struct {
	DB        *gorm.DB
	Providers map[string]storage.Provider
	Driver    string
	Now       func() time.Time
	locks     [64]sync.Mutex
}

// New 装配存储提供者和文件元数据服务。
func New(db *gorm.DB, driver string, p map[string]storage.Provider) *Service {
	return &Service{
		DB:        db,
		Driver:    driver,
		Providers: p,
		Now:       time.Now,
	}
}
func (s *Service) lock(key string) *sync.Mutex {
	h := sha256.Sum256([]byte(key))
	return &s.locks[int(h[0])%len(s.locks)]
}
~~~

`locks [64]sync.Mutex` 是一个固定长度的锁数组。`New` 里没有初始化它——数组是值类型，64 个互斥量随结构体一起分配好了。`lock(key)` 取 key 的 SHA-256 摘要第一个字节，对 64 取模，得到 0 到 63 之间的下标。这就是 striped mutex 的由来：不按 key 建无限多的锁，而是把 key 映射到固定数量的桶上。

代价是不同 key 可能落到同一把锁上，导致它们互相等待；换来的是内存可控——无论有多少对象，锁的总数始终是 64。由于摘要分布均匀，碰撞概率低，被误伤的两个对象本来也只是短暂互斥。

锁的粒度是同一个 key，不同 key 的请求互不影响：并发上传两张不同的图片不会互相阻塞。

`Providers` 是 `map[string]storage.Provider`，按驱动名索引。`Delete` 用的是 `s.Providers[a.Storage]`——按记录自己声明的存储驱动找 provider，而不是当前的 `s.Driver`，所以迁移期间留下的旧对象仍能被正确定位和删除。

Mutex 不跨进程、不跨容器，也不在重启后保留。如果两个服务副本共享 R2 和数据库，各自的本地锁互相不可见，仍可能发生竞态。单实例测试通过不能证明多副本共享对象安全。若拓扑改为多写实例，应使用数据库对象锁/状态机、延迟删除标记、分布式协调或其它可验证的方案。

SQLite 单实例加单写连接缩小一部分并发范围，但 R2 对象仍是外部共享资源。部署结构和媒体存储架构必须一起审阅。

## 五、请求取消与补偿 context

上传时 Provider.Put 收到原始请求 context。客户端中断后，对象服务可能取消上传；若 Put 已经完成而 DB insert 随即失败，补偿仍要尝试删除对象，因此 Create 清理用 WithoutCancel 派生一个独立的五秒 context。这个 context 仍受超时约束，不会让清理无限运行。

Delete 的数据库事务之后调用 Provider.Delete 时使用原 request context。若请求已取消，删除可能失败并被记录为待清理；由于元数据已经提交，API 不会再做虚假回滚。这个风险应由日志监控和清理对账承接。更可靠的设计会在事务里写待删除任务，后台 worker 使用自己的受控 context 重试。

## 六、哪些补偿方案可以演进

| 方案 | 优点 | 代价 |
|---|---|---|
| 当前同步补偿 | 实现少、失败路径直接、适合单实例 | 进程锁局部；对象失败后需人工清理 |
| 删除队列表 | SQL commit 时可靠记录待删 key | worker、重试、幂等和死信管理 |
| Outbox | 业务变更与待处理事件同事务提交 | 消费端仍要幂等，增加基础设施 |
| 定期对象对账 | 可发现历史孤儿 | 需要对象列表权限和安全删除策略 |
| 分布式锁 | 协调多实例同 key 操作 | 锁租期、失效和故障恢复更复杂 |

选择取决于数据量、丢对象代价、允许的孤儿量和服务拓扑。教学项目以可读性为先，但边界需要诚实写出；有明确对象数据价值后，清理任务和对账就应进入工程计划。

## 七、失败注入比只测成功上传更重要

关键用例包括：Put 失败时没有 Attachment 行；Put 成功而 DB create 失败且无引用时对象被补偿；存在共享引用时失败不会删对象；引用检查失败时保留对象并告警；删除非最后引用只删当前元数据；删除最后引用后尝试删对象；对象 Delete 失败后元数据已经消失并生成告警；同 key 并发上传/删除在单实例内串行。

再使用两个 Service 实例共享同一个数据库和 Provider，证明进程 mutex 的局限；只有明确支持多实例后，才能把新的协调方案作为验收要求。故障测试应断言附件行数、对象是否存在、返回错误和日志/待清理信号。

## 小结：补偿把部分成功变得可恢复，但不是原子事务

M6 上传先 Put 再插元数据，失败时只在确认没有引用后用独立短 context 补偿；删除先提交元数据移除，再在最后引用消失时删除对象。按 key 的互斥仅在当前进程有效；外部删除失败会留下可观测的孤儿清理需求。

跨资源流程要明确选择部分成功策略：什么状态可接受、何时重试、如何发现 orphan、什么条件能安全删除。把这些事实说出来，比声称“事务保证文件和数据库一致”更能帮助后续维护。
