# 成为全栈·Go 后端篇·Go 后端怎么测试：从成功响应到故障后置状态

> 测试的价值不在“代码跑过”，而在于它能把关键业务不变量变成失败时也可检查的证据。对重写项目，成功响应、数据库状态、跨语言差分和客户端 smoke 各自证明不同事情。

> 测试快照：Go 提交 ceac4e0；完整验证记录见 docs/go-backend/07-验证与兼容报告.md。文章所列范围只对应该报告。

## 前言：测试数量不等于兼容

Go 后端面对冻结 OpenAPI 的 68 个操作。逐个接口只测 200 和 JSON 形状，仍然可能漏掉权限、重复提交、事务回滚、空值语义和多数据库差异。重写项目还要回答一个额外问题：与 Node 相比，客户端实际观察到的行为是否相同？

M6 的验证分层执行：接口工作流覆盖成功路径和响应 schema；边界测试检查逐操作鉴权与输入；领域测试检查数据库后置状态和并发不变量；真实 PostgreSQL、MySQL、SQLite 分别运行迁移及业务用例；差分执行器重放中立请求 trace；四客户端请求层回归检查既有调用代码能否继续工作。

本文用这些证据说明测试金字塔如何适配后端复刻，为什么要注入失败、控制时间、跑真实数据库，以及为什么 test suite 全绿也不能证明线上切换已经完成。

## 一、从 operation 清单建立可追踪覆盖

OpenAPI 1.12.0 包含 54 个路径、68 个 operation。Go 测试中的 workflow 使用实际 HTTP 路由、JWT、数据库和 local storage，74 次请求覆盖 68/68 个 operation；成功响应逐项验证冻结 schema。额外请求用于多个状态或业务路径，不代表契约新增 operation。

boundary 测试包含 152 项逐 operation 鉴权/输入断言，并验证错误信封和 4001 字段错误 schema。缺失字段错误必须保留具体路径。health 和 /files/{key} 是实现已有运行时能力，单独验收，不能悄悄计入冻结 OpenAPI operation 数。

覆盖报告把每项测试输入和结果绑定到真实操作。它解决“哪些操作有证据”的问题，但不能说明所有输入组合都穷尽。接口路径覆盖是底线；边界组合仍应按权限、状态、字段语义和并发风险选择。

## 二、最有价值的断言在数据库里

许多重要错误不会出现在正常响应结构中。例如发布通知写失败后，HTTP 返回错误，但如果文章状态已经提交就留下业务不一致；刷新令牌重放被拒绝，却没有提交会话族撤销；重复点赞返回成功，但关系表和 like_count 却不相符。

M6 的测试会在请求后重新查询数据库：审核与通知失败时状态一起回滚；重复成功不重复通知；点赞重复操作保持关系唯一且计数精确；会员历史 progress 的 0/null/缺失分别保留；分类树不成环且最多四级；文章删除释放 slug；刷新重放提交撤销家族；微信建号只生成唯一 user/identity。

这类测试通常比 mock 一个 GORM method 更能证明业务行为。mock 可以确认某个函数曾被调用，无法证明 transaction commit 之后关系约束成立。对于核心不变量，使用隔离的真实数据库跑实际 service/HTTP 路径更可靠。

## 三、事务测试要主动让中间步骤失败

只运行一遍成功路径不能证明原子性。工程通过通知插入错误注入，确认文章审核、PUT 发布及评论复核与通知处于同一事务；通知失败，业务状态仍是旧值且没有通知记录。附件上传则模拟存储成功、元数据创建失败、共享引用存在和补偿失败，检查对象是否安全保留。

故障注入不是随机破坏环境，而是为关键依赖提供可控失败点。每个失败场景都应该说明期望后置状态：哪些行被回滚，哪些状态有意提交，哪些对象需要清理。刷新重放尤其特殊，业务请求被拒绝但安全撤销必须提交；测试若只断言 error，会错过它最重要的行为。

对事务路径建立小的状态表，再在测试中验证各状态。这样实现者和评审者都知道“失败”的含义，而不是只看 exception 是否传出来。

## 四、时间、并发和三数据库分别测试

时间规则使用注入时钟，避免等待实际 24 小时。阅读冷却测试固定到午夜前后、窗口边界和并发访问；JWT fixture 测试 token 到期时刻；业务通知和更新时间也能得到确定值。时间注入不是把所有业务都变成可随意改时钟，而是把时间边界变成显式输入。

Go 的 race detector 检查进程共享内存数据竞争，但不能检测 SQL 行锁和事务不变量。并发测试针对 refresh rotation、微信建号/首次设密、点赞与滚动阅读冷却运行多请求并检查最终状态。单测即便使用 goroutine，也要实际打到隔离数据库才能验证数据库结果。

SQLite 使用 WAL、busy timeout 和单写连接；测试采用临时文件库以覆盖持久化和锁行为。PostgreSQL 17 与 MySQL 8.4 使用真实容器，独立执行 15 张表 migration、重复迁移、00001 到 00002 升级、完整业务流程、并发和 local 文件补偿。三个数据库都通过当前报告列明门禁，但并不代表每种生产版本、操作系统和部署拓扑都已覆盖。

## 五、双实现差分不能先把差异忽略掉

Go 生成中立请求 trace，再用相同 seed、受控时钟和微信替身调用 Node Hono 与 Go。状态码、业务码、字段类型、null、数组顺序、ID、计数都严格比较；只规范化随机 token、随机微信用户名和明确列出的生成时间。

成功流程 74 次请求中，71 项完全一致，3 项是明确记录的产品差异：搜索默认 pageSize，以及 Go 新增发布通知与 Node 旧实现差异（通知列表默认值与生成事件单独核验）。111 次受保护操作鉴权失败全部一致。数字必须连同场景、边界和允许差异一起引用；不能写成“两个后端 100% 等价”。

差分结果能够发现实现行为差异，但不能决定谁正确。碰到不同结果，回到冻结契约、PRD、Node 源码和既有客户端，建立证据后记录接受或修正。为了让测试全绿而把两个实现的错误都复制过去，并不是兼容成功。

## 六、已有客户端 smoke 的范围要讲准确

M6 用现有网站、后台、小程序与 Flutter 的真实请求层或会话代码访问测试后端。网页验证真实请求模块及状态；管理后台检查管理权限；Flutter 使用真实 Dio 网络栈；Taro 的平台 HTTP/存储传输使用测试替身。微信流程通过测试服务器的固定身份替身建号并设密，随后 Flutter 的真实 Dio 使用同一账号登录。

这些结果属于 API 请求和会话层 smoke。它们不等于浏览器真实 Cookie 策略完全验收，不等于微信开发者工具真机联调，也不等于所有 UI 页面逐项回归。把证据分级写清楚，后续团队才知道还需在哪里补测试。

## 七、质量工具各自拦住不同问题

make verify 包括 gofmt、文档/包说明检查、go vet、OpenAPI 快照一致性和 go test；三库矩阵与全包 race 是单独验证命令。格式化只能保证代码格式，vet 可发现一些静态问题，schema 同步检查防止快照落后，race 检查共享内存竞争，业务测试验证输出与后置状态。

依赖安全报告也有范围：当时未发现可达或已导入包的漏洞，但依赖模块中仍存在未使用 crypto/openpgp 漏洞条目。准确表述应是“当前未发现可达/已导入问题”，不能写成“依赖绝对没有安全公告”。静态工具有边界，安全结论必须描述具体扫描目标和版本。

## 小结：每个结论都要匹配一条证据链

M6 用 operation coverage、边界矩阵、事务失败、数据库后置状态、真实三库、差分 trace、客户端请求层 smoke 和工程门禁互相补充。它们证明不同层次，任何一项通过都不能替代其他项。

写测试报告时，用四个问题核对每个结论：测试了什么输入？实际运行了什么实现和数据库？检查了哪个可观察结果或后置状态？没有覆盖什么环境？这些答案比单独公布通过数量更能帮助别人复核。
