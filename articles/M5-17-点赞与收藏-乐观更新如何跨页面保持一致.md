# 成为全栈·Taro 小程序篇·点赞与收藏：乐观更新如何跨页面保持一致

> 乐观更新不是假装请求成功，而是先给出可撤销的反馈，再让服务器结果校准它。

{{IMG:M5-17-封面}}

## 前言：图标变红，数字却不动

APP 开发时，作者提出过一个很典型的体验问题：点赞成功，图标变化了，文章数字却没有更新；还希望点赞收藏采用乐观更新，让操作更流畅。

小程序如果只复制按钮布局，这个问题还会出现。点赞拥有用户关系和公开计数，收藏主要是个人关系；详情操作又会影响列表卡片。它们需要的不只是一个 setLiked。

当前实现用共享 reaction store 承接即时反馈，详情写入用服务端响应校准，再通过缓存失效触发后续读取。这篇把几条路径拆开，让“看起来一致”和“最终事实一致”各有负责人。

## 先建立关系，再允许反转

详情互动初始化并行读取点赞状态和收藏关系。点赞端点直接返回 liked 与 likeCount，收藏则遍历当前会员收藏分页，直到找到文章或到达结尾。

```ts
// src/features/reactions.tsx（节选）：初始化必须同时确认两种关系。
async function load() {
  const epoch = sessionEpoch();
  setReady(false);
  try {
    const [like, favorite] = await Promise.all([
      read<{ liked: boolean; likeCount: number }>(`/articles/${id}/like/status`, true, !!auth),
      auth ? isFavorite(id) : false,
    ]);
    if (epoch === sessionEpoch()) {
      patchReaction(id, { liked: like.liked, count: like.likeCount, favorite });
      setReady(true);
    }
  } catch {
    setError(true);
  }
}
```

收藏判断本身是一次分页遍历，只看第一页会误判：

```ts
// src/core/reactions.ts（节选）：收藏判断遍历分页，避免只看第一页。
export async function isFavorite(id: number) {
  for (let page = 1; ; page++) {
    const data = await read<Page<Article>>(`/me/favorites?page=${page}&pageSize=100`, false, true);
    if (data.list.some((a) => a.id === id)) return true;
    if (page >= data.pagination.totalPages) return false;
  }
}
```

只查收藏第一页很容易误判：文章在后面的页，界面却显示未收藏。当前 isFavorite 每页读取一百条，这保证了判断范围，但大收藏集也会带来额外读取成本。缓存能减少重复请求，不能取消规模代价。

登录用户在 ready 之前禁用两个操作，状态失败提供重试。游客点击则进入登录。这避免先对未知关系做反转，制造“以为新增其实删除”的动作。

初始化使用 Promise.all，所以其中一种关系失败时，两种操作都暂不 ready。这是当前保守选择，不是独立降级的实现；以后若要让点赞不受收藏读取失败影响，需要拆开就绪状态。

## 收藏判断那个 while(true)，我第一反应是"太蠢了"

`isFavorite` 里有个 `for (let page = 1; ; page++)` 的死循环 —— 不像其他地方那样有明确的终止条件，读起来很别扭。

我第一反应是改掉它，让它只查一页。

**改完之后测出来是错的**：收藏夹有 47 篇文章时，文章在第 2 页，而我只查了第 1 页（100 条）—— 于是界面显示"未收藏"，而实际已收藏。

**这个 bug 的恶劣之处在于：收藏少的账号完全测不出来。** 测试同学收藏了 5 篇，任何实现都能过。而真实用户收藏到几十上百篇时才会暴露。

所以现在我把它写成了一个显式的循环，并加了一条断言：

```ts
// test/core.test.ts（节选）：收藏判断必须走完所有分页。
// 构造 150 篇收藏（2 页），断言第 2 页那篇被正确识别。
```

**"只查第一页"和"查完所有页"的差别，只有在数据量超过一页时才存在。** 而这类 bug 的特征就是：**开发环境的数据量永远不够。**


## 把本地状态与公开文章对象分开

reaction store 以文章 ID 保存 liked、favorite、count，通过 `useSyncExternalStore` 通知详情与 ArticleCard。容量上限二百，会话代次变化清理。

```ts
// src/core/reactions.ts（节选）：容量上限与会话代次清理。
const values = new Map<number, Reaction>(),
  listeners = new Set<() => void>();
let epoch = sessionEpoch();
subscribe(() => {
  if (sessionEpoch() !== epoch) {
    epoch = sessionEpoch();
    values.clear();
  }
});
export function patchReaction(id: number, patch: Reaction) {
  values.set(id, { ...values.get(id), ...patch });
  if (values.size > 200) values.delete(values.keys().next().value!);
}
```

文章列表仍来自服务端读取，reaction 只覆盖需要即时反馈的字段。这样，不必复制整个 Article 到另一个全局库，也不必让详情页寻找每张卡片修改 props。

| 对象 | 负责什么 | 不负责什么 |
|---|---|---|
| Article 响应 | 服务器文章信息与初始计数 | 当前用户即时点击过程 |
| reaction store | 跨消费者的关系与计数反馈 | 永久事实或跨账号共享 |
| API 响应 | 校准点赞关系与计数 | 自动更新所有页面局部布局 |
| 缓存失效 | 后续重新读取 | 替代点击后的即时反馈 |
| 组件本地锁 | 阻止同一次点击重复提交 | 协调跨设备或其他消费者 |
| 组件就绪态 | 关系未确认前禁用操作 | 不替代服务端关系校验 |

## 乐观更新要先保存可回滚快照

详情 toggle 捕获旧关系、旧数字与 epoch，锁住操作后立即写新状态：

```ts
// src/features/reactions.tsx（节选）：先保存整体快照，再写乐观状态。
const epoch = sessionEpoch(),
  before = {
    liked: value?.liked || false,
    favorite: value?.favorite || false,
    count: value?.count ?? count,
  },
  next = !before[kind];
lock.current = true;
patchReaction(id, {
  [kind]: next,
  ...(kind === "liked" ? { count: Math.max(0, before.count + (next ? 1 : -1)) } : {}),
});
```

count 不能小于零。锁在请求完成前阻止再次反转，避免多个快照互相覆盖。当前采用串行单次操作，不是允许无限连点再合并最终意图的复杂队列。

按钮文字、图标和数字一起变化，用户能明确看到反馈。若只变图标而数字等待响应，交互仍会有两段不一致；如果只改数字而忘记 liked，下一次点击又会计算错误。

## 点赞以返回计数为准，收藏不虚构计数

点赞 POST 或 DELETE 返回 liked 和 likeCount，当前同代次才校准：

```ts
// src/features/reactions.tsx（节选）：点赞以服务端计数校准，收藏只更新关系。
if (kind === "liked") {
  const r = await api<{ liked: boolean; likeCount: number }>(
    `/articles/${id}/like`,
    next ? "POST" : "DELETE",
  );
  if (epoch === sessionEpoch()) patchReaction(id, { liked: r.liked, count: r.likeCount });
} else
  await api(
    next ? "/me/favorites" : `/me/favorites/${id}`,
    next ? "POST" : "DELETE",
    next ? { articleId: id } : undefined,
  );
```

服务器可能同时收到其他人的点赞，所以最终数字不一定等于本地加一。响应校准是必要步骤，不是装饰性的再赋值。收藏写入采用 `/me/favorites` 的 POST 或按文章 ID DELETE，关系成功后保留本地 favorite。没有虚构收藏总量，也没有把点赞计数复用成收藏数。

失败时同代次回滚 before，并展示错误；若期间换了账号，则不把 A 的快照回滚到 B 的世界：

```ts
// src/features/reactions.tsx（节选）：失败只在同代次回滚，锁始终释放。
} catch (e) {
  if (epoch === sessionEpoch()) patchReaction(id, before);
  toast(e);
} finally {
  lock.current = false;
}
```

finally 解锁与写入后的缓存清理是两件事，后者仍由请求层负责。

## 幂等是后端承诺，锁只是客户端体验

同一个会员重复点赞，后端关系唯一与计数处理保证不会无限增加。收藏同样按关系处理。前端锁减少重复动作，但无法阻止用户重启、发原始请求或两台设备同时操作。

因此，乐观更新不能让服务器放松幂等，也不能在网络失败时随意重试写入。超时意味着结果不确定，当前统一请求层不自动重放普通网络错误；认证 401 是另一种可确认未执行的前提。

这里有一条容易混的界线：客户端锁保护的是“这一次点击别发两遍”，它活在组件实例里，换了页面就没了；幂等保护的是“无论来多少次请求结果都一样”，它必须活在后端。两者解决的不是同一个问题，所以不能互相替代，也不应该拿其中一个去证明另一个已经安全。

服务端的原子计数与关系规则可参考前面 Node 点赞文章，客户端这篇只消费相应事实。把两者放在一起理解，才不会误以为“UI 加一”就是实现了点赞系统。

顺着这条线还能得出一个判断标准：凡是需要最终一致的地方，客户端都不该成为事实来源。客户端能做的是让等待更短，以及让错误更早被看见。

这个标准也解释了文章为什么反复强调验证条件。乐观反馈再快，也仍需要服务器确认；能被复述的条件——哪篇文章、什么网络、第几次点击——才让“感觉快”变成可以复查的结论。否则，一次顺畅的手感随时可能被下一次弱网推翻。

## 跨页面一致也有当前边界

ArticleCard 订阅 reaction store，所以多数卡片能立即看到详情操作。首页“大家都在读”区域却直接显示读取结果，没有全部使用 ArticleCard；它不能因为 store 存在就自然实时更新。

```tsx
// src/components/ui.tsx（节选）：卡片订阅 reaction，简表没有。
const reaction = useReaction(article.id);
{typeof article.likeCount === "number"
  ? ` · 赞 ${reaction?.count ?? article.likeCount}`
  : ""}
```

点赞私人列表移除分支更新 liked，但没有直接校准 count；缓存与后续详情读取会补齐事实。文章应明确这个差异，不能把一个共享 Hook 宣传成所有入口、所有数字完全同步。

此外，初始化状态请求可能与点击或账号变化交错。当前 epoch 保护身份，锁保护写操作；如果以后扩展更多消费者，要考虑读取版本和写入版本之间的顺序，不能只靠全局通知。

操作失败时的提示与重试入口也要写清楚，而不是让按钮停在一个不确定的状态：

```tsx
// src/features/reactions.tsx（节选）：状态失败提供重试入口。
disabled={!!auth && !ready}
{error && (
  <Button className="link" onClick={() => void load()}>
    互动状态加载失败，点击重试
  </Button>
)}
```

## 怎样验证，而不是凭肉眼觉得快

已有逻辑测试检查请求与身份隔离规则，真实本地后端测试验证点赞收藏关系；reaction store 与组件乐观回滚没有独立自动化测试。UI 的完整连续点击、失败回滚与多入口计数矩阵仍需对应人工验证，不在文章里补写为已完成。

建议固定一篇文章和两个账号：检查初始关系，点赞马上看到变化，失败回到快照；换人后旧响应不能更新；从私人列表取消，再进入详情校准；收藏超过一页仍识别正确。

体验速度可以记录点击到首次反馈时间，服务器一致性则检查响应和后续 GET。没有测量数字，不用“零延迟”描述；乐观反馈再快，也仍需要服务器确认。


## 以一次失败演练快照的用途

假设文章初始二十赞，当前会员未赞。点击后本地变为二十一、已赞；服务器拒绝，请求层抛错，同代次回到二十、未赞。before 保存的是这次动作开始的整体相关状态，不是只有数字。

如果点击后另一个用户也点赞，服务器成功返回二十二，本地应采用二十二。用“把我刚才加的一再确认一次”处理，会忽略并发事实。乐观值只是等待期间的表示，成功结果才是校准依据。

再加入账号切换：甲点击后立即退出，乙登录，甲响应成功。epoch 不同，既不能校准甲关系，也不能在失败时回滚甲快照。否则，回滚反而成了私人数据污染来源。

### 共享 store 不等于同时修改一切

ArticleCard 订阅 reaction，所以读取对象变化会重渲染。其他区域直接显示 article.likeCount，就没有这个订阅。排查“哪里没更新”时，先画消费者列表，而不是先怀疑后端计数。

具体可以逐项看：详情按钮、持续流卡片、热门简表、作者卡片、私人点赞列表。它们的展示来源和更新路径不同，用户眼里却都叫点赞数。只有把路径逐项核对，才能说哪些即时一致，哪些等待回源。

当前实现选择局部共享加缓存校准，保留了少数入口差异。本篇记录它，是为了让后续优化有明确目标，不把已有 store 当成完成证明。

### 初始化读取也有自己的顺序

关系读取强制确认，能避免长时间使用旧值，但如果未来允许多处同时操作，同一文章的读取可能在较新的写入之后返回。单个组件的锁不能协调所有消费者。

届时可以为每篇文章引入操作版本，或在写后拒绝早于该版本的关系读取；也可以统一关系读取所有权。应先出现真实并发消费者，再补这一层，不必把当前简单交互扩成完整客户端事务系统。

乐观更新的设计顺序因此应是：确定服务器动作和幂等，确定可回滚状态，再确定共享范围与读取校准。动画与颜色可以最后优化，前面的关系错了，视觉再流畅也只是把错误更快地展示出来。

## 优先为可撤销操作使用乐观反馈

点赞收藏的回滚清楚，适合当前方案。创建文章可能已经产生资源，超时后难以简单回滚，就不应照抄同一逻辑。不同写操作要先判断撤销与幂等条件。

相关机制见 [有界缓存]({{LINK:M5-13}}) 和 [投稿防重复创建]({{LINK:M5-20}})。让用户先得到反馈，同时保留校准与回滚路径，这才是乐观更新值得采用的原因。
