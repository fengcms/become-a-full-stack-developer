# 成为全栈·Taro 小程序篇·Taro 工程落地：锁定依赖、AppID 与可复现构建

> 能在自己的机器上打开一次，还不算工程搭好了。下一位读者拿到仓库，应该知道装什么、导入哪里、哪些配置绝不能进入产物。

{{IMG:M5-09-封面}}

## 前言：先导入一个基础工程，再继续开发

这次小程序开发有一个很务实的起点：先构建基础代码，让作者在微信开发者工具里导入项目；AppID 配置好、工具打开之后，再开发业务。

这个顺序看着朴素，却省掉了许多沟通成本。我们先确认“工具能找到产物”，再确认“页面能工作”，没有把工程配置问题和业务问题混在同一轮联调里。

这篇就从这个起点展开。我要留下的不是一份过几个月可能失效的安装口令，而是当前代码快照的构建约定：依赖怎样锁定，AppID 和 API 怎样分工，什么证据能说明工程可以重建。

## 一、版本要落到文件，别只写在文章里

当前 `package.json` 里，Taro 相关包统一为 4.3.0，React 为 18.3.1，TypeScript 为 5.7.3。包管理器也声明了具体版本：

```json
{
  "packageManager": "pnpm@11.25.0",
  "scripts": {
    "build:weapp": "taro build --type weapp",
    "dev:weapp": "taro build --type weapp --watch",
    "typecheck": "tsc --noEmit",
    "test": "node scripts/test.mjs",
    "test:integration": "node scripts/integration.mjs"
  }
}
```

这里的脚本直接来自工程。依赖中还有带范围的开发包，所以不能只看 `package.json` 就声称“所有依赖都精确锁死”。真正的解析结果还要依靠 `pnpm-lock.yaml`。

安装时使用锁文件，才有机会让读者与开发者拿到同一组依赖。若本机版本不同导致锁文件被改写，应该先检查工具链，而不是把变更随手提交。教学文章最怕读者照着敲，结果调的是另一套工程。

本次构建证据记录 Node 24.19.0。这个数字描述实际验证环境，不意味着其他版本一定失败，也不替代框架对运行环境的要求。升级时应重新验证，不能把一次通过推广成永久兼容声明。

## 二、三个配置值，三种不同的归属

| 配置 | 放在哪里 | 是否可以出现在客户端 |
|---|---|---|
| AppID | 开发工具项目配置 | 可以，它标识小程序项目 |
| API 基址 | Taro 构建环境与配置 | 可以，请求目标本来可见 |
| AppSecret | 后端部署 Secret | 不可以，它用于服务端换取微信身份 |

这三者常被一起叫“微信配置”，但安全边界完全不同。特别是 `TARO_APP_API_BASE` 只是切换公开地址；不能照这个办法再发明一个 `TARO_APP_WECHAT_SECRET`。

源码里公开的默认接口是 `https://api-befull.kao9.com/api/v1`。测试可以覆盖基址，正式交付要恢复到目标环境。会话和草稿存储键也带 API，避免本地用户与线上用户编号重合时误读数据。

仓库忽略 `.env` 和构建产物。忽略规则只能减少误提交，不能代替秘密扫描；如果秘密曾进入 Git 历史，删文件不是撤销泄露。本项目文章不展示 AppSecret 内容，也不记录换取身份时的敏感完整 URL。

## 三、导入的是工程入口，运行的是构建产物

Taro 源文件不能直接被开发工具当作小程序页面运行。开发工具项目配置应指向编译输出目录，业务开发则仍修改 `src`。

这一步最容易发生的误操作，是在开发工具里改了生成后的 JS，然后以为已经修改源码。下一次构建就会覆盖它。我们应该让“源码入口”和“运行产物”在目录层面可分辨。

复现顺序如下，前提是已经具备对应 Node 与 pnpm：

```bash
cd taro-miniprogram
pnpm install --frozen-lockfile
pnpm typecheck
pnpm test
pnpm build:weapp
```

`dev:weapp` 适合联调，`build:weapp` 用于检查交付产物。集成测试会启动临时真实后端并使用测试数据，应按测试脚本的约定执行，不能临时把生产接口改成写入测试场地。

开发工具里还要选择实际 AppID。本轮演示按约定关闭域名校验，但这是一个显式测试条件，应写进验收记录，不是隐藏在个人工具设置里的“大家都懂”。

## 四、构建成功后，继续检查它到底包含什么

我们记录的产物包含 14 个页面、4 个原生 Tab。保留在源码中的旧实验页没有注册到 `app.config.ts`，不能因为文件存在就算成用户可用页面。

构建检查还确认临时本地测试夹具没有进入交付包，生产 API 地址已经恢复。这比只看终端最后一句 success 更接近真正的工程交付。

证据中的 `artifactBytes` 是 758869：对生成文件大小求和得到的约 759 KB。不要拿它和平台上传包大小直接等号，更不要据此推导首屏耗时。压缩、分包、运行时加载与设备条件是不同维度。

| 检查 | 能证明什么 | 不能证明什么 |
|---|---|---|
| TypeScript 通过 | 当前类型约束成立 | 运行时服务一定返回正确结构 |
| weapp 构建通过 | 当前目标能生成产物 | 所有原生交互正确 |
| 页面与基址扫描 | 路由清单和环境符合交付目标 | 真机网络和审核已通过 |
| 开发工具打开 | 工具可以加载当前工程 | 正式发布条件已齐备 |

这些检查不是重复劳动。它们分别保护不同边界，混成一句“验证通过”，后续协作就不知道该相信到哪一层。


## 一次干净重建，比保存成功截图更有价值

开发工具打开后，最容易保留的是页面截图。但截图不会告诉下一位协作者，产物是不是来自当前源码，是否残留了 watch 构建中的旧文件，或者配置是否仍指向临时服务。

更可靠的复现演练，是在确认可再生成的前提下清理输出，按锁文件安装、类型检查、测试、生产构建的顺序重新执行，再导入新产物。这里说的是后续复现方法，不是把没有重跑的操作补写成历史事实。

遇到问题时，保留完整错误与版本比反复点击重新编译更有效。依赖解析失败先看安装日志；编译失败先看源码与框架插件版本；运行时请求失败再看 API 地址和接口响应。不同层的失败不要用同一种“重装试试”处理。

### AppID 配好后，也可能仍然登录失败

客户端 AppID 与后端 AppID、AppSecret 必须属于对应项目。项目导入成功只说明工具认得它，不说明后端已经配置了匹配凭据。

当线上微信登录返回 500，客户端现在会提供暂不可用与密码登录兜底文案。但这个文案只是帮助用户退出死胡同，不能精确诊断是配置、平台换码还是 Workers 执行失败。真正的分类需要服务端安全诊断。

这就是工程记录应分层的原因。Taro 构建、项目导入、code 获取、后端换码、用户创建、会话返回，每一段都可以成功或失败。把它们分开，问题才能收敛到负责的模块。

### 仓库交付还包括“没有什么”

临时测试夹具不在交付包，真实秘密不在源码，生成文件不参与正常业务编辑，这些都是可检查的交付要求。但检查时不能把秘密值打印出来当证据，验证变量名称与注入方式即可。

如果要在 CI 重建，建议先复用相同脚本，再补工作目录、运行时版本、锁文件策略和产物检查。不要在 CI 发明另一组编译命令，否则本地通过与流水线通过会慢慢变成两种工程。

现在尚未提供一个完成过的跨机器构建矩阵。我们留下了版本与检查记录，后续协作者可以据此复现，而不是把本机一次成功当成所有环境都被验证。

## 五、工程文档应帮助下一次失败定位

假如读者安装失败，我希望他先检查 Node、pnpm 和锁文件；假如开发工具找不到页面，先检查输出路径和注册清单；假如微信登录失败，再看后端 Secret 与真实换码链路。

这样分层，避免一个登录 500 被当成 Taro 版本问题来回重装。后面确实发生过 Workers 运行时差异，那件事已在 [Node 测试通过，Workers 登录为什么仍然 500]({{LINK:M1-34}}) 中单独复盘。

工程搭好之后，进入 [多端代码组织]({{LINK:M5-06}})。保留命令、版本、产物检查和工具条件，下一位协作者才不必先复原你的电脑环境，再理解你的业务代码。
