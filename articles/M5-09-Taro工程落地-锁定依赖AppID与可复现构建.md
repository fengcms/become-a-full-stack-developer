# 成为全栈·Taro 小程序篇·Taro 工程落地：锁定依赖、AppID 与可复现构建

> 能在自己的机器上打开一次，还不算工程搭好了。下一位读者拿到仓库，应该知道装什么、导入哪里、哪些配置绝不能进入产物。

{{IMG:M5-09-封面}}

## 前言：我最怕的一句话是"在我这能跑"

这次小程序开发有一个很务实的起点：**先构建基础代码，让作者在微信开发者工具里导入项目；AppID 配好、工具能打开之后，再开发业务。**

这个顺序看着朴素，却省掉了大量沟通成本。我们先确认"工具能找到产物"，再确认"页面能工作" —— **没有把工程配置问题和业务问题混在同一轮联调里。**

那为什么强调这个顺序？因为我见过反过来的做法：一边写业务一边调工程，然后某个页面渲染不出来，**所有人都在怀疑自己的业务代码，而问题其实在输出目录配错了。**

这篇留下的不是一份过几个月可能失效的安装口令，而是当前代码快照的构建约定：**依赖怎样锁定、AppID 和 API 怎样分工、什么证据能说明工程可以重建。**

## 版本要落到文件里，别只写在文章里

当前 `package.json` 里 Taro 相关包统一为 4.3.0，React 18.3.1，TypeScript 5.7.3。包管理器也声明了具体版本：

```json
{
  "packageManager": "pnpm@11.25.0",
  "scripts": {
    "build:weapp": "taro build --type weapp",
    "dev:weapp": "taro build --type weapp --watch",
    "typecheck": "tsc --noEmit",
    "test": "node scripts/test.mjs",
    "test:integration": "node scripts/integration.mjs"
  }
}
```

依赖组同样写在文件里，读者不必从文章正文里抄版本号：

```json
"dependencies": {
  "@tarojs/components": "4.3.0",
  "@tarojs/helper": "4.3.0",
  "@tarojs/plugin-framework-react": "4.3.0",
  "@tarojs/plugin-platform-weapp": "4.3.0",
  "@tarojs/react": "4.3.0",
  "@tarojs/taro": "4.3.0",
  "markdown-it": "14.1.0",
  "react": "18.3.1"
},
"devDependencies": {
  "@tarojs/cli": "4.3.0",
  "@tarojs/webpack5-runner": "4.3.0",
  "babel-preset-taro": "4.3.0",
  "esbuild": "0.25.12",
  "typescript": "5.7.3",
  "webpack": "5.98.0"

```

**注意这里的措辞是"统一为 4.3.0"，不是"所有依赖都精确锁死"。** 依赖中还有带范围的开发包，所以真正的解析结果要依靠 `pnpm-lock.yaml`。

安装时使用锁文件，才有机会让读者与开发者拿到同一组依赖。**若本机版本不同导致锁文件被改写，应该先检查工具链，而不是把变更随手提交。**

本次构建证据记录 Node 24.19.0。这个数字描述实际验证环境，不意味着其他版本一定失败，**也不替代框架对运行环境的要求** —— 升级时应重新验证，不能把一次通过推广成永久兼容声明。

把这些都写进文件之后，文章本身就不会成为版本的唯一载体。**读者升级依赖时，改动落在 `package.json` 与锁文件里，文章只需说明判断**，而不必同步维护一串随时会过期的数字。

### 命令顺序也有讲究

先装依赖、再查类型、再跑逻辑测试，**最后才是生产构建**。

```sh
pnpm install --frozen-lockfile
pnpm typecheck
pnpm test
pnpm build:weapp
```

我把构建放在最后是刻意的。**早期版本我把它放第一位，结果每次类型错误都被包装成"构建失败"，定位反而更慢** —— 终端只给一个红叉，没人知道根因是类型还是配置。

顺序固定下来，失败落在哪一层就一目了然。`dev:weapp` 适合联调，`build:weapp` 用于检查交付产物。

集成测试会启动临时真实后端并使用测试数据。**应按测试脚本的约定执行，不能临时把生产接口改成写入测试场地** —— 这条我在 M5-08 里也强调过。

把这几条命令固定下来还有一个隐性收益：**任何一次"我这里能跑"的争论，都可以回到同一条命令序列上复核**，而不是各自回忆装过什么。

## 三个配置值，三种不同的归属

| 配置 | 放在哪里 | 是否可以出现在客户端 |
|---|---|---|
| AppID | 开发工具项目配置 | 可以，它标识小程序项目 |
| API 基址 | Taro 构建环境与配置 | 可以，请求目标本来可见 |
| AppSecret | 后端部署 Secret | **不可以**，用于服务端换取微信身份 |

这三者常被一起叫"微信配置"，但**安全边界完全不同**。

特别是 `TARO_APP_API_BASE` 只是切换公开地址 —— **不能照这个办法再发明一个 `TARO_APP_WECHAT_SECRET`。** 我见过这个思路的变体："那我把 Secret 换个名字放进去"，而"改个名字"对任何能解包产物的人来说毫无区别。

API 基址最终落在构建常量里，而不是散在请求代码中：

```ts
// config/index.ts（节选）：构建常量、源码目录与产物路径集中在这里。
import { defineConfig } from "@tarojs/cli";
export default defineConfig({
  defineConstants: {
    __API_BASE__: JSON.stringify(
      process.env.TARO_APP_API_BASE || "https://api-befull.kao9.com/api/v1",
    ),
  },
  designWidth: 750,
  sourceRoot: "src",
  outputRoot: "dist",
  framework: "react",
  compiler: "webpack5",
  plugins: ["@tarojs/plugin-platform-weapp"],
});
```

**这三个路径参数（sourceRoot / outputRoot / miniprogramRoot）必须和开发工具里的项目配置对上。** 而它们分散在两个文件里 —— `config/index.ts` 定义 `outputRoot: "dist"`，`project.config.json` 定义 `miniprogramRoot: "dist/"`。**两处各写一半，改了一处忘了另一处，工具就会说"找不到页面"。**

开发工具里还要选择实际 AppID。本轮演示按约定关闭域名校验，**但这是一个显式测试条件，应写进验收记录**，不是隐藏在个人工具设置里的"大家都懂"。

## 三个真实踩过的坑，都属于"看起来没问题"

工程搭建这一段我记了三个坑，形态都很典型 —— **单个看都像是我犯了低级错误，但它们都指向同一个原因：某个默认值恰好和我的环境一致。**

**第一个：图标全部空白。** 代码里引用了 `assets/icons/home-light.png`，文件也确实在 `src/assets/icons/` 里，TypeScript 通过、构建成功。但工具打开后 Tab 是空的。

原因在配置里那句 `copy`：

```ts
// config/index.ts（节选）：源码资源必须显式复制到产物。
copy: { patterns: [{ from: "src/assets", to: "dist/assets" }] },
```

**Taro 不会默认把静态资源搬进产物。** 而"文件在 `src` 里"这件事给了我一种安全感 —— 我以为构建会把所有需要的东西带过去。实际不会。

**第二个：本地开发时页面显示正常，导入工具后请求地址变了。** 原因是我用了 `process.env.TARO_APP_API_BASE || "线上地址"`，而 watch 构建那次的 shell 里恰好有这个环境变量指向本地后端。

于是本地跑得通、构建产物指向线上。**而我是在导入工具之后才发现的** —— 因为我在开发工具里一直用的是构建产物，不是 watch 的那份。

**第三个：类型检查一直通过，但页面渲染是空的。** 这个最误导人。原因是 `pages` 数组里有一个路径写错了大小写，而 Taro 的路径解析在某些平台上是大小写不敏感的 —— **于是构建成功、类型正确、只有实际渲染时才出问题。**

这三个坑的共同点是：**它们都不能靠"编译通过"排除。** 编译只保证代码语法和类型成立，不保证资源被复制、不保证环境变量一致、不保证平台大小写规则和你想的一样。

所以现在我在这三个位置各加了一条**可检查的东西** —— 资源复制写进配置、环境变量默认值写死加注释、页面路径跟 `app.config.ts` 逐条对照。它们不防止我犯错，但**会让错误在更早的地方停下来**。

## 构建成功后，继续检查它到底包含什么

我们记录的产物包含 14 个页面、4 个原生 Tab。

**保留在源码中的旧实验页没有注册到 `app.config.ts`，不能因为文件存在就算成用户可用页面。** 这类"僵尸页面"是最容易造成文档失真的 —— 路由清单和实际可用页面从此对不上。

构建检查还确认临时本地测试夹具没有进入交付包，生产 API 地址已经恢复。**这比只看终端最后一句 success 更接近真正的工程交付。**

证据中的 `artifactBytes` 是 758869：对生成文件大小求和得到的约 759 KB。**不要拿它和平台上传包大小直接等号，更不要据此推导首屏耗时** —— 压缩、分包、运行时加载与设备条件是不同维度。

| 检查 | 能证明什么 | 不能证明什么 |
|---|---|---|
| TypeScript 通过 | 当前类型约束成立 | 运行时服务一定返回正确结构 |
| weapp 构建通过 | 当前目标能生成产物 | 所有原生交互正确 |
| 页面与基址扫描 | 路由清单和环境符合交付目标 | 真机网络和审核已通过 |
| 开发工具打开 | 工具可以加载当前工程 | 正式发布条件已齐备 |

**这些检查不是重复劳动。它们分别保护不同边界，混成一句"验证通过"，后续协作就不知道该相信到哪一层。**

### 一次干净重建，比保存成功截图更有价值

开发工具打开后，最容易保留的是页面截图。但**截图不会告诉下一位协作者，产物是不是来自当前源码，是否残留了 watch 构建中的旧文件，或者配置是否仍指向临时服务。**

更可靠的复现演练是：确认可再生成的前提下清理输出，按锁文件安装 → 类型检查 → 测试 → 生产构建的顺序重跑，再导入新产物。

遇到问题时，**保留完整错误与版本比反复点击重新编译更有效**：

| 失败现象 | 先看什么 | 不要做什么 |
|---|---|---|
| 依赖解析失败 | 安装日志 | 改业务代码 |
| 编译失败 | 源码与插件版本 | 重装依赖 |
| 运行时请求失败 | API 地址与接口响应 | 改 Taro 版本 |

**不同层的失败不要用同一种"重装试试"处理。** 而错误信息要连版本一起保留 —— 只截图一个红色报错，下一位协作者没法判断它属于哪套依赖。

工程问题最怕的不是失败，**而是失败没有被记录成可重复的最小条件。**

### AppID 配好后，也可能仍然登录失败

客户端 AppID 与后端 AppID、AppSecret 必须属于对应项目。**项目导入成功只说明工具认得它，不说明后端已经配置了匹配凭据。**

当线上微信登录返回 500，客户端会提供暂不可用与密码登录兜底文案。**但这个文案只是帮助用户退出死胡同，不能精确诊断是配置、平台换码还是 Workers 执行失败。**

这就是工程记录应分层的原因：

```text
Taro 构建 → 项目导入 → code 获取 → 后端换码 → 用户创建 → 会话返回
   ①           ②            ③           ④          ⑤          ⑥
```

**每一段都可以单独成功或失败。** 把它们分开，问题才能收敛到负责的模块 —— 而不是像那次一样，围着 Taro 版本重装了三轮。

### 仓库交付还包括"没有什么"

临时测试夹具不在交付包，真实秘密不在源码，生成文件不参与正常业务编辑 —— **这些都是可检查的交付要求**。但检查时**不能把秘密值打印出来当证据**，验证变量名称与注入方式即可。

如果要在 CI 重建，建议先复用相同脚本，再补工作目录、运行时版本、锁文件策略和产物检查。**不要在 CI 发明另一组编译命令**，否则本地通过与流水线通过会慢慢变成两种工程。

现在尚未提供一个完成过的跨机器构建矩阵。**我们留下了版本与检查记录，后续协作者可以据此复现，而不是把本机一次成功当成所有环境都被验证。**

## 工程文档应帮助下一次失败定位

假如读者安装失败，先检查 Node、pnpm 和锁文件；开发工具找不到页面，先检查输出路径和注册清单；微信登录失败，再看后端 Secret 与真实换码链路。

这样分层，**避免一个登录 500 被当成 Taro 版本问题来回重装**。后面确实发生过 Workers 运行时差异，那件事已在 [Node 测试通过，Workers 登录为什么仍然 500]({{LINK:M1-34}}) 中单独复盘。

工程搭好之后，进入 [多端代码组织]({{LINK:M5-06}})。

回过头看，这次工程落地没有用到什么高深工具，无非是把版本、配置和证据三样东西各就各位。**但正是这三样，决定了第二位读者能不能在一小时内把一个陌生工程跑起来。**
