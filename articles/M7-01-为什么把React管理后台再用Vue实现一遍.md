# 成为全栈·Vue 管理后台篇·为什么把 React 管理后台再用 Vue 实现一遍

> 重写一个已经能用的管理后台，听起来像是在重复劳动。真正要回答的问题却是：换了框架之后，怎样证明业务行为仍然一致？

> 本文代码快照：Vue 后台提交 `d3ee41a`；React 对照提交 `d72df53`；API 契约 `1.12.0`。后续如代码继续演进，以文章引用的提交和契约版本为准。

## 前言：这次不是“把 JSX 翻译成模板”

如果你已经跟着项目做过 React 管理后台，再看到一个 Vue 版本，第一反应很可能是：“页面差不多，找个自动化工具把 JSX 改成 Vue 模板，不就行了吗？”

我一开始也觉得，这个项目的业务已经存在，重写时最大的工作无非是换语法、换组件库。真正开始梳理以后才发现，最难的部分不是 `<div>` 要不要变成 `<template>`，而是怎样让两套实现继续遵守同一套产品规则：member 能进入个人中心，却不能进入后台；编辑文章时可以传图片，但“文件选择成功”不代表“图片上传成功”；接口返回 `totalPages: 9`，表格也必须真的能翻到第 9 页。

这些规则散落在路由、请求层、表单、查询缓存和后端契约里。若只照着页面截图重做，很容易得到一个“长得像后台、行为却不完全一样”的项目。于是 M7 的目标不是证明 Vue 比 React 好，也不是再造一套产品，而是把同一个管理后台放进第二种技术实现里，用相同的 API 契约和用户行为做一次工程对照。

这篇先把重写的理由、边界和验收基线说清楚。明确这些，后面讨论 Composition API、Pinia、请求刷新和页面实现时，才不会把“迁移”误写成“另起炉灶”。

## 为什么已经有 React 版，还要再做 Vue 版？

这不是因为 React 项目不能维护，也不是因为 Vue 有什么天然优势。原来的 React 后台已经承担了真实的内容管理工作，Vue 项目承担的是另一种学习目标：在产品规则和服务端契约保持稳定的情况下，用不同的前端运行模型实现相同的工作流。

这里有三层收获。

第一，框架差异终于有了共同参照。单独学习 Vue 的 `ref`，我们可以背 API；把它放进一张需要筛选、翻页、加载和刷新数据的表格，再与 React 的 state 和渲染过程对照，才会遇到真实的依赖追踪、状态边界和异步更新问题。

第二，可以把“相同业务”与“相同代码”区分开。两个后台都要登录、审核文章、上传图片、管理用户，但不要求它们使用同样的组件或目录。React 版使用 React 生态，Vue 版使用 Vue SFC、Vue Router、Pinia、Vue Query 和 Naive UI；可替换的是实现手段，不能随手替换的是用户可观察到的业务规则。

第三，重写过程能暴露迁移中的盲区。比如，接口文档里已经有 `total`，而列表却不能翻页。问题不在后端少返回了数据，而在前端表格没有按服务端分页模式完整接线。这个缺陷正好说明：接口成功、页面出现数据、用户能完成操作，是三种不同的验收结果。

因此，M7 不是两套后台的竞赛，而是一场受约束的对照实验。我们不预先宣布赢家，先让它们面对相同的契约和工作任务，再记录真实差异。

## 重写的基线：哪些东西必须保持稳定？

本项目开始 M7 时，已经有一套冻结的 API 契约和完整的 React 管理后台。两者分别承担不同角色：契约说明客户端可以依赖什么；React 代码说明现有产品实际怎样工作。Vue 实现需要同时参考它们，遇到冲突时要先查明依据，不能在页面里自行发明第三套规则。

| 对照项 | React 管理后台 | Vue 管理后台 | 重写时的约束 |
|---|---|---|---|
| 项目目录 | `manage-frontend/` | `manage-frontend-vue/` | 新旧工程并存，Vue 不覆盖 React 文件 |
| UI 与路由 | React 组件体系、React Router | Naive UI、Vue Router | 组件可以不同，访问结果和业务动作要一致 |
| 客户端状态 | Zustand 等 React 状态方案 | Pinia | 都不能把服务端列表复制成另一份事实源 |
| 服务端数据 | TanStack Query React 适配 | `@tanstack/vue-query` | 缓存和失效行为需要按 Vue 版本重新接线 |
| API 契约 | OpenAPI 1.12.0 | 同一份 OpenAPI 1.12.0 | 不为 Vue 单独改路径、字段、状态或权限 |
| 后台角色 | member / editor / admin | member / editor / admin | 菜单显隐与直接访问路由使用同一能力边界 |

需要强调的是，表格中的版本和工具是这次工程的实现快照，不是推荐所有项目无条件照抄的“最佳组合”。例如，M7 使用 Vue 3.5.43、Vite 8.3.4、Naive UI 2.45.3；依赖的精确解析版本由锁文件固定。后续文章讨论这些选择时，也会说明选择依据和适用范围。

## “功能相同”不等于“每一行代码都相同”

跨框架重写最容易踩进两个极端。

一种极端是机械翻译：React 页面有多少组件，Vue 就照着做多少组件；原来用了什么状态库，Vue 里也找一个名字相似的库塞进去。这样看起来“对齐”，实际可能把旧结构的偶然性也一起复制过来。

另一种极端是借重写机会重新设计产品：路由规则改了、字段语义改了、审核状态变了，还顺手把 API 补几个“更方便”的参数。这样可以让新实现更顺手，却再也无法公平比较两套代码，因为产品本身已经不同。

M7 采取的是第三种做法：用户行为对齐，实现细节按 Vue 的特点选择。

例如，两个版本都要在多个请求同时遇到可刷新的 401 时避免并发刷新令牌。React 和 Vue 请求层可以使用不同的模块组织方式，但共同的验收要求是：刷新过程合并、刷新成功后原请求最多重放一次、失败时清理会话。实现结构不同，安全语义不变。

再比如，两个版本都需要展示文章列表。Vue 版使用 Naive UI 的 `NDataTable`，它的分页属性和事件有自己的接法。不能因为 React 表格已经能翻页，就认为 Vue 表格也会自动得到相同行为。我们要把“服务端总数、当前页、页码更新、查询参数变化”分别接通并实际验证。

可以把这个边界记成一句话：**产品契约固定，框架方案可替换；替换方案要通过可观察的验收证明行为没有漂移。**

## 用一张验收表，代替“页面差不多做完了”

在迁移页面前，先把完成标准写成能够验证的问题，比先画一批 Vue 组件更有用。

| 验收层 | 要问的问题 | 可观察证据 |
|---|---|---|
| 契约 | Vue 是否仍请求同一条 API、发送同一字段并解析同一信封？ | 请求模块、生成类型、请求层测试与 OpenAPI 版本 |
| 身份 | 未登录、普通会员、编辑和管理员分别会到哪里？ | 会话恢复测试、路由守卫测试、菜单权限判断 |
| 业务流程 | 文章保存、审核、图片上传、评论管理是否走完闭环？ | 页面交互、成功与失败反馈、缓存刷新或最终状态 |
| 工程质量 | 改动能否通过类型、规范、测试和生产构建？ | Biome、`vue-tsc`、Vitest、`vite build` |
| 运行环境 | 本地代理与生产构建的 API 地址是否正确？ | `API_TARGET` 配置、公开 API smoke、部署回退验证 |

这张表刻意把“接口契约”和“页面功能”拆开。类型生成通过，只说明当前代码能从契约得到静态类型，不证明接口请求路径正确；构建通过，只说明生产资源可以打包，不证明用户能登录；列表首屏出现 10 条数据，也不证明用户能切换到第二页。

同样，单元测试通过也有明确边界。M7 的请求层、路由权限、状态和构建有自动化验证；公开站点设置等端点可以经代理检查响应。真实管理员账号、受保护的线上写操作、线上图片上传等环境验证，需要有相应测试环境和授权账号后才能完成。文章不能把“代码写好了”写成“线上端到端已经全部验收”。

## 重写边界：不改的和允许重做的

为了让这次对照有效，以下内容保持稳定：

- API 契约仍使用 `docs/api/openapi.v1.yaml` 中的 1.12.0，不在 Vue 页面里补字段或改变含义。
- Node 与 Go 后端不因 Vue 迁移而改动。
- 原 React 工程完整保留，继续作为业务行为和实现对照。
- 三种角色的菜单与页面权限维持现有规则，服务端授权仍是最终边界。
- 文章、评论、分类、标签、用户和个人中心的核心操作流程保持一致。

以下内容允许按 Vue 的工程特点实现：

- 单文件组件怎样拆分，组合式逻辑怎样复用。
- 使用 Pinia 保存哪些客户端状态，使用 Vue Query 管理哪些服务端数据。
- 用 Naive UI 还是自定义样式组织表格、表单和反馈。
- 主题变量、登录页布局和响应式侧栏如何落地。
- 哪些自动化测试最适合验证 Vue 模板、路由和交互。

设计细节可以变化，但变化要可解释。比如，本次 Vue 登录页和侧栏体验后来进一步对齐 React 后台的配色与响应式行为；这属于界面实现的调整，不是改变登录 API 或角色规则。文章会说明这类改动的动机和验证方法，而不是把“看起来更好看”当作唯一证据。

## 从读代码的角度看项目

如果你想自己核对文章里的判断，可以从下面几个位置开始，不必先把整个仓库通读一遍：

```text
manage-frontend-vue/src/
├── api/          # 按文章、评论、用户等业务组织的请求函数
├── config/       # 菜单、角色标签等固定配置
├── layouts/      # 管理后台与个人中心的页面外壳
├── lib/request/  # fetch 请求、信封解析、刷新与会话处理
├── pages/        # 登录、列表、编辑器、仪表盘等页面
├── router/       # 路由、懒加载与访问守卫
└── stores/       # auth 与界面偏好等客户端状态
```

这是**当前实现的目录**，不是理想架构示意图。技术方案文档曾讨论按 `features/` 划分业务域，但实际项目仍以 `api/`、`pages/`、`lib/` 等目录组织。写作时应该如实说明已落地结构，再讨论它的边界和是否需要进一步拆分，不能把方案图误当成代码现状。

可以先用这几组文件做定点对照：

| 要追踪的行为 | Vue 实现 | React 对照 |
|---|---|---|
| 文章列表与分页 | `manage-frontend-vue/src/pages/articles/ArticleListPage.vue` | `manage-frontend/src/pages/articles/ArticleListPage.tsx` |
| 文章 API | `manage-frontend-vue/src/api/articles.ts` | `manage-frontend/src/api/articles.ts` |
| 登录与当前会话 | `manage-frontend-vue/src/api/auth.ts`、`src/stores/auth.ts` | `manage-frontend/src/api/auth.ts`、`src/store/auth.ts` |
| 路由与权限 | `manage-frontend-vue/src/router/`、`src/lib/permission.ts` | `manage-frontend/src/router/`、`src/lib/permission.ts` |

沿调用方向读文章列表：页面管理筛选和页码，API 模块选择方法和路径，请求层补认证信息并解析响应，Vue Query 决定何时缓存或刷新。沿着一次交互走完整条链路，通常比先从某个组件库的 API 文档开始读，更容易发现系统里真正需要守住的规则。

## 给读者的一个小练习

打开 React 与 Vue 两个项目的文章列表，先不看样式，分别回答这些问题：

1. 当前页和筛选条件放在哪里？刷新按钮会重新请求，还是只重绘当前组件？
2. 服务端总数如何进入分页组件？翻页事件又如何影响查询参数？
3. 用户切换筛选条件后，页码会不会复位到第一页？
4. 删除文章成功后，列表缓存怎样更新？一批删除中有一项失败时，用户能不能知道是哪种结果？

如果只能回答“页面上有个分页器”，那我们还没有真正读懂它。把每个答案都追到代码和测试，你就会发现“同一产品的两种实现”不是把两个截图摆在一起，而是把每个状态变更的来源和结果摆在一起。

## 小结：M7 要证明的是可迁移，而不是可复制

Vue 管理后台的价值，不在于又多了一套页面，而在于它让我们能在产品规则不变的前提下，观察另一套前端工程如何组织组件、客户端状态、服务器缓存、路由权限和用户反馈。

所以，M7 的第一步不是急着比较 React 和 Vue 的优劣，而是锁定共同基线：同一份冻结契约、同一组角色规则、同一批用户任务和能够复现的质量门禁。接下来的文章会依次解释 Vue 工程基座、响应式运行模型、请求与会话、数据缓存和各项管理功能；遇到差异时，我们会说明它来自哪里、影响了什么、用什么证据判断。

先把尺子校准，再比较两种实现。这一步做扎实了，后面学到的就不只是 Vue API，而是如何在真实项目里做一场边界清楚、证据可靠的技术迁移。
