# 成为全栈·React 管理后台篇·站点配置页：如何组织低频但高风险的全局设置

> 站点配置改得不频繁，却会影响导航、搜索展示和所有读者。它需要比普通表单更清楚的分组、预览、基线和缓存传播。

## 前言

站点名称保存成功，设置页已经显示新值，后台侧栏却仍是旧名称。刷新几次之后它才变化。接口没有错，表单也没有错，问题是同一配置存在后台编辑缓存和公开品牌缓存，写操作只更新了前者。

全局设置的风险正来自传播范围。改昵称主要影响一个账号，改站点标题可能影响浏览器标签、导航、搜索摘要和前台页面。本篇讨论怎样让低频配置的后果可见且可控。

## 按用户理解分组，而不是按数据库字段排列

当前页面将六个字段分为：

- 站点品牌：siteName、logoUrl；
- 搜索展示：siteTitle、siteDescription、siteKeywords；
- 页脚：copyright。

这些分组对应用户能观察到的区域。若按字符串、URL、长文本分组，虽然接近 schema，却要求管理员自己推断每个字段会影响哪里。

每组卡片提供一句后果说明，字段标签使用自然语言，slug 式内部名称只留在代码中。全局配置页不是数据库控制台。

## 预览要说明自己能证明什么

搜索展示区根据输入实时预览标题和描述：

```tsx
<p>{values.siteTitle || values.siteName || '你的站点标题'}</p>
<p>{values.siteDescription || '这里将展示站点描述'}</p>
```

它能帮助发现标题过长、描述为空和信息层级问题，却不能承诺搜索引擎最终展示效果。因此界面明确写着“文字预览，实际展示由前台决定”。

若预览做得和真实搜索结果一模一样，用户反而容易误以为保存后立刻改变搜索排名。可靠的预览既要接近结果，也要说清模拟边界。

## 配置编辑同样需要基线

页面首次收到数据时回填一次，并把完整 SiteSetting 保存在 baseline ref。用户修改期间，Query 后台更新不自动覆盖表单；撤销按钮回到最近一次服务器确认值。

```ts
if (settings.data && !baseline.current) {
  baseline.current = settings.data
  form.reset(toValues(settings.data))
}
```

保存成功后，用响应重新建立 baseline 和 dirty 基线；失败时提示“修改已保留”。站点配置影响范围大，更不能在一次网络错误后清空用户输入。

保存按钮仅在 dirty 且非 busy 时启用，旁边持续显示“有未保存的修改”或“所有修改已保存”。低频表单尤其需要状态反馈，因为管理员可能不熟悉它的保存行为。

## 一次保存要更新两个缓存视角

后台设置页使用 `qk.site.adminSettings`，侧栏和品牌区域使用公开配置 `qk.site.publicSettings`。成功后：

```ts
onSuccess: (saved) => {
  baseline.current = saved
  form.reset(toValues(saved))
  queryClient.setQueryData(qk.site.adminSettings, saved)
  void queryClient.invalidateQueries({
    queryKey: qk.site.publicSettings,
  })
}
```

后台缓存与返回值一一对应，可以直接写入；公开配置可能经过字段裁剪或另一接口转换，因此选择失效后重取。这样侧栏、浏览器标题和其它消费者会重新确认。

这条传播关系属于业务，而不是 Query 自己能猜出来的依赖。新增配置消费者时，应同时审阅保存后要失效哪些 key。

## Logo 上传属于保存事务之前的异步阶段

图片上传成功只得到 URL，站点配置尚未保存。如果用户此时离开，服务器可能留下未引用附件。页面用 UploadScope 汇总上传任务，上传中禁用保存和离开；上传结束后表单进入 dirty，等待用户明确保存。

更完整的系统可以为临时附件增加过期清理。前端无法让“上传文件”和“更新配置”跨存储原子提交，因此必须承认孤儿文件边界，并由后端清理策略兜底。

## PATCH 还是整体保存，要看契约语义

当前页面一次提交完整配置对象。即使接口使用 PATCH，也不能假设遗漏字段一定保持不变；应以契约为准。`toValues` 将缺失值稳定映射为空字符串，避免受控输入在 undefined 与字符串之间切换。

全局配置若多人同时编辑，还会出现覆盖。当前后台没有版本字段或 ETag，因此只能以后写覆盖先写。高协作场景应增加 updatedAt/版本条件，冲突时展示差异，而不是依靠前端 dirty 阻止另一个浏览器。

## 保存前是否需要二次确认

并非所有设置都要弹确认框。修改描述和关键词可以通过撤销、dirty 状态与保存反馈控制；每次都确认会让用户形成无脑点击习惯。域名、认证方式、全站关闭评论等可能导致访问中断的配置，才值得单独确认并要求说明后果。

当前六个字段没有不可逆迁移，因此页面使用明确的“保存设置”按钮而不增加弹窗。Logo 上传期间禁用提交，实际保存失败保留输入。风险控制要与后果匹配，不能用确认框数量假装安全。

## 回滚不能只靠浏览器后退

“撤销未保存修改”只回到本次加载或最近保存的 baseline。一旦保存成功，旧配置就不在浏览器里了。真正的配置回滚需要后端保存版本、操作者、时间和变更内容，再提供选择历史版本恢复的命令。

当前系统尚未实现配置历史，因此文章不会把表单撤销称为回滚。对于品牌文字这类可快速再次修改的配置，这个边界可以接受；若以后加入支付、邮件或安全开关，就应先补审计和版本，而不是只扩展同一张表单。

## 空值也要定义业务含义

页面把缺失字段映射为空字符串，保证输入受控。但提交空字符串究竟表示“清空配置”还是“保持旧值”，必须由契约规定。当前页面提交完整 Values，因此空值表达清空。

Logo 字段更明显：上传新图得到 URL，清空则传空字符串；如果后端希望使用 null，需要在映射层明确转换。含糊处理会出现用户删除 Logo、刷新后旧图又回来的问题。

## 配置发布可能需要缓存之外的传播

Query 失效只更新当前 SPA。真实前台可能有 CDN、服务端渲染缓存或独立部署，它们是否立即读取新配置取决于系统架构。后台提示“保存成功”只能保证配置接口接受，不能承诺所有外部缓存已经刷新。

将来若加入 CDN purge 或配置事件，保存流程应展示传播状态：数据库已保存、缓存刷新中、部分节点失败。当前项目没有这层基础设施，因此预览与提示都保持克制。

## 权限与审计要覆盖全局影响

站点设置只向 `canManageSiteSettings` 成立的 admin 开放，菜单隐藏和路由守卫使用同一能力。editor 即使知道地址也会进入 403，最终接口仍由后端再次拒绝。

权限只解决谁能改，审计还要回答谁在什么时候改了什么。当前页面没有配置变更历史，出现错误只能依靠服务端日志排查。随着设置项风险提高，后端应记录旧值、新值、操作者和 requestId；前端可以在提交前展示差异，而不是让审核者比较整张表单。

敏感配置还不应在普通查询中完整回显。例如第三方密钥应只显示“已配置”，更新时提交新值，不能像站点描述一样进入 Query 缓存。全局设置页面可以共用布局，却必须按数据敏感度拆分读写模型。

## 小结

站点配置页以影响区域分组，用有限预览说明结果，以服务器响应维护表单基线，并显式同步后台和公开缓存。上传、未保存保护与冲突边界也必须纳入设计。

各位看官，全局设置不能只验证“接口返回 200”。保存后请沿着导航、浏览器标题、前台展示和刷新恢复逐项检查，确认变化真正传播到了所有观察者。
