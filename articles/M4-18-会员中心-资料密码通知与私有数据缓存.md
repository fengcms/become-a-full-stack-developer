# 成为全栈·Flutter App 篇·会员中心：资料、密码、通知与私有数据缓存

会员中心最难发现的问题通常不是某个页面打不开，而是账号 A 的通知、收藏或头像在账号 B 登录后短暂闪现。只清一个 Provider 并不能自动清理所有私有状态。

这篇从 `AppSession.logout()`、Repository 的私有缓存和未读数 Provider 出发，梳理退出、账号切换与通知更新的完整数据流。

{{IMG:M4-18-封面}}

## 会员入口只是导航，不是授权判断

“我的”页面聚合资料卡、投稿、收藏、点赞记录、阅读历史、通知和设置。导航入口根据登录状态呈现，但 API 仍需服务端认证与资源归属检查。深链接到私有页面时也要走登录回跳，不能靠把入口藏起来当作权限控制。

## 资料与密码是不同的写流程

昵称、头像等资料修改可以显示保存中、成功和失败；修改密码通常会使凭据失效或触发重新认证，应按接口契约处理会话更新。表单失败要保留输入，敏感字段不能写日志或本机普通缓存。

{{IMG:M4-18-会员数据边界}}

## 通知列表和未读数要保持一致

通知中心有未读统计、列表刷新、标记已读等不同操作。标记已读可以乐观更新，但失败必须还原；未读数不能仅因页面打开就永久减一。当前 App 已接入通知展示和已读状态，服务端通知产生机制不由客户端补造。

## 私有缓存只在当前会话短期复用

项目对会员展示数据采用 API 环境、账号 ID、会话 epoch 的完整隔离，只保留内存，不落公开磁盘缓存。退出清理私有状态；资料编辑、稿件编辑和私有预览要求实时读取。公共文章则可继续使用公开缓存。

```text
public article → bounded memory + disk
member overview → account/session scoped memory
private preview/edit → live request
```

如果私有缓存 key 只包含文章 ID，不同用户访问同一 ID 就可能相互污染；若退出时清空全局所有缓存，则又会不必要地清除公开阅读内容。

## 私有资源 key 至少包含身份上下文

缓存 key 设计可以把数据隔离写成代码约束：

```text
privateKey = apiOrigin + userId + sessionEpoch + resource + query
```

这样测试环境和线上环境即使用户 ID 相同，也不共享会员数据；同一账号重新登录后，旧会话的在途结果也不能命中新会话缓存。退出时先提升 epoch，再清理私有条目，避免清理期间又有旧请求回填。

对资料保存、密码修改和通知已读，分别定义成功后的失效集合。密码修改的会话行为服从后端响应；通知失败则还原乐观已读。共用一个“刷新会员中心”动作很难覆盖每类资源的正确更新语义。

## 退出顺序需要先隔离，再做网络清理

退出时登出 API 可能失败或网络不可用，但本地用户仍应能够离开当前账号。项目在 finally 路径执行 `api.clear()`，会话 epoch 先递增、access/user 清空、触发私有缓存清理，然后持久删除 refresh token。logout 请求异常不能阻止本机清会话。

这不代表后台注销必然成功：服务端 token 可能仍有一段时间可用，客户端不再保存它并不等于服务端撤销完成。UI 需反馈适当状态，但不能为等待网络无限阻塞本地退出。安全敏感场景可由服务端 token family/revocation 策略进一步降低风险。

## 通知和私有缓存的刷新触发点

通知有较短的缓存新鲜窗口，未读数单独通过 FutureProvider 读取，并监听用户 ID 与 epoch。用户点进通知页时可刷新列表，标记已读后通知列表和未读计数需一起失效；如果只改通知卡片本地文字，底部徽标仍可能展示旧值。

会员 overview 可以短时从当前身份内存缓存返回，切换账号立即重建私有数据边界；没有通知推送服务时，别把未读徽标描述成实时同步。前台恢复和主动刷新是客户端发现服务端变化的当前手段。

## 账号切换测试要用两个真实身份

单测把 session epoch 从 1 改成 2，可以证明缓存 key 不同；集成测试用会员 A 加载收藏，再退出并登录会员 B，才可以验证页面路由、未读徽标、私有文章列表和头像是否一起切换。只检查 MemberPage 的昵称不足以证明所有子资源都已清理。

另外要验证启动恢复失败的状态：refresh 过期时不展示上次保留的会员页数据，公开首页仍可用；网络暂时不可达与凭据已失效也需要不同反馈策略。安全边界与可用体验要同时验收。


## 贴着工程代码读实现

下面这段节选自 `flutter-app/lib/features/data/member_overview.dart 第 11–74 行`（保留原始实现；为突出主线省略了文件其余部分）。读代码时可以顺着调用链确认：A 用户浏览会员页后立即登出并登录 B，观察缓存 key 与页面状态。我会继续追踪它的返回值和副作用，直到页面状态稳定下来。

```dart
class MemberOverview {
  MemberOverview({
    required this.cache,
    required this.key,
    required this.read,
    required this.trackKey,
    required this.forbidden,
  });
  final DataCache cache;
  final String Function(String, Map<String, dynamic>, {bool private}) key;
  final Future<dynamic> Function(String, {Map<String, dynamic> query}) read;
  final void Function(String) trackKey;
  final bool Function(Object) forbidden;
  // 概览只驻留内存，键包含账号与会话代际。
  Future<Map<String, dynamic>> load({bool forced = false}) async {
    final k = key(CacheKeys.overview, const {}, private: true);
    trackKey(k);
    return jsonMap(
      await cache.get(
        k,
        const CachePolicy(Duration(minutes: 1), Duration(minutes: 5)),
        () async {
          final results = Map.fromEntries(
            await Future.wait(
              {
                'favorites': Endpoints.meFavorites,
                'history': Endpoints.meHistory,
                'articles': Endpoints.meArticles,
              }.entries.map(
                (entry) async => MapEntry(
                  entry.key,
                  await read(entry.value, query: {'page': 1, 'pageSize': 3}),
                ),
              ),
            ),
          );
          // 点赞接口没有总数，必须逐页扫描，不能把首屏长度当成累计数量。
          int likes = 0, page = 1;
          while (true) {
            final batch = await read(
              Endpoints.meLikes,
              query: {'page': page, 'pageSize': 100},
            ) as List;
            likes += batch.length;
            if (batch.length < 100) break;
            page++;
          }
          return CacheReply({
            'counts': {
              'favorites': results['favorites']['pagination']['total'],
              'likes': likes,
              'history': results['history']['pagination']['total'],
              'articles': results['articles']['pagination']['total'],
            },
            'history': results['history']['list'],
          });
        },
        force: forced,
        tags: {'private', 'overview'},
        forbidden: forbidden,
      ),
    );
  }
}
```

## 把容易出错的路径走一遍

我会用这个场景做一次可复现排查：**退出账号后另一个账号短暂看到前一账号会员缓存**。先A 用户浏览会员页后立即登出并登录 B，观察缓存 key 与页面状态；如果把问题定位在“按 endpoint 共用”，修正方向是“私有键纳入 userId/epoch，账号边界重置 Provider 和私有缓存”。最后再验证正常路径没有退化，并把边界条件留在自动化检查里。

| 方案比较 | 简化做法 | 当前实现/推荐做法 |
|---|---|---|
| 本文核心选择 | 按 endpoint 共用 | 按身份隔离 |
| 错误处理 | 失败后清空或静默忽略 | 保留可恢复状态，给出明确反馈 |
| 验证方式 | 只检查成功结果 | 注入边界条件并检查回归 |

| 排错步骤 | 要观察什么 | 通过条件 |
|---|---|---|
| 复现 | 退出账号后另一个账号短暂看到前一账号会员缓存 | 可以稳定触发或明确构造该输入 |
| 定位 | A 用户浏览会员页后立即登出并登录 B，观察缓存 key 与页面状态 | 找到责任层和状态归属 |
| 修正 | 私有键纳入 userId/epoch，账号边界重置 Provider 和私有缓存 | 失败不污染后续页面或账号 |

## 小结

会员中心围绕身份和私有数据组织页面，但权限由服务端最终裁决。资料、密码和通知有各自写语义；私有展示缓存必须包含完整身份维度并限于会话内存，退出清私有状态而保留可公开复用的文章。
