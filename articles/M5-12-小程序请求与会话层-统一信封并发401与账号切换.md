# 成为全栈·Taro 小程序篇·小程序请求与会话层：统一信封、并发 401 与账号切换

> 自动刷新令牌只能解决过期，不能解决换人。请求层必须同时知道“令牌是否还能用”和“响应还属于谁”。

## 前言：三个请求一起过期，会发生什么

会员中心可能同时读取资料、收藏和未读通知。如果访问令牌过期，三个请求都收到 401，各自刷新就会争抢同一个刷新令牌。后端采用刷新旋转时，这种竞争会把本来有效的会话弄乱。

前面的 Web 和 APP 已经处理过类似问题。小程序可以继承判断，却不能照搬它们的存储 API。当前会话存入微信本地存储，请求由 `Taro.request` 执行。

这篇围绕两个问题展开：并发 401 如何共享刷新，账号切换后旧响应如何失去写入资格。两者少一个，都不能算请求层完成。

## 先把 HTTP 和业务错误放到同一出口

后端响应使用 `code`、`message`、`data` 的统一信封。最底层请求函数同时检查 HTTP 状态和业务 code，并把它们收敛成一个错误类型：

```ts
// src/core/api.ts：raw 是唯一的网络出口，token 由调用方决定带不带。
async function raw<T>(path: string, method: Method, data: unknown, token: string): Promise<T> {
  const r = await Taro.request<Envelope<T>>({
    url: API + path,
    method,
    data: data as object,
    timeout: 20000,
    header: {
      "Content-Type": "application/json",
      ...(token ? { Authorization: `Bearer ${token}` } : {}),
    },
  });
  if (r.statusCode >= 400 || r.data?.code !== 0)
    throw new ApiError(r.statusCode, r.data?.code || 5000, r.data?.message || "网络请求失败");
  return r.data.data;
}
```

页面因此消费业务数据，不必每次再拆信封。`ApiError` 保留 HTTP 状态与业务码，方便决定是否可以刷新；普通网络异常仍会抛出，不能伪装成某个认证业务码。

| 字段 | 含义 | 请求层如何使用 |
|---|---|---|
| `code` | 业务码，0 为成功 | 非 0 视为业务失败 |
| `message` | 可直接展示的文案 | 作为 `ApiError` 的 message |
| `data` | 业务数据 | 成功时原样返回页面 |
| HTTP 状态 | 传输与协议层结果 | 与 `code` 一起判失败 |

超时配置为 20 秒，是当前请求设置，不是整个应用响应时间的承诺。网络很慢时，页面仍应提供等待和错误状态，不能把一个较长超时当成改善体验的办法。

## 公共请求主动不带会员身份

公开内容读取使用 `authenticated=false`，只有私有数据读取才带 Bearer。这样，公共文章缓存不会因为当前会员登录而暗中变成个人响应。

这条规则还减少另一种意外：公共文章接口正常，会员令牌却过期。如果每个公开请求都顺手带令牌，阅读首页可能无缘无故卷入认证失败。

当前 read 根据 privateData 决定身份与缓存区域，缓存键里带上账号与代次，公开内容则统一归到 public：

```ts
// src/core/api.ts：身份决定读哪个缓存区，也决定请求带不带令牌。
export function read<T>(path: string, force = false, privateData = false, ttl = 60000) {
  const identity = privateData ? `${session()?.user.id || "guest"}:${sessionEpoch()}` : "public";
  return (privateData ? privateCache : cache).read(
    `${API}:${identity}:${path}`,
    () => api<T>(path, "GET", undefined, privateData),
    ttl,
    force,
  );
}
```

页面必须正确标注：通知、个人收藏和投稿预览是私有内容，公开文章、分类和标签是公共内容。底层不会自动猜测一个端点应该属于谁。

公开内容归到 public 缓存区，意味着游客和会员读到的首页、分类、标签是同一份。这既省请求，也避免“登录后首页突然变样”的错觉。反过来，收藏、通知这类私有数据各自成键，账号 A 的缓存不会出现在账号 B 的界面里。

### 那次 bug 为什么在开发工具里看不出来

值得记一句：**这个 bug 在开发工具里几乎复现不了。**

原因是开发工具的调试体验太好了 —— 网络面板能看每一次请求，能调网络延迟，于是我可以慢慢看着时序发生。**而我第一次遇到它是在真机上，三个请求并行返回，闪屏只持续了不到两秒。**

那两秒里发生了什么，我完全没看清。我只看到了结果：**用户被登出了。**

所以后来我写并发相关代码时有个习惯：**先用 `Promise.all` 写一个能稳定复现的测试，再写实现。** 那个 bug 如果当时有并发测试，第一次跑就会红 —— 因为断言"只发出一次刷新请求"会直接失败。

**能稳定复现的 bug 不难修，难的是知道它存在。** 而"能不能写出那个测试"决定了后者。


## 刷新只有一个在途 Promise

如果不共享，三个同时 401 的请求会同时发起刷新。后端启用刷新令牌旋转后，第一个刷新会让旧 refreshToken 失效，另外两个拿着已经作废的令牌去换，会把一次普通的过期扩大成“会话被踢”。共享一个在途 Promise，正是为了避免这种自伤。

`refreshFlight` 保存当前刷新任务。后来的调用复用它，结束后仅由同一任务清理自己：

```ts
// src/core/api.ts：刷新飞行任务全程只允许一个。
export async function refreshSession() {
  if (refreshFlight) return refreshFlight;
  const old = session(),
    generation = sessionEpoch();
  if (!old) throw new ApiError(401, 1004, "请先登录");
  const flight = raw<Auth>("/auth/refresh", "POST", { refreshToken: old.refreshToken }, "")
    .then((auth) => {
      if (sessionEpoch() !== generation) throw new Error("账号已切换，请重新操作");
      setSession(auth, false);
    })
    .catch((error) => {
      if (sessionEpoch() === generation && error instanceof ApiError && error.status === 401)
        setSession(null);
      throw error;
    })
    .finally(() => {
      if (refreshFlight === flight) refreshFlight = null;
    });
  refreshFlight = flight;
  return flight;
}
```

`setSession(auth, false)` 表示这是同一个身份更新令牌，不是换了一个账号。因此不会因为刷新旋转清空全部私人页面状态，也不会改变会话代次。

如果刷新明确返回 401，并且代次仍匹配，才清除当前会话。临时网络失败不等于身份被撤销，不能把每次超时都变成退出登录。

## 晚到的 401，也别再刷新一次

还有一种容易漏掉的情况：A、B 同时发出，A 先刷新成功，B 的旧 401 才回来。此时共享 Promise 可能已经清空了。

请求层会比较当前 accessToken 与发送时 token。只有仍然相同，才需要发起刷新；如果已经变了，说明其他请求完成了刷新，直接使用新 token 重放一次即可。

重放调用 raw，而不是递归调用 api。这样，重放再返回 401 就结束，不会陷入无限刷新。认证端点本身也被排除，避免刷新失败再次要求刷新。

```ts
// src/core/api.ts：只有认证失败且身份未变，才刷新后重放一次。
if (
  !(error instanceof ApiError) ||
  error.status !== 401 ||
  !token ||
  path.startsWith("/auth/") ||
  sessionEpoch() !== generation
)
  throw error;
if (session()?.accessToken === token) await refreshSession();
if (sessionEpoch() !== generation) throw new Error("账号已切换，请重新操作");
value = await raw<T>(path, method, data, session()?.accessToken || "");
```

这里的写请求重放有明确前提：认证 401 表示业务尚未执行。普通网络异常和 500 不自动重试写入，因为服务端可能已完成创建、只是响应没回来。投稿的“不确定创建”正是这个边界的具体应用。

| 失败类型 | 含义 | 是否自动重放 |
|---|---|---|
| 401（认证拒绝） | 业务尚未执行 | 刷新后重放一次 |
| 403（无权限） | 换令牌也不会通过 | 否 |
| 网络超时 | 无法证明是否已写入 | 否（尤其写请求） |
| 500（服务端错误） | 可能已完成，只是响应失败 | 否 |

## 令牌更新和身份变化不是一回事

会话模块维护 epoch。登录、退出和账号变化递增它；同身份令牌刷新保留它。每个认证请求捕获发送时的 epoch，返回时再次检查。

```ts
// src/core/session.ts：换人才递增 epoch，并清空私有缓存。
export function setSession(value: Auth | null, identityChange = true) {
  current = value;
  if (identityChange) {
    epoch++;
    privateCache.clear();
  }
  // …持久化与通知订阅者
}
```

于是，会员 A 发起读取，随后退出并登录 B，A 的慢响应即使 HTTP 200，也不会作为成功数据交给当前私有界面。

缓存与页面还分别有版本和请求序号保护。这不是重复：请求层阻止跨身份结果，缓存层阻止失效后回填，页面层阻止旧筛选覆盖新筛选。三层检查各自守住自己的写入点。

| 层次 | 拦截什么 | 依据 |
|---|---|---|
| 请求层 | 跨身份的响应 | epoch 与发送时不一致 |
| 缓存层 | 失效后回填 | revision 版本变化 |
| 页面层 | 旧筛选覆盖新筛选 | 请求序号 serial |

### 一个时序样本怎样检查代次保护

A 会员开始读取资料，测试暂停响应；退出后登录 B，递增 epoch；最后释放 A 的响应。正确结果不是“请求没成功”，而是成功响应不能作为当前身份结果返回。

缓存层随后还要检查版本，页面层检查自己的读取序号。测试可以分别证明这些写入点，避免一条大测试因为某个上层挡住了错误，就误以为所有底层保护都有效。

刷新也可以使用类似方法：开始刷新后切换身份，再放回旧 Auth。旧结果不能覆盖 B 的令牌，也不能清除 B 的会话。错误处理时的代次判断和成功处理一样重要。

有一个仍需知道的实现边界：当前刷新飞行任务是全局单个 Promise，账号切换时不会主动取消底层网络任务。旧刷新结果会被代次拒绝，但新操作可能先遇到这次被拒绝的共享任务。它保护数据归属，不保证切换期间每次操作都无感成功。


## 把失败按“能不能重放”重新分类

请求层最容易被过度封装的是自动重试。GET 超时、创建文章超时、认证 401 和业务 403，看起来都叫失败，实际含义不同。

401 在这里允许刷新后重放一次，是因为认证层拒绝发生在业务执行之前；403 表示当前身份没有权限，换令牌不应该反复尝试；网络超时则无法证明服务端是否已经完成写入。若把这些都写成重试三次，客户端会主动制造重复动作。

把失败先分类、再决定动作，是请求层最值得保留的一条纪律：能否重放取决于“服务端是否可能已经执行”，而不是“用户是否希望它成功”。

当前代码只为符合条件的 401 重放，不为普通错误自动重试。对于创建不确定的稿件，编辑器会保留本机文本并要求先检查“我的文章”。这看起来没有自动重试顺滑，却比重复创建一批稿件更可控。

### 日志保留过程，不保留凭据

排查并发问题需要知道请求阶段、HTTP 状态和业务码，但不需要输出 accessToken、refreshToken、微信 code 或完整用户响应。客户端临时日志同样可能进入截图与提交。

如果要增加诊断，可以用操作名称和匿名关联标记记录“开始刷新、复用任务、拒绝旧代次、重放失败”。关联标记本身也不应由令牌截取。这份原则来自真实线上换码排障的要求，不能等到上线再补。

最后，统一请求函数只是错误分类入口，不会自动让页面具备正确文案。认证页、列表和编辑器面对相同错误，用户下一步可能不同：改输入、重试读取、检查已创建稿件。请求层提供事实，页面负责把它转成合理动作。


### 验证刷新时，观察令牌而不打印令牌

并发测试用受控旧值与新值区分请求阶段，实际诊断则记录是否复用刷新、是否重放和是否拒绝旧代次即可。不要把测试里的示例 token 输出习惯直接带到真实环境。身份竞态可以被定位，同时让凭据始终留在必要的执行边界内。

## 存储与上传，别被统一请求名掩盖

当前 Auth 包括 accessToken 和 refreshToken，整体保存到平台本地存储，键带 API 基址。恢复时做基本形状检查：

```ts
// src/core/session.ts：恢复时做形状检查，缺字段就当游客启动。
export function restoreSession() {
  if (restored) return;
  restored = true;
  try {
    const saved = Taro.getStorageSync(key);
    if (
      saved?.user?.id &&
      typeof saved.refreshToken === "string" &&
      typeof saved.accessToken === "string"
    )
      current = saved;
  } catch {
    /* 无缓存以游客启动 */
  }
}
```

这不是 HttpOnly Cookie，也不是硬件加密安全存储；同一端的日志和存储边界应单独审视。

图片上传走 `uploadFile`，没有接入这套自动 401 刷新重放。它在选择前后各查一次账号：

```ts
// src/core/api.ts：上传是独立路径，代次变化即中止。
const generation = sessionEpoch();
const choice = await Taro.chooseMedia({ count: 1, mediaType: ["image"], sizeType: ["compressed"] });
if (sessionEpoch() !== generation) throw new Error("账号已切换");
// …校验大小后调用 Taro.uploadFile，再查一次代次
```

而写操作成功后会按范围清理缓存，这是它和只读请求分开处理的一处：

```ts
// src/core/api.ts：写请求结束后按范围失效缓存（/view 除外）。
if (method !== "GET" && !path.startsWith("/auth/") && !path.endsWith("/view")) {
  privateCache.clear();
  if (!path.startsWith("/me/")) cache.clear();
}
```

但认证过期时上传仍可能失败，需要用户重试。文章必须让这个差别可见——统一请求名不等于统一能力，自动刷新服务的是 `api` 这条路径，而不是整个客户端。

已有逻辑测试覆盖关键会话竞态，真实本地后端验证密码登录、账号隔离和退出。线上微信登录验证的是另一条入口。三类证据分别回答不同问题，彼此不能替代，在 [质量验证]({{LINK:M5-24}}) 中汇总。
