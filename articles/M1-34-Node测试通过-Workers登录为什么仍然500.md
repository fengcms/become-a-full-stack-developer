# 成为全栈·Node 后端篇·Node 测试通过，Workers 登录为什么仍然 500

微信登录代码写完，本地测试全绿。然后我把 AppID 和 AppSecret 上传到 Cloudflare——**工具明确显示上传成功**，密钥名我也检查过一遍，没问题。

点"微信快捷登录"，500。

那一瞬间我最想做的两件事是：重置 AppSecret，然后去 ping 一下微信的接口。

**这两件都是错的，而且如果我真去做了，会浪费掉本来能找到答案的时间。**

这篇讲一个只改了 3 行的 bug，是怎么穿过单测和部署检查的。

## 先说为什么不能立刻怀疑密钥

当时的判断链是这样的：

**证据一：普通文章接口正常。** 说明 Worker 在跑，数据库连着，路由正常。如果是服务整体挂了，不会只有登录这一条。

**证据二：`secret list` 能看到那两项。** 说明上传到了正确的 Worker、键名没错。

**证据三：故意用一个无效 code 去调 callback。** 同样返回 500——**而不是预期的"凭证无效"。**

第三条是关键。如果 code 无效却返回了"凭证无效"，那说明请求成功发出去了、微信返回了错误码、只是 code 是假的。而现在返回的是 500，**意味着请求大概率根本没发出去，或者响应不符合预期。**

一个无效 code 换来的 500，**把"创建会员、写数据库"这些动作暂时排除在了主要排查路径之外**——因为如果请求真的发到了微信，那一步应该先失败。

所以密钥"存在"这件事，能证明的只有"上传成功"。**它不能证明微信请求被执行过。** 这两件事之间隔着一次网络调用和一次运行时校验。

**而这次错的正是后者。**

## 错误藏得太安全，也是一种藏得太深

原来的实现是好的方向：捕获上游异常，返回统一的内部错误，不把微信的敏感字段交给客户端。

但这带来一个副作用——**日志里只有一个笼统的内部错误**，它无法区分：

- 环境变量没配
- 请求根本没发出去
- 微信拒绝了这个 code
- 微信返回了非预期格式

四种情况的处理完全不同，而它们在客户端看到的是同一个 500。

所以我加的是**受控的原因枚举**，而不是把异常对象整个打出来：

```ts
console.warn('[wechat.exchange]', {
  reason: 'transport_or_invalid_response',
});
```

其他分支也只记静态原因、HTTP 状态码，或者上游的数值错误码。

**为什么不能直接 `console.error(error)`？** 因为这次出错的异常对象里，**URL 是作为属性挂着的**——而那个 URL 的查询串里有 `appid`、`secret` 和用户的临时 `code`。

同理也不能打印请求 URL 本身，也不能打印微信的响应全文。**而这三条恰好是最容易在"加个日志看看"时被顺手打出去的东西。**

脱敏在这里不是"把每个字符替换成星号"，而是**先决定日志真正需要哪些字段，然后只记那些字段**。前者是事后处理，后者是事前约束。

线上诊断于是指向 `transport_or_invalid_response` ——覆盖"请求发出但失败或响应不可解析"这一段。

**它不够精确（没指认具体某个参数），但已经足够改变下一步的方向**：问题在 fetch，不在数据库、不在密码逻辑、不在令牌签发。

**这就是受控枚举的价值：它不是为了定位到根因，是为了排除掉更多的范围。**

## 真正的错误长这样

用本机的 Miniflare/workerd，保持项目在 `wrangler.toml` 里声明的兼容日期，构造一个最小请求。目标 URL 不含真实 Secret，也不需要有效 code。

返回的是一个 TypeError，直接说明了运行时接受什么：

```text
TypeError: Invalid redirect value ... "follow" or "manual"
```

而出问题的代码是：

```ts
// 修复前
const response = await fetch(url, {
  signal: AbortSignal.timeout(8000),
  redirect: 'error',
});
```

**`redirect: 'error'` 这个选项在 workerd 里不存在。**

选它的意图完全正确：这个请求带着 AppSecret 和用户的临时 code，**绝对不能被 302 跟到别处去**——如果跟了，AppSecret 就发给了微信指定的任意地址。

这个安全要求没有错。**错在"我以为目标运行时支持这个选项"。**

而这个错误为什么在本地测不出来？因为本机的 `fetch` 是 Node 的实现（undici），**它支持 `error`**，而且行为符合预期——你传一个 302 回来，它会抛错。

于是：**本地跑通、类型检查通过、单测全绿，线上在请求发出去之前就崩了。**

## 一个必须说清的细节

我复现的是**实际执行**，不是检查类型定义。

这件事值得强调，因为第一反应往往是"那 TypeScript 类型里有没有这个值？"——**有。** `RequestInit.redirect` 的类型包含 `'error'`，所以 `tsc` 完全不会报错。

而**类型声明允许某个字符串，不证明每一种目标运行时都执行相同语义。** Node 的 `fetch` 和 workerd 的 `fetch` 是两个不同项目的实现，它们对同一个选项的接受范围可以不同。

**这是"本地绿、线上红"这类问题里最隐蔽的一种**：出问题的不是逻辑，是"这段代码在你没有运行过的地方能不能跑"。

顺便说，这个错误发生在**处理请求选项时**，所以微信那边压根没收到请求，自然也不会有任何微信的业务错误码。**日志里没有错误码，不是因为微信正常，而是因为它没参与。**

## 修复不能只是把报错关掉

最快的"修复"是删掉 `redirect` 这行，或者改成 `'follow'`。**改完大概率就好了——但安全要求被悄悄丢了。**

如果微信返回 302 而我们跟着跳，AppSecret 就进了对方指定的地址。而微信是可信的一方，但"微信返回的重定向目标"这件事，**在 SSRF 的语境下不该默认可信**。

所以选 `'manual'` + 显式检查状态：

```ts
const response = await fetch(url, {
  signal: AbortSignal.timeout(8000),
  redirect: 'manual',
});
if (!response.ok) {
  console.warn('[wechat.exchange]', {
    reason: 'http_status', status: response.status,
  });
  throw new Error('upstream');
}
```

**关键在 `if (!response.ok)`。**

`response.ok` 的语义是 `status` 在 200–299 之间，**3xx 不算成功**。所以微信一旦返回 302，我们在这里就抛错了，**根本走不到解析 `body` 那一步**，更不会拿 `Location` 再请求一次。

| 配置方向 | 运行时行为 | 判断 |
|---|---|---|
| `error` | 请求阶段直接拒绝 | **不可用**（虽然意图正确） |
| `follow` | 自动跟随跳转 | 安全要求丢失 |
| `manual` + 检查状态 | 跳转响应交给我们，**我们拒绝** | 采用 |

第三种把"要不要跟随跳转"的决定权从运行时拿回到业务代码手里。**这比 `error` 稍微啰嗦一点，但它是能在目标环境成立的方式。**

顺带说 `AbortSignal.timeout(8000)` 那一行也不能省。Cloudflare Workers 的 CPU 时间是硬配额，**一个挂住的上游请求就足以耗尽这次调用的时间**。8 秒是权衡值：微信正常响应在几百毫秒，超时主要防的是"上游挂住"而不是"上游慢"。

## 为什么 mock 测试没抓到

这个项目的微信测试用了 mock：

```ts
// 概念示意
vi.stubGlobal('fetch', mockFetch);   // 给某个 code 返回 { openid: '...' }
```

然后检查"同一身份只建一人""设置凭据后旧 refresh 被撤销"等等。**这些测试是有价值的**——它们证明了业务规则。

但它们**不会执行真实的 RequestInit 参数校验**。你传 `'error'`，mock 照样返回一个成功的 Response，测试照样通过。

**所以这类 mock 测试的边界要说清楚：**

| 它证明了 | 它没有证明 |
|---|---|
| 上游给出某种结果后，我们如何处理 | **目标运行时能不能发出这条请求** |
| 并发建号、凭据撤销等规则 | 这段代码在 workerd 里能不能执行 |

我原来的测试全在左列。**这次失败发生在右列。**

而修法不是"把 mock 改得更真"，而是**加一条针对运行时行为的测试**：

```ts
it('使用 Workers 支持的 manual 且拒绝重定向，不向跳转目标发送凭据', async () => {
  const fetchMock = vi.fn(
    async () => new Response(null, {
      status: 302,
      headers: { Location: 'https://untrusted.example/redirect' },
    }),
  );
  vi.stubGlobal('fetch', fetchMock);

  expect((await post('/auth/wechat/callback', { code: 'private-code' })).status).toBe(500);
  expect(fetchMock).toHaveBeenCalledTimes(1);                        // 只请求了一次
  expect(fetchMock).toHaveBeenCalledWith(
    expect.any(URL),
    expect.objectContaining({ redirect: 'manual' }),               // 用的是 manual
  );
  expect(await db.select().from(users)).toHaveLength(0);             // 没建账号
});
```

这个测试有意思的地方在它的**四条断言分别守什么**：

- **status 是 500** —— 说明我们没有把 302 当成有效响应去解析
- **`toHaveBeenCalledTimes(1)`** —— **这是最关键的一条**：如果代码写了"跟随 Location 再请求"，这里会是 2
- **`redirect: 'manual'`** —— 锁住配置，防止有人"顺手优化"改回 `follow` 或者删掉
- **数据库为空** —— 确保失败路径不会留下半个账号

而**它仍然是 mock**，所以严格说它没有验证 workerd 是否接受 `manual`。**这一点只能靠那次 Miniflare 复现来保证。**

**这个坦白很重要**：这条测试锁住的是"我们的处理逻辑"，不是"运行时支持这个选项"。前者能防回归，后者不能。

**要真正防住后者，得在 CI 里加一条针对目标运行时的最小执行检查**——比如用一个极简的 Worker 跑一次带同样选项的 fetch，断言不抛 TypeError。这是这次之后我打算补的，当前还没有。

## 一条我一开始想省掉的事

那 19 行测试，第一反应是"是不是多余了"。

因为 mock 测试"看起来"已经覆盖了登录流程——它确实测了并发建号、测了凭据设置、测了旧 token 撤销，**一共 10 个用例、248 行**。

而这次 bug 的表现是"本地全绿"。从代码上看不出任何问题，**加一条 mock 测试也拦不住它**（mock 不校验参数）。

我后来想清楚了：**这次不是"测试不够"，是"测试的边界没有写在明面上"。**

原来那 10 个用例的名字都在说"业务规则是什么"，没有一个在说"这段代码在哪个运行时上跑"。所以看测试列表的人会以为"登录这块测得挺全的"——**而实际上是"登录的业务逻辑测得挺全，但请求能不能发出去没测"**。

而我加的那条用例名是：

> 使用 Workers 支持的 manual 且拒绝重定向，不向跳转目标发送凭据

**它把"目标运行时"和"安全意图"都写进了名字。** 这样以后有人看测试列表，就知道这块的边界在哪、哪些保证是有测试的、哪些没有。

**这和 M1-32 讲的那个 `changes()=1` 是同一个道理**：给"故意不做的事"留下可见的标记。因为半年后看到一行 `redirect: 'manual'`，没人能确定它是"特意选的"还是"随手写的"。

## 小结

这个 bug 本身很简单——一个选项不被支持。但它暴露的三个问题都不简单：

1. **"配置存在"不等于"功能可用"。** `secret list` 证明的是上传成功，不是请求发出去了。
2. **类型检查不等于运行时行为。** `RequestInit.redirect` 的类型有 `'error'`，但 workerd 不支持它。
3. **mock 测试的边界要说出来。** 它证明"上游给结果后我们怎么处理"，不证明"请求能不能发出"。

而排查上最有用的一条经验是那个**故意用无效 code 探测**：

> 如果无效 code 返回的是"凭证无效"，说明请求发出去了、微信拒绝了；如果返回 500，说明它连微信都没走到。

**一次廉价的探测，把排查范围砍掉了一大半。** 而它成立的前提是——你事先知道"无效 code 应该得到什么响应"。

这比"密钥有没有配错"那种猜测有用得多，因为**它检验的是流程，而猜测检验的是某个具体值**。

至于还没补的那块：**CI 里应该有一条针对目标运行时的最小执行检查。** 当前状态是"这次靠手动复现发现"，不是"以后每次 CI 都会发现"。这是笔真实的债。
