# 成为全栈·Node 后端篇·冻结契约如何兼容增补：为微信登录补齐最小能力

> 一个新登录入口，可能只需要三个契约增补，也可能拖出一整套账号中心。差别往往发生在写代码之前。

{{IMG:M1-32-封面}}

## 前言：后端都收官了，怎么又要改？

写完前面的 31 篇，我原以为这套 Node 后端可以先安静一阵。网站和 Flutter APP 已经用起来，接口也冻结了。接下来开发微信小程序，问题来了：用户点一下微信登录，能不能直接成为会员？以后又能不能用用户名密码，在网站和 APP 登录这个会员？

单看按钮，需求很小。往账号体系里一放，却能长出绑定、合并、解绑、手机号、登录方式管理等一串分支。

各位看官，这还是一个教学项目。把业务做完整很重要，让读者为了一个入口先学半套身份平台，就有点喧宾夺主了。

这篇讨论的，是我怎样把新需求收回到最小范围：**保留既有客户端的使用方式，在明确版本差异的前提下，兼容增加微信登录能力。**

> 代码范围：本文属于原冻结版本之后的增补，契约从 1.11.0 更新到 1.12.0。前 31 篇对应的历史快照仍保留，不能拿旧快照寻找本文的新端点。

## 一、先把“账号打通”翻译成人能验证的动作

“账号打通”听着很省事，实际最容易藏需求。

如果意思是“把微信账号绑定到网站老会员”，就必须回答：凭什么证明两个身份属于同一个人？两边都有文章、收藏和评论，合并时谁覆盖谁？解绑之后还能不能登录？

这次我把需求改写成三个动作：

1. 用户用微信登录，首次创建一个独立会员，后续回到这个会员。
2. 该会员可以一次性设置用户名密码。
3. 网站和 APP 继续用现有密码登录接口，登录到这个会员。

**同一个 userId 可以拥有微信身份和密码凭据，不代表两个已有 userId 会被合并。** 已有网站账号仍可以密码登录；另行微信建号，得到的是独立账号。

| 候选方案 | 能解决什么 | 额外成本 | 本次判断 |
|---|---|---|---|
| 绑定、合并、解绑全套 | 整合多个已有账号 | 所有权验证、数据冲突、恢复策略 | 超出当前教学目标 |
| 微信登录后强制补齐资料 | 所有新用户立即有密码 | 阻断阅读互动，增加中间流程 | 没必要强制 |
| 微信建号，之后首次设置凭据 | 同一会员跨端密码登录 | 一个资格字段、一个设置端点 | 采用 |

选择第三种，并不是第一种永远不好。业务真要整合存量账号时，就得重新设计。当前先把已经答应的流程做清楚。

## 二、冻结的价值，是让变化可以被点名

翻开原契约，第三方回调扩展点已经存在：

```text
POST /api/v1/auth/{provider}/callback
```

因此，微信 code 的接收不需要另造一组 `/wechat/mini/*` 路径。我们落实 `provider=wechat` 的行为，并继续返回现有 `AuthResult`。其他 provider 不因为路径存在，就被算作已经实现。

最后留下的差异只有三项：

| 增补 | 消费方看到的变化 | 既有调用如何处理 |
|---|---|---|
| 实现微信 callback | code 换取现有登录结果 | 密码登录不改入口 |
| User 可选 canSetCredentials | 决定是否展示首次设置入口 | 不读该字段的旧端继续工作 |
| 新增 /me/setup-account | 已登录用户首次设置凭据 | 旧端不必调用新端点 |

这不能叫“契约完全没变”。它已经从 1.11.0 增补为 1.12.0。兼容性指的是旧用法保留，不是版本号装作没看见新需求。

同样，路径早有预留，也不代表实现一个新行为就无需审查。code 的含义、失败响应、用户创建规则，都得落入可验证的契约。

## 三、可选字段，默认值比字段名更重要

`docs/api/openapi.v1.yaml` 中的增补字段是：

```yaml
canSetCredentials:
  type: boolean
  description: >
    可选增补。true 仅表示微信自动建号且尚未设置本地登录凭据；
    缺失按 false。状态由服务端计算，不能通过资料接口修改。
```

客户端判断也要保持这个方向：

```ts
// 示例：只有服务端明确给出资格，才展示入口。
const showSetup = user.canSetCredentials === true;
```

如果写成 `!user.canSetCredentials`，一个没有新字段的历史响应就会被误判。这里 false 和缺失不是“随便处理”，而是兼容规则的一部分。

另外，这个字段只告诉界面该显示什么。服务端不能相信客户端传回的 true，也不能仅凭“按钮没出现”保护设置接口。真正的资格还要重新查数据库。

**“新增响应字段”也不是对任何客户端都自动安全。** 某些严格解析器会拒绝未知字段，生成类型可能改变构造参数。发布前仍应检查真实消费者的解析方式，以及旧登录、刷新、资料等路径。可选，是兼容设计的手段，不是免检通行证。

## 四、新端点只做首次设置，别顺手接管改密

新增端点采用现有 Bearer 认证：

```http
POST /api/v1/me/setup-account
Authorization: Bearer <当前会员的访问令牌>
Content-Type: application/json

{"username":"my_writer","password":"示例密码请自行设置"}
```

示例仅展示请求形状，不是可公开复用的测试凭据。用户名 1～32 字符，密码至少 8 字符；确认密码是客户端输入检查，不增加到服务端请求。

成功后返回现有 `AuthResult`，客户端整体替换会话。首次设置完成，后续改密仍走 `/me/change-password`。

为什么不用已有资料更新接口？因为改昵称和“从无密码到有密码”不是同一种操作。后者还涉及资格检查、唯一用户名、密码哈希和旧刷新令牌撤销。把它伪装成普通 PATCH，接口表面少了一条，语义却藏进了通用表单。

| 情况 | 响应与恢复方式 |
|---|---|
| 未登录或令牌无效 | 401，恢复身份后再操作 |
| 用户名被占用 | 409 / 3002，保留输入并换名称 |
| 已完成首次设置 | 409 / 3002，不覆盖已有凭据 |
| 禁用账号 | 拒绝，不因为来自微信而放行 |
| 提交结果不确定 | 不把超时当作失败；用新密码或重新微信登录确认状态 |

这张表比“请求成功显示 Toast”更接近一个完整流程。

## 五、数据库增补也要尊重老用户

契约可选，不代表数据库状态可以含糊。老会员本来就有密码，迁移默认值应当体现这个事实：

```sql
ALTER TABLE users
ADD COLUMN credentials_configured INTEGER NOT NULL DEFAULT 1;
```

这段来自本地增量迁移；D1 使用对应迁移文件。微信新建用户显式写入 0，老用户不重新哈希密码，不改 userId，不要求重新注册。

发布顺序也不是“把最新代码推上去看看”：

```text
核对契约差异 → 本地测试 → 备份线上库
    → 应用增量迁移 → 部署代码 → 兼容烟测 → 真实微信验证
```

本次线上迁移采用加列、加表，没有重建用户表。代码异常时，可以优先回滚代码、保留兼容新增结构；若新用户已经写入，直接拿旧备份覆盖整库，会把合法的新数据一起抹掉。备份存在，并不意味着任何时候都适合整库恢复。

## 六、怎么证明“旧端不用一起改”

我把证据分成三层，避免一个绿色勾勾包办所有结论：

- **契约层**：检查原密码登录、注册、刷新和改密的请求要求，确认不是偷偷加了必填字段。
- **数据与业务层**：增量迁移保留历史账号；自动化覆盖未设置用户不能密码登录、用户名冲突、重复设置和旧 refresh 撤销。
- **实际环境层**：本地与 D1 验证迁移，线上微信登录进入会员中心。真实身份设置密码后跨端登录尚未逐项操作，不能用测试桩冒充这项证据。

还应做一个容易被遗漏的反向检查：新客户端连接缺少资格字段的响应，不能自动展示首次设置入口。兼容既要看“旧端遇到新服务”，也要看“新端遇到旧响应”。

## 小结

这次增补让我更愿意把“冻结”理解成一个可以对照的基线。它让我们知道改了什么、影响谁、怎样验证，也让原来的文章和代码依然可复现。

下次有人提“加一个快捷登录”，我会先问：是增加身份来源，还是合并已有账号？是否一定要让旧消费者改变？这些问题回答清楚，代码通常反而变少。
