# 成为全栈·Node 后端篇·冻结契约如何兼容增补：为微信登录补齐最小能力

写完前面 31 篇，我原以为这套 Node 后端能安静一阵。网站和 Flutter APP 已经用起来，接口冻结了，标签是 `node-backend-v1.0`。

然后要做微信小程序。

需求看起来很小：**用户点一下微信登录，能不能直接成为会员？**

我把这个需求原样丢进设计里，写到一半发现自己在设计一个**账号合并系统**——绑定、所有权验证、合并时的数据冲突、解绑后能不能登录、两边文章收藏评论怎么算。

**而我要的只是一个登录入口。**

于是我停下来，重新问了一个问题：用户从微信登录之后，他想做的事是什么？

答案是：看文章、点赞、收藏、评论。然后——**下次他想用电脑登录，想用用户名密码。**

这两句话加起来，就够了。剩下的都是我自己想出来的。

这篇讲我怎么把一个会长成账号平台的需求，收回成三个端点。

## 先把需求写成能验证的动作

“账号打通”是最容易藏需求的说法，因为它听起来很省事。

如果它的意思是"把微信账号绑定到网站老会员"，就必须先回答一串问题：

- 凭什么证明两个身份属于同一个人？
- 两边都有文章、收藏和评论，合并时谁覆盖谁？
- 解绑之后还能不能登录？

这些问题的答案会决定一整套数据模型。而**它们全都不是这个需求真正要的。**

所以我把需求改写成三个可以验证的动作：

1. 用户用微信登录，首次创建一个会员，后续回到这个会员
2. 该会员可以**一次性**设置用户名密码
3. 网站和 APP 继续用现有的密码登录接口，登录到这个会员

| 候选方案 | 能解决什么 | 额外成本 | 判断 |
|---|---|---|---|
| 绑定、合并、解绑全套 | 整合多个已有账号 | 所有权验证、数据冲突、恢复策略 | 超出当前目标 |
| 微信登录后强制补齐资料 | 所有新用户立即有密码 | 阻断阅读互动 | 没必要强制 |
| **微信建号，之后首次设置凭据** | 同一会员跨端密码登录 | 一个资格字段、一个端点 | **采用** |

关键在最后那条：**"同一个 userId 可以有微信身份和密码凭据"，和"两个已有的 userId 会被合并"，是完全不同的两件事。**

前者是给一个新账号加第二种登录方式，后者涉及存量数据。前者只影响新用户，后者要动老用户的数据。

**已有网站账号继续用密码登录，另行微信建号得到的是独立账号。** 这个口径看起来不够"打通"，但它诚实地反映了需求——**用户没要求打通存量账号，是我以为他要。**

## 三处增补，其余不动

冻结契约的价值，是让变化可以被点名。翻开原契约，第三方回调的扩展点已经存在：

```text
POST /api/v1/auth/{provider}/callback
```

所以微信 code 的接收**不需要另造一组 `/wechat/mini/*` 路径**。我们落实 `provider=wechat` 的行为，继续返回现有的 `AuthResult`。

而其他 provider **不因为路径存在就算作已实现**——预留路径和实现行为是两件事，这一点在契约里必须分开。

最后留下的差异只有三项：

| 增补 | 消费方看到的变化 | 既有调用怎么处理 |
|---|---|---|
| 实现微信 callback | code 换现有登录结果 | 密码登录不改入口 |
| User 可选 `canSetCredentials` | 决定是否展示首次设置入口 | 不读该字段的旧端继续工作 |
| 新增 `POST /me/setup-account` | 已登录用户首次设置凭据 | 旧端不必调用新端点 |

这**不能叫"契约完全没变"**。它已经从 1.11.0 增补为 1.12.0。

兼容性指的是"旧用法保留"，不是"版本号装作没看见新需求"。**说清楚这一点，是为了让人知道哪些地方需要重新验证。**

## 可选字段：默认值比字段名更重要

契约里这个字段是这样的：

```yaml
canSetCredentials:
  type: boolean
  description: >
    可选增补。true 仅表示微信自动建号且尚未设置本地登录凭据；
    缺失按 false。状态由服务端计算，不能通过资料接口修改。
```

客户端这一侧的写法有个陷阱：

```ts
// ✅ 只有服务端明确给出资格，才展示入口
const showSetup = user.canSetCredentials === true;

// ❌ 这样写会把没有新字段的历史响应误判为需要设置
const showSetup = !user.canSetCredentials;
```

**`=== true` 那三个字符是兼容规则的一部分。** 一个来自旧服务端的响应没有这个字段，`user.canSetCredentials` 是 `undefined`，而 `!undefined` 是 `true`——**所有老用户一进 App 都会看到"设置密码"的入口。**

而这里 false 和"缺失"不是"随便处理"，它们在这里**语义相同**：都不能设置。

还有一点必须说清：**这个字段只是告诉界面该显示什么，不能作为保护。**

服务端不能相信客户端传回的 true，也不能因为"按钮没出现"就认为安全。真正的资格要重新查库——下面的实现里能看到这一层。

## 随机密码：一个看起来像 bug 的正确设计

现在讲这次增补里我最想解释的一个决定。

微信建号的时候，`users` 表的 `password_hash` 是**非空的**。但这个账号此时根本没有密码。

看代码：

```ts
const username = `wx_${crypto.randomUUID().replaceAll('-', '').slice(0, 28)}`;
const hash = await hashPassword(crypto.randomUUID() + crypto.randomUUID());
const now = Date.now();
await atomic(db, [
  {
    sql: `INSERT INTO users (username,password_hash,credentials_configured,role,email,display_name,level,status,created_at,updated_at)
    VALUES (?, ?, 0, 'member', NULL, '微信会员', 1, 'active', ?, ?)`,
    params: [username, hash, now, now],
  },
  ...
```

**存了一个随机 UUID 的哈希。**

为什么不用空值？因为 `password_hash` 是 `NOT NULL`，而且**改动这一列的可空性会牵动所有相关的索引和查询**。相比之下，"存一个不可知的随机值"成本几乎为零。

而它的**安全性**来自另一个字段：

```ts
if (!user.credentialsConfigured || !(await verifyPassword(password, user.passwordHash))) {
  throw new AppError(ErrCode.USERNAME_OR_PASSWORD_ERROR, 401); // 1001
}
```

**`credentialsConfigured` 为 0 时，密码校验直接短路，根本不执行。**

这一行是整段代码里最关键的安全边界。因为哈希是随机的、且从不告诉任何人，所以即使这个字段判断写漏了，攻击者也无法构造出能通过验证的密码——**但我们不依赖这层保险**。

**两道独立的防线**是这个设计值得的地方：随机哈希让人猜不到，`credentialsConfigured` 让逻辑根本不去猜。

顺带说 `username` 的生成：`wx_` + UUID 前 28 位。带前缀是为了在后台列表里一眼认出这是微信建号的账号，而 28 位是够用的（用户名列上限 32）。

**注意 email 存的是 NULL。** 不是空串。因为"没有邮箱"和"邮箱是空的"在语义上不同——**而 M1-10 讲过，客户端传什么都不能直接当事实，数据库的 NULL 是在表达一个明确的信息。**

## 条件更新：让并发竞争只有一个赢家

现在讲设置凭据这个端点，它是整次增补里最难写对的地方。

```ts
export async function setupAccount(userId: number, username: string, password: string) {
  const db = getDb();
  const current = (await db.select().from(users).where(eq(users.id, userId)).all())[0];
  if (!current) throw new AppError(ErrCode.TOKEN_INVALID, 401);
  if (current.status === 'disabled') throw new AppError(ErrCode.ACCOUNT_DISABLED, 401);
  if (current.credentialsConfigured)
    throw new AppError(ErrCode.CONFLICT, 409, '账号已设置登录凭据');
  const hash = await hashPassword(password),
    now = Date.now();
  try {
    const changed = await atomic(db, [
      {
        sql: `UPDATE users SET username=?, password_hash=?, credentials_configured=1, updated_at=?
        WHERE id=? AND status='active' AND credentials_configured=0
        AND EXISTS (SELECT 1 FROM wechat_identities WHERE user_id=users.id)`,
        params: [username, hash, now, userId],
      },
      {
        sql: 'UPDATE refresh_tokens SET revoked_at=? WHERE user_id=? AND revoked_at IS NULL AND changes()=1',
        params: [now, userId],
      },
    ]);
    if (changed[0] !== 1) throw new AppError(ErrCode.CONFLICT, 409, '账号状态已变化，请重新登录');
```

这里有四层保护，每一层都不多余。

**第一层：读一次做快速失败。** 开头那个 `select` 是为了给用户一个清晰的错误（"账号已设置登录凭据"），而不是让数据库报冲突。

**但它不是安全边界。** 因为从读到这个 `UPDATE` 之间有时间差，两个并发请求都可能通过这一层检查。**真正的判断在 UPDATE 的 WHERE 里。**

**第二层：`WHERE id=? AND status='active' AND credentials_configured=0`。** 这才是并发安全的核心——数据库保证这一条只会成功一次，第二个请求的 `changes()` 会是 0。

注意这里带了 `status='active'`：**禁用账号不能设置凭据**。即使上一层的检查被竞态绕过去了，这一层还会挡住。

**第三层：`AND EXISTS (SELECT 1 FROM wechat_identities WHERE user_id=users.id)`。**

这一条最容易被忽略。**它保证只有"有微信身份映射"的账号才能通过这个端点设置凭据。**

如果少了它，**任何一个登录用户只要拿到自己的 access token，就能给自己设置用户名密码**——而这条端点是为微信建号账号准备的。一个普通网站用户调用它，就能把账号改成有密码，等于拿到了一个后门。

**这是"这个端点属于哪类用户"的机器表达。** 靠客户端判断做不到，因为客户端可以伪造。

**第四层：`changes()=1`。**

这一句是 SQLite 特有的：它表示"上一个语句影响了多少行"。而整个 `atomic()` 是一个**多语句事务**（D1 没有单语句多返回值的能力）。

看用法：

```sql
UPDATE refresh_tokens SET revoked_at=? WHERE user_id=? AND revoked_at IS NULL AND changes()=1
```

**撤销旧 refresh token 这个动作，只有在第一步确实更新了用户行的时候才执行。**

为什么需要这个？因为如果第一步失败（比如用户名冲突），而刷新令牌已经被撤销了——**用户的现有会话就全废了，而且他还没能设置新凭据。** 那种状态下他只能重新微信登录。

而用 `changes()=1` 把撤销操作"绑"在上一步的成功上，就避免了这种状态。

注释里写得很准：**"条件更新保证仅成功一次；changes() 使失败竞争者不会撤销成功者的新会话。"**

## 事务里的两个 INSERT

回头看微信建号那段，两条 INSERT 也在一个事务里：

```ts
await atomic(db, [
  {
    sql: `INSERT INTO users (...) VALUES (...)`,
    params: [username, hash, now, now],
  },
  {
    sql: `INSERT INTO wechat_identities(app_id,open_id,user_id,created_at)
    SELECT ?, ?, id, ? FROM users WHERE username = ?`,
    params: [appId, openId, now, username],
  },
]);
```

**第二条用 `SELECT ... FROM users WHERE username = ?` 来拿 id，而不是假设 id 是已知的。**

这个写法有点绕，但它是必要的：D1 的 `lastInsertRowid()` 在多语句事务里不保证可靠，**而用户名是这一批里唯一的、我们确知其唯一的标识**（带随机 UUID）。

而支撑它的是一个数据库约束：

```sql
CREATE UNIQUE INDEX uniq_wechat_identity ON wechat_identities(app_id, open_id);
CREATE UNIQUE INDEX uniq_wechat_user ON wechat_identities(user_id);
```

**两个唯一索引，各挡一类并发问题**：

| 索引 | 挡什么 |
|---|---|
| `(app_id, open_id)` | **同一个微信用户重复建号** |
| `user_id` | **一个本地账号绑定多个微信身份** |

第二个索引是我一开始没想到加的。加了之后，"一个网站会员绑两个微信号"这个状态**在数据库层面就不可能存在**。

而并发建号是靠捕获唯一约束冲突处理的：

```ts
} catch (error) {
  if (!isUniqueConstraintError(error)) throw error;
}
user = await find();
if (!user) throw new AppError(ErrCode.INTERNAL, 500, '微信账号创建失败，请重试');
```

**冲突不是错误，是"别人先建好了"。** 捕获之后重新查一次，拿到对方建的那个账号，继续用。

**如果捕获后查不到，就抛 500。** 那说明发生了别的唯一约束冲突（很可能是用户名碰撞，虽然 UUID 几乎不可能），此时不能返回一个未知的用户。

## 密钥和临时 code 都不能进日志

微信 code 换 session 这个调用，有几处细节值得单独说。

```ts
// workerd 不支持 redirect:error；manual + 非 2xx 拒绝保持禁止重定向的边界。
const response = await fetch(url, {
  signal: AbortSignal.timeout(8000),
  redirect: 'manual'
});
if (!response.ok) {
  console.warn('[wechat.exchange]', { reason: 'http_status', status: response.status });
  throw new Error('upstream');
}
```

**`redirect: 'manual'` 是防 SSRF 的。**

URL 里带着 `secret` 参数。如果微信（或者中间任何一环）返回 302 跳转，我们跟过去就意味着**把 AppSecret 发到了对方指定的地址**。

而 workerd 不支持 `redirect: 'error'`，所以只能手写：`manual` 表示"不自动跟随，告诉我重定向了"，然后我们检查 `response.ok` 并直接拒绝。

**`AbortSignal.timeout(8000)`** 是另一个必要的边界。如果没有超时，一个卡住的上游请求会占住 Worker 的执行时间，而 Cloudflare Workers 的 CPU 时间是硬限制——**一个挂住的第三方请求就能耗尽这次调用的配额。**

然后是日志：

```ts
console.warn('[wechat.exchange]', { reason: 'missing_configuration' });
...
// 不记录异常对象或请求 URL：它们可能包含 AppSecret 和临时 code。
console.warn('[wechat.exchange]', { reason: 'transport_or_invalid_response' });
```

**注意那句注释：异常对象和请求 URL 都不能记录。**

这看起来有点苛刻——出错时记一下详情不是更有用吗？问题在于：`fetch` 抛出的异常对象里，**URL 是作为属性挂着的**，而那个 URL 里有 `secret=`。而 `code` 也在 URL 里。

所以这里只能记一个**枚举出来的原因字符串**，不能记原始对象。

**判断标准很直接：这条日志会不会出现在一个用户能看到的地方。** 如果会，那它里面的每一个字段都要按"用户可能看到"来审。

而微信自己的错误码也要分类处理：

```ts
if ([40029, 40163, 40226].includes(body.errcode ?? 0)) {
  throw new AppError(ErrCode.TOKEN_INVALID, 401, '微信凭证无效，请重新登录');
}
if (body.errcode === 45011) throw new AppError(ErrCode.RATE_LIMITED, 429);
```

| 微信码 | 含义 | 我们映射成 |
|---|---|---|
| 40029 / 40163 / 40226 | code 无效、被吊销、过期 | 401 + TOKEN_INVALID（**客户端该重新授权**） |
| 45011 | 调用频率超限 | 429（**客户端该退避**） |
| 其他 | 服务异常 | 500 |

**映射的依据是"客户端下一步该做什么"。** code 无效时小程序应该重新拉起授权，限流时应该等一会儿——**这两种情况如果都映射成 500，客户端就只能显示"服务异常"，用户会反复重试而永远不成功。**

顺带注意 45011 直接 `new AppError(ErrCode.RATE_LIMITED, 429)` **不带 message**——因为这时候给用户一句"请求较多"不如什么都不说，客户端会自己显示标准的限流提示。

## 迁移：一个 DEFAULT 值体现了多少尊重老用户

最后是数据库迁移。这个文件只有六行，但第一行注释就说明了它的性质：

```sql
-- 增量迁移；必须先备份并确认该列不存在。不要重放已有 0000 全量迁移。
ALTER TABLE users ADD COLUMN credentials_configured INTEGER NOT NULL DEFAULT 1;

CREATE TABLE wechat_identities (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  app_id TEXT NOT NULL,
  open_id TEXT NOT NULL,
  user_id INTEGER NOT NULL REFERENCES users(id),
  created_at INTEGER NOT NULL
);
```

**`DEFAULT 1` 这一个数字，决定了几万个老账号的命运。**

如果是 `DEFAULT 0` 会怎样？**所有老用户都会被判成"没有设置凭据"**，然后：

- 他们的密码登录会直接失败（因为 `!user.credentialsConfigured` 短路了验证）
- 登录页会给他们显示"设置密码"入口，而他们已经有密码了

所以老用户必须是 `1`——**"默认认为已经设置好了"，新的微信账号才显式写 0。**

这也是为什么迁移顺序不能反：**先加列（默认 1），再部署代码。** 如果先部署代码，那段时间里数据库还没有这一列，所有查询都会报错。

而微信建号那段里显式写了 `credentials_configured` 的值 `0`，所以不需要依赖默认值——**默认值只服务于历史数据，新数据一律显式写。**

发布顺序也不可能是"把最新代码推上去看看"：

```text
核对契约差异 → 本地测试 → 备份线上库
    → 应用增量迁移 → 部署代码 → 兼容烟测 → 真实微信验证
```

注意这次线上迁移是**加列、加表，没有重建用户表**。这不是偶然——**D1 上重建一张有数据的表，风险和成本都高得多。**

而且代码异常时可以优先回滚代码、保留兼容的新增结构。**新增的列对新代码是必需的、对旧代码是多余的，所以留着它不影响回滚。**

反过来那句也要说：**备份存在，不意味着任何时候都适合整库恢复。** 如果新用户已经写入，整库恢复会把这些合法的新数据一起抹掉。**这是备份最反直觉的一个特性——它在你最需要它的时候可能最不能用。**

## 怎么证明"旧端不用一起改"

我把证据分成三层，避免一个绿色勾勾包办所有结论。

**契约层**：检查原密码登录、注册、刷新和改密的请求要求，确认没有偷偷加必填字段。

**数据与业务层**：增量迁移保留历史账号；自动化覆盖未设置用户不能密码登录、用户名冲突、重复设置、旧 refresh 撤销。

**实际环境层**：本地与 D1 验证迁移，线上微信登录进入会员中心。

还有一条容易被遗漏的**反向检查**：

> 新客户端连接缺少资格字段的响应，不能自动展示首次设置入口。

兼容不只看"旧端遇到新服务"，也要看"**新端遇到旧响应**"。而后者恰恰是 `=== true` 那个写法和 `credentialsConfigured` 默认值要解决的两件事——**它们保护的都是新客户端连旧服务的情况。**

## 一条我一开始想省掉的事

那个 `changes()=1` 的条件，第一版我没写。

当时的逻辑是："先更新用户，再撤销旧 token，不在一个事务里但也没什么问题。"

问题出现在我手工模拟并发的时候：**两个请求同时设置凭据，第一个因为用户名冲突失败，第二个成功。** 而撤销 token 那一步是独立执行的——**第一个请求的失败也执行了撤销，把这个用户的所有会话全干掉了。**

那个用户的状态就是：**既没设置成功，又被登出。** 他得重新走微信登录。

而这个 bug 在串行测试里永远不会出现，因为串行时第一个失败之后不会再有第二个请求来"顺手撤销"。

**这是"顺序执行的测试发现不了并发问题"的典型例子**——和 M4-12 讲的那个列表 `serial` 竞态是同一类，只不过这里跨了网络请求。

修复之后我加了一条测试：**构造两个并发 setup 请求，断言失败的请求不能影响另一个请求建立的会话。**

顺带说，那条测试不是靠 sleep 实现的——而是**用两个不同的用户名同时打，靠 `atomic` 的事务顺序制造竞争**。这种测试有概率性，所以我跑了多次确认稳定。

## 小结

这次增补让我更愿意把"冻结"理解成**一个可以对照的基线**，而不是一个不能动的承诺。

它让我们能清楚地说出：改了哪三处、影响谁、怎样验证。也让前面的 31 篇依然可复现——**用旧快照能跑通旧代码，用新契约能跑通新代码，两者都有据可查。**

下次有人提"加一个快捷登录"，我会先问三个问题：

1. **是增加身份来源，还是合并已有账号？**
2. **是否一定要让旧消费者改变？**
3. **失败了用户下一步该做什么？**

这三个问题回答清楚，代码通常反而变少。

而这次最实的一个体会是：**"看起来像 bug 的设计"往往藏着最强的约束。** 那个随机密码哈希、`credentialsConfigured` 的短路、`changes()=1` 的绑定——每一处第一眼都显得多余，删掉之后立刻会出真实问题。
