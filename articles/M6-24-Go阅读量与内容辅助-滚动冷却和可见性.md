# 成为全栈·Go 后端篇·阅读量与内容辅助：滚动冷却为什么不能按天分桶

> 去重规则若是“同一用户 24 小时内只计一次”，就必须保存上次计数的具体时刻。按自然日分桶会在午夜边界制造错误结果。

> 本文代码快照：提交 ceac4e0。阅读计数使用滚动 24 小时窗口；内容辅助只向有权限的调用方返回公开文章。

## 前言：自然日不是 24 小时

访客在 23:55 阅读一篇文章，隔天 00:05 再次访问。按自然日分桶会将两次访问分到不同日期，仅隔十分钟就计两次；而真正的滚动 24 小时冷却应等到次日 23:55 才再次计数。反方向也一样：上午 9 点与当天晚上 11 点相隔 14 小时，按“每天一次”可能都计数，但滚动窗口只计一次。

M6 按匿名访客或登录用户建立文章级去重记录，比较当前毫秒时间与上次计数时间。达到 86,400,000 毫秒才更新记录并增加文章阅读量。锁定文章、维护去重行和原子更新计数都在同一事务内。

本文还会看相邻文章、相关文章、TOC 和面包屑等辅助数据：它们共享公开可见性规则，却使用不同的计算方法和成本边界。

## 一、去重键要能识别访问主体

登录访问者的 key 使用 user ID；匿名访问者使用 IP 与 User-Agent 组合后计算 FNV 标识。数据库只保存短 key，而非原始 IP 和 UA。该方式减少个人信息的直接存储，但 FNV 不是密码哈希或匿名化的强隐私保证：输入空间可能被猜测，且 IP/UA 会变化或被伪造。文章计数用它近似区分访客，不应当作身份认证。

匿名标识的计算函数只有七行：

~~~go
// internal/article/toc.go（fnv）
func fnv(s string) string {
	h := uint32(0x811c9dc5)
	for _, ch := range utf16.Encode([]rune(s)) {
		h ^= uint32(ch)
		h *= 0x01000193
	}
	return strconv.FormatUint(uint64(h), 16)
}
~~~

这是一段标准的 32 位 FNV-1a：初始值 `0x811c9dc5`，每个单元先异或再乘质数 `0x01000193`，最后以十六进制字符串输出。和 `moderate` 一样，它先把输入转成 UTF-16 单元，保证中文或 emoji 的参与方式与 JavaScript 一致。

注意它的定位：输入是 `ip + "|" + ua`，输出是一个固定长度的短串，数据库里存的是这个短串而不是原始 IP 和 UA。这样做减少了直接存储的个人信息，但 FNV 是快速哈希，不是密码学哈希，也没有加盐——它的作用是让“同一访客”在大多数情况下落到同一个 key，而不是保护隐私或抵抗伪造。换 IP、改 UA 都能得到新 key，这正是后文要说的“去重不等于反刷”的由来。

代理配置影响匿名 IP 的可信来源。若应用直接信任任意 X-Forwarded-For，客户端可以伪造地址绕过去重；Go 实现只在 RemoteAddr 命中可信代理列表时解析转发链。User-Agent 也由客户端控制，所以匿名 key 只能是轻量去重启发，不是抗刷系统。

会员访问按 user ID 计数，不依赖浏览器地址变化。退出登录后访问会退回匿名键，登录前后是否合并历史没有在当前模型里处理。身份规则应按契约和数据模型明确描述。

两种主体的键构成可以并排看：

| 访问主体 | 前缀 | 键的构成 | 特点 |
|---|---|---|---|
| 已登录会员 | `u:` | user ID | 与浏览器、网络环境无关 |
| 匿名访客 | `a:` | IP 与 User-Agent 组合的 FNV 值 | 只是轻量去重启发 |

前缀把两种键放进同一个字段却不混淆。会员的键稳定，退出登录后就换成匿名键——同一个人登录前后会被算作两个主体，当前模型没有做合并。匿名键则会因为换 IP、换 UA 而改变。两者都不代表“真实的人数”，只代表“多少个不同的标识”。

## 二、锁住文章后执行滚动窗口

Views 在事务里使用 database.Lock 读取公开文章，再计算去重 key。若没有记录，插入当前时间并增加 view_count；如果已存在且 now - created_at 大于等于 24 小时，则更新时间并增加；否则只返回现有计数。

~~~text
事务开始
  ↓ 锁定已发布文章
  ↓ 计算 member key / anonymous key
  ↓ 读取该 article 的 dedup row
  ├─ 不存在：插入 + 计数增加
  ├─ 已存在且冷却到期：更新时间 + 计数增加
  └─ 未到期：保持计数
  ↓ 读取新计数并提交
~~~

~~~go
// internal/article/discovery.go（Views，节选）
// Views 在事务中维护阅读量和滚动 24 小时去重记录。
func (s *Service) Views(ctx context.Context, id int64, actor values.Actor, ip, ua string) (any, error) {
	db := s.DB.WithContext(ctx)
	var a model.Article
	txErr := db.Transaction(func(tx *gorm.DB) error {
		var err error
		a, err = Published(database.Lock(tx), id)
		if err != nil {
			return err
		}
		key := "u:" + strconv.FormatInt(actor.ID, 10)
		if actor.ID == 0 {
			key = "a:" + fnv(ip+"|"+ua)
		}
		now := s.Now().UnixMilli()
		var dedup model.ViewDedup
		err = tx.Where("article_id = ? AND dedup_key = ?", id, key).First(&dedup).Error
		increment := false
		if err == gorm.ErrRecordNotFound {
			dedup = model.ViewDedup{
				ArticleID: id,
				DedupKey:  key,
				CreatedAt: now,
			}
			if err := tx.Create(&dedup).Error; err != nil {
				return err
			}
			increment = true
		} else if err != nil {
			return err
		} else if now-dedup.CreatedAt >= 86400000 {
			if err := tx.Model(&dedup).UpdateColumn("created_at", now).Error; err != nil {
				return err
			}
			increment = true
		}
		if increment {
			if err := tx.Model(&model.Article{}).
				Scopes(database.ActiveArticles).
				Where("id = ?", id).
				UpdateColumn("view_count", gorm.Expr("view_count + 1")).Error; err != nil {
				return err
			}
		}

		return tx.First(&a, id).Error
	})
	return map[string]any{"viewCount": a.ViewCount}, txErr
}
~~~

事务开头是 `Published(database.Lock(tx), id)`：既取出已发布的文章（没发布就直接失败），又对这篇文章加了行锁。锁的对象是文章而不是去重行，所以同一篇文章的所有并发访问会在这里排队，后面的窗口判断因此是串行的。

key 的构造只有两行：默认用 `"u:" + userID`，只有 `actor.ID == 0` 时才换成 `"a:" + fnv(ip+"|"+ua)`。`actor.ID == 0` 就是匿名——没有有效令牌时解析出的 Actor 是零值。

接下来是关键的三分支。`gorm.ErrRecordNotFound` 表示这个主体第一次读这篇，插入一行去重记录并把 `increment` 置为 true。其他查询错误直接上抛。查到记录时比较 `now - dedup.CreatedAt >= 86400000`——整整 24 小时的毫秒数，用的是时间差而非日期，所以 23:55 要到次日 23:55 才算到期。满足就更新 `created_at` 并置位 `increment`；三分支都不命中时 `increment` 保持 false，也就是“冷却期内，这次不计”。

计数更新只有一句：`UpdateColumn("view_count", gorm.Expr("view_count + 1"))`。加法交给数据库执行，而不是读出来在 Go 里加一再写回，避免覆盖并发的其他增量。最后 `tx.First(&a, id)` 重新读出文章，把提交前的计数快照返回给调用方。

将文章作为竞争点锁定，使相同文章的并发请求按事务顺序检查同一个窗口；去重表唯一约束防止一主体一文章出现重复行；文章计数在同一事务更新。若并发实现只做“读记录后 insert”，两个请求都可能读到不存在。唯一约束和冲突处理应与锁策略共同验证。

条件是滚动毫秒差值，不按本地时区、午夜或日历日期切分。控制时钟的测试可覆盖 23:55/00:05、恰好 24 小时、少一毫秒和多个并发请求。使用固定时钟还能避免测试受执行时间影响。

三个分支的判据与动作可以列成一张表：

| 去重记录状态 | 判据 | 计数动作 |
|---|---|---|
| 不存在 | 该主体首次读这篇文章 | 插入记录，计数加一 |
| 存在且 `now - created_at ≥ 86400000` | 冷却已到期 | 更新时间，计数加一 |
| 存在且时间差不足 24 小时 | 仍在冷却期内 | 保持原计数 |

第二行的判据是 `>=`，所以时间差恰好等于 86400000 毫秒时会再计一次；少一毫秒则落在第三行。这个边界是测试要盯住的地方，也正是“不能按自然日分桶”的落点——第三行看的是时间差，与访问发生在几点、跨不跨午夜都无关。

## 三、计数准确和反刷能力是两件事

当前规则能减少同一标识的重复请求，但不能证明是真实人在读。攻击者可换 IP、清理 UA 或控制代理流量；一个共享 NAT 后的不同访客也可能被合并。若产品需要更强的防刷，应结合网关、风险评分、限速或分析系统，且要另行定义隐私和成本。

读取次数的写入在每个访问冷却到期后更新文章行，热点文章会成为锁竞争点。当前选择的优势是事务和计数语义清楚；大规模下要用负载实验判断是否改成异步聚合或分片计数。变更后仍要定义用户看到的是精确值还是最终一致近似值，不能只讨论吞吐。

阅读量返回的是事务完成后的计数快照。其他并发访问可能在响应发出前又改变它，因此客户端看到的数字是某个时刻的值，不代表响应一直最新。

## 四、相邻和相关文章的可见性

Adjacent 先要求目标文章已发布，再分别寻找发布时间更早和更晚的 published 内容，并以时间与 ID 排序。不存在任何一侧时返回 null stub。相邻逻辑只基于发布时间，不是按 ID 排序，也不会包含草稿。相同发布时间记录的定位规则要以实现和测试为准。

~~~go
// internal/article/discovery.go（stub 与 Adjacent，节选）
func stub(a model.Article) any {
	if a.ID == 0 {
		return nil
	}
	return map[string]any{
		"id":    a.ID,
		"title": a.Title,
		"slug":  a.Slug,
	}
}

// Adjacent 按发布时间寻找公开文章的上一篇和下一篇。
func (s *Service) Adjacent(ctx context.Context, id int64) (any, error) {
	db := s.DB.WithContext(ctx)
	a, err := Published(db, id)
	if err != nil {
		return nil, err
	}
	result := map[string]any{"prev": nil, "next": nil}
	if a.PublishedAt == nil {
		return result, nil
	}
	for _, side := range []struct{ k, op, order string }{{
		"prev",
		"<",
		"DESC",
	}, {
		"next",
		">",
		"ASC",
	}} {
		var row model.Article
		r := db.Scopes(database.ActiveArticles).
			Where("status = ? AND published_at "+side.op+" ?", "published", *a.PublishedAt).
			Order("published_at " + side.order + ", id ASC").
			Limit(1).
			Find(&row)
		if r.Error != nil {
			return nil, r.Error
		}
		result[side.k] = stub(row)
	}
	return result, nil
}
~~~

`Published(db, id)` 先确认目标文章存在且已发布，未发布就直接返回错误——相邻列表不会因为没有发布而暴露内容。`a.PublishedAt == nil` 时立刻返回两侧都为 `nil` 的结果，一篇没有发布时间的文章没有可比对的基准。

主体是一个两轮循环，`side` 里放着 `prev` 和 `next` 两个方向。`prev` 用 `published_at < ?` 配 `DESC`，取更早的文章里时间最晚的一篇；`next` 用 `published_at > ?` 配 `ASC`，取更晚的文章里时间最早的一篇。两个方向的 `Order` 都补了 `id ASC` 作为次级键，避免同一时间戳的几条文章顺序不定。

`Limit(1)` 表示每侧只取一条。`Find(&row)` 在没有匹配行时不会返回 `ErrRecordNotFound`，而是留下一个零值 `row`。这正是 `stub` 存在的理由：`row.ID == 0` 说明这一侧没有文章，函数返回 `nil`，序列化后是 JSON `null`，而不是一个字段全空的假对象。

Related 同样先校验目标文章公开，再遍历其他公开且未删除文章，对共享标签计分、同分类加分，按分数和 viewCount 排序，限制返回数量最多 10。当前实现把候选文章取到 Go 内存中计算，不是数据库全文相似度搜索；当文章规模增长时，应该评估查询成本和内存占用，而不能假定 limit=10 就只读取了 10 篇。

~~~go
// internal/article/discovery.go（Related，节选）
	if limit < 1 {
		limit = 5
	}
	if limit > 10 {
		limit = 10
	}
	var rows []model.Article
	if err = db.Scopes(database.ActiveArticles).
		Where("status = ? AND id <> ?", "published", id).
		Order("id ASC").
		Find(&rows).Error; err != nil {
		return nil, err
	}
	type scored struct {
		a     model.Article
		score int
	}
	items := []scored{}
	tags := map[string]bool{}
	for _, t := range Tags(a.Tags) {
		tags[t] = true
	}
	for _, r := range rows {
		n := 0
		for _, t := range Tags(r.Tags) {
			if tags[t] {
				n += 2
			}
		}
		if a.CategoryID != nil && r.CategoryID != nil && *a.CategoryID == *r.CategoryID {
			n++
		}
		if n > 0 {
			items = append(items, scored{r, n})
		}
	}
	sort.SliceStable(items, func(i, j int) bool {
		if items[i].score != items[j].score {
			return items[i].score > items[j].score
		}
		return items[i].a.ViewCount > items[j].a.ViewCount
	})
	out := []map[string]any{}
	for i, item := range items {
		if i >= limit {
			break
		}
		r := stub(item.a).(map[string]any)
		r["viewCount"] = item.a.ViewCount
		out = append(out, r)
	}
	return out, nil
~~~

候选查询 `db.Scopes(database.ActiveArticles).Where("status = ? AND id <> ?", ...).Find(&rows)` 没有任何 `Limit`，它把所有公开且未删除、除自己以外的文章都读进 `rows`。这就是“取到 Go 内存中计算”的具体含义，也是“输出 limit 不等于扫描 limit”的原因。

`limit` 的钳制发生在查询之前：小于 1 取默认值 5，大于 10 压到 10。调用方传 100 也只会返回 10 条，但扫描的文章数仍然是全表公开文章。

评分规则两行写清：每共享一个标签加 2 分，分类相同再加 1 分。同一分类只加一次，而标签可以命中多个，所以标签的权重被有意设得更高。`n > 0` 才收集，分数为 0 的文章（既无共同标签也不同分类）不进候选。

排序用 `sort.SliceStable`：先比分数，分高在前；分数相同时比 `view_count`。稳定排序意味着分数与阅读量都相同时保留它们在 `rows` 里的原始顺序，也就是 `id ASC`，结果因此可复现。

输出时复用 `stub` 只取 id、title、slug 三个字段，再补一个 `viewCount`。推荐列表不需要正文或作者信息，返回体因此很小。

两个辅助接口的判据与边界可以对照：

| 接口 | 判据 | 排序 | 返回上限 |
|---|---|---|---|
| `Adjacent` | 发布时间早于或晚于目标 | `published_at`，其次 `id` | 每侧 1 篇 |
| `Related` | 共享标签计分、同分类加分 | 分数，其次 `view_count` | 最多 10 篇 |

两种接口都复用 ActiveArticles 和 published 条件，避免把私稿放到公开推荐中。可见性规则比推荐算法复杂度更关键。

## 五、TOC 要和 Markdown 展示的锚点一致

ParseToc 按行识别 Markdown # 标题，忽略反引号代码围栏内的标题。锚点小写化，只允许指定字符集合，重复标题追加编号后缀，长度按 JavaScript UTF-16 语义限制。中文和 emoji 会让 Go rune 与 JS string length 不同，因此实现使用 unicode/utf16 helper 复刻边界。

~~~go
// internal/article/toc.go（jsSlice 与 ParseToc，节选）
func jsSlice(s string, n int) string {
	u := utf16.Encode([]rune(s))
	if len(u) > n {
		u = u[:n]
	}
	return string(utf16.Decode(u))
}

// ParseToc 解析标题，跳过代码围栏，并保持与 Node 一致的中文和重复锚点。
func ParseToc(content string) []map[string]any {
	out := []map[string]any{}
	seen := map[string]int{}
	fence := false
	for _, line := range strings.Split(content, "\n") {
		if strings.HasPrefix(strings.TrimLeft(line, " \t\r"), "```") {
			fence = !fence
			continue
		}
		if fence {
			continue
		}
		m := heading.FindStringSubmatch(line)
		if m == nil {
			continue
		}
		text := strings.TrimSpace(m[2])
		if text == "" {
			continue
		}
		anchor := strings.Trim(invalidAnchor.ReplaceAllString(strings.ToLower(text), "-"), "-")
		anchor = jsSlice(anchor, 100)
		if anchor == "" {
			anchor = "heading"
		}
		n := seen[anchor]
		seen[anchor]++
		if n > 0 {
			suffix := "-" + strconv.Itoa(n)
			anchor = jsSlice(anchor, 100-len(suffix)) + suffix
		}
		out = append(out, map[string]any{
			"level":  len(m[1]),
			"text":   jsSlice(text, 200),
			"anchor": anchor,
		})
	}
	return out
}
~~~

`jsSlice` 是这套规则里最需要解释的辅助函数。它把字符串编码成 UTF-16 单元再按 `n` 截断，最后解码回字符串——`len(s)` 是字节数，`len([]rune(s))` 是 code point 数，两者都不等于 JavaScript 的 `length`，只有 UTF-16 单元数才与之一致。

`ParseToc` 的骨架是一个状态机。`fence` 记录当前是否在代码围栏内：遇到以三反引号开头的行就翻转标记并跳过，`fence` 为真时整行跳过。这样正文里出现的注释式标题、或代码示例里的井号行都不会被当成目录项。判断前先 `strings.TrimLeft(line, " \t\r")`，缩进的围栏同样能识别。

标题正则同时提取井号数量和标题文字，`level` 就是井号的个数。锚点生成分三步：整体小写、用 `invalidAnchor` 把不属于小写字母数字下划线和汉字的字符替换成连字符、修剪首尾连字符；结果为空时兜底成 `heading`。

重复标题靠 `seen` 计数处理：第一次出现时 `n` 为 0，直接用原锚点；再出现时 `n` 大于 0，生成 `-1`、`-2` 这样的后缀。拼接前用 `jsSlice(anchor, 100-len(suffix))` 给后缀留出空间，保证加后缀后总长度仍不超过 100。`text` 也做了 200 的 UTF-16 截断。

这仍是一个受限 Markdown 标题解析器，不是完整 CommonMark/remark AST。列表中出现的伪标题、缩进代码块、不同围栏形式可能需要按冻结 Node 行为进一步测试。前端渲染器必须用相同锚点规则，否则 TOC 链接可能指向不存在的 DOM id。完整渲染细节应以客户端页面验收为准。

## 六、辅助接口的测试清单

- 阅读量：未发布文章隐藏、匿名和会员 key、24 小时前后边界、午夜、并发重复；
- Adjacent：两侧均有/只有一侧/均无、相同时间边界和软删除过滤；
- Related：共享标签权重、同分类加分、viewCount 平局、limit 上限和私稿排除；
- TOC：代码围栏、中文、emoji、重复标题、长度边界；
- Breadcrumb：根节点、深层父链、缺失分类与无效循环数据；
- 跨库：事务/行锁与 SQLite 单写、分页或排序差异。

每项检查响应形状和数据库后置状态。辅助功能不应拖垮文章正文读取；各自查询可以独立失败并由客户端合理降级，这属于端到端用户体验需要进一步验收的部分。

## 小结：先准确说明规则，再选择计数优化

M6 的阅读去重窗口是精确滚动 24 小时，不是自然日；会员按 user ID，匿名按可信 IP 与 UA 组合形成 key；文章锁、去重记录和计数增量在事务中。辅助接口只处理公开文章，并按各自规则计算相邻、相关和目录数据。

设计计数系统时先定义窗口数学规则，再选择标识和并发控制。自然日、固定小时桶和滚动窗口不同；计数防重复也不等于抗刷。要扩容时，先用数据规模和竞争指标说明问题，再改变一致性模型。
