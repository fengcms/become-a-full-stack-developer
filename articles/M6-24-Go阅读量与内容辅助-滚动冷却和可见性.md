# 成为全栈·Go 后端篇·阅读量与内容辅助：滚动冷却为什么不能按天分桶

> 去重规则若是“同一用户 24 小时内只计一次”，就必须保存上次计数的具体时刻。按自然日分桶会在午夜边界制造错误结果。

> 本文代码快照：提交 ceac4e0。阅读计数使用滚动 24 小时窗口；内容辅助只向有权限的调用方返回公开文章。

## 前言：自然日不是 24 小时

访客在 23:55 阅读一篇文章，隔天 00:05 再次访问。按自然日分桶会将两次访问分到不同日期，仅隔十分钟就计两次；而真正的滚动 24 小时冷却应等到次日 23:55 才再次计数。反方向也一样：上午 9 点与当天晚上 11 点相隔 14 小时，按“每天一次”可能都计数，但滚动窗口只计一次。

M6 按匿名访客或登录用户建立文章级去重记录，比较当前毫秒时间与上次计数时间。达到 86,400,000 毫秒才更新记录并增加文章阅读量。锁定文章、维护去重行和原子更新计数都在同一事务内。

本文还会看相邻文章、相关文章、TOC 和面包屑等辅助数据：它们共享公开可见性规则，却使用不同的计算方法和成本边界。

## 一、去重键要能识别访问主体

登录访问者的 key 使用 user ID；匿名访问者使用 IP 与 User-Agent 组合后计算 FNV 标识。数据库只保存短 key，而非原始 IP 和 UA。该方式减少个人信息的直接存储，但 FNV 不是密码哈希或匿名化的强隐私保证：输入空间可能被猜测，且 IP/UA 会变化或被伪造。文章计数用它近似区分访客，不应当作身份认证。

代理配置影响匿名 IP 的可信来源。若应用直接信任任意 X-Forwarded-For，客户端可以伪造地址绕过去重；Go 实现只在 RemoteAddr 命中可信代理列表时解析转发链。User-Agent 也由客户端控制，所以匿名 key 只能是轻量去重启发，不是抗刷系统。

会员访问按 user ID 计数，不依赖浏览器地址变化。退出登录后访问会退回匿名键，登录前后是否合并历史没有在当前模型里处理。身份规则应按契约和数据模型明确描述。

## 二、锁住文章后执行滚动窗口

Views 在事务里使用 database.Lock 读取公开文章，再计算去重 key。若没有记录，插入当前时间并增加 view_count；如果已存在且 now - created_at 大于等于 24 小时，则更新时间并增加；否则只返回现有计数。

~~~text
事务开始
  ↓ 锁定已发布文章
  ↓ 计算 member key / anonymous key
  ↓ 读取该 article 的 dedup row
  ├─ 不存在：插入 + 计数增加
  ├─ 已存在且冷却到期：更新时间 + 计数增加
  └─ 未到期：保持计数
  ↓ 读取新计数并提交
~~~

将文章作为竞争点锁定，使相同文章的并发请求按事务顺序检查同一个窗口；去重表唯一约束防止一主体一文章出现重复行；文章计数在同一事务更新。若并发实现只做“读记录后 insert”，两个请求都可能读到不存在。唯一约束和冲突处理应与锁策略共同验证。

条件是滚动毫秒差值，不按本地时区、午夜或日历日期切分。控制时钟的测试可覆盖 23:55/00:05、恰好 24 小时、少一毫秒和多个并发请求。使用固定时钟还能避免测试受执行时间影响。

## 三、计数准确和反刷能力是两件事

当前规则能减少同一标识的重复请求，但不能证明是真实人在读。攻击者可换 IP、清理 UA 或控制代理流量；一个共享 NAT 后的不同访客也可能被合并。若产品需要更强的防刷，应结合网关、风险评分、限速或分析系统，且要另行定义隐私和成本。

读取次数的写入在每个访问冷却到期后更新文章行，热点文章会成为锁竞争点。当前选择的优势是事务和计数语义清楚；大规模下要用负载实验判断是否改成异步聚合或分片计数。变更后仍要定义用户看到的是精确值还是最终一致近似值，不能只讨论吞吐。

阅读量返回的是事务完成后的计数快照。其他并发访问可能在响应发出前又改变它，因此客户端看到的数字是某个时刻的值，不代表响应一直最新。

## 四、相邻和相关文章的可见性

Adjacent 先要求目标文章已发布，再分别寻找发布时间更早和更晚的 published 内容，并以时间与 ID 排序。不存在任何一侧时返回 null stub。相邻逻辑只基于发布时间，不是按 ID 排序，也不会包含草稿。相同发布时间记录的定位规则要以实现和测试为准。

Related 同样先校验目标文章公开，再遍历其他公开且未删除文章，对共享标签计分、同分类加分，按分数和 viewCount 排序，限制返回数量最多 10。当前实现把候选文章取到 Go 内存中计算，不是数据库全文相似度搜索；当文章规模增长时，应该评估查询成本和内存占用，而不能假定 limit=10 就只读取了 10 篇。

两种接口都复用 ActiveArticles 和 published 条件，避免把私稿放到公开推荐中。可见性规则比推荐算法复杂度更关键。

## 五、TOC 要和 Markdown 展示的锚点一致

ParseToc 按行识别 Markdown # 标题，忽略反引号代码围栏内的标题。锚点小写化，只允许指定字符集合，重复标题追加编号后缀，长度按 JavaScript UTF-16 语义限制。中文和 emoji 会让 Go rune 与 JS string length 不同，因此实现使用 unicode/utf16 helper 复刻边界。

这仍是一个受限 Markdown 标题解析器，不是完整 CommonMark/remark AST。列表中出现的伪标题、缩进代码块、不同围栏形式可能需要按冻结 Node 行为进一步测试。前端渲染器必须用相同锚点规则，否则 TOC 链接可能指向不存在的 DOM id。完整渲染细节应以客户端页面验收为准。

## 六、辅助接口的测试清单

- 阅读量：未发布文章隐藏、匿名和会员 key、24 小时前后边界、午夜、并发重复；
- Adjacent：两侧均有/只有一侧/均无、相同时间边界和软删除过滤；
- Related：共享标签权重、同分类加分、viewCount 平局、limit 上限和私稿排除；
- TOC：代码围栏、中文、emoji、重复标题、长度边界；
- Breadcrumb：根节点、深层父链、缺失分类与无效循环数据；
- 跨库：事务/行锁与 SQLite 单写、分页或排序差异。

每项检查响应形状和数据库后置状态。辅助功能不应拖垮文章正文读取；各自查询可以独立失败并由客户端合理降级，这属于端到端用户体验需要进一步验收的部分。

## 小结：先准确说明规则，再选择计数优化

M6 的阅读去重窗口是精确滚动 24 小时，不是自然日；会员按 user ID，匿名按可信 IP 与 UA 组合形成 key；文章锁、去重记录和计数增量在事务中。辅助接口只处理公开文章，并按各自规则计算相邻、相关和目录数据。

设计计数系统时先定义窗口数学规则，再选择标识和并发控制。自然日、固定小时桶和滚动窗口不同；计数防重复也不等于抗刷。要扩容时，先用数据规模和竞争指标说明问题，再改变一致性模型。
