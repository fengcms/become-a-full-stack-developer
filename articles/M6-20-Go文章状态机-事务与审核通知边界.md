# 成为全栈·Go 后端篇·文章状态机与审核通知：事务该由谁持有

> 文章投稿并不是改一个 status 字符串。权限、前置状态、标签关系、发布时间和通知必须在同一个可验证的业务事务里协调。

## 前言：CRUD 形式下面藏着状态机

文章系统至少有 draft、pending 和 published 等状态。会员创建文章时不能通过请求直接跳过审核；投稿动作只允许从草稿进入待审核；管理员审核通过后发布；发布文章被会员改写时需要重新审核；重复审核不能重复发送发布通知。

如果 handler 把状态字段直接写回数据库，用户可以用一个 status 参数尝试越权。若先更新文章，再另一个请求写通知，通知失败时文章已经发布但作者没有收到通知。M6 将状态转换、文章字段和标签关系纳入事务，并让 notification helper 使用调用者提供的 tx。

本文从创建、更新、投稿审核和删除几个动作说明事务边界。重点不是状态名，而是“谁可执行、允许从哪种前态转移、失败时留下什么”。

## 一、先把状态转移表达为动作

保存草稿、提交审核、批准发布和撤稿不是同一个动作。普通保存应尽可能保留当前工作流状态；明确的 transition endpoint 才改变状态。创建会员文章时，如果请求意图是 published，服务端会降为 pending；普通会员不能通过 body 自授 slug 或发布权限。

这两条限制在创建入口就写死了：

~~~go
// internal/article/mutation.go（Create 开头，节选）
func (s *Service) Create(ctx context.Context, actor values.Actor, in values.Fields) (map[string]any, error) {
	now := s.Now().UnixMilli()
	status := in.String("status")
	if status == "" {
		status = "draft"
	}
	// 会员只能投稿，不能通过创建请求跳过审核。
	if actor.Rank() < 2 && status == "published" {
		status = "pending"
	}
	slug := in.Text("slug")
	if actor.Rank() < 2 {
		slug = nil
	}
	if slug != nil && (!ValidSlug(*slug)) {
		return nil, fault.Field("slug", "slug非法或为预留路径")
	}
~~~

`actor.Rank() < 2` 是这段代码的核心判据：角色秩小于 2 即普通会员，达到 2 才是 editor 及以上。两处降级都用同一个判据——发布意图被改写成 `pending`，请求里带的 slug 被直接丢弃。第二处写成 `slug = nil` 而不是报错，是因为会员仍应能正常创建文章，只是拿不到自定义地址。`ValidSlug` 在降级之后才执行，检查的是最终留下来的那个非空 slug。

`ValidSlug` 同时挡两类输入：格式不符，以及和固定路由撞名。后者靠一份保留词清单实现，清单里是 `admin`、`categories`、`tags`、`comments` 这类后台与聚合路径；如果允许文章占用它们，路由行为会变得无法预测。

投稿转换锁定文章，确认调用者是作者或管理员，且当前状态是 draft，再设为 pending。审核通过要求文章处于 pending，改为 published。已处于目标状态时幂等返回，不重复新增发布通知。用户身份、资源所有权和状态前提都在服务端判断。

表格把常见规则展开：

| 动作 | 操作者 | 前置状态 | 后置状态 | 副作用 |
|---|---|---|---|---|
| 会员创建并请求发布 | member | 尚无文章 | pending | 创建文章及标签关系 |
| 投稿 | 作者或 admin | draft | pending | 更新修改时间 |
| 审核通过 | 有管理资格者 | pending | published | 记录发布时间并写通知 |
| 会员修改已发布内容 | 作者 | published | pending | 重新进入审核 |
| 重复发布到已发布状态 | 允许的管理动作 | published | published | 不重复通知 |
| 删除 | 作者或 editor/admin | 未删除 | 软删除 | 清标签关系并释放 slug |

这张表是行为摘要，具体角色层级和路径权限以契约及代码为准。不能只用角色判断而不检查 owner，也不能只检查 owner 而忽略状态合法性。

## 二、锁定文章并在事务中复核前态

Transition 开始数据库事务后锁定目标文章，再读取当前状态、作者和发布时间。事务外先查再写会让状态在两步之间被并发请求改变；锁后读取把业务决策建立在当前事务可见的前态上。

整个转换逻辑集中在一个私有函数里：

~~~go
// internal/article/mutation.go（transitionTx，节选）
// transitionTx 锁定文章并执行前态检查，发布通知与状态同事务提交。
func (s *Service) transitionTx(tx *gorm.DB, id int64, actor values.Actor, action, status string, a *model.Article) error {
	current, err := Get(database.Lock(tx), strconv.FormatInt(id, 10))
	if err != nil {
		return err
	}
	*a = current
	if action == "submit" {
		if !actor.Allows("admin", a.AuthorID) {
			return fault.New(fault.Forbidden)
		}
		if a.Status != "draft" {
			return fault.New(fault.State)
		}
		status = "pending"
	}
	if action == "approve" {
		if a.Status != "pending" {
			return fault.New(fault.State)
		}
		status = "published"
	}
	// 幂等置位直接返回，避免重复发布通知。
	if status == a.Status {
		return nil
	}
	now := s.Now().UnixMilli()
	var published *int64
	if status == "published" {
		published = a.PublishedAt
		if published == nil {
			published = &now
		}
	}
	if err = tx.Model(&model.Article{}).Where("id = ?", id).Updates(map[string]any{
		"status":       status,
		"published_at": published,
		"updated_at":   now,
	}).Error; err != nil {
		return err
	}
	if err := tx.First(a, id).Error; err != nil {
		return err
	}
	if status == "published" {
		return notification.Published(tx, *a, now)
	}
	return nil
}
~~~

`Get(database.Lock(tx), ...)` 一次做两件事：按 id 读出文章，并让 PostgreSQL 与 MySQL 对这条记录加行锁。读出后 `*a = current` 把结果写回调用者的指针，外层 `Transition` 才能返回最终数据。

两个动作的检查各有侧重。`submit` 先用 `actor.Allows("admin", a.AuthorID)` 判断调用者是管理员还是文章作者本人，再要求前态必须是 `draft`，否则返回状态错误。`approve` 没有单独的角色检查，因为传输层的 `x-authz` 已经把这一操作限定在管理角色上，函数内只确认前态是 `pending`。权限因此是分层承担的：能不能调这个接口由 x-authz 决定，能不能对这篇、在这个状态下执行由领域层决定。

`if status == a.Status { return nil }` 是幂等出口，重复审核已发布的文章不会写出第二行通知。`published_at` 的取法也值得留意：文章已有发布时间就保留，只有从未发布过才填入当前时间，这样撤稿后重新发布的文章不会刷新出一个新的发布时间。

更新状态时设置 published_at。第一次发布填入当前 UTC 毫秒时间；如果文章曾经发布且后续重新审核，已有发布时间按实现规则保留。更新文章后重新读取，再使用最终数据创建通知。任何一处 SQL 错误都从 callback 返回，回滚整个事务。

相同文章上并发审核时，第二个请求拿到锁后会看到新的状态。若动作要求 pending，而前一个已发布，第二个就按非法前态返回，而不是再跑一遍发布工作流。重复状态置位则走幂等出口。

## 三、通知不是事务之外的“顺手调用”

发布通知记录存放在 notification 表。notification.Published 接受调用者传入的 tx，不自行开启新事务。这样文章状态与通知处于同一提交边界：通知插入失败，发布回滚；发布状态写入失败，通知不会单独留下。

它的实现短到可以整段读完：

~~~go
// internal/notification/event.go（节选）
// Published 在调用者事务内创建文章发布通知，失败应使状态更新一起回滚。
func Published(tx *gorm.DB, a model.Article, now int64) error {
	n := model.Notification{
		UserID:    a.AuthorID,
		Type:      "article_published",
		Title:     "文章已发布",
		Body:      values.Text(a.Title),
		Link:      values.Text(fmt.Sprintf("/articles/%d", a.ID)),
		CreatedAt: now,
	}
	return tx.Create(&n).Error
}
~~~

三个参数里最关键的是第一个：函数接收 `tx *gorm.DB`，而不是自己从某处取连接，这就是“不自行开启事务”的写法。包的注释也写明“使用调用者的事务写入明确的领域通知”。这样 `Published` 不提供任何默认路径，调用者无法在忘记传事务时“看起来也能跑”。

注意函数体内没有 push、没有邮件、没有队列投递，只有一行 `tx.Create(&n)`。通知记录落库和文章状态落库因此共享同一个提交点，两者要么都成功，要么都回滚。这个边界之外的事——把通知送到用户设备——不在数据库事务能保证的范围内。

这不等于事务可靠地向用户设备发送 push。当前领域通知是数据库记录；外部推送需要队列、outbox 或重试设计。数据库事务不能覆盖微信、邮件或 HTTP 服务。应把“写通知行”和“向外发送消息”区分开，避免把持久化通知能力描述成实时送达保证。

重复发布不重复创建通知，靠状态前态和目标状态比较共同保证。若未来增加发送端，消息消费也必须幂等，不能因为数据库只创建了一行就假设外部投递只发生一次。

## 四、编辑内容为什么可能重新进入审核

会员编辑已发布文章时，正文改变而状态仍保持 published，会让修改内容直接出现在公开页面，绕过审核。服务根据原状态和新意图，将会员的发布内容修改转成 pending；管理角色可依契约执行相应操作。更新标签、分类投影与文章字段也在同一事务。

字段 presence 同样重要：未提交标签不应改变关系，显式空数组才清除全部标签；文章分类变更时，外键 category_id 与响应冗余字段 category_name/category_slug 同步更新。若只更新一部分，查询可能呈现旧分类名称与新分类 ID。

字段到列的映射集中在一个函数里：

~~~go
// internal/article/mutation.go（updatePatch，节选）
// updatePatch 按字段存在性组装补丁，保留未提交、NULL 和零值的区别。
func (s *Service) updatePatch(tx *gorm.DB, a model.Article, actor values.Actor, in values.Fields) (map[string]any, error) {
	patch := map[string]any{"updated_at": s.Now().UnixMilli()}
	for key, col := range map[string]string{
		"title":      "title",
		"content":    "content",
		"summary":    "summary",
		"coverImage": "cover_image",
	} {
		if in.Has(key) {
			patch[col] = in[key]
		}
	}
	if patch["cover_image"] == "" {
		patch["cover_image"] = nil
	}
	// 分类名称和 slug 是响应投影，和外键必须一起更新。
	if in.Has("categoryId") {
		name, slug, err := categoryFields(tx, in.Number("categoryId"))
		if err != nil {
			return nil, err
		}
		patch["category_id"] = in.Number("categoryId")
		patch["category_name"] = name
		patch["category_slug"] = slug
	}
	if actor.Rank() >= 2 && in.Has("slug") {
		slug := in.Text("slug")
		if slug != nil && !ValidSlug(*slug) {
			return nil, fault.Field("slug", "slug非法或为预留路径")
		}
		patch["slug"] = slug
	}
	status := a.Status
	if in.Has("status") {
		status = in.String("status")
	}
	// 已发布文章被会员改写后重新审核，避免审核结果覆盖新正文。
	if actor.Rank() < 2 && (status == "published" || a.Status == "published") {
		status = "pending"
	}
	patch["status"] = status
	var published *int64
	if status == "published" {
		published = a.PublishedAt
		if published == nil {
			n := s.Now().UnixMilli()
			published = &n
		}
	}
	patch["published_at"] = published
	return patch, nil
}
~~~

整个函数只往 `patch` 这一个 map 里塞键值，绝不直接落库，落库动作留给调用它的 `updateTx`。这样“决定改什么”和“执行更新”被分成两步，中间可以插入标签同步，失败时整体回滚。

三个 `in.Has` 判断对应三种不同的语义。文本字段只有提交了才进补丁，没提交就完全不动。`cover_image` 多一步：显式传空字符串会被转成 `nil`，把封面真正清空，而不是留一个空串。`categoryId` 一旦出现，就必须同时更新 `category_id`、`category_name` 和 `category_slug` 三项——后两项是响应里的冗余投影，只改外键会让接口返回新分类的 ID 配旧分类的名字。slug 的修改额外要求 `actor.Rank() >= 2`，普通会员即使提交了也会被忽略。

状态那一小段是审核规则的核心：`if actor.Rank() < 2 && (status == "published" || a.Status == "published")`。条件里同时看新意图和当前状态，只要其中任一侧是已发布，普通会员的写入就被压回 `pending`。这正好覆盖“会员编辑已发布文章”和“会员试图把草稿直接置为已发布”两种绕过路径。

标签同步先清旧关系，再按名字或 slug 找目标标签并写关系，使用冲突忽略应对重复映射。事务保证中途失败时旧关系恢复，不出现半套标签。文章修改和审核通知也共用 tx。

标签同步的实现只有二十来行：

~~~go
// internal/article/mutation.go（syncTags）
func syncTags(tx *gorm.DB, id int64, names []string, now int64) error {
	if err := tx.Where("article_id = ?", id).Delete(&model.ArticleTag{}).Error; err != nil {
		return err
	}
	if len(names) == 0 {
		return nil
	}
	var tags []model.Tag
	if err := tx.Where("name IN ? OR slug IN ?", names, names).Find(&tags).Error; err != nil {
		return err
	}
	for _, t := range tags {
		r := model.ArticleTag{
			ArticleID: id,
			TagID:     t.ID,
			CreatedAt: now,
		}
		if err := tx.Clauses(clause.OnConflict{DoNothing: true}).Create(&r).Error; err != nil {
			return err
		}
	}
	return nil
}
~~~

策略是“先清后写”。第一步无条件删除这篇文章已有的全部标签关联，第二步如果 `names` 为空就直接返回——这就是“未提交标签不动关系、显式空数组清空全部”的落地方式：调用方只有在 `in.Has("tags")` 为真时才会调它。

查询那一步用 `name IN ? OR slug IN ?` 同时按名字和 slug 匹配，因为用户可能填任一种。写关联时套了 `clause.OnConflict{DoNothing: true}`：如果传入的多个名字指向同一个标签，会生成重复的 `(article_id, tag_id)`，冲突忽略让重复映射不会报错。

整个过程都在调用者的事务里，所以“删了旧关系、写新关系写到一半失败”不会留在库里——事务回滚会把删除也一并撤销，旧标签关系恢复原状。

## 五、软删除和 slug 的路由含义

删除文章使用软删除字段保留业务历史，并清理 article_tags 关系，同时将 slug 设为空以释放唯一 slug。若只设置 deleted_at 而未释放 slug，新文章可能永远无法使用旧 URL；若物理删除主行，历史互动与数据迁移可能失去关联。

删除动作把这三件事写在一个事务里：

~~~go
// internal/article/mutation.go（Delete，节选）
// Delete 软删除文章、释放 slug 并清除标签关联，保留历史业务记录。
func (s *Service) Delete(ctx context.Context, id int64, actor values.Actor) error {
	return s.DB.WithContext(ctx).Transaction(func(tx *gorm.DB) error {
		a, err := Get(database.Lock(tx), strconv.FormatInt(id, 10))
		if err != nil {
			return err
		}
		if !actor.Allows("editor", a.AuthorID) {
			return fault.New(fault.Forbidden)
		}
		if err := tx.Where("article_id = ?", id).Delete(&model.ArticleTag{}).Error; err != nil {
			return err
		}
		return tx.Model(&model.Article{}).Where("id = ?", id).Updates(map[string]any{
			"deleted_at": s.Now().UnixMilli(),
			"updated_at": s.Now().UnixMilli(),
			"slug":       nil,
		}).Error
	})
}
~~~

`Get(database.Lock(tx), ...)` 先锁住文章，既拿到 `AuthorID` 用于权限判断，也防止删除与同时进行的编辑交错。权限判据是 `actor.Allows("editor", a.AuthorID)`——作者本人可以删自己的文章，editor 及以上可以删任何人的。

三个写入按顺序发生：删掉 `article_tags` 关联、写入 `deleted_at`、把 `slug` 置为 `nil`。最后一步是释放地址的关键。之所以整段包在事务里，是因为漏掉任何一步都会留下不一致：只写 `deleted_at` 会让这个 slug 被永久占用，只清标签而不软删除则文章仍然可见。中间任何一步返回错误，前面的写入都会回滚。

删除事务先校验调用者权限，再更新关系与文章。对外查询显式使用 ActiveArticles scope 屏蔽软删除记录。软删除不意味着所有相关记录都删除：评论、历史、通知等保留策略要按具体实体定义，不能让 ORM 的默认关联级联替项目作决定。

scope 本体只有一行谓词：

~~~go
// internal/platform/database/scopes.go
// ActiveArticles 限定未软删除文章，供普通查询和关联查询共同使用。
// 固定 articles 表名避免 JOIN 时列名歧义；使用别名的离线审计需显式表达自己的谓词。
// 这是文章的查询规则，不会自动过滤其他表，也不替代 published 可见性判断。
func ActiveArticles(db *gorm.DB) *gorm.DB {
	return db.Where("articles.deleted_at IS NULL")
}
~~~

注释里的三条边界比代码本身更重要。第一，谓词固定写 `articles.deleted_at` 这个带表名的列，避免多表 JOIN 时和别的 `deleted_at` 混淆；一旦查询给 articles 起了别名，这个 scope 就不再适用，调用方必须自己写条件。第二，它只过滤文章表，不会顺带过滤评论或标签。第三，也是最容易忽略的一条：屏蔽软删除和判断 `published` 是两件独立的事——文章没被删掉，不代表它已经发布，可见性判断另有其地。

## 六、验证状态机的关键不是 happy path

至少测试以下前置与后置状态：

- 会员直接创建 published 仍进入 pending；
- 非作者会员不能修改他人文章；
- draft 可以投稿，published 不能被重复投稿；
- pending 可以审批，draft 不能直接审批；
- 发布通知插入错误时文章保持原状态；
- 重复设置 published 不新增第二条通知；
- 修改 category/tag 的中间 SQL 失败时，文章和关系均回滚；
- 删除后 slug 可按契约重新使用，公开读取仍不可见。

每个测试都要查数据库，不只观察返回状态码。时钟固定后，published_at 与 created_at 的边界也能确定。状态机一旦承载实际审核工作，就应把失败路径当作第一类用例。

## 小结：事务边界跟着业务动作走

M6 将状态规则留在 article service，HTTP 层负责协议边界；事务锁住文章、验证权限和前态，再更新状态、标签和通知。notification helper 透传同一个事务，确保数据库副作用共同提交。外部通知投递则另需可靠队列设计。

实现工作流时先定义动作和合法前态，再标出必须一起成功的数据。最后通过中间步骤失败和并发重复操作检查后置状态，CRUD 返回成功只是最表面的一层证据。
