# 成为全栈·Node 后端篇·数据库选型：关系型还是文档型

前面三篇我们把工程、框架、分层都铺好了。这一篇要碰一个让很多前端同学发怵的话题——**数据到底存哪、怎么存**。

我在带新人转全栈时观察到一个规律：写接口、写页面大家都敢上手，但一聊到"你这个数据为什么要建这张表、为什么要有外键"，很多人就卡壳了。这很正常，前端平时接触的"数据"是接口返回的一坨 JSON，而从"JSON"往回推到"数据库该怎么设计"，是一次思维范式的跳跃。

![成为全栈·Node 后端篇·数据库选型：关系型还是文档型](https://i-blog.csdnimg.cn/direct/7638c5f7137c4db299445f9eee381cbc.png)

所以这一篇，我想把"数据库选型"这件大事讲透，而且尽量不堆术语——你就当我们在决定：这个专栏网站的内容，该用什么样的柜子来装。

## 一、关系型 vs 文档型：两种"柜子"的哲学

市面上的数据库大体分两派，最典型的两位代表是 **PostgreSQL / MySQL（关系型）** 和 **MongoDB（文档型）**。

| 维度 | 关系型（表/行） | 文档型（文档/集合） |
|---|---|---|
| 数据形态 | 二维表，每行是固定结构的记录 | 类 JSON 文档，字段可灵活嵌套 |
| Schema | 建表时定死列，改结构要迁移 | 写入时随意，字段可不一致 |
| 关联 | 靠外键 + JOIN 表达"谁属于谁" | 倾向把关联数据直接嵌进文档 |
| 强项 | 强一致、复杂关联查询、事务 | 灵活、写入快、水平扩展容易 |
| 典型痛点 | 改表结构要谨慎 | 多层嵌套后查询与一致性头疼 |

举个具体例子。一个"文章"在文档型里可能长这样：

```json
{
  "title": "分层架构",
  "author": { "name": "FungLeo", "id": 7 },
  "tags": ["Node", "后端"],
  "comments": [ { "user": "张三", "text": "写得好" } ]
}
```

作者、标签、评论全塞进一篇文章文档里，读的时候一把取出来，爽。但代价是：你想统计"张三在所有文章下一共评论了多少次"，就得扫描所有文档——文档型不擅长这种跨文档聚合。

而在关系型里，文章、用户、标签、评论是**四张独立的表**，通过 `author_id`、`article_id` 这种外键串起来。要统计张三的评论数，一条 `JOIN + COUNT` 就完事。代价是：你写数据时得先想清楚它们之间怎么关联。

![关系型 vs 文档型：两种"柜子"的哲学](https://i-blog.csdnimg.cn/direct/0ac5114746fb4461a0a492c7c3afd8c7.png)

## 二、为什么我们选关系型

回到《领域建模》那篇（里面我们用真实系统把"文章/用户/分类/标签/评论"之间的关系画清楚了）[领域建模](https://blog.csdn.net/fungleo/article/details/164139553)，这个专栏网站的核心数据有几个特征：

1. **关联极其密集**：一篇文章属于一个作者、挂一个分类、贴多个标签、收一堆评论；一个用户有多篇文章、多个评论、多个点赞。
2. **需要强一致**：你删了分类，相关文章的分类字段得有交代；你发了评论，作者的"评论数"不能算错。
3. **需要复杂聚合**：热门文章排行、标签云计数、按分类筛选——全是跨表统计。

这三点恰好是关系型的舒适区。文档型那种"把评论嵌进文章"的写法，在我们这种"评论要独立审核、要计数、要分页"的场景下反而会处处别扭。

不过我得说句公道话，免得你把"关系型好"理解成"文档型差"。文档型在三类场景里是真的香：

**第一，以文档为中心的创作类数据。** 比如做一个"用户个性化草稿"功能，每个用户的草稿结构天差地别，今天多一个字段明天少一个，这种"schema 随写随变"的需求，关系型每次都得迁移，文档型直接塞进去就行。

**第二，超高写入吞吐、且几乎不跨文档聚合。** 设备上报的 IoT 日志、埋点事件流，每秒上万条，查询基本是"按设备 ID 拉最近 N 条"，文档型水平扩展的能力在这里碾压关系型。

**第三，需要无限水平扩展。** 关系型做分库分表是工程大活，文档型天生为分片设计。

所以选型的本质不是"哪个高级"，而是"你的关联多不多、要不要强一致、扩不扩得出去"。我们的专栏网站关联密、要强一致、初期根本用不上水平扩展——三者都指向关系型。等你去做别的业务，完全可能反过来选 MongoDB。**全栈工程师的价值，正在于能根据业务形状做判断，而不是背结论。**

还有一个很现实的原因：**关系型是行业通用技能**。SQL 这套语言几十年没大变，你今天用 SQLite 写的查询，明天换成 PostgreSQL 几乎不用改。而 MongoDB 的聚合管道是它自家的一套，迁移成本高。作为全栈工程师，把关系型吃透，是性价比最高的一笔投资。

## 三、具体落地：SQLite，而且是"一份代码双部署"的 SQLite

选了关系型，下一个问题是选哪个具体产品。我们的约束在《项目全貌》里就定过：这个后端要**既能跑在 Cloudflare 上（用 D1），又能跑在普通 Linux 服务器上**。而 Cloudflare D1 的底层就是 **SQLite**。

于是答案很自然——**统一用 SQLite 语义**。本地开发用 SQLite 文件（甚至内存库），上 Cloudflare 用 D1（它兼容 SQLite 的 SQL 方言）。这样同一份 schema、同一套查询代码，两套环境通吃。

有人会问：既然能跑在 Linux 服务器上，为什么不直接用 PostgreSQL，性能更强？答案是**双部署的一致性成本**。如果我们 Linux 用 PG、Cloudflare 用 D1，就等于要维护两套 SQL 方言、两套迁移脚本、两套类型定义——这和我们"一份代码双部署"的初衷直接相悖。SQLite 在 D1 与本地是同一套方言，代价只是放弃了 PG 的某些高级特性（如复杂存储过程、部分索引的精细控制），对一个内容型专栏网站完全够用。先让"能双部署"成立，再谈性能，这是优先级问题，不是技术退让。

但这里有个坑，引出我们第一个踩坑点（P-08）：**Node 自带了一个 `node:sqlite` 实验模块，为什么我们不用，而选了 `better-sqlite3`？**

原因很实在。`node:sqlite` 在 Node 22 下仍需用 `--experimental-sqlite` 启动标志，属于不稳定特性，而且它的 API 还在摇摆。而 `better-sqlite3` 是一个**预编译好的原生二进制**，装完即用，API 简洁（同步调用，对测试和简单脚本极其友好），最关键的是——它和 D1 共用同一套 SQLite SQL 方言，迁移到 Cloudflare 时几乎零成本。对一个要长期维护的项目，"启动不优雅的实验特性"是必须避开的雷。

## 四、适配层：把"脏活"收敛在边界（P-09）

选了 SQLite，真正的工程挑战才刚开始：**本地 SQLite 和 Cloudflare D1，驱动类型不一样**。如果让业务代码直接 `import` 各自的驱动，那整套 service 层就会被环境绑架，双部署就成了空话。

我们的解法是建一个**数据库适配层** `src/db/client.ts`，业务代码永远只认一个 `getDb()`：

```ts
export type Db = BetterSQLite3Database<typeof schema>;

let current: Db | null = null;

export const setDb = (db: Db): void => { current = db; };

export const getDb = (): Db => {
  if (!current) throw new Error('Database not initialized; call setDb() first.');
  return current;
};
```

注意两个关键点：

**第一，`Db` 类型被锁定为本地 SQLite 的 Drizzle 类型。** 业务层（`services/*`）只 `import { getDb } from '@/db/client'`，它根本不知道底层是本地还是 D1。

**第二，环境差异只在入口处被"消化"一次。** 本地入口 `index.ts` 调 `createLocalDb(env.DB_FILE)`；CF 入口 `worker.ts` 调 `createD1Db(env.DB)`。而 D1 驱动返回的类型和本地不同，它们之间的"受控转换"只发生在 `createD1Db` 这一处：

```ts
export const createD1Db = (binding: D1Binding): Db =>
  drizzleD1(binding, { schema }) as unknown as Db;
```

这就是 P-09 想强调的纪律——**`as unknown as Db` 这种"危险转换"在整个项目里只出现一次**。D1 和本地 SQLite 共享同一个 Drizzle 的 SQLite 内核，所以这次转换是安全受控的；而它一旦被收口到边界，业务层就彻底无感了。如果这层转换散落在十几个文件里，哪天 D1 类型一变，项目就崩得到处都是。

`src/db/client.ts` 顶部那句注释说得好：**"业务代码统一通过 getDb() 访问，不感知底层是本地 SQLite 还是 Cloudflare D1——'脏活'收敛在边界。"** 适配层真正的价值，不是"能跑"，而是"让脏活有且仅有一个出口"。

## 五、一个必须知道的 SQLite 脾气

SQLite 有个容易被坑的点：**外键约束默认是不开启强制的**（严格说是 `PRAGMA foreign_keys` 默认 off）。也就是说，即便你写了 `FOREIGN KEY (author_id) REFERENCES users(id)`，如果你硬插一条 `author_id` 指向不存在用户的文章，SQLite 默认不会拦你。

我们的应对是：**父记录的存在性由应用层保证**。比如建文章时，service 层会先确认作者存在；删分类时，会先想清楚关联文章怎么处置（这部分在分类树那篇 {{LINK:M1-16}} 细讲）。这意味着——**数据库的 FK 是"声明"，真正的强制在代码里**。这是 SQLite 路线必须记牢的一课，也是为什么"领域建模"不能只停留在画 ER 图，得落到代码里的校验。

## 六、小结与前瞻

这一篇我们定了数据库的"大政方针"：

1. **选关系型**：关联密集、要强一致、要复杂聚合，关系型最对味；且 SQL 是通用硬技能。
2. **落地用 SQLite 语义**：因为 Cloudflare D1 底层就是 SQLite，一份代码能双部署。
3. **P-08**：用 `better-sqlite3` 而非实验性的 `node:sqlite`，启动优雅、API 稳、D1 兼容好。
4. **P-09**：建 `db/client.ts` 适配层，`getDb()` 类型锁定，D1 的 `as unknown as Db` 受控转换**全项目只此一处**，业务层零感知。
5. **SQLite 外键默认不强制**：父存在性由应用层兜底，不能迷信数据库约束。
