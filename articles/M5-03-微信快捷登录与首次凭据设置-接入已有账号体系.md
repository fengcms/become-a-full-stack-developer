# 成为全栈·Taro 小程序篇·微信快捷登录与首次凭据设置：接入已有账号体系

> 微信让用户少输入一组密码，但内容仍属于我们自己的会员。登录入口变了，用户身份的所有权不能跟着散掉。

## 前言：这个需求最凶的地方不在登录按钮上

作者提需求的时候附了一个约束：**不要把账号体系做复杂。** 微信登录能建用户，这用户之后能设用户名密码、在网站和 APP 登录；已有账号合并、绑定、解绑本轮不做。

这个约束帮我省掉了大批容易失控的分支。但它也直接把最凶的那个问题摆到了台面上：

**如果不做合并，用户心里的"我明明在这个网站注册过"凭什么被满足？**

我第一版文案写的是「微信登录」，四个字挂在按钮上。结果测试的同事点完就问：**"我以前在网站注册的那个号呢？登进来变成另一个人了？"**

技术上他是对的。这篇讲客户端怎么接这条最小流程 —— 后端实现另有一篇展开，这里重点看界面、会话和失败路径怎样承接它。而"文案必须承担产品边界"这件事，是这次踩出来的。

## code 只是平台凭证，不是我们的令牌

认证页把三种入口收在同一个函数里：微信快捷登录、用户名密码登录、注册后登录。前置校验不同，但最终都落到同一个会话对象上 —— **没必要为每种入口各写一套成功处理。**

```ts
// src/pages/auth/index.tsx（节选）：先做前置校验，再决定走哪条分支。
async function login(wechat = false) {
  if (busy) return;
  if (!wechat && (!username.trim() || password.length < 8)) {
    setError("请填写用户名和至少 8 位密码");
    return;
  }
  let result: Auth;
  if (wechat) {
    const { code } = await Taro.login();
    if (!code) throw new Error("未取得微信登录凭证，请重试");
    result = await api<Auth>("/auth/wechat/callback", "POST", { code }, false);
  } else
    result = await api<Auth>(
      register ? "/auth/register" : "/auth/login",
      "POST",
      { username: username.trim(), password, ...(register ? { email: email.trim() } : {}) },
      false,
    );
```

`Taro.login()` 返回的 code **不能直接当文章接口的 Bearer**。它要送到后端，由后端向微信换身份，再返回自己的 `AuthResult`。

保存下来的是后端 `AuthResult`，不是微信 code。文章、收藏、评论、投稿继续用系统 accessToken，刷新继续用系统 refreshToken。

AppSecret 留在后端部署 Secret 里，小程序只需要 AppID 和 code。**不能为了让按钮跑通把换码过程搬进客户端** —— 客户端产物可被检查，"放在环境变量里"也不会让它变成服务器秘密。

## 首次建号与已有账号登录，必须明确分开

| 用户情况 | 本轮入口 | 后续结果 |
|---|---|---|
| 从未使用本系统 | 微信快捷登录 | 首次创建独立会员 |
| 已用微信创建过会员 | 微信快捷登录 | 回到对应系统会员 |
| 已有网站用户名密码 | 账号登录 | 回到原有会员 |
| 微信会员尚无本地凭据 | 会员中心首次设置 | 同一 userId 获得密码登录能力 |

这四行其实是三个产品判断的落点：微信身份能不能等同于会员身份、已有会员从哪条路回来、同一会员能不能拥有第二种登录方式。**先把判断写下来，界面提示才有依据** —— 而不是等用户撞上冲突再补一句解释。

第四行**不是把两个已有账号合并**。如果填写的用户名已被别人使用，应该按服务端冲突反馈处理，**不能拿"占用用户名"当作"帮我绑定老账号"的暗号**。

所以认证页现在明确写着：首次微信登录创建独立会员，已有网站账号请密码登录，本期不合并账号。这段文字承担实际产品边界，比按钮旁一个小微信图标重要得多。

## 登录成功，要回到用户原来的任务

游客可能从收藏、评论或编辑器进入认证。成功后，**页面栈有来源就 `navigateBack`，否则进会员 Tab。**

```ts
// src/pages/auth/index.tsx（节选）：成功出口对两种登录共用。
setSession(result);
setPassword("");
setConfirm("");
Taro.showToast({ title: "登录成功", icon: "success" });
if (Taro.getCurrentPages().length > 1) await Taro.navigateBack();
else await tab("member");
```

用户名密码注册和微信登录共用这个出口，所以**清理输入状态、提示、跳转三件事只写一遍**。

失败则保持当前页面与错误文案，让用户可以改输入或换另一入口，**不强行跳到一个"登录失败页"**。跳转过去等于把用户的输入全丢了，那比留在原地更糟。

当前有 `busy` 状态防重复触发。但**它改善按钮体验，不替代后端对重复身份创建的唯一性处理** —— 两次客户端调用仍可能在网络与设备条件下同时发生，真正的会员映射要由服务端保证。

回到来源也**不自动发送先前的评论或收藏**。登录证明身份，写操作仍要由用户点击。把认证与业务重放分开，能少一批隐含参数与重复执行问题。

## 首次凭据设置入口由服务端资格驱动

会员中心检查 `canSetCredentials`，符合资格才展示「设置用户名和密码」，并说明以后可以在网站与 APP 登录同一个账号。设置页读的是 `/me/profile`，**不是只相信入口页缓存**。

```tsx
// src/pages/profile/index.tsx（节选）：资格为假时按钮保持禁用。
disabled={busy || (isSetup && !result.data?.canSetCredentials)}
```

提交成功后替换会话并返回来源：

```ts
// src/pages/profile/index.tsx（节选）：设置凭据后替换会话。
const auth = await api<Auth>("/me/setup-account", "POST", {
  username: username.trim(),
  password,
});
setSession(auth);
Taro.showToast({ title: "账号设置成功", icon: "success" });
Taro.navigateBack();
```

密码至少八位并确认一致，用户名做基本输入检查；**更完整的格式、占用与资格验证仍归后端。**

首次设置与修改密码在代码里相邻，语义却完全不同：

| 流程 | 需要提交 | 成功后的处理 |
|---|---|---|
| 首次设置凭据 | 新用户名 + 新密码 | 替换会话，返回来源，仍是同一 userId |
| 修改密码 | 旧密码 + 新密码 | 清空会话并要求重新登录 |

```ts
// 修改密码是另一条分支：成功后清会话并要求重新登录。
await api("/me/change-password", "POST", { oldPassword, newPassword: password });
setSession(null);
Taro.showToast({ title: "密码已修改，请重新登录", icon: "none" });
go("auth");
```

**不能拿"首次设置"端点绕过旧密码校验，也不能把它当成任意会员重设用户名的工具。**

## 线上 500 让我明白"配置好了"是什么意思

这次接入出现过一个真实现象：**AppID 和 AppSecret 都配了，前端也拿到 code 了，线上回调仍然 500。**

第一反应是查配置。查完发现配置没问题，于是开始怀疑代码。绕了一圈才发现根因在 Workers 对 `fetch` 的 `redirect` 参数支持上 —— **类型定义里有这个值，运行时却不认。**

这件事另有一篇专门分析，它给我的教训不是"要小心运行时差异"，而是更具体的一条：

> **"我配好了"只说明配置文件里有这几行，不说明运行时会用它们。**

所以客户端不能把所有 500 都描述成"密码错误"或"AppSecret 错误"。当前文案把微信不可用与普通失败分开：

```ts
// src/pages/auth/index.tsx（节选）：微信 500 与普通失败分开提示。
} catch (e) {
  setError(
    wechat && e instanceof ApiError && e.status === 500
      ? "微信登录暂不可用，请使用账号登录；服务端需配置匹配的 AppID 和 AppSecret。"
      : message(e),
  );
}
```

而**具体的 500 为什么发生，要看服务端日志，客户端文案只负责不让用户背锅**。

修复之后，开发工具做了真实线上微信登录，会员页出现「微信会员」和首次凭据设置入口。**这个证据证明真实登录与建号入口跑通，不等于已经人工完成"设密后跨 APP 登录"的完整矩阵。**

## 会话存储是客户端自己的责任

登录结果用带 API 基址的键存入平台本地存储。账号变化递增 epoch、清私有缓存和互动状态，**避免上一个会员的响应进入新界面**。

```ts
// src/core/session.ts（节选）：键带 API 基址，切换身份时递增代际。
const key = `befull:session:${API}`;
let current: Auth | null = null;
let epoch = 0;
export function setSession(value: Auth | null, identityChange = true) {
  current = value;
  if (identityChange) {
    epoch++;
    privateCache.clear();
  }
}
```

恢复会话时**只接受形状正确的缓存**，避免一份损坏的数据把应用带进半登录状态：

```ts
// src/core/session.ts（节选）：形状不符合就按游客启动。
export function restoreSession() {
  if (restored) return;
  restored = true;
  try {
    const saved = Taro.getStorageSync(key);
    if (
      saved?.user?.id &&
      typeof saved.refreshToken === "string" &&
      typeof saved.accessToken === "string"
    )
      current = saved;
  } catch {
    /* 无缓存以游客启动 */
  }
}
```

这个 `try` 里只有一句注释，没有错误处理 —— **因为"读不到就游客启动"是想要的行为，不是需要上报的异常。**

当前并非 HttpOnly Cookie，也不是 Flutter 的安全存储方案。**三端认证存储不混成一种实现**，这一点要说清楚。平台存储写入异常时提示"会话仅保留至本次关闭"。

密码与微信 code 不应进入调试日志；排查只记阶段和业务码。

## 一条完整验收路径应该包含什么

本地真实后端测试覆盖密码注册、会话与账号隔离；后端专项测试覆盖微信身份映射与首次设置规则；线上开发工具验证真实 code 换会话。**三种证据互补，不能合并成"所有场景都人工通过"。**

账号隔离是这条链路里最容易被忽略、也最应该在测试里固定下来的部分。它要证明的不只是"新会话生效"，还有**"旧请求不会把上一个账号的私有数据写回来"**：

```ts
// test/core.test.ts：切换账号后旧请求必须作废。
setSession(auth(1));
const old = api("/me/profile");
setSession(auth(2));
wait.resolve(ok("private-old"));
await assert.rejects(old, /账号已切换/);
assert.equal(session()?.user.id, 2);
```

退出登录则要保证代际递增，同时**不误伤公共阅读缓存**：

```ts
// test/core.test.ts：退出会话递增代际并保持公共缓存。
const old = sessionEpoch(),
  version = cache.revision();
setSession(null);
assert.ok(sessionEpoch() > old);
assert.equal(cache.revision(), version);
```

第二条断言我一开始漏了。退出登录后我把公共缓存也清了，结果**用户退登再登录，首页要重新拉一遍文章列表** —— 而公共数据根本没变。

现在这条断言锁住了"只清私有"这个决定。

完整人工矩阵建议这样走：游客微信建号 → 确认未设置资格 → 提交占用用户名 → 看到冲突且仍可修正 → 成功设置 → 确认 userId 保持一致、资格消失 → 网站与 APP 密码登录 → 回小程序确认数据归属。**重复点击和网络失败也要加进去。**

这是建议的路径，其中跨端真实人工矩阵**并没有在本轮全部执行**。保持这个区别，读者才知道下次交付还要验证什么。

## 从两个同名用户理解"占用"而非"绑定"

假设网站已有用户名 `writer` 的会员甲，微信首次登录创建会员乙。**乙在首次设置页面填写 `writer`，正确结果是占用冲突，而不是进入甲的收藏和文章。**

为什么这么严格？

用户名不是身份所有权证明。知道一个公开用户名的人很多 —— **如果仅凭填了相同名称就合并，相当于让任何微信身份接管它。** 真正绑定需要甲的认证或其他可信验证，本轮没有这一套流程。

乙改一个可用用户名，完成设置以后仍是乙。之后密码登录返回同一个 userId，原先的微信身份也仍对应它。

**这个具体样例比一句"跨端打通"更能解释承诺。**

同样，首次设置过程中令牌过期，客户端可以按普通认证请求规则刷新，但服务端仍重新判断资格。**若另一设备已经完成设置，当前页面的旧入口不应再次获得修改凭据权限** —— 按钮禁用与后端拒绝共同表达"一次性动作"，前者照顾体验，后者决定事实。

## 把最小流程做完整，比增加入口数量更有用

这次没有加入手机号、UnionID 跨应用绑定或老账号合并。它们都有独立的身份风险与产品规则，**不该顺手藏进一个登录按钮**。

当前流程已经表达了清楚的承诺：微信身份进入自己的会员体系，同一会员可以获得密码凭据，旧端继续使用既有登录。更多私人能力与会话竞态的处理，后面会分别展开。

做完这一轮，我对"最小实现"的理解变了一点。它不是"少做功能"，而是：

**把每一个产品判断显式写出来（哪怕写"本轮不做"），而不是让它藏在一个按钮的文案背后。**

那句"已有网站账号请密码登录，本期不合并账号"看起来像免责声明，但它是我能想到的**最有效的一段产品文案** —— 它把一个必然发生的用户困惑提前回答了。
