# 成为全栈·Taro 小程序篇·微信快捷登录与首次凭据设置：接入已有账号体系

> 微信让用户少输入一组密码，但内容仍属于我们自己的会员。登录入口变了，用户身份的所有权不能跟着散掉。

{{IMG:M5-03-封面}}

## 前言：一个按钮，为什么先讨论账号关系

作者提出小程序登录需求时，同时给了一个教学约束：不要把账号体系做得太复杂。微信登录可以建用户，这个用户之后能设置用户名密码，在网站和 APP 登录即可；已有账号合并、绑定、解绑都不在本轮范围。

这个约束帮我们省掉了许多容易失控的分支，也给前端文案提出要求。不能只写“微信登录”，让已有会员误以为会自动回到网站账号。

各位看官，这篇讲客户端如何接入这条最小完整流程。后端实现已经在 [微信登录与首次账号设置]({{LINK:M1-33}}) 展开，这里重点看界面、会话和失败路径怎样承接它。

## 一、code 只是平台凭证，不是我们的令牌

认证页调用 `Taro.login`，把 code 送到后端既有 provider 回调路径：

```ts
// src/pages/auth/index.tsx
const { code } = await Taro.login();
if (!code) throw new Error('未取得微信登录凭证，请重试');
const result = await api<Auth>(
  '/auth/wechat/callback', 'POST', { code }, false
);
setSession(result);
```

最后一行保存的是后端 AuthResult，不是微信 code。文章、收藏、评论和投稿接口继续使用系统 accessToken；刷新继续使用系统 refreshToken。

AppSecret 留在后端部署 Secret 中，小程序只需要 AppID 与 code。不能为了让按钮跑通，把服务端换码过程搬进客户端。客户端产物可被检查，“放在环境变量里”也不会让它变成服务器秘密。

## 二、首次建号与已有账号登录，要明确分开

| 用户情况 | 本轮入口 | 后续结果 |
|---|---|---|
| 从未使用本系统 | 微信快捷登录 | 首次创建独立会员 |
| 已用微信创建过会员 | 微信快捷登录 | 回到对应系统会员 |
| 已有网站用户名密码 | 账号登录 | 回到原有会员 |
| 微信会员尚无本地凭据 | 会员中心首次设置 | 同一 userId 获得密码登录能力 |

第四行不是把两个已有账号合并。如果填写的用户名已被别人使用，应该按服务端冲突反馈处理，不能拿占用用户名作为“帮我绑定老账号”的暗号。

当前认证页明确提示：首次微信登录创建独立会员，已有网站账号请密码登录，本期不合并账号。这段文字承担实际产品边界，比按钮旁一个小微信图标更重要。

## 三、登录成功，回到用户原来的任务

游客可能从收藏、评论或编辑器进入认证。成功后，页面栈有来源就 navigateBack，否则进入会员 Tab。用户名密码注册与微信登录共用这个成功出口。

认证页还清空密码与确认密码状态，展示成功反馈。失败则保持当前页面与错误文案，让用户可以改输入或选择另一入口，不强行跳到一个“登录失败页”。

当前认证操作有 busy 状态防重复触发与 loading。它改善按钮体验，但不替代后端对重复身份创建的唯一性处理。两次客户端调用仍可能在网络与设备条件下发生，真正的会员映射要由服务端保证。

回到来源也不自动发送先前的评论或收藏。登录证明身份，写操作仍要由用户点击。把认证与业务重放分开，能少一批隐含参数与重复执行问题。

## 四、首次凭据设置入口由服务端资格驱动

会员中心检查 `canSetCredentials`，符合资格时展示“设置用户名和密码”，并说明以后可以在网站与 APP 登录同一个账号。

设置页再次读取 `/me/profile`，不是只相信入口页缓存。只有服务端仍明确给出资格，确认按钮才允许提交；缺失或 false 按不能设置处理。

```ts
const auth = await api<Auth>('/me/setup-account', 'POST', {
  username: username.trim(), password
});
setSession(auth);
```

这个端点返回新的 AuthResult，客户端替换会话，再返回来源。密码至少八位并确认一致，用户名做基本输入检查；更完整的格式、占用与资格验证仍归后端。

首次设置与修改密码是不同流程。修改密码要提交旧密码，成功后当前客户端退出重新登录。不能拿“首次设置”端点绕过旧密码校验，也不能把它作为任意会员重设用户名的工具。

## 五、真实线上失败让“配置好了”露出另一层含义

本次接入曾出现一个真实现象：AppID 和 AppSecret 已配置，前端拿到了 code，线上回调仍返回 500。问题最后落在 Workers 对 fetch redirect 参数的运行时差异上。

客户端因此不能把所有 500 精确描述成“密码错误”或“AppSecret 错误”。当前文案提供微信暂不可用和账号登录兜底，并提示后端需要匹配配置；详细定位依赖服务端安全日志。

这件事已经在 [Workers 登录排障]({{LINK:M1-34}}) 单独分析。它也提醒我们，平台 code、服务端换码、会员映射与会话返回是连续链路，任何一段成功都不能替下一段背书。

修复之后，开发工具进行了真实线上微信登录，会员页出现“微信会员”和首次凭据设置入口。这个证据证明真实登录与建号入口跑通，不等于已经人工完成真实账号设密后跨 APP 登录矩阵。

## 六、会话存储是客户端自己的责任

登录结果使用带 API 基址的键存入平台本地存储。账号变化递增 epoch，清理私有缓存和互动状态，避免此前会员的响应进入新界面。

当前并非 HttpOnly Cookie，也不是 Flutter 的安全存储方案。文章不把三端认证存储混成一种实现。平台存储读取异常时可以游客启动，写入异常则提示会话只能保留到本次关闭。

密码与微信 code 不应进入调试日志；错误排查记录阶段和业务码即可。上传、读取和刷新也都要尊重账号代次，登录模块并不是成功后可以不再关心身份。

## 七、一条完整验收路径应该包含什么

本地真实后端测试覆盖密码注册、会话与账号隔离；后端专项测试覆盖微信身份映射与首次设置规则；线上开发工具验证真实 code 换会话。证据之间可以互相补充，不能合并成“所有场景都人工通过”。

后续完整人工矩阵可以这样走：游客微信建号，确认未设置资格；提交占用用户名，看到冲突且仍可修正；成功设置，确认 userId 保持一致、资格消失；网站与 APP 密码登录，再回小程序确认数据归属。重复点击和网络失败也应加入。

这是建议的完整路径，其中跨端真实人工矩阵并没有在本轮记录中全部执行。保持这个区别，读者才能知道下一次交付还要验证什么。


## 从两个同名用户理解“占用”而非“绑定”

假设网站已有用户名 writer 的会员甲，微信首次登录创建会员乙。乙在首次设置页面填写 writer，正确结果是占用冲突，而不是进入甲的收藏和文章。

为什么这么严格？用户名不是身份所有权证明。知道一个公开用户名的人很多，如果仅凭填写相同名称就合并，相当于让任何微信身份接管它。真正绑定需要甲的认证或其他可信验证，本轮没有这一套流程。

乙改一个可用用户名，完成设置以后仍是乙。后续密码登录返回的应该是同一个 userId，原先微信身份也仍对应它。这个具体样例比一句“跨端打通”更能解释承诺。

同样，首次设置过程中令牌过期，客户端可以按普通认证请求规则刷新，但服务端仍重新判断资格。若另一设备已经完成设置，当前页面旧入口不应再次获得修改凭据权限。按钮禁用与后端拒绝共同表达一次性动作，前者照顾体验，后者决定事实。

作者以后要增加账号绑定，可以从这个反例出发补所有权验证和冲突处理，而不必推翻当前最小流程。我们先守住 userId 的边界，后续功能才有可信基础。

## 八、把最小流程做完整，比增加入口数量更有用

这次没有加入手机号、UnionID 跨应用绑定或老账号合并。它们都有独立的身份风险与产品规则，不该顺手藏进一个登录按钮。

当前流程已经表达了清楚的承诺：微信身份进入自己的会员体系，同一会员可以获得密码凭据，旧端继续使用既有登录。更多私人能力见 [会员中心边界]({{LINK:M5-19}})，会话竞态见 [请求层]({{LINK:M5-12}})。
