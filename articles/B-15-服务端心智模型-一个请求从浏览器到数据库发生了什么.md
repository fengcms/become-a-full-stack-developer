# 成为全栈·基础补充·服务端心智模型：一个请求从浏览器到数据库发生了什么

写这一章的时候，我把这个项目里一个真实请求的完整路径打印了出来。

`GET /articles?page=1&sort=-publishedAt` 这个请求，走过的代码是这样的：

```text
worker.ts: fetch(request, env)
  → readEnv(env)                    配置校验
  → createApp(appEnv, ...)          组装应用
  → app.onError(errorHandler)       挂错误兜底
  → app.use('*', corsMiddleware)    跨域
  → app.use('*', optionalAuth)      可选鉴权
  → articlesRoute                    路由匹配
  → guard('member')                  授权（跳过，匿名可读）
  → queryArticles                    业务：查缓存或查库
  → parsePage / buildSortSql         分页与排序（白名单）
  → atomic(db, [...])                查询执行
  → paginate(list, meta(...))        响应信封
```

**十八步。** 而这十八步分属五个不同的关注点，**排查任何一个问题，都得先知道它在哪一步。**

这篇就是把这张图讲清楚——因为新人最常做的事就是"在错误的层找 bug"。

## 第一段：请求进来之前

先说清楚一件容易被忽略的事：**请求到达你的代码之前，已经经过了两段你控制不了的旅程。**

```text
浏览器 → DNS 解析 → TCP 握手 → TLS 握手 → HTTP 请求
```

**B-10 讲的那几段就发生在这里。** 如果页面打不开，问题可能压根没到你的代码：

| 现象 | 大概率在哪一段 |
|---|---|
| "域名解析失败" | DNS |
| "连接超时" | 网络 / 防火墙 |
| "证书错误" | TLS |
| "502 Bad Gateway" | 你的服务没起来，但代理在 |

而 M1-34 讲的那个微信登录 bug 属于一个特殊类别：**请求到了 Cloudflare、但你的代码在执行请求时崩了**——所以它表现为"接口返回 500"，而不是"连不上"。

**这两类故障的现象完全不同**：前者是浏览器报错，后者是正常的 HTTP 响应里带着错误码。

**第一步判断永远应该是：请求到达我的代码了吗？** 没到达就往上游查，到达了才往下查。

## 第二段：入口与配置校验

进了你的代码，第一件事是读配置：

```ts
/**
 * Cloudflare Workers 入口（裁决 Q5）。复用同一套 Hono app，实现"一套代码双部署"。
 */
export default {
  async fetch(request: Request, env: AppEnv, _ctx: unknown): Promise<Response> {
    const appEnv = readEnv(env as Record<string, string | undefined>);
```

**注意 `readEnv` 是在每个请求上调用的**，不是启动时一次。

而它的实现是 zod 校验（B-19 讲过）：

```ts
export const readEnv = (src: Record<string, string | undefined>): AppEnv => schema.parse(src);
```

**这意味着配置错误会在第一个请求上就暴露**，而不是启动时。

**在 Workers 上这是必然的**——没有"启动"这个时刻，每个请求都是一个全新的 isolate。而 `wrangler.toml` 里那行注释就是在解释这类约束：

```toml
# 注意：即便生产用 STORAGE_DRIVER=r2、local 驱动永不被实例化，
# 顶层 node:fs 导入仍会求值，故本 flag 不可省。
compatibility_flags = ["nodejs_compat"]
```

**这一段最容易出的问题是"配置对了但没用上"。** B-19 讲过那个真实案例：本地 `wrangler dev` 时 `ENVIRONMENT` 也是 production，导致代码走了错误的分支。

**而这一层能做的排查很有限**——因为失败要么是启动就崩（配置校验失败），要么是行为异常（配置读到了但没用）。

**如果现象是"某个功能连生产环境的数据都读不到"，那问题在这一层。**

## 第三段：中间件——横切规则

中间件是这个项目里最容易看漏的一层，因为它不在路由文件里。

看真实的注册顺序：

```ts
app.onError(errorHandler);         // ① 错误兜底（最先注册，覆盖全局）
app.use('*', corsMiddleware(env)); // ② 跨域
```

**而 `onError` 要最先注册**，因为它是最外层的兜底——**任何后续代码抛出的异常都会走到这里**：

```ts
export const errorHandler: ErrorHandler = (err, _c) => {
  if (err instanceof AppError) {
    return failResponse(err.code, err.httpStatus, err.details);
  }
  console.error('[unhandled]', err);
  return failResponse(ErrCode.INTERNAL, 500);
};
```

**中间件这一层可以处理的，是"每个请求都要做的事"：**

| 中间件 | 做什么 | 出问题时表现 |
|---|---|---|
| `corsMiddleware` | 跨域头 | 浏览器报 CORS 错误，**但服务端日志一切正常** |
| `optionalAuth` | 提取用户身份 | 匿名可读端点带上坏令牌 → 静默降级 |
| `authMiddleware` | 强制认证 | 401 |
| `guard` | 授权 | 403 / 404 |

**而 CORS 那个特别值得说**：它是唯一一个"**服务端全对、用户还是用不了**"的故障。

因为浏览器的跨域检查在**响应回来之后、交给页面代码之前**。所以：

```text
服务端返回 200 + 正确的 CORS 头 → 用户能用
服务端返回 200 + 缺 CORS 头     → 用户看不到，Network 面板里是红色
服务端返回 500                    → 用户看到错误，日志里有记录
```

**这一层的排查方法是明确的**：看浏览器的 Network 面板和 Console，**不要先怀疑业务代码**。

## 第四段：路由匹配

匹配到路由之后，才进入具体处理。

而路由文件里能看到的东西有限——通常是一串中间件和一个 handler：

```ts
articlesRoute.get('/', optionalAuthMiddleware, async (c) => {
  const result = await queryArticles(c);
  return paginate(result.list, meta(result.page, result.pageSize, result.total));
});
```

**而"这个路由有哪些前置条件"这件事，看这一行是看不出来的。** 它散在三处：路由里挂了哪些中间件、契约里声明了什么（`x-authz`）、以及 handler 内部可能再查一次归属。

**这正是 B-16 讲契约门禁的原因**：契约里的 `x-authz` 是这个路由授权要求的唯一权威来源，而代码要匹配它。

**排查这一层的问题**：如果请求 404 了，先确认路径和 HTTP 方法对不对——**这个项目里 `GET /articles/{idOrSlug}` 和 `POST /articles` 是同前缀的路由，写错方法就会 404 而不是 405**。

## 第五段：业务逻辑

进入 handler 之后，就是业务代码了。这一层的问题最多，但也是最好定位的——**因为错误信息最具体**。

而这个项目里最值得看的一处是分页：

```ts
/** 解析页码与页大小（带边界钳制，page≥1、pageSize∈[1,100]）。 */
export const parsePage = (c: Context): { page: number; pageSize: number; offset: number } => {
  const page = Math.max(1, Number(c.req.query('page') ?? 1) || 1);
  const pageSize = Math.min(100, Math.max(1, Number(c.req.query('pageSize') ?? 20) || 20));
  return { page, pageSize, offset: (page - 1) * pageSize };
};
```

**`Math.min(100, ...)` 那个 100 是关键。** 它是契约里声明的上限，而客户端可以不传或者传一个更大的值。

**如果这一层没有钳制，一个 `pageSize=999999` 会让数据库去取一百万行**——而这不是注入，是纯粹的资源耗尽。

而排序那一层（B-11 讲过）是白名单：

```ts
const raw = bare && bare in SORT_COLUMNS ? (sort ?? '-publishedAt') : '-publishedAt';
```

**两个防御在同一个函数里，各防一类问题**：数量钳制防资源耗尽，白名单防注入。**它们的共同点是"都在进入 SQL 之前"。**

**排查这一层的方法是加日志**——而 B-19 讲过日志的脱敏要求。

## 第六段：数据访问

再往里就是数据库了，而这一层的失败分两种。

**查询本身失败**（语法错误、表不存在）——这类通常在开发就发现了，因为测试会跑真实查询。

**查询成功但慢**——B-06 讲过：**用 `EXPLAIN QUERY PLAN` 看是 `SCAN` 还是 `SEARCH`**。

而这个项目里数据访问有一层特殊的东西：

```ts
export async function atomic(db: Db, statements: Statement[]): Promise<number[]> {
  const client = (db as unknown as { $client: Database.Database | D1Client }).$client;
  if ('batch' in client) { ... }
  return client.transaction(() => ...)();
}
```

**这一层同时承载了"双运行时"和"事务原子性"两件事**（B-14 和 B-18 都讲过）。

**而它在排查上有一个特殊之处**：本地和线上走的是**不同的代码分支**。

所以一类问题的表现是"**本地好好的，线上出问题**"。而 M1-34 那个 `redirect` 属于这一类的极端——**本地分支根本没执行**。

**判断依据是：本地复现不了 + 代码路径和环境有关** → 优先怀疑这一层。

## 第七段：响应构造

最后回到出口：

```ts
export const paginate = <T>(list: T[], pagination: Pagination, message = 'ok'): Response =>
  Response.json(
    envelope(0, message, { list, pagination } satisfies { list: T[]; pagination: Pagination }),
    { status: 200 },
  );
```

**而 `envelope` 里有一个我一度没意识到问题的字段：**

```ts
const envelope = <T>(code: number, message: string, data: T | null): Envelope<T> => ({
  code, message, data,
  requestId: requestId(),
  timestamp: new Date().toISOString(),
});
```

**`requestId` 每次响应即时生成**——所以它**和日志里的任何东西都没有关联**。用户报错报上来的 ID，服务端查不到对应日志。

**这是 B-19 讲的那个缺口。** 而它在排查这一层时的直接影响是：**你无法用用户提供的 requestId 定位到那次请求的日志。**

**契约里声明了这个字段，检查脚本也确认它存在——但没有一条断言会说"它必须出现在日志里"。**

**这就是"契约自洽"和"跨系统对得上"之间的差别。**

## 失败发生在哪一层，决定了怎么恢复

把上面串起来，得到一张排查对照表：

| 层 | 现象 | 第一步看什么 |
|---|---|---|
| DNS / TLS | 打不开页面 | 浏览器错误码 |
| 入口配置 | 所有请求都 500 | 服务端日志第一个错误 |
| CORS | 页面空白，Console 报错 | Network 面板的响应头 |
| 路由 | 404 | 路径 + HTTP 方法 |
| 认证 | 401 | 有没有带令牌 |
| 授权 | 403 / **404** | 归属判断（B-12 讲过 404 的含义） |
| 业务 | 4xx 带具体 message | 后端返回的 `fields`（字段级错误） |
| 数据 | 慢 / 超时 | `EXPLAIN QUERY PLAN` |
| 响应 | 数据不对但 200 | 契约字段是否一致 |

**这张表的价值不在于它有多完整，而在于它能把排查范围快速缩小。**

**而最常见的错误是跳过前面几层直接看业务代码**——因为业务代码是"我写过的"，而中间件和网关配置是"我配过但没仔细看的"。

## 一条我一开始想省掉的事

有一段时间，客户端反馈"文章列表偶尔会重复"。

我按直觉去了业务层——查了 Repository 的合并逻辑、查了分页参数、查了缓存失效。**全都没问题。**

最后是在网关那边发现的：Caddy 配了 `lb_try_duration 5s`，**而我们的 SQL 查询偶尔会超过 5 秒**——于是网关主动断开了连接，客户端重试了。

而客户端的重试产生了第二个请求，于是列表里出现了重复。

**也就是说：问题在"超时重试"这个我完全没写过的环节。**

修的方式有两步：

1. **把那个超时调长**（因为查询确实慢）
2. **加请求去重**——因为"超时后客户端一定会重试"这件事，任何时候都可能发生

而第二步现在在客户端那一侧（M4-12 的 `serial` 是另一回事，但"重复请求要能容忍"这个原则一样）。

**这个 bug 我花了半天，因为它不在我以为的十八步里的任何一步。**

## 小结

一个请求经过的那些层，各自有明确的职责和排查方式：

1. **请求到达之前**（DNS/TLS/网关）——现象是"打不开"，先确认请求到没到你的代码。
2. **入口与配置**——配置错误表现为"所有请求都 500"。
3. **中间件**——横切规则，**CORS 是唯一一个"服务端全对但用户用不了"的**。
4. **路由**——404 先查路径和方法，授权要求查契约而不是代码。
5. **业务**——错误最具体，最好定位。
6. **数据**——本地和线上走不同分支，"本地好好的"是重要信号。
7. **响应**——注意那些"看起来实现了"但实际没连上的字段。

而最值得记住的是两条经验：

> **排查的第一步是判断问题在哪一层，而不是在猜具体原因。**

> **有些环节不在你写的代码里**——网关超时、客户端重试、浏览器跨域检查。它们同样会让你的功能失效。

第二条是我那次"文章重复"花半天学到的。**而这个专栏里的很多 bug，根因都不在那个"十八步"里**——这也是为什么纯靠读代码找不到它们。
