# 成为全栈·基础补充·服务端心智模型：一个请求从浏览器到数据库发生了什么

> 前端发出一条请求后，服务端不是“收到 JSON 就查数据库”。请求会经过网络入口、路由、中间件、身份与权限判断、业务服务和持久化，再被转换成客户端能理解的响应。

## 前言：把看不见的链路画出来

当页面显示“发布失败”时，问题可能发生在 DNS、TLS、反向代理、HTTP 路由、登录状态、请求校验、业务规则、数据库事务、通知写入或响应序列化。只在按钮代码里加一个 try/catch，无法知道失败点，也无法判断服务端是否已经提交操作。

本文以“会员发布文章”为例，画出一次请求的典型链路。不同框架的函数名称不一样，但职责大致相通；真实项目还会受缓存、队列、对象存储和部署平台影响。

## 一、客户端先把请求送到服务入口

用户点击提交后，客户端整理标题、正文和凭证，按接口契约发出 HTTP 请求。浏览器可能先查询 DNS、建立 TCP/TLS 连接，再把请求发给 CDN、网关或反向代理。移动 App 也会经历网络连接，但不受浏览器 CORS 规则控制；小程序还会受到开发工具与平台域名配置约束。

反向代理根据域名、路径或其他规则把请求转发给应用。代理可能终止 HTTPS、限制请求体大小、设置超时、写访问日志或返回自己的 502/504。若后端没有请求记录，故障可能发生在应用收到请求之前；若代理日志有记录而应用没有，则要检查 upstream、路由和连接。

## 二、应用入口解析协议并建立请求上下文

应用读取方法、路径、查询参数、请求头、Cookie 和 body。首先要限制请求体大小、解析 Content-Type，并拒绝无法理解的格式。请求 ID 可以贯穿代理和应用日志，帮助把同一次调用的各层记录关联起来。

随后路由器根据方法和路径找到处理器。例如 POST /api/v1/member/articles 可能被映射到会员投稿操作。未知路径、错误方法、超大 body 或 JSON 无法解析，都应在进入业务代码前得到明确响应。

## 三、中间件处理横切规则

中间件围绕多个路由重复执行的规则，例如：

- 生成或传播 request ID。
- 记录请求耗时、状态码和脱敏错误。
- 恢复意外 panic，避免服务进程整体退出。
- 处理 CORS 预检与响应头。
- 解析可选身份或要求身份认证。
- 对特定公开操作进行限流。
- 根据路由元数据检查角色。

中间件顺序会影响行为。例如身份解析要在角色授权之前；CORS 预检可能在业务处理器之前结束；错误转换要覆盖下层异常。全局 middleware 也不应一刀切地对所有端点限流或强制登录，具体规则要按操作配置。

## 四、身份认证和授权是两个步骤

应用可以从 Authorization 头或 Cookie 中读取凭证，验证签名、过期时间或会话状态，得到当前用户。认证失败通常在此处终止，服务层不应把匿名请求误当成合法会员。

身份成立后，还要检查该用户能否发布、编辑当前文章或访问当前资源。角色不足、文章不属于本人、文章状态不允许修改，属于不同授权或业务拒绝原因。客户端隐藏按钮只改善交互，不能代替服务端检查。

## 五、输入校验后才进入业务规则

HTTP 层先验证 JSON 形状、必填字段、长度和枚举；业务层再验证更复杂的规则，例如会员是否达到投稿限制、标题 slug 是否冲突、目标分类是否可用、文章状态是否允许从 draft 进入 pending。

这两种校验不能混为一谈：请求格式错误通常是 400；资源当前状态不允许操作可能是 409；无身份是 401；有身份但无权限可能是 403。具体状态与业务码应以接口契约为准。输入字段的缺失、null 和零值语义也要保留，避免 DTO 解码时丢掉用户意图。

## 六、应用服务组织数据库和外部副作用

应用服务把一个用户动作编排为有意义的业务操作。发布文章可能包括读取作者、校验状态、更新文章并生成通知。若这些数据库写入必须一起成功，就在同一事务中完成；通知写入失败时，文章状态也应回滚。

若操作还上传图片到对象存储，数据库事务无法撤销对象存储写入。系统需要先上传再写元数据并在失败时补偿删除，或采用其他可重试状态机。网络请求和昂贵计算通常不应放在持有数据库锁的长事务里。

事务提交后，服务层返回明确结果。若连接在 COMMIT 后断开，客户端可能看不到成功响应，但数据已经成功提交；这就是为什么写接口要考虑幂等和请求重试，详见 [B-20]({{LINK:B-20}})。

## 七、响应序列化并沿原路返回

应用把业务结果映射成公开 DTO，再序列化为 JSON，设置状态码、Content-Type、Cookie 和缓存头。数据库模型不应直接原样返回：内部字段如密码哈希、OpenID、刷新令牌摘要和管理状态可能不适合公开。

响应经过代理返回客户端。代理可能改写缓存、压缩或添加安全头；浏览器之后还会执行 CORS、Cookie 和内容类型策略。客户端收到 HTTP 200 后，也可能看到业务失败码；成功响应同样要按契约字段解析。排查网络错误要同时看状态码、响应头、响应体和浏览器控制台。

## 八、失败发生在哪一层，决定了怎么恢复

| 失败位置 | 示例 | 常见处理方向 |
|---|---|---|
| DNS/TLS/连接 | 域名错误、证书无效、拒绝连接 | 检查 DNS、证书、端口和入口 |
| 代理 | upstream 超时或路径改写错误 | 检查代理规则、上游连通和日志 |
| HTTP 解析 | JSON 格式错误、body 超限 | 返回明确参数错误，客户端修正请求 |
| 认证/授权 | token 过期、角色不足 | 刷新会话或提示权限，不盲目重试 |
| 业务规则 | 状态冲突、重复 slug | 返回可解释错误，用户修改输入 |
| 数据库 | 唯一冲突、锁等待、连接失败 | 事务回滚、有限重试或告警 |
| 外部资源 | 微信/R2 超时 | 超时、补偿、幂等重试并留下诊断信息 |
| 响应客户端 | 响应丢失、客户端取消 | 查询业务状态或安全重试写操作 |

## 九、日志和追踪让链路可见

日志应记录请求 ID、路由/operation、耗时、状态码和脱敏错误类别；不要记录密码、Cookie、访问令牌、AppSecret 或完整请求正文。按请求 ID 搜索代理与应用日志，可以确定请求是否到达应用、在哪一步失败。

一次失败还需要看数据库后置状态。若状态未变，客户端可以提示重试或修正；若数据已提交而响应丢失，则不应盲目执行非幂等动作。可观测性不是多打日志，而是留下足够的上下文并保护敏感信息。

## 小结：从入口到响应，逐层定位责任

一次完整请求穿过网络、代理、协议解析、中间件、身份权限、输入校验、业务服务、数据库和外部资源，最后变成响应返回客户端。理解各层职责后，能区分传输失败、应用拒绝和业务冲突，也能在写入失败时判断数据是否已经提交。服务端心智模型让前端开发者从“请求按钮”走到“系统状态变化”。
