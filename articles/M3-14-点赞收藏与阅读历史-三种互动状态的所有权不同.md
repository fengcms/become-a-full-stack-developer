# 成为全栈·Next.js 网站前台篇·点赞、收藏与阅读历史：三种互动状态的所有权不同

> 点赞、收藏和阅读历史都围绕“用户与文章”，却不是同一种状态。点赞有公开计数，收藏只有本人可见，阅读历史还带时间与进度；把它们塞进一个布尔值模型，缓存和界面都会失真。

![成为全栈·Next.js 网站前台篇·点赞、收藏与阅读历史：三种互动状态的所有权不同](https://i-blog.csdnimg.cn/direct/39df5216b86b4e0eb16eeb1007561531.png)

## 前言

文章详情页上，点赞和收藏只是两个相邻按钮；会员中心里，点赞、收藏和阅读历史也只是三张列表。视觉相似很容易诱导我们写一个通用 `toggleArticleState(type)`，再用同一套缓存处理。

但三者的契约不同。游客可以看到点赞总数，却看不到任何人的收藏；阅读历史不是一次开关，而是会随着再次阅读更新最后时间和进度。前端复用应该停留在展示层，不能抹掉数据语义。

## 先比较三种状态

| 状态 | 公开信息 | 私有信息 | 写入语义 | 典型列表字段 |
| --- | --- | --- | --- | --- |
| 点赞 | `likeCount` | 当前用户是否点赞 | 点赞/取消，服务端幂等 | 文章摘要 |
| 收藏 | 无公开计数 | 当前用户是否收藏 | 添加/移除，服务端幂等 | 文章摘要 |
| 阅读历史 | `viewCount` 是另一项公开统计 | 最后阅读时间、进度 | 写入或更新同一记录 | 文章 + `lastReadAt` + progress |

公开 `viewCount` 也不等于会员阅读历史数量。游客会贡献阅读次数，同一个人可能多次阅读，统计口径必须在文案中保持诚实。

## 点赞状态可以按文章查询

```tsx
const like = useQuery({
  queryKey: ['like', user?.id, articleId],
  queryFn: () => getArticleLikeStatus(articleId),
  enabled: ready,
})

const liked = like.data?.liked || false
const count = like.data?.likeCount ?? serverCount
```

游客也需要看到实时公开计数，所以会话启动完成后可以查询点赞状态接口；返回的 `liked` 对游客为 false，`likeCount` 则继续可见。

按钮同时表达可操作状态和当前值：

```tsx
<button
  type="button"
  aria-pressed={liked}
  disabled={mutation.isPending || !like.data}
  onClick={() => mutation.mutate('like')}
>
  {liked ? '已赞同' : '赞同'} · {count}
</button>
```

在初始私有状态尚未返回前禁用按钮，避免用户基于错误默认值执行相反操作。

## 收藏缺少单篇状态接口，就必须承认代价

当前契约没有 `/articles/{id}/favorite-status`。前端只能遍历本人收藏分页，得到 id 集合：

```ts
export async function favoriteIds() {
  const ids: number[] = []
  let page = 1
  let totalPages = 1

  do {
    const result = await getMyFavorites({ page, pageSize: 100 })
    ids.push(...result.list.map((article) => article.id))
    totalPages = result.pagination.totalPages
    page += 1
  } while (page <= totalPages)

  return ids
}
```

```tsx
const favorite = useQuery({
  queryKey: ['favorite-ids', user?.id],
  queryFn: favoriteIds,
  enabled: !!user,
})
```

这能保证功能正确，却会随着收藏数量增加而放大请求。文章应明确它是契约缺口下的当前方案；未来更合理的接口是单篇状态或批量 id 状态，而不是继续提高 pageSize。

## 一次 mutation 可以分流动作，失效不能只刷新当前按钮

```tsx
const mutation = useMutation({
  mutationFn: async (kind: 'like' | 'favorite') => {
    if (kind === 'like') {
      return liked ? unlikeArticle(id) : likeArticle(id)
    }
    return saved ? removeFavorite(id) : addFavorite(id)
  },
  onSuccess: () => {
    void client.invalidateQueries({ queryKey: ['like'] })
    void client.invalidateQueries({ queryKey: ['favorite-ids'] })
    void client.invalidateQueries({ queryKey: ['member'] })
    setNotice('操作已完成')
  },
})
```

点赞会影响详情按钮和“我的点赞”；收藏会影响详情按钮和“我的收藏”。成功后按领域失效相关查询，比只在本地翻转布尔值更不容易与服务端分叉。

当前实现没有激进乐观更新。互动请求很轻，等待服务端确认可以避免审核、权限或幂等返回与本地猜测不一致。若未来加入乐观更新，就要同时设计回滚与并发点击顺序。

## 未登录不是 mutation 错误

```tsx
{user ? (
  <InteractionButtons />
) : (
  <>
    <Link href={`/login?redirect=/articles/${id}`}>登录后点赞 · {count}</Link>
    <Link href={`/login?redirect=/articles/${id}`}>登录后收藏</Link>
  </>
)}
```

游客看到的是清楚的登录入口，而不是先允许点击、等 API 返回 401 再弹错。登录后返回路径还要经过同源校验，防止开放重定向。

## 阅读历史在五秒后写入，并以用户身份去重

```tsx
const key = `${user?.id}:${articleId}`

const timer = setTimeout(() => {
  if (user && !recorded.has(key)) {
    recorded.add(key)
    void reportReadingProgress(articleId).catch(() => recorded.delete(key))
  }
}, 5000)

return () => clearTimeout(timer)
```

历史记录失败不会遮住正文；删除去重标记后，下次进入仍能重试。A 与 B 使用不同 key，账号切换不会互相抑制上报。

若后续真正记录滚动进度，可以传 0～100：

```ts
await reportReadingProgress(articleId, progress)
```

但不能用滚动百分比直接宣称阅读完成。长代码、目录跳转和页面布局都会影响滚动位置，它只是一种近似进度。

## 三种会员列表可以复用控制器，不能伪造字段

```ts
if (kind === 'history') {
  const data = await getMyHistory({ page, pageSize: 10 })
  return {
    items: data.list.map((item) => ({
      article: item.article,
      time: item.lastReadAt,
      progress: item.progress,
    })),
    totalPages: data.pagination.totalPages,
    total: data.pagination.total,
  }
}
```

收藏和点赞接口没有“收藏于”“点赞于”字段，页面就不显示虚构时间。共享 `ArticleCard` 不代表三种接口必须被压成完全相同的数据。

点赞当前返回完整数组，前端临时切片分页：

```ts
const list = await getMyLikes()
return {
  items: list.slice((page - 1) * 10, page * 10).map((article) => ({ article })),
  totalPages: Math.ceil(list.length / 10),
  total: list.length,
}
```

数据量增长后应由后端提供分页。客户端切片仍需要先下载全部数据，只是视觉上分了页。

## 删除操作后的缓存与页码恢复

```tsx
const remove = useMutation({
  mutationFn: async (id: number) => {
    if (kind === 'favorites') return removeFavorite(id)
    if (kind === 'history') return removeHistoryItem(id)
    return unlikeArticle(id)
  },
  onSuccess: () => {
    if (query.data?.items.length === 1 && page > 1) setPage(page - 1)
    void client.invalidateQueries({ queryKey: ['member'] })
    void client.invalidateQueries({ queryKey: ['favorite-ids'] })
    void client.invalidateQueries({ queryKey: ['like'] })
  },
})
```

最后一页删空就回退一页；相关详情状态一起失效。不要只从当前数组 `filter` 掉一项，否则总数、分页和其他页面仍然是旧值。

## 一致性验收矩阵

| 操作 | 详情页 | 会员列表 | 公开计数 |
| --- | --- | --- | --- |
| 点赞 | 按钮变为已赞同 | 我的点赞出现文章 | likeCount 更新 |
| 取消点赞 | 按钮恢复 | 列表移除 | likeCount 更新 |
| 收藏 | 按钮变为已收藏 | 我的收藏出现文章 | 无公开变化 |
| 取消收藏 | 按钮恢复 | 列表移除并处理空页 | 无公开变化 |
| 阅读五秒 | 正文不受影响 | 历史出现或更新时间 | view 是另一条上报 |
| 删除历史 | 无按钮状态变化 | 历史移除 | viewCount 不回退 |

![一致性矩阵](https://i-blog.csdnimg.cn/direct/a38575d010f040499ec4859c6abe636a.png)

测试时还要切换两个账号，确认 query key 和阅读去重键不会串用户；让互动接口失败，确认按钮不显示虚假的成功状态，已加载正文仍可阅读。

## 适用边界

普通博客可以接受服务端确认后刷新状态。高频社交产品可能需要乐观更新、离线队列和实时计数，此时必须定义多端冲突与回滚策略。

收藏数量很大、点赞列表很长时，当前契约的全量读取会成为瓶颈。那是后端接口能力需要升级，不应靠客户端缓存永久掩盖。

## 小结

点赞、收藏和阅读历史的共同点只有“用户与文章有关”。公开性、字段、写入语义和列表契约都不同。

前端可以共享按钮样式、文章卡片和分页外壳，但缓存键、失效范围和文案必须尊重各自的数据所有权。复用结构，不要复用错误的语义。
