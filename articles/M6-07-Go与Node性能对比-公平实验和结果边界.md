# 成为全栈·Go 后端篇·同一套接口的性能对比：先把实验做公平

> 一次基准测试只能回答一个有限问题。若数据库、数据量、请求、缓存和运行方式不一致，最终数字讲的是整套环境差异，不是 Go 与 Node 的速度差异。

{{IMG:M6-07-封面}}

> 实测记录：2026-10-08，同一台 arm64 Mac；原始数据见 docs/go-backend/reports/performance.json。

## 前言：比较之前先写出比较对象

“Go 是不是比 Node 快？”听上去像一个问题，其实可能指 CPU、HTTP 响应、数据库延迟、启动速度、内存占用或工程交付效率。若拿 Go + PostgreSQL 与 Node + Cloudflare D1 对比，测到的是语言、数据库、网络和部署位置的混合差异。

M6 的性能实验将 Node Hono 与 Go 原生服务放在同一台 arm64 Mac 上，使用同一份 500 篇文章的 SQLite 数据副本，执行公开列表、详情、搜索、bcrypt12 登录和点赞/取消。服务都无业务缓存、读取完整响应；每场景先预热 5 次，读请求并发 8，登录并发 2，点赞和取消成对操作并发 4。

本文会呈现这组实测数字，同时解释样本和采集边界。结论是一次本地观察，不是语言排名或线上容量承诺。

## 一、实验控制了什么，保留了什么差异

Go 使用原生编译服务；Node 使用 tsx 加载 Hono 源码。两者访问相同数据库文件和 fixture，search 明确指定 pageSize=20，避免默认分页大小不同造成返回行数差异。读场景各 50 个样本，登录 8 个，点赞与取消合计按 30 组成对操作统计。计时由本地客户端 performance.now 采集。

这些约束不是文字描述，而是写进脚本的实际步骤。`scripts/benchmark-local.sh` 负责把两份服务拉起在同一台机器、同一份数据的两个副本上：

~~~sh
# scripts/benchmark-local.sh（节选）：同机、同 fixture、各一份 SQLite 副本。
export DB_DRIVER=sqlite DATABASE_URL="$scratch/source.db" JWT_SECRET=benchmark-shared-secret-32-characters
export SEED_USERNAME=bench-admin SEED_PASSWORD=bench-password STORAGE_DRIVER=local
CGO_ENABLED=1 go build -trimpath -o "$scratch/server" ./cmd/server
go run ./cmd/migrate
go run ./cmd/seed -articles 500
# Seed command has closed SQLite before these copies, so no WAL is omitted.
cp "$scratch/source.db" "$scratch/go.db"
cp "$scratch/source.db" "$scratch/node.db"
DATABASE_URL="$scratch/go.db" HTTP_ADDR=127.0.0.1:18081 DB_METRICS_FILE="$scratch/db-go.json" "$scratch/server" > "$scratch/go.log" 2>&1 &
~~~

脚本里有几个细节决定了数字是否可比：种子在复制前关闭，避免 WAL 未落盘造成两份数据库不一致；Go 与 Node 各用一个端口、各连一份副本，互不写同一文件；Node 侧用 `exec node --import tsx` 直接启动，让记录的进程号就是服务器本身，而不是它的启动父进程。

实验没有使用业务缓存，避免一边热缓存、一边冷查询；每个场景先执行 5 次预热。Go 先执行，Node 后执行，无法消除系统缓存、调度和后台进程差异。Node 的 tsx runner 与 Go 原生二进制启动方式不同，因此进程 RSS 包含工具链运行时开销，不能当成语言的纯内存成本。

登录固定 bcrypt cost 12；它本来就占主要耗时。为了让 Go 看起来更快而把 cost 降低，会改变安全参数，实验不再比较同一业务。点赞/取消作为成对操作统计，吞吐定义为完成一组两次请求的操作数，不与单次 GET 的请求/秒直接比较。

哪些被控制、哪些只能如实保留，可以列成一张表：

| 维度 | 本轮控制 | 只能保留的差异 |
|---|---|---|
| 机器与 OS | 同一台 arm64 Mac | 后台进程与调度抖动 |
| 数据 | 同一份 500 篇 fixture 的两个副本 | 复制前后无 |
| 缓存 | 双方都关业务缓存 | 操作系统页缓存无法清零 |
| 运行方式 | Go 原生二进制 / Node tsx | 启动与内存口径不同 |
| 顺序 | 固定 Go 先、Node 后 | **未交替，无法消除顺序效应** |
| 计时 | 本地 performance.now | 只覆盖客户端观测 |

## 二、实际观察到的延迟与吞吐

| 场景 | Go p50 / p95 / p99 ms | Node p50 / p95 / p99 ms | Go / Node 操作每秒 |
|---|---|---|---|
| 文章列表 | 2.79 / 5.02 / 5.89 | 4.95 / 10.41 / 16.60 | 2312.30 / 1503.25 |
| 文章详情 | 1.50 / 2.73 / 2.90 | 3.03 / 6.54 / 7.37 | 4338.66 / 2001.04 |
| 搜索 | 3.82 / 7.21 / 8.52 | 4.92 / 9.07 / 10.10 | 1796.89 / 1364.52 |
| bcrypt cost 12 登录 | 259.49 / 264.85 / 264.85 | 552.83 / 554.77 / 554.77 | 7.67 / 3.62 |
| 点赞加取消 | 3.87 / 4.76 / 4.84 | 3.57 / 6.26 / 6.27 | 1014.68 / 879.58 |

这些百分位由客户端采集后排序取值，`scripts/benchmark.mts` 里就一行取位逻辑：

~~~ts
// scripts/benchmark.mts（节选）：按并发数分发请求，客户端计时并取百分位。
const percentile=(p:number)=>Number(samples[Math.min(samples.length-1,Math.ceil(samples.length*p)-1)].toFixed(2));
~~~

同一文件里固化了场景参数，避免每次手工改变量：

~~~ts
// scripts/benchmark.mts（节选）：读 50、登录 8、成对写 30。
const cases=[{name:'列表',path:'/articles',n:50,c:8},{name:'详情',path:'/articles/1',n:50,c:8},{name:'搜索',path:'/search?q=Go&pageSize=20',n:50,c:8},{name:'登录 bcrypt12',path:'/auth/login',n:8,c:2},{name:'点赞与取消',path:'/articles/1/like',n:30,c:4}];
~~~

本轮所有请求都成功。在这组样本里，Go 的读取和登录延迟较低，点赞/取消的 p50 是 Node 更低，但 Go 的尾延迟和成对操作吞吐较好。这个结果可以支持“在该机器、本数据库、副本数据和请求方式下，Go 观察到这些数字”；不能支持“Go 在生产必然更快”。

登录只有 8 个样本，p99 基本就是最大样本值，统计稳定性有限。50 个读样本也适合初步观察，不足以刻画长时间负载、突发流量和资源耗尽。报告保留样本数，避免让百分位显得比它实际更可靠。

点赞/取消这一行尤其值得慢看：Go 的 p50（3.87）比 Node（3.57）略高，但 p95、p99 与吞吐都更好。这说明单看一个场景的一个分位数，很容易得出与整体相反的印象。趋势要连同场景、并发和样本量一起读，不能挑一格当结论。

## 三、吞吐、CPU、RSS 和数据库统计不能混为一谈

Go 进程末尾 RSS 为 32,240 KiB，Node 为 237,040 KiB。由于 Node 通过 tsx 加载，差值包括运行工具和进程采样时点，不应解释为 Node 应用天生多占几倍内存。

Go 数据库统计记录 667 次 GORM 调用，总计 260.86 ms，最大 5.31 ms；Node 记录 552 次原生 SQLite 调用，总计 37.40 ms，最大 1.03 ms，均无错误。这两种采集口径不同：Go 包含 GORM 调用及等待，Node 是原生 SQLite 调用。不能将它们相除后写“Go 数据库慢六倍”或“Node SQL 快六倍”。

三类统计各自的含义和不能推出的结论，可以列成一张表：

| 指标 | 实际含义 | 不能推出的结论 |
|---|---|---|
| 客户端延迟 p50/p95/p99 | 客户端观测的完整往返 | 不等于服务端内部耗时 |
| 进程 RSS | 采样时进程常驻内存 | Node 全量内存成本（含 tsx） |
| 数据库调用统计 | Go 的 GORM 调用 / Node 的原生 SQL | 两者不可直接相除比快慢 |
| operationsPerSecond | 每场景单位时间内完成的请求/操作 | 成对写不与单次 GET 直接比 |

调用数差异可以作为调查线索：检查服务端请求包含哪些初始化或附加查询，理解 ORM 调用和原生 SQL 记录口径，再用统一的 trace 或 SQL 采样重做实验。工具统计定义不同，数字越精确，越需要说明采集的是什么。

把这三类统计放在一起看，容易犯的错误是拿一个指标去解释另一个。RSS 高未必说明处理慢，数据库调用次数多也未必说明查询慢，客户端延迟低也未必说明服务端没做额外工作。要判断一个数字说明了什么，先确认它的采集位置、包含范围和单位，再决定它能支持哪一类结论。

## 四、为什么没有拿 PostgreSQL 和 D1 比速度

Node 线上方案会使用 Cloudflare D1，Go 主要验证 PostgreSQL。若把 Node+D1 和 Go+PostgreSQL 放在一次端到端测试里，网络往返、数据库位置、连接协议、托管限额和查询计划都会影响结果，无法归因为语言。

本轮使用同一 SQLite 副本，是为了尽量隔离语言运行时差异。即便如此，它也不是完全受控实验：Node 执行 tsx，Go 执行原生二进制；数据库调用统计不同；执行顺序固定；样本有限。更严谨的后续实验可以构建 Node 原生生产产物、交替服务执行顺序、延长稳定负载、记录 CPU/RSS 时间序列，并使用统一连接池与数据库观测。

若实际问题是“Cloudflare 部署下用户体验如何”，就应另测真实 Node/D1 与目标 Go/PostgreSQL 部署栈，并把它称为部署方案对比，不是语言基准。

这类“混合环境”的对比还有一个常见误区：把一次端到端延迟直接当成某个组件的耗时。端到端数字里包含 DNS、TCP、TLS、代理、应用、数据库和返回序列化的总和，任何一环变化都会改变结果。若目标是找到瓶颈，就需要把链路拆开分别观测；若目标只是确认端到端体验是否达标，那就明确把它报告为部署方案对比，而不是语言层面的结论。

## 五、下一轮实验如何设计得更稳

一个更可信的性能计划包含：

- 固定服务 commit、依赖版本、构建方式和环境变量；
- 生成同一数据库文件副本，检查 fixture 行数与索引；
- 交替运行 Go/Node 顺序，多轮测量；
- 预热后跑足够样本，分离读请求、登录和成对写操作；
- 记录 p50/p95/p99、吞吐、错误率、CPU、RSS 时间序列；
- 统一客户端计时口径与服务端数据库观测；
- 分析查询计划、缓存命中和 ORM 查询数；
- 保留原始 JSON、脚本、机器架构与操作系统版本。

计划本身也要能被执行。列一份更可信的实验步骤，最容易失败的地方不是测量，而是环境准备：fixture 行数对不上、索引没建、端口被占、旧进程没清干净。这些都会让数字悄悄失真，所以在正式测量前先做一次自检，确认两个服务读到的确实是同一份数据。

如果业务缓存、TLS 代理、数据库位于远端，应该单独建立一组真实架构测试，而不是把本地数据库测试结果外推。结论要对应测量环境。

还应该记下一次实验“没测什么”。本地 SQLite 副本没有覆盖并发连接池耗尽、慢查询堆积、GC 停顿和网络抖动，这些恰恰是生产环境最容易出问题的位置。把这些空白项写进报告，比补一句“结论仅供参考”更有用，因为它告诉下一个人该从哪里继续，也避免把一份有限样本当成容量承诺。

## 六、怎样把一组性能数字读完整

报告一组数字，至少要说清四件事：这次测的是什么场景，样本和并发是多少，结果是在什么机器和数据库上得到的，以及哪一部分是被控制的、哪一部分只能如实保留。少了任何一件，数字就会显得比它实际能支撑的结论更硬。

判断它够不够用，可以先问：我要回答的是不是这个问题？如果关心的是线上容量，本地同机 SQLite 的读数就不能直接搬过去；如果关心的是某个查询是否变慢，就该把观测口径收到那一条 SQL；如果关心的是登录等待，那 bcrypt 的 cost 才是主要变量，而不是语言。分清问题类型，再决定要不要把这份实验重做一遍。

最后，性能报告要给数字配上版本。服务 commit、依赖版本、构建方式、机器架构和操作系统都应在同一个快照里，这样别人复现时才知道差异来自代码还是来自环境。一个没有版本的漂亮数字，第二次运行时往往就找不回来了。

## 小结：报告数字，也报告数字的边界

M6 本地样本显示 Go 在多数读取与登录场景的观测延迟较低，但 Node 在点赞/取消的 p50 更低；Go 进程 RSS 也不能脱离 tsx 与原生构建差异解读。数据库内部统计不是同一口径，样本数量有限，实验顺序没有交替。

性能测试不是用来证明选型正确，而是帮助找到下一个要测的问题。如果差异影响产品目标，就在目标环境重复实验；如果差异来自 SQL 调用数量，优化查询；如果用户等待主要来自 bcrypt，就不要为提升数字破坏安全参数。诚实的限制说明是性能报告的一部分。
