# 成为全栈·Go 后端篇·微信身份在 Go 中复刻：建号、首次设密与并发冲突

> 微信 code 只是一次性登录凭证，不能直接当作应用用户 ID。后端要把平台身份映射到自己的账号，并在重复回调与并发首次登录时只创建一个用户。

{{IMG:M6-19-封面}}

> 本文代码快照：提交 ceac4e0。登录流程依据冻结契约 1.12.0 与当前 Node/Go 实现；线上微信联调状态按交付报告表述。

## 前言：外部身份和站内账号是两层关系

小程序拿到 wx.login 的临时 code 后，需要把它交给后端。后端使用 AppID 和 AppSecret 向微信换取 openid，再以自己的用户体系签发 access token 与 refresh token。openid 是微信平台身份，user id 是文章系统账号；两者有关联，但不是一个概念。

首次微信登录会自动创建普通会员账号。由于用户可能还要在网站或 Flutter App 使用传统用户名密码登录，账号可在登录后设置本地凭据。这个流程复用已有注册登录契约的能力扩展，不要求网站和 App 增加微信快捷登录，也不引入复杂的跨平台绑定合并。

难点不是调用一次 HTTP API，而是确保秘密不泄露、同一个身份不会重复建号、首次设密只能完成一次、会话撤销与账号更新原子化，以及外部服务不可用时不制造半个用户。

## 一、code 必须由服务端换取 openid

客户端拿到 code 后只把 code 发给自己的后端。后端按配置的 AppID、AppSecret 和 code 请求微信 jscode2session endpoint，读取 openid。AppSecret 不能放进小程序包、前端环境变量或浏览器代码，客户端二进制可被提取。

M6 的 WechatHTTP 固定请求官方 endpoint，配置缺失时返回内部错误；HTTP client 设置 8 秒超时，并拒绝自动跟随 redirect。响应读取有字节上限，只接受 HTTP 200、无供应商错误且 openid 非空的结果。已知 code 错误与上游限流映射成契约错误，其余异常不把上游响应原文透传给客户端。

这些边界减轻错误配置和恶意上游行为的影响，但不代表 AppSecret 轮换、平台控制台配置、真实微信网络环境已经覆盖。代码里的 WechatClient 接口允许测试替身控制 code 换身份结果；替身测试证明业务分支，不等于真实微信凭据联调。写文章时要把这两种证据分开。

## 二、AppID 与 openid 组成身份唯一键

openid 的唯一范围依赖微信应用。相同用户在不同 AppID 下不应默认视为同一个平台身份，所以关联键是 app_id + open_id。数据库唯一约束承担并发首次登录的最终仲裁。

账号首次建立时，Go 生成不可预测的随机用户名，并准备随机的不可用本地密码哈希，CredentialsConfigured 标为 false。用户角色为 member、状态 active，显示名使用默认微信会员文案。响应通过 Public 映射，不暴露密码哈希或 openid，同时给客户端 canSetCredentials 能力标志。

重复登录首先按 app_id 和 open_id 查找关联。已有身份就读取并锁定对应用户，检查账号未禁用，然后签发新会话。它不会因为第二次登录再创建一个新 user，也不通过用户名猜测并合并历史账号。账号绑定合并会产生归属验证、冲突和撤销策略，属于另一套明确产品能力，不应隐含地加进此次重写。

## 三、并发首次登录用唯一约束而不是“先查再建”

两个相同 code 或两个并发 code 可能同时查不到 identity。如果只在应用层做一次 SELECT，再分别 INSERT user 和 identity，就会生成两个用户，或者其中一笔在唯一冲突后留下孤立 user。

M6 在事务中再次检查 identity，然后创建用户和身份关联；唯一约束确保同一个 app_id + open_id 只能落一条。遇到唯一冲突时，整笔事务回滚，再重试一次，第二次从数据库读取已创建身份并继续登录。只对可识别的冲突重试；数据库不可用、上游失败或其他业务错误都直接返回，不做无界循环。

~~~text
请求 A 和 B 都先看到“尚无身份”
            ↓
A 事务创建 user + identity，唯一键获胜并提交
B 事务插入 identity 遇到唯一冲突，整笔回滚
            ↓
B 有界重试，读到 A 创建的 identity
            ↓
A、B 都映射到同一个 user，不产生孤儿记录
~~~

有界重试的依据是数据库约束已经完成仲裁，下一次读取可见获胜记录。无限重试会把持续配置错误或数据库故障变成资源耗尽。真实数据库并发测试要检查最终 identity 数量、user 数量和错误结果，而不只断言两次请求都返回 token。

## 四、首次设置用户名密码要成为一次性状态动作

首次微信登录用户没有可用本地凭据。客户端可以提示用户设置用户名密码。Go Setup 先在事务外计算 bcrypt 哈希，随后锁用户并确认：账号 active、CredentialsConfigured 仍为 false、该用户确实存在微信身份。更新使用 credentials_configured=false 条件，再检查 RowsAffected 必须为 1；若已有请求先完成，后来的请求得到冲突，不能覆盖第一次的用户名密码。

更新用户名、密码哈希和凭据标记后，旧 refresh token 全部撤销，并在事务内签发新的认证结果。这样设置凭据与会话状态一起提交；任何一步失败都回滚，不会产生“已经改了用户名却没新 token”或“旧会话仍有效”的半完成状态。

后续用户可用这个用户名密码走原有登录流程。网站和 App 不需要新增微信按钮或微信 SDK；这正是把小程序外部身份接到站内通用账号后的复用价值。

## 五、失败语义和安全边界

需要覆盖的失败分支包括：上游 code 无效、微信限流、响应超时、未配置 AppID/Secret、账号禁用、唯一冲突重试耗尽、用户名占用、重复设置凭据和数据库提交失败。上游 secret、完整换码 URL 和 openid 不应写入普通日志；code 也不应长期保存或当作用户身份标识。

临时 code 是短期且一次性凭证。后端应限制 body、只接受预期格式，并尽快换取身份。拿到 openid 后数据库只保存身份映射所需值；访问 token 和 refresh token 按现有认证设计处理。用户公开响应只包含契约约定字段。

部署时还需要在环境中分别配置 AppID、AppSecret，并确认线上运行时能访问微信 endpoint。测试中的 HTTP transport 替身可以模拟错误码、重定向与超时，但不证明真实域名、密钥和平台账号已正确配置。

## 六、测试要分别证明换码和账号状态机

建议将测试拆成两层：

| 层次 | 测试输入 | 要证明的行为 |
|---|---|---|
| WechatHTTP 单测 | 200/openid、code 错误、限流、超时、redirect、超大响应 | 网络边界与错误映射 |
| WechatLogin 服务测试 | 新身份、已存在身份、禁用用户、唯一冲突 | 建号、复用与受限重试 |
| Setup 服务测试 | 首次成功、并发重复、凭据已配置、非微信用户 | 一次性状态转换 |
| 数据库并发测试 | 两次首次登录、两次设密 | 唯一身份、单一用户、会话撤销与最终状态 |
| 客户端闭环 | 微信替身登录、设置凭据、传统用户名密码登录 | 用户 ID 和权限角色保持一致 |

HTTP 替身不是“假测试”，但它回答的是可控输入下业务是否正确；真实微信测试回答生产凭据、网络和平台配置是否联通。报告两者时要分别命名。

## 小结：把微信接成身份提供方，不把账号体系推倒重来

M6 的流程以 AppID + openid 识别微信身份，首次登录创建普通站内会员；后续重复登录复用用户；用户可以一次性设置用户名密码，再从传统网站或 App 登录。数据库唯一约束处理并发建号，事务将身份关系、凭据更新和 refresh 会话串在一起。

这一方案限制了新增概念：没有账号自动合并，没有给网站/App 加微信快捷登录，也没有改变既有密码协议。设计类似平台登录时，先划清外部身份映射、站内账号与会话三层，再明确唯一键和首次凭据状态，最后用并发后置状态测试证明流程只有一份事实。
