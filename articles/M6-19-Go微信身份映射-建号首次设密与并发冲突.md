# 成为全栈·Go 后端篇·微信身份在 Go 中复刻：建号、首次设密与并发冲突

> 微信 code 只是一次性登录凭证，不能直接当作应用用户 ID。后端要把平台身份映射到自己的账号，并在重复回调与并发首次登录时只创建一个用户。

> 本文代码快照：提交 ceac4e0。登录流程依据冻结契约 1.12.0 与当前 Node/Go 实现；线上微信联调状态按交付报告表述。

## 前言：外部身份和站内账号是两层关系

小程序拿到 wx.login 的临时 code 后，需要把它交给后端。后端使用 AppID 和 AppSecret 向微信换取 openid，再以自己的用户体系签发 access token 与 refresh token。openid 是微信平台身份，user id 是文章系统账号；两者有关联，但不是一个概念。

首次微信登录会自动创建普通会员账号。由于用户可能还要在网站或 Flutter App 使用传统用户名密码登录，账号可在登录后设置本地凭据。这个流程复用已有注册登录契约的能力扩展，不要求网站和 App 增加微信快捷登录，也不引入复杂的跨平台绑定合并。

难点不是调用一次 HTTP API，而是确保秘密不泄露、同一个身份不会重复建号、首次设密只能完成一次、会话撤销与账号更新原子化，以及外部服务不可用时不制造半个用户。

## 一、code 必须由服务端换取 openid

客户端拿到 code 后只把 code 发给自己的后端。后端按配置的 AppID、AppSecret 和 code 请求微信 jscode2session endpoint，读取 openid。AppSecret 不能放进小程序包、前端环境变量或浏览器代码，客户端二进制可被提取。

M6 的 WechatHTTP 固定请求官方 endpoint，配置缺失时返回内部错误；HTTP client 设置 8 秒超时，并拒绝自动跟随 redirect。响应读取有字节上限，只接受 HTTP 200、无供应商错误且 openid 非空的结果。已知 code 错误与上游限流映射成契约错误，其余异常不把上游响应原文透传给客户端。

这些边界在代码里是逐条落下来的：

~~~go
// internal/auth/wechat.go（节选）
// WechatHTTP 保存官方换码配置；密钥只用于请求，不进入业务数据或日志。
type WechatHTTP struct {
	AppID, Secret string
	Client        *http.Client
}

// Exchange 访问固定微信官方地址，限制超时和重定向，并映射供应商错误。
func (w WechatHTTP) Exchange(ctx context.Context, code string) (string, error) {
	if w.AppID == "" || w.Secret == "" {
		return "", fault.New(fault.Internal)
	}
	q := url.Values{
		"appid":      {w.AppID},
		"secret":     {w.Secret},
		"js_code":    {code},
		"grant_type": {"authorization_code"},
	}
	req, err := http.NewRequestWithContext(ctx, "GET", "https://api.weixin.qq.com/sns/jscode2session?"+q.Encode(), nil)
	if err != nil {
		return "", fault.New(fault.Internal)
	}
	client := w.Client
	if client == nil {
		client = &http.Client{
			Timeout: 8 * time.Second,
			CheckRedirect: func(*http.Request, []*http.Request) error {
				return http.ErrUseLastResponse
			},
		}
	}
	r, err := client.Do(req)
	if err != nil {
		return "", fault.New(fault.Internal)
	}
	defer r.Body.Close()
	var b struct {
		OpenID string `json:"openid"`
		Code   int    `json:"errcode"`
	}
	if r.StatusCode != 200 || json.NewDecoder(io.LimitReader(r.Body, 65536)).Decode(&b) != nil {
		return "", fault.New(fault.Internal)
	}
	if b.Code == 45011 {
		return "", fault.New(fault.Limited)
	}
	if b.Code == 40029 || b.Code == 40163 || b.Code == 40226 {
		return "", fault.New(fault.Token)
	}
	if b.Code != 0 || b.OpenID == "" {
		return "", fault.New(fault.Internal)
	}
	return b.OpenID, nil
}
~~~

函数体里每一层都收着一个边界。配置缺失直接返回内部错误，不让请求带着空 secret 发出去；`http.Client` 默认超时 8 秒，`CheckRedirect` 返回 `http.ErrUseLastResponse` 表示不跟随 302，避免被上游重定向带走；响应体用 `io.LimitReader(r.Body, 65536)` 截到 64 KB，防止异常上游用超大响应拖垮内存。错误码分三档映射：`45011` 是调用频率限制，转成限流；`40029`、`40163`、`40226` 分别是 code 无效、已使用、已过期，转成令牌错误；其余非零 `errcode` 与空 `openid` 一律归为内部错误。函数只返回 `openid` 字符串，上游 JSON 原文不会被透传给调用方，也不会写进响应。

这里还有一处为测试留的口子：`WechatHTTP` 的 `Client` 字段可以注入，生产为 nil 时才构造默认客户端。`WechatClient` 接口则在更外层，允许测试替身完全绕开网络，直接决定 `Exchange` 返回哪个 `openid` 或哪种错误。

这些边界减轻错误配置和恶意上游行为的影响，但不代表 AppSecret 轮换、平台控制台配置、真实微信网络环境已经覆盖。代码里的 WechatClient 接口允许测试替身控制 code 换身份结果；替身测试证明业务分支，不等于真实微信凭据联调。写文章时要把这两种证据分开。

## 二、AppID 与 openid 组成身份唯一键

openid 的唯一范围依赖微信应用。相同用户在不同 AppID 下不应默认视为同一个平台身份，所以关联键是 app_id + open_id。数据库唯一约束承担并发首次登录的最终仲裁。

这张关系表的全部内容就是一个模型文件：

~~~go
// internal/platform/model/wechat_identities.go
// WechatIdentity AppID 和 openid 到本地用户的绑定，不保存 session_key。
type WechatIdentity struct {
	ID        int64  `gorm:"column:id;primaryKey;autoIncrement"`
	AppID     string `gorm:"column:app_id"`
	OpenID    string `gorm:"column:open_id"`
	UserID    int64  `gorm:"column:user_id"`
	CreatedAt int64  `gorm:"column:created_at"`
}

func (WechatIdentity) TableName() string { return "wechat_identities" }
~~~

只有五列，却说清了几个设计决定。`app_id` 和 `open_id` 一起构成业务上的身份键，它们指向 `user_id`，把外部平台身份与站内账号连起来。表里没有 `session_key`，没有 `unionid` 缓存，也没有头像昵称：这些要么是微信侧的敏感数据，要么可以从别处取到，存进来只会扩大泄露面。`created_at` 用毫秒整数，与模型库中其他时间列保持一致。唯一约束写在迁移 SQL 里，不写在 Go 结构体上，因为并发时的最终仲裁者是数据库而不是这段代码。

账号首次建立时，Go 生成不可预测的随机用户名，并准备随机的不可用本地密码哈希，CredentialsConfigured 标为 false。用户角色为 member、状态 active，显示名使用默认微信会员文案。响应通过 Public 映射，不暴露密码哈希或 openid，同时给客户端 canSetCredentials 能力标志。

重复登录首先按 app_id 和 open_id 查找关联。已有身份就读取并锁定对应用户，检查账号未禁用，然后签发新会话。它不会因为第二次登录再创建一个新 user，也不通过用户名猜测并合并历史账号。账号绑定合并会产生归属验证、冲突和撤销策略，属于另一套明确产品能力，不应隐含地加进此次重写。

## 三、并发首次登录用唯一约束而不是“先查再建”

两个相同 code 或两个并发 code 可能同时查不到 identity。如果只在应用层做一次 SELECT，再分别 INSERT user 和 identity，就会生成两个用户，或者其中一笔在唯一冲突后留下孤立 user。

M6 在事务中再次检查 identity，然后创建用户和身份关联；唯一约束确保同一个 app_id + open_id 只能落一条。遇到唯一冲突时，整笔事务回滚，再重试一次，第二次从数据库读取已创建身份并继续登录。只对可识别的冲突重试；数据库不可用、上游失败或其他业务错误都直接返回，不做无界循环。

重试循环的写法如下：

~~~go
// internal/auth/wechat.go（WechatLogin 的重试循环，节选）
	// 唯一身份约束裁决并发建号；仅在唯一键冲突且事务回滚后重试。
	for attempt := 0; attempt < 2; attempt++ {
		err = s.DB.WithContext(ctx).Transaction(func(tx *gorm.DB) error {
			var identity model.WechatIdentity
			err := tx.Where("app_id = ? AND open_id = ?", s.AppID, openid).First(&identity).Error
			var u model.User
			if err == gorm.ErrRecordNotFound {
				u = model.User{
					Username:              name,
					PasswordHash:          passwordHash,
					CredentialsConfigured: false,
					DisplayName:           values.Text("微信会员"),
					Role:                  "member",
					Status:                "active",
					Level:                 1,
					CreatedAt:             now,
					UpdatedAt:             now,
				}
				if err = tx.Create(&u).Error; err != nil {
					return err
				}
				identity = model.WechatIdentity{
					AppID:     s.AppID,
					OpenID:    openid,
					UserID:    u.ID,
					CreatedAt: now,
				}
				if err = tx.Create(&identity).Error; err != nil {
					return err
				}
			} else if err != nil {
				return err
			} else {
				if err = database.Lock(tx).First(&u, identity.UserID).Error; err != nil {
					return err
				}
			}
			if u.Status == "disabled" {
				return fault.New(fault.Disabled)
			}
			result, err = s.Result(tx, u)
			return err
		})
		if err == nil {
			return result, nil
		}
		if fault.Resolve(err).Code != fault.Conflict {
			return nil, err
		}
	}
	return nil, err
~~~

`for attempt := 0; attempt < 2; attempt++` 把重试上限写死为两次。第一轮失败后，只有 `fault.Resolve(err).Code` 等于 `fault.Conflict` 才会进入第二轮；数据库断开、上游失败、账号禁用这些错误会走 `return nil, err` 直接退出，一个持续故障不会把循环变成忙等。

事务里的三个分支各管一件事。查到 `gorm.ErrRecordNotFound` 说明是首次登录，先 `tx.Create(&u)` 建用户，再 `tx.Create(&identity)` 建关联，两步在一个事务里，失败则整体回滚，不会留下没有身份的孤儿用户。其他查询错误直接上抛。查到了身份，就 `database.Lock(tx).First(&u, identity.UserID)` 锁住账号行，与刷新令牌路径共用同一把锁。三条路最后都汇到 `s.Result(tx, u)`，让会话签发留在同一个事务内。

注意 `passwordHash` 是在循环外算好的。二次重试不会再跑一次 bcrypt，也不会因为重试而生成第二个用户名。

~~~text
请求 A 和 B 都先看到“尚无身份”
            ↓
A 事务创建 user + identity，唯一键获胜并提交
B 事务插入 identity 遇到唯一冲突，整笔回滚
            ↓
B 有界重试，读到 A 创建的 identity
            ↓
A、B 都映射到同一个 user，不产生孤儿记录
~~~

有界重试的依据是数据库约束已经完成仲裁，下一次读取可见获胜记录。无限重试会把持续配置错误或数据库故障变成资源耗尽。真实数据库并发测试要检查最终 identity 数量、user 数量和错误结果，而不只断言两次请求都返回 token。

## 四、首次设置用户名密码要成为一次性状态动作

首次微信登录用户没有可用本地凭据。客户端可以提示用户设置用户名密码。Go Setup 先在事务外计算 bcrypt 哈希，随后锁用户并确认：账号 active、CredentialsConfigured 仍为 false、该用户确实存在微信身份。更新使用 credentials_configured=false 条件，再检查 RowsAffected 必须为 1；若已有请求先完成，后来的请求得到冲突，不能覆盖第一次的用户名密码。

代码把这几条要求一次写全：

~~~go
// internal/auth/credentials.go（节选）
// Setup 仅为未配置凭据的微信账号设置一次用户名密码，并旋转会话。
func (s *Service) Setup(ctx context.Context, id int64, in values.Fields) (map[string]any, error) {
	hash, err := Hash(in.String("password"))
	if err != nil {
		return nil, err
	}
	var result map[string]any
	err = s.DB.WithContext(ctx).Transaction(func(tx *gorm.DB) error {
		var u model.User
		if err := database.Lock(tx).First(&u, id).Error; err != nil {
			return err
		}
		var count int64
		if err := tx.Model(&model.WechatIdentity{}).Where("user_id = ?", id).Count(&count).Error; err != nil {
			return err
		}
		if u.Status != "active" {
			return fault.New(fault.Disabled)
		}
		if u.CredentialsConfigured || count == 0 {
			return fault.New(fault.Conflict)
		}
		patch := map[string]any{
			"username":               in.String("username"),
			"password_hash":          hash,
			"credentials_configured": true,
			"updated_at":             s.Now().UnixMilli(),
		}
		r := tx.Model(&model.User{}).Where("id = ? AND credentials_configured = ?", id, false).Updates(patch)
		if r.Error != nil {
			return r.Error
		}
		if r.RowsAffected != 1 {
			return fault.New(fault.Conflict)
		}
		if err := s.Revoke(tx, id); err != nil {
			return err
		}
		if err := tx.First(&u, id).Error; err != nil {
			return err
		}
		var err error
		result, err = s.Result(tx, u)
		return err
	})
	return result, err
}
~~~

`Setup` 的第一件事是 `Hash(in.String("password"))`，bcrypt 在事务外完成，理由与登录路径相同：昂贵计算不占着数据库锁。进入事务后，`database.Lock(tx).First(&u, id)` 先锁账号，再用 `Count` 数出该用户的微信身份条数——这是“只给微信账号开放首次设密”的具体实现。三道前置检查依次是状态必须为 `active`、`CredentialsConfigured` 必须为 false、微信身份数必须大于 0，任何一条不满足就返回禁用或冲突。

真正的状态转换落在这一句上：`Where("id = ? AND credentials_configured = ?", id, false).Updates(patch)`。条件里带着 `credentials_configured = false`，所以即使两个请求都通过了前面的检查，也只有第一个能改到行；第二个拿到 `RowsAffected` 为 0，立刻返回冲突。这是“先检查、再条件更新”的组合，而不是只靠检查。改完之后 `s.Revoke(tx, id)` 撤掉旧会话，`s.Result(tx, u)` 在同一事务里签发新会话。中间还有一次 `tx.First(&u, id)` 重新读取用户，为的是让 `Result` 拿到包含新用户名的行。

更新用户名、密码哈希和凭据标记后，旧 refresh token 全部撤销，并在事务内签发新的认证结果。这样设置凭据与会话状态一起提交；任何一步失败都回滚，不会产生“已经改了用户名却没新 token”或“旧会话仍有效”的半完成状态。

后续用户可用这个用户名密码走原有登录流程。网站和 App 不需要新增微信按钮或微信 SDK；这正是把小程序外部身份接到站内通用账号后的复用价值。

## 五、失败语义和安全边界

需要覆盖的失败分支包括：上游 code 无效、微信限流、响应超时、未配置 AppID/Secret、账号禁用、唯一冲突重试耗尽、用户名占用、重复设置凭据和数据库提交失败。上游 secret、完整换码 URL 和 openid 不应写入普通日志；code 也不应长期保存或当作用户身份标识。

这些分支各自产生在哪一步、最终变成什么错误，可以列成一张对照表：

| 失败分支 | 产生位置 | 返回给客户端 |
|---|---|---|
| AppID 或 Secret 为空 | `Exchange` 入口检查 | 内部错误 |
| 上游 HTTP 非 200 或 JSON 解析失败 | `Exchange` 响应读取 | 内部错误 |
| 微信限流（errcode 45011） | `Exchange` 错误码映射 | 请求过多 |
| code 无效、已使用或已过期 | `Exchange` 错误码映射 | 令牌错误 |
| 上游超时或网络不可达 | `Exchange` 的 `client.Do` | 内部错误 |
| 账号被禁用 | 事务内状态检查 | 账号禁用 |
| 唯一冲突重试两轮仍失败 | `WechatLogin` 循环结束 | 冲突 |
| 凭据已配置或不是微信账号 | `Setup` 前置检查 | 冲突 |
| 条件更新影响行数为 0 | `Setup` 的 `RowsAffected` | 冲突 |
| 事务任意步骤返回错误 | 数据库或领域层 | 内部错误 |

前五行都在 `Exchange` 内，属于外部依赖边界；中间几行在服务事务内，属于账号状态；最后一行是基础设施错误。分开列的好处是写测试时能确定每个分支该断言哪个错误码，而不是笼统断言“请求失败”。

临时 code 是短期且一次性凭证。后端应限制 body、只接受预期格式，并尽快换取身份。拿到 openid 后数据库只保存身份映射所需值；访问 token 和 refresh token 按现有认证设计处理。用户公开响应只包含契约约定字段。

部署时还需要在环境中分别配置 AppID、AppSecret，并确认线上运行时能访问微信 endpoint。测试中的 HTTP transport 替身可以模拟错误码、重定向与超时，但不证明真实域名、密钥和平台账号已正确配置。

## 六、测试要分别证明换码和账号状态机

建议将测试拆成两层：

| 层次 | 测试输入 | 要证明的行为 |
|---|---|---|
| WechatHTTP 单测 | 200/openid、code 错误、限流、超时、redirect、超大响应 | 网络边界与错误映射 |
| WechatLogin 服务测试 | 新身份、已存在身份、禁用用户、唯一冲突 | 建号、复用与受限重试 |
| Setup 服务测试 | 首次成功、并发重复、凭据已配置、非微信用户 | 一次性状态转换 |
| 数据库并发测试 | 两次首次登录、两次设密 | 唯一身份、单一用户、会话撤销与最终状态 |
| 客户端闭环 | 微信替身登录、设置凭据、传统用户名密码登录 | 用户 ID 和权限角色保持一致 |

HTTP 替身不是“假测试”，但它回答的是可控输入下业务是否正确；真实微信测试回答生产凭据、网络和平台配置是否联通。报告两者时要分别命名。

## 小结：把微信接成身份提供方，不把账号体系推倒重来

M6 的流程以 AppID + openid 识别微信身份，首次登录创建普通站内会员；后续重复登录复用用户；用户可以一次性设置用户名密码，再从传统网站或 App 登录。数据库唯一约束处理并发建号，事务将身份关系、凭据更新和 refresh 会话串在一起。

这一方案限制了新增概念：没有账号自动合并，没有给网站/App 加微信快捷登录，也没有改变既有密码协议。设计类似平台登录时，先划清外部身份映射、站内账号与会话三层，再明确唯一键和首次凭据状态，最后用并发后置状态测试证明流程只有一份事实。
