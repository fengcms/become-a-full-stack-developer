# 成为全栈·Go 后端篇·Go 工程如何运行：模块、四个命令与退出生命周期

> 一个后端不是“执行 go run 就算启动”。模块身份、配置来源、数据库准备、进程退出和数据搬迁，都是运行模型的一部分。

> 本文代码快照：提交 ceac4e0（Go 1.26.6）；后续文档整理提交未修改 Go 业务源码。示例命令以仓库根目录的 go-backend/Makefile 为准。

## 前言：先把“怎么运行”拆成几件事

接手一个后端项目，我们通常先找启动命令。但一个可靠的运行手册至少需要回答五个问题：Go 到哪里找模块和包？开发、构建、迁移、初始化数据分别用什么命令？配置从哪里来，哪些配置缺失时要拒绝启动？进程被停止时，当前请求和数据库连接怎样收尾？数据导出和导入是否与服务启动混在一起？

M6 把这几件事拆成四个命令：server 运行 HTTP 服务，migrate 管理表结构，seed 初始化演示数据，data 承担受控的数据导出与导入。它们共享一个 Go module 和一组内部包，但不是同一个生命周期。这样安排的价值不是命令数量，而是让每项操作有清楚的副作用边界。

本文会沿着一次本地启动，从模块身份开始，走到配置、数据库连接、HTTP 运行、优雅退出，再解释迁移和数据搬迁为什么要分开。运行命令看起来简单，真正要理解的是命令背后的状态变化。

## 一、go.mod 是模块身份，不是目录说明

项目位于仓库的 go-backend/ 子目录。它自己的 go.mod 声明模块路径：

~~~go
module github.com/fengcms/become-a-full-stack-developer/go-backend

go 1.26.6
~~~

Go 的 import 路径会以 module path 为前缀。例如内部数据库包的完整导入路径是：

~~~go
"github.com/fengcms/become-a-full-stack-developer/go-backend/internal/platform/database"
~~~

本地目录叫 internal/platform/database，远程模块身份却由 go.mod 决定。理解这两件事的区别，能避免在模块路径、Git 仓库根目录、包目录之间来回混淆。go.mod 位于子目录并不妨碍 Go 工具链工作；从 go-backend/ 进入后，go test ./... 和 go build ./... 都以这个模块作为范围。

模块身份还影响未来版本标签。如果模块路径以 /go-backend 结尾，那么仓库发布时的标签需要对应模块子目录约定，例如 go-backend/v1.0.0。若主版本升到 v2，模块路径需要带上 /v2，不能只把 Git tag 改名。Go modules 把版本与导入身份连接起来，这比“给仓库随便打一个版本号”严格。当前快照没有创建正式发布 tag，所以文章里的代码快照提交用于复现，不能误写成已经发布的模块版本。

在本地开发，先进入模块目录：

~~~sh
cd go-backend
go version
go env GOMOD
~~~

GOMOD 能告诉你当前命令实际读取的是哪一个 go.mod。目录定位问题通常比代码问题更早出现；显式核对模块文件，可以排除在仓库根运行命令却误以为自己处于 Go module 的情况。

## 二、四个命令表达四种运行目的

项目 Makefile 提供了四个主要入口：

| 命令 | 对应程序 | 责任 | 是否启动 HTTP |
|---|---|---|---|
| make run | cmd/server | 本地启动 API 服务 | 是 |
| make build | server、migrate、data、seed | 编译四个可执行程序到 bin/ | 否 |
| make migrate | cmd/migrate | 按当前数据库驱动执行 goose migrations | 否 |
| make seed | cmd/seed | 插入开发用户与演示文章 | 否 |

data 是专门的数据转换工具，不参与应用启动。它通过 TRANSFER_DATABASE_URL 指定数据源或目标，支持 export/import 模式、sqlite/postgres/mysql 驱动、输入文件以及 dry-run。把 data 单列出来，是因为导出和导入可能读取大量数据、写入目标库，而且涉及文件系统；它的权限和执行时机与 web 请求不是一回事。

本地从空数据库开始的典型顺序是：

~~~sh
make migrate
make seed
make run
~~~

这三个命令不是一个不可分割的脚本。迁移失败时，seed 不应该继续制造“似乎成功”的样本；seed 冲突时，服务也可以单独启动来排查；线上运行通常不会在每次服务重启时重建演示数据。分开运行能让操作者知道哪一步改变了数据库。

make build 则把四个程序编译为 bin/server、bin/migrate、bin/data 和 bin/seed。构建产物的存在只证明 Go 编译完成，不证明数据库连得上、迁移成功、服务能访问对象存储或线上配置正确。工程文档必须把这些证据分开描述。

## 三、配置加载是进程启动边界

本项目使用配置加载逻辑读取环境变量，也允许本地 .env 文件辅助开发。dotenv 的一个重要语义是：已有进程环境变量不会被 .env 覆盖。比如 CI 已提供 DATABASE_URL，即使目录中有本地 .env，进程仍以环境变量为准。这个规则让部署平台注入的配置优先，但也意味着调试时要确认当前 shell 是否残留旧值。

服务器启动前会校验必要配置，例如数据库驱动和 DSN、足够长度的 JWT_SECRET、CORS 设置以及存储驱动相关配置。缺失或不合法的配置应使程序明确失败，而不是用空值偷偷启动一个看似正常、实际无法安全服务的实例。JWT_SECRET 至少需要 32 字节；判断的是字节长度，不是中文字符数量。

配置边界也包括密钥管理：.env 适合本机开发，不应提交真实凭据；生产密钥由运行环境注入。日志可以说明使用哪一种 driver 或某个非敏感开关，却不能打印数据库密码、JWT 密钥、访问令牌或微信密钥。错误消息应足够定位问题，同时避免把完整 DSN直接暴露到用户可见响应。

服务器不会偷偷替你跑迁移。这个决定降低了应用重启的意外副作用：滚动发布期间，新旧进程可能同时启动，若每个进程都试图改表，发布顺序会更难推理。生产的数据库结构变化由明确的 migrate 操作负责，应用启动只连接数据库并执行连通性检查。

## 四、server 的启动和退出都是有边界的

cmd/server 的生命周期可以概括为：

~~~text
读取并校验配置
        ↓
打开数据库连接池
        ↓
最多等待 5 秒检查数据库连通性
        ↓
装配依赖与 HTTP 应用
        ↓
监听请求并执行服务
        ↓ 收到 SIGINT / SIGTERM
停止接收新请求，最多等待 10 秒
        ↓
关闭数据库资源并退出
~~~

这张流程图对应的就是 cmd/server 里的两个函数：

~~~go
// cmd/server/main.go（节选，省略数据库指标输出）
func main() {
	if err := run(); err != nil {
		slog.Error("server stopped", "error", err)
		os.Exit(1)
	}
}
func run() error {
	c, err := config.Load()
	if err != nil {
		return err
	}
	db, err := database.Open(c.Driver, c.DSN)
	if err != nil {
		return err
	}
	sqlDB, _ := db.DB()
	defer sqlDB.Close()
	ctx, cancel := context.WithTimeout(context.Background(), 5*time.Second)
	err = sqlDB.PingContext(ctx)
	cancel()
	if err != nil {
		return err
	}
	app, err := bootstrap.New(db, c, bootstrap.Options{})
	if err != nil {
		return err
	}
	server := &http.Server{
		Addr:              c.Address,
		Handler:           app,
		ReadHeaderTimeout: 5 * time.Second,
		ReadTimeout:       30 * time.Second,
		WriteTimeout:      30 * time.Second,
		IdleTimeout:       60 * time.Second,
	}
	done := make(chan error, 1)
	go func() {
		slog.Info("server listening", "address", c.Address, "database", c.Driver)
		done <- server.ListenAndServe()
	}()
	signals := make(chan os.Signal, 1)
	signal.Notify(signals, syscall.SIGINT, syscall.SIGTERM)
	defer signal.Stop(signals)
	select {
	case err := <-done:
		if !errors.Is(err, http.ErrServerClosed) {
			return err
		}
	case <-signals:
		ctx, cancel := context.WithTimeout(context.Background(), 10*time.Second)
		defer cancel()
		return server.Shutdown(ctx)
	}
	return nil
}
~~~

这段代码把前面几件事串了起来。`database.Open` 之后立刻用带 5 秒超时的 `PingContext` 确认连通性，失败就返回错误；`http.Server` 的四个超时字段依次对应读头、读体、写响应和空闲连接；`select` 同时等待「服务自己退出」和「收到信号」两条路径，只有拿到 SIGINT/SIGTERM 才走 `Shutdown`。函数结尾没有单独的清理分支，是因为 `defer sqlDB.Close()` 已经挂在 `run` 的返回路径上。

数据库 ping 有五秒超时，因此错误 DSN 或不可达数据库不会让进程无限等待。HTTP Server 配置了 Header 5 秒、Read 30 秒、Write 30 秒、Idle 60 秒超时。这些值分别控制请求头读取、请求读取、响应写入和 keep-alive 空闲连接，目的是给资源使用设定上限。超时是服务行为的一部分，应按请求类型和部署环境评估，不能为了“避免超时”全部设成无限。

收到 SIGINT 或 SIGTERM 后，程序调用 HTTP Server 的优雅关闭流程，并给正在处理的请求一个最多十秒的完成窗口。达到截止时间仍未完成的请求会被取消或连接关闭。Graceful shutdown 并不意味着任意长任务都能完成：任务要尊重 context 取消，后台 goroutine 也要有明确的所有权和退出路径。本文快照里的关闭窗口是进程级资源收尾策略，不是队列任务的可靠交付机制。

数据库连接池需要在服务关闭时释放。连接池配置与单个请求的 context 也不同：请求 context 表达一次操作的截止时间和取消信号，连接池控制并发连接和复用。把这两类生命周期混为一谈，很容易写出“HTTP 已停止，但后台仍持有连接”的退出漏洞。

## 五、迁移和 seed 有自己的责任边界

migrate 命令通过 goose 管理显式版本迁移。它知道当前数据库方言，依次应用尚未执行的迁移。每个版本迁移都应能被代码审查：创建了什么表、索引、约束，是否有数据转换，回滚能力如何。ORM 的模型定义并不自动替代迁移记录，本项目不在 server 启动时调用 AutoMigrate。

seed 只用于初始化开发样本。当前实现检查演示用户名是否已存在；重复执行不会静默覆盖已有账号。初始化用户和示例文章放在同一个事务内，避免只创建了一半数据。seed 的存在不能被理解为生产建管理员的通用工具，生产账号建立应遵循部署的安全流程。

这两条规则可以合在一个心智模型里：迁移负责“数据库结构版本”，seed 负责“开发样本数据”，业务数据搬迁则由 data 命令负责。结构变化和数据迁移的回滚成本完全不同，不要用一个模糊的 startup hook 承担三种工作。

## 六、data 导入导出要显式指定来源和模式

data 命令使用 TRANSFER_DATABASE_URL，而服务的常规数据库连接由应用配置读取。分离配置可以减少操作员把迁移工具误指向服务数据库的概率，也让导入导出任务可以使用独立凭据。常见的 dry-run 形式如下：

~~~sh
TRANSFER_DATABASE_URL='postgres://...' \
  go run ./cmd/data -mode import -driver postgres -file ./backup.json -dry-run
~~~

参数名和驱动必须与当前版本实现一致；此处示意命令中的连接串应从安全环境注入，真实密钥不要贴在 shell 历史、文章或截图里。dry-run 能帮助检查文件、模式和目标配置，但它不等同于真正导入，也不能证明写入后所有业务关系都正确。实际切换之前仍需要在隔离库演练，核对记录数量、主外键、关系表、计数与附件引用。

导出可以是只读操作，但仍可能产生包含个人数据的文件。数据文件要设定访问权限、保留时间和删除方式。导入更需要谨慎：目标环境应明确、备份可用、操作可重复性经过验证。命令行工具不会因为它不是 HTTP API 就自动安全。

## 七、命令成功分别能证明什么

| 证据 | 可以说明 | 不能说明 |
|---|---|---|
| go test ./... / make verify | 当前模块的测试与工程门禁通过 | 真实生产服务已部署 |
| make build | 四个程序在当前构建环境编译成功 | 目标操作系统镜像能运行 |
| make migrate | 所选数据库已执行对应迁移 | 其他数据库方言都通过 |
| make seed | 开发样本已初始化 | 生产账号或内容已正确建立 |
| make run | 当前配置下服务启动 | 线上 DNS、TLS、代理、R2 可用 |
| data dry-run | 导入导出路径的预检执行 | 目标库数据已完整迁移 |
| Dockerfile 检视 | 构建意图和依赖路径可审阅 | 镜像已真实构建并验收 |

本项目构建使用 CGO_ENABLED=1，因此 SQLite 驱动需要本机 C 工具链。Dockerfile 采用 Debian/glibc 路径来支持原生 SQLite 依赖。我们没有以本文快照声称“已在所有 Linux 发行版构建并运行镜像”；若部署时要做跨平台镜像，必须在目标构建环境实际执行并验证动态库、架构和证书。

对教学项目来说，这类证据边界很有价值。正确报告“构建成功但未做线上部署”，比把代码具备部署配置夸成“已上线”更可信。

## 小结：运行文档要描述状态变化

这套工程把 HTTP 服务、结构迁移、开发数据初始化和数据搬迁拆开。go.mod 确定模块身份；Makefile 给出可重复入口；配置加载在启动早期拒绝不安全状态；server 设置了请求超时和有界退出；migrate、seed 与 data 各自管理一种数据库操作。

如果你要为自己的服务写运行手册，可以按同样的问题检查：命令读写什么？失败后留下什么状态？敏感值如何注入？进程被终止时会发生什么？当前成功证据覆盖哪一个环境？只有这些问题有答案，“一条启动命令”才是真正可运维的工程入口。
