# 成为全栈·基础补充·Web 安全基础：XSS、CSRF 与 SQL 注入

> Web 安全的第一步不是记住漏洞缩写，而是知道信任边界在哪里：用户输入不可信，浏览器会解释输出，数据库会执行查询，Cookie 会随请求自动发送。

## 前言：同一段文本，在不同上下文会有不同风险

文章评论里的 script 标签是一串字符，进入 HTML 后可能变成可执行脚本；字符串中的引号和 SQL 片段放进拼接语句里，可能改写查询条件；带着登录 Cookie 的浏览器访问恶意页面时，也可能悄悄向站点发起请求。

这三类风险分别是跨站脚本（XSS）、跨站请求伪造（CSRF）和 SQL 注入。它们都与“信任了不该信任的输入”有关，但触发点与防护方法不同。给所有输入做一次通用过滤，不能解决所有问题。

## 一、XSS：让数据变成了浏览器执行的代码

XSS 发生在攻击者控制的数据被页面当成可执行标记或脚本解释时。评论、文章正文、用户昵称和 URL 参数都可能成为来源。若服务端或前端把输入直接拼进 HTML，恶意标签就有机会在其他用户浏览器中执行。

基本防护原则是**按输出上下文编码**：写入 HTML 文本节点时进行 HTML 编码；写入属性、URL、JavaScript 或 CSS 时，采用各自安全的处理方式。优先使用框架默认的文本插值，不要随意启用原始 HTML 渲染。需要渲染 Markdown 或富文本时，用维护良好的解析器和严格 allowlist 清洗允许的标签、属性与 URL 协议。

输入校验仍有价值，例如限制长度、拒绝非法业务格式，但“保存前删掉所有尖括号”既会破坏合法文本，也不能覆盖所有输出上下文。CSP 可以作为额外防线限制脚本来源，却不能代替安全输出和依赖管理。

HttpOnly Cookie 可降低脚本直接读取凭证的风险，但如果页面已有 XSS，攻击者仍可能以当前用户身份发起请求、读取页面可见数据或修改内容。它是纵深防护的一层，不是 XSS 免责证明。

## 二、CSRF：浏览器替用户自动带上了凭证

如果登录状态保存在 Cookie，浏览器会按域、路径和 SameSite 规则自动在请求中携带它。恶意站点可能诱导用户浏览器向目标网站发起请求；服务端看到有效 Cookie，误以为操作由用户主动发起，这就是 CSRF 的核心条件。

常见防护包括：

- 对状态变更使用 POST/PUT/PATCH/DELETE，不通过 GET 改数据。
- Cookie 设置合适的 SameSite，HTTPS 站点使用 Secure，敏感凭证设置 HttpOnly。
- 对跨站写操作验证 CSRF token 或 Origin/Referer 等来源信息。
- 结合 CORS 限制可读取响应的来源，但不要把 CORS 当作单独的 CSRF 防护。
- 敏感操作要求重新认证或二次确认。

SameSite 的效果会受站点拓扑、嵌入场景和浏览器行为影响。若刷新 Cookie 采用跨站模式，要逐项验证 Cookie 属性、前端请求 credentials、CORS 凭据和服务端来源检查；只改其中一项，登录可能失败或留下缺口。

## 三、SQL 注入：输入改变了查询语法

危险写法把用户输入直接拼进 SQL：

    const sql = "SELECT * FROM users WHERE username = '" + username + "'";

若 username 含引号或 SQL 片段，数据库解析到的语句结构可能与开发者预期不同。正确做法是使用参数化查询：

    const result = await db.query(
      "SELECT * FROM users WHERE username = ?",
      [username],
    );

占位符语法因数据库驱动而异，但原则相同：SQL 结构由程序确定，用户值作为数据绑定。动态表名、字段名、排序方向不能通常作为普通值参数绑定；这些部分应从固定白名单映射到 SQL 片段，不能直接接收用户任意字符串。

ORM 也不代表永远没有 SQL 注入。如果使用 raw SQL、动态排序或不安全模板，仍然可能把输入拼进语句。要审查最终 SQL 的构造边界，而不只是看是否引入 ORM。

## 四、输入校验、输出编码和授权各自解决什么

| 控制 | 主要目的 | 不能替代 |
|---|---|---|
| 输入校验 | 拒绝格式和范围不合法的数据 | 输出编码、权限检查 |
| 输出编码/清洗 | 防止页面将数据解释为危险代码 | SQL 参数化、身份验证 |
| 参数化查询 | 防止值改变 SQL 语法 | 业务授权和数据范围控制 |
| 身份认证 | 确认请求来自哪个账号 | 确认该账号能否操作资源 |
| 授权检查 | 限制角色和资源归属 | 防止 XSS/SQL 注入 |
| CSP/CORS | 限制部分浏览器脚本和跨源行为 | 服务端访问控制 |

这些控制应组合使用。用户已登录，不代表他能修改任意文章；输入合法，不代表可以直接放入 HTML；使用参数化查询，也不代表用户可以读取所有行。

## 五、密钥、依赖和错误信息同样需要保护

不要把数据库密码、JWT secret、微信 AppSecret 或对象存储私钥放进前端 bundle 和公开 Git。密钥应在服务端配置，最小权限使用，并能轮换；日志、错误响应和崩溃报告需要脱敏。错误页面不要暴露堆栈、SQL 参数、内部文件路径和基础设施地址。

第三方包、构建工具、依赖更新和权限配置也属于攻击面。锁定依赖版本、运行漏洞扫描、及时修补可利用问题；对上传文件限制大小和类型，使用随机对象 key，防止路径穿越，并将可执行内容与静态站点隔离。

## 六、怎样测试安全边界

用测试确认恶意 HTML 不会执行，未知标签和危险 URL 被清理；尝试跨站表单是否能触发状态变更；检查动态排序只接受白名单字段；用越权账号请求他人资源，确认服务端返回拒绝且数据未改变。安全测试同时要验证响应和后置状态。

不要在真实生产账号和数据上进行攻击性测试。使用隔离环境、虚构账户和专门 payload；运行扫描器后仍需人工理解发现结果。工具报告是线索，不是安全认证。

## 小结：按解释上下文选择防护

XSS 关注浏览器如何解释输出，CSRF 关注浏览器如何自动携带凭证，SQL 注入关注输入能否改变数据库语句结构。输出编码、CSRF 防护、参数化查询、身份授权和密钥管理各有边界。先确定数据从哪来、会进入什么执行上下文，再选择防护并用测试验证。
