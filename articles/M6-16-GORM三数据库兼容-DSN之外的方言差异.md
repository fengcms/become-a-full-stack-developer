# 成为全栈·Go 后端篇·GORM 支持三数据库：三个 DSN 远远不够

> 能连接 PostgreSQL、MySQL、SQLite，只能说明驱动打开了连接。真正的多数据库支持，要证明类型、排序、锁、迁移和失败行为都符合业务预期。

> 本文代码快照：提交 ceac4e0。PostgreSQL 为主库，MySQL 与 SQLite 有独立迁移和真实服务验证。

## 前言：驱动列表不是兼容性报告

Go 服务通过 GORM 打开 PostgreSQL、MySQL 和 SQLite，代码里存在三个 dialector。很多项目看到这里就会写“支持三种数据库”。但一个成功建立的连接，并不能说明相同查询在三种方言下返回相同结果，也不能说明事务、唯一约束、时间和排序规则一致。

M6 明确把 PostgreSQL 作为主数据库，同时验证 MySQL 与 SQLite。为了达到这个目标，工程不仅配置三个驱动，还为每个数据库维护显式 goose SQL migration、设置 SQLite 外键与 WAL、使用单写连接，并针对数据库特有行为测试。实现中仍有针对方言的适配，因为 GORM 抽象掉了部分 SQL 书写，却没有消除数据库本身的语义差异。

本文从连接池开始，依次讨论时间与布尔表示、唯一约束与排序、RowsAffected、锁和 SQLite 写入，再总结怎样为“支持某数据库”准备证据。

## 一、连接配置是每种数据库的第一道差异

database.Open 根据 driver 选择 GORM PostgreSQL、MySQL 或 SQLite dialector，并启用错误翻译、静默 ORM logger 与 SkipDefaultTransaction。普通连接池允许最多 16 个打开连接、4 个空闲连接，连接最长复用 30 分钟；SQLite 则将 MaxOpenConns 限为 1。

为什么 SQLite 单独处理？在这个项目的本地和迁移使用方式中，单连接把写入串行化，减少同一文件库的并发写冲突。SQLite 启用 WAL、busy_timeout 和 foreign_keys。WAL 能改善读写并发体验，但不代表可以无条件运行多个独立写实例；一个连接池内单连接也不能消除其他进程对同一数据库文件的竞争。

DSN 中显式要求开启外键，避免调用方意外关闭后让文章关系或附件引用失去数据库约束。busy timeout 给锁竞争一个有限等待窗口；超过后仍可能失败，业务层要能回滚并向客户端返回合适错误。增加 timeout 不是把 SQLite 变成多写数据库。

PostgreSQL 和 MySQL 的池设置也需结合实例连接限制与部署拓扑调整。连接池配得过大可能让应用连接数超过数据库上限，配得过小则引发排队。每进程最大 16 条并不等于整个服务集群最多 16 条；实例数、迁移工具和监控任务都要计入总账。

## 二、时间和布尔需要统一到业务语义

M6 的业务时间以毫秒级 Unix 时间存储，再由 values.ISO 转换成契约使用的 UTC 毫秒字符串。这样避免 ORM 在不同驱动中自动决定时区和小数精度。写入与读取都遵循同一转换规则，nullable 时间使用指针保留 NULL。

如果把一个时间交给三种数据库的默认 timestamp 类型，列类型、时区解释、精度和驱动扫描形式可能不同。特别是只有秒级精度的数据库字段会把两条同毫秒内记录变成同一时间，稳定排序和边界测试也会变化。项目选择统一毫秒整数后，仍要确认整数范围、JSON 格式和所有客户端解析约定。

布尔字段也要用真实方言测试。SQLite 没有和 PostgreSQL 完全相同的原生 Boolean 存储类型；GORM 驱动会在底层映射值。应用不能仅依赖“字段是 bool”就假定迁移 DDL、默认值、索引和读取行为等价。数据库门禁需要检查字段定义和查询结果。

## 三、字符串排序与唯一性不只是 collation 设置

文章 slug、用户名和标签名可能参与唯一约束或搜索比较。不同数据库的默认字符集、大小写规则、尾随空格处理、索引长度与排序规则可能造成差异。一个环境认为两个值不同，另一个环境可能认为它们相同；反过来也可能发生。

例如数据库若按不区分大小写的规则比较 slug，Foo 和 foo 可能冲突；若按二进制或大小写敏感排序，它们可能成为不同记录。标签查询和排序顺序也会因此不同。要保持契约行为，先明确产品层规范化规则，再让方言 migration 建立相应列与索引，最后测试边界值。不可把测试中的默认数据库排序当作 API 排序协议。

SQL order by 也必须显式设置次级排序，避免时间相同记录的顺序不稳定。LIKE/搜索的大小写行为需按照各库 SQL 语义验证，必要时在数据库适配层使用确定表达式。不可为了兼容把输入一律小写，除非契约和既有 Node 逻辑本来如此。

## 四、RowsAffected 和 upsert 行为要看业务动作

GORM 可以通过 RowsAffected 让服务判断某条更新是否改变行，但不同 driver 对冲突写入、重复值更新和 affected rows 的报告可能不同。MySQL 默认行为尤其容易让代码把“记录存在但值未变化”与“没有匹配行”混淆。若业务语义依赖计数、幂等和首次创建，必须为每种操作设计明确 SQL 和数据库级唯一约束，并在三个驱动上验证。

像点赞、收藏这种关系，不应仅靠“先查不存在，再插入”来保证幂等；两个并发请求可能同时通过查询。数据库唯一键是最终保护，冲突后的处理再按驱动语义统一。与计数更新相关时，还要保证关系记录和计数变化处于同一事务。文章路线 M6-25 会专门追踪这类不变量。

SQLite、PostgreSQL、MySQL 的 upsert 语法不同。GORM clause.OnConflict 可表达部分共同意图，但字段名、更新表达式、冲突目标和 affected rows 的结果仍要观察。跨库抽象可以减少重复代码，不会替代集成测试。

## 五、锁语义随数据库而变化

刷新 token 轮换、点赞计数以及文章状态转换可能需要数据库行锁或条件更新。PostgreSQL 的 row-level locking 能锁定指定记录；MySQL InnoDB 也有相应锁语义，但隔离级别和索引计划会影响锁范围；SQLite 使用文件级写锁模型，不能把 FOR UPDATE 的方法调用理解成三库完全相同的保护。

工程要使用具体适配和条件更新控制竞争，再用并发测试检查结果。锁只能保护当前事务触及的数据，不会替代唯一约束；进程互斥只保护一个进程，不会跨副本；事务回滚也无法回滚 R2 对象存储操作。锁范围、顺序和提交结果需要结合具体业务设计。

M6 为 SQLite 设单写连接，是运行策略中的限制而非数据库锁的万能替代。若未来水平扩容，必须重新评估写拓扑，不能仅把连接池数改大。

## 六、显式 migration 让方言差异可见

项目有 15 张业务表，并按 PostgreSQL、MySQL、SQLite 分别维护两个 goose 版本 migration。GORM model 描述字段映射，但启动时不会 AutoMigrate；结构变更通过显式 SQL 版本化。这让团队可以审阅不同数据库对字段类型、索引、约束和默认值的实际定义。

迁移不仅要在空库执行，还要从上一版本升级，检查既有数据保留和约束是否建立。数据库 schema 相同名字不表示实际类型和约束一样。每个方言的迁移目录都必须参与检查，不能只改 PostgreSQL 的 SQL 后默认另外两种也能运行。

## 七、把“支持”写成可复核的矩阵

一份可信的数据库兼容报告至少应覆盖：

| 面向 | PostgreSQL | MySQL | SQLite |
|---|---|---|---|
| 空库 migration | 实际数据库执行 | 实际数据库执行 | 文件库执行 |
| 升级 migration | 保留既有数据 | 保留既有数据 | 保留既有数据 |
| 唯一冲突/幂等 | 真实操作与并发 | 真实操作与并发 | 真实操作与并发 |
| 时间与空值 | 写入读取边界 | 写入读取边界 | 写入读取边界 |
| 分页排序/搜索 | 稳定结果 | 排序与比较规则 | 实际查询结果 |
| 锁与事务 | 关键竞争用例 | 关键竞争用例 | 单写和锁超时 |
| 回滚/失败 | 后置状态核对 | 后置状态核对 | 文件库重新查询 |

这里的“真实数据库”很重要。用 SQLite 替身跑完所有测试，最多能证明 SQLite 下通过，不能证明另外两种数据库。CI 若无法提供某个数据库，也应明确标记该矩阵未执行，而不能根据 GORM 文档推断兼容。

## 小结：多数据库是一组可验证承诺

GORM 的三个 driver 是入口，不是结论。连接池与 SQLite WAL、外键和单写策略只是起点；时间精度、排序规则、RowsAffected、冲突语义、锁和 migration 都需要方言意识。M6 通过每库显式 SQL 和真实数据库矩阵来支撑兼容承诺。

如果你准备支持第二种数据库，先列出业务依赖了哪些数据库语义，再逐项设计测试。抽象层能隐藏重复的调用方式，但只有真实运行才能证明它没有隐藏行为差异。
