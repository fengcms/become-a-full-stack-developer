# 成为全栈·Flutter App 篇·投稿状态机：草稿、待审核与已发布

编辑器是这个项目里唯一一个"用户投入了真实劳动"的界面。用户花了四十分钟写了一篇文章，然后点了提交——**然后呢？**

我第一版写的是：提交成功，提示"已发布"。

但后端的行为不一样。M1 定的规则是投稿要过审：**提交后进入 `pending`，管理员通过后才变 `published`。**

于是就出现了一个我最初觉得是"接口设计问题"、后来才明白是**最正常的一种设计**的情况：

**用户的文章提交成功了，但没有发布。**

这篇讲 `features/editor.dart` 那三百九十九行里的状态处理，以及一个更麻烦的问题——**用户可能在另一台设备上也在改这一篇稿件。**

## 三个状态，客户端不能自己编

先把状态机说清楚：

```text
新建 ─────────────→ draft
                      ↓ 保存
                    draft
                      ↓ 提交审核
                    pending ──→ （管理员通过）→ published
                      ↓           published
                    pending        ↓ 修改
                                  pending（重新审核）
```

这张图里有几个客户端特别容易搞错的地方：

**第一，`draft → published` 不存在。** 草稿不能直接发布，必须先提交审核。这条链路在界面上要表达出来——如果编辑器只有一个"保存"和一个"提交审核"两个按钮，那是对的；如果只有"保存"，用户会以为保存完就发布了。

**第二，`pending → published` 客户端做不了。** 这是管理员的动作。客户端唯一能做的是显示"审核中"。

**第三，已发布文章被修改后，会重新进入 `pending`。** 这一点最反直觉——用户改一个错别字，结果文章下线了要重新审。

但这个规则是对的：**已经发布的内容被改动，等于产生了一份未审核的新内容。** 如果不重新审，就等于开了后门——任何作者都能先发一篇文章，然后把敏感内容改进去。

所以现在的处理是：**修改已发布文章时，界面明确提示"修改后需要重新审核"**（和 M4-18 那个改密码提示是同一个模式：**会造成后果的操作要提前告知**）。

## 动作按钮由状态决定

界面上的按钮不是固定的，是根据状态算出来的：

```dart
Set<ArticleAction> actionsFor(ArticleStatus status) => switch (status) {
  ArticleStatus.draft => {ArticleAction.edit, ArticleAction.submit},
  ArticleStatus.pending => {ArticleAction.edit},
  ArticleStatus.published => {ArticleAction.edit, ArticleAction.delete},
};
```

三个状态，分别对应三套动作。这里有个刻意的缺失：**`pending` 状态下没有"撤回"按钮。**

产品文案里我原本写过"作者可以撤回待审核的文章"。但实现的时候发现——**服务端没有这个能力**。

现在有两个选择：要么去后端加这个端点，要么把文案里的这句话删掉。

我选了后者。理由是：**一个点了会报错的按钮，比没有这个按钮糟糕得多。** 而且这个功能其实价值不大——审核通常很快，用户等一下就行。

那如果用户后悔了呢？答案是**什么都不用做**——`pending` 状态下仍然可以编辑。如果他改着改着不想发了，可以直接放着。审核通过之后那才是需要"删除"的时候。

**"暂时不做"在这里比"做一个半成品"好。**

## 保存和提交是同一个函数

```dart
Future<void> save(bool submit) async {
```

一个参数，两个动作。因为它们的流程几乎完全一样：校验 → 检查冲突 → 发请求 → 成功回写状态。

```dart
if (submit && status == 'draft') { ... }
```

唯一的区别在成功后怎么处理结果：

```dart
if (wasNew && status != (submit ? 'pending' : 'draft')) { ... }
if (submit && status == 'draft') { ... }
```

- 新建时保存 → 状态是 `draft`
- 新建时提交 → 状态是 `pending`
- 编辑已发布时保存 → 后端把它退回 `pending`

**注意最后这一条：客户端不能假设"保存完还是原来的状态"。** 后端有权改变状态，而客户端必须用服务端返回的值：

```dart
updatedAt = a.data.updatedAt ?? '';
```

这行出现两次，而且是在请求成功之后。**服务端的 `status` 和 `updatedAt` 是唯一权威**，客户端的本地状态只是乐观假设。

## 冲突检测：更新前再读一次

现在说那个更麻烦的问题。

用户 A 在手机上编辑一篇已发布的文章，改了几个字，还没有保存。这时候他在平板上也打开了这篇，改了另一段，然后保存了。

现在手机上的用户 A 点保存——**服务端的数据被覆盖了，平板上改的内容消失。**

这个问题服务端能不能解决？能，用版本号或者 `If-Match`/`ETag`。但本项目的契约里只有 `updatedAt`。

所以客户端做了一层乐观检测：

```dart
// 保存已有稿件前再次请求私有详情
if (latest.data.updatedAt != updatedAt) {
  // → 提示冲突
}
```

完整一点的写法：

```dart
Future<void> save(bool submit) async {
  ...
  if (id != null) {
    final latest = await api.request(Endpoints.article(id!));
    if (latest.data.updatedAt != updatedAt) {
      // 服务端已被修改：提示用户，不要覆盖
    }
  }
  ...
}
```

而 `updatedAt` 这个基准值是从哪来的？进页面时读的：

```dart
updatedAt = a.data.updatedAt ?? '';
```

**所以整个检测依赖一个前提：这个值从进页面到保存之间，一直存在内存里没有被改过。**

### 这个检测防不住什么

必须说清楚它的边界，因为**假装它能防住并发是危险的**：

| 能防住 | 防不住 |
|---|---|
| 用户在**另一台设备**改了同一篇 | 另一个客户端在**这次 GET 和 PUT 之间**又保存了 |
| 多人协作时的意外覆盖 | 完全没有版本控制的严格原子性 |

第二行是本质问题：客户端做的是"检查—然后执行"，这两步之间有时间差。如果服务端不校验版本，那么**两个客户端同时保存，两边都可能通过检查**。

**真正的解法在服务端**：更新时要求带上"我基于哪个版本修改"（`If-Match` / ETag / 版本号字段），由服务端原子地比对和拒绝。

现在这层检查的价值是：**它挡住了绝大多数误覆盖场景**（人不会精确地在同一个毫秒点保存），代价只是一次额外的 GET。**它不是分布式锁，但比什么都不做安全得多。**

## 本机草稿：编辑器真正的保险

现在讲这个功能里我认为最重要的部分。

前面所有讨论都是"服务端怎么存"。但用户可能面临更糟的情况：**写了四十分钟，App 崩溃了，或者手机没电了。**

所以本机存一份草稿：

```dart
String get draftKey =>
  'draft.${Uri.parse(ref.read(sessionProvider).api.baseUrl).authority}.$owner.${id ?? 'new'}';
```

这个键的三个部分各挡一类问题：

| 组成 | 挡什么 |
|---|---|
| `baseUrl` 的 authority | 开发环境和线上环境的草稿不串（和 M4-14 的别名表同一个道理） |
| `owner` | **A 用户的草稿不会被 B 用户看到** |
| `id ?? 'new'` | 新文章和已有文章分别存 |

**`owner` 是关键。** 没有它的话，用户 A 退出登录、用户 B 登录，B 会看到 A 的草稿——**这是实实在在的隐私问题**，而且发生概率不低（家庭共用设备）。

草稿内容包含什么：

```dart
Map<String, dynamic> draft() => {
  ...
  'baseUpdatedAt': updatedAt,
};
```

**存了 `baseUpdatedAt`。** 这个字段的用途是恢复草稿时的冲突判断——如果草稿是基于某个旧版本写的，而服务端已经变了，恢复出来之后用户保存会被上面的检测拦住。**没有它，恢复出来的草稿可能覆盖别人的修改。**

写入是串行的：

```dart
final value = jsonEncode(draft()), key = draftKey;
draftWrite = draftWrite.catchError((Object _) {}).then((_) async {
  ...prefs.setString(key, value);
});
return draftWrite;
```

和 M4-09 那个 `_persist` **是同一个模式**：`catchError` 吞掉上一次的失败，否则前一次写失败会让整条链断掉，之后的保存全都不执行。

这个串行化是必需的——**如果两次保存并发，最后写入的不一定是最后修改的那份。** 而草稿是用户唯一的数据备份，写丢一次就是真的丢了。

保存成功后清草稿：

```dart
await draftWrite;
await prefs.remove(draftKey);
```

**注意先 `await draftWrite` 再 `remove`。** 如果并发执行，`remove` 可能先于某次写入完成——**结果是一篇已保存的文章，它的草稿还留在本机。** 下次进编辑器会提示"发现草稿"，但内容和服务端一样，制造一次虚假的冲突提示。

顺序反过来就不对。这和"提交后再清理缓存"是同一个原则：**清理必须在写入确认之后。**

## 离开保护

最后一个容易被忽略的：`PopScope`。

```dart
Widget build(BuildContext context) => PopScope(
  canPop: allowLeave || (!dirty && !busy),
```

`canPop` 为 false 时，系统返回手势和返回键都失效，需要自己弹出确认框。

三个条件：

- `allowLeave`：**保存成功后要给一条出路**——用户刚存完，再提示"有未保存内容"是荒谬的
- `!dirty`：内容没改过就不拦
- `!busy`：正在请求时不能拦，否则用户走了请求还在飞

而 `dirty` 的判断是**和服务器端内容的比较**，不是"用户有没有碰过键盘"。用户打开编辑器随手点了一下又撤销了，内容没变，就不算 dirty。**否则用户会频繁看到"确定离开吗"，很快就不理这个提示了。**

这个和 M4-18 的"改密码要重新登录"提示是同一类问题的两种做法：一个是**事前告知**，一个是**事前拦截**。区别在于后果严重程度——丢四十分钟的文章比丢一个登录态严重得多，所以要拦截。

## 私有预览不走公开缓存

用户在待审核状态下点"预览"，能看到自己的文章。这个预览有几个特殊要求：

```dart
// 本人预览走鉴权请求并绕过公开正文缓存。
Future<Article> article(String id, {bool private = false}) async =>
    Article.fromJson(
      private
          ? jsonMap(await api.request(Endpoints.article(id)))
          : jsonMap((await bundle(id))['article']),
    );
```

`private: true` 走 `api.request` 直连，**完全绕过缓存**。理由上一篇讲过：**待审核的稿件如果进了公开正文缓存，可能被任何用户读到。** 这是安全事故，不是体验问题。

而 M4-13 讲过的那个 `publicImages` 和代码块的 `public` 开关，在预览状态下也要关掉：

```dart
/// 正文渲染依赖内容、目录定位键与主题，私有预览禁用公开图片和词法缓存。
ReaderMarkdown(
  content: ...,
  publicImages: !preview,
)
```

**三处隔离：正文缓存、图片缓存、代码高亮缓存。** 漏掉任何一处都是泄露。

## 验收该测什么

投稿是这个项目里最需要测试的功能，因为它涉及不可逆的操作：

| 场景 | 该验证 |
|---|---|
| 新建后保存 | 状态是 `draft`，草稿被清除 |
| 新建后提交 | 状态是 `pending`，不是 `published` |
| 编辑已发布文章 | 服务端返回 `pending`，界面更新 |
| 服务端状态被别人改了 | 保存被拦截，草稿保留 |
| App 崩溃后重进 | 草稿被恢复到编辑器 |
| B 登录 | 看不到 A 的草稿 |
| 开发环境切线上 | 草稿不串 |

其中"服务端状态被别人改了"这条最容易漏测，因为要构造两个客户端。**我的做法是在测试里手动改一下服务端数据的时间戳**，模拟另一个设备保存过。

而"App 崩溃后重进"这条要有真实的测试入口——现在测试里是直接调 `recoverDraft`，绕过了"什么时候会触发恢复"的逻辑。**这是一个我知道的测试盲区。**

## 一条我一开始想省掉的事

草稿保存的串行链，我最初写的是直接调：

```dart
prefs.setString(key, value);      // 不 await，不排队
```

看起来能工作。问题在**快速连续输入的场景**——用户打字很快，而 `setString` 是异步的。如果他在 100 毫秒内触发了两次保存，两次写入并发，**后写入的不一定是最后的内容**。

这个 bug 的表现极其恶劣：**用户刚打的一句话消失了**。而且难复现——要特定时序。

加上串行链之后，每次保存都排队执行，顺序保证。而 `catchError((Object _) {})` 那句保证前一次失败不会污染后面。

顺带说一个我没有做的优化：草稿写入现在**每次按键都触发**（或者说是每个 debounce 周期）。理论上可以只在离开页面时写一次，但那样崩溃就丢了。**高频写入换来的是"任何时刻崩溃都不丢数据"，我选了这个。** 代价是存储写入次数多，而 `SharedPreferences` 的写入成本在移动端并不高（底层是异步的 KV 存储）。

这个权衡和 M4-14 那个"浏览量宁可多算"是同一类：**在数据保真和数据成本之间，选择保真。**

## 小结

投稿状态机看着简单，但客户端要处理的不是一个"状态字段"，而是三件事：

1. **状态决定可用动作**，而不是反过来。而且要诚实地反映服务端能力——没有"撤回"就不画这个按钮。
2. **服务端是状态的唯一权威**，客户端的 `status` 和 `updatedAt` 都只是乐观假设，响应回来必须覆盖。
3. **并发修改靠检测减少，靠版本控制解决**。`updatedAt` 比较能挡住大多数误覆盖，但挡不住精确时序的并发——真正的解法在服务端的原子校验。

而这一页真正不可替代的部分不是状态机，是**本机草稿**：带 owner 隔离、带环境隔离、带串行写入、清理在写入确认之后。

**如果只能保留一个机制，我会保留草稿。** 因为状态显示错了用户能看出来、自己写的东西丢了用户永远无法挽回。
