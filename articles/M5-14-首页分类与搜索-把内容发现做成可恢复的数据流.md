# 成为全栈·Taro 小程序篇·首页、分类与搜索：把内容发现做成可恢复的数据流

> 内容入口看起来是几块卡片，底下却是不同的数据来源。把它们混成一个请求或一个数组，错误与恢复都会变得含糊。

{{IMG:M5-14-封面}}

## 前言：读者不是来欣赏接口列表的

首页要让读者开始阅读，分类要帮他沿着系列学习，搜索要让他找回知道大概名字的文章。它们都展示文章，却不是同一个任务。

从 APP 功能迁移过来时，我没有把它们合成一个“万能文章页”。首页保留焦点、最新、热门和持续列表，分类显示层级与标签，搜索区分输入中的文字和已提交查询。

这篇讨论的，是这几种入口怎样共享读取能力，同时保留自己的状态。页面恢复并不只是少请求一次，还包括不让读者丢掉刚刚表达的意图。

## 一、首页按模块组织，不让装饰绑架正文

当前首页分别读取文章流、阅读量排序的热门三篇、发布时间排序的焦点三篇，以及站点设置。焦点请求暂时没有结果时，可以从已加载文章流取前三篇。

四份读取各自独立，谁失败都不影响其他模块继续显示：

```tsx
// src/pages/index/index.tsx（节选）：四份独立读取，失败互不牵连。
const feed = useFeed("/articles");
const popular = useResource<Page<Article>>("/articles?sort=-viewCount&pageSize=3");
const focus = useResource<Page<Article>>("/articles?sort=-publishedAt&pageSize=3");
const settings = useResource<{ copyright: string; siteDescription: string }>("/site/settings");
const featured = focus.data?.list.length ? focus.data.list : feed.items.slice(0, 3);
```

这个组合没有专门“广告管理”的新后端。中间横幅是小程序内的系列学习入口，点击进入分类，不应写成已经接入广告投放系统。视觉形态相似，业务能力并不相同。

| 模块 | 当前数据或行为 | 失败时的影响 |
|---|---|---|
| 顶部入口 | 搜索与通知图标 | 不依赖文章请求 |
| 焦点轮播 | 最新三篇，必要时用文章流兜底 | 不应阻断下方列表 |
| 最新发布 | 文章流前三篇 | 随列表加载出现 |
| 大家都在读 | 按阅读量排序三篇 | 独立错误与重试 |
| 发现更多 | 每页 12 条的持续列表 | 保留已显示内容并提示失败 |
| 页脚 | 站点版权设置，缺失时默认文案 | 不阻断阅读 |

我选择多份小请求，是为了让数据来源与失败边界清楚。它不是一个无条件性能最优的结论；若接口成本提高，可以评估聚合端点，但聚合后仍要保留局部状态含义。

拆开还有一个副作用值得说明：图片、标题和数字在首屏出现的时机不再统一。读者可能先看到列表、后看到热门。这在教学项目里是可以接受的——比起同时变灰，一块能先读的内容更有用。

另一个实际约束是请求数量。首屏会同时发起文章流、热门、焦点与站点设置四份读取，它们共享同一个公共缓存分区。容量与 TTL 都是按这个规模估算的；如果以后再加模块，就应该回头看看 80 条的上限是否还合适。

## 二、分类树里的展开和进入，是两种动作

分类节点既可以展开子项，也可以进入该分类文章。如果点击整行同时触发两件事，读者很容易迷路。

当前 Branch 组件把“进入列表”和“展开／收起”分开。顶层默认展开，子层保留自己的 expanded 状态。进入文章列表传分类 slug，标题显示分类 name。

这是接口参数与界面文案的区分。数字 ID、slug、name 不能因为都叫“分类”就相互替代。文章页拿到 categoryId 时，还需要从分类树找到 slug，再形成列表跳转。

把两种动作放在同一个组件里，还有一个好处：展开状态天生属于本地。它不需要进缓存，也不需要进后端。判断一个状态该放哪里，先看它是否只服务于当前这次点击，基本就能得出结论。

标签入口也走列表筛选。后续增加新的入口时，应先确认契约接受的筛选值，而不是直接把显示文字原样拼进请求。

## 三、输入状态与查询状态，必须拆开

搜索页保留 `input` 与 `query` 两个状态。输入框每次变化只改 input，确认或按钮提交后才更新 query，trim 后的空字符串不发请求。

```ts
// src/pages/search/index.tsx（节选）：输入与查询是两个状态。
const historyKey = "befull:search-history";
const [input, setInput] = useState(""),
  [query, setQuery] = useState("");
const [history, setHistory] = useState<string[]>(() => {
  const value = Taro.getStorageSync(historyKey);
  return Array.isArray(value) ? value.slice(0, 12) : [];
});
const tags = useResource<Tag[]>("/tags"),
  feed = useFeed(query ? `/search?q=${encodeURIComponent(query)}` : "");
function submit(value = input) {
  const q = value.trim();
  if (!q) return;
  setInput(q);
  setQuery(q);
  const next = [q, ...history.filter((s) => s !== q)].slice(0, 12);
  setHistory(next);
  Taro.setStorageSync(historyKey, next);
  Taro.hideKeyboard();
}
```

注意 `feed` 只在 `query` 非空时才拿到路径。空字符串传给 `useFeed` 会在内部直接短路，因此初始状态不会发出一次无意义的全量请求。

因此，这不是网站端的实时搜索方案。它减少逐字请求，更适合当前移动输入流程。文章标题仍可讨论搜索数据流，但正文必须点明“提交式搜索”。

最近搜索最多保留 12 项，去重后把新项放前面。当前历史键是设备级固定键，没有按 API 或会员分区；它表示本机使用痕迹，不属于服务器私人搜索记录。同一设备换账号会看到同一份历史，清空入口应保持可见。

## 四、统一分页，先归一响应再合并文章

useFeed 接收普通 Page、搜索结果里的 articles Page，以及部分列表返回的数组。阅读历史还需要先把 HistoryItem 中的 article 解包。

```ts
// src/hooks/data.ts（节选）：归一响应，再按文章 ID 去重。
const separator = path.includes("?") ? "&" : "?";
let result = await read<
  Page<Article | HistoryItem> | Article[] | { articles: Page<Article> }
>(`${path}${separator}page=${next}&pageSize=12`, force, privateData);
if ("articles" in result) result = result.articles;
const list = (Array.isArray(result) ? result : result.list).map((item) =>
  "article" in item ? item.article : item,
);
if (id !== serial.current || (privateData && epoch !== sessionEpoch())) return;
setItems((old) => [
  ...new Map((reset ? list : [...old, ...list]).map((a) => [a.id, a])).values(),
]);
setMore(Array.isArray(result) ? list.length === 12 : next < result.pagination.totalPages);
```

这一段解决展示模型差异，不创造服务端不存在的分页能力。对于裸数组，当前使用长度判断是否还有下一页；若端点实际不分页，仍要按契约认识它的限制，不能把所有列表都宣传成无限滚动。

正常 Page 用 totalPages 判断结尾，下一页失败不推进页码。切换查询会重置列表，并通过请求序号拒绝旧响应。缓存键包含完整查询，因此分类 A、分类 B 与不同关键词不会命中同一个结果。

路径变化时的重置动作集中在同一个 effect 里，避免状态更新散落各处：

```ts
// src/hooks/data.ts（节选）：路径变化即重置列表与页码。
useEffect(() => {
  serial.current++;
  lock.current = false;
  setItems([]);
  setPage(0);
  setMore(true);
  if (path && (!privateData || auth)) void latest.current(true);
}, [path, privateData, auth?.user.id]);
```

## 五、没有结果和请求失败，不能画成同一个状态

搜索没有匹配文章，应该告诉读者可以换一个词；请求失败则提供重试。列表末尾也应区分“已到底”和“暂时加载失败”。

当前 Feed 与 State 承担基础展示。它们能让页面保持一致，但仍需要页面传对 loading、error 和 empty。状态组件本身不会猜测一个空数组是成功无结果还是请求尚未开始。

恢复也有层次：当前 Tab 可以保留本次打开期间的查询；内存缓存可以复用短时间结果；本机历史可以帮助关闭后重新选择。我们没有实现服务端跨设备搜索历史，也没有序列化整个列表滚动状态。

也正因为恢复是分层的，验收时要一层一层看：切走再回来，查询还在不在；退出小程序再进来，历史还在不在；换一个账号，看到的是不是同一个人的记录。三个问题的答案不同，能说明的可靠性也不同——前两个验证本机体验，最后一个验证归属有没有守住。

还要承认一点：历史记录是设备级的，因此它天然不适合承载敏感信息。当前它只存关键词，没有文章正文或身份标识。如果以后想让它变成“跨设备同步的收藏式历史”，那就是一个新的产品能力，需要新的归属设计，而不是把键改一改。


## 顺着一次搜索，检查所有状态归属

假设用户输入“缓存”，还没提交，又改成“评论”。此时结果列表不应该随着第一段输入闪动，因为 query 仍没有更新。提交后，完整查询路径才进入读取层。

搜索结果展开到第二页，再点进文章返回，当前运行中的查询仍在。若之后清空 query，页面返回最近搜索和关键词区；这不等于删除服务器数据，也不等于清除文章缓存。每个按钮只处理它承诺的状态。

再假设网络故意让旧关键词响应晚到。路径变化触发序号变化，旧结果不能覆盖当前列表。去重也只处理同一结果集里重复文章，不能替代响应归属判断：不同查询恰好有相同文章，不代表它们可以随意合并。

### 分类标题是给人看的，筛选参数是给契约看的

浏览页同时接收 title 和 category／tag。title 只是页面标题，真正请求条件来自筛选参数。这样，显示名称变化不必改变接口含义，读者也能看到友好的标题。

不过，参数都需要编码。空格、中文与特殊符号如果直接拼接进 URL，会让查询边界变得含糊。项目导航与筛选路径均显式编码，但后端仍负责验证可接受的字段和值，客户端编码不是业务校验。

当前排序提供发布时间、阅读量和点赞数三个选项。切换排序需要从第一页重来，不能在已加载的旧排序数组后追加新排序第二页。useFeed 将完整 path 当作状态重置依据，正是为了让排序与分页一起变化。

### 作者主页为何采用另一种翻页方式

公开作者页按页读取，提供上一页和下一页，依据 articleCount 决定后续页。它没有强行套无限流。作者作品集合和首页发现流的使用目标不同，保留一个可回到上一页的明确分页也合理。

这说明共享数据能力不要求共享每个交互。基础卡片可以一致，分页意图可以不同；后端返回 Page 与公开会员对象也有不同结构。模块复用应该保留这些事实，而不是为一个 Hook 扭曲所有响应。

后续如果要保存精确滚动位置，需要再定义数据快照、排序稳定性与恢复时机。当前缓存与 Tab 保留状态改善短路径返回，并没有完成关闭后原位置恢复。这条边界值得在设计和文章里都写清楚。

## 六、用读者路径验证数据流

本次线上首页与文章阅读已在开发工具观察；逻辑测试验证缓存与请求隔离。账号隔离与并发读取在测试里被固定成可重复的断言：

```ts
// test/core.test.ts：两次失败请求只交换一次会话。
setSession(auth(1));
mockRequest(async (o) => {
  if (o.url.endsWith("/auth/refresh")) {
    refresh++;
    return ok(auth(1, "new"));
  }
  return o.header.Authorization === "Bearer old" ? expired() : ok("accepted");
});
assert.equal(refresh, 1);
```

若要增加更细的体验证据，可检查搜索 A 后切换 B，故意让 A 慢返回；或者加载第二页失败，再确认重试仍请求第二页。

这些是可复现的检查方法，不应写成已经全部人工跑过。读者路径比接口数量更能揭示问题：找到文章、进入阅读、返回继续、再换筛选，数据是否仍属于他的选择？

数据流写清楚之后，页面里剩下的问题基本都能归到三类：状态放在哪里，失败怎么表达，恢复从哪里来。这三问也适用于后面每一篇文章页面。
