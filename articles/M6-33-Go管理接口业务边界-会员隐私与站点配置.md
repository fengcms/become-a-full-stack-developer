# 成为全栈·Go 后端篇·管理接口也有业务边界：用户、公开资料与站点配置

> 管理 API 不只是把数据库记录返回给高权限用户。角色变更可能锁死整个后台，公开会员资料可能泄露隐私，站点设置也要限定为允许编辑的字段。

## 前言：admin 权限不是跳过所有规则的通行证

后台接口我一直觉得是最省事的部分：只有 admin 能调，权限过了就让它写。直到我意识到，管理员可以把最后一个 active admin 停掉。那一下点下去，整个后台就没人进得去了。

用户管理接口通常只能由 admin 调用，但它仍有业务约束：不能让管理员把自己降级或禁用；不能移除最后一个 active admin，否则系统将无人管理。用户表里有 password_hash、微信身份相关关联和内部状态，响应必须使用安全 projection。公开会员页又需要展示作者昵称、头像、等级和公开文章，不应返回邮箱、用户名或角色。

站点设置看起来像单例 CRUD，但允许字段必须白名单化，并与公开配置接口的响应 envelope 保持契约一致。M6 将这些能力放在 administration 包，并复用 auth.Public 和 article 查询规则。

本文从管理列表、用户修改、公开会员和站点配置说明“管理能力仍有业务边界”。

## 一、管理用户列表与安全投影

Users 支持 role、status 精确筛选和 username/display_name/email 关键词查询，按 created_at、ID 稳定倒序分页。结果通过 auth.Public 映射，而不是把 GORM User 行直接 JSON 序列化。公开响应不包含密码哈希；用户详情也使用同一投影边界。

auth.Public 本身对应登录用户资料和管理视角，含 id、username、nickname、avatar、role、status、level、createdAt、canSetCredentials，email 仅在非空时输出。哪些字段允许特定 API 返回由契约定义；不同 endpoint 可以采用不同投影，不能因为一个“公共 User DTO”方便，就让公开会员页继承管理字段。

`auth.Public` 是一段显式代码，不是靠结构体标签省略字段：

```go
type Public struct {
	ID                int64     `json:"id"`
	Username          string    `json:"username"`
	Nickname          string    `json:"nickname"`
	Avatar            string    `json:"avatar"`
	Role              string    `json:"role"`
	Status            string    `json:"status"`
	Level             int       `json:"level"`
	CreatedAt         time.Time `json:"createdAt"`
	CanSetCredentials bool      `json:"canSetCredentials"`
	Email             string    `json:"email,omitempty"`
}

func PublicFrom(u model.User) Public {
	return Public{
		ID:                u.ID,
		Username:          u.Username,
		Nickname:          u.Nickname,
		Avatar:            u.Avatar,
		Role:              u.Role,
		Status:            u.Status,
		Level:             u.Level,
		CreatedAt:         u.CreatedAt,
		CanSetCredentials: u.PasswordHash == "",
		Email:             u.Email,
	}
}
```

`model.User` 上多一列，不会自动出现在响应里；要让新字段对外可见，必须同时改这个结构体和冻结契约。方向是刻意选的：字段遗漏在联调时立刻暴露，字段泄露往往要等有人翻响应才被注意到。

关键词 SQL 的筛选字段名在服务端写死，用户输入只作为参数值；不让 query string 提供任意列名或 SQL 片段。分页默认和上限由 values.Paging 规范化，统计与列表使用相同筛选。

## 二、保护自己和最后一个 active admin

UpdateUser 在一个事务中先锁定当前 active admin 集合，再锁定目标用户，判断是否为权限字段修改。操作者不能修改自己的 role/status；若目标用户是最后一个活跃 admin，也不能将其降级或设 disabled。通过锁定管理员集合，再执行检查和更新，减少两个并发请求同时移除不同管理员导致最后一个也被移除的竞态。

更新字段通过 map 白名单仅接收 role、status、level。displayName、passwordHash、createdAt 等不在这个管理 patch 里就不能被用户管理 endpoint 顺手改掉。密码重置有单独认证服务动作，更新凭据并撤销该用户刷新会话；角色和状态更新也不能绕过其事务和权限边界。

这里的三步顺序不能换：

```go
func (s *Service) UpdateUser(ctx context.Context, operatorID, targetID int64, patch map[string]any) error {
	return s.db.WithContext(ctx).Transaction(func(tx *gorm.DB) error {
		var activeAdmins []int64
		if err := tx.Model(&model.User{}).
			Clauses(clause.Locking{Strength: "UPDATE"}).
			Where("role = ? AND status = ?", model.RoleAdmin, model.StatusActive).
			Pluck("id", &activeAdmins).Error; err != nil {
			return err
		}

		var target model.User
		if err := tx.Clauses(clause.Locking{Strength: "UPDATE"}).
			First(&target, targetID).Error; err != nil {
			return err
		}

		if targetID == operatorID {
			if _, ok := patch["role"]; ok {
				return ErrSelfRoleChange
			}
			if _, ok := patch["status"]; ok {
				return ErrSelfStatusChange
			}
		}

		if len(activeAdmins) == 1 && activeAdmins[0] == targetID {
			if _, ok := patch["role"]; ok {
				return ErrLastAdmin
			}
			if st, ok := patch["status"]; ok && st != model.StatusActive {
				return ErrLastAdmin
			}
		}

		return tx.Model(&model.User{}).Where("id = ?", targetID).Updates(patch).Error
	})
}
```

先取活跃管理员集合、再锁目标用户，是为了让两个并发的降级请求排在同一把锁后面：第一个提交后集合已经变小，第二个读到的新集合才是判断依据。反过来先锁目标再数管理员，两边可能各自数到"还有两个管理员"，然后各降一个。

`patch` 用 `map[string]any` 而不是结构体，也是同一类考虑：结构体会把零值一起带进来，`status: ""` 和"没传 status"在 map 里是两个不同的键，在结构体里可能塌成同一个空字符串。

这段代码在三种数据库上并不等价。SQLite 没有 `FOR UPDATE`，锁 clause 在那里不生效，能依靠的是单写事务本身；这也是为什么最后管理员保护的并发用例必须在目标数据库上真跑一遍。

“最后管理员保护”是高风险规则，需要真实数据库并发测试；PostgreSQL/MySQL 行锁语义与 SQLite 单写限制不同。若部署多个写实例，锁语义依赖数据库而非应用进程，测试矩阵需覆盖目标方言。

## 三、公开会员资料最小化

Member 按 id 和 active 状态查询账号，再复用文章服务查询该会员已发布文章。响应只包括 id、昵称、头像、level、文章数量和文章摘要列表。它没有返回 username、email、role、status、passwordHash 或微信 openid。

用户被禁用时公开主页按不存在处理；文章列表只包含 published 且未软删除内容。复用 article.Page 保证排序、分类/标签、软删除及摘要投影遵循同一规则，避免会员页另写一套私稿可见性判断。

文章数量不是另算一次 `count(*)`，而是和列表走同一套筛选：只统计 published 且未软删除的记录。两处口径一旦分开，页面上就会出现"显示 12 篇、点进去 11 篇"这种没人说得清的差异。

这里的“公开”是业务展示范围，不代表任意用户数据都公开。新增会员 profile 字段前，先分类其是否可公开、是否属于账号隐私，再更新特定 DTO 和契约，而不是直接在 auth.Public 添加字段后自动扩散到页面。

## 四、站点配置是单例白名单

SiteSetting 以 id=1 作为单例，读取和更新都围绕该行。允许修改 siteName、siteTitle、siteDescription、siteKeywords、logoUrl、copyright 等契约字段，输入映射到固定数据库列；更新时间由服务器写入，客户端不能修改内部 ID、createdAt 或 updatedAt。

更新只处理请求中存在的字段，因此空值更新语义需要符合契约。若没有字段则读取当前设置。响应显式构造字段，不把 ORM 行当响应。后台管理设置 endpoint 和公开读取 endpoint 的 envelope 处理有历史 schema 差异，Go 保持客户端已经使用的信封并使用共享 schema checker/测试检查其 data payload；生产响应路径并未自动执行每个 response schema 校验，不能将测试能力说成线上拦截器。

允许修改的字段用一张显式的表映射，而不是反射结构体：

```go
var siteSettingColumns = map[string]string{
	"siteName":        "site_name",
	"siteTitle":       "site_title",
	"siteDescription": "site_description",
	"siteKeywords":    "site_keywords",
	"logoUrl":         "logo_url",
	"copyright":       "copyright",
}

func settingPatch(input map[string]any) (map[string]any, error) {
	if len(input) == 0 {
		return nil, nil
	}
	out := make(map[string]any, len(input))
	for field, value := range input {
		col, ok := siteSettingColumns[field]
		if !ok {
			return nil, ErrUnknownSettingField
		}
		out[col] = value
	}
	return out, nil
}
```

新增一个可编辑的站点字段，要同时改契约、这张映射表和响应构造，三处缺一处都不会"碰巧生效"。未知字段直接报错而不是忽略：忽略会让调用方以为保存成功，等页面上没变化再来排查，成本高得多。

站点配置虽然是全局数据，也应有权限、审计与缓存失效边界。缓存是否在 60 秒后更新属于客户端/服务层策略，更新数据库成功不代表每个客户端缓存立即同步。

## 五、Admin API 仍按契约最小化授权

传输层先依据 OpenAPI operation 元数据确认 admin 角色，管理 service 接收 operator ID 做业务层最后管理员/自我保护判断。服务内部需要这些约束，即使未来被命令行或测试直接调用也不应该默认没有安全规则。

管理端 403、目标用户不存在和字段校验错误要按契约映射。前端隐藏危险按钮只能提升体验，不能代替后端角色限制。审计日志可以记录操作者、目标 ID、字段名与结果，但不应记录密码或刷新 token。

目标用户不存在返回 404、权限不足返回 403，这两个码不能合并成 400。客户端靠它们区分"换个 ID 再试"和"去找管理员要权限"，合并之后这两种情况在前端只能靠猜。

## 六、关键验证用例

- 管理员可筛选用户，但结果绝不包含 password_hash；
- 普通 member/editor 无法访问管理员用户管理 operation；
- admin 修改自己 role/status 被拒绝；
- 最后一个 active admin 无法降级或禁用；
- 两个管理员并发变更时，数据库仍至少保留一个 active admin；
- 管理员重置密码会撤销目标用户刷新会话；
- public member 不返回邮箱、用户名、角色和微信身份；
- disabled member、私稿和软删除文章不出现在公开资料；
- site setting 更新仅接受 allowlist，未知字段不能映射到列；
- 站点更新失败时旧设置保持，响应 envelope 与客户端约定一致。

测试检查数据库后置状态与具体 DTO 字段。只检验管理请求返回 200，无法证明没有泄露或没有把最后一个管理员锁掉。

## 小结：高权限接口更需要显式约束和投影

M6 administration 包负责用户管理、公开会员和站点设置。后台用户使用安全投影；角色/状态更新禁止自我权限修改并保护最后一个 active admin；公开主页返回最小资料和已发布文章；单例站点设置只映射允许字段。

在管理端设计中，高权限只说明操作者有资格进入操作，不等于所有写入都合法。逐项检查最小权限、目标状态、字段白名单、数据可见范围和事务后置条件，能让后台保持可控。
