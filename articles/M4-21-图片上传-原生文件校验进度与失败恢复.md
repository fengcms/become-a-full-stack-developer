# 成为全栈·Flutter App 篇·图片上传：原生文件、校验、进度与失败恢复

图片已经选中了，却还没上传；上传成功了，文章保存又失败；或者系统在相册选择期间回收了进程。移动端上传不是一个按钮和一个 URL，而是一串可能在不同时间失败的步骤。

这篇跟着 `ImagePicker`、`XFile` 和 `uploadImage()` 的真实路径，说明当前 APP 支持什么、进度表示什么，以及正文如何在失败后保持完整。

## 从设备文件到 API 请求

移动图片由系统选择器交给 APP 的 `XFile`。当前实现使用 `ImagePicker` 从相册选择；相机入口和通用文件选择器不是已交付功能。客户端要读取文件元数据，检查允许类型和大小，再形成 multipart 请求。不能只看文件扩展名；服务器仍需校验 MIME、内容和权限，客户端检查只是体验层。

```text
XFile → size/type checks → upload request → server attachment URL
```

测试中通过真实原生 XFile 验证了本地隔离后端的上传和下载；系统相册权限与设备厂商行为仍需发布前真机测试，相机权限目前没有作为功能范围。

## 上传进度不等于稿件已保存

文件成功上传后，正文或封面还要引用返回的 URL，文章保存请求再将引用写入稿件。若上传成功但保存失败，附件可能已存在但编辑内容仍留在页面；重试应继续复用已上传 URL，而不是重新创建整篇投稿。

## 错误恢复要保留输入

网络失败时显示进度终止和重试入口，正文与元信息保持不变。不同类型错误应可区分：文件超限让用户换图；无权限/选择取消不是服务端故障；网络超时允许重试。正在上传时禁用重复提交，避免并发产生重复附件。

## 私有图片不能混进公开缓存

草稿图片、私有预览图片和签名 URL 可能具有身份或时效属性，不能无条件落公共磁盘缓存。图片缓存策略对带查询参数或私有图片采取保守处理，避免签名泄露和跨账号复用。

## 上传状态需要跟文件项绑定

一篇正文可能上传多张图片。用单一 `isUploading` 布尔值会无法表达哪张失败、哪张成功；每个待上传文件至少需要稳定本地 ID、阶段、进度、错误和服务端 URL。

```text
selected → validating → uploading(progress)
                         ├─ success(url)
                         └─ failed(error) → retry same item
```

上传重试尽量复用同一文件项并避免重复创建稿件。进度百分比只代表字节传输，不代表服务端已完成处理或稿件已保存；界面文案要区分这几步。用户删除失败项时不能误删已经插入正文的其它图片链接。

## 原生选择器返回后校验页面生命周期

调用 `ImagePicker().pickImage` 会跨越平台异步流程；Android 进程可能在外部选择器期间被系统回收。项目启动编辑器时还调用 `retrieveLostData()` 尝试取回丢失的选择结果。拿到 XFile 后应确认页面仍 mounted、稿件身份未改变，再启动上传；关闭编辑页后的迟到上传回调不能修改另一个稿件的状态。

错误提示也应分开：用户主动取消不显示“上传失败”；平台返回空文件时提示重新选择；格式/大小拒绝应指出原因；传输失败提供重试。权限弹窗和设备相册表现还没有真机全面验收，不能仅凭 fake XFile 测试声称跨厂商完备。

## Multipart 上传要让数据来源和目的明确

上传层接收 API client 与 XFile，进度回调只更新当前上传任务。Dio 对上传路径使用统一 API 配置，但文件下载图片的 ImageStore 会显式移除 Authorization header，避免把 API 凭据发送到图片域名。传输 URL 和 API base URL 也应分开处理，尤其是后端返回相对附件路径时由同一环境解析。

验收除了检查按钮进度，还要验证返回的附件 URL 能从隔离后端读取，拒绝非法文件，并检查上传中退出编辑页不会触发并发二次上传。生产写入未在真实线上做测试，避免污染会员稿件。


## 贴着工程代码读实现

下面这段节选自 `flutter-app/lib/core/storage/upload.dart 第 7–40 行`（保留原始实现；为突出主线省略了文件其余部分）。读代码时可以顺着调用链确认：使用错误扩展名、超出上限文件以及网络中断分别验证。把这几步连起来，才看得到数据如何从服务边界走到界面。

```dart
Future<String> uploadImage(
  ApiClient api,
  XFile file, {
  void Function(int, int)? onProgress,
}) async {
  final ext = file.name.split('.').last.toLowerCase();
  const types = {
    'png': 'image/png',
    'jpg': 'image/jpeg',
    'jpeg': 'image/jpeg',
    'webp': 'image/webp',
    'gif': 'image/gif',
  };
  if (!types.containsKey(ext)) {
    throw const ApiFailure('请选择 PNG、JPG、GIF 或 WebP 图片');
  }
  if (await file.length() > 10 * 1024 * 1024) {
    throw const ApiFailure('图片不能超过 10MB');
  }
  final form = FormData.fromMap({
    'file': await MultipartFile.fromFile(
      file.path,
      filename: file.name,
      contentType: DioMediaType.parse(types[ext]!),
    ),
  });
  final result = await api.request(
    Endpoints.upload,
    method: 'POST',
    data: form,
    onSendProgress: onProgress,
  );
  return api.fileUrl(result['url'] as String);
}
```



上传控件还负责把进度映射到界面，并在失败时保留同一个 XFile 供重试。下面节选自 `flutter-app/lib/features/editor.dart` 第 214–251 行：

```dart
  Future<void> upload(XFile file, bool isCover) async {
    setState(() {
      busy = true;
      progress = 0;
      failedUpload = null;
    });
    try {
      final url = await uploadImage(
        ref.read(sessionProvider).api,
        file,
        onProgress: (n, total) {
          if (mounted) setState(() => progress = total == 0 ? null : n / total);
        },
      );
      if (!mounted) return;
      if (isCover) {
        setState(() => cover = url);
        changed();
      } else {
        insert('\n![图片]($url)\n', '');
      }
    } catch (e) {
      if (mounted) {
        setState(() {
          failedUpload = file;
          failedCover = isCover;
        });
        notice(context, e);
      }
    } finally {
      if (mounted) {
        setState(() {
          busy = false;
          progress = null;
        });
      }
    }
  }
```

## 把容易出错的路径走一遍

我会用这个场景做一次可复现排查：**不支持格式或超大图片上传到一半才失败**。先使用错误扩展名、超出上限文件以及网络中断分别验证；如果把问题定位在“先发请求后校验”，修正方向是“上传前先校验类型和大小，再传进度回调与可重试状态”。最后再验证正常路径没有退化，并把边界条件留在自动化检查里。

| 方案比较 | 简化做法 | 当前实现/推荐做法 |
|---|---|---|
| 本文核心选择 | 先发请求后校验 | 本地预检后上传 |
| 错误处理 | 失败后清空或静默忽略 | 保留可恢复状态，给出明确反馈 |
| 验证方式 | 只检查成功结果 | 注入边界条件并检查回归 |

| 排错步骤 | 要观察什么 | 通过条件 |
|---|---|---|
| 复现 | 不支持格式或超大图片上传到一半才失败 | 可以稳定触发或明确构造该输入 |
| 定位 | 使用错误扩展名、超出上限文件以及网络中断分别验证 | 找到责任层和状态归属 |
| 修正 | 上传前先校验类型和大小，再传进度回调与可重试状态 | 失败不污染后续页面或账号 |

## 小结

图片上传包含原生文件校验、传输状态、附件返回和稿件引用多个步骤。上传成功不代表稿件保存完成；重试策略应避免重复创建内容，失败时保留编辑状态，私有/签名图片则遵守严格缓存边界。
