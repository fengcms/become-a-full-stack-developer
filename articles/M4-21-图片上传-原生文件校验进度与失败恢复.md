# 成为全栈·Flutter App 篇·图片上传：原生文件、校验、进度与失败恢复

图片上传是编辑器里最简单的一个按钮，也是最容易出问题的一个。

我的第一版是这样的：

```dart
// 这是我最初的做法
final file = await ImagePicker().pickImage(source: ImageSource.gallery);
final url = await uploadImage(api, file);
insert('\n![图片]($url)\n', '');
```

四行，逻辑清晰。测试的时候完全正常。

然后真机测试时出了三个问题，每一个都不是"代码写错了"：

1. **上传失败，正文里什么都没留下，用户不知道发生了什么。**
2. **选了 15MB 的图，客户端传完 14MB 才被拒。**
3. **Android 上从"最近任务"切回来，正在选的那张图丢了。**

第三个问题最费解，因为它压根不在我的代码里。

## 校验必须在发请求之前

先说第二个问题，因为它最容易改。

第一版没有任何本地校验，靠服务端拒绝。然后用户看到的是"上传失败"，他不知道是格式不对还是太大。

现在的做法是在发请求之前全部拦掉：

```dart
Future<String> uploadImage(
  ApiClient api,
  XFile file, {
  void Function(int, int)? onProgress,
}) async {
  final ext = file.name.split('.').last.toLowerCase();
  const types = {
    'png': 'image/png',
    'jpg': 'image/jpeg',
    'jpeg': 'image/jpeg',
    'webp': 'image/webp',
    'gif': 'image/gif',
  };
  if (!types.containsKey(ext)) {
    throw const ApiFailure('请选择 PNG、JPG、GIF 或 WebP 图片');
  }
  if (await file.length() > 10 * 1024 * 1024) {
    throw const ApiFailure('图片不能超过 10MB');
  }
  ...
```

四个点：

**一、`toLowerCase()`。** `.PNG` 和 `.png` 是同一个文件，用户不该因为大小写被拒。这条看起来是细节，但它挡掉了一类"明明能显示却传不上去"的问题。

**二、MIME type 从扩展名推断，不用客户端给的头。** `DioMediaType.parse(types[ext]!)` 的来源是这张白名单表，不是文件内容。

为什么不信？**因为客户端能给的任何东西都可能是错的**——文件名可以改，Content-Type 可以乱填。这和 M1 里"不信客户端传来的 role"是同一条原则：**客户端提供的元数据只能用作提示，不能作为事实。**

**三、大小检查用 `file.length()` 而不是 `file.size`。** `XFile` 提供了两个看起来都像"大小"的东西，但 `length()` 是 Future，能可靠地读到实际字节数。这不是风格问题——在某些平台上 `size` 可能返回 0。

**四、抛的是 `ApiFailure`，不是别的异常类型。**

这个选择很值。`ApiFailure` 是 M4-08 定的统一错误类型，带 `code` / `status` / `fields`。因为本地校验的错误走的是同一套展示路径，所以**用户看到的是一个普通的错误提示，而不是一个"程序出错"的红屏。**

而且 `ApiFailure.toString()` 返回 `message`，所以它可以被直接塞进 `notice()`：

```dart
catch (e) {
  if (mounted) notice(context, e);
}
```

**整个上传流程只有这一个错误出口。** 服务端返回的错误、客户端校验的错误、超时、网络不可用——全部收敛到这一行。

## 进度回调：两个细节

进度条的实现很简单：

```dart
onProgress: (n, total) {
  if (mounted) setState(() => progress = total == 0 ? null : n / total);
},
```

注意那个 `total == 0 ? null : n / total`：

- `total` 已知 → 给出**确定进度条**（能显示 45%）
- `total` 未知 → 传 `null` → **不确定进度条**（那个来回滑动的条）

为什么要分两种？因为 Dio 在某些情况下拿不到 `content-length`（比如分块传输）。这时候如果硬算 `n / 0` 会得到 `NaN`，而 `LinearProgressIndicator` 传 `NaN` 会抛异常。

```dart
if (progress != null) LinearProgressIndicator(value: progress),
```

而 `progress` 是可空类型，所以 `null` 和 `0.0` 必须区分开：

| 值 | 含义 | 显示 |
|---|---|---|
| `null` | 上传中但不知道总量 | 不确定动画 |
| `0.0` | 刚开始 | 确定，0% |
| `0.45` | 进行中 | 确定，45% |

**如果把 `null` 和 `0.0` 混为一谈，用户会看到进度条"闪一下然后变成动画"，像是出了错。**

顺带说 `if (mounted)` 这个检查。它在上传回调里出现很多次，因为**上传是个长时间的异步过程，页面随时可能被销毁**。如果没有这个检查，`setState` 会在已销毁的 State 上调用，直接抛异常。

## 失败恢复：把"待重试的东西"存起来

现在说第一个问题——上传失败后用户不知道发生了什么。

第一版的 catch 块只有一行提示。用户看到"上传失败"，然后发现正文里什么都没多，就结束了。**他不知道刚才那张图去哪了，也不知道能不能重来。**

现在的做法是**把失败的文件记住**：

```dart
} catch (e) {
  if (mounted) {
    setState(() {
      failedUpload = file;      // ← 记住是哪个文件
      failedCover = isCover;    // ← 记住是封面还是正文
    });
    notice(context, e);
  }
}
```

注意 `isCover` 也要记住——因为封面上传和正文上传的**成功后行为不一样**：封面是替换 `cover` 字段，正文是往光标位置插入 Markdown。

而这个记住的东西会被渲染成一条提示：

```dart
if (uploadFailed)
  ListTile(
    title: const Text('图片上传失败，正文已保留'),
    trailing: TextButton(
      onPressed: busy ? null : retryUpload,
      child: const Text('重试'),
    ),
  ),
```

重试回调是：

```dart
retryUpload: () => upload(failedUpload!, failedCover),
```

**重试不是"重新让用户选一次文件"，而是直接用之前那个文件。** 因为 `XFile` 持有的是文件路径，那个文件还在（用户没删它的话）。

这个设计有一个前提：**`XFile` 在页面存活期间是有效的。** 如果用户在失败后重启了 App、或者系统清理了缓存目录，这个路径就失效了，重试会失败。

现在的处理是**如实报错**——用户会看到"文件不存在"之类的错误。更好的做法是检测路径是否存在并提示"请重新选择图片"。**这是一个我知道的不足。**

而"正文已保留"这四个字值得单独说。因为上传失败时，用户最担心的是"我写的东西没了"。明确告诉他正文还在，他的反应就从"放弃"变成"重试一下"。

**这个信息成本极低（一句话），但它决定了用户会不会白写四十分钟。**

## Android 的 retrieveLostData：那个查了一小时的问题

现在说第三个问题，也是唯一一个"不在我代码里"的。

现象：Android 上，从文章页点进编辑器，选一张图，**在系统相册界面停留一会儿（比如超过 30 秒），然后直接返回编辑器**——图片没了，也没有任何提示。

如果是点得太快就没问题。

这个行为的根源在 Android 本身：**当 App 进程被系统回收后重新进入，系统会通过 `onActivityResult` 恢复那次请求的结果。** Flutter 为此提供了 `retrieveLostData()`。

代码在这里：

```dart
final lost = await ImagePicker().retrieveLostData();
```

它的作用是：**每次进编辑器时，先问系统"上次有没有未完成的图片选择"。**

这里有个必须做对的细节——**如果查到有 lost data，要清理掉它**：

```dart
if (lost.isEmpty) { ... }
// 处理完之后必须再次调用并清空，否则下次进来还会拿到同一份
```

Flutter 的文档里明确说了这个约定：**处理完之后必须再次调用 `retrieveLostData()` 来清空队列**，否则它会被反复返回。

我第一版漏了这句清理。结果是：用户第一次进来恢复了图片，第二次进来**又出现"是否恢复"提示**，即使他什么都没选。

**这类 bug 的恶劣之处在于它"看起来像功能"**——多弹一次框，很多用户不会当成 bug，只会当成干扰。

而这个处理必须在 `initState` 里做（或者在恢复稿件之后），因为它可能影响用户看到的内容。

顺带说 iOS：iOS 没有这个问题。`pickImage` 的结果通过正常的回调返回，App 被回收时那次选择就真的丢了，不需要恢复。

**同一个 API 在两个平台上有完全不同的语义**，这是原生桥接的常态。而这种差异只能靠文档和真机测试发现——**模拟器上几乎测不出来，因为模拟器不会频繁回收进程。**

## FormData 的一次性消费

还有一个和上传相关的坑，不在这个文件里，在 M4-09 提过的重试逻辑里：

```dart
data: data is FormData ? data.clone() : data,
```

**`FormData` 被消费一次之后就不能重用。** Dio 读它来构造 multipart 请求，读完之后它的内部流已经耗尽。

所以在重试场景里，如果直接复用同一个 `FormData` 对象，第二次请求会发出一个空的或者损坏的请求体。

而 M4-09 那个"刷新后重放请求"的场景正好会用到 `FormData`（文件上传是 POST + multipart）。

`clone()` 生成一个可重读的副本。这行代码看起来多余——**除非你真的遇到了"重试时请求体是空的"这个现象**。我是这么遇到的。

## 封面和正文：两条不同的路径

前面提过，这里把差异说完整：

```dart
if (isCover) {
  setState(() => cover = url);
  changed();                        // ← 标记内容已修改
} else {
  insert('\n![图片]($url)\n', '');  // ← 插入 Markdown
}
```

**封面走 `changed()`，正文走 `insert()`。**

`insert()` 是什么？它是 M4-20 那个 `wrapSelection(content, before, after)`——**它会修改正文内容，从而自动标记 dirty**。而封面不在正文里，`cover` 是一个独立的字段，所以要手动调 `changed()`。

如果忘了调，**用户换了封面，然后退出，弹窗不出现，那次修改丢了**。

这个 bug 的隐蔽之处在于：正文编辑后退出一定会弹窗（因为正文变了），而只改封面时忘了标记——用户会觉得"有时候弹有时候不弹"，很难关联到具体原因。

**`changed()` 这行只有七个字符，但它是一个数据丢失的开关。**

## 验收该测什么

上传的测试要能覆盖这些：

| 场景 | 该验证 |
|---|---|
| 正常上传 | URL 被插入正文，dirty 被标记 |
| 封面上传 | 走 `cover` 分支，`changed()` 被调用 |
| 非白名单格式 | 在发请求前被拒 |
| 超大文件 | 在发请求前被拒 |
| `total` 为 0 | 进度条不崩，用不确定模式 |
| 上传失败 | 记住文件，提示可重试 |
| 重试 | 复用同一个 `XFile` |
| Android lost data | 进页面时恢复，且恢复后清空队列 |

第二和第四条值得说：**"在发请求前被拒"这条断言要求测试能验证"没有发请求"**，而不只是"抛了异常"。做法是注入一个会记录调用的假 ApiClient，断言调用次数为 0。

而 Android 那条**只能真机测**。模拟器上 `retrieveLostData` 永远返回空。

## 一条我一开始想省掉的事

`failedUpload` 这个状态的整个机制，我最初觉得是过度设计——"失败了让用户重新选一次不就行了？"

改主意是因为想到一个具体场景：**用户选了一张 8MB 的图，网络很慢，上传到 90% 断了。**

如果让他重新选：他得回到相册、重新找到那张图、重新选。而那张图可能是他刚拍的，找起来很麻烦。**更糟的是他会想"刚才白传了 90%"，对 App 的信任直接下降。**

所以现在的重试是"**继续用同一个文件重新开始**"（不是断点续传——那需要服务端支持）。用户要做的只是点一下"重试"。

顺带说，重试**不自动进行**。我可以做成"3 秒后自动重试"，但那会造成一个问题：**网络断了的时候，App 会一直重试，用户看到的界面在反复闪。**

现在改成手动，是因为**上传失败是一个用户能理解和处置的状态**——他知道自己网不好，可以换个时间。而自动重试剥夺了他这个判断权，还会占着 `busy` 状态让他什么都做不了。

这和 M4-08 那个"429 超过 3 秒就交给用户决定"是同一个原则：**自动化的持续时间必须短到用户还愿意等，超了就该把决定权还给人。**

## 小结

图片上传本身只有四十行代码，但它把几个跨端问题集中在一起：

| 问题 | 跨端原因 |
|---|---|
| 大小校验 | 要读实际字节，不能信元数据 |
| lost data | Android 特有，iOS 没有 |
| FormData 重用 | Dio 的一次性消费 |
| 进度回调 | 部分场景拿不到 total |

处理这四件事的共同原则是：**把不确定的判断留在客户端，把可信的判断交给服务端，而把"出了什么问题"如实告诉用户。**

最后一条尤其重要。上传失败时的提示不只是"出错了"，它要包含三件事：**发生了什么、什么没丢、下一步能做什么**。

对应到代码上就是那句"图片上传失败，正文已保留"加上一个"重试"按钮——**它同时回答了第二个和第三个问题。**
