# 成为全栈·React 管理后台篇·文章管理工作流：保存修改、投稿、发布与下架

> 后端状态机落到界面上，不能只剩一个 status 下拉框。按钮的名称、出现条件和提交参数，都应该准确表达一次业务动作。

## 前言

文章编辑页曾经有一个看似合理的按钮：“保存草稿”。新文章点击它确实保存为 draft，可编辑一篇已经发布的文章时，它也会把 status 固定传成 draft。编辑者本来只想改一个错别字，保存后文章却从网站下线了。

接口没有报错，表单也保存成功，问题出在界面把“保存内容”和“改变发布状态”混成了一个动作。后端状态机设计得再严谨，前端若只提供一个任意状态下拉框，同样会把业务语义重新打散。

## 本文要解决什么

- 保存修改为什么应该保留文章原状态。
- 发布和下架为什么必须成为显式动作。
- 新建文章第一次保存后怎样切换为编辑会话。
- 状态、权限、校验与按钮文案如何保持一致。

前置阅读：[文章 CRUD 与投稿状态机](https://blog.csdn.net/fungleo/article/details/164453121)、[表单页范式：校验、数据回填与未保存保护]({{LINK:M2-09}})

## 先把机器状态翻译成用户动作

当前文章存在 draft、pending、published 三种状态。界面真正要呈现的不是三个英文值，而是用户在当前状态下可以完成什么：

| 当前状态 | 普通保存 | 独立动作 | 结果 |
| --- | --- | --- | --- |
| 新文章 | 保存草稿 | 发布文章 | draft 或 published |
| draft | 保存草稿 | 发布文章 | 保持 draft 或进入 published |
| pending | 保存修改 | 发布文章 | 保持 pending 或进入 published |
| published | 保存修改 | 下架 | 保持 published 或回到 draft |

这里最关键的规则是：**保存内容默认不改变状态**。状态迁移必须由名称清楚的独立动作触发。

## 保存时保留当前状态

编辑 hook 不再把所有普通保存都写死为 draft：

```ts
const status: ArticleStatus = publish
  ? 'published'
  : (saved?.status ?? 'draft')

const payload = articlePayload(values, status, saved?.slug)
```

新文章没有 saved，普通保存回落为 draft；已有文章则沿用服务端基线中的状态。只有调用 `submit(true)` 时才明确进入 published。

为什么基于 saved，而不是表单里的 status？因为普通编辑者不应该通过一个隐蔽字段任意改变状态。saved 是上一次由服务器确认的文章，表单只负责内容和设置；状态动作由工作流按钮负责。

发布还有额外前置条件。例如草稿可以暂时没有分类，正式发布必须选择分类：

```ts
if (publish && !values.categoryId) {
  form.setError('categoryId', { message: '发布前请选择分类' })
  setActiveTab('settings')
  return
}
```

这条校验属于“发布”动作，不应该粗暴地让所有草稿保存都失败。

## 按钮文案跟着当前状态变化

页面底部没有永远不变的“提交”按钮，而是直接说明结果：

```tsx
<Button onClick={editor.save} disabled={locked || (!dirty && !!article)}>
  {article?.status === 'published' || article?.status === 'pending'
    ? '保存修改'
    : '保存草稿'}
</Button>

{article?.status !== 'published' && (
  <Button onClick={editor.publish} disabled={locked}>
    发布文章
  </Button>
)}
```

用户看到“保存修改”，可以合理预期文章仍然保持原状态；看到“发布文章”，才知道内容将对外可见。按钮文案本身就是状态机文档。

按钮禁用也要说明原因。没有修改时不允许重复保存；上传和保存过程中统一 locked；已发布文章存在未保存修改时，下架按钮先禁用，并提示“请先保存修改”。这样可以避免“下架成功后又用旧表单覆盖状态”的竞态。

## 下架是高影响动作，需要确认和更高权限

当前实现把任意状态强改留给 admin。已发布文章的下架按钮只在 `canForceArticleStatus(user)` 成立时出现，并用确认框明确后果：文章不再公开展示，内容保留为草稿。

```tsx
{article?.status === 'published' && canForceArticleStatus(user) && (
  <Button onClick={() => setUnpublish(true)} disabled={locked || dirty}>
    下架
  </Button>
)}
```

确认后调用独立的状态接口，而不是再次提交整份文章表单。成功响应交给 `acceptSaved`，页面基线和状态标签一起更新。

编辑通过审核与 admin 强改状态也不是同一能力。editor 可以执行 pending → published 的审核动作；任意状态切换则只开放给 admin。前端把它们混成一个下拉框，会掩盖权限和审计语义。

## 新建成功以后不能继续停在 `/new`

新文章保存成功后，服务器才分配 id。页面必须立即从创建会话转成编辑会话：

```ts
if (!isEdit) {
  allowNavigation.current = true
  navigate(`/articles/${article.id}/edit`, {
    replace: true,
    state: { from: returnTo },
  })
}
```

否则第二次保存仍可能调用创建接口，产生重复文章。使用 replace 还能避免浏览器返回到一个已经完成的新建页面。

成功响应必须重建表单基线并保存服务器返回的状态。失败时保持输入，让用户修改后重试；不能为了“恢复干净界面”把整张表单清空。

## 列表页也要说动作，而不是说状态值

待审核文章的行操作叫“通过审核并发布”，而不是“改为 published”；删除需要确认；批量操作只选出当前页状态为 pending 的 id。界面始终围绕用户意图组织。

如果未来增加投稿动作，作者端应出现“提交审核”，而编辑端出现“通过审核”或“退回修改”。即便最终都修改 status，角色、前置条件和通知副作用也不同，不能复用一个无语义的状态选择器。

## 页面状态必须以服务端成功响应为准

点击发布后，前端不能立刻把本地文章改成 published，再假设请求一定成功。后端还会校验分类、权限、当前状态和内容字段，任何一项失败都应让表单继续停留在原状态。

当前流程等待 mutation 返回完整 Article，再统一交给 `acceptSaved`。这一步同时更新 saved、表单基线、保存时间和新建文章地址。状态标签、按钮组合与 dirty 判断因此来自同一个服务端结果。

如果分别执行 `setStatus('published')`、`reset(values)`、`toast.success()`，中间任意一步遗漏都会产生短暂矛盾：界面说已发布，列表仍是草稿；或者发布失败后保存按钮已经变成“保存修改”。集中接收成功结果，能让一次业务提交成为原子的界面转换。

写操作成功后还会失效 `['articles']` 和 `['site']`。前者更新列表与详情，后者更新仪表盘统计。工作流不只存在于编辑页，所有观察这篇文章的视图都应重新确认。

## “投稿”为什么没有硬塞进当前按钮

路线图标题包含投稿，但当前管理后台的主壳只允许 editor/admin 进入；普通 member 会被 `RequireConsole` 拦在外面。已有后台页面因此主要承担编辑与管理动作，没有伪造一个当前入口无法自然完成的会员投稿流程。

后端状态机仍然保留 pending，列表也能筛选并审核待投稿文章。未来读者端或独立作者工作台接入后，member 的“提交审核”应该在那里实现，再由管理后台承接审核。把所有角色都塞进同一个后台壳，反而会产生大量只能看到 403 的菜单。

这也是写技术文章必须说明的现实边界：契约拥有一种状态，不代表当前端已经覆盖产生它的全部入口。前端应忠实消费自己负责的那一段工作流。

## 删除不是另一种状态

删除文章采用软删除，但对用户而言仍是高影响动作，需要独立确认。它不能伪装成 status 的第四个选项：删除会影响默认列表可见性、关联内容和恢复策略，语义与下架不同。

下架保留文章作为可继续编辑的 draft；删除则让它退出正常管理视图。即使数据库最终只是更新字段，界面也应根据业务后果区分动作。这条原则同样适用于“禁用用户”和“修改用户角色”：存储形式相似，用户意图完全不同。

## 前端不能自行发明状态迁移

前端的按钮映射必须来自后端契约和状态机。隐藏非法按钮能减少误操作，但用户仍可绕过页面直接请求 API，所以后端必须再次验证当前状态、操作者权限和目标状态。

反过来，后端若新增 archived 状态，前端也不能仅给下拉框多加一项。需要先回答它从哪些状态进入、谁能操作、是否可恢复、列表和公开端怎样变化，再设计相应动作。

## 小结

文章工作流的核心，是让普通保存保留原状态，让发布、审核和下架成为显式动作。按钮名称、出现条件、确认文案、校验规则和接口端点共同表达同一条状态迁移。

各位看官，测试文章编辑页时，不要只验证新建草稿。请修改一篇已发布文章并普通保存，确认它没有下线；再分别执行发布和下架，确认每次状态变化都来自用户清楚选择的动作。
