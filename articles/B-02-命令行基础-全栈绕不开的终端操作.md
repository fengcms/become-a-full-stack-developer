# 成为全栈·基础补充·命令行基础：全栈绕不开的终端操作

我第一次打开这个项目的终端时，做的是 `git log`。

然后我用 `↑` 翻了 40 次历史，翻到头之后发现**我不知道怎么停下来**。

不是玩笑——那时候我以为方向键是文本编辑器里的东西。查资料之后才知道，终端有自己的历史机制（`↑` / `↓`），而它和光标位置、Tab 补全这些是**同一套 readline 家族**的东西。

这篇讲我后来每天都在用的那些命令，以及一个更重要的东西：**终端不是"跑命令的地方"，它是一个有状态的环境，而搞清楚那个状态能省掉大量困惑。**

## 先搞清楚你在哪个 shell 里

新人不理解终端时，第一个问题往往是"我输入 ls 之后发生了什么"。

而回答这个问题之前，要先知道**是谁在接收你的输入**：

```bash
# 看当前 shell
echo $SHELL          # Linux/macOS 通常是 /bin/zsh 或 /bin/bash
echo $0               # 更可靠：当前运行的进程名
```

而这个项目的脚本开头都是这两行：

```bash
#!/usr/bin/env bash
set -euo pipefail
```

**这两行值得单独讲，因为它们是这个专栏所有 shell 脚本的基础。**

`#!/usr/bin/env bash` 是"用 PATH 里找到的 bash"，而不是写死 `/bin/bash`。区别在于：**macOS 上可能同时装了多个 bash，写死路径会用到系统自带的旧版本**（macOS 自带的 bash 3.2，而脚本通常需要 4+）。

`set -euo pipefail` 是三个选项：

| 选项 | 含义 | 不加会怎样 |
|---|---|---|
| `-e` | 命令失败就退出 | 中间某步失败，脚本继续跑，**最后一步成功 → 整体看起来成功** |
| `-u` | 用了未定义变量就退出 | `$TYPO` 展开成空，**你以为传了参数其实没传** |
| `-o pipefail` | 管道里任一环失败就失败 | `curl ... \| jq ...` 里 curl 失败，**jq 处理空输入成功 → 管道整体成功** |

**这三条组合起来防的是同一类错误：脚本"假成功"。**

而这个项目的 `run_android.sh` 就是典型：

```bash
#!/usr/bin/env bash
set -euo pipefail
APP_ROOT="$(cd "$(dirname "$0")/.." && pwd)"
cd "$APP_ROOT"
flutter pub get
exec flutter run -d "${1:-emulator-5554}" --dart-define=API_BASE_URL="${API_BASE_URL:-https://api-befull.kao9.com/api/v1}" --dart-define=DEV_HTTP_PROXY="${DEV_HTTP_PROXY:-}"
```

**注意它不写死工作目录**，而是先算出脚本自己的位置再 `cd`：

```bash
APP_ROOT="$(cd "$(dirname "$0")/.." && pwd)"
```

**这样你从任何目录调用它都能工作。** 而如果直接写 `cd flutter-app`，那么从项目根目录跑脚本就会失败——**而你第一次跑它很可能就是在根目录。**

顺带说那个 `exec`：

```bash
exec flutter run ...
```

**`exec` 会用新进程替换当前 shell。** 效果是 `Ctrl-C` 直接传给 `flutter`，而不是"杀掉脚本、留下 flutter 继续跑"。

**少了 `exec` 的症状很怪**：你按了 `Ctrl-C`，终端回来了，但 `flutter run` 还在设备上跑着、还占着端口。

## 命令行里最值钱的三个操作

### 一、管道：把上一个的输出当下一个的输入

```
命令 | 命令
```

而这个专栏里最常用的组合是这三个：

```bash
# 统计错误码在契约里出现多少次
grep -c "code: 4" openapi.v1.yaml

# 只看包含关键词的行
grep -n "x-authz" openapi.v1.yaml

# 处理 JSON
cat package.json | jq '.scripts'
```

**而 `jq` 这个工具值得专门说**，因为它在 API 项目里几乎是必备的：

```bash
# 从 API 响应里提取一个字段
curl -s https://api-befull.kao9.com/api/v1/articles | jq '.data.list[0].title'

# 只列出所有操作 ID
curl -s .../openapi.yaml -o - | yq '.paths | keys'

# 数一共有多少个操作
yq '.paths | to_entries | map(.value | keys) | flatten | length' openapi.v1.yaml
```

**最后那条的价值在于：它把"我以为有多少个接口"变成了一个可复现的数字。** 而这个项目的真实答案是 68——**而这个数字是我用脚本数的，不是数出来的。**

**为什么这个区别重要**：如果你说"大概 60 多个接口"，没人能反驳；如果你说"68"，而脚本跑出来是 68，那它就是事实。

**这也是 B-16 讲的"契约能被检查"的思路在日常里的体现**——用一个能复现的命令代替一个凭印象的数字。

### 二、重定向：把输出存下来而不是打屏

```bash
命令 > 文件       # 覆盖写入
命令 >> 文件      # 追加
命令 2>&1 | tee 日志.txt   # 同时输出到屏幕和文件
```

**第三条在这个项目里用到过**——M1-34 讲的那个微信登录排查：

```bash
wrangler tail | tee wechat-debug.log
```

**为什么要 `tee` 而不是直接重定向？** 因为排障时你需要**看着日志跑**，而不是等它跑完再看。

而这里有一个**很容易犯的错误**：

```bash
wrangler tail > wechat-debug.log    # ❌ 屏幕什么都不显示
wrangler tail | tee wechat-debug.log    # ✅ 屏幕有、文件也有
```

**我第一次写成了重定向版本，然后困惑了五分钟为什么"什么都没发生"。** 而实际上它在正常工作——只是输出去了文件。

**而这个坑的性质是"没报错但看不到东西"**，和 M1-34 讲的那个 `secret list` 一模一样：**"我以为能看到"和"实际能看到"是两件事。**

### 三、`&&` 和 `;`：控制执行顺序

```bash
命令1 && 命令2      # 命令1 成功才执行 2
命令1 ; 命令2       # 无论如何都执行 2
```

而这个项目的一次真实使用（发布流程）：

```bash
cd flutter-app && node tool/generate_contract.mjs && flutter analyze
```

**用 `&&` 是因为这三步有依赖**：不生成契约就没法 analyze，而 analyze 失败说明代码有问题、不该继续。

**而如果第三步失败了，第四步就不该跑**——这就是 `&&` 的价值。

反过来，**清理脚本必须用 `;`**：

```bash
rm -rf build/ ; npm install    # ✅ 删不掉也要装
```

**这里如果用 `&&`，删不掉就不装了**——而"删不掉"往往是因为目录不存在，而这恰恰是正常情况。

**`&&` 和 `;` 的选择，取决于"失败后该不该继续"，而不是哪个看起来更简洁。**

## 后台运行：这个项目踩过的坑

有些命令要跑很久（`wrangler tail`、开发服务器），你不想被它占住终端。

```bash
npm run dev &              # 启动到后台
npm run dev &> /dev/null & # 同时不输出
jobs                       # 列出后台任务
fg %1                      # 拉回前台
kill %1                    # 杀掉
```

而这个项目用了一个更好的办法——**`nohup`**：

```bash
nohup npm run dev > dev.log 2>&1 &
```

**`nohup` 解决的是"终端关掉之后进程被杀"的问题。**

而它的原理值得知道：`nohup` 让进程忽略 `SIGHUP` 信号（终端关闭时发出的"你该走了"）。

**而这个知识是从一次踩坑里学到的**：`nohup` 起的服务，第二天早上还在跑——**但它的日志我找不到在哪了。** 因为我重定向到了一个不存在的目录。

**所以 `nohup` 的两个部分要一起写**：`nohup 命令 > 文件 2>&1 &`。少了任何一个都会出问题。

## 查找：三个命令的分工

新手最常问"怎么快速找到一个文件"。答案是先明确你要找什么。

**找文件（按名字）：**

```bash
find . -name "*.ts" -not -path "*/node_modules/*"
ls **/*.dart 2>/dev/null
```

而这个项目里最常用的那条：

```bash
find lib -name "*.dart" -exec wc -l {} \; | sort -rn | head -10
```

**它输出"最大的 10 个文件"** ——而我改文章前统计规模就用它（B-17 那些数字就是这么来的）。

**注意 `-exec ... \;`**：把 find 的结果交给后面的命令执行。**而 `{}` 是占位符，`;` 是结束符**——**这个写法没有第二个分号就不完整**，很多初学者在这里卡住。

**找内容（按文本）：**

```bash
grep -rn "credentialsConfigured" node-backend/src/
grep -rE "get|post" route.ts          # 扩展正则
grep -rIn "TODO" .                     # 显示行号
```

**而 grep 有一个我必须提醒的坑**——这个项目的开发环境里踩过：

```bash
grep "错误码\|错误表" file.md        # ⚠️ 静默返回空
```

**在某些环境里 `\|`（BRE 的"或"）不被支持**，于是它返回 0 条匹配——**而且不报错**。

正确写法：

```bash
grep -E "错误码|错误表" file.md        # ✅ 扩展正则
grep -e "错误码" -e "错误表" file.md   # ✅ 或多个 -e
```

**这个坑的性质比一般 bug 恶劣**：**它不会报错，只会让你以为"没有这个东西"。** 而如果你据此得出"这个功能没实现"的结论——**那就是一个完全基于错误信息做的决策。**

**我自己在改这批文章时踩过两次。** 后来凡是涉及"或"的匹配，一律用 `-E`。

**找命令（不知道命令叫什么）：**

```bash
man git        # 手册
git --help     # 简要
which git      # 在哪
type -a git    # 所有版本（装了多个时）
```

## 这个专栏特有的用法：脚本化统计

前面都是通用命令，而我在改文章时真正高频的是**用命令行做统计**。

因为"某系列的文章字数中位数是多少"这类问题，**肉眼数不出来，但脚本一行就能给出精确答案**。

```bash
# 数一篇 md 的字数
wc -m articles/M4-03-*.md

# 数所有 M4 文章的总行数
wc -l articles/M4-*.md | tail -1

# 按行数排序找出最大的文件
wc -l articles/*.md | sort -rn | head -10
```

**而 `wc -l` 有个容易搞错的地方：它数的是"行数"，不是"字符数"。**

一篇 3000 字的中文文章，字符数（含标点和换行）可能是 3200，而行数可能只有 200。**所以 `wc -c` 和 `wc -m` 才是字符数。**

而更准确的做法是用脚本（因为我需要排除代码块、只数正文）：

```bash
python3 -c "
import re
t = open('articles/M4-03.md', encoding='utf-8').read()
body = t[:cut] if cut > 0 else t
print(len(re.findall(r'[\u4e00-\u9fff]', body)))
"
```

**为什么不用 `wc`？** 因为我要的是"正文字数"，而 `wc` 会把代码块、发布辅助信息都算进去。

**这个区别在批量处理时很致命**——比如那个辅助区注释标记，它是**发布时要整段删除**的，而如果统计时没排除，每篇都会虚增几百字。

**而这个"辅助区标记"本身是个很好的工程实践**，顺便说一下：

```html
```

**它解决的问题是"怎么区分正文和写作辅助内容"**，而三个条件同时满足才可靠：

1. **HTML 注释**——Markdown 渲染时不显示
2. **有明确的起止标记**——能用脚本精确定位
3. **名字里带"删除"**——人看到也知道

**而这批文章的验收脚本就是靠第 2 条定位正文的。** 如果只有"从这里开始是辅助信息"而没有结束标记，那段之后的正文就会被误删或误计。

## 一个我到现在还会犯的错

上面提到的 `>` 和 `| tee` 那个坑，我后来又踩了一次。

那次是部署之后想看实时日志：

```bash
wrangler tail > tail.log
```

然后盯着屏幕等了半分钟，什么都没有。

**我知道原因，但那一刻就是没想到。** 因为在我的经验里"跑起来没反应"通常意味着程序挂了或者报错了——**而"它在写文件"这个状态不在我的默认预期里。**

于是我又去检查了 Worker 是不是真的部署了、日志是不是有内容、环境变量对不对——**花了一分多钟，而实际问题只是我需要按 `Ctrl+C` 然后 `cat tail.log`。**

而这件事让我重新想了一下"无输出"这件事：

| 现象 | 可能的解释 |
|---|---|
| 程序真的挂了 | 日志里会有错误 |
| 程序正常但没输出 | **可能是真的没产生日志** |
| **输出被重定向到文件了** | **屏幕当然什么也没有** |

**第三种是最反直觉的，因为它要求你"知道自己重定向过"。** 而人对"我刚做过的事"的记忆在几分钟后就不牢靠了。

**所以现在我的习惯是：任何带重定向的命令，后面一定加 `| tee`**，让输出同时出现在屏幕和文件里。

**这不是因为重定向不好用——它对长时间运行的任务是必需的**（比如打包几小时的视频，或者持续写日志的服务）。**而是因为"看不见输出"这件事，会把我的排查引向完全错误的方向。**

## 顺带说一个判断脚本结果的原则

上面那个"统计正文字数"的脚本，它给我的答案也可能不准——**如果我的正则表达式写错了。**

而这件事我在改这批文章时遇到过一次：我第一版统计的是"文章总字数"（含代码块和发布辅助区），第二版才是"正文字数"。

**两个数字都"看起来对"，但差了几百。** 而如果我据此判断"这批文章达标了"——那就是一个假结论。

**所以判断脚本结果的原则是：先看它测的是不是你关心的东西。**

具体的做法有两个：

1. **在小样本上验证** —— 比如手动数一篇文章的前 200 字，看脚本数和实际差多少
2. **看两个数字的差值是否符合预期** —— "正文比总字数少 700 字"合理，"少了 3 万字"就说明有 bug

**而这两个做法在 B-17 那篇讲测试时也出现过**——"测试覆盖率"这个数字同样可以因为统计口径不同而差几倍。**所以任何"看起来客观"的数字，都要先问口径。**


## 一条我一开始想省掉的事

上面那个"统计正文字数"的脚本，我一开始是直接用 `wc` 的。

结果第一次跑出来"每篇 3800 字"，而我自己数的正文只有 3100。**差了 700。**

排查之后发现是辅助区之后的内容被算进去了——而那段里有文章简介、Tag 列表、配图提示词。

**而这件事的恶劣之处在于：如果我据此判断"这批文章字数达标了"，那就是一个假结论。**

改法就是上面那个脚本——**排除辅助区之后再统计**。

而这带来的判断标准变化是：

> **任何"统计"类命令，默认都会把不该算的东西算进去。** 因为它不知道你的意图——`wc` 只知道数字符，不知道什么叫"正文"。

**所以凡是统计，先问自己"我要数的到底是什么"，然后确认工具知不知道。**

顺带说，这个 bug 和我记忆里另一条经验是同一个：**检测脚本报"全部通过"时，要先确认它测的是不是你关心的东西。** 一个量错了口径的绿灯，比没有绿灯更危险。

## 小结

命令行这一章，沉淀下来的是三件事：

1. **`set -euo pipefail` 是 shell 脚本的基础**，防的是"假成功"。
2. **管道和重定向组合起来是最实用的**，但 `>` 和 `| tee` 的区别（看不看得见输出）是个高频坑。
3. **统计类命令要确认口径**——`wc` 不知道什么叫"正文"，而假绿灯比没绿灯危险。

而最重要的其实是第 3 条背后那个想法：

> **终端的价值在于它可复现。** 一条命令跑三遍结果一样，一个数字对任何人都是一样的——**而这正是这个专栏做文章质量判断时一直依赖的东西。**

"字数中位数 1679"和"我觉得有点单薄"是完全不同性质的信息。**前者能被验证，后者只是感觉。** 而这一批文章的优化之所以能推进，靠的就是把感觉转成了可测的数字。
