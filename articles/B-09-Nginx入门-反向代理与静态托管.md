# 成为全栈·基础补充·Nginx 入门：反向代理与静态托管

这个专栏的线上流量，走的是 Cloudflare 的路由：

```toml
# ── 自定义域名（部署后需在 CF 配 DNS + SSL）──
routes = [{ pattern = "api-befull.kao9.com", custom_domain = true }]
```

**一行配置，Cloudflare 帮你做了 TLS 终止、域名路由、Worker 转发。**

而如果没有这个平台，同样的事情要自己用 Nginx 配——**而那个配置文件里的每一行，都对应着一个"配错了会怎样"的问题。**

这篇讲 Nginx 到底在解决什么问题，以及为什么这个专栏最终把它交给了 Cloudflare。

## 反向代理：解决"浏览器不能直接访问后端"

先说清楚它解决的问题。

**浏览器的同源策略**决定了：网页只能请求和它同源的接口。所以如果你在 `example.com` 上打开网页，它不能直接请求 `api.other.com/articles`——**浏览器会拦下来**。

而反向代理的做法是：

```text
浏览器 → https://example.com/api/articles
          ↓ 同一个域名，浏览器不拦
        Nginx（或 CDN）
          ↓ 按路径转发到不同服务
        http://127.0.0.1:3000/api/articles   ← 后端
```

**在服务器这一侧，"跨域"不存在**——它只是把请求转给了另一个进程。

而它带来的另一个效果是：**浏览器永远只看到一个域名。**

| 需求 | 反向代理怎么解决 |
|---|---|
| 前后端不同源 | 路径前缀统一（`/api/*` → 后端） |
| 多个后端服务 | 按路径分发（`/api/*` → A，`/admin/*` → B） |
| HTTPS | 在代理这一层终止，前端不需要知道 |
| 隐藏内部结构 | 外部看不到有几个服务、端口是多少 |

## 静态托管：Nginx 最常见的用法

而这个专栏的"网站前台"（Next.js）其实是可以静态托管的——**如果它不是 SSR 的话。**

```nginx
server {
    listen 80;
    server_name befull.kao9.com;

    # 静态资源
    location / {
        root /var/www/web-frontend/out;
        try_files $uri $uri/index.html /index.html;   # ← SPA 回退
    }

    # 压缩
    gzip on;
    gzip_types text/css application/javascript application/json;

    # 缓存策略
    location ~* \.(js|css|png|jpg|svg|woff2)$ {
        expires 1y;
        add_header Cache-Control "public, immutable";   # 带 hash 的文件名
    }
}
```

**三处值得说：**

**一、`try_files ... /index.html` 是 SPA 的必需项。**

没有它，用户访问 `/articles/123` 时 Nginx 会去找 `.../articles/123` 这个文件——**找不到，返回 404**。而前端路由明明是客户端处理的，路径在服务器上并不存在。

加上回退之后，Nginx 对所有未知路径都返回 `index.html`，**由前端路由接管**。

**这个症状很有迷惑性**：首页能打开、点进详情页就 404——**而开发者往往会以为是"路由配错了"。**

**二、静态资源那一段的 `immutable` 和 1 年缓存。**

它成立的前提是**文件名里有 hash**（Next.js 的默认产物是 `main.abc123.js`）——**内容变了 hash 就变，URL 变，所以可以永久缓存。**

**而如果文件名不带 hash**（比如 `main.js`），这条规则会让用户永远拿到旧版本——**一个比"缓存不够久"严重得多的问题。**

**三、`gzip` 对 JSON 的处理。**

而这个专栏有个相关的实际问题：**JSON 比 HTML 更值得压缩**，因为它重复结构多。而很多默认配置里 `gzip_types` 没有包含 `application/json`——**于是接口响应完全没有压缩。**

顺带说一个更现代的选择：**Brotli（`br`）**。它在小文本上的压缩率优于 gzip，而这个项目的接口响应大量是小 JSON——**收益是明显的。**

## 负载均衡和健康检查

第三块 Nginx 常做的事，而它和"健康检查"一起用才有意义：

```nginx
upstream app_backend {
    least_conn;                  # 按连接数分配，而不是轮询
    server 127.0.0.1:3001 max_fails=3 fail_timeout=30s;
    server 127.0.0.1:3002 max_fails=3 fail_timeout=30s;
    keepalive 32;
}
```

而健康检查要区分两种：

| 类型 | 谁做 | 特点 |
|---|---|---|
| **被动**（`max_fails`） | 代理自己 | **某个请求失败了才标记** |
| **主动**（`health_check`） | 代理定期探 | **故障在流量到达前就被发现** |

**而 `max_fails` 这个被动检查有一个滞后性**：第一个请求会被转发到已经挂掉的实例上，**用户感受到一次超时**，然后才被标记。

**而这个专栏不需要关心这件事——因为 Cloudflare 帮它做了。**（FaaS 平台的实例调度是内置的。）

**顺带说一个我们真实遇到的问题**（B-15 讲过）：网关的超时配置。

```
lb_try_duration 5s
```

**而这个项目里有些 SQL 查询偶尔超过 5 秒**——于是网关主动断开连接，客户端重试，列表出现重复。

**这个问题出在 Nginx（或 Caddy）这一层，不在任何应用代码里。** 而它的表现是"列表偶尔重复"，**排查方向自然会被引向业务代码**。

**B-15 那篇写的教训是：有些环节不在你写的代码里。**

## WebSocket 和长连接

如果要用 Nginx 代理 WebSocket，需要额外配置：

```nginx
location /ws {
    proxy_pass http://127.0.0.1:3000;
    proxy_http_version 1.1;
    proxy_set_header Upgrade $http_upgrade;
    proxy_set_header Connection "upgrade";     # ← 少了这两行握手失败
    proxy_read_timeout 3600s;                  # ← 默认 60s 会断
}
```

**两个容易漏的点：**

| 配置 | 不配的后果 |
|---|---|
| `Upgrade` / `Connection` 头 | 握手失败，**连接直接建立不起来** |
| `proxy_read_timeout` | **60 秒后自动断开**——而用户以为还连着 |

第二个特别隐蔽：**它表现为"每隔一分钟就掉线一次"**，而症状看起来像客户端的问题。

**而这个专栏没有 WebSocket**——它的"实时"需求（M4 讲的那个角标）是轮询实现的，周期 15 秒。

**而这个选择也是权衡的结果**：轮询的实现简单、跨环境行为一致（NAT、企业代理都不会挂），代价是 15 秒延迟。**对于"有没有新通知"这个场景，15 秒完全够用。**

## 为什么这个专栏最终不用 Nginx

现在讲我做的判断。

**核心原因是：Cloudflare 已经把 Nginx 的绝大多数能力接管了。**

| Nginx 能力 | 这个专栏的归属 |
|---|---|
| 反向代理 | `routes` 配置（1 行） |
| TLS 终止 | Cloudflare 自动签发 |
| 静态托管 | Cloudflare Pages / R2 |
| DDoS 防护 | Cloudflare 免费提供 |
| HTTP/2、HTTP/3 | Cloudflare 自动 |
| CDN 缓存 | Cloudflare Edge |
| 负载均衡 | FaaS 平台内置 |

**而省下来的不只是配置工作，还有"配置错了要排查"的时间。** B-15 那个网关超时的 bug 就是这类成本的例子——**如果它存在这个项目里，每个月都会有人被它绊一次。**

**但有一个代价必须说清楚：**

**"用 Cloudflare"这个决定，意味着这个项目不能在裸服务器上跑。** 而一旦要迁移，那需要补上：

1. 一份 Nginx/反代配置（含超时、缓存、WebSocket）
2. TLS 证书的申请和续期
3. DDoS 防护的另外方案
4. 负载均衡
5. **M1-34 那个 bug 的复现环境**（B-04 讲过：本地 ≠ 线上）

**第 5 条最关键**——**换平台不只是换配置，而是换一整套"环境差异"的来源。**

**而这正是 B-08 讲的那个判断的另一个版本**：Docker 和 FaaS 的区别不只是"怎么部署"，而是"**谁来保证运行环境**"。

**自己管 Nginx，意味着你自己保证；交给 Cloudflare，意味着它保证但你被绑定。**

**这个专栏选了后者——因为它要讲的是全栈开发，不是运维。** 而这个选择应该被写出来，而不是假装"所有人都该用 Cloudflare"。

## 反向代理在移动端那批文章里的对照

B-09 讲的"按路径转发"，在 Flutter 那批文章里有一个精确的对照——M4-15 讲的 WebView：

```text
Flutter 栈：  Article → WebPage          （两层，返回即回文章）
WebView 内部： URL A → URL B             （不体现在 Flutter 栈上）
```

**这两套"路由"的层级关系和 Nginx 的 upstream 很像**——**外层路由不变，内层跳转不影响外层**。

而这个设计选择解决的是一个真实问题：用户在文章里点了个外链，进网页后又点了两个链接，**此时按返回应该去哪？**

现在选的是"回来源文章"，所以 WebView 内部跳转完全不进 Flutter 栈。

**如果换成浏览器语义，就得在 `PopScope` 里先检查 `canGoBack()`，并且处理 Android 硬件返回和 iOS 边缘手势两条路径。**

**而"只有一条路径要维护"本身就是一种简化。** 这和 Nginx 里"能不 proxy 就不 proxy"是同一个判断——**每多一层转发，就多一处可能配错的地方。**


## 一条我一开始想省掉的事

有一段时间，文章详情页在手机上打开很慢，而在电脑上正常。

我一开始以为是图片太大——**然后把图片压缩了三轮，收益很小。**

真因是**服务端没有压缩接口响应**。

而那个接口返回的东西里包含**整篇 Markdown 正文**（一个几千字的 JSON）——**不压缩的话，每次请求都要传十几 KB 的纯文本。**

**而 Cloudflare 默认对 JSON 也做了压缩**——**所以这个问题在测试环境（本地）根本不会出现。**

也就是说：**这不是"配漏了"，而是"平台已经替你做了，而你不知道"。**

**而它的危险之处在于：如果你某天换平台（比如迁到自己的服务器），这个问题会突然出现，而你会花时间重新查一遍。**

所以现在我在 B-04 那篇里明确写了这一条：

> 配置项不能只按"当前会不会用到"来决定值，要按"万一被用到时会怎样"来决定。

**而这个判断扩展到基础设施上就是**：

> **要清楚哪些能力是平台提供的，哪些是自己写的。** 因为前者消失时，你不会收到任何警告。

## 小结

Nginx 这一章，沉淀下来的是四件事：

1. **反向代理解决同源和路径分发** ——浏览器只看到一个域名，服务器侧不需要跨域概念。
2. **SPA 必须有回退配置** ——`try_files ... /index.html`，否则详情页 404。
3. **缓存策略的前提是文件名带 hash** ——不带 hash 却设长缓存，会让用户永远拿旧版本。
4. **平台接管是有代价的** ——省下配置和排查，但丢失了"换平台不踩坑"的假设。

其中第 4 条是这一章真正的判断：

> **用托管服务替代自建能力，得到的省事和失去的自主权是同一件事的两面。**

而第 3 条是最实用的一个：**"长缓存 + 无 hash"这个组合会静默地让用户永远拿不到新版本** ——而且它只在发版之后暴露，**在那之前一切正常。**

而这个专栏最终的选择是 `routes` 一行配置 + 平台托管。**代价是这个项目和 Cloudflare 绑定了**，而收益是 B-15 那个"网关超时"的 bug 根本不存在。
