# 成为全栈·React 管理后台篇·分类树与标签管理：层级数据在后台怎么编辑

> 分类和标签都用于组织文章，却不是两套相同的增删改查。分类要维护层级与无环约束，标签要呈现引用关系与使用入口。

## 前言

后端可以用一张自关联表保存分类，接口也能返回嵌套 children。若前端把它拍平成普通表格，编辑者看到的只是十几个并列名称，不知道“React”属于“前端开发”，也不知道移动一个父分类会影响多少后代。

标签看起来更简单，但删除一个仍被几十篇文章使用的标签，后端必然返回 409。让用户点完删除再看到错误，说明界面明明掌握引用数量，却没有把它变成可用信息。

这一篇把分类树和标签放在一起比较，重点不是 CRUD，而是怎样把关系约束翻译成操作。

## 分类树必须保留路径

分类页递归渲染 `children`，用缩进表达层级，用展开集合控制显示。分类数量较少时首次默认全部展开，让结构一眼可见；数量增长后仍可手工折叠。

搜索不能只返回匹配节点。若“React”命中而祖先“前端开发”被丢掉，用户仍不知道它处在哪条路径。当前过滤逻辑保留命中节点的祖先；父节点自己命中时则保留整个子树：

```ts
const filterTree = (nodes: CategoryNode[]): CategoryNode[] =>
  nodes.flatMap((node) => {
    if (`${node.name} ${node.slug}`.toLowerCase().includes(keyword)) {
      return [node]
    }
    const children = filterTree(node.children ?? [])
    return children.length ? [{ ...node, children }] : []
  })
```

搜索结果强制展开祖先路径，而不破坏用户原本的 expanded 集合；清除搜索后，之前的折叠习惯仍在。

## 契约没有 parentId，前端就从树反推

当前 `CategoryNode` 只返回 children，没有 parentId。但编辑接口是全量替换，若编辑子分类时遗漏父 id，后端可能把它移到根节点。

因此前端遍历树建立 `id → parentId` 映射：

```ts
export const buildParentMap = (nodes: CategoryNode[]) => {
  const map = new Map<number, number | null>()
  const walk = (list: CategoryNode[], parentId: number | null) => {
    for (const node of list) {
      map.set(node.id, parentId)
      walk(node.children ?? [], node.id)
    }
  }
  walk(nodes, null)
  return map
}
```

这是一层适配，不是在前端创造第二棵树。源数据仍是接口返回的嵌套结构，parentMap 只为编辑回填、深度判断和路径计算服务。

## 父级候选必须排除自己和所有子孙

把分类设为自己的父级会自环；把父分类挂到某个子孙下会形成更长的环。后端会返回 409，但前端已经拿到完整树，可以在选择器里提前排除非法选项。

```ts
const excluded = new Set(collectSubtreeIds(node))
const options = flattenTreeOptions(tree, excluded)
```

父级选项带缩进，用户能够看到目标位置。最大深度为 4，达到上限的节点直接禁用“新建子分类”，并用 title 说明原因。

这些纯函数被单独测试，因为环检测与深度边界靠肉眼很难覆盖。前端护栏改善体验，后端仍要再次校验并发修改后的真实树。

## 删除分类要先处理后代和文章

有子节点时，删除按钮直接禁用；确认框也明确提示先迁移分类下的文章和子分类。没有子节点仍不代表没有文章引用，因此最终请求可能被后端拒绝。

理想情况下，分类节点也应返回 articleCount，并把数字链接到已筛选文章列表。当前契约未提供这个字段，前端不能假装知道引用情况，只能在确认文案中说明约束并展示后端 409。

这也说明 UI 能做到什么取决于契约。为了减少一次错误请求而需要的引用计数，应在接口设计阶段提出，而不是在浏览器里拉取全部文章自行统计。

## 标签没有层级，但有使用关系

标签列表返回 articleCount。页面默认按使用量排序，并把“12 篇”做成链接：

```tsx
<Link to={`/articles?tag=${encodeURIComponent(tag.slug)}`}>
  {tag.articleCount ?? 0} 篇
</Link>
```

这比单独展示一个数字更有用。管理者可以进入对应文章列表，判断标签是否重复、是否需要迁移内容。

articleCount 大于 0 时删除按钮禁用并提示“仍有文章引用”。没有引用时才进入不可恢复确认。分类和标签在这里遵循同一原则：让关系成为操作入口，而不是把外键约束留给错误弹窗解释。

## 不要自动给中文名称生成错误 slug

标签和分类 slug 必须符合小写字母、数字与连字符规则。中文名称直接套一个简单 slugify 往往得到空串，或者生成不稳定的拼音。

当前表单让用户明确填写 slug，并在前端复用契约正则：

```ts
const SLUG_PATTERN = /^[a-z0-9-]{1,64}$/
```

重复仍由后端用 409 判断，因为只有数据库知道全局唯一性。前端负责格式，后端负责事实。

如果以后接入可靠的拼音转换，可以给出建议值，但应允许编辑者确认。URL 标识一旦发布，修改还涉及旧链接重定向，不能把它当成名称输入的无害副作用。

## 契约没有标签合并，就不要伪造一个

后台常见“合并标签”功能，但当前 API 没有原子合并端点。前端若自行遍历文章、逐篇替换标签再删除旧标签，会遇到部分失败和并发修改，最终可能只迁移一半。

因此当前页面没有合并按钮。能力缺失应明确留在规划中，等后端提供带事务语义的命令，再设计预览影响范围和确认流程。把复杂业务命令拼成一串 CRUD，并不会让它变得可靠。

## 树更新后，展开状态也可能过期

展开集合保存的是分类 id。删除节点、移动子树或重新获取整棵树后，其中可能留下已经不存在的 id。它不会直接破坏渲染，却会让状态持续积累，并在 id 策略变化时产生意外。

当前页面只在首次拿到数据时默认展开全部，不会每次 Query 更新都重置用户的折叠选择：

```ts
const initialized = useRef(false)

useEffect(() => {
  if (initialized.current || tree.length === 0) return
  initialized.current = true
  setExpanded(new Set(parentMap.keys()))
}, [tree.length, parentMap])
```

这是“数据刷新不覆盖交互状态”的同一原则。规模扩大后，可以在树变化时求交集，只移除不存在的 id；不能简单 `setExpanded(allIds)`，否则用户每次编辑分类后整棵树都会突然展开。

递归渲染使用稳定的 node.id 作为 key，而不是数组下标。移动节点以后，React 才能识别这是同一个分类换了位置，而不是销毁旧行再创建新行。

## 写操作后为什么失效整棵分类树

创建、编辑和删除一个节点都可能改变父子关系。精准修改嵌套缓存需要找到旧父节点、移除子树、插入新位置并维护排序，任何一步遗漏都会让前端树与服务器不同。

当前数据量较小，mutation 成功后直接失效 `['categories']`，重新获取权威树。这比在客户端实现一套树迁移算法可靠。若未来分类达到数千节点，需要按需加载子树，再重新设计更细的查询键和局部更新；不能拿当前小树策略硬套。

标签是平铺数组，同样在写后失效标签缓存。编辑接口返回完整 Tag 时也可以精准替换，但 articleCount 可能受其他文章操作影响，重新获取仍是稳妥选择。

## 名称、slug 与路径分别服务不同对象

名称给人阅读，slug 给 URL 和接口识别，树路径给管理者理解上下文。三者不能互相替代。两个不同父级下可以出现语义相近的名称，但 slug 必须全局唯一；移动分类改变路径，却不一定应该改变 slug。

因此表单不会根据父级和名称自动重写已发布 slug。若确需修改，产品还应决定旧地址是否保留重定向，以及文章链接如何迁移。一个看似普通的文本框，背后可能是公开 URL 的兼容承诺。

## 小结

分类树的重点是保留路径、反推父级、阻止成环和控制深度；标签管理的重点是呈现使用数量、提供文章入口和阻止删除仍被引用的数据。两者都把后端关系约束变成了用户能提前理解的操作条件。

各位看官，层级数据不是换一种表格缩进，关系数据也不只是多显示一列数量。界面必须让用户看见“我正在移动什么、会影响谁、为什么现在不能删除”。
