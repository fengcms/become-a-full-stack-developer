# 成为全栈·Vue 管理后台篇·Vue 后台测试怎么分层：从纯函数到真实页面路径

> “测试通过”只说明已执行的断言成立，不能自动证明浏览器中的所有用户流程正确，更不能证明线上写请求已验收。本文盘点 Vue 管理后台实际的测试层次，说明每层适合回答什么问题、当前还缺哪些证据。

> 本文代码快照：Vue 后台提交 `d3ee41a`。主要参考 `manage-frontend-vue/src/**/*.test.ts`、`vitest.config.ts`、`package.json` 和 React 后台测试配置。

## 前言：测试不是越多越好，而是要知道证明范围

测试名称容易给人过度信心。“权限测试通过”可能只测了一个纯函数；“登录测试通过”可能只是 mock fetch；“页面构建成功”也没有打开真实浏览器。我们需要清楚每条证据覆盖了什么行为，也知道它没有覆盖什么。

Vue 后台当前配置 Vitest、jsdom 和 Vue Test Utils 依赖，测试文件主要集中在权限函数、请求内核、UI store 和路由守卫。它们保护了高风险的逻辑边界，但目前并没有为每个表单和后台页面建立组件级交互测试，也没有仓库内的浏览器 E2E smoke 套件。文章会把实际情况与建议路线区分开。

## 第一层：纯函数测试

纯函数不依赖 DOM、Pinia 实例或网络，输入相同就应得到相同输出，适合用小测试覆盖权限映射、格式转换、树形投影和过滤策略。

当前 Vue 项目有 `lib/permission.test.ts`，验证角色/资源归属函数是否返回预期能力。例如 editor 能否管理内容、普通会员能否操作自己的资源、admin 是否具备更高层级能力。纯权限测试快速、稳定，能保护共享业务规则；它不能证明路由守卫已正确调用函数，也不能证明后端采用了同一规则。

分类 `rows` 树投影目前在页面 computed 中内联。若这段算法出现更多边界需求，抽成独立函数后再测深度、parentId、子节点和环路过滤会更容易；但不要为了测试覆盖率把单行展示表达式机械抽出。

## 第二层：请求内核测试

`lib/request/index.test.ts` mock 全局 fetch，覆盖成功信封拆包、并发过期请求共享一次 token refresh 并用新 token 重放，以及 FormData 不设置 Content-Type、body 原样传递。它们测试的是请求层拥有的契约：请求头、调用次数、信封、认证刷新和 multipart 边界。

这类测试比组件点击按钮更低层，但对关键基础设施很重要。若 request 层错误地 JSON.stringify FormData，图片上传会全部失败；若并发请求各自刷新，轮换令牌可能互相冲突。测试能快速、确定地重现这类问题。

它仍然运行在 jsdom/mock 环境，不证明真实浏览器跨域 Cookie、CORS、TLS、对象存储或线上令牌配置成功。模拟 Response 也不会验证 Node/Go 服务端实际返回了同一信封。

## 第三层：UI 偏好 store 测试

`stores/ui.test.ts` 测试主题偏好解析、明暗切换、系统媒体查询和 localStorage 侧栏格式。它保护非敏感 UI 偏好在 Vue 重写后继续按预期保存。相比截图回归，它很适合验证 store 的状态转换和持久化协议。

测试存储格式也有迁移价值：React 版 Zustand 曾保存 `befull-admin-ui`，Vue 版要兼容该状态而不是无意中重置用户偏好。不过，jsdom 中 `matchMedia` 是 mock，无法证明操作系统设置变化时所有真实浏览器都立即刷新；还需要浏览器验证。

## 第四层：路由守卫集成测试

`router/index.test.ts` 使用真实 Router 实例和 Pinia store 推进路由，验证匿名访问受保护路径回登录、member 可进个人中心但不能进控制台，以及 editor 可管理文章却不能访问用户管理。

它比单独测试 `canManageUsers()` 更接近用户实际导航，因为测试覆盖路由 meta 与全局守卫的组合。但它没有挂载每个页面组件，也没有完整验证登录表单填写、点击按钮、加载状态、真实网络跳转和浏览器 history 行为。

## 当前测试层次与尚未覆盖的区域

| 层次 | Vue 项目当前证据 | 仍不能据此推导 |
|---|---|---|
| 纯逻辑 | permission.test.ts | API 后端授权必然正确 |
| 请求内核 | 信封、并发刷新、FormData 测试 | 生产域名 Cookie/CORS/文件存储已正常 |
| UI store | 主题与侧栏持久化测试 | 所有 Naive UI 弹层的视觉对比正确 |
| 路由 | 匿名、member、editor 代表性边界 | 每个页面表单操作已在浏览器跑通 |
| 页面组件交互 | 当前没有系统化组件测试套件 | 无法声称全页面操作全覆盖 |
| 浏览器 E2E | 当前项目未配置 Playwright/Cypress 项目级脚本 | 无法声称登录到文章发布的真实路径已自动验收 |

这个清单不是贬低现有测试，而是帮助我们准确表述项目质量。当前四组测试保护了最重要的共用基础逻辑；下一步可以依风险逐步补页面测试，不需要先写一套庞大而脆弱的模拟系统。

## 选择测试工具和边界

Vitest 与 Vite 共用配置，适合运行 TypeScript/Vue 测试；jsdom 提供基础 DOM；Vue Test Utils 已安装，可用于挂载组件和触发交互。项目当前 test script 是 `vitest run`。如果要加真实浏览器 E2E，需要另行安装浏览器驱动、配置启动服务和数据种子；现在不能把依赖“已安装”说成套件“已落地”。

组件测试适合验证局部交互：点击页码发出 page=2 请求、上传失败时显示错误、dirty 状态阻止离开、筛选变化重置页码。对页面级表单，尽量 mock API 边界而保留真实 Vue component、Router 和 QueryClient 的关键组合。mock 所有子组件会降低集成可信度；什么都不 mock 又会让测试慢且容易受第三方库实现影响。

浏览器 smoke 适合走关键用户路径：登录、文章列表翻页、打开编辑器、保存草稿、打开评论审核、修改主题、移动端打开抽屉。与单测不同，它要处理端口、认证账号、数据库状态和网络，因此应以隔离的测试环境运行。

## 避免镜像测试和过度断言

不需要测试框架本身的 `ref(1)` 会变成 1，也不需要对每个静态标题写一个快照。测试应保护项目自己的约束：权限矩阵、API 字段、错误重试、筛选→请求参数、部分失败、回跳和主题 key。

不要将内部函数调用次数设为产品验收标准，除非次数本身影响正确性（例如并发 refresh 必须只有一次）。对渲染输出和用户动作的断言通常比“某个 helper 被调用”更稳定。

依赖固定时间、全局 localStorage、window 尺寸和 Promise 的测试要在 afterEach 恢复状态，避免测试顺序不同造成偶发失败。共享 auth store 的测试应在每个用例前清理会话。

## 测试通过之后仍要检查什么？

代码门禁可以验证格式、lint、Vue-aware 类型、Vitest 和生产构建；开发人员仍要对照原型和 React 后台检查页面，验证 API target、登录账号和浏览器实际交互。部署验收则需要确认真实域名、Cookie、CORS 和数据写入。它们是不同层次的证据。

如果只完成单测，最终报告应写“单测通过”，不能写“线上全功能验收通过”；如果开发服务器打开过某页面，也不能据此推导所有角色和异常状态均正确。专业交付的可信度来自证据范围描述准确。

## 小结：每个测试回答一个清楚的问题

纯函数测试保护业务映射，请求测试验证网络边界，store 测试验证本地偏好，路由测试保护访问路径，组件测试验证可交互页面，浏览器 E2E 验证真实主流程。Vue 项目当前已落地前四类中的重点测试，系统化组件/E2E 仍有建设空间。每一项“通过”都应说明测试环境和覆盖边界。

下一篇进入工程质量门禁：Biome、`vue-tsc`、Vitest、Vite build、深层路由和 API proxy 如何组合，怎样通过 `API_TARGET` 切换 Node/Go 后端，并诚实记录线上凭证验证限制。
