# 成为全栈·Taro 小程序篇·开发工具跑通之后：演示验收与正式发布还有哪些差距

> 演示成功可以是一个完整交付目标，但必须公开它成立的条件。开发工具的调试豁免，不应成为正式发布能力的替身。

{{IMG:M5-05-封面}}

## 前言：这次我们明确不追求上架

小程序规划开始时，作者已经说明当前后端部署与域名条件：服务在 Cloudflare，域名未完成备案，本项目是教学性质，不以真实上架为目标。开发者工具关闭域名校验后，能够跑通约定业务，就算本轮验证成功。

这个约定让我们能够集中做阅读、会员和投稿，也避免为了一个教学演示先改造整套部署。但它不能被省略。读者拿到项目，需要知道为什么工具能请求，以及这份结果可以被相信到哪里。

这篇记录范围判断和发布差距，不给出未来某一时点必然适用的监管结论。平台要求会变化，正式发布时应按当时官方流程重新核对。

## 一、让验收条件变成显式配置

项目 `project.config.json` 把“关闭域名校验”写成了显式配置，而不是口头约定：

```json
// taro-miniprogram/project.config.json（节选）
{
  "miniprogramRoot": "dist/",
  "appid": "wx3dc6aad170329a3a",
  "setting": {
    "urlCheck": false,
    "minifyWXSS": true,
    "minifyWXML": true
  }
}
```

`urlCheck: false` 是**演示条件**，不是发布能力。工具里还需确认相关调试选项实际生效——本地覆盖设置可能与仓库配置不同，不能只看文件就断言验证条件一致。

构建与验证入口同样落成脚本，读者可以照着复现：

```json
// taro-miniprogram/package.json（节选）
{
  "packageManager": "pnpm@11.25.0",
  "scripts": {
    "build:weapp": "taro build --type weapp",
    "dev:weapp": "taro build --type weapp --watch",
    "typecheck": "tsc --noEmit",
    "test": "node scripts/test.mjs",
    "test:integration": "node scripts/integration.mjs"
  }
}
```

当前记录包括开发工具版本 2.02.2609292 Nightly、基础库 3.17.3、模拟器类型、真实 AppID 和关闭校验条件。版本是这次证据的一部分，不是永久推荐的唯一组合。

```text
本轮演示：构建产物 + 已配置项目 + 工具关闭域名校验
          + 真实后端请求 + 约定业务操作

未来发布：另行核对平台资格、域名与隐私等条件
          + 真机验证 + 上传审核与发布流程
```

两条清单并排看，差别更清楚：

| 维度 | 本轮演示清单 | 正式发布清单 |
|---|---|---|
| 网络校验 | 工具内关闭域名校验 | 合法请求域名与证书 |
| 身份 | 真实微信登录（已专项） | 主体、类目与账号资格 |
| 数据与隐私 | 设置页本地说明 | 隐私声明与实际数据一致 |
| 设备 | 开发者工具为主 | 真机与弱网矩阵 |
| 交付 | 可复现构建产物 | 上传、审核、灰度、回滚 |

二者不是同一个清单，也不应该在结尾用一句“待上线即可”把中间工作消掉。

## 二、关闭校验没有替我们生成身份能力

调试选项不会生成 AppID、AppSecret，不会替后端实现 callback，也不会把模拟 OpenID 变成可信微信身份。真实微信登录必须走真实 code 与后端换码。

本项目已经配置后端 Secret，修复 Workers 参数差异，并在工具通过线上真实登录。这个专项可以单独成立，即使正式上架被排除。

反过来，不能把真实登录未跑通偷偷归入“上架不做”。登录是本轮产品能力，平台发行是另一个目标。规划和验收要把两者分开。

手机号、订阅消息和任意 web-view 也不会因关闭校验自动获得。本轮没有开发这些能力，不能把调试豁免解释成平台能力通行证。

## 三、网络域名、图片和业务网页要分别看

| 对象 | 本轮使用方式 | 正式阶段需要重新确认的方向 |
|---|---|---|
| API 请求 | 工具豁免条件下请求已有服务 | 合法请求域名、TLS 与证书等平台要求 |
| 图片上传与加载 | 已有接口和资源 URL | 上传、下载与资源域名条件 |
| 外部网页 | 复制地址降级 | 若加 web-view，核对业务域名与账号能力 |
| 微信身份交换 | 后端固定平台地址换码 | 秘密配置、运行时、安全诊断与异常策略 |

这张表是发布前检查方向，不是当前法规的逐条解释。正式决定应核对平台当时规则，不能从文章发布日期推断永久有效。

Cloudflare 也不应被单独当作“绝对不能上架”的因果解释。本轮排除上架，是当前域名条件与作者目标共同确定的范围；未来换条件，需要重新评估。

## 四、产品范围完整，与发行准备完整是两回事

当前十四页面、四 Tab 覆盖内容发现、阅读、互动、会员和投稿。它们构成一份可演示的产品，不是临时接口测试台。

正式发行还要看主体与类目、当前备案／认证流程、隐私声明与实际使用的数据、用户内容治理、投诉处置、真机适配、包体性能与回滚等。这些是后续评估项，不计作本轮偷偷遗留的开发任务。

如果一个项目从一开始就以发布为目标，则应把相关条件前置，而不是复用我们的演示约定。这是适用边界。教学项目可以缩小目标，但文章不能教读者把缩小目标当成绕过正式要求。

### 未来规则核对与当前技术事实要分开

本文可以确定的技术事实是 urlCheck 调试条件、现有组件与证据。主体、域名和审核的具体要求，应在真正推进发行时查官方当前规则。

不能把几个月前的博客清单当成确定法律意见，也不能因为用了某一家云服务就作一刀切结论。当前范围排除了上架，文章保留检查方向即可。

### 完成条件改变时，先更新范围再增加开发

假如作者以后决定发布，第一步是重新定义成功：哪些设备、哪些平台能力、哪些正式配置与何种发布证据必须具备。之后再补页面、隐私和部署，不是简单把 urlCheck 改为 true。

这也让教学项目有清楚的演进路线：当前演示版本可学习和复现，下一阶段按新目标补验证。范围缩小是公开选择，范围扩大也应成为公开决策。

## 五、隐私说明要按实际数据来写

当前本地保存会话、主题、搜索历史和按会员隔离的草稿；后端保存会员资料、互动关系与投稿等。首次微信登录不要求自动读取头像昵称，资料修改由自己的页面完成。

一份未来隐私说明应追踪这些实际流向，不能从模板里复制“我们不收集任何信息”。同样，没有使用的手机号或订阅消息也不应为了显得完整就写成已经收集。

退出后草稿保留，清理阅读缓存不删除创作材料，这些行为需要与说明一致。共享设备的风险提示来源于当前存储策略，不是额外假设平台提供加密保障。

本轮设置页已有教学与本地存储说明，它不替代未来正式发布需要的完整审查。产品文案和发行文档有不同目的。

## 六、真机验收需要新增证据，不能复制工具结果

开发工具观察过线上阅读、目录、本机测试账号、投稿与深色主题；真实微信登录专项也成功。相册上传、原生分享接收、真机键盘和弱网恢复没有全部人工验收。

正式阶段应固定设备、系统、基础库、网络与数据样本，检查冷启动、后台恢复、长文、图片、权限拒绝和账号切换。设备性能不同，工具里顺滑不等于真机都顺滑。

可以先把这份矩阵写下来，让“还没验”与“已验收”一目了然：

| 真机项 | 本轮状态 | 正式阶段动作 |
|---|---|---|
| 冷启动与后台恢复 | 未全部人工验收 | 固定机型与系统逐项过 |
| 相册上传 | 未验收 | 真机授权与失败恢复 |
| 原生分享接收 | 未验收 | 跨账号接收链路 |
| 真机键盘 | 未验收 | 输入法与布局适配 |
| 弱网恢复 | 未验收 | 弱网注入与重试 |
| 深色主题 | 工具内观察 | 真机亮度与对比核对 |

包体也有不同口径。当前文件总量约 759 KB，不是平台上传包的正式统计。分包、加载与资源缓存要按真实产物和测量判断，不能把一个小数字写成“上架无压力”。

## 七、发布推进可以分成四个可审查节点

第一个节点核对资格与域名，明确能否进入发布流程；第二个核对数据与隐私，确认页面能力和说明一致；第三个执行真机与弱网矩阵，更新技术证据；第四个再做上传、审核、灰度与回滚准备。

| 节点 | 目标 | 产出物 |
|---|---|---|
| ① 资格与域名 | 明确能否进入发布流程 | 主体 / 类目 / 域名清单 |
| ② 数据与隐私 | 页面能力与说明一致 | 隐私声明与数据流对照 |
| ③ 真机与弱网 | 补真机技术证据 | 设备矩阵验收记录 |
| ④ 上传与发布 | 走完平台流程 | 审核、灰度与回滚预案 |

每个节点应留具体配置与结果，秘密只记录名称和注入方式。这样，发布被阻塞时可以知道缺什么，而不是重新怀疑已经验收的业务流程。

当前没有执行上传审核或正式发布，也没有给出平台通过保证。把未来步骤列出来，是为了让下一轮工作可计划，不是要求作者现在为演示额外购买服务或迁移部署。


## 八、演示交付也需要一份可复现交接

如果下一位协作者的工具没有关闭校验，他可能看到网络错误，然后误以为接口或请求层坏了。因此交接要同时提供导入入口、运行脚本、目标 API、AppID 来源与调试条件。

README 把这些写成可复制执行的命令，而不是散落在聊天里：

```sh
# 安装、类型检查、单元测试、构建
pnpm install --frozen-lockfile
pnpm typecheck
pnpm test
pnpm build:weapp
```

单元测试入口并不是直接跑源文件——它先用 esbuild 把测试用例打包，再交给 Node 自带 test runner：

```js
// taro-miniprogram/scripts/test.mjs（节选）
await build({
  entryPoints: ["test/core.test.ts"],
  outfile: ".test-build/core.test.cjs",
  bundle: true,
  platform: "node",
  format: "cjs",
  alias: { "@tarojs/taro": resolve("test/taro-mock.ts") },
});
execFileSync(process.execPath, ["--test", ".test-build/core.test.cjs"], { stdio: "inherit" });
```

隔离环境的集成测试则在启动前拉起一个只监听本机的真实后端，用临时数据库，结束后清理：

```js
// taro-miniprogram/scripts/integration.mjs（节选）
const server = spawn(process.execPath, [resolve(backend, "node_modules/tsx/dist/cli.mjs"), entry], {
  cwd: backend,
  env: {
    ...process.env,
    NODE_ENV: "test",
    DB_FILE: join(temp, "db.sqlite"),
    JWT_SECRET: "isolated-integration-only-key",
    PORT: "13997",
  },
  stdio: ["ignore", "pipe", "pipe"],
});
```

秘密只在后端，不随这份交接复制。前端能看到公开地址是正常的，能看到 AppSecret 则是部署边界出错。工具设置、源码配置与后端 Secret 应分别核对。

演示还要有数据边界。线上阅读使用真实文章，写操作验收优先在隔离环境，临时数据不污染已发布内容。真实微信认证因为需要平台 code，有独立线上专项，但它不要求顺便发表一篇测试文章。

## 九、给演示交付一个准确结论

本轮结论可以写成：在记录的开发工具与调试条件下，约定业务流程可运行；真实微信登录已专项验证；正式发行与未完成的真机矩阵另行推进。

这句话比“不能上架，所以不算完成”公平，也比“工具能跑，所以随时可上线”可信。相关证据见 [质量验证]({{LINK:M5-24}})，平台选择见 [小程序与 APP 取舍]({{LINK:M5-07}})。把目标说清楚，完成才有明确含义。
