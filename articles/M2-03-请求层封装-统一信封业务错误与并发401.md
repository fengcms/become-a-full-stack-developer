# 成为全栈·React 管理后台篇·请求层封装：统一信封、业务错误与并发 401

> 页面发请求并不难，难的是让所有页面面对成功、业务失败、令牌过期和网络异常时，做出一致且可恢复的反应。旋转刷新令牌再遇上首屏并发，这件事还会比想象中更麻烦。

![成为全栈·React 管理后台篇·请求层封装：统一信封、业务错误与并发 401](https://i-blog.csdnimg.cn/direct/a9cf62a6ca6a40af92da8f8154356839.png)

## 前言

管理后台刚开始写时，直接封一层 `fetch` 很容易：拼接 base URL，带上 token，非 200 就抛错。列表、表单、详情都能用，看着已经够了。

真正让我重新审视请求层的，是刷新令牌旋转和首屏并发撞在了一起。仪表盘加载时，统计、文章、评论可能同时请求；若 access token 刚好过期，它们会一起收到 401。每个请求若各自刷新一次，第一个刷新请求已经作废旧 refresh token，后面的刷新请求再拿旧值访问，就会被后端当成失效甚至重放。用户什么都没做，却被踢回登录页。

各位看官，这类 bug 手工点页面很难复现。它说明请求层不能只做“少写几遍 fetch”，还必须维护协议和恢复秩序。

## 本文要解决什么

- HTTP 成功为什么不等于业务成功。
- 网络错误、业务错误和 401 恢复怎样统一。
- 多个并发 401 为什么只能共享一次刷新任务。
- 请求层应该负责到哪里，哪些反馈仍应留给页面。

前置阅读：[统一响应结构](https://blog.csdn.net/fungleo/article/details/164289071)、[认证方案：JWT 还是 Session](https://blog.csdn.net/fungleo/article/details/164363240)

## 先把后端协议翻译成前端结果

这个项目的接口统一返回信封：

```ts
export interface ApiResponse<T = unknown> {
  code: ErrorCode
  message: string
  data?: T
  requestId: string
  timestamp: string
}
```

这里存在两层成功：HTTP 2xx 表示请求被服务器正常处理；`code === 0` 才表示业务成功。后端完全可能返回 HTTP 400 + 参数错误，也可能因网关或历史兼容出现 HTTP 200 + 非零业务码。页面若只看 `response.ok`，会把后一种失败当成功。

请求核心因此按固定顺序处理：

```text
拼接 URL 与 query
  → 注入 Authorization
  → fetch
  → 解析响应文本/JSON
  → 识别可恢复 401
  → 校验 HTTP 状态与业务 code
  → 成功只返回 data
```

![请求流水线](https://i-blog.csdnimg.cn/direct/ce6d8c8b21034e71b4954a80a0d8c41d.png)

页面最后拿到的不是整个信封，而是已经收窄的 `T`；失败则拿到统一的 `ApiError`，其中保留业务码、HTTP 状态、字段错误和 `requestId`。这样页面只判断“这次业务怎样恢复”，不用重复理解传输协议。

## 错误不是一句 message

我不建议把所有失败都变成 `throw new Error(message)`。至少要保留三类信息：

| 信息 | 用途 |
| --- | --- |
| HTTP status | 区分网络协议层失败，如 401、404、500 |
| 业务 code | 区分令牌过期、账号禁用、字段冲突等领域原因 |
| requestId | 让前后端能追同一次请求 |

参数校验还可能带字段列表。表单页应该把“标题不能为空”落到标题字段，而不是统一弹一条“请求失败”。请求层负责把响应转换成稳定错误对象；页面负责决定是字段提示、内联错误页还是 toast。

这条边界很重要。若请求层对任何错误都 toast，批量删除十条数据可能弹十次；若页面完全自己解析，又会出现每个页面说法不一样。当前实现把协议解析放底层，把面向任务的反馈放在 hooks 或页面。

## 真实网络不会永远返回 JSON

请求封装还有两条不显眼、但上线后很实用的兜底。第一条是网络调用本身可能失败：断网、DNS、代理没有启动时，`fetch` 连 Response 都拿不到。这里统一转换成 `status: 0` 的 `ApiError`，并给用户“检查网络后重试”，而不是把浏览器的 `Failed to fetch` 原样扔到界面。

第二条是响应可能根本不是 JSON。Nginx 超时页、Cloudflare 错误页通常返回 HTML；若直接 `response.json()`，页面只能得到一个语法异常，看不出原始 HTTP 状态。当前实现先读 text，再尝试解析，失败时保留状态码和前 200 个字符用于定位。

请求体也分两类。普通对象由底层序列化并设置 `Content-Type: application/json`；`FormData` 必须原样交给浏览器，让浏览器自动生成带 boundary 的 Content-Type。手工写成 `multipart/form-data` 反而会漏掉边界，上传接口无法解析。这些都属于协议细节，放在请求层解决一次，页面上传头像和文章封面时就不需要重复记忆。

## 并发 401 的错误写法

最直觉的恢复逻辑大概是：

```ts
if (response.status === 401) {
  await refreshToken()
  return request(path, options)
}
```

单请求没有问题，并发时却会变成：

```text
请求 A ─401─→ refresh(old) ─→ new token ─→ 重放成功
请求 B ─401─→ refresh(old) ─→ 旧令牌已失效 ─→ 登出
请求 C ─401─→ refresh(old) ─→ 旧令牌已失效 ─→ 登出
```

真正需要互斥的不是业务请求，而是“正在进行的刷新任务”。项目使用模块级 Promise 作为锁：

```ts
let refreshInFlight: Promise<string> | null = null

const refreshOnce = (): Promise<string> => {
  if (!refreshInFlight) {
    refreshInFlight = performRefresh().finally(() => {
      refreshInFlight = null
    })
  }
  return refreshInFlight
}
```

第一个 401 创建刷新 Promise，后续 401 直接等待同一个 Promise。刷新成功后，新会话写入内存，所有原请求分别重放；刷新失败才统一清空会话。

![并发刷新时序](https://i-blog.csdnimg.cn/direct/02635c0b001c442c92a83f75398cc896.png)

这里没有引入队列库或全局事件总线。浏览器单实例内，一个共享 Promise 就足以表达“同一时刻只有一个刷新”。够用，而且行为很好测。

## 两个防递归细节

刷新接口自己若返回 401，不能再次触发刷新，否则会无限递归。因此内部请求带 `_isRefresh` 标记，明确跳过恢复逻辑。

业务请求也只能重放一次。若刷新后仍然 401，说明问题不再是普通过期，可能是账号禁用、权限改变或新令牌无效。`_retried` 会阻止第二次重放，并进入强制登出。

不同 401 也不能一概刷新。后端业务码区分 token 可刷新失效、令牌缺失和账号禁用。账号禁用时再刷没有意义，应该清空会话并告诉外层跳转。**恢复机制必须服从业务语义，不能只看 HTTP status。**

## 用测试撑开那个很窄的窗口

并发 bug 的麻烦在于，手工操作通常太慢。测试里让刷新接口故意延迟 20ms，再同时发三个请求：

```ts
const results = await Promise.all([
  request<{ ok: boolean }>('/a'),
  request<{ ok: boolean }>('/b'),
  request<{ ok: boolean }>('/c'),
])

expect(refreshCalls).toBe(1)
expect(results).toEqual([{ ok: true }, { ok: true }, { ok: true }])
```

20ms 不是业务参数，只是把并发窗口撑开，让后两个请求到达时，第一个刷新仍在进行。这个断言钉住的不是实现细节，而是系统不变量：无论同时来多少个可恢复 401，只能消费一次 refresh token。

当前测试还确认刷新后的 access token 写回内存，并且不会走 localStorage。令牌为何这样存、页面刷新怎样恢复，我们留给 M2-07；请求层在这里只保证拿到新会话后正确重放。

测试没有把实现写死成“必须存在某个变量名”。它观察三个外部结果：刷新端点只调用一次、三个业务请求最终都成功、新令牌进入会话。以后即使把 Promise 锁换成别的协调方式，只要这三条行为不变，测试仍然成立。对并发逻辑而言，守行为比守代码形状更耐用。

## 适用边界

如果后端使用不会旋转、可重复使用的 refresh token，多次刷新未必立刻失败，但仍会造成请求风暴和状态覆盖，共享任务依然有价值。

如果应用有多个浏览器标签页，模块级 Promise 只能协调当前标签。跨标签需要 BroadcastChannel 或服务端容忍策略，本项目没有为了这个低频场景增加复杂度。若业务要求同账号多标签强一致，就应该把它列为独立需求，而不是假装当前锁覆盖了整个浏览器。

## 小结

一个靠谱的请求层做三件事：把后端信封翻译成稳定结果，把错误保留成可判断的信息，再把可恢复的 401 排成正确顺序。

我认为这里最值得带走的不是某段封装代码，而是那个共享 Promise：并发恢复场景里，大家需要共享的是“正在做的工作”，不是共享一个布尔值。各位看官遇到重复刷新、重复初始化、重复加载配置时，都可以先问问自己：能不能让调用方等待同一个 Promise？
