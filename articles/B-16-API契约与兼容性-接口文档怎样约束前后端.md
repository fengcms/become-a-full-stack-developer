# 成为全栈·基础补充·API 契约与兼容性：接口文档怎样约束前后端

> 接口文档不只是给人看的说明书。当前后端、网页、管理后台、App 和小程序分别由不同代码实现时，契约是它们共同遵守的边界，也是判断一次改动会不会破坏现有用户的依据。

{{IMG:B-16-封面}}

## 前言：接口“能调通”为什么还不够

前端开发中最常见的接口协作方式，是先让后端返回一个 JSON，再由前端按需要读取字段。项目很小时，这样确实快；但接口一旦被多个端使用，字段类型、错误格式、默认分页、身份要求和空值行为都会变成隐形约定。一个端把 `null` 当成“清空”，另一个端把它当成“没有提交”，看起来只是一个字段，最终却可能让用户资料被意外清空。

我们这个内容系统先后有 Node 后端、网页前台、管理后台、Flutter App 和 Taro 小程序，后来又用 Go 实现同一套后端。它们共享冻结的 OpenAPI 契约 1.12.0：54 个路径、68 个操作。Go 重写阶段没有因为新实现方便就改接口，而是把契约作为对照基线，再用实际客户端请求和差分测试找出不一致。这个过程说明：契约不是开发早期的一张表，而是贯穿实现、测试和升级的产品资产。

## 一、契约写的是什么

以“获取文章列表”为例，完整契约至少需要回答：请求方法和路径是什么；哪些查询参数可选、类型与默认值是什么；是否需要登录；成功响应有哪些字段和类型；失败时 HTTP 状态码、业务码与错误详情是什么；列表顺序是否稳定；分页边界怎么计算。

| 契约部分 | 例子 | 它避免的问题 |
|---|---|---|
| 路径与方法 | `GET /articles` | 前后端各自猜接口地址 |
| 参数 | `page`、`pageSize`、`keyword` | 数字字符串、默认值和上限不一致 |
| 身份要求 | 匿名可读，会员可访问个人资源 | 前端误以为隐藏按钮就等于权限保护 |
| 响应结构 | `{ code, message, data }` | 某端直接读 `response.article`，另一个读 `response.data` |
| 错误语义 | `401` 与业务码、字段错误列表 | 只处理“请求失败”，无法给出有用提示 |
| 空值与存在性 | 字段缺失、`null`、`0` 分别定义 | 更新时清空、保留和写入零值互相混淆 |

OpenAPI 可以把其中许多内容写成机器可读格式。它可以描述路径、参数、请求体、响应 schema、安全方案和复用组件，让文档、类型生成与校验共享一份事实来源。但它不会自动替团队做产品决策：`PUT` 是完整替换还是局部更新？空数组是否有效？某项角色检查是必须还是可选？这些仍要由人根据产品规则确定，再写进契约。

## 二、契约优先不是“先写 YAML 就万事大吉”

契约优先的关键不是文件格式，而是变更顺序。新增接口时先定义消费者可观察到的行为，再实现服务端和客户端；修改字段时先分析已有消费者，再决定兼容的迁移路径。契约要能被检查，变更才不容易悄悄漂移。

一个实用流程可以这样走：

1. 写清用户场景和业务状态变化，例如“审核发布成功后，文章公开且作者收到通知”。
2. 在契约中定义请求、身份、成功响应、错误响应和边界值。
3. 对契约做结构校验，并检查新旧版本差异。
4. 生成或更新客户端类型，编译依赖该接口的调用方。
5. 实现服务端，并用契约测试请求和响应。
6. 回归所有已支持客户端，尤其检查字段默认值、错误处理和会话刷新。

这不意味着任何小改动都要生成一套复杂 SDK。小项目可以手写类型，但类型仍应从唯一契约校对；关键是不能让接口事实同时散落在后端注释、前端类型和某份过时的 Wiki 中。

## 三、字段缺失、null 和零值必须分开

考虑个人资料更新：

```json
{}
```

```json
{"bio": null}
```

```json
{"bio": ""}
```

这三个请求是否等价，不能靠语言的默认值猜。它们可能分别表示“不修改简介”“清空简介”“把简介设为空字符串”。如果服务端把 JSON 解码到一个普通 struct，缺失字段和显式零值可能落到同一个内存状态；如果更新语句又忽略空字符串，最终行为会进一步偏离契约。

因此契约需要写清楚字段是否必填、是否可空、空字符串是否允许，以及每种状态的业务含义。实现则要保存字段是否出现的信息。Go 重写中，更新 DTO 不能只依赖一个 `*string` 同时表达“没传”和“传 null”，于是保留存在标记，再由业务服务做白名单映射。Node、TypeScript 和 Flutter 也各自有不同的表达方法，契约提供的是共同语义，而不是强迫所有语言使用相同的数据结构。

## 四、兼容性要站在消费者一侧判断

“新增可选字段是兼容的”常常成立，但不是无条件成立。严格解析未知字段的消费者可能失败；新增的枚举值可能击穿写死分支的客户端；改变默认排序会让翻页重复或漏项；将错误响应从 401 改成 200 业务失败，也会让统一请求层错误处理失效。

评估一项接口变更时，可以逐一检查：

| 变更 | 通常风险 | 还需要检查 |
|---|---|---|
| 响应新增字段 | 较低 | 客户端是否严格拒绝未知字段、生成模型是否完整解析 |
| 删除或改名字段 | 高 | 所有客户端和历史数据展示都可能依赖它 |
| 放宽请求可选项 | 中 | 服务端是否兼容旧客户端，默认值是否一致 |
| 新增枚举值 | 中到高 | 客户端 switch 是否有未知值兜底 |
| 改分页默认值 | 高 | 数据量、重复项、客户端默认请求是否变化 |
| 改错误码/状态码 | 高 | 登录刷新、权限提示和重试策略可能被触发 |

兼容不是只比较 JSON 字段。它还包括状态码、Cookie 属性、身份边界、排序、计数、事务失败后的数据库状态和重复请求结果。客户端可能完全不关心某个内部字段，却高度依赖一次请求失败后 refresh token 是否仍有效。

## 五、用证据处理“契约和旧实现不一致”

旧实现不一定是契约的权威副本。项目 Go 重写时，契约搜索默认 pageSize 是 10，而旧 Node 通用分页默认 20；Go 依冻结契约采用 10。发布通知也是产品流程要求，但 Node 历史实现没有生成这类通知，Go 按产品规则补齐。差分报告将它们作为明确差异记录，并没有通过放宽比较器让结果变绿。

遇到不一致时，先固定双方版本和输入，再检查原始请求、响应、契约、产品说明、调用方代码与数据库后置状态。随后判断这是 Go 的缺陷、旧实现的历史偏差，还是契约本身需要一个经过评审的新版本。最终结论要留下可复核的原因，不能只在测试脚本里写“忽略这个字段”。

## 小结：契约是团队协作时可以验证的承诺

接口契约把端点、类型、权限、错误和更新语义从口头约定变成可检查的边界。它既不是代码生成器，也不是不会变化的石碑。契约要随着产品演进，但每次变更都应先理解消费者，再用版本、测试和迁移策略保护已有用户。
