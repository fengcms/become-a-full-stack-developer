# 成为全栈·基础补充·API 契约与兼容性：接口文档怎样约束前后端

我这个专栏有个被别人问过很多次的问题：**"你写这么多文档，接口文档不就在那儿吗？为什么还要专门写一篇讲它？"**

后来我把这个项目从 Node 换写成 Go，答案就出来了。

Go 那一轮，68 个接口全部重写。**我没有让任何一端"方便一点"**——但如果只靠一份 YAML 文件，我根本没有办法确认"方便一点"这件事到底发生了没有。

而真正帮我守住底线的，是一个**24 条断言的门禁脚本**。这篇讲它到底在防什么。

## "能调通"是最弱的验收标准

先说这个问题，因为它决定了后面所有的做法。

前端和后端联调时的默认流程是：后端返回一个 JSON，前端按需要读字段。**项目小的时候这确实最快。**

但接口一旦被多个端使用，一些东西会悄悄变成"隐形约定"：

- 这个 `null` 是"清空"还是"没提交"？
- `page` 传 0 会怎样，传 10000 呢？
- 403 和 404 对这个页面来说有区别吗？

举个我遇到过的真实例子：用户资料接口有个 `nickname` 字段，Flutter 端把 `null` 理解成"清空昵称"，而管理后台把 `null` 理解成"这次没改昵称，保持原值"。

**两边代码都"正确"，功能测试全绿**——只有在"用户在小程序清空昵称、然后去管理后台看"这个跨端场景下，才会发现昵称被清空了。

而这个 bug 极难复现，因为**你得先知道两端的语义不一致，才能构造出触发它的操作**。

所以契约要解决的不是"文档好不好看"，而是**"这些语义有没有被写下来，并且能被检查"**。

## 一份契约必须回答的六件事

以"获取文章列表"为例，契约至少要回答：

| 契约部分 | 本项目的写法 | 它避免的问题 |
|---|---|---|
| 路径与方法 | `GET /articles` | 前后端各自猜地址 |
| 参数 | `page`、`pageSize`、`keyword`、`sort` | 默认值和上限不一致 |
| 身份要求 | 匿名可读 / 需登录 / 需角色 | 以为隐藏按钮就等于权限 |
| 响应结构 | `{ code, message, data }` | 一端读 `response.article` 另一端读 `response.data` |
| 错误语义 | HTTP 状态码 + 业务码 + 字段错误 | 只处理"请求失败" |
| 空值与存在性 | 缺失 / `null` / `0` 分别定义 | 清空、保留、零值互相混淆 |

最后一行是上面那个 bug 的根源。**"字段缺失"、"值为 null"、"值为 0"是三件事**，而 JSON 里前两者很容易混淆——`{"nickname": null}` 和 `{}` 在某些解析器眼里是一样的。

而 OpenAPI 能帮你把它写成机器可读的：

```yaml
PatchUser:
  type: object
  properties:
    nickname:
      type: string
      nullable: true      # ← 显式声明"可以是 null"
      maxLength: 32
```

**而 `nullable: true` 写下来之后，它就成了可以检查的东西**——而"不写下来"，它就只是一个约定。

也要说清楚 OpenAPI 不能做什么：它**不会替你做产品决策**。`PUT` 是完整替换还是局部更新？空数组算不算有效？某个角色检查是必须还是可选？

**这些仍然要人根据产品规则决定，再写进契约。** 契约能做的是"逼你把它写下来"，不是"替你决定"。

## 契约优先的关键不是先写 YAML

先纠正一个常见误解：**契约优先不等于"先建一个 YAML 文件"。**

真正的关键是**变更顺序**：

```text
1. 写清用户场景和业务状态变化
2. 在契约中定义请求、身份、成功响应、错误响应和边界值
3. 做结构校验 + 新旧版本差异检查
4. 生成客户端类型，编译依赖方
5. 实现服务端，用契约测试请求与响应
6. 回归所有已支持客户端
```

第 3 步和第 6 步是这个专栏特有的——因为我们有五六个端，**"契约改了"和"消费者跟着改了"是两件事，必须分别验证**。

而第 6 步里最容易被漏掉的是**跨端的语义一致性**：不是"这个端能不能跑"，而是"两个端对同一个字段的理解是不是一样"。

## 契约能不能检查？能，这是最有用的一点

前面说契约要"能被检查"，那具体怎么检查？

这个项目的做法是一个门禁脚本 `docs/api/check_contract.py`，**24 条断言，分成 A~G 七组**。

它不是什么智能工具，**它就是一堆断言**。但正是这些断言，把"契约应该怎样"变成了可执行的东西。

看几条实际的断言文案：

| 断言 | 它在防什么 |
|---|---|
| 全部 47 个 `$ref` 均可解析 | 引用了不存在的 schema，生成器直接崩 |
| 全部 68 个操作均有 operationId 且全局唯一 | 代码生成时方法名冲突 |
| 全部 schema 均被端点可达引用，**无孤儿实体** | 写了 20 个 schema，只有 3 个真被用到 |
| 评论三态 `approved/rejected/reviewing` 均有端点可写入 | 枚举里有个状态，但没有任何接口能写进去 |
| Sort 已枚举 N 个合法组合，默认 X | 排序参数传什么值合法，只存在于口头约定 |
| 全部 N 种结构化错误码均落在 ErrorCode 枚举内 | 契约里写了 4003，后端代码里根本没有这个码 |
| ErrorCode 枚举全部非零 | 某个码被定义成 0，而 0 是"成功" |
| N 个需登录端点均声明 401 | 忘了声明，后端不返回它，前端就不知道怎么处理 |
| N 个需登录端点均声明 `x-authz.minRole` | **授权要求只存在于口头** |
| `ownerOverride.param` 均指向真实 path 参数 | 归属校验声明了，但指向一个不存在的参数 |

**"无孤儿实体"和"三态均有端点可写入"这两条，我认为是最有价值的。**

它们防的不是"写错"，而是**"写了一半"**——

你在 schema 里定义了 `CommentStatus`，包含三个值。但你有没有真的写一个接口能让评论进入 `reviewing` 状态？如果没有，**那个状态就是永远到不了的**。

而这类问题**人工 review 极难发现**，因为它是"存在但没被使用"，不是"缺失"。契约文件读起来很完整，缺陷在里面是不会显形的。

## 机器化之后，权限这件事才有了着落

M0-05 讲契约先行的时候，权限部分只能写成一段文字：**"只有作者或管理员能修改文章"**。

到了五端时代，这段文字出了一个问题：**谁来实现它？六个端，六份代码。**

所以契约里加了 `x-authz`：

```yaml
x-authz:
  minRole: member
  ownerOverride:
    param: id
    ownerField: authorId
```

这行的意思是：**需要 member 角色，但如果 URL 里的 `id` 属于当前用户本人，则放行。**

它的价值不在于表达得多简洁，而在于**它可以被检查**：

- `minRole` 取值必须是 `member`/`editor`/`admin` 之一
- `ownerOverride.param` 必须指向这个操作真实存在的 path 参数
- `ownerOverride.ownerField` 必须指向主实体真实的归属字段

**第三条尤其有用。** 我可以想象一个很自然的错误：某个端点声明 `ownerField: userId`，但那个 schema 里根本没有 `userId` 字段。**声明看起来完全合理，只有对照真实 schema 才知道它是空的。**

契约里 `x-authz` 的写法有两种，这在无意中造成过一次不一致。真实片段：

```yaml
    post:
      operationId: logout
      x-authz:
        minRole: member
      tags: [Auth]
      summary: 登出，作废刷新令牌
```

而另一个端点是压缩写法：

```yaml
      tags: [Auth]
      summary: 微信新会员一次性设置本地登录账号
      x-authz: {minRole: member}
```

**两种写法在 YAML 里完全等价，但它们让"这条端点到底有没有 `x-authz`"变成了一个需要用正则去解析 YAML 的问题。**

现在当然不是了——脚本解析 YAML。但在我第一次写检查的时候是真的。而这个故事想说明的是：

> **把一个本来可以归一的东西写成多种形式，你就要为它写一个更复杂的检查。**

我们最后统一成了多行写法，理由不是"多行更规范"，而是**多行形式在 diff 里更明显**——`x-authz: {minRole: member}` 整行改动，而多行形式的改动会单独占一行。

**一个纯格式的选择，价值在于它让 diff 更可读。** 这听起来是小事，直到某次有人改错而 review 没看出来。

而这个项目的 Go 重写里，**权限实现是靠这个标记对照检查的**——六份实现各自的权限逻辑可能写法不同，但它们声明要遵守的是同一份契约。

顺带说一个我改过的坑：最初用的是 `x-required-roles` 和 `x-owner-resource` 两个字段，后来重构成了统一的 `x-authz`。**因为两个字段的组合会产生"只有一个"的非法状态**——声明了角色但没声明归属，或者反过来。**把维度合并到一个对象里，非法组合就表达不了了。**

## 兼容性：新增字段不等于安全

讲兼容性要先说一个反直觉的结论：**在契约里加一个可选响应字段，不是天然安全的。**

听起来很奇怪——可选字段，旧客户端读不到它，应该没事。

但有两类客户端会出问题：

**严格解析器。** 某些 JSON 解析库在遇到未知字段时会抛错（尤其那些开了严格模式的序列化框架）。**这不是假设，是真实存在的。**

**生成类型。** 如果旧客户端的类型定义里没有这个字段，而新响应里有——**当客户端把响应原样 round-trip 回去时，这个字段可能被丢掉或者被拒绝。**

所以判断"这次改动是否安全"，**不能只看契约 diff，还要看真实的消费者怎么解析**。这是我在 Go 重写那轮踩过的坑：契约上完全兼容，但某个端的解析器对新字段有反应。

而真正的兼容做法是这样的：

| 改动 | 兼容性 | 需要做什么 |
|---|---|---|
| 新增可选响应字段 | 条件兼容 | 检查所有消费者的解析器 |
| 新增可选请求参数 | 通常兼容 | 确认默认值不改变旧行为 |
| 新增必填请求参数 | **不兼容** | 必须先部署支持它的服务端 |
| 字段类型收窄 | **不兼容** | 新建字段 + 双写 + 迁移 |
| 删除字段 | **不兼容** | 先废弃（停止输出），等消费者下线后再删 |

第三行值得强调：**新增必填请求参数意味着必须先部署服务端。** 因为老客户端还在请求，而它不传这个参数——服务端如果不做兜底就会 400。

**这是发布顺序问题，不是兼容性问题。** 但它在 review 时经常被当成"兼容的改动"而跳过。

## 版本号：兼容不等于可以不改

这个专栏的契约从 1.0 一路到 1.12。**每次增补都会升版本**——包括 M1-32 那次只加了三处。

而升版本的代价是**所有消费者都要确认一次**。所以我在考虑是否要加一个破坏性变更时，会先算这个成本。

判断标准很简单：

> 如果这次改动会让任何一个已支持的端"必须改代码"，它就是破坏性变更，不管多小。

而"让某个端必须改代码"的范围比想象中大——**改了默认值也是**。比如 `pageSize` 默认从 12 变成 20，旧客户端不传时会拿到 20 条而不是 12 条，**它不会报错，但它的布局会崩**。

这类"不报错但行为变了"的改动，**比直接报错难发现得多**，因为它不会让任何测试变红。

## 一条我一开始想省掉的事

契约门禁这个脚本，最初只有 6 条断言，而且**没有立刻加**——我打算等"真正出问题了"再加。

结果第一次出问题的就是那 6 条没覆盖的：**我给 `Comment` 加了一个新状态 `hidden`，但没有任何端点能让评论进入这个状态。**

它在代码里完全正常：schema 有这个枚举值，TypeScript 类型有它，前端的 `switch` 也加了分支处理它。**所有测试都通过。**

而它的实际效果是：**`hidden` 是一个永远到不了的状态**，它对应的那个 `switch` 分支是死代码。

**这个问题没有任何 review 会发现**——因为它的每个部分都是"正确"的。缺陷在于**部分之间的组合**：状态存在，但没路径能到达它。

而加断言的过程也让我意外：**在写"三态均有端点可写入"这条检查时，我又发现了另一个类似的问题**——`Article` 的一个 `sort` 枚举值定义了但没有端点支持。

**所以这个门禁不只是防未来的错，它在写的过程中就抓出了两个现存的错。** 这是我没想到的。

顺便说，那些"防御性代码"（比如处理 `hidden` 状态的分支）在当时写的时候觉得"以防万一"，但**它掩盖了一个事实：没人知道这个状态怎么产生。** 而一个没人知道怎么产生的状态，最终要么被删掉，要么一直误导读代码的人。

## 小结

这篇讲的其实是一件事：**契约的价值不在于它写得多完整，而在于它有多少内容是"能被检查的"。**

一份纯描述性的契约（"这里返回文章列表，字段是 id、title、slug"）读起来很清楚，但它保证不了任何事。

而一份能被检查的契约，能保证：

- 引用的 schema 都存在
- 没有永远到不了的状态
- 每个需登录端点都声明了授权要求
- 归属校验指向真实的字段
- 破坏性变更必须升版本

而版本判断本身也可以机器化。这是 Go 重写那轮用过的对比思路——**不是读 diff 靠眼睛，而是把新旧两个 spec 都加载进内存，逐项对比**：

```python
# 概念示意：同一路径下比较 required 集合
def breaking_changes(old, new):
    out = []
    for path, item in (new.get("paths") or {}).items():
        old_item = ((old.get("paths") or {}).get(path) or {})
        for method, op in item.items():
            if method not in ("get", "post", "put", "patch", "delete"):
                continue
            old_op = old_item.get(method, {})
            new_req = {p["name"] for p in op.get("parameters", [])
                       if p.get("required")}
            old_req = {p["name"] for p in old_op.get("parameters", [])
                       if p.get("required")}
            # 新增必填参数 = 破坏性
            added = new_req - old_req
            if added:
                out.append((path, method, "新增必填参数", sorted(added)))
    return out
```

**注意它只看"新增必填参数"这一类**，因为那是这个专栏里最常见的破坏性变更。而"删除响应字段""收窄字段类型"那几类更复杂——**要判断它们需要理解 schema 的引用关系**，而那已经接近实现一个完整的语义分析器了。

所以现在的做法是**先覆盖最容易判断的那一类，剩下的靠 code review**。

**这不是"不够完善"，而是"知道自己的边界在哪"。** 一个只覆盖 60% 破坏性变更的脚本，比一个假装覆盖 100% 但偶尔误报从而被人忽略的脚本更有用——**因为后者会训练出"忽略这个工具"的习惯。**



**最后那一条尤其重要，因为它把"要不要升版本"从一个判断题变成了规则题。** 而规则的好处是不依赖执行者当天的心情。

下一篇讲测试分层——**它和这篇是同一套思路的下半段**：契约保证"应该怎样"，测试保证"真的是这样"。而我在这个项目里踩过的坑是，测试全绿但功能是坏的。
