# 成为全栈·Next.js 网站前台篇·服务端组件与客户端组件：边界画错，整棵树都会变重

> `'use client'` 只有两个单词，它划定的却是服务端与浏览器之间的模块边界。放在哪里，决定了多少 JavaScript 要送给用户。

{{IMG:M3-02-封面}}

## 前言

我刚开始拆这个网站时，遇到一个很诱人的方案：顶层 `Providers` 需要恢复会话，那就给整个布局加上 `'use client'`，子组件里什么 Hook 都能用，写起来像熟悉的 React SPA。

功能是好写了，代价却被藏了起来。页头、页脚、文章列表、Markdown 正文，原本都可以只在服务端工作；一旦它们被拉进客户端模块图，浏览器就需要下载、解析和执行更多 JavaScript。

所以这篇我想证明一件事：**Client Component 应该由真实交互需求定位，不应该由开发方便程度向上扩散。**

## 先澄清一个常见误解

`'use client'` 不表示“这个组件只在浏览器生成 HTML”。Client Component 的首次页面加载仍可参与服务端预渲染，但它的代码会进入客户端 JavaScript，并在浏览器里完成 hydration。

Server Component 与 Client Component 的核心差别更接近下表：

| 能力 | Server Component | Client Component |
| --- | --- | --- |
| 直接读取服务端环境变量 | 可以 | 不可以暴露私密变量 |
| 直接异步获取公开内容 | 适合 | 通常要等浏览器请求 |
| `useState` / `useEffect` | 不可用 | 可用 |
| DOM、localStorage、浏览器事件 | 不可用 | 可用 |
| 组件代码进入客户端 bundle | 不需要 | 需要 |
| 向客户端传入 props | — | 必须可序列化 |

当我们把文章正文保留为 Server Component，用户依然能在页面里点赞、查看目录和记录阅读历史。做法不是把整篇文章变成客户端组件，而是将互动拆成小岛。

## 看看文章详情页的切法

当前文章页由 `app/articles/[slug]/page.tsx` 在服务端完成主要工作：

```tsx
const Page = async ({ params }: Props) => {
  const article = await load((await params).slug)
  const { body, headings } = renderMarkdown(article.content)

  return (
    <>
      <header className="articlehead">...</header>
      {body}
      <Interactions id={article.id} count={article.likeCount || 0} />
      <Comments id={article.id} />
      <ReadingTracker id={article.id} />
    </>
  )
}
```

`body` 是服务端已经解析好的 Markdown 内容。只有下面三块进入客户端：

- `Interactions`：读取会员状态，处理点赞和收藏。
- `Comments`：加载评论、回复、删除与错误恢复。
- `ReadingTracker`：在浏览器中记录阅读历史。

{{IMG:M3-02-交互岛}}

这种结构的好处是，即使会员请求失败，文章标题、正文、面包屑和相关阅读仍然在。核心内容与互动能力不再是一个同生共死的客户端页面。

## `'use client'` 标记的是模块边界

假设我们给 `ArticlePage` 本身加上 `'use client'`，它静态 import 的组件和工具就会被纳入客户端模块图。问题并不只是文件多了一行指令，而是边界上移了。

我更愿意按以下顺序判断：

1. 这块内容是否需要点击、输入、浏览器 API 或持续的本地状态？
2. 如果需要，可否把交互拆到叶子节点？
3. 服务端是否可以先把首屏数据作为可序列化 props 传进去？
4. 客户端组件失败时，核心阅读任务是否仍然成立？

这比简单数 `'use client'` 的数量有用。一个复杂编辑器本来就应该是 Client Component，没必要为了指令少而硬拆。反过来，一个只因为手机菜单要开合，就把整个站点布局变成 Client Component 的方案，边界就太高了。

## Provider 可以是客户端，它的 children 不必被重写

当前根布局有一个客户端 `Providers`：

```tsx
const Layout = ({ children }: { children: React.ReactNode }) => (
  <html lang="zh-CN">
    <body>
      <Providers>
        <Header />
        <main id="main-content">{children}</main>
        <Footer />
      </Providers>
    </body>
  </html>
)
```

这里容易出现另一个误解：既然 `Providers` 是 Client Component，它包住的所有内容是不是都变成了客户端组件？

不是。Server Component 可以在服务端组合好，通过 `children` 这样的槽位传入 Client Component。真正需要避免的，是在客户端文件里静态 import 原本可留在服务端的大量模块。

`Providers` 处理会话恢复与 React Query 上下文，这是它的职责。页面的公开数据和 Markdown 不因此改由浏览器获取。

## 边界上还有一道可序列化约束

Server Component 把数据传给 Client Component 时，props 要能被 React 序列化。文章列表、数字、字符串和布尔值很自然；数据库连接、服务端函数、带有特殊原型的对象则不应跨过边界。

这个约束反而能帮我们看清数据所有权：服务端完成访问与整理，客户端拿到一份足够交互的初始快照。后续交互再通过 API 发生，而不是把服务端能力整个传给浏览器。

## “能传 children”不等于“可以随意穿越边界”

服务端组件作为 `children` 传入 Client Component，是因为它已经在服务端渲染树中完成组合。客户端容器拿到的是 React 可以协调的结果，不是服务端模块本身。如果在客户端文件中直接 import 一个读取 `API_ORIGIN`、文件系统或数据库的模块，就越过了边界。

对大型项目，可以用 `server-only` 与 `client-only` 标记模块意图，让错误 import 在构建阶段失败。当前项目主要靠目录责任和类型检查维持边界：

```text
lib/api/server.ts       只给 Server Component 使用
lib/request/*           给浏览器交互使用
components/article/*   按是否需要交互分界
```

边界还决定了错误在哪里爆发。如果 `API_ORIGIN` 缺失，公开内容应在服务端请求层给出配置错误，不应把 `undefined/api/v1` 这样的地址打包到浏览器后再失败。越早阻止边界泄漏，故障信息就越接近真正原因。

## 怎么验证边界确实有效

我们可以从三个方向检查：

- **功能**：禁用 JavaScript 或在 hydration 前查看首屏，文章标题与正文仍然存在。
- **依赖**：服务端专用配置不能出现在客户端 bundle，项目中只有 `NEXT_PUBLIC_` 变量允许公开。
- **失败隔离**：点赞或评论接口失败时，正文不应被替换为全页错误。

当前代码还没有用一个单独数字宣布“减少了多少 KB”。这种数字必须来自同一次生产构建的前后对比，不能凭组件数量猜。这里能确定的事实是边界位置和失败隔离，具体性能数据留到 M3-21 专门验证。

## 适用边界

管理后台、在线编辑器、实时看板这类高交互页面，Client Component 很可能是主体。不必为了追求一棵“纯 Server Component 树”而把状态拆得无法维护。

公开文章、商品详情、文档和落地页则往往相反：主任务是阅读，交互只占局部。此时把客户端边界压到按钮、菜单、表单和记录器，通常能得到更好的结构。

## 小结

Server Component 与 Client Component 不是两套组件库，而是同一棵页面树里的执行边界。真正的设计目标不是消灭 `'use client'`，而是让每个跨过边界的模块都有清楚理由。

各位看官，下次看到一个必须使用 Hook 的小功能，先别给整页加指令。先问它能不能成为叶子节点，这一问往往就是一棵轻量页面和一个大型 SPA 的分界线。
