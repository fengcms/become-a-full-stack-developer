## 前言：评论的“盖楼”展示不等于嵌套 API

一条评论可以回复另一条评论，数据模型通过 parentId 表达关系。用户会把评论区理解成楼中楼，但后端契约仍返回分页的平面评论列表。客户端把同一页记录按 parentId 组装成树状视觉结构；这两个层次可以同时成立。

后端负责确保评论对应已发布文章、回复父评论属于同一篇文章、公开列表只展示 approved、后台审核执行权限控制、删除父评论时不留下孤儿子评论。内容安全还要保持与 Node 侧 JavaScript 字符长度一致，避免把 Go 的 rune 数当成 UTF-16 长度。

本文说明 M6 评论服务如何在不修改响应协议的前提下支持盖楼显示，并介绍敏感词阈值、审核通知与递归整支删除。

## 一、回复关系由 parentId 表达

Create 先读取文章并确认它已发布，再读取当前登录用户。若请求包含 parentId，查询条件同时要求评论 ID 和相同 article_id。这样，用户不能把文章 A 的评论 ID 当成文章 B 下的回复父节点。

这段校验在代码里就是三个查询的先后顺序：

~~~go
// internal/comment/service.go（Create，节选）
// Create 只允许对公开文章评论，并校验回复属于同一篇文章。
func (s *Service) Create(ctx context.Context, key string, actor values.Actor, in values.Fields) (any, error) {
	db := s.DB.WithContext(ctx)
	a, err := article.Get(db, key)
	if err != nil {
		return nil, err
	}
	if a.Status != "published" {
		return nil, fault.New(fault.NotFound)
	}
	parent := in.Number("parentId")
	if parent != nil {
		var p model.Comment
		if err = db.Where("id = ? AND article_id = ?", *parent, a.ID).First(&p).Error; err != nil {
			return nil, err
		}
	}
	var u model.User
	if err = db.First(&u, actor.ID).Error; err != nil {
		return nil, err
	}
	content, status := moderate(in.String("content"), s.RejectRatio)
	c := model.Comment{
		ArticleID: a.ID,
		UserID:    u.ID,
		UserName:  values.Name(u.DisplayName, u.Username),
		ParentID:  parent,
		Content:   content,
		Status:    status,
		CreatedAt: s.Now().UnixMilli(),
	}
	err = db.Create(&c).Error
	return View(c), err
}
~~~

第一步 `article.Get(db, key)` 拿到文章，紧接着检查 `a.Status != "published"`，不是已发布就返回“不存在”。这里刻意不用“无权限”之类的错误，而是与匿名访问不存在的资源保持一致，避免通过错误码探测草稿的存在。

第二步是回复关系的核心：`Where("id = ? AND article_id = ?", *parent, a.ID)`。条件里同时有 `id` 和 `article_id`，所以拿别的文章的评论 ID 来挂接时查不到记录，请求直接失败。这不是在应用层比较两个字段，而是把“必须是同一篇文章”写进了查询条件本身。

第三步取用户信息，然后用 `values.Name` 组合出评论要展示的 `UserName`，落库一行 `model.Comment`。`status` 来自 `moderate`，不是请求里传的——评论状态由服务端判定，客户端无权指定。

Page 对公开调用只过滤当前文章且 status=approved 的记录，按 created_at、id 升序返回；后台列表可以按状态、articleId 筛选，并用管理排序。响应保留每一行的 parentId，分页结构仍是 list + pagination。前端应以 parentId 建索引，再把根评论和回复分组，遇到父节点不在当前页时按产品规则处理。

三种读取场景的差别就在范围与排序上：

| 调用场景 | 范围条件 | 排序 |
|---|---|---|
| 公开列表 | 指定文章且 `status = approved` | `created_at ASC, id ASC` |
| 未发布文章的预览 | 作者或管理员可读该文章全部状态 | `created_at ASC, id ASC` |
| 后台列表 | 可按 `status`、`articleId` 筛选 | `created_at DESC, id ASC` |

这三行对应 `Page` 里 `if !admin` 两个分支。公开路径先取文章、再判断可见性，最后把范围压到 `status = approved`；未发布文章的预览复用同一分支，只是放行作者本人和管理员。后台路径不加状态限制，而是把 `status` 与 `articleId` 当作可选筛选条件，默认排序也换成倒序——审核场景下最新的评论更值得先看。

排序里两个键同样重要：`created_at` 相同时按 `id` 兜底，避免同一毫秒内的几条评论在不同数据库上顺序不一致。

分页边界带来一个现实问题：父评论和子评论可能落在不同页。如果 UI 需要完整 thread，应在客户端补查父级上下文或以逐页流方式建立节点，而不能假设一个分页结果永远包含整棵评论树。后端新增嵌套返回会改变 API shape，客户端和契约都需共同升级；当前实现没有这么做。

未审核或拒绝评论不进入公开列表。作者或管理员查看未发布文章评论的管理预览需要符合对应权限。公开可见性和 parentId 结构彼此独立：有 parentId 不代表可以让被拒绝父评论及其内容泄漏。

## 二、敏感词判断为何要用 UTF-16 长度

JavaScript 的字符串 length 按 UTF-16 code unit 计数；Go 的 len(string) 是字节数，遍历 rune 则按 Unicode code point 计数。对含中文或 emoji 的文本，三种长度都可能不同。如果 Node 根据 UTF-16 计算敏感词占比，Go 使用字节数，就会在阈值附近作出不同审核决定。

M6 使用 unicode/utf16 将内容转成 UTF-16 单元计算总长度，也计算匹配片段的长度。当前敏感词包括中文与英文样例；匹配不区分大小写，命中片段按其 UTF-16 长度替换为星号。若敏感词覆盖比例大于 10%，状态设为 rejected；否则为 approved。空文本不会触发除零判断，实际输入长度和内容限制另由契约/传输边界控制。

判定函数本身不到三十行：

~~~go
// internal/comment/service.go（moderate）
// Moderate 以默认阈值判断敏感词，长度按 JavaScript UTF-16 规则计算。
func Moderate(raw string) (string, string) { return moderate(raw, 0.1) }
func moderate(raw string, threshold float64) (string, string) {
	content := raw
	hits := 0
	for _, word := range []string{
		"广告",
		"spam",
		"fuck",
		"shit",
		"垃圾",
		"代开发票",
	} {
		re := regexp.MustCompile("(?i)" + regexp.QuoteMeta(word))
		for _, m := range re.FindAllString(raw, -1) {
			hits += len(utf16.Encode([]rune(m)))
		}
		content = re.ReplaceAllStringFunc(content, func(m string) string {
			return strings.Repeat("*", len(utf16.Encode([]rune(m))))
		})
	}
	status := "approved"
	length := len(utf16.Encode([]rune(raw)))
	if length > 0 && float64(hits)/float64(length) > threshold {
		status = "rejected"
	}
	return content, status
}
~~~

函数返回两个值：替换星号后的正文和审核状态。长度计算统一走 `len(utf16.Encode([]rune(m)))`，把字符串先转成 rune 序列再编码成 UTF-16 单元——这正是 JavaScript `String.prototype.length` 的口径。如果用 `len(m)`，中文会按 3 字节计，用 `len([]rune(m))` 则按 1 个 code point 计，emoji 还会出现两者都不等于 2 的情况，任何一种都会让阈值附近的判断和 Node 版本产生分歧。

词表里的每项都经过 `regexp.QuoteMeta` 转义再拼上 `(?i)` 前缀，所以匹配不区分大小写。先按 `FindAllString(raw, -1)` 统计命中的 UTF-16 长度累加到 `hits`，再用 `ReplaceAllStringFunc` 把命中片段替换成等长的星号——星号个数与命中片段的 UTF-16 长度一致，替换后整体长度不变。

最后一行判断有两个前置条件：`length > 0` 挡住空文本，避免 `hits/length` 出现除零；比值用 `>` 而不是 `>=`，所以覆盖率恰好等于 10% 时仍是 approved。这两个细节都对应测试里的边界用例。

这里的实现只是为了保持现有 Node 行为，不是成熟的内容安全产品。固定词表存在误判和漏判，也不包含上下文识别、人工申诉或模型审核。教学文章应说明行为复刻，不把规则包装成推荐的通用审核方案。

Go 的 rune 截断也用于展示内容限制。数据库保存完整输入，View 将评论展示文本截到最多 2000 个 Unicode code point，拒绝理由最多 200 个。截断、审核存储和页面显示是三个不同规则，不能因为返回被截断就说原文已经丢弃。

展示截断由两个小函数完成：

~~~go
// internal/comment/service.go（节选）
func display(s string, n int) string {
	r := []rune(s)
	if len(r) > n {
		return string(r[:n-1]) + "…"
	}
	return s
}
func reasonView(s *string) *string {
	if s == nil {
		return nil
	}
	v := display(*s, 200)
	return &v
}
~~~

`display` 先把字符串转成 `[]rune` 再按 rune 数比较，所以“2000 个字符”指的是 2000 个 Unicode code point，而不是 2000 字节。超出时取前 `n-1` 个 rune 再补一个省略号，结果总长度正好是 `n`。

它返回新字符串，不改动原值：数据库里存的仍是完整正文，被裁掉的只是 `View` 生成响应时的展示文本。`reasonView` 多一层处理：`RejectedReason` 是 `*string`，为 nil 时保持 nil，让 JSON 里出现 `null` 而不是空字符串，这样契约中“没填理由”与“理由为空”不会混成同一个值。

## 三、状态变化和通知共享事务

Review 在事务内锁住评论，记录先前状态，再写入新状态和审核理由。首次从非 approved 改为 approved 时，调用 notification.Approved，将会员通知插入同一个 tx。通知写失败，审核状态一起回滚；重复审核已批准评论不会再次触发同一类通知。

审核逻辑整段如下：

~~~go
// internal/comment/service.go（Review，节选）
// Review 更新审核状态；首次转为 approved 时在同一事务写通知。
func (s *Service) Review(ctx context.Context, id int64, in values.Fields) (any, error) {
	var c model.Comment
	txErr := s.DB.WithContext(ctx).Transaction(func(tx *gorm.DB) error {
		if err := database.Lock(tx).First(&c, id).Error; err != nil {
			return err
		}
		previous := c.Status
		c.Status = in.String("status")
		if c.Status == "approved" {
			c.RejectedReason = nil
		} else if in.Has("reason") {
			c.RejectedReason = in.Text("reason")
		}
		if err := tx.Model(&c).
			Updates(map[string]any{
				"status":          c.Status,
				"rejected_reason": c.RejectedReason,
			}).Error; err != nil {
			return err
		}
		if previous != "approved" && c.Status == "approved" {
			return notification.Approved(tx, c, s.Now().UnixMilli())
		}
		return nil
	})
	return View(c), txErr
}
~~~

`database.Lock(tx).First(&c, id)` 先锁住这条评论，`previous := c.Status` 把改动前的状态存下来——后面判断要不要发通知就靠这个值。写入的两列是 `status` 和 `rejected_reason`。

理由字段的处理分两种情况：状态是 `approved` 时把 `RejectedReason` 置为 nil，清掉上一次的拒绝理由；状态不是 approved 且请求带了 `reason` 时才写入。这保证一条已批准的评论不会残留拒绝理由。

通知条件 `previous != "approved" && c.Status == "approved"` 要求同时满足“之前不是已批准”和“现在是已批准”。重复审核一条已批准的评论时，`previous` 已经是 `approved`，条件不成立，不会写第二行通知。通知通过 `notification.Approved(tx, ...)` 在同一个 `tx` 里插入，失败则整个事务回滚，状态改动也不落地。

审核拒绝时可以记录理由；批准时清除 rejectedReason。响应 View 将理由限制展示长度并保留 null 语义。管理员端和公开端的错误与可见性仍依据契约，service 不把数据库原始异常直接回给客户端。

和文章发布一样，这里数据库通知只是持久化的一条通知记录。若未来增加推送服务，需要独立处理外部发送失败和重复消费。SQL transaction 不能让手机 push 与数据库更新成为真正的原子事务。

## 四、删除一条评论要清理整支回复

外键指向 parent comment 时，直接删除父评论可能被数据库拒绝，或级联删除后端未预期的内容。M6 在事务里先锁定目标评论，验证操作者是评论作者或 editor/admin，然后读取同一 article 的评论集合，逐轮找出所有后代 ID。

整支删除分两段：先收集、后删除。

~~~go
// internal/comment/service.go（deleteBranchTx）
// deleteBranchTx 收集整支回复，再从叶子删除，尊重评论的自引用外键。
func deleteBranchTx(tx *gorm.DB, id int64, actor values.Actor) error {
	var c model.Comment
	if err := database.Lock(tx).First(&c, id).Error; err != nil {
		return err
	}
	if !actor.Allows("editor", c.UserID) {
		return fault.New(fault.Forbidden)
	}
	var rows []model.Comment
	if err := tx.Where("article_id = ?", c.ArticleID).Find(&rows).Error; err != nil {
		return err
	}
	ids := map[int64]bool{id: true}
	for changed := true; changed; {
		changed = false
		for _, r := range rows {
			if r.ParentID != nil && ids[*r.ParentID] && !ids[r.ID] {
				ids[r.ID] = true
				changed = true
			}
		}
	}
	// 子评论先删除，再删除父评论；不能靠关闭外键换取成功。
	for len(ids) > 0 {
		progress := false
		for child := range ids {
			hasChild := false
			for _, r := range rows {
				if r.ParentID != nil && *r.ParentID == child && ids[r.ID] {
					hasChild = true
					break
				}
			}
			if !hasChild {
				if err := tx.Delete(&model.Comment{}, child).Error; err != nil {
					return err
				}
				delete(ids, child)
				progress = true
			}
		}
		if !progress {
			return fault.New(fault.Conflict)
		}
	}
	return nil
}
~~~

第一段是收集。`ids` 从目标评论开始，然后在 `rows` 上反复扫描：只要某条评论的父节点已经在 `ids` 里，就把这条评论也加进去。外层用 `changed` 标记本轮是否新增了成员，直到一轮下来没有任何新增才停——这样多层回复会被逐层吸收进来。它只读同一篇文章的评论——`Where("article_id = ?", c.ArticleID)`，跨文章的 parentId 不在考虑范围内。

第二段是自底向上删除。每轮遍历 `ids`，对每个候选节点检查“它是否还有仍未删除的子节点”；没有子节点的就是当前叶子，删除并从集合里移除。一轮删完，上一层的节点变成新叶子，继续下一轮，最终删到最初的父评论。因为每轮只删没有子节点的项，自引用外键不会在删除过程中被违反。

`if !progress { return fault.New(fault.Conflict) }` 是死循环保险。正常情况下每轮至少能删掉一个叶子；如果一轮下来一个都没删掉却还剩节点，说明父链数据有异常（比如库中残留了环），这时返回冲突比无限循环或临时关掉外键更可控。整个函数在 `Delete` 的事务里执行，任何一步出错，已经删掉的评论都会随事务回滚。

确定整支后，从叶子开始删除：每轮选择当前没有仍需删除子项的节点，删掉叶子后再向上，最终删除原始父评论。若遍历没有进展却仍有节点，说明数据关系有异常，应该返回错误而不是无限循环或关掉外键继续执行。

删除事务确保任何一步失败时整支评论恢复。实现没有把所有评论响应嵌套，也没有靠关闭自引用外键换取一次删除成功。深度和数据量若未来显著增加，还需评估递归 SQL、批量删除和有界查询策略；当前逐行算法的适用规模需由实际数据验证。

## 五、评论测试应覆盖协议和父子关系

测试场景至少包括：

| 场景 | 预期 |
|---|---|
| 对已发布文章发表评论 | 生成评论和 parentId=null |
| 对同文章评论回复 | parentId 保留并可被客户端组楼 |
| 回复其他文章的评论 ID | 拒绝，不跨文章挂接 |
| 对草稿文章发表评论 | 公开语义下按 404 隐藏 |
| 敏感词占比刚低于/高于 10% | 按当前严格大于阈值规则分流 |
| 中文和 emoji 组合 | UTF-16 计算结果与 Node 向量一致 |
| 审核首次通过 | 状态和通知一起提交 |
| 通知插入失败 | 状态回滚且无通知 |
| 删除带多层回复的父评论 | 整支删除，不留下孤儿 |
| 删除中途失败 | 整支保持原数据 |

请求返回的平面数组只是 API 证据之一；数据库 parent_id、status、notification 和删除结果同样要检查。客户端验收再验证页面如何用 parentId 展示楼层。

## 小结：后端守关系和状态，客户端决定楼层呈现

M6 评论契约返回平面分页数据，以 parentId 表示回复关系。服务端校验回复同文章、公开仅列 approved、按 UTF-16 规则复刻敏感词覆盖率，并在审核和通知之间共享事务。删除父评论时计算整支后代并从叶子向上处理。

实现“盖楼”先区分数据结构和展示结构。只要契约保留 parentId，客户端可以组织树状 UI；后端则继续以平面响应和明确关系执行分页、权限、审核和删除。
