# 成为全栈·Go 后端篇·评论后端的边界：敏感词、审核和整支删除

## 前言：评论的“盖楼”展示不等于嵌套 API

一条评论可以回复另一条评论，数据模型通过 parentId 表达关系。用户会把评论区理解成楼中楼，但后端契约仍返回分页的平面评论列表。客户端把同一页记录按 parentId 组装成树状视觉结构；这两个层次可以同时成立。

后端负责确保评论对应已发布文章、回复父评论属于同一篇文章、公开列表只展示 approved、后台审核执行权限控制、删除父评论时不留下孤儿子评论。内容安全还要保持与 Node 侧 JavaScript 字符长度一致，避免把 Go 的 rune 数当成 UTF-16 长度。

本文说明 M6 评论服务如何在不修改响应协议的前提下支持盖楼显示，并介绍敏感词阈值、审核通知与递归整支删除。

## 一、回复关系由 parentId 表达

Create 先读取文章并确认它已发布，再读取当前登录用户。若请求包含 parentId，查询条件同时要求评论 ID 和相同 article_id。这样，用户不能把文章 A 的评论 ID 当成文章 B 下的回复父节点。

Page 对公开调用只过滤当前文章且 status=approved 的记录，按 created_at、id 升序返回；后台列表可以按状态、articleId 筛选，并用管理排序。响应保留每一行的 parentId，分页结构仍是 list + pagination。前端应以 parentId 建索引，再把根评论和回复分组，遇到父节点不在当前页时按产品规则处理。

分页边界带来一个现实问题：父评论和子评论可能落在不同页。如果 UI 需要完整 thread，应在客户端补查父级上下文或以逐页流方式建立节点，而不能假设一个分页结果永远包含整棵评论树。后端新增嵌套返回会改变 API shape，客户端和契约都需共同升级；当前实现没有这么做。

未审核或拒绝评论不进入公开列表。作者或管理员查看未发布文章评论的管理预览需要符合对应权限。公开可见性和 parentId 结构彼此独立：有 parentId 不代表可以让被拒绝父评论及其内容泄漏。

## 二、敏感词判断为何要用 UTF-16 长度

JavaScript 的字符串 length 按 UTF-16 code unit 计数；Go 的 len(string) 是字节数，遍历 rune 则按 Unicode code point 计数。对含中文或 emoji 的文本，三种长度都可能不同。如果 Node 根据 UTF-16 计算敏感词占比，Go 使用字节数，就会在阈值附近作出不同审核决定。

M6 使用 unicode/utf16 将内容转成 UTF-16 单元计算总长度，也计算匹配片段的长度。当前敏感词包括中文与英文样例；匹配不区分大小写，命中片段按其 UTF-16 长度替换为星号。若敏感词覆盖比例大于 10%，状态设为 rejected；否则为 approved。空文本不会触发除零判断，实际输入长度和内容限制另由契约/传输边界控制。

这里的实现只是为了保持现有 Node 行为，不是成熟的内容安全产品。固定词表存在误判和漏判，也不包含上下文识别、人工申诉或模型审核。教学文章应说明行为复刻，不把规则包装成推荐的通用审核方案。

Go 的 rune 截断也用于展示内容限制。数据库保存完整输入，View 将评论展示文本截到最多 2000 个 Unicode code point，拒绝理由最多 200 个。截断、审核存储和页面显示是三个不同规则，不能因为返回被截断就说原文已经丢弃。

## 三、状态变化和通知共享事务

Review 在事务内锁住评论，记录先前状态，再写入新状态和审核理由。首次从非 approved 改为 approved 时，调用 notification.Approved，将会员通知插入同一个 tx。通知写失败，审核状态一起回滚；重复审核已批准评论不会再次触发同一类通知。

审核拒绝时可以记录理由；批准时清除 rejectedReason。响应 View 将理由限制展示长度并保留 null 语义。管理员端和公开端的错误与可见性仍依据契约，service 不把数据库原始异常直接回给客户端。

和文章发布一样，这里数据库通知只是持久化的一条通知记录。若未来增加推送服务，需要独立处理外部发送失败和重复消费。SQL transaction 不能让手机 push 与数据库更新成为真正的原子事务。

## 四、删除一条评论要清理整支回复

外键指向 parent comment 时，直接删除父评论可能被数据库拒绝，或级联删除后端未预期的内容。M6 在事务里先锁定目标评论，验证操作者是评论作者或 editor/admin，然后读取同一 article 的评论集合，逐轮找出所有后代 ID。

确定整支后，从叶子开始删除：每轮选择当前没有仍需删除子项的节点，删掉叶子后再向上，最终删除原始父评论。若遍历没有进展却仍有节点，说明数据关系有异常，应该返回错误而不是无限循环或关掉外键继续执行。

删除事务确保任何一步失败时整支评论恢复。实现没有把所有评论响应嵌套，也没有靠关闭自引用外键换取一次删除成功。深度和数据量若未来显著增加，还需评估递归 SQL、批量删除和有界查询策略；当前逐行算法的适用规模需由实际数据验证。

## 五、评论测试应覆盖协议和父子关系

测试场景至少包括：

| 场景 | 预期 |
|---|---|
| 对已发布文章发表评论 | 生成评论和 parentId=null |
| 对同文章评论回复 | parentId 保留并可被客户端组楼 |
| 回复其他文章的评论 ID | 拒绝，不跨文章挂接 |
| 对草稿文章发表评论 | 公开语义下按 404 隐藏 |
| 敏感词占比刚低于/高于 10% | 按当前严格大于阈值规则分流 |
| 中文和 emoji 组合 | UTF-16 计算结果与 Node 向量一致 |
| 审核首次通过 | 状态和通知一起提交 |
| 通知插入失败 | 状态回滚且无通知 |
| 删除带多层回复的父评论 | 整支删除，不留下孤儿 |
| 删除中途失败 | 整支保持原数据 |

请求返回的平面数组只是 API 证据之一；数据库 parent_id、status、notification 和删除结果同样要检查。客户端验收再验证页面如何用 parentId 展示楼层。

## 小结：后端守关系和状态，客户端决定楼层呈现

M6 评论契约返回平面分页数据，以 parentId 表示回复关系。服务端校验回复同文章、公开仅列 approved、按 UTF-16 规则复刻敏感词覆盖率，并在审核和通知之间共享事务。删除父评论时计算整支后代并从叶子向上处理。

实现“盖楼”先区分数据结构和展示结构。只要契约保留 parentId，客户端可以组织树状 UI；后端则继续以平面响应和明确关系执行分页、权限、审核和删除。
