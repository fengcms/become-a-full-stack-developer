# 成为全栈·Go 后端篇·分类树与标签关系：目录变更为何需要协调

> 分类和标签看似是两张简单的字典表，但文章既保存外键关系，也保留面向列表的冗余展示字段。目录改名、移动和删除会触及文章数据，不是单行 CRUD。

## 前言：树结构的数据约束会随着修改传播

分类是有父子关系的目录，契约限制最多四级。管理员把一个节点移动到另一个父级时，不仅要避免把它移到自己的后代造成环，也要检查它整棵子树的新深度是否超过上限。分类改名或 slug 后，文章表里为了展示保存的 category_name/category_slug 需要同步更新。

标签也有两种表示：article_tags 是可查询的真实关系；文章的 tags JSON 字段是既有响应所需的展示投影。修改标签目录项，需要维护已有文章的投影；删除仍被引用的标签则应拒绝。两种数据职责不同，变化必须在同一事务中协调。

M6 将分类、标签管理放在 taxonomy 包，通过事务更新实体和文章投影，并在单个 Service 实例内串行化目录写入。本文讲清楚这套实现保护什么，以及进程 mutex 的边界在哪里。

## 一、把最大深度和无环约束写成校验

validateTree 先把所有分类按 ID 建索引，再从每个节点沿 ParentID 向上走。遍历过程中使用 seen 记录已经访问的祖先；再次遇到同一 ID 就说明形成环。每向上一层增加 depth，超过 4 就拒绝。

更新父级时，仅检查“新 parent 不是当前节点”还不够。例如 A 的子节点 B 移入深度为 4 的 C 下面，B 自己可能是第 2 层，但它的后代会超过深度限制。对全树逐节点重新验证，覆盖了变更影响到的所有后代路径。

创建新分类时，服务把待创建节点临时放进待验证集合，使用临时 ID 表达其树位置；通过后才执行 INSERT。更新操作则将修改后的节点放入当前树快照验证，再写回数据库。数据库约束与业务校验共同保护数据，但环和最大深度是跨行拓扑规则，单一行 CHECK constraint 不够表达。

最大深度来自冻结契约。界面可能只显示四层导航，但服务端仍要验证直接 API 请求，不能把客户端组件当成数据完整性门槛。

## 二、树查询与面包屑是不同投影

Categories 返回平面目录；Tree 根据 sortOrder、ID 稳定排序，再递归组装 children。叶子 children 是空数组而不是 null。Breadcrumb 则从当前节点向父链回溯，再按根到叶子顺序输出 id/name/slug。公开分类列表还可能包含文章数等统计字段。

这些输出是同一分类实体的不同投影。树结构依赖 ParentID，排序和展示依赖名称、slug、sortOrder，文章数依赖公开且未删除文章。不能把一个全量 Category ORM struct 直接序列化后声称它适用于所有接口。

Tree 构造使用 seen 以避免意外循环导致无限递归，即使写入校验本来不允许环。读取端防御和写入端约束作用不同：前者避免坏数据造成请求卡死，后者阻止坏数据进入数据库。

## 三、category_id 与名称投影要一起改变

文章保存 category_id 外键，也保存 category_name 与 category_slug，便于列表投影和既有契约输出。更新文章分类时，服务从事务里的分类表读取最新名称/slug，并和 category_id 一起更新。分类自身改名时，saveCategoryTx 在同一事务内更新所有未软删除且关联该分类的文章投影。

如果只改分类目录，文章列表会继续展示旧名称；如果只更新文章的 category_id，其他请求可能见到新 ID 搭配旧 category_name。事务将实体目录与冗余展示字段维持一致。若后续取消冗余设计，需要迁移与查询性能评估，而不是只删除两个列。

删除分类前检查是否仍有子节点，且没有未软删除文章引用。存在引用时返回冲突，不静默把文章改成未分类，也不绕过关系约束。

## 四、article_tags 是标签关系，JSON 是兼容投影

标签关系通过 article_tags 精确存储，可用于 EXISTS 筛选和引用约束。文章 tags JSON 则保留名称或 slug 文本，供既有响应表示。查询与筛选不应把文本 JSON 当成可靠关系来源，因为改名、重复值和数据库 JSON 能力会增加一致性难度。

改名标签时，服务记录 oldName 与 oldSlug，更新标签表，然后沿 article_tags 找到关联文章，把其 JSON 投影里匹配到的旧名称或旧 slug 替换为新值。整个过程在同一事务中。JSON 解析失败时当前实现跳过该项；这类历史数据异常要靠专项数据核查和修复处理，不应误称关联表不存在。

删除标签先统计 article_tags 引用，仍有关系时拒绝删除。管理员需要先通过文章编辑流程解除关系，之后再删标签。这样的约束比删除标签后留下孤儿关系更容易维护。

## 五、进程 mutex 的保护范围

taxonomy.Service 的分类和标签写操作用同一个 sync.Mutex 串行化。它保护同一个 Go service 实例中进行的拓扑校验和目录修改，减少两个并发写操作都基于旧树校验、最后互相覆盖的风险。

它不能保护第二个进程或副本。服务扩容后，每个实例都拥有独立 mutex；如果允许多个副本同时修改目录，当前约束就不再足够。需要在数据库层引入事务隔离/锁定方案、版本字段条件更新或其他分布式协调机制，并通过多实例并发测试证明。

SQLite 单实例也受文件库单写模型约束。进程内 mutex 和数据库写锁是不同层级的措施，不能互相替代。工程部署拓扑是数据一致性设计的一部分。

## 六、事务失败要恢复整个投影

分类改名涉及 categories 和多条 articles 更新；标签改名涉及 tags 和多个文章 JSON 字段。若中途一条文章更新失败，事务应让分类/标签目录和之前已更新的投影全部回滚。删除冲突则在写入之前阻止操作。

测试应覆盖：四层内增加子节点成功；第五层失败；把节点移入其后代形成环失败；移动整棵子树导致深度超限失败；分类名称变更同步到文章摘要；被引用分类不能删除；标签改名同步所有关系文章；仍被引用标签不能删除；中途写失败后目录和投影保持旧值。

并发测试要区分同一个 Service 的 mutex 串行和多 Service / 多进程竞争。单实例单测通过不能证明分布式安全。文档和部署承诺应精确说明这个边界。

## 小结：目录是业务实体，变更有传播半径

M6 通过全树校验维护分类无环和最多四级，通过事务将目录变更传播到文章展示字段；article_tags 保存标签关系，文章 JSON 保存兼容投影；仍被引用的目录项不允许删除。进程 mutex 只协调单个服务实例的写入。

当表中保存树、反范式投影或多对多关系，更新操作就要按传播半径设计。先找出真实关系和缓存/投影，再定义事务和删除规则；最后通过并发与失败注入观察数据库实际状态。
