# 成为全栈·Taro 小程序篇·原生分享与文章入口：小程序的平台能力边界

> 分享不是把当前页面复制一份。它给下一位用户提供一个入口，这个入口必须在没有原会话的情况下仍然说得通。

{{IMG:M5-04-封面}}

## 前言：读者点分享，接收者到底进入哪里

技术文章写好之后，分享按钮看上去只差一个图标。可它真正影响的是另一位用户：对方没有我们的页面栈，也不一定登录，更不应该继承分享者的预览权限。

网站分享的是 URL，APP 可以交给系统分享，小程序则使用原生分享入口和页面路径。相同的“分享文章”需求，在三端并没有相同的输出格式。

这篇围绕当前小程序的分享行为展开：怎样形成公开文章入口，怎样避免预览链接外泄，以及为什么服务端权限不能由前端路径替代。

## 一、先区分文章地址与小程序页面路径

公开网站地址可以被浏览器打开，小程序分享 path 则描述接收者要进入的注册页面。当前文章页使用 `useShareAppMessage` 提供标题与 path：

```ts
useShareAppMessage(() => ({
  title: preview ? '成为全栈' : article?.title || '成为全栈',
  path: preview
    ? '/pages/index/index'
    : `/pages/article/index?id=${article?.id || params.id}`,
}));
```

文章入口用 ID 定位数据，不携带 accessToken、refreshToken 或个人资料。接收者以自己的会话或游客身份请求文章，这是分享能力的基本所有权规则。

正因如此，文章页必须能仅凭这个参数开始读取，而不是要求先经过首页预热：

```ts
// src/pages/article/index.tsx：入口只带 id，正文读取全靠它。
const params = useRouter().params,
  preview = params.preview === "1",
  auth = useSession();
const result = useResource<Article>(`/articles/${encodeURIComponent(params.id || "")}`, preview);
```

同一个 `useResource` 里，`preview` 决定这次读取是否携带会员身份：公开分享走匿名，本人预览才带认证。

三个客户端对“分享文章”给出的产出各不相同，接收侧的成本也因此不同：

| 客户端 | 分享产出 | 接收者如何打开 | “成功”如何验证 |
|---|---|---|---|
| 网站 | 一条公开 URL | 浏览器直接访问 | URL 可访问 |
| APP | 交给系统分享面板 | 点击进入 APP 详情页 | 详情页读到正文 |
| 小程序 | 页面 path（含 id） | 微信在页面栈内打开 | 接收者能定位到内容 |

当前只有微信小程序目标验证，这段 Hook 不能证明网站或其他小程序目标都实现了同样分享。如果未来增加另一平台，应重新核对入口机制与返回值，而不是改个构建类型就默认完成。

## 二、按钮触发交给平台，而不是自造菜单

互动区使用原生 Button 的 `openType="share"`，由平台提供分享行为。页面 Hook 决定分享内容，按钮决定用户触发入口。

```tsx
// src/features/reactions.tsx：按钮只声明“用平台分享”，内容由页面 Hook 提供。
<Button className="reaction-button" openType="share">
  <Icon name="share" />
  <Text>分享</Text>
</Button>
```

而站内跳转共用同一个入口函数，文章入口也不例外——它只负责把 id 拼进页面 path：

```ts
// src/core/navigation.ts：所有站内导航共用一套拼路径与失败兜底。
export function go(page: string, params: Record<string, string | number> = {}) {
  const query = Object.entries(params)
    .map(([k, v]) => `${k}=${encodeURIComponent(v)}`)
    .join("&");
  const url = `/pages/${page}/index${query ? "?" + query : ""}`;
  return Taro.navigateTo({ url }).catch(() =>
    Taro.showToast({ title: "页面打开失败，请返回重试", icon: "none" }),
  );
}
export function openArticle(id: string | number, preview = false) {
  return go("article", { id, ...(preview ? { preview: 1 } : {}) });
}
export function requireLogin() {
  if (session()) return true;
  go("auth");
  return false;
}
```

这两者分开有利于检查：用户点的是明确动作，页面返回的是当前文章的公开信息。我们没有自行模拟微信联系人界面，也没有把复制链接包装成原生转发。

| 入口 | 当前行为 | 不能顺带推导的能力 |
|---|---|---|
| 公开文章分享 | 标题加原生文章 path | 不是浏览器通用 URL |
| 本人预览分享配置 | 返回首页 | 不分享未发布正文 |
| 外部链接 | 提示复制 HTTP(S) 地址 | 不是自动系统转发 |
| 其他分享渠道 | 本轮未交付 | 朋友圈等不在本轮交付范围 |

图标语义也应明确。复制、原生分享和站内跳转是三种不同动作，各用各的图标，用户才不必猜结果。

分享 path 指向的是一个**已注册的页面路径**，不是任意字符串。它必须出现在 `app.config.ts` 的页面列表里，否则接收者根本进不去：

```ts
// src/app.config.ts：分享要指向的文章页在 pages 列表中注册（节选，未含 window / tabBar）。
export default defineAppConfig({
  pages: [
    "pages/index/index",
    "pages/categories/index",
    "pages/search/index",
    "pages/member/index",
    "pages/browse/index",
    "pages/author/index",
    "pages/article/index",
    "pages/auth/index",
    "pages/collection/index",
    "pages/notifications/index",
    "pages/profile/index",
    "pages/settings/index",
    "pages/editor/index",
    "pages/my-articles/index",
  ],
```

## 三、预览模式不能变成公开内容入口

会员可能在“我的文章”里查看草稿或待审核文章。当前预览读取带认证，并在页面显示本人预览提示；互动、评论和公开阅读辅助也有模式限制。

```tsx
// src/pages/article/index.tsx：预览横幅只在 preview 分支出现。
{preview && (
  <View className="banner">本人预览 · {article.status} · 未发布内容不会公开展示</View>
)}
```

分享配置对 preview 直接返回首页，标题使用站点名称。这样，前端不会主动把未发布稿件组织为对外传播入口。

不过，这不是后端安全机制。用户仍可以手工拼页面参数，或者修改客户端。服务器必须根据文章状态与请求身份决定是否允许读取。前端隐藏按钮只减少误操作，不能证明数据不可访问。

这一点已经在真实后端集成里通过不同账号的权限请求验证。分享入口和资源权限属于两个层次，不应该让一个 UI 判断承包二者。

### 不要为了传播把私人模式带出去

预览页面上可能带 preview 参数，但它只是前端选择私有读取与展示方式。分享配置退回首页，是为了减少用户误分享，不是宣布这个参数拥有安全权限。

服务端依然检查用户与文章关系。其他会员即使得到相同 ID，也不能因此读到未发布正文——这层边界由服务端的身份判定兜底，而不是靠前端藏按钮。

未来若要做审核协作链接，需要另一个有期限、有受众、有撤销能力的设计。它不能从“当前本人预览能打开”自然演变成公开临时链接；更不能把访问令牌塞进分享 path 当作方便方案。

## 四、标题与 ID 来自当前数据，加载失败要有边界

文章读取成功，分享优先使用服务端返回的 article.id 和 title；尚未拿到文章时，代码保留站点标题与路由参数兜底。它让 Hook 有稳定返回值，却不证明传入的 ID 一定有效。

分享携带的字段由数据模型决定，只有公开字段会进入入口：

```ts
// src/core/models.ts：分享只用其中的 id 与 title（节选，其余字段略）。
export interface Article {
  id: number;
  slug: string;
  title: string;
  summary: string | null;
  status: string;
  publishedAt: string | null;
}
```

接收者进入之后仍然要走详情请求、loading 与 error。文章被删除、状态变化或者 ID 不存在，都可能让入口失效。这是内容产品的正常状态，不能只在分享者端检查一次就假设永久有效。

因此，分享验收需要看接收侧：从新入口进入，游客读已发布文章；无效 ID 显示可理解错误；未发布内容不能因路径带参数就被公开。这些是建议补充的场景，本次记录没有把所有转发接收矩阵写成已实测。

### 分享内容需要与实际展示同步

Hook 闭包读取当前文章数据，标题优先取服务端值。文章状态改变后，接收者再次读取可能看到新的标题或不可用状态，这是正常的数据时间差。

不应在分享前额外写入一份文章副本来保证“永远像当时那样”，除非产品明确要做快照。当前分享的是活跃资源入口，后端当前状态才是最终事实。

如果路由参数丢失，当前兜底返回仍可能形成无效详情路径，随后由错误状态处理。后续可以进一步收窄未加载时的分享入口，但不能把现有兜底描述成已经验证所有非法参数。

## 五、别在演示环境里夸大平台交付

开发工具能展示原生分享按钮和页面配置，但真实跨账号接收、真机分享链路以及正式版本的可用范围，需要对应环境验证。

本项目本轮目标明确：开发者工具关闭域名校验，完成演示流程。AppID 已配置，线上真实微信登录也已成功，这些都是事实；它们没有自动补齐正式发布与分发条件。

如果教学文章把工具中的按钮叫作“已经完成全渠道分享”，读者会在真正部署时才发现缺失。把能力范围写清楚，是文章质量的一部分。

分享要按“接收侧”逐种情况核对，而不是只看发送端按钮是否点得动：

| 接收场景 | 期望结果 | 依据 |
|---|---|---|
| 游客打开已发布文章 | 正常读到正文 | 公开 `GET /articles/{idOrSlug}` |
| ID 不存在 / 已删除 | 显示可理解的错误态 | 详情请求返回错误 |
| 未发布文章（他人） | 不可读，走错误态 | 服务端按状态与身份判定 |
| 本人预览（preview=1） | 带认证读到草稿 / 待审 | 服务端对作者放宽 |
| 站外 HTTP(S) 链接 | 提示复制，不自动打开 | `openLink` 外链分支 |

### 验收记录要写清发送与接收

一份完整分享记录应包含目标环境、发送来源、文章状态、接收身份与最终页面。只写“点击分享按钮成功”还不知道消息是否被接收，也不知道接收者能否读取。

这次保留实现事实与验证边界，后续真机矩阵可以逐项追加。文章的目的不是用平台按钮制造完成感，而是让分享成为一条可解释、可检查的入口路径。


## 六、把接收侧当成第一次访问来设计

分享者刚刚看过文章，缓存已经存在，加载通常很顺；接收者则可能冷启动，既没有缓存也没有登录。用分享者的页面体验推断接收者速度，会漏掉真正的入口成本。

因此，文章页本身要能仅凭 ID 开始读取。分类、上下篇和相关文章等辅助模块稍后加载，不能要求先进入首页把它们预热。分享入口是检验页面独立性的好方法。

```ts
// src/pages/article/index.tsx：正文按 id 先读，辅助模块随后挂载，预览态不发公开辅助请求。
const categories = useResource<Category[]>("/categories/tree");
const adjacent = useResource<{ prev: Article | null; next: Article | null }>(
  article && !preview ? `/articles/${article.id}/adjacent` : "",
);
const related = useResource<Article[]>(
  article && !preview ? `/articles/${article.id}/related` : "",
);
```

如果接收者想收藏，先读公开文章，再进入认证，成功后返回。这个流程把登录放在公开阅读之后，也不把分享者会员关系附加给接收者。谁发起互动，关系就属于谁。

分享入口和资源权限始终是两个层次，可以用一张表收束：

| 层次 | 由谁负责 | 前端能保证的 | 前端不能保证的 |
|---|---|---|---|
| 分享入口（UI） | 页面 Hook + 原生按钮 | 公开文章才提供分享 | 不能替代服务端鉴权 |
| 资源读取（API） | 服务端状态与身份判定 | 只做展示与否的选择 | 无法证明数据不可访问 |

## 七、分享入口的稳定性来自普通页面能力

一个好的分享实现，最终依赖文章页本身能处理游客、失效内容和网络错误。它不要求接收者先经历分享者的首页筛选，也不依赖之前缓存过文章。

所以，页面参数必须能独立定位内容，公开读取必须不依赖私人会话，错误状态必须能独立呈现。分享没有新建复杂系统，却迫使我们检验这些原本就该成立的条件。
