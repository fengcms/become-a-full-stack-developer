# 成为全栈·Taro 小程序篇·原生分享与文章入口：小程序的平台能力边界

> 分享不是把当前页面复制一份。它给下一位用户提供一个入口，这个入口必须在没有原会话的情况下仍然说得通。

{{IMG:M5-04-封面}}

## 前言：分享按钮是我最后才写的那一版

这个功能我拖到最后才做。技术上它是最简单的——一个按钮、几个字、不到二十行。

但真正动手的时候我意识到，它其实是对整套页面设计的**最后一次压力测试**。因为分享出去的页面，接收者是在**完全空白的上下文**里打开的。

我第一版写完，拿自己的手机点了一下分享，然后切到微信打开 —— 页面卡在骨架屏，然后报了一个"文章不存在"。

原因很朴素：我在开发工具里点开过那篇文章，缓存已经热了，**而接收者什么都没有。**

那一下让我明白：分享不是"发个链接"，而是**造一个必须独立成立的入口**。这篇讲当前小程序怎么做的，以及为什么很多看起来是 UI 的事，最后都要落到服务端。

## 先分清文章地址与小程序页面路径

网站分享的是 URL，可以被浏览器打开。小程序分享的是 `path`，描述接收者要进入哪个注册页面。

```ts
// src/pages/article/index.tsx（节选）：标题与路径由页面 Hook 提供。
useShareAppMessage(() => ({
  title: preview ? "成为全栈" : article?.title || "成为全栈",
  path: preview
    ? "/pages/index/index"
    : `/pages/article/index?id=${article?.id || params.id}`,
}));
```

**入口用 ID 定位数据，不携带 accessToken、refreshToken 或任何个人资料。** 接收者以自己的会话或游客身份请求文章 —— 这是分享能力的基本所有权规则。

因为入口只带 id，文章页必须能**仅凭这一个参数**开始读取，不能要求先经过首页预热：

```ts
// src/pages/article/index.tsx（节选）：入口只带 id，正文读取全靠它。
const params = useRouter().params,
  preview = params.preview === "1",
  auth = useSession();
const result = useResource<Article>(
  `/articles/${encodeURIComponent(params.id || "")}`,
  preview,
);
```

同一个 `useResource` 里，`preview` 决定这次读取是否携带会员身份：**公开分享走匿名，本人预览才带认证。**

| 客户端 | 分享产出 | 接收者如何打开 | "成功"如何验证 |
|---|---|---|---|
| 网站 | 一条公开 URL | 浏览器直接访问 | URL 可访问 |
| APP | 交给系统分享面板 | 点击进入 APP 详情页 | 详情页读到正文 |
| 小程序 | 页面 path（含 id） | 微信在页面栈内打开 | 接收者能定位到内容 |

**当前只验证了微信小程序目标。** 这段 Hook 不能证明网站或其他小程序目标实现了同样的分享 —— 如果未来增加另一平台，入口机制和返回值都要重新核对，而不是改个构建类型就默认完成。

## 按钮触发交给平台，不自造菜单

互动区用原生 Button 的 `openType="share"`，分享行为由平台提供。**页面 Hook 决定分享什么，按钮决定用户从哪触发。**

```tsx
// src/features/reactions.tsx（节选）：按钮只声明"用平台分享"，内容由页面 Hook 提供。
<Button className="reaction-button" openType="share">
  <Icon name="share" />
  <Text>分享</Text>
</Button>
```

站内跳转共用同一个入口函数，文章入口也不例外 —— 它只负责把 id 拼进 path：

```ts
// src/core/navigation.ts（节选）：所有站内导航共用一套拼路径与失败兜底。
export function go(page: string, params: Record<string, string | number> = {}) {
  const query = Object.entries(params)
    .map(([k, v]) => `${k}=${encodeURIComponent(v)}`)
    .join("&");
  const url = `/pages/${page}/index${query ? "?" + query : ""}`;
  return Taro.navigateTo({ url }).catch(() =>
    Taro.showToast({ title: "页面打开失败，请返回重试", icon: "none" }),
  );
}
export function openArticle(id: string | number, preview = false) {
  return go("article", { id, ...(preview ? { preview: 1 } : {}) });
}
export function requireLogin() {
  if (session()) return true;
  go("auth");
  return false;
}
```

这个 `.catch()` 有它的来历。**小程序页面栈有上限**，从很深的入口连续跳转时 `navigateTo` 会失败，而失败的 Promise 如果没人接就变成一个静默的 unhandled rejection —— 用户看到的是"点了没反应"。

分成"用户点的是明确动作"和"页面返回当前文章的公开信息"两层有利于检查。我们没有自行模拟微信联系人界面，也没把复制链接包装成原生转发。

| 入口 | 当前行为 | 不能顺带推导的能力 |
|---|---|---|
| 公开文章分享 | 标题加原生文章 path | 不是浏览器通用 URL |
| 本人预览分享配置 | 返回首页 | 不分享未发布正文 |
| 外部链接 | 提示复制 HTTP(S) 地址 | 不是自动系统转发 |
| 其他分享渠道 | 本轮未交付 | 朋友圈等不在交付范围 |

图标语义也要明确：**复制、原生分享和站内跳转是三种不同动作**，各用各的图标，用户才不必猜结果。

分享 path 指向的是一个**已注册的页面路径**，不是任意字符串：

```ts
// src/app.config.ts（节选，未含 window / tabBar）：分享目标必须在 pages 里注册。
export default defineAppConfig({
  pages: [
    "pages/index/index",
    "pages/categories/index",
    "pages/search/index",
    "pages/member/index",
    "pages/browse/index",
    "pages/author/index",
    "pages/article/index",
    "pages/auth/index",
    "pages/collection/index",
    "pages/notifications/index",
    "pages/profile/index",
    "pages/settings/index",
    "pages/editor/index",
    "pages/my-articles/index",
  ],
});
```

**这一条我用错了半年。** 有一回测试同学从别的页面跳到作者页，作者页里再点文章 —— 文章页当时还没加进 `pages`，微信直接拒绝跳转，而 `navigateTo` 的失败在前端看起来只是"没反应"。**注册列表是静态的，加页面必须改这里，而忘了改不会有编译错误。**

## 预览模式不能变成公开内容入口

会员可能在「我的文章」里查看草稿或待审核文章。当前预览读取带认证，并在页面显示本人预览提示：

```tsx
// src/pages/article/index.tsx（节选）：预览横幅只在 preview 分支出现。
{preview && (
  <View className="banner">本人预览 · {article.status} · 未发布内容不会公开展示</View>
)}
```

分享配置对 `preview` 直接返回首页，标题用站点名称。**这样前端不会主动把未发布稿件组织成对外传播入口。**

但这不是安全机制。用户仍可以手工拼参数或改客户端。

> **服务器必须根据文章状态与请求身份决定是否允许读取。前端隐藏按钮只减少误操作，不能证明数据不可访问。**

这一点已经在真实后端集成里用不同账号的权限请求验证过。**分享入口和资源权限属于两个层次，不该让一个 UI 判断承包二者。**

{{IMG:M5-04-分享入口边界}}

### 不要为了传播把私人模式带出去

预览页可能带 `preview` 参数，但它只是前端选择私有读取方式。分享配置退回首页，是为了减少误分享，**不是宣布这个参数拥有安全权限**。

服务端依然检查用户与文章关系。其他会员即使拿到相同 ID，也不能因此读到未发布正文 —— 这层边界由服务端身份判定兜底。

未来若要做审核协作链接，需要另一个**有期限、有受众、有撤销能力**的设计。它不能从"当前本人预览能打开"自然演变成公开临时链接；更不能把访问令牌塞进分享 path 当作方便方案。

## 标题与 ID 来自当前数据，加载失败要有边界

分享优先用服务端返回的 `article.id` 和 `title`；还没拿到文章时保留站点标题和路由参数兜底。

```ts
// src/core/models.ts（节选）：分享只用其中的 id 与 title。
export interface Article {
  id: number;
  slug: string;
  title: string;
  summary: string | null;
  status: string;
  publishedAt: string | null;
}
```

**注意这里只有公开字段。** 这不是巧合 —— 分享能带什么，由数据模型决定。如果 `Article` 里塞了 `authorEmail` 之类字段，那么"不小心带出去"就变成一个迟早会发生的事故。

接收者进入之后仍然要走详情请求、loading 与 error。文章被删除、状态变化或 ID 不存在，都会让入口失效 —— **这是内容产品的正常状态，不能只在分享者端检查一次就假设永久有效。**

### 分享内容需要与实际展示同步

Hook 闭包读取当前数据，标题优先取服务端值。文章状态改变后接收者再次读取可能看到新标题或不可用状态，**这是正常的数据时间差**。

不应在分享前额外写一份文章副本以保证"永远像当时那样"，除非产品明确要做快照。当前分享的是活跃资源入口，**服务端当前状态才是最终事实**。

## 一个我差点当成"平台 bug"的问题

分享功能做完那天，测试同学发来一张截图：从作者页点进一篇文章，**什么都没发生**。

我第一反应是 `navigateTo` 写错了 —— 因为同一个入口从首页点文章完全正常。查了半天才反应过来：**这两个入口的页面栈深度不一样。**

小程序页面栈有上限（微信是 10 层）。从作者页进来已经在第 3 层，再点文章是第 4 层，明明没超。但微信还有另一条规则会拦你：**目标页面必须出现在 `app.config.ts` 的 `pages` 列表里**，而我当时还没把文章页加进去。

于是行为就是：微信静默拒绝这次跳转，Promise 被 reject，而我那个 `.catch()` 只写了"页面打开失败，请返回重试"的 toast —— **在测试机上看过去，和网络失败一模一样。**

真正修它的不是加日志，是问了一个问题：**"这个页面注册了吗？"** 一查就发现漏了。

而这次之后我改了一个习惯：**新增页面时，`app.config.ts` 和页面文件当成同一处改动来做。** 因为它漏了不会有编译错误、不会有 lint 报错，只会在某个特定的跳转路径上静默失败 —— 这属于最难发现的一类问题。

**关于分享入口能不能被信任，还有一层更重要的判断：** 上面这个 bug 是"入口不存在"，还有一种是"入口存在但权限不对"。前者微信会拦，后者微信不拦 —— **它会正常打开，然后把错误交给服务端。** 那一次就必须靠上一节说的"服务端按状态与身份判定"来兜底。

**两者的区别在于：页面注册是平台的硬约束，资源权限是服务端的责任。** 前者漏了会静默失败，后者漏了会数据泄露 —— 后者严重得多，也更靠测试而不是靠小心。


## 别在演示环境里夸大平台交付

开发工具能展示原生分享按钮和页面配置，但**真实跨账号接收、真机分享链路、正式版本可用范围，需要对应环境验证。**

本项目本轮目标明确：开发者工具关闭域名校验，完成演示流程。AppID 已配置，线上真实微信登录也已成功 —— 这些是事实；**但它们没有自动补齐正式发布与分发条件。**

如果教学文章把工具里的按钮叫作"已完成全渠道分享"，读者会在真正部署时才发现缺失。

分享要按**接收侧**逐种情况核对，而不是只看发送端按钮是否点得动：

| 接收场景 | 期望结果 | 依据 |
|---|---|---|
| 游客打开已发布文章 | 正常读到正文 | 公开 `GET /articles/{idOrSlug}` |
| ID 不存在 / 已删除 | 显示可理解的错误态 | 详情请求返回错误 |
| 未发布文章（他人） | 不可读，走错误态 | 服务端按状态与身份判定 |
| 本人预览（`preview=1`） | 带认证读到草稿 / 待审 | 服务端对作者放宽 |
| 站外 HTTP(S) 链接 | 提示复制，不自动打开 | `openLink` 外链分支 |

**一份完整的分享记录应包含目标环境、发送来源、文章状态、接收身份与最终页面。** 只写"点击分享按钮成功"，既不知道消息是否被接收，也不知道接收者能否读取。

## 把接收侧当成第一次访问来设计

分享者刚看过文章，缓存已经存在，加载通常很顺；**接收者可能冷启动，既没有缓存也没有登录。** 用分享者的体验推断接收者的速度，会漏掉真正的入口成本。

所以文章页本身必须能仅凭 ID 开始读取。分类、上下篇和相关文章等辅助模块稍后加载：

```ts
// src/pages/article/index.tsx（节选）：正文按 id 先读，预览态不发公开辅助请求。
const categories = useResource<Category[]>("/categories/tree");
const adjacent = useResource<{ prev: Article | null; next: Article | null }>(
  article && !preview ? `/articles/${article.id}/adjacent` : "",
);
const related = useResource<Article[]>(
  article && !preview ? `/articles/${article.id}/related` : "",
);
```

`&& !preview` 这个条件是我加的：**本人预览一张草稿时，不该顺手发三个公开辅助请求** —— 那些文章对草稿根本不存在，结果只会是三个报错，既浪费又干扰调试。

如果接收者想收藏，先读公开文章，再进认证，成功后返回。**这个流程把登录放在公开阅读之后，也不把分享者的会员关系附加给接收者。谁发起互动，关系就属于谁。**

分享入口和资源权限始终是两个层次：

| 层次 | 由谁负责 | 前端能保证的 | 前端不能保证的 |
|---|---|---|---|
| 分享入口（UI） | 页面 Hook + 原生按钮 | 公开文章才提供分享 | 不能替代服务端鉴权 |
| 资源读取（API） | 服务端状态与身份判定 | 只做展示与否的选择 | 无法证明数据不可访问 |

## 分享入口的稳定性，来自普通页面能力

一个好的分享实现，最终依赖文章页本身能处理游客、失效内容和网络错误。**它不要求接收者先经历分享者的首页筛选，也不依赖之前缓存过文章。**

所以那三个条件本来就该成立：页面参数能独立定位内容、公开读取不依赖私人会话、错误状态能独立呈现。

**分享没有新建复杂系统，却迫使我们检验了这些本来就该成立的条件** —— 这才是把它放在最后的理由。
