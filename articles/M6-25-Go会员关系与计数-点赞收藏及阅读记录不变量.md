# 成为全栈·Go 后端篇·点赞收藏与会员记录：关系表如何守住计数不变量

> 点赞状态、收藏列表和阅读进度都属于会员数据，但它们的幂等语义并不相同。实现时要先确定关系表、计数列和用户可见记录各自的事实来源。

## 前言：同一张按钮，背后有多种状态

文章页上的点赞按钮可能只是一个心形图标，但服务器要维护用户与文章的关系、文章 likeCount，以及重复操作时的幂等性。收藏也有关系表，却不一定需要文章冗余计数。阅读历史则包含 lastReadAt 和可选 progress，字段缺失、null、0 的更新语义需要区分。通知又是只属于当前用户的私有集合。

若把这些都建模为“给文章加一个布尔值”，就无法记录是谁点的；若只加关系但不校验唯一性，并发请求会产生重复；若计数和关系不在同一事务，页面数字会漂移。

M6 将关系实体分别保存在 likes、favorites、view_history 等表，并通过 user_id 做私有范围过滤。本文围绕点赞精确计数、收藏幂等、历史更新和多库 affected rows 差异展开。

## 一、点赞关系是真实事实，计数是展示投影

likes 表中的 user_id + article_id 表示某用户是否给一篇文章点赞，并有唯一约束。文章 like_count 是便于读取的聚合值。由于有两份相关数据，写入应在一个事务中完成，避免只插关系或只改计数。

三张关系表的模型放在一起看，差别很小：

~~~go
// internal/platform/model/likes.go
// Like 用户与文章的点赞关系，文章计数必须与关系行数一致。
type Like struct {
	ID        int64 `gorm:"column:id;primaryKey;autoIncrement"`
	UserID    int64 `gorm:"column:user_id"`
	ArticleID int64 `gorm:"column:article_id"`
	CreatedAt int64 `gorm:"column:created_at"`
}

func (Like) TableName() string { return "likes" }

// internal/platform/model/favorites.go
// Favorite 用户与文章的收藏关系，唯一约束确保重复收藏幂等。
type Favorite struct {
	ID        int64 `gorm:"column:id;primaryKey;autoIncrement"`
	UserID    int64 `gorm:"column:user_id"`
	ArticleID int64 `gorm:"column:article_id"`
	CreatedAt int64 `gorm:"column:created_at"`
}

func (Favorite) TableName() string { return "favorites" }

// internal/platform/model/view_history.go
// History 阅读历史行，可空进度区分没有记录与明确的零。
type History struct {
	ID         int64  `gorm:"column:id;primaryKey;autoIncrement"`
	UserID     int64  `gorm:"column:user_id"`
	ArticleID  int64  `gorm:"column:article_id"`
	LastReadAt int64  `gorm:"column:last_read_at"`
	Progress   *int64 `gorm:"column:progress"`
}

func (History) TableName() string { return "view_history" }
~~~

三张表的骨架几乎相同，差别集中在两点。点赞和收藏的关系列都是 `user_id` + `article_id`，而 `Progress *int64` 是唯一的指针——它必须能同时表达“没有进度记录”和“进度为零”。如果写成 `int64`，`0` 会同时承担这两个含义，接口层面再也分不出“刚打开文章”和“从未上报过进度”。

结构体本身不声明唯一约束，`gorm` tag 里只有列名和主键。`(user_id, article_id)` 的唯一性写在迁移 SQL 里，这样约束对所有写入路径都生效，而不是只对走 GORM 的那条路径生效。

三个机制各自负责一件事：

| 机制 | 作用 | 缺了会怎样 |
|---|---|---|
| 文章行锁 | 同一篇文章的互动写入串行 | 并发增删互相覆盖 |
| 关系唯一约束 | 一个用户对一篇文章只有一条关系 | 重复点击产生多行 |
| 事务 | 关系与计数一起提交 | 只改了一边，数字漂移 |

Like 操作先锁定公开文章，再按 add 选择新增或删除关系。新增使用冲突忽略，确保重复添加不创建多行。之后重新统计该文章 likes 关系数量，将精确总数写到 articles.like_count，再读取新文章返回 liked 和 likeCount。取消时同样删除关系并重算计数。重复取消不会把计数减成负数。

为什么重算而不是直接 +1？因为 MySQL 在冲突忽略语句上的 RowsAffected 行为不适合被直接当成“这次一定新增一行”。通过查询关系表真实数量，计数的依据明确。代价是增加一次 count 查询；若后续要优化成增量，需要准确处理首次插入、冲突、取消和重试，并用竞态测试证明不会双增。

锁文章让针对同一篇文章的互动写入串行化；唯一约束是关系去重的数据库防线；事务确保关系和计数一起提交。三个机制责任不同，不能只留其中一个。

## 二、收藏同样幂等，但不需要复制点赞的计数逻辑

Favorites 关系表示用户保存了一篇文章。新增前要求文章当前公开，使用 user/article 冲突忽略；重复收藏保持成功和同一状态。取消收藏可以删除匹配关系，多次删除仍然得到无收藏状态。

收藏的实现短到可以整段读完：

~~~go
// internal/member/interactions.go（Favorite，节选）
// Favorite 幂等增删收藏；新增只能引用公开文章。
func (s *Service) Favorite(ctx context.Context, user, id int64, add bool) error {
	db := s.DB.WithContext(ctx)
	if !add {
		return db.Where("user_id = ? AND article_id = ?", user, id).Delete(&model.Favorite{}).Error
	}
	if _, err := article.Published(db, id); err != nil {
		return err
	}
	f := model.Favorite{
		UserID:    user,
		ArticleID: id,
		CreatedAt: s.Now().UnixMilli(),
	}
	return db.Clauses(clause.OnConflict{DoNothing: true}).Create(&f).Error
}
~~~

取消分支直接删除匹配关系，`Where` 里带 `user_id` 和 `article_id` 两个条件，所以只能删自己那条；删不到行也不算错误，重复取消因此总是成功。新增分支先 `article.Published(db, id)` 确认文章公开，再 `Clauses(clause.OnConflict{DoNothing: true}).Create(&f)` 写入。冲突忽略让第二次收藏落到唯一约束上并被忽略，返回的仍是成功。

和 `Like` 相比，`Favorite` 没有重算任何计数。这不是遗漏：收藏关系本身不需要在文章行上冗余一个计数列，列表页要显示的是“我收藏了哪些”，而不是“这篇文章被收藏多少次”。两者的事实来源不同，代码也就没有强行共用同一条写入路径。

收藏列表按 user_id 筛选，并以收藏时间、关系 ID 稳定排序；输出文章摘要并过滤软删除记录。收藏历史仍可显示什么内容，取决于契约：未发布文章是否可见、被软删文章是否隐藏都需明确。不能通过客户端传 userId 查询别人的收藏，身份主体从 Actor 来。

点赞列表和收藏列表同属私有查询，但响应分页形状可能不同。代码要遵循对应 operation，不能为复用一个统一 helper 而改变 JSON 结构。

一个函数同时承载两种列表，差异靠参数区分：

~~~go
// internal/member/interactions.go（Articles，节选）
// Articles 查询收藏或点赞文章，按对应契约选择分页和响应形状。
func (s *Service) Articles(ctx context.Context, user int64, q url.Values, likes bool) (any, error) {
	table := "favorites"
	if likes {
		table = "likes"
	}
	p := values.Paging(q)
	if likes {
		p = values.PagingWith(q, 10, 50)
	}
	db := s.DB.WithContext(ctx).
		Model(&model.Article{}).
		Joins("JOIN "+table+" ON "+table+".article_id=articles.id").
		Scopes(database.ActiveArticles).
		Where(table+".user_id = ?", user)
	if likes {
		db = db.Where("articles.status = ?", "published")
	}
	var count int64
	if err := db.Session(&gorm.Session{}).Count(&count).Error; err != nil {
		return nil, err
	}
	var rows []model.Article
	if err := db.Select(article.SummaryColumns).
		Order(table + ".created_at DESC, " + table + ".id DESC").
		Limit(p.Size).
		Offset(p.Offset()).
		Find(&rows).Error; err != nil {
		return nil, err
	}
	list := article.List(rows)
	if likes {
		return list, nil
	}
	return p.Result(list, count), nil
}
~~~

`Where(table+".user_id = ?", user)` 里的 `user` 来自认证后的 Actor，不从查询参数取——这就是“不能通过客户端传 userId 查别人收藏”的落点。`Joins` 用关系表关联文章表，配合 `ActiveArticles` 过滤掉已软删除的文章。

`likes` 参数控制四处差异。表名在 `favorites` 和 `likes` 之间切换；分页默认值不同，点赞列表用 `PagingWith(q, 10, 50)`，收藏列表用默认的 `Paging(q)`；点赞列表额外要求 `articles.status = "published"`，因为“我点过赞的文章”只应包含还能打开的；返回形状也不同，点赞直接返回数组，收藏返回带分页信封的 `p.Result(list, count)`。

这四处差异正是“不能为复用而改变 JSON 结构”的例子。共用一个查询构造是对的，共用一个响应形状就会让其中一个接口偏离契约。

## 三、阅读历史的 progress 缺失与零值

view_history 按 user_id + article_id 唯一定位一条阅读记录。Report 更新 last_read_at；只有当请求包含 progress 字段时才将 progress 加入 upsert 的更新 map。因此缺失 progress 会保留旧值；显式 0 会写入 0；显式 null 会把可空列清为 NULL。

~~~go
// internal/member/history.go（Report，节选）
// Report 上报阅读位置，未提交进度保留原值，显式零与 NULL 分别处理。
func (s *Service) Report(ctx context.Context, user int64, in values.Fields) (any, error) {
	id := in.Int("articleId")
	db := s.DB.WithContext(ctx)
	a, err := article.Published(db, id)
	if err != nil {
		return nil, err
	}
	h := model.History{
		UserID:     user,
		ArticleID:  id,
		LastReadAt: s.Now().UnixMilli(),
		Progress:   in.Number("progress"),
	}
	patch := map[string]any{"last_read_at": h.LastReadAt}
	if in.Has("progress") {
		patch["progress"] = h.Progress
	}
	err = db.Clauses(clause.OnConflict{
		Columns: []clause.Column{
			{
				Name: "user_id",
			},
			{
				Name: "article_id",
			},
		},
		DoUpdates: clause.Assignments(patch),
	}).
		Create(&h).Error
	if err != nil {
		return nil, err
	}
	if err = db.Where("user_id = ? AND article_id = ?", user, id).First(&h).Error; err != nil {
		return nil, err
	}
	return historyView(a, h), nil
}
~~~

关键在于 `patch` 的构建：`last_read_at` 无条件写入，`progress` 只有 `in.Has("progress")` 为真时才加入。这个 `Has` 判断直接决定了三种语义的差别：

| 请求中的 progress | 更新 map 的内容 | 数据库结果 |
|---|---|---|
| 字段缺失 | 只含 `last_read_at` | 保留原进度 |
| `0` | `progress = 0` | 写入 0 |
| `null` | `progress = NULL` | 清为 NULL |

`Clauses(clause.OnConflict{...})` 把并发重复上报压到同一个唯一关系上：`Columns` 指明按 `(user_id, article_id)` 判重，`DoUpdates` 用 `patch` 覆盖。第一次上报时是普通插入，之后每次都是对同一行的更新，所以“同文章多次上报只留一条 history”由数据库保证。

函数最后重新读一次 `h`，用 `historyView(a, h)` 返回。这样做是因为 upsert 返回的行不含数据库里的最终值，重新查询才能拿到真正落库的 `progress`。验证最终值比相信 upsert 的返回值更直接。

这三个状态对阅读体验有意义：用户刚打开文章时进度可以为零；清除进度可能用 null；若本次只报告浏览，则不应误把已有进度重置。读取时 DTO 若 progress 为 NULL，当前 mapper 不输出该字段；有数值时返回具体值。契约中的 required/nullable/optional 语义要分别核对，不能把“Go 指针 nil”一概序列化成同一种响应。

Report 先要求文章已发布，再按当前会员主体写入关系。OnConflict 将并发重复上报压到同一唯一关系上，patch 只包含更新时间和实际提交的 progress。数据库读取验证最终值比检查 upsert 返回行数更直接。

## 四、私有数据查询必须从当前身份出发

History 查询通过 view_history.user_id = 当前 Actor ID 限定结果，并 join articles 检查未软删除。响应由 article Summary 和阅读时间/进度组成，页面只得到当前会员的数据。DeleteHistory 同样以当前用户 ID 为首个条件；传 articleId 删除一条，不传则清空本人历史。

~~~go
// internal/member/history.go（historyView 与 History，节选）
func historyView(a model.Article, h model.History) map[string]any {
	r := map[string]any{"article": article.Summary(a), "lastReadAt": values.ISO(h.LastReadAt)}
	if h.Progress != nil {
		r["progress"] = *h.Progress
	}
	return r
}

// History 读取当前会员的未删除文章历史，不输出其他用户的记录。
func (s *Service) History(ctx context.Context, user int64, q url.Values) (any, error) {
	p := values.Paging(q)
	db := s.DB.WithContext(ctx)
	filter := db.Model(&model.History{}).
		Joins("JOIN articles ON articles.id=view_history.article_id").
		Scopes(database.ActiveArticles).
		Where("view_history.user_id = ?", user)
	var n int64
	if err := filter.Session(&gorm.Session{}).Count(&n).Error; err != nil {
		return nil, err
	}
	var rows []model.History
	if err := filter.Select("view_history.*").
		Order("view_history.last_read_at DESC, view_history.id DESC").
		Limit(p.Size).
		Offset(p.Offset()).
		Find(&rows).Error; err != nil {
		return nil, err
	}
	ids := []int64{}
	for _, h := range rows {
		ids = append(ids, h.ArticleID)
	}
	articles := []model.Article{}
	if len(ids) > 0 {
		if err := db.Select(article.SummaryColumns).Where("id IN ?", ids).Find(&articles).Error; err != nil {
			return nil, err
		}
	}
	by := map[int64]model.Article{}
	for _, a := range articles {
		by[a.ID] = a
	}
	list := []map[string]any{}
	for _, h := range rows {
		list = append(list, historyView(by[h.ArticleID], h))
	}
	return p.Result(list, n), nil
}
~~~

`Where("view_history.user_id = ?", user)` 是第一条也是最重要的一条条件，`user` 来自认证后的 Actor。查询里不出现任何来自请求的 userId，换个令牌只会得到自己的历史。

`Joins("JOIN articles ON ...")` 加上 `ActiveArticles`，让已软删除的文章从历史列表里消失。历史行本身没有被删除，只是查询时不再带出来——这是“软删除影响展示、不影响记录”的一致做法。

`historyView` 有意把 `progress` 做成条件字段：`h.Progress != nil` 时才写进返回 map，为 nil 时该键根本不出现。响应里“没有进度”表现为字段缺失，而不是 `progress: null`。数据库里的 NULL 与响应里的字段缺失是两个层面的表达，契约对哪一层用哪种形状有明确规定。

数据组装分两步：先按分页取出历史行，再用 `id IN ?` 一次取回对应文章摘要，最后在内存里用 `by` 索引拼装。这避免了 N+1 查询，也避免在一条 SQL 里拼出响应结构。

删除逻辑同样把当前用户放在最前面：

~~~go
// internal/member/history.go（DeleteHistory）
// DeleteHistory 删除本人单条历史；文章 ID 为零时清空本人历史。
func (s *Service) DeleteHistory(ctx context.Context, user, id int64) error {
	q := s.DB.WithContext(ctx).Where("user_id = ?", user)
	if id > 0 {
		q = q.Where("article_id = ?", id)
	}
	return q.Delete(&model.History{}).Error
}
~~~

`q` 一开始就限定 `user_id = ?`，只有 `id > 0`（传了 articleId）时才追加 `article_id` 条件。不传 articleId 时条件只剩 user_id，删除该用户的全部历史——这就是“清空本人历史”的实现。user_id 必须放在最前面，即使将来有人加错了条件，作用范围仍然锁在当前用户身上。

通知列表、未读数和标记已读接口也需要相同的 self-scoped 规则。不要让会员接口接受任意 userId 后仅依赖前端隐藏用户选择器；直接调用 API 的用户可以修改参数。传输层 operation 权限和领域查询的 user scope 共同落实边界。

数据导出工具可能读取所有会员记录，但它是独立管理命令和受控的数据迁移路径；不能把这个权限带到普通 HTTP handler。

## 五、幂等与并发测试矩阵

| 操作 | 重复请求 | 应保持的不变量 |
|---|---|---|
| 点赞添加 | 同一用户多次 add | 一条关系，likeCount 不重复增加 |
| 点赞取消 | 同一用户多次 remove | 关系不存在，计数不负数 |
| 点赞并发 | 同用户同文章并发 add/remove | 关系数与计数一致 |
| 收藏添加 | 重复收藏 | 一条关系，不报重复键错误 |
| 历史上报 | 同文章多次 report | 一条 history，更新时间按新请求刷新 |
| progress 缺失 | 更新其他上报信息 | 原进度保留 |
| progress = 0 | 明确归零 | 数据库存 0 |
| progress = null | 明确清除 | 数据库按契约存 NULL |
| 私有历史 | 换成另一个用户 token | 不得读取或删除他人记录 |

数据库级唯一键和事务是重点。race detector 能查 Go 共享内存竞态，不能证明关系表没有重复；差分测试能比响应，也应再查后置数据库状态。

## 六、计数一致性和缓存时效

点赞响应返回事务后的 likeCount，文章详情或列表可能来自另一次查询或客户端缓存。用户刚点完赞后若页面仍显示旧统计，可能是客户端查询缓存未失效，也可能是后端统计逻辑；应通过直接读取数据库和接口区分。服务器返回的一致计数不能自动刷新其他客户端已经拿到的响应。

如果计数不再每次重算，而改为异步聚合，API 就可能返回最终一致值。那是产品语义变化，需要定义容忍延迟、修复任务和计数重建方案。M6 当前使用精确关系计数并在事务内更新，性能容量要单独测量。

## 小结：每类会员状态都要有自己的幂等规则

点赞依赖关系唯一性和精确 likeCount；收藏保持幂等但不复制计数逻辑；阅读历史使用 user/article 唯一关系，并区分 progress 缺失、0 与 NULL；私有查询通过认证主体而非请求参数限定范围。通知和历史也遵守用户作用域。

遇到会员按钮或个人记录，先回答“事实记录在哪张表、重复执行结果是什么、谁能读取、计数是否为投影、请求字段缺失意味着什么”。再选 upsert、事务和索引。这样可以避免用一个通用 toggle 抹平不同业务行为。
