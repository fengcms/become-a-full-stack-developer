# 成为全栈·Node 后端篇·参数校验：为什么必须在最外层做

从前端转后端的同学，最常带过来的一个误区是："校验不就是表单那边 `required`、正则匹配一下吗？我前端都验过了，后端还要再验？"

要命就在这句话上。前端校验是为了**用户体验**——你输错邮箱，页面立刻红字提示，不用等请求往返。但前端校验**绝对不等于安全**。任何人都可以打开浏览器 DevTools，绕过你的 JS，直接发一个构造好的恶意请求。如果你的后端也"信任"前端传来的数据，那等于把家门钥匙挂在"请随手关门"的提示牌上。

举个具体的"信任客户端"惨案。假设注册时你让前端传 `role` 字段，后端直接 `INSERT ... role = body.role`。攻击者在 DevTools 里把请求体的 `role` 改成 `'admin'`，一条请求就成了管理员——这就是经典的**越权 / 批量赋值（mass assignment）**漏洞。正确的做法是：后端**根本不从客户端接收 `role`**，注册时强制写死 `'member'`，提升权限只能走后台审核接口（且操作者自身得是 admin）。这条"客户端传入的角色一律不认"的规则，正是信任边界思维的直接产物。

所以请记住一句冷酷但必须接受的结论：**前端校验是给用户看的，后端校验才是给系统看的；前者可以被完全绕过，后者不能**。两层不是重复劳动，而是各司其职——前端管体验、后端管安全，合起来才叫"纵深防御"。

这一篇聊参数校验，核心就一句话：**所有外部输入都不可信，校验必须放在后端的最外层（信任边界）**。

## 一、信任边界：后端的第一道安全意识

"信任边界（trust boundary）"是个值得记住的词。它的意思是：**数据从"不可信区"（客户端、外部系统）跨进"可信区"（你的服务器逻辑）的那条线，必须在线上做一道安检**。

跨过这条线之前，数据是敌人；跨过之后，你才能当它自己人。所以校验的黄金位置，是**路由最外层**——请求一进来，先过 Zod 这道关，非法输入当场被挡在门外，根本进不到 service、碰不到数据库。

为什么不能"在 service 里顺便验一下"？两个原因：

1. **污染深层逻辑**。如果每个 service 函数都要先 `if (!username) throw ...`，业务代码会被校验噪音淹没，而且同一个字段可能在五六个地方各验一遍，规则一改漏改哪处都不知道。
2. **格式不统一**。散落的校验抛出的错误五花八门，前端没法用一套逻辑接。统一在最外层，所有校验失败都长一个样（下面讲）。

对比一下就懂。没有最外层校验时，你的 `registerUser` 可能开头就是：

```ts
function registerUser(body: any) {
  if (!body.username) throw '用户名必填';
  if (body.username.length > 32) throw '用户名太长';
  if (!/^.+@.+$/.test(body.email)) throw '邮箱格式错';
  if (!body.password || body.password.length < 8) throw '密码太短';
  // ...真正的业务逻辑才刚开始
}
```

光校验就占了函数一半篇幅，而且 `articles`、`comments`、`users` 各自的创建函数都要复制一遍这套判断，规则一变就得改五六个地方。统一到最外层后，service 函数收到的已经是"保证合法"的对象，它只关心"业务上能不能注册"（比如用户名是否已被占用），不再操心格式——**职责干净了，重复也消失了**。这是分层思想在"校验"这件小事上的又一次胜利。

## 二、Zod 实践：用 schema 声明"合法长啥样"

我们用 Zod 在路由层声明"这个接口的输入合法长啥样"。看 `src/routes/auth.ts` 里注册接口的入参 schema：

```ts
const registerSchema = z.object({
  username: z.string().min(1).max(32),
  email: z.string().email().max(255),
  password: z.string().min(8),
  nickname: z.string().max(32).optional(),
});
```

读起来几乎就是人话：用户名非空、最长 32；邮箱必须合法格式、最长 255；密码至少 8 位；昵称可选、最长 32。Zod 把"校验规则"和"类型定义"合二为一——`z.infer<typeof registerSchema>` 直接给出 `RegisterInput` 类型，字段约束变了，类型自动跟着变。

注意这些约束不是我们拍脑袋定的，是和 OpenAPI 契约里"用户注册"端点的字段约束**一一对齐**的。这就是"**校验即契约**"：Zod schema 是契约字段约束在代码里的实体化，契约改了字段范围，这里必须同步改，否则双门校验会报红。契约先行的价值，在这里又体现一次 {{LINK:M0-05}}。

顺带提一个 Zod 新手常混的"三兄弟"：`optional()`、`nullable()`、`default()`。`optional()` 表示字段可以**不出现**；`nullable()` 表示字段可以出现但值是 **`null`**——JSON 里"没传"和"传了 null"是两回事，搞反了前端和你会对线；`default()` 则是"没传就用这个默认值"。我们注册 schema 里 `nickname` 用 `optional()`，因为昵称可以不填；而刷新接口 `refreshToken` 用 `z.string().nullable().optional()`，因为浏览器可能不带 body、只靠 Cookie，此时字段既可能缺失也可能为空。把这三个分清，能少写一堆 `if (x === undefined || x === null)` 的防御代码，schema 本身就是最好的文档。

## 三、P-20：最外层校验失败，统一返回 4001 信封

校验放在哪、用什么验，都定了，剩下的问题是"失败了怎么回"。我们的纪律（P-20）是：**最外层校验失败，直接返回契约的 `4001` 信封，且把字段级错误装进 `data.errors`**。

`src/middleware/validate.ts` 是这道安检的统一实现：

```ts
const toValidationResponse = (error: { issues: ...[] }): Response => {
  const errors = error.issues.map((issue) => ({
    field: issue.path.join('.') || '_',
    message: issue.message,
  }));
  return failResponse(ErrCode.VALIDATION, 400, { errors });
};

export const v = {
  json: (schema) => zValidator('json', schema, (r) =>
    r.success ? undefined : toValidationResponse(r.error)),
  query: (schema) => zValidator('query', schema, /* 同上 */),
  param: (schema) => zValidator('param', schema, /* 同上 */),
};
```

返回给前端的错误信封长这样：

```json
{
  "code": 4001,
  "message": "参数校验失败",
  "data": {
    "errors": [
      { "field": "email", "message": "Invalid email" },
      { "field": "password", "message": "Too small: expected string to have >=8 characters" }
    ]
  },
  "requestId": "abc",
  "timestamp": "2026-08-27T..."
}
```

`data.errors` 是个数组，每项带 `field` 和 `message`。前端拿到它，能**精确高亮出是哪个输入框格式不对、错在哪**——而不是笼统弹一句"提交失败"。这正是统一信封 + 字段级错误组合出来的好体验，也是《工程公约》里"输入要校验、错误要清晰"的落地 {{LINK:M0-06}}。

`v.json / v.query / v.param` 三个辅助，对应三种校验目标：请求体、查询参数、路径参数。注册接口用的就是 `v.json(registerSchema)`，写在路由处理函数之前，形成"先校验、后处理"的硬顺序。

## 四、P-21：Zod v4 下的类型退化，以及我们的 workaround

这里有个真实的工具链坑（P-21），值得记一笔，因为它会突然出现在你某次升级依赖之后。`@hono/zod-validator` 在 `zod v4` 环境下，有个已知问题：经它校验后，`c.req.valid('json')` 的**类型会被退化成 `unknown`**，而不是你 schema 推导出的精确类型。

也就是说，中间件明明已经用 Zod 把数据校验过了，但 TypeScript 在 handler 里却认为"这是个 unknown，你不能 `.username`"。我们的应对（见 `auth.ts` 顶部注释）是：

```ts
authRoute.post('/register', v.json(registerSchema), async (c) => {
  const input = c.req.valid('json') as RegisterInput; // 中间件已运行时校验，此处 as 安全
  // ...
});
```

用 `as RegisterInput` 把类型"拿回来"。**为什么这个 `as` 是安全的，而不是偷懒？** 因为校验已经由上游的 `v.json(registerSchema)` 在运行时做掉了——数据走到 handler 时，要么是合法对象、要么早就在中间件返回 4001 了，根本到不了这行 `as`。所以这个 cast 不是"掩盖类型错误"，而是"告诉编译器一个它推断不出的、但运行期已保证的事实"。

这套话术对所有"工具链版本错配导致的类型退化"都适用：**运行时校验兜底的 `as`，是 workaround 不是 hack；但前提是校验确实先执行了**。如果你连校验都没做就 `as`，那就是真·埋雷。

这也提醒我们：依赖升级（尤其是 `zod-validator` 这类与框架强耦合的）要带着契约测试和门禁一起升，别孤立地 bump 版本号——否则今天还是绿的门禁，明天一个 `npm update` 就可能悄悄把类型退化塞进你的 handler，而你毫无察觉。

## 五、三层校验位置一览

把前面的点收一下，我们的参数校验体系是：

- **位置**：路由最外层（信任边界），进 service 前完成，不污染深层逻辑。
- **工具**：Zod 声明 schema，与契约字段约束对齐（校验即契约）。
- **失败响应**：统一 `4001` 信封 + `data.errors` 字段级明细。
- **目标**：`v.json`（体）/ `v.query`（查询）/ `v.param`（路径）三类全覆盖。
- **类型陷阱**：zod v4 下 `c.req.valid` 退化 `unknown`，靠"已运行时校验"的 `as` 取回类型。

校验看着琐碎，却是后端安全的"第一道门"。它和错误处理、统一信封是一套组合拳：边界拦非法、错误包异常、信封统格式。

## 六、小结与前瞻

1. **信任边界**：所有外部输入不可信，校验必须放在后端最外层（跨进可信区前的安检）。
2. **不污染深层逻辑**：统一在路由层验，service 专心业务，规则改一处即可。
3. **Zod 即契约**：schema 字段约束与 OpenAPI 契约对齐，契约改这里必改。
4. **P-20**：校验失败统一 `failResponse(VALIDATION, 400, { errors })`，`data.errors` 带 `field/message`，前端精确高亮。
5. **P-21**：zod v4 下 `c.req.valid('json')` 退化 `unknown`，用"已运行时校验"的 `as Schema` 取回类型——是安全的 workaround 而非 hack。
