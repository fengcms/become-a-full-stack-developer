# 成为全栈·Taro 小程序篇·Markdown 投稿编辑器：原生输入、工具条与预览

> 移动端编辑器首先要保护输入，其次才是提供更多格式按钮。没有 DOM，也不必把整个桌面编辑体验硬搬过来。

{{IMG:M5-21-封面}}

## 前言：参考后台编辑器，不等于复制后台组件

管理后台已经有 Markdown 编辑器，网站与 APP 也能投稿。小程序要参考它们的功能，却不能直接使用桌面编辑器的 DOM 选区、快捷键和粘贴事件。

当前方案使用原生 Input、Textarea、Picker，提供常用语法工具条，编辑与预览切换。它不是所见即所得，也不是缩小后的代码编辑器，而是一个可在移动环境完成稿件的文本工具。

这篇先把这个选择说清楚，再看光标、异步上传与最新文本如何配合。小编辑器里的竞态，往往比工具条按钮数量更值得认真处理。

## 一、先列出必须完成的创作任务

| 任务 | 当前控件或能力 | 主要约束 |
|---|---|---|
| 标题和摘要 | Input、Textarea | 200 与 500 字符限制 |
| 正文输入 | 原生 Textarea | 65535 字符上限 |
| 分类选择 | 原生 Picker | 树展平，保留层级提示 |
| 标签 | 逗号分隔输入 | payload trim、去空、去重 |
| 常用格式 | 工具条插入 Markdown | 不实现 DOM 选区包裹 |
| 预览 | 复用阅读 Markdown | 标题与正文，不完整模拟公开详情 |

字符上限是当前代码与契约限制，不是按汉字数量计数。JavaScript length 的口径与用户所说“字数”也可能不同，尤其表情与组合字符。页面文案使用“字符”，更接近实现。

这一层先确保能够写、能够看、能够保存。复杂语法提示与编辑器扩展系统，不是教学小程序的首要目标。

## 二、正文只有一个拥有者

Editor 页面保存完整 Draft，EditorForm 接收 draft 与 onChange。表单每次只产生字段 patch，再合并到最新值。

```ts
const latest = useRef(draft);
latest.current = draft;
function change(patch: Partial<Draft>) {
  onChange({ ...latest.current, ...patch });
}
```

latest 很重要。图片上传可能等待几秒，其间用户继续修改标题或正文；回调若使用开始上传时的 draft，就会把新输入覆盖成旧快照。

这不是把全部表单变成 ref。可见输入仍由 state 驱动，ref 只为异步动作保留当前值。职责分开后，预览和保存都消费同一份 Draft，而不是各维护一份正文。

## 三、工具条在当前光标插入，而非猜测选区

Textarea 的 onInput 与 onBlur 更新 cursor。未拿到有效位置时在末尾插入，位置超过当前长度则收窄到文本结尾：

```ts
const d = latest.current;
const at = cursor.current < 0
  ? d.content.length : Math.min(cursor.current, d.content.length);
change({ content: d.content.slice(0, at) + before + after + d.content.slice(at) });
cursor.current = at + before.length;
```

H2、粗体、链接、代码、列表、引用分别提供 before／after。代码默认 TypeScript 围栏，这是工具条默认值，用户仍可手动改语言。

当前没有读取完整选择区间，所以“粗体”插入 `****` 结构，不是把任意选中文字自动包裹。内部 cursor 引用移动，也不等于平台可见光标已被强制设回目标。文章不能把文字拼接能力写成桌面编辑器那样完整的光标控制。

## 四、分类树展平，但层级仍要看得出来

Picker 接收选项数组，分类树递归展开，在名称前加缩进提示。选项保存 ID，显示 name；未分类使用空值，而不是把零当作真实分类 ID 发给服务端。

这保留了后台已经定义的分类体系，不需要小程序重建一棵自己的分类树。与此同时，移动选择器的呈现与网站多级导航不同，是平台控件的合理转换。

分类读取失败会显示重试入口，正文仍保留。选不到分类不能成为清空作者输入的理由。后端负责最终分类有效性，客户端只是提供选择范围。

标签输入支持英文和中文逗号。payload 生成时去空、trim、Set 去重，这一步负责表示转换，不负责所有标签权限与长度规则。接口校验仍应保留。

## 五、预览用同一阅读组件，但承诺要说准确

编辑页切到预览后，显示当前标题与 Markdown 正文，读取的还是未提交 Draft。格式、代码、表格与链接算法因此沿用阅读器，不会出现另一套 Markdown 解释。

但它不是完整公开页快照。摘要、封面、上下篇、互动和评论没有全部进入预览。作者检查的是主要排版与内容，不是最终所有页面模块。

预览不需要写服务器，更不触发公开阅读计数。这让作者可以反复查看，不用为每次预览生成稿件。真正本人稿件预览则是另一个认证阅读入口，权限仍由后端控制。

链接在预览中也沿用统一策略。外链不会因为编辑器环境变成任意 WebView，站内导航可能离开当前页，因此未保存保护仍有价值。

## 六、输入、上传和保存不能各自宣布完成

EditorForm 选图期间通知父页 uploading，父页禁用服务端保存和提交。回调拿到 URL 后，用最新文本插入图片或更新封面。

输入当前并没有因为上传而全部冻结，作者仍能继续写。这正是 latest 引用需要存在的原因。上传完的文本应叠加在最新稿件上，而不是替换它。

取消媒体选择不显示错误，真正失败显示可修正提示。页面切换与组件卸载期间的上传回调还需要进一步人工场景验证，不能只凭 finally 重置状态就宣称所有中断都安全。

## 七、本机保存与云端保存，文案必须区分

修改触发约六百毫秒后的本机写入，页面提示自动保存到本机。用户点“保存文章”才调用服务端；“提交审核”还涉及状态推进。

写入本机失败会提示尽快保存至服务器，不能继续显示一个无条件“已保存”。本机草稿恢复也需要账号与稿件归属，细节见 [草稿恢复]({{LINK:M5-22}})。

此外，存本机可以保留用户内容，不会创建远端资源。清理阅读缓存也不删除它。让几个动作名称明确，用户才不会把一种保存当成另一种备份。


## 工具条的简单实现，也有值得检查的边缘

用户删除一大段正文后，旧 cursor 可能超过当前长度，所以插入前收窄位置。输入事件更新 cursor，失焦也更新，减少点击工具条时忘记位置的情况。

但最新记录位置不保证平台真正选区保持不变，也没有自动选中插入的占位文字。用户需要继续编辑链接说明与代码语言。这是原生文本方案的代价，应该用文案和操作样本帮助理解，而不是假称完全智能编辑。

如果以后增加选区包裹，应先核对平台支持的选择信息和设置光标能力，再定义空选区与已有选区两种语义。直接沿用 before／after 插入不会自然实现它。

### 表单校验和内容格式是两层工作

标题、正文必填与最大长度在 validateDraft 处理；封面要求 HTTP(S)，标签 payload 负责拆分去重。Markdown 本身允许很多普通文本，所以“格式没有高亮”不必然是校验失败。

写作工具不应该因作者用了未知代码语言就拒绝整篇投稿。阅读器可以纯文本降级，服务器继续校验内容与权限。把可读降级和表单错误分开，作者才不会被不必要的限制打断。

### 类似界面不必有相同快捷键

后台可以支持桌面粘贴和更丰富的编辑能力，小程序工具条适合触控，APP 则有自己的输入组件。共同的是内容字段与保存状态，不是每个端都有相同键盘组合。

移动端还要关注原生键盘遮挡底部操作、横竖屏和输入高度。当前固定正文输入区保留滚动空间，但真机是否舒适需要实际观察；工具成功输入一次还不能证明长期写作体验。

### 让用户可以从小程序继续到其他端

服务器保存后的稿件由同一 userId 管理，作者可以在网站或 APP 接着编辑。未上云的本机草稿却只存在当前设备，不会自动同步到其他端。界面明确“本机”和“服务器”，正是为了让这条转换不误导。

以后若要支持导出本机稿，需要另行设计文件或剪贴板出口。当前没有这个功能，也不把共享账号描述成所有输入已经跨设备备份。保住当前输入、讲清保存位置，比一张功能很多的工具条更重要。

## 八、验证可编辑，而不只验证能渲染

开发工具实际输入过标题和 Markdown，切换预览、保存与提交都操作过；逻辑测试验证 payload 与草稿隔离。相册上传、真实光标位置与真机键盘矩阵没有全部人工验收。

建议后续关注正文中段插入、上传期间继续输入、预览返回不丢文字、分类失败后重试、字符达到上限、外部点击收起键盘。每个场景都能检验一条明确约束。

更多上传细节见 [图片选择与提交协调]({{LINK:M5-23}})。移动编辑器不必拥有所有桌面能力，但它答应保留的输入与操作结果，必须能解释、能恢复。
