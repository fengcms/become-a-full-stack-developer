# 成为全栈·基础补充·认证与授权：两个总被混淆的概念

这两个词在中文技术圈里经常混着说，但**它们回答的是两个完全不同的问题**：

- **认证（Authentication）**：**你是谁？**
- **授权（Authorization）**：**你能做什么？**

而它们被混淆是有原因的——在这个项目里，它们的代码**在同一个文件里**。

看真实实现：

```ts
/**
 * 鉴权中间件 + 守卫工厂。实现契约第 4 铁律的授权求值：
 *   ④(a) 角色层级 ≥ minRole → 放行
 *   ④(b) 否则若 resolveOwner 返回的资源归属 == 当前用户 → 放行
 *   否则 → 2001 无权限
 */
```

同一个文件里，`authMiddleware` 管认证（你是谁），`guard` 管授权（你能做什么）。

**而它们之间那条分界线，是这个项目里我花时间最多的地方之一**——因为"认证通过"和"可以操作"之间，还隔着一整套资源归属判断。

## 认证只回答一件事：令牌是不是你

认证在这个项目里只有一种方式：`Authorization: Bearer <token>`。

```ts
export const authMiddleware: MiddlewareHandler<AuthVars> = async (c, next) => {
  const header = c.req.header('authorization') ?? '';
  const token = header.startsWith('Bearer ') ? header.slice(7).trim() : '';
  if (!token) throw new AppError(ErrCode.TOKEN_MISSING, 401, '未携带访问令牌');

  const claims = await verifyAccessToken(token, getActiveEnv().JWT_SECRET);
  c.set('user', { id: claims.sub, role: claims.role });
  await next();
};
```

**整段只做三件事**：提取令牌 → 验证 → 把 `userId` 和 `role` 放进请求上下文。

**注意它没有查数据库。** 这是 JWT 的核心特性——**令牌自包含身份信息，所以验证不需要访问存储**。

而它的直接后果是：**如果一个用户被禁用了，他手里的令牌在到期前仍然有效。**

这不是 bug，是 JWT 的固有性质。而这个项目的应对在别处：

```ts
api.onExpired = () {
  user = null;
  PaintingBinding.instance.imageCache.clear();
  notifyListeners();
};
```

**以及 M4-09 讲的那些字段**：`epoch`（会话代次）、`canSetCredentials`（能不能设密码）。

所以严格说，这个项目的认证是**两层的**：

| 层 | 机制 | 覆盖范围 |
|---|---|---|
| JWT 本身 | 签名验证 | 令牌没被伪造、没过期 |
| **会话状态** | `epoch`、撤销的 refresh token | 账号状态变化后的即时失效 |

**第一层管"令牌是真的"，第二层管"令牌还有效吗"。** 只有第一层的话，禁用一个用户要等他令牌到期。

## 授权的分层：角色只是其中一条路

现在说授权。这个项目的角色只有三个：

```ts
/**
 * 角色层级：内部 0-based（member=0 / editor=1 / admin=2），
 * 对应契约文档「第 4 铁律」的 member(1) < editor(2) < admin(3) 口径，仅表示法不同，语义等价。
 */
const ROLE_RANK: Record<Role, number> = { member: 0, editor: 1, admin: 2 };
```

而授权判断的真实逻辑是这个：

```ts
export const guard =
  (minRole: Role,
   resolveOwner?: (c: Context<AuthVars>) => string | null | Promise<string | null>,
  ): MiddlewareHandler<AuthVars> =>
  async (c, next) => {
    const user = c.get('user');
    if (!user) throw new AppError(ErrCode.TOKEN_MISSING, 401, '未携带访问令牌');

    const roleOk = (ROLE_RANK[user.role] ?? -1) >= (ROLE_RANK[minRole] ?? 99);
    if (roleOk) return next();                    // 路径一：角色够

    if (resolveOwner) {
      const ownerId = await resolveOwner(c);
      if (ownerId === null) throw new AppError(ErrCode.NOT_FOUND, 404);
      if (ownerId === user.id) return next();      // 路径二：我是作者
    }
    throw new AppError(ErrCode.FORBIDDEN, 403);
  };
```

**两条放行路径，顺序很关键。**

| 路径 | 条件 | 例子 |
|---|---|---|
| 一 | 角色层级 ≥ minRole | admin 改任何文章 |
| 二 | 角色不够，但**我是这个资源的作者** | member 改自己的草稿 |

**而"我是作者"这条路径，正是 M0-05 契约里那个 `ownerOverride` 的实现：**

```yaml
x-authz:
  minRole: member
  ownerOverride:
    param: id
    ownerField: authorId
```

**为什么角色判断排在前面？** 因为它更便宜——不需要查数据库。而作者判断要查。

**所以这个顺序不是随意的，是一个成本权衡。** 大部分请求（admin 操作）走第一条，一次查库都不需要。

而这里的 `?? -1` 和 `?? 99` 也值得看：

```ts
const roleOk = (ROLE_RANK[user.role] ?? -1) >= (ROLE_RANK[minRole] ?? 99);
```

**如果出现了一个不在 `ROLE_RANK` 里的角色，`-1 >= 99` 为 false → 拒绝。** 而如果 `minRole` 传了个非法值，`>= 99` 也为 false → 拒绝。

**两边的默认值都是"拒绝"而不是"放行"。** 这是处理未知输入的通用原则：**当你不认识某个值时，倾向于拒绝。**

## 404 优于 403：这个注释是重点

现在讲整个授权逻辑里我最想展开的一段。

```ts
if (ownerId === null) throw new AppError(ErrCode.NOT_FOUND, 404); // 资源不存在 → 404（守契约，优于 403）
if (ownerId === user.id) return next();
...
throw new AppError(ErrCode.FORBIDDEN, 403); // 存在但非归属者 → 403
```

**`resolveOwner` 返回 `null` 表示"这个资源不存在"，此时抛 404。**

**而返回了一个 id 但不等于当前用户，才抛 403。**

这两个的区别不是随便定的——它是一个**信息泄露的判断**。

考虑这个场景：用户 A 想看文章 999 的编辑页。

| 方案 | 响应 | 用户能推断出什么 |
|---|---|---|
| 全部返回 403 | 403 | **"文章 999 存在，但不是你的"** |
| 全部返回 404 | 404 | "文章 999 不存在" |
| **区分** | **404 或 403** | **信息泄漏** |

**而这个项目选了"区分"**——注释里写着"守契约，优于 403"。

**这是有意的决定，而且我认为在内容产品上是对的。** 理由是：

**如果全部返回 404，一个作者会以为自己文章的编辑链接坏了**，而实际上是他没有权限——这个信息差会导致他反复尝试、反复困惑。

**而"泄漏是否存在"这个风险，在这个项目里可以接受**，因为：文章是公开内容，任何人都能通过列表看到它存在。**"这篇文章存在"根本不是秘密。**

**这就是判断标准：这个区分泄漏的信息，本身是秘密吗？**

| 资源 | 存在性是否敏感 | 该不该区分 |
|---|---|---|
| 公开文章 | 不敏感（列表里能看到） | **可以区分** |
| 别人的草稿 | **敏感**（不该被知道存在） | 必须统一返回 404 |
| 别人的私有数据 | **敏感** | 必须统一返回 404 |

**这个项目里至少有一处就是这么做的**——M1-32 那个微信端点在检查 `resolveOwner` 返回值时，先查资源再判归属。

**而"是否存在"和"是否有权"这两个问题的答案，在敏感资源上必须合并。** 这不是技术做不到，是产品选择。

## 可选鉴权：降级而不是报错

现在讲一种特殊场景：**有些端点登录与否都能访问。**

比如文章详情——游客能看（但不能点赞），登录用户能看且能看到自己的点赞状态。

```ts
/**
 * 可选鉴权中间件：携带有效 Bearer 则注入 c.set('user')，否则按匿名继续（不抛错）。
 * 用于契约 `security: [{}, {bearerAuth: []}]` 端点（如文章详情 / 阅读量），
 * 实现「可匿名、也可携带令牌」的标准语义；令牌无效时静默降级为匿名，不阻断请求。
 */
export const optionalAuthMiddleware: MiddlewareHandler<AuthVars> = async (c, next) => {
  const header = c.req.header('authorization') ?? '';
  const token = header.startsWith('Bearer ') ? header.slice(7).trim() : '';
  if (token) {
    try {
      const claims = await verifyAccessToken(token, getActiveEnv().JWT_SECRET);
      c.set('user', { id: claims.sub, role: claims.role });
    } catch {
      // 可选鉴权：无效令牌按匿名处理，不抛错
    }
  }
  await next();
};
```

**注意那个空的 `catch`。**

一个令牌无效（过期、被撤销、格式错），这里**不报错，直接当匿名处理**。

**为什么？** 因为端点是"可匿名"的，报错会造成一个奇怪的结果：**游客能看这篇文章，带了个过期 token 的用户反而看不了。**

而"静默降级"对用户更友好——他看到的是游客视图，**而登录态的处理是前端的另一件事**（M4-09 讲的 401 会触发刷新）。

**但这个设计有一个明确的前提**：**匿名和登录用户看到的内容差异必须可接受。**

对文章详情来说，差异是"能不能点赞"，而不是"能不能看到文章"——**可接受。**

**而如果这是"我的草稿"，令牌无效就必须报错**，因为匿名用户根本不该看到任何内容。

**同一个"令牌无效"，在不同端点应该有不同的处理。** 而"可匿名"这个属性是**写在契约里的**（`security: [{}, {bearerAuth: []}]`），不是靠每个路由自己判断。

## 刷新令牌：认证的一半在这里

前面说的都是"认证"，但认证的完整流程还包含刷新。

而刷新这件事的复杂度，比"验证令牌"大得多——M4-09 整篇都在讲它。这篇只提三个设计决定：

**一、刷新令牌是数据库里的实体，不是 JWT。**

```sql
CREATE UNIQUE INDEX `uniq_token_hash` ON `refresh_tokens` (`token_hash`);
```

**因为它必须可撤销**——而 JWT 是无状态的，撤销不了。

**二、轮换（rotation）。** 每次刷新都发一个新的，旧的那个作废。

**这直接缓解了 CSRF 和令牌泄露**（M4-11 讲过）——**一个被偷走的 token 用一次就没了。**

**三、刷新成功时撤销所有旧会话。**

这正是 B-18 和 B-20 讲的 `changes()=1` 那个设计：

```sql
UPDATE refresh_tokens SET revoked_at=? WHERE user_id=? AND revoked_at IS NULL AND changes()=1
```

**而"撤销所有"这个决定是有代价的**——它意味着用户在手机上登录，**会把自己在电脑上的会话也踢掉。**

这个行为对用户来说可能是意外的。**但对安全性来说，它是必要的**——因为如果设置凭据成功了却没撤销旧会话，那些旧令牌就变成了"永久有效的东西"。

## 授权测试要覆盖失败路径

最后讲测试，因为这一章最容易写出"看起来对"的测试。

**授权测试的核心不是"该放行的能放行"，而是"不该放行的确实被挡住了"。**

这个项目里几个真实的用例：

| 场景 | 断言 |
|---|---|
| 会员改别人文章 | 403 |
| 会员改自己文章 | 200 |
| 改不存在文章的 id | **404**（不是 403） |
| 无令牌访问需登录端点 | 401 |
| editor 改任何文章 | 200（角色路径） |
| 可选鉴权端点带无效令牌 | **200，行为等同匿名** |

**第三行和第六行是最容易被漏的**，因为它们测的是"边界"而不是"主路径"。

而**每条断言都要写清楚是走哪条路径放行的**。比如"会员改自己文章"这条，如果实现里 `resolveOwner` 写错了（比如返回了 category 的 id 而不是 author 的 id），那测试仍然可能通过——**因为它只断言了 200，没断言走的是作者路径**。

**这也是 B-17 讲的"用例名即测试文档"的另一个应用**：测试名要写清楚保护的是哪条路径。

## 一条我一开始想省掉的事

那个"资源不存在 → 404 优于 403"的判断，第一版我写的是**全部返回 403**。

理由听起来很正当："统一返回更安全，不泄漏信息。"

而真实使用时的反馈是：**用户反馈"我明明有一篇文章，点了编辑进不去"。**

排查之后发现是 id 打错了，而 403 让它看起来像"权限问题"——用户于是去检查自己是不是被降权了。

**而如果返回 404，他会立刻意识到"这个 id 不存在"，然后重新去列表里找。**

这就是那两种设计的实际差别：**一个是"系统拒绝了你"，一个是"你要找的东西不存在"。** 而前者会让用户怀疑自己被惩罚了。

**改完之后我在代码里留了那条注释**：

```ts
if (ownerId === null) throw new AppError(ErrCode.NOT_FOUND, 404); // 资源不存在 → 404（守契约，优于 403）
```

**注释里写"守契约，优于 403"** ——因为这个决定不只是技术选择，**契约里就是这么声明的**，而代码要匹配契约。

**注释写下来的作用是：将来有人觉得"统一返回 403 更安全"时，能看到这是个有意的决定。** 否则他很可能会"顺手优化"回去——而那正是我第一版做的事。

## 小结

认证和授权在这个项目里的分层：

1. **认证**：验证 Bearer 令牌，注入 `userId` 和 `role`。**不查数据库**，所以要靠 `epoch` 补第二层。
2. **授权**：两条路径——角色层级够，或者我是作者。**角色判断在前**（更便宜）。
3. **未知值默认拒绝**：`ROLE_RANK[user.role] ?? -1` 让非法角色通不过。
4. **404 vs 403 是产品判断**：公开资源可以区分（帮助用户定位问题），敏感资源必须统一（防信息泄露）。
5. **可匿名端点静默降级**：令牌无效当匿名，而不是报错——**前提是匿名视图可接受**。
6. **刷新令牌的复杂度在"可撤销"上**，而它的代价是"改密码会踢掉所有设备"。

其中第 4 条我觉得最值得记，因为它体现了一个通用原则：

> **技术选择的安全性和可用性经常对立，而"哪个更重要"是产品判断，不是技术判断。**

统一返回 403 更"安全"，但它让用户困惑。区分 404/403 泄漏一点信息，但**在这个项目里文章存在性本来就不是秘密**。

**而做出这个判断的前提是：你知道自己保护的资源里，哪些的"存在"是秘密。** 不知道这一点时，保守（统一 404）是合理的默认值。

下一篇讲 Node 事件循环。它会解释为什么这个项目里所有"异步身份核对"的写法都是必需的——**因为在单线程事件循环里，`await` 之间的那个时间点足以让用户切换账号。**
