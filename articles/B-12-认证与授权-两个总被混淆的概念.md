# 成为全栈·基础补充·认证与授权：两个总被混淆的概念

> 认证回答“你是谁”，授权回答“你能做什么”。登录成功只是建立了身份，并不自动赋予这个身份访问每一个资源的权限。

## 前言：为什么隐藏按钮不等于保护接口

管理后台把“删除用户”按钮藏起来，普通会员就真的不能删除用户了吗？如果服务端接口没有验证角色，任何人都可以绕过页面直接构造 HTTP 请求。界面控制是用户体验，安全边界必须由服务端执行。

认证（authentication）确认主体身份，授权（authorization）判断主体对某个动作或资源是否有权限。两者在一次请求中相继发生，但解决的是不同问题。

## 一、认证建立主体身份

用户可以通过账号密码、一次性验证码或第三方身份完成认证。服务端验证凭据后，建立一个会话或签发访问令牌，后续请求据此识别用户。密码应使用专门的密码哈希算法存储，不能明文保存，也不能用普通快速哈希代替；盐和成本参数由所选算法处理。

Cookie 会由浏览器按规则附加到请求，适合 Web 会话；Bearer token 通常由客户端显式放入 Authorization 头，常见于移动 App 和 API 调用。两种方式都有保护和更新策略：Cookie 需要 Secure、HttpOnly、SameSite 等属性并考虑 CSRF；访问 token 要妥善保护存储，不能放在可被任意脚本读取的地方就认为安全。

JWT 是一种包含声明并由签名保护的 token 格式，不等于加密。持有者可能读取其中的声明，因此不要放密码或秘密；服务端应限制允许算法、验证签名和过期时间。JWT 被签发后，如果系统没有额外撤销机制，已发出的 access token 可能在过期前继续有效。

## 二、授权应在每次资源操作时检查

角色授权是常见做法，例如 member、editor、admin；但只检查角色并不总够。会员可以编辑自己的资料，却不能编辑别人的资料；作者可以编辑自己的草稿，编辑者可能能管理全站文章。

一个可靠的授权决策通常组合：

    已认证主体 + 操作权限 + 资源状态 + 资源归属 → 允许 / 拒绝

例如“删除评论”要确认当前用户已登录、具有管理或作者权限、评论仍允许删除，并且目标评论属于可操作文章。前端可以提前隐藏按钮或显示提示，但服务端每次请求仍需重新判断，不能信任客户端传来的 role、userId 或 isOwner。

## 三、访问令牌与刷新令牌

访问令牌通常短时有效，携带请求身份；刷新令牌寿命较长，用于在 access 过期后换取新 access。刷新令牌是高价值凭证，应通过安全 Cookie 或平台安全存储保护，并能撤销或轮换。

常见刷新流程：

1. 客户端用 access 请求受保护资源。
2. 收到明确的过期认证错误后，使用 refresh 请求新凭证。
3. 并发的多个 401 请求共享一次 refresh，避免重复消费。
4. 刷新成功后，客户端只重放符合条件的原请求。
5. 刷新失败时清理本地会话，转到登录流程。

请求库应避免对所有错误无限重试，写操作的重放还要考虑幂等性。刷新令牌轮换、重放撤销与并发行为，见 [B-20]({{LINK:B-20}}) 和 [M6-18]({{LINK:M6-18}})。

## 四、登出、改密和会话撤销

登出可以清理当前客户端保存的凭证；服务端是否能让已签发 access token 立刻失效，取决于系统是否维护撤销列表、会话版本或短有效期策略。清除浏览器存储不等于服务端撤销所有 token。密码修改通常应撤销刷新会话或要求其他设备重新登录，并明确当前 access token 的剩余有效行为。

账户删除、禁用和角色变更同样需要明确已有会话如何处理。若授权只在登录时把角色写入长效 token，管理员降权后旧 token 可能仍包含旧角色。可以缩短 token 时长、在关键请求查数据库或使用会话版本等方式，但每种方法有性能和复杂度代价。

## 五、第三方登录建立的是外部身份映射

微信或其他 OAuth 登录首先证明用户控制某个外部平台身份。应用仍要把外部身份映射到自己的内部用户，并确定首次登录时创建什么角色、如何绑定已有账号、怎样设置本地密码。外部平台的 OpenID 不应直接当成本地用户主键，也不能仅凭相同昵称或邮箱自动合并账号。

登录回调中的一次性 code 应由服务端安全交换；AppSecret 和 session key 不应进入客户端或日志。流程要处理重复回调、外部服务错误、并发创建和首次设置密码。第三方认证成功并不自动等于本地授权成功：新用户仍受本地角色、资源归属和账号状态约束。

## 六、常见授权模型

- **RBAC**：按角色授予权限，适合“会员、编辑、管理员”这类职责清晰的系统。
- **资源归属**：判断资源的 owner 与当前主体是否匹配。
- **规则/属性授权**：结合资源状态、组织、时间或其他属性作决策。

真实系统经常组合使用。角色应来自可信服务端状态，资源归属要查询或可靠绑定；不要把用户可提交的 query 参数当成权限事实。拒绝访问时也要避免泄露不应公开的资源详情。

## 七、授权测试要覆盖成功与失败路径

测试至少包括匿名访问、过期或伪造凭证、角色不足、非资源所有者、被禁用账号和合法授权访问。要检查 HTTP 状态、业务错误码，以及数据库没有发生不该发生的变化。只测“管理员可以操作”不足以证明会员不能越权。

错误语义要稳定：未认证通常返回 401，已认证但无权通常返回 403；有些系统出于防枚举考虑对不存在和无权资源采用相同 404，需按产品安全策略定义。客户端根据状态处理重新登录或提示权限不足，不要把所有 403 都刷新 token。

## 小结：登录成功之后，权限检查才开始

认证确认请求主体，授权逐次判断该主体能否执行当前动作并操作目标资源。会话、JWT、Cookie 和第三方登录是身份传递机制，不是业务权限本身。把服务端授权作为真实边界，对角色、资源归属、状态和会话撤销建立明确规则，并对拒绝路径做自动化验证。
