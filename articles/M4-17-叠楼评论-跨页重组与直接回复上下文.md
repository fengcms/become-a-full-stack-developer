# 成为全栈·Flutter App 篇·叠楼评论：跨页重组与直接回复上下文

> 评论分页返回的是一段数据，不一定是一段完整讨论。回复可能属于尚未加载的楼层，树形结构还可能包含循环或异常父节点；客户端必须在不丢语义的前提下组织展示。

{{IMG:M4-17-封面}}

## 本文目标

解释 Flutter 评论组件如何展示直接回复对象、跨页重组楼层、限制视觉缩进并防止异常数据造成无限递归。

## 前置知识

了解评论 parentId、分页和 Flutter 列表。实现位于 `features/comments.dart` 与 `features/comment_widgets/`。

## 先区分数据关系和视觉层级

评论记录的 parentId 表达回复关系；视觉上无限缩进会让深层回复迅速变得不可读。项目显示直接回复对象与上下文，但将缩进限制在有限层数。层级限制只影响布局，不应改写服务端真实关系。

```text
评论 A
  回复 B（回复 A）
    回复 C（回复 B）
      回复 D（仍展示回复对象，缩进不再增加）
```

读者仍需知道 D 回复谁，不能只靠缩进猜。

{{IMG:M4-17-评论结构}}

## 跨页数据要归回原楼

若评论列表按分页加载，某条回复可能先于其父楼进入客户端，或父评论出现在上一页。按当前页面顺序直接渲染，会让回复成为孤儿。客户端需要在已加载集合中按 ID 建立关系索引，并在新页到达后重组。

若父楼暂时未加载，界面要保留“回复某用户”的上下文；不要凭空把它提升成新的顶级楼层。后续加载父项后再归并，同时防止重复 ID。

## 异常关系必须防循环

服务端数据也需防御性处理。parentId 指向自身或形成 A→B→A 循环时，递归渲染可能无限展开。项目使用循环保护测试，发现无法继续追溯时以有限上下文呈现，而不是崩溃。

```text
visited = {当前评论 ID}
遍历 parentId：
  若 parentId 已在 visited → 停止追溯并标记异常
  否则加入 visited，继续
```

伪代码说明算法意图；以当前模型和测试实现为准。

## 删除和提交状态影响交互

评论提交失败要保留输入，成功后刷新相关楼层；删除只允许后端授权范围内的操作。UI 不因按钮存在就推断用户有权限。分页长度也不等于某楼回复总数，后端没有提供总量时不能标“共 N 条回复”。

## 验收场景

测试跨页父子归并、父楼缺失时保留直接回复对象、重复 ID 去重、无限层缩进上限、自环/循环保护、删除权限失败和网络失败后输入保留。当前本地集成测试在隔离后端验证评论写入；生产环境不执行写入验收。

## 用索引避免每条回复重复扫描全列表

如果每渲染一条评论都从整个数组里找父级，数据量增大后会反复做 O(n) 搜索。分页接入时把已知评论按 ID 建索引，并在增量加载后重建或更新索引：

```text
byId = { comment.id: comment }
for comment in newlyLoaded:
  byId[comment.id] = comment
  root = walkParents(comment, byId, visitedIds)
  attach comment to root when parent is present
```

父级尚未加载时要暂存可见回复，等新页抵达再归并；渲染顺序变化不能把同一条评论显示两次。还需区分 API 返回的“当前页条数”和一楼全部回复总数，后者不存在时就不展示未经证明的数字。

## 评论加载、发送和删除是三个独立状态

分页加载失败不能清空已有楼层；发送中应暂时防止重复点提交；成功后按返回评论 ID 合并或重新拉取当前页；删除自己的评论则以服务端响应为准，权限失败时保留内容并反馈。不要让一个 `isLoading` 同时控制首屏、加载更多、发送和删除，否则一次后台刷新会禁用整页所有操作。

```text
initialLoad / loadMore / submit / delete
分别拥有 loading、error 和 retry action
```

隔离后端集成测试覆盖真实发表评论，纯 Dart 测试覆盖跨页归并和 parent 循环；两类测试结合，才能既验证业务算法又证明 API 写路径可走通。

## 刷新期间不要丢掉正在输入的回复

评论组件把 `TextEditingController` 和当前 reply target 留在 State；缓存通知只触发评论列表 reload，不重建整个 composer。发送请求时保留输入，只有服务端返回 approved 才清空文本和回复对象；若状态未通过或网络异常，正文继续留在输入框供修改和重试。

```dart
if (c.status == 'approved') {
  setState(() {
    items.add(c);
    reply = null;
    input.clear();
  });
} else {
  notice(context, c.rejectedReason ?? '评论未通过，请修改后重试');
}
```

这是项目中的真实处理分支。评论可能进入审核，所以 HTTP 请求返回对象不等于评论已公开；界面按照返回状态提示，而不是立刻把所有提交都插入公开楼层。

## 小结

评论呈现要同时尊重 parentId 关系和有限屏幕空间。跨页重组保留讨论上下文，循环保护避免恶意或异常数据拖垮 UI，数量和权限则服从后端实际契约。树形 UI 不意味着客户端可以自行定义评论业务。
