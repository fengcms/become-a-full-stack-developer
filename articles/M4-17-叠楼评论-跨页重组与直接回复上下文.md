# 成为全栈·Flutter App 篇·叠楼评论：跨页重组与直接回复上下文

评论功能上线前，我在原型里点了两下就发现了问题。

一篇评论有 12 条回复，正常；翻到第 2 页，回复又来 15 条。**但第 2 页里有一条回复，它指向的是第 1 页的某条评论。**

界面上，它孤零零地出现在第 2 页最底下，头顶写着"回复 张三"，可张三那条明明在上面那页。用户会问：这楼怎么断了？

后端分页是平的，前端要显示成楼。而"平的数据"和"楼的显示"之间，隔着一个比想象中麻烦的问题。

这篇讲 `flutter-app/lib/features/comments.dart`（296 行）里怎么处理的，以及三个我没在原型里想到的坑。

## 先分清：数据是平的，显示是叠的

先把结构说清楚。评论在数据库里是**邻接表**——每条评论有一个 `parentId`：

```text
id=1  parentId=null   "文章写得不错"
id=2  parentId=1      "同意，学到了"
id=3  parentId=1      "同问"
id=4  parentId=2      "哪里学到的？"
```

注意 id=4 指向 id=2，所以它**不是第 1 楼**，而是第 2 楼的回复。这就是"叠楼"——任意深度，不限两层。

这里有个容易偷懒的做法：既然大部分评论只两层，那我用 `parentId == null ? 楼主 : 回复` 二分不就完了？

不行。因为 `parentId=4` 的回复（如果有）会挂到 id=4 下面，二分法就把三层和两层当成了同一种。用户在三层回复里看到的缩进和"回复某某"提示都会不对。**只要你的产品允许"回复一条回复"，深度就必须是任意的。**

于是有了归组函数。整个实现只有十九行，但每一行都在处理一件事：

```dart
Map<int, List<ApiComment>> groupComments(List<ApiComment> comments) {
  final byId = {for (final c in comments) c.id!: c};
  final groups = <int, List<ApiComment>>{};
  for (final c in comments) {
    var root = c.id!;
    var at = c;
    final seen = <int>{root};
    while (at.parentId != null) {
      final p = at.parentId!;
      if (!seen.add(p)) break;
      root = p;
      final parent = byId[p];
      if (parent == null) break;
      at = parent;
    }
    groups.putIfAbsent(root, []).add(c);
  }
  return groups;
}
```

核心是那个 `while`：从一条评论出发，**一路往上走到没有 parent 的那条**，那个 id 就是这组回复的"楼"。走的过程中顺便把整条链收集进 `at` 变量，所以后面能直接构建嵌套。

注意 `putIfAbsent(root, () => []).add(c)` 里插入的是 **`c` 自己**，不是链上的父节点。也就是说 `groups` 里的每一项是"这个楼和它下面所有层级的评论"，而显示时的递归结构是在 Widget 里构建的（下一节）。

为什么这里要分开？因为 `Map<int, List<...>>` 保证了**同一个楼的所有回复在数据上是连续的**，这直接决定了"跨页重组"能成立。

## 坑一：跨页时，一条回复的父节点不在这页

上面那个 id=4 的问题，现在说清楚。

分页是从后端拿的，第 2 页里可能有一条 `parentId=1` 的回复，而 id=1 那条评论**在第 1 页**。此时 `items` 里只有第 2 页的数据，`byId` 里没有 id=1。

看循环里那两行：

```dart
final parent = byId[p];
if (parent == null) break;      // ← 父节点不在本页，停下
root = p;                       // ← 但 root 已经记下了
```

**先 `root = p`，再检查 `parent == null`。** 顺序反了这条回复就会被归到自己名下，变成一个孤立的"楼主"。

这个顺序我写错过。改对之后的实际效果：这条回复显示在"未显示在当前页的楼"的位置——因为它的 `root` 是 1，而第 1 页的评论现在不在 `items` 里，所以第 1 页的内容不会被渲染，这条回复自然也就跟着不显示。

**下次上拉加载第 1 页时，它会自动归位。** 这就是"跨页重组"的含义：不需要特殊处理，数据到齐了就自动对上了。

这个设计的代价是明确的——**往下翻几页再往回翻，中间那条回复会短暂消失**。我认为可以接受，理由有二：一是大多数用户是顺序浏览的；二是另一个选择是"把父节点的残缺信息缓存下来"，那要在客户端维护一份可能永远不完整的影子数据，复杂度和出错概率都高得多。

顺带说另一处降级，在回复框组件里：

```dart
final parent = items.where((p) => p.id == c.parentId).firstOrNull;
...
Text('回复 ${parent?.userName ?? '原评论暂不可见'}'),
```

如果引用的父评论被删了，或者在别的页，这里显示"原评论暂不可见"，而不是空白或者崩溃。`firstOrNull` 是 Dart 3 的扩展方法，避免了 `firstWhere` 找不到就抛异常的老写法。

## 坑二：数据里可能有环

上面那个 `while` 循环，有个我一开始完全没想到的风险：**如果 `parentId` 构成环，循环会永远转下去。**

```dart
final seen = <int>{root};
while (at.parentId != null) {
  final p = at.parentId!;
  if (!seen.add(p)) break;      // ← 走过了就停
  ...
}
```

`seen` 是这条路径上走过的所有 id。每走一步先 `seen.add(p)`，**返回 false 就说明这个节点已经访问过**，说明有环，立刻停止。

这行代码是防御性的，但它防的不是"理论上的可能"。本项目的契约里 `parentId` 由服务端写入，正常不会有环。但有三件事客户端管不了：历史数据被人工改过、服务端某次 bug 写错了、或者未来接入了第三方数据源。

**一个 `while(true)` 在生产环境挂起，表现为 App 直接卡死且无崩溃日志**——这类 bug 排查起来极其痛苦，因为日志里什么都没有。加这行三行的成本，几乎为零。

顺便说，`byId` 的构建用了一个 Dart 集合字面量的特性：

```dart
final byId = {for (final c in comments) c.id!: c};
```

`{for (...) k: v}` 是集合字面量里的推导式，能直接构造 Map。比 `for` 循环里 `byId[c.id!] = c` 少一行，而且是惯用写法。

## 坑三：回复别人时，父节点在另一页

前两个坑都是"读"的问题。这个是"写"的。

用户想回复某条评论，而那条评论在第 3 页。他点了那条评论的"回复"按钮，输入框上方需要显示"回复 张三"——这个信息此刻是有的（那条评论在屏幕上）。所以前端能构造请求。

但我在实现时想过一个更"贴心"的方案：**把被回复的那条评论的完整内容也一起传上去**，这样服务端可以存一份快照，日后即使原评论被删，回复也还能显示上下文。

然后我放弃了。理由是**信任边界**：客户端传来的任何内容都不能直接入库。如果这个字段能被篡改，就变成了"任何人可以在任意回复下面伪造一段引文"。而评论区的引文是用户之间互相影响的载体——伪造引文比伪造评论本身更容易造成误解。

现在的做法是最朴素的：只传 `parentId`，上下文由客户端从本地数据里取，服务端只存关系。

```dart
final c = ApiComment.fromJson(
  jsonMap(
    await ref.read(sessionProvider).api.request(
      Endpoints.comments(widget.articleId),
      method: 'POST',
      data: {
        'content': input.text.trim(),
        if (reply != null) 'parentId': reply!.id,   // ← 只传 id
      },
    ),
  ),
);
```

顺带注意 `'content': input.text.trim()`。`trim` 不是可有可无的——服务端会做长度校验，而用户打到一半的空格和换行不该占配额，也不该让首行变成空白。

## 提交后不是立刻就显示

这是评论区最容易做错的一处。看 `send()` 的成功分支：

```dart
if (c.status == 'approved') {
  setState(() {
    items.add(c);
    reply = null;
    input.clear();
  });
  notice(context, '评论已发布');
} else {
  notice(context, c.rejectedReason ?? '评论未通过，请修改后重试');
}
```

**只有 `status == 'approved'` 才 `items.add(c)`。**

按 M1 的约定，评论提交后进入三态之一：`approved`（直接过）/ `reviewing`（待审）/ `rejected`（被拒）。所以有个我们必须面对的情况：**用户提交了一条评论，它被送去审核了。**

这时候有两种做法：

- 立刻插进列表，标一个"审核中"的灰色占位
- 不插，提示"已提交，等待审核"

我选了后者，而且这个选择有个实际理由：**用户会截图发朋友圈。** 一条显示"我的评论正在审核中"的灰色条目，截图出来很难看，而且用户会反复刷新看它通过了没有。而一句"评论已提交"就结束了。

更重要的是**别把草稿内容也清掉**——看代码里 `input.clear()` 和 `reply = null` 都在 `approved` 分支里。如果被拒绝了，输入框里的文字还在，用户改了再提交就行。

不过这里有个我承认的不完美：用户提交后完全不知道状态，也无从查询。如果他的评论一直没通过，他不会知道。要解决得加一个"我的评论"列表，那是另一块功能，不在这篇范围里。**我知道它缺失，但我不打算在评论区里塞一个半成品的查询入口。**

## 删除：确认之后才动本地数据

删除更简单，但有个顺序问题：

```dart
Future<void> remove(ApiComment c) async {
  if (!await confirm(context, '删除评论', '删除后不可恢复，是否继续？')) return;
  try {
    await ref.read(sessionProvider).api.request(Endpoints.comment(c.id!), method: 'DELETE');
    if (mounted) setState(() => items.removeWhere((e) => e.id == c.id));
  } catch (e) {
    if (mounted) notice(context, e);
  }
}
```

**先确认、再请求、最后改本地。** 顺序反过来会有两个问题：本地先删了但请求失败，界面上这条评论消失了刷新又回来（幽灵）；或者不确认就发请求，用户误触直接删掉了。

注意这里只 `removeWhere(id == c.id)` 移除被删的那一条，**不递归移除它的回复**。这是对的——回复属于另一个人，而且服务端大概也允许"回复存在但父评论没了"（这就是"原评论暂不可见"那个降级存在的原因）。

删除按钮的可见性判断在 `_CommentFooter` 里，依据是 `userId` 和评论的归属。这条属于服务端该管的（M1 里已经做了权限复核），客户端判断只是为了不显示一个点了会报错的按钮，**不是安全边界**。

## 加载状态要分成三个

评论区的状态变量比文章列表多一个：

```dart
bool busy = false, sending = false, more = true;
```

`busy` 是加载中，`sending` 是发送中。为什么要分开？因为它们对 UI 的影响完全不同：

- `busy` → 显示加载指示器、隐藏"加载更多"
- `sending` → **禁用发送按钮**（`SubmitButton(busy: sending)`），但评论列表照常可点可滚

如果合并成一个变量，会出现"我正在发评论，列表也跟着转圈，滚动都卡住"这种怪异体验。而用户发一条评论可能等好几秒（要过审核、可能有内容检查），这几秒里他应该能继续浏览已有评论。

还有一个细节，`load()` 的入口判断：

```dart
if (busy || (pendingUpdate && !reset && !check)) return;
```

对比 M4-12 的列表，那里是 `if (busy && !reset) return;`——**评论区这里 `busy` 没有 `!reset` 的例外**。也就是说评论区的"刷新"不能打断进行中的加载，列表页的下拉刷新可以。

这个差异是有意的：评论区的数据变动没那么剧烈，刷新请求可以等；列表页的排序漂移要尽快响应（M4-12 讲的"翻页前检查首屏"）。

而缓存事件的处理里，评论区把 `sending` 也算进了熔断条件：

```dart
if (!mounted ||
    !cacheVisible ||
    busy ||
    sending ||                                    // ← 发送中不响应缓存事件
    (!dependencies.contains(e.key) && e.key != '*')) {
  return;
}
```

**正在发评论的时候，不因为缓存变化去重载列表。** 否则用户刚提交、服务端触发缓存失效、列表被重载，他那还没显示出来的新评论位置就变了。

## 输入草稿和楼层数据是两件事

最后一个我一开始处理错的点。

注释里写得很清楚：

```dart
/// 评论分页与输入草稿各自保留；刷新楼层数据不会清空正在输入的文字。
```

`input` 是 `TextEditingController`，`items` 是楼层数据。**它们各自独立，互不影响。**

我最初写的时候，在 `reset` 分支里顺手清了输入框——想的是"用户点了刷新评论，那就重新开始"。结果用户正在打一段两百字的长评论，点了"评论有更新，点击刷新"，**输入框里的字全没了**。

那种感觉就像你在填一张很长的表，网页刷新了一下，你打的字全没了。

现在 `reset` 只清 `items` 和 `pendingUpdate`：

```dart
void applyPage(
  PageResult<ApiComment> p, {
  required bool reset,
  required bool check,
}) {
  if (reset) {
    items = [];
    pendingUpdate = false;      // ← 只重置数据，不碰 input
  }
  ...
}
```

而 `check` 分支（检测到更新）的处理更有讲究：

```dart
if (check && page > 1) {
  pendingUpdate = p.items.map((c) => c.json.toString()).join() !=
      items.take(p.items.length).map((c) => c.json.toString()).join();
  final byId = {for (final c in p.items) c.id: c};
  items = items.map((c) => byId[c.id] ?? c).toList();   // 逐条替换，不动顺序
  return;
}
```

**它把已有评论里的同 id 项替换成新版本，但保持原有顺序。** 这跟 M4-12 的"检测到变化只提示不替换"不同——评论区的数据本来就该跟着变（新评论的点赞数变了、编辑过的评论内容变了），用户不会觉得"顺序怎么变了"，因为评论区的顺序本来就由时间决定，稳定的。

而 `page > 1` 这个条件是：只有已经翻过页的用户才需要这个提示。还在第 1 页的用户，内容变了直接刷新就行，不用多一次点击。

## 用 `part` 还是分文件

`comments.dart` 引了三个 `part`：

```dart
part 'comment_widgets/comment_footer.dart';
part 'comment_widgets/comment_reply.dart';
part 'comment_widgets/comment_thread.dart';
```

它们能直接用 `comments.dart` 里定义的 `_CommentThread`（私有类）和 `items`，不用 import，所以是 `part` 而不是普通 import。

**为什么这么分？** 因为这几个组件都是评论区的私有部件，`_CommentThread` 前面那个下划线就说明了"不出这个文件"。它们耦合极紧——三个组件共享同一套回调和同一份 `items`，拆成独立文件后每处都要把 `items` 传进去，签名会变得很长。

代价是这个项目其它地方验证过的：**`part` 文件不能自己 import，也不能独立测试。** 所以这三个组件的测试只能通过 `Comments` 整体来做。这是我接受的取舍——它们的价值在于组合后的展示，单独测一个 `_CommentReply` 意义不大。

## 验收时该看什么

评论区要验的场景比列表多，因为它多了"别人也在操作"这个变量：

| 场景 | 预期 |
|---|---|
| 回复一条在其他页的评论 | 不显示错位，父评论加载后自动归位 |
| 评论被删除后看它的回复 | 显示"原评论暂不可见"，不崩溃 |
| 提交被拒的评论 | 输入框内容保留，提示具体原因 |
| 发送中触发缓存失效 | 列表不重载，发送按钮保持禁用 |
| 输入长评论时点刷新 | 输入内容不丢 |
| 数据中存在环 | 不死循环 |

最后一条可以在测试里构造：`parentId` 指向自己，或者 A 指向 B、B 指向 A，然后调用 `groupComments`，断言它能返回结果。**这类防御性代码必须写测试**，因为它的正确性在正常数据上无法体现——不测的话，将来有人删掉那行 `seen.add` 检查，测试也不会红。

## 一条我一开始想省掉的事

`groupComments` 那个 `while` 循环里的 `seen` 检查，我最初觉得多余。理由是"服务端不会写出环的数据"。

后来我想到一个具体场景：**数据迁移**。这个项目的内容会从别处导入，如果导入脚本把 `parentId` 写错一位，或者把两条评论的 parent 互相指向，环就产生了。而导入是离线操作，跑完之后没人会立刻发现，直到某个用户打开那篇文章——然后 App 卡死。

**这不是假想的安全性问题，是一个我自己在流程里埋下的风险。** 一个 `while` 循环在生产环境挂起，症状是 App 假死且无崩溃日志，用户会直接卸载。

三行代码换掉这个风险，我认为是这整个文件里性价比最高的三行。

同类的还有那句 `if (parent == null) break;`——它挡的是"父节点不在本页"这种**正常情况**下的意外后果。写它的时候我也没觉得多必要，直到我在真机上刷了 20 条评论看到了那个断裂的楼层。

**这两处的共同点：触发条件都很罕见，但后果都是用户直接可见的。** 这类代码的判断标准不是"会不会发生"，而是"发生时有多难受"。

## 小结

叠楼评论的技术难点不在渲染，在于**它是列表之外唯一一处"客户端要自己维持结构关系"的功能**。

三个问题的答案：

1. **跨页断裂** —— 归组时先记 `root` 再检查父节点是否存在，父节点缺失的数据等到齐了自动归位。
2. **数据异常** —— `while` 里带 `seen` 集合，环出现时立即停止。
3. **草稿丢失** —— 输入框和楼层数据彻底解耦，数据刷新永不碰输入内容。

另外两个偏判断而非技术的选择：**待审评论不插入列表**（用户截图难看、也会反复刷新），**回复只传 `parentId` 不传内容快照**（客户端数据不可信，伪造引文比伪造评论更容易误导人）。

下一篇讲点赞收藏的乐观更新——那是另一个方向的问题：**操作成功了但界面还没更新时怎么办**，以及失败了怎么回退。
