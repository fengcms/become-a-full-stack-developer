# 成为全栈·Taro 小程序篇·四 Tab 与页面栈：小程序生命周期如何影响页面状态

> 页面回来了，不代表它重新创建了；数据变了，也不代表该把整页清空。页面生命周期与数据生命周期需要分别处理。

{{IMG:M5-11-封面}}

## 前言：返回文章列表，不该像第一次进站

用户从首页点开文章，点赞后再返回，期待的是继续浏览刚才的列表。若每次返回都重新加载，他会觉得页面很慢；若返回后计数永远不变，他又会觉得操作没成功。

这两种问题的根源很接近：把“页面显示”错误地等同于“页面初始化”，或者完全忽略页面重新显示。

当前小程序有首页、分类、搜索、我的四个原生 Tab，另外十个注册页面承接阅读、认证和会员操作。这篇以这个导航结构为基础，说明为什么 React Effect 之外，还必须理解平台事件。

## 两类导航，不能用一个动作糊弄

首页、分类、搜索、会员是长期入口，用 `switchTab`。文章、作者、设置、编辑器等二级页面用 `navigateTo`，返回则结束当前二级页面或回到来源。

```ts
// src/core/navigation.ts：Tab 与二级页面走不同的平台动作。
export function tab(page: string) {
  return Taro.switchTab({ url: `/pages/${page}/index` });
}
```

| 用户动作 | 导航方式 | 状态方面的期待 |
|---|---|---|
| 首页切换到搜索 | switchTab | 搜索入口有自己的状态 |
| 列表进入文章 | navigateTo | 返回后继续原列表 |
| 游客点击收藏 | 打开认证页 | 登录后回到原操作来源 |
| 会员打开编辑器 | navigateTo | 离开前保护未保存内容 |

当前认证成功优先返回来源，不能返回时再进入会员 Tab。它不把所有登录都强行变成“回首页”，因为用户可能正在评论或投稿。

不过，返回原页面并不代表自动重放用户先前的写操作。登录门禁只是把用户带回来；点击收藏、发送评论仍应由用户明确触发。自动重放涉及动作参数和幂等边界，本项目没有把它当作默认能力。换句话说，导航只解决“用户现在在哪一页”，不解决“那个动作要不要重来”。两件事分开之后，登录门禁与写操作幂等就能各自独立验收。

## 挂载读取和显示读取各有职责

资源 Hook 的 Effect 负责参数变化与初始加载；`useDidShow` 负责页面再次显示时补读。看起来重复，但底层读函数先查缓存，因此补读不一定产生网络请求。

```ts
// src/hooks/data.ts：useResource 的挂载读取与显示补读。
useEffect(() => {
  setData(undefined);
  void load();
  return () => {
    serial.current++;   // 卸载即让旧响应失效
  };
}, [load]);
useDidShow(() => {
  void load();          // 再次显示时补读，缓存命中则不产生请求
});
```

读取前还有一道闸门：路径为空，或私有资源未登录时，直接清空而不是发出注定失败的请求：

```ts
// src/hooks/data.ts：无效或无权时不做请求。
if (!path || (privateData && !auth)) {
  setData(undefined);
  return;
}
```

分页列表进一步检查距离上次成功读取的时间，以及缓存版本是否发生变化：

```ts
// src/hooks/data.ts 中 useFeed 的显示条件节选。
if (
  !lock.current && loadedAt.current &&
  (Date.now() - loadedAt.current > 60000 ||
    revision.current !== (privateData ? privateCache : cache).revision())
) void latest.current(true);
```

这段条件不是所有 Hook 的统一规则。`useResource` 在显示时会调用 load，由缓存决定是否命中；`useFeed` 则先判断是否需要重置读取。写文章时必须区分，否则读者会误以为每种资源都执行相同的时间判断。

`latest` 引用保存最近的 load，避免平台回调拿着早期闭包，使用过时页码或筛选条件。React 的渲染与平台事件注册交织时，这个问题尤其值得检查。

## 旧响应不能因为页面还在就获得写入权

用户在分类 A 加载下一页，随后切到分类 B。A 的响应晚一点回来，如果直接追加到当前数组，B 页面就会出现不属于它的文章。

更隐蔽的一种是筛选连点：第一次请求 A 还在途中，第二次请求 B 已经发出。没有序号时，A 晚到的响应会把 B 的结果覆盖，用户看到的是与当前筛选不符的列表——界面不会报错，只是内容悄悄错了。

列表 Hook 用请求序号处理这个问题：参数变化、卸载或新读取会改变序号，响应只有与当前序号一致才可以写状态。私有列表还检查会话代次，防止 A 会员的结果进入 B 会员页面。

```ts
// src/hooks/data.ts：序号与会话代次共同决定一次响应是否可写。
const id = ++serial.current,
  epoch = sessionEpoch();
// …发起请求后：
if (id !== serial.current || (privateData && epoch !== sessionEpoch())) return;
setItems(/* … */);
```

因此，我们同时维护三件事：页面参数决定当前内容，序号决定哪次读取仍然有效，会话代次决定结果属于哪个身份。这几个判断不能用一个 loading 标记代替。

写入时还有一处细节：分页追加不是简单拼接，而是按 id 去重合并，避免同一篇文章在翻页边界出现两次：

```ts
// src/hooks/data.ts：按 id 去重后再写入。
setItems((old) => [
  ...new Map((reset ? list : [...old, ...list]).map((a) => [a.id, a])).values(),
]);
```

分页锁只负责阻止重复加载，不负责证明响应归属。把 lock 设为 false 也不会让一个旧响应自动失效。

## 主动刷新与返回补读，不应有同一种代价

下拉刷新表达“我要现在联网确认”，所以调用强制读取，并在 finally 中停止平台刷新动画。用户不应因为错误响应一直看到转圈。

返回补读表达“看看刚才的数据是否仍可用”，因此允许命中缓存。触底则继续下一页，不重置已读内容。三种事件同属页面行为，但数据意图不同。

```ts
// src/hooks/data.ts：三种页面事件，三种数据意图。
usePullDownRefresh(() => {                     // 下拉：强制联网
  void latest.current(true, true).finally(() => Taro.stopPullDownRefresh());
});
useDidShow(() => {                             // 返回：时间或版本变化才补读
  if (!lock.current && loadedAt.current &&
      (Date.now() - loadedAt.current > 60000 ||
       revision.current !== (privateData ? privateCache : cache).revision()))
    void latest.current(true);
});
useReachBottom(() => {                         // 触底：续下一页
  void latest.current();
});
```

| 页面事件 | 数据意图 | 是否强制联网 | 失败时 |
|---|---|---|---|
| 下拉刷新 | 现在确认 | 是 | 停动画并保留旧列表 |
| 返回补读 | 检查是否仍可用 | 否（可命中缓存） | 保留旧列表 |
| 触底 | 续下一页 | 是 | 保留已读内容 |

当前列表失败时保留已有 items，并展示错误；资源 Hook 的失败则会清空该资源结果。这也意味着，我们并没有实现一套所有页面一致的 stale-while-revalidate 策略。保留列表是局部行为，不能把它扩大成“断网全站仍能读”。

## 一条我自己画的判断：页面事件不是数据事件

刚进小程序时，我把 `useDidShow` 当成了"页面初始化"，把 `useEffect` 当成了"数据加载"。**这个对应关系是错的**，而且错得很自然 —— 因为在浏览器 SPA 里，`useEffect` 确实经常承担初始化的角色。

画完那张事件表之后，我给自己留了四句话：

```text
useDidShow   → 这个页面又被看见了，此刻该确认什么？
useDidHide   → 它藏起来了，哪些动作该停？
useEffect    → 参数变了，哪些东西该重置？
unmount      → 它真的没了，在途的东西还有效吗？
```

**四个问题里有三个的答案不是"重新加载"。**

尤其是最后一个：**页面真的没了，在途的请求还有效吗？** 答案是没有 —— 这就是 `serial.current++` 在 cleanup 里做的事。

我把这个区分当成一条规则：**任何平台事件回调进入的地方，先问"这是通知我发生了什么"，而不是"让我重新做一遍"。** 因为前者会让我检查状态，后者会让我直接覆盖状态。

而我开头那个闪白屏，恰恰是"重新做一遍"的典型后果 —— **清空 items 是为了显示 loading，而 loading 是给请求用的，不是给页面显示用的。**



## 页面隐藏时，计时动作也要停下来

文章页有阅读计时。它不是页面一挂载就无条件上报，也不应该把用户切到别处后的时间继续算进当前阅读。

计时由显示事件安排，并在真正写入前再校验一次会话代次：

```tsx
// src/pages/article/index.tsx：五秒后写入，且写入前确认账号没变。
function startReading() {
  if (!article || preview || recorded.current) return;
  clearTimeout(timer.current);
  const epoch = sessionEpoch();
  timer.current = setTimeout(() => {
    if (epoch !== sessionEpoch()) return;
    recorded.current = true;
    void api(`/articles/${article.id}/view`, "POST", undefined, false).catch(() => {});
    if (session())
      void api("/me/history", "POST", { articleId: article.id, progress: progress.current }).catch(() => {});
  }, 5000);
}
```

当前实现以页面可见条件安排约五秒后的阅读相关动作，并在隐藏时清理计时器。公开阅读计数与登录会员历史是两个不同请求，预览模式也有独立处理。

```tsx
// src/pages/article/index.tsx：显示时安排计时，隐藏时清理并补报进度。
useDidShow(startReading);
useDidHide(() => {
  clearTimeout(timer.current);
  if (recorded.current && article && session() && !preview)
    void api("/me/history", "POST", { articleId: article.id, progress: progress.current }).catch(() => {});
});
```

这类副作用比一个简单列表更能说明生命周期的重要性。只靠卸载清理，无法覆盖页面还在栈内但已隐藏的情况。实际计时分支在文章页中集中管理，而不是散在 Markdown 子节点里。


## 把一次返回写成时间顺序，就容易发现漏洞

我们可以用一个无需复杂业务的检查场景：列表读取成功，进入详情，执行点赞，返回列表。缓存失效版本变化，列表显示事件决定补读，共享互动状态则先提供即时计数。

如果返回时无条件清空 items，用户看见闪白；如果完全不检查版本，服务器的新数据无法进入；如果只相信本地计数，其他用户的变化又永远看不到。三个机制各管一段时间，才让返回既快又能校准。

再加入慢请求：列表补读开始，用户立刻切换筛选。响应虽然成功，却属于先前参数，必须由序号拒绝。页面存在、网络成功和响应有效，不能彼此替代。

### 不要把“恢复”说成比实现更多的东西

当前 Tab 与二级页面栈能保留部分本次运行状态，内存缓存能减少短时间读取，本机草稿可以跨关闭恢复。但文章列表的滚动位置没有被保存成跨冷启动的完整快照。

长时间后台后再打开，进程也可能已经重建。这个场景不能继续依赖原先 React 状态；应从路由、会话与必要存储恢复，再读取服务端事实。是否完整满足各种后台时长，需要设备矩阵，不宜从工具里的短暂切换推导。

页面栈也可能无法继续增加二级页。当前 navigateTo 失败显示返回重试提示，没有宣称无限层级导航。内容中连续跳文章时，需要留意这一平台行为；未来若要替换当前页，应单独设计返回语义。

把这些动作整理成一张事件表，比通读 Effect 更容易发现漏洞：

| 触发事件 | 捕获参数 | 允许的副作用 | 清理 / 拒绝条件 | 失败反馈 |
|---|---|---|---|---|
| 页面显示 | 路由参数 | 补读、安排计时 | 会话代次变化则放弃 | 保留旧数据 |
| 页面隐藏 | 当前进度 | 取消计时、补报进度 | —— | 静默 |
| 页面卸载 | —— | 递增序号、清计时 | —— | —— |
| 下拉刷新 | —— | 强制联网 | finally 停动画 | 保留旧列表 |
| 触底 | 当前页码 | 续下一页 | 锁或序号不符则拒绝 | 保留已读内容 |

这张表也是给后续协作者的接口说明：新页面只要回答“我属于哪一类事件、捕获什么参数、允许什么副作用”，就不必复制一堆看不出用途的 Effect。

## 编辑器需要相反的离开策略

阅读页可以取消非关键任务；编辑器离开时，却要尽量保存本机草稿。它还有未保存提醒和账号归属检查。相同的隐藏与卸载事件，不同业务要给出不同响应。

所以，我不建议做一个万能生命周期 Hook，把所有页面离开都包装成“清理”。先回答动作的产品含义：取消、保存、确认，还是重新校验？再选择平台事件。

开发工具中已经观察过登录返回、编辑保存与主题切换。长时间后台恢复和真机页面栈组合需要后续对应验收；这篇给出的是当前实现和检查方法。

### 清理动作别互相抵消

Hook 卸载时递增序号，计时器隐藏时取消，编辑器卸载时保存草稿。这些操作可能都发生在一次返回中，但它们不应该通过同一个“清空全部”动作处理。

尤其本机草稿属于用户输入，缓存属于可再读取数据。退出和清理阅读缓存的逻辑要按所有权区分，不能因为大家都在本机就一起删除。生命周期设计会一路延伸到存储策略。

对后续协作者，我更愿意留下一个事件表：触发事件、捕获的参数、允许的副作用、清理条件、失败反馈。它让潜在竞态能被讨论，也让新页面无需照抄一堆不知用途的 Effect。

接着读请求与会话层和有界缓存。页面回来的速度，最终取决于导航、读取与身份边界能否配合。
