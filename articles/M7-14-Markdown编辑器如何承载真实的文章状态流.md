# 成为全栈·Vue 管理后台篇·Markdown 编辑器如何承载真实的文章状态流

> 编辑器不是一个“大文本框”。它需要承载正文、摘要、封面、分类、标签、状态流转、图片上传、保存反馈、预览和离开保护。本文从 Vue 后台的文章编辑页出发，分析 Markdown 编辑器如何融入真实内容工作流。

## 前言：把编辑器嵌进内容生命周期

Markdown 编辑器常被当作第三方组件来介绍：装依赖、放进页面、绑定一个 `v-model`。但后台文章创作的主要复杂度不在工具栏，而在内容如何从未保存的表单成为草稿、待审核或已发布文章；编辑过程中何时允许离开；上传中的图片能否被保存；保存失败后是否保留输入。

本项目使用 `md-editor-v3` 承载正文，并由页面负责文章实体的其它字段和动作。编辑器控制内容编辑体验，页面将内容和发布设置组成契约请求，再依据当前状态选择保存、发布或下架操作。工具组件不会自行决定后端状态流转。

## 编辑页有两种入口：创建与编辑

页面依据 route 参数和路径判断当前是新建还是编辑。编辑模式通过 Vue Query 查询详情，收到数据后填入标题、正文、摘要、封面、分类和标签；新建模式则从空草稿开始。分类树与标签列表是另一组稳定查询，提供选择项。

加载阶段需要和编辑态区分：详情仍在请求时显示加载提示；请求失败时显示错误并提供重试；详情还没到之前，不能把空表单当作真实数据让用户误以为文章内容为空。查询成功后才将 `loaded` 设为 true，避免初始化写入触发 dirty 状态。

这个 `loaded` flag 看起来简单，却对应一个重要事实：从服务器回填表单与用户编辑表单是两种不同状态转移。若不区分，watcher 可能在加载详情时就报告“有未保存的修改”。

## 正文、元数据与发布设置分开组织

表单将正文和发布设置放在两个 tab。正文包含标题与 Markdown 内容，设置包含摘要、封面、分类和标签。它们最终组成一份 `ArticleCreate` payload：

```ts
function payload(status: ArticleStatus): ArticleCreate {
  return {
    title: title.value.trim(),
    content: content.value,
    summary: summary.value || null,
    coverImage: coverImage.value || null,
    categoryId: categoryId.value,
    tags: tags.value,
    slug: saved.value?.slug ?? null,
    status,
  }
}
```

有些字段是可选或 nullable，前端要按契约表达“没填写”的方式：这里空摘要和空封面映射为 `null`，分类可以为 `null`，标签使用数组。TypeScript 的请求类型来自 OpenAPI 生成 schema，提交 payload 时应逐项核实字段含义，不要把字符串空值、`undefined` 和 `null` 当成必然相同。

标题和正文不能为空，标题、摘要和正文有契约长度限制；发布前分类为必填。保存验证失败时，界面切到对应内容或设置 tab，并给用户明确提示。校验在前端提升体验，服务端仍必须执行相同的权威验证。

## 草稿、待审核、发布和下架不是按钮标签

项目有文章状态流：会员可以创建草稿或提交审核，编辑可以审核并发布，管理员可以按契约更改状态。编辑页保存修改时保留现有状态；点击发布则以 `published` 提交；对于已发布文章，下架调用状态接口转为 draft。动作和权限以冻结契约、后端状态机为准。

这里要避免一个危险简化：把“保存”一律做成 status=published，或在前端想象一条契约不存在的状态迁移。页面应根据当前实体状态决定按钮文案和可操作范围；后端返回新的文章实体后，以响应更新 `saved`，而不是只相信前端预想的状态。

单篇审核通常走专门的 approve 端点；管理员强改状态使用独立 status 端点。它们虽然都会改变 `status`，业务语义、权限和状态转换并不相同。管理文章状态流时，应该让动作名称与契约端点对应，避免用一个“设置状态”通用按钮掩盖差异。

## 保存状态：dirty、busy 与 savedAt

页面观察标题、正文、摘要、封面、分类和标签。用户修改后设 `dirty=true`；提交时进入 `busy`，防止重复保存；成功后采用服务端返回结果、清除 dirty 并显示保存时间；失败时保留输入并显示错误。

```ts
watch(
  [title, content, summary, coverImage, categoryId, tags],
  () => { if (loaded.value || !editing.value) dirty.value = true },
  { deep: true, flush: 'sync' },
)
```

实现细节有边界：新建页面初始字段改变就标记 dirty；编辑页等待回填完成后才开始追踪。保存成功清除 dirty；上传动作单独用 uploading 计数，避免文件还没完成上传就提交文章。若未来需要“撤销到已保存版本”或多字段精细变更跟踪，简单 dirty boolean 可能不够，要保存基线快照并比较。

保存成功后失效 `['articles']` 列表缓存，确保用户返回列表看到最新状态。新建保存成功后把路由替换为新文章编辑地址；这样再按保存不会重复创建记录。路由变化也应该保留用户从哪里进入，方便回到正确筛选状态。

## 未保存离开保护有两条路径

应用内导航通过 `onBeforeRouteLeave` 检查 dirty 状态，并使用确认对话框阻止意外离开；浏览器刷新或关闭标签则由 `beforeunload` 事件提醒。两者覆盖不同离开方式，不能只做一条。

上传或保存正在进行时，`busy` 会阻止普通离开确认逻辑，防止请求正在提交时状态被误判。浏览器对 `beforeunload` 的文案和行为受浏览器策略限制，网页无法完全自定义原生提示，也不能保证所有移动浏览器场景都出现确认框。

离开守卫使用 `window.confirm` 是轻量实现。若产品要求统一品牌化确认框，需要用异步导航守卫和 Naive UI Dialog 建立明确的导航决策机制；不能异步显示对话框后立即返回 true，让路由已经离开。

## 暗色主题和预览

编辑器主题绑定 UI store 解析后的 `resolvedTheme`，确保系统/手动主题变化后编辑区域同步切换。正文预览通过路由进入文章预览页，预览页继续调用详情 API并按 Markdown 内容渲染，而不是假设保存前编辑器预览等于公开文章页面最终呈现。

发布设置与预览一致性要通过实际渲染验证：封面、摘要、分类、标签和正文格式都可能影响前台显示。保存前没有后端返回文章 ID 的新稿，附件关联或预览能力也有边界，不能把本地编辑区内容当成已经线上发布。

## 编辑器组件自身负责什么？

`MdEditor` 负责 Markdown 输入、工具栏、快捷编辑和上传回调入口；父页面负责内容状态、附件 API、认证、发布设置、保存、状态流转和路由保护。父子边界清楚后，替换编辑器库不会改写文章领域规则。

同样，编辑器的 `on-upload-img` 回调只是通知宿主处理文件，不代表文件已上传。文件上传需要独立 API 请求、认证、关联文章 ID、处理文件 URL、失败恢复和按钮禁用，这部分在 M7-15 单独展开。

## 小结：编辑体验围绕状态流组织

一个可用的 Markdown 编辑页要同时处理详情加载、字段校验、状态机、保存进度、上传互锁、dirty 跟踪、离开保护和缓存失效。编辑器只是正文输入的一部分；页面和后端契约共同决定文章的真实生命周期。
