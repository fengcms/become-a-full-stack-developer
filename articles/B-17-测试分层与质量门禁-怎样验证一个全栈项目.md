# 成为全栈·基础补充·测试分层与质量门禁：怎样验证一个全栈项目

这个专栏写过 31 篇 Node 后端，我一直没有公开过测试覆盖率。

原因有点难以启齿：**前 30 篇的很多代码，我是写完之后才补的测试。**

更糟的是，补的时候我已经记不清当时为什么那么写了。有一处逻辑我知道是处理并发时序的，但它防的是什么，我想了三分钟才想起来。

而"想三分钟才想起来"意味着——**如果我明天再去改那段代码，我可能又会改错。**

这篇讲测试在这个多端项目里到底起什么作用，以及一个我观察到的现象：**测试会系统性地覆盖你想到的情况，遗漏你没想到的。** 而"想到"这件事，和写完功能之后的兴奋程度成反比。

## 三个层次，各证明不同的事

先看这个项目的实际规模（下表是实测，不是估算）：

| 层 | 位置 | 规模 | 证明什么 |
|---|---|---|---|
| 契约门禁 | `docs/api/check_contract.py` | 24 条断言 | **契约本身是否自洽** |
| 单元/集成测试 | `node-backend/test/` | 22 文件 / **155 用例** / 4170 行 | 业务规则在构造场景下成立 |
| Widget/集成测试 | `flutter-app/test/` + `integration_test/` | 11 文件 / 43 用例 / 2096 行 | 组件与页面流程 |
| 前端 lint/typecheck | `manage-frontend`、`web-frontend` | CI 工作流 | 静态一致性 |

**四层加起来，没有一层能单独证明"系统是对的"。**

举个具体例子。契约门禁通过了，155 个后端用例全绿，前端 CI 也绿。但 M4 优化时我发现的一个真实 bug 是这样的：

> Flutter 的列表页有个 `serial` 票据机制，用于解决"翻页和下拉刷新同时触发，旧响应晚回来把列表搞乱"的问题。

**这个 bug 没有任何测试失败。** 因为要触发它需要两个请求精确重叠——而我的测试都是构造假数据同步返回的。

所以"测试全绿"在这里的含义是：**我测过的那些场景是好的。** 它没有说"其他场景也是好的"。

## 第一层：契约门禁——测"契约本身"

这是最容易被忽略、但性价比最高的一层。

契约测试和业务测试问的是不同的问题。业务测试问"功能对不对"，**契约测试问"这份契约自身有没有毛病"。**

比如这三条断言：

| 断言 | 防什么 |
|---|---|
| 全部 schema 均被端点可达引用，**无孤儿实体** | 写了 20 个 schema，只有 3 个真被用到 |
| 评论三态均有端点可写入 | 枚举里有个状态，但没有任何接口能写进去 |
| 全部结构化错误码均落在 ErrorCode 枚举内 | 契约写了 4003，后端代码里没这个码 |

**"无孤儿实体"这条，我认为是全部断言里最有价值的一条。**

它防的不是"写错"，而是**"写了一半"**。你定义了一个实体，它的字段、类型、描述都很完整——**但没有任何端点用到它**。

而这类问题**人工 review 极难发现**，因为契约文件读起来是完整的，每一部分都正确。缺陷在于**部分之间的组合**：存在但没被使用。

更糟的是它会产生连锁影响：读者（包括几周后的你）看到那个 schema，会以为它是这个系统的一部分，然后**基于它写代码，或者围绕它做设计决策**。

而"三态均有端点可写入"防的是同一类问题的另一个变体：**枚举值定义了，但没路径能到达。**
写这个检查时我才发现一个真实的坑。看这段：

```python
def resp_structured_codes(resp):
    codes = set()
    if not isinstance(resp, dict):
        return codes
    aj = resp.get("content", {}).get("application/json", {})
    ex = aj.get("example")
    if isinstance(ex, dict) and isinstance(ex.get("code"), int):
        codes.add(ex["code"])
    exs = aj.get("examples")
    if isinstance(exs, dict):
        for v in exs.values():
            val = v.get("value", v) if isinstance(v, dict) else v
            if isinstance(val, dict) and isinstance(val.get("code"), int):
                codes.add(val["code"])
    return codes
```

**它同时处理了 `example`（单个）和 `examples`（多个）两种 OpenAPI 写法。**

而这个项目里**两种写法都存在**——因为它们在 YAML 里都合法，写哪个都"对"。

我第一版只处理了 `example`。于是：

- 那些用 `examples` 写的错误响应，**错误码被漏掉了**
- 而漏掉的意思是"这个码不在 ErrorCode 枚举里"这条检查**对它们不生效**
- 结果是**契约里可能存在一个后端根本没有的错误码，而门禁说通过了**

**这不是门禁抓不到，是门禁自己失效了一部分。**

而更值得记的是：**`examples` 里每一项还可能是 `{value: {...}}` 包装形式**，所以代码里才有那行 `v.get("value", v)`。

三层判断嵌套在一个 `if` 里：是不是 dict → 取出 value → 是不是 dict → code 是不是 int。**四个条件任一不满足就跳过**，而"跳过"意味着这条响应不贡献任何错误码。

**这是"防御性解析"的典型代价：它保证了不崩，但也保证了漏。** 而漏在这个场景里是危险的——因为漏掉的恰好是"契约写了但实现没有"这种最该抓的问题。

这个坑我现在标注在检查脚本的注释里：**解析必须覆盖全部合法写法，否则门禁是"部分生效"的假绿。**



**这个门禁在写出来的过程中就抓出了两个现存的错**——一个 `Comment` 的 `hidden` 状态没有写入路径，一个 `Sort` 枚举值没有端点支持。**这不是预期中的功能，是意外收获。**

## 第二层：业务测试——测"我以为的规则"

这一层的关键是：**它的测试样本是自己构造的，所以它只能证明"构造场景下的规则"。**

看一个真实的测试用例，看它保护的是什么：

```ts
it('并发首次登录只建一人，设置只成功一次且失败方不撤销成功方令牌', async () => {
```

**这行用例名保护了三件事**：

1. 并发首次登录只建一个人
2. 设置凭据只成功一次
3. **失败方不会撤销成功方的令牌**

第三点是 M1-32 讲的那个 `changes()=1` 的原因：两个请求竞争，失败的那个如果无条件撤销 refresh token，会让用户"既没设置成功、又被登出"。

**而这个 bug 在串行测试里永远不会出现**——串行时第一个失败之后不会有第二个请求来"顺手撤销"。

所以这条用例名必须把三件事都写出来，**因为它们防的是三个不同的失败**。写成"并发场景测试正常"，将来失败时你根本不知道是哪一件坏了。

### 用例名就是测试文档

这一点我在 M1-33 讲微信测试时展开过，这里再强调一次，因为它在 155 个用例里的价值被放大了。

对比：

```ts
// 不好的命名：失败时你只知道"expected 1, actual 0"
it('并发测试', async () => { ... });

// 好的命名：失败时你直接知道坏了什么
it('并发首次登录只建一人，设置只成功一次且失败方不撤销成功方令牌', async () => { ... });
```

**155 个用例的名字加起来，就是一份可读的功能规格说明。**

而它还有另一个作用：**当有人（包括你自己）问"这个系统保证什么"时，你可以直接把测试列表念一遍**，而不是去翻设计文档。因为**测试列表不会过期，设计文档会**。

## 第三层：静态检查——测"写法一致"

第三层是 lint 和 typecheck，它们的特点是**快到可以在每次保存时跑**。

这一层看起来最简单，但它防的东西有自己的性质：**它抓的是"人眼最容易忽略的东西"。**

比如：

- 一个变量声明了没用（`no-unused-vars`）
- 一处类型不匹配（TypeScript 会抓）
- 一个 import 顺序不对（lint 抓，虽然是风格问题）
- **一处 Promise 没有 await**（这类需要 `no-floating-promises` 之类的规则）

最后这条在本项目里抓到过真实问题。**一个没 await 的 Promise 不会让程序崩溃，它只是让错误在别处冒出来**——而"在别处"意味着你会往完全错误的方向排查。

**静态检查的价值在于它对"人累了"免疫。** 下午四点改第 15 个文件时，人眼不会注意到少了个 await；但 lint 会，每一次都会。

## 我为什么不为覆盖率补测试

Flutter 有官方的覆盖率工具，我看过那份报告——**大约三分之一**。

而我**不打算补那三分之二**。理由在 M4-26 里说过，这里再说一遍更完整的：

**测试的投入应该和"错了之后能不能被用户发现"成反比。**

| 代码类型 | 错了的表现 | 用户会发现吗 | 值得测吗 |
|---|---|---|---|
| 缓存键计算 | 用户看到别人的数据 | 会，且很严重 | **必须** |
| 状态机转换 | 按钮显示错误的动作 | 会 | **必须** |
| 权限校验 | 越权访问 | 也许不会（直到出事） | **必须** |
| 表单校验规则 | 错误提示 | 会 | 值得 |
| 某个卡片的 padding | 视觉不对 | 只有设计评审能看 | 不如去看一眼 |
| 某个 getter 的实现 | 视情况 | 也许 | 跟着调用方测 |

**补覆盖率是为了让数字好看，而我判断那样做会掩盖真实风险。** 一个"低覆盖但关键路径全测"的测试集，比"高覆盖但大半是渲染成功断言"的测试集有用得多。

举个反面例子：如果给 122 个 Widget 各写一个"渲染出来不崩溃"的测试，覆盖率会好看很多。**但它们抓不到任何 bug——因为大部分 bug 不导致崩溃。**

这个判断有一个前提：**我知道哪些路径重要。** 这个判断如果错了就会漏。所以现在的做法是：**每次真机或线上出问题，回来补一条测试。**

而 M4-25 讲的那类问题（大字号、深色对比度）**我没有任何机制**——只能靠 review 时记得。**这是我知道的缺口，写在这里而不是假装它不存在。**

## 修 bug 时必须补测试

这是我这条规则的核心，而且它不是"应该"，是"必须"。

理由有一个：**修 bug 的那一刻，你对那个 bug 的理解是最深的。**

比写功能的时候更深，因为你在复现和定位上花了时间。**你刚刚搞明白"为什么两个请求会重叠""为什么这个响应会被丢弃"——而这三个小时后你就会忘掉。**

所以规则是：**每次修 bug，必须同时加一条测试，即使那个区域本来就有测试。**

M4-10 那个 `AsyncPane` 的例子正好是这条规则的由来：

我修的是"后台更新被新请求取代，而页面不可见导致数据永远停在旧值"。修完之后我意识到——**我的假 Repository 不支持制造"被取代"这个场景**，所以这类 bug 测不出来。

于是我给假 Repository 加了那个能力：

```ts
class ControllableRepository extends FakeRepository {
  var supersedeNext = false;
  // 下一次 load 立刻让前一次抛 CacheSuperseded
}
```

**这个能力是为了测那个 bug 才加的，之前没人想过要它。**

而这条测试后来又抓到过一次同类问题。**一次投入，两次回报。**

## 一个真实的缺口：node-backend 没有 CI

体检这篇的时候我发现一件事，如实说：**`node-backend` 没有 CI 工作流。**

而 `manage-frontend` 和 `flutter-app` 都有。

后果是明确的：**后端的 155 个测试不会在每次提交时自动跑**，只在我本地主动执行。而这意味着——**"本地全绿"和"提交时全绿"之间有一段依赖自觉的空白。**

而 M1-34 那个 bug（`redirect: 'error'` 在 workerd 不被支持）**本质上就是 CI 该抓而没抓的**：本地 Node 的 fetch 支持这个选项，本地测试也全绿，只有目标运行时才会崩。

那件事我最后是手动用 Miniflare 复现才发现的。**而手动复现不会每次提交都做。**

所以这篇要记的债是：**node-backend 需要一个 CI，至少跑 typecheck + test + 契约门禁三条。** 加上"针对目标运行时的最小执行检查"，才能防住 M1-34 那类问题。

**我不写"以后会加"，因为"以后"经常等于"不会"。** 这条债记在这里，等它被解决或者被明确放弃。

## 一条我一开始想省掉的事

那 24 条契约断言，第一版只有 6 条，而且**我打算等"真正出问题了"再加**。

结果第一次出问题就是那 6 条没覆盖的——我给 `Comment` 加了 `hidden` 状态，但没有端点能让评论进入它。

它在代码里完全正常：schema 有这个枚举值，TypeScript 类型有它，前端的 `switch` 也加了分支。**所有测试都通过。**

而它的实际效果是：**`hidden` 是一个永远到不了的状态**，那个 `switch` 分支是死代码。

这个问题**没有任何 review 会发现**，因为它的每个部分都是"正确"的。

而更让我警觉的是另一件事：**当时写那个 `hidden` 分支的人是我自己。** 我写的时候觉得"以防万一"——万一以后有这个需求呢。

**但"防御性代码"在这里有个副作用：它掩盖了一个事实（没人知道这个状态怎么产生）。** 一个没人知道怎么产生的状态，最终要么被删掉、要么一直误导读代码的人。

所以现在我的判断标准变了：**不是"缺测试就加测试"，而是"发现了一个不存在的东西（不可达状态、孤儿 schema、无用分支），就补一条断言防止它再次被无声地加进来"。**

**门禁的职责不只是"防止退化"，还有"防止不存在的东西被悄悄加入"。**


这条用例的实现方式也值得看，因为它示范了**怎么测并发而不依赖时序**：

```ts
it('并发首次登录只建一人，设置只成功一次且失败方不撤销成功方令牌', async () => {
  const [a, b] = await Promise.all([wechat(), wechat()]);
  expect(a.user.id).toBe(b.user.id);                        // 同一个身份
  expect(await db.select().from(users)).toHaveLength(1);    // 只建了一个用户

  const result = await Promise.all(
    ['first', 'second'].map((username) =>
      post('/me/setup-account', { username, password: 'Password123' }, a.accessToken),
    ),
  );
  expect(result.map((r) => r.status).sort()).toEqual([200, 409]);   // 一成一败
  // 关键断言：只允许一个有效会话，失败方不能把成功方的令牌撤销掉
  expect((await db.select().from(refreshTokens)).filter((t) => !t.revokedAt)).toHaveLength(1);
});
```

**注意它没有用 `sleep`。**

很多人测并发会先 `await sleep(100)` 制造重叠，但那样测试结果**依赖机器速度**——CI 慢一点就不重叠了，测试变成"永远通过但什么也没测"。

而这个写法用的是 **`Promise.all` 同时发起两个请求**，重叠由运行时保证。

而**最后那行断言是最能说明问题的一条**：

```ts
expect(refreshTokens.filter((t) => !t.revokedAt)).toHaveLength(1);
```

它验证的正是 M1-32 讲的 `changes()=1`：**如果失败的那个请求无条件撤销了所有令牌，那这里会是 0。**

**也就是说，这条断言直接锁住了"条件绑定"那个设计。** 如果将来有人把 `changes()=1` 删掉（觉得"反正事务会回滚"），这条测试立刻变红。

**这比在注释里写"这里很重要"可靠得多。**


## 小结

测试在这个项目里的作用，可以拆成四句话：

1. **契约门禁测"契约本身有没有毛病"** —— 孤儿 schema、不可达状态、不存在的错误码。
2. **业务测试测"我以为的规则在构造场景下成立"** —— 而"我以为"这三个字是关键。
3. **静态检查测"写法一致"** —— 它对"人累了"免疫。
4. **跨端一致性谁也测不了** —— 除非你显式构造跨端场景。

而最有用的一条工作习惯是：**修 bug 时必须同时补测试。** 因为那一刻你对 bug 的理解最深，而测试是最便宜的方式来不让这份理解流失。

至于我的取舍：**不为覆盖率补测试，只为"错了用户会发现"补测试。** 这个判断的前提是我知道哪些路径重要——如果判断错了，靠"每次出问题回来补"来兜。

**那条兜底现在有个洞：node-backend 没有 CI。** 这是真实的债，写在这里。
