# 成为全栈·基础补充·测试分层与质量门禁：怎样验证一个全栈项目

> 测试通过不是一句“没有报错”，而是一组针对不同风险的证据。理解每种测试能证明什么、看不到什么，才能把质量门禁设计得有用又不过度。

{{IMG:B-17-封面}}

## 前言：为什么“我本地点过了”不够

手动打开页面，注册一个账号，点几次按钮，是很有价值的检查。但它只能覆盖你当时走过的路径：某个浏览器、某组数据、某种身份和某个运行环境。它很难稳定重放并发刷新、数据库回滚、过期 Cookie、异常文件上传或分页边界。更难的是，当代码改动后，没人知道要重新点哪些页面。

测试的目标不是把所有代码都包起来，而是让重要行为可以重复验证。不同层级各自回答不同问题：函数计算对不对？HTTP 边界是否符合约定？真实数据库事务是否成立？两个后端是否保持同一产品行为？客户端能否继续调用？没有一种测试能回答全部问题。

## 一、从风险出发选择测试层

可以把一个请求画成一条链：

```text
客户端 → HTTP/API → 业务规则 → 数据库/文件/外部服务
            ↑          ↑              ↑
         边界测试    单元/服务测试     集成测试
```

这张图不是要求每层都写同样多的测试，而是帮助定位失败。敏感词比例算法适合快速单元测试；角色权限适合通过 HTTP 边界验证；唯一约束和回滚要用真实数据库；网页会话刷新则需要让现有请求层代码实际发请求。

| 测试层 | 适合检查 | 不足以证明 |
|---|---|---|
| 静态检查与编译 | 格式、类型、引用、部分危险模式 | 业务行为正确 |
| 单元测试 | 状态机、排序解析、纯函数、边界值 | ORM 与真实数据库语义一致 |
| HTTP/集成测试 | 路由、鉴权、信封、Cookie、数据库后置状态 | 生产平台与真实外部服务可用 |
| 契约测试 | 请求/响应结构符合接口定义 | 业务流程完整、并发安全 |
| 差分测试 | 同一输入下两种实现的行为差异 | 两者都符合产品，或输入集合足够完整 |
| 客户端回归 | 既有调用代码能否继续使用 | 所有 UI 页面和真实设备环境都通过 |
| 手工验收 | 视觉、易用性、真实场景 | 可重复覆盖所有历史缺陷 |

测试策略应由风险决定。密码校验、支付和权限边界，错一次代价高，应有明确自动化保护；纯展示性文字换行，手工确认也许更经济。不要为了追求覆盖率数字，让测试数量代替风险判断。

## 二、一个测试用例至少要说清四件事

一个可读的测试，通常包含准备、动作、结果和清理：

```text
准备：会员 A 已登录，文章属于作者 B，文章仍是草稿
动作：会员 A 请求发布这篇文章
结果：返回 403；文章状态仍为 draft；没有发布通知
清理：删除临时数据或回滚测试事务
```

仅断言“返回 403”不够。如果错误处理器已经返回了正确状态码，但业务层此前误写了文章，页面看起来安全，数据却已经被污染。反过来，只检查数据库没变，也无法确认客户端得到的是契约约定的错误信封。

高价值测试通常会覆盖两类结果：外部可见行为和内部后置状态。前者包括 HTTP 状态、业务码、字段存在性和 Cookie；后者包括文章是否发布、通知是否写入、刷新令牌是否消费、计数是否增加。错误路径也需要检查事务是否回滚、对象是否清理。

## 三、契约测试与差分测试不是一回事

契约测试拿一次响应对照 OpenAPI：字段类型、是否允许 null、错误结构是否符合定义。差分测试则拿同一请求分别调用两个实现，比较它们的行为。二者可以同时发现不同问题：两个后端可能响应完全一样，但都违反契约；也可能都各自通过结构校验，却一个返回默认 pageSize 10、另一个返回 20。

项目 Go 重写阶段做了真实的跨实现验证：74 次成功流程请求覆盖冻结契约的 68 个操作，71 项比较完全一致，3 项差异由契约或产品规则解释；另有 111 次鉴权失败比较全部一致。数字不能解释所有问题，报告还要明确输入范围、版本、测试数据、随机字段如何处理，以及哪些客户端环境被替身模拟。

差分测试的比较器应默认严格。随机 token 可以列入有限规范化白名单，但状态码、null、字段类型、数组顺序、计数不能一股脑忽略。否则测试变绿只是因为我们不再观察差异。

## 四、真实环境测试很重要，但测试环境也要隔离

SQLite 测试通过，不等于 PostgreSQL 和 MySQL 也正确。数据库的唯一冲突、布尔类型、更新时间、行锁、序列和 DDL 事务行为都可能不同。M6 因此对 PostgreSQL 17、MySQL 8.4 和 SQLite 分别运行迁移、升级和完整业务流程，而不是只换连接字符串。

外部微信服务和对象存储则使用可控替身验证超时、错误响应和补偿逻辑。替身能稳定制造罕见失败，但它不能证明真实账号权限、网络策略或云厂商配置正确。测试报告应该说清“真实数据库”“真实 HTTP 客户端代码”“微信替身”“UI 未覆盖”等范围，避免让一个绿色 CI 被读成完整生产验收。

隔离同样关键：测试用独立数据库、随机临时目录和明确凭据；不能拿生产数据库做失败注入，也不要把测试令牌、真实用户数据和 AppSecret写进日志。可重复、可清理的测试环境会让失败更容易被调查。

## 五、质量门禁要按反馈速度分层

每次保存都运行所有容器数据库、四端 smoke 和完整差分，成本会很高。可以按反馈速度安排：

1. **提交前快速检查**：格式、静态分析、编译、单元测试。
2. **合并前完整检查**：HTTP 集成、契约覆盖、真实数据库迁移和关键并发测试。
3. **发布前验收**：差分、客户端回归、目标平台构建、人工关键流程和安全配置复核。

快速检查帮助开发者马上定位简单问题；慢检查覆盖跨层风险。即使 CI 分层，也要把必需门禁明示，不让“本地跑得快”变成跳过核心验证的借口。失败时保留日志、版本、数据库和输入范围，避免只看到一个绿色勾或一个红叉。

## 六、覆盖率是线索，不是正确性分数

行覆盖率可以发现完全没被执行的代码，却不能说明断言是否有意义。一个测试可以执行每一行，却只断言“程序没有 panic”；另一段关键并发代码也可能只有少量行，但它决定刷新令牌是否会被重复消费。测试质量更依赖边界、状态变化和失败场景。

可以用“风险—证据”表来检查测试计划：

| 风险 | 最低有用证据 |
|---|---|
| 未登录访问会员资源 | HTTP 鉴权状态和错误码测试 |
| 更新时字段被意外清空 | 缺失、null、零值三类输入与数据库结果 |
| 重复点赞让计数增长两次 | 并发请求、关联行数和计数后置状态 |
| 通知写入失败但文章已发布 | 故障注入与事务回滚检查 |
| 新后端破坏现有客户端 | 真实请求层回归与关键会话流程 |

每次发现线上或验收缺陷，先问“哪一条证据本应抓住它”，再补相应测试。这样回归集会随着真实风险成长，而不是机械地给每个函数配一个镜像测试。

## 小结：测试是分层的证据，不是一张绿灯截图

先明确要证明的行为，再选择最靠近风险的测试层；同时检查响应和状态、用真实数据库验证数据库语义、用替身控制外部故障，并公开测试边界。一个可信的交付结论通常来自多种互补证据，而不是单一覆盖率、一次手工点击或 CI 的绿色图标。
