# 成为全栈·Flutter App 篇·列表分页与下拉刷新：去重、失败保留和返回位置

滚到列表底部时再请求下一页，是分页最容易的一步；难的是刷新失败不能清空已经读到的文章，Tab 返回不能把滚动位置重置，第一页更新后还不能继续拼接旧版本的第二页。

我会沿 `ArticleFeed.load()` 的实际流程，拆解 reset、append、版本检查和快照恢复，并用代码说明一次刷新如何避免列表闪空和页间重复。

## 分页状态必须包含查询身份

页码不是完整列表身份。分类 ID、标签、搜索词和排序条件变化，都是新的查询；若沿用旧页游标，就会把不同查询的文章拼起来。缓存快照 key 应由 endpoint 和全部筛选条件组成。

```text
articles?category=3&page=2
articles?tag=flutter&page=2
search?q=flutter&page=2
```

这三个“第 2 页”互不兼容。列表端还要按稳定文章 ID 去重，并只在仍可追加时触发下一页，避免滚动接近底部时重复发请求。

## 下拉刷新要先保留画面

传统做法是刷新时清空列表再重新加载，用户会看到闪烁和空白。项目的刷新保留当前内容，拿到新结果后再替换；请求失败则继续显示旧数据并给出反馈。

```text
已有列表 A → 用户下拉
显示 A + 刷新指示器
成功得到 B → 安装 B，清除旧分页
失败 → 保留 A，显示可重试提示
```

重新验证发现新版本时，旧列表暂停继续追加，避免第 1 页是版本 B、第 2 页仍是旧版本 A。用户接受刷新后，旧分页被清除再载入新快照。

## 返回 Tab 应保留列表和位置

从文章详情返回列表，期待回到原来的滚动位置，而非再次从首屏开始。项目限制保存的查询快照数量及每个快照页数，活跃列表可以继续加载。保存快照也要关联查询 key，否则返回不同搜索条件时会恢复错数据。

## 客户端无法制造服务端快照

即使客户端页面缓存完美，页码接口若没有 snapshot/version token，服务端在两次翻页之间插入或删除文章仍可能造成分页漂移。去重能消除重复 ID，却无法证明没有漏项。可靠恢复动作是主动刷新重新读取，而不是声称客户端具备事务快照。

## 验收场景

使用隔离后端插入内容，验证第一页刷新后不混入旧分页；模拟第 2 页失败后重试，确认第一页仍在；切换 Tab 返回检查滚动位置；搜索词变化后检查旧请求不覆盖新查询；连续加载检查重复 ID 被抑制。

## 一个分页控制器需要哪些不变量

分页逻辑最好集中维护当前查询、下一页、是否还有更多和正在加载标志。关键不变量包括：同一查询同一时间最多一个 append；reset 后旧请求不能写入；下一页合并按文章 ID 去重。

```dart
Future<void> loadNext() async {
  if (loadingNext || !hasMore) return;
  final requestGeneration = generation;
  loadingNext = true;
  try {
    final page = await repository.fetchPage(query, nextPage);
    if (requestGeneration != generation) return;
    items = mergeById(items, page.items);
    nextPage++;
    hasMore = page.hasMore;
  } finally {
    if (requestGeneration == generation) loadingNext = false;
  }
}
```

这是算法示意，不替代项目 `ArticleFeed` 的具体实现。实际分页还需区分首屏失败与追加失败：追加失败应保留已经读到的文章，并在列表尾部提供重试，而不是把整页切成错误屏。

## 首屏校验比每次 Tab 返回都强刷更克制

页面回到前台时，Repository 能检查可见依赖是否 fresh。列表在继续请求下一页前会检查第一页版本：若发现公共内容更新，则暂停追加并提示“有新内容，点击更新”；私有列表为了账号准确性可立即同步。主动下拉则使对应 feed tag 失效并强制取新页。

快照只保存有可用依赖的页面，当前上限为 10 个查询、每个最多 20 页；窗口超限后会淘汰较旧快照。容量边界能防止用户浏览多个搜索条件后无限占用内存，也意味着某个旧列表可能需要重新加载，属于明确的体验取舍。

## 列表结果比较避免将排序变化藏起来

Feed 检查更新时不只比较第一项 ID，而是比较已展示前缀的完整文章摘要，用来检测排序或内容变化。若公共第一页和已加载前缀不同，App 显示“有新内容，点击更新”；用户确认后从第一页重开，避免自动替换导致阅读位置突然移动。私有列表不能长期展示已失效的数据，所以检查后可立即采用新的第一页。

列表还要考虑并发：`serial` ticket 让 reset 发出的新请求取代旧 append；旧请求即使晚返回，也不会 `setState`。添加文章时先收集已有 ID 再 merge，避免相邻页因数据插入而出现重复卡片。


## 贴着工程代码读实现

下面这段节选自 `flutter-app/lib/shared/widgets/article_feed.dart 第 160–213 行`（保留原始实现；为突出主线省略了文件其余部分）。读代码时可以顺着调用链确认：先延迟旧分页请求，再触发刷新并让旧响应最后返回。沿着调用链读下去，才能看清这个选择如何影响实际页面。

```dart
  Future<void> load({
    bool reset = false,
    bool check = false,
    bool verify = false,
  }) async {
    if (busy && !reset) return;
    if (pendingUpdate && !reset && !check) return;
    final firstKey = repository.key(widget.path, {
      'page': 1,
      'pageSize': 12,
      ...widget.query,
    }, private: widget.path.startsWith(Endpoints.privatePrefix));
    // 翻下一页前先检查首屏是否变化，阻止旧页混入新的排序结果。
    if (page > 0 && !reset && !check && !repository.cache.fresh(firstKey)) {
      await load(check: true, verify: true);
      if (!mounted || pendingUpdate || error != null) return;
    }
    final ticket = ++serial;
    setState(() {
      busy = true;
      error = null;
    });
    final repo = ref.read(repositoryProvider);
    if (reset) repo.cache.invalidate({repo.feedTag(widget.path, widget.query)});
    try {
      final p = await repo.track(
        dependencies,
        () => repo.articles(
          page: reset || check ? 1 : page + 1,
          path: widget.path,
          query: widget.query,
          force: reset || verify,
        ),
      );
      if (!mounted || ticket != serial) return;
      setState(() => _applyPage(p, check, reset));
    } catch (e) {
      if (mounted &&
          ticket == serial &&
          e is! SessionChanged &&
          e is! CacheSuperseded) {
        setState(() {
          error = e;
          if (repo.forbidden(e) ||
              dependencies.any((k) => !repo.cache.usable(k))) {
            items = [];
            page = 0;
          }
        });
      }
    } finally {
      if (mounted && ticket == serial) setState(() => busy = false);
    }
  }
```

## 把容易出错的路径走一遍

我会用这个场景做一次可复现排查：**上一页慢响应在下拉刷新后追加到新列表**。先先延迟旧分页请求，再触发刷新并让旧响应最后返回；如果把问题定位在“无请求代次”，修正方向是“为请求分配代次并在应用结果前检查，刷新后清理重复项”。最后再验证正常路径没有退化，并把边界条件留在自动化检查里。

| 方案比较 | 简化做法 | 当前实现/推荐做法 |
|---|---|---|
| 本文核心选择 | 无请求代次 | ticket 与去重 |
| 错误处理 | 失败后清空或静默忽略 | 保留可恢复状态，给出明确反馈 |
| 验证方式 | 只检查成功结果 | 注入边界条件并检查回归 |

| 排错步骤 | 要观察什么 | 通过条件 |
|---|---|---|
| 复现 | 上一页慢响应在下拉刷新后追加到新列表 | 可以稳定触发或明确构造该输入 |
| 定位 | 先延迟旧分页请求，再触发刷新并让旧响应最后返回 | 找到责任层和状态归属 |
| 修正 | 为请求分配代次并在应用结果前检查，刷新后清理重复项 | 失败不污染后续页面或账号 |

## 小结

分页需要完整查询身份，刷新要保留可用画面，Tab 返回需恢复匹配快照。客户端去重和版本提示只能缓解漂移，不能代替服务端快照契约。把边界和限制写清楚，比把列表组件包得更厚更重要。
