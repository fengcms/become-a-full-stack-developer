# 成为全栈·Flutter App 篇·分类、标签与搜索：移动端内容发现

分类、标签和搜索页都能做成文章列表，但它们的查询身份完全不同：分类是层级路径，标签是主题筛选，搜索是读者提交的关键词。我最不想看到的 bug，是用户换了关键词，屏幕上却还挂着旧查询的结果。

这篇从当前搜索路由和本机历史实现切入，讨论三种内容发现模型如何进入查询键、页面状态和缓存边界。

## 分类是树，标签是集合

分类接口提供层级树，界面需要保留父子关系和可展开状态；若把节点拍平成文本列表，路径语义会丢失。标签则是离散主题集合，点击后进入以 tag 为筛选条件的文章流。它们共享文章卡片，但查询参数和空态并不相同。

```text
分类树：父分类 → 子分类 → 该分类文章
标签集：标签 → 匹配标签的文章
搜索：关键词 + 分页 → 搜索结果
```

客户端不重造分类树规则，数据以服务端返回为准；交互展开态可由 Widget 管理。

## 搜索输入有自己的状态机

搜索页至少包含初始建议、输入中、请求中、结果为空、结果有内容和请求失败。空关键词不是接口失败，也不必发起空请求。输入防抖可降低高频请求，但切换关键词时必须避免旧请求迟到后覆盖新结果。

```text
输入“flutter”发请求 A
改成“riverpod”发请求 B
B 先返回并显示
A 后返回 → 因查询代次不同而丢弃
```

如果搜索通过 Repository 缓存，缓存键需要包含完整 query 与筛选条件；只用 `search` 一个 key 会让不同词相互污染。

## 移动端筛选不一定映射成 URL

网站常把筛选条件写入 URL，便于分享与浏览器前进后退。APP 使用 go_router 深链承载页面身份，搜索历史则可保存在设备本地；这不意味所有输入每键都改路由。产品要决定哪些状态需外部恢复、哪些只在页面存活期间有效。

## 失败与无结果要让用户看懂

空结果给出清晰的“未找到匹配文章”，同时允许修改关键词；网络错误保留输入并提供重试；分类树为空可展示空态但不能伪造分类。搜索历史不是后端搜索数据，清理历史也不应清掉文章内容缓存。

## 查询边界落到缓存键和异步结果

实现上，页面应该让查询身份显式化，而不是用一个可变的 `currentArticles` 保存所有发现结果：

```dart
class SearchQuery {
  const SearchQuery(this.keyword, {this.page = 1});
  final String keyword;
  final int page;

  String get cacheKey => 'search:${keyword.trim()}:$page';
}
```

这个模型说明 key 需要包含影响结果的输入；生产实现还要纳入排序、筛选和 API 环境。发起新搜索时可用递增序号或可取消请求确保响应顺序正确：

```text
generation += 1
requestGeneration = generation
result = await repository.search(query)
if (requestGeneration != generation) return  // 新查询已开始
state = result
```

分类、标签页面也应使用各自资源 key。只有语义相同、数据更新规则相同的内容才适合共享同一缓存条目。

## 当前是显式搜索，实时搜索才需要防抖

当前页面在用户提交关键词后更新 query 并写入路由，不会因每次按键实时请求，所以不需要为现有实现虚构 debounce。若产品以后改成实时搜索，防抖只会减少尚未发出的请求；已经发出的请求仍可能晚于新 query 返回。此时可用 Dio CancelToken 尽量取消旧请求，但仍应以 query generation 检查响应，因为取消无法撤销已完成的服务端读取。

现有搜索历史保存最近 10 个非空关键词，搜索词通过 `/search?q=...` 路由保存，返回页面时可以恢复输入。分类树则要测深层节点、无文章分类和网络失败；标签页面需要处理很长的标签名和零计数数据。页面共用 ArticleFeed 时，应将分类 ID 或 tag slug 作为查询的一部分传入，而不是只改标题文字。

## 搜索状态要反映用户提交的条件

搜索框里正在输入的文字和“已提交查询”并不是同一个值。用户编辑新词时，旧结果仍可能留在页面；提交后路由 query 更新，结果页才对新词发请求。UI 可以在输入框变化后提示“按搜索继续”，但不能把旧结果标题改成新词造成误导。

搜索历史的清理只移除 `SharedPreferences` 的 `search.history`，不会影响 API 搜索结果缓存；历史最多保存 10 个去重关键词。退出账号也不需要清理它，因为它是设备级搜索偏好而不是会员私有数据。不同状态分开保存，能避免一次“清理缓存”误删用户偏好。


## 贴着工程代码读实现

下面这段节选自 `flutter-app/lib/features/discovery/search_page.dart 第 58–95 行`（保留原始实现；为突出主线省略了文件其余部分）。读代码时可以顺着调用链确认：快速连续提交两个不同词，检查 URL query、结果与历史记录。这里关注的是它如何改变数据流，而不只是记住一个 API 名称。

```dart
  void search([String? term]) {
    FocusScope.of(context).unfocus();
    final q = (term ?? input.text).trim();
    if (q.isNotEmpty) {
      history = [q, ...history.where((s) => s != q)].take(10).toList();
      ref
          .read(sessionProvider)
          .preferences
          .setStringList('search.history', history);
    }
    setState(() {
      query = q;
      input.text = q;
    });
    context.go(q.isEmpty ? '/search' : '/search?q=${Uri.encodeComponent(q)}');
  }

  void clearHistory() {
    setState(() => history = []);
    ref.read(sessionProvider).preferences.remove('search.history');
  }

  @override
  Widget build(BuildContext context) => PageFrame(
    title: '搜索',
    child: Column(
      children: [
        _SearchHeader(input: input, search: search),
        _SearchResults(
          query: query,
          history: history,
          search: search,
          clearHistory: clearHistory,
        ),
      ],
    ),
  );
}
```

## 把容易出错的路径走一遍

我会用这个场景做一次可复现排查：**输入过程每个字符都请求，旧结果晚到覆盖新查询**。先快速连续提交两个不同词，检查 URL query、结果与历史记录；如果把问题定位在“每键请求”，修正方向是“显式提交查询并以路由 query 为准，保持结果与可分享地址一致”。最后再验证正常路径没有退化，并把边界条件留在自动化检查里。

| 方案比较 | 简化做法 | 当前实现/推荐做法 |
|---|---|---|
| 本文核心选择 | 每键请求 | 提交式搜索 |
| 错误处理 | 失败后清空或静默忽略 | 保留可恢复状态，给出明确反馈 |
| 验证方式 | 只检查成功结果 | 注入边界条件并检查回归 |

| 排错步骤 | 要观察什么 | 通过条件 |
|---|---|---|
| 复现 | 输入过程每个字符都请求，旧结果晚到覆盖新查询 | 可以稳定触发或明确构造该输入 |
| 定位 | 快速连续提交两个不同词，检查 URL query、结果与历史记录 | 找到责任层和状态归属 |
| 修正 | 显式提交查询并以路由 query 为准，保持结果与可分享地址一致 | 失败不污染后续页面或账号 |

## 小结

分类、标签、搜索对应树形归属、主题集合和自由关键词三种发现方式。共享卡片不代表共享查询语义。为每个查询建立正确缓存键和独立空错状态，再处理请求竞态，移动端发现功能才不会把旧结果显示在新条件下。
