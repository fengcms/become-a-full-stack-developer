# 成为全栈·Flutter App 篇·移动端错误与限流：429、重试和写请求边界

429 出现时，最直觉的处理是等一会儿再试；但如果这是一次投稿、评论或收藏写入，客户端其实不知道服务端是否已经完成操作。盲目重放可能让同一动作发生两次。

我会从 Flutter `ApiClient` 的限流分支出发，展示项目为什么只对有限的 GET 读取做一次短等待，并给出如何测试“该重试”和“绝不能重试”的差异。

## HTTP 200 也可能不是业务成功

服务端可能用统一 envelope 返回业务 code。调用方应同时检查 HTTP 状态和业务结果；认证过期、字段不合法、资源不可见和频率限制均需保留原因。将所有错误显示为“网络开小差”，会导致用户反复提交不能解决的问题。

| 错误 | 合适动作 |
|---|---|
| 断网/读取超时 | 保留旧内容，提供手动重试 |
| 401 且可刷新 | 单飞刷新后按安全规则重放读取 |
| 403/404 | 按权限或资源状态呈现，不无限重试 |
| 业务字段校验 | 定位并保留表单输入 |
| 429 | 按 Retry-After 等待并给出提示 |

## Retry-After 是服务端给出的等待线索

项目 ApiClient 读取 `Retry-After` 秒数，并对符合条件的请求采用有界重试。其目的不是“失败了就加个 delay 再试”，而是尊重服务端节流窗口，避免客户端重试风暴。

```dart
final seconds = int.tryParse(
  response.headers.value('retry-after') ?? '',
);
```

代码应结合 status/code 判断是否属于契约声明的限流，再限制次数、最大等待和允许的请求类型。头缺失、格式不合法或等待时间过长时，转为用户可感知的稍后重试，而非无限等待。

{{IMG:M4-08-重试策略}}

## 读取与写入的重试风险不同

公开 GET 一般可安全重复读取，因此项目对短等待读取设置有限重试。但“GET”不天然保证无副作用，仍需以契约为准。创建投稿、评论或切换互动状态属于写操作：请求到服务端后连接断开，客户端无法仅从超时判断服务端是否已提交。

```text
客户端发送 POST
服务端已创建成功
响应在网络中丢失
客户端盲目再发 POST → 可能创建第二条
```

需要幂等保障时，应由 API 提供幂等键或资源 ID 语义。当前投稿流程拿到稿件 ID 后复用它更新，不能把任意写操作统一放进自动重试拦截器。

## 可重试错误不代表可以丢弃当前画面

文章或列表已有可用缓存时，刷新失败应显示仍可读的数据和轻量错误提示；首次加载失败才使用整页错误与重试入口。表单提交失败应保留标题、正文和当前编辑状态。异步 Pane 负责按页面场景呈现状态，API Client 不应直接弹 Snackbar。

## 用测试证明“没有重试”也很重要

网络测试应断言读请求收到 429 后最多重试约定次数，并核对等待；写请求收到 429 或超时不应自动重复。另测 Retry-After 缺失/非法、refresh 失败、403 和 404。若只测试成功路径，就不知道拦截器是否悄悄重复提交。

当前 Flutter 测试记录覆盖 429 读写区分；集成写操作运行在隔离本地后端。此证据说明对应路径成立，不代表移动网络中的所有代理和服务端限流配置均被完整实测。

## 退避时间也需要上限和取消

读取重试不能在应用切到后台后无期限等待，也不能因为 Retry-After 是异常大数字而挂起页面。将等待限制在产品允许范围内，页面离开或请求代次变化后取消后续动作；没有合法 header 时可显示可操作的手动重试。

```text
retryable = request is safeRead AND status/code is rateLimit
wait = clamp(retryAfter, minWait, maxWait)
最多自动重试一次
否则返回带 retryAfter 的可呈现错误
```

具体阈值应来自项目实现和后端策略，不应在文章里臆造默认秒数。提示“稍后再试”也要避免鼓励用户连续点击同一写请求。

## 当前代码的自动重试范围非常窄

项目 `_retryAfter` 仅当 HTTP 429、method 为 GET、Retry-After 能解析且等待不超过 3 秒时，等待后再发一次。条件外不自动重试，而是保留服务端限流信息交给 `ApiFailure` 和页面反馈。这个边界有意保守：没有合法时间提示时，客户端不会猜测服务端何时放行；POST、PUT、DELETE 不会因为 429 透明重放。

```dart
if (response.statusCode == 429 &&
    method == 'GET' && seconds != null && seconds >= 0 && seconds <= 3) {
  await Future<void>.delayed(Duration(seconds: seconds));
  if (start != epoch) throw SessionChanged();
  response = await dio.request(path, ...);
}
```

文章讲解时应保留这项具体限制，不能泛称“采用指数退避”。若未来改成指数退避，应加入随机抖动、总时限和请求取消测试，再更新文档。


## 贴着工程代码读实现

下面这段节选自 `flutter-app/lib/core/network/api_client.dart 第 259–320 行`（保留原始实现；为突出主线省略了文件其余部分）。读代码时可以顺着调用链确认：构造 429 与 Retry-After 响应，记录方法、延迟和发送次数。沿着调用链读下去，才能看清这个选择如何影响实际页面。

```dart
  Future<Response<dynamic>> _retryAfter(
    Response<dynamic> response,
    String path,
    String method,
    Map<String, dynamic>? query,
    bool anonymous,
    int start,
  ) async {
    final seconds = int.tryParse(response.headers.value('retry-after') ?? '');
    // 只对 GET 做一次有界等待；写请求绝不自动重放。
    if (response.statusCode == 429 &&
        method == 'GET' &&
        seconds != null &&
        seconds >= 0 &&
        seconds <= 3) {
      await Future<void>.delayed(Duration(seconds: seconds));
      if (start != epoch) throw SessionChanged();
      response = await dio.request(
        path,
        queryParameters: query,
        options: Options(
          method: method,
          headers: {
            if (!anonymous && accessToken != null)
              'Authorization': 'Bearer $accessToken',
          },
        ),
      );
      if (start != epoch) throw SessionChanged();
    }
    return response;
  }

  // 信封解码统一字段错误和会话失效，成功后的响应头由调用方派发。
  Future<dynamic> _decode(Response<dynamic> response, int start) async {
    final body = response.data;
    if (body is! Map) throw const ApiFailure('服务器返回了无法识别的数据', status: 500);
    final code = (body['code'] as num?)?.toInt() ?? 5000;
    if (code != 0) {
      if ([1003, 1005].contains(code) && start == epoch) {
        await clear();
        onExpired?.call();
      }
      final fields = <String, String>{};
      if (body['data'] is Map) {
        for (final e in ((body['data'] as Map)['errors'] as List? ?? [])) {
          if (e is Map) fields['${e['field']}'] = '${e['message']}';
        }
      }
      throw ApiFailure(
        fields.isNotEmpty
            ? fields.values.join('\n')
            : _messages[code] ?? '请求未能完成',
        code: code,
        status: response.statusCode ?? 0,
        retryAfter: int.tryParse(response.headers.value('retry-after') ?? ''),
        fields: fields,
      );
    }

    return body['data'];
  }
```

## 把容易出错的路径走一遍

我会用这个场景做一次可复现排查：**把 Retry-After 机械应用到写请求，造成重复提交**。先构造 429 与 Retry-After 响应，记录方法、延迟和发送次数；如果把问题定位在“自动重试所有请求”，修正方向是“仅对安全的 GET 且短延迟执行一次自动重试，写操作交给用户决策”。最后再验证正常路径没有退化，并把边界条件留在自动化检查里。

| 方案比较 | 简化做法 | 当前实现/推荐做法 |
|---|---|---|
| 本文核心选择 | 自动重试所有请求 | 按幂等性设边界 |
| 错误处理 | 失败后清空或静默忽略 | 保留可恢复状态，给出明确反馈 |
| 验证方式 | 只检查成功结果 | 注入边界条件并检查回归 |

| 排错步骤 | 要观察什么 | 通过条件 |
|---|---|---|
| 复现 | 把 Retry-After 机械应用到写请求，造成重复提交 | 可以稳定触发或明确构造该输入 |
| 定位 | 构造 429 与 Retry-After 响应，记录方法、延迟和发送次数 | 找到责任层和状态归属 |
| 修正 | 仅对安全的 GET 且短延迟执行一次自动重试，写操作交给用户决策 | 失败不污染后续页面或账号 |

## 小结

错误分类决定恢复动作，Retry-After 提供等待线索，有限重试保护服务端。公开读取与非幂等写入不能用同一套重试策略；真正安全的写重试需要服务端协作。用户已有输入和缓存内容应在失败后继续可用。
