# 成为全栈·Node 后端篇·数据建模手艺：状态机、冗余计数与适配层的心法清单

三十篇写下来，我们实现了认证、授权、CRUD、分类树、搜索、评论、通知……每一篇都在回答"这个功能怎么做"。可把代码翻回来看，真正决定这套系统好不好改、扛不扛得住并发的，其实是一些反复出现的**建模选择**：状态该用字段还是枚举、聚合该实时算还是存冗余、多变的部分该摁在哪一层。

最后这篇不做新功能，而是回头把散落各篇的"数据建模手艺"拧成一张心法清单：状态机与转移矩阵、冗余计数、把唯一约束当锁用、适配层、软删除与公开铁律、一对多与多对多的取舍。前面每篇教的是"怎么实现一个功能"，这篇讲的是"怎么把功能背后的数据想对"。

## 一、数据建模是后端的基本功

同样一个"文章系统"，新手和老手写出来天差地别：新手堆字段、遇问题就加列；老手先想"这东西的生命周期是什么、会和谁关联、读写比例如何"，再动手。本项目的 `node-backend` 冻结代码里，反复出现几种**可复用的建模手艺**，下面逐一拆解，每一条都对应前面某篇的真实代码。

## 二、状态机：用字段 + 转移矩阵表达生命周期

凡是"有生命周期"的资源，别用一堆布尔 flag（isPublished / isPending / isDraft）互相组合——那会 combinatorial explosion，状态之间还能出现"既发布又草稿"的矛盾态。正确做法是**一个枚举状态字段 + 一份允许的转移清单**：

- 文章：`draft / pending / published`（M1-15）。投稿默认 `pending`，member 不能自发布（published 被降级回 pending），editor 审核通过才 `published`。
- 评论：`approved / rejected / reviewing`（M1-27）。自动流只产前两者，`reviewing` 仅人工置位。

关键是**转移不是写在 if-else 里，而是机器化进契约**：`openapi.v1.yaml` 的 `Article.status.x-allowed-transitions` 用矩阵写死六条合法转移，`check_contract.py` 语义门能校验代码没偷偷加非法转移（M1-14 / M1-20）。

> **心法 1**：有生命周期的资源，用单一状态枚举 + 机器化的转移矩阵，别用布尔 flag 组合；转移规则进契约，让门禁替你盯。

## 三、冗余计数：读多写少时把聚合降级为字段

赞数、阅读量都是"高频展示、低频变更"的数字。每次都 `COUNT(*)` 聚合是浪费，所以本项目把它们**冗余成一个字段**：`articles.viewCount`（M1-26）、`articles.likeCount`（M1-29）。写时多维护一下，读时零计算。

代价是"写路径变复杂"——点赞要 `changes>0` 才 `+1`、取消要 `CASE` 下限夹 0（M1-29），阅读量要插去重记录再 `+1`（M1-26）。但这份复杂换来所有读者瞬时拿到数字，对内容产品几乎总是划算的（P-49 的尺度判断）。

> **心法 2**：高频展示、低频变更的聚合值，冗余成字段；复杂度留在写路径，读路径零成本。是否冗余取决于读写比，别为想象中的海量提前上缓存。

## 四、唯一约束当锁：幂等 + 并发安全的零成本方案

"防重复"最优雅的实现，往往不是应用层加锁，而是**让数据库的唯一索引当裁判**：

- 点赞：`uniq_like(userId, articleId)` + `ON CONFLICT DO NOTHING`，`changes>0` 才 `+1`，并发双发仅 +1 不 500（M1-29）。
- 阅读去重：`uniq_article_view_dedup(articleId, dedupKey)`，时间桶撞唯一约束即"已计过"（M1-26）。
- 标签关联：`uniq_article_tag(articleId, tagId)`，`onConflictDoNothing` 防重复绑定（M1-16）。

共同套路：**让数据库告诉你"这次到底插进去了没有"，而不是应用层先查再判**。这样既没有读改写竞态，又不需要分布式锁，是"用数据库特性兜底并发"的典范。

> **心法 3**：防重复 / 幂等，优先用唯一约束 + `ON CONFLICT` / `changes` 判断，把并发正确性交给数据库，而非自己加锁。

## 五、适配层：把"变的东西"摁在边界

一套代码要跑 Node 和 Cloudflare Workers 两套运行时（M1-24），核心手艺是**适配层**：把"会变的东西"（数据库驱动、存储后端）收敛到边界，核心逻辑保持不变。

- 数据库：`db/client.ts` 的 `setDb / getDb` 注入模式 + `createLocalDb`（better-sqlite3）/ `createD1Db`（D1）两个工厂，业务层永远 `getDb()` 不感知底层（M1-24）。
- 存储：`STORAGE_DRIVER` 选 local 还是 r2，文件上传逻辑对上层透明（M1-18）。

配套的一个反直觉决策（P-33）是：**自引用外键不声明 `.references`**。分类 `parentId`、评论 `parentId`、附件 `articleId` 都故意不写 `.references`，原因有二——Drizzle 自引用会类型成环（`TS7022`）、SQLite 的 FK 默认不强制。约束全部由应用层（环检测、删除守卫）保证（M1-25）。

> **心法 4**：变化的只在边界，不变的核心自由生长。自引用 / 弱约束场景，宁可不声明 FK，把正确性交给应用层测试覆盖，也不要让数据库特性破坏编译或给虚假安全感。

## 六、去规范化 JSON 列 vs 关联表：读路径选最稳源

标签是个经典两难：既要"精确的多对多关联"（用于按标签筛文章、统计标签文章数），又要"高效地算两篇标签重合度"（用于相关推荐）。本项目**两者都要**，分两条读路径：

- `article_tags` 关联表（M1-16）：精确多对多，用于 `tagArticleCounts` 的 `GROUP BY` 精确计数、按标签查文章。
- `articles.tags` 去规范化 JSON 列（M1-28）：创建/更新文章即写，相关推荐直接 `parseTags` 在内存算共享标签数，**不依赖关联表同步是否完成**（P-35）。

两条路径各有适用场景，不是"用了关联表就不能有冗余列"。判断标准是**"这条读路径最稳的数据源是什么"**——相关推荐要快且不受回填任务滞后影响，所以读 JSON 列；精确统计要对齐真实关联，所以读关联表。

> **心法 5**：同一份数据可以有多个投影。读路径选"最稳、最快、最不易过期"的那个源，去规范化列和关联表不互斥。

## 七、软删除 + 公开铁律：一行 `isNull` 全站统一

全站删除几乎都是软删除——置 `deletedAt`，查询统一带 `AND isNull(deletedAt)`（M1-15 / M1-16 / M1-25）。这一行 `isNull` 同时实现了两件事：

1. **可恢复**：误删能找回来，审计也有迹可循。
2. **公开铁律**：未发布 / 已软删的资源，对公开接口"不存在"——详情 404、列表不出现、评论只吐 approved、搜索只查 published（M1-15 / M1-27 / M1-28）。

把"软删除过滤"做成所有查询的默认底座，比在每个端点单独判断"该不该显示"可靠得多。

> **心法 6**：默认软删除 + 查询恒带 `isNull(deletedAt)`；未发布 / 已删对公开接口集体失明，是公开可见性铁律的物理实现。

## 八、P-31 / P-32：一对多 vs 多对多，外键该不该声明

最后补两个最常被问的建模判断：

- **一对多用字段，多对多用中间表**（P-31）。文章归属一个分类 → `articles.category_id` 单字段；文章挂多个标签 → `article_tags` 中间表（M1-16）。判断标准：一个文章有几个父？一个就是字段，多个就是中间表。
- **外键的强制交给应用层**（P-32）。本项目几乎所有引用（author、category、tag、parent）都**不声明 `.references`**，因为 SQLite FK 默认不强制、且自引用会类型成环。存在性、级联、成环全由 service 层保证（删除守卫、环检测、级联删子回复）。这不是偷懒，是把"数据库能强制"和"逻辑正确"分开后，选择让测试覆盖后者。

> **心法 7**：一对多落字段、多对多落中间表；外键是否声明，看"它能不能真的强制 + 会不会破坏编译"，不能就交给应用层，并用测试兜底。

## 九、31 篇回顾地图

把本篇的心法映射回前面的文章，就是整张 M1 地图：

| 手艺 | 对应篇章 |
|---|---|
| 状态机 + 转移矩阵 | M1-14 权限 / M1-15 投稿状态机 / M1-27 评论三态 |
| 冗余计数 | M1-26 阅读量 / M1-29 点赞 |
| 唯一约束当锁 | M1-16 标签 / M1-26 阅读去重 / M1-29 点赞 |
| 适配层 + 不声明 FK | M1-24 双部署 / M1-25 分类树（P-33） |
| 去规范化 vs 关联表 | M1-16 标签 / M1-28 相关推荐（P-35） |
| 软删除 + 公开铁律 | M1-15 / M1-25 / M1-27 / M1-28 |
| 一对多 vs 多对多 | M1-16（P-31 / P-32） |

你会发现，这些手艺**反复出现在不同功能里**——点赞用唯一约束、阅读量也用；分类树不声明 FK、评论也不声明；冗余计数在赞数和阅读量上同源。它们不是 31 个孤立技巧，而是一套**连贯的建模哲学**：把变化摁在边界、让数据库替你保证正确性、按读写比和访问模式选存储形态、用机器化契约守住业务规则。这七条心法，值得誊抄进你自己的工程笔记——它比任何单篇教程都更耐读，也会在你下一次设计表结构时默默救你一命。
