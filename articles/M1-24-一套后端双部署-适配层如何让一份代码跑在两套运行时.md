# 成为全栈·Node 后端篇·一套后端双部署：适配层如何让一份代码跑在两套运行时

如果你翻过项目根目录，会看到两份入口：`src/index.ts` 和 `src/worker.ts`。它们不是重复代码，而是同一套业务逻辑插在两套运行时上的两个"插头"——自管 Linux 是一个，Cloudflare Workers 是另一个。

这一篇讲清楚适配层是怎么做到这件事的：`setDb` / `getDb` 的注入模式、两个入口怎么复用同一个 `createApp`、`app.ts` 为什么绝不能在顶层创建默认实例，以及这套"一套代码双部署"到底值不值。

## 一、什么是"一套代码双部署"

普通项目做部署，是"选一个目标"：要么上容器，要么上 Serverless，二选一。我们不一样——从立项起就要求**同一份代码同时支持两种运行时**，原因是成本与掌控的权衡：

- 自管 Linux（Node）：完全掌控，本地磁盘、SQLite 文件库都能用，适合内网 / 对数据位置敏感的场景。
- Cloudflare Workers：免运维、全球边缘、按量付费，适合对可用性要求高、不想自己管机器的场景。

但"同时支持"不是把代码写两套，而是**业务代码写一份，只在边界处适配两套运行时**。这全靠一个设计良好的"适配层"（adapter layer）。下面从数据库适配和 App 装配两处，看真实代码怎么做的。

## 二、共享内核：Drizzle 的 SQLite dialect 统一

双部署最大的技术障碍是**数据库**。Node 端用 `better-sqlite3`（本地文件 / 内存），Workers 端用 Cloudflare D1（基于 SQLite 的托管数据库）。两种驱动 API 完全不同，怎么让业务代码无感？

读 `src/db/client.ts` 就能看到答案：**两者共享同一个 Drizzle 的 SQLite 内核**。Drizzle 的 `better-sqlite3` 驱动和 `d1` 驱动都实现了同一套 SQLite dialect，所以上层查询（schema、查询构造）是**完全相同**的。差异只在最底层的"连接"——这一步被收敛在 `client.ts` 的两个工厂函数里：

```ts
// 本地 SQLite（better-sqlite3）
export const createLocalDb = (file = ':memory:'): Db =>
  drizzle(new Database(file), { schema });

// Cloudflare D1
export const createD1Db = (binding: D1Binding): Db =>
  drizzleD1(binding, { schema }) as unknown as Db;
```

注意 `Db` 这个类型被统一定义为 `BetterSQLite3Database<typeof schema>`——业务层拿到的永远是同一个 `Db` 类型，无论底层是 SQLite 还是 D1。这是双部署能成立的技术前提：**查询语言统一，连接层分叉**。

## 三、适配层边界：setDb / getDb 注入模式

光有工厂不够，还得让业务代码"拿得到"数据库而不"看得见"它从哪来。`client.ts` 用了一个经典的**注入 / 获取（inject / get）模式**：

```ts
let current: Db | null = null;
export const setDb = (db: Db): void => { current = db; };
export const getDb = (): Db => {
  if (!current) throw new Error('Database not initialized; call setDb() first.');
  return current;
};
```

业务 service 层统一通过 `getDb()` 访问数据库，**完全不感知**底层是本地库还是 D1。两个入口各自在启动时 `setDb` 注入不同的实例：

- `index.ts`：`const db = createLocalDb(env.DB_FILE); ... setDb(db);`
- `worker.ts`：每次请求 `setDb(createD1Db(appEnv.DB))`。

这就是适配层的精髓——**"脏活"（驱动差异、连接管理）收敛在边界 `client.ts`，业务代码保持纯净**。新人读 service 层时，永远看到的是 `getDb().query.articles.findMany(...)`，而不是一堆 `if (isCloudflare) ... else ...` 的分支。可维护性因此极高。

关于那句 `as unknown as Db`：它不是偷懒的 `any`，而是一次**受控类型转换**——D1 驱动返回类型和本地 `Db` 在 Drizzle 类型系统里不完全等价，但运行时共享 SQLite 内核，业务用法一致。注释里特意写明"非 any"，意思是：这里做过判断，确信二者行为一致，才做转换，而不是无脑抹平类型。这正是适配层该有的克制。

## 四、两个入口如何复用 createApp

再看 `src/app.ts`——它是所有路由、中间件的总装配点，但**只导出一个工厂 `createApp(env)`**，不创建任何默认实例：

```ts
export const createApp = (env: AppEnv): Hono => {
  setActiveEnv(env);
  const app = new Hono();
  app.onError(errorHandler);
  app.use('*', corsMiddleware(env));
  app.route('/api/v1/articles', articlesReadRoute);
  // ……所有路由在此挂载
  return app;
};
```

两个入口的"复用"就发生在这里：`index.ts` 和 `worker.ts` 都只是各自调用 `createApp(env)`，传进不同的 `env`，拿到同一个结构的应用。业务路由（articles / comments / users / upload……）一份定义，两端共享。**这就是"双部署"在应用层的落地：App 装配一次写好，运行时各调一次。**

## 五、P-13：app.ts 绝不在顶层创建默认实例

这里有个反直觉但致命的细节（P-13）。你可能想："直接在 `app.ts` 里 `export const app = createApp(readEnv(process.env))` 多省事？"——**绝对不能**。代码注释里的"审阅 B02"讲清了原因：

> Cloudflare Workers 导入本模块时若触发 `process.env` 求值会崩溃（CF 不保证 `process.env`）。

也就是说，Workers 运行时**没有 Node 的 `process.env`** 那种全局对象保证。如果 `app.ts` 在模块顶层就 `readEnv(process.env)`，那么当 `worker.ts` 只是 `import { createApp }` 时，这个顶层求值就会在 CF 环境崩溃。所以默认实例的创建**必须下沉到各运行时入口**——`index.ts` 在 Node 里用 `process.env`，`worker.ts` 在每次请求用 CF 注入的 `env`。`createApp` 保持纯净工厂，谁调用谁负责喂 env。这一个决定，避免了一个只有部署到 Workers 才会暴露、本地永远测不出来的崩溃。

## 六、P-09：env 显式传入，利于测试复用

`createApp(env)` 把环境**显式传入**而非内部隐藏读取，这带来一个附带收益（P-09）：测试时可以轻松构造不同的 `env`（比如 `NODE_ENV=test`、内存库），复用同一个 `createApp` 跑集成测试，而不必依赖全局状态。我们前一篇讲测试时提到的 `app.request` 不发端口、`:memory:` 库，正是建立在这个"env 可注入"的设计之上。双部署和"可测试性"其实是同一个设计原则的两面：**依赖从外部注入，而非内部硬编码**。

## 七、配置驱动：同一份代码靠 env 分叉到两端

把上面串起来，双部署的"开关"完全在配置层（`env.ts` 的 schema）：

| 维度 | Node 路线（index.ts） | Workers 路线（worker.ts） |
|---|---|---|
| 数据库连接 | `createLocalDb(env.DB_FILE)` | `createD1Db(env.DB)`（D1 绑定） |
| 迁移时机 | 运行时 `await migrate(db)` | deploy 阶段 drizzle-kit |
| 文件存储 | `STORAGE_DRIVER=local` → `uploads/` | `STORAGE_DRIVER=r2` → R2 |
| env 来源 | `process.env` | CF 请求注入 |

业务代码一处都不用改，全靠 `env` 把同一份 `createApp` 导向不同运行时。这就是"适配层"的全部价值：**变化的只在边界，不变的是核心。**

## 八、P-48：双部署的代价与收益

任何架构都有代价，双部署也不例外（P-48）。收益很明显——一套代码两种部署，弹性拉满，成本可按场景优化。代价则是：

1. **适配层要写对**：`client.ts` 的类型转换、`setDb/getDb` 注入，一旦写错，两端行为不一致，调试极其痛苦。
2. **最低公共分母约束**：代码不能依赖某一端独有的能力。比如本地磁盘写入在 Workers 上不存在，所以存储必须抽象成 `STORAGE_DRIVER`；`process.env` 不能顶层求值（见 P-13）。
3. **测试要覆盖两侧语义**：D1 和 better-sqlite3 虽共享 SQLite 内核，但仍有细微差异（如某些函数、事务语义），关键路径要在两侧都验证。

所以"双部署"不是免费午餐，它用一层适配层的复杂度，换来了部署灵活性的上限。对我们这个"教学 + 演示"定位的项目，这个权衡是划算的——读者既学到 Node 自管，又学到 Serverless 边缘，一份代码两头都用。

## 九、P-39 / P-42：存储适配层同样驱动无关

双部署思想不只用在数据库。我们前面的文件上传篇（M1-18）讲过：附件存储也是一个 `StorageProvider` 适配层，`STORAGE_DRIVER` 选 local 还是 r2（P-39 内容寻址去重 sha256 逻辑在适配层之上、与驱动无关，两端共享；P-42 SVG 的 `Content-Disposition: attachment` + `X-Content-Type-Options: nosniff` 安全头，在 local 直出路径也照常生效）。这再次印证：**适配层的模式是一以贯之的——把"会变的东西"摁在边界，让"不变的核心"自由生长。** 双部署和双存储，是同一个设计哲学的两个实例。

## 十、一次请求如何穿过适配层

理论讲完，用一次真实的 `POST /api/v1/articles`（需要 editor 角色）把双端时间线拉通，你会更直观地看到"变与不变"的边界在哪。

**Node 路线（index.ts）：**
1. 反向代理把请求转给 `serve` 起的 Node 进程。
2. `createApp(env)` 装配好 CORS、错误处理、路由（env 来自 `process.env`、`JWT_SECRET` 已由 `readEnv` 校验）。
3. 请求进入 `auth` 中间件，读 `getActiveEnv().JWT_SECRET` 验 token。
4. `guard('editor', resolveArticleOwner)` 鉴权 → 落到 `articlesWriteRoute`。
5. service 层 `getDb().insert(articles).values(...)`——这里的 `getDb()` 返回的是启动时 `setDb(createLocalDb(DB_FILE))` 注入的 better-sqlite3 实例。
6. 写库、返回信封。

**Workers 路线（worker.ts）：**
1. 边缘收到请求，进入 `worker.fetch(request, env)`。
2. `readEnv(env)` 解析 CF 绑定，`setDb(createD1Db(env.DB))` 注入 D1 实例。
3. `createApp(appEnv)` 装配**完全相同**的 CORS、错误处理、路由。
4. 同样的 `auth` 中间件、同样的 `guard('editor')`、同样的 `articlesWriteRoute`。
5. service 层同样是 `getDb().insert(articles).values(...)`——但这次 `getDb()` 返回的是 D1 实例。
6. 写库、返回信封。

两条时间线**唯一的不同在步骤 2**（数据库怎么注入），以及底层驱动不同；从步骤 3 往后的中间件、路由、service、查询，逐字相同。这就是适配层成功的标志：**业务路径 100% 复用，变化被摁死在入口那一行 `setDb`**。你调试业务 bug 时，完全不用关心当前跑在 Node 还是 Workers——除非 bug 本身就出在适配层。

## 十一、小结

"一套后端双部署"不是口号，而是用适配层把"变与不变"切开：

1. **共享内核**：Drizzle SQLite dialect 统一，SQLite 与 D1 查询语言相同，差异只在连接层（`createLocalDb` vs `createD1Db`）。
2. **适配层边界**：`setDb/getDb` 注入模式，业务层 `getDb()` 完全不感知底层驱动；`as unknown as Db` 是受控转换而非 `any`。
3. **复用 createApp**：两个入口各自 `createApp(env)`，路由中间件一份定义两端共享。
4. **P-13**：`app.ts` 只导工厂、不建默认实例，避免 CF 导入时 `process.env` 求值崩溃。
5. **P-09**：env 显式传入，双部署与可测试性同源。
6. **配置驱动分叉**：`DB_FILE`/`DB`、`STORAGE_DRIVER`、迁移时机全靠 env 导向两端。
7. **P-48**：双部署的代价是适配层复杂度与最低公共分母约束，收益是部署弹性上限。
8. **P-39/P-42**：存储适配层同样驱动无关，去重逻辑与 SVG 安全头两端共享。
