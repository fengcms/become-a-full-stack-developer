# 成为全栈·Flutter App 篇·写后缓存失效与图片缓存治理

上一篇讲了缓存本身的三态。这一篇讲两个具体的治理问题：

1. **写操作之后，哪些缓存要清、哪些不清。**
2. **图片缓存和 JSON 缓存为什么必须用两套完全不同的逻辑。**

第二个问题比第一个严重。因为图片缓存的失效如果照搬 JSON 那一套，会出**安全问题**。

## 写后失效：一张表管住所有关联

用户做了一次写操作（点赞、评论、投稿、改资料），哪些缓存受影响？

我最初的思路是"在每个写操作的地方手动清相关缓存"。写了十几个之后发现：漏了三处，而且**三处漏的都是"看起来不相关"的关联**。

比如：点赞一篇文章之后，什么变了？

- 这篇文章的反应状态（`reactions:{id}`）
- **我的点赞列表**（`meLikes`）
- **会员中心的数字**（`overview`）
- **文章列表里的点赞数**（`articleLists`）

后两个是我最初完全没想到的。用户点赞之后切到会员中心，那个数字应该已经变了。

所以现在改成一张映射表，`cache_policy_table.dart`：

```dart
/// 写操作开始先隔断旧请求，结束后按相同分类失效关联摘要与会员统计。
Set<String> mutationTags(String path, Object? data) => switch (family(path)) {
  ResourceFamily.reaction => {
    'reactions:${Endpoints.articleId(path)}',
    Endpoints.meLikes,
    'overview',
  },
  ResourceFamily.favorites => {Endpoints.meFavorites, 'overview'},
  ResourceFamily.history => {Endpoints.meHistory, 'overview'},
  ResourceFamily.notifications => {'notifications'},
  ResourceFamily.comments => {'comments:${Endpoints.articleId(path)}'},
  ResourceFamily.comment => {'comments'},
  ResourceFamily.article || ResourceFamily.articleList => {
    CacheTags.articleBodies,
    'articleLists',
    Endpoints.meArticles,
    'overview',
    Endpoints.tags,
    Endpoints.categoriesStats,
  },
  ResourceFamily.profile => {'profile', 'articleLists'},
  _ => {},
};
```

这张表的设计有个关键前提：**`family(path)` 只判一次，读策略、响应校验、写后失效三处共用**（M4-07 讲过）。

而 `article` 那一支最能说明问题——**发一篇文章要失效六个标签**：

| 标签 | 为什么 |
|---|---|
| `articleBodies` | 文章正文（如果已发布） |
| `articleLists` | 所有列表里都可能出现它 |
| `meArticles` | 我的稿件列表 |
| `overview` | 会员中心的稿件数 |
| `tags` | 新文章带标签，标签页要更新 |
| `categoriesStats` | **新文章让分类计数 +1** |

最后两个是"侧效应"。**发布文章会让标签和分类的统计数字变化**，而这些数字展示在完全不同的页面上。发完之后不去清它们，用户会在标签页看到一个不包含新文章的标签，在分类页看到一个偏小的数字。

**这类失效最容易被漏掉，因为触发它的操作和被影响的页面没有直接关系。**

调用方是这样的：

```dart
// 写操作失败也会使相关读取失效，因为请求可能已被服务器接收。
void _mutation(String path, String method, Object? data, bool started,
               dynamic result, Object? error) {
  final affected = policies.mutationTags(path, data);
  if (started) {
    cache.fence(affected);
    return;
  }
  if (error is SessionChanged) return;
  cache.invalidate(affected);
  ...
}
```

M4-23 讲过 `fence` 和 `invalidate` 的区别。这里还有一个值得说的判断：**`error is SessionChanged` 时直接 return，不失效。**

因为 `SessionChanged` 的含义是"会话换代了，这条响应当废"——而会话换代本身会触发 `resetPrivate`（M4-18），它已经把私有缓存全清了。**再失效一次是多余的，而且可能清掉新会话刚建立的数据。**

## 图片缓存：不能照搬 JSON 那套

现在说第二个问题，也是这一篇的重点。

图片缓存和 JSON 缓存的**相似点**很多：有内存、有磁盘、有过期时间、要在写操作后失效。所以最自然的想法是复用同一套机制。

**但复用会出安全问题。** 差别在三处。

### 差别一：URL 里可能带签名

这是最关键的一点。

JSON 接口的 URL 里只有路径和查询参数（`/articles?page=2`）。而图片 URL 可能是这样：

```text
https://cdn.example.com/img/abc.jpg?sign=xxxxx&expires=1730000000
```

那个 `sign` 是一个**签名凭证**——服务端用它验证"这个请求者有权访问这张图"。它和 refresh token 一样敏感。

如果带签名的 URL 被原样存进磁盘缓存，会怎样？**过期之后缓存里还留着那个签名，而签名本身仍然有效一小段时间。** 更糟的是缓存文件可能通过其他途径被读取。

所以有了这个判断：

```dart
// 含查询参数的链接可能携带签名，不能写入公开图片磁盘缓存。
bool canPersist(Uri uri, bool public) =>
    public &&
    ['https', 'http'].contains(uri.scheme) &&
    !uri.hasQuery &&        // ← 有任何查询参数就不落盘
    uri.userInfo.isEmpty;
```

**`!uri.hasQuery` 这一条把"签名 URL"整个排除在磁盘缓存之外。**

代价是：**带签名的图片永远走网络**。对于本项目（M1 里说附件走 R2，签名是生成的）这意味着上传的图片每次都要重新下载。

而这恰恰是**正确**的取舍——一张图几百 KB，重复下载的代价比多占一点磁盘小得多。**而且签名 URL 有过期时间，缓存一个会过期的凭证本身就是 bug。**

### 差别二：图片请求不带鉴权头

第二点更微妙。看实际请求：

```dart
// 图片请求明确移除鉴权头，避免把 API 令牌发送给图片域名。
final response = await dio.get<List<int>>(
  url,
  options: Options(
    responseType: ResponseType.bytes,
    ...
```

**注意那个"明确移除"** —— 因为这个 `dio` 是从 `ApiClient` 拿的，它配置了 `validateStatus: (_) => true` 和一整套拦截逻辑。

如果不做特殊处理，**图片域名会收到你的 Authorization 头**。设想图片托管在第三方 CDN——**你的 access token 就发给了那个第三方。**

这和 M4-15 讲的 WebView 那个问题是同一个性质：**跨信任边界时，凭证不能自动跟随。** 而它是**隐式发生的**，因为复用了同一个 Dio 实例。

`canPersist` 里那个 `uri.userInfo.isEmpty` 也是同一类防护：`https://user:pass@host/image.jpg` 这种 URL 里嵌了凭证，不该落盘。

### 差别三：会话代次要拦住回填

第三点和 M4-23 讲的 `fence` 类似，但图片这边用的是另一个机制：

```dart
// 先复用有效内存和在途请求；会话变化后旧图片请求不能回填。
Future<Uint8List> load(String url, {required bool public,
                                    required int epoch, bool force = false}) {
  final k = key(url, public, epoch), generation = _generation;
  ...
  final bytes = await disk.read(k);
  if (bytes != null && generation == _generation) {
    _put(k, bytes, disk.expiresAt(k) ?? DateTime.now());
    return bytes;
  }
```

**`generation == _generation` 这个检查。** 它解决的是 M4-09 那个老问题：**用户在看私有图片时退出了登录，那个图片请求还在飞，回来之后不能回填。**

因为如果回填了，那张私有图片的字节就留在了内存缓存里，键是 `session:旧epoch:url`——虽然新会话用不同的键读不到，但它**还占着内存**，而且如果将来某个 bug 让 epoch 检查失效了，就会真的泄露。

而键的构造：

```dart
String key(String url, bool public, int epoch) =>
    '$namespace|${public ? 'public' : 'session:$epoch}:$url';
```

**私有图片的键带 epoch，公开的不带。** 和 JSON 缓存完全一致的口径（M4-23 讲过）。

`namespace` 在最前面，因为 `ImageStore` 是从 `api.baseUrl` 建的——**开发环境和线上环境的图片缓存必须隔离**，理由和 M4-14 的别名表一样。

## 内存里的 LRU，和磁盘不一样

图片缓存的内存部分和 M4-13 讲的代码高亮缓存是同一个套路：

```dart
if (!force && existing != null && DateTime.now().isBefore(existing.$2)) {
  _memory.remove(k);
  _memory[k] = existing;    // ← 移到队尾，实现 LRU
  return Future.value(existing.$1);
}
```

**`remove` 再 `put` 就是 LRU。** 命中时移到队尾，淘汰时删队首。

而 `_flights` 是请求去重：

```dart
if (_flights.containsKey(k)) return _flights[k]!;
```

**同一个 URL 有多个组件要用时，只发一个请求。** 文章封面 + 详情页大图 + 相关推荐，可能都指向同一张图。

这个模式和 M4-09 的单飞刷新是同一个思想，只是这里更简单——因为图片请求**不需要担心幂等性之外的任何问题**（它不修改状态，重复请求无害）。

## 两套缓存的对比

把差异列出来：

| 维度 | JSON 缓存 | 图片缓存 |
|---|---|---|
| 键 | 结构化（baseUrl + 类型 + 路径 + 查询） | 字符串拼接（namespace + 类型 + URL） |
| 落盘条件 | 策略显式允许 + 未被服务端禁止 | **URL 无查询参数、无 userInfo、scheme 合法** |
| 鉴权头 | 正常携带 | **明确移除** |
| 会话隔离 | 键里带 `userId:epoch` | 键里带 `epoch`（私有时） |
| 失效触发 | `mutationTags` 标签表 | 换 `namespace`（重置整个 store） |
| 过期依据 | 策略 + `Cache-Control` + `Age` | 磁盘过期时间 |

**唯一相同的是内存 LRU 和请求去重。** 而那部分恰好是最容易写对的——因为它只涉及内存管理，不涉及安全边界。

这个对比说明一件事：**缓存框架可以复用，但缓存策略必须按数据性质定制。** 图片数据是"公开且可预测"的，JSON 数据是"可能敏感且形状多样"的，用同一套规则必然在其中一个上出错。

而 M4-23 讲的那个原则在这里依然成立：**数据来源决定信任级别，信任级别决定哪些默认行为可用。**

## 什么时候清图片缓存

图片缓存的失效和 JSON 不同。看 `resetPrivate`：

```dart
void resetPrivate() {
  ...
  images.resetPrivate();
  ...
}
```

而个人资料改动之后：

```dart
if (path.startsWith(Endpoints.profile)) {
  images.clear();        // ← 整个清掉
}
```

**改头像之后清空整个图片缓存。** 这看起来粗暴，但理由充分：**我们无法知道哪些图片属于用户、哪些不属于。**

因为图片 URL 里可能没有用户信息（`https://cdn/img/uuid.jpg`），**从 URL 判断不了归属**。而 JSON 缓存可以——它的键里有路径和标签。

所以图片缓存只有两种清理方式：

| 时机 | 动作 | 理由 |
|---|---|---|
| 退出登录 | `resetPrivate()`，只清私有部分 | 键里有 epoch |
| 改资料（头像） | `clear()` 全清 | **无法判断归属** |
| 缓存空间不足 | LRU 淘汰 | 自动 |

**"无法判断归属"这个限制是根本性的。** 更彻底的做法是给私有图片单独的域名或者路径前缀，这样 URL 本身就能标识归属——但那需要服务端配合，牵动 R2 的配置。

现在这个方案已经能用，**但它意味着用户改一次头像就要重新下载所有图片**。这个代价我接受，因为改头像是极低频操作。

## 一条我一开始想省掉的事

图片请求移除鉴权头这件事，我一开始没做。

因为 `ImageStore` 是 `ApiClient` 的 `dio` 构造的（`late final ImageStore images = ImageStore(api.dio, ...)`），而那个 dio 已经配好了拦截器——**我以为"什么都没配"就是不带 header**。

实际上 Dio 的拦截器是全局的，任何请求都会走。**图片请求也不例外。**

发现的方式是我抓包看了一下：图片请求的 header 里赫然有 `Authorization: Bearer eyJ...`。

**这个问题如果上生产，意味着所有图片托管方都能拿到用户的 access token。** 而这正是 M4-15 讲的那个原则在另一个地方重演：**复用传输层时，凭证边界会被继承。**

修复之后我加了一个断言：**图片请求的 header 里不能有 Authorization。** 这条断言留在测试里。

顺带说，**这也是"传输层复用"的一个隐性代价**。省下的是代码，付出的是边界清晰度——每复用一层，就要重新确认一遍"这一层会不会把不该带的东西带出去"。

## 小结

写后失效和图片治理这两件事，核心都是**"哪些东西被影响了"这个问题不能靠想**：

1. **失效关系要用表，不能靠记** —— 发一篇文章要失效六个标签，其中两个（标签页、分类统计）是侧效应。
2. **签名 URL 不能落盘** —— `!uri.hasQuery` 一条规则，把会过期的凭证挡在磁盘外。
3. **图片请求不带鉴权头** —— 复用 Dio 实例会继承拦截器，而拦截器会加 header。
4. **改资料只能全清图片缓存** —— URL 里判断不了归属，这是根本限制。
5. **传输层复用有隐性代价** —— 每复用一层，要重新确认凭证边界。

其中第 3 条我认为是这一篇最值得记的。它和 M4-15 的 WebView 令牌注入是**同一个错误的两个变体**：把"我需要凭证"和"这个请求需要凭证"混为一谈。

**这两个 bug 都不会报错，也不会崩溃，它们只是安静地把令牌发给了不该发的人。** 在开发环境（API 和图片同域）它们完全看不出来。

第 2 条则是一个通用判断：**任何带凭证的 URL 都不该被持久化**，因为凭证会过期而缓存不会。
