# 成为全栈·基础补充·Docker 入门

> Docker 把应用及其运行环境打包成镜像，降低“我电脑可以运行，服务器不行”的差异。它不会自动解决数据库、数据备份、密钥管理和生产部署问题，理解容器边界比会写一份 Dockerfile 更重要。

## 前言：镜像、容器和主机分别是什么

可以把镜像理解为只读的应用模板，把容器理解为基于镜像创建的一次运行实例。镜像包含文件系统、启动命令和元数据；容器启动后运行进程，并拥有隔离的网络、进程和文件视图。Docker Engine 在主机上管理镜像、容器、网络和卷。

容器不是虚拟机。它通常共享主机内核，启动更轻，但隔离边界和资源方式不同。容器退出后，可写层可能随容器删除；需要保留的数据库和上传文件应放在 volume 或外部存储，而不是依赖某个临时容器的文件系统。

## 一、Dockerfile 描述如何构建镜像

```dockerfile
FROM node:22-bookworm-slim AS build
WORKDIR /app
COPY package*.json ./
RUN npm ci
COPY . .
RUN npm run build

FROM node:22-bookworm-slim AS runtime
WORKDIR /app
ENV NODE_ENV=production
COPY --from=build /app/dist ./dist
COPY package*.json ./
RUN npm ci --omit=dev && chown -R node:node /app
USER node
CMD ["node", "dist/server.js"]
```

这是讲解多阶段构建的简化示例，项目入口、产物目录、运行时依赖和 Node 版本必须按实际工程验证。构建阶段可以安装编译工具并执行测试，运行阶段只复制需要的产物；非 root 用户运行能减少进程被攻破后的权限范围。

`COPY` 与 `.dockerignore` 会影响镜像内容。若把 `.env`、`node_modules`、Git 历史或构建缓存复制进镜像，不但变大，也可能泄露秘密。密钥应该在运行时由安全配置注入，而不是写进 Dockerfile 的 `ENV` 或构建参数中。

## 二、构建、运行和查看状态

常见生命周期是构建镜像、启动容器、观察日志、检查退出状态，然后更新镜像并重建容器。容器中的进程通常以前台主进程运行，由容器运行时管理；不要在容器里再启动一个不受控的后台守护进程。

如果容器立刻退出，检查启动命令、入口文件、环境变量和日志。若容器运行但外部访问不到，检查端口映射、应用监听地址和容器网络。Docker 的 `EXPOSE` 是镜像元数据说明，不会自动把端口公开到主机；运行时还需要明确映射或由编排网络访问。

## 三、数据、网络和服务编排

容器网络允许服务通过网络互相访问。在 Docker Compose 中，应用通常通过服务名连接数据库，例如 `db:5432`；主机上的 `localhost` 与容器里的 `localhost` 指向不同网络命名空间。这个区别是本地容器调试的常见陷阱。

Compose 用 YAML 描述多个服务、端口、卷、环境和健康检查，适合本地启动应用依赖：

```yaml
services:
  db:
    image: postgres:17
    volumes:
      - pgdata:/var/lib/postgresql/data
volumes:
  pgdata:
```

卷可在容器重建后保留数据库文件，但仍不是备份；误删卷、磁盘损坏和错误迁移仍会损失数据。备份文件要异地保存并演练恢复。健康检查可以帮助判断服务是否就绪，但 `depends_on` 是否等待健康取决于 Compose 配置和版本行为，不应靠默认猜测。

## 四、多阶段构建与原生依赖

镜像应与目标运行环境兼容。CPU 架构、glibc/musl、动态库和原生扩展都可能让“本机编译通过”在 Linux 容器失败。Go 项目若使用 CGO SQLite 驱动，需要 C 编译器和匹配的系统库，不能简单假设 `CGO_ENABLED=0` 就能构建相同功能的二进制。

多阶段构建常用一个阶段编译，再用更精简的运行时镜像；但不能为追求小镜像而移除程序运行需要的库和证书。目标平台的完整镜像构建、启动、数据库连接、上传和关闭行为需要实测。Dockerfile 存在、镜像 manifest 可查、容器已在目标环境运行，是不同级别的证据。

## 五、安全与资源边界

- 尽可能使用固定版本或 digest，定期更新基础镜像和依赖。
- 以非 root 用户运行，不挂载不必要的主机目录。
- 不把密码、私钥和 `.env` 打入镜像层。
- 限制容器 CPU、内存和文件系统写入，避免异常进程耗尽主机资源。
- 明确持久卷、备份、日志轮转和镜像清理策略。
- 只公开必要端口，数据库通常仅在应用网络内部可访问。

容器能隔离进程和依赖，但不是绝对安全边界。错误配置的特权容器、敏感主机挂载和开放管理端口仍可能带来严重风险。

## 六、本地开发与生产镜像不要混为一谈

开发容器常挂载源码、启用热重载和调试工具；生产镜像通常只含编译产物和必要运行依赖。开发体验优先与最小运行攻击面是不同目标。可以共享基础构建步骤，但要清楚区分镜像目标和环境变量。

Docker 也不意味着必须把所有东西都容器化。托管数据库、Cloudflare Worker 或 R2 等服务可能在平台外运行；本地 Compose 可以只启动数据库，让应用在主机运行。关键是记录本地服务拓扑、端口和数据卷所有权，避免清理命令误删其他项目的数据。

## 小结：容器封装环境，数据和部署仍需设计

镜像定义可复制的运行环境，容器执行镜像中的进程，网络和卷连接服务并保存需要保留的数据。多阶段构建、非 root、依赖锁定和秘密管理能提升可维护性，但 Docker 不替代备份、迁移、监控和目标平台验收。发布前要在与生产相近的架构上真正构建并运行镜像。
