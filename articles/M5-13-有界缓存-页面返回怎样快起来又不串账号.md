# 成为全栈·Taro 小程序篇·有界缓存：页面返回怎样快起来，又不串账号

> 缓存快不快，先看命中；缓存对不对，要看失效之后谁还能把数据写回来。

{{IMG:M5-13-封面}}

## 前言：点到哪里都等一次，用户会记得

APP 开发时，作者提出过很直接的反馈：点到哪个页面，数据都重新加载，感觉没有缓存。这个体验问题不能到了小程序再重演。

但“加一个 Map”只解决了最容易的一半。文章公开，收藏私有；点赞后列表需要更新；退出账号时旧请求还可能在飞行。我们要让返回更快，也要让错误的旧数据没有机会借缓存长期留下来。

当前方案刻意保持小：60 秒有效期、公共与私有分区、相同请求合并、容量上限和失效版本。没有引入持久化内容库，也没有离线写入队列。这篇把它的能力和边界一起说明。

## 一、缓存键先回答“是谁的数据”

read 生成的键包含 API、身份与完整路径。私有身份还带会话代次：

```ts
const identity = privateData
  ? `${session()?.user.id || 'guest'}:${sessionEpoch()}`
  : 'public';
```

API 区分本地与线上，userId 区分会员，epoch 区分同一会员退出再登录前后的会话上下文。路径中的筛选与页码则区分不同查询。

只用 `/me/favorites` 做键，A 退出后 B 会命中 A 的收藏；只加 userId，仍可能把一个旧会话读取的结果当成新会话结果。键的组成不是字符串技巧，而是数据所有权的声明。

公共读不带 Bearer，私有缓存单独存放。这样，公开文章不需要随每次换人全部丢弃，私人列表却必须及时清理。

## 二、有界，比“永远缓存”更诚实

当前公共容量为 80，私有容量为 60。数据超过有效期就不作为命中；写入超过容量时移除 Map 中较早的条目。

| 规则 | 解决的问题 | 当前边界 |
|---|---|---|
| 默认 60 秒 TTL | 短时间返回重复读取 | 不是实时一致性 |
| pending 合并 | 同一查询同时发起 | force 会绕过合并 |
| 80 / 60 条容量 | 长会话无限增长 | 按写入顺序淘汰 |
| 公私分区 | 公开内容与个人信息混放 | 页面仍要正确指定 privateData |
| clear 版本栅栏 | 旧读取在清理后回填 | 不取消底层网络请求 |

特别说明：当前不是完整 LRU。读取命中不会移动 Map 条目，只在写入时更新顺序。名字说准确，比套一个听起来高级的算法标签更有价值。

这是内存缓存，关闭小程序后不会保留正文。会话和草稿有各自本地存储，不能因为它们持久化，就宣称公开内容也支持离线启动。

## 三、清空 Map，为什么还不够

假设请求 A 正在读取收藏。用户退出，缓存被 clear；随后 A 返回。如果缓存无条件保存响应，清理动作就被旧任务撤销了。

项目在读取时捕获 version，回填时同时检查版本与任务身份：

```ts
// src/core/cache.ts
if (version === this.version && this.pending.get(key) === task) {
  this.entries.delete(key);
  this.entries.set(key, { value, until: Date.now() + ttl });
  while (this.entries.size > this.limit)
    this.entries.delete(this.entries.keys().next().value!);
}
```

version 保护 clear 之后的世界，pending 身份保护同一 key 的新读取。两者缺一个，force 新任务或失效清理都可能被更晚返回的旧结果覆盖。

清理也只由当前任务执行。旧任务 finally 不能把新任务的 pending 删除，否则并发合并会在最需要它的时候失效。

## 四、写操作采用保守失效，而非精细依赖图

普通非 GET 写入在 finally 清理私有缓存；非 `/me/` 的写入还会清理公共缓存。认证路径和阅读 `/view` 被排除。即使写操作失败，这个清理也会执行，因为失败并不总能证明服务端没有变化。

好处是规则直观，读者容易检查：评论或点赞之后，公共列表不会无限依赖旧计数；私人操作之后，会员列表会补读。代价是失效范围较粗，一次写入可能让无关公开资源也需要重新获取。

我们没有维护“某篇文章影响哪些列表”的实体依赖图。数据规模小、教学目标明确时，粗粒度规则更容易交付。以后请求成本升高，再依据实际热点收窄，而不是先写一套无人能完整验证的图。

本地互动 store 负责更快的跨页面计数反馈，缓存失效负责后续服务器校准。两者协作，但不能互相替代。

## 五、返回补读与主动刷新各走各的路

分页列表在显示时看成功时间与缓存 revision，必要时重新读第一页；资源 Hook 的显示补读也允许缓存命中。下拉刷新明确带 force，绕过旧命中和现有 pending。

因此，“调用 load”不等于“又联网了”。排查缓存时应看 read 的命中分支和请求证据，不能只从 loading 状态猜测网络次数。

失败时也有边界：缓存没有统一保留过期值并后台更新的 SWR 机制。列表 Hook 可能保留已经显示的 items，资源 Hook 则会清空失败结果。若产品以后要完整离线阅读，需要另行设计持久化、淘汰、账号清理和更新策略。

## 六、测试重点放在最容易出错的时间顺序

已有逻辑测试覆盖去重、隔离与失效竞态。人工观察返回体验有用，却很难稳定制造“旧请求恰好在清理后返回”。这类场景适合控制 Promise 完成顺序，断言缓存不会被旧结果重新填满。

可追加的性能验收，则应固定文章、网络和设备，记录返回路径的请求次数与时间。本次没有给出这类测量数字，因此不写“速度提升百分之多少”。
