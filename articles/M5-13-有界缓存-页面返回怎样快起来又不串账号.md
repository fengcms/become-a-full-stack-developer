# 成为全栈·Taro 小程序篇·有界缓存：页面返回怎样快起来，又不串账号

> 缓存快不快，先看命中；缓存对不对，要看失效之后谁还能把数据写回来。

{{IMG:M5-13-封面}}

## 前言：点到哪里都等一次，用户会记得

APP 开发时，作者提出过很直接的反馈：点到哪个页面，数据都重新加载，感觉没有缓存。这个体验问题不能到了小程序再重演。

但“加一个 Map”只解决了最容易的一半。文章公开，收藏私有；点赞后列表需要更新；退出账号时旧请求还可能在飞行。我们要让返回更快，也要让错误的旧数据没有机会借缓存长期留下来。

当前方案刻意保持小：60 秒有效期、公共与私有分区、相同请求合并、容量上限和失效版本。没有引入持久化内容库，也没有离线写入队列。这篇把它的能力和边界一起说明。

## 一、缓存键先回答“是谁的数据”

read 生成的键包含 API、身份与完整路径。私有身份还带会话代次：

```ts
// src/core/api.ts（节选）：键由 API、身份与完整路径组成。
export function read<T>(path: string, force = false, privateData = false, ttl = 60000) {
  const identity = privateData ? `${session()?.user.id || "guest"}:${sessionEpoch()}` : "public";
  return (privateData ? privateCache : cache).read(
    `${API}:${identity}:${path}`,
    () => api<T>(path, "GET", undefined, privateData),
    ttl,
    force,
  );
}
```

API 区分本地与线上，userId 区分会员，epoch 区分同一会员退出再登录前后的会话上下文。路径中的筛选与页码则区分不同查询。

只用 `/me/favorites` 做键，A 退出后 B 会命中 A 的收藏；只加 userId，仍可能把一个旧会话读取的结果当成新会话结果。键的组成不是字符串技巧，而是数据所有权的声明。

公共读不带 Bearer，私有缓存单独存放。这样，公开文章不需要随每次换人全部丢弃，私人列表却必须及时清理。换句话说，分区的依据不是“数据敏不敏感”，而是“它属于谁、换了人还算不算同一份”。

把键拼在一处还有一个可维护性收益：将来要新增身份维度（比如多租户或测试环境标识），只需要改这一行，而不用去每个调用方补参数。

## 二、有界，比“永远缓存”更诚实

当前公共容量为 80，私有容量为 60。数据超过有效期就不作为命中；写入超过容量时移除 Map 中较早的条目。

```ts
// src/core/cache.ts（节选）：两个分区只是同一实现的不同容量实例。
export class DataCache {
  private entries = new Map<string, { value: unknown; until: number }>();
  private pending = new Map<string, Promise<unknown>>();
  private version = 0;
  constructor(private limit = 80) {}
  revision() {
    return this.version;
  }
}
export const cache = new DataCache();
export const privateCache = new DataCache(60);
```

命中与合并都发生在很靠前的位置，因此重复读取几乎不会产生额外开销：

```ts
// src/core/cache.ts（节选）：命中直接返回，同 key 并发复用同一个 Promise。
const hit = this.entries.get(key);
if (!force && hit && hit.until > Date.now()) return hit.value as T;
const pending = this.pending.get(key);
if (!force && pending) return pending as Promise<T>;
```

| 规则 | 解决的问题 | 当前边界 |
|---|---|---|
| 默认 60 秒 TTL | 短时间返回重复读取 | 不是实时一致性 |
| pending 合并 | 同一查询同时发起 | force 会绕过合并 |
| 80 / 60 条容量 | 长会话无限增长 | 按写入顺序淘汰 |
| 公私分区 | 公开内容与个人信息混放 | 页面仍要正确指定 privateData |
| clear 版本栅栏 | 旧读取在清理后回填 | 不取消底层网络请求 |
| revision 递增 | 调用方判断缓存是否可能过期 | 只是信号，不等于数据已变 |

特别说明：当前不是完整 LRU。读取命中不会移动 Map 条目，只在写入时更新顺序。名字说准确，比套一个听起来高级的算法标签更有价值。

这是内存缓存，关闭小程序后不会保留正文。会话和草稿有各自本地存储，不能因为它们持久化，就宣称公开内容也支持离线启动。

容量取 80 和 60，不是经过压测得出的最优点，而是对内容站规模的估算。文章列表一次 12 条，几个分类加上搜索与详情，一个人在几十次跳转里也很少撑满；反过来，上限存在的意义是防止长会话无限增长，而不是精确控制内存。写清这一点，比给数字编一个来历更诚实。

同理，60 秒这个数字也不承载“数据最多旧一分钟”的承诺。它只表示在这个窗口内，返回同一页面可以先用已有结果；窗口之外是否重新请求，还要看页面自己的判断。把 TTL 当作数据新鲜度的保证，是这类实现最容易犯的误读。

如果以后要调整这两个数字，判断依据也应该是实际请求量与返回体验，而不是“别人写了 300 秒”。参数背后有没有可复述的理由，决定了它是配置还是猜测。

## 三、清空 Map，为什么还不够

假设请求 A 正在读取收藏。用户退出，缓存被 clear；随后 A 返回。如果缓存无条件保存响应，清理动作就被旧任务撤销了。

项目在读取时捕获 version，回填时同时检查版本与任务身份：

```ts
// src/core/cache.ts（节选）：回填前同时确认版本与任务身份。
if (version === this.version && this.pending.get(key) === task) {
  this.entries.delete(key);
  this.entries.set(key, { value, until: Date.now() + ttl });
  while (this.entries.size > this.limit)
    this.entries.delete(this.entries.keys().next().value!);
}
```

version 保护 clear 之后的世界，pending 身份保护同一 key 的新读取。两者缺一个，force 新任务或失效清理都可能被更晚返回的旧结果覆盖。

清理也只由当前任务执行。旧任务 finally 不能把新任务的 pending 删除，否则并发合并会在最需要它的时候失效。

这里有一个容易被跳过的细节：`this.pending.get(key) === task` 比较的是 Promise 对象本身，不是 key。同一个 key 在一次 clear 之后可能已经有第二个任务在飞，光看 key 存在与否，没法判断这次的返回到底属于哪一次请求。

## 四、写操作采用保守失效，而非精细依赖图

普通非 GET 写入在 finally 清理私有缓存；非 `/me/` 的写入还会清理公共缓存。认证路径和阅读 `/view` 被排除。即使写操作失败，这个清理也会执行，因为失败并不总能证明服务端没有变化。

```ts
// src/core/api.ts（节选）：写操作按范围保守失效，失败也执行。
} finally {
  if (method !== "GET" && !path.startsWith("/auth/") && !path.endsWith("/view")) {
    privateCache.clear();
    if (!path.startsWith("/me/")) cache.clear();
  }
}
```

好处是规则直观，读者容易检查：评论或点赞之后，公共列表不会无限依赖旧计数；私人操作之后，会员列表会补读。代价是失效范围较粗，一次写入可能让无关公开资源也需要重新获取。

“失败也清理”这一点值得单独说。一次 POST 超时，并不等于服务端没有落库；如果只在成功分支清理，就可能留下一个与服务端真实状态不符的缓存。宁可多清一次，也不要把不确定当成没发生。

我们没有维护“某篇文章影响哪些列表”的实体依赖图。数据规模小、教学目标明确时，粗粒度规则更容易交付。以后请求成本升高，再依据实际热点收窄，而不是先写一套无人能完整验证的图。

本地互动 store 负责更快的跨页面计数反馈，缓存失效负责后续服务器校准。两者协作，但不能互相替代。

## 五、返回补读与主动刷新各走各的路

分页列表在显示时看成功时间与缓存 revision，必要时重新读第一页；资源 Hook 的显示补读也允许缓存命中。下拉刷新明确带 force，绕过旧命中和现有 pending。

```ts
// src/hooks/data.ts（节选）：显示时按时间与版本决定补读。
useDidShow(() => {
  if (
    !lock.current &&
    loadedAt.current &&
    (Date.now() - loadedAt.current > 60000 ||
      revision.current !== (privateData ? privateCache : cache).revision())
  )
    void latest.current(true);
});
usePullDownRefresh(() => {
  void latest.current(true, true).finally(() => Taro.stopPullDownRefresh());
});
```

资源 Hook 也有类似的作废动作，只是判据换成了请求序号与会话代次：

```ts
// src/hooks/data.ts（节选）：资源 Hook 也会作废在途请求。
const id = ++serial.current, epoch = sessionEpoch();
if (!path || (privateData && !auth)) {
  setData(undefined);
  return;
}
```

因此，“调用 load”不等于“又联网了”。排查缓存时应看 read 的命中分支和请求证据，不能只从 loading 状态猜测网络次数。

失败时也有边界：缓存没有统一保留过期值并后台更新的 SWR 机制。列表 Hook 可能保留已经显示的 items，资源 Hook 则会清空失败结果。若产品以后要完整离线阅读，需要另行设计持久化、淘汰、账号清理和更新策略。


## 哪些内容暂时不值得缓存

缓存不是把每一次接口响应都留下来。一次性认证结果应交给会话管理；创建与提交响应应更新当前编辑状态；上传返回地址属于草稿内容；公开阅读计数上报是副作用。这些对象各有归属，塞进读取缓存反而让清理规则更复杂。

甚至同一个 GET，也可能需要明确 force。互动状态初始化强制确认点赞，避免只凭文章初始计数猜用户关系；私人收藏判断遍历分页，缓存可以减少重复读取，但不能只缓存第一页就断言全局不存在。

所以，引入缓存之前最好写清楚三个问题：可以复用多久，变化由什么动作触发，旧响应还有没有资格回填。答不清楚时，先保持显式读取比加一个永不清理的 Map 更安全。

### 版本失效有成本，也有容易理解的收益

全局公共版本递增，意味着多个资源的旧在途响应都可能失去缓存回填资格。它们仍可能把结果返回给原调用者，是否允许展示还由页面与身份检查决定。缓存版本并不直接取消一切 UI 更新。

这个区别值得认真看代码：缓存负责将来是否再复用，Hook 负责现在是否写状态。若产品需要“写入之后任何旧读取都不能显示”，需要额外在 Hook 检查读取时的缓存版本，不能假设 clear 已经包办。

当前粗粒度清理可能带来额外请求，但容量小、规则简单，便于教学和复核。只有测量表明某类资源重复读取造成明显成本，才有充分理由为它建立细粒度失效策略。

### 失败不该污染下一次命中

读取失败会拒绝 Promise，当前任务清理自己的 pending；同 key 当前失败还会删除旧条目。这样下一次不会把失败当成成功值缓存。

但是页面已经显示的数据是否保留，依然取决于 Hook。缓存中没有一个统一“离线旧值”出口。因此后续若增加断网阅读，要定义明确的来源提示、保存期限与私人信息处理，不能直接把 TTL 改成一天就称为离线模式。

缓存测试应控制时钟与 Promise 顺序，性能测试则应固定网络条件。前者证明规则，后者测量体验；没有量化记录时，就不要用“秒开”给文章收尾。

## 六、测试重点放在最容易出错的时间顺序

已有逻辑测试覆盖去重、隔离与失效竞态。人工观察返回体验有用，却很难稳定制造“旧请求恰好在清理后返回”。这类场景适合控制 Promise 完成顺序，断言缓存不会被旧结果重新填满。

```ts
// test/core.test.ts：清理之后，旧请求不能再把值填回。
const pending = c.read("a", () => wait.promise);
c.clear();
wait.resolve(1);
await pending;
assert.equal(await c.read("a", async () => 2), 2);
```

同一份测试里也固定了“同 key 并发只发一次请求”的约定：

```ts
// test/core.test.ts：并发读取共享同一次请求。
const a = c.read("key", fetcher), b = c.read("key", fetcher);
assert.deepEqual(await Promise.all([a, b]), [3, 3]);
assert.equal(calls, 1);
```

可追加的性能验收，则应固定文章、网络和设备，记录返回路径的请求次数与时间。本次没有给出这类测量数字，因此不写“速度提升百分之多少”。

继续阅读 [内容发现数据流]({{LINK:M5-14}}) 和 [点赞收藏跨页一致性]({{LINK:M5-17}})。缓存的价值，是让该复用的数据及时复用，让已经失去归属的数据无法悄悄回来。这两句话也正好对应它最难的两个部分：命中率，与归属。
