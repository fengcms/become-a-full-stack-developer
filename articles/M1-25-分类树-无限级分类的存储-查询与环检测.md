# 成为全栈·Node 后端篇·分类树：无限级分类的存储、查询与环检测

"给文章分个类"听起来简单，但真要做成一个能无限嵌套、能在前端渲染成树、还能防止用户把分类挂成环的系统，坑比想象中深得多。这一篇对照我们 `node-backend` 真实的 `categories` 表与 `services/category.ts`，讲清无限级分类怎么存、怎么查、以及那个经典的"环检测"问题。

## 一、无限级分类怎么存：parentId 自关联

最朴素也最常用的方案是**邻接表（adjacency list）**：每个分类一行，用 `parentId` 指向自己的父分类；根分类的 `parentId` 为 `NULL`。读 `src/db/schema.ts` 的 `categories` 表定义，正是这样：

```ts
// schema.ts 第 138-140 行
// 自关联父节点；SQLite 自引用 FK 会造成 Drizzle 类型成环，且 FK 默认不强制，
// 父存在性 / 成环 / 级联由应用层（services/category.ts + 删除守卫）保证，故此处不声明 references。
parentId: integer('parent_id'),
```

几个关键点：

- **`parentId` 可为 `NULL`**：表示这是根分类。一棵树的"根"就是所有 `parentId IS NULL` 的行。
- **最大深度 4 级**：契约 `Category.x-max-depth:4` 约束，注释里写明"由应用层在创建/变更 parentId 时校验"——数据库不强制，逻辑在 service 层把关。
- **slug 唯一索引**：`uniq_category_slug` 保证 slug 不重复；注释特别说明"分类 slug 必填，故等价于非空唯一"（不像文章 slug 允许 NULL 多行）。

## 二、P-33：为什么 parentId 不声明 references

注意 schema 里 `parentId` **没有**像 `articles.authorId` 那样写 `.references(() => categories.id)`。这不是漏写，是有意为之（P-33）：

1. **Drizzle 类型成环**：自引用外键会让 Drizzle 的类型推导陷入循环（`TS7022` 隐式 any / 类型无法解析），编译直接挂。
2. **SQLite 的 FK 默认不强制**：即使声明了，不加 `PRAGMA foreign_keys = ON` 也不会真正校验父存在性，等于摆设。
3. **约束要落在应用层**：父存在性、成环、级联删除，全部由 `services/category.ts` + 删除守卫在业务代码里保证。

结论：**数据库只负责存 `parentId` 这个整数，树的正确性由代码守护**。这是一种清醒的取舍——把"能编译、能跑"和"逻辑正确"分开，后者必须靠测试覆盖，而不是指望数据库帮你兜底。

## 三、怎么查：取全量，在内存里组装成树

无限级树最忌讳"每个节点发一次 SQL"（N+1）。我们的做法是**一次取全量，内存里组装**：

```ts
// category.ts
export const allCategories = async (): Promise<CategoryRow[]> =>
  getDb().select().from(categories).all();
```

`buildTree` 接收全部行，先按 `parentId` 分桶（`childrenOf` Map），再从根递归拼 `CategoryNode`：

```ts
export const buildTree = (rows: CategoryRow[]): CategoryNode[] => {
  const childrenOf = new Map<number | null, CategoryRow[]>();
  for (const r of rows) {
    const key = r.parentId ?? null;
    const bucket = childrenOf.get(key);
    if (bucket) bucket.push(r); else childrenOf.set(key, [r]);
  }
  const seen = new Set<number>();
  const toNode = (r: CategoryRow): CategoryNode => {
    if (seen.has(r.id)) return { /* 截断：避免环导致死递归 */ ... };
    seen.add(r.id);
    return {
      id: r.id, name: r.name, slug: r.slug,
      description: r.description ?? null, sortOrder: r.sortOrder,
      children: (childrenOf.get(r.id) ?? []).sort(bySort).map(toNode),
    };
  };
  return (childrenOf.get(null) ?? []).sort(bySort).map(toNode);
};
```

为什么一次性取全量？因为**树、深度、环检测、面包屑全部依赖"完整父链"**——你没法在只知道一个节点的前提下判断它会不会成环、深度多少。数据量在该项目规模下（几十到几百个分类）完全可控，全量取回内存处理是正确且高效的选择。如果将来分类涨到十万级，再考虑物化路径（path enumeration）或闭包表（closure table），那是另一个话题。

## 四、P-34：深度限制，四级封顶

契约规定分类最多嵌套 4 级。`category.ts` 用 `MAX_CATEGORY_DEPTH = 4` 常量收口，并提供 `depthOf(rows, id)` 沿 `parentId` 向上数祖先层级（根=1）：

```ts
export const depthOf = (rows, id) => {
  const byId = new Map(rows.map((r) => [r.id, r]));
  let cur = byId.get(id), depth = 0;
  const seen = new Set<number>();
  while (cur) {
    if (seen.has(cur.id)) break; // 防御：数据异常成环时避免死循环
    seen.add(cur.id);
    if (cur.parentId == null) break;
    cur = byId.get(cur.parentId);
    depth += 1;
  }
  return depth + 1;
};
```

注意 `seen` 集——它不止是性能优化，更是**防御性编程**：万一数据已经腐化成环（比如直接手改库），`depthOf` 不会陷入死循环。`createCategory` 在挂父时校验 `depthOf(parent) + 1 > MAX` 就抛 409（错误码 3002，超出最大嵌套深度）；`updateCategory` 移动整棵子树时，用 `subtreeHeight` 算出"被移动子树高度"，要求 `父深度 + 子树高度 ≤ 4`，防止"把一个很深的子树挪到某父下"后整体超限。

## 五、P-36：环检测，千万别把节点挂到自己的子孙下

邻接表最大的雷是**成环**：如果允许把 A 挂到它的子孙 B 下面，整棵树就出现了循环引用，`buildTree` 会死递归，面包屑会无限循环。所以建/改 `parentId` 前必须做环检测：

```ts
export const wouldCreateCycle = (rows, nodeId, newParentId) => {
  if (newParentId == null || nodeId == null) return false;
  if (newParentId === nodeId) return true;        // 自挂
  const byId = new Map(rows.map((r) => [r.id, r]));
  let cur = byId.get(newParentId);
  const seen = new Set<number>();
  while (cur) {
    if (seen.has(cur.id)) break;
    seen.add(cur.id);
    if (cur.id === nodeId) return true;            // 新父是自身的子孙 → 成环
    if (cur.parentId == null) break;
    cur = byId.get(cur.parentId);
  }
  return false;
};
```

逻辑很直白：从"拟设的新父"向上爬父链，如果在父链上撞见"被移动的节点自身"，说明新父是它的子孙，挂上去就成环，拒绝（409 / 3002）。`updateCategory` 只在 `newParent !== existing.parentId` 时才跑这个检测——父没变就不必检。

这里有个值得记住的工程经验：**环检测分两层**。第一层是"写入时拒绝成环"（`wouldCreateCycle`），从源头堵住；第二层是 `buildTree` / `depthOf` / `toBreadcrumb` 里的 `seen` 防御，假设"万一数据已经脏了"也不崩。两层互补，前层防人为错误，后层防历史脏数据，健壮性就来自这种"不信任输入"的叠加。

## 六、P-28：删除守卫，x-cascade:none

分类不能随便删。如果它下面还有子分类、或还挂着文章，直接删会让那些数据变成"孤儿"。契约规定 `x-cascade:none`（不级联），所以删除前必须查引用，有依赖就拒：

```ts
export const deleteCategory = async (id) => {
  // ... 存在性校验
  const child = await db.select({ id: categories.id })
    .from(categories).where(eq(categories.parentId, id)).limit(1).all();
  if (child) throw new AppError(ErrCode.CONFLICT, 409); // 3002 仍有子分类

  const ref = await db.select({ id: articles.id })
    .from(articles)
    .where(and(eq(articles.categoryId, id), isNull(articles.deletedAt)))
    .limit(1).all();
  if (ref) throw new AppError(ErrCode.CONFLICT, 409);   // 3002 仍有文章归属

  await db.delete(categories).where(eq(categories.id, id)).run();
};
```

两点细节：

- **查子分类**用 `parentId = id`，存在即拒——逼着调用方先删叶子、再删父。
- **查文章引用**带 `isNull(articles.deletedAt)`：软删除的文章不算"活引用"，不会误拦删除（和全站软删除纪律一致）。

这正是 P-28 删除守卫的范本：删除是破坏性操作，先问"还有谁依赖我"，有就返回 409 让调用方自己处理依赖，而不是替它做危险的级联删除。

## 七、getCategoryStats：各分类已发布文章数

前端常要在分类树旁显示"该分类下多少篇文章"。这个统计如果靠"先取分类、再逐个 count 文章"会又掉进 N+1。我们的 `getCategoryStats` 用一次 `LEFT JOIN` 解决：

```ts
export const getCategoryStats = async () => {
  const rows = await getDb()
    .select({
      id: categories.id, name: categories.name, slug: categories.slug,
      articleCount: sql<number>`count(${articles.id})`,
    })
    .from(categories)
    .leftJoin(articles, and(
      eq(articles.categoryId, categories.id),
      eq(articles.status, 'published'),     // 只数已发布
      isNull(articles.deletedAt),           // 排除软删除
    ))
    .groupBy(categories.id)
    .all();
  return rows.map((r) => ({ ...r, articleCount: Number(r.articleCount) }));
};
```

`LEFT JOIN` + `count(articles.id)` 的精妙在于：没有文章的分类，`count` 自然返回 0（不会因 INNER JOIN 被过滤掉）；`eq(status,'published')` + `isNull(deletedAt)` 保证只统计"活的已发布"文章。这和我们在 M1-16 讲过的"标签精确计数"是同一条原则——**统计要对齐真实可见口径，别用 JSON 子串那种会虚高的土办法**。

## 八、面包屑：从当前分类一路回溯到根

电商/博客详情页顶部的"首页 > 后端 > Node > 部署"就是面包屑。`toBreadcrumb` 从当前节点沿 `parentId` 向上爬，把路径 `unshift` 成"根在前"的数组：

```ts
export const toBreadcrumb = (rows, id) => {
  const byId = new Map(rows.map((r) => [r.id, r]));
  const path = []; const seen = new Set<number>();
  let cur = byId.get(id);
  while (cur && !seen.has(cur.id)) {
    seen.add(cur.id);
    path.unshift({ id: cur.id, name: cur.name, slug: cur.slug });
    if (cur.parentId == null) break;
    cur = byId.get(cur.parentId);
  }
  return path;
};
```

同样带 `seen` 防御——哪怕数据成环，也最多回到起点就停，不会无限循环。返回空数组表示 id 不存在，路由层据此返回 404。

## 九、薄路由：读公开，写要 editor

`routes/categories.ts` 把所有端点收在一处，清晰分成两半：

- **公开读**：`GET /`（平铺列表）、`GET /tree`（无限级树）、`GET /stats`（统计）、`GET /:id/breadcrumb`（面包屑），全部 `security:[]`，匿名可访问。
- **editor 写**：`POST /`、`PUT /:id`、`DELETE /:id`，统一 `authMiddleware, guard('editor')`，薄路由只做校验 + 委托 service + 包信封。

可以看到"骨架"和之前讲的文章、标签路由完全一致——**薄路由纪律**在这里再次体现：路由不碰 `getDb`、不做业务判断，所有树的复杂度都收敛在 `services/category.ts`。这也是为什么 `category.ts` 文件偏长（约 373 行），但注释里明确标注了"services 例外"——因为序列化、树、环检测、深度、面包屑、增删改这些逻辑**紧密耦合**，拆开反而割裂它们的协作。

## 十一、常见误区与升级信号

把上面几个点反过来看，就是新手最容易踩的坑，对照我们的真实实现逐条避雷：

1. **误区：每个节点发一次 SQL 取子**。有人写"先查根，再对每个根查它的子，再对每个子查孙子……"——这是教科书级 N+1，层级越深越慢。我们一律 `allCategories()` 一次取全量，内存里 `childrenOf` 分桶组装，SQL 数量恒为 1。
2. **误区：只在写入时检测环，以为数据永远干净**。`wouldCreateCycle` 确实从源头堵住人为成环，但万一有人直接手改库、或历史迁移带入脏数据呢？我们的 `buildTree` / `depthOf` / `toBreadcrumb` 全都带了 `seen` 防御集——即使数据已经成环，递归也会在撞见重复 id 时停下，绝不死循环。这是"不信任任何输入"的工程底线。
3. **误区：删除时级联把子分类一起删**。看似方便，实则危险：用户可能并不知道底下还挂着重要文章。我们严格 `x-cascade:none`，有子分类或活文章引用就返回 409，逼调用方显式先处理依赖，删除行为完全可预期。
4. **误区：统计用嵌套 count 子查询或 JSON 子串**。`count(select ...)` 在列表里会放大成 N+1；JSON 子串统计还会把"内容里恰好出现关键词"误算进去。我们 `LEFT JOIN` + `groupBy` + 已发布/未删过滤，一次 SQL 出全部精确数字。

**什么时候该换存储模型？** 邻接表（parentId）在"分类几十到几百、偶尔整树读取"的场景下是最优解。但如果你遇到下面任一信号，就该考虑升级：

- 分类涨到十万级，`allCategories()` 一次取全量开始吃内存 → 改用**物化路径（path enumeration）**，每行存 `/1/3/7` 这样的祖先路径，查子树用 `LIKE '/1/3/%'` 一次命中。
- 频繁需要"查某节点的所有祖先"或"所有后代"做权限/归类 → 上**闭包表（closure table）**，单独一张 `(ancestor, descendant, depth)` 表，空间换时间，查询 O(1)。
- 要支持"移动到新父时整棵子树自动重算路径" → 物化路径 + 触发器，或闭包表的批量更新。

对我们这个教学 + 演示定位的项目，规模远没到那一步，邻接表 + 内存组装既直观又好测，刻意不过度设计——这本身也是一种纪律：**架构匹配当前规模，别为想象中的十万分类提前背上闭包表的复杂度。**

## 十二、小结

无限级分类看似一个字段（`parentId`），实则一整套守护逻辑：

1. **存储**：邻接表 `parentId` 自关联，`NULL` 为根；最大 4 级（契约 `x-max-depth:4`）；slug 唯一。
2. **P-33**：`parentId` 不声明 `references`——避开 Drizzle 类型成环，且 SQLite FK 默认不强制，约束交应用层。
3. **查询**：一次取全量 `allCategories()`，内存 `buildTree` 组装，杜绝 N+1。
4. **P-34**：`MAX_CATEGORY_DEPTH=4` + `depthOf`，建/移子树超界即 409（3002）；`seen` 防御脏数据死循环。
5. **P-36**：`wouldCreateCycle` 写入时拒绝成环；`buildTree` 的 `seen` 再兜底，两层防御。
6. **P-28**：删除守卫 `x-cascade:none`，有子分类或活文章引用即 409，逼调用方先清依赖。
7. **统计**：`getCategoryStats` 用 `LEFT JOIN` + `count` + 已发布/未删过滤，精确计数不虚高。
8. **面包屑**：`toBreadcrumb` 向上回溯，`seen` 防环；薄路由读公开、写 `guard('editor')`。
