# 成为全栈·React 管理后台篇·前端质量门禁：契约守卫、纯函数测试与浏览器验收

> 类型检查、规范检查、单元测试、生产构建和浏览器验收发现的是不同错误。全部通过也不是“零缺陷”，而是一组有边界的证据。

## 前言

这个后台曾出现一种很危险的情况：TypeScript 通过，单测通过，接口函数也返回数据，页面却因为把分页写成 `items` 而拿不到列表。类型声明本身就是前端手写的错误版本，类型系统只证明代码符合错误声明。

还有一些问题完全相反：代码和契约都正确，连续粘贴图片时却覆盖正文；390px 窄屏出现横向滚动；返回列表丢失页码。这些必须在真实交互中才能发现。

## 四道自动门禁各管什么

```bash
pnpm typecheck
pnpm lint
pnpm test
pnpm build
```

| 门禁 | 擅长发现 | 无法证明 |
| --- | --- | --- |
| typecheck | 类型、空值、调用形状 | 声明是否符合真实接口 |
| Biome | 可疑写法、格式与 import | 业务行为是否正确 |
| Vitest | 已声明的输入输出边界 | 未编写的交互路径 |
| build | 生产解析、资源与分包 | 页面是否好用 |

四者不能互相替代。构建成功不代表测试通过，测试通过也不代表生成代码能被生产打包。

## 契约守卫为什么要写反向断言

项目以 OpenAPI 为唯一事实源，但计划曾把用户端点写成 `/admin/users`，实际是 `/users`；likes 曾被误认为分页，实际返回裸数组。除了验证正确路径，还要钉死错误路径不存在：

```ts
expect(requestedUrl).not.toContain('/admin/users')
expect(result).not.toHaveProperty('list')
```

反向断言防止后来者凭经验把代码“修回”错误方案。它们保护的是项目特有差异，而不是 HTTP 客户端能不能发 GET。

请求信封、评论 method、站点公开/后台路径和分页字段都使用同类守卫。测试价值不在覆盖率数字，而在拦住会静默失败的契约误读。

## 纯函数测试守住难以目测的边界

分类树的父级映射、子孙收集、最大深度和成环排除被抽成纯函数；文章表单映射、图片大小校验与权限判断也同样处理。这些逻辑输入输出明确，运行快，失败容易定位。

并发刷新测试则人为延迟刷新接口，让三个 401 落入同一窗口，断言只调用一次 `/auth/refresh`。手工点击几乎无法稳定复现这类竞态，自动测试正适合守它。

最终验收为 14 个测试文件、69 个用例。旧阶段复盘中的 12/62 是当时快照，不能继续作为最终数字。

## 浏览器验收补上用户路径

最终真机走查覆盖新建保存、发布校验、已发布文章普通保存、未保存离开提醒、连续粘图、列表返回、批量审核、评论上下文、站点品牌刷新，以及 390px/1280px 的明暗主题。

浏览器验收不是随便点几下。每条路径要写出前置数据、动作和可观察结果，并使用独立临时数据库，避免污染已有环境。

它仍有边界：中文输入法组合、精确上传竞态、批量部分失败和过滤拒绝尚未全部做自动化故障注入。验收报告明确记录这些未验证项，而不是用“全绿”掩盖。

## 为什么当前没有硬补 E2E

项目现有测试集中于请求层、契约守卫和纯函数，没有 jsdom 组件测试或 Playwright E2E。对关键发布路径，E2E 确实有价值；但为了数字好看临时写一批只检查页面标题的测试，并不能保护真正风险。

合理的下一步是覆盖登录恢复、文章发布、列表返回和图片上传等跨层路径，并为后端准备可重复测试数据。测试成本要花在高损失、易回归、人工难复现的地方。

## 门禁必须在 CI 中只读运行

本地 lint 使用 `--write` 可以自动修复，CI 必须使用只读 `biome check`。如果 CI 一边检查一边修改工作区，它可能“修好”问题后返回成功，却没有把修复提交回仓库。

生成类型也应在契约变更时重新运行并检查 diff。未来可以在 CI 中生成到临时位置后比较，证明 OpenAPI 与提交的 `api.gen.ts` 没有漂移。

## 小结

质量门禁是一组互补证据：契约守卫保护前后端事实，纯函数测试保护边界算法，并发测试制造人工难撞的窗口，构建验证生产产物，浏览器验收确认完整工作流。报告未覆盖项与报告通过项同样重要。
