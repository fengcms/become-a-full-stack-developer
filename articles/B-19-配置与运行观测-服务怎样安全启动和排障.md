# 成为全栈·基础补充·配置与运行观测：服务怎样安全启动和排障

这个项目有条我给自己定的规矩：**不在业务代码里读 `process.env`。**

原因是 M1 讲的那个原则——**外部输入要在一个地方收口**。而这条规矩后来救了我一次，也暴露出它的不足。

先说救的那次。

微信登录出故障（就是 M1-34 那个 `redirect` 的问题），我第一反应是怀疑密钥配错了。理由听起来很充分：**密钥名我检查过、上传工具显示成功。**

而真正的原因是运行时不接受一个 fetch 选项。**密钥完全没问题。**

这两件事之间隔着一次网络调用和一次运行时校验——而"上传成功"只能证明前面那一半。

这篇讲这个项目的配置怎么收口，以及排障时我逐渐意识到的一个缺口。

## 配置收口：不在业务代码里读环境变量

先看这个项目的配置入口：

```ts
/**
 * 运行环境单一入口。所有外部配置（JWT 密钥、DB 路径、CORS…）都收口到这里，
 * 业务 / 中间件不直接读 process.env，统一经 readEnv 解析校验后注入。
 */
import { z } from 'zod';

const schema = z.object({
  WECHAT_MINI_APP_ID: z.string().optional(),
  WECHAT_MINI_APP_SECRET: z.string().optional(),
  JWT_SECRET: z.string().min(1, 'JWT_SECRET 必填'),
  DB_FILE: z.string().default(':memory:'),
  STORAGE_DRIVER: z.enum(['local', 'r2']).default('local'),
  CORS_ORIGINS: z.string().default('*'),
  NODE_ENV: z.enum(['development', 'production', 'test']).default('development'),
  PORT: z.string().default('3000'),
  R2_BUCKET: z.unknown().optional(),
  DB: z.unknown().optional(),
});

export const readEnv = (src: Record<string, string | undefined>): AppEnv => schema.parse(src);
```

这个 schema 就是**唯一的配置真相源**。它带来四个东西：

**一、类型从 schema 推导。**

```ts
/** 应用运行环境类型（由 schema 推导，保证与校验一致）。 */
export type AppEnv = z.infer<typeof schema>;
```

**这一行消掉了一类真实 bug**：以前 `process.env.STORAGE_DRIVER` 的类型是 `string | undefined`，而它实际只能是 `'local' | 'r2'`。**于是各处都要写一次类型判断**，而其中一处漏写就是运行时的意外分支。

**二、`z.infer` 意味着 schema 和类型不可能不一致。** 因为类型是"算出来的"，不是"写的"。

**三、默认值集中在 `default` 里。** 这对 M4-27 讲的那个问题很重要——配置散落在各处时，你根本不知道哪些有默认值。

**四、枚举值被约束。**

```ts
STORAGE_DRIVER: z.enum(['local', 'r2']).default('local'),
NODE_ENV: z.enum(['development', 'production', 'test']).default('development'),
```

而 `zod` 对无效值会抛错，配合后面的 `parse` 意味着**服务在启动时就崩，而不是在第一次用到的时候。**

**配置错误在启动时暴露，代价是重启；在运行时暴露，代价是一个奇怪的线上故障。**

## 为什么"未安装时抛错"是必要的

还有一小段，但它是整个文件里我最看重的一部分：

```ts
let active: AppEnv | null = null;

/** 安装当前环境（应用启动时调用一次）。 */
export const setActiveEnv = (env: AppEnv): void => {
  active = env;
};

/** 取当前环境；未安装时抛错，防止配置被悄悄遗漏。 */
export const getActiveEnv = (): AppEnv => {
  if (!active) throw new Error('Env not installed; call setActiveEnv() first.');
  return active;
};
```

**为什么不让 `getActiveEnv()` 在未安装时返回 null 或一个默认对象？**

因为那两种都会让配置问题"安静地存在"：

- 返回 null → 后面所有 `env.XXX` 都是 `undefined`，而大部分地方不会崩，只是拿到 undefined 后行为异常
- 返回默认对象 → 更糟，因为 `JWT_SECRET` 会是 `undefined`，**而代码里 `sign(undefined)` 可能真的能跑出一个 token**——直到线上才出问题

而抛错的版本是：**忘记调用 `setActiveEnv()` 会立刻炸，栈指到确切的位置。**

**这和 M4-06 讲的那个 `sessionProvider` 抛 `UnimplementedError` 是同一个模式。** 用"显式失败"代替"默认的假值"，让配置遗漏变成一个立刻可见的错误。

**判断标准是：错误的默认行为 vs 错误的报错，哪个更容易被发现。** 配置这一项，报错明显更容易。

## 排障的第一步：先确认失败在哪条边界

回到那次故障。

我当时能做的低成本检查有三个，前两个我已经做了：

| 检查 | 结果 | 能支持的判断 |
|---|---|---|
| 普通文章 GET | 正常返回 | 服务在跑、数据库连着、路由正常 |
| `secret list` | 两项微信配置存在 | 上传到目标 Worker 的键名正确 |
| **用无效 code 调 callback** | **返回 500**（而非"凭证无效"） | **请求大概率没发出去** |

**第三条是真正有信息量的那一条。**

一个无效 code，如果请求成功发到了微信，应该得到"凭证无效"的响应（或者微信的错误码被映射成 401）。而我拿到的是 500——**说明它在到达微信之前就失败了。**

所以这次探测**把"创建会员、写数据库、签发令牌"这些全部排除在了主要排查路径之外**，而这个判断只需要发一个请求。

这比"密钥有没有抄错"有用得多，因为：

**它检验的是流程，而猜测检验的是某个具体值。**

而"猜测某个具体值"有个问题：**它永远有可能性成立**。你可以换密钥、可以改配置、可以重启——每次都有一个新的"也许"。而流程探测一次就能收敛。

## 日志：脱敏的难点在"你不知道它会带出什么"

现在讲这次故障里我加的东西，以及为什么它值得单独一节。

原来的实现方向是对的：**捕获上游异常，返回统一的内部错误，不把微信的敏感字段交给客户端。**

但它的日志不足以区分四种情况：

- 环境变量没配
- 请求根本没发出去
- 微信拒绝了 code
- 微信返回了非预期格式

所以加了受控的原因枚举：

```ts
if (!appId || !secret) {
  console.warn('[wechat.exchange]', { reason: 'missing_configuration' });
  throw new AppError(ErrCode.INTERNAL, 500, '微信登录尚未配置');
}
```

而这个 `reason` 是**枚举出来的字符串**，不是原始对象。这是有意的：

```ts
// 不记录异常对象或请求 URL：它们可能包含 AppSecret 和临时 code。
console.warn('[wechat.exchange]', { reason: 'transport_or_invalid_response' });
```

**为什么不能直接 `console.error(error)`？** 因为 `fetch` 抛出的异常对象里，**URL 是作为属性挂着的**——而那个 URL 的查询串是 `?appid=...&secret=...&js_code=...`。

同理不能打印请求 URL，也不能打印微信的响应全文（万一它回显了什么）。

**而这三条恰好是"加个日志看看"时最容易被顺手打出去的东西。**

所以这里的做法是：

> **先决定日志真正需要哪些字段，然后只记那些字段。**

而不是"先记全的，之后再脱敏"。因为**事后脱敏要求你事先知道哪些字段敏感**——而漏掉一个就是泄露。

判断标准可以直接给：

> **这条日志会不会出现在一个用户能看到的地方？** 如果会，它里面的每个字段都要按"用户可能看到"来审。

云原生的日志系统会把日志转发到第三方服务，而**能读日志的人通常比能读数据库的人多**。所以这个标准不能放宽。

## 一个我以为做了、其实没做的功能

现在说我逐渐意识到的缺口。

契约里，每个响应都有 `requestId`：

```yaml
required: [code, message, requestId, timestamp]
```

而实现是：

```ts
/** 生成请求 ID（优先 Web Crypto 的 UUID，降级用时间戳）。 */
const requestId = (): string =>
  globalThis.crypto?.randomUUID?.() ?? `req_${Date.now().toString(36)}`;

/** 组装信封。requestId / timestamp 每次响应即时生成。 */
const envelope = <T>(code: number, message: string, data: T | null): Envelope<T> => ({
  code, message, data,
  requestId: requestId(),
  timestamp: new Date().toISOString(),
});
```

**这段代码没问题。** requestId 生成了、信封里有、契约里声明了。

问题在于它**每次响应即时生成**，也就是说：

**响应里的 requestId 和服务端日志里的任何东西都没有关联。**

用户报错说"我看到了 requestId: xxx"，而我拿着这个 ID **无法在日志里找到对应的任何一行**——因为它只出现在响应体里，从来没进过日志。

**而 requestId 的全部意义就是"把用户的报错和服务器的日志对上"。** 现在它是随机生成的一个漂亮字符串，没有连接任何东西。

正确的做法应该是什么，我很清楚：

- 请求进入时生成（或从上游 header 取，比如 `cf-ray`）
- **存进请求上下文**（Hono 的 `c.set`）
- 响应里的 `requestId` 用它
- 所有日志行也带上它

而这个项目没有做。**而且它现在有一半的基础设施了**——`envelope()` 已经是唯一出口，只要把 `requestId()` 换成从上下文取值就能接上。

**为什么一直没做？** 因为单看代码，"有 requestId 字段"这件事看起来已经完成了。而契约测试也过了（字段存在、类型对、示例完整），**没有任何一条断言会说"这个 requestId 必须在日志里出现"**。

**这就是契约门禁的一个天然边界**：它检查"契约自身是否自洽"，检查不了"这个字段和别的系统对不对得上"。

**我把它记在这里而不是等出问题再说**，因为这类缺口的特点是——**没有人会因为它报错，它只是让排障变难。**

## 排障工具的边界

顺带说一个我实际用过的方法，它在这次故障里救了时间。

排查时我做的第一件事不是看代码，是**构造一个最小的、会失败的调用**：

```text
用无效 code 调 callback
  → 如果返回 401/1002 → 请求发出了，问题在微信侧或 code 生成
  → 如果返回 500        → 问题在发出请求之前或之后解析
```

这个方法的价值在于它**不依赖任何假设**。它只问"流程走到哪一步了"。

而对比我原本的做法——"检查密钥有没有抄错"——**那是一个关于具体值的猜测，它有无穷多种可能，而且每一个都能让我感觉"也许是它"**。

**排查的第一原则是：先确定边界，再怀疑具体。** 而确定边界的手段是一次廉价的探测，不是对代码的反复阅读。

这条经验和 M1-34 是配套的：**M1-34 讲怎么找到那个 bug，这篇讲怎么在找到之前缩小范围。**

## 一条我一开始想省掉的事

`env.ts` 里那个 `active` 全局变量和"未安装时抛错"的检查，第一版我写的是：

```ts
// 第一版
export const getActiveEnv = (): AppEnv => active ?? parseEnv(process.env);
```

这样在测试里很方便——不用先调 `setActiveEnv`，直接能用。

后来发现的问题是：**它把两种完全不同的失败变成了同一种。**

一种是"服务没启动到 `setActiveEnv` 那一步"（初始化顺序错了），另一种是"这个测试环境忘了装配置"。前者是**部署问题**，后者是**测试问题**，但它们都不会立刻炸——而是"看起来能跑"。

而更糟的是第三种情况：**某个中间件在启动早期读了配置，而那会儿 `active` 还是 null，于是它拿到的是当时的 `process.env` 快照**。等 `setActiveEnv` 调用之后，后面的代码用的是 `active`。**同一个进程里，两处用了不同来源的配置。**

这种问题极难查，因为它表现出来的症状是"某个功能的配置不生效"，而不是任何明确的报错。

改成"未安装就抛错"之后，这个窗口消失了——**要么你能读到配置，要么你立刻知道读不到。**

代价是每个测试文件开头都要写一行 `setActiveEnv(...)`。**而这个代价是可以接受的：它换来的是"配置来源永远只有一个"。**

## 小结

配置与观测这件事，本项目沉淀下来的三条：

1. **配置在启动时收口并校验**，类型从 schema 推导，枚举值受约束，默认值集中。
2. **未初始化就抛错**，而不是返回默认对象——因为错误的配置会安静地存在，而报错立刻可见。
3. **日志先决定要记什么，再记**——事后脱敏要求你事先知道哪些字段敏感，而漏一个就是泄露。

而这次故障最大的收获是一句排查原则：

> **先确定流程走到哪一步，再怀疑具体值。**

一次"用无效 code 探测"的成本是发一个请求，而收益是**把六七个可能的故障方向砍到一条**。

至于那个缺口：**requestId 目前只存在于响应里，没有和日志关联，所以用户报上来的 ID 我用不了。** 而修它需要的不是新知识，是把 `envelope()` 里那个函数调用换成上下文取值——**难点从来不在实现，而在发现"它看起来已经做完了"。**

下一篇讲并发幂等与重复请求。它会回到 `changes()=1` 那个例子，但视角不同：**那次故障里，"两个请求同时到达"不是一个异常场景，而是一个必然会发生的正常场景。**
