# 成为全栈·基础补充·配置与运行观测：服务怎样安全启动和排障

> 服务能在开发机启动，只说明一组本地配置可用。可靠的运行环境还要能拒绝危险配置、保护密钥、留下足够的排障线索，并在停止时把正在处理的请求安全收尾。

## 前言：最难排查的故障，往往发生在“代码没变”时

数据库地址填错、JWT 密钥为空、对象存储切到了 R2 却没有凭据、代理转发了错误的客户端 IP，这些问题不一定来自业务代码，却可能让服务无法启动、所有登录失效，或把内部错误暴露给用户。另一些问题则表现为“偶尔很慢”“某些用户上传失败”，只有请求耗时、错误类型和依赖状态等信号，才能缩小调查范围。

运行配置和可观测性不是大公司才需要的复杂平台。即使是一个人维护的服务，也要回答三个基本问题：程序拿到了什么配置？它现在是否健康？发生错误时，日志是否足以说明问题又没有泄露秘密？

## 一、配置要在启动时集中解析和验证

应用不要在每个业务函数里随手读取环境变量。更稳妥的做法是启动时读取环境、解析类型、校验组合，然后构造一个不可变的配置对象并注入依赖：

```text
环境变量 / .env
       ↓
读取与解析 → 必填项校验 → 组合约束校验
       ↓
不可变 Config → HTTP、数据库、存储、认证依赖
```

这样业务逻辑不需要到处检查 `os.Getenv`，测试也可以直接构造配置，不依赖开发者电脑的 shell 状态。配置错误最好尽早、明确地在启动时失败，而不是等到第一位用户上传文件时才发现 R2 密钥为空。

常见配置校验包括：

| 配置 | 应有的检查 |
|---|---|
| 数据库驱动与 DSN | 驱动在允许列表中，地址非空，测试/生产库分开 |
| JWT 密钥 | 生产环境有足够随机性，不使用公开示例值 |
| CORS 来源 | 生产不接受任意通配，凭据请求只允许明确来源 |
| 代理信任 | 仅从配置的代理网段读取转发 IP |
| 存储驱动 | local/R2 参数成套校验，缺少必要项时拒绝启动 |
| 超时与限制 | 正数、合理上界，避免零值关闭保护或无限等待 |

应用配置与部署环境分离：代码仓库存默认值和校验逻辑，环境注入密钥和地址；`.env` 仅用于本地开发并加入忽略清单。一个方便的本地文件不应该成为生产凭据管理方案。

## 二、配置变化要有来源和优先级

同一项配置可能同时出现在进程环境、`.env` 文件、命令行参数或部署平台设置里。若优先级不清楚，开发者以为自己改了数据库地址，程序实际却继续使用另一处旧值。

项目 Go 工具在本地自动读取 `.env`，已有进程环境变量优先；迁移导入工具还使用单独的 `TRANSFER_DATABASE_URL`，不自动复用应用数据库地址。这类隔离减少了“把数据导入错库”的风险。配置文档要明确优先级、适用命令和是否会覆盖已有数据，尤其是迁移、seed 和数据导入工具。

不要在启动日志里完整输出配置对象。可以记录数据库驱动、存储类型、监听地址和配置来源，但要隐藏 DSN 密码、JWT 密钥、AppSecret、签名 URL 和 Cookie。日志本身也可能被集中收集、长期保存或多人访问。

## 三、日志记录“发生了什么”，不要记录秘密

结构化日志将字段作为独立属性保存，而不是把所有内容拼成一段难以查询的字符串。一个普通请求可以记录：

```json
{
  "request_id": "req-...",
  "operation": "GET /articles/{slug}",
  "status": 200,
  "duration_ms": 18
}
```

出现故障时，再关联脱敏错误类别、数据库操作统计或外部服务耗时。用户密码、访问令牌、刷新令牌、Cookie、微信 code、AppSecret、OpenID 和完整上传内容不应进入普通日志。记录“请求失败，错误类型是数据库超时”通常足够排查，不需要把 DSN 和 SQL 参数一起打印出来。

日志级别也要有约定：正常访问用信息级别，预期的参数错误避免刷屏，异常和关键失败提供上下文；调试输出不能默认包含敏感请求体。错误要带请求标识，才能从用户报告的时间范围找到对应事件。

## 四、健康、就绪和业务诊断是不同信号

“健康检查返回 200”不一定说明所有依赖都可用。常见地可以区分：

- **存活**：进程是否还在运行，是否需要被重启。
- **就绪**：服务是否可以接收流量，必要依赖和初始化是否完成。
- **依赖诊断**：数据库、对象存储或微信服务的状态和耗时，用于内部观察。

不要把诊断细节通过公网健康端点返回。若数据库暂时不可用，存活探针可能仍应保持成功，避免编排系统不断重启一个正在等待恢复的进程；就绪探针则可以让它暂时退出流量池。具体策略要结合运行平台，不能把同一个 `/health` 端点当成万能监控系统。

业务指标也要选少而有用的信号：请求失败率、响应耗时分布、数据库连接和查询错误、文件清理失败、刷新失败、队列积压（若有）。一个指标必须有清晰口径；如果 Node 记录原生 SQLite 调用而 Go 记录 GORM 等待，不能直接把两边毫秒数当作可比指标。

## 五、超时和优雅关闭让失败有边界

网络调用如果没有超时，慢依赖可能一直占住请求和连接。HTTP 服务还要限制读请求头、请求体和空闲连接的时间；数据库连接池设定上限；外部微信或存储请求设置合理截止时间。超时不是“强行让一切更快”，而是让等待时间有上界，让系统能释放资源并明确返回失败。

关闭服务时，应停止接受新请求，给正在处理的请求一个有限完成窗口，然后关闭数据库和其他资源。如果进程被杀时数据库连接仍在执行写入，事务通常会由数据库清理，但后台任务、文件写入和外部调用还要分别设计退出行为。优雅关闭也需要被演练，而不只是加一个信号处理函数。

## 六、运行边界要写进交付结论

本地跑通、容器文件存在、镜像可以构建、目标云环境部署成功，是四个不同的状态。M6 实际交付完成了本机 PostgreSQL 服务、三数据库验证、原生构建和 Docker 镜像 manifest 检查；完整 Linux 容器构建运行与生产切换仍留待部署验收。把这几种状态混写成“已部署”会让读者误以为有生产证据。

发布说明应列清楚：在哪个环境验证，哪些依赖是真实服务，哪些使用替身，哪些配置没有真实账号，是否连接生产数据，是否完成备份和回退演练。诚实的边界说明不是削弱成果，而是让下一位维护者知道还需要做什么。

## 小结：服务的运行状态也属于产品质量

启动时验证配置，避免错误延迟到用户请求；保护秘密，记录可关联、可检索的脱敏日志；用健康与就绪信号表达服务状态；为网络、数据库和关闭流程设置边界。最后清楚记录验证环境，区分“准备好部署”和“已经在目标环境运行”。这些做法规模不大，却能显著降低排障和交接成本。
