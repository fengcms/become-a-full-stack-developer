# 成为全栈·产品篇·本系列怎么读：主线、支线与学习路径

**本文目标**：M0 八篇到这里收尾。这篇给你一张阅读地图——两套编号（主线 M0–M8 / 支线 B）怎么排、两类读者（有前端基础 / 零基础）分别怎么走、以及面对 130 篇的规模该怎么不慌。读完后，你就知道从哪一页开始翻了。

**前置知识**：本篇是 M0 收官，建议 M0-01 ~ M0-06 已读。它把前面所有内容收束成一条可执行路径。

## 一、两套编号：主线与支线

整套专栏的篇目编号分两类，看懂这个就不会迷路：

| 前缀 | 含义 | 角色 |
|---|---|---|
| `M0` | 开篇与规划（地基） | 世界观 + 契约，写代码前发完 |
| `M1` | Node 后端（API 首实现） | 价值密度最高的一段 |
| `M2` | React / Vite 管理后台 | 消费契约的第一个前端 |
| `M3` | Next.js 网站前台（含会员中心） | 读者访问的网站 |
| `M4` / `M5` | Flutter App / Taro 小程序 | 移动端，可延后 |
| `M6` / `M7` | Go 后端重写 / Vue3 后台重写 | 同契约重写，可延后 |
| `M8` | 收官 | 复盘与能力地图打勾 |
| `B` | 支线 · 基础补充 | 面向零基础，按需引用 |

编号一经确定不再变动，因为它要和 git tag、代码仓库、文章链接**三方绑定**（这正是 [git tag、仓库组织与 CSDN 发布流程](https://fungleo.blog.csdn.net/article/details/164166250) 工程公约的来由）。一个 `M` 系列只讲一件实现——M1–M7 是具体端，M0/M8 是特殊段落（产出规划文档与总结，不对应独立代码库）。

为什么要搞两套编号，而不是把所有文章混着排？因为主线读者和支线读者是两种人。主线读者有前端底子，不该被「SQL 是什么」这种基础拖慢；零基础读者如果一头扎进主线，会在 M1 后端当场卡死。分开编号，等于给两类人各发了一张地图——你只看自己那张，不迷路。

## 二、两类读者，两条路

**第一类：有 1–5 年前端经验，会调接口、想转全栈。**
你就是本系列的主目标读者。主线（M0–M8）就是为你设计的成长路径，支线 B 按需引用即可——比如某篇提到 SQL 你忘了，去翻对应的 B 篇补一下。

**第二类：零基础或基础薄弱。**
支线 B 是你的地基：命令行、Git 进阶、SQL 入门、TypeScript、Web 安全基础、服务端心智模型。这几样不补，主线一开工你就会卡。

这里有个硬约束（R15 前置必发）：`B-02` 命令行、`B-03` Git 进阶、`B-05` SQL 入门、`B-07` TypeScript、`B-11` Web 安全基础、`B-15` 服务端心智模型，被 P0 主线篇直接依赖，**必须在 M1-01 开工前或同期发布**。其余支线自由排期、允许滞后。

给第一类读者的提醒：别因为「全栈」二字就焦虑补支线。主线里凡是依赖支线知识的，我都会标注「参见 B-xx」，你遇到不会的再去翻，不要从头补起。给第二类读者的提醒：支线 B 不是放水，是地基——它薄但硬，跳过任何一个，主线都会在某处绊你。

## 三、主线怎么读：顺序即能力阶梯

主线不是一个大杂烩，顺序本身就是能力阶梯：

1. **M0 地基**：世界观（为什么走全栈）→ 能力地图（目的地）→ 七端全貌 → 技术选型 → 领域建模 → 契约先行 → 工程公约。这一步不发完，不写第一行代码。
2. **M1 Node 后端**：从零搭后端、实现契约。这是你作为前端最缺的一段，价值密度最高，也最熬人。
3. **M2 React 后台 + M3 Next.js 前台**：消费同一套契约，看前端怎么对接你刚写好的 API；M3 还能在框架内自己写一部分后端。
4. **M4–M7（可延后）**：Flutter / Taro / Go 重写 / Vue 重写。加分项，有余力再补。
5. **M8 收官**：回看 [全栈能力地图](https://blog.csdn.net/fungleo/article/details/164167281) 那张能力地图，逐格自评打勾。

把这条阶梯画出来：

![阅读阶梯图](https://i-blog.csdnimg.cn/direct/96488a82e97e4c208990b357e5557266.png)

走完 M0，你拿到的是「世界观 + 一张可执行的地图」；走完 M1，你拿到的是「一个能跑的后端 + 看穿接口背后那一层的能力」；走完 M2/M3，你拿到的是「前后端自己一个人打通的完整体验」。每一阶都有可握在手里东西，不是虚无的「学了很多」。

记住「波次串行、一篇成文即停」：每个 M 结束都有可发布的文章，不追求一次写透。这也是为什么这套能坚持得下去。

## 四、面对 130 篇，怎么不慌

全量 130 篇是个跨年度的承诺（周更 2 篇约 15 个月）。给个实在的建议：

- **先跑通骨架，再回补细节**。只做 P0 主线骨架约 25 周（半年），P1/P2 视节奏动态插入。
- **M4–M7 可延后**：系列在 M3 结束就是完整可交付的产品，不算烂尾。别被「必须学完七个端」绑架。
- **宁可先发完骨架再回补，也不要第一波就把所有细节写透然后断更。** 持续产出比一次性完美重要。

如果你时间紧，只想要「能独立做个全栈项目」这一件事：M0 全读 + M1 全读 + M2/M3 中挑一个读完，就够你上线一个真实产品了。M4–M7 是让你「见多识广」的加分项，不是门槛。

写到这里，预感你会问三个问题，提前答了：

**Q：我零基础，主线 M1 会不会直接劝退？**
不会，但前提是你先发完支线 B 里那 6 篇被 P0 依赖的（命令行、Git、SQL、TS、Web 安全、服务端心智）。它们薄但硬，补完再去 M1，你会发现后端不过如此。

**Q：周更 2 篇我追不上怎么办？**
不用追。这是我的产出节奏，不是你的学习节奏。你按自己速度读，文章不会跑。甚至建议你「先读 M0+M1+M2/M3 其中一个」，就够独立做项目了。

**Q：M4–M7 不学是不是白买？**
不是。M1–M3 已经是一个完整产品（后端+后台+网站）。M4–M7 是让你「见多识广」——看同一套契约被不同技术实现，加深抽象能力，不是门槛。

**Q：文章和代码对不上怎么办？**
先 `git checkout` 对应 tag，再看文章。如果还不一致，那是我的 bug，去评论区拍我。公约的存在，就是为了让「对不上」能被精确定位，而不是互相猜。

## 五、回到起点

你在 [为什么前端工程师要走向全栈](https://blog.csdn.net/fungleo/article/details/164119914) 结尾被我劝去读了 [全栈能力地图](https://blog.csdn.net/fungleo/article/details/164167281) 的能力地图——那时你看到的是一张目的地清单。现在八篇走完，你应该清楚这条路怎么走了：从「调接口的人」，沿着 M1 后端、M2/M3 前端、一路到 M8 复盘，变成「设计系统的人」。

M8-01 收官时，请回到 [全栈能力地图](https://blog.csdn.net/fungleo/article/details/164167281) 那张自评表，把右边一列填上。如果七格都接近 5，你就已经走完这一程了。

最后送你三句话，记住它们就不慌：第一，主线是给你这种有前端底子的人设计的，别被「零基础」的支线吓退，那是另一条路的人的起点；第二，文章不会跑，你按自己的节奏读，周更只是我的产出频率，不是你的考核；第三，M1–M3 已经是完整产品，M4–M7 是加分不是门槛，不学不会白买。把这三句贴在你显示器边上，这套专栏就是你随时可翻开的工具书，而不是又一座要一口气爬完的山。你爬不爬山，山都在那；但先拿走能用的那一块，才是真的学会了——而这，恰恰是全栈思维的第一课：先看清楚手里有什么，再决定下一步。

路已经画好，你只管迈第一步——M0-01 就在前面等你。

别想太远，先把这一篇关掉，去读 M0-01——那是你和全栈故事的开始。

八篇读下来，你已经是半个产品设计者了——因为你看见的不只是代码，而是整个系统。

## 小结

- 编号分主线（M0–M8）与支线（B），一经确定三方绑定（tag / 代码 / 链接），不再变动。
- 两类读者：有前端基础走主线、零基础先补支线 B；B 中 6 篇被 P0 依赖的必须前置必发（R15）。
- 主线顺序即能力阶梯：M0 地基 → M1 后端（最值钱）→ M2/M3 前端 → M4–M7 可延后 → M8 复盘。
- 面对 130 篇：先骨架后细节、M4–M7 可延后、持续产出优先于一次完美。
- 回到 [全栈能力地图](https://blog.csdn.net/fungleo/article/details/164167281) 地图：出发前看目的地，M8 收官时打勾验收。
