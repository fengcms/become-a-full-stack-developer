# 成为全栈·基础补充·数据库索引：为什么加了索引还是慢

> 索引让数据库更快找到一部分数据，但每个索引都要占空间、维护写入，还受查询形状和数据分布影响。索引不是给字段贴上的“加速标签”。

## 前言：一个列表接口为什么突然变慢

文章列表最初只有几十条记录，直接扫描全表也很快。随着文章、评论、点赞和阅读记录增加，查询可能要检查更多行；若再按作者筛选、按时间排序和分页，数据库需要做的工作会变得难以预测。索引能帮助它缩小查找范围，但是否有效要看实际查询和执行计划。

## 一、索引是什么

可以把索引想成书末的索引表：不必从第一页读到最后，先根据关键词找到大致位置。数据库的 B-tree 索引维护键值的有序结构，适合相等、范围和排序场景。哈希索引、全文索引等则服务于不同查询，具体能力依数据库而异。

没有合适索引时，数据库可能扫描表中的大量行，再筛选、排序；有索引时，它可以先找到符合条件的键，再回表取其他列。若筛选命中大多数数据，扫描全表可能反而更便宜，优化器会根据统计信息选择计划。所以“存在索引”不等于“查询一定使用索引”。

## 二、索引要从查询开始设计

先记录实际 SQL：

```sql
SELECT id, title, published_at
FROM articles
WHERE status = 'published'
  AND category_id = ?
ORDER BY published_at DESC, id DESC
LIMIT 20;
```

再问：每次请求会过滤哪些列？结果通常占总表多少？是否需要排序？是否经常走另一种筛选？索引应该服务真实高频查询，而不是因为某列“看起来重要”就单独建立。

复合索引 `(status, category_id, published_at)` 与三个单列索引不是同一件事。B-tree 复合索引通常按最左列开始组织，因此只按 `category_id` 查询时，前面的 `status` 可能让该索引无法按预期发挥作用。列顺序要结合常用过滤、基数、排序和数据库优化器行为，最后用执行计划与实测确认。

## 三、为什么加了索引仍然慢

### 1. 查询没有匹配索引的结构

对索引列做函数处理、在前面加通配符搜索、隐式类型转换，可能使普通 B-tree 不适用。例如 `LIKE '%keyword%'` 通常不能像 `LIKE 'prefix%'` 那样利用常规前缀索引。需要全文检索、专门 trigram 索引或其他策略时，要按数据库能力单独设计。

### 2. 过滤条件区分度太低

若某列只有 true/false 两种值，且大部分记录都为 true，单独索引该列可能无法减少多少读取。索引的价值取决于数据分布，不能只看字段类型。

### 3. 排序与分页仍需大量工作

查询筛选了很多行后再排序，或者 offset 很大，数据库仍可能处理大量记录。稳定排序能保证结果顺序，但深分页可能需要游标分页或调整产品查询。索引不能替代良好的分页策略。

### 4. 返回数据本身很大

`SELECT *` 读取正文、JSON 和大文本，即使索引很快定位到 20 行，传输和序列化仍可能成为瓶颈。只选择页面需要的列，减少 N+1 查询和大型关联，往往比新增索引更有效。

### 5. 索引带来的写入与维护成本

插入、删除、更新索引列时，数据库还要维护相关索引。索引越多，写入和存储成本越高；低频查询的索引可能只有维护成本，没有实际收益。

## 四、使用 EXPLAIN 看执行计划

数据库通常提供 `EXPLAIN` 或类似命令，展示优化器打算如何访问表。具体语法和输出字段因 PostgreSQL、MySQL、SQLite 等不同。关注：是否全表扫描；预计或实际扫描多少行；使用了哪个索引；是否需要额外排序；关联表的顺序和循环次数。

`EXPLAIN ANALYZE` 会实际执行查询，可能对昂贵语句产生负载；在生产环境使用前要理解影响。估算行数与真实数据偏差很大时，统计信息可能过期；优化器选错索引也可能是数据分布或条件表达的问题。

一套可靠流程是：

1. 先捕获实际慢查询和真实参数范围。
2. 查看执行计划和数据量，确认成本花在哪里。
3. 一次只改变一个条件、索引或查询写法。
4. 用代表性数据比较延迟、扫描行数和写入代价。
5. 再观察索引是否被其他查询使用，删除无收益索引前先评估风险。

## 五、跨数据库不能照抄索引结论

不同数据库的索引类型、DDL、排序规则、查询计划和在线建索引能力不同。某个 PostgreSQL 索引写法不一定能在 MySQL 或 SQLite 中直接使用；相同复合索引在不同数据分布下也可能有不同效果。

多数据库项目应统一业务查询语义，再为各数据库验证迁移和执行计划。M6 将 PostgreSQL 作为主数据库，同时通过真实 MySQL 和 SQLite 测试验证业务；功能通过不代表性能计划相同。性能对比还必须固定数据、请求、缓存和计时口径，见 [M6 性能实验]({{LINK:M6-07}})。

## 六、索引设计的一个例子

假设网站常见查询有两种：公开文章按发布时间倒序浏览；管理后台按状态和更新时间筛选。不要急着建一个包打天下的超宽索引。先分别记录查询频率、过滤列、排序和选中字段，然后在真实数据上测试几个候选索引：

```sql
-- 仅为示意，实际索引应由目标数据库和查询计划验证
CREATE INDEX idx_articles_status_published
ON articles (status, published_at, id);
```

索引列顺序应与具体过滤、排序和数据库规则匹配。若查询只取很少字段，某些数据库可以使用覆盖索引减少回表，但额外包含列也增加空间。最终判断依据是执行计划和代表性负载，而非 SQL 看起来更“专业”。

## 小结：索引优化是测量过程

从真实慢查询出发，判断扫描、排序、关联、回表还是数据传输最贵；再结合数据分布设计索引，并检查执行计划。索引会提高一些读取路径，也增加写入和维护成本。加完索引仍慢，先确认查询是否使用它，以及瓶颈是否根本不在索引。
