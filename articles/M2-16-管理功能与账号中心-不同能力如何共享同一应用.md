# 成为全栈·React 管理后台篇·管理功能与账号中心：不同能力如何共享同一应用

> 同一个人既是内容管理者，也是一个需要修改头像、密码和查看通知的普通账号。共享同一 SPA 没有问题，但管理能力与个人能力必须分开建模。

## 前言

后台做完文章、评论和用户管理后，很容易把个人资料页也当成“管理员设置”的一部分。结果是改头像也要求 admin 权限，或者普通会员登录后进入后台，却只能面对一整排 403 页面。

当前项目把 editor/admin 的管理工作与 `/me/*` 个人能力放在同一应用中，但没有把它们混成同一种权限。路由壳、二级导航、数据缓存和操作文案都围绕“我在管理系统，还是管理自己”做区分。

## 先说明当前路由的真实边界

个人中心路由虽然额外包了一层 `RequireAuth`，但它声明在 `RequireConsole → AdminLayout` 的子路由中。因此普通 member 仍会在外层被送到 `/no-access`，当前实际访问者只有 editor/admin。

```text
RequireAuth
  → RequireConsole
    → AdminLayout
      → /articles、/comments 等管理能力
      → /profile/* 个人能力
```

代码注释里“member 即可访问”只描述 `/me/*` 接口最低角色，不能覆盖真实嵌套结构。文章和规划以运行时结构为准。

## 管理能力和个人能力的判据不同

文章管理需要 `canManageArticles`，用户管理需要 `canManageUsers`；个人资料、改密码、通知、点赞和收藏只要求当前会话已认证。admin 修改某个用户资料与 admin 修改自己资料，也应该调用不同端点。

管理用户走 `/users/{id}`，表达管理员对他人账号的操作；个人资料走 `/me/profile`，表达当前用户更新自己。即使字段相似，两条命令的审计、校验与权限都不同。

| 页面 | 数据语义 | 当前入口 |
| --- | --- | --- |
| 用户管理 | 管理其他账号 | admin 能力 |
| 个人资料 | 修改当前账号 | 已登录的后台使用者 |
| 修改密码 | 验证旧密码后修改本人密码 | 已登录的后台使用者 |
| 通知 | 当前账号的消息与未读数 | 已登录的后台使用者 |
| 点赞、收藏 | 当前账号的内容关系 | 已登录的后台使用者 |

## ProfileLayout 提供局部导航

后台主侧栏承载管理模块，个人中心再使用二级导航组织资料、安全、通知、点赞与收藏。这样不会把大量个人入口铺满全局菜单，也让 `/profile/*` 保持稳定层级。

布局只负责导航与 Outlet，不获取每个子页数据。资料页、通知页各自通过 Query 管理远端状态，互相失败时不会拖垮整个个人中心。

如果未来希望 member 也使用账号中心，应把 `/profile` 移到 `RequireConsole` 外、仍留在 `RequireAuth` 内，并给它一个不含管理侧栏的账号布局。这是清晰的路由重构，而不是在 `RequireConsole` 里到处增加例外。

## 资料更新要同步会话快照

个人资料 Query 是远端事实，认证 store 里的 user 则供头像、菜单和守卫同步读取。更新接口成功后，两处都接受同一个服务器返回值：

```ts
onSuccess: (user) => {
  useAuthStore.getState().setUser(user)
  queryClient.setQueryData(qk.me.profile, user)
  toast.success('资料已更新')
}
```

只更新 Query 会让表单显示新昵称，顶栏仍是旧昵称；只更新 store 则重新进入资料页又看到旧缓存。这里不是让两份数据各自修改，而是同步更新两个用途不同的投影。

头像上传和资料保存共享 UploadScope。上传未完成时不能先提交旧 URL；成功后以服务端 user 重建表单基线，邮箱冲突则保留输入并提示 409。

## 修改密码不能沿用普通资料保存

改密码需要旧密码、新密码和确认值，成功后其它设备会退出。表单成功即清空敏感输入，不把密码放进 Query、Zustand 或 localStorage。

前端可以校验两次新密码一致与最小长度，但旧密码是否正确只能由后端判断。错误提示应说明可修正原因，又不能回显任何凭据。

密码改变后是否让当前设备退出，取决于后端会话策略。当前提示说明其它设备退出，前端不自行猜测并清除本会话。

## 通知、点赞和收藏不是“后台数据”

它们都属于当前账号。通知列表与未读数使用独立 query key，标记已读后同时失效相关缓存；收藏切换后失效 `['me', 'favorites']`。这些关系不会因为使用者是 admin 就变成管理动作。

文章预览同样值得放在后台主壳：编辑者需要查看未发布内容，但预览只读，不应借机暴露编辑或状态操作。只读页面与编辑页面分开，能减少误触，也让分享内部预览地址时语义明确。

## 个人列表仍要遵守各自契约

“我的点赞”当前返回裸数组，“我的收藏”则返回分页结构。它们看起来都是文章列表，却不能为了复用组件就假装响应完全相同。likes query 可以直接渲染数组；favorites query 需要 page、pageSize 与 pagination。

这类差异应该在 API 和 hook 层被吸收，页面只消费明确类型。强行把裸数组包成本地伪分页，会让总数、最后一页和服务端筛选都变成前端猜测；反过来为了统一而丢掉收藏分页信息，也会让数据增长后无法导航。

收藏的添加与取消是幂等动作，成功后失效收藏前缀。点赞和通知同理，要根据实际接口返回决定是直接写缓存还是重新获取，不能因为它们同处“个人中心”就共用一个全局刷新。

## 二级导航也要表达未读与当前路径

个人中心导航不只是五个链接。当前路径要有明确选中态，键盘焦点与移动端横向空间也要可用。通知若展示未读数，这个数字来自独立查询；标记已读后必须同时更新列表与角标。

角标失败不应阻止用户进入通知页。它是一项辅助信息，可以显示占位或隐藏；通知正文加载失败则需要局部错误和重试。把两者绑成一个 Promise，会因为一个小红点失败而让整个入口不可用。

## 账号数据的错误后果各不相同

邮箱重复是可修正的 409，应保留表单；旧密码错误同样允许重新输入；账号被禁用则是会话无法继续，必须清空状态并返回登录页。不能把 `/me/*` 的所有错误统一显示成“保存失败”。

个人资料还可能包含隐私数据。后台顶栏只需要昵称和头像，就不应把邮箱等完整 profile 到处传递。认证 store 越小，误用和无关重渲染越少；详细资料留在有访问需求的 Query 缓存和页面中。

## 从同一应用拆分出去的判断标准

当 member 账号中心的访问量、导航结构和部署节奏开始独立，继续与管理后台共用 bundle 可能不再划算。届时可以拆成读者端账号中心，但 API、类型和个人能力语义仍可复用。

是否拆应用取决于使用人群、发布边界与性能，而不是页面路径数量。当前 editor/admin 高频在管理工作与个人通知之间切换，共用 SPA 能减少登录切换，仍是合理选择。

## 小结

共享 SPA 的关键不是把所有页面套进一个角色，而是区分管理资源和管理自己。当前应用让 editor/admin 在后台主壳中使用 `/me/*` 个人能力；普通 member 尚不能进入这套壳，未来需要时应调整路由层级。

各位看官，权限设计时请把“我是谁”“我能管理什么”“我能修改自己的什么”分开回答。页面路径和接口语义自然会清楚很多。
