# 成为全栈·Vue 管理后台篇·登录页从表单变成产品入口

> 后台登录页既要让授权成员快速进入工作台，也要解释这是一个什么系统、哪些账号可以使用。视觉升级可以改变信息层次和品牌呈现，但登录 API、角色规则和认证安全边界仍然必须保持稳定。

> 本文代码快照：Vue 后台提交 `d3ee41a`。主要参考 `manage-frontend-vue/src/pages/login/LoginPage.vue`、`src/api/site.ts`、`src/api/auth.ts` 和登录后角色路由。

## 前言：登录表单是产品入口，不是孤立页面

后台登录页常常只有用户名、密码和按钮。功能上可以登录，但用户不知道品牌、系统用途、谁有访问权限，也看不到移动窄屏如何使用。项目重写登录页时把它设计成桌面双栏：品牌介绍和产品能力在一侧，登录表单在另一侧；小屏则收敛成单列表单，避免双栏压缩到不可读。

视觉上可以加入站点 Logo、名称、描述和版权信息，但它仍是认证入口。表单请求必须继续使用现有账号密码契约，成功后按照用户角色跳转，失败时以友好错误反馈。不能为了做漂亮登录页而增加未规划的第三方登录或修改后端契约。

## 品牌信息来自公开站点设置

Vue 登录页在挂载后调用公开站点设置接口，读取 siteName、logoUrl、siteDescription 和 copyright：

```ts
onMounted(async () => {
  try {
    site.value = await getPublicSiteSettings()
  } catch {
    // 品牌配置不是登录前置条件。
  }
})
```

失败时保留本地默认名称和介绍，品牌接口不会阻止用户登录。这是重要的依赖原则：站点描述只是品牌增强，不是 authentication 的前置条件。如果它暂时不可用，表单仍应可交互。

站点 Logo 为空时页面显示名称首字作为标识；有 Logo 时提供 alt 文本。桌面与移动版权分别布局，移动版在表单卡片之后显示，确保窄屏内容顺序合理。

## 双栏信息结构和小屏降级

品牌侧包括系统名称、内容运营工作台提示、后台能力介绍和版权；表单侧包括欢迎语、登录标题、适用账号说明、用户名与密码控件、登录按钮和访问授权提示。布局用 CSS media query 在宽屏双栏与窄屏单列之间切换。

设计双栏时，品牌文案应解释系统提供的工作能力，而不是占据大面积的营销空话。表单卡片要保持足够输入宽度，窄屏不能依赖悬浮背景图遮挡控件。还要保证键盘焦点顺序、输入 autocomplete 属性、可见 label、错误消息和按钮 disabled/loading 状态都能被用户理解。

暗色模式由全局主题系统提供。登录页引用 CSS 令牌和 Naive UI 主题，不应维护第三套独立配色；若使用图片 Logo，需检查深色背景下的可读性。

## 表单交互仍按认证契约执行

用户名和密码是本地 ref。提交前检查用户名去空白后非空、密码非空；请求时调用 `login({ username, password })`。按钮显示 loading，避免重复提交；接口错误通过 `ApiError` 映射后的 message 呈现；最终在 finally 恢复按钮状态。

成功后读取 auth result 中的 user.role：member 被引导到个人中心/无后台访问页，editor/admin 则进入保存的目标路由或角色默认首页。用户若原本试图访问某个受保护 URL，登录后回到该路径；目标路由再次执行守卫，未授权仍会被挡住。

开发环境可以通过 `VITE_DEV_LOGIN_USERNAME` 和 `VITE_DEV_LOGIN_PASSWORD` 预填本地测试账号，但只在 `import.meta.env.DEV` 分支读取；生产构建不应泄露开发账号配置。发布和截图前也要避免把真实凭证填在可见输入框里。

## 错误反馈：业务错误可解释，技术细节不要泄漏

登录失败可能是用户名密码错误、账号停用、网络问题或服务端异常。统一请求层先把错误转成可读 `ApiError`，页面显示它的 message；未知错误使用通用“登录失败，请稍后重试”。不要展示堆栈、敏感请求头或完整 token，也不要把所有失败都伪装成“密码错”。

登录接口的认证错误特殊处理很重要：登录请求本身不应该因无 access token 就触发自动 refresh，也不应该在失败时先清掉另一个页面已有认证状态。代码通过 `skipAuth`、`skipRefresh` 和 `skipAuthRedirect` 控制这条请求路径。

账号停用可能在 refresh 或后续访问时被后端发现；登录页应配合全局会话错误处理显示正确原因，不能只靠登录表单本地判断 status。

## 登录页不能自己决定是否有权限

页面上的“使用编辑或管理员账号登录”提示只是帮助用户理解。真实角色来自后端认证响应，登录成功后前端按 role 做导航体验；后端每个 API 仍检查权限。即使用户直接打开 `/users`，router guard 会拒绝；即使他绕过页面调用 `/users`，后端还要拒绝。

视觉升级不能改变认证契约的参数、响应、刷新 cookie 处理或错误码语义。若未来支持忘记密码、多因素认证或 OAuth，需要作为独立产品和契约规划，不能在登录页面上先放一个无效链接。

## 验收清单

- 桌面视口双栏内容完整，窄屏变为可用单列，没有水平滚动。
- 站点 Logo/名称/描述有配置时呈现；接口失败或缺字段时默认内容仍正常。
- 表单可用键盘提交，autocomplete 分别为 username/current-password。
- 空字段及时提示；请求期间按钮 loading 并阻止重复点击。
- 错误提示可读，不泄漏技术信息；账号停用与普通登录失败区分处理。
- member、editor、admin 登录后分别落到合理区域；被保护的原始回跳目标再次经守卫验证。
- 明暗主题都检查品牌、表单、错误态和输入框对比度。

代码可以证明表单和路由逻辑，但线上认证、Cookie、跨域、账号状态和品牌接口还需要真实部署环境验收。不要把本地开发账号预填作为线上登录能力。

## 小结：视觉信息服务于清楚、安全的登录

登录页通过品牌信息和响应式双栏建立工作台入口感，但站点信息接口失败不阻断登录；表单继续遵守账号密码契约、统一错误处理和角色分流；桌面与移动布局、键盘和主题状态也要纳入验收。界面可升级，认证安全边界保持清晰。
