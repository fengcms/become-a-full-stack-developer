# 成为全栈·基础补充·HTTP 协议：前端天天用却说不清的那些事

> 浏览器里的一次“请求失败”，可能是 DNS、TCP/TLS、HTTP 状态码、跨域策略或业务响应中的任何一环。把这些层次分开，排查问题就不必靠猜。

## 前言：点一下按钮，网络上发生了什么

你点击登录，页面发出请求，服务器验证账号，再把结果返回。前端通常只接触 `fetch` 或一个请求库，但真正的往返由一组协议组成：浏览器先找到主机地址，建立连接，在 HTTPS 下完成 TLS 握手，然后发送 HTTP 请求；服务器解析请求、处理业务并返回状态行、响应头和响应体；浏览器再根据状态、内容类型、Cookie 策略和跨域规则决定如何交给页面代码。

理解 HTTP 不要求先成为网络工程师。先能读懂一次请求的结构，知道状态码和业务码不是同一层，明白 Cookie、缓存、跨域和代理分别在何处发挥作用，就已经能解决许多前端常见问题。

## 一、HTTP 请求由哪些部分组成

一个 HTTP 请求可以简化成：

```http
POST /api/v1/auth/login HTTP/1.1
Host: example.test
Content-Type: application/json
Accept: application/json

{"username":"reader","password":"..."}
```

第一行包含方法、路径和协议版本；请求头描述内容类型、期望格式、认证信息和缓存条件；请求体承载 JSON、表单或文件内容。响应也由状态行、响应头和响应体组成：

```http
HTTP/1.1 200 OK
Content-Type: application/json
Set-Cookie: refresh=...; HttpOnly; Secure; SameSite=None

{"code":0,"message":"ok","data":{"accessToken":"..."}}
```

浏览器开发者工具的 Network 面板就是把这些信息可视化。先检查最终 URL、方法、状态码、请求头、响应头和响应体，再决定问题出在浏览器、网络、服务器还是业务逻辑。

## 二、方法表达意图，安全性和幂等性是另一回事

常见方法包括：`GET` 获取表示，`POST` 提交处理或创建，`PUT` 更新资源，`PATCH` 局部更新，`DELETE` 删除。方法是语义约定，不是服务端自动实现的安全屏障。服务端仍需验证登录、角色、资源归属和请求内容。

两个容易混淆的属性是：

- **安全方法**：按协议语义不应改变用户可见资源状态，`GET` 是典型例子。日志、访问计数等内部副作用仍可能存在，因此不要把可变业务操作塞进 GET。
- **幂等方法**：相同请求重复执行，预期最终状态相同。`PUT` 和 `DELETE` 通常按幂等设计；`POST` 通常不是，但业务也可以做成幂等。

方法名字无法保证实现符合约定。一个错误的 `GET /delete?id=1` 依然会删除数据；一个 `POST /me/read` 也可以被设计成重复调用只更新同一个阅读进度。判断重试是否安全，最终要看业务语义。相关的并发和幂等问题可读 [B-20]({{LINK:B-20}})。

## 三、状态码和业务码处在不同层

HTTP 状态码回答传输和请求处理的大致结果：200 成功、201 创建、204 无响应体成功、400 请求错误、401 未认证、403 禁止访问、404 未找到、409 状态冲突、429 过多请求、500 服务异常。具体 API 是否采用这些状态，要看它的契约，不能仅凭习惯推断。

一些 API 在 HTTP 200 的 JSON 信封里还有业务 `code`：

```json
{"code":0,"message":"ok","data":{}}
```

这时 HTTP 200 表示 HTTP 层正常返回，业务码再描述应用结果。客户端要按服务实际约定解析两层，不能把“状态码是 200”直接当成“用户操作一定成功”。反过来，401 与 403 也有不同意义：401 表示缺少有效身份，403 表示身份已知但没有权限。把两者混为一谈，会造成错误的登录跳转或权限提示。

## 四、头部、Cookie 和内容类型

`Content-Type` 表示请求体实际采用的格式；`Accept` 表示客户端希望接收的格式。JSON 请求通常使用 `application/json`。文件上传常用 `multipart/form-data`，浏览器会自动生成 boundary；不要手工把 multipart 的 `Content-Type` 写死，否则 boundary 可能丢失。

Cookie 由服务器通过 `Set-Cookie` 控制，浏览器是否保存和发送还受 Domain、Path、过期时间、Secure、HttpOnly、SameSite 影响。`HttpOnly` 能阻止 JavaScript 直接读取 Cookie，但不能防止站点脚本以用户身份发请求；`Secure` 约束 HTTPS 传输；SameSite 则影响跨站请求中是否携带 Cookie。认证方案需要把 Cookie 属性、刷新流程与跨站来源一起设计，详见 [B-12]({{LINK:B-12}})。

## 五、HTTPS 和 CORS 不是一回事

HTTPS 为客户端与服务器之间的连接提供加密和服务器身份验证；CORS 是浏览器对跨源脚本读取响应的限制机制。CORS 不是服务器防火墙，也不会阻止 curl、移动 App 或其他服务器发请求。一个请求可能已经到达服务器并执行，只是浏览器不把响应交给页面脚本。

跨源请求的预检通常是浏览器先发 `OPTIONS`，询问目标是否允许某种方法和请求头。服务端要正确返回允许的 Origin、方法、头部及凭据策略。带 Cookie 的跨源请求不能简单使用任意 `*` 作为允许来源。排查时应看 Network 面板中有没有 OPTIONS、实际请求是否发送、响应头是否匹配；不要只看到“CORS error”就认定后端没有处理。

## 六、缓存与代理会改变你看到的路径

HTTP 缓存可能来自浏览器、CDN 或反向代理。`Cache-Control`、`ETag`、`Last-Modified` 等头部会影响响应能否复用和如何重新验证。代理还可能改写 Host、转发客户端 IP、终止 TLS 或把同一个公开域名下的 `/api` 路由到后端。

所以排查“代码改了页面没变”时，要区分构建产物、浏览器缓存、CDN 缓存和服务器缓存；排查“登录后拿不到 Cookie”时，要同时检查 HTTPS、代理转发和 Cookie 属性。缓存层级见 [B-13]({{LINK:B-13}})，代理部署见 [B-09]({{LINK:B-09}})。

## 七、一个实用的网络排查顺序

1. 确认请求最终 URL、方法和环境地址是否正确。
2. 检查请求是否真的发送；若失败在 DNS、TLS 或连接阶段，服务器日志可能完全没有记录。
3. 查看 HTTP 状态码、响应头和响应体，分开识别 HTTP 错误与业务错误。
4. 对照请求头、Cookie、Content-Type、Origin 和预检结果。
5. 检查代理、CDN 和缓存是否返回旧响应或改写了请求。
6. 用 curl 或服务端日志交叉验证浏览器行为，但注意 curl 不会执行浏览器 CORS 限制。

## 小结：先分层，再定位

HTTP 是浏览器与服务之间的应用协议。学会读取方法、路径、头部、状态码和响应体，分清 HTTP 状态与业务码、HTTPS 与 CORS、Cookie 与 JavaScript 存储，就能用证据定位问题。遇到故障不要只盯页面报错；沿着“浏览器—网络—代理—服务—业务”逐层检查。
