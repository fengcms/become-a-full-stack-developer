# 成为全栈·基础补充·HTTP 协议：前端天天用却说不清的那些事

我曾经被一个问题问住：一个文章接口返回 401，客户端该跳转登录页还是弹提示？

我说"看情况"。然后对方追问"什么情况"，我没答上来。

**而这个问题的答案完全在 HTTP 里**——是状态码、请求方法、还有几个响应头共同决定的。这篇讲那些"天天在用但说不清"的部分，以及它们在这个项目里的具体取值。

## 状态码是契约，不是建议

先看这个项目实际返回的状态码：

| 码 | 含义 | 例子 |
|---|---|---|
| 200 | 成功 | `GET /articles` |
| 201 | 创建成功 | `POST /articles` |
| 401 | 未认证 | 没带令牌 / 令牌过期 |
| 403 | 已认证但无权 | 不是文章作者 |
| 404 | 资源不存在 | 文章被删 / 资源不可见 |
| 409 | 冲突 | 用户名被占用 |
| 429 | 限流 | 30 秒内第 5 次请求 |
| 500 | 服务端错误 | 未预期的异常 |

而**关键在于 401 和 403 的区别**，因为它们决定了客户端做什么：

```ts
if (!user) throw new AppError(ErrCode.TOKEN_MISSING, 401, '未携带访问令牌');
// ...
if (ownerId === null) throw new AppError(ErrCode.NOT_FOUND, 404);
if (ownerId === user.id) return next();
throw new AppError(ErrCode.FORBIDDEN, 403); // 存在但非归属者
```

| 码 | 含义 | 客户端该做什么 |
|---|---|---|
| 401 | **你是谁？不知道** | 刷新令牌 / 跳登录 |
| 403 | **知道你是谁，但你不能做这个** | 提示无权限 / 不重试 |
| 404 | **这个东西不存在** | 提示找不到 |

**而这个区分不只是语义上的，它直接决定了客户端的行为**：

- 收到 401 → 客户端会去刷新令牌（M4-09 讲的单飞刷新），刷新成功就重放原请求
- 收到 403 → 客户端**不刷新**，因为刷新也不会让它有权
- 收到 404 → 客户端显示"内容不存在或暂不可见"

**如果服务端把 403 错发成 401，客户端会陷入"不断刷新令牌"的无意义循环里。** 而它永远无权，因为问题不在身份上。

**所以状态码发错，比状态码"不好看"严重得多**——因为它是接口和客户端之间的契约。

## 一个 404 优于 403 的判断

上面那段代码里有一处值得展开：`ownerId === null` 时返回 **404**，而不是 403。

B-12 讲过这个判断，这里说它的另一个面向——**从客户端角度看，404 和 403 会触发不同的行为**。

设想一个场景：用户点进一篇被删除的文章的文章页。

| 服务端返回 | 客户端行为 | 用户看到 |
|---|---|---|
| 404 | 触发"资源不存在"的空状态 | "文章已被删除" |
| 403 | 可能提示"无权限查看" | "你没有权限" |

**第二句对用户来说是误导的**——文章不是"你没权限看"，是"它没了"。

而这个项目的折中策略是：**公开文章区分（404/403 都可能），敏感资源统一 404。**

理由在 B-12 讲过：**因为公开文章的存在性不是秘密**（列表里能看到），而私有资源的"存在"才是要保护的信息。

**这个判断的通用形式是**：

> 返回 404 还是 403，取决于"这个资源存不存在"这件事本身是否敏感。

## 请求方法的语义差别

第二组说不清的东西是：**GET、POST、PUT、PATCH、DELETE 到底有什么区别**。

教科书上的答案（GET 安全、POST 幂等之外……）在实际工程里不够用。**更有用的判断是：这个操作重复执行会怎样？**

| 方法 | 重复执行 | 这个项目里的例子 |
|---|---|---|
| GET | 无影响 | 查文章 |
| POST 创建 | **产生多份** | 发评论、发帖 |
| PUT | 幂等（覆盖） | 改设置 |
| PATCH | 取决于实现 | 改资料 |
| DELETE | 幂等（删了就没了） | 删文章 |

而**"幂等"这个性质决定了客户端能不能重试**，这是 M4-08 讲的那个核心问题：

```ts
// 只对 GET 做一次有界等待；写请求绝不自动重放。
if (response.statusCode == 429 && method == 'GET' && ...) {
```

**而即便是 PUT/PATCH/DELETE 这些"幂等"操作，也不该盲目重试**——因为"幂等"是接口的设计性质，而客户端不知道对方是不是真的设计成了幂等。

**这个项目里唯一明确标了幂等的是契约：**

```yaml
x-idempotent: true
```

而 B-20 讲过：**这个标记在代码里并没有实现**——它是一个声明，不是保证。所以客户端不能依赖它。

**这一条值得反复强调**：契约里的"是幂等的"和实现里的"重复执行安全"，是两件事。**只有后者的测试能证明。**

## 状态码之外：那些决定行为的头

真正让 HTTP 变得难懂的不是状态码，是**响应头**。而这个项目里最重要的三个：

### Cache-Control：决定客户端缓存多久

M4-23 讲过三态缓存的完整逻辑。而它的输入之一就是这个头：

```ts
final control = response.headers.value('cache-control') ?? '';
...
if (control.contains('no-cache')) {
  fresh = Duration.zero;
  max = Duration.zero;
}
```

**而 `no-cache` 这个名字有个陷阱**：它的字面意思是"不要缓存"，但规范里的实际语义是"**可以缓存，但每次使用前必须验证**"。

真正的不缓存是 `no-store`。

**而这个项目把两者都当"不缓存"处理**——这是有意的取舍，因为这里不需要"缓存但验证"这种中间态：

```dart
if (control.contains('no-store')) ...  // 不写入缓存
```

顺带说 `Age` 头（B-13 讲过）：

```ts
age = Duration(seconds: int.tryParse(response.headers.value('age') ?? '') ?? 0);
```

**它是"响应在中间层停留了多久"**，用来让客户端知道这份数据的真实年龄。

**这个头是可选的**——而且忽略它的后果是静默的（缓存看起来更新，实际更旧）。

### Set-Cookie：四个属性各管一件事

这个项目只在一种情况下用 Cookie——**refresh token**：

```ts
// ---- Cookie 辅助（浏览器端 refreshToken 载体，HTTP 层职责）----
const COOKIE = 'refreshToken';
const COOKIE_ATTRS = 'HttpOnly; SameSite=None; Secure; Path=/';

export const setRefreshCookie = (c: Context, token: string, maxAgeSec: number): void => {
  c.header('Set-Cookie', `${COOKIE}=${token}; ${COOKIE_ATTRS}; Max-Age=${maxAgeSec}`);
};
```

**四个属性，每个都在防一类问题：**

| 属性 | 防什么 | 去掉会怎样 |
|---|---|---|
| `HttpOnly` | JS 读不到这个 Cookie | 一个 XSS 就能偷走长期凭证 |
| `Secure` | 只在 HTTPS 上传输 | **明文 HTTP 上凭证直接暴露** |
| `SameSite=None` | 允许跨站携带 | 不加这个，跨站调用会被拦 |
| `Path=/` | 只对全部路径生效 | 限定路径后某些接口拿不到 |

而这里有个值得注意的组合：**`SameSite=None` 必须配 `Secure`**——这是规范强制要求的，否则浏览器会拒绝这个 Cookie。

**而这条要求反过来证明了一件事**：`SameSite=None` 意味着**这个 Cookie 会被跨站请求携带**，也就是 CSRF 风险面重新出现了。

**所以这个项目其实不是"不用 Cookie"，而是"只在 refresh 这一个环节用 Cookie"。** B-11 讲的"CSRF 风险接近零"是个更精确的说法——access token 走 Authorization 头，不受 CSRF 影响；而 refresh 接口因为用 Cookie，**它需要额外注意**。

而它采用的是 M4-09 讲的那个办法：**refresh token 轮换**（用一次就作废），**让一个偷到的 token 只能用一次**。

**这不是"防住了 CSRF"，而是"即使 CSRF 成功，损失有限"。** 两者的区别在安全论证里很重要。

### Authorization：这个项目的主认证方式

```ts
headers: {
  if (!anonymous && accessToken != null)
    'Authorization': 'Bearer $accessToken',
}
```

**`Bearer` 这个词的作用是声明"后面是一个令牌，不是一个基本认证的用户名密码"**。

而它相比 Cookie 的关键优势是：**浏览器不会自动帮你加这个头。**

**这就是 B-11 讲的那个 CSRF 结论的技术基础**——不是"我们加了防护"，而是"浏览器不会自动带"。

顺带说 `anonymous` 那个判断：

| 场景 | 头 | 原因 |
|---|---|---|
| 公开读（未登录） | 不带 | 没有令牌 |
| 公开读（登录了） | 带 | 读多显示点赞状态 |
| 私有读 | 带 | 否则 401 |
| WebView 加载图片 | **不带** | M4-24 讲的，避免把 token 发给图片域名 |

**最后一行是安全边界**：图片域名是第三方，**把 token 发过去等于把它交出去**。

## 一个能自查的清单

HTTP 的知识点很多，但排查时用到的就这几个：

| 现象 | 先看什么 |
|---|---|
| 401 | 有没有带 `Authorization` / 有没有过期 |
| 403 | 归属判断逻辑，不是令牌问题 |
| 404 | 路径 + 方法（`GET` 写成 `POST` 会 404） |
| 429 | `Retry-After` 头有没有、`cache-control` 是什么 |
| 跨域失败 | 响应的 `Access-Control-Allow-Origin` |
| 登录态莫名丢失 | `Set-Cookie` 的 `SameSite` / `Secure` / `Domain` |
| 缓存不对 | `Cache-Control` + `Age` + `ETag` |

**而这张表里最有用的一条是最后三行**——因为它们的问题是"看起来正常但行为不对"，最难自查。

## 用 curl 自查：三个命令定边界

这一章的东西都能用三条命令验证，而这个项目的健康检查端点正好提供了最外层的探针：

```bash
# 1. DNS 层：名字解析对不对
dig api-befull.kao9.com @1.1.1.1
# 失败 → DNS 层，与你的代码无关

# 2. 传输层：服务在不在、证书对不对
curl -sS https://api-befull.kao9.com/api/v1/health | jq '.data.status'
# 连不上 → 路由或服务层；连上但报证书错 → TLS 层

# 3. 业务层：返回的是不是成功信封
curl -s https://api-befull.kao9.com/api/v1/articles | jq '.code'
# 0 → 一切正常；非 0 → 是你的代码在按契约返回错误
```

而那个健康检查端点本身只有一行：

```ts
healthRoute.get('/', () => ok({ status: 'ok' }));
```

**它故意不查数据库**——因为它的用途是"这个进程还活着吗"，而如果它查数据库，数据库一抖它就会挂，**而你分不清是进程挂了还是数据库挂了。**

**分层的诊断端点应该只回答自己那一层的问题。** 这和 B-15 讲的那张排查表是同一件事：**每条命令只可能在一个层失败。**


## 一条我一开始想省掉的事

那个 `SameSite=None` 我一开始写的是 `SameSite=Lax`。

**它工作得好好的**——因为我自己测试时用的是同一站点（`localhost:3000`），而同站请求不受 SameSite 限制。

**然后部署到线上之后管理后台登不上了。**

原因很简单：**管理后台（`manage-befull.kao9.com`）调用后端（`api-befull.kao9.com`）时是跨站请求**，而 `SameSite=Lax` 会在跨站 POST 时不带 Cookie。

**而"我测试时能用"和"跨站能用"是两个场景**——这个 bug 的隐蔽之处在于**它只在部署后出现，而部署前的所有测试都通过**。

改法就是 `SameSite=None` + `Secure`。而 `Secure` 那部分是规范强制的：**没有它，浏览器直接拒绝 `SameSite=None` 的 Cookie**，于是症状变成"改了 SameSite 之后连同站也登不上了"——**排查起来会更绕**。

**这一条对应的是 B-15 讲的"有些环节不在你写的代码里"**——SameSite 是浏览器强制的约束，你在响应里写的只是"请求"，**接受不接受是浏览器决定的**。

而它和 M4-25 讲的"不用 innerHTML"是同一类问题：**你的代码表达的是意图，执行权在别人手里。**

## 小结

HTTP 这一章，真正需要记住的不是状态码列表（那个查表就行），而是三个判断：

1. **状态码是接口和客户端之间的契约**，发错了会让客户端做错事——把 403 发成 401 会导致无限刷新令牌。
2. **404 和 403 的选择取决于"存在性是否敏感"**，公开资源可以区分（帮助用户），私有资源必须统一（防泄漏）。
3. **判断一个操作能不能重试，看"重复执行会怎样"**，而不看方法名——而契约上的 `x-idempotent` 是声明，不是保证。

而响应头那部分，最实际的三条：

| 头 | 一句话 |
|---|---|
| `Cache-Control` + `Age` | 决定缓存新鲜度，**而 `Age` 忽略了会静默出错** |
| `Set-Cookie` 四个属性 | 每个防一类问题，**而 `SameSite` 的影响要部署后才发现** |
| `Authorization` | **浏览器不会自动加，这是 CSRF 免疫的技术基础** |

其中第三条是这个专栏最有价值的一个架构决定的原理——**"用 Bearer token 而不是 Cookie"不只是风格选择，它消掉了一整类攻击面。**

代价是 M4-09 讲的那套手动 token 管理复杂度。**这个专栏在安全上的选择一贯是"消除攻击面，而不是防护攻击面"**，HTTP 的这三条正好印证了这个原则。
