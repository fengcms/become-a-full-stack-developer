# 成为全栈·Vue 管理后台篇·文章列表的筛选、批量操作和部分失败反馈

> 批量删除不是把选中的 ID 一次性塞进 `Promise.all` 就结束。筛选范围、软删除语义、部分失败、重试入口和缓存刷新都影响用户能否理解结果。本文对照 Vue 与 React 两端的文章工作台，分析相同行为目标下真实实现的差异。

> 本文代码快照：Vue 后台提交 `d3ee41a`，React 对照提交 `d72df53`。主要参考两端文章列表页、文章 API 模块、React `useBatchSelection` 与批量失败展示组件。

## 前言：选择几行之后，用户期待什么？

文章列表通常支持状态筛选、关键词搜索、分页、行选择、审核和删除。用户选择几篇稿件并点击“删除所选”时，会期待明确知道：会删掉哪些文章？是否只是当前页？如果其中两项失败，哪些成功、哪些还在？能否方便重试？列表是否会刷新？

这不是单纯的按钮交互，而是一组产品承诺。API 契约若没有批量删除端点，前端不能捏造一个 `/bulk-delete`；可以按资源逐条调用契约中的删除操作，并定义批次执行策略。与此同时，文章删除是服务端软删除语义，前端只请求删除，不直接假设数据库记录物理消失的细节。

## 筛选状态决定查询，也决定选择范围

Vue 文章页把 page、status 和 keyword 合成 query，然后交给 `listAdminArticles`。更改状态或关键字时页码复位到 1；选择状态则保存在组件内，不属于服务器数据。写操作成功后失效 `['articles']` 前缀，让列表和相关详情重新对齐。

批量选择必须有明确范围。当前列表支持跨页数据查询，但表格只显示当前页；若用户切换关键词或状态，之前选中的 ID 是否仍然有效需要明确。React 的 `useBatchSelection` 用当前查询范围的 JSON 字符串作为 scope，范围变化后清除旧选择和失败信息。Vue 当前页面使用 `selected` ref 管理 NDataTable 选择，筛选变化会重置页码，但并没有同样复杂的 scope/失败重试状态层。

这个差异值得讲出来：两端同契约和相近功能，不意味着实现成熟度完全一样。重写后应该按真实代码评估功能完整度，不能把 React 的失败保留能力写成 Vue 已经具备。

## 为什么要逐条调用 API？

Vue 版在没有批量端点的情况下，对所选 ID 分别调用 `deleteArticle`，用 `Promise.allSettled` 收集成功与失败：

```ts
const ids = selected.value.map(Number)
const results = await Promise.allSettled(
  ids.map((id) => deleteArticle(id)),
)
const failed = results.filter((result) => result.status === 'rejected').length

message[failed ? 'warning' : 'success'](
  failed ? `删除完成，${failed} 篇失败` : `已删除 ${ids.length} 篇文章`,
)
selected.value = []
await refresh()
```

`Promise.all` 遇到第一项 reject 就整体 reject，无法直接给用户一个“部分成功”的汇总；`Promise.allSettled` 等所有操作结束，再统计失败条数。批量流程仍然要考虑请求并发量和服务端限流：所选数量很大时，并发发出所有删除请求未必合适。当前界面只操作已选行，后续若扩大批次规模，应考虑有界并发或服务端批量端点。

这里的反馈是汇总级别：告知失败数量，但不列每条失败 ID，也不保留失败项的选中状态；刷新后失败行仍在列表中，用户可以重新选择处理。不能误称 Vue 版提供了逐项可重试记录。

## React 版如何保留失败项

React 项目将批量选择抽成 `useBatchSelection`：

1. 以当前查询 scope 管理选择，scope 改变清除失效选择和失败消息。
2. 对 ID 顺序执行操作，减轻服务端限流压力。
3. 捕获单项异常，记录失败 ID 与错误文案，继续处理下一项。
4. 操作完成后只保留失败 ID 的选择，调用 refresh 并展示汇总。
5. `BatchFailures` 持久显示每条失败信息，用户可以再次对保留项执行操作。

顺序执行更易控制负载，但耗时会随条数线性增加；并行执行速度更快，却可能造成请求洪峰。失败项明细提高可恢复性，但也需要设计错误信息长度和重试后的清理时机。这是具体产品取舍，不存在对所有批量任务都正确的单一方式。

两种实现如果要达到行为一致，可以统一批量策略：例如 Vue 侧也按顺序处理、保留失败项并显示明细，或明确产品接受只显示失败数量并允许用户在刷新列表后重新选择。文档应如实记录代码，而不是把改进方向写成已完成事实。

## 批量操作要映射到契约，而非突破契约

文章列表的 API 模块逐个封装 `DELETE /articles/{id}`，端点权限由契约决定（管理员/编辑或文章作者本人依资源规则）。`POST /admin/articles/{id}/approve` 是单篇审核发布。若批量审核需要逐条调用 approve，失败原因可能包括状态冲突、权限不足或资源已删除；前端要呈现失败，不能擅自把审核失败改成成功。

后端负责逐项验证角色、资源归属和合法状态迁移。前端按钮显隐减少误操作，但不能让客户端传入一组 ID 就跳过服务端授权。批量操作的每个单项请求仍要走统一请求内核，因此 token 刷新、错误信封和 requestId 处理一致。

若未来要提供原子性批量 API（全部成功或全部回滚），这属于契约和后端事务能力，需要单独规划，不是前端改成 `Promise.all` 就能得到数据库事务。

## 确认提示和软删除语义

单条删除前，Vue 页面显示包含文章标题的确认框，并说明会执行软删除。批量确认则告知所选项数量。避免静默提交危险操作，也避免把用户误导成“彻底从数据库删除”。

选择按钮应在没有选中项时禁用或不显示；操作进行中要阻止重复提交；完成后清除已处理状态、失效查询并展示结果。若产品希望支持撤销软删除，需确认 API 是否提供恢复端点；没有契约支持时不能只靠 UI 放一个撤销按钮。

## 错误信息如何既可操作又不过度暴露

用户需要知道哪些项目失败以及下一步怎么办。React 项目显示 `#id：错误` 明细，适合内部管理工具定位具体记录；对公开或更广泛用户，展示文章标题可能比数字 ID 更可理解，错误详情则需要过滤技术栈和敏感信息。request ID 可以用于支持人员排障，但不必在 UI 直接展示所有内部数据。

Vue 当前仅展示失败总数，减少实现复杂度，却增加了用户自己回到列表找失败项的成本。这个差异可作为后续优化讨论：

- 若批次很小且刷新后失败行明显可见，汇总数字可能足够。
- 若批次较大、失败原因各不相同，应保留失败 ID/标题、错误摘要和重试入口。
- 若重试可能重复触发非幂等动作，必须先确认 API 是否幂等或可安全重复。

## 测试重点：检查部分成功的真实行为

单测或组件测试可让三项操作返回：成功、失败、成功，然后确认成功数、失败数、查询失效和选择状态是否符合产品定义。还应覆盖空选择、重复点击保护、筛选切换后清除旧选择，以及操作全失败时是否仍显示合理提示。

测试不需要重写 Promise.allSettled 自身的行为，也不必只 mock “成功全部”这一条快乐路径。最有价值的案例是部分失败，因为这正是批量 UI 与单条操作最大的差异。

线上验收需要使用真实权限账号验证 editor/member/admin 的可操作范围，以及服务端的软删除结果。代码中的单测通过不等于线上写请求已经执行成功；发布记录要区分本地验证、测试环境验证和线上数据操作。

## 小结：批量是工作流，需要设计恢复路径

批量操作要从筛选范围、契约端点、并发策略、单项授权、部分失败、用户反馈和缓存刷新一起设计。Vue 版通过 `Promise.allSettled` 提供失败数量汇总并刷新列表；React 版顺序执行、保留失败项及明细。两端差异说明“同一功能目标”不代表已经完全相同的恢复体验。
