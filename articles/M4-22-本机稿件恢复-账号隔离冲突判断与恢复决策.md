# 成为全栈·Flutter App 篇·本机稿件恢复：账号隔离、冲突判断与恢复决策

上一篇讲了图片上传失败怎么恢复。这一篇讲一个更基础、也更敏感的问题：**App 崩溃之后，用户写的东西还在不在？**

编辑器每敲几个字就往本机写一份草稿。这件事听起来简单，但做对需要解决三个问题，而这三个问题的难度递增：

1. 草稿存在哪，怎么避免串号。
2. 存的内容是 JSON，**万一解析失败怎么办**。
3. 恢复草稿时，**如果服务端那份已经变了**，恢复还是不恢复。

第三个问题是真正的难点。前两个是工程细节，第三个是产品决策。

## 草稿键：三个部分各挡一类问题

M4-19 提过这个键，这里展开：

```dart
String get draftKey =>
  'draft.${Uri.parse(ref.read(sessionProvider).api.baseUrl).authority}.$owner.${id ?? 'new'}';
```

拆开看：

| 部分 | 挡什么 | 少了会怎样 |
|---|---|---|
| `baseUrl` 的 authority | 开发/线上环境串号 | 开发时写的内容出现在线上 App |
| `owner` | **不同用户串号** | **A 退出后 B 看到 A 的草稿** |
| `id ?? 'new'` | 新建和编辑同一篇的草稿混淆 | 编辑已有文章时恢复了新建的草稿 |

**`owner` 是隐私底线。**

设想家庭共用一台平板：A 登录写了半篇文章没保存就退出，B 登录进编辑器，系统提示"发现上次未保存的内容"。B 点了恢复，看到了 A 的草稿。

而 `owner` 的来源是会话里的用户 id——**未登录时 `owner` 是空字符串**，所以未登录用户的草稿不区分。但未登录时用户根本不能进编辑器（要发稿必须登录），所以这个空值场景实际不会出现。

`id ?? 'new'` 那部分值得说一句：新建文章时还没有 id，所以用 `'new'`。等第一次保存成功、服务端返回 id 之后，键就变了：

```dart
final oldKey = draftKey;
...
updatedAt = a.data.updatedAt ?? '';
...
await prefs.remove(draftKey);      // 用新键删
```

这里有个容易出错的地方：**`oldKey` 要在更新 id 之前算出来，因为那时 `draftKey` 还是 `'new'` 版本。** 而清理时要用新键（带 id）——等等，实际上这里需要仔细想：

```dart
final oldKey = draftKey;              // 保存前：...new
// 请求成功，id 被赋值
// ...
await draftWrite;                       // 等最后一次本机写入完成
await prefs.remove(draftKey);           // 此时 draftKey 已经带 id 了
```

`oldKey` 被算出来是为了处理另一种情况：如果清理时发现旧键还在（比如某次写入失败），也要清掉。

**这个顺序（M4-19 讲过）不能颠倒：先 `await draftWrite` 再 `remove`。** 否则并发写入可能在 remove 之后完成，**草稿又回来了**——用户下次进来会看到一个"幽灵草稿"，内容和服务端一样，制造一次虚假的冲突提示。

而"先清理旧键、再写入新键"这个操作顺序，和 M4-08 那个 `cache.fence()` 是同一个思想：**在状态切换的过程中，不允许旧数据回写。**

## JSON 解析失败：只清这一个键

第二个问题。用户存的草稿是 JSON：

```dart
final cached = prefs.getString(key);
if (cached == null || !context.mounted) return null;

Map<String, dynamic> recovery;
try {
  recovery = jsonMap(jsonDecode(cached));
} catch (_) {
  await prefs.remove(key);        // ← 解析失败就删掉这一个
  return null;
}
```

**为什么可能解析失败？** 三种情况：

1. App 上一个版本存的字段结构变了
2. 写入过程中 App 被杀（虽然有了串行链，但极端情况下可能有半条）
3. 存储介质损坏

现在的处理是**直接删掉这个键，然后当作没有草稿**。

**关键在于只删这一个键，不是清空整个存储。** 因为草稿是按键存的，不同文章、不同用户、不同环境各有一份。清空整个存储意味着**把所有其他草稿都删了**——那会造成真正的数据丢失。

而"当作没有草稿"这个降级也是对的：用户看到的是"编辑器里没有你的草稿"，而不是崩溃或者一个看不懂的错误页面。

**这是我在这个功能里最想强调的一个原则：单个数据的损坏，不应该连累其他数据。**

## 恢复的决策：先问用户，但要说清后果

现在说第三个问题。

发现草稿之后，要不要问用户？**必须问。** 因为用户可能不想要它——他可能已经放弃了那篇文章，或者草稿内容是半句话，恢复出来还要手动删掉。

但**问的方式有讲究**：

```dart
final accepted = await confirm(
  context,
  '恢复本机草稿',
  '发现上次未保存的内容，是否恢复？服务器稿件不会立即被修改。',
);
```

那句"服务器稿件不会立即被修改"是刻意的。

考虑用户的心理：他看到这个弹窗时，最担心的是什么？**是"点了恢复会不会把服务器上那份覆盖掉"。**

如果不说这句，他可能不敢点——因为他不信任这个操作。而这个担心是合理的：**恢复草稿确实会把编辑器内容替换成本机那份，而那份可能更旧。**

所以那句话同时传达了两件事：

1. **恢复是安全的**（不会立刻动服务器）
2. **但需要你自己决定**（因为你可能想要服务器那份）

而"要不要恢复"这个决策的正确做法是**让用户对比着看**，而不是替他选。但现在的实现是直接恢复到编辑器，用户可以自己切"预览"看内容，或者退出重新进来拿服务端版本。

**这是一个可以改进的地方**——理想做法是在弹窗里显示草稿的标题和最后修改时间，让用户有判断依据。**现在只能看到"发现上次未保存的内容"这一句话。**

## 恢复之后：冲突由保存时的那道检测来管

这里有个衔接问题：M4-19 讲过保存时会比较 `updatedAt` 来检测冲突。

**恢复草稿之后，这个检测还成立吗？**

成立，而且**草稿里专门存了做检测需要的那个字段**：

```dart
Map<String, dynamic> draft() => {
  ...
  'baseUpdatedAt': updatedAt,
};
```

草稿记下的是"**我这份内容是基于哪个服务端版本写的**"。

恢复草稿的时候，这个字段被一并恢复：

```dart
final recovery = await recoverDraft(prefs, draftKey, context);
if (recovery != null && mounted) {
  apply(recovery);      // ← 这里会把 baseUpdatedAt 一起应用回去
}
```

于是时序变成：

```text
用户写草稿（基于服务端版本 V1）
  ↓ 本机保存时记下 baseUpdatedAt = V1
  ↓
（此时服务端被别人改成了 V2）
  ↓
用户重进编辑器，恢复了草稿（编辑器现在认为基线是 V1）
  ↓
用户点保存
  ↓
M4-19 的检测：服务端是 V2 ≠ 编辑器的基线 V1
  ↓
提示冲突，不覆盖
```

**如果没有 `baseUpdatedAt` 这个字段会怎样？**

恢复草稿时，编辑器会**用服务端当前的值作为基线**（因为先加载了服务端数据，再应用草稿）。那么保存时比较的就是"V2 vs V2"，**检测通过，直接覆盖**。

而用户看到的界面里显示的是他的草稿内容。**他知道内容和服务端不一样（因为服务端是别人的版本），但 App 不会告诉他。**

**`baseUpdatedAt` 这个字段的全部作用，就是让"冲突检测"在恢复草稿之后依然有效。** 它让编辑器回到"我记得我是基于哪个版本写的"这个状态，而不是"我以为我现在看到的就是最新的"。

这是个很小的字段，但它承载了一个容易被忽略的语义：**恢复数据时，要一起恢复"这个数据是基于什么产生的"这个上下文。**

## 恢复的时机：三个入口

草稿恢复可能在三个时机被触发：

| 时机 | 场景 |
|---|---|
| 打开编辑器 | 最常见，用户重进 App |
| 应用启动 | Android 的 lost data（上一篇讲的图片） |
| 稿件保存成功后 | 清理，不是恢复 |

而 `initState` 里的顺序很重要：

```dart
updatedAt = a.data.updatedAt ?? '';          // ① 先加载服务端版本
final recovery = await recoverDraft(prefs, draftKey, context);   // ② 再问要不要恢复
if (recovery != null && mounted) {
  apply(recovery);                           // ③ 应用草稿
}
```

**① 必须在 ② 之前。** 因为恢复草稿要覆盖的是"服务端加载上来的内容"。

而这个顺序也解释了为什么 `baseUpdatedAt` 必须在 `apply` 里恢复——**它覆盖的正是 ① 刚设置的那个 `updatedAt`。** 如果 `apply` 不包含它，基线就还是服务端的 V2，冲突检测失效。

**这个依赖关系很隐蔽**：一个字段的存在与否，取决于"恢复操作覆盖了哪些字段"。如果将来有人往草稿里加字段但忘了加 `baseUpdatedAt`，冲突检测会静默失效，而且**没有任何测试会失败**——除非有人专门构造"服务端被改过"的场景。

所以我把这条写成了断言。

## 这个 bug 我真的踩过一次

`baseUpdatedAt` 这个字段现在看起来理所当然，但它是我**补上去的**，而且是在一次真实的数据覆盖之后。

当时的场景：我自己用模拟器写稿，写完不保存直接杀掉进程，然后重启恢复草稿。这条路径是通的。

但后来有一次，我在两台设备上测同一篇稿子——手机改完保存了，平板上是旧的草稿。平板恢复草稿之后点保存，**手机的修改被覆盖了。**

我当时第一反应是"冲突检测没生效"，去查代码，发现 `updatedAt` 比较那一段明明是对的。查到最后才明白：**草稿恢复的时候，`updatedAt` 被重置成了服务端当前的值，而不是草稿记下来的那个基线。**

于是检测逻辑变成了"V2 vs V2"，永远通过。

修复就是加上 `baseUpdatedAt` 字段并在 `apply` 里恢复它。**从那以后我才明白，`updatedAt` 是"当前服务端状态"，而 `baseUpdatedAt` 是"我这份内容基于什么"——这是两个不同的东西，不能互相替代。**

这个 bug 的恶劣之处在于**单设备永远测不出来**：只有当"服务端被别的设备改过"和"本机有旧草稿"这两个条件同时成立时才会触发。而这个组合在开发时很不常见——因为你通常只有一台设备。

**这类 bug 的共同特征是：触发条件是"多设备 + 中断操作"，而单人开发环境天然不满足。**


## 一个我没做的判断：草稿存多久

现在的草稿**一直存着**，直到保存成功才清。

这意味着：如果用户写了一半然后再也不管了，那份草稿会一直在本机。而且——**它会计入"本机存储占用"，但不会自动清理。**

理想的做法是给草稿加过期（比如 7 天），过期自动清。理由是：**半个月前的半篇文章，对用户已经没意义了，但对存储是负担。**

我没做，理由是这个优先级判断：**这个功能的核心风险是"用户丢了刚写的东西"，而过期的风险只是存储占用。** 前者严重得多。

但我知道这是个技术债。而且它有一个更实际的副作用：**如果用户很多年不清理，存储里可能有几百份旧草稿。** 到那时候加过期机制时，还需要考虑"哪些该保留、哪些该清"——**现在不做，到时候反而更难决策**，因为已经有历史数据了。

顺带说一个相关的清理逻辑：**退出登录时不删草稿**。这一点看起来违反直觉（毕竟是私有数据），但理由是：**草稿是按 owner 存的，A 的草稿不会出现在 B 的编辑器里。** 而且删掉它意味着 A 重新登录后要重写一遍。

**这是一个有意的取舍**：隐私上，因为 owner 隔离已经保证了 B 看不到 A 的草稿；体验上，保住了用户的工作。**代价是设备上确实留有 A 的数据**——如果 A 退出登录后又把设备给了别人，而那个人能拿到 root 权限，那他能读到。

**在正常使用场景下（家人共用平板）这个取舍是合理的**，因为 owner 隔离挡住了 UI 层面的泄露。而要防 root 级别的读取，得靠系统级的加密存储——那又超出了这个功能的必要复杂度。

## 小结

本机草稿这个功能，代码只有二十几行，但它要回答三个问题，每个的难度递增：

| 问题 | 难点 |
|---|---|
| 存在哪 | 键要带 owner、环境、文章 id 三层隔离 |
| 坏了怎么办 | **单个损坏不连累其他**，降级为"没有草稿" |
| 恢复吗 | **要问用户，且说清"不会立刻改服务器"** |

而第三个问题的延伸——**恢复之后怎么保证一致性**——靠的是那个不起眼的 `baseUpdatedAt` 字段。

这个字段体现了一个我认为很通用的原则：**当你要恢复一份数据时，要连同"它基于什么产生"一起恢复。** 否则恢复出来的数据看起来是完整的，但它是基于一个已经过时的假设做的。

一个我知道的不足：**草稿没有过期机制**。我给出了不做的理由（核心风险优先级更高），但也承认它是个债——**而且越晚做越难做**，因为那时已经有历史数据要处理了。

下一篇讲缓存的三态——fresh、stale、expired。这篇讲的草稿其实已经是"缓存"的特例了，只是它的策略完全不同：**草稿永远不过期，直到保存成功**。
