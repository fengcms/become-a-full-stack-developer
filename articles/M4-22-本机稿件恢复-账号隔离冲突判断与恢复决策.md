# 成为全栈·Flutter App 篇·本机稿件恢复：账号隔离、冲突判断与恢复决策

我不希望“清理缓存”顺手删掉读者写了一半的稿件。本机恢复副本虽然也存储在设备上，但它的价值与可重新下载的文章缓存完全不同。

这篇以编辑器的恢复键、串行写队列和恢复确认框为线索，展示账号/稿件隔离、损坏副本处理和服务端更新时间冲突该怎样协作。

{{IMG:M4-22-封面}}

## 草稿属于用户数据，不属于可随意淘汰缓存

文章缓存可以重新请求，未提交正文不能简单当作缓存垃圾。项目按 API host authority、用户账号和稿件 ID 构造恢复键，隔离当前本机测试与线上 host、不同账号和不同稿件，避免覆盖彼此。

```text
recovery key = apiAuthority + accountId + draftId
```

当前新建稿件在服务端返回 ID 前使用 `new` 作为稿件键，保存创建成功后将内容迁移到 ID 对应键。若以后同一 host 使用多个 API base path 部署不同环境，建议把规范化后的完整 API base URL 纳入恢复 key；当前采用 authority 的前提是已配置环境足以由 host 区分。

{{IMG:M4-22-恢复流程}}

## 恢复不是自动覆盖服务端

打开编辑页时，如果本机副本与服务器最新稿件都存在，需比较本机保存时间、服务端 `updatedAt` 和内容基准。服务器在另一设备或审核流程中发生更新时，静默用本机旧内容覆盖会丢失他人修改。

合理流程是提示“发现本机未提交修改”，向用户展示恢复选项；如果服务端版本更新，说明冲突并让用户决定查看/恢复，而不是自动提交。客户端时间可能不准，因此时间戳是冲突线索，不能代替服务端版本号或 ETag。

## 清理时机需要明确

服务端保存成功后，当前恢复副本可以清理或更新基准；用户明确放弃稿件时按产品策略清理；退出登录不应把另一账号稿件错误显示，但是否保留其恢复文件要遵循隐私与产品约定。缓存清理按钮不删除本机未提交稿件。

## 不要把恢复机制说成完整离线编辑同步

当前 APP 允许恢复本机副本，但没有离线写队列、自动重放和多设备冲突合并系统。没有网络时编辑内容可留在本机，写入仍需用户联网后显式提交。离线副本不会自动解决服务端权限和状态变化。

## 测试案例

同一稿件不同账号不能交叉恢复；不同 API 环境下键隔离；服务端保存后本机副本清理；服务端更新时间变化时不静默覆盖；缓存清理入口保留稿件恢复数据；退出与重新登录仍遵循明确账号策略。

## 恢复副本需要版本元信息

正文之外，本机副本可保存本地更新时间、服务端基线更新时间和稿件环境标识，供冲突提示判断；不要把 refresh token 或其它认证秘密放进恢复记录。

```json
{
  "environment": "https://api.example.test/api/v1",
  "accountId": 42,
  "draftId": "local-or-server-id",
  "baseUpdatedAt": "2026-10-01T10:00:00Z",
  "savedAt": "2026-10-01T10:15:00Z"
}
```

该 JSON 只展示元信息结构，不应包含真实用户正文或凭据。系统时钟可被调整，`savedAt` 只能帮助用户理解先后，不能作为服务器并发写保护；若后端未来提供版本号/ETag，应优先使用服务端版本机制。

## 损坏副本要局部恢复，不要阻断整个编辑器

本机偏好记录可能被系统清理、旧版本字段改变或 JSON 不完整。恢复解析失败时只删除当前稿件对应的坏键，继续从服务端稿件加载；不要因为一份本地副本损坏就让用户无法编辑服务器内容。恢复对话框明确说明“服务器稿件不会立即被修改”，让用户知道选择恢复只把值载入编辑器。

```text
no recovery → use server draft
valid recovery + user accepts → populate controllers
invalid recovery → remove one key + continue
user declines → preserve or discard according to explicit policy
```

退出账号后，恢复键仍带账号 ID；新账号不会读取旧人的稿件。但是否在用户主动清理数据时一并删除恢复副本，应与“清理缓存”分开呈现。

## 输入监听、计时器和 dispose 必须协同

当前页面在输入发生后取消旧 Timer，500ms 无新输入再写偏好；dispose 时取消 Timer，如果仍 dirty 就立即尝试一次写入。已存在 `draftWrite` 队列，所以连续输入不会让磁盘写顺序倒置。恢复时先载入服务端稿件建立基线，再询问本机副本是否覆盖编辑器值，不会自动提交给 API。

测试要模拟快速输入、马上离页、损坏 JSON、用户拒绝恢复、账号 A/B 轮换与保存成功清理。SharedPreferences 写入仍可能被 OS/应用卸载影响，所以关键内容应提醒用户及时保存到服务端，不能把本机恢复作为唯一保存承诺。


## 贴着工程代码读实现

下面这段节选自 `flutter-app/lib/features/editor/recover_draft.dart 第 4–25 行`（保留原始实现；为突出主线省略了文件其余部分）。读代码时可以顺着调用链确认：切换账号并准备损坏 JSON，检查 key 命名和清理粒度。我会继续追踪它的返回值和副作用，直到页面状态稳定下来。

```dart
Future<Map<String, dynamic>?> recoverDraft(
  SharedPreferences prefs,
  String key,
  BuildContext context,
) async {
  final cached = prefs.getString(key);
  if (cached == null || !context.mounted) return null;
  Map<String, dynamic> recovery;
  try {
    recovery = jsonMap(jsonDecode(cached));
  } catch (_) {
    await prefs.remove(key);
    return null;
  }
  if (!context.mounted) return null;
  final accepted = await confirm(
    context,
    '恢复本机草稿',
    '发现上次未保存的内容，是否恢复？服务器稿件不会立即被修改。',
  );
  return accepted && context.mounted ? recovery : null;
}
```


草稿键与写入队列也在编辑器中实现，节选自 `flutter-app/lib/features/editor.dart` 第 74–115 行：

```dart
  String get draftKey =>
      'draft.${Uri.parse(ref.read(sessionProvider).api.baseUrl).authority}.$owner.${id ?? 'new'}';
  @override
  void initState() {
    super.initState();
    final session = ref.read(sessionProvider);
    prefs = session.preferences;
    owner = session.user!.id!;
    id = int.tryParse(widget.id ?? '');
    for (final c in [title, summary, content, tags]) {
      c.addListener(changed);
    }
    load();
  }

  Map<String, dynamic> draft() => {
    'title': title.text,
    'summary': summary.text,
    'content': content.text,
    'tags': tags.text,
    'categoryId': category,
    'coverImage': cover,
    'baseUpdatedAt': updatedAt,
  };
  Future<void> persist() {
    final value = jsonEncode(draft()), key = draftKey;
    draftWrite = draftWrite.catchError((Object _) {}).then((_) async {
      await prefs.setString(key, value);
    });
    return draftWrite;
  }

  void changed() {
    if (applying || !loaded) return;
    setState(() => dirty = true);
    timer?.cancel();
    timer = Timer(const Duration(milliseconds: 500), () {
      persist().catchError((Object e) {
        if (mounted) notice(context, '本机草稿保存失败，请尽快保存到服务器');
      });
    });
  }
```
## 把容易出错的路径走一遍

我会用这个场景做一次可复现排查：**恢复草稿按稿件 ID 覆盖不同账号或误删其他恢复记录**。先切换账号并准备损坏 JSON，检查 key 命名和清理粒度；如果把问题定位在“全局 draft key”，修正方向是“按 baseUrl、owner 与稿件 ID 隔离，只清理无法解析的单条 key”。最后再验证正常路径没有退化，并把边界条件留在自动化检查里。

| 方案比较 | 简化做法 | 当前实现/推荐做法 |
|---|---|---|
| 本文核心选择 | 全局 draft key | 身份命名空间 |
| 错误处理 | 失败后清空或静默忽略 | 保留可恢复状态，给出明确反馈 |
| 验证方式 | 只检查成功结果 | 注入边界条件并检查回归 |

| 排错步骤 | 要观察什么 | 通过条件 |
|---|---|---|
| 复现 | 恢复草稿按稿件 ID 覆盖不同账号或误删其他恢复记录 | 可以稳定触发或明确构造该输入 |
| 定位 | 切换账号并准备损坏 JSON，检查 key 命名和清理粒度 | 找到责任层和状态归属 |
| 修正 | 按 baseUrl、owner 与稿件 ID 隔离，只清理无法解析的单条 key | 失败不污染后续页面或账号 |

## 小结

本机稿件恢复是用户数据保护机制，必须与普通缓存区别对待。键同时绑定环境、账号和稿件；服务端版本变化时让人参与冲突决策；成功保存后清理副本。它不等于离线写入同步，也不应自动覆盖服务器。
