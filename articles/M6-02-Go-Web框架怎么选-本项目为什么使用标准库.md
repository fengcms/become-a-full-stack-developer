# 成为全栈·Go 后端篇·Go Web 框架怎么选：本项目为什么使用标准库

> 选框架之前先数清楚要解决的问题。依赖少只是结果之一，真正要看的是路由、校验、权限和响应边界由谁负责。

## 前言：这次不是把 Node 框架换个名字

在 Node 后端里，我们已经用 Hono 组织路由、中间件和请求处理。来到 Go，第一反应很可能是挑一个熟悉的 Web 框架：Gin、Echo、Fiber，或者一套更完整的工程框架。它们都能接 HTTP 请求，但“能接请求”并不足以决定本项目需要什么。

M6 要在既有 OpenAPI 契约前实现 68 个操作，处理认证、角色、字段校验、错误信封、限流、上传、Cookie 和请求日志。选型要回答的问题是：路由和 HTTP 基础能力需要外部框架提供多少？契约与业务规则应该由谁掌握？加一套依赖，实际省掉了哪段代码？

最终实现使用 Go 标准库 net/http。路由由标准库 ServeMux 管理，项目自己的 transport/httpapi 负责把冻结契约、鉴权和错误处理连接起来。这个选择不是“标准库一定比框架好”，而是当前工程所需的能力已经可以由标准库和明确的小型适配层承接。

## 一、先看框架究竟替我们解决什么

Web 框架通常帮忙处理以下一部分工作：

| 能力 | 本项目是否需要 | 决策 |
|---|---|---|
| 方法和路径路由 | 必须 | 使用标准库 ServeMux |
| 路径参数读取 | 必须 | 使用请求 PathValue |
| 中间件组合 | 需要，但链路有契约要求 | 由 httpapi 集中执行 |
| JSON 请求与响应 | 必须 | 受限读取、契约校验、统一信封 |
| 鉴权和权限 | 必须 | 依据每个 OpenAPI 操作元数据执行 |
| 参数校验 | 必须 | 使用冻结契约 schema 与领域边界 |
| Cookie、CORS、限流 | 必须 | 按项目既定语义显式实现 |
| HTML 模板、复杂会话、自动资源注入 | 本项目不需要 | 不引入一套额外框架概念 |

这张表给出了决策的起点：不是先投票决定用 Gin 还是 Echo，而是盘点功能。标准库提供路由和 HTTP 原语，但不会替我们完成 OpenAPI 操作级鉴权、统一错误信封或业务事务。选择标准库之后，这些职责仍然要有人负责。

如果团队不愿维护 HTTP 边界代码、项目需要大量框架中间件或生态插件、团队已经统一使用某个框架并形成可靠规范，那么采用框架完全合理。框架能提供约定和经过检验的组件，价值可能高于少量依赖。反过来，如果系统已有明确契约和边界逻辑，单为“大家都用框架”再叠一层抽象，未必让责任更清楚。

## 二、Go 标准库的路由能力已经覆盖本项目的基本需求

较新的 Go 标准库 ServeMux 支持按 HTTP 方法和路径模式注册 handler。文章系统里常见的路径可以写成：

~~~go
mux.HandleFunc("GET /api/v1/articles/{id}", getArticle)
mux.HandleFunc("POST /api/v1/articles", createArticle)
~~~

匹配之后，可以从请求中读取路径参数：

~~~go
id := r.PathValue("id")
~~~

这让路由本身保持显式，不需要再引入一个 router 包才能表达“GET 某资源”和“POST 创建资源”。Go 1.22 起，标准库增强了 ServeMux 的 method、wildcard 和 PathValue 能力；本项目使用 Go 1.26.6，因此代码可以基于这些模式组织。

标准路由仍然有能力边界。它不会根据 OpenAPI 自动校验请求体，不知道用户是否拥有某篇文章，不会因为路径写成 /admin 就自动要求管理员，也不会保证响应 JSON 与契约一致。这些是应用规则，不是 path matcher 应该猜出来的事情。

当前工程并不是在入口手写 68 行 HandleFunc。契约目录已经提供操作元数据，transport/httpapi 按 operation id 绑定 handler，再统一执行公共边界。注册表负责把“哪个操作由谁处理”连接起来；请求处理链负责通用 HTTP 行为；领域包负责内容规则和数据库事务。

## 三、路由表不是权限表，更不是业务逻辑

看一个简化后的注册入口：

~~~go
func (a *App) Register(operation string, handler Handler) {
    op := a.Catalog.Operations[operation]
    pattern := strings.ToUpper(op.Method) + " " + op.Path
    a.Mux.HandleFunc(pattern, func(w http.ResponseWriter, r *http.Request) {
        // 公共请求边界
        // 之后调用对应的业务适配器
    })
}
~~~

这里的 op 来自冻结契约，而不是从任意客户端输入拼出新的路由。注册时可以利用契约中的 HTTP 方法、路径和鉴权元数据，把公共规则安排到一次请求流程里。

实际顺序是先读取凭据并解析可用身份；受保护操作检查必需身份和角色，公开操作则按操作标识执行限流；之后限制并解码请求体、校验契约 schema，再调用业务 handler，最后统一组装响应。最外层还处理 CORS、安全响应头和 panic 恢复，注册 handler 记录操作耗时。限流并非对所有路由无差别套用，而是遵循契约标记的公开操作范围。把次序读清楚很重要：如果先把所有请求都按匿名限流，合法会员可能与游客共用额度；如果先解析业务 body 才限制大小，大请求已经消耗了不必要的资源。

这个流程之所以集中，是因为散落在 68 个 handler 里的公共判断很容易不一致：有的忘记角色校验，有的错误返回裸 JSON，有的把未认证与无权限混成同一种状态。集中处理让这些共性规则更容易审阅；但它也要求测试明确验证调用顺序与失败行为，不能只看路由注册成功。

有些端点需要整数资源 ID。项目用 registerID 适配器解析 ID，然后委托给公共 Register。它没有另造一条绕过认证、限流和 schema 校验的快捷通道。复用代码不能悄悄改变执行链。

## 四、中间件要回答“谁有权决定顺序”

Gin 或 Echo 的中间件通常以链式方式接到路由上。这个抽象很方便，但中间件执行顺序仍然是系统行为的一部分：CORS 在哪一步响应？限流发生在 token 解析前还是后？请求体大小限制是否早于 JSON 解析？鉴权失败是否也经过统一日志？

M6 把公共请求流程放在 httpapi 的注册 handler 中，目的是让一条操作的通用处理次序可以沿着同一段代码读下来。它并没有宣称“所有中间件都不应该组合”。请求 ID、压缩、Tracing 等稳定的横切能力完全可以成为独立 middleware；只是本项目没有为了框架的 API 形状而把同一组规则拆成很多隐式闭包。

例如，上传请求与 JSON 请求的解析形式不同，但都必须接受有界请求体和统一错误处理。仅按 Content-Type 分支也要落在清晰的位置，否则文件大小限制可能被遗漏。拆分粒度要由行为边界决定，不是由“中间件听起来更优雅”决定。

还有一处教学上的取舍：测试可以直接构造 App、请求和 recorder，验证权限拒绝、公开端点限流、非法输入以及错误信封。标准库的 httptest 工具能在进程内调用 handler，不必先启动真实监听端口。它当然不能代替真实数据库集成或客户端 UI 验收，但适合测试传输层能独立保证的行为。若未来引入新框架，也应继续验证这些可观察结果，而不是只检查路由能返回 200。

## 五、标准库不是把所有代码塞回 main.go

“没引框架”有时会被误读成“所有路由写在 main 里”。这正是我们要避免的结果。标准库只是 HTTP 能力来源，不代表项目不需要分层。

M6 的入口位于 cmd/server：它读取配置、打开数据库、检查连接、创建应用、设置服务器超时并响应退出信号。bootstrap 是依赖装配根，创建领域服务并把它们连接到 HTTP 操作。httpapi 负责协议边界。article、auth、comment、member 等领域包表达各自业务。platform 包封装数据库和对象存储驱动。

因此，框架选择和架构分层是两个问题。一个项目完全可以使用 Gin，同时保持领域隔离；也可以用标准库，却把所有业务塞进 handler。框架无法替团队决定领域边界，标准库也不会自动让代码更清晰。

标准库还提供 context、http.Server、响应写入器、测试 recorder 等基础件。M6 设置读写和空闲超时，在收到进程信号时执行有界关闭。这里可以看到，采用标准库让关键生命周期比较显式，但服务启动和退出仍需认真设计。

## 六、什么时候该换成 Gin、Echo 或其他框架

有几个具体信号出现时，框架可能更合适：

1. 团队已有统一框架标准，新项目需要和其他服务共享中间件及运维知识；
2. 路由、绑定、校验、API 文档等重复能力很多，框架能明显减少维护负担；
3. 第三方组件与目标框架有稳定集成，自己拼接会增加维护风险；
4. 工程需要模板、会话、WebSocket、复杂参数绑定等当前服务没有的能力；
5. 团队成员对框架约定更熟悉，框架能减少新人理解成本。

也有一些不充分的理由：因为代码里出现 ServeMux 就“太原始”；因为某个框架 benchmark 数字更大；因为项目想看起来更企业级；因为网上教程都用某个库。这些理由没有说明业务复杂度、可维护性或可靠性到底改善在哪里。

实际评估时，可以选一个端点做小型验证：路由怎样注册？权限从哪来？请求体怎么限制？schema 校验是否发生在业务之前？错误结构怎样保持契约一致？可观察的启动和测试怎么做？用端点的完整纵切片比较，比只比较 Hello World 更有参考价值。

## 七、本项目的真实依赖面

查看 go.mod，可以看到 HTTP 服务并未引入 Gin 或 Echo。它使用标准库作为传输底座，额外依赖用于 GORM 驱动、JWT、JSON Schema 校验、对象存储、数据库迁移和配置加载等实际需求。这不等于依赖越少越好，而是依赖选择按能力拆分，路由框架不是本项目的必要来源。

HTTP 边界的代码并非零成本。项目需要自己维护公共流程，也需要保证标准库版本与路由模式匹配。如果把 Go 版本降到不支持当前 ServeMux 模式的版本，路由行为就需要重写或引入第三方 router。因此 Go 工具链版本属于工程约束，应跟代码和构建环境一起记录。

标准库还提供 httptest、context、http.Server 和响应写入器等基础能力。这里的好处不是“零依赖就零维护”，而是服务使用的 HTTP 模型与 Go 自带接口一致。代价是边界规则要由项目自己写、自己更新，也需要明确支持的 Go 版本。若准备下调工具链版本，就应先验证 ServeMux 的方法和路径模式是否仍可用，再决定改路由还是引入 router，不能只改 go.mod 的版本号。

标准库没有替我们管理依赖注入容器、自动生成 API 文档，也没有替我们验证中间件配置。这个项目本来就需要按冻结 OpenAPI 逐操作绑定与校验，依赖一个“自动从路由生成协议”的约定反而会形成第二个事实源。用 ServeMux 只负责匹配请求；契约加载、operation id 和响应 schema 仍由 contract 包负责。下一篇工程架构会沿着这些入口解释 cmd、bootstrap 和各领域包之间的依赖。

## 小结：比较一条真实请求链

本项目选择标准库，不是因为框架没有价值，而是当前需要的路由能力由 ServeMux 覆盖，而鉴权、契约校验、错误信封和领域事务有自己的边界。把这些规则留在项目可见的 transport/httpapi 里，能够与 OpenAPI 操作绑定并接受直接测试。

如果你在自己的项目里做选择，不妨从完整请求链问起：框架替你做了什么？团队还需要写什么？公共顺序能否看见并测试？升级工具链会不会改变路由行为？有没有真实的维护成本或能力缺口支撑选择？

只比较框架名字和 benchmark，不足以回答这些问题。
