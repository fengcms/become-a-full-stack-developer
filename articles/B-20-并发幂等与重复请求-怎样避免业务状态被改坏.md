# 成为全栈·基础补充·并发幂等与重复请求：怎样避免业务状态被改坏

写这篇的时候我先查了一下自己的代码，然后发现一件让我有点尴尬的事：

**契约里写着 `x-idempotent: true`，标了四个端点。但代码里没有任何一处实现了幂等处理。**

也没有限流中间件——契约里写的是"所有公开端点受网关层统一限流保护"，而网关层……在这个项目里并不存在。

我先说结论：**这两件事我不打算在本文里假装它们有。** 但它们恰好是这个主题最好的例子——**"声明了幂等"和"实现了幂等"之间，隔着一个真实的技术决策。**

这篇讲那个决策，以及三个已经落地的并发处理。

## 先把三个词分开：并发、重复、幂等

这三个词经常混用，但它们回答的问题不同。

| 词 | 问题 | 例子 |
|---|---|---|
| **并发** | 两个请求**同时**到达 | 用户双击"提交" |
| **重复** | 同一个请求**到了两次** | 网络重试、用户重复点 |
| **幂等** | 重复执行**结果相同** | `PUT /settings` 执行 10 次 = 执行 1 次 |

它们的关系是：**并发和重复都会导致同一次业务被触发多次**，而**幂等是抵抗这件事的手段之一**。

但幂等不是唯一的手段。这个项目里用了三种不同的方式，各有适用场景：

1. **数据库唯一约束**（防重复创建）
2. **条件更新 + 影响行数判断**（防重复执行状态变更）
3. **让接口本身幂等**（防重复设置的副作用）

而**防重复重放**这个手段，项目里明确没有在服务端做——这是 M1-27 讲过的决定，下面会说为什么。

## 手段一：唯一约束——把判断交给数据库

最直接的场景：微信用户首次登录时创建账号。

第一版代码是"先查，没有就插"：

```ts
const find = async () => (...).find();
let user = await find();
if (!user) {
  await insertUser();
}
```

看起来对，但**两个并发请求可能同时查到"不存在"，然后各插一个用户**。结果是同一个微信号对应两个本地会员。

正确的做法是把判断交给数据库：

```ts
try {
  await atomic(db, [
    { sql: `INSERT INTO users (...) VALUES (...)`, params: [...] },
    { sql: `INSERT INTO wechat_identities(...) SELECT ?, ?, id, ? FROM users WHERE username = ?`, params: [...] },
  ]);
} catch (error) {
  if (!isUniqueConstraintError(error)) throw error;
}
user = await find();
if (!user) throw new AppError(ErrCode.INTERNAL, 500, '微信账号创建失败，请重试');
```

**注意那个 catch 的含义**：唯一约束冲突在这里**不是错误，而是"别人先建好了"的信号**。吞掉它，然后重新查。

而它依赖这个索引：

```sql
CREATE UNIQUE INDEX uniq_wechat_identity ON wechat_identities(app_id, open_id);
CREATE UNIQUE INDEX uniq_wechat_user ON wechat_identities(user_id);
```

**为什么用数据库而不是应用层加锁？** 三个原因：

- **应用层的锁只在一个进程内有效。** Cloudflare Workers 是无状态的，同一个请求可能被路由到不同的 isolate。**一个 isolate 里的 `Map` 对其他 isolate 不可见。**
- **数据库的唯一约束是跨进程、跨机器、跨并发连接的唯一事实。**
- **它不会因为代码路径遗漏而失效。** 而应用层的检查只要有一条路径忘了加锁，就漏了。

**"检查后再操作"在有并发的情况下永远是不够的**，因为检查和操作之间有时间差。唯一约束把这个时间差消掉了——**它不是"检查时没有"，而是"不可能有两个"**。

### 冲突之后为什么必须重新查

上面那段代码里，`catch` 之后有一行 `user = await find()`。

**这一行不能省。** 因为捕获冲突之后，手上的 `username` 对应的那个用户**不是我们要的**——我们想要的是"持有这个微信身份的那个用户"，而它可能是另一个请求建的。

如果直接用本地生成的用户继续，**数据库里就会多出一个没有微信映射的孤儿会员**：他永远无法登录（没有身份映射），也永远无法被识别（有账号但找不到微信）。

而最后那行 `if (!user) throw 500` 处理最后一种情况——**捕获了冲突但重新查还是查不到**。那说明冲突来自别的约束（几乎肯定是随机用户名碰撞），此时不能返回任何用户。

**"查不到就抛错"和"查不到就用本地的"是两种完全不同的错误处理**，而后者会造出脏数据。

## 手段二：条件更新 + 影响行数

第二个场景：用户首次设置用户名密码。

这里的问题不一样——**不是重复创建，是重复执行状态变更**。

如果两个请求同时到达，两个都通过了"还没设置过凭据"的检查，然后都去 UPDATE：

- 第一个成功，`credentials_configured` 变成 1
- 第二个也"成功"——**因为它的 WHERE 里没有再检查一次状态**

所以条件必须写进 SQL：

```sql
UPDATE users SET username=?, password_hash=?, credentials_configured=1, updated_at=?
WHERE id=? AND status='active' AND credentials_configured=0
AND EXISTS (SELECT 1 FROM wechat_identities WHERE user_id=users.id)
```

**注意 `AND credentials_configured=0`** ——这一句是整个并发安全的核心。

它保证的是：**这个 UPDATE 只可能成功一次。** 第二个请求执行时，`credentials_configured` 已经是 1，条件不成立，**影响行数是 0**。

而应用层必须检查这一点：

```ts
const changed = await atomic(db, [...]);
if (changed[0] !== 1) throw new AppError(ErrCode.CONFLICT, 409, '账号状态已变化，请重新登录');
```

**如果这里不检查影响行数，条件更新就白做了**——SQL 确实没让第二个请求改坏数据，但应用会拿着自己那个 `hash` 继续往下走，以为成功了。

### 那个 EXISTS 也在防并发

`AND EXISTS (SELECT 1 FROM wechat_identities WHERE user_id=users.id)` 看起来是"确认这个用户有微信身份"，是个业务规则。

**但它同时也是安全边界。**

这个端点的用途是"给微信建号的账号设置凭据"。如果没有这条 EXISTS，**任何一个登录用户（网站注册的、密码登录的）都能调用它给自己设置用户名密码**——而这条端点是为微信账号准备的。

这不是"业务规则"，是"**这个端点属于哪类用户**"的机器表达。靠客户端判断做不到，因为客户端可以伪造。

**几个条件各有分工，合起来构成完整的判断：**

| 条件 | 防什么 |
|---|---|
| `id=?` | 改错人 |
| `status='active'` | 禁用账号不能设置 |
| `credentials_configured=0` | **并发重复设置** |
| `EXISTS (微信身份)` | **越权**（非微信用户也能设） |

**只有第三条是并发相关的，另外三条是权限相关。** 但它们写在同一个 WHERE 里，**一次原子操作同时保证了全部四条**——这比在应用层分开检查可靠，因为应用层的检查和操作之间有时间差。

## 手段三：changes() 绑定——并发场景下最难的那个

现在说这次增补里最难写对的地方，它同时用到了上面两个手段。

先看完整代码：

```ts
const changed = await atomic(db, [
  {
    sql: `UPDATE users SET username=?, password_hash=?, credentials_configured=1, updated_at=?
    WHERE id=? AND status='active' AND credentials_configured=0
    AND EXISTS (SELECT 1 FROM wechat_identities WHERE user_id=users.id)`,
    params: [username, hash, now, userId],
  },
  {
    sql: 'UPDATE refresh_tokens SET revoked_at=? WHERE user_id=? AND revoked_at IS NULL AND changes()=1',
    params: [now, userId],
  },
]);
```

**第二条 UPDATE 里的 `changes()=1` 是整段代码最难懂的部分。**

`changes()` 是 SQLite 的函数，含义是"上一个语句影响了多少行"。

那为什么要用它？

**先看不加它会怎样。**

时序：

```text
请求 A：查 → 通过 → 开始设置
请求 B：查 → 通过 → 开始设置
（A 和 B 都通过了应用层的前置检查）

A 执行第一条 UPDATE → 成功（credentials_configured 变成 1）
B 执行第一条 UPDATE → 影响 0 行 → 抛 409 ← 正确
```

看起来没问题。但**撤销旧 refresh token 那一步是无条件的**：

```sql
-- 如果没有 changes()=1，这是原本的写法
UPDATE refresh_tokens SET revoked_at=? WHERE user_id=? AND revoked_at IS NULL
```

在这个时序下，B 虽然第一条 UPDATE 失败了，**但它会继续执行第二条**（如果两条不在一个事务里）——**把 A 刚刚签发的新会话撤销掉。**

结果：**A 设置成功了，拿到了新令牌，但那个令牌立刻失效了。** 而 A 的客户端还不知道，它以为登录着。

**这就是 `changes()=1` 解决的问题：让"撤销旧会话"这个动作，只在"我确实更新成功了"的时候才发生。**

而 B 那个用户的处境也很糟：**他既没设置成功（第一条失败了），又被撤销了会话**——只能重新走微信登录。

而加了 `changes()=1` 之后，B 的第二条 UPDATE 的条件不成立，**它什么都不做**，A 的会话安全了。

**这本质上是一个"条件绑定"**：把第二步的生效条件绑在上一步的结果上。而这只有在同一条原子批次里才做得到——**所以两条语句必须放进同一个 `atomic()`。**

### 为什么这需要 atomic 的 changes 返回值

现在回头看 M1-33 讲的那个设计，就有实际意义了：

```ts
export async function atomic(db: Db, statements: Statement[]): Promise<number[]>
```

**为什么它返回 `number[]` 而不是 void？**

因为调用方需要知道每条语句影响了多少行。而如果只返回"成功/失败"，就区分不了"更新了 0 行"和"更新了 1 行"——**而这两个在设置凭据这个场景里意义完全不同**。

**一个返回 void 的 atomic，会让 `changes()=1` 这个条件无法在应用层判断。** 而如果不判断，应用就会拿着自己那个 `hash` 继续往下走，**以为设置成功了**。

所以这两处设计是配套的：**SQL 层的条件 + 应用层的判断，缺一不可。**

### 为什么必须放在一个事务/batch 里

`changes()` 的语义决定了它只能引用**紧邻的上一个语句**。

而两条语句之间的原子性保证了"第一步失败时第二步不会执行"——但如果它们不在一个原子批次里，那么**B 的两条语句都执行了**（第一条失败、第二条成功），此时 `changes()` 引用的是"失败的第一条"，条件不成立，B 什么都不做——**这恰好是我们想要的**。

而如果在一个事务里，第一条失败会整体回滚，第二条根本不执行——**结果一样，但机制不同**。

**两种机制都能得到正确结果**，但它们的差异在别的地方：**如果在一个普通的事务里，第一条失败后整个批次回滚，那么"撤销 refresh"这个动作也一起没了**——这是对的。

而 D1 的 `batch` 语义不同（它是并发执行而非顺序执行），所以 `changes()` 在 batch 里能不能引用前一条语句，是需要验证的。**这一点我验证过并写进了注释和测试**，而不是假设它成立。

## 防重复重放：为什么服务端没做

现在说契约里那四个 `x-idempotent: true`。

它们标的是"这个操作是幂等的"——**也就是说，它靠的是客户端不重复发，而不是服务端防重。**

M1-27 讲过这个决定，理由是：

**幂等键要真正的幂等，需要存储。** 服务端收到 `Idempotency-Key`，得把它和响应结果存起来，重复的请求返回上次的结果。这需要：

- 一个存储（至少缓存几分钟）
- 一个清理策略（键不能无限增长）
- 一个并发处理（两个请求同时带同一个键）

而这个项目的写操作大多是：

| 操作 | 是否幂等 | 客户端行为 |
|---|---|---|
| `PUT /articles/{id}` | 是（设置类） | 重试安全 |
| `DELETE /articles/{id}` | 是 | 重试安全 |
| `POST /articles` | **否**（创建类） | **不能重试** |
| `POST /articles/{id}/comments` | **否** | **不能重试** |

**真正需要防重放的是创建类操作。** 而那些操作的服务端幂等，本项目没有实现。

**这是一个明确的缺口，不是疏漏。** 在这个专栏的定位下（教学 + 少量真实流量），我认为可以接受——**但写清楚比含糊过去重要**。

而客户端那一侧的处理是 M4-08 讲的：写请求失败不自动重试，让用户手动决定。因为**服务端不知道上一次请求是否已经在服务端执行了**——M1-32 讲的那个"响应没到不等于设置失败"就是这个问题的客户端版本。

**如果服务端有幂等键，客户端就能安全重试。** 没有它，客户端只能保守处理。这是一条清晰的因果链。

## 三种手段的适用边界

| 手段 | 防什么 | 依赖什么 | 例子 |
|---|---|---|---|
| 唯一约束 | 重复创建 | 数据库 | 微信身份映射 |
| 条件更新 + 检查行数 | 重复状态变更 | 数据库 + 应用层判断 | 设置凭据 |
| 幂等键 | 重复执行整体副作用 | 存储 + 清理策略 | **本项目未实现** |
| 接口本身幂等 | 无需额外机制 | 语义设计 | `PUT` 设置类 |

而"接口本身幂等"是最省事的一种——**所以设计接口时应该优先考虑它**。M1 里那个"角色不能由客户端自定"、"注册永远创建 member"，都属于"通过语义设计避免重复执行的问题"。

**如果一个接口必须是非幂等的（比如创建），那就必须显式面对重复的问题**——要么加幂等键，要么让客户端不要重试。

**不能默认"网络不会重试"。** 因为请求可能因为超时、因为用户刷新、因为客户端实现 bug 而重来一次。

## 一条我一开始想省掉的事

那个 `changes()=1` 的条件，第一版我是这么写的：

```ts
// 第一版
await atomic(db, [
  { sql: 'UPDATE users SET ... WHERE id=? AND credentials_configured=0', params: [...] },
  { sql: 'UPDATE refresh_tokens SET revoked_at=? WHERE user_id=? AND revoked_at IS NULL', params: [...] },
]);
```

当时的逻辑是："先更新用户，再撤销旧 token，不在一个批次里但也没什么问题。"

**问题出现在我手工模拟并发的时候。**

我构造了这样一个场景：两个请求同时到达，第一个因为用户名冲突失败，第二个成功。而撤销 token 那一步是无条件执行的——**第一个请求的失败也执行了撤销，把这个用户的所有会话全干掉了**。

那个用户的状态就是：**既没设置成功，又被登出。**

**而这个 bug 在串行测试里永远不会出现**，因为串行时第一个失败之后不会再有第二个请求来"顺手撤销"。

修复之后我加了一条测试：**构造两个并发 setup 请求，断言失败的那个不能影响另一个请求建立的会话。**

而这条测试的实现方式值得一提：**它不是靠 sleep 制造竞争的**，而是靠两个不同的用户名同时打，然后靠 `atomic` 的事务顺序制造结果差异。**这样测试的结果是确定的，不依赖时序。**

顺带说，这种测试有它的局限——**它验证的是"在我构造的这个竞争里，失败方不撤销成功方"**，而不是"在任何竞争下都这样"。

**要更彻底，需要知道 `atomic` 在各种数据库状态下的执行顺序**，而那是实现细节。**我在注释里写清了这条 SQL 依赖 SQLite/D1 的语义，换数据库要重新验证**——而不是假装它换个平台也对。

## 小结

并发处理的三种手段，各有明确的适用边界：

1. **唯一约束**防重复创建，依赖数据库的跨进程唯一性——比应用层加锁可靠，因为它不受多实例影响。
2. **条件更新 + 检查影响行数**防重复状态变更，条件要写进 SQL，判断要在应用层——两者缺一不可。
3. **接口本身幂等**是最省的方案，设计时应该优先考虑。

而 `changes()=1` 属于第二种的延伸：**它把两个动作的生效条件绑在一起**——只有上一步真的成功了，后续动作才执行。这个能力依赖 `atomic` 返回影响行数，也依赖它把多条语句放进同一个原子批次。

至于那四个 `x-idempotent: true`：**契约里标了，服务端没实现。** 这不是遗漏而是一个明确的取舍——**因为防重复重放需要存储、清理策略和并发处理，而当前规模下"让客户端不重试"是更简单的选择。**

**但要写清楚这个缺口**，因为它决定了客户端的行为：**服务端没有幂等键，所以客户端在写请求失败时不能自动重试。** 这不是客户端的保守，是服务端的现状。

**一句话总结并发处理：不要问"怎么防止并发"，要问"这个操作重复执行了会怎样"**——如果结果相同，它本来就幂等，不需要额外机制；如果不同，才需要上面那些手段。
