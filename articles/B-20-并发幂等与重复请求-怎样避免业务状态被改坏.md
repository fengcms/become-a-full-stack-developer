# 成为全栈·基础补充·并发、幂等与重复请求：怎样避免业务状态被改坏

> 并发问题不只出现在高流量网站。用户连点两次、客户端超时后重试、两个设备同时操作，都可能让同一个业务动作重复发生。正确性要靠状态约束、事务和可验证的业务规则共同保护。

## 前言：一个请求在网络里可能出现不止一次

用户点击“点赞”后手机网络断开，界面没有收到响应。用户不知道服务端是否已经处理，于是再次点击。第一次请求也许成功了，只是响应丢失；第二次请求则又到达服务端。若接口实现为“计数加一”，一篇文章就可能被一个用户点出两个赞。

这不是罕见的极端并发。浏览器重试、移动网络、负载均衡器、用户双击和后台任务重放都会让重复到达成为正常情况。系统不能依赖“用户只点一次”或“请求只投递一次”来维持数据正确。

## 一、并发和重复请求是两个相关但不同的问题

**并发**指多个操作的执行时间有重叠；**重复请求**指同一个逻辑动作可能被执行多次。并发下，一个操作可能只提交一次，但与另一个操作交错后产生错误；重复请求也可能串行发生，仍然导致重复副作用。

**幂等**描述重复执行的结果：对同一逻辑操作执行一次或多次，最终状态相同。比如“把通知标记为已读”天然容易实现为幂等的状态赋值；“余额加 10”则不是，重复执行会不断增加余额。接口是否幂等，要看业务状态和副作用，而不是 HTTP 方法名字。

## 二、为业务不变量设计操作

先写出不变量，再决定锁和代码结构。文章点赞的简单不变量是：同一用户对同一文章至多有一条 like 关系；文章 `likeCount` 与关系数量保持一致。仅在客户端禁用按钮，只能减少重复点击，不能保护另一台设备、脚本或并发请求。

一种可靠方案是给 `(user_id, article_id)` 加唯一约束，并在事务中创建或删除关系、更新计数。更好的是让业务操作表达“确保已点赞”与“确保未点赞”，而非无条件加减。重复点赞检测到关系已存在时返回成功的最终状态，不再增加计数；取消时只有实际删除关系才减少计数。

```text
BEGIN
  尝试建立唯一的 user/article 关系
  如果关系本次新建：计数增加一次
  如果关系已存在：保持当前状态
COMMIT
```

数据库约束是最后一道防线，应用检查用于产生可读的结果，事务用于保证关联变更和计数一起提交。不能只相信“先查询不存在，再插入”——两个请求可能同时查到不存在，然后都尝试创建。

## 三、令牌轮换说明了为什么锁顺序很重要

刷新令牌通常一次性消费：请求用旧 refresh token 换取新 token。若两个请求同时提交同一旧令牌，期望只有一个成功；另一个发现令牌已消费，应按安全规则处理重放。若只在内存里加互斥锁，多实例部署时两台机器各有一把锁，仍可能同时消费。

项目 Go 后端在事务中定位令牌、锁定用户记录、再次校验令牌状态、消费旧令牌并签发新令牌。并发测试确认只有一个消费者成功；重放请求会撤销令牌家族。实现还必须注意事务返回语义：如果先撤销家族，再从事务回调返回错误导致事务整体回滚，撤销就没有真正生效。安全决策提交后，服务再返回相应错误。

这个例子说明并发正确性不只是“加锁”。还要决定锁的对象和顺序、冲突后的业务结果、事务是否提交、失败后客户端是否能重试，以及多个实例是否共享协调状态。

## 四、数据库锁与进程锁保护的范围不同

数据库行锁和唯一约束可以协调访问同一数据库的多个服务进程；进程内 `mutex` 只对当前进程有效。把它们混为一谈，是部署后常见的并发陷阱。

Go 项目的 PostgreSQL/MySQL 账户与互动操作通过数据库事务和行锁保护关键状态；SQLite 使用单写连接串行执行事务。分类树互斥和对象 key 生命周期仍含进程内协调，所以当前部署边界是单写服务实例，不能仅凭“用了 PostgreSQL 行锁”就宣称任意多实例都安全。扩容前要把这些状态移到数据库约束、共享锁或其他跨实例协调机制中，并验证失效恢复。

| 协调方式 | 可以保护 | 不能自动保护 |
|---|---|---|
| 客户端禁用按钮 | 减少正常交互中的重复点击 | 恶意请求、跨设备、网络重试 |
| 进程内锁 | 同一进程里的并发协程 | 另一个进程或另一台机器 |
| 数据库唯一约束 | 同一数据库中的重复关系 | 外部文件、微信调用和跨库操作 |
| 数据库事务 | 同一连接内的相关 SQL | 已完成的 HTTP/R2 副作用 |
| 幂等键 | 可识别的同一业务请求重放 | 错误的业务状态机或不一致事务 |

## 五、何时需要幂等键

对“创建订单”“发起支付”一类请求，客户端可能在超时后重试，但服务端需要避免创建两笔业务记录。可以为一次逻辑请求生成幂等键，服务端将键与请求摘要、处理状态和结果关联起来；同一键、同一请求返回已记录结果，同一键却携带不同参数则拒绝。

幂等键要有作用域和过期策略：是按用户、接口还是业务对象唯一？结果保存多久？并发首次提交如何原子抢占？处理过程中服务宕机后，状态如何恢复？如果这些问题没有答案，幂等键只会增加一张状态含糊的表。像“标记已读”这种可通过状态赋值自然幂等的操作，不必机械套用幂等键。

## 六、超时后不要盲目重试写操作

客户端超时只能说明客户端没有及时收到响应，不能说明服务端没有提交。对于读请求，有限次数退避重试通常风险较低；对于写请求，要先确认操作是否幂等，或携带可复用的幂等标识。重试同一逻辑操作时必须重复使用同一键，不能每次生成新键。

服务端也要限制重试次数和时间，识别明确可重试的数据库错误。把所有数据库异常都捕获后重试，可能延长故障、放大流量，甚至重复外部副作用。日志要记录请求标识和业务对象 ID（在合适脱敏后），帮助判断请求是否已被处理。

## 七、用故障与并发测试验证，而不只看 happy path

并发测试应构造真实竞争：同时提交两个刷新请求、两个微信首次建号、重复点赞和取消、同一分类树更新；然后检查状态、关系数量、令牌状态和错误响应。测试通过一个共享 barrier 让请求尽量同时到达，比顺序调用两次更能暴露竞态。

测试还应包含失败注入：在通知写入时失败，文章状态是否回滚？R2 上传成功但 SQL 失败，临时对象是否清理？清理失败是否留有可观察记录？对 Go 代码运行 race detector 可以发现一部分内存数据竞争，但它不替代数据库并发和事务后置状态测试。通过一组顺序单测，也不能证明跨进程协调有效。

M6 的并发验证覆盖刷新令牌、微信建号、首次设密、点赞与阅读冷却；文件 key 与分类树则明确保留单实例协调边界。文章记录这些事实时，需要分别写清“已验证的并发场景”和“当前部署承诺”，不能用某个测试通过推导出系统支持无限扩容。

## 小结：先保护不变量，再谈锁和吞吐

为每项写操作定义最终状态和重复执行结果；用唯一约束、条件更新、短事务和合适的锁实现不变量；区分数据库协调与进程内互斥；对外部副作用设计补偿；客户端只有在语义安全时才重试。最后用真实竞争和失败状态测试证明行为，并把多实例边界写进部署说明。
