# M0-06 工程公约：git tag、仓库组织与 CSDN 发布流程

**本文目标**：前面几篇讲了「做什么」——七端、建模、契约。这篇讲「怎么把这一切组织起来，让它能复现」。一套专栏最大的承诺是「读者跟着做能跑起来」，而让这个承诺成立的东西，就是工程公约：monorepo 单仓、每篇一个 git tag、一份 `ARTICLES.md` 对照表、以及 CSDN 发布流程。

**前置知识**：建议先读 M0-02（七端全貌）、M0-05（契约）。本文把它们的「组织形式」钉死。

---

## 一、monorepo 单仓多目录

七个子项目（M1–M7）放在**同一个 git 仓库**里，用目录区分：

```
become-a-full-stack-developer/
├── node-backend/        # M1
├── manage-frontend/     # M2
├── web-frontend/        # M3
├── app-frontend/        # M4
├── go-backend/          # M6
├── docs/                # 章程 / 路线图 / 领域模型 / 契约
├── articles/            # 本系列文章草稿
└── ARTICLES.md          # 文章 ↔ 代码 ↔ tag 对照表
```

为什么是单仓而不是七个独立仓库？因为七端**共享同一份契约**。单仓让契约和所有端处在同一条版本历史里——你打一个 tag，锁住的是「契约 + 全部端」那一刻的完整状态，而不是某个端孤立的快照。读者 checkout 一个 tag，拿到的是整个系统当时长什么样。

配套铁律是「一个 M 只讲一件实现」：每篇文章聚焦一个端/目录，不把后端和前台塞进同一篇。这样你读的时候心智干净，代码归属也清晰。

---

## 二、每篇文章一个 git tag

这是可复现性的核心。约定：

- 每篇文章发布时，打一个全局 tag，命名 `article/M1-05`、`article/M3-12`……
- 读者执行 `git checkout article/M1-05`，就能拿到**那篇文章发布时刻**的完整代码状态——契约、后端、前端，全部对齐。
- 我们的工程产出指标（P2）就这一条：读者能 checkout 到任意一篇文章对应的代码状态并跑起来。

为什么非要 tag？因为代码是流动的。你今天写的 M1 后端，三个月后 M6 用 Go 重写时早变了。没有 tag，读者读到 M1-05 那篇想照着跑，拿到的却是半年后的代码，对不上号。**tag 是文章和代码之间的一根锚绳**——它让「文字描述的那个世界」和「实际可运行的那个世界」始终指向同一点。

---

## 三、根目录 `ARTICLES.md` 对照表

仓库根维护一份 `ARTICLES.md`，把三件事钉在一起：

| 文章标题 | 对应 tag | 代码位置 / 链接 |
|---|---|---|
| M0-01 为什么前端要走向全栈 | `article/M0-01` | `articles/M0-01-...md` |
| M1-05 … | `article/M1-05` | `node-backend/...` |

它的价值是**双向跳转**：从文章能跳到当时的代码，从代码（tag）能跳回讲了它的那篇文章。没有它，文章和代码会逐渐脱节——这是我们在风险表里明确列过的坑。

> 你正在读的 `articles/` 目录，是写作期的临时草稿归属。随着 M0-06 落地，正式绑定机制以本文为准：文章发布后，标题与 CSDN 链接回填进 `ARTICLES.md`，代码状态由对应 tag 锁定。

## 四、CSDN 发布流程

写作和代码之外，还有「怎么发出去」：

- **主阵地是 CSDN**（`blog.csdn.net/fungleo`）。自建站只作成果展示，不分发。
- **单篇约 2500 中文字（±300）**。够把一个技术决策或一步实现讲透，不注水；**每篇只讲一件事**，对应一个 tag。
- **质量项但内容优先**：配图 2–4 张、文末 ≥2 条站内往期互链、排版有多样性——这些是 CSDN 的基本质量分工程项，会做，但**内容为王、密度优先**，绝不为了凑分注水。
- **发布后回填**：文章发到 CSDN 后，把链接回填进 `ARTICLES.md` 和本文的延伸阅读区，闭环。

这套流程的意义，是把「写一篇技术博客」升级成「交付一个可复现的教学产品」。读者不是来看热闹，是来跟着做出来的。

---

## 五、为什么这套公约值得费劲

一句话：**它让「文章是产品」这句话落地，而不是口号。**

没有 monorepo，契约和端会各走各的版本；没有 tag，代码流动后读者对不上；没有 `ARTICLES.md`，文章和代码迟早脱节；没有 CSDN 流程，再好的内容也触达不到人。四样东西单独看都小，合起来是专栏可信度的地基——和契约一样，是「值得提前投入、不能返工」的那类东西。

---

## 小结

- 七端放同一个 git 仓库（monorepo 单仓多目录），共享契约，一个 tag 锁全局状态。
- 每篇文章一个全局 tag（`article/Mx-yy`），读者 checkout 即拿到发布时刻完整代码——这是「可复现」的硬承诺。
- 根 `ARTICLES.md` 把「文章 ↔ tag ↔ 代码」钉在一起，支持双向跳转，杜绝文章代码脱节。
- CSDN 主阵地，单篇约 2500 字、每篇一事、内容密度优先；发布后回填链接闭环。
- 四样东西合起来让「文章是产品」落地：可复现、可追溯、可触达。
