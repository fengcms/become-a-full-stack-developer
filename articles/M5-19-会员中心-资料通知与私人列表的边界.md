# 成为全栈·Taro 小程序篇·会员中心：资料、通知与私人列表的边界

> 头像放上去，下面排上收藏、历史、投稿和设置，“我的”页面看起来就做完了。

{{IMG:M5-19-封面}}

## 前言：登录后的页面，比头像和昵称更复杂

点进去之后，问题才出现：哪个接口属于本人，哪些数据可以公开，退出时又该清理什么？一个“我的”页面放了很多入口，却不应把公开身份、私人数据和设备偏好当成同一种状态。

成为全栈小程序延续 APP 的会员能力，又增加微信会员首次凭据入口。它需要组合多份私人数据，也需要给游客留下清楚的登录路径。

这篇从数据所有权出发看“我的”。页面布局可以统一，存储和权限不能因为入口相邻就被合并。

## 一、先把三种归属分开

| 数据 | 所有者 | 读取与存储方向 |
|---|---|---|
| 作者昵称、公开文章 | 公开身份 | 公共会员接口与缓存 |
| 收藏、通知、个人稿件 | 当前会员 | Bearer、私有缓存、服务端权限 |
| 主题与本机搜索历史 | 当前设备使用环境 | 本机存储，不当作服务器账户资料 |

公开作者页与私人资料页是不同页面。前者展示可公开的信息和已发布作品，后者允许修改当前会员资料，不能把完整 User 响应顺手放进公共作者缓存。

主题也不是某个会员的服务器字段。当前设置存于设备，换账号仍可保持选择。搜索历史同样是本机级键，这个取舍要让用户可清空，而不是假称它已经按账号同步。

### 最近阅读为什么不直接成为公开履历

会员页显示最近三条 history，帮助本人继续阅读。公开作者页没有把这份历史展示给其他读者。作者作品与阅读习惯是两类信息，即使都与同一个 userId 关联，公开范围也不同。

通知更是如此。它可以包含审核、互动等针对性消息，不能为省一个接口直接复用到公开会员对象。页面共享 Avatar 和 ArticleCard，只共享展示结构，不共享底层权限。

## 二、统计只读需要的范围，不把整库拉下来

会员首页读取收藏与个人文章各一条，用 pagination.total 显示总量；未读通知使用专门 count；最近历史取三条。四条读取都带同一个登录前置条件：

```tsx
// src/pages/member/index.tsx：auth 为空时传空路径，服务端不会被请求。
const unread = useResource<{ count: number }>(auth ? "/me/notifications/unread-count" : "", true);
const favorites = useResource<Page<Article>>(auth ? "/me/favorites?pageSize=1" : "", true);
const articles = useResource<Page<Article>>(auth ? "/me/articles?pageSize=1" : "", true);
const recent = useResource<Page<HistoryItem>>(auth ? "/me/history?pageSize=3" : "", true);
```

片段展示请求意图，实际页面在游客状态将路径置空，不发这些私人读取。空路径不是"请求失败"：Hook 在发出前就先拦下了它，返回结果还带一次会话代次校验。

```ts
// src/hooks/data.ts：两道闸门——入口处拦空路径，回来时校验 epoch。
if (!path || (privateData && !auth)) {
  setData(undefined);
  return;
}
// ...
if (id === serial.current && (!privateData || epoch === sessionEpoch())) {
  setData(result);
}
```

这里的 `serial` 是每个 Hook 实例自己的递增序号。用户快速改条件、页面重渲染时可能有多个请求同时在飞，只有序号最大的那个有资格写入状态——先发后到的旧响应会被丢弃，不会盖掉新结果。

它还配合可见性钩子：`useDidShow` 重新进入页面时补一次读取，卸载时把 `serial` 再推一格，让所有在途响应失效。私人列表因此不会出现“退到上一页再回来，看到几秒前旧数字”的情况。

计数未就绪用破折号，不能默认零并让用户误以为数据丢了：

```tsx
// 统计卡片：加载不出来时显示 —，而不是 0。
<View className="stat-value">{favorites.data?.pagination.total ?? "—"}</View>
```

当前统计模块没有专门的聚合接口，也没有把各请求错误统一做成一块详细故障面板。它们可以独立到达；需要进一步改善错误可见性时，应依据页面观察补充，而不是在文章里宣布所有失败体验已经完善。

### 私人列表失败后，别把零当成真实结果

计数未加载显示破折号，列表错误显示重试，成功空列表再显示没有内容。三种状态分开后，用户才知道数据正在来、暂时来不了，还是确实没有。

当前各页错误展示成熟度并不完全一致，文章记录实现与可检查边界。后续改善统计卡片时，应增加局部错误反馈，而不改变服务器数据的所有权。这比重新造一个万能会员聚合对象更容易维护。

## 三、门禁是体验，权限是后端事实

collection、notifications、profile、editor 等私有页面统一由 `Private` 包住。游客看到登录入口，已登录则渲染实际内容：

```tsx
// src/components/private.tsx：未登录给入口，登录后按 userId 重建子树。
export function Private({ children }: PropsWithChildren) {
  const auth = useSession();
  if (!auth)
    return (
      <View className="panel center">
        <View className="section-title">登录后继续</View>
        <Text className="muted">你的阅读、收藏和创作，都在这里</Text>
        <Button className="button" onClick={() => go("auth")}>登录 / 注册</Button>
      </View>
    );
  return <View key={auth.user.id}>{children}</View>;
}
```

注意最后一行那个 `key`。它不是装饰——账号从甲切到乙时 `key` 变了，React 会丢弃整棵子树重建，页面上所有 `useState`、`useRef` 随之归零。没有它，切换账号后上个账号填了一半的表单、滚动位置都可能留在屏幕上。

然而，门禁只说明客户端如何引导。用户可以手工发请求，服务端必须检查当前会员和资源所有权。真实本地后端集成中有不同账号访问验证，这才为私人边界提供独立证据。

私有 read 的缓存键带 API、userId 和 epoch；账号变化清理缓存。页面 Hook 也检查结果归属。不能只靠“退出后导航到登录页”，旧异步任务仍可能在后台完成。会话层的 `setSession` 把三件事绑在一起：

```ts
// src/core/session.ts：换身份即递增代次并清空私有缓存。
export function setSession(value: Auth | null, identityChange = true) {
  current = value;
  if (identityChange) {
    epoch++;
    privateCache.clear();
  }
  // …写入或清除本机会话…
}
```

`epoch` 是给在途请求用的：`useResource` 发出前记下 epoch，结果回来时再比对一次，不一致就丢弃。`privateCache.clear()` 则把已经落到内存里的私有数据擦掉。两者缺一不可——只清缓存不管在途请求，慢响应仍会把旧账号的数据填回界面。

## 四、资料、首次设密与改密不能混成一个保存按钮

当前 profile 根据 mode 进入资料修改、首次设置或修改密码。同一份表单按 `mode` 分岔成三个出口：

```ts
// src/pages/profile/index.tsx：三个模式共用布局，出口各不相同。
if (isPassword) {
  await api("/me/change-password", "POST", { oldPassword, newPassword: password });
  setSession(null);            // 清会话，强制重新登录
  go("auth");
} else if (isSetup) {
  const auth = await api<Auth>("/me/setup-account", "POST", {
    username: username.trim(),
    password,
  });
  setSession(auth);            // 直接换上新会话
  Taro.navigateBack();
} else {
  const user = await api<User>("/me/profile", "PATCH", {
    nickname: nickname.trim(),
    avatar,
    ...(email.trim() ? { email: email.trim() } : {}),   // 空邮箱不提交
  });
  setUser(user);               // 只更新当前用户对象
}
```

微信会员只有 `canSetCredentials` 明确为真，才允许首次设置用户名密码。改密则调用独立 change-password，成功后清除当前会话并要求重新登录。

三个模式的差别可以列成一张表：

| 模式 | 接口 | 关键资格 | 成功后动作 |
|---|---|---|---|
| 资料修改 | `PATCH /me/profile` | 已登录 | 更新当前用户对象 |
| 首次设密 | `POST /me/setup-account` | `canSetCredentials` 为真 | 换上新会话 |
| 修改密码 | `POST /me/change-password` | 已登录且提供旧密码 | 清会话强制重登 |

前端做第一道校验——密码两次一致、长度达标、设密时必须填用户名——后端继续承担最终验证。前端校验是为少一次无谓往返，不是权限判据。

头像上传走公共 upload 能力，拿到 URL 后再作为资料字段提交。选图成功不等于资料已经保存，用户需要知道这两个动作之间的区别。当前上传失败不自动刷新重放，也不能在资料文章中遗漏这一边界。

## 五、通知里的正文叫 body，不是 content

契约对通知的字段是 title、body、link、isRead 等。当前页面按 body 渲染文本，link 交给统一 openLink。不同模型里相似内容字段不能凭习惯取名。

通知每页十五条，切换全部／未读时回到第一页。单条已读使用 PATCH，全部已读用 read-all，成功后强制补读当前列表。一个函数靠 id 是否存在分岔：

```ts
// src/pages/notifications/index.tsx：不传 id 即“全部已读”，写入后强制重读。
async function mark(id?: number) {
  if (busy) return;
  setBusy(true);
  try {
    await api(
      id ? `/me/notifications/${id}` : "/me/notifications/read-all",
      id ? "PATCH" : "POST",
      id ? { isRead: true } : undefined,
    );
    await result.reload(true);
  } catch (e) {
    toast(e);
  } finally {
    setBusy(false);
  }
}
```

点击详情时，页面同时发起标已读与导航，没有等待标记成功后才打开。这样不会为了一个状态写入阻断阅读，但两者不是事务：标记失败而详情打开是可能状态，不能写成“点击即保证已读”。

link 也不是任意深链都被支持。当前 openLink 识别站内文章与 HTTP(S) 外链，其余类型提示不支持。通知平台若增加新的目的页面，前端还要增加对应路由能力。

## 六、收藏、点赞和历史，共用展示但不共用写语义

collection 用 kind 白名单选择页面，非法参数回到 favorites。它共享 ArticleCard 和读取逻辑，删除动作却依归属不同：收藏删会员关系，点赞调用文章 like DELETE，历史移除记录或确认清空全部。

收藏移除后更新本地 favorite 状态，点赞移除后更新 liked。当前点赞列表删除分支没有直接采用服务端计数响应更新共享 count；因此不能声称所有跨页入口都已经完全同步计数。详情点赞路径会用响应校准，列表路径仍依后续读取确认。

裸数组与 Page 的分页能力也不同。统一 useFeed 能归一展示，不等于后端 likes 自动增加真实分页。文章应把这个契约事实留下，避免教读者用客户端猜一个不存在的 totalPages。

## 七、清理缓存和退出，不应误删作者文本

设置页清理阅读缓存针对可再获取的数据，不删除本机草稿。退出清理会话与私人内存数据，草稿按账号隔离保留。用户的创作输入和服务器读取副本有不同价值。

草稿的隔离写在 key 里——它同时带 API 地址、账号和稿件 ID，换环境、换账号、换稿件都不会串：

```ts
// src/core/drafts.ts：草稿键自带环境与账号，天然隔离。
export const draftKey = (userId: number, id: string) => `befull:draft:${API}:${userId}:${id}`;
```

把这个 key 和私有读缓存的键放在一起看，会发现它们遵循同一条规则：凡是属于某个人的数据，都先把“是谁、在哪台环境”写进标识，而不是靠调用处自觉。这样即使某处忘了判权限，也拿不到别人的内容。

同设备上其他人仍可能通过设备级条件访问存储，所以账号键隔离不是加密保证。若产品引入高敏感草稿，要考虑更严格的本机策略，不能用 userId 字符串替代安全存储。

当前退出还调用后端 logout，其服务器令牌影响应按既有契约理解；客户端本地清理不能证明远端撤销已经成功。失败反馈与再次认证要如实展示。


## 八、用一次退出观察数据边界是否真的成立

会员甲先进入收藏、通知和编辑器，随后退出登录。页面不应该继续允许这些私人动作，未完成读取也不应稍后把甲的结果放回当前游客界面。

接着登录会员乙：公开首页文章可以继续复用，私有收藏应重新按乙的身份读取，甲的本机草稿不进入乙的编辑器。主题仍保持原选择，搜索历史也仍是设备级。这些不同结果，正是前面归属表的实际含义。

如果把退出实现为“清空全部 storage”，主题和创作材料可能一起丢失；若只删除一个 token，不处理缓存与旧请求，又可能留下私人内容。正确策略不是清得越多越好，而是清理与保留都有解释。

## 九、以所有权检查新功能

开发工具看过登录会员入口与主题，本地集成验证资料、关系和账号隔离。完整通知导航与头像上传人工矩阵不应顺带算作已完成。

以后给会员中心增加入口，先写清谁的数据、谁能改、换账号如何处理、退出后留不留。再决定缓存与界面。相关实现继续见 [互动状态]({{LINK:M5-17}}) 与 [本机草稿]({{LINK:M5-22}})。
