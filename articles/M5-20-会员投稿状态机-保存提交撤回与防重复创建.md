# 成为全栈·Taro 小程序篇·会员投稿状态机：保存、提交、撤回与防重复创建

> “提交审核”是用户看到的一个动作，却可能需要两次请求。第二次失败，不能把第一次已经创建的稿件忘掉。

{{IMG:M5-20-封面}}

## 前言：一个按钮背后的两个事实

作者希望会员可以投稿，网站、APP 已经实现，小程序延续同一流程。最容易的写法，是点击提交先创建文章，再调用 submit；全部成功就跳转，任何失败统一显示错误。

问题出在“任何失败”四个字里。草稿已经创建，提交审核失败，用户再点一次，如果客户端仍认为没有稿件，就会再次创建。一个按钮变成两篇文章，后台和作者都会困惑。

这篇围绕当前编辑器的处理展开：先固定身份，再推进状态；明确失败在哪一步，尤其不把不确定结果当成没有发生。

## 一、状态由服务端定义，按钮只表达动作

会员文章有 draft、pending、published 三种常见状态。我的文章提供状态筛选，草稿可以提交，审核中可以撤回，公开作品修改后需要重新审核。

| 当前情境 | 用户动作 | 当前服务端交互 |
|---|---|---|
| 新文章 | 保存 | POST 创建 draft |
| 已有稿件 | 保存 | PUT 固定 ID |
| 草稿 | 提交审核 | 保存后 POST submit |
| 审核中 | 撤回 | PUT status=draft |
| 已发布 | 修改保存 | 确认后保存，按会员规则重新审核 |

客户端不能把 status 随便改成 published 来完成“发布”。权限、状态转换与内容审核仍由后端承担。前端显示按钮，是告诉用户现在可以发起什么，而不是自己决定最终结果。

保存与提交也不是完全同义。保存让作者文本进入云端，提交让它进入审核流程。一个通用绿色“成功”不应该掩盖二者差别。

## 二、新稿件必须先获得稳定 ID

编辑器同时保留展示用 id 和 currentId 引用。创建返回后立即固定引用，并把本机 new 草稿迁移到该 ID：

```ts
// src/pages/editor/index.tsx 的创建完成分支。
currentId.current = String(article.id);
setId(currentId.current);
saveDraft(owner, currentId.current, draft);
deleteDraft(owner, 'new');
creating = false;
```

为什么既有 state 又有 ref？下一步逻辑需要立即知道 ID，不能等下一次 React 渲染。展示状态可以稍后更新，业务链路不能暂时失忆。

随后仅对 draft 调用 submit。若这个请求失败，currentId 已保留，后续保存继续 PUT 同一篇，不再 POST 创建。这个顺序是整个防重复策略的核心。

## 三、请求锁保护本次操作，不保证远端只执行一次

保存入口检查 locked、uncertain 和 uploading，再做 validateDraft。真正开始后设置 locked 引用与 busy 状态，结束在 finally 解锁。

locked 立即阻止重复进入，busy 控制按钮与表单体验。二者解决当前实例里的并发点击，不等于服务端幂等键，也不能阻止另一设备创建相似文章。

统一 API 不对普通网络失败自动重试写入。认证 401 可以在确认未执行业务的前提下刷新重放一次，创建超时却不同：服务器可能已经写完，只是响应没回来。

所以，重复点击与不确定结果必须分开处理。把按钮禁用一秒，并不能解决后者。

## 四、创建结果不确定，先保留稿，再停止盲目创建

当前创建阶段遇到普通异常或 500 以上错误，会进入 uncertain：

```ts
if (creating && (!(e instanceof ApiError) || e.status >= 500)) {
  setUncertain(true);
  setError('创建结果未确认，已保留本机草稿。请先到“我的文章”检查是否已创建，避免重复投稿。');
}
```

这里没有假装回滚远端。客户端不知道远端有没有文章，就保留本机内容、停止继续创建、提示先检查私人列表。

这个策略会让流程多一步，但用户至少不会在不知道发生什么时连续生成稿件。要做到自动精确恢复，需要服务器支持可确认的幂等创建标识与查询规则，本轮没有增补这种契约。

还有一个具体边界：创建返回 ID 后，本机迁移如果抛错，也可能进入不确定提示，即使远端已知成功。当前代码偏保守地停止后续创建。文章应解释这是防重复选择，而非所有异常都能精确分类。

## 五、保存前看云端更新时间，只是一层提醒

已有稿件保存前重新 GET，比较 latest.updatedAt 与 baseline。不同则弹窗，让作者决定覆盖或取消；已发布还会确认重新审核的影响。

这能发现另一设备或后台修改，但不是服务端 CAS。GET 与 PUT 之间，仍可能有人继续改文章。我们没有 If-Match、ETag 或版本条件写入，不能把提醒称为原子冲突控制。

对于教学项目，先提供明确覆盖选择，比静默丢数据更好。若产品走向多人高频协作，需要后端条件写入与冲突返回，届时再讨论字段级合并。

取消覆盖不会删除本机草稿，作者仍能保存或比较内容。错误也不会自动清空输入，这才让冲突提醒有真正可用的下一步。

## 六、第二步成功之后，才清理本机恢复材料

保存或提交链路成功，dirty 置 false，删除当前 ID 本机草稿，关闭离开提醒，并根据状态显示“保存到服务器”或“等待审核”。

如果提交失败，后续清理不会执行，因此本机内容继续可恢复，ID 也继续可用。用户看到的错误应该指向继续同稿，而不是重新写一篇。

这条策略还与上传协调：图片没有返回 URL 前，服务端保存与提交禁用。否则文章很可能保存旧正文，上传完成后又插入了新图片，产生“明明点了提交却没有图”的时间差。

## 七、撤回与删除是另一类明确影响动作

我的文章对 submit、withdraw、delete 都先确认。撤回更新状态，不复制新稿；删除按资源 ID 请求，提示保留需要的内容。服务器检查所有权，客户端成功后强制刷新私人列表。

已发布文章被会员修改，服务端重新审核规则会影响公开可见性，保存前的确认必须讲清楚。仅写“保存成功”而不说明审核变化，会让作者误以为线上仍立即显示新版本。

未发布预览使用认证读取，分享配置退回首页，也不进入公开互动和阅读上报。创作状态会一路影响阅读页，不能只在列表贴一个标签。


## 把两个失败位置放进同一张操作记录

一次提交可以记成：本机文本保留，POST 创建开始，返回稿件 ID，迁移本机键，POST submit，返回审核状态。每一步都比“提交中”更具体。

如果失败在 submit，已有 ID 是继续工作的起点；如果失败在创建响应，连 ID 都不知道，需要先查私人列表；如果失败在本机迁移，远端文章可能已知存在，但恢复材料写入没有完成。三个失败不能用“重新创建即可”处理。

读者可以在本地临时后端模拟这些时间点，观察请求方法与资源数量。关键断言是第二次操作是否仍指向同一 ID，页面输入是否保留，以及 uncertain 是否真的挡住再次 POST。只看 toast 成功或失败不够。

### 云端与本机是两份不同证据

本机文本能够恢复，不证明远端状态；远端 pending 能证明进入审核，不证明本机最新输入都已提交。上传协调和请求开始时的 payload 决定这次服务器拿到哪一版。

当前保存期间表单禁用，减少提交快照与继续编辑交错；上传期间则允许输入，却禁用服务端动作。两种锁定策略分别服务不同阶段，不能简化成一律锁整页。

### 状态按钮也需要负面场景

草稿显示提交，审核中显示撤回，已发布保存前提醒重新审核。还应检查资源在打开后被后台改状态的情况，不能只根据页面最初标签操作。

当前保存前 GET 不只比较更新时间，也观察 latest.status；最终后端继续验证。我的文章列表点击动作后刷新，避免旧标签长期停留，但它没有把全部操作转换成实时推送。

这套做法服务单人创作与审核。若未来多端频繁同时编辑，应该优先增强服务器条件写入，而不是在前端增加更多确认弹窗来掩盖缺少原子判断。知道当前方案保护到了哪里，才能正确安排下一步成本。

## 八、验证固定 ID，而不是只看成功提示

真实本地后端集成验证草稿创建、固定 ID 更新、提交和撤回；开发工具也实际操作过输入、预览、保存后提交，并在本机数据库检查没有重复创建。

失败时序还应补充测试：创建成功提交失败，第二次仍用原 ID；创建响应丢失，uncertain 阻止重复 POST；云端变化弹窗取消，输入不丢。这些建议不能冒充全部既有 UI 证据。
