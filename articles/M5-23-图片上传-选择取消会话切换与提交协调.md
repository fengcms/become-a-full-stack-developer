# 成为全栈·Taro 小程序篇·图片上传：选择、取消、会话切换与提交协调

> 上传不是一个 Promise 而已。用户选择、平台取消、账号变化、文件返回与正文提交，共同决定图片最后属于哪份内容。

{{IMG:M5-23-封面}}

## 前言：拿到地址之前，文章应该保存哪一版

移动投稿很常见的一条路径是：写到一半，选一张图片，继续输入，然后提交。若保存与上传各自运行，保存可能先完成，图片 URL 稍后才插入，用户以为提交了有图文章，后台实际只有旧正文。

还有一个更敏感的情况：A 会员打开媒体选择后退出，B 登录，选图结果回来。如果直接读取当前 token 上传，就可能把 A 的选择交给 B 的会话。

当前实现因此同时处理上传流程与编辑协调。它仍有明确限制：没有自动认证刷新重传，也没有声明完整真机相册矩阵已通过。这篇把这两个层面一起讲。

## 一、选择文件是第一阶段，不是已经上传

uploadImage 先确认会话，捕获 epoch，再使用平台媒体选择：

```ts
const generation = sessionEpoch();
const choice = await Taro.chooseMedia({
  count: 1, mediaType: ['image'], sizeType: ['compressed']
});
if (sessionEpoch() !== generation) throw new Error('账号已切换');
```

一次选择一张、请求压缩形式，是当前产品范围。压缩选项并不保证文件一定小于限制，也不保证所有图片保留相同清晰度，选定后仍要检查大小。

用户关闭选择界面属于取消，EditorForm 与头像页当前通过错误信息中的 cancel 区分，不展示上传错误。这个判断依赖平台错误形式，不是一个正式封装好的取消类型。若未来发现其他格式，要补分类，不能把所有异常都吞掉。

## 二、文件限制前置，服务端验证仍保留

选中后检查 tempFiles[0] 存在，文件超过十兆字节则拒绝。之后使用 tempFilePath 发 multipart 上传，字段名为 file。

```ts
if (file.size > 10 * 1024 * 1024)
  throw new Error('图片不能超过 10MB');
const r = await Taro.uploadFile({
  url: API + '/upload', filePath: file.tempFilePath, name: 'file',
  header: { Authorization: `Bearer ${session()!.accessToken}` }
});
```

这是客户端体验检查，不是安全验证。客户端没有检查文件魔数，也不能保证修改后的请求仍遵守大小。最终类型、大小与权限必须由后端控制。

限制口径按字节，不能拿压缩前图片尺寸推断一定可上传。文章也不把 chooseMedia 的 compressed 当成免费无限存储或质量保证。

## 三、uploadFile 返回字符串，要单独拆信封

普通请求由 Taro.request 泛型消费 JSON，uploadFile 的 data 则需要 JSON.parse。当前上传解析后检查 HTTP 状态和业务 code，返回 data.url。

| 阶段 | 可能结果 | 当前界面含义 |
|---|---|---|
| 选择 | 取消 | 不当作失败提示 |
| 文件检查 | 缺文件或过大 | 停止上传，保留稿件 |
| HTTP 上传 | 网络失败、认证错误 | 显示错误，允许后续人工重试 |
| 信封解析 | 服务端成功返回 URL | 更新封面或插入 Markdown |
| 返回后身份检查 | epoch 改变 | 拒绝旧身份结果 |

返回体若不是合法 JSON，当前会抛普通解析异常，经页面错误出口显示；没有独立友好的“上传响应异常”分类。这个边界应留下，不能在文章里替现有代码补上一套不存在的转换。

## 四、为什么检查两次身份变化

选择之后检查，阻止旧选择借新账号上传；上传之后再检查，阻止旧身份结果更新当前页面。请求发出前后一共跨了不同异步边界，两次检查各有价值。

但上传中途账号变化不会取消底层网络，服务器可能已经接收文件。epoch 能拒绝 UI 采用，不能撤销远端资源。这个区别与缓存一样：客户端结果资格和服务器执行事实不同。

因此本次没有宣称上传具有自动清理孤儿文件的完整生命周期。文件上传成功、正文最终没保存，资源是否清理属于后端存储治理，需要另行定义。

## 五、父页需要知道上传还没结束

EditorForm 同时维护本地 uploading，并通过 onUploading 通知父编辑器。父页在 uploading 时拒绝 save，保存文章与提交审核按钮禁用。

这解决的是“地址尚未出现就提交”。正文输入仍可继续，上传完成用 latest draft 插入图片；封面模式则只更新 coverImage。操作完成或失败在 finally 通知结束。

这样没有把整个页面锁死，却让资源依赖动作等待必要前提。若未来支持多张并发，需要把布尔状态改成更明确的任务集合或计数，避免一张完成就提前允许提交。当前一次一张，不宣称批量上传队列。

页面预览切换会改变表单挂载状态，上传回调如何处理组件中断仍需要对应人工验收。代码里有结束回调，不能仅据此推广到所有离开场景。

## 六、上传不自动刷新，是一个必须公开的差异

普通 API 在符合条件的 401 后单飞刷新并重放一次。uploadImage 当前直接调用 uploadFile，没有接入这个逻辑，所以令牌过期可能上传失败。

本轮选择显示错误，用户在会话刷新后重试，而非自动重传文件。原因不只是少写代码：重传需要确认失败是否发生于认证之前、临时文件是否仍可用、当前身份是否相同、服务端有没有已保存资源。

未来要扩展，应为上传设计清楚的认证重放边界，而不是在 catch 里无条件再上传一次。网络异常更不应该自动重传，结果可能不确定。

## 七、图片进入正文与进入资料，各有第二步

正文插图在拿到 URL 后拼入 Markdown，封面更新草稿字段；头像则更新本地表单，普通资料保存才 PATCH 到服务端。

所以“上传成功”不等于“文章已保存”，更不等于“头像资料已更新”。当前这些动作有各自按钮与反馈，文章要帮助读者理解中间状态，而不是用一个 toast 覆盖全流程。

移除封面只把草稿地址清空，不等于删除存储中的文件。后端资源删除与引用关系不在当前客户端动作里，不能从一个移除按钮推断实现了文件回收。


## 用“继续输入”场景检查异步结果合并

作者开始上传时正文是甲，等待中输入成甲加乙。上传返回后，正确结果应是甲加乙再插入图片，而不是回到甲加图片。

EditorForm 的 latest 引用就是为这个顺序服务。保存草稿拥有者仍在父页，上传回调只产生 patch，不接管整份旧 Draft。它也避免封面上传覆盖等待期间新改的标题和标签。

不过，图片插入位置取当前保存的 cursor，而不是一份独立的上传开始选区。等待期间如果光标变化，结果会插到更新后位置。这是当前语义，应通过人工场景确认用户是否理解；不能把它写成始终插回原位置。

### 不确定上传与不确定创建的区别

创建文章会产生作者可在“我的文章”检查的资源，当前有明确 uncertain 处理。图片上传结果丢失时，客户端没有可用资源列表去精确认领，也不自动重传。

因此，失败保留文本是必要的，但它不能回收远端可能已经保存的图片。更完整的方案可能需要上传任务标识、资源查询或后端过期清理；这些都不在当前客户端承诺。

### 用户取消与平台拒绝也要区分

取消表示用户不继续选择；权限拒绝、找不到文件和网络错误则需要不同修正路径。当前只做 cancel 字符串兜底分类，后续要依据实际平台返回补更稳定类型与文案。

错误记录可以保留阶段与状态码，不必输出完整文件路径或访问凭据。诊断有助于复现，前提是它不会把私人资源和令牌变成文档素材。

如果本期继续加强上传，先跑真实选择、拒绝和弱网矩阵，再决定重试策略，比先加一个“重试三次”的参数更安全。文件写入与正文写入的时间顺序，应始终是验收的核心。

## 八、验收不要用接口脚本替代平台选择

本轮构建通过，编辑器交互经过工具操作，真实相册上传与用户照片没有逐项人工验收。集成测试也没有证明微信媒体权限和真机临时文件行为。

后续矩阵应包括取消、超限、网络中断、认证过期、选择期间换人、上传时继续输入、上传未结束点击提交，以及成功后再保存。每项都观察文本是否保留、归属是否正确、错误能否修正。

更多内容归属见 [编辑器]({{LINK:M5-21}}) 与 [本机草稿]({{LINK:M5-22}})。上传做得可靠，是因为我们知道每个“完成”到底完成到哪一步。
