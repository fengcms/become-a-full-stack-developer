# 成为全栈·Taro 小程序篇·把 APP 原型落到小程序：图标、Design Token 与深色模式

> 原型给出的不只是几张漂亮页面。颜色、图标、间距和状态共同构成产品语言，换一个运行平台也不该随手换掉。

{{IMG:M5-10-封面}}

## 前言：功能相同，视觉也要说同一种话

做 Flutter APP 时，作者明确指出过一个问题：页面虽然能用，UI 却没有严格跟随确认过的原型。这个反馈给小程序开发立下了很清楚的前提：参考 APP 功能，也继承已经确认的设计，而不是重新自由发挥。

白色或极浅蓝背景，深色但不纯黑的文字，克制的蓝色点缀；图标沿用原型；文章页把正文放在最重要的位置。深色模式也不是临时盖一层滤镜。

这篇讲的不是重新设计一套审美，而是如何把这套已有设计翻译到 Taro：让颜色有语义，让图标有来源，让平台原生区域和页面内容一起变化。

## 一、先确定设计资产的来源

现有原型位于 `docs/flutter-app/prototype/02-高保真可交互原型.html`，Flutter 中的图标路径集中在 `flutter-app/lib/shared/prototype_icons.dart`。

小程序使用这些路径生成 PNG 资源，分别提供 light、dark、active 版本，而不是从另一套图标库挑选名字相似的图案。输出尺寸为 72×72，组件显示尺寸由样式控制。

这种转换保留了线条与轮廓来源，也兼顾原生 Tab 配置需要图片路径的使用方式。资源不是手工截屏，因此重新生成时仍有可追踪的输入。

但“同一个图标”不意味着任何场景都用同一种颜色。普通状态、深色状态和选中状态分别服务不同层级。设计资产复用的对象是形状与语义，资源形式可以随平台改变。

## 二、颜色命名要说明用途

`app.scss` 的页面根节点集中定义了颜色变量：

```scss
/* 从当前样式中提取的关键变量。 */
.screen {
  --bg: #f7fafd;
  --surface: #fff;
  --line: #e9eff5;
  --text: #34465a;
  --brand: #3277b5;
}
.screen.dark {
  --bg: #121820;
  --surface: #1a222c;
  --line: #2e3a46;
  --text: #c6d2de;
  --brand: #7fb6e4;
}
```

为什么不叫 `blue1`、`blue2`？因为组件需要知道“这是品牌操作色”，而不是“这是第几号蓝”。当背景变深时，品牌色要保持可辨识，正文也要重新确定亮度。颜色的职责稳定，具体值可以随主题切换。

当前还区分标题、次要文字、凹陷区域、浅色强调和危险操作。代码块、评论回复楼层、输入框不能都使用同一种底色，否则深色页面容易变成一片无法分层的灰。

这些变量不是覆盖所有设计知识的完整平台。字号与间距目前仍主要集中在样式类中，没有单独建立一个可跨语言自动生成的 Token 包。文章应如实描述当前范围，而不是把几组变量说成庞大设计系统。

## 三、主题有三个选择，实际显示只有两个结果

用户可以选择 light、dark、system。前两者固定主题，system 跟随系统变化。当前结果由一个快照函数计算：

```ts
// src/core/theme.ts
const snapshot = () =>
  mode === 'system' ? (systemDark ? 'dark' : 'light') : mode;
```

这个区别很重要。设置页应展示用户选择的 mode；页面需要的是计算后的实际主题。如果直接把当前深色结果保存为用户偏好，跟随系统就会悄悄变成固定深色。

主题模块使用 `useSyncExternalStore` 通知组件。`Screen` 根据结果加主题类，`Icon` 根据结果选资源：

```tsx
<Image
  className="icon"
  src={`/assets/icons/${name}-${active ? 'active' : theme}.png`}
/>
```

这段代码保护的是页面图标的一致性。原生 Tab 的图标仍由静态配置指定，当前没有动态替换其 light/dark 图片路径。原生 Tab 文字和背景会更新，但不能因此声称所有原生图标都已动态换色。

## 四、页面之外的颜色，也要有人负责

只改 `.screen.dark`，顶部导航栏与底部原生 Tab 仍可能是亮色。项目的 `applyTheme` 同时调用导航栏颜色、页面背景和 Tab 样式 API。

页面显示时再次应用主题，系统主题改变时也会更新。这样，用户从设置返回文章，不依赖文章页重新挂载才能获得正确原生颜色。

平台 API 失败在这里被捕获，避免某个不适用的原生区域让整个页面崩溃。但捕获不是“所有平台行为都验证通过”。视觉验收仍应观察标题栏、Tab、键盘和正文，而不能只检查根节点类名。

| 区域 | 当前主题来源 | 需要观察什么 |
|---|---|---|
| 页面卡片与正文 | CSS 语义变量 | 分层、正文可读性、危险提示 |
| 页面图标 | 实际主题与 active | 轮廓清晰、状态颜色稳定 |
| 导航栏 | applyTheme | 返回与标题是否可见 |
| 原生 Tab | 样式 API 加静态图标 | 文字与图标是否协调 |
| 原生输入交互 | 平台行为 | 设备上的键盘与遮挡情况 |

## 五、原型还原也包括空隙与状态

文章正文结束后，互动条使用上方间距和分隔线内边距；评论输入区与已有楼层之间也保留空间。这些并不是可有可无的装饰。用户需要知道“正文已经结束”“这里是可操作区域”“下面是别人的讨论”。

加载、空内容和请求错误同样属于页面设计。没有文章时不能只剩一张空白卡片；请求失败时要显示可重试动作。当前基础 State 组件集中处理这些展示，但具体页面仍要提供正确状态。

开发工具里已观察过深色主题切换与文章阅读。真机长文、系统切换时的完整视觉矩阵不在这次记录中，我不会把工具里的成功推广成所有设备表现一致。


## 用页面矩阵代替“看起来差不多”

原型验收最容易被首页吸走注意力。首页已经清爽，编辑器输入框却可能没有深色背景；文章标题正常，通知正文却可能沿用默认黑色；空状态图标又可能来自另一套风格。

我会把首页、文章、评论、认证、会员、通知、编辑、设置列成行，把浅色、深色、加载、空内容和错误列成列。不是要求每个格子都制作一张新设计，而是明确哪些状态有实际意义，再逐个观察。

这个矩阵还能揭示某些 Token 是否职责混乱。如果次要文字和危险提示都借用品牌色，读者就无法区分“可以点击”和“发生问题”。如果卡片边界只依赖阴影，深色时又可能看不见层次。变量的价值要在这些场景中检验。

### 图标和控件语义要同时还原

原型上的收藏图标说明了操作含义，实际 Button 则说明它如何被触发。只复制图形、不处理可点区域和禁用状态，仍不是完整还原。

当前关键操作使用原生 Button，并通过统一样式移除默认外观。选中图标不应成为唯一反馈，按钮文字也有“已赞”“已收藏”等变化。这样，颜色看不清时用户仍能理解状态。

字号和间距也要考虑正文密度。技术文章中，标题层级、表格和代码已经带来大量信息，外围卡片没必要不断加边框与阴影。白底不是把所有内容都摊平，而是依靠克制的边线、语义背景和留白建立秩序。

### 深色模式不是反相算法

把所有亮色取反，会让品牌蓝、代码高亮和图片出现不可预测效果。当前主题为背景、文字和操作色分别选择值，原图保持原图，代码高亮则使用当前定义的颜色。

这也留下一个需要人工关注的点：高亮颜色不是两套完全独立的主题调色板。是否在具体深色设备上足够可读，应通过长代码样本检查，不能只因背景变黑就算验收结束。

设计迁移的判断因此有两层：是否忠于确认过的视觉语言，是否适应当前平台与真实内容。两层都成立，才值得称为原型落地；截图像原型只是其中一份证据。

## 六、让设计要求能够持续检查

我建议在后续修改中使用同一份页面矩阵：亮色与深色、内容与空状态、登录与游客、正常与错误。新增按钮先选语义色，新增图标先核对原型来源。

这样，原型不只是开工时展示一次的图片，而是能约束后续实现的参照。下一篇看 [四 Tab 与页面栈]({{LINK:M5-11}})，设计语言会继续遇到平台生命周期的实际边界。
