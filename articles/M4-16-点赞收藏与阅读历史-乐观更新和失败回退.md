# 成为全栈·Flutter App 篇·点赞、收藏与阅读历史：乐观更新和失败回退

点赞、收藏和阅读历史都出现在文章页或会员中心，很容易被合成一个 `isActive`。可它们一个影响公共计数，一个是个人集合，一个是带时间语义的记录；网络失败后如何恢复也不一样。

这篇结合 `ReactionStore` 和 `FavoriteIndex`，把真实接口限制、乐观更新、并发扫描和账号切换后的缓存失效讲清楚。

{{IMG:M4-16-封面}}

## 三种状态归属不同

点赞通常表达用户与文章的一次互动，并可能影响聚合计数；收藏表示个人稍后再读的集合；阅读历史是带时间语义的私有记录。它们可能共享 ArticleCard，却不共享同一个 API 和生命周期。

| 状态 | 事实来源 | 特别限制 |
|---|---|---|
| 点赞 | 写接口响应及用户互动记录 | 失败需回退并校准计数 |
| 收藏 | 会员收藏列表/写接口 | 后端无单篇收藏状态接口时需索引扫描 |
| 阅读历史 | 私人阅读记录 | 不是文章浏览量 |

## 乐观更新改善响应，但不等于成功

点击收藏后可以立刻切换图标，再发送请求；成功后以服务器结果确认，失败就恢复原值并提示。多个快速点击需锁定或按请求序列避免旧响应反向覆盖最新动作。

```text
旧状态 false → 乐观显示 true → API 成功确认
                               ↘ API 失败恢复 false
```

点赞计数若服务端返回权威新值，应校准所有共享卡片；只本地 `count + 1` 会在重试、重复点击和并发下漂移。写请求不可盲目自动重发。

## 收藏状态的查询成本不能藏起来

当前契约没有单篇收藏状态查询时，客户端可能需要逐页建立收藏索引。只扫描前若干页无法准确判断“不在收藏中”；必须标记索引是否完整。项目对已知命中复用结果，并发扫描共用任务，收藏变更或账号切换后重置索引。

这意味着首次状态确认可能有成本。不能为了按钮立即变色就展示不准确状态，也不能声称后端支持批量状态接口。

## 账号切换要隔离私有列表

收藏、点赞记录和阅读历史属于账号。私有缓存仅在当前会话内存中复用，key 包含环境、用户和 epoch；切换账号后旧响应被丢弃。公开文章缓存可以继续保留，不应与会员列表一起写入磁盘。

## 乐观状态应保留回滚快照

快速连续点击可能出现两个相反请求并发。最简单的保护是同一资源在一次 mutation 确认前禁用按钮；若产品允许连续切换，则需对动作排序，只有最新动作的响应能更新 UI。

```text
previous = state[articleId]
state[articleId] = desiredValue
try:
  result = await api.setReaction(articleId, desiredValue)
  if requestVersion is current:
    state[articleId] = result.userReaction
    count = result.likeCount
catch:
  if requestVersion is current:
    state[articleId] = previous
  show retryable failure
```

这段伪代码强调“快照 + 版本”而非具体项目 API。收藏状态没有单篇状态接口时，加载索引不能只返回真假，还要记录 `isComplete`；扫描尚未完成时，不能把“未知”映射成 false。

## 计数、状态和会员列表由失效标签重新汇合

一次点赞 mutation 成功后，文章 likeCount、当前用户 liked 状态和“我的点赞”列表都可能变更。Repository 依据 mutation tags 使相关读取失效，API 响应再校准 ReactionStore。缓存策略把私有 reaction 与公开 article 分开，避免为更新个人状态清掉整篇正文。

收藏索引是另一条路径：逐页扫描期间，已经命中的 ID 可立即确认收藏；没命中只有在扫描完毕后才表示 false。收藏变更会重置索引，防止之前的完整扫描在写入后仍被当成最新结果。首次访问成本来自契约缺少单篇状态接口，而不是 Flutter 的状态管理性能问题。

## 收藏列表扫描不是无限拉全量

收藏索引每次只加载一页，并在找到目标 ID、扫描到服务端末页或遇到错误时停止/继续。多个卡片并发检查时共享 `_scan` Future；否则一屏十张卡会同时重复请求第一页。索引上的 `_version` 在收藏变化时递增，旧分页返回后抛出 superseded 并重扫，避免用写入前数据得出新结论。

若阅读历史是分页列表，用户点开文章后应由历史接口记录，不能客户端自行把文章 append 成“已完成阅读”；有进度字段时保持原 API 语义。隐私清理与公开缓存清理也分开：退出清除 private reaction/cache，公开文章内容仍可显示。


## 贴着工程代码读实现

下面这段节选自 `flutter-app/lib/features/data/reaction_store.dart 第 10–85 行`（保留原始实现；为突出主线省略了文件其余部分）。读代码时可以顺着调用链确认：快速连点后让较早请求失败，比较当前状态与请求发出时快照。沿着调用链读下去，才能看清这个选择如何影响实际页面。

```dart
class ReactionStore {
  ReactionStore({
    required this.cache,
    required this.key,
    required this.policy,
    required this.resourceTags,
    required this.favoriteOverrides,
  });
  final DataCache cache;
  final String Function(String, Map<String, dynamic>, {bool private}) key;
  final CachePolicy? Function(String) policy;
  final Set<String> Function(String) resourceTags;
  final Map<int, (bool, DateTime)> favoriteOverrides;
  final reactions = <int, Map<String, dynamic>>{};
  final events = StreamController<int>.broadcast();
  // local=false 表示读取基线，只更新展示值而不续期互动状态缓存。
  void set(
    int id, {
    bool? liked,
    int? count,
    bool? favorite,
    bool local = true,
  }) {
    final old = reactions[id] ?? {};
    if (reactions.length >= CacheLimits.reactions &&
        !reactions.containsKey(id)) {
      reactions.remove(reactions.keys.first);
    }
    reactions[id] = {
      ...old,
      'savedAt': DateTime.now().millisecondsSinceEpoch,
      'liked': ?liked,
      'likeCount': ?count,
      'favorite': ?favorite,
    };
    // 点赞状态与数量必须成对种入，防止单独更新计数破坏状态一致性。
    if (local && liked != null && count != null) {
      final path = Endpoints.likeStatus(id);
      cache.seed(
        key(path, const {}, private: true),
        {'liked': liked, 'likeCount': count},
        policy(path)!,
        resourceTags(path),
      );
    }
    if (favoriteOverrides.length >= CacheLimits.favoriteOverrides &&
        !favoriteOverrides.containsKey(id)) {
      favoriteOverrides.remove(favoriteOverrides.keys.first);
    }
    if (local && favorite != null) {
      favoriteOverrides[id] = (favorite, DateTime.now());
    }
    // 仅修改具有文章标题的摘要，避免误改评论等同名 id 对象。
    if (count != null) {
      dynamic patch(dynamic value) {
        if (value is List) return value.map(patch).toList();
        if (value is Map) {
          return {
            for (final e in value.entries)
              e.key:
                  e.key == 'likeCount' &&
                      value['id'] == id &&
                      value.containsKey('title')
                  ? count
                  : patch(e.value),
          };
        }
        return value;
      }

      cache.patch(patch);
    }
    // 所有页面订阅同一文章事件，使详情与列表立即反映乐观结果。
    events.add(id);
  }
}
```

## 把容易出错的路径走一遍

我会用这个场景做一次可复现排查：**乐观更新失败时回滚整个列表覆盖了另一条并发互动**。先快速连点后让较早请求失败，比较当前状态与请求发出时快照；如果把问题定位在“失败清空状态”，修正方向是“只回滚该操作拥有的字段/版本，并同步触发跨页文章事件”。最后再验证正常路径没有退化，并把边界条件留在自动化检查里。

| 方案比较 | 简化做法 | 当前实现/推荐做法 |
|---|---|---|
| 本文核心选择 | 失败清空状态 | 定向恢复与共享事件 |
| 错误处理 | 失败后清空或静默忽略 | 保留可恢复状态，给出明确反馈 |
| 验证方式 | 只检查成功结果 | 注入边界条件并检查回归 |

| 排错步骤 | 要观察什么 | 通过条件 |
|---|---|---|
| 复现 | 乐观更新失败时回滚整个列表覆盖了另一条并发互动 | 可以稳定触发或明确构造该输入 |
| 定位 | 快速连点后让较早请求失败，比较当前状态与请求发出时快照 | 找到责任层和状态归属 |
| 修正 | 只回滚该操作拥有的字段/版本，并同步触发跨页文章事件 | 失败不污染后续页面或账号 |

## 小结

相同视觉控件可能对应不同业务状态。为点赞、收藏、阅读历史分别定义事实来源、写入语义和缓存范围；乐观更新必须有回退，聚合计数以服务端校准，无法完整扫描的收藏索引不能假装精确。
