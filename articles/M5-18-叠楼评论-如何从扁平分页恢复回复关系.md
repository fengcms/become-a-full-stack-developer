# 成为全栈·Taro 小程序篇·叠楼评论：如何从扁平分页恢复回复关系

> 接口返回扁平数组，界面仍可以叠楼。但分页缺父楼、审核与删除，会让“完整评论树”成为一个需要谨慎使用的说法。

{{IMG:M5-18-封面}}

## 前言：回复 #x，读者不知道在跟谁说话

网站早期评论按一条条列表展示，回复只写“回复 #x”。作者指出这不友好，希望改成叠楼形式。APP 后续也要求与原型一致，小程序自然不能退回原来的表达。

后端没有返回一棵预先嵌套好的评论树，而是分页 Comment 列表，包含 id、parentId、userName 等信息。我们依靠关系恢复讨论组，再用有限层级展示楼层。

这篇的关键判断是：接口已有父子关系，足够支持叠楼；但当前只拿到部分分页，界面不能假装掌握所有祖先和所有回复。

## 一、数据模型保留关系，界面选择层级

当前每次读取二十条评论，合并时按 ID 去重。groupComments 为已加载评论建索引，沿 parentId 向上找根，再把同根回复组成一组。

```ts
// src/core/comments.ts 的向上追溯节选。
const seen = new Set([root]);
while (at.parentId && !seen.has(at.parentId)) {
  root = at.parentId;
  seen.add(root);
  const parent = index.get(root);
  if (!parent) break;
  at = parent;
}
```

这里使用 seen 防止坏数据循环把渲染卡住。它只是终止追溯，不是修复服务端循环关系的算法。正常业务仍应由后端约束 parentId 属于正确文章与有效关系。

展示采用主楼加浅色回复区，不把每一层继续横向缩进。手机宽度有限，十层嵌套很容易把正文挤成一列。关系可以多级，视觉层级保持克制，两者不必完全相同。

## 二、父楼没加载，不应丢弃回复

分页可能先拿到回复，而祖先不在当前页；审核或删除也可能让父楼不可见。当前分组保留这种回复，root 缺失时显示“前面的评论尚未加载或已不可见”。

| 情况 | 当前展示 | 不应编造的内容 |
|---|---|---|
| 主楼与回复都在 | 主楼加楼内回复 | 无需额外猜测 |
| 父楼不在当前集合 | 缺楼提示加现有回复 | 不造作者、原文或时间 |
| 回复的直接父评论可见 | 显示回复对象姓名 | 不只写数字 ID |
| 父评论不可见 | “前面的读者”兜底 | 不断言一定被删除 |

后续页加载后重新分组，关系可以变得更完整。当前 group 数量和 replies 数量只代表已加载数据，不能被当作全站或全帖总楼层数。

这也是一个产品文案判断：我们不知道是未加载、审核还是删除，就把不确定范围说出来。直接写“该评论已删除”，可能把分页现象错误描述成管理行为。

## 三、把回复折叠成可继续展开的区域

每组默认显示前三条回复，更多回复用“展开 N 条回复”，展开后可以收起。N 由当前已加载组计算，不承诺服务器上全部剩余回复。

回复按 createdAt 排序，展示姓名、日期、文本与回复动作。Text 直接显示评论内容，没有把用户评论交给 Markdown HTML 渲染。评论是讨论文本，不继承文章富文本的全部能力。

外层楼与回复区的边界、缩进和留白来自原型的叠楼语言。输入框与已有楼层之间保留 margin，避免提交区域和别人发言粘成一块。

这个视觉设计不要求修改冻结接口。只要父子关系字段成立，客户端就能选择更友好的阅读组织；若未来需要服务器一次返回整棵树，则是新的性能与分页契约问题。

## 四、回复动作同时设置对象与焦点

点击回复先检查会话，再保存目标 Comment，设置 focus，并滚到 composer。输入区显示“回复某某”，可以取消目标回到主楼评论。

提交 body 包含 trim 后内容与 `parentId: reply?.id || null`。直接回复谁，就提交谁的 ID；展示时追溯到组根，不代表写入时把所有 parentId 改成根楼。

账号变化清空 content 和 reply，防止 A 的未发送文本在 B 会话下继续提交。文章页还以文章和用户组合为 Comments key，帮助重建对应讨论状态。

Screen 点击外部收起键盘，composer 阻止冒泡，Textarea 用 onFocus 与 onBlur 更新 focus。完整设备键盘行为需要真机观察，不能仅凭代码分支宣布没有任何遮挡。

## 五、发送成功，不总意味着立即公开

后端返回评论状态。approved 显示发表成功；待审核显示待审核；rejected 提示修改，并保留当前输入供修正。

发送后重新读取评论，而不是无条件把返回对象塞入公开列表。审核规则决定什么可公开，前端不能为了“乐观显示”绕开它。评论与点赞不同，公开可见状态不是只由点击决定。

当前发送有 sending 状态防重复触发，但普通网络失败不自动重试 POST。结果不确定时，用户需要结合后续读取判断，客户端不能假设失败就没有创建。

## 六、删除自己评论也可能影响别人回复

本人评论显示删除入口，先确认“关联回复也会被删除”。服务端负责权限与级联，客户端成功后重读列表，不自行猜整棵关系全部删除范围。

这个提示很重要：用户看到的是自己一条文本，动作影响可能是一串回复。删除按钮隐藏于他人评论只是体验，后端仍要拒绝越权请求。

真实本地后端集成验证过评论回复与级联删除、不同账号权限。逻辑测试覆盖分组与循环保护。它们不等于所有分页视觉都已人工查看。

## 七、用缺数据测试，而不只用整齐样例

建议回归时准备主楼不在第一页、回复父楼在后续页、三级关系、重复 ID、超过三条回复与循环输入。观察是否丢回复、是否重复显示、展开数量是否诚实。

审核与删除还需要独立样本：待审核不强行公开，拒绝保留修正机会，删除确认清楚，刷新后的楼层关系重新生成。网络失败应与空讨论区分，而不是清空后告诉用户“暂时没有评论”。

当前分页与分组策略在小型内容站足够直接。评论规模扩大时，可考虑按主楼分页与服务器聚合，但它会改变接口含义，应先有规模证据再推进。

## 八、楼层友好，依赖的是不伪造关系

叠楼不只是缩进和背景色。姓名、直接回复对象、缺楼提示、审核状态和删除影响共同决定读者是否理解讨论。

相关数据边界见 [会员中心]({{LINK:M5-19}})，接下来进入 [投稿状态机]({{LINK:M5-20}})。展示可以更丰富，前提是我们仍忠于接口已经告诉我们的事实。
