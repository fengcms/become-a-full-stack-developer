# 成为全栈·Taro 小程序篇·叠楼评论：如何从扁平分页恢复回复关系

> 接口返回扁平数组，界面仍可以叠楼。但分页缺父楼、审核与删除，会让“完整评论树”成为一个需要谨慎使用的说法。

{{IMG:M5-18-封面}}

## 前言：回复 #x，读者不知道在跟谁说话

网站早期评论按一条条列表展示，回复只写“回复 #x”。作者指出这不友好，希望改成叠楼形式。APP 后续也要求与原型一致，小程序自然不能退回原来的表达。

后端没有返回一棵预先嵌套好的评论树，而是分页 Comment 列表，包含 id、parentId、userName 等信息。我们依靠关系恢复讨论组，再用有限层级展示楼层。

这篇的关键判断是：接口已有父子关系，足够支持叠楼；但当前只拿到部分分页，界面不能假装掌握所有祖先和所有回复。

## 数据模型保留关系，界面选择层级

当前每次读取二十条评论，合并时按 ID 去重。groupComments 为已加载评论建索引，沿 parentId 向上找根，再把同根回复组成一组。

```ts
// src/core/comments.ts（节选）：先建索引，再沿 parentId 追根。
export function groupComments(items: Comment[]) {
  const index = new Map(items.map((c) => [c.id, c])),
    groups = new Map<number, Comment[]>();
  for (const comment of items) {
    let root = comment.id,
      at = comment;
    const seen = new Set([root]);
    while (at.parentId && !seen.has(at.parentId)) {
      root = at.parentId;
      seen.add(root);
      const parent = index.get(root);
      if (!parent) break;
      at = parent;
    }
    const group = groups.get(root) || [];
    group.push(comment);
    groups.set(root, group);
  }
  return [...groups.entries()].map(([id, list]) => ({
    id,
    root: index.get(id),
    replies: list.filter((c) => c.id !== id).sort((a, b) => a.createdAt.localeCompare(b.createdAt)),
  }));
}
```

这里使用 seen 防止坏数据循环把渲染卡住。它只是终止追溯，不是修复服务端循环关系的算法。正常业务仍应由后端约束 parentId 属于正确文章与有效关系。

把索引与分组放在同一个纯函数里，还有一个测试上的好处：它不依赖网络、平台或组件，只要给一组 Comment 就能验证结果。评论最容易出错的地方恰好是“顺序”和“缺数据”，这两件事都能在这里被固定住。

展示采用主楼加浅色回复区，不把每一层继续横向缩进。手机宽度有限，十层嵌套很容易把正文挤成一列。关系可以多级，视觉层级保持克制，两者不必完全相同。

## 父楼不在这一页时，我第一版把它当成了楼主

跨页回复的场景：第 1 页有评论 A、B，第 2 页有一条 `parentId = A` 的回复 C。

我第一版分组时是这样写的：

```ts
// ❌ 第一版：先判断是不是顶层，再往上找
if (at.parentId === 0) { root = at.id; }
else { root = at.parentId; /* ... */ }
```

结果 C 被当成了一条**独立的顶层评论** —— 因为它的 `parentId` 不为 0，但 A 也不在这一页里。

**而用户看到的是"某评论回复了一个不存在的对象"。**

修法是把"往上找根"提到最前面，**不管它是不是顶层**：

```ts
// ✅ 现在：先沿 parentId 追到能追到的最上面，再判断
let root = at.id;
while (at.parentId && !seen.has(at.parentId)) {
  root = at.parentId;
  const parent = index.get(root);
  if (!parent) break;
  at = parent;
}
```

关键在 `if (!parent) break;` —— **追到一个不在本页的 id 就停下，把它当作这一组的代表。** 界面显示这一组时再补一句"原评论暂不可见"，而不是假装它是楼主。

**这个 bug 只在"回复恰好跨页"时出现** —— 而那取决于评论有多少条、每页多少条。测试数据通常凑不出这个组合。


## 父楼没加载，不应丢弃回复

分页可能先拿到回复，而祖先不在当前页；审核或删除也可能让父楼不可见。当前分组保留这种回复，root 缺失时显示“前面的评论尚未加载或已不可见”。

```ts
// src/features/comments.tsx（节选）：按 ID 去重合并，按请求代次拒绝旧响应。
const data = await read<Page<Comment>>(
  `/articles/${articleId}/comments?page=${reset ? 1 : page + 1}&pageSize=20`,
  reset,
);
if (version !== generation.current) return;
setItems((old) => [
  ...new Map((reset ? data.list : [...old, ...data.list]).map((c) => [c.id, c])).values(),
]);
setMore(data.pagination.page < data.pagination.totalPages);
```

| 情况 | 当前展示 | 不编造的内容 |
|---|---|---|
| 主楼与回复都在 | 主楼加楼内回复 | 无需额外猜测 |
| 父楼不在当前集合 | 缺楼提示加现有回复 | 不造作者、原文或时间 |
| 回复的直接父评论可见 | 显示回复对象姓名 | 不只写数字 ID |
| 父评论不可见 | “前面的读者”兜底 | 不断言一定被删除 |
| 回复超过三条 | 默认折叠，按已加载数量展开 | 不代表全帖剩余回复数 |
| 循环 parentId | 追溯在 seen 处停止 | 不修复服务端坏关系 |

后续页加载后重新分组，关系可以变得更完整。当前 group 数量和 replies 数量只代表已加载数据，不能被当作全站或全帖总楼层数。

这也是一个产品文案判断：我们不知道是未加载、审核还是删除，就把不确定范围说出来。直接写“该评论已删除”，可能把分页现象错误描述成管理行为。

## 把回复折叠成可继续展开的区域

每组默认显示前三条回复，更多回复用“展开 N 条回复”，展开后可以收起。N 由当前已加载组计算，不承诺服务器上全部剩余回复。

```tsx
// src/features/comments.tsx（节选）：缺楼与展开都由已加载数据决定。
{group.root ? (
  comment(group.root)
) : (
  <View className="muted">前面的评论尚未加载或已不可见</View>
)}
{group.replies.length > 0 && (
  <View className="comment-floor">
    {(expanded.includes(group.id) ? group.replies : group.replies.slice(0, 3)).map((c) =>
      comment(c, true),
    )}
  </View>
)}
```

回复按 createdAt 排序，展示姓名、日期、文本与回复动作。Text 直接显示评论内容，没有把用户评论交给 Markdown HTML 渲染。评论是讨论文本，不继承文章富文本的全部能力。

外层楼与回复区的边界、缩进和留白来自原型的叠楼语言。输入框与已有楼层之间保留 margin，避免提交区域和别人发言粘成一块。

这个视觉设计不要求修改冻结接口。只要父子关系字段成立，客户端就能选择更友好的阅读组织；若未来需要服务器一次返回整棵树，则是新的性能与分页契约问题。

折叠与展开也只影响本机视图。它不写回服务器，不改变评论顺序，也不影响别人看到的内容。把这类纯展示状态留在组件里，是评论模块相对轻量的原因之一。真正需要写的东西只有两件：一条新评论，和它的 parentId；其余都交给读取重新组织。分页、审核、删除都会改变列表，与其在客户端维护一棵会过期的树，不如每次读回来重新算一次。

## 回复动作同时设置对象与焦点

点击回复先检查会话，再保存目标 Comment，设置 focus，并滚到 composer。输入区显示“回复某某”，可以取消目标回到主楼评论。

```tsx
// src/features/comments.tsx（节选）：回复同时设置目标与焦点。
if (requireLogin()) {
  setReply(c);
  setFocus(true);
  Taro.pageScrollTo({ selector: "#composer", duration: 250 });
}
```

提交 body 包含 trim 后内容与 `parentId: reply?.id || null`。直接回复谁，就提交谁的 ID；展示时追溯到组根，不代表写入时把所有 parentId 改成根楼。

这两个概念经常被混在一起：展示归属由客户端按已加载数据推算，写入关系由用户当前指向的那条评论决定。前者可以随分页变化而改变，后者一旦提交就是服务端事实。把它们区分开，才不会为了排版好看而写错数据结构。

账号变化清空 content 和 reply，防止 A 的未发送文本在 B 会话下继续提交。文章页还以文章和用户组合为 Comments key，帮助重建对应讨论状态。

Screen 点击外部收起键盘，composer 阻止冒泡，Textarea 用 onFocus 与 onBlur 更新 focus。完整设备键盘行为需要真机观察，不能仅凭代码分支宣布没有任何遮挡。

## 发送成功，不总意味着立即公开

后端返回评论状态。approved 显示发表成功；待审核显示待审核；rejected 提示修改，并保留当前输入供修正。

```ts
// src/features/comments.tsx（节选）：按服务端状态决定是否清空输入。
const result = await api<Comment>(`/articles/${articleId}/comments`, "POST", {
  content: content.trim(),
  parentId: reply?.id || null,
});
if (epoch !== sessionEpoch()) return;
if (result.status === "rejected") {
  setError("评论未通过审核，请修改后重试");
  return;
}
setContent("");
setReply(undefined);
await load(true);
```

发送后重新读取评论，而不是无条件把返回对象塞入公开列表。审核规则决定什么可公开，前端不能为了“乐观显示”绕开它。评论与点赞不同，公开可见状态不是只由点击决定。

这也是为什么发送的成功提示有两套文案：已发表和待审核对用户意味着不同的可见范围。把两者都说成“评论成功”，下一句就会变成“为什么我自己看不到”。

当前发送有 sending 状态防重复触发，但普通网络失败不自动重试 POST。结果不确定时，用户需要结合后续读取判断，客户端不能假设失败就没有创建。

## 删除自己评论也可能影响别人回复

本人评论显示删除入口，先确认“关联回复也会被删除”。服务端负责权限与级联，客户端成功后重读列表，不自行猜整棵关系全部删除范围。

```ts
// src/features/comments.tsx（节选）：删除先确认影响范围，再重读列表。
const confirmed = await Taro.showModal({
  title: "删除评论",
  content: "关联回复也会被删除，确认继续？",
});
if (!confirmed.confirm) return;
await api(`/comments/${c.id}`, "DELETE");
await load(true);
```

这个提示很重要：用户看到的是自己一条文本，动作影响可能是一串回复。删除按钮隐藏于他人评论只是体验，后端仍要拒绝越权请求。

真实本地后端集成验证过评论回复与级联删除、不同账号权限。逻辑测试覆盖分组与循环保护。它们不等于所有分页视觉都已人工查看。

## 用缺数据测试，而不只用整齐样例

建议回归时准备主楼不在第一页、回复父楼在后续页、三级关系、重复 ID、超过三条回复与循环输入。观察是否丢回复、是否重复显示、展开数量是否诚实。

```ts
// test/core.test.ts：多层归并、缺失父楼与循环保护。
const groups = groupComments([c(3, 2), c(1, null), c(2, 1), c(4, 9)]);
assert.equal(groups.find((g) => g.id === 1)?.replies.length, 2);
assert.equal(groups.find((g) => g.id === 9)?.root, undefined);
```

审核与删除还需要独立样本：待审核不强行公开，拒绝保留修正机会，删除确认清楚，刷新后的楼层关系重新生成。网络失败应与空讨论区分，而不是清空后告诉用户“暂时没有评论”。

当前分页与分组策略在小型内容站足够直接。评论规模扩大时，可考虑按主楼分页与服务器聚合，但它会改变接口含义，应先有规模证据再推进。


## 用四条评论推演分页归楼

假设主楼一号，二号回复一号，三号回复二号，四号回复一个当前不可见的九号。输入顺序哪怕是三号、一号、二号、四号，索引仍可让前三条归到一组，四号形成缺楼提示。

这个推演说明，我们不是依赖“父评论永远排在前面”。先建立全体已加载索引，再追父链，能处理分页合并时的顺序变化。回复区按时间排序，也不等于主楼集合按全帖关系重新分页。

后续九号到达，四号会重新归楼。若九号本身还有一个未到达祖先，根提示仍可能继续变化。当前只是尽可能组织已有事实，不承诺一次加载就得到稳定完整树。

### 删除后的客户端怎么重新认识关系

主楼删除且关联回复级联，客户端成功后重读第一页。它不在旧数组里只 splice 主楼，然后留下没有解释的子回复，也不自己计算所有后代作为服务器事实。

如果删除请求失败，列表仍可保留原评论并显示错误。请求层不盲目重试写入，避免结果不确定时重复动作。下一次读取才帮助校准可见状态。

删除按钮只有本人出现，但这不是权限证据。不同账号直接请求仍要被后端拒绝，本地集成的越权断言就在保护这一层。

### 回复输入是一份尚未提交的用户内容

提交失败保留内容与目标，用户可修正或重试；审核拒绝也保留输入。成功才清空并收键盘。账号变化清掉目标和文本，是为了防止甲的发言在乙身份发送。

这与编辑草稿的保留策略不同。评论输入没有实现独立本机恢复，不应该把编辑器的自动保存承诺套过来。每种用户输入都需要单独决定生命周期。

叠楼的长期扩展可以考虑按根楼分页、返回已知回复总数和可定位父楼，但这些是新数据能力。当前坚持“展开已加载回复”的含义，让界面更友好，同时不越过已有契约。

## 楼层友好，依赖的是不伪造关系

叠楼不只是缩进和背景色。姓名、直接回复对象、缺楼提示、审核状态和删除影响共同决定读者是否理解讨论。

相关数据边界见会员中心，接下来进入投稿状态机。展示可以更丰富，前提是我们仍忠于接口已经告诉我们的事实。
