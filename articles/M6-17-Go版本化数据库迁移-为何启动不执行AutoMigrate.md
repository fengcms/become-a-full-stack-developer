# 成为全栈·Go 后端篇·版本迁移与模型设计：为什么启动不执行 AutoMigrate

> 数据库结构是有版本的生产状态。让每个应用实例启动时自行“对齐模型”，会把一次发布变成难以控制的并发变更。

> 本文代码快照：提交 ceac4e0。Go 数据库迁移由 goose 管理，每个支持方言有两版显式 SQL。

## 前言：模型能描述字段，却不一定能安全升级数据

ORM 常带有自动建表或 AutoMigrate。开发时看见模型字段新增，数据库随后出现一列，体验确实轻快。但生产迁移不只是“模型和表不一样，就补一下”：删除列会丢数据，修改索引可能锁表，新旧应用版本可能同时运行，默认值会影响存量记录，跨数据库 DDL 行为也不同。

M6 用 GORM 映射持久化模型，但服务启动不执行 AutoMigrate。数据库结构由版本化 goose migration 显式管理，PostgreSQL、MySQL 和 SQLite 各有独立 SQL。当前结构覆盖 15 张业务表，并由两版迁移组成。这样做让结构变化能够先审阅、再按数据库执行，并记录当前库已经应用到哪个版本。

本文解释 model 与 migration 的分工、启动期不迁移的理由、三方言脚本的意义、seed 为什么不同于 migration，以及从开发验证走向生产变更需要哪些证据。

## 一、模型定义和数据库版本解决不同问题

GORM model 表达应用需要如何读写某张表：字段类型、列名、主键、关联和表名。Migration 表达数据库从版本 N 到 N+1 如何安全演进：创建表、添加约束、索引，或对已有数据做必要转换。

两者可能共享字段信息，但承担的责任不同。模型可以描述当前代码所预期的最终结构，却不能独自解释旧数据如何转化，也不能保证生产数据库执行 DDL 时没有风险。把 model 自动同步到数据库，会丢失明确的变更历史与审阅入口。

M6 的迁移通过 goose 按版本执行。SQL 文件存放在 platform/database/migrations 下的方言目录，编译时嵌入程序；migrate 命令读取配置、连接所选数据库并调用 goose provider。应用启动路径只打开数据库、ping 连通性、组装业务服务，不会隐式更改表结构。

## 二、为什么启动时不做 AutoMigrate

把迁移放到启动代码里会产生几个现实问题：

1. 多副本部署时，每个新实例可能同时尝试变更同一 schema；
2. 应用进程的数据库权限必须足以执行生产 DDL，扩大凭据权限；
3. 迁移失败与服务启动失败绑在一起，发布系统难以分辨是应用还是结构问题；
4. 无法在变更前执行针对旧数据的检查和备份；
5. 自动修正的实际 SQL 不如显式脚本容易审阅和追溯；
6. 一个应用版本可能删掉模型字段，自动流程却无法判断旧数据是否还需保留。

独立 migrate 命令把结构变化变成发布流程里的明确步骤。运维可先备份，再执行迁移、检查结果，最后启动新版本。实际部署要设计兼容发布顺序：先加字段和兼容代码，再逐步切换，最后才考虑删除旧结构。单体项目也可能有滚动部署或回滚要求，因此这不是只有“大型微服务”才需要的纪律。

## 三、方言目录是对真实数据库差异的承认

当前工程分别维护 PostgreSQL、MySQL、SQLite 的 00001_initial.sql 和 00002_indexes.sql。相同的逻辑表会映射到不同 DDL：主键类型、文本类型、布尔表示、默认值、索引长度、外键语法和迁移事务能力可能有差异。

将 SQL 分目录并不表示业务 schema 可以各自漂移。三份迁移应实现同一组逻辑表和约束，并通过对照检查避免漏项。每个支持方言都需要执行空库迁移和旧版本升级，再检查表、索引、唯一键、外键与字段默认值。

数据库模型也不使用 GORM 自动软删除约定。M6 的模型选择显式 DeletedAt 等字段与查询 scope，以吻合既有数据结构和接口语义。若直接嵌入 gorm.Model，自动字段、deleted_at 查询过滤和 JSON 结果可能改变旧接口行为。表结构历史应通过迁移保存，不能寄希望于 ORM 默认猜中。

## 四、迁移版本和业务数据搬迁不是一件事

结构 migration 改变目标库的 schema；data 工具则把已有业务记录从一个数据库导出或导入。两者的安全要求不同：

- migration 关心当前 schema version、DDL 和结构升级；
- seed 关心开发环境初始账号和样本；
- data transfer 关心用户、文章、关系、计数和附件引用是否完整迁移。

不应该因为结构迁移工具能运行 SQL，就把整库内容复制也塞进 migration。数据量、失败恢复、幂等性和源目标连接权限都不同；一个版本化结构文件也不适合存储庞大的业务快照。

M6 的 data 命令单独使用 TRANSFER_DATABASE_URL，并对导出源使用只读连接策略；导入目标需要明确驱动和文件路径。dry-run 会在事务中完成导入校验后回滚，证明输入与导入路径能运行，却不代表数据已持久化，也不代替真实目标的迁移验收。离线迁移策略将在 M6-28 具体讲解。

## 五、Seed 应可重复检查，不能覆盖账号

seed 不是 migration。它创建的是开发用用户和演示内容，不改变表结构。当前命令检查演示用户名是否已经存在，避免重跑时静默覆盖已有账号；用户与样例文章在同一事务中建立，使部分初始化失败时可以整体回滚。

如果 seed 只判断“表不为空就退出”，对开发者可能不够方便；如果每次重置默认账号密码，又可能破坏已有本机环境。具体策略要考虑运行目标，并且启动命令不应自动调用 seed。生产系统创建管理员通常应使用受控管理操作或一次性部署流程，而不是保留明文默认密码的初始化脚本。

迁移、seed、服务启动和数据导入应有不同权限、不同日志与不同人工操作入口。一个完整 Makefile 能提供方便命令，但命令存在不代表它适合任何环境。

## 六、迁移测试要模拟升级，而非只测空库

空库 migration 仅证明可以创建当前结构。至少还需要以下检查：

1. 在每种真实数据库上从空库执行所有版本；
2. 从前一已发布版本构造存量，再执行升级；
3. 核对旧记录数量、字段值、唯一关系和外键；
4. 验证索引存在并支持关键查询；
5. 在迁移故障后检查部分 DDL/数据状态，并验证恢复步骤；
6. 使用实际应用版本启动，确保模型查询和写入与迁移后的结构一致；
7. 检查不支持的版本跳跃会明确失败。

SQLite 的临时文件测试有价值，因为它包含真实文件锁和持久化；纯内存 SQLite 不能代表 WAL、重连和外部进程竞争。PostgreSQL 与 MySQL 也需各自数据库服务，不能把 SQLite 作为方言替身。

迁移回滚并非每条 DDL 都能安全撤销。删列或转换数据可能不可逆。遇到不可逆变化，运行手册需要明确备份、前向修复或恢复策略。goose 中存在 down migration 也不意味着它能恢复已经丢失的数据。

## 七、一个相对安全的变更流程

对新增文章字段，可以按如下思路推进：

~~~text
确认 API 与数据需求
  ↓
为每个支持方言写 migration
  ↓
在旧结构上验证升级与数据保留
  ↓
先部署兼容新增列的应用版本
  ↓
检查生产备份与迁移窗口
  ↓
独立执行 migrate 并检查状态
  ↓
启动应用、核验读写与监控
  ↓
满足回滚条件后再安排旧列清理
~~~

“先扩展、再切换、最后收缩”降低新旧代码共存时的风险。小规模教学项目可以减少流程环节，但仍应在测试库跑升级路径，并保留明确备份。

不要把迁移失败自动吞掉，也不要让 server 以“尝试修好数据库结构”的方式继续监听。数据库 schema 与当前程序不兼容时，早点失败比返回结构错误或静默丢字段更容易定位。

## 小结：数据库结构要可见、可审阅、可复现

M6 用 GORM 描述持久化模型，用 goose 显式管理迁移版本，分别为三个数据库维护 DDL；启动时只连接和检查数据库，不自行改结构。seed 用事务建立开发样本，data 命令负责业务数据搬迁。四种责任分开后，发布时更容易判断每一步会改变什么。

如果一个 ORM 功能会在程序启动时自动改 schema，先问：谁审阅了实际 DDL？多副本如何协调？旧数据如何迁移和恢复？应用账号是否需要 DDL 权限？只有这些问题有答案，自动迁移才是一个可控选择。
