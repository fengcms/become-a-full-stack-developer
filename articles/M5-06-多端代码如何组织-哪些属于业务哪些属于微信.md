# 成为全栈·Taro 小程序篇·多端代码如何组织：哪些属于业务，哪些属于微信

> “以后可能支持别的平台”很容易变成今天的抽象负担。真正值得提前分开的，是已经看见的变化边界。

{{IMG:M5-06-封面}}

## 前言：目录不能替我们完成架构判断

写了网站和 APP，再写小程序，我很容易产生一种冲动：建一个巨大的 shared，把文章、会员、编辑器都扔进去，仿佛目录名越通用，未来越容易复用。

但浏览器请求、Flutter 网络库和 Taro API 并不能互相调用。把它们放在一个名字好看的目录里，只会让“共享”停留在口号上。

本项目选择更克制的做法：在小程序内部，分开产品规则、异步协调和平台动作。真正纯粹的逻辑容易测试；接触 Taro 的地方则明确依赖。暂时不为没有交付的目标发明一整套适配器框架。

## 一、用“为什么会变”检查模块归属

当前目录不是按接口名称堆文件，而是让变化原因尽量集中：

| 层次 | 例子 | 主要变化原因 |
|---|---|---|
| core | 评论分组、草稿校验、Markdown 解析 | 数据规则、文本处理或底层协调 |
| hooks | useResource、useFeed | 页面生命周期与读取策略 |
| components | Screen、Icon、ArticleCard | 一致的展示与交互基础 |
| features | Comments、Markdown、EditorForm | 一个完整业务能力的组合 |
| pages | article、editor、member | 页面参数、路由和功能编排 |

`core` 也并非全都是纯函数。请求与存储模块仍依赖 Taro。判断纯不纯，应看依赖，不应看文件夹名字。比如 `groupComments` 只消费评论数组；`saveDraft` 却调用平台存储。两者测试方式本就不同。

这种诚实的分层，比宣传“业务完全与平台解耦”有用。下一位维护者看到 import，就知道哪里可以直接移植，哪里需要替换运行环境。

## 二、页面只决定组合，不重新发明底层规则

文章页需要正文、目录、点赞、收藏、评论和上下篇。如果每一项都直接在页面里处理请求、缓存和错误，最终会形成一个谁也不敢动的长文件。

项目把 Markdown 渲染、互动条、评论区拆为 feature；底层解析与分组放入 core；页面负责提供文章 ID、预览模式和生命周期条件。

同样，会员页展示收藏数量，不应该再实现一套会话存储。编辑页提交文章，也不应该绕过统一 API。否则，同一个账号切换动作会有四五种处理方式，任何一次修复都只能修到其中一个入口。

这里还有一个实用约束：当平台行为影响业务结果时，不要把它隐藏到万能组件里。编辑器的离开保护、图片选择、页面显示补读，都应在明确的位置可追踪。

## 三、导航集中管理，但不伪装成跨平台路由器

`src/core/navigation.ts` 中的普通页面跳转统一编码参数：

```ts
export function go(page: string, params: Record<string, string | number> = {}) {
  const query = Object.entries(params)
    .map(([k, v]) => `${k}=${encodeURIComponent(v)}`)
    .join('&');
  const url = `/pages/${page}/index${query ? '?' + query : ''}`;
  return Taro.navigateTo({ url }).catch(() =>
    Taro.showToast({ title: '页面打开失败，请返回重试', icon: 'none' })
  );
}
```

参数编码、错误提示在一个地方处理，文章和作者入口就不必各写一份。Tab 则独立调用 `switchTab`，不混进普通跳转函数。

但这仍是小程序导航模块。它不需要接收 Flutter 的 Navigator，也不需要返回网页 URL。跨端产品共同的规则是“站内文章应进入文章详情”，具体跳转由各端完成。

`requireLogin` 也是相同思路：当前有会话则继续，否则打开认证页。它是前端体验门禁；服务端仍要检查 Bearer 与资源所有权。让客户端函数名叫 guard，不会增加任何后端安全性。

## 四、纯逻辑测试靠真实边界，而不是替换整个应用

评论分组、缓存、草稿 payload 与 Markdown 节点都可以在 Node 环境执行。测试脚本使用 esbuild 编译目标模块，并为平台依赖提供测试替身。

这有两个好处。第一，循环评论和过期响应不需要靠人工等一个偶发竞态；第二，测试失败能指向某条规则，而不是只告诉我们整个页面打不开。

但替身不会证明微信媒体选择正确，也不会证明 Textarea 在设备上的光标行为。因此，平台组件继续交给开发工具交互记录。测试分层不是省事的借口，而是承认每一层证据的能力范围。

本次留下 11 项逻辑测试结果；真实后端集成记录又检查了账号隔离、投稿状态与评论权限。没有把这两套测试都叫“端到端通过”。验证细节见 [小程序质量验证]({{LINK:M5-24}})。

## 五、什么时候才值得增加平台适配接口

如果下一步真的交付另一个小程序目标，我会先梳理登录、分享、上传和外链这几个已经明确不同的能力，再提取接口。每个接口都要有两个实际消费者，才容易看出哪些参数是共同语义，哪些只是微信 API 的影子。

反过来，现在就造几十个泛型适配器，会让读者先理解一层没有使用场景的抽象。对于教学项目，它的成本大于收益。

也不能把全部平台判断塞进业务页面，等增加第二端时再一页页搜索 `if (weapp)`。当前集中导航、上传和会话底层动作，就是为未来保留明确切口；这已经足够。


## 从一个新增动作反推依赖方向

假设下一步增加“复制文章中的代码”。页面应该只负责提供正文，Markdown feature 识别代码节点，平台剪贴板动作留在对应渲染位置。它不需要让会员中心知道，也不需要修改缓存键。

如果为了这一个按钮，必须给所有页面增加回调，再把剪贴板状态塞进全局 store，说明功能边界已经偏离了业务。模块数量多，并不能抵消依赖方向不清楚。

换一个例子，投稿保存成功后要更新私人列表。它依赖请求层的写入失效规则与列表显示补读；编辑页不应该手工寻找每一个“我的文章”实例并修改数组。后端事实通过读取重新校准，本地即时反馈则由页面自己的保存状态承担。

### 什么状态值得共享

当前互动状态有跨页消费者：详情与 ArticleCard 都要看到点赞计数，因此使用独立 reaction store。编辑器的预览开关只有当前页使用，就留在局部。会话影响多页权限与身份，需要统一；输入框光标却没有必要变成全局状态。

这个判断可以写成三个问题：谁读它，谁修改它，谁对最终事实负责？只被一个组件读写的交互状态，通常留在组件；服务器负责的文章列表，进入读取与缓存层；跨页瞬时反馈，使用有明确清理条件的共享状态。

共享状态也要有容量与归属。reaction store 设上限并在会话代次变化时清理，而不是为了“全局一致”把它永远保存。全局不是永久，更不是跨账号通用。

### 少建一层，也是一种架构决策

当前导航和上传函数直接调用 Taro，并没有统一成十几个抽象接口。我认为这是可以解释的选择：本轮只有一个目标，已知差异集中，实际修改入口可追踪。

未来增加第二个目标时，抽象应从真正不同的实现中提取。只有一种实现就设计一个特别通用的接口，往往只是把微信参数换了一组名字，业务并没有获得更好的表达。

读者可以用一次具体修改检查自己的目录：改变错误提示、增加新分享方式、修改缓存失效、增加草稿字段，分别会触及哪些模块。把这份影响清单画出来，比争论目录名字叫 common 还是 shared 更有帮助。

## 六、分层的效果，要在修改时观察

缓存策略改变，主要修改请求层和数据 Hook；图标资源改变，主要修改基础组件和生成脚本；评论楼层关系改变，主要修改分组函数和评论展示。这才是目录有价值的证据。

如果一个很小的变化仍然迫使我们横跨所有页面，那应当重新审视职责，而不是继续加一层目录。
