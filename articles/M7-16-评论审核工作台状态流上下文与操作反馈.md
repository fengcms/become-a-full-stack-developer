# 成为全栈·Vue 管理后台篇·评论审核工作台：状态流、上下文与操作反馈

> 评论审核不是在表格里加两个“通过/拒绝”按钮。编辑需要看懂评论属于哪篇文章、它在回复链的什么位置、拒绝理由如何产生，以及审核、回复或删除之后列表怎样保持可信。本文沿评论工作台的真实实现展开。

> 本文代码快照：Vue 后台提交 `d3ee41a`。主要参考 `manage-frontend-vue/src/pages/comments/CommentListPage.vue`、`src/api/comments.ts` 和冻结 OpenAPI 评论 schema。

## 前言：审核页面连接的是内容治理流程

评论可能处于待复核、已通过或已拒绝状态。编辑需要筛选状态、查看正文、判断上下文、做审核决定；也可能代表官方账号回复读者；若删除父评论，下面的回复会不会一起删除也必须在确认提示里说清楚。

前端工作台为这些动作提供清晰操作和反馈，但状态合法性、敏感词判断、审核权限和级联删除最终都由后端契约定义。尤其是“官方回复”：它仍然走普通发表评论端点，服务端根据内容安全规则可能返回 rejected，不能因为回复者是编辑就假设一定通过。

## 评论状态筛选与远程分页

Vue 页面默认筛选 `reviewing`，可以选择全部、待复核、已通过和已拒绝。状态与页码进入 query key，请求 `GET /admin/comments`；表格使用 remote pagination 和接口的 total。状态改变时页码重置为 1，避免旧页码超出新筛选结果范围。

评论列表与公开前台查询不同：公开接口通常只返回 approved 内容，而管理接口必须能看到 reviewing/rejected 项。按项目 API 模块注释，`GET /admin/comments` 是审核状态内容的唯一列表读取路径。管理页面不可改用公开评论列表后期待它包含待审核内容。

## 一行评论需要什么上下文？

工作台至少展示评论正文、评论者、状态、时间和相关动作。当前 Vue 实现用 `articleId` 和 `parentId` 区分文章评论与回复，并在回复弹窗中引用目标评论正文，帮助编辑确认自己回复的是哪一条。

当前行信息仍有可改进空间：它展示的是“文章 #123”和“回复 #456”，而不是文章标题和完整嵌套楼层。若要让审核工作台更友好，可以依契约可用字段链接文章详情或追加上下文查询，但应避免为每一行各发一次请求造成 N+1 流量。优先确认列表响应是否已有标题/父评论摘要，或设计批量/包含式接口；不能凭 UI 需求直接假定已有数据。

分层评论的语义来自 `parentId`，前端显示 parent id 只是摘要，不等同于完整树形讨论串。复杂上下文可通过进入文章评论详情页或展开一楼内容补足，方案需结合 API 数据形状和审核工作量评估。

## 审核状态更新使用专用端点

通过或拒绝时，页面调用 `PATCH /comments/{id}/status`，提交目标状态和拒绝原因：

```ts
await moderateComment(row.id, {
  status: next,
  reason: next === 'rejected' ? '由管理后台审核拒绝' : null,
})
message.success('评论状态已更新')
await client.invalidateQueries({ queryKey: ['comments'] })
```

状态改变成功后失效评论列表，当前筛选会重新读取，刚审核的评论可能离开当前筛选结果，这是预期行为。重复提交失败时显示后端可读错误；不能先乐观地把行状态改掉却无回滚机制。

拒绝原因目前由页面传入固定说明，若产品需要由审核者填写具体理由，应有相应 UI 并按契约长度、空值语义和隐私策略校验。成功后端点会清理或设置 rejectedReason 等字段的规则以契约为准，前端不自行维护另一份状态机。

## 官方回复也要经过发表流程

回复使用 `POST /articles/{articleId}/comments`，payload 含正文和 `parentId`。前端打开 modal 时将当前评论设为 replyTarget，并在引用块显示原评论。发送前对空白文本校验，最多 2000 字；请求成功后，根据返回评论 status 选择 success 或 warning 文案：如果内容安全规则将它标成 rejected，就提示“已提交，但被内容安全规则拦截”，不会谎称已经公开展示。

这里体现“请求已接受”和“内容已公开”的差别。接口返回一条 Comment 实体，却可能状态为 rejected；页面应遵照返回状态，而不是把它直接放进已通过评论列表。回复成功后，重置输入并失效评论查询，服务端成为最新状态来源。

## 删除评论：确认提示必须说明级联影响

删除评论之前，Naive UI 对话框说明：删除该评论会级联删除它下面的全部回复。后端契约以 `x-cascade: children` 约定级联行为。若只写“确定删除这条评论吗”，用户会以为只影响当前一条，产生内容丢失风险。

删除操作之后失效评论列表。前端不手动递归删除本地评论树，因为服务端已经执行级联，缓存重新获取才能反映实际结果。用户是否能删除由后端角色及资源归属规则决定；页面上的按钮对于管理后台角色可见，不表示所有删除行为都绕过资源授权。

## 查询失效与错误反馈

审核成功、回复提交、删除成功后都调用 `invalidateQueries({ queryKey: ['comments'] })`，覆盖 comments 域相关列表。这样当前页面会刷新，其他页面使用的评论缓存也会被标 stale。若细分 key 后，可按审核列表、详情或 dashboard summary 精确失效；缓存策略要和数据的真实影响范围一致。

失败处理保留当前 UI 状态并显示错误。列表查询失败时页面有重试按钮。加载失败、空结果、请求中不能被混成一个 `[]`，否则审核员无法辨别是“没有待审评论”还是“服务不可用”。当前页面分别用了表格加载状态和错误重试提示；后续可进一步统一空态视觉和错误详情格式。

## 权限边界：评论工作台不能自己裁判

工作台只对具备评论审核能力的编辑/管理员开放。菜单、路由和按钮按 `canModerateComments` 控制；每个端点还要由服务端校验角色、评论状态、资源所有权和可用动作。前端隐藏“通过”按钮不会阻止伪造 PATCH 请求，审核工作台也不是安全边界。

拒绝原因、评论正文和用户信息都可能涉及敏感内容，错误日志和截图应避免暴露不必要的个人数据。运营上若需要审计“谁在何时审核了什么”，应依赖服务端审计记录或契约已有字段，不应只用前端 toast 代替审计。

## React/Vue 重写对照

两个后台都提供评论筛选、审核、回复和删除，但代码组织方式可以不同。React 版将审核和回复表单拆成 dialog 组件，通过 mutation hooks 统一请求状态；Vue 版在 `CommentListPage.vue` 中集中声明 query、操作函数、表格列和回复 modal。比较时应看：端点是否相同、状态结果是否被遵守、失败是否反馈、删除提示是否说清级联影响、成功后是否刷新缓存。

若某一页面文件增长到难以阅读，确实可以把审核对话框、回复对话框抽成组件；抽离时仍要保留行为边界和 API 契约，不能为了追求目录对称机械复制 React 的文件结构。

## 小结：评论治理要让上下文和后果可见

评论工作台围绕三态筛选、远程分页、父回复关系、审核端点、官方回复安全过滤、级联删除和查询失效展开。界面应该说明正在处理什么、操作将产生什么后果、请求失败怎么办；后端负责最终授权与状态判断。
