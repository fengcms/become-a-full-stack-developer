# 成为全栈·基础补充·Git 进阶：分支策略与协作

这个专栏的提交历史，如果只看提交信息，是能读出整个开发过程的。

```text
b178c9d docs(articles): 完成B系列安全运行与缓存基础
82c2c60 docs(articles): 完成B系列开发与部署基础
b999787 docs(articles): 完成B系列网络工具与SQL基础
10e200c docs(articles): 完成B系列工程基础补充文章
268d493 fix(auth): 修复微信登录请求的Workers重定向兼容性
```

**注意那个 `268d493`**——它是 M1-34 讲的那个 bug 的修复。而它的提交信息里有一个词很关键：

```
fix(auth): 修复微信登录请求的**Workers**重定向兼容性
```

**它没说"修了个 bug"，它说清了"在什么环境下、什么问题"。**

而那个 diff 只有 3 行代码 + 19 行测试。**3 行的改动能通过提交信息说清上下文，这才是提交信息该有的样子。**

这篇讲提交历史怎么变成文档，以及这个专栏用它做的几件具体事。

## 提交信息是给未来的人看的

先说为什么提交信息这么重要。

**半年后你查一个 bug，会先 `git log`，而不是先 `git blame`。** 而如果提交信息只写"修复问题"，你等于什么都没得到。

这个专栏的约定是：

```
type(scope): 中文描述
```

而这个格式的价值在 `268d493` 上体现得最清楚：

```text
fix(auth): 修复微信登录请求的Workers重定向兼容性
```

**拆开看它提供了三个信息：**

| 部分 | 信息 | 为什么重要 |
|---|---|---|
| `fix` | 这是修复不是新功能 | 决定要不要小心对待 |
| `(auth)` | 只动了认证相关 | **决定这个 bug 影响面有多大** |
| 描述 | Workers 环境下的重定向兼容 | 说清了"在哪儿出的问题" |

**如果只写"修复登录 500"**，半年后你会以为是别的原因，因为同一个现象有多种可能。

而 `(auth)` 这个 scope 的价值更高——**它让你能按目录筛选历史**：

```bash
git log --oneline --grep="auth"     # 只看认证相关
git log --oneline -- node-backend/src/middleware/auth.ts   # 只看这个文件
```

## 一次提交应该多大

这是另一个更实际的判断。

而这个专栏有个很能说明问题的对照——M1-34 那个修复提交：

```bash
$ git show --stat 268d493
 node-backend/src/services/wechat.ts     |  3 ++-
 node-backend/test/routes/wechat.test.ts | 19 ++++++++++++++++++++
 2 files changed, 21 insertions(+), 1 deletion(-)
```

**3 行代码 + 19 行测试，放在同一次提交里。**

这是正确的做法：**修 bug 和加回归测试应该在同一次提交里**——因为它们是同一个意图的两半。

而如果分成两次：

```text
abc123 fix: 修复微信登录在 Workers 上的重定向兼容性
def456 test: 补充微信登录测试
```

**问题在于：如果有人只 revert 了 `abc123`（比如发现它在别的环境引入了问题），那个测试还在，而它会失败。** 然后下一个人会困惑："这个测试从哪来的？它测的东西被删了。"

**"让一次提交自洽"的意思是：它要么完整地解决了问题并验证了，要么完整地不存在。**

而拆得太细的代价是对称的——一个只有 1 行的提交会让历史被淹没：

```text
abc123 style: 改了个空格
def456 docs: 加了句注释
ghi789 fix: 忘了改文件路径
```

**而 B-17 讲的排查方式"先 git log 找上下文"，在这种历史里完全失效。**

## 这个专栏用 git log 做过什么

这部分是我认为最实用的部分。

**第一，用提交历史统计规模。**

```bash
# 按提交类型分组统计
git log --oneline --grep="^fix" | wc -l
git log --oneline --grep="^docs" | wc -l

# 某个文件被改过多少次
git log --oneline -- node-backend/src/services/wechat.ts
```

**而"某个文件被改过多少次"这个数字本身有诊断价值**——**一个被改了几十次的文件，通常说明它职责不清**（或者有 bug 反复）。

**第二，用提交历史定位"什么时候坏的"。**

这是 B-19 讲的那个排查方法的延伸：

```bash
git log --oneline -10 -- node-backend/src/config/env.ts
```

**如果某次提交大改了配置处理，而故障是在那之后出现的——那它就是首要嫌疑。**

而这个专栏里"什么时候坏的"经常是确定的，因为提交很聚焦：`fix(auth)` 之后又是几个 `docs`，**那么 auth 那个改动就是这段时间唯一的代码变更**。

**第三，用提交信息交叉验证文档。**

B-17 记的那个数字是"22 个测试文件、155 个用例、4170 行"——而这个数字在记忆里被记下来，是因为**某次提交的 diff 里测试文件增加了**。

```text
$ git show --stat <某提交> | grep test
 test/routes/wechat.test.ts | 19 ++++++++++++++++++
```

**所以"测试规模"这个数字是有出处的，不是编的。** 而这就是"提交历史也是文档"的另一种用法。

## 分支策略：这个专栏只有一条

大多数项目的分支策略都很复杂（git-flow、GitHub flow、release branch……）。

而这个专栏没有——**它一直在 master 上工作**，用提交类型而不是分支来区分性质：

```text
fix(auth): ...        ← 修复
feat: ...             ← 新功能
docs(articles): ...   ← 文档
chore: ...            ← 杂务
```

**这个选择的前提是"只有一个人写"，而且这些提交会立刻发布。**

**而如果你在多人协作的项目上，"用提交类型区分性质"是不够的**——因为两个人同时提交 feat，合并时依然会有冲突。

**多人协作时的最低要求是：**

```bash
# 按功能开分支，合并前至少能独立测试
git checkout -b feat/wechat-login
git checkout -b fix/cache-invalidation

# 合并前先确认自己的分支是最新状态
git fetch origin && git rebase origin/master
```

**而这个专栏用不到这些，是因为它的"协作"场景是"我自己和未来的我"。** 未来的我不认识现在的我，但他会读提交信息——**所以提交信息要写给未来的自己。**

## 几个我天天用的命令

这一节是纯实用清单，都是我在这个项目里真实用过的。

**看改动：**

```bash
git diff                          # 未暂存
git diff --staged                 # 已暂存
git diff HEAD~1                   # 和上一个提交比
git show                          # 当前提交的全部改动
git show --stat                   # 只看文件列表和行数
```

**而 `git diff --stat` 那个是最有用的**——**它在提交前能告诉你"这次改动有多大"**：

```text
 node-backend/src/services/wechat.ts     |  3 ++-
 node-backend/test/routes/wechat.test.ts | 19 +++++++++++++++++++
 2 files changed, 21 insertions(+), 1 deletion(-)
```

**一眼就能看出"3 行代码 + 19 行测试"，符合预期，可以提交。** 而如果输出是 400 行，说明我可能忘了只提交一部分。

**回退（要慎用）：**

```bash
git restore <file>              # 丢弃工作区的改动
git reset --soft HEAD~1         # 撤销上一次提交，但改动还在暂存区
git revert <commit>             # 生成一个"反向提交"
```

**`reset` 和 `revert` 的区别是这一节最重要的内容：**

| 命令 | 做什么 | 影响历史 | 什么时候用 |
|---|---|---|---|
| `reset --soft` | 撤销提交，改动回暂存区 | **改写** | 自己的未推送提交 |
| `reset --hard` | 撤销提交，改动全丢 | **改写** | 自己的未推送提交（**危险**） |
| `revert` | 生成一个反向提交 | 不改写 | **已推送的提交** |

**规则很简单：已推送的提交只能用 `revert`。**

因为 `reset` 是改写历史——**别人（或者你另一个设备上的仓库）已经拉走了那些提交**，你 reset 之后他们再次 pull 会出冲突，**而冲突解决起来远比"多一个反向提交"麻烦**。

**而这个专栏的发布提交都是推送过的**，所以一旦发现某篇发错了，**只能用 `revert` 加一个新提交**，不能 reset。

**查找：**

```bash
git log --oneline --grep="契约"
git log --oneline --since="2026-10-01"
git log --oneline --author="funcleo" -- src/config/
git log -p -- src/services/wechat.ts    # 看这个文件的完整历史
```

**最后那条 `-p` 在排查时最有用**——它会把每次改动的具体内容都打印出来，**能看出"这个文件的行为是怎么一步步变成现在这样的"**。

## 提交信息里的一个细节：scope 要有信息量

最后说一个我踩过的坑。

我一开始的提交信息里 scope 写得很随意：

```text
fix: 修复若干问题
docs: 更新文档
```

**这种信息等于没写。**

而改成有信息量的 scope 之后：

```text
fix(auth): 修复微信登录请求的Workers重定向兼容性
docs(articles): 完成B系列安全运行与缓存基础
chore(deps): 升级 highlight 依赖
```

**每个 scope 都能定位到一个目录或模块**，于是 `git log --grep` 变得真的能用。

而 `fix: 修复若干问题` 这种还有一个具体害处：**它会让"按类型筛选"失效**，因为所有修复混在一起。

**而判断标准很简单：如果两个人写同一个 scope，那它一定不够细。** 因为他们改的是不同的东西。

## 一条我一开始想省掉的事

`git show --stat` 这个命令，我一开始觉得"看个改动而已，用 IDE 不就行了"。

而这个判断在一次误操作之后被推翻了。

那次我改了一堆文件，跑完测试发现一个之前也修过的 bug 又出现了——**而我完全不记得上次是怎么修的**（因为那些提交发生在几个月前）。

IDE 只能告诉我"当前文件的第 47 行是这样"，**它不能告诉我"谁在什么时候把它改成了这样"**。

而 `git show --stat <那个修复提交>` 直接告诉我：**改了哪两个文件、加了哪些测试**。然后 `git show <提交>` 看完整 diff，五分钟解决。

**这就是"提交历史是文档"的实际价值**——它不是理念，是**你真的会因为不知道它而多花几小时**的场景。

顺带说，那次我补的 19 行测试现在还在 `wechat.test.ts` 里（B-20 和 B-17 都引用过它）。**而如果我当时没加那 19 行，下一次同样的问题就要再查一遍。**

## 小结

Git 进阶在这个专栏里的实际用法，沉淀下来是四件事：

1. **提交格式 `type(scope): 中文描述`** —— scope 决定影响面，描述决定可读性。
2. **修 bug 和加测试在同一次提交** —— 让提交自洽，避免 revert 后留下孤儿测试。
3. **用提交历史做排查** —— `git log -- <file>` 找"什么时候坏的"，`git show <commit>` 看"当时怎么改的"。
4. **已推送的提交只能用 `revert`** —— `reset` 改写历史会让协作者冲突。

其中第 3 条我觉得价值最高，而且它不只服务于"修 bug"——

> **提交历史的另一个用途是"回答关于过去的问题"。** 这个专栏里那 22 个测试文件、155 个用例的统计能有据可查，就是因为某次提交的 diff 里写着 `test/routes/wechat.test.ts | 19 +++`。

**而这一批 B 系列文章的 20 篇里，有 8 篇的规模数字就是这么来的。** 如果提交信息只写"docs: 更新文章"，这些数字就会变成"我记得大概是这些"——**而"大概是"在需要引用的时候毫无价值。**
