# 成为全栈·基础补充·Git 进阶：分支策略与协作

> Git 的价值不只是“保存代码”。它让每次修改有来历、能比较、可审阅，也能把文章、实现和可复现版本绑定起来。理解提交、分支和远端，协作时就不必靠复制文件夹。

## 前言：版本控制解决的是可追踪问题

项目开发中，经常需要回答：这段代码是谁什么时候改的？改动前后差了什么？某个发布版本对应哪一份源码？能不能撤销一个错误提交而保留其他工作？Git 就是用一张提交历史图来回答这些问题。

Git 保存的是一系列快照。一个 commit 记录某个时刻的文件状态、提交说明和父提交关系；branch 是指向某个提交的可移动名称；tag 通常指向一个确定版本，适合标记发布点。它们不是远端备份的同义词：本地仓库也有完整历史，但磁盘损坏时仍需要远端副本。

## 一、工作区、暂存区和提交

日常 Git 有三个重要区域：

```text
工作区 --git add--> 暂存区 --git commit--> 本地仓库
```

工作区是当前文件；暂存区是你准备放进下一次提交的变更集合；仓库保存提交历史。常用检查命令：

```bash
git status --short
git diff
git diff --staged
```

`git status` 看哪些文件变化，`git diff` 检查未暂存差异，`git diff --staged` 检查已暂存内容。不要在不了解差异的情况下直接 `git add .`，因为它可能把调试输出、密钥或无关文件也加入提交。

一次提交尽量表达一个完整、可解释的变化。比如“新增文章列表查询”与“格式化整个仓库”混成一个提交，评审和回滚都会变难。提交前检查内容，再写能说明目的的消息，例如 `feat(auth): 支持刷新令牌轮换` 或 `docs(articles): 完成B系列工程基础补充文章`。

## 二、分支用于隔离正在进行的工作

主分支代表团队认可的集成状态；功能分支让一项改动可以独立开发和审阅。短周期、主题清晰的分支通常更容易合并：

```bash
git switch -c feature/article-search
# 修改、测试、提交
git switch main
git merge feature/article-search
```

分支不必越多越好。一个分支同时积累几个月的改动，会与主线越来越远，冲突和评审成本都会上升。提交小而有意义、经常同步主线、及时合并或删除已完成分支，历史会更容易理解。

## 三、远端、fetch、pull 和 push

远端是仓库的另一个副本，常见名称是 `origin`。`git fetch` 下载远端的新提交但不自动改当前分支；`git pull` 通常等价于 fetch 加 merge 或 rebase；`git push` 把本地提交发送到远端。

协作前先拉取最新历史，提交后推送自己的分支。多人同时改同一分支时，最好避免直接强推覆盖他人提交。`--force-with-lease` 比裸 `--force` 多一道远端状态保护，但仍会重写共享历史，只有明确理解影响并获得团队约定时再用。

## 四、合并冲突是两个历史同时前进的结果

Git 无法自动决定两边对同一片内容的最终意图，就会出现冲突标记：

```text
&lt;&lt;&lt;&lt;&lt;&lt;&lt; HEAD
当前分支的内容
（此处是 Git 自动插入的分隔线）
合并进来的内容
&gt;&gt;&gt;&gt;&gt;&gt;&gt; feature/article-search
```

冲突解决不是简单保留一边，而是阅读两边变更、理解功能目标并写出正确的最终版本。处理后删除标记，运行测试，再 `git add` 冲突文件并完成 merge commit 或 rebase。不要只因冲突消失就认为逻辑正确。

## 五、merge 和 rebase 怎么选

merge 保留分支合并关系，适合记录团队协作过程；rebase 把自己的提交重新放到最新主线之后，历史更线性，但会改写这些提交的 ID。对尚未共享的个人功能分支，rebase 常能让提交历史清楚；对已经多人使用的公共分支，重写历史会让其他人的本地提交需要重新处理。

选择不是宗教问题：团队要统一习惯，避免每个人用不同方式造成难懂历史。无论选择哪种，都要在合并前看最终 diff 并运行该项目的验证命令。

## 六、撤销修改要分清是否已经共享

`git restore file` 可以丢弃工作区中未提交的文件修改；`git reset` 会移动当前分支指针或调整暂存状态，模式不同影响不同；`git revert <commit>` 会新增一个反向提交，适合撤销已经共享的历史。对于远端已使用的提交，revert 通常比重写历史安全。

任何会丢弃修改的命令，都先运行 `git status` 和 `git diff`。不确定时先建立临时分支或备份 patch。Git 能帮你找回很多历史，但它无法恢复从未提交、从未备份且已经被覆盖的文件。

## 七、tag、代码快照和文章发布

在教学仓库里，文章往往描述某个确定代码状态。Git tag 可以把文章编号与源码快照关联；读者 checkout 到对应 tag 时，看到的应是该文提到的实现状态。tag 是本地名称，推送仓库时还要推送 tag；创建了 tag 不代表文章已发布，也不代表代码已经部署。

本项目采用 `article/Mx-yy` 形式绑定主线文章代码快照。写文章时要确认编号、标题和快照对应，不要复用或移动已经公开的 tag。支线文章如果只解释通用知识，不一定需要独占一个项目版本 tag；以路线图与项目约定为准。

## 八、协作时的简单提交约定

提交信息最好描述“做了什么”，不是“修改”“更新”。Conventional Commits 的结构是 `type(scope): 描述`：

```text
feat(api): 增加文章搜索筛选
fix(auth): 修复并发刷新令牌重放
docs(articles): 完成B-03 Git基础文章
```

`type` 表示变更类型，`scope` 表示影响范围，后面用简洁描述说明结果。团队可以约定中文，也可以用英文；一致比语言更重要。提交前查看 `git diff --check`、测试结果和未跟踪文件，不要把提交消息当成测试报告。

## 小结：让每次改变都有上下文

把一个完整主题作为提交单位，先审查暂存差异再提交；用短分支隔离工作，明确 merge/rebase 对共享历史的影响；撤销时区分本地改动与已共享提交；用 tag 标定可复现版本。Git 不是替你理解代码的工具，但它能让理解、讨论和恢复都有可追踪的依据。
