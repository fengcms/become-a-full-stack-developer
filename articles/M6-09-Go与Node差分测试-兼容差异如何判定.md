# 成为全栈·Go 后端篇·契约一致性与差分测试：两套实现如何互相校验

> 两个后端返回相同 JSON，不代表整个系统等价；一个已知差异也不一定是缺陷。差分测试要严格保留关键行为，只规范化明确的随机部分，再由契约和产品事实判断差异。

> 差分快照：Node 提交 7effc0276ffdf2fbd8183ec2e60d544ed8998bec；Go 提交 ceac4e0；契约 1.12.0。

## 前言：同名字段是最弱的一种兼容证据

Go 重写常见的“兼容测试”是用相同请求分别调用两套 API，然后比较响应 JSON。这个思路正确，但如果比较脚本忽略很多字段，或者把测试差异一律列进允许列表，结果全绿也没有证明力。

M6 的差分执行器使用隔离 seed、受控时间、微信替身和中立请求 trace。它保留 HTTP 状态码、业务码、字段是否存在、null、类型、ID、数组顺序和计数，只对明确随机的 token、随机微信用户名和生成时间做规范化。

74 次成功流程请求覆盖全部 68 个 operation，71 项比较完全一致；3 项已由契约与产品证据解释。另有 111 次针对 47 个受保护 operation 的鉴权失败比较，111 项全部一致。本文解释如何阅读这些数字、处理不一致，以及为什么不应以全部 green 为唯一目标。

## 一、先冻结输入与运行条件

差分的双方必须使用明确版本。Node 固定在 v1.0.4 commit，Go 固定在业务代码快照 ceac4e0，OpenAPI 版本为 1.12.0，SHA-256 记录在验证报告。客户端请求不是人工分别敲两遍，而是从中立 trace 生成，包含 method/path、身份、前置数据、请求体和预期操作。

两边使用隔离数据库、相同初始数据和受控时钟。微信身份用测试替身提供相同 openid，local storage 避免 R2 网络因素。测试请求不触碰生产网络、账号或数据。只要数据库 seed 或时间不同，文章 ID、通知时间和阅读窗口就可能不同，比较会失去意义。

中立 trace 还要声明请求后的状态检查。例如创建文章后，后续审核、通知和列表请求依赖刚写入的数据。若两边执行顺序不同，差异可能来自测试准备，而不是实现。

## 二、规范化要像白名单，越少越好

有些响应自然包含不可预测值：签名 token、随机微信用户名、受控生成时间。可以对这些字段建立明确 path 白名单，将两边值替换成占位符后比较。所有其他值都应该严格匹配。

不应该因为某个数值不同就忽略整段 data；不应该把数组排序后再比较，因为数组顺序可能是契约；不应该将所有 null 转成缺失，因为客户端会以此区分清空和未定义；不应该把所有状态码归一成“成功/失败”，那会隐藏鉴权差异。

把可规范化路径作为独立数据保存，脚本应能显示规范化前后的值。若必须新增一条白名单，评审要问它为何随机、来源是什么、是否能用固定时钟或种子消除随机性。白名单是例外证据，不是调成全绿的旋钮。

## 三、真实结果包含三项明确差异

本轮成功流程里有三项差异，分别对应三个 operation：

| Operation | Node 结果 | Go 结果 | 判断依据 |
|---|---|---|---|
| search | 默认 pageSize=20 | 默认 pageSize=10 | 冻结契约规定搜索默认 10 |
| listMyNotifications | 1 条系统消息、分页默认 20 | 2 条消息、默认 10，其中多出文章发布通知 | Node 没有生成产品定义的发布通知；Go 按业务事件写入 |
| getUnreadNotificationCount | count=1 | count=2 | 与新生成的发布通知对应 |

通知差异不能只忽略“列表不同”。脚本进一步检查通知类型、标题、正文、链接、未读标志和确切增量；搜索差异只允许默认分页大小不同，其余文章列表和计数仍需相同。鉴权失败则 111 次比较无差异。

每项差异先有证据再决定。search 以冻结契约默认值为准，Go 行为正确；通知则要区分契约与历史 Node 源码：冻结产品流程要求发布产生通知，Node 缺失这项行为，Go 补齐它。报告既记录 Go 与 Node 的差异，也记录为什么没有照搬 Node 实现。

差异数量小不等于业务全覆盖。报告明确指出，其他边界由 Go schema 和领域断言验证，185 次差分并未穷尽所有参数组合。

## 四、鉴权差分为何单独计数

成功流程回答业务操作能否按同一请求完成；鉴权失败单独检查未带 token、过期/无效 token、角色不足和资源归属等失败路径。若把失败流程混进成功计数，报告看不出权限覆盖是否完整。

鉴权差分场景针对 47 个受保护 operation，共 111 次请求；两边状态码和业务码逐项一致，无预期或未解释差异。这不能证明没有遗漏的权限上下文，例如所有者身份与复杂角色组合仍应在单后端边界测试中覆盖。operation 数和请求数不同，是因为一个 operation 会有多个身份失败样例。

## 五、遇到未解释差异时怎样处理

每次 mismatch 都依次查看：

1. 请求、身份和前置数据库状态是否一致；
2. 原始响应中哪些字段不同，是否实际受规范化；
3. 对应 OpenAPI schema 和响应 envelope 怎么定义；
4. Node 源码与产品文档表达了什么；
5. 差异是明确兼容要求、历史实现 bug，还是 Go 实现缺陷；
6. 若有意保留，是否会让现有客户端产生影响，后续是否需要契约版本变更。

只有完成这条证据链，才能把差异加入 expectedDifferences。发现 Node 与契约不一致时，不应在差分工具里把 Node 行为当作真理，也不该擅自改契约满足 Go 生成器。要记录决策来源并保持 OpenAPI 冻结边界。

## 六、差分和单实现验证互补

Node/Go 之间相同，仍可能都违反 OpenAPI；因此每项成功响应还要单独通过 schema 校验。两边都返回 200，却在数据库重复创建 relation，也要通过后置状态断言发现。差分是一种观测对照，不是完整测试策略。

M6 把证据组合起来：契约 schema 验证结构；边界测试验证身份和输入；领域测试验证状态与关系；真实数据库测试验证方言；差分 trace 检查跨实现行为；客户端 smoke 验证调用者能否继续使用。每种方法的盲区不同。

## 小结：允许差异要有理由，不要用它们逃避兼容

差分测试要固定双方版本、输入、数据和时钟，最小化随机值规范化，并保留状态、空值、类型、顺序、ID 和计数。M6 的 74 次成功请求有 3 项明确产品差异；111 次鉴权失败请求全部一致。它们共同给出一张可审阅的兼容快照，而非“全系统完全等价”的绝对承诺。

测试目标不是让比较器变绿，而是解释哪些行为必须一样、哪些历史差异应被修复、哪些边界尚未覆盖。这样，差分工具才是产品和工程决策的证据。
