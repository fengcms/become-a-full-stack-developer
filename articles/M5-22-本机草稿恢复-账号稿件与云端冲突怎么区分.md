# 成为全栈·Taro 小程序篇·本机草稿恢复：账号、稿件与云端冲突怎么区分

> 本机草稿是用户输入的恢复材料，不是服务器读取缓存。它需要更明确的归属，也需要让作者自己选择是否恢复。

{{IMG:M5-22-封面}}

## 前言：自动保存，保存到哪里了

移动端写文章最怕误触返回或临时离开。加一个自动保存很自然，但“保存了”三个字也容易误导：作者以为已经上云，实际只是本机存储；换账号以后，又可能看到别人的文本。

当前编辑器明确区分本机草稿和服务器稿件。输入约六百毫秒后写本机，保存文章才写服务器，提交还推进审核。本机恢复材料按环境、会员和稿件隔离。

这篇讲它的键、时机和恢复选择，也解释为什么更新时间提醒不能自动解决多设备冲突。

## 存储键就是归属清单

草稿的读写都落在一个由 API、userId 与 id 拼成的键上：

```ts
// src/core/drafts.ts（节选）
export const draftKey = (userId: number, id: string) => `befull:draft:${API}:${userId}:${id}`;
export function saveDraft(userId: number, id: string, value: Draft) {
  Taro.setStorageSync(draftKey(userId, id), { ...value, updatedAt: new Date().toISOString() });
}
export function readDraft(userId: number, id: string): Draft | null {
  const value = Taro.getStorageSync(draftKey(userId, id));
  return value && typeof value.title === "string" && typeof value.content === "string"
    ? value
    : null;
}
export function deleteDraft(userId: number, id: string) {
  Taro.removeStorageSync(draftKey(userId, id));
}
```

API 防本地与线上编号重合，userId 防会员互串，id 区分不同稿件。新稿没有服务器 ID，暂时使用 new；创建成功后再迁移。

readDraft 取出之后还检查 title 与 content 是不是字符串，形状不对就返回 null。这一步把“存了别的键”与“存了可用的草稿”分开：键对不上会读空，键对上了但对象已经损坏，也当作没有草稿，而不是把一个残缺对象塞回表单。写入端每次都会补一个 updatedAt，读取端却不依赖它——时间只用于向作者展示，不参与恢复判定。

这比“draft”一个固定键多几段字符串，却挡住了非常直接的一种数据损失：A 写到一半退出，B 新建文章，把 A 的文本覆盖。隔离键也让清理当前稿件不需要删除整个设备的创作材料。

但同一会员的未创建稿件当前只有一个 new 槽位，不是多本地文档管理器。若要同时保存多篇还没上云的新稿，需要本机独立 ID、目录和迁移关系，不能仅增加一个列表入口。

## 隔离键这件事，是我补第二次才补对的

草稿键要隔离账号，这件事我第一版就想到了。**但我漏了一个维度。**

当时我的键是 `befull:draft:${userId}:${id}`。用本地测试后端联调时一切正常 —— 直到我把构建切回线上，打开编辑器，**看到了本地测试时写的那段文字。**

原因和 M5-01 那个存储键是同一个：**本地环境的会员 1 和线上环境的会员 1 是两个不同的人，而我的键里只有 `1`。**

修法是加上 `API`：

```ts
// src/core/drafts.ts（节选）：键里必须同时包含环境、会员和稿件。
export const draftKey = (userId: number, id: string) =>
  `befull:draft:${API}:${userId}:${id}`;
```

**我漏掉它的原因很具体：本地开发时 `userId` 恰好是够用的唯一维度。** 也就是说，我在"只有一个环境"的情况下把问题解决了，然后带着这个假设去了两个环境。

> 这已经是同一个坑在本项目里的第三次出现（M5-01 会话键、M5-01 草稿键、草稿键补 API）。

所以现在我给自己定了一条：**凡是要跨环境或跨账号隔离的数据，键里必须同时包含这两个维度** —— 因为我几乎不可能只在一个环境下验证它。

**这条规则的价值不在于记住了某个具体的键写法，而在于它告诉我"我该在什么时候怀疑自己的键"。**


## 本机更新时间和云端更新时间不是一个指标

saveDraft 写入本机时加 updatedAt，用来告诉作者本机保存时间；编辑器的 baseline 则来自服务器 Article.updatedAt，用于保存前比较云端变化。

两者虽然同名，所有权不同。本机时间不是服务器版本，不能拿它做可靠的“谁更新”排序，更不能凭设备时钟判断哪份内容应该自动覆盖。设备时间可以被手动调整，也可能因为时区或休眠而跳变，一旦把它当成版本依据，恢复逻辑就会在错误的前提上运行。

Draft 恢复检查基本 title 与 content 形状，不是全面迁移和字段验证框架。如果历史存储结构变化，应增加明确版本和转换，而不是假设一个基本 shape 检查能支持所有旧稿。

| 数据 | 用途 | 不承担的职责 |
|---|---|---|
| 本机 Draft | 恢复未上传输入 | 不证明服务器已保存 |
| 本机 updatedAt | 展示保存时间 | 不作为云端条件版本 |
| 云端 baseline | 提醒外部更新 | 不提供原子 CAS |
| dirty | 决定是否保留修改 | 不代表审核或发布状态 |
| 本机草稿键 | 按环境、账号、稿件隔离 | 不加密，不防设备所有者 |
| 恢复弹窗选择 | 决定本次载入哪份文本 | 不决定服务器版本 |

这张表也是整篇的组织方式：每种数据只负责一件事，跨界的判断一律交回作者确认。

## 自动保存采用防抖，离开再补一次

draft 改变且 dirty 后设置 600ms 定时器，新输入取消旧定时。卸载与 useUnload 尝试 persist，减少最后一段输入没有等到防抖的窗口。

```ts
// src/pages/editor/index.tsx（节选）
function persist() {
  if (dirty.current) {
    try {
      saveDraft(owner, currentId.current || "new", currentDraft.current);
    } catch {
      setError("本机存储已满，草稿未能保存。请尽快保存至服务器。");
    }
  }
}
useEffect(() => {
  if (!ready || !dirty.current) return;
  const timer = setTimeout(persist, 600);
  return () => clearTimeout(timer);
}, [draft, ready]);
useUnload(persist);
useEffect(
  () => () => {
    persist();
    Taro.disableAlertBeforeUnload({ fail: () => {} });
  },
  [],
);
```

这不保证电脑崩溃或进程被强杀前最后一次按键一定存下。系统没有机会调用离开事件时，只能恢复已成功写入的版本。文章不能把防抖保存宣传成零丢失，能承诺的只是“已经写进去的那一版还在”。

当前 persist 使用最新 draft ref，防止清理回调拿早期闭包：防抖的 setTimeout 与卸载的清理都可能在旧闭包里执行，如果不从 ref 取值，最后写下的会是一段过时文本。存储满了会提示尽快保存服务器，而不是继续无条件显示“已保留”。写失败也走同一套错误出口，让本机可靠性有可见的失败文案，而不是静默丢字。

## 恢复前先读云端，再交给作者选择

已有稿件先读服务器，检查 authorId 是当前 owner，记录 baseline 与状态；随后读取对应本机草稿。如果存在，弹窗显示本机保存时间，让作者选择恢复或使用云端。

```ts
// src/pages/editor/index.tsx（节选）
const local = readDraft(owner, initialId || "new");
if (local) {
  const r = await Taro.showModal({
    title: "发现本机草稿",
    content: `保存于 ${local.updatedAt?.replace("T", " ").slice(0, 19) || "此前"}，是否恢复？`,
    confirmText: "恢复草稿",
    cancelText: "使用云端",
  });
  if (r.confirm) {
    value = local;
    dirty.current = true;
    protect();
  } else deleteDraft(owner, initialId || "new");
}
if (epoch !== sessionEpoch()) return;
setDraft(value);
setReady(true);
```

恢复会替换当前 Draft，设 dirty 并启用离开提醒；选择云端则删除这份本机恢复材料。不是只要本机时间更晚就静默覆盖服务器，也不是每次进入都重新上传。

不同进入方式，载入的两份候选其实不同：

| 进入方式 | 云端来源 | 本机来源 | 默认载入 |
|---|---|---|---|
| 新建文章 | 无 | new 键 | 空稿，本机可选恢复 |
| 编辑已有稿件 | 服务器 Article | 该稿件 id 键 | 云端，本机可选恢复 |
| 创建失败后重进 | 可能已存在 | 迁移后的稳定 id 键 | 以云端为准，本机需确认 |

新稿没有云端内容，取消恢复意味着使用当前空稿，同样会删除对应 new 材料。这个动作有实际影响，文案与用户理解应在人工回归中关注，不宜把“使用云端”无条件套到新稿当成已经完美表达。

身份在弹窗期间改变，初始化最终检查 epoch，旧账号恢复结果不写入新界面。读取键已经隔离，异步采用仍要再次检查：行是同一行，但会话可能在等待期间切换。

## 云端冲突提醒只保护一次观察结果

保存已有稿件前，编辑器重新读取 latest.updatedAt。与 baseline 不同就让作者选择覆盖。取消保留本机文本，方便稍后处理。

但 GET 后到 PUT 前仍可能出现另一次写入。当前没有服务端版本条件，因此只能叫冲突提醒，不是防丢更新的最终协议。

真正升级需要后端比较版本、返回冲突并保留两份内容；自动字段合并还要判断标题、正文与分类的语义。教学项目先明确选择，不为少见情况引入复杂合并器，但要留下诚实边界。读者应该能从这里读出一个判断：提醒有用，但它把风险推给了人，而不是由系统兜住。

## 创建与成功清理各有自己的时机

创建拿到 ID 后，本机稿从 new 迁到稳定 ID，后续提交失败还能恢复同一稿件。完整保存链路成功才删除对应恢复材料，关闭提醒。

```ts
// src/pages/editor/index.tsx（节选）
if (creating) {
  currentId.current = String(article.id);
  setId(currentId.current);
  saveDraft(owner, currentId.current, draft);
  deleteDraft(owner, "new");
  creating = false;
}
```

迁移顺序是先写稳定 ID、再删 new。反过来先删后写，一旦新写入失败，两处都没有稿件。

如果远端创建已经完成、本机迁移却失败，客户端不能简单倒退成“没创建”。当前防重复策略会保守提示检查私人列表。它保住了不盲目再 POST 的原则，但异常分类仍有改进空间。

稿件删除时也不必把该会员所有本机材料一起清掉。每个清理动作需要确定环境、owner 与 id。缓存清理只处理可再读数据，创作恢复与它分开。

## 退出后保留，与共享设备安全不是一回事

当前退出清会话和私人内存缓存，本机草稿仍按账号键保留。再次登录同一会员能找到对应文本，另一会员正常页面不会读取它。

这是一种恢复优先的选择，不是加密保障。设备拥有者或平台存储访问条件可能仍让数据可见。设置页因此提醒不要在共享设备保留敏感草稿。后续若有高敏感内容，应重新评估退出删除与存储安全方案。

主题与搜索历史也有各自设备级键，不能因为一起使用 storage，就把所有数据清理成一锅。归属决定保留策略，API 名称不决定。

## 一次恢复选择，为什么不能只比较时间

作者在手机写了半篇，电脑上又修改了同一文章。手机本机时间可能更新，却不代表它包含电脑新增的段落。较晚时间单凭决不出赢家，两个内容分支也不能自动合并。

当前弹窗把选择交给作者，后续保存前再看云端 baseline。它没有自动 diff，也没有三方合并。对于少量个人创作，明确覆盖比偷偷选一个版本更容易理解，但真正合并仍可能需要作者手动处理。

如果用户选择云端，删除的只是当前恢复键，而不是删除服务器文章；选择本机，也只是载入表单，没有立即覆盖远端。恢复与上传分开，让用户有机会预览、比较和取消。

### 本机数据要为未来升级留出解释

现在保存字段与 Draft 一致，没有独立 schemaVersion。后续新增重要字段或改变格式时，readDraft 的基本形状检查可能不够，应该明确旧值如何转换、哪些不可用部分要提示。

自动恢复失败不能成为清空原始材料的理由。可以先保留原值、提示不兼容，再提供可检查的迁移方式。教学代码当前没有完整迁移器，文章把这个边界点明即可，不直接承诺永久兼容。

### 清理与恢复要同一套键规则

save、read、delete 都使用 draftKey，减少拼写差异产生孤立材料。创建迁移则先写稳定 ID，再删除 new；不能先删 old，再尝试一个可能失败的新写入。

即便这样，存储配额和异常仍存在，所以页面保留内存文本与错误出口。可靠恢复不是单靠一行 setStorageSync，而是让归属、顺序、失败与用户选择都能被解释。

这个思路也适用于表单草稿、长评论和其他未提交输入。先判断它是否值得跨退出保留，再设计身份键与恢复动作，别把所有输入默认扔进公共缓存。

## 测试隔离，也测试“最后一段文字”

已有逻辑测试覆盖账号与稿件键隔离、标签 payload；开发工具执行了输入预览与保存提交。独立的退出再进入恢复弹窗人工路径还没完成，不写成已实测。

```ts
// test/core.test.ts（节选）
saveDraft(1, "new", d);
assert.equal(readDraft(2, "new"), null);
assert.equal(readDraft(1, "3"), null);
assert.equal(readDraft(1, "new")?.title, "标题");
deleteDraft(1, "new");
assert.equal(readDraft(1, "new"), null);
```

这段断言同时覆盖了三件事：另一个账号读不到、同一账号的另一稿件读不到、删除之后确实为空。它证明的是键的隔离，不是恢复弹窗的行为——后者需要真机路径，单靠单元测试代替不了。

建议补充：同账号两稿不串，两个环境不串，创建后 new 键迁移；输入后立刻返回，检查最新文本；存储异常保留页面输入；恢复后遇云端变化，可以取消而不丢稿。

更多失败顺序见 [投稿状态机]({{LINK:M5-20}})。本机草稿做得清楚，用户就知道自己拥有哪份内容、保存到了哪里，以及下一次该怎样找回来。
