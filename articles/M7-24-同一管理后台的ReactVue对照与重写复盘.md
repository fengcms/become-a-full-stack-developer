# 成为全栈·Vue 管理后台篇·同一管理后台的 React/Vue 对照与重写复盘

> 当同一个管理后台分别由 React 和 Vue 实现，最有价值的不是宣布谁赢了，而是观察相同契约和业务约束如何落在两套组件模型中。本文回到 M7 系列的源码、实际缺陷和验证结果，复盘一次具体的工程重写。

> 本文代码快照：React 管理后台提交 `d72df53`，Vue 管理后台提交 `d3ee41a`。契约来源为冻结的 `docs/api/openapi.v1.yaml` v1.12.0；项目后续文章及修复提交可能更新工作树，发布前应重新核对代码快照。

## 前言：为什么做第二套实现？

React 版本已经具备完整管理后台能力。重新用 Vue 实现并不是因为原版本不行，而是为了在同一产品、同一 API 契约和同一角色模型下，比较两种现代前端框架的工程表达。与从零创造一个新功能相比，复刻已有行为能把学习焦点放在状态模型、组件边界、请求缓存、路由守卫、主题系统和质量门禁上。

这是一种教学和工程对照实验，不是受控性能基准：依赖版本、组件库、代码组织、测试深度、开发时间和开发者经验都不完全相同。本文结论只适用于这两个具体仓库，不能据此推出“Vue 普遍比 React 快”或“React 更适合后台”。

{{IMG:M7-24-共用契约}}

## 对照成立的前提：共用冻结契约

两个项目都从同一份 `docs/api/openapi.v1.yaml` 生成 TypeScript API 类型，页面 API 函数仍由各自仓库维护。Vue 重写没有修改冻结契约，也没有要求后端为它增加专属端点。用户角色、文章状态、评论状态、上传字段和分页信封以 OpenAPI 为唯一协议基线。

这个前提让比较更公平：如果一个前端用 `{items,total}`，另一个用 `{list,pagination}`，差异可能来自接口，而不是框架。共用契约把接口形状约束为一致，剩余差异才更多落在 UI 组件和前端状态组织上。

不过契约相同不代表运行环境相同。浏览器配置、Node/Go 目标、环境变量、Cookie 与文件存储都可能影响联调结果；类型生成也不会自动验证线上 JSON。任何比较都要把部署和验证条件说清楚。

## 两套技术栈的真实差异

| 关注点 | React 管理后台 | Vue 管理后台 |
|---|---|---|
| UI 框架 | React 19 | Vue 3.5 |
| 组件与样式 | Radix/shadcn 风格组件、Tailwind CSS | Naive UI、语义 CSS Variables |
| 客户端共享状态 | Zustand | Pinia |
| 服务端状态 | TanStack React Query | TanStack Vue Query |
| 路由 | React Router | Vue Router |
| 表单/校验 | React Hook Form、Zod | 页面状态与 Naive UI 表单控件，按契约校验 |
| Markdown | `@uiw/react-md-editor` / preview | `md-editor-v3` |
| 质量工具 | Biome、TypeScript、Vitest | Biome、`vue-tsc`、Vitest |

它们并非每一行 API 都能一对一映射。例如 React 用函数组件和 JSX，Vue SFC 把 template/script/style 靠在一起；Zustand selector 与 Pinia composition store 的订阅和组件集成方式不同；React Router 与 Vue Router 的守卫模型也不同。迁移时应保留领域行为，不要求目录和代码长得相同。

## 同一功能在两边如何表达

### 状态与依赖

React 组件在 state 更新后重新渲染，Hooks 依靠调用顺序和显式依赖数组；Vue 用响应式 ref/reactive 收集依赖，`computed` 派生值，`watch` 处理明确副作用。两者都能让文章筛选页做到 keyword/status/page → 查询参数 → API → 表格，阅读代码时要用各自的运行模型解释，而不是把 `useEffect` 逐个替换成 `watch`。

### 服务端缓存

两端分别使用 TanStack Query 的 React/Vue 适配层。Query key 都要涵盖影响响应的参数，审核、保存和删除后都要让相关缓存重新可信。库名相同不代表可以忽略适配层差异；错误状态、ref 包装和模板解包需要各自理解。

### 导航和权限

React 路由使用 RequireCan/guard 结构，Vue 用 route meta 加全局 beforeEach；两边共用纯权限领域函数的思想：菜单、直接 URL 和操作按钮从同一能力模型推导。后端仍执行最终授权。

### 主题

React 使用 `next-themes` 管理系统/手动主题类和主题 context；Vue 通过 Pinia UI store 监听媒体查询，并驱动 CSS `.dark`、Naive UI `NConfigProvider` 和 Markdown 编辑器。它们都需要把主题传到第三方组件，不能只改页面背景。

## 真实缺陷比框架印象更有教学价值

M7 重写过程中用户发现过分页只显示第一页、登录页过于简陋、没有暗色模式、侧栏没有收起按钮和配色偏向前台等问题。这些不是某个框架天生的问题，而是需求梳理、实现覆盖和验收反馈的结果。

分页问题尤其说明端到端数据链的重要性：接口已经返回 `total=85` 和 `totalPages=9`，但 Vue 表格还需要 `remote`、受控 page、正确 `itemCount` 和页码回调；点击后 Query key 和请求参数必须变化。修复前端映射才是正确方向，不是造本地页数。

批量失败展示也提供了一个真实对照：Vue 当前用 `Promise.allSettled` 并行执行，汇总失败数量后清空选中状态；React 版按顺序执行、保留失败 ID，并展示逐项错误。两个版本目标相似，恢复体验却不同。重写不等于自动达到完全一致，差异应该显式记录，再由产品判断是否补齐。

还有一些差异可能是债务而非框架特点：例如新文章尚无 ID 时上传附件无法直接关联 articleId；移动抽屉虽有遮罩、aria label 和滚动锁，还需要继续确认 Escape/焦点管理；组件级和 E2E 测试也未在 Vue 项目中系统化建立。把这些真实边界写清，比在总结里宣称“全面复刻完成”更有帮助。

## 代码规模和性能不能用单个数字下结论

Vue 生产构建会拆分路由和第三方模块，文章编辑器的 Markdown/语法高亮依赖可能形成较大的独立 chunk。只报 Vite transform 模块数或最大的单块 gzip，就不能说明用户首屏加载、切换页面或重复访问的整体体验。

公平的性能比较至少需要相同设备、浏览器、网络、数据、构建模式和压缩/缓存策略，测量首屏资源、交互时延、主要 chunk、内存和网络请求，并多次运行取稳定区间。若没有这些条件，文章只可以说“当前构建产物包含某些分块”，不能把它升格成框架速度结论。

源文件数量或代码行数也受拆分方式影响：React 可能把表格列、hooks、弹窗拆到独立文件；Vue 页面可能集中在一个 SFC。文件更少不等于复杂度更低，行数更少也不等于维护性更高。应根据页面职责、变更频率、复用和可测性讨论边界。

## 质量证据：本轮实际验证了什么

撰写 M7-23 后，当前本地 Vue 工程的门禁结果是：

- `pnpm check`：Biome 检查 62 个文件通过。
- `pnpm test`：4 个测试文件、12 个测试通过。
- `pnpm typecheck`：`vue-tsc` 通过。
- `pnpm build`：Vite 8.3.4 转换 6266 个模块后完成生产构建。

这些结果证明当前工作树中的静态质量检查、测试和 Vue 生产构建通过；它们不证明线上 Cookie、CORS、静态托管 history fallback、对象存储或真实用户写入已经验收。Vue 项目当前包含权限、请求、UI store、路由测试，但没有完整的 Playwright/Cypress 浏览器 E2E 项目。React 与 Vue 的测试数量也不适合直接当作实现质量排名。

发布时还要核对工作树是否变动、门禁是否因最新修改需要重跑。上述结果属于本轮运行快照，不会自动覆盖 M7-01/M7-02 文章注明的历史 commit，也不构成线上部署报告。

## 哪些经验可以带到下一次重写？

1. **先冻结行为基线**：列页面、角色、状态流、错误行为和契约端点；不要以像素差作为唯一验收标准。
2. **分清状态所有权**：本地交互由页面管理、跨页面偏好由 UI store 管、服务器数据由 Query 缓存、导航状态按需要进 URL。
3. **先跑通纵向切片**：登录→受保护页面→一个真实列表→一项 mutation→缓存刷新；再扩展所有页面。
4. **双端对照契约**：同一 schema 生成类型，API 函数不散落到组件里，发现矛盾先查 OpenAPI。
5. **留出体验验收**：分页、窄屏、暗色、空态、上传失败和权限拒绝要做成可验证场景。
6. **报告证据范围**：单测、本地浏览器、测试环境和生产数据验证分开记录。

这些原则适用于重写项目，但不是某一框架专属套路。Vue、React 都需要明确数据来源、权限边界、失败语义和发布验收。

## 本系列到此结束，后续文章如何继续？

M7 的 24 篇从迁移基线、工程基座、SFC、响应式、OpenAPI、request/session/router、store/query，到分页、仪表盘、文章/评论/分类用户页面、主题、响应式导航、测试、门禁和最终复盘。每篇的例子以 `manage-frontend-vue/` 当前实现为主，并与 React 版本或契约对照。

文章不是代码冻结声明。后续代码审阅、线上验证和用户反馈可能引出新修复；发布前应核对每篇顶部的代码快照、发布辅助信息中的 TODO 和仓库当前状态，更新示例与链接。特别是没有真实生产凭证的事项，不要为了让系列看起来完整而写成已通过线上验收。

## 小结：同一契约让差异可读，边界让结论可信

这次 Vue 重写展示了两套框架如何承载同一后台业务，也暴露出重写过程里那些与框架无关的工程问题：分页契约映射、移动导航、主题、文件关联、测试范围和验收证据。最可靠的结论不是某个框架“胜出”，而是我们能够从真实代码解释每个选择、差异、缺陷和未验证边界。

如果你跟着本系列动手，建议把两套代码同时打开，选同一个用户路径，从路由一路追到请求、缓存和后端契约，再自己完成一项小改动并比较调试过程。能解释为什么这么做，才是复刻带来的工程学习成果。
