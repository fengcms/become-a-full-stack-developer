# 成为全栈·Node 后端篇·微信登录与首次账号设置：把平台身份接到自己的用户体系

> 微信证明的是一个平台身份。会员的文章、收藏和评论，仍然应该归属于我们自己的 userId。

{{IMG:M1-33-封面}}

## 前言：没有密码，也可以是一个完整会员

开发小程序时，一个看似矛盾的要求摆在面前：用户点一下微信登录，就能阅读、评论、投稿；但他可能还没有用户名密码。

我最初很容易把“注册完成”和“密码设置完成”当成同一件事。毕竟前面的注册接口，用户名、邮箱、密码一次提交，后面的逻辑自然就默认每个用户都有本地凭据。

微信登录把这个假设拆开了。一个人可以已经是我们系统的会员，却还不能走密码登录。

这篇就沿着这个变化，讲清楚三件事：平台身份怎样映射到 userId，未设置密码的会员怎样存储，以及首次设置凭据怎样避免并发重复和误撤销会话。JWT 的基础实现仍沿用前文，我们只补新增的身份逻辑。

> 本篇基于 2026-10-07 后续实现。完整代码见 `src/services/wechat.ts`、`src/services/setup-account.ts`；不是原 node-backend-v1.0 快照的一部分。

## 一、code 先交给后端，业务接口继续认 JWT

客户端通过 `wx.login` 取得临时 code，提交给：

```text
POST /api/v1/auth/wechat/callback
```

后端向固定微信接口交换结果，再查自己的会员、签发原有 `AuthResult`。流程可以画成两段：

```text
小程序 → code → Node 后端 → 微信验证 → 平台身份
                      ↓
               查找或创建 userId
                      ↓
             accessToken + refreshToken
                      ↓
             原有文章、评论、投稿接口
```

我没有让业务接口接收微信 code，更没有把 AppSecret 放进小程序。这样文章系统不用到处判断“这个请求来自密码还是微信”，授权仍基于会员、角色和资源归属。

微信 session_key 也不是我们的访问令牌；它不下发给客户端，不进入文章、收藏或评论表。本项目把“验证平台身份”压在认证服务这一处。

## 二、身份映射独立成表，不改文章归属

新增 `wechat_identities` 保存 app_id、open_id、user_id。身份空间用 `(app_id, open_id)` 表达，而不是单独使用 open_id。

| 数据 | 所属职责 | 本次约束 |
|---|---|---|
| app_id + open_id | 识别平台身份 | 联合唯一 |
| user_id | 连接自己的会员 | 一名会员仅一个微信身份映射 |
| users.id | 所有业务数据归属 | 设置用户名时不变 |
| username + password_hash | 本地密码凭据 | 可以在微信建号后设置 |

“一个会员仅一个微信身份映射”来自本期单小程序、无绑定合并的范围，不是所有产品都应照搬的限制。

首次登录先查询映射，没有才建号。只写“先查后插”还不够：两个请求可能同时查到不存在。因此创建会员和映射必须原子执行，并让唯一约束处理竞争。

`authenticateWechat` 的关键结构如下，省略了 SQL 参数细节：

```ts
let user = await find();
if (!user) {
  try {
    // 同一原子批次内：创建 users，再插入微信身份映射。
    await atomic(db, createUserAndIdentityStatements);
  } catch (error) {
    if (!isUniqueConstraintError(error)) throw error;
  }
  user = await find();
  if (!user) throw new AppError(ErrCode.INTERNAL, 500);
}
```

这是讲解用的精简结构，批次变量代表源码中的两条 SQL。重点是竞争失败后**重新读取已经提交的同一身份**。不能随便抓住一个唯一冲突，就把别的会员当成登录成功。

批次失败会回滚新会员，避免留下没有微信映射的孤儿账号。随机用户名碰撞后如果仍查不到该微信身份，也会失败，不会误认用户。

## 三、随机密码哈希存在，不等于允许密码登录

旧表的 `password_hash` 非空。如果为了微信登录把它改成 nullable，密码验证、管理员重置、历史迁移和类型定义都要重新检查。

本次选择保留结构：微信建号时产生不可预测的随机值，只保存它的哈希，原值丢弃；同时增加 `credentials_configured`。

| 用户状态 | credentials_configured | 密码登录 | 首次设置 |
|---|---|---|---|
| 历史密码会员 | 1 | 允许正常验证 | 拒绝 |
| 微信新会员 | 0 | 拒绝 | 允许检查资格 |
| 微信会员已设凭据 | 1 | 允许正常验证 | 拒绝 |
| 禁用会员 | 不改变原状态 | 拒绝 | 拒绝 |

历史迁移默认 1，微信创建显式写 0。`src/services/user.ts` 的密码入口明确检查：

```ts
if (!user.credentialsConfigured ||
    !(await verifyPassword(password, user.passwordHash))) {
  throw new AppError(ErrCode.USERNAME_OR_PASSWORD_ERROR, 401);
}
```

这里使用项目实际的 401 / 1001 错误码。这里不能依赖“随机密码应该猜不到”来替代资格判断。

微信身份服务最后仍检查禁用状态。快捷登录改变认证来源，没有豁免账号管理规则。

## 四、首次设置，真正的锁在 UPDATE 条件里

客户端看到 `canSetCredentials=true`，显示入口；服务端收到提交后，还要查会员是否存在、活跃、未设置，并确认有微信身份。

预检查能提供合理错误，但挡不住两个同时到达的请求。真正约束一次成功的，是 `setup-account.ts` 的条件更新：

```sql
UPDATE users
SET username=?, password_hash=?, credentials_configured=1, updated_at=?
WHERE id=? AND status='active' AND credentials_configured=0
AND EXISTS (
  SELECT 1 FROM wechat_identities WHERE user_id=users.id
);
```

第一条更新成功后，条件已经不再成立，第二个请求不会覆盖用户名密码。实现检查受影响行数必须等于 1，否则返回 409。

同一原子批次的下一条语句是：

```sql
UPDATE refresh_tokens SET revoked_at=?
WHERE user_id=? AND revoked_at IS NULL AND changes()=1;
```

为什么要带 `changes()=1`？设想请求 A 设置成功并拿到新刷新令牌；请求 B 是竞争失败方。如果 B 无条件撤销所有 refresh，就可能把 A 的新会话也撤销。关联上一条更新的结果，让“更新会员”和“撤销旧会话”属于同一个成功者。

用户名唯一约束冲突，则整个批次回滚。用户名、凭据状态、旧刷新令牌不应各成功一半。

SQLite 通过事务执行，D1 通过 batch 执行，差异收在 `src/db/atomic.ts`。我不让业务服务到处判断当前部署在哪里。

这里保留少量显式 SQL，是因为受影响行数与上一条语句的结果直接参与业务判断。把它们藏进几个彼此独立的 ORM 调用，看上去更统一，实际更难看清原子边界。代价也明确：这段依赖 SQLite/D1 的语义，未来若增加另一种数据库，要重新实现并验证适配层，不能只换连接字符串。

## 五、数据库提交完成，响应却没到怎么办？

路由在批次完成后调用 `buildAuthResult`，签发并保存新的刷新令牌，返回统一登录结果。这里有一个不能糊弄过去的边界：**账号更新与旧 refresh 撤销是原子的，新令牌签发和客户端收到响应不属于那个数据库批次。**

所以，网络超时不一定意味着设置失败。客户端盲目重复提交，可能得到“已经设置”的 409。

恢复策略不是重新造一个账号，而是用新密码登录，或重新微信登录，读取这个会员的最新资格。userId 没变，原来的收藏和投稿也不用搬家。

旧 access JWT 则沿用既有到期策略。撤销 refresh 不等于所有已签发 JWT 立即失效。若产品要求即时踢掉全部设备，需要另加访问令牌撤销机制，本次没有顺手承诺。

## 六、把最难的失败路径写进测试

`test/routes/wechat.test.ts` 并不只断言登录返回 200。我们检查的是状态能不能保持一致：

| 测试场景 | 要保护的事实 |
|---|---|
| 同一身份重复登录 | 返回相同 userId，只创建一人 |
| 并发首次登录 | 唯一竞争不留下额外账号 |
| 并发首次设置 | 仅一方成功，另一方不能撤销成功者会话 |
| 用户名占用 | 原状态、原 refresh 保留，换名后可重试 |
| 设置后密码登录 | userId 与昵称不变，旧 refresh 不能继续刷新 |
| 禁用及未设置用户 | 微信、密码、首次设置各入口遵守限制 |

这些使用模拟微信响应验证业务规则。另有真实开发者工具 code 接入线上服务，已经进入“微信会员”的会员中心。

但真实身份的重复登录、实际设置密码后在 APP/网站登录，尚未逐项人工操作。业务测试能证明构造场景下的规则，不能替代平台和真实跨端的全部验收。

## 小结

这次最值得带走的，是把身份、凭据和业务归属分开。微信身份帮助找到会员；用户名密码增加一种登录方式；文章始终属于稳定的 userId。

各位看官，少做绑定合并，并不意味着少处理异常。并发、冲突和结果不确定，才是这条“小流程”真正容易出问题的地方。把它们保护好，比给账号中心多添几个菜单更有用。
