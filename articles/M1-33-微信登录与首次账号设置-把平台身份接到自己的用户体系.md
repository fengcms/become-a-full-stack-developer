# 成为全栈·Node 后端篇·微信登录与首次账号设置：把平台身份接到自己的用户体系

上一篇讲了怎么把"加一个微信登录"这个需求收回成三个端点。那是决策层面。

这一篇进到代码里，讲三件上一篇没细讲的事：

**第一，同一套 SQL 怎么在 SQLite 和 D1 上都跑。** 第二，一个"看起来应该做成完整会员"的微信用户，到底怎么表示"还没有密码"。第三，怎么证明这套东西在并发下不产生双份数据。

先说清一个前提：上一篇说的随机密码、唯一索引那些已经讲过了，这里不重复。

## code 换的是身份，不是令牌

客户端拿到 code，交给后端：

```text
小程序 → code → Node 后端 → 微信验证 → 平台身份
                      ↓
               查找或创建 userId
                      ↓
             accessToken + refreshToken
                      ↓
             原有文章、评论、投稿接口
```

**整个链路上只有一处接触微信凭证，其余全是本地流程。**

而且这里有两个"没有"值得说：

**没有让业务接口接收微信 code。** 文章、评论、投稿这些接口只认 Bearer token，不判断"这个请求来自密码还是微信"。

**没有把 AppSecret 放进小程序。** 这条更容易犯——因为小程序的 code 交换天然发生在客户端侧，很多教程就直接在小程序里调 `jscode2session`。

那做不了吗？做不了。因为 `jscode2session` 需要 `appid` 和 `secret`，而 **secret 是服务端的凭据**，放进小程序包等于公开给所有人。

而 code 本身也是有有效期的（通常五分钟，且一次性）。**一个能拿到有效 code 的人，就可以用别人的身份登录。** 所以 code 必须由服务端接收、由服务端去换——**它的价值在于"只在这个 App 里才有"，而 App 包是可以被反编译的。**

还有一个更隐蔽的：**微信的 `session_key` 不是访问令牌。**

`session_key` 是微信用来解密用户敏感信息的密钥，它**不该下发到客户端，也不该进我们任何一张业务表**。本项目把它完全限制在认证服务内部——用完即弃。

而我们自己签发的 JWT 才是唯一进入业务链路的凭据。**这两套凭据的生命周期、撤销方式、信任范围都不同，混在一起就一定会出事。**

## 身份映射独立成表

微信身份不能塞进 `users` 表。为什么：

| 放哪 | 问题 |
|---|---|
| `users.wechat_open_id` 加一列 | 一个用户绑多个身份怎么办？加第二列？第三列？ |
| `users` 改主键 | `users.id` 是所有业务表的外键，改不得 |

所以独立成表：

```sql
CREATE TABLE wechat_identities (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  app_id TEXT NOT NULL,
  open_id TEXT NOT NULL,
  user_id INTEGER NOT NULL REFERENCES users(id),
  created_at INTEGER NOT NULL
);
```

三个设计点。

**一、身份空间是 `(app_id, open_id)` 而不是单独 `open_id`。**

`open_id` 的语义是"某个 App 内某个用户的标识"——**同一个人在微信小店和小程序里的 open_id 完全不同**。

只用 `open_id` 做唯一索引，意味着**两个不同 App 的用户可能撞上同一个 open_id**，然后被认成同一个人。现在有 `app_id` 参与，语义就准确了。

**二、`user_id` 上也有唯一索引。**

```sql
CREATE UNIQUE INDEX uniq_wechat_user ON wechat_identities(user_id);
```

**一个本地会员只能有一个微信身份映射。** 加上这个索引，"一个网站会员绑两个微信号"在数据库层面就不可能存在。

这个限制来自本期范围（单小程序、不做绑定合并）。别的产品要支持多绑定，这行索引就得去掉——**但去掉之前要想清楚：多绑定之后，登录时认哪一个？**

**三、`users.id` 在设置用户名时不变。**

这一条看起来是废话，但它是整个设计的锚点：**用户的文章、收藏、评论全部挂在 `users.id` 上，而微信登录只影响"怎么证明你是你"，不影响"你是谁"。**

## 并发登录：让唯一约束当裁判

现在说那个具体的并发问题。

先查后插，看起来够了：

```ts
const find = async () => (...)[0]?.user;
let user = await find();
if (!user) {
  // 建号
}
```

但两个请求可能**同时**查到不存在，然后各建一个用户。**结果是两个微信用户映射到两个本地会员。**

正确的做法是先查一次（这是优化，不是保证），然后把判断交给数据库：

```ts
let user = await find();
if (!user) {
  const username = `wx_${crypto.randomUUID().replaceAll('-', '').slice(0, 28)}`;
  const hash = await hashPassword(crypto.randomUUID() + crypto.randomUUID());
  const now = Date.now();
  try {
    await atomic(db, [
      {
        sql: `INSERT INTO users (username,password_hash,credentials_configured,role,email,display_name,level,status,created_at,updated_at)
        VALUES (?, ?, 0, 'member', NULL, '微信会员', 1, 'active', ?, ?)`,
        params: [username, hash, now, now],
      },
      {
        sql: `INSERT INTO wechat_identities(app_id,open_id,user_id,created_at)
        SELECT ?, ?, id, ? FROM users WHERE username = ?`,
        params: [appId, openId, now, username],
      },
    ]);
  } catch (error) {
    if (!isUniqueConstraintError(error)) throw error;
  }
  user = await find();
  if (!user) throw new AppError(ErrCode.INTERNAL, 500, '微信账号创建失败，请重试');
}
```

**注意那个 catch 块：唯一约束冲突被吞掉了。**

这不是"忽略错误"，而是**这正是它该发生的信号**——意味着另一个并发请求已经先建好了。吞掉它之后重新 `find()`，拿到对方建的那个账号，继续用。

**而"冲突之后重新查"这一步不能省。** 因为如果直接用本地那个 `username` 对应的 user 继续，你手上是个没有微信映射的账号——**数据库里多了一个孤儿会员。**

而那两条 INSERT 必须在同一个事务里。如果 users 插进去了但 wechat_identities 失败了，**就会留下一个没有任何身份映射的会员**——他永远无法登录，也永远无法被识别。

`if (!user) throw ...500` 那一行处理的是最后一种情况：捕获了唯一冲突，但重新查还是查不到。那说明冲突来自别的约束（几乎肯定是随机用户名碰撞，虽然 UUID 几乎不可能撞），**此时不能返回任何用户**——宁可不登录。

## 没有密码的完整会员

上一篇讲了随机密码哈希，这里补一个不同角度的问题：**为什么"非空"这个约束值得保留？**

我一度想过把 `password_hash` 改成 nullable，理由听起来很直接："微信用户本来就没有密码，为什么要存一个假的？"

改动的连带影响：

| 受影响的地方 | 后果 |
|---|---|
| 密码验证函数 | 要处理 null |
| 管理员重置密码 | 要决定对 null 账号的行为 |
| 历史迁移 | 老数据和新数据语义不一致 |
| 类型定义 | `string` → `string \| null`，波及所有读它的地方 |

而收益是什么？**省掉一个用户永远不知道、攻击者猜不到的随机哈希。**

代价收益比很清楚：**保持非空，加一个布尔标志表达"有没有设置"。**

而这个布尔标志在密码验证的入口处生效：

```ts
if (!user.credentialsConfigured ||
    !(await verifyPassword(password, user.passwordHash))) {
  throw new AppError(ErrCode.USERNAME_OR_PASSWORD_ERROR, 401); // 1001
}
```

**短路在前面。** `credentialsConfigured` 为 0 时，`verifyPassword` 根本不执行——**bcrypt 的成本（12 轮哈希）也不会发生**。

这不只是性能考虑，也是安全边界：**"未设置凭据的账号不允许密码登录"是一条规则，而"随机密码猜不到"是另一条。** 前者被绕过时后者还在，后者被绕过时前者还在。

四类用户的完整状态：

| 用户状态 | credentials_configured | 密码登录 | 首次设置 |
|---|---|---|---|
| 历史密码会员 | 1 | 正常验证 | **拒绝**（409） |
| 微信新会员 | 0 | **拒绝** | 允许 |
| 微信会员已设凭据 | 1 | 正常验证 | **拒绝**（409） |
| 禁用会员 | 不变 | 拒绝（1005） | 拒绝（1005） |

注意最后一行：**微信登录不豁免账号管理规则。**

```ts
if (user.status === 'disabled') throw new AppError(ErrCode.ACCOUNT_DISABLED, 401);
```

这一行在微信服务里，位置在最后。**快捷登录改变的是"怎么证明身份"，不是"你有没有资格用这个账号"。**

一个被管理员禁用的账号，用微信登录应该一样被拒——**否则禁用功能就有了绕过路径**。这是个很容易漏的点，因为它在"新增功能"的语境下很容易觉得"先不管这个"。

## 一套 SQL，两个运行时

现在讲这篇最"工程"的一部分。

项目要同时在本地 SQLite 和 Cloudflare D1 上跑，而这两个的执行模型不一样：

| | 本地 SQLite | D1 |
|---|---|---|
| 驱动 | `better-sqlite3` | Cloudflare 的 `$client` |
| 多语句原子性 | `db.transaction(() => {...})` | `client.batch([...])` |
| 事务/批次是 | **同步** | **异步** |

而业务代码需要的是**同一个函数，两种实现**：

```ts
/** 同一批 SQL 在 SQLite 事务或 D1 batch 中执行；异常整体回滚。 */
export async function atomic(db: Db, statements: Statement[]): Promise<number[]> {
  const client = (db as unknown as { $client: Database.Database | D1Client }).$client;
  if ('batch' in client) {
    const results = await client.batch(
      statements.map((s) => client.prepare(s.sql).bind(...s.params)),
    );
    return results.map((r) => r.meta.changes);
  }
  return client.transaction(() =>
    statements.map((s) => client.prepare(s.sql).run(...s.params).changes),
  )();
}
```

几个细节值得说。

**一、环境探测用 `'batch' in client`。**

不查配置、不读环境变量、不传参数——**直接探测底层对象有没有 `batch` 方法**。这看起来简单，但它避免了"配置说我是 D1，对象却不是"的那种错位。

**而 `atomic` 声明成 `async`，即使本地分支其实是同步的。** 这是刻意的：**业务代码不用关心当前是哪种运行时**，它拿到的永远是 Promise。

代价是**本地测试里每个 atomic 调用都会多一个微任务**——不影响正确性，只是理论上比同步慢一点点。

**二、返回 `changes` 数组，而不是 void。**

这是上一篇 `changes()=1` 能成立的前提：**调用方需要知道每条语句影响了多少行**。

```ts
const changed = await atomic(db, [...]);
if (changed[0] !== 1) throw new AppError(ErrCode.CONFLICT, 409, '账号状态已变化，请重新登录');
```

如果 `atomic` 只返回"成功/失败"，那就没法区分"更新了 0 行"和"更新了 1 行"——**而这两个在设置凭据这个场景里意义完全不同。**

**三、为什么这段保留显式 SQL。**

Drizzle 的写法会更统一：

```ts
await db.transaction(async (tx) => {
  await tx.update(users).set({...}).where(...);
  await tx.update(refreshTokens).set({...}).where(...);
});
```

但**你需要上一条的 `changes()` 来决定下一条要不要执行**。而 ORM 把每次 update 抽象成独立调用之后，你要拿到"影响了多少行"就得换一种查询方式——**要么另开一条语句去查（多一次往返，且不在同一个原子边界里），要么用底层 API。**

而这个原子边界恰恰是上一节讲的 `changes()=1` 的基础。**所以这里明确选择显式 SQL，并在注释里写清代价**：这段依赖 SQLite/D1 的语义，未来换数据库要重新实现并验证适配层，**不能只换连接字符串**。

顺带说 D1 用 `batch` 而不是真正的"事务"这件事本身也值得知道——**batch 保证原子性，但所有语句在同一个请求里执行**，而 SQLite 的 `transaction` 是同步逐条跑。**所以 D1 上不能把 batch 里的语句之间的结果互相引用**（比如第一条的结果被第二条用），除非在 SQL 内部实现——而我们那个 `SELECT id FROM users WHERE username = ?` 正是这么做的。

## 响应没到，不等于设置失败

还有一个边界必须单独说，因为它经常被忽略。

路由的流程是：批次执行完 → `buildAuthResult` 签发新令牌 → 返回。

而上一篇说过：**账号更新和旧 refresh 撤销是原子的，但新令牌签发和响应到达客户端，不属于那个批次。**

时序：

```text
[批次] 更新用户 + 撤销旧 refresh    ← 原子
[批次外] 签发新 refresh + 返回响应   ← 不原子
```

如果请求 B 是在 A 成功之后才到达的，它会看到"已经设置过了"——**但 A 的响应可能因为网络问题没到 A 的客户端。**

**从 B 的视角看，这是"失败"；从数据库的视角看，这是"成功"。**

而**客户端的直觉反应是重新提交**——那会得到一个 409，弹出一个"账号已设置登录凭据"的红色错误，**而用户压根不知道自己已经设置成功了。**

所以恢复策略必须是：**不要重新提交，而是换个方式确认状态**。

- 用新密码登录 → 成功即说明设置成功了
- 重新微信登录 → 读取这个会员的最新状态（`canSetCredentials` 会变成 false）

**关键在于 userId 没变**，所以原来的收藏、投稿、评论都不用"搬家"——因为根本没有第二个账号存在。

顺带说一个**本次没有承诺的事**：撤销 refresh token 不等于所有已签发的 access JWT 立即失效。

JWT 是无状态的，服务端默认不查黑名单，所以一个已经发出去的 access token 在它到期前仍然可用。

**如果产品要求"改完密码立刻踢掉所有设备"，需要额外的令牌撤销机制**（版本号、Redis 黑名单、或短有效期 + 主动刷新）。本次没做，所以我也不写成"已支持"。

**这个"没有做"的边界要说明，而不是含糊过去**——因为用户如果发现"改完密码手机上还是登录着"，会觉得是 bug。
## 一条我一开始想省掉的事

`atomic` 那个 `'batch' in client` 的环境探测，第一版我写的是读环境变量：

```ts
// 我最初的写法
const isD1 = env.ENVIRONMENT === 'production';
if (isD1) { return client.batch(...); }
return client.transaction(...);
```

本地测试全绿（因为测试环境是 SQLite），部署到 D1 也全绿——**但 D1 那条分支从来没被执行过**，因为线上根本没有对应的测试。

问题出在一个我完全没预料到的地方：**本地跑 `wrangler dev` 时，`ENVIRONMENT` 也是 production。**

于是本地用 Miniflare 跑（本地事务）时，代码走了 D1 分支去调 `client.batch` ——而 Miniflare 的 SQLite 客户端**确实有 batch 方法**（它是 D1 兼容模拟器），所以没报错，但**事务语义和真正的 `transaction()` 不同**。

最后的结果是：**本地 Miniflare 和线上 D1 表现一致了，而本地原生 Node 表现不同了。** 一个"修好一个环境、弄坏另一个"的经典案例。

改成探测底层对象之后就没有这个问题了——**因为判断依据从"配置声称我是什么"变成了"我实际上是什么"。**

而这次真正让我记住的，不是某个语法细节，而是一条判断规则：**任何"根据配置选择实现"的分支，都可能配置和现实不一致。** 而探测能力（capability）比读取声明（declaration）可靠。

顺带说，`atomic` 声明成 `async` 而本地分支同步执行，这个不一致是有意的：业务代码拿到的永远是 Promise。**代价是本地测试里每个 atomic 调用多一个微任务**，这个成本可以忽略，换来的是"业务代码不用关心自己在哪"。



## 用例名就是测试文档

最后说测试。这个项目的微信测试有十个用例，248 行。

而我想说的是**它们的命名**：

| 用例名 | 保护的事实 |
|---|---|
| 使用 Workers 支持的 manual 且拒绝重定向 | 不向跳转目标发送凭据 |
| 线上诊断仅记录原因和上游数值码 | 不记录凭据或响应原文 |
| 首次自动建号，后续回到同一会员 | 不泄露微信身份和密钥 |
| 设置后跨端密码登录同一 userId | 撤销旧 refresh，重复设置拒绝 |
| 用户名冲突整体保留原状态和刷新令牌 | 随后可重试 |
| 并发首次登录只建一人 | 设置只成功一次且失败方不撤销成功方令牌 |
| 禁用会员不能微信登录或设置 | 未设置会员不能密码登录 |
| 管理员重置关闭首次设置 | 支持原用户名密码登录 |
| 新迁移可重复执行 | 历史账号默认已设置且不改变原密码 |

**注意它们的主语全是"什么不能发生"**，而不是"什么应该返回"。

比如"并发首次登录只建一人"——它不测"返回了正确的 userId"，而测**没有多出第二个账号**。

而"并发首次登录只建一人，设置只成功一次且失败方不撤销成功方令牌"这一条，**一句话保护了三件事**：只建一人、只设置一次、失败方不撤销成功方。

这些用例名是可以直接读的测试文档。**写测试时把断言翻译成一句话再写进用例名，能让失败日志自己说明问题**——否则 CI 上只会看到一个 `expected 1, actual 0`，还得去翻代码才知道是哪件事没成立。

而有一条我必须如实说明：**真实微信身份的重复登录、以及设置密码后在 APP/网站的登录，我还没有逐项人工操作过。**

测试用的是模拟微信响应，它能证明"构造场景下的规则"，不能替代平台和真实跨端的全部验收。**这两者的区别，是自动化测试和真实验收的区别——前者证明规则，后者证明链路真的通。**

## 小结

这一篇讲了三个上一篇没碰的层面：

1. **凭据分层** —— 微信 code 和 session_key 都不进业务链路，业务接口只认 JWT。
2. **表达"没有密码"** —— 保持 `password_hash` 非空 + 独立布尔标志，让两条防线各自独立。
3. **同一套 SQL 两个运行时** —— `atomic` 探测环境后分流，返回 `changes` 让上层能判断影响行数。

而这些里最值得记住的是第 3 条背后的一个取舍：**为了让"上一条影响了多少行"参与业务判断，这段代码明确放弃了 ORM 的统一写法。**

**抽象和"看清边界"之间，总要选一个。** 这里选了后者，代价写在了注释里——换数据库要重新实现，不能只改连接字符串。

至于还没做完的那部分（真机验证、iOS、access token 即时撤销），**记下来的意义是让它们不会被忘掉，而不是假装它们不存在。**
