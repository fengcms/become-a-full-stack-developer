# 成为全栈·React 管理后台篇·Vite + React + TypeScript：搭起一个有门禁的后台工程

> Vite 创建出来的 React 项目，几秒钟就能在浏览器里跑起来。但“页面能打开”和“工程可以长期维护”，中间还隔着类型、格式、测试、构建和目录边界好几道门。

## 前言

各位看官，从这一篇开始，我们正式进入 React 管理后台。

我最早看这个工程时，它的页面其实已经能跑了。登录、侧栏、仪表盘都有，`pnpm dev` 也没有报错。若只看浏览器，很容易得出一个结论：脚手架搭好了，可以开始堆页面。

可我这些年接手旧项目，最怕的就是这种“看起来已经好了”。代码里写错一个可空值，开发服务器照样热更新；路径别名只配了 Vite，没有配 TypeScript，编辑器和构建各说各话；格式化命令顺手改了生成文件，下一次重新生成又是一大片 diff。真正折磨人的，往往不是某个页面不会写，而是工程没有明确告诉你：什么代码允许进入仓库。

所以这一篇我不急着讲布局。我们先把 React 19、Vite 8、TypeScript 6 这套工程的地基钉牢。

## 本文要解决什么

- 一套管理后台为什么需要多道工程门禁。
- Vite 别名、TypeScript 别名和严格模式怎样保持一致。
- 哪些代码应该检查，哪些生成代码应该明确排除。
- 为什么开发服务器、类型检查、测试和生产构建不能互相替代。

前置阅读：[Node 后端工程从零搭建](https://blog.csdn.net/fungleo/article/details/164186950)

## 能启动，只证明入口没有立刻崩

Vite 的开发体验很好，创建项目、安装依赖、运行开发服务器，几分钟就能看到页面。这一点没什么可挑剔的。但开发服务器主要负责转换模块和热更新，它不会替我们完成全部质量判断。

比如下面这些问题，页面可能暂时都能打开：

- 某个可空字段直接调用字符串方法，只是测试数据刚好不为空。
- 写了未使用变量，意味着一段逻辑已经失去连接。
- import 顺序和格式到处漂，代码审阅被无意义 diff 淹没。
- 测试没跑，刚修好的刷新令牌竞态又被改了回去。
- 开发模式正常，生产打包才发现循环依赖或资源路径错误。

因此我把这个项目的检查分成四道门：

| 门禁 | 命令 | 主要负责什么 | 它发现不了什么 |
| --- | --- | --- | --- |
| 类型 | `pnpm typecheck` | 空值、类型漂移、未使用声明 | 业务行为是否正确 |
| 规范 | `pnpm lint` | 格式、可疑写法、统一约定 | 接口运行结果 |
| 测试 | `pnpm test` | 已知边界与回归 | 未覆盖的视觉和交互 |
| 构建 | `pnpm build` | 生产编译、分包、资源产物 | 页面是否真的好用 |

{{IMG:M2-01-工程门禁链}}

这四个命令看着有点重复，其实各管一段。**门禁的价值不在命令多，而在失败得足够早。** 一个空值问题若能在提交前由 TypeScript 报出来，就没必要等用户点到那个页面再报白屏。

## TypeScript strict 要在项目还小时打开

当前工程把 `strict` 明确设为 `true`，同时打开未使用检查：

```json
{
  "compilerOptions": {
    "target": "es2023",
    "moduleResolution": "bundler",
    "verbatimModuleSyntax": true,
    "noEmit": true,
    "strict": true,
    "noUnusedLocals": true,
    "noUnusedParameters": true,
    "noFallthroughCasesInSwitch": true
  }
}
```

我比较赞成项目一开始就开严格模式。等几十个页面写完再开，出现的不是“一些类型错误”，而是一笔集中偿还的技术债。尤其后台接口字段多、权限分支多，`undefined` 往往只藏在少数角色或少数失败响应里，正常路径很难撞到。

当然，严格模式也不是越多选项越高级。本项目没有为了显得严谨，把所有 TypeScript 开关都打开。选择的尺度很简单：它能不能提前暴露真实问题，团队能不能持续遵守。工具若只制造绕过代码，最后大家满屏 `as unknown as`，那门禁反而失去意义。

## 路径别名必须在两套系统里同时成立

项目源码统一使用 `@/` 指向 `src/`。这件事需要同时告诉 TypeScript 和 Vite。

TypeScript 侧：

```json
{
  "compilerOptions": {
    "paths": {
      "@/*": ["./src/*"]
    }
  }
}
```

Vite 侧：

```ts
import { fileURLToPath, URL } from 'node:url'

const srcPath = fileURLToPath(new URL('./src', import.meta.url))

export default defineConfig({
  resolve: {
    alias: [{ find: '@', replacement: srcPath }],
  },
})
```

只配其中一边，会出现很别扭的分裂：编辑器认识路径，构建器不认识；或者开发服务器能跑，`tsc` 却报找不到模块。这里还有个版本细节：当前使用 TypeScript 6，`paths` 直接按配置文件位置解析，不再依赖旧的 `baseUrl` 写法。复制几年前的配置，很可能把已经过时的选项一起带进来。

别名也不能滥用。同一目录内部的紧邻文件，用相对路径更容易看出局部关系；跨模块引用再使用 `@/`。这样移动整个模块时，影响范围更清楚。

## 工具要知道哪些文件不该碰

这个项目的 `src/types/api.gen.ts` 来自 OpenAPI 自动生成，`src/components/ui` 主要是 UI 基础组件。它们和手写业务代码的维护方式不同，因此 Biome 明确排除了这些目录：

```json
{
  "files": {
    "includes": [
      "**",
      "!dist",
      "!node_modules",
      "!src/components/ui",
      "!src/types/api.gen.ts"
    ]
  },
  "linter": {
    "rules": {
      "preset": "recommended",
      "suspicious": { "noExplicitAny": "error" },
      "style": { "noNonNullAssertion": "warn" }
    }
  }
}
```

排除不是放任质量，而是明确所有权。生成文件的问题应该回到 OpenAPI 或生成器解决，直接格式化生成产物，下次执行 `pnpm gen:types` 还是会被覆盖。UI 基础组件也尽量保持上游结构，业务约束落在我们自己封装的表单和页面组件里。

规则严重度同样需要取舍。显式 `any` 会让类型链直接断掉，所以设为 error；非空断言有时用于框架边界，当前先作为 warning。把所有规则都升为 error 很容易，难的是每次提交都能守住。

## scripts 是团队真正使用的工程入口

最后把命令收进 `package.json`：

```json
{
  "scripts": {
    "dev": "vite",
    "build": "tsc -b && vite build",
    "typecheck": "tsc -b --noEmit",
    "lint": "biome check --write .",
    "test": "vitest run",
    "gen:types": "openapi-typescript ../docs/api/openapi.v1.yaml -o src/types/api.gen.ts"
  }
}
```

我不喜欢把关键命令只写在某个人的笔记里。脚本名就是工程接口：新成员不必知道工具的每个参数，也能用相同方式检查项目。CI、文档和本地开发都调用同一入口，才不会出现“我电脑上那条命令不一样”。

当前基线实测通过类型检查、69 个测试和生产构建。Biome 仍报告编辑器样式里 5 个 `!important` 警告，我们没有抬高阈值或隐藏它。告警可以经过判断后暂时接受，悄悄消音却会让后来的人误以为问题不存在。

### 本地自动修复，CI 只负责裁决

当前 `pnpm lint` 带 `--write`，适合本地开发：能安全整理的格式和 import 顺序由工具直接修掉，开发者不用把时间浪费在引号和逗号上。但 CI 里不应该依靠“检查时顺便修改”来通过。远端门禁应使用只读的 `biome check .`，发现差异就失败，让修改明确回到提交里。

这两个入口看似只差一个参数，职责却不同：本地命令帮助我把代码修好，CI 命令负责判断仓库里的代码是否已经合格。如果 CI 在临时工作区悄悄修完再给绿灯，提交本身仍然是坏的，下一位开发者拉下来照样看到差异。

类似的纪律也适用于生成类型。`gen:types` 是主动更新契约产物，不应该塞进每次普通构建；否则上游契约变化可能在构建时制造一个没有经过审阅的巨大 diff。生成、审阅、提交是一次显式动作，类型检查只消费已经确认的结果。

## 适用边界

如果只是一个当天丢弃的原型，四道门全部配齐可能确实重了。但只要项目会接后端、会有多角色、会持续迭代，严格类型和统一脚本很快就能回本。

反过来，门禁也不能证明产品正确。测试全绿的页面，按钮文案仍可能让人误操作；构建成功的 SPA，部署后仍可能深链 404。工程门禁负责缩小错误空间，无法替代真实使用。这一点我们会在 M2-20 再完整复盘。

## 小结

搭工程真正要完成的，不是让 Vite 打开一个页面，而是给后续代码划出可执行的边界：TypeScript 守类型，Biome 守代码纪律，Vitest 守已知回归，生产构建守最终产物。

各位看官以后接手一个“已经能跑”的前端项目，我建议先别急着看页面多少。先跑一遍类型、规范、测试和构建，再看看生成文件、别名和脚本有没有明确归属。地基有没有裂缝，这几步基本就能看出大半。
