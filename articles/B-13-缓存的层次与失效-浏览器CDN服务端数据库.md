# 成为全栈·基础补充·缓存的层次与失效：浏览器、CDN、服务端、数据库

> 缓存可以降低重复计算和网络等待，但它也会让旧数据继续存在。设计缓存时，最难的问题通常不是“怎么存”，而是“谁能看到、什么时候过期、写入后如何失效”。

## 前言：为什么刷新后还看到旧内容

网页更新了文章标题，浏览器仍显示旧标题；CDN 已经缓存了首页，后台发布后首页迟迟没变；App 切到另一个账号，收藏列表却出现上一个用户的数据。这些问题都可能被叫作“缓存问题”，但缓存所在层、缓存键和失效方式不同。

常见缓存分布在浏览器 HTTP 缓存、CDN/反向代理、服务端进程、客户端请求状态和数据库内部。它们有不同的生命周期和安全边界。给接口加一个 TTL 并不能自动解决所有层的陈旧数据。

## 一、缓存的是结果，必须有明确的键

缓存系统通常以一个 key 对应一个结果。key 需要包含所有会影响结果的输入：资源 ID、分页参数、排序、语言、权限范围或用户身份。若缓存键只用路径，却忘了包含 query 参数，page 1 和 page 2 可能互相覆盖；若忘了权限范围，私有响应可能被错误共享。

缓存设计先回答四个问题：

1. 缓存对象是什么：HTML、API 响应、图片、数据库查询结果还是客户端页面状态？
2. 缓存键包含哪些维度？
3. 数据允许陈旧多久？
4. 哪些写操作要使它失效？

这些问题没答案时，先不缓存通常比加一层不可解释的缓存更安全。

## 二、浏览器 HTTP 缓存

服务器可用 Cache-Control 控制浏览器和共享缓存如何处理响应。常见指令要区分：

- max-age：响应在指定时间内可直接复用。
- no-cache：可以存储，但复用前要向服务器重新验证。
- no-store：不应存储该响应。
- private：响应仅供单个用户的私有缓存使用，不应被共享缓存复用。
- public：允许共享缓存按规则保存响应，是否能缓存仍受其他指令和状态影响。

ETag 等验证器允许客户端询问资源是否变化；若未变化，服务器可以返回 304，减少重复传输。缓存仍需要正确的资源版本和验证逻辑。

会员资料、通知和账号信息通常不应进入公共 CDN 缓存。页面退出登录时清理客户端私有状态，也不能代替服务端设置正确的缓存响应头。配置错误可能让下一个用户复用上一个用户的响应。

## 三、CDN 和反向代理缓存

CDN 把可复用内容放在靠近用户的节点，适合公开文章、静态资源和图片。它使用 URL、查询参数、请求头等形成缓存键；如果缓存键策略与应用内容变化条件不一致，就会返回错误变体或旧版本。

发布文章后可以通过短 TTL 等待过期，也可以主动 purge/tag revalidate。主动失效更及时，但要维护变更到缓存键的映射；TTL 更简单，却意味着用户可能在窗口内看到旧内容。系统还可以采用 stale-while-revalidate：先返回旧值，再后台刷新；这提升体验，却必须接受短时间陈旧。

带 Cookie、Authorization 或个性化内容的响应需要格外谨慎。共享缓存若忽略身份维度，可能造成隐私泄漏。不要因为 URL 看起来是 GET，就默认可以 public cache。

## 四、服务端缓存和数据库缓存

服务端进程可以缓存配置、字典、热门查询或计算结果。进程内缓存重启后消失，多实例之间也不自动共享；若每台实例各有一份缓存，失效通知需要广播或改用共享缓存。引入 Redis 等外部缓存会增加网络依赖、序列化、容量和失效机制，并非免费加速。

数据库本身也有页缓存、查询计划缓存等内部机制。它们减少磁盘读取或重复解析，不代表应用拿到的业务结果就是最新正确的。应用层缓存与数据库缓冲池的职责不同，观察指标和失效策略也不同。

## 五、客户端数据缓存

网页状态库、移动 App repository、离线缓存可以避免页面切换时重复加载。常见策略包括：

- **fresh**：数据仍在有效期内，可直接展示。
- **stale**：先显示旧数据，同时后台刷新。
- **expired**：必须重新请求，或仅在离线时展示并标注可能过期。

公开内容缓存可以跨页面复用；会员私有数据应绑定当前会话或账号。退出登录、切换账号、权限改变时，要清理或隔离私有缓存。刷新请求可能在用户退出后才返回，因此客户端还需要会话代次或类似保护，避免旧响应重新写回新会话状态。

## 六、缓存失效策略

### TTL 过期

按时间自动失效，简单但不保证写入后立即更新。TTL 越长，命中率可能越高，陈旧窗口也越大。

### 写后删除

更新数据库后删除对应缓存键，下次请求重建。要处理“数据库提交成功、删缓存失败”和并发重建覆盖新值的竞态。

### 写后更新

成功写入数据库后同步更新缓存，读取更快但需要保证两边一致，写路径复杂度上升。

### 版本化键或事件失效

对资源带版本号，或由事件清理相关键。适合一项写入影响多个列表、详情和聚合页面的场景，但依赖映射与失败重试。

不论选哪种策略，都要先列出写操作会影响哪些读视图。例如文章发布可能影响首页、分类列表、标签列表、作者页和搜索结果。只清理文章详情键不够。

## 七、先缓存正确的数据，再测命中收益

缓存应该优化已经正确且足够常用的查询。先测数据库和接口延迟，确认瓶颈；再选择稳定的缓存键、私有范围、TTL 和失效方法。记录命中率、陈旧错误和失效失败，而不只看响应更快。

缓存还会改变压测结果。比较两个实现时，要确保缓存状态和热身方式一致，或明确说明测试的是冷读还是热读。M6 本地性能实验关闭业务缓存，避免一端热缓存而另一端冷查询；这让结果更容易解释，但仍有运行时和样本差异，不能外推到线上容量。

## 小结：缓存是一项一致性决策

缓存有多个层次，各层拥有自己的键、生命周期和安全范围。区分 no-cache 与 no-store，隔离会员数据，明确写后影响范围，监控命中与陈旧窗口。先用数据定位瓶颈，再缓存高价值、可定义失效策略的结果；无法说明如何失效的缓存，往往是未来的数据错误。
