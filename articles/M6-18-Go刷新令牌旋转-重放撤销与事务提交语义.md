# 成为全栈·Go 后端篇·刷新令牌旋转：为什么返回错误反而要提交事务

> 刷新令牌被重放时，系统要撤销整个会话族。若把业务错误直接从事务回调返回，ORM 会回滚撤销动作，安全处理恰好失效。

## 前言：事务错误和业务拒绝不是一回事

刷新接口要完成一组状态变化：找到旧 token、核验账号、原子消费旧 token、创建新 token。若旧令牌已经被用过，系统将其视为可能发生重放，需要撤销该用户当前所有刷新会话并拒绝请求。

常规 GORM transaction callback 的约定是：返回 nil 提交，返回 error 回滚。开发者看到“这次请求失败”，很自然地从 callback 返回一个 RefreshToken 无效错误。但这会让“撤销会话族”的写入一起回滚，数据库保留攻击者可继续尝试的状态。

M6 将事务执行错误与业务决策分开保存：重放时在事务内执行整族撤销，然后 callback 返回 nil，让撤销提交；事务完成之后，再把业务错误返回给 HTTP 层。这个模式不常见，却是状态安全要求的直接结果。

## 一、数据库里保存摘要，不保存 bearer secret

Refresh Token 由安全随机数生成，明文只在签发响应和客户端 Cookie/body 中短暂出现；数据库存其 SHA-256 摘要。后续请求将明文做同样摘要，再按 hash 查记录。数据库泄露时，攻击者拿到的不是可直接提交给 refresh 接口的原始 bearer token。

摘要方案改变了运维观察方式：不能从数据库恢复刷新 token；排障要依赖用户 ID、创建/过期/撤销时间和请求 ID等非秘密信息。禁止为方便调试而把明文 token 写入日志。哈希查找也需要唯一索引，确保摘要不会匹配多行。

每枚 token 有创建、到期和 revoked_at 状态。成功刷新会撤销旧行并在同一数据库事务创建新摘要。用户 logout、改密和账号管理操作可以撤销其全部未撤销会话。

签发动作集中在 `Result` 里，它同时生成明文与摘要，却只有摘要进入数据库：

~~~go
// internal/auth/service.go（节选）
// Result 签发短期访问令牌和刷新令牌，数据库只保存刷新令牌哈希。
func (s *Service) Result(db *gorm.DB, u model.User) (map[string]any, error) {
	now := s.Now()
	raw := make([]byte, 32)
	if _, err := rand.Read(raw); err != nil {
		return nil, err
	}
	refresh := hex.EncodeToString(raw)
	digest := sha256.Sum256([]byte(refresh))
	row := model.RefreshToken{
		TokenHash: hex.EncodeToString(digest[:]),
		UserID:    u.ID,
		CreatedAt: now.UnixMilli(),
		ExpiresAt: now.Add(7 * 24 * time.Hour).UnixMilli(),
	}
	if err := db.Create(&row).Error; err != nil {
		return nil, err
	}
	token, err := jwt.NewWithClaims(jwt.SigningMethodHS256, jwt.MapClaims{
		"sub":  strconv.FormatInt(u.ID, 10),
		"role": u.Role,
		"exp":  now.Unix() + 3600,
	}).SignedString([]byte(s.Secret))
	if err != nil {
		return nil, err
	}
	return map[string]any{
		"accessToken":  token,
		"refreshToken": refresh,
		"expiresIn":    3600,
		"user":         Public(u),
	}, nil
}
~~~

这段代码有三点值得停下来看。第一，`rand.Read` 填入 32 字节熵，`hex.EncodeToString` 之后明文刷新令牌是 64 个十六进制字符，猜测空间足够大。第二，`TokenHash` 存的是 `sha256.Sum256` 摘要再 hex 的结果，而返回给客户端的 `refreshToken` 字段是明文 `refresh`，两者不会相等；因此数据库泄露时，攻击者读到的列无法直接拿去提交刷新接口。第三，`ExpiresAt` 取 `now.Add(7 * 24 * time.Hour)`，刷新会话 7 天过期，而访问令牌 `exp` 只有 1 小时，两个时间尺度各司其职：短令牌压小泄漏窗口，长会话减少重复登录。

另一个细节是 `Result` 的第一个参数类型是 `*gorm.DB`，不是 `*Service` 自己保存的连接。这样它既能在 `Register`、`Login` 的事务里被调用，也能在需要时独立执行，调用方传入什么连接，写入就落在哪个事务里。

## 二、先定位记录，再锁用户并复核 token

Rotate 先根据 token hash 找到旧记录，获得所属 user ID。随后开启事务，先锁用户，再重新查询 token 行。这个顺序不依赖事务外初次查询一直有效：另一请求可能已经旋转同一枚 token，所以事务内必须复核最新状态。

PostgreSQL/MySQL 通过 database.Lock 为用户行加锁；SQLite 的该 helper 不追加 FOR UPDATE，依赖每实例单写连接和事务。所有涉及账号与 refresh token 的路径都应遵守一致的锁顺序，避免交叉锁形成死锁。

之后检查几个前置状态：旧 token 是否已撤销、是否过期、用户是否被禁用。token 消费使用带 revoked_at IS NULL 条件的更新，并要求 RowsAffected 等于 1。即使前面的读取看起来可用，条件更新仍再次表达“仅消费尚未撤销的记录”。

~~~text
查摘要得到 user id
        ↓
开启事务，锁 user
        ↓
重新读取 refresh row
        ↓
判断重放/过期/账号状态
        ↓
条件更新撤销旧 row，确认恰好一行
        ↓
创建新 token 摘要，提交
~~~

这张时序图的前半段，在代码里就是 `Rotate` 的开头：

~~~go
// internal/auth/service.go（Rotate 前半段，节选）
// Rotate 原子消费刷新令牌；检测重放时提交整族撤销，再返回业务错误。
func (s *Service) Rotate(ctx context.Context, raw string) (map[string]any, error) {
	hash := sha256.Sum256([]byte(raw))
	key := hex.EncodeToString(hash[:])
	var old model.RefreshToken
	if err := s.DB.WithContext(ctx).Where("token_hash = ?", key).First(&old).Error; err != nil {
		if err == gorm.ErrRecordNotFound {
			return nil, fault.New(fault.Token)
		}
		return nil, err
	}
	var result map[string]any
	// decision 是业务结果，txErr 是执行失败；两者不能混为回滚原因。
	var decision error
	txErr := s.DB.WithContext(ctx).Transaction(func(tx *gorm.DB) error {
		var u model.User
		if err := database.Lock(tx).First(&u, old.UserID).Error; err != nil {
			return err
		}
		var r model.RefreshToken
		if err := tx.Where("token_hash = ?", key).First(&r).Error; err != nil {
			return err
		}
~~~

事务外的那次查询只有一个用途：把明文换成 `old.UserID`，让事务知道该锁哪个用户。它不承担授权判断，因为事务里会拿 `key` 再查一次 `r`。`database.Lock(tx).First(&u, old.UserID)` 先锁用户行，`tx.Where("token_hash = ?", key).First(&r)` 再取最新 token 行——顺序反过来同样安全，关键在于所有涉及账号与 token 的路径都采用同一顺序，否则两个事务可能各持一半锁互相等待。

这里也能看到下一节要讨论的那对变量：`decision` 声明在回调之外，`txErr` 接住 `Transaction` 的返回值。两者类型相同，语义完全不同，代码在声明处就用注释把这一点钉住了。

## 三、为什么重放分支不能直接 return error

M6 将业务 decision 和 txErr 分开，回调内的分支与返回如下：

~~~go
// internal/auth/service.go（Rotate 回调与返回，节选）
		// 重放表示会话可能泄露：返回 nil 提交撤销，业务错误在事务外返回。
		if r.RevokedAt != nil {
			decision = fault.New(fault.Refresh)
			return s.Revoke(tx, u.ID)
		}
		if r.ExpiresAt < s.Now().UnixMilli() {
			decision = fault.New(fault.Refresh)
			return nil
		}
		if u.Status == "disabled" {
			decision = fault.New(fault.Disabled)
			return nil
		}
		changed := tx.Model(&model.RefreshToken{}).
			Where("id = ? AND revoked_at IS NULL", r.ID).
			Update("revoked_at", s.Now().UnixMilli())
		if changed.Error != nil {
			return changed.Error
		}
		if changed.RowsAffected != 1 {
			decision = fault.New(fault.Refresh)
			return s.Revoke(tx, u.ID)
		}
		var err error
		result, err = s.Result(tx, u)
		return err
	})
	if txErr != nil {
		return nil, txErr
	}
	return result, decision
~~~

对照这段代码，几个分支的差别就清楚了。重放分支把 `decision` 设为刷新失败，然后 `return s.Revoke(tx, u.ID)`——它返回的不是业务错误，而是撤销动作自己的执行结果。只要 `Revoke` 成功就返回 nil，事务提交整族撤销；如果 `Revoke` 失败，返回的是数据库错误，事务回滚，服务不会在撤销没有落地时假装已经处理完。过期分支和禁用分支把 `decision` 设好之后 `return nil`，事务照常提交，只是没有任何写入。条件更新的影响行数如果不是 1，处理方式与重放相同：这时很可能另一个请求刚刚消费了同一行。

最外层只有两行判断：`txErr` 非 nil 时把数据库错误原样返回，否则把 `decision` 交给 HTTP 层。业务拒绝和执行失败于是走了两条不同的路，一条提交安全副作用，一条回滚。

把每个分支摊开成表，可以更直观地看到 decision 与回调返回值的关系：

| 事务内观察到的状态 | decision | 回调返回值 | 事务结果 |
|---|---|---|---|
| token 未撤销、未过期、用户正常 | nil | `s.Result` 的 error | 提交，创建新会话 |
| token 已撤销（重放） | 刷新失败 | `s.Revoke` 的 error | 提交整族撤销 |
| token 已过期 | 刷新失败 | nil | 提交，无写入 |
| 用户已禁用 | 账号禁用 | nil | 提交，无写入 |
| 条件更新影响行数不是 1 | 刷新失败 | `s.Revoke` 的 error | 提交整族撤销 |
| 任意数据库执行错误 | 未设置 | 非 nil | 回滚 |

业务错误不是 SQL 失败。重放时期待的结果其实是“撤销写入成功，HTTP 刷新请求被拒绝”。因此事务 callback 返回 nil，让数据库提交；外层才把 decision 返回给传输层。若 `Revoke` 自身失败，它返回数据库错误，事务会回滚，服务不能假装撤销成功。

这是一种必须谨慎使用的模式。若每个业务错误都存起来然后提交，权限或校验失败可能意外保存部分更改。只有明确要提交安全副作用或审计记录时，才将决策与事务错误拆开，并写测试证明提交范围正确。

## 四、并发重放的时序

同一 refresh token 被两个请求同时使用：

~~~text
请求 A                      请求 B
查到同一 token row          查到同一 token row
锁住 user                   等待 user
复核旧 token 有效
条件撤销旧 token
创建新 token
提交、释放 user 锁
                            获得 user 锁
                            重新读取旧 token，发现已撤销
                            撤销该用户所有刷新会话
                            提交撤销
                            返回重放错误
~~~

第二个请求被识别为重放后，当前用户新刚签发的 refresh token 也会撤销。这是会话族策略的安全取舍：同一旧 token 同时出现时，无法仅凭服务端分辨是合法客户端重试还是窃取者重放，因此选择让用户重新登录。客户端应处理此类失败并清理本地会话。

这个策略需要结合网络重试理解。客户端若在服务器完成旋转后没有收到响应，再用旧 token 重试，会触发家族撤销。若要在容忍丢包的同时避免重放，通常需要更复杂的幂等窗口或设备/会话族模型；M6 沿用冻结契约现有行为，不在重写中新增协议字段。

## 五、过期、禁用和执行失败的差异

过期 token 是业务拒绝，但不一定意味着存在攻击，因此当前流程拒绝并保持其他会话；用户已禁用也拒绝签发新会话。查不到 token、数据库暂时故障、条件更新返回异常则分别映射不同执行结果。不要把所有分支统称“刷新失败”后忽略事务差异。

密码计算等高成本工作避免放在持锁期间。登录时先读账号并验证 bcrypt，再在事务内锁用户、复核账号状态和密码哈希未变化，然后签发会话。改密时也在锁外计算新哈希，锁内复核旧哈希后更新密码和撤销 refresh。这缩短锁持有时间，同时防止读取后被另一请求更改的前态覆盖。

这段描述对应 `Login` 的事务部分：

~~~go
// internal/auth/service.go（Login 的锁内复核，节选）
txErr := s.DB.WithContext(ctx).Transaction(func(tx *gorm.DB) error {
	var current model.User
	if err := database.Lock(tx).First(&current, u.ID).Error; err != nil {
		return err
	}
	if current.Status == "disabled" {
		return fault.New(fault.Disabled)
	}
	if current.PasswordHash != u.PasswordHash {
		return fault.New(fault.Credentials)
	}
	var err error
	result, err = s.Result(tx, current)
	return err
})
~~~

事务外的 `u` 来自一次普通查询，用来确认用户名存在、密码匹配；进入事务后，代码用 `database.Lock(tx)` 重新取出 `current`，并再比一次状态和密码哈希。两次读取之间账号可能已经被改密或禁用，`current.PasswordHash != u.PasswordHash` 正是用来发现这种变化的。这里也没有在持锁期间做 bcrypt 计算——`Verify` 已经在事务外完成。

撤销整族会话的动作被抽成一个独立方法，`Rotate` 的重放分支与 `Logout` 都复用它：

~~~go
// internal/auth/service.go（Revoke）
// Revoke 撤销一个账号的全部刷新会话；调用者决定所在事务。
func (s *Service) Revoke(tx *gorm.DB, id int64) error {
	return tx.Model(&model.RefreshToken{}).
		Where("user_id = ? AND revoked_at IS NULL", id).
		Update("revoked_at", s.Now().UnixMilli()).Error
}
~~~

`Revoke` 接收 `tx` 而不自己开事务，所以它既能用在 `Rotate` 的回调内部，也能用在 `Logout` 的锁保护下，提交边界交给调用方决定。

这种优化要求复核，而不是简单把锁提前释放。锁外得到的旧用户状态只是候选结果，提交时仍要确认它成立。

## 六、让测试检查提交后的事实

刷新测试应当断言记录状态，不只看 HTTP code：

| 用例 | 应检查的数据库状态 |
|---|---|
| 正常旋转 | 旧摘要 revoked，新摘要存在且未撤销 |
| 重复使用旧 token | 当前用户所有有效 refresh 都已撤销 |
| 过期 token | 请求失败，没有签发新 refresh |
| 禁用用户 | 无新会话，账号状态保持 |
| 摘要不存在 | 未误撤销其他用户记录 |
| 新记录插入失败 | 旧 token 的消费应随事务回滚 |
| 并发同 token | 按锁序执行，只允许一条正常旋转路径，重放策略有确定结果 |

PostgreSQL、MySQL、SQLite 的行锁能力与 RowsAffected 行为不同，需在真实数据库上跑并发用例。SQLite 单写连接可能把竞态序列化，但仍需验证最终 token 状态；不能据此推断 PostgreSQL 的锁行为。

## 小结：提交安全副作用，再向客户端报告拒绝

刷新流程把随机 bearer token 变成摘要持久化，成功时在一个事务内消费旧值、创建新值。重放时则要求先提交整族撤销，再返回错误。M6 用 decision 和 txErr 将业务拒绝与数据库失败分开，避免事务语义反转。

设计类似流程时，先写状态机和并发时序，再决定错误应否触发回滚。遇到“操作失败但要留下安全状态”的路径，不能机械地从事务回调直接 return error；数据库后置状态才是最终证明。
