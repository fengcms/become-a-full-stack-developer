# 成为全栈·Flutter App 篇·第四批复盘：复用了什么，移动端又新增了什么

做完 Flutter 后再看 Web 前台，最容易被“复用率”这个词带偏：两端确实消费同一份 API 契约，却没有共享 React 和 Flutter 的 UI 代码。若只报一个百分比，反而看不见这次实现真正复用的是什么。

这篇按契约、业务语义、界面和验收证据复盘 M4，再把并发会话、移动导航、原生上传与缓存边界整理成下一端开工前可以复用的问题清单。

{{IMG:M4-28-封面}}

## 复用发生在哪一层

| 复用对象 | 具体内容 | 是否共享 UI 代码 |
|---|---|---|
| API 契约 | OpenAPI operation、字段、错误语义 | 否 |
| 业务规则 | 投稿状态、收藏/点赞归属、权限约束 | 否，客户端分别实现 |
| 设计意图 | 品牌色、页面角色、交互目标 | 否，转译为各端组件 |
| 前端组件 | React/DOM 与 Flutter Widget | 否 |

契约复用降低字段和行为漂移，不会自动生成适合手机的布局。复盘要测契约覆盖、真实接口适配和端侧差异，而不是拿“共享代码行数”衡量独立客户端。

{{IMG:M4-28-复用边界}}

## Flutter 新增了哪些问题

相对网站，移动端引入了四 Tab 多栈导航、系统返回、深链接、原生 XFile 上传、OS 安全存储、设备尺寸与字号、前后台缓存刷新、有限磁盘空间和 WebView 双历史。页面数量没有翻倍，生命周期和平台边界却显著增加。

缓存复盘也改变了原路线设想：项目并未实现完整离线下载和冲突同步，而是实现受预算和 TTL 约束的公开数据复用、账号隔离的私有内存和本机稿件恢复。把“缓存”说成“离线模式”会夸大交付范围。

## 哪些证据已具备，哪些还没有

已完成 Flutter analyze、单元/Widget/集成测试、隔离本地后端写流程、Android Pixel 8 模拟器关键路径和生产匿名只读缓存样本。没有完成 iOS 真机、应用商店签名、正式发布、所有机型权限和长期弱网测试；也没有宣称远端 CI 已执行。

这些结论互不替代：真实本地写操作证明流程可行，生产只读证明特定公开读取样本可达，模拟器布局证明限定尺寸可用，均不能合并成“全平台生产就绪”。

## 下一端可以复用哪些准备

1. 先冻结并校验 API 契约，尤其是身份、错误、分页和写入幂等语义。
2. 复用领域命名与状态转换，不照搬 Flutter 路由和 Provider 结构。
3. 为目标平台重新设计导航、缓存与原生能力边界。
4. 在独立测试环境验证所有写操作。
5. 把平台验收证据写进交付文档，并明确未覆盖范围。

## 用证据矩阵替代无依据的复用百分比

“复用了多少”可以拆成更可审计的指标：契约中多少 operation 被 App 消费、关键 schema 是否自动生成、关键业务转换是否有跨端一致测试、各端还需要多少适配。代码行数不适合比较 Dart 与 TypeScript，因为语言、框架和原生能力差异巨大。

```text
契约共享：OpenAPI 源文件
端侧独立：Dart DTO/Repository/Widget 与 TS client/Server Component
行为对齐：认证、投稿状态、权限错误、分页和缓存语义
证据：生成器 + 单测 + 本地集成 + 只读线上检查
```

后续端应记录新增的契约缺口，而不是私自改变业务语义。若发现能力不够，先补契约/后端决策，再分别实现客户端适配。这样才有可能真正复利。

## 本系列可以沉淀成下一端的工程问题清单

M5 或其它客户端开工前，先用接口契约回答：鉴权是 Cookie 还是 Bearer？refresh 是否旋转？哪些端点限流？分页有无快照？私有预览是否独立？上传是否可复用附件？评论接口返回完整父楼还是需跨页重组？缓存响应头是否给出可验证的新鲜度？

再写客户端矩阵：路由恢复、账号隔离、列表错误、长内容、无障碍、文件能力、离线边界和平台发布证据。能在开发前发现契约缺口，就不必在每个客户端各写一套隐藏假设。

## M4 带来的返工提醒

最容易返工的并不是 Dart 语法，而是从 Web 经验里带来的隐含假设：详情返回后列表是否仍在原位置、多个 401 是否同时刷新、公开磁盘缓存能否包含会员数据、原生图片上传的失败是否会丢正文、TOC 与 Markdown 是否使用同一种标题规则。

这些问题适合在 M5 开发前变成验收用例。新端落地前画出请求与状态所有权图，拿真实 API 响应建 fixture，确定读写环境和返回导航；若实现过程中发现后端契约缺口，先记录并修订契约，而不是在每个端用一套互不兼容的猜测补丁。

    if ([Endpoints.categoriesTree, Endpoints.siteSettings].contains(path)) {
      return ResourceFamily.dictionaries;
    }
    if ([Endpoints.categoriesStats, Endpoints.tags].contains(path)) {
      return ResourceFamily.statistics;
    }
    if (path == Endpoints.articles) return ResourceFamily.articleList;
    if (path == Endpoints.search) return ResourceFamily.search;
    if (path.startsWith(Endpoints.memberPrefix)) return ResourceFamily.member;
    if (path.endsWith(Endpoints.adjacentSuffix)) return ResourceFamily.adjacent;
    if (path.endsWith(Endpoints.commentsSuffix)) return ResourceFamily.comments;
    if (path.endsWith(Endpoints.likeStatusSuffix) ||
        path.endsWith(Endpoints.likeSuffix)) {
      return ResourceFamily.reaction;
    }
    if (path.startsWith(Endpoints.meFavorites)) return ResourceFamily.favorites;
    if (path.startsWith(Endpoints.meLikes)) return ResourceFamily.likes;
    if (path.startsWith(Endpoints.meHistory)) return ResourceFamily.history;
    if (path.startsWith(Endpoints.meNotifications)) {
      return ResourceFamily.notifications;
    }
    if (path == Endpoints.meArticles) return ResourceFamily.manuscripts;
    if (path.startsWith(Endpoints.commentPrefix)) return ResourceFamily.comment;
    if (path.startsWith(Endpoints.articles)) return ResourceFamily.article;
    if (path.startsWith(Endpoints.profile)) return ResourceFamily.profile;
    return ResourceFamily.unknown;
  }

  /// 互动状态可读缓存，点赞写端点本身不进入 GET 缓存规则。
  CachePolicy? policy(String path) =>
      path.endsWith(Endpoints.likeSuffix) ? null : _rules[family(path)]?.policy;

  Set<String> resourceTags(String path) {
    final kind = family(path), id = Endpoints.articleId(path);
    return {
      path,
      ...?_rules[kind]?.tags,
      if (path.startsWith(Endpoints.privatePrefix)) 'private',
      if (kind == ResourceFamily.comments) 'comments:$id',
      if (kind == ResourceFamily.reaction) 'reactions:$id',
    };
  }

  Set<String> mutationTags(String path, Object? data) => switch (family(path)) {

    ResourceFamily.favorites => {Endpoints.meFavorites, 'overview'},
    ResourceFamily.history => {Endpoints.meHistory, 'overview'},
    ResourceFamily.notifications => {'notifications'},
    ResourceFamily.comments => {'comments:${Endpoints.articleId(path)}'},
    ResourceFamily.comment => {'comments'},
    ResourceFamily.article || ResourceFamily.articleList => {
      CacheTags.articleBodies,

    ResourceFamily.profile => {'profile', 'articleLists'},

## 把容易出错的路径走一遍

我会用这个场景做一次可复现排查：**把 Web 复用的接口和 App 新增能力一律套同一缓存策略**。先按数据来源逐条标注可复用、移动端新行为与身份边界；如果把问题定位在“整套照搬 Web”，修正方向是“保留稳定契约层，补足原生存储、交互与离线恢复的移动端专属策略”。最后再验证正常路径没有退化，并把边界条件留在自动化检查里。

| 方案比较 | 简化做法 | 当前实现/推荐做法 |
|---|---|---|
| 本文核心选择 | 整套照搬 Web | 复用契约、重做边界 |
| 错误处理 | 失败后清空或静默忽略 | 保留可恢复状态，给出明确反馈 |
| 验证方式 | 只检查成功结果 | 注入边界条件并检查回归 |

| 排错步骤 | 要观察什么 | 通过条件 |
|---|---|---|
| 复现 | 把 Web 复用的接口和 App 新增能力一律套同一缓存策略 | 可以稳定触发或明确构造该输入 |
| 定位 | 按数据来源逐条标注可复用、移动端新行为与身份边界 | 找到责任层和状态归属 |
| 修正 | 保留稳定契约层，补足原生存储、交互与离线恢复的移动端专属策略 | 失败不污染后续页面或账号 |

## 小结

M4 的主要复利来自共享契约和业务理解；前端实现仍然按平台独立。Flutter 带来新的会话竞态、缓存所有权、原生文件和导航挑战。真正的复盘不制造一个漂亮但无依据的百分比，而是列出复用层、差异、真实证据和未完成发布事项。
