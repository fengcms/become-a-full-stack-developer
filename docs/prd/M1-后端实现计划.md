## 〇、为什么有这份计划

API 契约已冻结（`docs/api/openapi.v1.yaml` v1.11.0，双门校验 33 OK），它本身就是一份机器可校验的实现规格。本计划不重新定义"做什么"，只解决三件事：

1. **实现顺序**：把约 65 个端点切成 8 个有依赖关系的批次，每批独立可测。
2. **工程约定**：目录结构、响应包络、错误码、鉴权、存储、测试——开发 AI 必须照此落地，使产出可被后续文章复用。
3. **验收门禁**：定义"什么叫做完"，用脚本证据而非口头自报。

你（开发 AI）的纪律：**契约是事实源，计划是施工顺序，门禁是验收标准。三者冲突时以契约为准，并把冲突反馈给总把控，绝不擅自改契约。**

## 一、技术栈与运行目标

| 维度 | 选型 | 说明 |
|---|---|---|
| 运行时 | Node.js ≥ 20（推荐 22） | 跨运行时，不绑定 Cloudflare |
| Web 框架 | **Hono** | 轻量、跨运行时（CF Workers / Node 通用） |
| ORM | **Drizzle** | schema 即类型，跨 SQLite/Postgres |
| 数据库 | Cloudflare **D1**（SQLite）/ 自管 Linux（SQLite 或 PostgreSQL） | 见下方"适配层" |
| 对象存储 | Cloudflare **R2**（主）/ 本地磁盘或 S3/MinIO（兜底） | `STORAGE_DRIVER` 驱动切换 |
| 校验 | **Zod** | 入参在最外层校验（信任边界） |
| 测试 | **vitest** + **supertest** | 端点级契约一致性断言 |
| 语言 | TypeScript（strict 全开） | `tsc --noEmit` 必须绿 |

### 适配层（高价值题材，M1-24 深讲）
同一套后端要能部署到 Cloudflare（D1/R2）和普通 Linux（SQLite/Postgres + 本地磁盘/S3）。
- **数据库连接**：抽象 `getDb()`，按环境变量选择 D1 binding 或本地 Drizzle 实例。
- **存储**：抽象 `StorageProvider`，`STORAGE_DRIVER=r2|local`，R2 为主、本地兜底。
- **开发/测试期**：一律用本地 SQLite + 本地磁盘（或内存），不依赖云账号。

> 你只需把"数据库访问"和"文件存储"两处收敛成接口，具体实现按环境注入。不要在业务代码里直接 `new D1Database()` 或硬编码 bucket。

## 三、全局约定（开发 AI 必须照做）

### 3.1 统一响应包络

> **以契约为准（v1.11.0）**：契约 `components.schemas.ApiResponse` 是事实源。本计划早期草稿的 `{data}` / `{error:{code,message,details}}` 信封与契约**直接冲突**，已在此更正——凡与契约不符的包络描述，一律以契约为准。

所有响应体形如（对齐契约 `ApiResponse`）：
```jsonc
// 成功（单对象）
{ "code": 0, "message": "ok", "data": { /* ... */ }, "requestId": "req_xxx", "timestamp": "2026-08-10T12:00:00Z" }
// 成功（列表）：data 内含 list + pagination
{ "code": 0, "message": "ok", "data": { "list": [ /* ... */ ], "pagination": { "page": 1, "pageSize": 20, "total": 100 } }, "requestId": "req_xxx", "timestamp": "..." }
// 业务错误：同样用顶层 envelope，错误明细放在 data 里（如 4001 的 data.errors）
{ "code": 1002, "message": "未登录", "data": null, "requestId": "req_xxx", "timestamp": "..." }
// 4001 参数校验失败示例
{ "code": 4001, "message": "参数校验失败", "data": { "errors": [ { "field": "email", "message": "邮箱格式不正确" } ] }, "requestId": "req_xxx", "timestamp": "..." }
```
- **信封字段固定**：`code`(业务码) / `message` / `data`(业务数据或错误明细，无数据可 `null`) / `requestId` / `timestamp`(ISO 8601)。**不要**套 `error` 包裹层。
- HTTP 状态码与业务 `code` **双层**：4xx/5xx 走 HTTP 码，业务细分走 `code`（见 3.2）。
- 分页参数约定 `?page=&pageSize=`，列表响应的 `data` 内含 `list` 与 `pagination`。

### 3.2 错误码（以契约为准）
`error.code` 取值集合见契约 `components.responses` 中各错误 schema 的 `code` 枚举。开发 AI 必须实现契约列出的**每一支** 401/403/4xx 及其 `code` 值（含 1002/1003/1004/1005/3002/3003 等）。**不要自造未在契约出现的 code。**

### 3.3 鉴权模型
- `POST /auth/login`、`/auth/refresh` 的 401 是**专用鉴权错误**（code 1001/1003/1005），语义不同于通用的未登录（1002/1004）。其余端点统一 401 = `$ref Unauthorized`。
- 角色三角 `member` / `editor` / `admin`：注册默认 `member`；`admin` 经 `PATCH /users/{id}` 升 `editor`；`editor` 管全站内容不管用户/角色/站点配置；`level` 仅展示。
- 端点授权门槛以契约 `x-authz`（minRole + ownerOverride）为准。中间件据此放行/拒绝。

### 3.4 状态机（机器化约束）
- `Article.status` 合法转移见契约 `Article.status.x-allowed-transitions`（draft→pending/published 等 6 条）。后端**必须**在校验层强制，非法转移返回 4xx + 对应业务码。
- `Comment.status`（approved/rejected/reviewing）契约未机器化，按 02 §二 语义实现：会员投稿默认 `reviewing`（管理员兜底态），`approved` 才对公开可见。

### 3.5 信任边界
所有入参在路由最外层用 Zod 校验，失败返回 422 + 业务码。绝不在深层逻辑里信任未校验输入。

## 五、验收门禁（定义"做完"）

每个批次"做完"的硬标准（开发 AI 自验，总把控验证据）：

1. **`npm run typecheck`（`tsc --noEmit`）全绿** —— strict 无 any 逃逸。
2. **`npm test`（vitest run）全绿** —— 每批至少覆盖本批端点的主干用例：
   - 成功路径返回正确包络与状态码；
   - 关键 4xx（鉴权/校验/状态机）返回契约规定的 `code`；
   - 分页端点返回 `pagination`。
3. **契约一致性自检**：响应字段、状态码、`error.code` 与 `docs/api/openapi.v1.yaml` 对应 operation 一致（可写一个小脚本用契约 schema 校验测试响应，或人工逐端点核对）。
4. **纪律自检**：本批未修改契约文件、未引入契约外的 `error.code`、未擅自加字段（如加，先在批次文件 NOTES 里登记并反馈）。

> 第 3 条是"信任但验证据"的关键：开发 AI 不靠口头说"符合契约"，而是用测试 + 对照契约的核查表交差。

## 六、开发纪律（违反即返工）

- **契约只读**：`docs/api/openapi.v1.yaml` 已冻结。发现契约缺陷 → **在批次 NOTES 登记并反馈总把控**，绝不自行改契约。
- **不炫技**：代码要能被文章逐步讲解。优先清晰、可读性，避免过度抽象的"天才写法"。
- **字段对齐**：DB 字段、响应字段命名以 02 §二 与契约为准；响应 camelCase、DB snake_case，在序列化层转换。
- **测试必带**：无测试不叫做完。
- **提交规范**：每批完成一个 commit，message 形如 `M1 B2 文章核心端点 + 测试`；不强制打 git tag（文章发布时由 M0-06 机制统一打 `article/M1-xx`）。
- **环境隔离**：开发/测试不碰云账号，用本地 SQLite + 本地磁盘。
