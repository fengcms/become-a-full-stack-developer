# M1 / M5 开发后内容增补评估

2026-10-07。依据本次小程序工程、后端微信身份增补、Cloudflare 配置及真实登录验收，更新内容路线图至 v1.19。本文件说明增补理由、文章边界和可用素材；属于创作规划，不代表新文章已经成文或发布。

## 判断

原 M5 的 8 篇适合立项时说明“为什么做小程序”，不足以带读者完成现在的产品。工程已包括 14 个页面、四个 Tab、受控 Markdown 阅读、评论叠楼、会员私人数据、投稿状态机、草稿恢复、缓存与多主题；原目录几乎没有这些实现步骤。

原目录还有三处与实况错位：

- “微信登录与账号打通”容易被读成绑定/合并已有账号。实际是微信独立建号，随后设置用户名密码，让 APP/网站密码登录该同一账号。
- “分享、订阅消息”把已实现的原生分享和未实现的订阅消息放在一起。分享可讲接线与入口，订阅消息只登记扩展边界。
- “发布与审核”容易变成真实上架教程。项目部署形态、域名和用户已确认的演示目标，应以开发工具验收及正式发布差距为主，不虚构审核成功记录。

M1 的 31 篇已有完整后端基础。本次有价值的增补来自旧系统如何接新身份、怎样兼容既有端、以及“Node 单测全绿仍在 Workers 失败”的真实事件。建议增补三篇，而非只塞入一篇综合文章；三者分别回答契约、身份和运行环境问题，每篇仍保持约 2500 字的聚焦粒度。

## Node 后端的三篇增补

### M1-32：冻结契约如何兼容增补

核心问题：已有网站、APP 和后台都使用冻结契约，新端需要微信登录，怎样增加能力而不迫使旧客户端一起改？

展开顺序：说明冻结基线 1.11.0 → 对照已有 callback 扩展点、User 可选字段与 setup-account 新端点 → 旧端缺字段默认 false → 增量迁移和兼容验证 → 登记历史与当前版本的边界。

不要把“兼容增补”写成“契约完全没变”：当前明确增补到 1.12.0。也不要把本项目的可选字段策略推广成所有客户端都自动兼容，仍需看生成器和解析方式。

素材：[最小契约增补说明](../node-backend/wechat-login/01-最小契约增补说明.md)、`docs/api/openapi.v1.yaml`、`node-backend/src/config/env.ts`、User 的 schema/序列化及迁移记录。

与 M1-20 的区别：M1-20 讲文档与代码不脱节，本篇讲多个已上线消费者面前的兼容演进判断。

### M1-33：微信身份与首次账号设置

核心问题：平台给出的临时 code，如何转换成自己系统中可持续使用的会员身份？

展开顺序：code 不是业务 Token → 后端交换与身份映射 → app_id + open_id 唯一性和重复建号冲突 → 老账号默认已配置、微信新用户未配置 → 首次设置用户名密码及旧 refresh 撤销 → 用户名占用、重复设置、禁用、并发和响应丢失。

强调 userId 和内容归属不变；随机内部密码只保存哈希，未设置用户不能密码登录；账号设置成功不等于旧 access JWT 立即失效。绑定、合并、ticket、手机号、解绑均不展开。

素材：`node-backend/src/services/wechat.ts`、`src/services/user.ts`、`src/db/migrate-wechat.ts`、`src/db/atomic.ts`、`test/routes/wechat.test.ts` 和 [本地实施记录](../node-backend/wechat-login/02-本地实施与迁移记录.md)、[线上迁移记录](../node-backend/wechat-login/03-线上迁移记录.md)。

与 M1-13 的区别：复用原有签发和刷新协议，重点增加“身份来源与登录凭据分离”的建模，不重新讲 bcrypt/JWT 入门。

### M1-34：Workers 500 的完整排查案例

核心问题：密钥已上传，单测已通过，真实登录为什么仍然失败？

展开顺序：真实 500 → 核对目标 Worker/密钥名及普通接口 → 增加静态原因诊断，不记录密钥/URL/微信身份 → workerd 复现 redirect:error 的 TypeError → manual 并拒绝 3xx → 回归证明只请求一次、不创建用户 → 部署 → 无效 code 的 401 和真实 wx.login 登录成功。

本篇最有价值的判断是：mock fetch 证明业务分支，但不能证明目标运行时接受 RequestInit 参数；密钥存在、无效 code 被拒绝、真实登录成功分别提供不同证据。不要把一次修复推广为所有 Workers 版本永远不支持某选项，注明兼容日期、运行环境和本次观察。

素材：[真实登录专项记录](../taro-miniprogram/implementation/03-微信线上配置与真实登录验收.md)、提交 `6e037c9` / `268d493`、脱敏日志与回归用例。不要为写文章复制生产密钥、Token、完整 tail 请求头或微信身份。

与 M1-24 的区别：前篇介绍双部署适配设计，本篇使用实际失败检验“相同 JavaScript API 名称不等于相同运行时行为”。M1-07/11/21 提供配置、日志和测试基础，本篇只在案例需要时引用。

## 小程序为何扩展到 24 篇

保留原 8 个编号与主题归属，修正超出实况的命题；追加 16 篇。新增不是按页面数量拆分，而是按有独立所有权和失败恢复方式的工程问题拆分。

|---|---|---|
| 工程与视觉 | 01/02/09/06/10/11 | 可复现构建、14 页与四 Tab、设计令牌和主题、理解页面生命周期 |
| 网络与数据 | 12/13/14 | 信封/单飞刷新、迟到响应隔离、有界缓存、真实内容和分页 |
| 阅读与平台 | 15/16/04 | 安全 Markdown、高亮目录、外链转换、原生分享路径 |
| 身份与会员 | 03/19 | code 登录、首次凭据入口、会员私人列表/通知/资料 |
| 互动 | 17/18 | 跨页面点赞收藏、乐观回滚、分页评论归楼和父楼缺失 |
| 创作 | 20/21/23/22 | 固定 ID 两阶段投稿、原生编辑预览、上传协调、本机恢复和云端冲突提示 |
| 验证与收尾 | 24/05/07/08 | 分层验收、演示与发布边界、APP 差异和复盘 |

编号保留意味着阅读顺序和数值顺序不同，路线图已列出推荐发布顺序。M5-08 仍为复盘，放在本组最后。新文章创作时用新增编号建立链接/tag，不重命名旧篇。

最值得独立展开的三组：

1. 请求与缓存：前者控制重试/刷新和身份，后者控制数据复用、时效、容量和写后失效。合写容易只剩一个通用 request 函数。
2. 投稿与草稿：状态机决定服务器上允许的动作，本机稿决定设备上未提交输入的存续；创建成功但提交失败、创建结果不确定与云端内容变化是不同情况。
3. Markdown 与评论：没有 DOM 的受控渲染、父评论可能跨页、异常父链与重复标题，都是“接口能读到”之后才出现的工程问题。

## 与 Flutter 篇的关系

M4/M5 可以同题互链，但不能只换框架名字复写。M5 需要写清 Taro/原生组件、页面生命周期、上传字符串响应、平台分享/外链限制、环境与账号存储键等真实差异。

比较只基于事实：Flutter 的公开磁盘缓存与小程序有界内存缓存不同；APP 有 WebView，小程序本期复制外链；双方复用 API/语义/视觉素材，未共享前端源码。没有测量的“节省比例”“代码复用率”不作为结论。

## 写作证据和边界

小程序素材见 [交付记录](../taro-miniprogram/implementation/02-开发交付与验收记录.md) 和专项真实微信记录。逻辑测试、临时 SQLite 真实后端、开发工具实际点击、生产只读与真实微信登录分别注明环境。

真实身份的重复登录、实际设置密码后跨端登录、图片选择上传、分享接收、真机键盘、弱网长期使用和正式上架尚无逐项人工验收证据。可以写已实现的代码和实验步骤，不能把这些项描述成已经成功操作。编辑器 updatedAt 检查也只是覆盖提醒，不是服务端原子并发控制。

M1-01～31 仍使用原冻结代码素材。新增三篇使用后续契约/代码快照，文章写作前建立各自可复现 tag；本次只更新规划，不提前创建文章 tag 或发布文章。

## 规模与排期

M1：31 → 34；M5：8 → 24。主线 142 → 161，支线仍 15，总计 157 → 176；每周两篇全量约 88 周。原 51 篇公开内容站应急集不扩张，完整多端系列另按阶段排期。新增篇均有素材来源，但文章数量不能替代质量，写作时如果具体主题无法形成独立论证，应合并 P1，而不是填充篇幅。
