## 一、这个项目到底在做什么

一句话：**用一个真实可运行的多端文章系统，作为素材载体，写一个成体系的全栈技术专栏。**

这里有个必须先说死的主次关系：

> **文章是产品，代码是素材。**

不是"做完系统顺便写文章"，而是"为了讲清楚全栈这件事，去建一套系统"。这个定位一旦确立，很多争议会自动消失：

| 遇到的问题 | 按这个定位怎么判 |
|---|---|
| 这个功能要不要做？ | 看它对应的文章值不值得写。不值得写的功能，不做 |
| 这个技术方案选哪个？ | 选**能讲清楚**的，不一定选最优的。选了非最优方案，就在文里说明白为什么 |
| 什么时候算做完？ | 文章发出去了才算。代码 merge 了不算 |
| 这块要做到多完善？ | 做到"够支撑一篇文章的完整度"就停，不追求生产级完备 |

### 发布阵地与单篇形态

- **主发布阵地：CSDN 博客**（`blog.csdn.net/fungleo`）。自建站是成果展示，不作为分发主渠道。
- **单篇篇幅：约 2500 中文字（±300）**。够把一个技术决策或一步实现讲透，不注水；每篇只讲一件事，对应一个 git tag。
- **发布频率：周更 2 篇**。稳定节奏优先于单篇完美；中途允许短暂调整，但单次断更不超过 3 周（见成功标准 P0）。
- **文风基调：比过往博客更克制、更结构化，但保留个人表达习惯。** 具体约定见下文「文风与编辑约定」一节。

## 二、目标读者（双轨）

### 主线读者：有基础的前端开发者

工作 1~5 年，React 或 Vue 至少精通一个，能独立完成中等复杂度的前端项目。痛点很具体：

- 后端只会调接口，不知道接口背后发生了什么
- 想做点自己的东西，卡在"部署到哪、数据库怎么建、域名怎么配"
- 面试被问架构问题答不上来，因为从没设计过一个系统
- 想转全栈，但网上的教程要么是 hello world，要么是几十集视频课

主线文章**默认这批人已经具备的知识不再重复讲**，直接进入架构决策、工程权衡和踩坑现场。

### 支线读者：零基础 / 转行者

不具备主线前置知识的读者，通过支线文章补齐。支线是**可跳过的旁路**，主线绝不为了照顾支线而降速或注水。

每篇主线文章开头会标注它依赖的支线篇目，读者自行判断是否需要先补。

### 明确不服务的读者

- 想要"复制粘贴就能跑"的速成党。本系列讲的是判断力，不是代码片段
- 追求生产级高可用架构的资深后端。本项目的技术复杂度对标"一个人能维护的产品"

## 三、成功标准

按优先级排序，上面的没达成，下面的没意义。

| 层级 | 指标 | 目标值 |
|---|---|---|
| **P0 · 内容产出** | 主线文章发布数 | 不中断地持续产出，M3 结束时至少 25 篇（主线骨架成型） |
| **P0 · 内容产出** | 断更间隔 | 单次断更不超过 3 周 |
| **P1 · 内容质量** | 单篇平均阅读量 | 高于个人历史均值 |
| **P1 · 内容质量** | 系列完读率 | 有稳定的读者从 M0 追到当前最新篇 |
| **P2 · 工程产出** | 可运行的子项目数 | M1–M2（2 个），最终 7 个 |
| **P2 · 工程产出** | 代码可复现性 | 读者能 checkout 到任意一篇文章对应的代码状态并跑起来 |

注意 P2 排在最后。**代码写得再好，文章没发出去，这个项目就是失败的。**

## 四、非目标（Non-goals）

这一节的作用是防止范围蔓延。以下内容明确不做，将来想做需要走变更流程。

### 产品层面不做

- **不做多租户 / SaaS 化**。单站点单管理员起步，用户体系只服务于会员中心
- **不自研富文本编辑器**。集成成熟 Markdown 编辑器即可
- **不做实时协作编辑**。收益极低，复杂度极高
- **不做推荐算法 / 个性化信息流**。数据量不支撑，讲不出真东西
- **不做支付与付费订阅**。自建站定位为演示品，不承担商业化
- **不做微服务拆分**。单体足够，硬拆是为了讲而讲

### 工程层面不做

- **不追求高并发架构**。不做分库分表、不做消息队列、不做分布式缓存，除非某篇文章专门讲它
- **不做完整的 CI/CD 流水线**（第一波内）。手工部署跑通即可，CI/CD 放到后面单独成篇
- **不做 100% 测试覆盖**。核心链路有测试即可，测试本身作为一个专题讲

### 内容层面不做

- **不做视频课**。本系列是文字专栏
- **不逐行讲解代码**。讲的是决策和结构，代码细节读者看仓库
- **不写"XX 入门"式的 API 说明书**。官方文档能查到的东西不重复写

## 五、七个子项目与推进节奏

采用**波次串行**，不并行。每一个 M（一件实现）结束都必须有可发布的文章产出。

| M 系列 | 实现（一个代码库） | 目录 | 优先级 |
|---|---|---|---|
| M1 | Node 后端（文章系统 API 首实现） | `node-backend/` | 必做 |
| M2 | Vite + React 管理后台 | `manage-frontend/` | 必做 |
| M3 | Next.js 网站前台（含会员中心） | `web-frontend/` | 必做 |
| M4 | Flutter App | `app-frontend/` | 可延后 |
| M5 | Taro 小程序 | 待建 | 可延后 |
| M6 | Go 后端重写（同契约） | `go-backend/` | 可延后 |
| M7 | Vue3 管理后台重写（同契约） | 待建 | 可延后 |

> **一个 M 只讲一件实现**：每个 M 系列对应一个独立代码库/端，不把一个 M 拆成"后端+前台"两件事。会员中心随 Next.js 网站（M3）一起讲，因为它属于同一个应用。

**为什么串行**：第一波（M1+M2）跑通后手里就有可发布内容了，后面每一波都是在有产出的基础上加码。并行推进的结局通常是七个半成品和零篇文章。

**M4–M7 标记为"可延后"的含义**：如果精力不足，系列在 M3 结束时是**完整可交付**的，不算烂尾。M4–M7 是加分项，其中 M6/M7（同契约重写）是本系列的差异化王牌。

## 六、唯一的硬地基：API 契约

七个子项目的依赖关系里，只有一样东西是刚性的：

- Go 后端要实现**和 Node 后端完全一致的接口**
- Vue3 后台要对接**和 React 后台完全一致的接口**
- Flutter 和 Taro 复用同一套 API

所以 **API 契约和领域模型是唯一值得提前投入设计的部分**。它在第一波定歪，后面六个子项目全部返工。这一步的产物是 [02-领域模型与API契约](./02-领域模型与API契约.md) 与 `docs/api/openapi.v1.yaml`，在写第一行代码之前就已经定稿。

其余所有东西（ORM 选型、UI 库、目录结构、状态管理方案）都允许边做边改，改动本身还是好素材。

配套要求：

- API 契约用 OpenAPI 3.1 规范维护，单一事实来源在 `docs/api/openapi.v1.yaml`
- 契约变更必须先改 OpenAPI 文档，再改实现
- 各端的请求层类型定义尽量由 OpenAPI 自动生成，避免手写漂移
- 领域模型与端点目录的设计说明见 [02-领域模型与API契约](./02-领域模型与API契约.md)

## 七、文章与代码的对应机制

这是教程类系列的关键工程实践，不做的话读者跟不上。

1. **每篇文章对应一个 git tag**，命名格式 `article/M1-05`
2. 读者 `git checkout article/M1-05` 就能拿到该文发布时的完整代码状态
3. 文章正文里给出本篇涉及的 diff 范围（起始 tag → 结束 tag）
4. 仓库根目录维护 `ARTICLES.md`，列出「文章标题 ↔ 链接 ↔ tag」对照表
5. 后续对旧代码的重构不回改历史 tag，在新文章里说明演进过程

> **仓库组织（R14 澄清）**：本系列采用**单一 git 仓库（monorepo 风格）**，各子项目作为仓库根下的顶级目录（`node-backend/`、`manage-frontend/`、`web-frontend/`、`app-frontend/`、后续 `go-backend/` 等）共存于同一份 git 历史。这样 `article/Mx-yy` 这一个 tag 能一次性 checkout 出「该文发布时整个系统的代码状态」（尚未动工的端其目录为空或占位）。M6 的 Go 后端作为**新顶级目录加入同一仓库**，而非独立仓库——否则旧 tag 下 `go-backend/` 不存在，会破坏「编号 ↔ tag ↔ 代码」三方绑定（见 01 §一）。

## 八、工作原则

1. **够讲清楚就停**。功能做到能支撑一篇文章的完整度即可，不镀金
2. **踩的坑要留下来**。走错的路、选错的库、返工的过程，都是内容资产，不要在文章里假装一次做对
3. **技术选型必须写理由**。每次选型在文章里交代备选方案和取舍依据，这是本系列区别于普通教程的核心
4. **业务与技术分离**。文章只讲通用技术命题，涉及具体业务的部分做通用化处理
5. **先文档后代码**。每一个 M 系列开工前先出该批的 PRD 和接口设计，避免边写边想

## 九、文风与编辑约定

本系列有意区别于过往博客的轻松口语风，整体更克制、更结构化，但仍保留个人表达习惯。

### 保留的个人习惯（不可丢）

- **第一人称"我"**：通篇用"我"，不用"笔者""本文作者"
- **鲜明的个人判断**：敢下结论、敢说"没必要"、敢承认方案调整后更优，不回避取舍
- **中文代码注释与 TSDoc**：代码块必须可直接运行，关键处中文注释
- **表格与 ASCII 图**：对比、结构、目录树优先用表格和字符图，不靠截图堆砌
- **一段一意、短段落**：保持节奏，不写三段式空壳论述
- **技术名词保留英文 + 中英空格**：如 `Taro 4 微信小程序`
- **通用化脱敏**：文章只讲通用技术命题，业务命名一律改成通用命名（沿用既有脱敏规则）

### 收掉的营销腔（刻意弱化）

- "各位看官"等口头禅频率大幅降低，仅在必要处点一次
- 儿化音、俗语、自黑式卖惨、极轻度粗口——基本不用
- 故事式抒情开头、文末求赞营销话术——弱化或改为"欢迎讨论/指正"
- 不端着的真诚保留，但"走一步看一步"的菜鸟感必须去除：技术决策显得成竹在胸，认知迭代写成"老手的正常演进"

### 每篇文章的固定结构（约 2500 字）

1. **本文目标 / 要点**：开头一句话说清这篇解决什么问题、能学到什么
2. **前置知识**：标注依赖的支线或前序篇目
3. **正文**：只讲一个聚焦的技术点，配代码/表格/图
4. **小结**：回扣核心结论
5. **延伸阅读**：文末放 ≥2 条 CSDN 站内往期文章互链（利于分发，也成体系）

> **契约与文章的命名边界（R20）**：`docs/api/openapi.v1.yaml` 与代码仓库使用**真实业务命名**（`Article` / `Member` / `Comment`），它们是本系列的真实素材；文章正文讲解通用技术命题时再按「通用化脱敏」规则改名。契约、代码、文章是同一套，命名差异只是讲解视角不同，不存在割裂。

### 与 CSDN 平台的关系

主阵地是 CSDN。仍遵循其基本质量分工程项（配图 2~4 张、站内互链、排版多样性），但**内容为王、密度优先**，不为凑分注水。封面图发布时建议配，但不计入正文质量。

## 十、技术方向与已确认的产品决策（已定）

### 10.1 后端技术栈方向（M1 已定，反向约束 M0-03）

Node 后端（M1）确定采用 **Hono + Drizzle ORM + Cloudflare D1（数据库）+ Cloudflare R2（对象存储）**，并**同时兼容部署在普通 Linux 服务器**。

- **Hono**：超轻量、跨运行时 Web 框架，同一份代码可跑在 Cloudflare Workers、Node、Bun、Deno。
- **Drizzle ORM**：TypeScript 原生、类型安全；在 Cloudflare 用 D1（SQLite），在 Linux 上用 SQLite 文件或 PostgreSQL，schema 不变。
- **D1 / R2**：Cloudflare 生态的数据库与对象存储；在 Linux 上对应 SQLite/PostgreSQL 与本地磁盘 / S3 / MinIO。

> 由此产生一个关键架构约束：**必须写"适配层"，让同一份业务逻辑在边缘（CF）和自管服务器（Linux）上都能跑**。这本身就是本系列高价值的内容题材——"一套后端，两种部署目标"。M0-03 与 M1 相关篇目会专门讲它。完整选型理由、备选方案与取舍见 M0-03。

### 10.2 已确认的产品功能决策

1. **会员等级**：User 增加 `level` 字段（int，默认 1），仅展示用、无业务功能，在会员公开主页呈现。
2. **会员投稿 + 审核状态机**：文章 `status` 三态 `draft / pending / published`。会员投稿默认 `pending`（待审核）；管理员发布直接 `published`（已审核）。极简状态机详见 [02-领域模型与API契约 §2.3](./02-领域模型与API契约.md)。
3. **会员公开主页**：新增公开端点 `GET /api/v1/members/:id`，聚合该会员的资料与其 `published` 文章，供前台展示。
4. **分类无限级树形结构**：Category 自关联 `parent_id` 表达任意层级，提供 `GET /api/v1/categories/tree` 整树返回；后台用平铺列表 + 客户端 `reduce` 构树。详见 [02 §2.2](./02-领域模型与API契约.md)。
5. **阅读量防刷**：新增 `POST /api/v1/articles/:id/view`，计数带去重（登录按 `user_id`、匿名按 `ip+ua` 哈希）+ 冷却窗口（默认 24h）+ 计数写分离，避免主表行锁竞争。详见 [02 §2.4](./02-领域模型与API契约.md)。
6. **评论内容安全**：评论提交即跑敏感词过滤，命中转等长 `*`；违规比率 > 阈值（默认 10%）→ `rejected`，否则 → `approved`（转义后展示）；`reviewing` 为管理员人工兜底态（评论 reviewing 与文章 pending 同名异义，特此区分）。详见 [02 §2.5](./02-领域模型与API契约.md)。
7. **附件双存储**：上传走适配层，R2 为主、本地磁盘兜底，由 `STORAGE_DRIVER` 配置驱动；Attachment 记录实际 `storage` 后端。详见 [02 §2.6](./02-领域模型与API契约.md)。

## 十一、主要风险与应对

| 风险 | 影响 | 应对 |
|---|---|---|
| **单人长周期，中途熄火** | 项目失败 | 波次串行 + 文章优先，保证任何时点停下来都有完整交付物 |
| **API 契约设计不当** | 后六个子项目返工 | M1 开工前专门做契约设计评审，用 OpenAPI 固化 |
| **范围蔓延** | 进度失控 | 本文档第四节 Non-goals 作为硬约束，变更需显式记录 |
| **代码与文章脱节** | 读者跟不上 | tag 机制 + ARTICLES.md 对照表 |
| **主线被支线拖慢** | 核心读者流失 | 支线独立编号、独立排期，允许滞后于主线 |
| **M4–M7 投入产出比低** | 精力浪费 | 已标记为可延后，M3 结束即为完整交付点 |
