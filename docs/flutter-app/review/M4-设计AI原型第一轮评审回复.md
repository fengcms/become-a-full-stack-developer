### N-1 🔴 编辑态「保存草稿」后门：移除撤回按钮后必须一并堵上

**这是评审没有指出、但性质与 B-1/B-2 同类（契约可达性）的一项，且优先级更高。**

**问题**：原型的稿件编辑页对**任何状态**都无条件渲染「保存草稿」按钮。

```
[编辑器] 待审核稿件 → 点「保存草稿」→ 提交 status: draft
```

契约对「会员更新 draft/pending 稿件」的**结果未作定义**：`PUT /articles/{id}` 只写了「编辑已 published → 退回 pending」这一种前态，请求体里 `status` 字段**未见约束**，而 `draft` 又是合法枚举值。这个空档意味着：**会员只要在待审稿件上点一次「保存草稿」，就可能把稿件撤回到草稿**——绕开管理员，正是 A-1 判定「会员端不提供撤回为草稿」想封死的那条路；且因为有歧义，Node 与 Go 两个实现很可能给出**不同**行为。

换句话说，**B-0 删掉的是显式的「撤回」按钮，但这个隐式后门还在**。两者是同一个洞，只堵一半不成立。

**处置**：按稿件状态区分底部操作条，做成小矩阵：

| 稿件状态 | 「预览/继续编辑」 | 主操作按钮 | 是否有「提交审核」 |
|---|---|---|---|
| `draft` 草稿 | 预览 | **保存草稿**（次要样式） | ✅ 有（主样式） |
| `pending` 待审核 | 继续编辑 | **保存**（主样式，不回退状态） | ❌ 无 |
| `published` 已发布 | 继续编辑 | **保存**（主样式，保存后转 pending） | ❌ 无 |

- 待审/已发布态按钮文案由「保存草稿」改为「保存」，点击 toast 也随状态变化：草稿态提示「草稿已保存」，其余状态提示「**已保存，审核状态不变**」——把「不会撤回」这件事直接告诉用户。
- 待审态额外加一条说明条：「⏱ 这是**待审核**稿件：保存只更新内容，状态保持待审核；会员端不提供撤回。」

**与文档侧口径已对齐（重要）**：产品 AI 在文档侧已被指出同源问题（评审 N-1，针对 `02 §5` 底部按钮），并落成 `02-页面地图与交互规格.md:49-50` 的状态矩阵：「`draft` → 预览、保存草稿、提交审核、删除」「`pending` → 预览、保存（保持待审核）、删除；**不显示"保存草稿"**」，`03-接口映射与数据约束.md:49` 另加「更新时客户端不得下发 `status`」。**本原型的按钮矩阵与之一致**——三条线（文档 §5 / 接口约束 §6 / 原型 UI）现在指向同一套规则，不会再出现「文档说不能撤回、原型却留着撤回按钮」的错位。

**回归测试**（新增 6 条断言：1 条前置 + 5 条矩阵）正向锁死这个矩阵：草稿态必须出现「保存草稿」+「提交审核」；待审态按钮文案必须**恰为**「保存」、且**不得**出现「提交审核」、且必须出现「会员端不提供撤回」说明条。

> **给评审的建议**：这类「状态机 × UI 操作」的交叉可达性，比单个端点是否存在更容易漏。建议后续评审增加一条通用检查——**凡原型提供「修改状态」的入口，都要问一句：这个目标态是不是契约允许作者自行到达的？** 若否（如 draft），就是越权后门。

## 4. 施工过程中的三个真 bug（供参考）

1. **我自己引入、被测试抓出的**：`handleAct` 里 `switch` 判断的是 `act.split(':')[0]`，我最初把目录入口的 case 写成 `'toc:panel'`（含冒号），**永远匹配不上**——功能静默失效、不报错。改回 `case 'toc': if(a === 'panel')`。这类错误不靠自测很容易漏到交付。
2. **测试脚本自指陷阱**：我最初用 `document.body.textContent` 断言「已不含 `like-status`」，结果**恒为真**——因为 `<script>` 就在 `<body>` 里，源码文本自身被算进去了，4 项断言全部假阳性。改为读取右侧说明面板（`#notes`）文本后恢复正常。这与第一轮原型排查时踩的坑同源：**判断「某文本是否消失」时，必须先排除 `<script>` 源码**。
3. **我的路由清单本身有错（已在本文订正）**：首版门禁我报的是「全路由 21/21」，但那份清单是我手写的，其中 `#/articles`、`#/about` **并不是原型里的路由**——它们命中兜底页，所以「不白屏」仍然成立、门禁结论没有被推翻，但**计数是虚的**：我把 2 条不存在的路由算成了通过，同时漏测了 `#/members/:id` 与 `#/member/articles/:id/preview`。本版已改为**从源码 `ROUTES` 表程序化抽取**（19 条 + 1 条兜底 = 20/20），不再依赖手写清单。
   > 教训与第 2 条同构：**凡是能程序化从被测对象自身推导的期望值（路由表、字段表、端点表），就绝不要手写**——手写清单会把「测试清单写错」伪装成「测试通过」。
