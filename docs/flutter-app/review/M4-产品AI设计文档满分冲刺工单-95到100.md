## 2. 整改工单

### 🔴 G-1 · 收 1 分 · 归属「契约事实准确性」 · 对应 N-19 主体

**落点**：`03-接口映射与数据约束.md` §5 第 4 条（当前为 `03:56`，以改动时实际行号为准）

**契约证据**（`docs/api/openapi.v1.yaml` L534-539，逐字）：

```yaml
        status:
          type: string
          enum: [draft, pending, published]
          description: >
            目标状态。权限约束：member 传入 published 时后端忽略并降级为 pending（会员无法直接发布）；
            editor 与 admin 可直接置为 published。
```

对照同 schema 的 `slug`（L527-533）——它自陈「**与 status 同规格显式化**」，却把创建/更新 × member/editor/admin **三条路径全写全了**：

```yaml
          description: >
            可选的 URL 别名。权限约束（与 status 同规格显式化）：
            **member 传入 slug 时后端一律忽略**（创建时留空、更新时保持原值），不报错也不写入；editor 与 admin 可直接指定。...
```

**结论**：`status` 只约束了 `published` 一个取值。**member 显式传 `draft` 的接受性，契约完全未定义**。文档当前把它当成既定事实下发实现指令，属事实不准确。

**现状原文**：

> - 创建文章使用 `POST /articles` 时，客户端必须显式下发 `status`：保存草稿发送 `draft`，提交审核发送 `pending`；任何创建请求不得省略 `status`，因为契约对 member 省略状态时的默认值“draft/pending”存在歧义。更新与创建的 status 规则不同，不能互相泛化。

**改为**（可直接替换）：

> - 创建文章使用 `POST /articles` 时，客户端显式下发 `status`：保存草稿发送 `draft`，提交审核发送 `pending`；任何创建请求不得省略 `status`（契约对 member 省略状态只写“默认 draft/pending”，无单一默认值）。**注意：契约对 `ArticleCreate.status` 仅声明了 `published` 的权限降级规则（member 传入 `published` 被忽略并降级为 pending），未声明 member 显式传 `draft`/`pending` 的接受性**——对照同 schema 的 `slug` 字段（自陈“与 status 同规格显式化”却写全了创建/更新 × 各角色的完整矩阵），这是同一范式下的**描述缺口**，不是已验证行为。因此“发 `draft` 落库为草稿”是客户端诉求，须经 `03 §6` 登记项在 Phase 4 前置检查中实测确认后方可视为契约行为。更新与创建的 status 规则不同，不能互相泛化。

**改动量**：1 段（约 3 行）。
**复核命令**：

```bash
grep -n "仅声明了 .published. 的权限降级" "docs/flutter-app/03-接口映射与数据约束.md"
```

### 🔴 G-2 · 收 1 分 · 归属「差异表完备性」 · 对应 N-18（本轮最高价值）

**落点一**：`01-技术方案与工程边界.md` §2 技术栈表 Markdown 行（当前 `01:18`）

**现状原文**（表格约束列，注意是**一整行**）：

> 与网站视觉一致，限制原始 HTML；文章目录以服务端 `/articles/{id}/toc` 为唯一事实源，使用返回的 `anchor` 字段定位标题，不自行生成目录锚点

**问题**：Flutter 里标题是 Widget，**没有 DOM id 这种可寻址标识**。「不自行生成目录锚点」字面上**无法实现**——渲染器必须为标题挂一个可寻址的 key/anchor，只是**值**应取自服务端。现措辞把「目录数据来源」和「渲染锚点生成」两件事压在一句话里，会让开发 AI 卡在「既不能自己生成、服务端又只给了字符串，那绑定动作写在哪一层」。

**改为**：

> 与网站视觉一致，限制原始 HTML；文章目录**数据**以服务端 `/articles/{id}/toc` 为唯一事实源（层级与文本一律取自返回的 `level`/`text`），客户端不自行解析正文生成目录；渲染正文时由**渲染器为标题生成锚点**，锚点**值采用服务端返回的 `anchor`**，客户端不自行 slug 化（契约未公开 slug 规则）

**落点二**：`03-接口映射与数据约束.md` §2 功能映射表「文章详情子资源」行（当前 `03:13`）

**现状原文**：

> `/toc` 使用服务端返回的 `level/text/anchor`，渲染器绑定相同 anchor，保证与网站一致；`/adjacent` 读取上一篇/下一篇。二者都要求整数文章 id

**改为**：

> `/toc` 目录**数据**取自服务端返回的 `level/text/anchor`；渲染器为标题生成锚点、锚点值采用服务端 `anchor`，客户端不自行 slug 化（契约未公开 slug 规则）；`/adjacent` 读取上一篇/下一篇，契约明确仅 published 参与。二者都要求整数文章 id，且对未发布文章的可见性口径见 `§6`；目录锚点配对规则见 `§6`

**落点三**：`03-接口映射与数据约束.md` §6 差异表**新增一行**（建议插在现有「Markdown 目录」行之后）

**契约证据**（L669-676，逐字）：

```yaml
    TocItem:

      description: 文章目录项，由正文 Markdown 标题解析生成
      properties:
        level: {type: integer, description: 标题层级 1-6}
        text: {type: string, maxLength: 200, description: 标题文本}
        anchor: {type: string, maxLength: 100, description: 锚点 id（slug 化标题）}

```

- 契约全文 `anchor` **只有 2 处命中**（L675 定义、L676 required）；

> | 创建时的默认状态 | `ArticleCreate.status` 非必填；契约写“member 创建默认 draft/pending”但未明确单一默认值；**权限约束只声明 `published` 会被忽略降级**（对照 `slug` 字段自陈“与 status 同规格显式化”却写全了创建/更新 × member/editor/admin 全矩阵）——**member 省略 `status`、显式传 `draft`、显式传 `pending` 三种情形的落库结果契约均未声明** | 客户端创建时显式发送 `draft` 或 `pending`；登记契约澄清 member 省略 `status` **及显式传 `draft`** 两种情形的落库状态；Phase 4 开工前用独立测试数据实测“传 `draft` 落库为 draft、传 `pending` 落库为 pending”，实测通过前不把“保存草稿已生效”视为契约行为 |
