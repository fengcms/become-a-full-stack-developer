### 1.1 A-5 🟡 P2 · 目录面板的加载/失败态缺席

**我接受这个定性，且认为它和 A-1 确实是同一类**：原型演示的是一个真实实现里不存在的形态。
A-1 演示了"客户端自造锚点"，本条演示了"目录不会失败"——**开发 AI 照抄哪一条都会写错**。

**已做（报告指定的最小改法）：**

1. `02` 注释块末尾追加声明：目录数据由本地 `SECTIONS` 派生 → 演示不出「目录请求加载中 / 失败」；
   真实实现里 `/toc` 是独立请求；出口归产品口径（产品侧 `02 §3` 未枚举该状态），本原型不擅自新增；
   列为跨侧待决项。
2. `notes.tip` 补一句设计原则：`目录、面包屑、相关文章都是辅助子资源，失败时不应阻塞正文。`

**未做，且是刻意的：没有往 `notes.states` 加「目录加载失败」。**

理由不是"麻烦"，而是**加了会制造一类你自己在两轮里都在清的东西**：

- `notes.states` 在原型里渲染成 **「必须状态」**。它是"本页已覆盖的状态清单"，**不是愿望清单**。
- 而原型**演示不出**这个状态（数据是本地派生的，没有请求，就不会失败）。加进去等于声明一个
  做不到的覆盖 → **死标注**——与 A-2 的死注释、N-2-2 的死字段、A-8 的 `related` 无消费方**同一类**。
- 更关键：产品侧 `02 §3` 已冻结的状态枚举里没有它。**加进去＝替 owner 决定了一个跨侧口径**，
  这正是报告 §6 明确划出红线的那件事。

**所以我要如实说清楚：A-5 我做到的是「声明 + 升级为跨侧待决」，不是「修复」。**
你扣的 2 分（"原型演示的是目录永远可用"）在形态上**依然存在**。要真修，只有两条路：
① owner 先把「目录失败态」写进产品侧口径，我再补可视化；② 我擅自加，但那就越权了。
**请按「是否接受声明式处置」判这 2 分**；若认为必须可视化，我请求先由 owner 定口径。

### 1.2 A-6 🟢 P3 · 层级口径只覆盖 1–2 级

先把报告 §5 的自我订正第 1 条确认一下：**你订正得对**，`L1173` 原本就有"与契约 level(1-6) 一一对应"
那半句，所以本项**不是"没声明"，而是"声明的覆盖范围够不到它自己派生出的值域"**。

**已做：**

1. **补全声明**（报告要求）——写明：本原型正文只演示 1-2 级；`level >= 3` 的目录标签口径与
   h 标签派生均未验证；`'h' + (level + 1)` 在 `level=6` 时得到非法标签 `h7`。
2. **顺带修了目录面板的标签压平**（报告说"不要求改渲染逻辑"，这一处是我主动加的，理由如下）：

   | | 原写法 | 现写法 |
   |---|---|---|
   | 3 级标题显示 | 「二级标题」（**对数据的错误陈述**） | 「三级标题」 |
   | 6 级标题显示 | 「二级标题」 | 「六级标题」 |

   为什么我认为这一处该改、而 `'h'+(level+1)` **不该**改：

   - 标签压平**与口径无关**：无论产品最后决定目录支持几级，只要 3 级标题出现在面板里，
     把它叫「二级标题」就是错的。改动**口径中性**，且 mock 最高只到 2 级 → **视觉零变化**。
   - `'h'+(level+1)` 是**口径问题**：`h1` 被文章标题占了，只剩 `h2`~`h6` 五格，
     而 `level` 有 6 个取值 → 五格装不下六级，这是**产品必须决定"目录最多支持几级"**的问题。
     **把它钳到 `h6` 不是修好**，只是把"非法标签"换成"5 级和 6 级静默撞成同一个标签"——
     两种都错，而且后者更隐蔽。所以**不动，只声明**。

3. **没有为它加新断言**，并说明为什么：mock 正文只有 1-2 级，任何针对 `level >= 3` 的断言
   在当前夹具下都**恒绿**——那正是你 §5 自我订正第 3 条批评的形态（也是我自己 README 规则 #6 的形态）。
   **能力边界写进注释，比假装覆盖到更诚实。** 要真覆盖，得先等口径定下来、再给 mock 加 3 级以上标题。

## 2. 与报告建议不一致的 1 处（附实测依据）

报告 A-8 的首选写法是：

```
'GET /articles/{id}/related（本阶段不实现，仅登记契约存在）'
```

报告自己留了例外分支（"若该写法会影响 API 门禁的解析，则改为…"）。**我没有靠读代码猜，而是实测了：**

```bash
# 1) 按首选写法临时改入
'GET /articles/{id}/related' → 'GET /articles/{id}/related（本阶段不实现，仅登记契约存在）'
# 2) 跑 API 门禁
$ python3 gates/check_api_vs_contract.py
  FAIL  [02-高保真可交互原型.html] GET /articles/{id}/related（本阶段不实现，仅登记契约存在）
        幽灵端点：契约 paths 中没有 /articles/{id}/related（本阶段不实现，仅登记契约存在）
结论：1 条标注与契约不符 ❌
```

**根因**：`extract_annotations()` 按**第一个空格**切分方法/路径，说明文字会并进路径，
带着尾巴去比对契约必然不命中。**这不是解析器不够健壮，而是"结构化字段里塞说明文字"本身
就是坏设计**——靠放宽解析器去兼容它，等于让门禁对"路径后面随便写什么都行"失去约束。

**所以我把这条从"一次性的写法选择"升级为"一条写进 README 的规则"**（规则 #8）：
标注元素严格是 `<方法> <路径>` 两段；要做语义区分，用**独立字段**并让门禁一并扫它。

> 顺带一个反向收获：这次偏差是**报告的例外分支救了场**——如果报告没写那句"若影响解析则…"，
> 我可能会先按首选写法改、跑出门禁变红，再回头怀疑是不是解析器的问题。**例外分支写清楚，
> 比论证唯一正确解更有用。**

### 3.2 A-6 的 `h7` 由静态推断升级为实测

报告 §2.2 的判断（`level=6` → `h7`）是**静态读代码**得出的。我用独立探针把 `TOC` 运行时
推到 3 级与 6 级，实测了两件事：

```json
"derivation": {
  "formulaForLv6": "h7",
  "h7TagName": "H7",
  "h7IsHeading": false,          // ← /^H[1-6]$/ 不匹配
  "h7CtorName": "HTMLUnknownElement",   // ← 浏览器把它当未知元素，不是标题
  "realLevelsInMock": [1, 1, 2, 2, 1]   // ← 确认 mock 只有 1-2 级
}
```

**这比"公式算出来是 h7"更有说服力**：`h7` 不是"一个等级不够高的标题"，
而是**浏览器不认识的元素**——开发 AI 照抄后，屏幕阅读器与样式表都当它不存在。
这也印证了你 §2.2 的另一半判断：**门禁发现不了它**（`'H7' === 'H7'` 自洽通过）。
