## 2. 新发现

### N-2-1 🔴 P1（已实测确证）· 目录点击**不滚动**，却 toast 谎报「已定位到对应章节」

**这是原型的硬要求与实现不符，且原型自己声明了这条目标。**

**契约/文档依据**：`02-页面地图与交互规格.md:39` 原文——

> 文章页把正文放在第一优先级。目录用可折叠底部面板或顶部抽屉，**点击目录后关闭面板并滚动到标题**。

**实测证据**（CDP，两次独立触发）：

| 触发点 | 页面可滚性 | scrollTop 变化 | toast |
|---|---|---|---|
| 顶栏「目录」→ sheet 内点第 2 条 | `scrollHeight 2757` / `clientHeight 711`（**确实可滚**） | **420 → 420，Δ=0** | 「**目录已定位到对应章节**」（可见） |
| 正文内 `.toc-bar` 点第 2 条 | 同上 | **Δ=0** | 「目录已定位到对应章节」（可见） |

**根因**（静态佐证）：
- 正文标题**无 `id` 锚点**（`grep '<h[23] id='` = 0 命中）；
- 全文件**无任何 `scrollTo` / `scrollIntoView`**（仅 L1962/1987/2197 做 `scrollTop = 0` 重置）；
- 代码路径：`case 'toc': if(a === 'panel'){…break;} render(); toast('目录已定位到对应章节'); break;` —— 非 `panel` 分支只重渲染 + 报成功。
- **原型自身的 `goals` 也写着「目录用可折叠面板，点击后关闭并滚动到标题」**（详情页说明面板可见）→ 目标与实现直接矛盾。

**为什么判 P1 而不是 P3「原型可简化」**：
1. 与 B-1 举报 toast 属**同一族缺陷**——「用户点了、界面报成功、实际什么都没发生」。区别只是 B-1 缺端点、本条缺实现；
2. **B-7.2 的整改目的就是解决「想跳章节要先滚到文末找目录」**。入口做出来了，点击却不跳转 → **痛点未被解决，B-7.2 的实际收益归零**；
3. 开发 AI 会照抄 `notes.goals` 与 `case 'toc'` 两个来源，且两者自相矛盾，必然产生一份「有入口、不跳转」的实现。

**建议修法**（纯客户端，无契约依赖，成本极低）：
- 给正文标题加锚点 `id="h-1"…"h-5"`（与现有 `TOC` 常量 `n` 对应）；
- `case 'toc'` 数字分支改为 `document.getElementById('h-' + a)?.scrollIntoView({behavior:'smooth', block:'start'})`；
- **拿不到锚点时不报「已定位」**——宁可不提示，也不谎报（与 B-5 复制链接同一原则）；
- 若本期不实现滚动，则必须把 `goals` 里的「滚动到标题」改为「原型不模拟滚动」，保持自洽。

### N-2-2 🟡 P2 · `rejectedReason` 挂在**文章**对象上，契约里它只属于 `Comment`

**原型 L766**（`MY_DRAFTS`，id:202，`status:'pending'` 的**文章**对象）：

```js
{id:202, …, status:'pending', viewCount:0, likeCount:0,
 createdAt:'2026-10-01', updatedAt:'2026-10-01 20:05', rejectedReason:null},
```

**契约事实**（脚本抽取三张表）：

| Schema | 是否含 `rejectedReason` |
|---|---|
| `Comment`（L395） | ✅ `rejectedReason: {type: string, maxLength: 200, nullable: true}` |
| `Article`（16 字段：id/title/slug/summary/content/coverImage/authorId/authorName/categoryId/categoryName/tags/status/viewCount/likeCount/publishedAt/createdAt/updatedAt） | ❌ **无**（且无任何 `reject`/`review`/`reason`/`note` 字样的字段） |
| `ArticleSummary`（14 字段） | ❌ 无 |

**两点危害**：
1. 开发 AI 照抄会在文章模型上定义一个**契约不存在**的字段；
2. 更实质：**契约里文章根本没有「被拒」这个概念**（`Article.status` 枚举只有 `draft/pending/published`）。若产品后续想要「稿件被管理员驳回并给出原因」这类 UI，**数据层无来源**，须先扩契约（对应 `03` 差异表登记）。

**这条恰恰是设计 AI 自己在回复 §2 第 2 项提出的检查维度**——「建议后续评审把『原型展示的每个数字/字段是否有 schema 支撑』也纳入比对范围」。**维度提得对，但没在自己的文件上跑一遍。** 我本轮已代跑：`Article` / `ArticleSummary` / `Comment` 三张表逐字段比对，除本条外未发现其他无支撑字段（`likeCount` / `viewCount` / `categoryName` 均有支撑）。
