## 4. 🔴 核心问题：门禁的第三代量程盲区（这是**我的**问题）

### 4.1 症状

`check_code_quality_v2.py` 报「最大函数 79 行 / >80 行函数 0 个」，但用一把修正后的尺子量，实际是 **6 个 / 最大 196 行**。

### 4.2 机理

v1 的盲区是**逐行正则**（看不见多行签名与箭头体），v2 修掉了。但 v2 引入了一个新的、更隐蔽的盲区：

> **Dart 的命名参数组 `{...}` 本身是一对花括号。**

```dart
Future<dynamic> _request(
  String path, {
  String method = 'GET',
  ...
}) async {          // ← 函数体的 `{` 回溯「上一个 `;{}`」时，停在了参数组的 `}`
```

v2 的解析器从函数体的 `{` 向前回溯到**上一个 `;` / `{` / `}`** 作为签名起点 —— 而命名参数组的 `}` 恰好是这样一个字符，于是 `seg` 只剩 `) async `，签名正则匹配失败，**整条函数不进枚举**。

受影响面：**所有带命名参数且有函数体的方法**。

### 4.3 实证（不是推理，是实测）

用 v2 的函数枚举器扫 `core/network/api_client.dart`：

```
v2 在 api_client.dart 里识别到的函数：
    1 行  read        L25-25
    3 行  write       L27-29
    1 行  toString    L46-46
    7 行  _persist    L89-95
    7 行  clear       L110-116
   33 行  refresh     L118-150
    6 行  fileUrl     L309-314
含 'request' 的函数名：[]
```

—— `request`（34 行）与 **`_request`（119 行）双双消失**。

### 4.4 后果链（与第二轮同构，只是深了一层）

1. 我给的 v2 报 `PASS=15 / FAIL=0` → 作者据此认为「>80 行函数 = 0」已达标；
2. 作者在回复里**主动写下**「新提取方法的命名 record 返回签名未进入函数枚举……不将『工具通过』等同于所有结构都被穷尽检查」—— **他察觉到了量具局限**；
3. 但他只写了免责声明，**没有再换一把尺子复量一次**（与第二轮同一处未满分项）；
4. 于是 6 个超线函数带着「已达标」的标签过关。

### 4.5 修正

新增 **`check_code_quality_v3.py`**（15 条断言，同集）：

| 修正项 | v1 | v2 | v3 |
|---|---|---|---|
| 多行签名 | ❌ | ✅ | ✅ |
| 箭头表达式体 | ❌ | ✅ | ✅ |
| **命名参数组长函数** | ❌ | ❌ | ✅ |
| **箭头体终止符**（不被内层 lambda 的 `;` 截断） | ❌ | ❌ | ✅ |
| **嵌套口径** | 花括号深度（虚高） | 花括号深度（虚高） | **仅控制流分支块** |
| `lib/app/theme/` 长函数 | 计入 | 计入 | **排除**（配置型，另列登记） |

**`--selftest` 注入 10 类缺陷，15/15 全部转红**，并额外断言「命名参数长函数被看见」与「主题目录被排除」两项口径正确。
**真实验收 `PASS=13 / FAIL=2`**（仅剩函数长度两条），**非空跑**。
**v1 / v2 均保留不删** —— 三代尺子的差异本身就是最有价值的发现。
