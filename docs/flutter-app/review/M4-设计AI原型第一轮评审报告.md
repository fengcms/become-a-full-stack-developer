## 2. 🔴 B-1 · 「举报内容」无后端端点（虚假成功）

原型 `handleAct` L2043-2049：

```js
case 'article':
  openSheet('文章操作',
    sheetChoice('复制链接', '', 'share:' + a) +
    sheetChoice('举报内容', '提交后由管理员复核', 'report') +   // ← 无契约支撑
    sheetChoice('取消', '', 'sheet:close'));
  break;
case 'report': toast('已提交，管理员会复核'); break;            // ← 虚假成功反馈
```

**契约核验**：grep `report|举报` 全文仅命中 `HistoryReport` / `reportReadingProgress`（**阅读进度上报**），**不存在任何内容举报端点**（无 `/reports`、无 `/articles/{id}/report`）。

**风险**：用户点「举报」→ 收到「已提交，管理员会复核」→ 实际什么都没发生。这是**误导性 UI**，比缺功能更糟。

**建议（二选一）**：① 移除「举报内容」菜单项；或 ② 保留入口但明确标注「本期不实现（契约无端点）」，并在 `03` §6 差异表登记「内容举报需新增契约」为后续议题。

## 3. 🟡 B-2 · 公开详情页展示「复核中」评论徽章（不可达状态）

- 样稿 `01-基本页面样稿.html` L671：`<div class="cname">Ming<span class="opt">复核中</span></div>` —— 在**公开文章详情页**给一条评论挂「复核中」徽章。
- 原型 `02` PS-05 `states` L1223：`['长文 / 代码 / 表格','图片加载失败','404','离线','评论复核中 / 未通过']` —— 把「评论复核中 / 未通过」列为文章详情页的必须状态。

**契约事实**（详见产品 AI 报告 §3 A-2）：

- `GET /articles/{idOrSlug}/comments` 原文「**只返回 status=approved 的评论——对任何调用者（匿名、评论作者本人、文章作者、admin）都一样**」；
- `POST` 自动流原文「**不产生 reviewing**」，返回 approved 或 rejected；
- **无 `/me/comments` 端点**；
- `Notification.type` 枚举**没有「评论被拒」类型**。

故该徽章与状态**永远不会从接口拿到**。

**建议**：移除样稿该徽章；PS-05 状态列表改为「评论列表空态 / 评论加载失败 / **发帖被拒即时提示**」。

## 4. 🟡 B-3 · 原型 API 标注与契约不符（10 处，含 5 处路径不存在）

开发 AI 会直接照抄 `notes.api` 实现请求层，故必须订正：

| 原型标注 | 契约实际 | 性质 |
|---|---|---|
| `GET /me`（会员中心未登录态） | **不存在**；会话恢复应为 `GET /api/v1/auth/me` | ❌ 路径不存在 |
| `GET /articles/{id}/like-status` | `GET /articles/{id}/like/status`（**斜杠**） | 路径错 |
| `GET/POST /articles/{id}/like` | `POST,DELETE /articles/{id}/like`（无 GET） | 方法错 |
| `POST /comments` | **不存在**；创建评论为 `POST /articles/{idOrSlug}/comments` | ❌ 路径不存在 |
| `GET /articles/{id}/comments` | `GET /articles/{idOrSlug}/comments` | 参数名错 |
| `GET /me/articles/{id}` | **不存在**（`/me/articles` 仅 GET 列表） | ❌ 路径不存在 |
| `PUT /me/profile` | `PATCH /me/profile` | 方法错 |
| `PUT /me/password` | **不存在**；应为 `POST /me/change-password` | ❌ 路径不存在 |
| `GET /categories/{slug}/articles` | **不存在**；应为 `GET /articles?category={slug}` | ❌ 路径不存在 |
| `GET/POST/DELETE /me/favorites` | `GET,POST /me/favorites` + `DELETE /me/favorites/{articleId}` | 路径错 |

> 注 1：`like-status` 的写法**源自产品 AI 回应文档 L26 的笔误**（已在产品 AI 报告 §5.2 登记），此处的订正以契约为准。
> 注 2：同文件另一处已正确写 `POST/DELETE /articles/{id}/like`，即**文件内自相矛盾**，需统一。

## 6. 🟡 B-5 · 交互语义细节

- **`复制链接` 误映射到分享动作**：`sheetChoice('复制链接', '', 'share:' + a)` → `case 'share': toast('实现阶段接入系统分享面板')`。复制链接应走剪贴板并 toast「已复制」，与系统分享面板是两种行为。
- **删除评论的提示与契约不符**：原型提示「删除后其回复会**一起隐藏**」；契约 `DELETE /comments/{id}` 原文是「删除评论时**级联删除**其所有子回复（parent_id 指向它的行一并删除），避免孤儿回复」——措辞应由「隐藏」改为「**一并删除**」（语义不同：隐藏可恢复，删除不可逆，直接影响用户确认预期）。
- **分类跳转的端点标注**：`PS-02` tip 说「分类跳转用 slug，不能用数字 id 拼路由」——**意图正确**（契约 `?category=` 正是按 slug 匹配且级联包含后代子分类），但端点标注需改为 `GET /articles?category={slug}`。

## 7. 🟡 B-6 · 令牌 Dart 侧同步项（`app_theme.dart`）

- **缺 `heroWashFrom / heroWashTo` 字段**：`06` §2.1 定义了焦点区渐变 `#F0F7FE → #E4F0FB`，原型/样稿用 CSS `--hero-wash`，但 `AppColors` 无对应字段。**待产品 AI 在 `06` §2.1 定下落地形态后**，在 `AppColors` 补两色（`ThemeExtension` 不能直接放 `LinearGradient` 才需拆色），并同步 `copyWith` / `lerp` / 双主题取值。
- **`textScaler` 未处理**：`06` §3 要求「放大 1.3 倍不横向溢出」，但 Flutter 的 `fontSize` 是逻辑像素，缩放靠 `MediaQuery.textScaler`；`app_theme.dart` 侧未做处理。实现阶段需用 `maxLines / ellipsis / 横向滚动`兜底（规范侧说明见产品 AI 报告 §4 A-3）。

## 8. 界面设计合理性专项（用户明确要求）

**结论：整体合理，符合移动端内容门户惯例，工程化细节到位；有 2 处可选优化。**

### 8.1 合理之处

- **信息架构**：单列门户「焦点 → 最新 → 热门」+ 底部 4 Tab（首页 / 分类 / 搜索 / 我的），是内容型 App 的主流且与页面地图吻合；二级页不替换 Tab 语义、编辑器可隐藏 Tab —— 与 `01`/`02` 一致。
- **正文优先真正落实**：`type.reading`（17sp / 1.85）唯一用于正文；操作条置于正文之后**不遮挡**正文（`02` §4 硬要求）；目录用可折叠面板且「点击后关闭并滚动到标题」。
- **移动端细节**：触控目标 ≥44dp、列表行高 ≥56dp、`overflow-x:auto` 处理代码块 / 表格、`overflow-wrap:anywhere` 防长串溢出、缩略图 96×72 且有 `noimg` 变体**不留空占位**（`06` §6.3）、骨架屏用透明度呼吸而非闪烁、状态图文并存、深色独立设计、动态字体考虑 —— 这些是很多移动端设计稿会漏的。
- **叠楼评论**：`reply` 块「回复 @某某 + 原文摘要（2 行截断）+ 缩进一档」，深层不再递归缩进 —— 层次清晰且防失控，符合 `02` §4 与 `05` 风险「禁止对不受控深度直接递归生成大量 widget」。
- **空态 / 错误态**：区分 8 类具体原因并提供重试 / 重登 / 返回动作，未退化为「加载失败」—— 符合 `01` §4 硬要求。
- **对比度**：`app_theme.dart` 与 `06` §2.5 对齐，浅色 12 项 + 深色 13 项实算达标，并显式保护两处刻意例外（禁止实现时「顺手统一」）。

### 8.2 可选优化（非缺陷，建议讨论）

1. **焦点区（hero）高度挤占首屏**：hero 约 150–200dp 置于最顶，首屏可见的「最新文章」条数偏少，用户每次进首页都要下滑才看到内容。建议评估 ①**降低 hero 高度**，或 ② 首屏让 hero 下方露出**至少 1 条**列表项（折叠 hero）。现「手动切换不自动播放」的决定是对的（Q5）。
2. **文章详情的信息顺序**：样稿顺序为「正文 → **目录** → **互动工具条** → 上下篇 → 评论」——目录与互动都放在正文**之后**。移动端更常见的做法是：目录入口放**顶部栏 / 正文前的浮动入口**（读前可跳转），互动工具条留在**正文末尾**（读完再赞）。现顺序导致「想跳章节要滚到文末找目录」，与阅读链路略反。

> 其余如「样稿自绘状态栏 / 电池」（实现用系统状态栏，勿照抄）、「搜索既是 Tab 又是首页右上入口」（重复入口可接受，需行为一致）属展示层或无碍项，不计入问题。
