## 2. 本轮新发现

### 🔴 N-18（P1，本轮最高价值）· 正文目录的「锚点配对规则」是未声明的实现前提

**事实链（全部取证）：**

1. `01:18` 写：「文章目录以服务端 `/articles/{id}/toc` 为唯一事实源，使用返回的 `anchor` 字段定位标题，**不自行生成目录锚点**」
2. `02:39` 写：「Flutter Markdown 渲染器须将标题**绑定到返回的 `anchor`**，目录点击按该锚点滚动」
3. `03:13` 写：「`/toc` 使用服务端返回的 `level/text/anchor`，**渲染器绑定相同 anchor**，保证与网站一致」
4. **契约核验**：`TocItem`（L669-676）只有三个字段，`anchor` 的定义是**一句话**——

   > `anchor: {type: string, maxLength: 100, description: 锚点 id（slug 化标题）}`

   我在契约全文 grep `anchor`，**只有 2 处命中**（L675 定义、L676 required）。`/toc` 的 `description` 全文是：「由正文 Markdown 标题解析生成目录，供长文侧边导航。」——**没有 slug 化规则，也没有「数组顺序 = 正文标题顺序」的排序保证**。
5. **`data` 是裸数组**（`data: {type: array, items: TocItem}`），无任何顺序字段（如 index/offset/line）。

**为什么这是 P1 而不是措辞问题：**

Flutter 里标题是 Widget，**没有 DOM id 这种可寻址标识**。客户端要「把标题绑定到服务端 anchor」，只有两条路：

- 路径 A（按字符串匹配）：客户端自己把标题文本 slug 化，再与服务端 anchor 比对 → **前提是契约公开 slug 化算法**。契约没公开 → 走不通。
- 路径 B（按顺序配对）：客户端解析正文得到有序标题序列，第 `i` 个标题 ↔ `TocItem[i]` → **前提是「数组顺序 = 正文顺序」**。契约没声明 → 是假设，不是保证。

即：**目录功能能跑起来，依赖两条未声明的契约前提**。一旦前提不成立（重复标题「小结」、代码块内的 `#` 行、Setext 标题、`maxLength: 100` 截断），就会出现目录项点不到 / 点错位置。

**这恰恰是 N-16 想消灭的分歧的未完成部分**：数据源统一了（都读 `/toc`），**定位算法没统一**。而 `01:18`「不自行生成目录锚点」在 Flutter 里也**无法字面实现**——渲染器**必须**在渲染时给标题挂上可寻址的 key/锚点，只是锚点的**值**应当取自服务端。现措辞会让开发 AI 困惑：既不能自己生成，服务端又只给了字符串，那绑定动作到底写在哪一层？

**建议（三件，均不改契约语义）：**

1. **措辞订正**（`01:18` / `03:13`）：改为「渲染器在渲染正文时为标题生成锚点，**锚点值采用服务端 `anchor`**；不自行生成目录**数据**（层级与文本一律取自 `/toc`）」——把"数据来源"与"渲染锚点"两件事分开，现在混在一句话里。
2. **差异表登记**（`03 §6`）：新增「文章目录锚点配对」行——当前已知「契约未声明 `TocItem` 顺序与 slug 化规则，`anchor` 描述仅『slug 化标题』一句」；开工前动作「Phase 2 用**含重复标题 + 代码块内 `#`** 的代表性文章，逐项比对服务端 `anchor` 与 Flutter 渲染绑定结果；按顺序配对作为**约定**记录并验证」。
3. **契约侧回流建议**（登记即可，本阶段不改契约）：`TocItem` 补一句「数组顺序与正文标题出现顺序一致」+ 说明重复标题的 anchor 去重规则。这条比 N-19 更容易被契约侧接受，因为它只是**把已有实现的事实写成文字**。

### 🔴 N-19（P1）· 「保存草稿」依赖契约未定义的行为 —— N-6 的镜像后门只关了一半

**事实链（全部取证）：**

1. `03:56` 要求：「创建文章使用 `POST /articles` 时，客户端**必须显式下发 `status`**：保存草稿发送 `draft`，提交审核发送 `pending`；任何创建请求不得省略 `status`。」
2. **契约核验**——`ArticleCreate.status` 的**完整** description 原文：

   > 目标状态。权限约束：**member 传入 `published` 时后端忽略并降级为 pending**（会员无法直接发布）；editor 与 admin 可直接置为 published。

   **只约束了 `published` 一个取值。** member 传 `draft` 会怎样——被尊重落库 draft？被降级？被忽略用默认？**契约全部未定义。**

3. **契约核验**——`POST /articles` 的 description 原文：「会员创建默认 **draft/pending**；admin 可 published。slug 仅 admin 可指定。」依旧没有单一默认值。
4. `03:71` 差异表登记的澄清项是：「`ArticleCreate.status` 非必填，契约写『member 创建默认 draft/pending』但未明确单一默认值」→ 开工前动作「登记契约澄清 member **省略** `status` 时的落库状态」。
   **登记的是「省略」的情形，不是「显式传 `draft`」的情形。**
5. `04:59` Phase 4 前置检查的澄清项同样只覆盖**更新**：「确认 member **更新** draft/pending 保持原值、published 转 pending 的契约描述已澄清」。
6. **最有力的对比证据**：同一 schema 里的 `slug` 字段，description 自己写着——

   > 可选的 URL 别名。权限约束（**与 status 同规格显式化**）：**member 传入 slug 时后端一律忽略**（创建时留空、更新时保持原值）…editor 与 admin 可直接指定。

   `slug` 把三条路径（创建/更新 × member/editor/admin）**写全了**，并自陈「与 status 同规格」。**反证：`status` 只写 `published` 一种，是同一范式下的遗漏**，不是设计者刻意的模糊。

**风险推演：**

`03:56` 让客户端「保存草稿必发 `draft`」，但**没有任何契约条款保证 `draft` 被尊重**。若后端实现者把 `published` 的降级规则**泛化**为「member 传入的非 pending 值一律降级」，则：

> 用户点「保存草稿」→ `POST /articles {status: draft}` → 服务端落库 `pending` → **草稿被当作投稿送审**。

这正是 N-6 要消灭的「待审被误撤回」的**镜像事故**，只是发生在创建侧。而 Phase 4 出口（`04:61`）恰恰断言「**草稿保存后仍为 draft**」——若契约未澄清，这条验收会**在后端行为分歧下失败**，且分歧归因不清。

**建议（三件，均不改契约语义）：**

1. **差异表登记**（`03:71` 该行扩写）：把澄清范围从「member 省略 `status` 时的落库状态」扩为「**member 省略、以及显式传 `draft` 时的落库状态**」——即登记「member 显式传 `draft` 的接受性未声明」。
2. **Phase 4 前置检查**（`04:59`）加一条：member **显式传 `draft`** 创建 → 落库为 `draft`；显式传 `pending` → 落库为 `pending`（与既有的「更新后状态不变」验证并列）。
3. **契约侧回流建议**：`ArticleCreate.status` 照 `slug` 的规格补「member × 各取值」矩阵。这是**纯描述补齐**，不改任何语义——与 N-18 的第 3 条同属最容易推动的契约澄清。

### 🟡 N-20（P2）· 第三方 callback 的限流口径三处不一致，且无验收落点

| 文档 | 原文 | 隐含结论 |
|---|---|---|
| `README:43` | 「第一阶段只做账号密码登录；第三方登录后端虽有契约占位，但当前不作为 APP 主线」 | **不实现** |
| `01:77` | 「不做第三方登录」 | **不实现** |
| `03:45` | 「当前免鉴权的 `/auth/login`、`/auth/register`、`/auth/refresh`、**第三方 callback**，以及公开读取、可选鉴权的 view 等多个操作明确声明 429/5001；**这些请求都必须处理限流**」 | 要求**处理** |
| `05:18` | 验收矩阵限流行：「公开读取、可选鉴权 view 及登录/注册/刷新接口注入 429」 | 落点**无 callback** |

**契约核验**：`/api/v1/auth/{provider}/callback`（L976）确实存在，且确实声明 `'429'`（实测 21 个声明 429 的操作中包含它）。所以 `03:45` 的事实**是准确的**。

**问题不在事实，在口径**：APP 不实现第三方登录 → 不会调用 callback → 「必须处理其限流」是**无落点要求**；而验收矩阵也确实没给它落点，形成自我矛盾。

**建议**：`03:45` 把 callback 从「必须处理清单」移出，改为**规则举例**——「`/auth/*` 是否限流须逐个看 operation 声明（例如 `/auth/{provider}/callback` 已声明 429；若后续启用第三方登录，须一并处理）」。这样既保住「不从路径名推断」的教学价值，又消除与 `README:43`、`01:77` 的冲突。

### 🟡 N-21（P2）· `/toc`、`/adjacent` 对未发布文章的行为未定义，而投稿预览页可能触达

**事实链：**

- `02:28` 投稿预览页：用带 Bearer 的 `GET /articles/{idOrSlug}` 读**本人未发布稿件**
- `02:47` 预览页：「预览时**使用和文章详情相同的 Markdown 样式**」
- `02:39` 文章详情：「目录使用 `GET /articles/{id}/toc`…」→ 详情页是**带目录**的
- **契约核验**：`/toc` 的 `security: []`（**空数组 = 完全公开**），无 `x-authz`，404 只写「文章不存在（code 3001）」，**没有一句**说明未发布文章对作者本人是否可见
- **对比**：`/view` 明确写「仅 `published` 文章可计数；**draft/pending 一律 404（含作者本人）**」——同类子资源里，`/view` 写了、`/toc` 没写
- `/adjacent` 描述写「仅 `published` 文章参与」（**筛选**语义），且其 404 写作「文章不存在**或不可见**」（含**可见性**表态，但未说明作者本人是否例外）

> **订正（v1.1）**：本项初版将 `/adjacent` 概括为「只写筛选语义」，**漏引了它 404 的「或不可见」措辞**。补正后本项定性**更锐利**：同族三端口径为「`/view` 明确 / `/adjacent` 隐含 / `/toc` **完全未表态**」，`/toc` 是唯一完全未表态者。**结论（方案 A）不变，推荐依据更强**。详见 [`满分冲刺工单 §5`](./M4-产品AI设计文档满分冲刺工单-95到100.md#5-本轮自我订正评审方自身)。

**结论**：若预览页照 `02:47`「与详情同样式」实现，则需要目录 → 调 `/toc` → **对未发布文章的行为未定义**（可能 404，也可能返回内容，取决于后端实现）。这正是七端一致性要消灭的分歧点。

**建议**：`03 §6` 差异表登记「`/toc`、`/adjacent` 对未发布文章的响应未声明」，开工前动作二选一并写死：
- **方案 A（推荐，零契约变更）**：预览页**不显示目录与上下篇**（上下篇对未发布文章本无意义），并在 `02:28` 预览页的「必须状态」里明确写出；
- **方案 B**：Phase 0 用作者 Bearer 实测 `/toc` 对 draft 文章的响应，据实测结果写入 `03`。
