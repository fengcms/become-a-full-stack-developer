# M4 Flutter 产品 AI 设计文档第五轮评审回应

评审报告：[`M4-产品AI设计文档第五轮评审报告.md`](./M4-产品AI设计文档第五轮评审报告.md)

## 总体结论

第五轮报告和配套工单提出的 G-1 至 G-5 均采纳，已修订产品规划文档并补齐 Phase 2、Phase 4 的验证门槛。核心原则是把 OpenAPI 已明确的内容写成实现依据，把 OpenAPI 没有保证的内容标成待验证行为；静态文档审查不能代替运行时验证。

本轮只修改 Flutter 规划与评审文档，没有改 OpenAPI、后端或 APP 实现。目录锚点配对、member 创建稿件的状态落库行为仍须在对应阶段实测；实测不通过时，应先由 API/后端负责人澄清契约，再开放相关功能验收。

## 逐项处理

| 工单 | 结论 | 处理结果 |
|---|---|---|
| G-1 / N-19：创建状态被写成契约保证 | 采纳 | `03 §5` 改为：客户端发送 `draft`/`pending` 是产品意图；契约只明示 member 传 `published` 的降级规则，没有说明 member 显式传 `draft` 或 `pending` 是否被接受。显式传 `draft` 落库为草稿需实测后才能视为已验证。 |
| G-2 / N-18：目录锚点配对前提未登记 | 采纳 | `01` 和 `03 §2/§6` 分开说明目录数据与渲染定位：层级/文本来自 `/toc`；渲染器为标题建立可寻址 Widget key，值采用服务端 `anchor`，客户端不自行 slug 化。差异表记录契约未规定 slug 算法和数组顺序；Phase 2 用重复标题、代码块内 `#`、Setext 标题样稿验证。只有通过实测后才采用顺序配对约定；失败则先澄清契约，不开放目录跳转。 |
| G-3 / N-19：创建状态差异登记不完整 | 采纳 | `03 §6` 将 member 省略 `status`、显式传 `draft`、显式传 `pending` 三种未定义结果一并登记。Phase 4 前置检查要求用独立测试数据验证 draft/pending 的实际落库结果，并由 API/后端负责人澄清契约。 |
| G-4 / N-21：投稿预览可能触达未定义子端点 | 采纳，采用方案 A | `02` 投稿预览只呈现正文与 Markdown 样式，不显示目录或上下篇；`03 §6` 登记三端点对未发布资源的口径差异；`04` Phase 2 前置检查与 `05` 验收矩阵均要求确认预览不请求 `/toc`、`/adjacent`，且这两个端点只用于已发布文章详情。 |
| G-5a / N-20：第三方 callback 限流口径冲突 | 采纳 | `03` 保留“逐 operation 读取 429”的通用规则，同时说明 callback 虽声明 429，但第一阶段不实现第三方登录，故不纳入本阶段处理与验收；启用第三方登录时再纳入。 |
| G-5b / N-22：第四轮回应措辞歧义 | 采纳 | 将“发布文章详情后”订正为“已发布文章的详情页加载后”。 |
| G-5c / N-23：README 评审索引会随轮次失修 | 采纳 | `README` 改为单一历轮索引入口，并新建本目录 [`README.md`](./README.md)，集中列出架构、产品 AI、设计 AI 各轮报告和回应。 |
| G-6 / N-24：产品与设计改动混在工作区 | 接受为流程观察 | 本轮不提交、不改动设计侧文件；提交拆分属于后续仓库协作安排，不影响本轮文档整改。 |
