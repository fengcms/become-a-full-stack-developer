## 2. 🔴 A-1 · 「会员撤回待审稿件」在契约中无端点支撑

**跨 7 处文档 + 原型的功能，契约不存在。**

文档侧主张：

| 位置 | 原文 |
|---|---|
| `README.md` §产品方向 | 「会员可以投稿：草稿、预览、提交审核、**撤回**、重新送审…」 |
| `02` §5 | 「待审核可编辑/**撤回**」 |
| `03` §4 | 「决定编辑、删除、**撤回**、送审…控件是否显示」 |
| `04` Phase 4 | 「保存草稿、提交审核、**撤回**、重新送审和删除」 |
| `05` §1 验收矩阵 | 「草稿、刷新恢复、预览、投稿、**撤回**、重投、删除」 |
| `06` §11 | 「投稿状态机按契约实现：草稿可提交、待审核可**撤回**…」 |
| `prototype/02` `handleAct` | `case 'draft': if(a==='withdraw'){ d.status='draft'; toast('已撤回为草稿'); }` |

契约侧事实（grep / 脚本取证）：

- **契约全文无「撤回」字样**。
- `pending → draft` 仅由 `POST /api/v1/admin/articles/{id}/status` 承载，其 `x-authz.minRole = admin`，契约原文：「**admin 的万能置位端点，可在三态间任意转移（下架 published→draft、退回 pending→draft 等）……故仅限 admin**——普通流转请用 submit / approve。」
- `POST /api/v1/articles/{id}/submit` 原文：「**合法前态仅 `draft`**。当前状态为 pending / published 时返回 409 / code 3003」。
- `PUT /api/v1/articles/{id}` 原文只定义一种状态副作用：「member 编辑自己已 published 的文章，保存后状态自动退回 `pending`」——**未定义 pending→draft**。

**风险**：`ArticleCreate` 虽含 `status: enum [draft, pending, published]`，但契约未授权 member 用 PUT 做 pending→draft。若前端照原型实现撤回，行为取决于各实现端「顺手」的写法——**这正是契约要消灭的 Node / Go 分歧**。

**建议（二选一，需 owner 拍板）**：

- **方案 A（推荐，零契约变更）**：从 APP 范围移除「撤回」。待审稿件仍可**编辑**（`PUT`，保持 pending）；退回草稿是**管理员**动作。文档 7 处 + 原型按钮同步删除。
- **方案 B**：若产品确需会员撤回，按项目铁律**先改契约再改实现**（登记 M4 契约变更请求），M4 本轮不实现。

> 🔗 原型侧联动项（按钮 + toast）已在设计 AI 报告中登记，见本报告 §7 交接表。

## 3. 🟡 A-2 · 评论「三态反馈」在 APP 中不可达

**主张**：`04` Phase 5「rejected / reviewing / approved 三态反馈，拒绝后保留输入」；`05` 验收「评论…审核隐藏、拒绝保留输入」；`06` §6.5 列「评论复核中 → 复核中」「评论未通过 → 未通过」。

**契约事实**：

- `GET /api/v1/articles/{idOrSlug}/comments` 原文：「**只返回 status=approved 的评论——对任何调用者（匿名、评论作者本人、文章作者、admin）都一样**。`reviewing` / `rejected` 不出现在本列表」。
- `POST /api/v1/articles/{idOrSlug}/comments` 原文：「违规比率超阈值则 rejected，否则 approved（**自动流不产生 reviewing**）」；成功 `data.status` 为 approved 或 rejected。
- **契约无 `/me/comments` 端点**（`/me/*` 全集：articles / attachments / favorites / history / profile / change-password / likes / notifications）。
- `Notification.type` 枚举 = `[article_published, comment_approved, system]`——**没有「评论被拒」类型**。

**结论**：`reviewing` 在 APP 内**不可达**；`rejectedReason`（Comment schema 字段）**无客户端入口**（仅 `GET /admin/comments` 可见，而 APP 不做后台）；所谓「三态反馈」实际只能在**发表评论的即时响应**中看到 approved / rejected 一次。

**建议**：

1. `06` §6.5 删除「评论复核中」行；「评论未通过」限定为「**发帖即时反馈**」语义，并建议补一条「发帖被拒 + 展示原因（若 POST 响应含 `rejectedReason`，Phase 0 联调确认）」的反馈态。
2. `04` Phase 5 与 `05` 验收把「三态反馈」改写为「**发帖响应即时反馈（approved / rejected）+ 通过后站内通知**（`comment_approved`）」，并显式声明「审阅中 / 被拒的持久状态在 APP 不可见（契约无 `/me/comments`）」。
3. 原型侧修正见设计 AI 报告 §3（样稿徽章 + PS-05 状态列表）。

## 4. 🟡 A-3 · 令牌层小缺口（06 侧）

- **`color.bg.wash` 未在 Flutter 令牌落地**：`06` §2.1 定义了焦点区渐变 `#F0F7FE → #E4F0FB`，但 `prototype/app_theme.dart` 的 `AppColors` **无对应字段**（原型/样稿用 CSS `--hero-wash`）。建议在 `06` §2.1 **明确落地形态**：或在 `AppColors` 增 `heroWashFrom / heroWashTo` 两色（`ThemeExtension` 不能直接放 `LinearGradient` 才需拆色），或明确「渐变由组件内联常量」。**规范侧先定形态，Dart 侧再补字段**（Dart 动作见设计 AI 报告 §7）。
- **`06` §6.1 次级按钮边界写死 `#C7DBEA`**（裸值），违反本规范 §0「页面只引用令牌，不出现裸值」的自定规则。建议立令牌（如 `line.button`）。
- **`sp` 与 Flutter 的关系需注明**：`06` §3 称「字号单位统一用 sp（随系统字体缩放）」，但 Flutter 的 `fontSize` 是逻辑像素，缩放靠 `MediaQuery.textScaler`。建议在 `06` §3 补一句实现说明（`app_theme.dart` 侧未做 textScaler 处理，§3「放大 1.3 倍不横向溢出」需在实现层用 `maxLines / ellipsis / 横向滚动`兜底）。
