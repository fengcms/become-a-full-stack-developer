## 2. 🆕 N-16（P1，本轮最高价值）端点映射缺 4 个「`02` 要求 + 契约已提供」的公开端点

### 审计方法

脚本导出契约全部 53 路径 / 67 操作，逐条比对 `03 §2 功能映射` 的登记情况，并排除 admin / 后台能力（`01:77` 明确「不做后台管理移动端」）。**结论：契约已提供、`02` 页面明确要求、但 `03` 完全未登记的公开读端点共 4 个。**

| `02` 页面要求 | 契约已提供（原文） | `03` 现状 |
|---|---|---|
| **目录**（`02:39`「目录用可折叠底部面板或顶部抽屉，点击目录后关闭面板并滚动到标题」、`02:36`「目录」） | `GET /api/v1/articles/{id}/toc`（`security: []` 公开）：「**由正文 Markdown 标题解析生成目录**，供长文侧边导航」 | ❌ **未登记**；且 `03:59` 差异表写「Markdown 目录 \| 网站从解析结果生成 \| **选择 Flutter 解析库并做中文/重复标题快照**」——把已完成的服务端能力安排成客户端解析 |
| **上下篇**（`02:36`「…目录和**上下篇**」） | `GET /api/v1/articles/{id}/adjacent`（公开）：「返回当前文章在同排序（`-publishedAt`）下的**相邻两篇**，仅 published 参与；用于文章底部导航」 | ❌ 未登记 |
| **阅读量**（`02:38`/`04:38`「点赞、收藏、**阅读量**/阅读历史的匿名与登录分流」） | `POST /api/v1/articles/{id}/view`（可选鉴权）：「**阅读量 +1（带防刷去重）**」 | ❌ 未登记（`03:17` 阅读历史行只写「阅读进度和历史写入节流」） |
| **分类页「多级分类树」**（`02:18`） | `GET /api/v1/categories/tree`（公开）：「**分类树（整树）**」——与 `GET /api/v1/categories`（「分类**平铺列表**」）是两个端点 | ❌ 未登记；`03:12` 只写了 `/categories`，**照此实现会拿到平铺列表、需客户端自行建树** |

（另有 `GET /articles/{id}/related`「基于共享标签 + 同分类打分…用于『看完还看』推荐」——`02` 未要求，属**可选**增强，可在 P2 层决定是否纳入。）

### 为什么这是本轮最该处理的一项

1. **「目录」是与网站口径分叉的高风险点**：契约端点由服务端解析正文生成，天然与网站一致；`03:59` 让客户端自己解析并「做中文/重复标题快照」——**同一篇文章在网站和 APP 会得到两份不同的目录**。这正是差异表本想消灭的那类分歧，却在差异表里被主动引入。
2. **阅读量上报有一条契约明写的客户端配置要求**，而 `03` 完全没有登记。`POST /articles/{id}/view` 的可选鉴权描述原文：

   > 「携带 Bearer 则按 `user_id` 去重，否则按 `ip+ua` 哈希去重……**各端生成客户端须配置『持有令牌则自动附加 Authorization』，否则登录用户会退化到匿名去重分支**——这是契约驱动生成的已知注意点。」

   即：若生成式客户端未对**可选鉴权**端点自动附加令牌，登录用户的阅读量会按 IP 去重，**与网站按 user_id 的去重口径不一致**，`viewCount` 会出现系统性偏差。且契约还明确分工：「本端点**只递增 view_count，不写入阅读历史**；阅读历史由鉴权端点 `POST /me/history` 上报」——`03` 也未登记这条分工，照现有文字容易只调 `/me/history` 而阅读量永不增长。

3. **实现注记**：`/toc`、`/adjacent`、`/related`、`/view` 的路径参数都是 **`{id}`（integer）**，而 APP 的文章详情路由是 `/articles/:slug`。因此客户端必须**先用 `GET /articles/{idOrSlug}` 拿到 `Article.id`，再用它调用这四个子资源端点**。建议在 `03` 一并写明，避免开发 AI 试图用 slug 调这些端点。

### 建议（不改契约语义）

1. `03 §2`：在「首页/列表/详情」行拆出**文章详情子资源**，登记 `GET /articles/{id}/toc`、`GET /articles/{id}/adjacent`、`POST /articles/{id}/view`；分类行把 `/categories` 明确为「平铺」、并登记 `/categories/tree` 用于分类页整树。
2. `03 §4`：补「**可选鉴权端点（`security: [{}, {bearerAuth: []}]`）必须配置『持有令牌则自动附加 `Authorization`』**」，并点名 `/articles/{id}/view` 的去重分支后果；同时登记「view 只递增计数、阅读历史走 `POST /me/history`」的分工。
3. `03 §6` 差异表：把「Markdown 目录」一行的「开工前动作」改为**二选一并说明理由**——(a) 直接用 `GET /articles/{id}/toc`（**推荐**，保证与网站一致）；(b) 仍走客户端解析，则须显式接受「与网站可能不一致」并说明是为了什么（如离线可用）。**不能像现在这样默认客户端解析而不提服务端已有端点。**

## 3. 🆕 N-14（P1）「投稿预览」页的数据源未登记，且不存在 `/me/articles/{id}`

### 事实

- `02:28` 有独立页面「**投稿预览** \| `/member/articles/:id/preview` \| 私人预览 \| 非本人、稿件不存在」；`02:59` 也说「草稿和待审核稿件进入编辑或**私人预览**」。
- 契约中能取到**未发布**单篇的端点**只有一个**：`GET /api/v1/articles/{idOrSlug}`，其描述原文：

  > 「**可选鉴权**：匿名可访问；携带 Bearer 时按登录身份放宽可见性。未发布文章（draft/pending）对匿名用户返回 404；**仅作者本人与 admin 可见未发布详情**。」

- 契约**只有 `GET /api/v1/me/articles`（集合，L1420），没有 `/me/articles/{id}`**。
- 但 `03` 全文**没有「预览」二字**：`03:19` 投稿行的端点族为 `GET /me/articles`、`POST /articles`、`PUT /articles/{id}`、`POST /articles/{id}/submit`、`DELETE /articles/{id}`——**不含 `GET /articles/{idOrSlug}`**；`03:12` 详情行则只标注「**只展示 published**」。

### 风险

开发 AI 要实现预览页时，在 `03` 里找不到「取未发布单篇」的端点，只有两条路可走：凭直觉写 **`GET /me/articles/{id}`（契约中不存在 → 404）**，或按 `03:12`「只展示 published」判断详情端点拿不到草稿 → **自造方案**（本地渲染草稿、或绕用 admin 端点）。两种都偏离契约。

### 建议

- `03:12` 补一句：「`GET /articles/{idOrSlug}` 为**可选鉴权**端点，携带 Bearer 时**未发布详情对作者本人与 admin 放宽**——这是「投稿预览」页的数据源」。
- `03:19` 投稿行端点族补 `GET /articles/{idOrSlug}`。
- 明确写「**不存在 `/me/articles/{id}`**；取单篇一律用 `GET /articles/{idOrSlug}`」，与上轮 N-6「把歧义堵在文档里」的做法一致。

## 4. 🆕 N-12（P2）Phase 3 出口的「特定 UX」错误码清单漏了该阶段最常撞的四个码

`04:49` Phase 3 出口写：「…私有请求不会进入公开缓存；**1003/1004/1005/5001 有特定 UX**。」

**先说结论：`5001` 留在 Phase 3 是正确的**——我脚本核验了 429 的声明范围，`POST /auth/login`、`POST /auth/register`、`POST /auth/refresh`、`POST /auth/{provider}/callback` **均声明了 `429`**，Phase 3 的认证链路确实会撞限流。（本轮我初期曾假设「鉴权端点不设此限 ⇒ auth 不限流 ⇒ 5001 放错阶段」，经核验**该假设不成立**，见 §7 方法学注记。）

**真正的问题是漏列**：

| 漏列码 | 契约中的可达路径（逐码脚本导出） | 阶段归属 |
|---|---|---|
| **1001** 凭据错误 | 仅 `/auth/login` **一处** | **Phase 3 唯一可达阶段** |
| **1002** token 无效/过期 | 仅 `/auth/refresh` **一处** | **Phase 3 唯一可达阶段** |
| **3002** 唯一性/引用冲突 | `/auth/register`（用户名或邮箱占用）、`/me/profile`（邮箱占用）等 | **Phase 3**（正是上轮刚修正 UX 的码） |
| **4001** 字段校验 | `/auth/register`、`/me/profile`、`/me/change-password` 等（契约共 9 处） | **Phase 3** |

Phase 3 恰好是这四个码的**唯一或主要可达阶段**，而出口条件只枚举了 1003/1004/1005/5001。`3002` 的 UX 上轮刚改（从「刷新重试」改成「提示更换取值」），**正是最需要在 Phase 3 验收的点**，却不在此列。

**建议**：`04:49` 改为「1001/1002/1003/1004/1005/3002/4001/5001 有特定 UX」，或在 Phase 3 前置检查里补一条「验证登录失败（1001）、刷新失效（1002）、注册/改邮箱冲突（3002）、表单校验（4001）四种反馈」。

## 5. 🆕 N-13（P2）限流的验收动作没有落点

- 契约 `x-rate-limit`：限流施加于**公开（未登录可访问）端点**，`limit: 60 / window: 1m / scope: per-endpoint`。
- 我脚本核验了**声明 429 的全部公开读端点**：`/articles`、`/articles/{idOrSlug}`、`/articles/{idOrSlug}/comments`、`/articles/{id}/adjacent`、`/articles/{id}/related`、`/articles/{id}/toc`、`/articles/{id}/like/status`、`/categories`、`/categories/tree`、`/categories/stats`、`/categories/{id}/breadcrumb`、`/members/{id}`、`/search`、`/site/settings`、`/stats`、`/tags`——**全部落在 Phase 2 公开阅读主线**。
- 但 `04:34` 的 Phase 2 前置检查只列 3001/3003/5000，**没有 5001**；`05:27` 风险条目已明确写「公开首页、文章列表和搜索可能返回 429 / code 5001，并携带 Retry-After……**验收时要注入 429 并验证提示与恢复**」，而 **`05 §1` 必过验收矩阵里没有任何限流行**。

即：**风险条目承诺了一项验收动作，验收矩阵里却没有承载它的行**。任一执行者按 `05 §1` 打勾验收时，限流退避这条会被整条跳过。

2. `05 §1` 增一行：`限流 | 公开端点注入 429 / code 5001 | Retry-After 提示与退避恢复；不把限流当 500 无限重试`（与 `05:27` 风险条目的判据逐字对应）。

## 6. 🆕 N-17（P2）契约「鉴权端点不设此限」一语有歧义，`03` 应把规则写实

- 契约 `x-rate-limit.description` 原文：「所有公开（未登录可访问）端点受网关层统一限流保护；超限返回 HTTP 429，带 Retry-After 头，业务 code 5001。**鉴权端点不设此限。**」
- 从**声明事实**看，「鉴权端点」指的是**需要鉴权的端点**：`/me/*`、`/admin/*`、以及 `POST/PUT/DELETE` 写操作**均未声明 429**；而**免鉴权的** `/auth/login`、`/auth/register`、`/auth/refresh`、`/auth/{provider}/callback` **都声明了 429**。
- 但「鉴权端点」字面上也可读作「认证端点 `/auth/*`」。若读者取后者，会得出「**登录/注册/刷新不限流**」的结论，从而**漏掉登录链路的 429 退避处理**——而它们恰恰声明了 429。

**建议**：不改契约语义，只在 `03` 把规则写实：「**所有免鉴权公开端点（含 `/auth/login`、`/auth/register`、`/auth/refresh`）都可能返回 429 / code 5001；需要鉴权的 `/me/*`、`/admin/*` 与写操作不声明限流**」。若要在源头消除歧义，则登记一条契约描述澄清（属文档层，不动语义）。

## 8. 方法学注记（本轮一次自我纠错）

本轮初期我基于契约 `x-rate-limit` 的「**鉴权端点不设此限**」一语，假设「Phase 3 的认证链路不会撞 5001」，进而准备把 `04:49` 列的 5001 判为「阶段错位」。**核验后该假设被推翻**：脚本逐操作检查 429 声明，`POST /auth/login`、`/auth/register`、`/auth/refresh` **都有 429**——真正的问题不是「5001 放错阶段」，而是「清单漏列了 1001/1002/3002/4001」（见 N-12），另加该措辞本身的歧义（见 N-17）。

## 11. 附：本轮独立核验所用命令（可复现）

```bash
# ① 端点覆盖审计：契约 53 路径 / 67 操作 vs 03 的登记情况
python3 - <<'PY'
import re
doc = open('docs/flutter-app/03-接口映射与数据约束.md', encoding='utf-8').read()
src = open('docs/api/openapi.v1.yaml', encoding='utf-8').read().split('\n')
cur = None; ops = {}
for ln in src:
    m = re.match(r'^  (/api/v1/[^:]+):\s*$', ln)
    if m: cur = m.group(1); ops.setdefault(cur, []); continue
    mm = re.match(r'^    (get|put|patch|post|delete):\s*$', ln)
    if mm and cur: ops[cur].append(mm.group(1).upper())
for p in sorted(ops):
    short = p.replace('/api/v1', '').replace('{idOrSlug}', '{id}')
    print(('✔' if short in doc else '✘'), ','.join(ops[p]), p)
PY

# ② 错误码可达路径（N-12 用）：按「code: XXXX」响应声明回溯所属路径
#     确认 1001 仅 /auth/login、1002 仅 /auth/refresh、
#     3002 含 /auth/register 与 /me/profile、4001 含 /auth/register 等 9 处。

# ③ 429 声明范围（N-17 用）：逐操作判定是否声明 '429'
#     结论：公开免鉴权端点（含 /auth/login、/auth/register、/auth/refresh）声明 429；
#           /me/*、/admin/* 与写操作不声明。

# ④ 四个子资源端点语义（N-16 用）
grep -n -A8 "^  /api/v1/articles/{id}/toc:$"      docs/api/openapi.v1.yaml
grep -n -A8 "^  /api/v1/articles/{id}/adjacent:$" docs/api/openapi.v1.yaml
grep -n -A8 "^  /api/v1/articles/{id}/view:$"     docs/api/openapi.v1.yaml
grep -n -A6 "^  /api/v1/categories:$"             docs/api/openapi.v1.yaml   # 平铺列表
grep -n -A6 "^  /api/v1/categories/tree:$"        docs/api/openapi.v1.yaml   # 整树
```
