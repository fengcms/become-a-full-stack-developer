## 2. 🆕 N-6（P1，本轮最高价值）「不得下发 status」只覆盖更新，创建侧留了镜像后门

### 事实（契约实证）

| 契约事实 | 出处 |
|---|---|
| `ArticleCreate.required: [title, content]` —— **`status` 是可选字段** | `openapi.v1.yaml` ArticleCreate 定义 |
| `ArticleCreate.status` 描述**只有一条权限约束**：「member 传入 `published` 时后端忽略并降级为 `pending`」——**未提任何默认值规则** | 同上 |
| `POST /articles` 描述原文：「**会员创建默认 draft/pending**；admin 可 published」 | L1065 |
| `PUT /articles/{id}` 描述原文：「member 编辑自己已 published 的文章，保存后状态自动退回 `pending`；editor 与 admin 编辑不改变状态」——**只定义了 published 一种前态** | L1166-1168 |

### 风险推演

本轮 `03:49` 的禁令写的是「**更新文章**使用 `PUT /articles/{id}` 时，客户端不得下发 `status`」。这个限定是准确的，但：

1. **开发 AI 极可能过度泛化**——文案主体是「客户端不得下发 `status`」，很自然会被理解成「所有文章写入接口都不下发 `status`」；
2. 一旦泛化到 `POST /articles`，「**保存草稿**」按钮就会创建出一篇**不带 `status` 的稿件**。而契约对这种情况的默认值只有一句有歧义的「默认 **draft/pending**」——**到底是 draft 还是 pending，契约没说**；
3. 若服务端按 `pending` 落库，用户点「保存草稿」实际得到的是**已进入审核队列的稿件**——内容被误投稿，且用户无从察觉。这与 N-1 的「待审核被误撤回」是**同一类静默事故的镜像**（一个误撤、一个误投）。

### 建议（不改契约语义，与「零契约变更」方案一致）

1. **`03 §5` 补创建侧规则**：创建时**必须显式下发** `status`——
   - 「保存草稿」→ `status: "draft"`；
   - 「提交审核」→ `status: "pending"`；
   - 任何情况下**不得省略 `status`**（因为契约默认值有歧义，省略即把歧义交给实现）。
   即与更新侧的规则**方向相反**：更新一律不带、创建一律必带。建议把这两条写在同一处并显式点明差异，避免读者只记住一半。
2. **`03 §6` 差异表新增一行**登记创建侧默认值歧义：

   | 项目 | 当前已知 | 开工前动作 |
   |---|---|---|
   | 创建时的默认状态 | 契约原文「会员创建默认 draft/pending」有歧义；`status` 在 `ArticleCreate` 中非必填 | 客户端创建时显式下发 `status`（草稿→draft、投稿→pending）；登记契约澄清「member 创建省略 status 时的落库状态」 |

3. 顺带在 `04 Phase 4 前置检查`（`04:59`）把「创建显式下发、更新不下发」并列作为检查项。

## 3. 🆕 N-7（P1）错误码 `3002` 的 UX 指引与契约语义不符

### 事实（脚本导出 3002 的全部出现处）

| 契约出现处 | 语义 |
|---|---|
| `POST /auth/register` L796 | **用户名或邮箱已被占用** |
| `PATCH /me/profile` L2793 | **邮箱已被占用** |
| `POST /articles` / `PUT /articles/{id}` L1106/1241 | 文章 slug 已被占用 |
| `/categories`、`/categories/{id}`、`/tags`、`/tags/{id}` L1520~1886 | slug 已存在 / 父级成环 / 删除被引用拒绝 |

**契约中没有任何一处把 3002 用于「并发状态冲突」**——状态冲突的码是 **3003**（`POST /articles/{id}/submit` 非 draft 前态、`POST /admin/articles/{id}/approve` 非 pending 前态）。

### 问题

`03:39` 本轮新写：「**3002 冲突并刷新后重试**」。但 3002 在**会员端真实可达**的两处恰恰是：

- **注册**时用户名/邮箱被占用；
- **资料页**改邮箱时邮箱被占用。

这两处的正确 UX 是「**提示更换取值**」（改用户名 / 换邮箱），**刷新重试永远不会成功**。按当前指引实现，用户会看到一个「请刷新后重试」的提示、照做、再次失败——比不提示更糟。

### 建议

改为：「3002 **唯一性 / 引用冲突**：提示用户更换取值（用户名、邮箱、slug），不重试。APP 会员端可达场景为注册与修改资料时用户名/邮箱被占用。」

## 5. 🆕 N-9（P2）`02 §5` 矩阵把**尚未澄清**的副作用写成了既定事实

`02:50` 的 `pending` 行写「保存（**保持待审核**）」。但这一条**在契约里没有依据**——它正是 `03:61` 差异表里「仍需澄清」的那一项（契约只定义了 published 前态）。

即：**同一份交付物里，`02` 把它当既定行为、`03` 把它当待澄清项。** `02` 是页面规格、是开发 AI 直接照做的那份，读者只看到 `02` 就会以为服务端已经保证该行为。

**建议**：`02:50` 该格改为「保存（**预期**保持待审核，以 `03 §6` 契约澄清结论为准）」，或在矩阵下方加一句注记，让两处口径显式挂钩，避免澄清结论变化时只改一处。

（`02:51` 的 `published` 行「保存后进入待审核」**有**契约依据 L1167，无需改。）
