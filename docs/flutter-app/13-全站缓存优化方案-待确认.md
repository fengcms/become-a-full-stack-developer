# Flutter APP 全站缓存优化方案

状态：用户已确认并授权实施。本文保留确认时方案；实际实现及验证见 [14-缓存优化实施与验收](14-缓存优化实施与验收.md)。
日期：2026-10-02。

## 一、结论与目标

采用“保留页面状态 + 内存数据复用 + 公开内容磁盘缓存 + 后台更新 + 写入联动失效”的完整方案，沿用 Flutter、Riverpod、Dio 和现有接口。

预期体验：第一次访问正常加载；再次访问先展示已有内容；过期后在后台更新；主动下拉刷新才明确等待最新数据。刷新失败保留仍可使用的旧内容，不把已加载页面清空。点赞、收藏、评论、投稿、资料修改在相关页面及时同步。

本方案中的时间和容量均为建议初值，不是现有能力或已测性能。用户确认后实现、测试并据实调整。

## 二、现状核查

| 位置 | 当前实现 | 影响 |
| --- | --- | --- |
| `app/router.dart` | StatefulShellRoute.indexedStack 保留四个底部导航分支 | 已有部分页面状态保留，不能说每次切换 Tab 都会重建；尚无统一数据新鲜度策略 |
| `features/repository.dart` | articles/article/categories/tags/toc/comments 都直接调用 ApiClient | 页面销毁后重进、不同页面请求同一资源，无法复用结果 |
| `core/network/api_client.dart` | 有认证刷新单飞、会话代次保护，无业务 GET 缓存/同请求合并 | 认证稳定性已具备，但普通重复读取仍会发出多份请求 |
| `shared/widgets.dart` 的 AsyncPane | 组件实例内保留 Future，loadKey 变化或重新挂载才加载 | 并非所有 build 都重新请求，但缓存生命周期局限于当前组件 |
| `shared/widgets.dart` 的 ArticleFeed | 页码/列表保存在 State；reset 先清空 items | 重新访问、切换查询会加载；下拉刷新会清空旧列表 |
| `features/member.dart` 的 MemberPage | 在 build 中给 FutureBuilder 传入 overview(ref) | 页面 rebuild 可能重新启动整组统计请求，这是明确的额外请求来源 |
| MemberPage.overview | 收藏、历史、稿件各请求一次；为点赞总数逐页遍历 /me/likes | 会员数据较多时，打开“我的”会放大请求量 |
| ArticlePage.loadInteractions | 收藏状态通过收藏列表逐页查找 | 同一账号阅读多篇文章会重复扫描；不能把未加载到的文章误判为未收藏 |
| 通知 | 列表重进加载，已读后清空重载；未读数由 FutureProvider 保留 | 同时存在重复加载与缺少前台恢复刷新两种问题 |
| 图片 | Image.network，使用 Flutter 默认图片内存缓存 | 有内存缓存，没有明确磁盘缓存、统一预算和按显示尺寸解码策略 |
| 本地存储 | 主题、搜索历史、本机稿件已经保存；refresh token 安全存储 | 这些不等于接口缓存，不能在“清理缓存”时一并删除 |
| WebView | 原生 WebView 自己管理网页资源和网站存储 | 与 APP 的接口缓存应分开处理 |

原规划已提出公开短缓存及有上限的图片磁盘缓存（01、03、05 文档），目前实现不完整。本次还建议把私有数据从“默认实时请求”细化为“当前登录会话内短时间复用，不写磁盘”。这是需要此次确认的规划调整，实施时同步修订原文档，避免规则互相矛盾。

## 三、用户可感知的统一行为

1. 没有缓存：只在首次加载时显示骨架或加载状态；请求失败给重试入口。
2. 缓存仍新鲜：立即展示，不重复发起该资源请求。
3. 已过新鲜期但未到最大可用时长：先展示已有内容，同时合并发起一次后台请求。更新成功替换对应数据，不闪白、不重置阅读位置。
4. 超过最大可用时长：不可继续作为可用数据展示，重新加载。表中时长均从上次成功校验/取得数据计算，读取缓存不会延长有效期。
5. 后台更新失败：仍在最大可用期内时保留旧内容，轻提示“更新失败，当前显示上次内容”；没有可用内容时正常报错。错误结果本身不缓存成成功数据。
6. 下拉刷新/明确重试：绕过新鲜期，请求最新数据；刷新指示器等待实际请求完成。失败不清空已有可用内容。
7. 返回列表、从 WebView 返回文章：保留滚动位置、筛选条件和已经加载的分页，不重新跑完整首屏请求链。
8. APP 回到前台：只检查当前可见页面和必要未读数；未过期不请求、过期合并刷新；连续前后台切换做 30 秒触发节流。隐藏 Tab 不轮询。
9. 后台发现列表排序/成员变化：正在阅读长列表时显示“有新内容，点击更新”，避免突然插入顶部导致跳动。用户刷新时替换为新分页代次。
10. 断网只允许读取仍在可用期内的已访问公开内容。没有访问过的内容不承诺可读；不增加下载中心、整站离线包或离线写入队列。

## 四、建议缓存策略

“磁盘”用于 APP 重启后的复用；私有数据只保留内存。最大时长到期后不得继续兜底。服务器更严格的缓存约束优先。

| 数据 | 新鲜期 | 最大可用时长 | 保存方式 | 备注 |
| --- | --- | --- | --- | --- |
| 首页最新/焦点、分类/标签文章列表 | 2 分钟 | 24 小时 | 内存 + 公开磁盘 | 每种查询最多持久化前 3 页；不同排序、分页大小分别存储 |
| 热门阅读 | 5 分钟 | 24 小时 | 内存 + 公开磁盘 | 不与最新列表混用 |
| 公开文章正文、配套 TOC | 10 分钟 | 24 小时 | 内存 + 公开磁盘 | 仅匿名公开读取且 published；正文和目录作为一个版本发布给 UI |
| 上一篇/下一篇 | 5 分钟 | 1 小时 | 内存 | 独立于正文更新 |
| 分类树 | 30 分钟 | 24 小时 | 内存 + 公开磁盘 | 编辑器复用分类字典 |
| 分类统计、标签及文章数 | 5 分钟 | 24 小时 | 内存 + 公开磁盘 | 防止数量长时间不更新 |
| 站点配置 | 30 分钟 | 24 小时 | 内存 + 公开磁盘 | 仅展示必要字段 |
| 作者公开主页 | 5 分钟 | 1 小时 | 内存 | 资料与文章列表按同一响应更新 |
| 搜索结果 | 2 分钟 | 10 分钟 | 内存 | 最近 20 组查询；搜索历史仍按原规则独立保存 |
| 评论分页 | 30 秒 | 5 分钟 | 内存 | 页面重进时复用；发表/删除即更新并校验 |
| 点赞/收藏状态 | 30 秒 | 5 分钟 | 账号会话内存 | 状态区分“未知、已选、未选”；最大时长后校验完成再允许依赖旧状态的切换 |
| 收藏/点赞/阅读历史列表 | 30 秒 | 5 分钟 | 账号会话内存 | 本机写入同步更新，无须等 TTL |
| 会员首页统计 | 60 秒 | 5 分钟 | 账号会话内存 | 独立于 Widget build；无法确认准确总数时展示加载/待同步，不以部分列表伪造总数 |
| 通知列表与未读数 | 15 秒 | 1 分钟 | 账号会话内存 | 页面可见/前台恢复时按策略校验，标记已读立即联动 |
| 我的稿件列表 | 15 秒 | 1 分钟 | 账号会话内存 | 保存、提交、删除后立即失效相关列表 |
| 编辑器已有稿件、私有预览 | 不复用服务端读取结果 | 无 | 每次进入读取最新版本 | 本机自动保存稿件另行恢复；后台结果不覆盖正在编辑的文本 |
| 个人资料展示 | 会话用户快照 | 当前会话 | 内存 | 进入资料编辑仍实时读取；保存后更新所有头像/昵称显示 |
| 认证、密码、上传、各类写请求 | 不缓存 | 无 | 不进入读取缓存 | 不自动离线排队重放 |

“已保存的公开文章后来被撤下”在无推送的现有接口下只能在重校验时发现。本方案接受最长新鲜期的可见延迟；一旦服务端返回 401/403/404 或不可见业务码，立即移除相关内容与别名缓存，不能再用旧正文掩盖权限或删除结果。24 小时旧内容兜底仅适用于断网、超时、临时服务故障等，不适用于拒绝访问。

## 五、实现架构与一致性规则

### 5.1 分工

- 保留 Dio 负责传输、认证和错误识别，保留现有 epoch 防串账号机制。
- Repository 统一定义每类数据的缓存策略、数据键、查询合并与写入后的联动；迁移页面中散落的 api.request 读取逻辑，避免遗漏。
- Riverpod 管理订阅和共享状态，让详情、列表和会员页看到同一条文章的互动变化；页面只保留滚动/输入等 UI 状态。
- 公共磁盘缓存采用应用缓存目录下的版本化 JSON 文件、元数据索引和原子写入。当前规模不必增加数据库；损坏/升级不兼容时丢弃可重建缓存，不影响业务数据。
- 图片使用独立文件缓存与 Flutter 解码缓存；具体文件缓存组件在实施时核验版本、响应头处理和容量控制。保留现有技术栈，不用 SharedPreferences 存大批正文或图片。
- 不在 Dio 全局无差别缓存所有 GET，也不依赖无限 keepAlive 保住全部页面。

### 5.2 键与生命周期

缓存键包含：缓存格式版本、完整 API 环境（协议/主机/端口/路径前缀）、接口、规范化查询参数、访问范围。私有键另加 userId 和会话 epoch。query 参数排序以消除等价参数的重复条目，区分排序、分类、标签、搜索词、分页大小和页码。

公开正文采用明确的匿名读取路径，不把携带账号权限取得的文章响应直接写入公开盘。稿件预览必须走私有实时路径，不能先命中同 ID 的旧公开文章。id 与 slug 建立别名索引，正文去重存储；别名失效跟随文章一起清除。

相同键的并发 GET 共用一次请求。过期刷新不重复并发；失败请求移出在途表。显式强刷和写后校验使用新代次，旧响应不得覆盖新状态。

只写入成功、通过模型校验且允许缓存的数据。遵守 no-store、no-cache、private 等响应约束；不擅自忽略服务器限制。磁盘写入失败可降级内存并记录诊断，不让页面加载失败。

目前不把 ETag/304 当作既有能力：ApiClient 仅返回 data，没有传递响应缓存元数据；本轮线上响应头探测超时，不能确认网关是否支持条件请求。第一版以应用策略工作，必要时给 ApiClient 增加内部响应元数据通道；未来确认服务端支持后可接入条件校验，不要求改后端。

### 5.3 写操作联动

| 操作 | 即时行为 | 成功后的校验/失效 |
| --- | --- | --- |
| 点赞/取消 | 详情与已缓存列表同一文章同步显示；失败统一回退 | 用响应总数校准；更新当前账号点赞状态，失效我的点赞及会员统计 |
| 收藏/取消 | 当前账号收藏状态同步，收藏页增删对应条目 | 失效相关分页/会员统计；失败回退 |
| 评论发表/删除 | 仅已审核通过评论加入列表，删除移除对应评论 | 重算叠楼，校验受影响分页，拒绝结果不伪造成功评论 |
| 保存/提交/删除稿件 | 本机编辑内容保持；用写响应更新已知状态 | 我的稿件列表及数量失效；若已发布文章转待审核，移除相关公开缓存并校验列表 |
| 资料/头像修改 | 会话用户资料立即更新 | 失效相关作者资料和对应图片；处理同 URL 图片替换 |
| 通知已读/全部已读 | 已读样式及未读数联动 | 校验通知列表/计数，不清空整个页面 |
| 阅读进度/清空历史 | 本机历史状态同步 | 合并写入并失效相关历史/统计 |
| 退出/账号切换/认证失效 | 立刻撤销旧私有 UI | 清除旧会话数据、在途订阅及乐观状态；旧请求与磁盘任务不能回填旧数据 |

写操作开始就递增受影响资源代次，防止此前启动的后台 GET 用旧值覆盖乐观状态。回退仅作用于对应操作仍有效的版本，不能回退掉后续成功操作。

### 5.4 分页、计数与状态扫描

- 页面会话保存已经加载的页、查询和位置；响应缓存按页保存，两者不能混为一谈。
- 刷新第一页后，旧的第 2 页以后属于旧分页代次，不能继续拼进新列表。后台发现新版本时先保留当前阅读快照，用户切换到新版本后从新第一页继续加载。
- 同查询最多保留 20 页内存快照，最多 10 个非活跃列表；超过预算淘汰最久未用的非活跃查询，不承诺无限长列表位置永久可恢复。
- 收藏扫描共享账号内索引，记录已覆盖分页和“是否完整”。未扫描完时不能把缺席条目当作未收藏。命中已知条目可立即返回，其余按需接续扫描；更换分页代次重新校验。
- /me/likes 没有 total：会员总数首次仍需完整读取才能准确。扫描移到共享后台任务、并发合并、60 秒内复用，本机增减联动后再校验。大账号的首次扫描成本无法仅靠缓存消除，不承诺首访零延迟，也不私自添加后端接口。
- 缓存读取和后台校验不能触发阅读量上报。明确由用户进入文章的阅读事件上报一次；进度保存保持节流，缓存命中不跳过正常阅读记录。

## 六、图片、页面和网页资源

图片：公开封面和已确认公开的正文图片可落盘；私有头像、草稿附件、带签名/权限 URL 不能进入公共文件缓存。未知权限按保守规则仅当前会话内存。遵守源站 Cache-Control，签名参数不可为了“去重”从 URL 去掉。小封面按显示尺寸与像素密度解码，避免用原图占据大量内存；失败图可重试，不将错误永久保存。

页面：四个底部导航分支继续保留；给查询和滚动位置稳定标识。修复“我的”在 build 中启动 Future，以及返回编辑器即无条件重建整份列表的问题，改为根据真实修改事件更新。公开文章从正文返回时不因会话无关的重建重新闪屏。

Markdown：同一正文版本避免因点赞、收藏、主题以外的无关更新重复进行全文解析；有界复用解析/高亮结果，主题相关颜色按当前主题生成。不保存带 GlobalKey、BuildContext 的 Widget 树作为磁盘/全局缓存。

WebView：使用系统 WebView 的 HTTP 缓存规则，不强制 cache-only，不把第三方网页接入 APP 的接口缓存，不常驻多个 WebView。关闭仍直接返回来源页面。网站 Cookie/登录存储与可清理的资源缓存分开，不因清理阅读缓存退出第三方网站。

## 七、容量、清理及保护范围

建议初始预算：

- 公开 JSON 磁盘缓存 30MB，公开详情最多 100 篇；单项超过 2MB 不落盘。
- 图片磁盘缓存 150MB，最长保留 7 天，尊重更短服务端时效；单图超过 10MB 不落盘。
- 数据内存缓存按序列化体积估算 20MB、最多 300 个条目；这不是 APP 总堆内存上限，真实模型/解析占用需性能测试。
- 图片解码缓存预算 64MB；活跃图片和原生 WebView 占用另行观察，不能把该值误称为 APP 总内存限制。
- 超量按最近最少使用淘汰；遇到系统内存压力清除非活跃缓存、减少预取。缓存目录可被系统回收，全部读取都必须允许缺失。
- 首轮不做整站预抓、文章下一篇正文预加载或后台定时同步。若首屏仍有瓶颈，再按指标决定少量可视图片预取。

设置新增“清理缓存”，展示已管理磁盘缓存大小，清除公开阅读数据、公开图片及可重建的内存数据。清理动作使旧在途缓存写入代次失效，避免刚清完又被旧请求写回。当前页面按需要重新读取，不删除登录令牌、主题、搜索历史、本机未提交稿件，也不自动清除 WebView 网站登录信息。

本机自动保存稿件是用户内容，不是可随意淘汰的缓存。沿用账号隔离、保留到本人恢复的规则；本次不借缓存优化改变其保存/退出行为。

## 八、实施顺序与验收

以下阶段属于同一份完整交付，确认后依次实施，不做完内存缓存就停止。

| 阶段 | 主要工作 | 出口 |
| --- | --- | --- |
| 1. 基线与缓存核心 | 记录重复请求；实现策略表、规范化 key、内存层、同请求合并、代次保护、订阅状态 | TTL、并发、强刷、旧响应、账号切换自动化通过 |
| 2. 公共页面 | 首页各模块、分类/标签、搜索、文章/目录/相邻文章、作者页接入；保留分页和位置 | 重进可复用，下拉不清空，过期后台更新，内容与目录版本一致 |
| 3. 会员与写入一致性 | 修复 overview Future；共享状态扫描；会员列表/通知接入；写事件联动 | 点赞、收藏、评论、稿件、资料跨页一致；无串账号 |
| 4. 磁盘与图片 | 版本化文件缓存、预算淘汰、响应头规则、图片尺寸、清理入口 | 冷启动复用公开数据，私有响应不落盘，清理不损坏稿件 |
| 5. 完整验收 | 弱网、断网、前后台、缓存损坏、容量压力、生产只读回归；Android 模拟器运行 | 提交实测记录与请求对比，保留可运行 APP |

关键验收用例：

1. 先访问分类、标签，再从其他页面回到相同资源，新鲜期内相同业务 GET 增量为 0。
2. 10 个同键并发读取只有 1 个在途 HTTP 请求；不同账号、分页或排序不得错误合并。
3. 首次无缓存允许正常加载；有内存缓存的简单首屏目标 100ms 内展示，有磁盘缓存的简单首屏目标 300ms 内展示。以固定模拟器、固定数据集和 profile 模式实测；不承诺所有长文/机型达成。
4. 新鲜期到期，多处订阅只产生 1 次后台更新，UI 不闪白；更新失败时旧内容保持且错误可见。
5. 主动刷新确实请求接口；首页焦点/最新/热门均按刷新范围更新，分类树/数量不只刷新其中一项。
6. 点赞、收藏后详情、相关列表和会员数据同步；写失败回退一致；迟到旧 GET 不覆盖新值。
7. 列表刷新与加载下一页并发不混页；相同搜索词、相同筛选重进保留有效位置。
8. 退出/切换账号后检查内存、页面和磁盘；新用户看不到旧私有响应。公开与私有同文章 ID 必须隔离。
9. 服务端返回不可见/删除时淘汰旧正文；断网不能伪装为内容被删除。损坏缓存和磁盘写入失败不阻断正常联网阅读。
10. 清理缓存后草稿、登录、主题、搜索历史仍在；旧在途响应不重新填回已清除缓存。
11. 文章内部网页返回保持文章位置；网页历史不改变 APP 返回约定。
12. 每类请求记录缓存命中、过期、合并、请求耗时与数量，日志不包含 token、稿件正文或搜索原文。验收比较同一路径、同一账号、同一数据量的前后结果。

预估 3–5 个开发工作日量级，含完整接入与测试，仅作范围评估，不是基于当前代码已测得的工期保证。后端不改动，网站不改动；iOS 代码与配置覆盖，但本机缺完整 Xcode，运行验收仍以 Android 为准。
