# 验收标准与风险清单

## 1. 必过验收矩阵

| 领域 | 场景 | 证据 |
|---|---|---|
| 启动 | 首次打开、已有会话、过期会话 | 页面截图 + 请求日志无 token 泄露 |
| 主题 | 跟随系统、手动浅色、手动深色、重启恢复 | 同一页面三种主题截图 |
| 阅读 | 首页、分类、搜索、长文、代码、表格、图片失败 | integration test + 真机 |
| 互动 | 点赞、取消、收藏、取消、阅读历史 | API 结果与 UI 状态一致 |
| 认证 | 登录、注册、退出、密码变化、账号切换 | 并发刷新和旧响应测试 |
| 会员 | 收藏/点赞/历史/通知/资料空态与错误 | widget/integration test |
| 投稿 | 草稿、刷新恢复、预览、投稿、撤回、重投、删除 | 独立测试库完整流程 |
| 上传 | 合法图片、超大图片、非法类型、网络中断 | 上传结果、错误和正文保留 |
| 评论 | 叠楼、跨页、多级、审核隐藏、删除、拒绝保留输入 | 20+ 条评论的真实数据回归 |
| 设备 | 320/375/393/430dp、Android/iOS、键盘和返回 | 真机视频或截图 |
| 发布 | release 构建、配置、签名、API origin、日志 | 构建产物检查清单 |

## 2. 风险和处理

### 移动端 refresh token 不兼容

网站依赖 HttpOnly Cookie，而原生 Flutter 没有同等浏览器上下文。这是最高优先级风险。处理方式是 Phase 0 先做真实请求验证；如契约不足，先提出兼容方案，不能在客户端复制敏感 Cookie 逻辑。

### Markdown 能力不一致

Flutter Markdown 包对 GFM 表格、代码高亮、图片、链接、HTML 和标题锚点的支持可能与网站不同。准备代表性文章快照，逐项比对；不能因为“能渲染 Markdown”就认为内容一致。

### 编辑器体验和平台差异

移动端 Markdown 编辑器的光标、选择、粘贴、软键盘和图片插入体验明显不同于 Web。投稿编辑器应先做技术 Spike，再承诺复杂工具栏；编辑/预览可先用可靠切换模式，避免直接追求桌面分栏。

### 深层评论性能

评论接口返回扁平分页，APP 需要在客户端组树。使用迭代构造、限制视觉层级和按楼展开；禁止对不受控深度直接递归生成大量 widget。

### 图片和缓存

移动网络下图片失败很常见。图片需占位、重试、尺寸限制和缓存上限；不能把私有头像、草稿附件或带权限 URL 放进公共缓存。

### 公开缓存与登录状态

点赞/收藏状态属于账号，文章正文属于公开内容。query/cache key 必须包含用户身份或彻底分开；退出和切换账号必须清理私有状态。

### 产品范围膨胀

推送、离线、第三方登录、分享海报、支付和推荐算法都很容易在移动端顺手加入。没有对应后端、契约、设计和验收证据前，保持在 P2，不阻塞第一版。

## 3. 开发完成的最低证据

一次成功的 `flutter analyze`、`flutter test` 和 release 构建不代表功能完成。P0 功能至少需要真实测试库联调、Android 和 iOS 各一条关键路径、弱网/过期会话验证、浅色/深色截图及错误恢复证据。
