# 缓存优化实施与验收

日期：2026-10-02。依据用户确认的 13 号方案实施；仅修改 Flutter APP 与相关文档，未修改后端或网站代码。

## 交付内容

- 缓存策略统一在 Repository，网络层保留现有认证与错误处理。页面的读取显式接入策略，未经批准的 GET、写请求不会自动进入缓存。
- 新鲜数据直接返回；可用旧数据先显示、后台合并更新；强刷使用新代次，旧响应不能覆盖强刷或互动状态。后台错误保留仍可用内容，拒绝访问/404 移除旧内容且不会无限自动重试。
- 公开文章匿名读取后才进入磁盘。正文与目录成组存储；存在 updatedAt 时，读取目录后再确认文章版本，变化则不安装不一致组合。id/slug 别名可从磁盘索引恢复。
- 会员展示数据按完整 API 环境、账号 ID、会话 epoch 隔离，只保留内存。稿件编辑和私有预览实时读取。退出清理私有状态；认证过程和迟到响应的保护保留。
- 修复会员首页在 build 中启动新统计 Future。收藏索引逐页累积、已知命中直接复用，只有完整扫描才可判定“不在收藏中”；并发扫描共用任务，账号切换与收藏变更重置索引。
- 写入开始即隔离相关旧读取，成功/失败后失效受影响资源。点赞与收藏保留乐观更新和失败回退，点赞响应校准共享计数；评论、稿件、历史、资料和通知更新关联列表。通知已读在本地先展示，失败还原。
- 列表刷新保留画面，成功后才替换。后台发现新版本时提示用户更新；未采用新版本前暂停继续追加旧分页。切换到新版本时按查询清除旧分页。返回复用已加载分页和滚动位置，快照限定 10 个查询、每个最多 20 页；活跃列表继续允许往后加载。
- 分类、标签、搜索、作者、首页各模块、评论、通知采用各自 TTL；路由/Tab 返回和前台恢复只校验可见页面，前台事件有节流，不给隐藏页面轮询。
- 公开图片文件缓存和内存复用，按显示尺寸解码封面。私有图片、草稿图片及带查询参数的 URL 不进入公共磁盘缓存；因此带签名或版本参数的图片采取更保守策略，仅内存复用。
- Markdown 内容组件在输入未变化时复用；公开代码语法 token 有界缓存，颜色随主题生成，私有编辑内容不进入全局 token 缓存。
- 设置新增“清理缓存”及磁盘大小。只清理可重建缓存，不删除登录凭据、主题、搜索历史和本机未提交稿件；不改变 WebView 网站 Cookie 或网页历史行为。

## 容量及协议

公开 JSON 文件上限 30MB，正文最多 100 篇，单项超过 2MB 不落盘；列表只持久化前 3 页。数据内存最多 300 条、按序列化大小估算 20MB；搜索条目另限 20 条。图片文件上限 150MB，单图 10MB，最长 7 天并尊重更短服务端时效；图片原始字节内存另限 20MB，Flutter 解码缓存 64MB。以上不代表 APP 总内存上限，活跃 Widget、原生 WebView 等占用另算。

文件写入及索引采用临时文件改名，按访问时间淘汰；损坏文件可重新请求，索引损坏可重建。清理和会话变更隔离旧在途任务，内存压力时释放可重建内容。

读取 Cache-Control/Age；no-store/no-cache 不作为可复用数据缓存，private 不写公共磁盘，更短 max-age 优先。未实现 ETag/304 条件协商，不将它作为接口既有能力。本轮经本机代理检查生产 `/categories/tree` 响应，没有看到 ETag、Last-Modified 或 Cache-Control；不能据此推断所有接口或未来网关行为。

## 验证

### 自动化

- `flutter analyze`：无问题。
- `flutter test`：30 项通过，包括原有功能，以及请求合并、TTL、硬过期、迟到响应隔离、强刷、清理、无权限淘汰、响应头限制、磁盘重建、图片私有隔离、收藏部分索引、列表重进和刷新保留画面。
- Android 隔离后端 `integration_test/app_test.dart`：2 项功能用例通过，覆盖登录、真实文章阅读/目录、稿件保存/预览/提交、收藏、评论、深色模式、原生上传与下载。所有测试写入均指向本地 11002，没有为了验收写入生产账号数据。
- Android profile 模式 `integration_test/cache_acceptance_test.dart`：生产匿名只读验证通过，覆盖内存复用、新建 Repository/缓存实例后的磁盘恢复、磁盘 slug → ID 读取、模拟断网后的可用旧内容、强制刷新失败、分类页往返。

### 生产只读实测

原始结果：[cache-acceptance.json](evidence/cache-acceptance.json)。这是同一模拟器上“分类树、标签、文章列表、一篇文章正文/目录”的顺序读取样本，不是多机型性能结论。

| 场景 | 数据读取耗时 | 新增 HTTP 请求 |
| --- | ---: | ---: |
| 首次读取上述数据组 | 4971ms | 6 |
| 从内存再次读取同组 | 5ms | 0 |
| 重建缓存实例后从磁盘读取，文章改用 ID | 187ms | 0 |
| 已加载分类页，经其他 Tab 返回 | 未单独统计渲染耗时 | 0 |

“重建缓存实例”验证的是同进程内创建新 Repository/DataCache 并从持久化文件恢复，不能称作已测完整进程冷启动耗时。缓存统计里的 network 是逻辑资源读取数；正文/目录组合含多个 HTTP，因此不等于传输层请求数。

测试期间一次 profile 直连因模拟器网络失败而中止，随后在测试传输层显式使用本机代理重跑成功，TLS 校验保持开启。以上采用成功复测结果，原始 JSON 可追溯。

## 保留边界

- 缓存需要首次访问填充；不能让未访问过的页面在断网时凭空有数据。
- 离线只复用仍在可用期内的已访问公开内容，不是离线下载中心，也不排队重放写操作。
- 点赞列表没有 total，收藏没有单篇状态接口，首次准确统计/判定仍受逐页扫描成本影响。此次消除了反复读取与重复扫描，没有添加后端接口或使用不准确的推测总数。
- 无服务端推送时，其他设备和后台修改按 TTL/主动刷新发现；正文撤下后在首次重校验发现不可见时移除，不能保证离线瞬时撤回。
- 页码接口不提供快照版本，本次防止客户端缓存的新旧分页混用；服务端在两次请求之间连续插入/删除导致的分页漂移仍只能刷新重新读取，不能声称客户端能提供服务端事务快照。
- 首屏 100ms/300ms 是方案目标。现有证据验证数据读取命中耗时，没有把它当作完整页面首帧渲染达标证明，也未执行所有机型的长时内存压力测试。
- iOS 配置与共享 Dart 代码已覆盖，本机没有完整 Xcode，未做 iOS 运行验收。
