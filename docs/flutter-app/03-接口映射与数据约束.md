# 接口映射与数据约束

## 1. 单一事实源

接口、字段、错误码和状态转换以 [OpenAPI v1](../api/openapi.v1.yaml) 为准。网站已经证明后端接口可以支撑主要前台能力，但 Flutter 仍需重新生成或校验客户端模型，不能复制网站中的手写假设。

## 2. 功能映射

| APP 能力 | 端点族 | 客户端策略 |
|---|---|---|
| 登录/注册/恢复/退出 | `/auth/*` | 安全存储 refresh、内存 access；单飞刷新；退出清缓存 |
| 首页/列表/详情 | `GET /articles`、`GET /articles/{idOrSlug}`、`GET /categories`（平铺）、`GET /categories/tree`（整树）、`GET /tags` | 公开短缓存；分页游标/页码按契约；公开列表只展示 published；详情携带 Bearer 时可读取作者本人的 draft/pending，用于投稿私人预览 |
| 文章详情子资源 | `GET /articles/{id}/toc`、`GET /articles/{id}/adjacent` | `/toc` 目录数据取自服务端返回的 `level/text/anchor`；渲染器为标题建立可寻址的 Widget key，key 值采用服务端 `anchor`，客户端不自行 slug 化（契约未公开 slug 规则）；`/adjacent` 读取上一篇/下一篇，契约明确仅 published 参与。二者都要求整数文章 id；未发布文章可见性见 §6，目录锚点配对规则也见 §6 |
| 阅读量 | `POST /articles/{id}/view` | 可选鉴权；公开文章详情加载后上报一次，持有 access token 时自动附加 Bearer；只递增 viewCount，不写阅读历史 |
| 搜索 | `/search` | 搜索提交后请求；防止每个按键都请求；无结果不当成错误 |
| 作者主页 | `/members/{id}` | 只显示公开资料和 published 文章 |
| 点赞 | `POST/DELETE /articles/{id}/like`、`GET /articles/{id}/like/status`、`GET /me/likes` | 幂等写入；状态和列表以账号为 key |
| 收藏 | `GET/POST /me/favorites`、`DELETE /me/favorites/{articleId}` | 幂等写入；账号切换后清理状态 key |
| 阅读历史 | `POST /me/history`、`GET /me/history` | 阅读进度和历史写入节流；私有 no-cache；与 `/articles/{id}/view` 阅读量计数分开调用 |
| 评论 | `/articles/{idOrSlug}/comments`、`/comments/{id}` | approved 列表、parentId 组楼、回复/删除、审核反馈 |
| 投稿 | `GET /me/articles`、`GET /articles/{idOrSlug}`（详情只对作者本人放宽未发布可见性）、`POST /articles`、`PUT /articles/{id}`、`POST /articles/{id}/submit`、`DELETE /articles/{id}` | 列表用 `/me/articles`；编辑与私人预览单篇用 `/articles/{idOrSlug}`；契约不存在 `/me/articles/{id}`；draft/pending/published 状态机，保存与投稿分开 |
| 上传 | `/upload`、`/files/{key}` | 类型/大小前置校验，上传队列，失败保留正文 |
| 通知 | `/me/notifications` | 未读数、标记已读、深链到具体资源 |
| 站点信息 | `/site/settings` | 只读配置短缓存；缺字段使用明确默认显示 |

## 3. 认证细节

契约已经确认移动端 refresh token 载体：网站通过 HttpOnly Cookie，Flutter 原生请求将 refreshToken 放在 `/auth/refresh` 请求体，access token 通过 Bearer header 发送。原生直连 API 不受浏览器 CORS 限制。Phase 0 仍需验证部署实例没有与冻结契约漂移：

1. 移动端登录返回的 refresh token 是否能安全存储并提交刷新接口。
2. refresh 成功后是否返回新的 refreshToken，并按强制旋转作废旧值。
3. 1003/1004/1005 的返回和 token family 失效行为。
4. 移动端 API origin、HTTPS、证书和生产限流配置。

如果部署行为与契约不一致，先登记后端兼容方案；不能把 refreshToken 写入普通偏好存储，也不能把网站 BFF 当成原生客户端的长期认证方案。

对 OpenAPI 中 `security: [{}, {bearerAuth: []}]` 的可选鉴权端点，API client 必须在内存中有 access token 时自动附加 `Authorization: Bearer <token>`，匿名时仍允许请求。尤其 `/articles/{id}/view` 按 bearer user_id 或匿名 ip+ua 哈希去重；缺少 Bearer 会让登录用户被错误地按匿名口径去重。

## 4. ownerOverride 与客户端控件

OpenAPI 的 `x-authz` 不会随模型生成器变成 Flutter 权限代码。客户端根据资源归属字段计算 `isMine`，决定编辑、删除、送审、取消收藏等控件是否显示；会员端不显示“撤回为草稿”，因为契约没有对应的 member 端点。后端仍是最终裁决，客户端隐藏控件不能替代服务端授权。

错误码建立集中映射：1001 凭据错误；1002 token 无效/过期；1003 refresh 重放并清理令牌；1004 缺少令牌并跳登录；1005 账号禁用并退出；2001 权限不足；3001 资源不存在并进入 404/空资源页；3002 唯一性或引用冲突，根据具体字段提示更换用户名/邮箱等取值或说明引用冲突，不自动刷新重试；3003 状态转移非法并提示状态已变化后刷新；4001 字段校验（读取 `data.errors`）；5000 服务异常并提供有限重试；5001 限流（读取 `Retry-After`，按有界退避后提示或恢复）。

限流判断逐 operation 读取 OpenAPI 的 429 response，不依据“鉴权端点”一词推断。当前明确声明 429/5001 的包括 `/auth/login`、`/auth/register`、`/auth/refresh`、公开读取、可选鉴权的 view 等多个操作；本阶段会调用的这些请求都必须处理限流。需要 Bearer 的 `/me/*`、`/admin/*` 操作不因此自动视为受公开限流策略保护。判定规则适用于全部 operation；例如 `/auth/{provider}/callback` 同样声明了 429，但 APP 第一阶段不实现第三方登录（见 `README`、`01 §7`），因此不列入本阶段处理清单，验收矩阵也不设落点；后续若启用第三方登录，须把该端点纳入处理清单。

## 5. 内容约束

- 公开文章列表和匿名文章详情只返回 published；带 Bearer 的详情端点可按契约允许作者本人预览 draft/pending。投稿预览使用 `GET /articles/{idOrSlug}`，不存在 `GET /me/articles/{id}`。
- 会员投稿不能由客户端直接伪造 published；会员保存已发布文章后会进入 pending。
- 投稿正文上限 65,535 字符，标题 200，摘要 500；客户端提前校验，服务端仍是最终裁决。
- 评论 parentId 必须属于同一文章；隐藏父评论时不泄露其内容。
- 图片类型和 10MB 限制与后端保持一致；SVG 处理遵循后端下载安全策略。
- slug、作者、发布时间、审核原因等字段不能由客户端自行补造。
- 更新文章使用 `PUT /articles/{id}` 时，客户端不得下发 `status` 字段；编辑器按钮按当前稿件状态区分，避免把待审核稿件伪装成“保存草稿”。在契约澄清完成前，只发送可编辑字段，服务端状态副作用以契约为准。
- 创建文章使用 `POST /articles` 时，客户端显式下发其目标 `status`：保存草稿发送 `draft`，提交审核发送 `pending`；任何创建请求不得省略 `status`（契约对 member 省略状态只写“默认 draft/pending”，无单一默认值）。注意：契约对 `ArticleCreate.status` 仅声明了 `published` 的权限降级规则（member 传入 `published` 被忽略并降级为 pending），未声明 member 显式传 `draft`/`pending` 的接受性。对照同 schema 的 `slug` 字段（自陈“与 status 同规格显式化”却写全创建/更新及角色规则），这是契约描述缺口，不是已验证行为。因此“发 `draft` 落库为草稿”是客户端诉求，须经本节差异表登记并在 Phase 4 前置检查中实测确认后，才能视为已验证行为。更新与创建的 status 规则不同，不能互相泛化。

## 6. 需要在编码前确认的差异表

| 项目 | 当前已知 | 开工前动作 |
|---|---|---|
| Refresh 认证载体 | 网站使用 Cookie + 内存 access | 用 Flutter 原生请求做登录/刷新/退出最小联调 |
| 文件下载 | 网站有同源 `/files/{key}` | 确认移动端 API origin 和图片 URL 拼接规则 |
| 推送通知 | 当前只有站内通知接口 | 第一版只做站内通知；推送另立需求 |
| 草稿本机恢复 | 网站已有策略 | Flutter 使用账号+稿件 ID 的本地草稿键 |
| Markdown 目录 | 契约提供 `GET /articles/{id}/toc`，服务端由 Markdown 标题生成；响应含 `level/text/anchor`。Flutter 用服务端目录数据作为唯一事实源，不自行解析正文生成目录数据；正文渲染器为标题建立可寻址 key，key 值采用服务端 `anchor`，客户端不自行 slug 化 | 先由详情取得 `Article.id` 再请求。Flutter 本地解析仅用于离线等明确新增需求，并接受与网站目录可能不同 |
| 目录锚点配对规则 | 契约 `TocItem` 只有 `level/text/anchor` 三字段；`anchor` 仅描述为“锚点 id（slug 化标题）”，未公开 slug 化算法，也未声明数组顺序与正文标题顺序一致；`data` 为裸数组，无 index/offset 字段 | Flutter 文章详情开发者在 Phase 2 开工前，以含重复标题、代码块内 `#` 行及 Setext 标题的代表性文章，对照 `/toc` 响应逐项验证标题与 `anchor` 的配对。仅在实测通过后，才把“正文第 i 个标题对应 `TocItem[i]`”记录为实现约定；失败时由 API/后端负责人先澄清契约并更新本表，未通过前不开放目录跳转。锚点值采用服务端返回值，不自行 slug 化 |
| API 分页 | 主要是 page/pageSize | 不把 APP 滚动状态误当成后端游标；按接口返回分页字段实现 |
| 更新时的状态副作用 | 契约明确 published 由 member 编辑后进入 pending，draft/pending 的 member 更新结果仍需澄清 | 登记描述澄清：member 更新 draft/pending 保持原值，更新 published 转 pending；在澄清前客户端不下发 `status` |
| 公开站点配置 | 首页和页脚依赖 `GET /site/settings`，旧后端可能整体返回 5000 | 开工前确认线上接口；异常时使用明确默认站点名、版权和主题配置降级显示 |
| 评论路径参数 | 评论端点支持文章 `idOrSlug` | 客户端路由和 API client 使用 `{idOrSlug}`，不要把评论接口参数硬编码成 `id` |
| 创建时的状态接受性 | `ArticleCreate.status` 非必填；契约写“member 创建默认 draft/pending”但未明确单一默认值；权限约束只声明 `published` 会被忽略并降级。member 省略 `status`、显式传 `draft`、显式传 `pending` 三种情形的落库结果均未声明 | Flutter 投稿开发者在 Phase 4 前，用独立测试数据分别验证显式传 `draft` 后落库仍为 draft、显式传 `pending` 后落库仍为 pending；API/后端负责人澄清省略与显式传 `draft` 的契约结果并更新本表。验证通过前不把“保存草稿已生效”视为契约行为，也不通过投稿验收 |
| 未发布文章的目录/上下篇 | `/articles/{id}/toc` 的 404 只写“文章不存在”，未说明作者本人可否访问未发布文章；`/adjacent` 的 404 写“文章不存在或不可见”，且仅 published 参与；`/view` 明确 draft/pending 一律 404（含作者本人），三端点对未发布文章的口径不一致 | 本阶段采用方案 A：投稿预览页不请求 `/toc` 与 `/adjacent`，只呈现正文和 Markdown 样式。Flutter 文章详情开发者在 Phase 2 验收时确认这两个端点仅用于已发布文章详情；若后续要在投稿预览中加入目录，API/后端负责人须先澄清或实测 `/toc` 对作者 draft 的响应并更新本表 |
| 阅读量与阅读历史 | `POST /articles/{id}/view` 只递增 viewCount；`POST /me/history` 单独记录登录用户历史 | 详情加载后分别调用；先由详情取得整数 `Article.id`；可选鉴权的 view 请求在有 token 时附加 Bearer |
| 子资源文章 ID | `/toc`、`/adjacent`、`/view` 使用整数 `{id}`，详情路由接受 id 或 slug | 先调用 `GET /articles/{idOrSlug}`，再使用响应 `Article.id` 请求子资源；不得把 slug 直接传入这些路径 |
