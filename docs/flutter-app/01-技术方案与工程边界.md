# 技术方案与工程边界

## 1. 总体原则

Flutter APP 是同一内容产品的移动端客户端，不复制网站的 DOM 结构，也不把管理后台缩小到手机上。APP 只消费现有 API，业务状态和权限以 `docs/api/openapi.v1.yaml` 与后端实际行为为准。

第一版优先完成公开阅读和会员闭环，再做平台特性。所有会影响生产数据的操作都必须经过 API 鉴权和错误反馈；客户端不能因为“界面上看不到”就认为操作成功。

## 2. 建议技术栈

| 层 | 建议 | 约束 |
|---|---|---|
| UI | Flutter stable + Dart stable | 创建工程时记录精确 SDK 版本并提交锁定文件 |
| 状态 | Riverpod | 服务器状态、会话状态、临时表单状态分开；第一版锁定 Riverpod |
| 路由 | `go_router` | 深链接、登录后回跳、文章/会员/投稿地址统一管理 |
| 网络 | `dio` 或标准 `http` 封装 | 所有请求经过一层 API client，禁止页面直接发请求 |
| JSON | OpenAPI 生成模型/客户端 | 生成代码与手写适配层分离；契约变化先重新生成 |
| Markdown | Flutter Markdown 渲染组件 + 自定义代码块/表格样式 | 与网站视觉一致，限制原始 HTML；目录数据（层级与文本）以 `/articles/{id}/toc` 为唯一事实源。正文渲染器为标题建立可寻址的 Widget key，key 值采用服务端 `anchor`；客户端不自行生成目录数据，也不自行 slug 化 |
| 本地存储 | `shared_preferences` 用于偏好；`flutter_secure_storage` 用于 refresh token | 不把密码、access token 明文写入普通偏好存储 |
| 图片缓存 | Flutter 图片缓存 + 有上限的磁盘策略 | 不缓存私有接口响应；附件 URL 遵循后端安全响应头 |
| 测试 | `flutter_test`、mock HTTP、integration_test | 业务纯函数、请求层、关键用户路径分层验证 |

这里不在准备文档中锁死第三方包的最新版本。真正创建工程时，应在可联网环境执行依赖解析、核对 Flutter/Dart 兼容矩阵，并将精确版本写入 `pubspec.lock`。

## 3. 分层结构

```text
lib/
  app/                 MaterialApp、主题、路由、全局 Provider
  core/
    config/             环境地址、超时、功能开关
    network/            API client、信封解析、刷新与重试
    storage/            安全存储、偏好、本地草稿
    errors/             错误码到用户可读消息
    markdown/           Markdown、目录、代码块、链接策略
  features/
    home/               首页焦点、最新、热门
    discovery/          分类、标签、搜索
    article/            文章详情、目录、互动、评论楼
    auth/               登录、注册、会话恢复
    member/             收藏、历史、点赞、通知、资料
    contribution/       草稿、编辑器、预览、上传、投稿
  shared/               图片、空态、错误态、加载态、主题组件
```

Feature 内部建议采用 `presentation / application / data / domain` 四层，但不为了层数机械拆文件。请求模型不能直接作为 UI 模型到处传递，文章、评论、投稿草稿应有明确的显示模型和转换边界。

## 4. 会话与安全

- 登录返回 access token 与用户；refresh token 使用 `flutter_secure_storage` 保存。
- 契约已确认支持原生客户端：Flutter 直接连接 API origin，使用 `Authorization: Bearer <accessToken>`；刷新时将 refreshToken 放入请求体，不依赖浏览器 Cookie 或 CORS 代理。
- 启动时只做一次会话恢复；并发 401 只允许一次刷新，其余请求等待同一个结果。这是 P0 正确性要求，不是性能优化：后端强制旋转 refreshToken，并发刷新会用旧 token 命中 1003，导致整个 token family 被作废。
- 每次刷新成功必须把新的 refreshToken 原子写入安全存储。1003/1004/1005 刷新失败时清空 access、refresh 和私有缓存，跳转登录；在途旧请求的迟到响应必须丢弃。
- 退出登录、账号切换和密码修改后，旧请求的迟到响应不能恢复旧账号。
- 公开 GET 可以匿名；收藏、点赞、评论、投稿和会员数据必须带会话。
- 未登录访问投稿编辑页时保存 redirect，登录成功后回到原路径。
- 服务器错误、网络离线、超时、401、403、404、业务校验失败必须分别呈现；不能统一显示“加载失败”。
- OpenAPI operation 明确声明的 429 / code 5001 均按限流处理：读取 `Retry-After`，采用有界退避并提示“请求较多，请稍后重试”。范围包括公开读取，以及明确声明限流的登录、注册、刷新等免鉴权操作；不得无限立即重试。
- 日志不得输出 access token、refresh token、密码、邮箱验证码或投稿正文。

## 5. 渲染与缓存

APP 不使用网站的 ISR/RSC 概念。公开列表和文章详情可以使用内存/磁盘短缓存，但必须有明确失效策略；会员和写操作默认实时请求。文章详情缓存不能覆盖草稿、待审核或用户私有数据。

推荐策略：文章列表短缓存并支持下拉刷新；文章详情允许短时间复用并在用户主动刷新时重新获取；点赞/收藏状态以当前账号为 key；投稿草稿以账号和文章 ID 隔离。

## 6. 主题与暗色模式

主题有三种用户选择：跟随系统、浅色、深色。默认跟随系统，用户选择持久化到本地。

浅色使用白色内容面、浅蓝背景、深蓝灰文字、晴蓝强调；深色使用深蓝灰背景和内容面、浅灰蓝文字、低亮度蓝色强调。暗色必须同时覆盖：导航栏、底部 Tab、文章正文、代码块、表格、评论回复背景、表单输入、错误/空态、图片占位和投稿编辑器。

不要用颜色反转生成暗色主题。正文、链接、引用、代码高亮和错误文字要分别检查对比度；图片本身不强制加滤镜。主题切换只改变显示，不清空页面数据和正在编辑的内容。

## 7. 不在本阶段做的事情

不新增后端字段、不修改旧网站、不做后台管理移动端、不做第三方登录、不做离线完整阅读、不做推送服务、不做支付、不做多账号同时登录。推送和离线能力可以保留扩展点，但没有服务端和产品确认前不进入任务清单。

OpenAPI 的 `x-authz` 是自定义扩展，模型生成器不会自动生成客户端权限行为。ownerOverride、角色阶梯和资源归属判断必须由 APP 手写权限适配层处理，后端仍是最终裁决。
