# 工程决策与取舍

## 保留技术组合，选择性复用

本次保留 Next.js、React、TypeScript、Tailwind、TanStack Query、Zustand、Biome 和 OpenNext 的既有组合，并沿用锁定依赖。页面与布局重新实现；类型、端点封装和请求层基础经过检查后复用。

这样可以把精力用于用户真正要求的前台体验，又能保留与现有契约协作的基础。但是复用带来了明确风险：旧代码可以编译，并不代表它与当前后端行为一致。退出登录漏带访问令牌，就是后续浏览器检查才发现的例子。

因此，“保持技术方案不变”和“照搬旧实现”需要分开理解。前者是约束，后者仍需要逐项验证。

## API 契约、后端实现和前端使用方式需要一起核对

生成类型能检查结构，检查不到每一个 URL 是否正确，也不能证明组件调用时携带了正确的认证状态。

本次修正过树形分类端点、点赞状态路径、搜索参数及代理查询串。分类还涉及 id 与 slug 的映射：数据关联使用 id，页面路径使用 slug，展示使用名称，不能混成一种标识。

验证应同时回答三个问题：契约怎么写，后端实际返回什么，页面最后发出了什么请求。三者缺一，就容易出现“接口测过，但页面仍不可用”。

## 公共内容与私有交互采用不同的数据路径

公开页面通过服务端请求获得正文、列表、分类和站点设置，提供首屏内容和 SEO。会员及互动请求走浏览器同源代理，使用内存中的 access token。

这让公共内容可以缓存，用户数据保持独立。代价是同一业务对象可能同时有服务端初始内容和客户端实时状态。例如文章初始统计与点赞按钮状态并非永远同一刷新时刻；互动状态需要以真实互动端点为准。

会员页面的客户端守卫用于交互体验，真正的权限边界仍然是后端鉴权。不能因为页面重定向到了登录，就认为接口已经安全；也不能把私有数据塞进公开预渲染结果来避免客户端加载。

## 登录的难点在并发和生命周期

access token 放内存，refresh token 放 HttpOnly Cookie。刷新页面后先恢复会话，失败时进入游客状态。

旋转刷新令牌不允许多个失效请求各自独立刷新，否则第一个请求换走令牌，后面几个可能用旧令牌失败。实现中让并发请求共用一个刷新 Promise，再重放原请求。

仅做 Promise 去重还不够。用户可能在刷新未完成时退出，或者在旧资料请求未返回时切换账号。因此加入会话代次检查：旧生命周期中的请求不能恢复已经结束的会话，也不能把旧账号资料提交给新账号界面。

这几条规则分别有测试，避免以后“简化请求层”时只保留看起来最常见的成功路径。

入口位置：`lib/request/core.ts`、`store/auth.ts`、`components/auth/Providers.tsx`，均位于新项目内。

## 新目录、新端口并不自动隔离 Cookie

浏览器 Cookie 不按端口隔离。在同一主机运行新旧前端，如果使用同名 Cookie，仍可能互相影响。

本次浏览器使用 `codex_refresh`，代理向后端转为它原来识别的 `refreshToken`，响应再改回新名称。这把隔离放在新前端边界内，避免修改后端。代理只转发新应用的刷新 Cookie，并去除登录、注册、刷新响应 JSON 中的刷新令牌。

生产的 Secure 属性保留；只有字面上的本机回环主机放宽 Secure，便于本地 HTTP 测试。SameSite 使用同源场景下的 Lax，并检查跨站写入来源。

这些是本次部署模型下的处理，不能直接套用到跨站 SSO、多个新站实例或不同 Cookie 域策略中。增加这些需求时要重新设计。

## 缓存是一项可观察行为

公开数据统一采用 60 秒重新验证，搜索实时获取，私有响应 no-store。选择 60 秒是实施默认值，不是业务已经承诺的发布时效 SLA。

Cloudflare 的构建成功不代表缓存行为正确。检查适配器的默认实现后，为 Worker 配置了独立 R2 增量缓存和直接重新验证队列。只运行本地模拟，没有创建远程桶。

实际通过临时修改独立测试库的站点描述，确认两个运行环境在过期后能取得更新，再恢复原值。这个验证比只检查配置里写了 `revalidate` 更有意义。

首次过期请求允许先返回旧结果，再进行后台更新。未来如果要求“管理员发布后立即全站可见”，需要明确的失效机制，不能只把轮询时间缩短当作等价方案。

## 目录和正文必须共享解析结果

单独用正则扫描 Markdown 标题，再让 Markdown 渲染器生成另一套锚点，容易在中文、重复标题、行内链接或代码中失配。

本次目录与正文来自同一棵 Markdown 解析树，在同一处为标题分配 id，重复标题追加后缀。浏览器实际验证了重复中文标题的第二个锚点。

原始 HTML 不执行；结构化数据单独做安全转义。代码复制真实调用剪贴板，并处理失败。正文的“能显示”之外，还需要考虑长代码、表格、图片和定位操作。

## 核心失败必须与空内容区分

文章列表失败时返回空数组，会让读者误以为站点没有文章；详情的任意错误都跳 404，会把服务故障误报为内容下架。

因此，核心内容失败进入错误边界，只有真实不存在才显示 404。热门、相关内容等辅助模块可以独立降级，以免次要接口拖垮主阅读任务。

降级不是删除故障证据。后续仍应通过服务端日志或监控发现这些问题。本次没有建设新的线上监控系统。

## 工具兼容问题尽量隔离解决

API 类型生成器使用 TypeScript 5 的内部能力，而应用使用 TypeScript 7。没有为了生成工具改动整个应用的版本，而是在 `.local/typegen/` 放置固定版本工具环境。

过程里网络安装等待过久，最终复用了本机已有依赖建立独立环境并完成生成。这说明本次生成命令运行成功，不等于已经在全新机器上完成了无缓存安装验证。接手者在新的环境中仍应按 README 验证依赖安装与类型生成。

## 写入测试必须有明确落点

测试使用原后端代码，但 `DB_FILE` 指向新项目内的独立数据库。测试会员、草稿、评论和密码修改都落在这份数据库里。

仅仅把前端端口换掉并不能保证写入安全，还必须知道代理最终连接哪个后端、那个后端连接哪个数据库。项目内的测试脚本只限制本地预览端口，不能替代对后端配置的确认。

最后以文件指纹核对旧前台、后端、后台和共享文档的 605 个原有文件，而不是仅凭“记得没有编辑过”来判断隔离成立。
