# 问题复盘与验证证据

这部分保留实际走过的弯路。它们不是待办清单，下面列出的应用问题已经在本次开发中修复。维护建议另外写在下一篇。

## 一、接口很快，文章流却一直显示“正在加载”

**实际现象**：登录用户刷新首页后，继续加载停住。直接请求分页 API 返回 200，响应很快；浏览器也没有明显脚本错误。

**问题所在**：会话恢复使用户身份从空变成当前会员，公共 Providers 在身份变化时清空了整个 QueryClient。首页文章流已经挂载，它的查询也被一起移除，后续观察和更新出现异常。

**修正**：身份变化时保留 `public-feed`，清理其他查询；会话与私有数据隔离逻辑继续保留。

**验证**：真实浏览器重新加载登录后的首页，追加后得到 24 个条目、24 个唯一链接，并显示全部加载完成。

**复盘价值**：缓存清理本身也会改变正在使用它的组件行为。“全部清空更安全”没有覆盖到公开数据与私有数据共存的情形。类型检查、API 测试和静态截图都无法单独证明这个流程正确。

**当前代价**：保留公开查询依赖一个特定 key。未来公开客户端查询更多时，建议明确查询的公开/私有属性，而不是不断增加字符串特例。这个建议尚未实施。

## 二、错误页面有重试按钮，但没有真正重新取数据

**实际现象**：停止独立测试后端后，搜索页显示预期错误。恢复后端，再点击“重新加载”，仍然停留在错误页面。

**问题所在**：最初只调用错误边界的 `reset`。当前框架文档明确区分了重置错误边界与重新获取内容，前者不能保证失败的服务端请求重新执行。

**修正**：按钮执行完整页面重新加载，使服务端内容和启动会话恢复重新走一遍。

**验证**：再次停止后端、进入错误页、恢复后端、点击按钮，真实搜索结果恢复，页面重新显示登录状态。

**取舍**：完整重新加载会丢失该页局部客户端状态，但当前错误页没有需要保留的编辑草稿，且这个动作名就是“重新加载”。如果未来页面承载长表单，应重新评估更细粒度的恢复方式。已安装版本文档也提供专门的 retry 语义，可以在明确测试后再采用。

**复盘价值**：错误界面出现只证明失败能被展示；恢复成功需要第二次操作的证据。不能把“有按钮”当作“恢复链路已完成”。

## 三、直接接口测试能退出，页面却退出失败

**实际现象**：最后检查会员菜单时，退出没有返回游客首页。进一步读取页面结构，才看到菜单里的“退出失败，请重试”。

**问题所在**：复用的 `logout` 客户端封装设置了 `skipAuth: true`，而实际后端 `/auth/logout` 需要访问令牌鉴权。直接接口测试工具一直携带 token，因此测试覆盖了后端端点，却没有覆盖这个客户端封装错误。

**修正**：退出请求携带 access token，继续保留失败反馈；增加针对真实 logout 封装的请求头测试。

**验证**：浏览器点击退出后回到游客首页；再次访问收藏页，跳转登录并保留原返回路径。新增测试确认 logout 封装携带后端所需的 Authorization。

**复盘价值**：测试越靠近真实调用路径，越能减少这种盲区。接口联调、组件使用和用户操作之间不是自动等价关系。今后复用认证代码，至少应逐个核对登录、刷新、退出、修改密码的权限与失效语义。

## 四、开发期生成类型损坏，不能立即归因于业务代码

开发中出现过 `.next/dev/types/validator.ts` 的语法错误，文件中有不完整的生成片段。问题发生在开发服务运行、路由修改和检查交错期间。

处理时先停止开发服务，清理该项目内的开发路由类型生成目录，再用 Next 的类型生成命令重新生成，随后类型检查通过。没有去修改生成文件中的某一行来掩盖问题。

这里能确认的是：重新生成后恢复正常。不能据此断言已经证明某个框架内部并发缺陷。生成物错误与业务源码错误要分开定位，根因不充分时不应把推测写成结论。

同一 `.next` 目录上的开发与生产构建也尽量串行，避免检查结果受到产物交替写入影响。

## 五、代理初版的来源比较误伤本地写请求

本地验证中曾出现真实页面写请求返回 403。最初比较来源与框架内部请求 URL 的 origin，在本地服务的地址规范化下出现不一致。

修正后依据请求 Host 校验 Origin 的主机部分，并拒绝明确的跨站请求；非法 Origin 也有处理。后续点赞、收藏、注册及跨站写入拒绝测试通过。

这里的经验是：对安全边界的调整需要同时验证“允许的请求确实成功”和“不允许的请求仍被拒绝”。只看到 403 就完全删除检查，或者只看到恶意请求被挡就认为实现正确，都不完整。

如果未来加入可信反向代理、多个域名或外部登录流程，这个比较规则需要结合真实部署重新复核。

## 六、图片与布局也需要实际查看

首页焦点封面早期裁切不理想，实际截图暴露了问题，随后调整展示方式，避免样例封面的重要内容被切掉。手机布局使用真实浏览器视口检查，而不是只把设计稿容器变窄。

反过来，样例封面的正常显示也不能证明任意运营图片都适合。以后更换真实图片，要查看裁切、长宽比和移动端文字大小，不能只检查 URL 能否打开。

## 本次没有验证到的东西

真实手机硬件、完整跨浏览器矩阵、生产规模数据、真实并发流量、线上性能指标、新机器从零安装，以及远程 Cloudflare 资源与域名配置，都没有在这次工作中完成验证。

Worker 的本地后台重新验证曾记录一次连接中断，后续请求正常拿到更新。本次有更新成功的证据，但没有据此消除所有生产缓存风险。这个记录保留在验收报告中。

## 关于“完成”的更准确表述

本次完成的是确认范围内的前台实现和本地验证。预览内容来自独立测试库，正式使用时仍要接入目标内容服务和运营素材；线上发布是另一个有环境前提的工作。

最有价值的交付不只是“通过”两个字，而是清楚记录通过了什么、在哪里通过、失败过什么，以及哪些结论仍然不能从现有证据中推出。
