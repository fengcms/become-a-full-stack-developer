# 后续协作与维护备忘

下面区分当前事实和后续建议。建议不代表已经排期，也不代表本次范围尚未完成。

## 接手时先建立这几项共识

- 用户确认的是传统门户和 A 配色，不要在修一个局部问题时顺手换成另一种视觉体系。
- 原前台保留，新前台独立；本次新增共享文档是用户另行指定的，不是扩大业务代码权限。
- 当前运行说明在新项目 README，配置入口在 `config/home.ts`，真实接口契约在共享 OpenAPI。
- 测试账号、数据库和环境文件在忽略目录，不要把它们当生产配置发布，也不要把里面的密码写进公共文档。
- 旧验收报告描述的是当时的版本和环境。改动后应验证受影响部分，不应把旧报告直接当作新版本证明。

## 几个看起来可以简化、实际上有原因的地方

### 刷新 Promise 和会话代次

前者防止旋转令牌被并发刷新打穿；后者防止迟到请求跨越退出或账号切换。删除它们前，需要相应的替代机制及并发测试，不能只验证单次登录成功。

### 公开文章流在身份变化时保留

这是浏览器发现实际问题后的修正。用户身份变化不应该把正在使用的公开文章流一起拆掉。扩展查询种类时，要重新检查清理范围。

### 独立 Cookie 名称

不同端口共享主机 Cookie。合并回旧名称之前，需要明确新旧前台是否仍并存，以及登录状态是否真的应该共享。

### 草稿不链接公开详情

会员能看到文章状态，不代表游客详情端点允许读取草稿。不要为了让每个标题都可点击，就把未发布文章引向公开 404；也不要因此绕过后端权限。

### 只有真实 404 才进入不存在页面

网络异常、接口 500 与内容不存在是不同事实。吞掉异常能让页面“看起来没报错”，也会让用户和维护者失去判断依据。

### 正文和目录共用解析树

修改 Markdown 插件顺序、标题渲染或锚点规则时，需要一起检查目录。至少保留中文重复标题及行内格式标题的用例。

## 当前方案的规模边界

### 收藏状态查询

后端没有单篇收藏状态端点，所以当前遍历收藏分页确认文章是否已收藏。这保证不会因文章落在第二页而判断错误，但收藏量很大时请求成本会增加。

**后续建议**：如果实际使用暴露成本，优先讨论轻量状态端点或明确的批量状态契约，再调整前端。不要简单改回“只取前 100 条”。

### 点赞列表

后端返回完整数组，前端按每页 10 条显示。界面分页不等于网络和内存使用已经分页。

**后续建议**：在用户数据规模增长时，再推动后端分页；届时一起调整总数、删除末页和查询 key。

### sitemap

当前枚举全部文章分页并加入公开分类、标签和作者，解决漏掉第一页以外内容的问题。

**后续建议**：内容量明显增长时检查生成时长、缓存、重复 URL 以及分片 sitemap。当前小规模本地验证不证明它适用于无限增长的数据量。

### 导航与长内容

四级栏目和现有测试样例通过，不表示所有长栏目名、多量一级栏目或异常内容组合都被覆盖。

**后续建议**：正式接入内容后，抽取最长标题、最深分类、最宽表格和最高比例封面重新检查。运营素材变化也可能产生布局回归。

## 当前维护上的折中

样式集中在全局 CSS，部分规则由已确认设计落地后逐步细化；少数请求和会员控制器保持高内聚，超过一般文件行数建议。这提高了本次交付时的一致性，但长期维护时需要留意覆盖顺序和模块职责。

**后续建议**：当同一块样式频繁变化，或多人修改容易冲突时，再按布局、阅读、认证、会员区域拆分。拆分本身不应改变视觉结果，也不必为了文件长度机械拆碎。

公共查询的身份变化保留规则目前显式识别 `public-feed`。后续增加更多公开查询时，可以用查询命名空间或元信息表达其性质，减少遗漏。这个调整应带上“登录恢复后继续加载”的浏览器回归。

错误页目前完整重新加载。这是已经验证有效的恢复方案；未来承载未保存输入的页面，应重新设计恢复时保留什么、重新获取什么。

## 常见改动对应的最小验证范围

| 要改的地方 | 至少检查 |
|---|---|
| 颜色、字体、间距 | 桌面及窄屏截图、正文可读性、焦点可见性 |
| Header 或会员菜单 | 多级展开、点击外部、Escape、站内跳转、登录前后、手机 |
| 文章流 | 首屏、追加、去重、筛选切换、失败重试、登录恢复、Footer 可达 |
| 请求内核/认证 | 并发过期、刷新失败、退出、账号切换、密码变化、浏览器真实按钮 |
| 同源代理 | 查询串、Cookie 隔离、认证头、跨站拒绝、后端不可达、两种运行环境 |
| Markdown/目录 | 中文、重复标题、行内链接、代码围栏、表格及实际锚点跳转 |
| 会员列表 | 空列表、分页、末页删除、账号切换、错误反馈 |
| 缓存或 Worker 配置 | 构建、启动、API 代理、内容过期更新、私有 no-store |
| 契约/生成类型 | 重新生成、类型检查、实际响应、消费者行为；不要只看生成文件能编译 |

这不是要求每次改一行文案都重跑全套。根据改动风险选检查；一旦涉及认证、缓存或运行平台，就不能只用截图或类型检查替代行为验证。

## 如何提出下一项协作任务

一个有效的任务可以说明：

- 哪个具体页面、用户状态和操作触发了问题。
- 预期行为与当前行为分别是什么。
- 当前连接的是独立测试库、开发库还是正式环境。
- 哪些边界保持不变，哪些地方允许调整。
- 希望通过什么可观察结果确认完成。

例如，“登录后刷新首页，再加载更多会停住，接口能正常返回；请保留现有布局和后端，只修复文章流并验证退出后也可继续浏览”，比“帮我优化一下状态管理”更容易形成可验证的交付。

## 正式上线前的环境工作

这些属于下一次部署任务，不是本次已经执行的操作：

1. 明确正式 API 地址、站点域名、内容与运营图片来源。
2. 使用正式 `NEXT_PUBLIC_SITE_URL` 重新构建，避免 canonical 和 sitemap 指向本机。
3. 准备独立 Worker、R2 资源与环境变量，不覆盖旧站资源。
4. 在目标环境检查 Cookie、安全来源判断、内容更新与实际账号操作。
5. 明确发布、切换和回退方式，再执行对线上有影响的动作。

不要直接发布本次预览构建来代替生产准备，其中包含构建时读取到的本地内容和站点地址。
