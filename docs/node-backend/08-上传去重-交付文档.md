## 二、核心改动（代码摘要）

### P1 · 存储层内容寻址（`src/shared/storage.ts`）

```ts
import { createHash } from 'node:crypto';            // 顶替 randomUUID（已移除，无残留）
// ...
async put(buffer: Buffer, ext: string): Promise<{ key: string; url: string }> {
  const key = `${createHash('sha256').update(buffer).digest('hex')}${ext}`; // 内容寻址：同字节 → 同 key
  const existing = await this.get(key);              // 命中则复用，跳过写盘（省 I/O，R2 省 PUT）
  if (existing) return { key, url: `${this.baseUrl}/${key}` };
  await mkdir(this.root, { recursive: true });
  await writeFile(join(this.root, key), buffer);
  return { key, url: `${this.baseUrl}/${key}` };
}
```

- key 格式 `sha256hex + 原 ext`（如 `a1b2…d4.png`），匹配 `SAFE_KEY = /^[A-Za-z0-9._-]+$/`，`files.ts` 反解 ext 零改动（§3.4）。
- 接口返回仍为 `{ key, url }`，**未新增 `hash` 字段**（决策 #2，sha256 仅内存派生 key，不出接口、不落库）。
- `randomUUID` 已从 import 移除（put 内不再使用）。

### P3 · 删除引用计数护栏（`src/services/attachment.ts`）

> ⚠️ **与原方案代码的一处必要偏差（已实现意图，非偷工）**：Drizzle better-sqlite3 的 `transaction` 回调**必须是同步函数**（异步回调会抛 "Transaction function cannot return a promise"）。因此把「DB 原子性动作」与「异步文件删除」分层：
> - **同步事务内**：读行 → 删行 → 数同 `storageKey` 兄弟行（`remaining`）。这一步与并发上传插入**由 SQLite 单写者串行化保证不交错**，这是消除 §7 并发删除窗口的关键原子性。行缺失（id 不存在）在事务内直接抛 `NOT_FOUND(404)`（**P2 修正**：原实现静默 resolve 致 editor 路径返回 200，违反冻结契约）。
> - **事务外**：`if (remaining === 0)` 才调用 `createStorage(...).delete(key)`，失败最佳努力吞掉（双存储边界，不阻塞行删除）。
>
> 文件删除本就是 best-effort（原方案也 catch 吞错）。**孤儿竞态窗口（P3-1，owner 接受）**：文件删除置于事务外（better-sqlite3 事务回调须同步，异步删文件会抛 "Transaction function cannot return a promise"），故存在极窄孤儿竞态窗口——并发上传相同字节恰逢删除间隙 → 新行孤儿（后果轻微，重传即恢复）。缓解方向：未来若引入 `ref_count` 列（需迁移，owner 当前否决）可在事务内计数并裁决删除。代码内已补注释使偏差透明。

```ts
export const deleteAttachment = async (id: number): Promise<void> => {
  const result = getDb().transaction(
    (tx): { storageKey: string; remaining: number } => {
      const row = (tx.select({ storageKey: attachments.storageKey })
        .from(attachments).where(eq(attachments.id, id)).limit(1)
        .all() as { storageKey: string }[])[0];
      if (!row) throw new AppError(ErrCode.NOT_FOUND, 404); // 缺失 → 404（守冻结契约，不静默 resolve）
      const res = tx.delete(attachments).where(eq(attachments.id, id)).run();
      if (res.changes === 0) throw new AppError(ErrCode.NOT_FOUND, 404);
      const remaining = (tx.select({ c: sql<number>`count(*)` })
        .from(attachments).where(eq(attachments.storageKey, row.storageKey))
        .all() as { c: number }[])[0]?.c ?? 0;
      return { storageKey: row.storageKey, remaining };
    },
  );
  if (result.remaining !== 0) return; // 仍有引用 → 不删物理文件
  try { await createStorage(getActiveEnv()).delete(result.storageKey); }
  catch { /* 底层删除失败不阻塞行删除（双存储适配层真实边界） */ }
};
```

## 六、回滚与风险

| 项 | 处置 |
|---|---|
| 回滚 | `put` 回退 `randomUUID()` 即还原「每传必新」（物理去重消失）；`deleteAttachment` 回退为直接删文件亦可；无 DB 列 / 迁移耦合，drop 风险为零 |
| 并发删除 | 同步事务内「删行 + 计数」已消除 DB 层交错窗口 |
| sha256 碰撞 | 2^256 实际不可行，忽略 |
| 同字节异 ext | 决策 #4 接受（轻微残留重复），不升级纯 hash |
| R2 未实测 | 沿用 B10 裁决（无凭证不实测）；local 落地同构，R2 接线时按 `head(key)` 复用补 |
