## 2. P1 — 存储层内容寻址（必做）

**目标文件**：`src/shared/storage.ts`（仅 `LocalStorage.put`，当前 `:42-47`）

**改动前（现状）**：
```ts
async put(buffer: Buffer, ext: string): Promise<{ key: string; url: string }> {
  const key = `${randomUUID()}${ext}`;
  await mkdir(this.root, { recursive: true });
  await writeFile(join(this.root, key), buffer);
  return { key, url: `${this.baseUrl}/${key}` };
}
```

**改动后（目标）**：
```ts
import { createHash, randomUUID } from 'node:crypto';   // randomUUID 保留（仅兜底/其它用途），sha256 新增

async put(buffer: Buffer, ext: string): Promise<{ key: string; url: string }> {
  const key = `${createHash('sha256').update(buffer).digest('hex')}${ext}`; // 内容寻址：同字节 → 同 key
  const existing = await this.get(key);                  // 命中则复用，跳过写盘（省 I/O，R2 省 PUT）
  if (existing) return { key, url: `${this.baseUrl}/${key}` };
  await mkdir(this.root, { recursive: true });
  await writeFile(join(this.root, key), buffer);
  return { key, url: `${this.baseUrl}/${key}` };
}
```

**行为规格**：
1. key 由 `sha256(buffer)` 十六进制 + 原始 `ext` 拼接；相同字节永远落到同一 key → 同一物理文件（覆盖写亦幂等，绝不会产生多份）。
2. 写入前 `this.get(key)` 命中（返回非 null）即复用，不再写盘。
3. **接口契约不变**：返回仍 `{ key, url }`，无 `hash` 字段（决策 #2，不落库）。
4. `ext` 为空串时 key = 纯 hex（仍匹配 `SAFE_KEY = /^[A-Za-z0-9._-]+$/`，`files.ts` 反解 ext 返回 `''` → MIME `octet-stream`，可接受）。

**接受准则（开发 AI 自验 + 我复验）**：
- `grep -n "randomUUID()" src/shared/storage.ts` 在 `put` 内**不再出现**（仅在 import 或兜底处保留）；
- 同 buffer 调 `put` 两次 → 返回**相同 key**；第二次不触发 `writeFile`（可用 spy 断言或比对盘上文件 mtime / 数量）。

> R2 分支当前为 deferred（`createStorage` 在 `r2` 时直接 throw，无凭证不实测，沿用 B10 裁决）。本期只在 `LocalStorage` 落地；R2 接线时按同构逻辑补 `head(key)` 复用即可。

## 3. P3 — 删除引用计数（必做，A+ 正确性核心）

**目标文件**：`src/services/attachment.ts`（仅 `deleteAttachment`，当前 `:118-137`）

**改动前（现状，有缺陷——多附件共享文件时会误删）**：
```ts
export const deleteAttachment = async (id: number): Promise<void> => {
  const db = getDb();
  const row = (await db.select({ storageKey: attachments.storageKey })
    .from(attachments).where(eq(attachments.id, id)).limit(1).all())[0];
  const res = await db.delete(attachments).where(eq(attachments.id, id)).run();
  if (res.changes === 0) throw new AppError(ErrCode.NOT_FOUND, 404);
  if (row) {
    try { await createStorage(getActiveEnv()).delete(row.storageKey); }
    catch { /* 底层删除失败不阻塞行删除 */ }
  }
};
```

**改动后（目标，事务内引用计数）**：
```ts
export const deleteAttachment = async (id: number): Promise<void> => {
  await getDb().transaction(async (tx) => {
    const row = (await tx
      .select({ storageKey: attachments.storageKey })
      .from(attachments).where(eq(attachments.id, id)).limit(1).all())[0];
    if (!row) return;                                   // 行已不存在，幂等返回
    const res = await tx.delete(attachments).where(eq(attachments.id, id)).run();
    if (res.changes === 0) throw new AppError(ErrCode.NOT_FOUND, 404);
    const remaining = (await tx
      .select({ c: sql<number>`count(*)` })
      .from(attachments).where(eq(attachments.storageKey, row.storageKey)).all())[0]?.c ?? 0;
    if (remaining === 0) {                              // 仅无人引用才真删物理文件
      try { await createStorage(getActiveEnv()).delete(row.storageKey); }
      catch { /* 底层删除失败不阻塞行删除（双存储真实边界） */ }
    }
  });
};
```

**行为规格**：
1. 「读行 → 删行 → 数同 `storageKey` 兄弟行 → 仅当 =0 才删物理文件」**必须在同一 DB 事务内**（消灭 §7 描述的并发交错窗口）。
2. 事务 API 形态以 Drizzle better-sqlite3 文档为准（`getDb().transaction(async (tx) => {...})`，`tx` 为事务作用域句柄，支持 `.select/.delete/.all/.run`）；若实际签名不同，按文档落地，**但四步原子性不可妥协**。
3. 物理删除失败仍 catch 吞掉（保持既有双存储边界，不阻塞行删除）。
4. `sql` 已在 `attachment.ts:6` 导入，无需新增 import。

**接受准则（开发 AI 自验 + 我复验）**：
- 同一物理文件被 2 个 attachment 行共享时，删除其中一个 → 文件**仍在盘**，另一附件 URL 仍可访问；
- 删除最后一个引用该文件的附件 → 物理文件**被删**；
- 事务内 `count` 与外部并发插入不交错（Drizzle better-sqlite3 单写者串行化保证）。
