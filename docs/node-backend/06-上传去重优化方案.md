# 06 · 上传附件去重优化方案（A+）

> 作者角色：BackendArchitect（仅设计 / 审查，不实现代码）
> 状态：已裁决（owner 2026-08-26 锁定 4 项开放问题）→ 进入实施；详见 `07-上传去重-批次任务包.md`
> 关联文档：`04-目标目录结构.md`、`B-结构调优-NOTES.md`、`docs/api/openapi.v1.yaml`（已冻结）
> 目标：消除「相同字节被存为多份物理文件」的浪费；**HTTP 契约零变更**；**删除正确性不退化**。

---

## 0. 一句话结论

采用 **方案 A（内容寻址物理去重）+ 删除引用计数护栏（事务内）**。对外接口完全不变，删除不会误伤仍在引用的附件。核心去重**不需要任何数据库 schema 变更**（仅存储层 + 服务层改动）；仅当要做存量 backfill / 未来记录级去重时，才建议追加一个 `content_hash` 可选列（内部列，不进契约响应）。

---

## 1. 问题根因（实证）

| 证据 | 位置 | 说明 |
|---|---|---|
| `const key = \`${randomUUID()}${ext}\`` | `src/shared/storage.ts:43` | 每次写入 key 与内容无关 → 同字节不同 key |
| `attachments` 表无 hash 列 | `src/db/schema.ts:232-244` | 无去重依据 |
| `storage.put(...)` + 无条件 `insert` | `src/services/attachment.ts:81, 84-97` | 每次上传必落新行 + 新文件 |

根因：**存储 key 由 `randomUUID()` 生成，与文件内容无关**。同一张图传 N 次 = N 个随机 key = N 份物理文件 + N 行记录。

---

## 2. 方案选型回顾与裁定

| 方案 | 做法 | 契约影响 | 裁定 |
|---|---|---|---|
| **A. 内容寻址物理去重** | key=`sha256(buffer)+ext`；`storage.get(key)` 命中则复用，不重复写盘 | ❌ 不动 | ✅ **采用（A+）** |
| **B. A + 记录级去重** | 加唯一 `content_hash`，命中直接返回既有行 | ❌ 不动 | ⏸ 留作未来增强（见 §4.2 / §11） |
| **C. 客户端预检** | 新增 `GET /upload/exists?hash=…` | ✅ **动契约** | ❌ 冻结下禁止 |
| D. 存储层去重 | A 的 key 改造下沉到 `storage.put` 内部 | ❌ 不动 | 即 A 的实现细节，并入 A |

## 3. 目标设计（A+ 核心）

### 3.1 存储层：内容寻址 key（必做）

`src/shared/storage.ts` 的 `LocalStorage.put` 改为：

```ts
import { createHash } from 'node:crypto';

async put(buffer: Buffer, ext: string): Promise<{ key: string; url: string; hash: string }> {
  const hash = createHash('sha256').update(buffer).digest('hex');
  const key = `${hash}${ext}`;                 // 内容寻址：同字节 → 同 key
  const existing = await this.get(key);
  if (existing) return { key, url: `${this.baseUrl}/${key}`, hash }; // 命中复用，不写盘
  await mkdir(this.root, { recursive: true });
  await writeFile(join(this.root, key), buffer);
  return { key, url: `${this.baseUrl}/${key}`, hash };
}
```

- 接口只需新增返回 `hash`（服务层落库用），调用方（`createAttachment`）无其它改动。
- R2 分支（当前 deferred，无凭证）同逻辑：`head(key)` 命中则复用，否则 `put`。

### 3.2 服务层：落库 content_hash（可选列，见 §4.2 / 决策锁定 §11）

> **决策锁定**：owner 于 2026-08-26 裁决 **不做** `content_hash` 列（开放问题 #2）。因此：
> - `StorageProvider.put` 的返回类型**维持 `{ key, url }` 不变**，不在接口上新增 `hash`；
> - `createAttachment` **不写** `content_hash`；
> - sha256 仅在 `storage.put` 内部用于派生 key，属一次性内存计算，不出接口、不落库。
>
> 本节原「落库 content_hash」步骤**本次跳过**；若未来做 scheme B / backfill，再按 §4.2 双源迁移补列。

`createAttachment` 仍**始终插入新 attachment 行**（保留「上传即落 Attachment 表」语义，响应仍是新 id），仅 `storageKey` 因内容寻址天然共享：

```ts
const { key, url } = await storage.put(input.buffer, input.ext);
// insert ... values({ ..., storageKey: key, url, ... })  // 不写 contentHash
```

### 3.3 删除护栏：事务内引用计数（必做，A+ 重点）

`deleteAttachment` 必须包裹在事务内，先删行、再数同 `storageKey` 的兄弟行、仅当为 0 才真删物理文件：

```ts
export const deleteAttachment = async (id: number): Promise<void> => {
  await getDb().transaction(async (tx) => {
    const row = (await tx
      .select({ storageKey: attachments.storageKey })
      .from(attachments).where(eq(attachments.id, id)).limit(1).all())[0];
    if (!row) return;                                  // 行已不存在
    const res = await tx.delete(attachments).where(eq(attachments.id, id)).run();
    if (res.changes === 0) throw new AppError(ErrCode.NOT_FOUND, 404);
    const remaining = (await tx
      .select({ c: sql<number>`count(*)` })
      .from(attachments).where(eq(attachments.storageKey, row.storageKey)).all())[0].c;
    if (remaining === 0) {                             // 无人引用才删物理文件
      try { await createStorage(getActiveEnv()).delete(row.storageKey); }
      catch { /* 底层删除失败不阻塞行删除（双存储真实边界） */ }
    }
  });
};
```

> 注：`db.transaction` 的准确 API 形态（better-sqlite3 驱动）由开发 AI 按 Drizzle 文档落地；本方案只规定「删行 + 计数 + 条件删文件」必须在同一事务内。

### 3.4 key 格式决策：`hash+ext` 而非「纯 hash」

- `src/routes/files.ts:41` 从 key 反解扩展名：`const ext = key.includes('.') ? \`.${key.split('.').pop()}\` : ''`。
- `files.ts:19` 的 `SAFE_KEY = /^[A-Za-z0-9._-]+$/` 对 `hash+ext`（如 `a1b2…d4.png`）合法。
- 若改用「纯 hash」（无 ext），`files.ts` 反解 ext 失败 → MIME 退化为 `octet-stream`，需同步改 serve 路由与 url 重建逻辑，**增大爆炸半径**。
- **裁定：采用 `sha256+ext`**，serve 路由与 `SAFE_KEY` 零改动。

## 4. 数据模型变更

### 4.1 核心功能所需 schema 变更：**无**

物理去重仅依赖：
1. 存储层 key 派生改为内容寻址（`storage.ts`，内部）；
2. 删除在事务内数兄弟行（`attachment.ts`，内部）。

**不需要任何数据库列**。这是「零契约风险 + 低迁移风险」的关键卖点。

### 4.2 推荐增强：`content_hash` 可选列（nullable + 索引）

| 用途 | 说明 |
|---|---|
| 存量 backfill | 按 hash 找重复、折叠冗余文件，无需重新读盘比对 |
| 观测 / 审计 | 直接查「哪些附件共享同一内容」 |
| 未来 scheme B 就绪 | 上记录级去重时可直接加唯一索引 |

**双源迁移（硬性，避免漂移）** —— `migrate.ts:7-8` 已警告 raw SQL 与 `schema.ts` 须同步：

1. `src/db/schema.ts` 的 `attachments` 增加：
   `contentHash: text('content_hash'),` （**nullable**，避免既有行迁移需补值）；
2. `src/db/migrate.ts:116-127` 的 `attachments` `CREATE` 语句同步加 `content_hash TEXT`；
3. 生产（Cloudflare D1）走 `drizzle-kit generate` 生成 `ALTER TABLE attachments ADD COLUMN content_hash TEXT` 迁移，deploy 阶段应用（与现有迁移纪律一致）；
4. **现有本地库**：`CREATE TABLE IF NOT EXISTS` 不会改已有表，需对既存本地 SQLite 做一次 `ALTER TABLE attachments ADD COLUMN content_hash TEXT`（或重建本地库）。开发 AI 应在 PR 说明此点。

> `content_hash` **不进 `Attachment` 响应 schema**（`openapi.v1.yaml:432-452`），故不构成契约变更。

## 6. 契约影响评估（正式裁定：零变更）

逐条比对冻结契约 `docs/api/openapi.v1.yaml`：

| 维度 | 现状 | 去重后 | 是否变 |
|---|---|---|---|
| 请求体 `POST /upload` | `multipart/form-data {file, articleId?}`（:2177-2201） | 同 | ❌ |
| 响应 `data: Attachment` | 完整实体（:2205-2214, :432-452） | 同（仍返回合法 Attachment，新 id） | ❌ |
| 端点集合 | `/upload` `/me/attachments` `/attachments/{id}`（:2167, :2234, :2258） | 同 | ❌ |
| 错误码 / 状态码 | 4001 校验、401、404、200 等 | 同 | ❌ |
| `Attachment` schema 字段 | id/userId/articleId/url/storage/mimeType/size/createdAt | 同（`content_hash` 不暴露） | ❌ |

- DB 列新增（§4.2）属**内部实现**，不在契约 HTTP 面；契约管接口不管库。
- 契约**无任何去重 / 幂等条款**，加去重不推翻既有承诺（契约未保证「每次必给新 url / 新文件」）。
- **裁定：本优化零契约变更，无需解冻。** 若未来做 scheme B（记录级去重）或方案 C（客户端预检），那才会动契约，本次不做。

## 7. 竞态与正确性（A+ 重点）

**插入并发** —— 安全。
两个相同新文件同时上传：都算同 hash → 都 `storage.get` 未命中 → 都写（同字节文件幂等覆盖）→ 都插入行，共享同一 `storageKey`。这正是目标态（多行一文件），无破坏。

**删除并发** —— 必须事务（§3.3）。
若不包裹事务，存在危险交错：删行 → 计数=0 →（此刻另一上传插入新行并写文件）→ 真删物理文件 → 新行指向已删文件。
SQLite 单写者 + 事务串行化可消除该窗口：**「删行 + 计数 + 条件删文件」必须在同一事务内**（见 §3.3 代码）。`db.transaction` 保证上传的整段插入/写文件要么 fully 先于、要么 fully 后于删除事务，无 mid-transaction 交错。

## 8. 测试策略

| 层级 | 用例 |
|---|---|
| 存储单测 | 同 buffer 调 `put` 两次 → 同 key；第二次不触发新写盘（可用 spy / 查盘） |
| 服务单测 | `createAttachment` 同字节两次 → 2 行、同 `storageKey`、同 `content_hash`、同 `url` |
| 删除护栏 | 删共享文件的其中一个附件 → 物理文件仍在（另一附件 url 可用）；删最后一个 → 文件被删 |
| 契约测试 | `POST /upload` 返回合法 `Attachment`（字段齐全）；重传同图 → 不同 id、相同 url |
| 回归 | 现有 126 测试须保持全绿；若有断言「N 次上传 = N 个物理文件」的用例需同步调整（契约行为不受影响） |

## 9. 风险与回滚

| 项 | 说明 / 处置 |
|---|---|
| 回滚 | `storage.put` 回退 `randomUUID()` 即还原物理去重；`content_hash` 列可保留或 drop，无功能耦合 |
| sha256 碰撞 | 实际不可行（2^256），忽略 |
| hash 计算开销 | 10MB 上限内 sha256 亚毫秒级，可忽略；超大文件可改流式 hash（本期不需要） |
| R2 未实测 | 沿用 B10 裁决（无凭证不实测），逻辑与 local 同构，接线时一并验证 |
| 同字节不同 ext | `hash+ext` 下会产生不同 key（轻微残留重复）。若不可接受，升级为「纯 hash + ext 存列 + serve 路由改重建」（见 §3.4，更大改动） |

## 11. 开放问题（owner 已于 2026-08-26 裁决）

1. **去重作用域** → **全局**（任何用户相同字节合并，省盘最多；公开博客图片无隐私顾虑）。
2. **是否做 `content_hash` 列** → **不做**（核心功能不需要；P0/P2 取消，零 DB 迁移）。
3. **是否做存量 backfill** → **不做**（P5 取消；仅新上传受益，历史冗余留待独立小任务）。
4. **同字节不同 ext 是否接受** → **接受**（默认 `hash+ext`；轻微残留重复可接受，不升级纯 hash）。
