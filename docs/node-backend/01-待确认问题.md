## 🟠 P1 — 影响 B1 架构，动手前建议裁定

### Q3 · 刷新令牌：无状态 JWT（计划"从简"）vs `refresh_tokens` 表（02 要求旋转/作废）

- **现状**：
  - 计划 B1：`refresh 也用 JWT`，`logout 无状态返回 200`，"如做黑名单可后置"——即**无状态**，旧 refresh 在过期前始终有效。
  - 但 02 §九 P11 明确写死：**refresh 旋转（作废旧令牌）+ 登出作废**；§三"登出清 Cookie 闭环"。无状态 JWT 无法实现真正的作废/旋转。
- **选项**：
  - **A（推荐，契约保真）**：建 `refresh_tokens` 表（token_hash, user_id, expires_at, revoked_at）。login/refresh 签发并存储；refresh 时校验未吊销且旋转作废旧；logout 置位 revoked。改动集中在 B1，约 +1 表 + 少量逻辑。
  - **B（计划从简）**：refresh 用无状态 JWT（如 7d 过期），logout 仅清 Cookie，旧令牌过期前仍可用。实现简单，但 02 的"旋转/作废" teaching 点落空，属已知权衡。
- **需总把控确认**：选 A 还是 B？我倾向 A（项目以契约保真为核心卖点）。

### Q4 · 用户表命名：`members` vs `users`

- **现状**：
  - 计划 B0："先建 `members` 表"。
  - 但 02 领域模型实体名为 **User**；契约路径同时暴露 `GET /members/{id}`（公开主页）与 `GET /users`、`GET /users/{id}`、`PATCH /users/{id}`（admin）。`members/{id}` 只是公开资料视图别名，底层是同一张用户表。
- **选项**：
  - **A（推荐）**：DB 表统一命名 `users`（对齐实体名 + admin 路径），路由层 `GET /members/{id}` 映射到 users 表并做脱敏。避免"同实体两张名"的认知负担。
  - **B**：表叫 `members`，admin 路径 `/users*` 在路由内映射到 members 表（别名反向，易混）。
- **需总把控确认**：表名用 `users`？
