## 三、统一响应包络（已裁定，见 Q1）

契约 `components.schemas.ApiResponse` 为**全局唯一信封**，成功/错误同构：

```jsonc
// 成功（单对象）
{ "code": 0, "message": "ok", "data": { /* ... */ },
  "requestId": "req_8f3a1b2c", "timestamp": "2026-08-10T12:00:00Z" }
// 成功（列表）：data 内嵌 { list, pagination }
{ "code": 0, "message": "ok", "data": { "list": [/*...*/],
    "pagination": { "page":1,"pageSize":20,"total":100,"totalPages":5 } },
  "requestId": "...", "timestamp": "..." }
// 业务错误
{ "code": 1002, "message": "未登录", "data": null,
  "requestId": "...", "timestamp": "..." }
// 4001 参数校验：data 为 { errors: [...] }（ValidationErrorList）
```

- `code`: `ErrorCode` 枚举，0=成功，>0 见错误码表（1xxx 认证/2xxx 授权/3xxx 资源/4xxx 参数/5xxx 服务）。
- `requestId` / `timestamp` 为**必填字段**（契约 required），需由中间件统一注入。
- HTTP 状态码与 `code` 双层：4xx/5xx 走 HTTP 码，业务细分走 `code`。

> 注意：M1 总纲 §3.1 描述的信封（`{data}` 顶层 / `{error:{...}}`）**与契约冲突**，按"冲突以契约为准"原则，落地以本节约定的 `ApiResponse` 为准。详见 Q1。

## 四、授权求值（第 4 铁律，自包含，直接落地中间件）

契约 `info.description` 第 4 铁律已机器化，中间件按以下确定性规则实现：

1. 角色层级 `member(1) < editor(2) < admin(3)`。
2. 匿名仅可访问未声明 `x-authz` 的端点（`security: []` 或可选鉴权 `[{},{bearerAuth:[]}]`）。
3. 已登录且 `admin` → 始终放行。
4. 否则当且仅当满足以下**任一**放行：(a) 用户角色层级 ≥ 端点 `x-authz.minRole`；或 (b) 端点声明 `x-authz.ownerOverride` 且当前用户对该资源有归属（`resource[ownerField] == userId`）。
5. `/me/*` 为 self-scoped ≡ `ownerOverride{ownerField: userId}`；含子资源参数（如 `/me/favorites/{articleId}`）额外显式 ownerOverride 断言子资源归属。

> 实现要点：规则④是 **OR** 语义。例如 `submitArticle`（minRole:admin + ownerOverride{param:id, ownerField:authorId}）——会员（member）虽不满足 ④(a)，但作为草稿作者满足 ④(b)，应放行。中间件**绝不能只判 minRole**。

## 五、技术决策（我方已定，无需阻塞，登记备阅）

| # | 决策点 | 选择 | 理由 |
|---|---|---|---|
| D1 | 本地 DB 驱动 | `better-sqlite3` | 同步、Drizzle 原生支持、测试用 `:memory:` 稳定；Node 22 实验性 `node:sqlite` 暂不采用（Drizzle 支持成熟度）。CF 部署走 `drizzle-orm/d1`。 |
| D2 | 密码哈希 | `bcryptjs`（纯 JS） | 免原生编译、跨平台可移植、教学友好；argon2 需原生构建，本期不选。 |
| D3 | JWT 库 | `hono/jwt` + 自写 `lib/jwt.ts` 封装 | 与 Hono 同栈，payload `{ sub: userId, role }`。 |
| D4 | 校验 | `@hono/zod-validator` + Zod | 入参最外层校验（信任边界）。 |
| D5 | 测试 | `vitest` + `supertest`（或 Hono 的 `app.request`） | 端点级契约一致性断言；测试 DB 用 `better-sqlite3 :memory:`。 |
| D6 | CORS | `@hono/cors` 中间件 | React/Vue 后台跨域需 `credentials:include`；计划结构未列但属必需，已登记 Q8。 |
| D7 | view 计数去重 | 独立 `article_view_dedup` 表（去重键+24h 冷却唯一约束，计数写分离） | 对齐 02 §2.4，B2 落地。 |
| D8 | 软删除 | `articles` 加 `deleted_at`（部分唯一索引 `uq_article_slug WHERE deleted_at IS NULL`） | 对齐 02 §2.2 R10；评论为硬删级联子回复。 |
| D9 | 敏感词 | `sensitive-words.txt` 样例词 + 违规比率阈值 10% → rejected/approved | 对齐 02 §2.5，B4 落地。 |
| D10 | 存储 | `STORAGE_DRIVER=local` 完整实现并测试；`r2` 分支按接口注入、无凭证时不实测 | 对齐 02 §2.6。 |

## 八、已知范围边界（确认无碍）

- **通知生成逻辑缺失**：合同只定义通知读取端，无端点生成通知（如"文章过审通知作者"）。M1 内 `notifications` 表存在但为空，属计划明确 deferred（B6 NOTES）。需在文章写作阶段说明此为"读取端先行"。
- **限流 429**：合同 21 个公开端点挂 429，明确"网关层施加"。Node 应用层不实现真实限流（Q6），仅保证错误包络结构一致。
- **第三方登录**：`oauthCallback` 首波 501 占位，M3-09 再实现。
