## 二、逐条复批取证（不采信自陈）

### 🔴 P1 · `/view` 去重时间桶（真缺陷，确证清零）

**核验 1 — `src/routes/articles.ts:289-356`（view 处理器真实改造）**

- `:311` `const bucket = Math.floor(Date.now() / VIEW_DEDUP_MS);`（`VIEW_DEDUP_MS` 在 `:34` 定义为 24h）
- `:312` `const dedupKey = \`${baseKey}#${bucket}\`;` —— 冷却编码进 key。
- `:314-319` `recent` 查询改为 `eq(articleViewDedup.dedupKey, dedupKey)`，**不再用 `gte(createdAt, now-24h)`**。
- `:320-346` `if (recent.length === 0)` 内 insert 真包进 `try/catch`；`:327` 命中 `isUniqueConstraintError` → 兜底读当前 `viewCount` 返回 200（跳过增量、不重复计数、不 500）；否则 `throw err`。
- `:341-345` insert 成功后 `UPDATE view_count +1`（写语句 `.run()`，无 `.all()` 误用残留）。

**推演验证（修复后根因消除）**
- 旧逻辑：永久唯一约束 + 应用层 `gte(createdAt, now-24h)`。24h 后旧记录仍在 → 再插同 key → 撞永久唯一 → 无 catch → 500。
- 新逻辑：冷却编码进 `dedupKey` 的 `bucket`，24h 后 `bucket` 变化 → `dedupKey` 变化 → INSERT 永不再撞旧记录 → 500 根除。
- 同窗口并发：两请求都通过 `recent` 后同时 INSERT，第二个撞唯一 → `isUniqueConstraintError` 兜底 → 200、不重复计数。
- `isUniqueConstraintError` 复用 B1 抽出的可复用工具（`src/lib/db-error.ts`），零 `any`，跨批次复用。

**核验 2 — 针对性回归测试（`test/routes/articles.test.ts` 新增 3 条，确认断言正确）**
```
✓ 24h 冷却过后重访仍成功计数（不再 500）  —— 直插旧桶 dedup 行（bucket-1, createdAt-25h）后重访，status 200、viewCount 1
✓ 并发同 key view 均 200 不 500，且不重复计数 —— Promise.all 双请求均 200，计 ≤1
✓ sort=-viewCount 按阅读量真降序          —— A=10/B=30，列表顺序为 [B,A]
```
前两条正是首轮"测试只测同一次内连续两次、从未测 24h 后/并发"的盲区补位，且断言精确（插旧桶记录模拟冷却过期）。

**判定**：✅ 真修复，根除路径正确，边界测试到位。

### 🟡 P2-1 · 排序白名单符号 bug（真缺陷，确证清零）

**核验 — `src/lib/pagination.ts:28-29`**
```ts
const bare = sort?.startsWith('-') ? sort.slice(1) : sort;
const raw = bare && bare in SORT_COLUMNS ? (sort ?? '-publishedAt') : '-publishedAt';
```
- 旧：`sort in SORT_COLUMNS` 直接判断，带 `-` 前缀（如 `-viewCount`）恒为 false → 静默回退 `-publishedAt`。
- 新：先 `slice(1)` 剥前缀查白名单，命中则保留原 `sort`（含方向）。`sort=-viewCount` 现真正按 viewCount 降序。
- 升序裸字段（`sort=viewCount`）仍走 `bare in SORT_COLUMNS` 分支，行为不变。

**判定**：✅ 真修复，2 行，白名单主张落地（与 BE11「白名单优于黑名单」对齐）。

### 🟡 P2 · scanLimit 缺失（DB-01，确证补上）

**核验 — `src/lib/article.ts:141,194-201`**
```ts
const SCAN_LIMIT = 2000;
// 计数分支
let total: number;
if (q.keyword) {
  const scanned = await getDb().select({ id: articles.id }).from(articles).where(where).limit(SCAN_LIMIT).all();
  total = scanned.length;   // 封顶 SCAN_LIMIT（DB-01）
} else {
  const totalRow = (await getDb().select({ count: sql<number>`count(*)` }).from(articles).where(where).all())[0];
  total = Number(totalRow?.count ?? 0);
}
```
- 仅 `keyword` 触发 LIKE 模糊扫描时套护栏；普通状态/分类筛选走精确 `count(*)`（索引可达），不受限。
- 命中超量时总数显示封顶值（搜索可用性 vs 性能取舍，与 BE11 DB-01 论证一致）。
- 选用 `.select({id}).limit(SCAN_LIMIT).all()` 而非裸 `db.get(sql)`：Drizzle better-sqlite3 查询构建器无顶层 `db.get` 裸 SQL 方法（已 grep `node_modules/drizzle-orm/better-sqlite3` 确认），此写法类型安全且语义与子查询 count 封顶等价，避免引入未经验证的 raw 路径。

**判定**：✅ 真修复，与用户 BE11 文章 DB-01 主张一致。
