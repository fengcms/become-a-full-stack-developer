## 五、缺陷清单

### P2-1（建议修，非阻塞）· 移动带子孙的子树可能越过 x-max-depth:4
- **现象**：`categories-write.ts:118-131` 变更 parentId 时，仅校验 `depthOf(newParent) + 1 > MAX_CATEGORY_DEPTH`（即**被移动节点自身**的新深度），未计入其**子孙子树高度**。
- **推演**：建 `A(深度3)→B(深度4)`；再把 `A` 挂到另一个深度 3 的节点 `P` 下。`depthOf(P)+1 = 4 ≤ 4` 通过 → `A` 变深度 4，其子孙 `B` 变深度 5，**违反契约 x-max-depth:4**。
- **为何可达**：创建路径已正确阻止深度 >4（测试覆盖），但「移动已有子树」绕过了子孙校验。需特定多步操作（建带子孙的节点 → 再移深父），属边缘但**确为契约约束的偏差**。
- **NOTES 过度声称**：`B3-NOTES` 第 3 节称「既覆盖新建过深子节点，也覆盖把某节点挂到深节点下使其超界」——后者对**被移动节点**成立，对**其子孙**不成立。这正是「不采信自陈」在交付说明层面也要警惕的点。
- **修复建议**：变更 parentId 时，计算被移动节点子树高度 `subH = subtreeHeight(rows, id)`（含自身），要求 `depthOf(newParent) + subH ≤ MAX_CATEGORY_DEPTH`；或移动后对该子树根做一次 `depthOf` 全树校验。可纯函数单测锁定。
- **是否阻放行**：不阻 B3（边缘 + 默认建树用法不触发）；建议随 B4 一并修，并补「移动带子孙节点使子孙超界 → 409」测试。

### P3-1（非阻塞）· `buildTree` 缺数据环防御
- `buildTree` 依赖 `childrenOf` Map 递归，无 `seen` 集合。正常由写守卫保证无环，实践中安全；但属「契约允许成环则截断」的防御性兜底缺口。建议加 `seen` 集防止数据腐化时死循环（与 `depthOf`/`toBreadcrumb` 同款防御）。

### P3-2（非阻塞）· 深度/parent 校验的 TOCTOU
- `categories-write.ts` 创建时先 `allCategories()` 读父链、再 `insert`，之间存在并发窗口。低流量博客 MVP 可接受，与 B1 已登记的同类 TOCTOU 同级别，不要求改。

### P3-3（非阻塞，契约侧观察）· `/stats` 响应结构
- `GET /categories/stats` 返回 `{id,name,slug,articleCount}[]`，代码与测试一致、合理。若契约未为其声明具名 `CategoryStats` schema（grep 未见独立定义，疑似内联/缺省），属契约完备性小瑕疵，不影响 B3 放行，登记给契约维护批次。
