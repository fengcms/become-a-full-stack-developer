## 二、逐条复批取证（不采信自陈）

### 🔴 P1 · /view 去重时间桶（真缺陷，确证清零）

**核验 1 — `src/routes/articles.ts:290-339`（view 处理器真实改造）**
```ts
const bucket = Math.floor(Date.now() / VIEW_DEDUP_MS);   // 每 24h 一个桶
const dedupKey = `${baseKey}#${bucket}`;                 // 冷却进 key

const recent = await db
  .select({ id: articleViewDedup.id })
  .from(articleViewDedup)
  .where(and(eq(articleViewDedup.articleId, id), eq(articleViewDedup.dedupKey, dedupKey))) // 改 eq(dedupKey)，不再用 gte(createdAt, now-24h)
  .limit(1).all();
if (recent.length === 0) {
  try {
    await db.insert(articleViewDedup).values({ articleId: id, dedupKey, createdAt: new Date() }).run();
  } catch (err) {
    if (isUniqueConstraintError(err)) {                  // 同窗口并发撞唯一约束 → 兜底
      const cur = (await db.select({ viewCount: articles.viewCount }).from(articles).where(eq(articles.id, id)).limit(1).all())[0];
      return ok({ viewCount: cur?.viewCount ?? existing.viewCount });
    }
    throw err;
  }
  await db.update(articles).set({ viewCount: sql`${articles.viewCount} + 1` }).where(eq(articles.id, id)).run();
}
```
- 旧逻辑：永久唯一约束 + `gte(createdAt, now-24h)` 范围判断。24h 后旧记录仍在（永久唯一）→ 再插同 key → 撞唯一 → 无 catch → 500。
- 新逻辑：冷却编码进 `dedupKey` 的 `bucket`，24h 后 `bucket` 变化 → `dedupKey` 变化 → INSERT 永不再撞旧记录 → 500 根除。
- 同窗口并发：两请求都通过 `recent` 后同时 INSERT，第二个撞唯一 → `isUniqueConstraintError` 兜底 → 跳过增量、返回 200（不重复计数、不 500）。
- `isUniqueConstraintError` 复用 B1 抽出的可复用工具（`src/lib/db-error.ts`），零 `any`，与 B1 P2-1 一致。

**核验 2 — `src/db/schema.ts:103-107`（注释同步，避免 stale）**
> 24h 冷却编码进 dedup_key 的时间桶（baseKey#bucket，bucket=floor(now/24h)），冷却过后桶号变化 → 不再撞旧记录 → 根除「永久唯一约束 vs 24h 冷却」的 500；同窗口并发撞唯一约束时由应用层 isUniqueConstraintError 兜底下发 200（见 routes/articles.ts）。

**核验 3 — 针对性回归测试（`test/routes/articles.test.ts` 新增 2 条）**
```
✓ 24h 冷却过后重访仍成功计数（不再 500）     —— 直插旧桶 dedup 行后重访，status 200、viewCount 1
✓ 并发同 key view 均 200 不 500，且不重复计数 —— Promise.all 双请求均 200，计 ≤1
```

**判定**：✅ 真修复，且根除路径正确（冷却进 key 而非依赖 created_at 范围），并覆盖 24h 后 + 并发两条门禁漏网的边界。

### 🟡 P2-1 · 排序白名单符号 bug（真缺陷，确证清零）

**核验 — `src/lib/pagination.ts:29`**
```ts
const bare = sort?.startsWith('-') ? sort.slice(1) : sort;
const raw = bare && bare in SORT_COLUMNS ? (sort ?? '-publishedAt') : '-publishedAt';
```
- 旧：`sort in SORT_COLUMNS` 直接判断，带 `-` 前缀（如 `-viewCount`）恒为 false → 静默回退 `-publishedAt`。
- 新：先 `slice(1)` 剥前缀查白名单，命中则保留原 `sort`（含方向）。`sort=-viewCount` 现真正按 viewCount 降序。

**核验 — 针对性回归测试（`test/routes/articles.test.ts` 新增 1 条）**
```
✓ sort=-viewCount 按阅读量真降序          —— A=10/B=30，列表顺序为 [B,A]
```

**判定**：✅ 真修复，2 行，白名单主张落地（与 BE11「白名单优于黑名单」对齐）。

### 🟡 P2 · scanLimit 缺失（DB-01，确证补上）

**核验 — `src/lib/article.ts:141,191-203`**
```ts
const SCAN_LIMIT = 2000;

// 计数分支
let total: number;
if (q.keyword) {
  const scanned = await getDb().select({ id: articles.id }).from(articles).where(where).limit(SCAN_LIMIT).all();
  total = scanned.length;   // 封顶 SCAN_LIMIT（DB-01）
} else {
  const totalRow = (await getDb().select({ count: sql<number>`count(*)` }).from(articles).where(where).all())[0];
  total = Number(totalRow?.count ?? 0);
}
```
- 仅 `keyword` 触发 LIKE 模糊扫描时套护栏；普通状态/分类筛选走精确 `count(*)`（索引可达），不受限。
- 命中超量时总数显示封顶值（搜索可用性 vs 性能取舍，与 BE11 DB-01 论证一致）。
- 选用 `.select({id}).limit(SCAN_LIMIT).all()` 而非裸 `db.get(sql)`：better-sqlite3 Drizzle 查询构建器无顶层 `db.get` 裸 SQL 方法（已 grep `node_modules/drizzle-orm/better-sqlite3` 确认），此写法类型安全且语义与子查询 count 封顶等价，避免引入未经验证的 raw 路径。

**判定**：✅ 真修复，与用户 BE11 文章 DB-01 主张一致。
