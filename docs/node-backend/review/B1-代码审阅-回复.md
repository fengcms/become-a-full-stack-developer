## 二、P2-1 · 并发重复注册 500→409（真缺陷，已修）

### 根因
`auth.ts` 注册逻辑先 `select` 查重、再 `insert`。两个并发同用户名请求可同时通过查重，其一 `insert` 命中 `uniq_username`/`uniq_email` 唯一约束抛 `SqliteError`（`code='SQLITE_CONSTRAINT_UNIQUE'`），未被捕获 → 顶层 `errorHandler` 归为 `INTERNAL/500`，与契约约定的 409/3002 不符。

### 修复
1. **新增可复用工具** `src/lib/db-error.ts`：
   - `isUniqueConstraintError(err: unknown): boolean` —— 从底层驱动错误中识别唯一约束冲突（`SQLITE_CONSTRAINT_UNIQUE` / `SQLITE_CONSTRAINT`）。
   - 用结构化类型判定（`'code' in err && typeof === 'string'`），**零 `any`**，符合 biome `noExplicitAny` 铁律；B2 文章 slug 唯一冲突等场景统一复用。
2. **注册端点** 把 `insert` 包进 `try/catch`：命中唯一约束则改抛 `CONFLICT/409`（3002），其余错误原样上抛。原有的 `select` 查重保留为常见路径的快速返回（避免走异常路径）。

### 门禁证据
- 既有测试 `test/routes/auth.test.ts` 已覆盖"重复用户名→409 / 邮箱冲突→409"（走查重快速路径），仍绿。
- `tsc` / `biome` / `vitest` 全绿（见第四节）。

> 说明：try/catch 分支是并发竞态（TOCTOU）的兜底，单线程单测难以确定性触发；但它是"真实唯一冲突"的语义收敛，确保任何路径下都返回 409 而非 500。

## 三、P2-2 · 契约 refresh 描述散文矛盾（已修契约）

### 根因
`POST /auth/refresh` 描述写"两者皆无 → 401 / code **1003**"，但其 401 `examples.token_missing` 明确为 **1004**，`Unauthorized` 共享组件亦定义 `1004=令牌缺失`，代码 `auth.ts:137` 抛 `TOKEN_MISSING/401`(1004)——**代码正确，契约描述散文自相矛盾**。该矛盾会误导 Go/M3 等后续端实现者。

### 修复
将 `docs/api/openapi.v1.yaml`（refresh 描述散文）的 `code 1003` 改为 `code 1004（令牌缺失）`，使"描述 / 示例 / 共享组件 / 代码"四方对齐。
