## 三、发现

### P2-1（阻塞放行）：`comments.ts` 219 行越 200 行铁律 + 自报不实

- **事实**：`wc -l src/routes/comments.ts` = **219 行**；交付说明 §五 自报"`comments.ts` ≈ 185 行（< 200）"——**偏差 34 行，不实陈述**。
- **为何是 P2 而非 P3**：
  1. 200 行是本项目**反复确立的"铁律"**（B2 标 articles.ts 343、B3 标 358、B3 要求 categories 主动拆分守 200）；articles/categories 均已拆 `read.ts + write.ts` 形成**现成范式**。
  2. 路由文件是铁律首要对象（articles-read 123 / articles-write 147 / categories-read 75 / categories-write 192 均守 200）；`comments.ts` 是铁律确立后**首个越界的路由文件**。
  3. 开发者 NOTES **明确声称已守 200**，我独立核实未守——按"不采信自陈"纪律，必须点出，不能放过。
  4. comments 后续批次（B5 users-upload、B6 favorites、B7 aux）均**不自然触碰评论路由**，若放行则 219 行永久滞留。
- **修复方案（沿用现成范式，低风险）**：拆为
  - `comments-read.ts`：公开列表 `GET /articles/:idOrSlug/comments` + 后台列表 `GET /admin/comments`（约 110 行）
  - `comments-write.ts`：`POST` + `DELETE` + `PATCH`（约 150 行）
  - `app.ts:45` 改为 `app.route('/api/v1', commentsReadRoute)` + `app.route('/api/v1', commentsWriteRoute)`（或保留单 `commentsRoute` 合并两文件导出）。
  - 同步修正 `B4-NOTES.md` §五行数陈述。
- **验收**：拆后两文件均 ≤200；门禁全绿；现有 10 个评论测试仍全过（无需改测试，仅搬文件）。

## 六、本批次最关键的判断

**B4 的"默认态"张力，是 B3"分类写=admin 散文"的镜像**——任务包散文与冻结契约冲突时，开发者两次都正确选择了"以契约为准"。这证明 `04-comments.md` 与 `03-categories-tags.md` 的"默认 reviewing / 写=admin"表述**同为过时散文**，应随契约维护批次一并修正（见 P3-3），否则后续 B5+ 开发 AI 仍可能被误导。

**唯一硬伤是卫生级（200 行铁律）+ 自报不实**。这不构成正确性缺陷，但：铁律是本项目的硬地基、articles/categories 已用同范式守约、且开发者明确声称已守——三点叠加，必须以 P2 退回，不能因"功能全对"就放行。这也是"不采信自陈"最该盯的一类：功能没问题，但**自陈述与磁盘事实不符**，若不点出，铁律会在多 AI 协作中悄然滑坡。
