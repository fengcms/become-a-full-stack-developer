## 三、🔴 P0 — 必须 B1 前清零

### B01 · 参数校验错误码 `4001` 的 HTTP 状态：代码 422，契约 400（确定性契约违反）

- **证据**：
  - 契约侧：全文检索 `'422'` **出现 0 次**；9 个 `4001` 响应的 HTTP 状态**全部为 `400`**（如 `POST /auth/register`、`POST /articles`、`POST /upload`、`PATCH /me/profile` 等），且契约所有 `400` 响应的 `example.code` 取值集合仅为 `{4001}`。
  - 代码侧：`src/lib/codes.ts:62` `HttpForCode[VALIDATION] = 422`；`src/middleware/validate.ts:20` `failResponse(ErrCode.VALIDATION, 422, { errors })`。
- **影响**：直接违反项目铁律"契约只读、以契约为准"（02-裁决书红线）。`VALIDATION` 是地基常量，`validate.ts` 的 `v.json/query/param` 会被**全部 67 端点**复用 → 9 个契约校验响应（register/articles/upload/change-password/reset-password/…）上线后将返回 **422**，而契约与 M2/M3/M7 前端约定的是 **400**。前端按契约做状态码断言会全部失败；M6-09 对照测试也会分歧。
- **修复（一行级）**：把 `codes.ts:62` 改为 `[ErrCode.VALIDATION]: 400`，并同步 `validate.ts` 的 `failResponse(ErrCode.VALIDATION, 422, ...)` → `400`。修复后建议加一条契约一致性测试：断言 `HttpForCode` 的每一个 key 都与契约中该 `code` 实际出现的 HTTP 状态一致（可脚本化比对 yaml）。

## 四、🟠 P1 — 应清零（阻断双部署 / 生产 / 安全）

### B02 · Cloudflare 双部署断裂：`app.ts` 顶层默认 `app` 在 worker 导入时崩溃

- **证据**：`src/app.ts:34` `export const app = createApp(readEnv(process.env as Record<string, string | undefined>));` 在**模块顶层**执行。
  `src/worker.ts:6` `import { createApp } from './app';` 会触发 `app.ts` 整体求值 → 第 34 行立即 `readEnv(process.env)`。
  Cloudflare Workers **不保证提供 `process.env`**（需 `compatibility_flags = ["nodejs_compat"]`，而 `wrangler.toml` 仅设 `compatibility_date = "2025-01-01"`，**未开启 nodejs_compat**）。`process.env` 为 `undefined`/空对象时 `readEnv` 抛错 → **worker 模块加载即崩溃**，整套"一套代码双部署"（裁决 Q5）落空。
- **影响**：Node 侧可跑，CF 侧 import 即死；违背 Q5 交付承诺。
- **修复**：不要在 `app.ts` 顶层创建默认 `app`。仅导出 `createApp`（工厂）；把默认实例的创建移入 `src/index.ts`（Node 入口）。`worker.ts` 已正确用 `createApp(appEnv)`，不受影响。修后 CF 导入 `app.ts` 不再触发 `process.env` 求值。

### B03 · `index.ts` 未 `await migrate(db)`：建表与起服存在竞态

- **证据**：`src/index.ts:14` `migrate(db);`（`migrate` 为 `async`，`db.run` 返回 Promise），未 `await`、未 `.catch`。
- **影响**：better-sqlite3 底层同步，但 Promise 在微任务才 resolve；`serve` 紧随其后启动。理论上首请求前建表已完成，但属**脆弱竞态**，且 `migrate` 若抛错会成为**未捕获 rejection**（服务器带着空表起、首请求即失败）。
- **修复**：`await migrate(db);` 或 `migrate(db).catch(...)`。`index.ts` 顶层可用 top-level await（ESM + Node 22 支持），或包一层 `async main()`。

### B04 · `LocalStorage` 路径遍历：未净化的 `key` 可越权读/删文件（安全）

- **证据**：`src/lib/storage.ts:39` `readFile(join(this.root, key))`；`:47` `unlink(join(this.root, key))`。`key` 直接拼进路径，无格式校验/越界检查。
- **影响**：当前 B0 无任何路由导入 `storage.ts`（dead code），但它是 B5 上传的底座。一旦 `key` 来自请求参数（如 `DELETE /me/attachments/{key}`），攻击者可传 `../../etc/passwd` 之类逃逸 `root` 读/删任意文件。属于典型的 path traversal。
- **修复**：`put` 生成的 `key` 已是 `randomUUID()+ext`，安全；但 `get/delete` 必须校验入参 `key` 匹配 `^[A-Za-z0-9._-]+$`，或 `path.resolve(root, key)` 后断言 `startsWith(path.resolve(root))`，否则拒绝。

### B05 · CORS `credentials:true` + 生产回退 `origin:'*'`：浏览器拒绝凭据请求（生产误配）

- **证据**：`src/middleware/cors.ts:17` `origin: env.NODE_ENV === 'production' && env.CORS_ORIGINS ? env.CORS_ORIGINS.split(',') : '*'`，且 `credentials: true` 恒开。
  `wrangler.toml:11` `CORS_ORIGINS = "*"`（生产配置里仍是通配）。
- **影响**：CORS 规范禁止 `Access-Control-Allow-Origin: *` 与 `Access-Control-Allow-Credentials: true` 同时出现 → **浏览器直接拦截**跨域凭据请求。即生产环境 M2/M3/M7 带 cookie/Bearer 的跨域调用全部失败；若误把 `*` 当作"允许任意源 + 凭据"，更是安全反模式。
- **修复**：生产 `CORS_ORIGINS` 必须填具体白名单（如 `https://admin.example.com`）；代码中 `*` 回退仅在 `development` 允许，生产无白名单时应**拒绝跨域**（返回无 CORS 头）而非 `*`＋凭据。建议：`origin: env.NODE_ENV==='development' ? '*' : (env.CORS_ORIGINS?.split(',') ?? [])`。

### B06 · 仓库卫生：`.env`/运行产物未被忽略（密钥泄露风险）

- **证据**：根 `.gitignore` 含 `node_modules`、`.env*.local`，但**不含 `.env`**（真实密钥）、`node-backend/uploads/`、`node-backend/data/`（SQLite 库 + 上传文件）。
- **影响**：开发者本地 `.env`（含 `JWT_SECRET`）一旦 `git add` 即泄露；`data/app.db`、上传文件也可能被误提交。
- **修复**：在 `.gitignore` 追加 `.env`、`node-backend/uploads/`、`node-backend/data/`、`*.db`。`.env.example` 已是占位（`change-me`），可安全提交。

## 五、🟡 P2 — 建议改进 / 范围确认（不阻塞 B1，但建议顺手做）

### B07 · "契约一致性核查表"过度自陈
B0-NOTES 把"契约一致性 ✅"列为门禁之一，但 B0 仅 `health`（契约外）+ 401 有测试。`guard` 角色数学、`validate` 的 4001 形状、错误信封等**地基逻辑零单测**。建议补 3~5 个 foundation 单测（如 `guard('editor')` 对 member/editor/admin 的放行/拒断；`failResponse` 信封字段；`HttpForCode` 对照契约脚本）。

### B08 · `schema.ts` 与 `migrate.ts` 双源定义 `users` 表，易漂移
D1 生产走 `drizzle-kit`（读 `schema.ts`），本地/测试走 `migrate.ts` 手写 raw SQL。两份表结构目前一致，但属**双源真值**，后续加列极易只改一处。建议在 `migrate.ts` 顶部加注释指明"以 schema.ts 为准，改动需同步"，或本地也用 `drizzle-kit push` 生成。

### B09 · `ROLE_RANK` 0-based 与契约文档口径不一致
`src/middleware/auth.ts:24` `ROLE_RANK = { member:0, editor:1, admin:2 }`，而契约「第 4 铁律」文档写 `member(1) < editor(2) < admin(3)`。功能等价，但注释/文档易让接手 AI 混淆。建议统一口径（代码注释标明"内部 0-based，对应契约 1/2/3"）。

### B10 · `storage` 的 `r2` 分支未实现（占位 throw）
`createStorage` 对 `r2` 直接 `throw`。"双存储适配"当前仅有 `local` 可用，r2 为占位。与裁决/计划 D10"r2 按接口注入、无凭证不实测"一致，但需在 B5 前明确是 deferred 还是待补，避免误以为已具备双部署存储能力。

### B11 · `verifyAccessToken` 类型收紧
`src/lib/jwt.ts:35` `as unknown as AccessToken` 强转 + `role: string` 宽松类型。建议把 `role` 收敛为 `'member'|'editor'|'admin'` 字面量联合，校验时一并断言，杜绝 role 注入类隐患（低危）。

## 六、已确认的良好实践（给开发 AI 的 credit）

- 信封构造器返回原生 `Response`，lib 层零框架依赖，可单测、可跨运行时。
- 双层错误码 `ErrCode`（`as const`）+ `ErrorMessages`/`HttpForCode` 用计算属性键 → **契约加 code 而漏配会在编译期报错**，把一致性前移到编译期，设计用心。
- `guard(minRole, resolveOwner?)` 正确实现第 4 铁律 ④(a) OR ④(b)，是 B2/B5 会员作者自改草稿的关键原语，复用设计到位。
- DB 适配层 `getDb/setDb` + 边界单处 `as unknown as Db` 受控转换，脏活收敛在边界。
- `authMiddleware` 缺令牌抛 `1004`、失效/篡改抛 `1002`，与契约 `Unauthorized` 组件双 example（1004/1002）一致；其余错误码（2001→403、3001→404、3002/3003→409、5000→500、5001→429）映射均与契约吻合。
- 严禁 `any`（biome `suspicious.noExplicitAny: error`）、`verbatimModuleSyntax`、`noUncheckedIndexedAccess` 全部启用，类型纪律到位。
- JWT 用 `verify(token, secret, 'HS256')` 显式指定算法，规避 alg 混淆攻击。
