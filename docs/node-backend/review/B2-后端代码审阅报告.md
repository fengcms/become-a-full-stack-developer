## 一、总评结论

B2 是体量最大的一批（11 端点），整体结构、错误码、状态转移矩阵、可见性铁律都做得**对且干净**——门禁 51 测试全绿、契约逐端点对齐。但这一轮抓到一个**门禁永远抓不到、却会让核心端点在实际流量下崩坏**的 P1：阅读量去重的"24h 冷却"与"永久唯一约束"语义错配，导致任何 24h 内看过一次的读者再次访问都返回 500。

## 四、已确认的良好实践（给开发 AI 的 credit）

- **base 条件永远 AND（软删不可省略）**：`queryArticles`（`article.ts:126`）以 `isNull(articles.deletedAt)` 起手，所有过滤 `and(...conds)`。这正是用户文章里 `runList` 的 `base` 思想——调用方绕不过软删。✅
- **pageSize 封顶（MAX_SIZE 护栏）**：`parsePage`（`pagination.ts:21`）`Math.min(100, Math.max(1, ...))`。对应文章"size 失控拉全表"护栏。✅
- **排序白名单（注入安全）**：`buildSortSql`（`pagination.ts:12-33`）`SORT_COLUMNS` 白名单 + `sql.raw(column)` 仅取自信任白名单，杜绝排序注入。✅（但见 P2-1 实现 bug）

- **解析/执行分离雏形**：列表查询逻辑集中在 `lib/article.ts`（`queryArticles`），路由层只传参——呼应文章 `buildListQuery`/`runList` 的"逻辑收口"思想（虽未做成纯函数 DSL，见建议）。✅
- **错误码/状态收紧**：专用码（3002/3003/3001）、member 降级、slug 忽略、ownerOverride（`resolveArticleOwner`）全部对齐契约与第 4 铁律。✅

## 五、发现的缺陷（按严重度）

### 🔴 P1 — `/view` 阅读量去重：永久唯一约束与 24h 冷却错配 → 正常流量大量 500（功能级，必须修）

**根因（双源确认）**
- `db/schema.ts:107-118`：`articleViewDedup` 唯一约束 `uniq_article_dedup ON (article_id, dedup_key)` —— **永久唯一**，无时间桶。
- `articles.ts:308-330` 应用层冷却：`recent` 查 `createdAt >= now - 24h`，未命中才 `insert` + `UPDATE view_count +1`；insert **无 try/catch**（`:321`）。
- NOTES 自述"24h 冷却：查询 `createdAt >= now - 24h` 是否已有记录；命中则不计"——与永久唯一约束**语义冲突**。

**复现（确定性）**
1. 用户 U 在 T0 首次 view 文章 A → 插入 `(A,'u:U',T0)` 成功，count=1。
2. T0+25h（冷却已过）：`recent` 判定 `T0 >= T0+1h` 为假 → 未命中 → 尝试再插 `(A,'u:U')` → **撞永久唯一约束 → 抛 SqliteError → 无 catch → errorHandler 归 INTERNAL/500**。
3. 结果：任何"24h 内看过一次"的读者再次访问，均 **500**。对真实博客，这意味着绝大多数回访流量打爆 `/view`。

**并发二次伤害**：即便在 24h 窗内，两个并发同键请求都先通过 `recent`（彼此都还没插）→ 都 insert → 第二个撞唯一 → 500。双击/并发 fetch 即 500。

**测试为何漏网**：`articles.test.ts:216-243` 的"阅读量去重"用例在同一次测试内连续两次 view（同一 IP/UA、毫秒级、库全新），既没测 24h 后、也没测并发 → 门禁全绿但缺陷存活。

**修复方案（最小且正确，复用 B1 的 `isUniqueConstraintError`）**
把 24h 冷却**编码进 dedupKey 的时间桶**，使唯一约束"按窗口"而非"永久"；并对同窗口并发冲突兜底：
```ts
const WINDOW_MS = VIEW_DEDUP_MS;                       // 24h
const bucket = Math.floor(Date.now() / WINDOW_MS);    // 每 24h 一桶
const baseKey = me ? `u:${me.id}` : `a:${fnv1a(`${ip}|${ua}`)}`;
const dedupKey = `${baseKey}#${bucket}`;               // 冷却窗口进 key

const recent = await db.select({ id: articleViewDedup.id })
  .from(articleViewDedup)
  .where(and(eq(articleViewDedup.articleId, id), eq(articleViewDedup.dedupKey, dedupKey)))
  .limit(1).all();
if (recent.length === 0) {
  try {
    await db.insert(articleViewDedup).values({ articleId: id, dedupKey, createdAt: new Date() }).run();
  } catch (err) {
    if (isUniqueConstraintError(err)) {
      // 同窗口并发重复：视作已计数，跳过增量，避免 500
      const cur = (await getViewCount(id));
      return ok({ viewCount: cur });
    }
    throw err;
  }
  await db.update(articles).set({ viewCount: sql`${articles.viewCount} + 1` }).where(eq(articles.id, id)).run();
}
```
- 冷却过后 `bucket` 改变 → `dedupKey` 改变 → insert 永不再撞旧记录 → 500 根除。
- 同窗口并发 → 第二者撞唯一 → `isUniqueConstraintError` 兜底 → 跳过增量、返回 200，无重复计数、无 500。
- **必须补测试**：① 同一 key 在"模拟 24h 后"仍应成功计数（用可控时钟或直插 `createdAt` 早于 now-24h 的旧记录再 view）；② 并发同 key 两次均 200 且不崩溃。

### 🟡 P2 — 排序白名单 bug：降序非默认字段被静默忽略（功能级）

**证据**：`pagination.ts:27`
```ts
const raw = sort && sort in SORT_COLUMNS ? sort : '-publishedAt';
```
`SORT_COLUMNS` 的键是裸字段名（`publishedAt`/`viewCount`/`createdAt`），但 `sort` 带可选 `-` 前缀（如 `-viewCount`）。于是：
- `sort=-viewCount` → `'-viewCount' in SORT_COLUMNS` 为 **false** → 静默回退默认 `-publishedAt`。
- 结论：**只有升序裸字段名能生效；任何"降序 + 非默认字段"的请求都被悄悄忽略**，与契约"带符号字段名"约定（pagination.ts:4 注释）自相矛盾。

**修复（2 行）**：先剥离 `-` 再查白名单：
```ts
const bare = sort.startsWith('-') ? sort.slice(1) : sort;
const raw = bare in SORT_COLUMNS ? sort : '-publishedAt';
```
**补测试**：`sort=-viewCount` 应真正按 viewCount 降序返回。

### 🟡 P2 — 缺扫描上限护栏（用户文章 DB-01，性能级）

**证据**：`article.ts:130-150` `queryArticles` 在 `keyword` 存在时，仍 `count(*) FROM articles WHERE ... LIKE '%kw%'`，**无 scanLimit 兜底**。

**对照用户文章**：BE11 把"q 搜索别直接 count"标为 **DB-01——整套系统最重要的性能护栏**。在 SQLite/D1 上 `LIKE '%前缀%'` 无法命中索引 → 文章表几十万行即全表扫，列表接口被打慢。用户文章的 `Q_SCAN_LIMIT=2000` 把扫描量钉死。

**修复建议**（与文章 DB-01 一致）：`keyword` 存在时，把 count 包一层 `LIMIT scanLimit` 子查询：
```ts
const SCAN_LIMIT = 2000;
// keyword 分支：
const totalRow = keyword
  ? await db.get<{n:number}>(sql`SELECT count(*) AS n FROM (SELECT 1 FROM ${articles} ${whereClause} LIMIT ${SCAN_LIMIT})`)
  : (await db.select({count:sql<number>`count(*)`}).from(articles).where(where).all())[0];
```
代价：极端超量搜索总数显示"≥2000 封顶"，是"搜索可用性 vs 性能"的合理取舍（同用户文章论证）。

> 严重度定 P2（非阻塞 MVP，但用户文章明确将其列为头号护栏；文章规模上来前务必补）。

### 🟡 P2/P3 — 列表查询 SELECT * 含 content（投影浪费，性能级）

**证据**：`article.ts:140` `.select()` 取全部列（含 `content` 最长 65535 字符），随后 `map(toArticleSummary)` 丢弃 `content`。列表/摘要接口本不需 `content`。

**对照用户文章**：BE11 专节讲"投影：只取指定列，其余不查"。热点列表每页拉 N 篇 `content` 大文本，内存/IO 浪费明显。

**修复建议**：列表查询改为只 `select` 摘要所需列（`id/title/slug/summary/coverImage/authorId/authorName/categoryId/categoryName/tags/status/viewCount/likeCount/publishedAt/createdAt/updatedAt`），不取 `content`。

### 🟡 P3 — tag 子串误匹配（精度，非阻塞）

**证据**：`article.ts:135` `sql\`${articles.tags} LIKE ${`%"${q.tag}"%`}\``。JSON 数组 `"json"` 会被 `"js"` 命中（子串匹配）。NOTES 已自承"B3 改造为 article_tags 关联后更精确"，属已知权衡，**B2 可接受，登记 TODO**。

### 🟡 P3 — `articles.ts` 超 200 行（343 行，软约束）

文件头（articles.ts:5-7）已说明"7 端点共用 Schema/slug/状态助手，强拆反违背复用纪律"——理由成立，属文档允许的"特殊情况"。若后续维护吃力，可按"公开/我的/后台"已拆的 `articles-me.ts`/`articles-admin.ts` 思路，进一步把 `view`/`submit` 独立。当前**不要求改**。

## 六、对照用户《BE11 通用列表查询 DSL》的专项建议

> 用户要求："我写的通用列表查询 DSL 文章，在本项目也有用，请给出调整建议。"以下建议均以该文为基准，且区分"当前该做 / 后续规模上来再做"。

| # | 文章主张 | B2 现状 | 建议 |
|---|---|---|---|
| 1 | **白名单优于黑名单**（未知字段一律拒） | sort/过滤均白名单化 ✅ | 保持；修 P2-1 的 sort 白名单 bug 即落地该主张 |
| 2 | **DB-01 scanLimit**（q 搜索 count 包 LIMIT 子查询） | 缺失（P2） | 补 `Q_SCAN_LIMIT`，与文章一致 |
| 3 | **MAX_SIZE 页大小封顶** | 已做（100）✅ | 保持；值可按需调 |
| 4 | **base 条件永远 AND**（软删/隔离绕不过） | 已做（`isNull(deletedAt)`）✅ | 保持 |
| 5 | **投影（只取指定列）** | 缺失（P2/P3） | 列表查询仅 select 摘要列，不取 `content` |
| 6 | **解析/执行分离**（`buildListQuery` 纯函数 + `runList`） | `queryArticles` 合并解析+执行 | 当前可接受（见下） |
| 7 | **敏感字段统一脱敏** | 文章无 PII 列，N/A | — |

**关于"是否要上通用 `field__op=value` DSL"（文章核心）的明确判断**：
文章场景是"二三十个内部后台列表，几乎复制粘贴"。本项目**公开文章 API 只有 4 个固定过滤维度**（keyword/tag/category/status/author），B2 用**固定白名单查询参数**而非通用 `field__op` DSL，是**更合适**的折中——避免过度下沉通用 DSL，契合本项目"代码是素材、文章是产品"的克制原则。
**但**：若后续 B3+ 后台列表（用户/评论/订单类）增多到一定规模，建议抽一个 `buildListQuery(fields, params)` 纯函数 + `runList` 执行器复用层（直接搬文章的骨架），把"白名单/扫描上限/投影/base AND"一次性收口——届时本批 `queryArticles` 可平滑迁移为它的特例。
