## 四、安全与正确性重点核查

1. **ownerOverride 矩阵正确（隐式本人限定）**：`/me/*` 删除类（removeFavorite / removeHistoryItem）以 `WHERE user_id = 当前用户` 实现"仅本人"，无法越权删他人数据（userId 恒为当前，articleId 仅定位"哪条"）。`updateNotification` 路径参数是通知 id（非当前用户标识），显式加载后 `existing.userId !== userId → 404`（不泄露存在性，符合契约 404 文案）。✅
2. **收藏 404 语义**：`favorites.ts:83` / `history.ts:95` 文章不存在 **或** `status !== 'published'` → 404（与 B2/B4 一致，契约明示"未发布不可收藏"）。✅
3. **历史 upsert 唯写路径**：`history.ts:96-115` 先查 `(user_id, article_id)`，存在则仅更新 `lastReadAt`（progress 仅请求携带时覆盖），否则插入；`view_count` 不动（与 B2 `POST /view` 职责分离，02 §2.4）。✅
4. **点赞双幂等**：`likeArticle` 先查存在性再 insert + `like_count+1`；`unlikeArticle` 先查存在性再 delete + `like_count-1`（下限 `Math.max(0,…)` 防负）。返回 `{liked, likeCount}`。✅（但见 **P2** 并发边界）
5. **通知生成端不在本批**：仅读取端，生成逻辑 NOTES 登记，测试用 DB 直插 `notifications` 模拟——符合禁止项"不实现通知自动生成"。✅
6. **脱敏/越权**：全部 `/me/*` 以 `c.get('user').id` 限定自身；通知 `userId` 不对外越权（PATCH 非本人 404）。无敏感字段泄漏。✅
7. **投影正确**：列表查询复用 `toArticleSummary` 摘要列，未拉 `content` 长文本（延续 B2 P2 投影主张）。✅
8. **DDL 一致**：`schema.ts` 四表 + `uniq_favorite`/`uniq_view_history`/`uniq_like` 三个唯一索引与代码 `onConflictDoNothing` / 存在性判定对应；`notifications` 含 `type` enum（`article_published`/`comment_approved`/`system`）+ `isRead` 布尔列。✅

## 六、判定与发现

### 🟠 P2（建议修复后放行 B7，非立即阻塞但属契约机器字段违反）

**P2-1（likeArticle 并发双插 500 + like_count 漂移）**：`likeArticle`（x-idempotent:true，契约 3331）的 insert（likes.ts:70）**裸 insert 无 `onConflictDoNothing`**，而同批 `addFavorite`（favorites.ts:87）正确使用了 `onConflictDoNothing`。后果：
- **契约违反**：两个**并发**在途的 `POST /articles/{id}/like`（如用户连点两下、"乐观 UI"双发、弱网重试重叠）→ 均通过 `if(!existing)` 检查 → 第二个 insert 撞 `uniq_like` 唯一约束 → 抛 `SQLITE_CONSTRAINT_UNIQUE` → 全局错误处理器 → **500**，而非契约承诺的 200（x-idempotent 机器字段被破坏）。
- **计数漂移**：`like_count` 用"读 `article.likeCount` 再 +1"的应用层 read-modify-write（likes.ts:73），并发下可重复 +1（一次真实点赞变 +2），且 `unlikeArticle` 同理（likes.ts:107）存在对称漂移（已用 `Math.max(0,…)` 防负，但读值仍陈旧）。
- **修复**（与 favorites 同构、低风险）：`likeArticle` 改为
  ```ts
  const res = await db.insert(likes).values({userId, articleId, createdAt: new Date()}).onConflictDoNothing().run();
  if (res.changes > 0) await db.update(articles).set({ likeCount: sql`like_count + 1` }).where(eq(articles.id, articleId)).run();
  ```
  并以 `sql\`CASE WHEN like_count > 0 THEN like_count - 1 ELSE 0 END\`` 做 `unlikeArticle` 的原子 -1（消除读改写竞态）。这样 x-idempotent 在 DB 层真成立，且计数一致。
- **判别依据**：满足本审阅 P2 准则"破坏契约"（x-idempotent 机器字段承诺 200 却可 500）。与 B1 并发唯一约束→500 同根，favorites 已示范正确写法，likes 漏用属不一致。属低频竞态但修复成本极低，建议 B7 前顺手修。

### 🟡 P3 非阻塞观察（不阻放行）

- **P3-1（reportReadingProgress upsert 竞态）**：`history.ts:110-114` 先查 `existing` 再 insert，与 likeArticle 同源 read-then-insert；并发双发同 (user,article) 会撞 `uniq_view_history` → 500。该端点契约**未标** x-idempotent，故非契约违反，但双发仍会 500。建议改 `insert … onConflictDoUpdate`（upsert 语义本就该 DB 层做）。与 P2-1 一并修。
- **P3-2（like_count 应用层维护漂移）**：已并入 P2-1 修复建议（原子 ±1）。
- **P3-3（`GET /me/likes` 契约内部不一致）**：契约 `data` 裸数组但 `parameters` 声明 `page`/`pageSize`（NOTES §五已登记）。代码严格按契约返回裸数组、仍用 limit/offset 截断——正确。属契约文档问题，留契约维护批次统一（呼应 B5 复批 N 项提醒）。
- **P3-4（`schema.ts` 336 行 > 200 软上限）**：该文件是"全部表单一事实源"，B2–B5 各批均在内增量加表且历次审阅未将其列 P 级（P2 拆分诉求历来针对 route 文件）。为不引入跨文件 import 大面积重构风险，本批保持单文件，沿用既往先例。若总把控认为需拆，可单独立项 `schema/*.ts`。非阻塞。
- **P3-5（NOTES §六 自陈与契约不符， benign）**：NOTES 称"契约对 clearMyHistory、removeHistoryItem、likeArticle、unlikeArticle 均标 x-idempotent"，但契约实测**仅** `addFavorite`(2552)/`removeFavorite`(2600)/`likeArticle`(3331)/`unlikeArticle`(3377) 标 `x-idempotent:true`；`clearMyHistory`(2685)/`removeHistoryItem`(2705) **未标**。属 NOTES 过度声称（DELETE 天然幂等、代码行为正确，无害），但与"不采信自陈"纪律同源——仅记录，不重复计分。
