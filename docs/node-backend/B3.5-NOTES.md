## 三、关键行为决策

### ① article_tags 写同步（create/update/软删）
- **create**：拿到新 `article.id` 后调 `syncArticleTags(id, input.tags)`。仅链接 `slug==name` 约定解析出的已存在 Tag（`SELECT id FROM tags WHERE slug=? OR name=?`）；不存在的标签名**跳过**（不自动建 catalog 标签——建标签属 editor 职责，越权）。
- **update**：`input.tags` 提供时调 `syncArticleTags(existing.id, input.tags)`（清旧 + 覆盖插，幂等）；`input.tags` 省略则沿用既有关联（与 B2 现状一致）。
- **软删**：`DELETE FROM article_tags WHERE article_id=?` 一并清理，junction 与文章生命周期一致（articleCount 的 JOIN 本就 `isNull(deletedAt)` 过滤，删不删不影响计数，但删了更干净）。
- 写入走 `uniq_article_tag` 唯一索引 + `.onConflictDoNothing()`（`lib/article-tags.ts`），并发/重复标签不抛错；`.run()` 统一写语句。

### ② 存量回填脚本（可重复跑）
- 运行（本地 Node / 自管 Linux）：`pnpm backfill`（= `tsx scripts/backfill-article-tags.ts`），读 `DB_FILE`（**务必指向真实库文件**，默认 `:memory:` 会告警无意义）。
- 逻辑：`SELECT id, tags FROM articles WHERE deleted_at IS NULL` → `parseTags` → 对每个标签名 `resolveTagIds` → `INSERT ... ON CONFLICT DO NOTHING`。
- **幂等**：依赖 `uniq_article_tag` + `ON CONFLICT DO NOTHING`，重复执行安全；已存在的关联被忽略。
- **Cloudflare D1**：不直接跑 Node 脚本，改用 `wrangler d1 execute` 跑等价 SQL（见脚本底部注释，用 `json_each` 展开 `articles.tags` 再 `JOIN tags`）。
- 选择：**部署后由人跑一次**（而非 `index.ts` 启动期调用），避免启动耦合与每次冷启动的重复扫描；NOTES 显式记录此选择。

### ③ 列表标签过滤切 JOIN（关 B2 P3）
- `queryArticles` 中 `q.tag` 由 `slug/name` 解析为 `tagId`，对 `article_tags` 做 `innerJoin` 精确过滤。
- **行为变化（预期且正确）**：旧 `LIKE "%"js"%" ` 会子串误匹配（如 `js` 命中 `json`）；新 JOIN 仅匹配真正链接到 catalog 标签的文章；若 `q.tag` 无对应 catalog 标签 → 直接返回空列表（不再「碰巧命中」）。
- 修复连带问题：`queryArticles` 在标签 JOIN 后与 `article_tags` 同表存在 `created_at`/`id` 歧义列，`buildSortSql`（pagination.ts）的排序列统一加 `articles.` 限定（含稳定键 `articles.id DESC`），根除 `ambiguous column` 500。

### ④ articles.ts 拆分
- 按「公开读 vs 登录写」职责拆为 `articles-read.ts`(123) 与 `articles-write.ts`(147)，二者在 `app.ts` 同挂 `/api/v1/articles`。
- 共享逻辑下沉：`lib/article-mutation.ts`（状态/slug 解析 + 创建/更新 DB 操作）、`lib/article-tags.ts`（标签关联同步）。`articles-write.ts` 仅作薄路由委托，改动不再膨胀单文件。
