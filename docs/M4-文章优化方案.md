# M4 系列文章优化方案

> 状态：**待 owner 拍板**，本文档不含任何已落盘的改动。
> 体检范围：`articles/M4-01` ~ `M4-28`，共 28 篇。
> 体检方式：全量脚本统计 + 抽样精读（M4-13 / M4-15 / M4-19 全文，M1-13 作基线对照）。
> 日期：2026-10-04

## 一、结论先行

M4 的「干瘪」是**两个独立病根叠加**的结果，不是一个问题：

| 病根 | 表现 | 药方 | 风险 |
|---|---|---|---|
| **A · 篇幅被压缩** | 正文 1679 字、代码 12 行，是 M1 的 1/3、M3 的 1/6 | 扩写：补代码、补对比表、补数据 | 低，纯增量 |
| **B · 文体是说明书** | 7.6 处/千字免责话术；28/28 篇用引用块开场；H3 恒为 6 个 | 重写：换叙述视角、去免责腔 | 中，改的是文的味道 |

**只做 A 会得到「更长但更干」的 28 篇；只做 B 会得到「好看但更短」的 28 篇。建议 A + B 同时做，且先做 B 再做 A** —— 文体定了，扩写才知道往哪儿扩。

## 三、病根 A：篇幅被压缩

### 症状
抽读 M4-15（WebView，1612 字 / 1 个代码块）能看到典型形态：整篇在**描述行为**，没有**展示实现**。

原文：

```text
Flutter 栈：Article → WebPage
WebView 内部：URL A → URL B（留在当前 WebPage）
App 返回：WebPage → Article
```

这是 `text` 语言标注的**示意图**，不是代码。真正的 `PopScope` / `canGoBack()` / `NavigationDelegate` 实现一个都没给。

M4-19（投稿状态机）状态转换同样只用 4 行伪码表示，真实的 `switch` 分支、按钮禁用条件、后端错误码映射全部缺席。

### 优化动作

| 动作 | 做法 | 预期 |
|---|---|---|
| A1 补真实代码 | 每篇 2–5 个可运行片段，取自 `flutter-app/` 真实实现，带文件路径 | 代码行 12 → 35+ |
| A2 补对比表 | 每篇 1–2 张「React 写法 vs Flutter 写法」「Web vs APP 边界」表 | 表格 0 → 3+ |
| A3 补数据/日志 | 有实测数字的（缓存命中、耗时、并发数）给真实值，没有的明说「未实测」 | 防止再次滑向免责腔 |
| A4 补失败现场 | 至少 1 处「我一开始写错了 / 报了什么错 / 怎么改的」 | 亲历感是 M1 基线的核心 |

**目标：中位字数 1679 → 2600+，代码行 12 → 40+，表格 0 → 3+。**

## 四、病根 B：文体是说明书（这才是「干瘪」的真正来源）

### 症状 1：免责话术密度是 M1 的 3.5 倍

M4 中位 7.6 处/千字，M1 只有 2.2。抽样命中的典型句：

> 「此段是结构示意，真实包的 builder 接口必须以锁定版本文档和 `reader_markdown.dart` 为准。」
> 「示例是产品规则示意，动作集合必须与后端实际能力及角色权限核对。」
> 「不能替代」「不等于」「以实际为准」「不能写成」「尚未验收」

这些句子本身没错，但**它们不是教程，是自我免责**。读者读到的不是「怎么做」，而是「作者在声明自己没做什么」。密度一高，整篇的叙述温度就降下来了——这正是「干瘪」的体感来源。

### 症状 2：28/28 篇用引用块开场

M1 是 2/31（叙事开场），M3 是 24/24，M4 是 28/28。引用块开场 = 一上来就给结论，没有故事。

M4-15 开场：

> 「WebView 看上去只是 App 里的一块网页，却同时拥有网页内部 URL 历史和 Flutter 路由历史。」

对比 M1-13 开场：

> 「把认证"聊明白"，和把它"写出来"，中间隔着一条很宽的河。上一篇我们刚把方案定下来……问题才一个个浮出水面：密码怎么存，才不至于数据库一泄露、用户就全被交代出去？」

后者有**痛点、有悬念、有上一期的钩子**；前者是**产品需求陈述**。

### 症状 3：H3 恒为 6 个（28 篇全部相同）

28 篇的 H3 数量**一模一样是 6**。这说明章节结构是被同一个模板批量套出来的，不是每篇按自己的内容自然长出来的。读者读三篇后会开始跳读。

### 症状 4：叙事主体是「项目」而非「我」

高频出现「本项目」「项目当前」「产品需要」——这是**第三方视角**。M1 全程是「我们」「我」。第三方视角天然疏离。

### 优化动作

| 动作 | 做法 |
|---|---|
| B1 开场重写 | 28 篇全部改为「痛点场景 + 悬念 + 任务句」两到三段，叙事主体改回第一人称 |
| B2 免责降级 | 把「不能替代 X」类句子**删除或改写为正面陈述**。原则：只保留对读者决策有实质影响的那一两条，其余删 |
| B3 章节个性化 | 拆掉统一的 6×H3 模板，按每篇真实内容重新规划小节 |
| B4 增加失败叙事 | 每篇至少一段「踩坑—定位—修正」，把现在的免责声明改造成真实的调试故事 |

## 五、改造分批策略

28 篇一次全改风险太高（文风是主观判断，改坏了不易发现）。建议**分三批走，每批只改 2–3 篇，你亲自验收后再推**。

| 批次 | 篇目 | 选择理由 |
|---|---|---|
| **第 1 批 · 标杆** | M4-15（WebView）、M4-19（投稿状态机）、M4-13（Markdown 阅读器） | 这三篇病根 B 最典型（免责话术密集、示意图冒充代码），**改好了就是全系列的模板** |
| **第 2 批 · 铺开** | M4-07（Dio）、M4-09（Refresh Token）、M4-12（分页）、M4-17（叠楼评论） | 技术密度最高、最依赖代码的 4 篇，改造价值最大 |
| **第 3 批 · 收尾** | 其余 21 篇 | 按第 1 批定下的新标准批量处理，逐篇过 |

每批改造后跑一次量化复核（字数/代码行/表格/免责密度/开场形态），确认指标真的动了，而不是我自称改了。

## 六、待你拍板的三个决策点

### 决策 1：是否动已发布文章

M4 目前**全部未发布**（M3 已发 01~15，M4 尚未开始发），所以现在改是零成本的。但需要你确认发布节奏：**是否按原计划发 M4，还是等三批改完再发？**

我的建议：先改第 1 批 3 篇，确认口味后再决定是否整体延后。

### 决策 2：目标字数定在哪

| 方案 | 中位目标 | 说明 |
|---|---|---|
| A · 对齐 M1 | 2600+ | 与后端篇持平，阅读成本偏高 |
| B · 对齐 M3 | 2400+ | 前端系列惯例，成本适中 |
| **C · 对齐 M3 但代码加倍（推荐）** | **2400–2800 字 + 代码 40+ 行** | 篇幅不必暴涨，靠代码和表格承载密度 |

我推荐 **C**。M4 的问题不完全是字数少，更是「代码和对比表太少」。单纯加字数会灌水，加代码才是真密度。

### 决策 3：免责话术的处置尺度

| 选项 | 做法 | 风险 |
|---|---|---|
| 保守 | 密度从 7.6 降到 4 左右 | 边界信息可能丢，读者按错误预期操作 |
| **激进（推荐）** | 降到 2.5，与 M1 持平，**但把该留的移到「延伸阅读」或文末小节** | 需要逐句判断，不能机械删 |
| 全删 | 全部删除 | 不推荐，可能丢掉「iOS 未验收」这类对读者有实质影响的边界 |

推荐**激进 + 有序迁移**：不是抹掉边界声明，而是把「作者对自己实现的不确定性声明」和「读者必须知道的事实性边界」分开——后者保留，前者删。

## 七、改造后的验收标准

每篇改完，逐条机器复核：

| 指标 | 门槛 |
|---|---|
| 正文字数 | ≥ 2400 |
| 真实代码行（取自 `flutter-app/`） | ≥ 30 行，且含至少 1 个文件路径标注 |
| 对比表 | ≥ 2 张 |
| 免责话术密度 | ≤ 3.0 处/千字 |
| 开场形态 | 引用块开头 = 0，改为两段式叙事 |
| 失败叙事 | ≥ 1 处踩坑段落 |
| H3 数量 | 不与其他篇重复（打破恒为 6 的模板） |
| 占位符 | `{{LINK:...}}` / `{{IMG:...}}` 保持不变 |
| 配图提示词 | 保持在发布辅助区内，不影响发布流程 |
