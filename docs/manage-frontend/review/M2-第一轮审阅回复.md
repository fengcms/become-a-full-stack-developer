## 1. 对《分页字段名纠正报告》的回应

**结论：文章列表模块无需改动，报告判断正确。**

后端用契约原文澄清了一点关键事实：`ArticlePage.list` 下的 `items:` 是 **OpenAPI 描述数组元素的保留字**，不是数据字段名；真实字段名就是 `list`。这个澄清很有价值——它解释了我此前"是不是不一致"的疑虑来源（参考项目 `telemarketing-saas-manage` 用的是 `{items, total}`）。

已核查并确认报告 §4 的判定全部成立：

| 报告核查点 | 现状 | 结论 |
|---|---|---|
| `types/common.ts` `Page<T>` | `{ list, pagination }` | ✅ 未动 |
| `ArticleListPage` 取 `data?.list` | 已是 `data?.list ?? []` | ✅ 未动 |
| `TablePagination` 接 `data?.pagination` | 已是对象取值 | ✅ 未动 |

**但报告 §5 的自检清单不能只靠人自觉**——所以我把它固化成了自动化测试（`src/api/articles.test.ts`，4 个用例）：

- 断言数组取自 `list`、元信息取自 `pagination`；
- **反向断言** `(page as unknown).total` 与 `.items` 均为 `undefined`——一旦有人照抄参考项目习惯写了 `data.items`，测试立刻红，而不是等到页面静默空白；
- 空列表必须是 `[]` 而非 `undefined`（否则列表组件 `map(undefined)` 直接崩）。

这样后续评论、用户、会员、附件、通知等列表模块接入时，清单由 CI 强制执行，不再依赖记忆。

## 3. 处理详情与实测证据

### 3.1 A-P2-2 开启 strict（0 错误）

`tsconfig.app.json` 加入 `"strict": true`。

**结果：现有代码 0 类型错误。** 这并非"没生效"，我用哨兵文件反向验证过门禁确实在工作——临时插入两个典型违规：

```
src/__strict_sentinel.ts(2,51): error TS18047: 's' is possibly 'null'.      ← strictNullChecks
src/__strict_sentinel.ts(3,34): error TS7006: Parameter 'v' implicitly has an 'any' type.  ← noImplicitAny
```

哨兵验证后已删除。现有代码之所以零错误，是因为此前已习惯性使用 `??` 兜底与 `isApiError` 类型守卫，补 `strict` 只是把隐性纪律变成编译期强制。

同时用 `tsc -p tsconfig.app.json --showConfig` 确认最终生效值确为 `"strict": true`。

### 3.2 P3-1 移除死依赖

`pnpm remove @tanstack/react-table`。移除前已确认：`src/` 下该包**仅有一处注释提及**（`DataTable.tsx` 说明"刻意用轻量自建列模型"），零真实引用，移除安全。

### 3.3 P3-2 编辑器 chunk 拆分与瘦身（重点）

分两步，第二步是真正的体积优化：

**第一步：物理隔离**（`vite.config.ts` 的 `manualChunks`）
把编辑器生态（`@uiw/`、`@codemirror/`、refractor、remark/rehype/micromark 链）归入独立 `md-editor` chunk。

- `ArticleFormPage`：**1.06 MB → 8.79 kB**
- 文章列表、仪表盘等页面不再被迫携带编辑器重量（报告 P3-2 的核心诉求达成）

**第二步：定位并消除真正的体积浪费**

隔离后 chunk 仍有 1,059.87 kB，我没有停在"已隔离"就交差，而是继续归因，发现根因：

> `rehype-prism-plus` 的默认入口**同时** import 了 `refractor`（36 种常用语言）与 `refractor/all`（**297 种全量语言**），而它的 `default` 导出用的正是全量版——于是 abap、agda、apl 这类在中文技术博客里永远不会出现的语法定义，全部进了产物。

处理方式：新增 `build/refractor-languages.ts`，用 vite alias **只顶替 `refractor/all`**，换成"common 36 种 + 补齐 5 种"的语言集。

> **为什么不是直接用官方 common 集**：实测发现 common 里**没有 jsx / tsx**——本项目是 React 技术栈后台，文章里 jsx/tsx 代码块出现频率极高，直接用 common 会让高亮**静默失效**。故补齐 `jsx / tsx / nginx / docker / http`。
>
> 另外确认 `html` 无需单独注册：markup 语法自带 html 别名（`Prism.languages.html = Prism.languages.markup`），```html 可正常高亮。

产物验证（grep 语言名标识符）：

| 语言 | 出现次数 | 说明 |
|---|---|---|
| `jsx` / `tsx` | 120 / 6 | ✅ 已打包 |
| `nginx` / `docker` | 2 / 7 | ✅ 已打包 |
| `abap` / `agda` / `apl` | 0 / 0 / 0 | ✅ 冷门语言已剔除 |

**体积结果：**

| 指标 | 整改前 | 整改后 | 变化 |
|---|---|---|---|
| md-editor chunk | 1,059.87 kB | **563.94 kB** | **-46.8%** |
| md-editor (gzip) | 363.46 kB | **180.24 kB** | **-50.4%** |
| ArticleFormPage | 1.06 MB | **8.79 kB** | -99% |
| 打包模块数 | 3,156 | **2,849** | -307 |

### 3.6 P3-5 补测试与 CI

**测试框架**：vitest 4.1.11，`environment: 'node'`（无需 DOM，更快、且 fetch/Headers 用 Node 原生实现更贴近真实）。配置复用 `vite.config.ts` 的 alias，避免两套解析逻辑漂移。

**28 个冒烟测试，精确覆盖审阅点名的四条关键路径：**

| 测试文件 | 用例数 | 覆盖路径 |
|---|---|---|
| `src/lib/permission.test.ts` | 10 | 能力判定 + `canOperateOwned` 归属越权（含匿名、无主资源边界） |
| `src/lib/request/envelope.test.ts` | 7 | 信封解析（code 0 / 业务码 / 非 JSON / 缺 code / 断网 / query 清洗） |
| `src/lib/request/refresh.test.ts` | 3 | **401 并发刷新去重**（3 个并发 401 只打 1 次 refresh）、新令牌落内存、不落 localStorage |
| `src/api/articles.test.ts` | 4 | 分页 `list` 消费 + 反向断言无 `items`/`total` 平铺 |
| `src/lib/request/helpers.test.ts` | 4 | `fileUrl` 不补 `/api/v1` 前缀（历史踩坑点） |

其中 401 并发去重这条最值得说：刷新令牌是**旋转**的，并发不去重会导致第一个请求换走令牌、后续全部失败、用户被莫名踢出。这类 bug **只在并发窗口内复现**，手工点页面几乎撞不上——测试里给刷新接口加了 20ms 延迟以撑开并发窗口，确保断言稳定。

**CI**：新增 `.github/workflows/manage-frontend-ci.yml`，仅前端子目录变更时触发，串联 lint / typecheck / test / build。

> CI 用 `biome check .`（只读）而非本地的 `check --write`。这当场抓到了 2 处 import 排序问题——本地 `--write` 会自动改掉、永远"看起来是绿的"，这类问题只有只读门禁才拦得住。已修复。

### 5.1 ✅ 编辑器 chunk 563.94 kB 超告警线 —— 裁决：接受，不改

**owner 裁决**：确定没问题。作为文章系统，包含一个优质的编辑器是必要项。

剩余体积构成是 CodeMirror + 41 语言 Prism + remark/rehype 解析链，**全部是编辑器功能本体**，已无可继续剥离的冗余——这也是本轮"先瘦身再判断是否接受"的意义所在：能省的（297 种语言里的 256 种）已经省掉，剩下的都是功能成本。

**这是一次主动取舍，不是遗留缺陷：**

| 指标 | 数值 | 影响面 |
|---|---|---|
| md-editor chunk | 563.94 kB（gzip 180.24 kB） | 仅编辑页 |
| 加载时机 | 路由级懒加载 | 进入 `/articles/new`、`/articles/:id/edit` 才下载，且仅一次 |
| 首屏 / 列表页 | 无影响 | 主入口 index chunk 379.24 kB 与之无关 |

已知代价：`vite build` 每次会打印一条 >500 kB 的 advisory 告警。该告警为提示性质，**不阻断构建、不影响产物正确性**。

> **可选（未执行，待 owner 决定）**：若想消除这条已接受的噪音，可在 `vite.config.ts` 调高 `build.chunkSizeWarningLimit` 至 700 并附注释说明"编辑器体积已评估并接受"。
> 我**未擅自调整**——不经说明地抬高阈值等同于把告警藏起来，这与本轮"不掩盖问题"的处理原则相悖。只有在配置里写明原因的前提下，它才是正当的工程动作。需要的话我可以补上。
