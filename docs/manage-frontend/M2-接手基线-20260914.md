- **文章是产品，代码是素材**。实现深度以能讲清技术决策、形成可复现文章为准。
- M1 后端已封版；M2 管理后台尚未由用户确认定型。历史日志中的“全系列收官”表示当时开发批次完成，不能代替用户验收。
- API 单一事实源：`docs/api/openapi.v1.yaml`，版本 `1.11.0`。历史计划、审阅意见与实现有出入时，先核实契约，不据旧计划直接改代码。
- 沿用 `docs/manage-frontend/开发规范.md`：文档归本目录；手写函数用箭头函数；文件头及函数 TSDoc；单文件原则上不超过 200 行，例外需说明。
- 用户自管 git 提交。后续选型、取舍、踩坑应留下记录，为 M2 文章提供素材。

角色为 `member/editor/admin`；文章状态 `draft/pending/published`；评论状态 `approved/rejected/reviewing`。分类虽为递归树，契约明确最大深度 4。`GET /me/likes` 按现有契约返回裸数组消费，不能套普通分页模型。

## 5. 后续启动与验证入口

在 `node-backend/` 运行 `pnpm dev:local`，默认端口 11000；脚本会准备本地目录并执行种子步骤，应先确认本地数据库用途。在 `manage-frontend/` 运行 `pnpm dev`，固定端口 12000，默认将 `/api/v1` 与 `/files` 代理至 `http://localhost:11000`。

`API_TARGET` 可覆盖前端代理目标。现有 `scripts/e2e-contract-check.mjs` 默认指向线上，且会注册用户、写入业务数据并生成报告；后续复跑必须显式指定测试后端。优先使用隔离本地数据，避免把默认线上目标当成无副作用测试入口。

## 6. 下一轮建议范围

以文章写作流程作为首个定型切片，先做浏览器走查，再对确认的问题做小步修改：

- 新建草稿 → 设置分类、封面、标签 → 发布 → 再编辑 → 返回列表，验证成功、失败与重复点击反馈。
- 验证浅色／深色、小视口、Tab 切换与图片粘贴上传的实际体验。
- 验证离开页面的稿件保护：当前只看到自定义返回按钮确认，未见 `beforeunload` 或路由 blocker；侧栏导航、浏览器返回和刷新需分别测试。
- 验证详情加载失败与数据重新获取：当前表单依赖 `article` 变化调用 `reset`，需检查错误状态和未保存编辑是否可能被回填覆盖。此项为读码关注点，尚未复现。
- 核对既有文章不同状态、不同角色下保存／发布的语义；页面的分类必填属于 UI 决策，应与产品意图一起确认。
- 当前文章页 315 行，超过规范默认上限，文件头未解释超长例外；功能调整时按职责拆分，避免仅为行数机械拆文件。

本次只建立基线，不将以上关注点直接定性为已复现缺陷，也不把历史待办自动转为本轮开发范围。
