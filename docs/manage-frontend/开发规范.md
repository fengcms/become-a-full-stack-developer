# M2 管理后台前端开发规范

> 适用范围：`manage-frontend/`（M2 React 管理后台）全部手写源码与文档。
> 本规范由首波骨架评审后（2026-08-29）根据用户要求确立，第一波代码已据此回炉。

---

## 0. 文档归位（铁律）

**所有与 `manage-frontend` 相关的文档，一律写在 `docs/manage-frontend/` 目录下**，不得散落到仓库根、`docs/` 根、`.workbuddy/` 或任意其他位置。

- 联调报告、设计取舍、这篇规范、后续每篇模块的设计说明，都放这里。
- 代码注释（文件头 / 函数 TSDoc）是代码的一部分，不是「文档」，不受此条约束。

---

## 1. 函数一律用箭头函数

**禁止 `function` 声明式写法**，全部用 `const fn = (...) => {...}`（含 `export`）。

```ts
// ❌ 不要这样
export function listArticles(query: Query): Promise<ArticlePage> { ... }
function buildUrl(path: string): string { ... }

// ✅ 要这样
export const listArticles = (query: Query): Promise<ArticlePage> => { ... }
const buildUrl = (path: string): string => { ... }
```

React 组件同样适用：

```tsx
// ❌
export default function LoginPage() { ... }
export function PageHeader({ title }: Props) { ... }

// ✅
const LoginPage = (): JSX.Element => { ... }
export default LoginPage

export const PageHeader = ({ title }: Props): JSX.Element => { ... }
```

**注意事项**

- 箭头函数是 `const`，**不会提升**。被依赖的函数要写在依赖方之前（或至少保证调用发生在模块初始化完成之后——我们的函数体引用都是运行时调用，顺序通常无所谓，但可读性上「被调用者在前」）。
- 组件若带泛型，`.tsx` 里写 `<T,>` 规避 JSX 歧义：`const List = <T,>(p: Props<T>) => {...}`。
- 类（如 `ApiError`）可以保留 `class`，类内方法按方法语法写——本规范只约束「独立函数」。
- 生成类代码（见 §5 豁免清单）不受此条约束。

**为什么**：统一写法、可预测的词法 `this`、便于 `export const` 与 `React.memo` 组合、与团队既有风格一致。

## 2. 文件头注释

**每个源文件顶部必须有说明性注释**，讲清「这个文件是干什么的 / 属于哪个模块」。

推荐统一格式（JSDoc 风格的 `@file` 块）：

```ts
/**
 * @file src/lib/request/core.ts
 * @description 请求内核：拼 URL、带令牌、拆统一信封、401 静默刷新与重放。
 * @module manage-frontend/lib
 * @date 2026-08-29
 */
```

- `.tsx` 页面/组件同理。
- 类型文件（`types/*.ts`）同样要有，说明该层职责（如「业务类型别名层，溯源 api.gen」）。
- 生成/第三方文件（见 §5）需保留一个来源说明头，标注「生成件，勿手改」。

---

## 3. 函数级 TSDoc

**每个函数（无论导出还是内部）都必须有 TSDoc 注释**（`/** ... */`），至少说明用途；带参数/返回的要写 `@param` / `@returns`。

```ts
/**
 * 后台文章列表。
 *
 * @param query - 分页与筛选条件；status 支持 draft/pending/published。
 * @returns 分页结果，形状为 `{ list, pagination }`。
 */
export const listAdminArticles = (query: AdminArticleQuery = {}): Promise<ArticlePage> => {
  return http.get<ArticlePage>('/admin/articles', { query })
}
```

约定：

- 端点类函数：注释里写清契约路径与角色（`GET /admin/articles（editor+）`）。
- 判定类函数（权限/角色）：注释里写清对应的契约 `x-authz` 端点，便于改前查契约。
- 内部工具函数：说明坑点（如 `fileUrl` 的 `/files` 挂在根路径陷阱）。
- 不强制 `@example`，但与「坑」相关的要写 `@warning`/`⚠️`。

---

## 4. 单文件 ≤ 200 行

**单个源文件不超过 200 行（含注释与空行）。**

- 超过则**拆分**为职责单一的小文件，而非堆长文件。
- 确属高内聚不可分割的整体（如请求内核、单一巨型表单），可超 200，但**必须在文件头用注释说明原因**，例如：
  ```ts
  /**
   * @file src/lib/request/core.ts
   * @description 请求内核（高内聚，拆分会引入循环依赖，故整体保留；已压缩至最小）。
   * ...
   */
  ```

配套原则：**页面组件尽可能分离，单文件单职责**。

- 一个页面文件只承载「这一页」。表单、子区块、复用卡片拆成独立组件文件。
- 错误页 / 状态页各自成文件，不塞在一个 `StatePages.tsx` 里。
- 路由表（`router/index.tsx`）作为「目录」，允许较长（它只是声明），但不把页面逻辑写进去。

## 5. 豁免清单（生成 / 第三方资产）

以下文件**不强制**遵守 §1（箭头函数）、§3（函数 TSDoc），但**必须**满足 §2（文件头）与 §4 的「超长需注释」：

| 路径 | 原因 | 处理 |
|---|---|---|
| `src/components/ui/*` | shadcn-ui CLI 生成的基础组件，沿用上游 `function` + `React.forwardRef` 写法 | 仅保留来源头；改动走 `shadcn add`，勿手改 |
| `src/types/api.gen.ts` | `openapi-typescript` 从契约机器生成，手改会被覆盖 | 仅保留生成头；类型改动改契约后重新生成 |
| `src/vite-env.d.ts` | Vite 注入的环境类型声明 | 仅保留来源头 |

> 除以上三类，其余 `src/` 下文件**全部**适用 §1–§4。

## 7. 目录约定（速查）

```
manage-frontend/src/
├── api/          # 契约端点 → 带类型函数（不碰状态/UI/toast）
├── components/   # 复用组件（ui/ 为 shadcn 生成件，feedback/·layout/ 为业务组件）
├── config/       # 菜单、角色等静态配置
├── hooks/        # React Query 封装（api + queryKey 绑定）
├── layouts/      # 后台主框架（AdminLayout 拆为 Sidebar/Topbar）
├── lib/          # 请求内核、错误码、权限判据、工具
├── pages/        # 页面（单文件单职责，子组件另拆）
├── router/       # 路由表 + 守卫
├── store/        # Zustand 状态（auth 仅内存 / ui 可持久化）
└── types/        # 业务类型别名层（溯源 api.gen）
```
