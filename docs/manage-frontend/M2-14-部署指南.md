# M2 管理后台 · 部署指南（M2-14）

> 产物：`pnpm build` → `dist/`（纯静态资源，无服务端渲染）。
> 后端已部署到 Cloudflare：`https://api-befull.kao9.com/api/v1`（契约 v1.11.0，全链路验收 GREEN）。
> 本指南只讲**前端静态托管**，不涉及后端 Worker 部署（见 `docs/node-backend/部署到Cloudflare指南.md`）。

---

## 0. 关键事实（部署前必读）

| 项 | 值 | 说明 |
|:---|:---|:---|
| 前端基址 | 视托管平台而定（如 `https://admin.kao9.com`） | `vite.config.ts` 默认 `base: '/'`；若挂子路径（如 `/admin`）须改 `base` 并重跑 `build` |
| 后端 API | `https://api-befull.kao9.com/api/v1` | 生产环境**不走 Vite 代理**（那是 dev 专用） |
| 附件根路径 | `https://api-befull.kao9.com/files/<key>` | 契约 `Attachment.url = /files/<key>` 挂在后端**根路径**，不带 `/api/v1`（见 FAQ） |
| 鉴权 | accessToken 存内存；refresh 走 HttpOnly+SameSite=None Cookie | 生产必须 HTTPS，Cookie 才回传（dev http 不回传是已知限制） |
| SPA 回退 | 所有非资源路径 → `index.html` | 否则刷新 `/articles` 等深链 404 |

> ⚠️ **CORS 方案 B 是 dev 专用**：本地 `vite.config.ts` 的 `/api/v1`、`/files` 代理只为绕开 dev CORS。生产静态托管**没有这个代理**，必须由托管层做反代，或后端把前端域名加入 `CORS_ORIGINS`。两条路二选一，见 §2 / §3。

## 1. 通用步骤（两种平台都适用）

```bash
# 1) 安装依赖（项目锁定 pnpm@9.4.0）
pnpm install

# 2) 类型检查 + 构建（门禁全绿才部署）
pnpm typecheck && pnpm build
#   → 产物落在 dist/

# 3)（可选）产物体积复盘，生成 dist/stats.html treemap
pnpm analyze
```

构建产物 `dist/` 内容：

```
dist/
├── index.html              # SPA 入口，含 <script type=module> 引导
├── assets/
│   ├── index-*.js          # 共享 vendor（react/router/query 等）
│   ├── md-editor-*.js      # Markdown 编辑器（仅文章编辑页按需加载）
│   ├── DashboardPage-*.js  # 仪表盘（含 recharts，仅 /dashboard 按需）
│   └── ……                  # 其余业务页均为独立懒加载 chunk
└── stats.html              # 仅 ANALYZE=1 时生成，体积分析用
```

## 2. 方案 A · Cloudflare Pages（推荐，与后端同生态）

### 2.1 构建配置

| 字段 | 值 |
|:---|:---|
| 构建命令 | `pnpm build` |
| 构建输出目录 | `dist` |
| 根目录 | `manage-frontend` |
| 环境变量 | 无（前端不内置后端地址，运行时由托管层反代） |

### 2.2 SPA 路由回退（关键）

Cloudflare Pages **默认只对含文件扩展名的请求回退到 404**，深链 `/articles/new` 会 404。两种修复：

**方式一：`_routes.json`（仅静态回退，无法反代 API）**

在 `dist/` 放 `_routes.json`（构建后手动加，或放 `public/_routes.json` 让它随构建拷贝）：

```json
{
  "version": 1,
  "include": ["/*"],
  "exclude": ["/api/*", "/files/*", "/assets/*", "/*.*"]
}
```

> 这样所有页面深链回退 `index.html`。但** API 与附件仍需浏览器直连后端域名** → 走方案 B 的 CORS（后端加 `CORS_ORIGINS`）。

**方式二：`_redirects` + 反代（推荐，彻底同源）**

CF Pages 支持 `_redirects` 做 200 回退 + 用 Cloudflare 的 **SNI/Transform Rules** 或 **Pages Functions** 反代 `/api/v1`、`/files` 到后端。最简是 Pages Functions：

```
# public/_routes.json 仍负责 SPA 回退
# public/functions/api/v1/[[route]].js —— 把 /api/v1/* 反代到后端
export async function onRequest(context) {
  const url = new URL(context.request.url)
  const target = 'https://api-befull.kao9.com' + url.pathname + url.search
  return fetch(target, {
    method: context.request.method,
    headers: context.request.headers,
    body: context.request.body,
  })
}
```

> 反代后前端用**相对路径** `/api/v1`、`/files` 即可，无需后端开 CORS（同源），Cookie 刷新分支（契约里有，dev 无实测）也在生产 HTTPS 下自然生效。附件同理加 `public/functions/files/[[key]].js`。

### 2.3 缓存策略

- `assets/*`（带内容哈希）→ `Cache-Control: public, max-age=31536000, immutable`（CF 默认给哈希资源长缓存）。
- `index.html` → `Cache-Control: no-cache`（每次校验最新），确保发版即时生效。

## 3. 方案 B · Nginx（自托管 / 内网）

```nginx
server {
    listen 443 ssl;
    server_name admin.kao9.com;

    # 静态资源（带哈希，长缓存）
    location /assets/ {
        root /var/www/manage-frontend/dist;
        expires 1y;
        add_header Cache-Control "public, immutable";
    }

    # 后端 API 反代（同源，免 CORS）
    location /api/v1/ {
        proxy_pass https://api-befull.kao9.com/api/v1/;
        proxy_set_header Host api-befull.kao9.com;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        # 透传 Set-Cookie（HttpOnly refresh Cookie 必须落到前端域名下）
        proxy_pass_header Set-Cookie;
    }

    # 附件反代（契约 /files 在后端根路径，不带 /api/v1）
    location /files/ {
        proxy_pass https://api-befull.kao9.com/files/;
        proxy_set_header Host api-befull.kao9.com;
    }

    # SPA 回退：所有非资源路径交给 index.html
    location / {
        root /var/www/manage-frontend/dist;
        try_files $uri $uri/ /index.html;
    }
}
```

> `try_files $uri $uri/ /index.html` 是 SPA 回退核心：刷新深链不再 404。
> 反代 `/api/v1` 与 `/files` 后，前端请求走相对路径即可，**后端无需开 CORS_ORIGINS**。

## 4. 部署后验证清单

- [ ] 打开首页 → 重定向 `/login`，登录后进入 `/dashboard` 正常。
- [ ] 刷新任意深链（如 `/articles/new`）→ 不 404（SPA 回退生效）。
- [ ] 登录后调 `/api/v1/*` → 网络面板看到的是同源 `/api/v1`（反代）或后端域名（CORS 方案），无 CORS 报错。
- [ ] 文章封面/头像等附件 `<img src="/files/...">` → 200 加载（反代或后端域名均可）。
- [ ] 刷新页面后**仍保持登录**（生产 HTTPS 下 HttpOnly refresh Cookie 回传；dev http 不回传是已知限制）。
- [ ] 编辑器页面（文章新建/编辑）首屏外才加载 `md-editor-*.js`（懒加载）。

## 5. FAQ

**Q1：为什么附件是 `/files` 而不是 `/api/v1/files`？**
契约 `Attachment.url` 定义为 `/files/<key>`（后端根路径），后端路由刻意挂在根（策略 A 中转）。前端用 `ORIGIN + url` 拼接，绝不能用 `API_BASE + url`，否则拼出 `/api/v1/files` 会 404。线上已复测 GREEN。

**Q2：dev 能登录、刷新后却要重登？**
dev 是 `http://localhost:12000`，后端 Set-Cookie 带 `Secure`，浏览器不回传 → 基于 Cookie 的静默恢复在 dev 不生效（方案 B 已知权衡）。生产 HTTPS 下正常。已在第四轮审阅登记为「上线前 checklist」。

**Q3：子路径部署（如 `/admin`）？**
改 `vite.config.ts` 的 `base: '/admin/'`，重跑 `build`，Nginx/CF 路由前缀同步加 `/admin`。

**Q4：构建报 `Some chunks are larger than 500 kB`？**
仅 `md-editor`（563.94 kB / gzip 180 kB）超线，属 owner 已裁决的主动取舍（文章系统须含优质编辑器）。其余业务页均 4–9 kB 懒加载。未擅自抬高 `chunkSizeWarningLimit`（避免藏问题）。
