# 链接与发布协作约定

> 本约定定义「统筹 AI（本项目内容/写作方）」与「blog AI（CSDN 发布/同步方）」之间的接口契约。
> 协作模式：**消费 blog AI 索引 + 自服务兜底**（2026-08-27 与 owner 确认）。

## 一、双方职责（接口契约）

| 角色 | 职责 | 产出 |
|---|---|---|
| **blog AI**（发布/同步方） | 你（owner）把文章发布到 CSDN 后，它运行同步脚本 | `materials/csdn-已发布链接.md`（全站 标题→URL 索引，单一真相源） |
| **统筹 AI**（内容/写作方，即本项目） | 只读消费上述索引，把本系列 URL 镜像进 `ARTICLES.md`；用于文章内链 | `ARTICLES.md` 的 CSDN 链接列 + 文章内链 |

## 二、链接真相源机制（已存在，无需新建）

- blog AI 的工作目录：`/Users/fungleo/Documents/Blogs`
- 同步脚本：`csdn_backup.py`（**公开抓取、无需登录**，经 CSDN 官方 RSS 接口枚举全量文章，幂等增量）
- 两个关键产物：
  1. `old-blogs/{articleId}.md` — 每篇已发布文章的备份，frontmatter 含 `original_url`（发布链接）
  2. `materials/csdn-已发布链接.md` — 由 `python csdn_backup.py links` 生成的**聚合索引**（标题→URL，按系列分组）
- 本系列（标题以「成为全栈」开头）发布后会出现在该索引中（当前归在「其他」分组，但不影响检索）。

## 三、标准流程（每批发布后）

1. owner 把一批文章发布到 CSDN。
2. 通知 blog AI 跑 `python csdn_backup.py run` + `python csdn_backup.py links`，刷新 `materials/csdn-已发布链接.md`。
3. 统筹 AI 读取该索引，grep 含「成为全栈」的行，提取本系列各篇 URL。
4. 把 URL 回填 `ARTICLES.md` 的「CSDN 链接」列（置 🟢），并执行内链注入（见下）。
5. **打 git 里程碑 tag（规范见第八节）**：**不再按「每篇文章」打 tag**，而是按**代码库里程碑**打——契约冻结、各端（后端/前端/移动端）代码定稿时，打 `contract-v1.11.0`、`node-backend-v1.0` 等。M0 产品侧文章不对应独立代码库，**不打 tag**。具体规范见第八节。

## 四、自服务兜底

若索引过期而我方急需链接，可**自行运行同款脚本刷新**（owner 已授权；脚本公开、幂等、无登录）：

```bash
python /Users/fungleo/Documents/Blogs/csdn_backup.py links
```

刷新后按第三节第 3–4 步消费。此兜底仅为避免被卡，主路径仍优先由 blog AI 维护索引。

## 五、内链占位约定

文章**先写后发**，内链需要真实 URL，故采用占位注入法：

- 写作时，兄弟篇互链用稳定占位符：`{{LINK:Mx-yy}}`（如 `{{LINK:M0-01}}`），**不写裸 URL**。
- 整批发布 + 索引刷新后，统筹 AI 跑**一次链接注入**：读索引 → 将每个 `{{LINK:Mx-yy}}` 解析为真实 URL 并替换。
- 解析依据：`ARTICLES.md` 的「文章标题」列 + 索引的「标题→URL」做 join；标题由我方控制、唯一，匹配稳定。

## 六、ARTICLES.md 的定位

`ARTICLES.md` 是**项目侧**的「标题 ↔ tag ↔ 代码 ↔ URL」映射表（M0-06 公约要求）。其中「CSDN 链接」列是本系列 URL 的**镜像**，真相源仍在 blog AI 的 `materials/csdn-已发布链接.md`。

## 七、可选润色（非必需）

blog AI 的 `gen_links()` 当前把本系列归「其他」组、且不进其 MEMORY 同步段。不影响我方 grep 检索；若希望索引里本系列有独立分组，可请 owner 转告 blog AI 在 `_series_of()` 增加「成为全栈」匹配规则。

## 八、git tag 约定（里程碑式，2026-08-27 与 owner 重订）

> 原约定「每篇文章打 `article/Mx-yy`」已废止——它对 M0（不对应独立代码库）无意义，且把「文章索引」与「代码里程碑」混淆。改为**里程碑式 tag**。

- **核心原则**：tag 只标记「代码库真正跨过一个阶段」的节点，命名直接表达「哪个端、什么状态」。整个项目生命周期约十来个 tag，每个对应一个可运行交付物，语义清晰、不会乱。
- **命名规范**：`<里程碑>-v<主版本>`，例如：
  - `contract-v1.11.0` —— API 契约冻结（地基锁定）
  - `node-backend-v1.0` —— M1 Node 后端正式冻结
  - `go-backend-v1.0` / `react-frontend-v1.0` / `next-frontend-v1.0` / `vue-frontend-v1.0` / `flutter-mobile-v1.0` / `taro-mobile-v1.0` —— 各端代码冻结
  - `final-v1.0` —— 全系列收官
- **M0 产品侧不打 tag**：M0 文章不对应独立代码库（见 `ARTICLES.md`），无需 tag；文章发布后只回填链接（见第三节），不触发打 tag。
- **触发时机**：在「该里程碑代码定稿并已提交」的提交上打，通常是该阶段收尾提交（即 HEAD 或就近提交）。**不是发布前动作，也不是每篇发布后动作**。
- **禁止**：① 为「先占个位」提前打 tag；② 把 tag 当文章索引用（per-article tag 已废止）。
- **命令**：`git tag <name> [<commit>]`；推远端 `git push origin <name>`。
- **历史补打**：里程碑若漏打，可事后在对应定稿提交上补打（tag 只是指针，不改写历史）。
