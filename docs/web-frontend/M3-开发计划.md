## 1. 技术约束（强制）

1. **包管理器**：全程 `pnpm`（用户硬规则）。
2. **箭头函数**：所有独立函数与组件一律用箭头函数（`const fn = () => {}`），禁用 `function` 声明式（用户硬规则 + 继承 M2 规范）。
3. **禁止内联样式**：所有样式走 Tailwind 类或 CSS 文件，不写 `style={{}}`（用户硬规则）。
4. **文档归位**：本计划与所有 M3 文档只写在 `docs/web-frontend/`。
5. **契约唯一真相**：端点/字段/错误码以 `docs/api/openapi.v1.yaml`（v1.11.0）为唯一来源；改动先改契约再改实现。
6. **后端已冻结**：前端只消费，发现契约缺口记「差异表」交后端 AI，不自行改后端。
7. **门禁强制**：每阶段结束 `pnpm typecheck` + `pnpm lint` + `pnpm build` 全绿再进下一阶段。
8. **先 curl 实测后编码**：对接每个新端点先 curl 对齐字段，差异入差异表。
9. **单文件 ≤ 200 行**：超限时拆分，例外须在文件头注释说明（继承 M2 规范）。
10. **文件头注释 + 函数级 TSDoc**：每个源文件顶部 `@file` 注释，每个函数带 TSDoc（继承 M2 规范）。

## 2. 技术栈选型（全部使用最新稳定版）

> 版本核查日期：2026-09-16。搭建时以 `pnpm add <pkg>@latest` 安装，确保拿到最新稳定版。

| 维度 | 选型 | 最新版本 | 理由 |
|:---|:---|:---|:---|
| 框架 | **Next.js（App Router）** | **16.3.x**（Active LTS） | 路线图 M3 明确指定；16.x 稳定 Turbopack、Cache Components（`"use cache"`）、React 19.2、Proxy（`proxy.ts` 替代 middleware）；M3-01/M3-03 核心讲点 |
| 语言 | **TypeScript（strict）** | **5.x**（Next 16.3 支持 TS 7） | 与 M1/M2 一致，契约类型生成的前提 |
| 样式 | **Tailwind CSS** | **4.3.x** | v4 是当前主线，性能大幅提升（CSS-first 配置、`@import "tailwindcss"`）；与 M2 一致 |
| UI 组件 | **shadcn/ui（Radix + Tailwind）** | latest | 与 M2 一致，可直接复用 button/card/dialog/dropdown 等基础件；前台按需 add，不整包引入 |
| 类型生成 | **openapi-typescript** | latest | 从 openapi.v1.yaml 生成 `types/api.gen.ts`，避免手写漂移（M3-04/M2-04 讲点） |
| 数据获取 | **RSC `fetch`（服务端）+ TanStack Query（客户端互动）** | latest | 公开内容走 RSC 直连 + 缓存；点赞/收藏/评论等互动走客户端 Query；M3-04 讲缓存层级 |
| Markdown 渲染 | **react-markdown + remark/rehype + rehype-pretty-code（shiki）** | latest | 服务端渲染（M3-06 讲构建时 vs 运行时取舍）；代码高亮选 shiki 引擎（语法全、暗色友好） |
| 表单 | **react-hook-form + zod** | latest | 与 M2 一致，会员中心表单复用 |
| 认证 | **HttpOnly Cookie（refresh）+ 内存 access token** | — | 与 M2 鉴权闭环一致；M3-08 讲 C 端登录态设计 |
| 反向代理 | **Next.js Route Handlers / rewrite** | — | 浏览器端通过同域 Route Handler 转发到后端，规避 CORS + 隐藏后端地址（M3-20 讲边界） |
| 部署 | **Cloudflare Workers + `@opennextjs/cloudflare`** | latest | 后端 M1 已在 Cloudflare（Hono+D1+R2），前台同网上 Cloudflare Workers 低延迟；OpenNext 适配器把 Next.js 构建产物转成 Workers 可执行格式，支持 Next.js 16 全部特性（App Router/RSC/ISR/Route Handlers） |
| 代码规范 | **Biome** | latest | 与 M2 一致，替代 ESLint+Prettier |
| 状态管理 | **Zustand（仅 UI/会话态）** | latest | 服务端态走 RSC/Query，不滥用全局 store；M2-05 三类状态原则延续 |

> **说明**：M3 不引入额外的状态管理库（如 Redux）。RSC 本身承担大部分「服务端状态」，客户端仅保留会话 token、UI 开关等轻量态。
>
> **Next 16 关键变化注意**：
> - `middleware.ts` → `proxy.ts`（网络边界更清晰，M3-20 讲点）。
> - 缓存从隐式改为显式（Cache Components，`cacheComponents: true` + `"use cache"`），默认动态执行，避免旧版隐式缓存的反直觉行为；M3-04 讲。
> - `async params`：页面 `params` 现在是 Promise，需 `await`。
> - 构建默认走 Turbopack，开发内存占用大幅降低。

> **Cloudflare Workers 部署约束（M3-13 讲点）**：
> - **运行时**：`workerd`（V8 隔离）+ `nodejs_compat` 标志，非完整 Node.js；**全程使用 Node.js runtime，禁止 `export const runtime = "edge"`**（OpenNext 在 Node 模式下支持最完整）。
> - **资源上限**：单 isolate 固定 128MB 内存；Worker 压缩包 ≤ 3MB（免费）/ 10MB（付费）。Markdown/shiki 等体积大头必须在**服务端渲染**，不进客户端 bundle。
> - **ISR 缓存**：用 R2 bucket（`NEXT_INC_CACHE_R2_BUCKET` 绑定）做增量缓存，避免 Workers 无持久磁盘的局限。
> - **图片优化**：走 Cloudflare Images（`IMAGES` 绑定），不用 Next.js 默认的 sharp（workerd 不支持原生模块）。
> - **环境变量**：构建时变量走 `process.env`，运行时绑定（D1/R2/KV）走 `getCloudflareContext().env`；两者分开设置，本地用 `.dev.vars`。
> - **与后端同网**：M1 后端已部署在 Cloudflare Workers，前台 Route Handler 反代后端走 Cloudflare 内网，延迟极低，无需公网回源。

### Phase 2 · 渲染策略与缓存（M3-02, M3-04）

**目标**：确立各页面的渲染模式与缓存策略。

| 页面 | 渲染模式 | 缓存策略 | 理由 |
|:---|:---|:---|:---|
| 首页 | SSG（revalidate: 1h） | `force-cache` + tag `articles` | 内容低频变，CDN 友好 |
| 文章列表 | SSG（revalidate: 10min） | `force-cache` + tag `articles` | 分页参数进 URL，缓存粒度按页 |
| 文章详情 | ISR（revalidate: 5min） | `force-cache` + tag `article:{id}` | 详情更新不频繁，ISR 平衡 |
| 分类/标签页 | SSG（revalidate: 1h） | `force-cache` + tag `categories`/`tags` | 结构稳定 |
| 会员公开主页 | ISR（revalidate: 10min） | `force-cache` + tag `member:{id}` | 公开内容 |
| 搜索 | SSR（动态） | `no-store` | 关键词不可预生成 |
| 会员中心 | SSR（动态） | `no-store` | 个人数据需实时 |

**交付物**：`lib/cache.ts`（统一 revalidate/tag 封装）、各页面 fetch 调用、`lib/api/*` 端点函数。

**出口**：文章列表/详情用静态数据可渲染，构建产物含静态 HTML。

### Phase 5 · 会员认证（M3-08, M3-20）

**目标**：C 端登录态闭环。

| 能力 | 端点 | 实现 |
|:---|:---|:---|
| 注册 | `POST /auth/register` | 注册页 + 表单 |
| 登录 | `POST /auth/login` | 登录页 + 表单；access token 存内存，refresh 走 HttpOnly Cookie |
| 刷新 | `POST /auth/refresh` | 请求内核 401 拦截，并发去重（继承 M2 方案） |
| 登出 | `POST /auth/logout` | 清内存 token + 后端清 Cookie |
| 当前用户 | `GET /auth/me` | 启动时静默拉取，写入 Zustand |
| 登录守卫 | — | `(member)` 路由组 middleware 或布局层判定，未登录跳登录 |

**关键设计**：
- 浏览器端 refresh token 走 Cookie（后端 Set-Cookie HttpOnly+SameSite=None+Secure），前端不触碰。
- access token 存 Zustand 内存（页面刷新丢失，借 refresh 续期）。
- 反代 Route Handler 自动转发 Cookie，浏览器无感。

**出口**：注册→登录→访问会员中心→刷新页面仍登录→登出，全链路通。

## 7. 与 M2（管理后台）的复用与差异

| 维度 | M2（Vite+React SPA） | M3（Next.js RSC 优先） |
|:---|:---|:---|
| 渲染 | CSR | RSC + SSR/SSG/ISR |
| 请求层 | `fetch` 封装 + 拦截器 | RSC 直连 `fetch` + 客户端 Query |
| 鉴权 | 内存 token + Cookie refresh | 同（继承 M2 方案） |
| 路由 | React Router | App Router 文件系统路由 |
| 样式 | Tailwind4 + shadcn | Tailwind 4 + shadcn |
| 部署 | 静态托管（CF Pages / Nginx） | Cloudflare Workers + OpenNext（与 M1 后端同网） |
| 设计语言 | shadcn new-york（后台工具风） | 极简编辑风（Medium/Substack 取向，C 端阅读优先） |
| 类型 | openapi-typescript 生成 | 同 |
| CORS | 需配跨域凭证 | 同域 Route Handler 反代，规避 |
| 状态 | Zustand + TanStack Query | RSC + Zustand（轻量）+ TanStack Query（互动） |
| SEO | 不适用（SPA） | metadata/sitemap/JSON-LD 全套 |

**可直接复用的思路**：请求内核设计、401 刷新竞态处理、权限判定逻辑（前台主要是「是否登录」+「是否作者本人」）、错误码映射、契约类型生成。

**必须重写的**：渲染模式、数据获取、路由、布局、SEO、所有页面（前台是 C 端展示，与后台管理页完全不同）。

## 8. 风险与待确认

| # | 风险/待确认 | 影响 | 处置 |
|:---|:---|:---|:---|
| R1 | **shadcn/ui 与 Next 16 + Tailwind 4 兼容** | shadcn 组件多为客户端组件 | 按需 add，使用时加 `'use client'`；不影响 RSC 主体；Tailwind 4 用 `@tailwindcss/postcss` |
| R2 | **后端反代策略**：同域反代还是直连后端 | CORS + Cookie 携带 | Phase 1 确定：Next.js Route Handler 反代（同域，Cookie 自动携带，隐藏后端地址） |
| R3 | **access token 跨页面刷新丢失** | 用户体验 | 启动时 `/auth/me` 静默拉取；失败则 refresh；refresh 失败跳登录 |
| R4 | **Markdown 渲染体积**：shiki 体积大影响构建 | 构建时长 | 服务端渲染，不进客户端 bundle；M3-06 讲取舍 |
| R5 | **第三方登录 OAuth 未实现**：后端按契约返回 500/code 5000（合法占位），但无法完成真实登录 | M3-09 无法联调真实 OAuth | 前端入口按 500/code 5000 提示"暂未开放"；待后端 OAuth 实现后联调；不阻塞主线 |
| R6 | **阅读量上报时机**：`POST /articles/{id}/view` 何时触发 | 防刷有效性 | 阅读满 N 秒（如 5s）后上报一次，不重复上报（前端节流） |
| R7 | **评论楼中楼递归深度** | 性能 | 限制最大展示层级（如 3 层），深层折叠为「查看更多回复」 |
| R8 | **Cloudflare Workers 资源限制**：128MB 内存 / Worker 体积 3MB(免费)/10MB(付费) / 无原生模块 | 构建失败或 OOM | Markdown/shiki 等大头走服务端渲染不进客户端包；不用 sharp，图片走 Cloudflare Images；构建后检查体积 |
| R9 | **OpenNext 与 Next 16 兼容性**：适配器对新特性的跟进 | 部分特性不可用 | 用 `@opennextjs/cloudflare`（社区活跃，支持 Next 16 全特性）；避开 Edge runtime，统一 Node.js runtime；遇阻查 [兼容性仪表板](https://opennext.js.org/cloudflare) |
| R10 | **契约类型生成**：openapi-typescript 对 v1.11.0 的兼容性 | 类型正确性 | Phase 1 实测生成，若有问题降级为手写关键类型 |
| R11 | **Next 16 破坏性变更**：`async params`、`proxy.ts`、Cache Components 默认动态 | 迁移成本 | Phase 1 搭建即按 16 规范写，不从旧版迁移；M3-01/03/04 讲清差异 |

## 9. 已确认决策

1. **部署目标**：**Cloudflare Workers + `@opennextjs/cloudflare`**（与 M1 后端同网，低延迟、单平台运维）。详见 Phase 9 与 §2 Cloudflare 部署约束。

## 10. 一句话总结

`web-frontend/` 从零搭建 **Next.js 16** App Router 工程，采用**极简编辑风**设计语言，以 RSC + SSG/ISR 为公开内容主轴、SSR 为会员中心主轴，通过同域 Route Handler 反代（与 M1 后端同处 Cloudflare 边缘网络）规避 CORS，鉴权继承 M2 的「内存 access + Cookie refresh」闭环，类型从已冻结契约 v1.11.0 生成，部署走 **Cloudflare Workers + `@opennextjs/cloudflare`**，按 15 个 Phase 串行推进（工程骨架→渲染缓存→文章系统→Markdown→会员主页→导航辅助→SEO→站点信息→认证→会员中心→通知→评论→搜索点赞→性能→部署复盘），每阶段门禁全绿，文档全程归位 `docs/web-frontend/`。
