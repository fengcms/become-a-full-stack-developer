# 分类页子分类文章聚合 — 方案分析

> 日期：2026-09-16
> 背景：访问 `/categories/frontend`（含子分类 React/Vue）时，页面返回 0 篇文章；实际文章挂在子分类下。

## 1. 现状

### 1.1 接口行为

`GET /api/v1/articles?category=frontend` 返回 `total=0`，而同分类树下的 `category=react` 返回 3 篇。

后端实现（`node-backend/src/services/article.ts:187`）：

```ts
if (q.category) conds.push(eq(articles.categorySlug, q.category));
```

仅按 `articles.category_slug` 精确等值匹配，**不展开子分类**。

### 1.2 契约描述

`docs/api/openapi.v1.yaml:142` 明确写道：

> 按分类 **slug** 精确匹配（非 id、非 name）。**不含子分类，只匹配该分类自身**

### 1.3 数据结构

- `categories` 表含 `parent_id` 自关联字段，支持无限级层级（契约约束最大深度 4）。
- `articles` 表冗余存储 `category_id` / `category_name` / `category_slug`（创建时从分类表反查补全）。
- 分类树接口 `GET /categories` 返回嵌套结构，前端可拿到任意节点的全部后代。

## 2. 调用方盘点

| 调用方 | 场景 | 传参 | 期望语义 |
|--------|------|------|----------|
| `web-frontend/categories/[slug]/page.tsx` | 前台分类页 | `category: slug` | **应包含子分类**（用户诉求） |
| `web-frontend/articles/page.tsx` | 前台文章列表筛选 | `category: sp.category` | 用户点选分类筛选，级联更符合直觉 |
| `node-backend/routes/articles-admin.ts` | 后台文章管理 | `category: query` | 按分类筛选，级联合理 |
| `manage-frontend/ArticleListPage.tsx` | 后台管理前端 | `category` | 同上 |

**结论：所有调用方都无强需求"只匹配自身"，级联语义对所有场景都更符合直觉。**

## 3. 方案对比

### 方案 A：前端聚合（不改契约、不改后端）

前端先调 `/categories` 拿树，递归收集当前分类 + 所有后代 slug，再逐个调 `listArticles({ category })` 合并。

- ❌ **分页语义破坏**：各分类独立分页后合并，`total` 与页码不准，无法实现正确翻页。
- ❌ **排序不全局**：各分类各自排序后拼接，整体顺序错乱。
- ❌ **N 次请求**：子分类越多请求越多，性能差。
- ❌ **去重复杂**：一篇文章只属一个分类，去重问题不大，但实现冗余。

**结论：不可行。**

---

### 方案 B：后端改语义为「级联包含子分类」（改后端 + 改契约描述）

`listArticles` 中 category 匹配改为：查出该分类及其所有后代分类的 slug 集合，用 `IN` 匹配。

```ts
if (q.category) {
  // 1. 查 slug 对应的分类
  // 2. 递归查所有后代分类（parent_id 链路，最大深度 4）
  // 3. 收集所有 slug
  // 4. inArray(articles.categorySlug, slugs)
}
```

同步更新契约描述为「匹配该分类及其所有后代子分类」。

- ✅ 分页、排序全局正确（单次 SQL）
- ✅ 一次请求，性能好
- ✅ 所有调用方语义统一，无需前端传额外参数
- ✅ 不改契约参数结构，仅更新描述 + 后端实现
- ⚠️ 需确认后台调用方接受级联语义（经盘点，均接受）

**结论：推荐。**

---

### 方案 C：新增参数 `categoryIncludeChildren`（改契约 + 改后端）

新增布尔参数控制是否级联，默认 `false` 保持现有语义。

- ✅ 不破坏现有语义
- ❌ 契约膨胀，需重新生成 `api.gen.ts`
- ❌ 前台分类页需传 `true`，后台保持默认，两处前端都要改
- ❌ 实际无调用方需要「只匹配自身」，参数无意义

**结论：过度设计，不推荐。**

---

### 方案 D：后端静默改语义，不改契约

同方案 B，但不更新契约文档。

- ❌ 契约与实现不一致，违反「契约优先」原则，后续易踩坑

**结论：不推荐。**

## 4. 推荐方案：B

### 4.1 实现要点

**后端 `services/article.ts`：**

```ts
// 替换原 eq(articles.categorySlug, q.category)
if (q.category) {
  const slugs = await resolveCategorySlugsWithDescendants(q.category);
  if (slugs.length === 0) {
    // 分类不存在 → 直接返回空
    return { list: [], pagination: meta(page, pageSize, 0) };
  }
  conds.push(inArray(articles.categorySlug, slugs));
}
```

**后代解析（应用层循环，分类数少、深度 ≤ 4，无需递归 CTE）：**

```ts
const resolveCategorySlugsWithDescendants = async (slug: string): Promise<string[]> => {
  const all = await getDb().select({ id, slug, parentId }).from(categories).all();
  const root = all.find((c) => c.slug === slug);
  if (!root) return [];
  const result = [root.slug];
  let parentIds = [root.id];
  // 最大深度 4，循环展开
  for (let depth = 0; depth < 4 && parentIds.length > 0; depth++) {
    const children = all.filter((c) => parentIds.includes(c.parentId ?? 0));
    result.push(...children.map((c) => c.slug));
    parentIds = children.map((c) => c.id);
  }
  return result;
};
```

**缓存注意**：`listArticles` 当前用 `force-cache` + `next.tags`。category 参数已在 serverFetch 的 cache key 中（URL query），级联后结果仍随 category 值区分，**缓存键天然正确**，无需额外处理。

### 4.2 契约更新

`docs/api/openapi.v1.yaml:142` 改为：

> 按分类 **slug** 匹配（非 id、非 name）。**包含该分类自身及其所有后代子分类**（级联）。

### 4.3 影响面

- **前端**：无需改动（`categories/[slug]/page.tsx` 已传 `category: slug`，后端级联后自动生效）。
- **后台**：语义变更，筛选「前端」会同时列出 React/Vue 下的文章——符合管理直觉，无需额外改动。
- **缓存**：无影响。
