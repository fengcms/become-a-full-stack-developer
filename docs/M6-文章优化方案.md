## 一、结论先行

**M6 与 M5 同病，但更重。** 两个系列的病根一样——**代码密度不足**；但 M6 的缺口比 M5 大一档：**18/33 篇正文一个代码块都没有**，全靠文字描述实现。

**M6 不需要抢救式重写**。文章文笔扎实、逻辑清楚、技术边界写得准（这是 M6 代码审阅「工程判断力强」的延续），开场也已是「导语 + 前言」的形态。要做的是**补真实 Go 代码 + 补对照表 + 适度扩充 + 治理免责密度**。

同口径数据对照：

| 系列 | 正文字数中位 | 代码行中位 | 表格行中位 | 免责/千字 |
|---|---:|---:|---:|---:|
| M4 优化前 | 1679 | 12 | 0 | 7.6 |
| **M4 优化后（目标线）** | **3095** | **86** | **13** | ≤3.0 |
| M5 优化前 | 2436 | 9 | 6 | ≈3.0 |
| M5 优化后（已达） | ≈3050 | ≈70 | ≈13 | ≤4.0 |
| **M6 现状** | **2201** | **0** | **7** | **2.4** |

**M6 唯一压倒性的差距就是「代码行」**（中位 0，且 18 篇为绝对 0）。字数与表格是第二梯队差距。

## 四、优化动作（按价值排序）

### 动作 1 · 补代码密度（最高优先，唯一的系统性差距）

从 `go-backend/internal/**`（96 个 .go / 8053 行）取**逐字节选**。源码是**教学级可读代码**（几乎每行都有中文注释），节选价值极高。重点素材池：

- `internal/values/values.go`（字段存在性 / 分页 / 角色）→ M6-14、M6-21
- `internal/article/{query,view,discovery,mutation}.go`（可见性 / 投影 / 排序白名单）→ M6-20、M6-21、M6-24
- `internal/platform/database/{scopes,transaction}.go`（软删除 scope / 事务）→ M6-20、M6-21
- `internal/auth/{service,credentials,wechat}.go`（JWT / 密码 / 微信）→ M6-05、M6-18、M6-19
- `internal/platform/storage/{storage,r2}.go`（Provider 接口）→ M6-26、M6-27
- `internal/comment/service.go`、`internal/member/interactions.go`、`internal/taxonomy/*` → M6-22、M6-23、M6-25
- `scripts/{benchmark-local.sh,benchmark.mts}` + `docs/go-backend/reports/*.json` → M6-07、M6-09、M6-29

**硬约束**：代码必须**逐字取自源码**；折叠/简化处须在代码块外注明「节选，省略了 X」。

### 动作 2 · 补对照表 + 适度扩充

把散落的并列信息收成表（如「本机键三要素」「三种恢复来源」「接口 × 状态 × 行为」）。字数提到 **≥3000**，只加**真实素材**，不灌水。

### 动作 3 · 免责密度治理（M4 口径：迁移而非删除）

把「并不保证 X」改写为「X 仍可能发生，因此要检查」，保留技术边界本身。

## 五、明确**不建议**做的

| 项 | 理由 |
|---|---|
| 机械删免责句 | M6 命中句多是真实技术边界，删了会误导读者；M4 经验是**迁移**不是删除 |
| 编造性能数字 / 经历 | 性能数据只能引 `docs/go-backend/reports/*.json` 的实测；不替 owner 编造个人经历 |
| 强行加 H3 | M6 是纯 H2 风格，为对齐而加会破坏结构 |
| 全系列统一改开场 | M6 开场已是「导语 + 前言」，无系统性问题，不做整批口味改动 |
| 动已发布内容 | M6 **全部未发布**（草稿），编辑零成本，**不涉及 CSDN** |
