## 4. SOP-A：单篇/批量发布后的例行维护

**触发**：owner 通知「Mx-yy 已发布」（或「今天发了 M0-04/05/06」）。

**步骤**：

1. **取 URL**：按 §3 从索引拿该篇真实 URL。若索引里搜不到，提醒 owner 先让 blog AI 刷新索引。
   - ⚠️ **搜不到 ≠ 没发布**：索引标题里可能有空格等差异（实例：搜「文章CRUD」无果，实际标题是「文章 CRUD 与投稿状态机」）。**优先用系列名（如 `Node 后端篇`）拉整段清单**再定位，不要凭一个词就下「未发布」的结论。
2. **更新 `ARTICLES.md`**：
   - 找到对应行，将「CSDN 链接」列从 `—` 改为真实 URL。
   - 将「状态」列从 `🟡 草稿中` 改为 `🟢 已发布`。
   - 「tag」列：**M0 产品侧一律保持 `—`（M0 不打 tag）**；其他端（M1+）仅在 owner 明确同步了里程碑 tag 时才填对应 tag（如 `node-backend-v1.0`），否则保持原值不动。
   - ⚠️ `ARTICLES.md` 是**同一个文件**：多处编辑必须**串行** Edit。并行编辑会发生写竞争、**静默丢改动**（曾丢过 2 次）。不同文件之间才可并行。
3. **回填本轮已发布编号的 `{{LINK:Mx-yy}}`**（owner 2026-09-21 修订裁定，取代原「留到里程碑全发完统一处理」）：
   - 对**本轮刚公布的每个编号逐个精确 grep**（例：本轮发 07/08，就分别查 `{{LINK:M1-07}}`、`{{LINK:M1-08}}`）。**不要通读一坨全量清单**——曾因通读漏注一处。
   - 命中的占位一律替换为真实链接，**包括已发布文章正文里的占位**（这是允许且必须的，见 §1 注）。
   - 指向「仍未发布」的占位**保持不动**。
   - **形态差异（重要）**：

     | 系列 | 原文形态 | 替换方式 |
     |---|---|---|
     | M1 及以前 | 裸占位 `{{LINK:Mx-yy}}` | 换成完整 `[标题](URL)` |
     | M2 起 | `[标题]({{LINK:Mx-yy}})` | 占位在 URL 位，**只填 URL**，不要重复套链接结构 |

   - 同文件多处占位**串行**替换（或 `replace_all` 整体替换）；不同文件可并行。
   - 注入的显示标题：用 `ARTICLES.md` 的「文章标题」列去掉前缀「成为全栈·<端>篇·」后的核心部分。
4. **注入「今日待发布篇」的内链**：owner 说「今天准备发 09/10」时，对这两篇草稿同样执行步骤 3 的判定——把其中指向**已发布**文章的占位补齐，指向未发布篇的保留。
   > 常见结论：待发篇若只引用「同批次/更晚」的篇目，则**本轮无可注入项、一个字都不用改**。这是正常现象，不是漏做——但必须在报告里明确说出来。
5. **核验图片占位**：读本地 `articles/Mx-yy-*.md` 成品，确认发布同步回来的版本里：
   - 不存在裸 `{{IMG:图名}}` 占位（会当字面文本显示）；
   - 不存在「占位符未删 + CSDN 另插一张图」的重复 bug（曾发生于 M0-02）。若有，合并为单行 `![{{IMG:图名}}](真实URL)`。
6. **出证据**：按 §9 跑 grep，确认 `ARTICLES.md` 对应行已 🟢 + URL 就位。

## 5. SOP-B：统一回填正文内链（已降级为「收尾/兜底」）

**触发**：owner 宣布「全发完了，统一回填」或「做一次内链回填」之类指令。

> **⚠️ 裁定已修订（owner 2026-09-21）**：原「里程碑全发完后一次性回填」的做法，在 M1 的实际执行中已改为**逐轮回填**（见 §4 步骤 3）。
> 本 SOP-B 因此退为**收尾/兜底**用途：① 补扫历史遗留（早期按旧规则漏注的占位）；② 里程碑收官时做最终清零核验。

**背景裁定（owner 2026-08-27 确认；2026-09-21 修订）**：

- 注入条件不变：**只在目标文章已发布时注入**，指向未发布篇的占位一律保留。
- 注入时机提前：由「里程碑全发完」→「目标篇发布的那一轮」（§4 步骤 3）。
- 反复编辑已发布文章正文**是允许的**（逐轮回填的必然结果）；由此产生的线上不同步，由「中途不重发」（§8 铁律 3）吸收。

**步骤**：

1. 从 `ARTICLES.md` 构建「标题 ↔ URL」映射（只取 `🟢 已发布` 行）。
2. 全仓 grep 所有 `{{LINK:Mx-yy}}` 占位。
3. 对每个占位：
   - 若 `Mx-yy` 已在 `ARTICLES.md` 有 URL → 替换为 `[文章显示标题](URL)`。显示标题用 `ARTICLES.md` 的「文章标题」列去掉前缀「成为全栈·<端>篇·」后的核心部分。
   - 若 `Mx-yy` 尚未发布（无 URL）→ **保留占位**，不动。
4. 再次 grep 确认：所有指向已发布篇的 `{{LINK}}` 已清零，仅剩指向未发布篇的占位。
5. 给 owner 一份「已注入 N 处 / 仍残留 M 处（未发布篇）」的清单。

> 匹配依据：标题由我方控制、唯一，`ARTICLES.md` 标题列 ↔ 索引标题做 join 稳定（详见协作约定 §五）。

## 6. SOP-C：全量链接审计（**每轮标准动作**，owner 2026-09-21 定稿）

**触发**：每轮维护（§4 SOP-A + 回填）完成后，**无条件执行**，一轮不落。

**为什么需要**：正文里存在两类**手工录入**的 CSDN 链接，它们不经过 `{{LINK}}` 占位链路，因此占位回填的核验查不出问题：

| 缺陷 | 定义 | 已发生实例 |
|---|---|---|
| **幽灵链** | ID 在正文里，但索引中**根本不存在** → 编造的 URL | 4 个 ID / 9 处（2026-09-19 修） |
| **错链** | ID 在索引中，但**链接文案指向的是另一篇文章** | 2 处（2026-09-22 修） |

> 对照：`{{LINK}}` 占位链路是**可信**的——回填时 URL 直接取自索引，不会错。**只有手工链接需要审计。**

**步骤**：

1. **取正文全部 ID**：全仓 grep `articles/` 下的 `article/details/(\d+)`，去重。
   - ⚠️⚠️ **关键陷阱**：Grep 的 content 模式对超长行只输出 `[Omitted long matching line]`。**这些被省略的行必须逐一 Read 出来**，否则审计是假的——错链恰恰就藏在其中（实例：19 处省略行里藏着 2 处错链）。
2. **取索引 ID 集合**：从 `materials/csdn-已发布链接.md` 提取全部 `article/details/(\d+)`。
3. **比对，查两类缺陷**（两类都要查，只查第一类会漏）：
   - **幽灵链**：正文 ID − 索引 ID ≠ ∅。
   - **错链**：对每个正文链接，核对**文案语义 ↔ 目标篇标题**是否一致（逐条比对，不能只看 ID 存在）。
4. **修复**：
   - 幽灵链：按**链接文案**确定它本来想指向哪篇，从索引取该篇真实 ID 替换。
   - 错链：同上，换成文案对应的正确 ID。
   - 修复仍属机械改动——**不新增链接、不删除链接、不改文案措辞**。
5. **出证据**：复核到「幽灵 0 / 错链 0」为止，并在报告里列出「本轮修复 N 处，分别是什么」。

**执行提示（本环境有沙箱限制，务必分片）**：
- 单次 Bash 调用读取约 **10 个文件**即被 `SIGTERM` 截断，`cat *.md |` 同样受限。**不要一次性扫全仓**。
- 做法：**分片落盘**（每片 ≤10 个文件，结果写 `/tmp/<name>_NN.txt`，最后合并比对）；个别读不动的文件用 **Grep / Read 工具**直接取。
- 沙箱中断是间歇性的，重试常可成功；但**不要靠重试硬扛**，优先改用分片。

## 7. 占位 Token 规范（必须遵守）

| Token | 写法 | 说明 |
|---|---|---|
| 内链（M1 及以前） | `{{LINK:Mx-yy}}` | 裸占位，写作时兄弟篇互链用，**不写裸 URL**；发布后按 §4 步骤 3 注入为 `[标题](URL)`。 |
| 内链（M2 起） | `[标题]({{LINK:Mx-yy}})` | 占位在 **URL 位**，回填时**只填 URL**。 |
| 图片 | `![{{IMG:图名}}](真实URL)` | 发布同步后，真实 URL 填进括号，`{{IMG:图名}}` 保留在 alt 里（便于后续换图识别）。 |

- 严禁在写作/回填中把 `{{LINK:Mx-yy}}` 直接写成裸 `https://...`（会丧失统一回填能力）。
- 已发布文章若仍见裸 `{{IMG:图名}}` 占位，视为 bug（见 §4 步骤 5）。

## 8. 铁律与禁忌

1. **里程碑式 tag，M0 不打 tag**：per-article tag（`article/Mx-yy`）已于 2026-08-27 废止。tag 只标记代码库里程碑（`contract-v1.11.0`、`node-backend-v1.0` 等）。你绝不打 tag，也绝不把 tag 当文章索引用。
2. **只读消费索引**：`materials/csdn-已发布链接.md` 是 blog AI 的产出，你只读不写。
3. **回填照做，但「中途不重发」**（owner 2026-09-21 裁定）：
   - 每轮仍要对**已发布文章**的本地源回填 `{{LINK}}`、修复坏链——这是允许且必须的。
   - 但 owner 在系列发布期间**不更新** CSDN 上的已发布文章（这些文章还要继续打磨）。本地源改动一律**累积**，待全系列发完、owner 统一打磨后**一次性全量更新**到 CSDN。
   - 因此：**不要每轮提示 owner「必须重发」**。改为：报「本轮新增 N 篇受影响，已累积」，并维护累积清单（当前在项目记忆 `.workbuddy/memory/MEMORY.md`）。
4. **不做同文件并行 Edit**：见 §4 步骤 2 的写竞争说明。
5. **不改代码/不写文章**：你的改动范围严格限定在 `ARTICLES.md` + `articles/` 的内链/图片占位机械改动。
6. **先核验再交付**：每次维护后必须给 grep 证据，不靠自报。
7. **SOP-C 每轮必跑**：它是唯一能发现手工坏链的手段，一轮不落（§6）。
