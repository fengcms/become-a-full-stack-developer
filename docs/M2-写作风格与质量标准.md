# M2 React 管理后台 · 写作风格与质量标准

> 目的：把“内容丰富、论点严谨、像 FungLeo”变成可检查的标准。  
> 优先级：FungLeo 已发表文章的真实声音 > 项目章程的系列约束 > M0/M1 的结构经验。M1 后期文章只作技术素材，不作为默认文风模板。

## 一、样本与结论

本标准重点精读了以下材料：

- 已发表前端文章：FE01 请求层刷新、FE04 批量提交、FE06 列表筛选 URL 同步。
- 已发表后端文章：BE11 通用列表查询 DSL。
- 真实排障文章：《一次 Web 服务雪崩的完整排查手记》。
- 系列文章：M0-01、M0-04，M1-01、M1-15、M1-27、M1-31。
- 既有规范：项目章程、`FungLeo-文风手册.md` 与实证分析。

你的稳定风格不是几个口头禅，而是四个更深的特征：

1. **从亲历问题开场。** 先说我为什么碰到它、原来怎么想、哪里不对，再进入方案。
2. **证据推动结论。** 错误、请求链、代码或数据先出现，判断随后落下；不是先喊“最佳实践”。
3. **像老开发和朋友复盘。** 第一人称，有明确判断，承认取舍和弯路，不摆老师架子。
4. **实用主义收束。** 最后给读者一套能带走的判断方法，说明什么场景适用、什么场景不值得做。

“各位看官”“说实话”“好啦”“闲言少叙”等只是表面标记。每篇自然出现一两处足够；如果没有真实经历和判断，堆再多口头禅也不像你。

## 二、M1 后期暴露的问题

后端后期部分文章技术信息并不少，主要问题是表达方式逐渐模板化：

| 问题 | 阅读感受 | M2 的修正 |
| --- | --- | --- |
| 一开篇就给目标、前置和最终结论 | 像交付文档，缺少“为什么值得读” | 前言先放具体冲突或反直觉现象，再提出本文问题 |
| 大量“心法 1/2/3”式结论并排 | 记住了口号，没经历推导 | 一篇只推导一个主结论；先证据、再原因、再判断 |
| 功能、接口、端点依次盘点 | 像 README 或 API 说明 | 围绕一个决策组织代码，非关键功能只作旁证 |
| 内链高频插入句子 | 阅读节奏被打断 | 正文只在关键承接处内链，其余集中到延伸阅读 |
| 每一节都使用相同句式收束 | AI 模板感明显 | 根据内容自然收束，不强制每节造一句格言 |
| 复盘篇重复前文结论 | 信息看似丰富，新增认知有限 | 总复盘只讲跨篇才看得见的模式、错误和演进 |
| 作者声音逐渐消失 | 技术正确，但不像个人博客 | 保留“我为什么这么选、当时误判什么、现在如何看” |

M2 不追求故意口语化。目标是让严谨的技术论证里一直能看见一个真实作者。

## 三、单篇论证结构

每篇先写一句“我要证明什么”。正文所有章节都必须服务这句话。

推荐结构：

```text
前言：一个真实问题或原先的错误判断
  ↓
问题定义：具体哪里坏了，为什么普通写法不够
  ↓
候选方案：至少两个方案，比较约束和代价
  ↓
最终选择：为什么当前项目选择这一种
  ↓
关键实现：只展示证明观点所需的代码
  ↓
验证：测试、网络请求、构建数据或浏览器行为
  ↓
适用边界：什么时候可以简化，什么时候需要升级
  ↓
小结：把结论还给读者的下一个项目
```

不是每篇都要写成事故故事。工程搭建类可以从一个真实配置冲突切入，设计类可以从两个方案的矛盾切入，复盘类可以从前后数据对比切入。关键是文章里必须有“问题如何被证据推到结论”的过程。

## 四、语言规则

### 必须保留

- 使用第一人称“我”，交代真实判断：“我一开始选择……”“实际联调后，我改成……”。
- 适度称呼“各位看官”，通常前言或小结出现一次；不强制每个章节出现。
- 句子和段落偏短，一段只说一个意思。
- 有立场但不装绝对：“在这个后台里，我更愿意……”“如果数据规模到了另一层级，这个选择要重新评估。”
- 技术词使用英文并保持中英空格；代码注释使用中文。
- 可以克制地自嘲真实误判，不能虚构事故或为了幽默表演。

### 应当删除

- “众所周知”“显而易见”“最佳实践”“完美解决”等无证据的绝对判断。
- “首先其次最后”连续排队、每节末尾固定“这就是……”的机械句式。
- 为了显得活泼硬塞网络梗、俏皮问答和夸张情绪。
- “赋能、抓手、闭环、沉淀、范式升级”等可以被具体动词替换的空话。
- 把代码逐行翻译成中文，或大段复述官方文档。
- 不准确的 AI 落款。当前系列沿用订阅块即可，不写“Deepseek 操刀/校阅”。

## 五、内容丰富度标准

丰富不是字多，而是观点有多种证据支撑。每篇至少满足下列五项中的四项：

- 一个真实问题、错误方案或反例。
- 一张对比表、状态图、时序图或结构图。
- 一段来自项目的关键代码，并解释它保护了什么。
- 一项可核验结果，如测试断言、请求次数、构建体积或浏览器行为。
- 一个适用边界或代价，告诉读者什么时候别照搬。

代码不以数量取胜。一个 30 行片段若能完整证明竞态如何解决，比贴三个完整文件更有价值。截图同理：只展示读者无法从代码直接看出的界面状态。

## 六、严谨性门槛

每个关键判断都要属于下面四类之一：

| 类型 | 写法 |
| --- | --- |
| 代码事实 | 给出真实文件或精简代码，确认当前版本存在 |
| 契约事实 | 对照 OpenAPI 的字段、状态和端点，不凭旧计划记忆 |
| 实测结果 | 写清命令、样本和结果；不要把静态推断写成“已经验证” |
| 作者判断 | 明确约束与代价，使用“在本项目中”限定范围 |

技术校验必须包含：

1. 路线图命题与当前实现一致。
2. 代码片段可编译或来自已通过检查的版本。
3. 状态、权限、字段和端点与冻结契约一致。
4. 性能数字来自同一次构建，不能混用不同日期的产物。
5. 没做过的浏览器场景写成风险或待验证，不写成结论。
6. “为什么不选另一个方案”至少说清一项实际代价。

## 七、标题、开头与小结

标题保留系列统一前缀，同时做到“技术点 + 具体矛盾”，避免空泛：

- 好：`成为全栈·React 管理后台篇·OpenAPI 生成类型，为什么请求函数仍然手写`
- 弱：`成为全栈·React 管理后台篇·OpenAPI 最佳实践`

前言控制在 200～350 字，完成三件事：场景、冲突、本文承诺。不能把摘要换一种说法再写一遍。

小结不重复目录，回答两个问题：

- 这篇最终改变了什么判断？
- 读者下次遇到类似问题，先检查什么？

结尾可以使用一次“各位看官”或邀请交流，随后接系列内链和订阅块；不堆叠点赞话术。

## 八、配图与排版

每篇建议 2～4 张图，按价值排序：

1. 状态/请求/数据流图。
2. 方案前后对比图。
3. 关键交互截图。
4. 封面图。

图中文字必须服务正文，中文标签简短；文章不能依赖图片才能理解。表格用于比较映射关系，步骤用有序列表，警示或核心约束用引用块。排版多样性服务阅读，不为 CSDN 评分堆元素。

## 九、三轮审稿机制

每篇正文完成后按三轮复审，不在写作过程中同时处理所有问题：

### 第一轮：技术审稿

- 核对代码、契约、状态机和实测证据。
- 搜索绝对词，检查是否有过度推广。
- 确认文章只证明一个核心命题。

### 第二轮：作者声音审稿

- 前言是否来自真实问题，而不是模板摘要。
- 是否说明“我为什么这样选”，有没有作者判断。
- “各位看官”等标志语是否自然；删去为了模仿而硬加的口头禅。
- 朗读一遍，凡是像汇报材料的长句就拆开。

### 第三轮：发布审稿

- 标题、文章简介、Tag、配图、代码语言标记和中文注释齐全。
- 至少两条有效站内互链；未发布兄弟篇保留 `{{LINK:*}}`。
- 发布辅助区完整并位于文末；发布时整段删除，不混入正式正文。
- `ARTICLES.md` 标题与草稿文件一致。

## 十、发布前辅助区

每篇 Markdown 草稿末尾必须带一个统一的辅助区，并使用下面两个注释标明边界：

```markdown
<!-- PUBLISH_ASSIST_START：发布前辅助信息，发布时整段删除 -->
...
<!-- PUBLISH_ASSIST_END -->
```

辅助区固定包含：

1. **文章 Tag**：5～6 个，按“核心框架 → 关键技术 → 问题场景”排序。Tag 必须在正文中有实际讨论，不能为了流量添加无关热词。
2. **文章简介**：建议 150～220 个中文字符，硬上限 250 个字符。写清问题、关键方案和读者收益，不照抄前言，不使用“本文全面介绍”等空句。
3. **封面图 AI 提示词**：说明主题、画面主体、关系、配色、风格、横纵比和中文文字要求。默认技术博客横版 16:9，少量清晰中文，不生成品牌 Logo。
4. **正文配图 AI 提示词**：逐张列出插入位置、占位符、图片类型和完整提示词。流程、状态与层级关系优先使用信息图；真实界面效果优先使用项目截图，不让 AI 臆造 UI。
5. **发布核对项**：图片占位符、兄弟篇内链、简介长度、Tag 数量、辅助区删除、CSDN 预览排版。

可选信息仅在确实有帮助时加入：建议分类、SEO 关键词、封面短标题、代码对应里程碑。不要让辅助区变成另一份文章摘要。

### Tag 质量要求

- 5～6 个，不多不少；同义词只留一个，例如 `React` 与 `React.js` 不同时使用。
- 至少 2 个技术实体，如 `React`、`Vite`、`TanStack Query`。
- 至少 1 个问题或场景，如 `前端鉴权`、`管理后台`、`性能优化`。
- 不固定给每篇都塞 `TypeScript`；正文没有深入讨论就不使用。

### 配图提示词质量要求

提示词不能只写“生成一张 React 架构图”。它至少要包含：

- 这张图帮助理解哪一个论点。
- 画面中的节点、箭头方向和层级关系。
- 必须出现的中文标签及禁止出现的额外文字。
- 视觉风格、主色、背景和比例。
- 复杂关系图要求“文字清晰、结构优先、避免装饰元素干扰”。

图片占位符统一使用 `{{IMG:M2-xx-短名称}}`。同一篇的提示词名称必须和正文占位符逐字一致，避免发布时找错图片。

完整格式见 [M2 文章 Markdown 模板](./M2-文章模板.md)。

## 十一、第一批校准方式

先写 M2-01～04，不连续写完 22 篇再统一回头修改。第一批分别覆盖工程、架构、竞态和契约四种文章形态，足以暴露风格偏差。

第一批验收时重点比较：

- 是否比 M1 后期更有具体问题和推进感。
- 是否保留你的第一人称与务实判断，同时比旧博客更克制。
- 是否有足够的代码和证据，但没有退化成开发文档。
- 四篇之间是否各讲一件事，没有重复解释请求层和鉴权。

第一批经 owner 确认后，这套标准才算冻结，后续 18 篇按同一尺度执行。
