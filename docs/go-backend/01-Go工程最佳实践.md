# M6 Go 工程最佳实践

> 状态：已确认并落实；实际决策见 05 文档。日期：2026-10-07。适用对象：本项目 Go 后端；不是要求所有 Go 项目遵循同一个目录模板。

## 1. 工程目标与技术决策

我们要实现一个可以长期维护、适合讲解、与 Node 后端共享契约的单体服务。主要难点是业务行为和数据库语义一致，不是搭建尽可能多的基础设施。

| 位置 | 建议 | 决策理由 |
| --- | --- | --- |
| Go | 1.26 系列，开发开始时锁定补丁版本 | 本机已安装 1.26.6；CI 与容器统一版本 |
| HTTP | 标准库 `net/http`、`ServeMux` | 当前路由规模适中，方法与路径模式足够，不再叠加框架约定 |
| ORM | GORM v2 | 官方支持 PostgreSQL、MySQL、SQLite；保留必要的受控 SQL |
| 主数据库 | PostgreSQL 17 | 作为开发、集成测试和部署的默认数据库 |
| 可选数据库 | MySQL 8.4 LTS、SQLite | 同一业务层，通过真实数据库验收后才称为支持 |
| 数据库迁移 | goose，按数据库方言管理版本 SQL | 可审阅、可复现，明确迁移历史 |
| 日志 | 标准库 `log/slog` | 结构化日志，无需额外日志框架 |
| 认证 | HS256 JWT、bcrypt、哈希存储刷新令牌 | 与现有认证协议兼容 |
| 对象存储 | 本地磁盘、R2 S3 兼容接口 | 维持既有 storage 枚举与文件 URL |
| 配置 | 环境变量解析为不可变配置对象 | 构造时注入依赖，避免业务代码读取全局环境 |

这是本项目的选择，不是性能结论。Gin、Echo 可以减少部分路由装配代码，但不会替我们解决事务、权限和多数据库问题；现阶段不引入它们。标准库已经提供方法与路径匹配，见 [ServeMux 文档](https://pkg.go.dev/net/http#ServeMux)。Go 版本背景见 [Go 1.26 发布说明](https://go.dev/doc/go1.26)。

不引入微服务、消息队列、Redis、分布式锁、泛化插件系统、CQRS 或复杂依赖注入框架。出现明确需求和测量证据后再讨论。

## 2. 工程布局与调用边界

拟新增 `go-backend/`，不替换 `node-backend/`。Go module 拟为 `github.com/fengcms/become-a-full-stack-developer/go-backend`，初始化时再次核对仓库路径。

```text
go-backend/
  cmd/
    server/main.go           # 装配服务、启动、优雅关闭
    migrate/main.go          # 显式迁移命令
    seed/main.go             # 仅开发/测试初始化
  internal/
    config/                 # 读取与校验环境变量
    transport/httpapi/      # 路由、中间件、DTO、信封、参数解析
    auth/                   # 账号、微信身份、令牌
    article/                # 文章、状态机、查询与衍生能力
    taxonomy/               # 分类、标签及同步
    comment/                # 评论、过滤、复核
    member/                 # 资料、互动、历史、通知
    administration/         # 用户与站点管理
    platform/
      database/             # GORM 连接、方言、数据库错误映射
      storage/              # local/R2 实现
      clock/                # 可测试时钟
  migrations/
    postgres/
    mysql/
    sqlite/
  test/                     # 集成、契约、兼容测试及 fixture
  go.mod
  go.sum
  Dockerfile
  .env.example              # 只含占位符
```

目录会随着真实模块形成，不预先铺满空文件。`internal` 限制外部导入，`cmd` 放入口，这是官方服务项目布局的常见组织方式，见 [Go module 布局说明](https://go.dev/doc/modules/layout)。

调用方向为 HTTP → 应用服务 → 持久化/外部适配器。HTTP 层负责协议解析和序列化；服务负责权限、状态变化和事务；仓储负责数据库访问。接口定义在使用方，只为需要替换或隔离测试的依赖定义小接口，不制造每张表一套通用 CRUD 接口。

不要直接把 GORM model 当作 JSON 响应。存储结构、业务对象、公开 DTO 分开；密码哈希、刷新令牌哈希、OpenID 和配置密钥不会因为字段新增而进入响应。避免嵌入 `gorm.Model` 自动带出的字段和软删除语义。

`context.Context` 从请求传到服务、数据库 `WithContext` 和外部 HTTP 请求；不存入长期存活的结构体。构造函数注入数据库、时钟、存储和微信客户端，便于隔离测试。错误用 `errors.Is/As` 判断，不用字符串比较；内部错误保留上下文，HTTP 层统一转为既有错误码。

## 3. 契约优先的 HTTP 实现

唯一协议来源是 `docs/api/openapi.v1.yaml`。业务成功仍返回 HTTP 200 和既有信封；不要改成 201/204。路径、方法、字段名、枚举、鉴权、Cookie、分页和错误数据都属于兼容性范围。

更新 DTO 要表达三种状态：没有提交、显式 `null`、提交实际值。单独的 `*T` 不足以区分前两种，可使用经过测试的 `Optional[T]`（存在标记 + 有效值标记）。响应中 `null`、字段省略和空数组必须按契约输出，不能随意使用 `omitempty`。

时间统一按既有 UTC 毫秒格式输出；ID 输出 JSON 数字；空集合为 `[]`；分页 `totalPages` 当前最小为 1。参数解析对非法数字、重复参数、大小写、空字符串和边界值建立样例，先明确契约与 Node 的差异再实现。

OpenAPI 3.1 的 DTO 生成工具需要做小型验证。`oapi-codegen` 当前主分支文档声明支持 3.1，但主分支能力不等于已发布版本可直接使用。G0 锁定一个发布版本，验证本契约的 `allOf`、可空类型、枚举与字段存在性；通过后生成 DTO，未通过则显式编写 DTO 并保留同一套 schema 校验。不得为了工具修改或降级冻结契约。见 [oapi-codegen 官方说明](https://github.com/oapi-codegen/oapi-codegen)。

中间件顺序显式装配：请求标识与恢复 → 日志 → CORS/预检 → 对公开操作限流 → 身份解析 → 操作级鉴权 → 处理器。可选认证端点同时测试无令牌、合法令牌和非法令牌；不能把“解析失败”自动等同匿名。未知路由、方法不匹配及业务异常要审查响应，不能泄漏 Go 默认 HTML 错误页面。

## 4. ORM 不是多数据库兼容保证

GORM 提供三类官方驱动，但连接成功只说明驱动可用。数据库兼容要覆盖 DDL、约束、事务、查询和并发。见 [GORM 数据库连接文档](https://gorm.io/docs/connecting_to_the_database.html)。

| 差异 | 本项目处理规范 |
| --- | --- |
| 主键、自增与导入 | HTTP ID 不变；迁移 SQL 各自定义；导入后重置序列/自增位置 |
| 字符串比较 | 用户名、邮箱、slug 的大小写规则与 Node 样例一致；MySQL 显式选择合适排序规则 |
| JSON 字段 | 可优先使用文本 JSON 编解码保证可移植性；关系查询使用关联表，不依赖 PostgreSQL 专属 JSON 运算符 |
| 时间与布尔 | 显式映射数据库类型，统一 UTC；SQLite 不直接复制整型布尔实现到全部数据库 |
| 外键 | 三种数据库均启用并测试；SQLite 每个连接的外键设置需要验证 |
| 冲突处理 | 数据库唯一约束作为最后防线；驱动错误映射为契约错误码 |
| Upsert | 使用已验证的方言实现；MySQL 的受影响行数不能照搬 PostgreSQL 的判断 |
| 查询与搜索 | 精确过滤、LIKE 转义及大小写行为、稳定排序、NULL 排序都做跨库测试 |
| 锁与事务 | PostgreSQL/MySQL 行锁与条件更新；SQLite 写锁、busy timeout 和有限重试单独验证 |

业务层不知道 DSN 或驱动错误号。差异集中在数据库适配器和迁移文件；不是复制三套服务。事务重试只能针对识别出的可重试错误且操作具备幂等性，设置次数与总时间上限，不能吞掉所有数据库异常。

GORM `Updates(struct)` 默认忽略零值，所以 PATCH/PUT 必须基于已解析字段构造白名单 map 或显式选择字段。禁止用 `Save` 代替条件更新，避免更新失败变插入。见 [GORM 更新文档](https://gorm.io/docs/update.html)。

`Order`、`Select`、字段名和原生 SQL 片段只能来自代码白名单；值通过参数绑定。`fields` 和排序 DSL 不允许直接拼入 SQL。见 [GORM 安全文档](https://gorm.io/docs/security.html)。

## 5. 迁移与事务规范

正式环境只通过 goose 运行已审阅的版本迁移，不在服务启动时执行 `AutoMigrate`。自动迁移不是升级历史和回滚方案，见 [GORM migration](https://gorm.io/docs/migration.html) 与 [goose](https://pressly.github.io/goose/)。三个方言目录使用一致的逻辑版本，每次新增版本都在三个数据库上执行从空库和上一个版本升级的验证。

迁移命令与运行服务使用不同权限账号；服务账号无 DDL 权限。MySQL 的 DDL 不能假定整个文件可事务回滚；生产迁移必须先备份和演练。破坏性 down 不作为线上回退常规手段，优先向前修复，必要时恢复备份。

服务层显式持有事务句柄，事务内仓储不得误用全局 DB；异常、回滚、死锁和重复请求都有测试。外部微信请求、R2 请求与 bcrypt 运算不放在持锁的数据库事务内。见 [Go 事务指南](https://go.dev/doc/database/execute-transactions) 和 [GORM 事务文档](https://gorm.io/docs/transactions.html)。

以下操作必须作为业务一致性单元设计：

- 文章与标签关系、分类冗余投影、审核结果与通知。
- 点赞/收藏关系与文章计数；通过唯一约束和原子更新防止重复增加或负数。
- 微信身份与新会员创建；并发回调只能建立一个身份。
- 首次设密、旧刷新令牌撤销和新认证结果生成；失败不得部分落库。
- 刷新令牌消费与新令牌签发；重放撤销必须提交，即便最终 HTTP 返回错误。

最后一项尤其容易出错：在 GORM 事务回调中直接返回“重放错误”，会把已经做的撤销也回滚。应提交安全处置结果，再在事务外返回相应业务错误。并发刷新中只能有一次成功消费；失败的重放请求可能撤销刚签发的刷新令牌，这也是需要验证的既有安全语义。

## 6. 认证、安全与文件边界

沿用既有 HS256、字符串 `sub` 和过期规则；限制允许算法，不额外强制契约未要求的 `issuer/audience`。刷新令牌只存 SHA-256 摘要，日志不记录令牌、密码、Cookie、微信 code、AppSecret、OpenID 或 session_key。

Node 当前 bcrypt cost 为 12。Go bcrypt 的生成函数拒绝超过 72 字节的密码，而既有 bcryptjs 有截断行为；契约密码长度又不能直接替换成 72 字节限制。开发时用跨语言测试向量确认 UTF-8 截断边界，兼容适配在哈希和校验两侧一致执行；不改为预哈希，也不悄悄缩小契约长度。需要记录这个兼容约束供教学解释。见 [Go bcrypt 文档](https://pkg.go.dev/golang.org/x/crypto/bcrypt)。

保持 `refreshToken` Cookie 的 `HttpOnly`、`SameSite=None`、`Secure`、`Path=/` 和生命周期，并保持 Cookie 优先于 body 的取值规则。本地浏览器验证用 HTTPS 或既有 BFF/body 流程，不能以方便调试为由改变线上 Cookie 语义。

限流只覆盖契约规定的公开操作，使用受信任代理配置获取 IP，不信任任意 `X-Forwarded-For`。单进程服务可先用有容量上限、过期清理的内存限流器；它不具备跨实例共享能力，部署多个实例前必须单独解决。CORS 白名单与是否允许凭据显式配置，生产配置不能任意反射 Origin。

上传继续限制 10 MiB，允许类型以契约与现有测试为准，校验重复 multipart 字段、路径穿越和文件名。SVG 下载响应保持 attachment 与 nosniff。存储 driver 明确选择 local 或 r2，R2 失败不自动写入本地。R2 的 S3 兼容 API 不是所有 S3 功能的完整实现，只使用验证过的 put/get/delete，见 [R2 S3 API 文档](https://developers.cloudflare.com/r2/api/s3/api/)。

文件与数据库无法共享事务。相同内容 key 可能被多条附件引用；删除前检查剩余引用，避免删除另一个用户仍使用的对象。数据库失败后的补偿不能无条件删除已存在的共享 key。孤儿对象与远端删除失败记录为可追踪的清理事项，先采用运维命令处理，不增加队列系统。

## 7. 可验证、可运行的工程

质量门禁包含 `gofmt`、`go vet`、`go test ./...`、关键并发测试的 `-race`、`govulncheck`，以及独立的三数据库集成任务。Race detector 发现内存竞态，不能替代数据库并发测试，见 [Race detector](https://go.dev/doc/articles/race_detector)；依赖漏洞检查见 [govulncheck](https://go.dev/doc/security/vuln/)。

测试分层：纯函数单测验证排序解析、状态机、敏感词、目录锚点；仓储测试验证实际数据库约束与事务；HTTP 测试验证权限、信封和 Cookie；跨实现测试验证 Node 与 Go；现有客户端本地回归验证接入。微信与存储故障使用可控替身，真实线上数据不用来写测试。

不要为每个 getter 写镜像测试。重点测试未授权访问、字段缺失/null/零值、并发冲突、回滚、重复请求和跨数据库差异。Schema 校验支持 OpenAPI 3.1 对应的 JSON Schema 2020-12；若使用 Go 校验器，可评估 [jsonschema 官方项目](https://github.com/santhosh-tekuri/jsonschema)，但 schema 检查不能取代 `x-authz` 和业务状态机用例。

服务配置连接池、连接超时、HTTP 读取头/请求/空闲超时、外部请求超时和优雅关闭；关闭流程停止接收请求，等待有界时间，然后关闭数据库。日志包含请求标识、操作名、状态码、耗时和脱敏错误，生产不输出完整请求体或 SQL 参数。诊断端口不暴露到公网，性能优化先测量与 profiling，见 [Go diagnostics](https://go.dev/doc/diagnostics)。

SQLite 官方 GORM 驱动使用 CGO。不能同时宣称使用该驱动和 `CGO_ENABLED=0` 静态构建；初版容器统一使用匹配 C 工具链和运行库的 Linux 构建/运行镜像。纯 Go SQLite 驱动属于以后有明确需求才评估的替代方案。

依赖和工具锁定版本并提交 `go.mod/go.sum`；不要用 `latest` 作为可复现构建规范。文档区分已测能力和计划能力。每个里程碑形成一个可运行、可审阅的提交，提交信息遵循 `type(scope): 中文描述`。

## 8. 中文教学代码的表达规范

代码内文档和关键规则注释使用中文，导出符号说明以符号名开头。优先解释权限、前态、幂等、事务提交/回滚及跨数据库差异；不把逐句翻译代码当作说明。目录树、凭据和对象补偿等规则应在实现位置有中文锚点，不能只存在于外部文档。

普通错误变量使用 `err`，事务整体结果使用 `txErr`，业务决策使用 `decision`。短作用域的 `if err := ...` 可以保留，但不要让业务失败与数据库执行失败共用同一个返回语义。数据库原生连接使用 `sqlDB`，避免与包名混淆。

DTO 与多字段结构体按字段排版，链式查询在有意义的步骤换行。行长、函数长度和注释数量用于发现阅读困难，不是通过填充注释或拆散完整事务来追求分数。

普通文章查询显式应用 `database.ActiveArticles`，JOIN 也使用固定文章表名的 scope；公开查询再叠加 published 条件。离线快照必须保留软删除历史，带别名的审计保留明确 SQL，不套用业务查询的过滤。这个显式 scope 不会自动阻止未来遗漏，新增查询仍需代码审阅与回归测试。

数字 ID 路由统一使用 `registerID`，该包装必须委托 `Register`，保持权限、限流、输入校验的执行链。命名事务函数只接收调用者的 `tx`，不得在内部使用主连接完成同一动作。对应第一轮调整和证据见 [审阅回复](review/M6-Go后端代码第一轮审阅回复.md)。
