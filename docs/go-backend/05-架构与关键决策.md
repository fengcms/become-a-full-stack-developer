# M6 实际架构与关键决策

日期：2026-10-08。本文描述已经写入代码的边界与取舍，可作为后续协作和教学素材。初始最佳实践和规划保留其背景；实现以本文件与验证报告为准。

## 1. 工程结构

```text
go-backend/
  cmd/
    server/           HTTP 服务入口、超时、信号与关闭
    migrate/          显式版本迁移
    seed/             显式开发管理员/演示文章初始化
    data/             只读导出、空目标库导入和 dry-run
  internal/
    bootstrap/        唯一装配根，绑定全部68个操作
    auth/             账号、本地凭据、JWT、refresh、微信身份
    article/          内容生命周期、查询、展示投影、TOC与阅读
    taxonomy/         分类树和标签、文章展示关系同步
    comment/          评论关系、敏感词、复核与整支删除
    member/           点赞收藏、阅读历史与私有通知
    administration/   用户管理、公开会员视图与站点设置
    attachment/       附件元数据及共享对象生命周期
    notification/     事务内事件写入，供文章/评论调用
    transport/httpapi/ 路由、鉴权、schema、Cookie、multipart、信封
    platform/
      model/          15张表的持久化行，禁止直接作为HTTP响应
      database/       驱动、连接池、行锁、SQL版本迁移和脱敏诊断
      storage/        local与S3兼容R2字节对象适配器
    contract/         冻结快照、schema校验及nullable内存转换
    values/           输入字段存在性、分页、身份与时间原语
    fault/            业务错误码与HTTP状态映射
    transfer/         离线迁移格式、标量检查、顺序和关系核查
    testutil/         测试数据库
  test/               跨领域HTTP、故障事务、客户端smoke
  scripts/            冻结快照检查、Node差分、三库与性能执行器
```

没有统一的“大 Service”，也没有把一个请求的业务规则拆成大量没有独立责任的接口。HTTP 不写业务 SQL；存储适配器不认识用户和文章；ORM 行不自动暴露密码/身份字段；装配根显式注入数据库、外部服务和存储。

## 2. 为什么没有通用 Repository<T>

本项目的难点是“在同一事务内变更文章、标签、通知”，而不是替换数据库产品。GORM已经提供驱动抽象，额外的通用CRUD Repository容易让行锁、条件更新、JOIN和事务透传变得隐蔽。

领域 Service 直接接收 `*gorm.DB`，SQL 与领域规则放在同一领域包中；跨领域能力通过小函数/明确服务方法复用。锁与驱动差异才下沉平台层。需要替换真实外部服务的地方保留接口：微信换码、对象存储。时间通过 `Now` 注入，便于过期与午夜边界测试。

这是按当前规模选择的最小抽象，不是“永远不需要 Repository”。如果将来引入多种来源的同一业务存储，再针对消费者真正需要的方法建接口。

## 3. 契约与 DTO

冻结 YAML 是事实源，生成 JSON 快照只为 Go 嵌入；`sync-contract.cjs --check` 防漂移。oapi-codegen 的锁定发行版对3.1的警告、nullable和指针存在性问题已实测，因此没有强行使用不可证明正确的生成类型。

输入先在HTTP边界验证，再形成 `values.Fields`。领域方法只映射白名单字段，并用 `Has` 区分未提交、null、0、false和空字符串。输出显式组装 User/Article/Summary 等 DTO；列表不携带 content 全文，用户不泄露密码哈希和微信 openId。

SiteSetting裸schema、URI相对地址、PUT必填和评论长文本等历史矛盾有明确局部处理，详见07报告；没有在“适配”名义下改冻结文件。

## 4. ORM 与三数据库

选择 GORM，是为了保留可读的关联查询、参数绑定和跨驱动事务，而不是用ORM替代SQL设计。不使用 `gorm.Model`，避免隐藏的软删除与时间字段；不使用启动 `AutoMigrate`，避免把上线和模式变更混在一起。

三套SQL共用逻辑迁移编号：00001创建15表与站点单例；00002添加访问索引。日期是UTC epoch毫秒bigint；bool按方言存储；标签JSON投影是文本，规范关系以article_tags为准。MySQL唯一字段/索引使用有界VARCHAR和二进制排序规则，保留用户名/slug的精确匹配。

连接池 PostgreSQL/MySQL最大16、空闲4、30分钟回收；SQLite单写连接、WAL、busy timeout、强制外键。SQLite并发业务由单连接串行执行，两个服务实例共享同一SQLite文件不在本轮承诺内。

## 5. 事务与安全边界

- refresh先定位摘要，再锁用户、复核令牌、消费并签发；重放撤销必须提交，不能用返回错误让撤销回滚。
- bcrypt在行锁外执行，避免成本12的CPU工作长时间占用锁；进入事务后再校验密码哈希/账号状态没有变化。
- 微信身份以appId+openId唯一，首次建号竞争依靠唯一约束及有限重试；首次设密条件更新、撤销和新认证结果同事务。
- 点赞锁文章，以关系数维护计数，规避MySQL冲突更新RowsAffected的语义差异。
- 文章发布与评论复核的通知与状态同事务，不使用异步队列做本项目尚不需要的复杂化。审核端点、后台置位及PUT从非发布转发布都维护发布通知；初次创建自己的已发布文章不发送审核通知。
- 阅读量锁文章，以同一身份记录的createdAt判断滚动24小时，不复制Node的午夜时间桶偏差。
- 外部对象与数据库不能原子提交。上传失败不写元数据；元数据失败以独立、有界清理上下文检查引用；删除最后引用后清理对象，失败记录待对账，不伪装成数据库回滚。

SQL值参数化，排序/选择/原生片段来自代码白名单。请求体和上传体有上限。生产CORS必须明确Origin，转发IP仅接受配置的代理CIDR。JWT保持既有短期无状态模式：修改密码/登出撤销refresh；已发access在有效期内的行为沿用Node，不额外发明撤销协议。

## 6. 部署拓扑与后续扩展

本轮交付采用**单个写服务实例**。分类树变更和对象key生命周期含进程内锁；PostgreSQL/MySQL的账户、互动、状态事务使用数据库行锁，但不能因此宣称整站已经支持任意多实例写入。若以后水平扩容，必须补分类结构/对象key的数据库或分布式协调，并把公开限流迁移到共享网关。

local需要持久目录；R2需要同一个桶的签名配置。URI仍是 `/files/{key}`，客户端通过后端Origin解析。读取旧local和r2元数据时，必须同时保留对应provider和实际对象，单纯改变STORAGE_DRIVER不搬运文件。

SQLite驱动使用CGO，所以构建需要C编译器；Linux配方保留glibc运行时，不能宣称 `CGO_ENABLED=0` 的同一二进制支持SQLite。参考 [驱动官方编译说明](https://github.com/mattn/go-sqlite3#installation) 与 [Go官方镜像维护仓库](https://github.com/docker-library/golang)。本机原生构建已验证；容器基础镜像manifest已核查，完整Linux镜像构建及目标环境运行留在部署验收。

## 7. 工程经验

“同契约”不是字段长得像：输入存在性、空值、稳定排序、Cookie、异常前态、计数幂等和失败后的数据库状态都必须有证据。差分有价值，但Node与冻结规则不一致时，应记录具体事实并服从契约，而不是为了绿色结果复制缺陷。

三数据库也不是三个连接字符串。真实MySQL验证发现其tinyint返回类型与SQLite/PostgreSQL不同，迁移格式必须统一为boolean；SQLite的Create(map)会回写额外生成键，导入需要复制输入行；MySQL容器初始化时临时socket服务可能让ping误报ready，健康检查改为TCP查询。这些是在实际运行中确认的判断，后续协作应保留它们。
