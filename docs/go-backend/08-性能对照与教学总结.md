# M6 性能对照与教学总结

日期：2026-10-08。原始结果见 [性能数据](reports/performance.json)、[Go 数据库统计](reports/db-go.json)、[Node 数据库统计](reports/db-node.json)。复现：在 `go-backend` 执行 `bash scripts/benchmark-local.sh`。

## 实验边界

在同一台 arm64 Mac 上，使用同一份 500 篇文章的 SQLite 数据副本，分别运行 Go 原生编译服务和既有 Node Hono 应用的本地 HTTP 服务。Node 通过 tsx 加载源码，Go 使用原生二进制；所以 RSS 包含不同启动工具的开销，不能视为语言固有内存成本。两个服务均读取完整响应，无业务缓存；每场景先预热 5 次，搜索显式指定 pageSize=20，避免两端默认值差异影响对照。读请求 50 个样本、并发 8；登录 8 个样本、并发 2；点赞与取消作为一次成对操作，30 个样本、并发 4。计时为客户端 `performance.now`，累计 CPU 与 RSS 取自本机进程。

这是小规模本地一次运行的观察，不是持续压测或线上容量证明。Go 先执行、Node 后执行，系统缓存、调度和后台数据库容器都可能影响结果。没有把 Go/PostgreSQL 与 Node/Cloudflare D1 的环境差异包装成语言性能结论；PostgreSQL/MySQL 已验证功能，未在本报告作性能比较。

所有请求均成功。在本轮样本里 Go 读取及登录更快，Node 点赞与取消的 p50 更低，Go 的尾延迟和本轮成对操作吞吐更好。登录保留 bcrypt cost 12，不能通过降低密码强度取得更漂亮的成绩。成对写操作的每秒数是“完成两次请求的操作数”，不能直接与单请求读吞吐比较。8 次登录样本的 p99 几乎就是最大值，统计稳定性有限。

Go 末尾 RSS 32240 KiB，Node 237040 KiB；这只是上述运行方式的进程采样。Go 数据库记录 667 次、总耗时 260.86 ms、最大 5.31 ms；Node 552 次、总耗时 37.40 ms、最大 1.03 ms，均无错误。Go 记录 GORM 调用及等待，Node 记录原生 SQLite 调用，两套统计口径不相同，不计算相互倍数。查询次数也包含初始化与业务策略差异，需要结合请求和 SQL 路径分析。

## 值得用于教学的决策

1. 复刻先锁契约，再核行为。相同 JSON 名称远远不够，空值、时间、分页、状态转换和权限也属于兼容性。
2. 按领域拆分代码，让事务由完成业务动作的 service 持有。不要为“用了 ORM”再套一个通用 Repository，把锁和查询能力藏起来。
3. 计数属于不变量。点赞以关系行维护计数，刷新令牌旋转需要原子消费，审核通知与状态必须一起提交或回滚。
4. 三数据库支持必须在真实数据库上验证。MySQL tinyint、更新影响行数、索引字段类型，PostgreSQL sequence，SQLite 外键及写锁，都有不同细节。
5. 数据迁移是独立交付物。只读导出、带版本快照、目标空库、拓扑排序、全事务 dry-run、核对外键和计数，比“复制几张表”更可靠。
6. 文件与 SQL 没有共同事务。共享文件引用及写失败补偿要单独设计；跨进程删除对象需要额外协调。本阶段明确限定单写实例。
7. 测试报告应公开覆盖范围。平台替身不是实际微信服务，客户端请求层 smoke 不是完整 UI 回归，Dockerfile 存在不是镜像已部署。

后续若要评估生产容量，应另做固定版本的 Node 编译产物、多轮交替执行、长时间稳定负载、连接池和数据库指标、部署环境对照。本阶段不据此引入 Redis 或额外缓存协议。
