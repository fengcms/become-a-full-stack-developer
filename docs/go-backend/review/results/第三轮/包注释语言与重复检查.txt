C) 新发现 1：**同包存在多处「包注释」**（go/doc 只呈现一处，其余为无效文档）
--------------------------------------------------------------------------------------
自写工具（go/parser + go/doc.NewFromFiles 真语法树）：
  [cmd/seed] 带包注释文件 2 个 [doc.go main.go]
      go/doc 呈现 = "Package main 显式初始化本地账号和演示文章，拒绝覆盖已有账号。"
  [internal/platform/model] 带包注释文件 15 个 [article_tags.go ... wechat_identities.go]
      go/doc 呈现 = "Package model contains persistence rows, never HTTP responses."

含义：Go 的 go/doc（go doc / pkg.go.dev 的来源）对每个包**只取一处**包注释，
      其余同名注释不会出现在文档里 → 是「写了但读者看不到」的**无效文档**，且会误导改注释的人。
溯源：
  - `internal/platform/model/*.go`（15 处）自原始基线 043fda2 即存在，**非本轮引入**。
  - `cmd/seed`：043fda2 时只有 main.go 的英文包注释（`// Seed is explicit and refuses to
    overwrite existing accounts.`），**没有** doc.go；doc.go 于第一轮整改（9590cb1）为
    「补齐包文档」而新增（中文），与 main.go 既有的包注释**从此并存**；第二轮整改
    又把 main.go 注释译成中文，使两处**语义重叠**（都讲「拒绝覆盖已有账号」）而彻底显形。
→ 属第一轮 A-9「补齐包文档」的**副作用**，落在第二轮同一「文档正确性」维度里。

D) 新发现 2：包注释语言**未统一**（9 中文 / 30 英文），且与本轮新写的口径**不完全自洽**
--------------------------------------------------------------------------------------
本轮在 docs/go-backend/01-Go工程最佳实践.md §8 新增口径：
  「函数、类型及业务规则的散文注释使用中文，导出符号说明以符号名开头。包级说明允许保留英文 Go 惯例；
    编译器指令、协议名、标识符和引用的原文不翻译。」

实测包注释语言分布（生产，按 package 子句前的注释块判定）：
  中文 9 个：cmd/seed cmd/server cmd/migrate cmd/data（各 doc.go）、internal/config/doc.go、
             internal/platform/database/doc.go、internal/testutil/doc.go、
             internal/transfer/snapshot.go、cmd/seed/main.go
  英文 30 个：article auth comment attachment taxonomy administration member notification fault
             values storage platform/model(×15) contract httpapi bootstrap test/clientserver ...
→ 口径写的是「包级说明**允许**保留英文」——「允许」不等于「统一」。
  结果：第一轮为「补缺失包文档」新加的 doc.go 用了**中文**，而原有领域包注释仍是**英文**，
  同一个仓库里两套并存，读者无法预期。对一个**中文教学**仓库，这更接近于「口径没写完」。
→ 需要一次明确拍板：统一中文（翻译 30 处英文）或统一英文（翻译 9 处中文）。
  考虑到「教学可读性」本维度的目标读者是中文学习者，建议**统一为中文**更贴题。
