## 4. 专题：`github.com/fengcms/…` 的「自我引用」解剖

> 用户提问：代码里有 `github.com/fengcms/become-a-full-stack-developer/go-backend/internal` 这样的引用，引用自己的代码为什么要到 GitHub 绕一层，感觉没必要。

**结论：在本项目里「绕一层」并不存在，这是误解；现状正确且惯用，不需要改。**

### 4.1 它是什么——模块**身份**，不是**下载地址**

```go
// go.mod
module github.com/fengcms/become-a-full-stack-developer/go-backend
```

`go.mod` 里的 `module` 行是给这个模块起一个**全球唯一的名字**。Go 允许用域名形状的路径，只是因为这样最容易保证不撞名。它与「要不要联网去取」**完全无关**。

而这份路径**恰好真实**——仓库远端就是它：

```
origin  git@github.com:fengcms/become-a-full-stack-developer.git
```

host / owner / repo / 子目录 `go-backend` 逐段对齐，不是编造的占位。

### 4.2 决定性实证：断网也能编译

```bash
$ GOPROXY=off GOFLAGS=-mod=mod go build ./...      # 关闭一切代理
build_exit=0                                        # 通过
$ GOPROXY=off go build ./internal/transport/httpapi/
httpapi_exit=0
$ go mod verify
all modules verified
```

**如果真要「绕到 GitHub 去取自己」，关掉代理必然失败。** 实测通过 ⇒ 同一个模块内的 import 一律从**本地目录树**解析。这是 Go 1.11+ modules 的基本行为。

### 4.3 两条硬佐证

```bash
$ grep -c "become-a-full-stack-developer" go.sum
0          # 主模块永远不会被当作外部依赖写进校验和
$ go list -m github.com/fengcms/become-a-full-stack-developer/go-backend
github.com/fengcms/become-a-full-stack-developer/go-backend
$ go list -m
github.com/fengcms/become-a-full-stack-developer/go-backend   # 逐字相同 → 解析到主模块自己
```

另外，全仓 `*.md`/`Makefile`/CI 配置里**没有任何** `go get` / `go install` / 依赖该远程路径的写法；179 处自我 import 全部落在本模块的 19 个内部包内，无一处指向模块外。

### 4.4 那到底「有没有值得改的地方」？

有一个**与自我引用无关、但容易被一起问到**的点：本模块位于仓库**子目录** `go-backend/`。若将来真要让外部 `go get`，语义化版本 tag 必须写成 `go-backend/vX.Y.Z`（子目录模块规则），否则取不到正确版本。这属**发布约定**，对当前「clone 即用」的交付方式**零影响**；建议在发布/交付文档里补一句即可。

**若 owner 仍想改名**：改成 `become-a-full-stack-developer/go-backend` 这类「首段带点」之外的路径，Go 本地构建仍可用，但该模块**不可被 `go get`**（首段无 `.` 的路径无法从 proxy 取得），并脱离 Go 社区惯例。改动量 = `go.mod` 1 行 + 51 文件 / 179 行 import 同步替换，**无功能收益**。故此我**不推荐**改，仅把代价列清楚供决策。

### 4.5 诚实边界

沙箱无外网，我**无法**探测该 GitHub 仓库是否 public。但这不影响结论：**本地构建不依赖它可达**；可达性只关系「外部消费者能否 `go get`」，与「自我引用」是两回事。

## 5. 本轮新发现（都落在门禁**语义盲区**里）

> 门禁 `check_go_quality.go` 的「顶层导出符号缺文档 = 0」「无包级文档的包 = 0」只保证**有**文档，**不保证**文档唯一、可达、语言一致。以下三条都在它的盲区里。

### 5-1　同包存在多处「包注释」→ `go/doc` 只呈现一处，其余是**无效文档**（P3）

用 `go/parser` + `go/doc.NewFromFiles` 真语法树检测：

```
[cmd/seed]                带包注释文件 2 个 [doc.go, main.go]
    go/doc 呈现 = "Package main 显式初始化本地账号和演示文章，拒绝覆盖已有账号。"
[internal/platform/model] 带包注释文件 15 个 [article_tags.go … wechat_identities.go]
    go/doc 呈现 = "Package model contains persistence rows, never HTTP responses."
```

- **`internal/platform/model`（15 处）**：每个文件都挂着逐字相同的包注释。`go/doc` 只取一处 → 其余 14 处是「写了但 `go doc`/pkg.go.dev 看不到」的**无效文档**，且会误导后续改注释的人（改了 14 个，文档仍显示第 15 个）。**溯源：自原始基线 `043fda2` 即存在，非本轮引入**（我 `git show 043fda2` 核对过）。
- **`cmd/seed`（2 处）**：`043fda2` 时只有 `main.go` 一条**英文**包注释，**没有** `doc.go`；`doc.go` 是第一轮为「补齐包文档」新增的（中文），从此并存；第二轮又把 `main.go` 那条**译成中文**，两处语义重叠（都讲「拒绝覆盖已有账号」）而彻底显形。→ 属**第一轮 A-9 的副作用**，只是直到这轮才被我的新尺子量出来。
- 反面对照：`storage` 包里 `Local.Put/Get/Delete` 与 `R2.Put/Get/Delete` 的文档逐字相同——这是**接口 + 两个实现**，文档相同**正当**，不构成缺陷。**同一把「重复文本」尺子，一处是真缺陷、一处是误报**，正说明为什么不能把它做成硬门禁（呼应 §6）。

### 5-2　包注释语言**未统一**（9 中文 / 30 英文），口径「允许」未收口（P3）

本轮在 `01-Go工程最佳实践.md §8` 新写的口径是：「散文注释用中文；**包级说明允许保留英文 Go 惯例**」。但实测：

| 语言 | 数量 | 例子 |
|---|---:|---|
| 中文包注释 | 9 | `cmd/*/doc.go`、`internal/config/doc.go`、`internal/platform/database/doc.go`、`internal/testutil/doc.go`、`internal/transfer/snapshot.go` |
| 英文包注释 | 30 | `article` `auth` `comment` `attachment` `taxonomy` `administration` `member` `notification` `fault` `values` `storage` `model(×15)` `contract` `httpapi` `bootstrap` … |

- 「**允许**保留英文」≠「统一」。结果：**第一轮为「补缺失包文档」新加的 `doc.go` 用了中文，原有领域包注释仍是英文**，同一仓库两套并存，读者无法预期。
- 对一个**面向中文学习者**的代码库，这条口径其实**指错了方向**——它把「英文」写成默认豁免，却让新增文档用了中文。**空白口径比错误口径更贵**，而「半截口径」介于两者之间：它让每个人都能为自己这半套找到依据。
- 建议**二选一并写死**：统一中文（翻译 30 处英文）或统一英文（翻译 9 处中文）。按本维度「教学可读性」的目标读者，**建议统一中文**。

### 5-3　接口内方法文档（P3，供参考）

`internal/platform/storage/storage.go:14` 的 `Provider` 接口类型本身有文档，但 `Put/Get/Delete` 三个方法**无各自文档**。门禁 A-3「顶层缺文档 = 0」查的是 `FuncDecl`（含方法），而**接口内方法规格在 AST 里是 `*ast.Field`，不是 `FuncDecl`** → 该断言看不见它们。即「缺文档 = 0」并不覆盖接口方法；这对教学代码是一处可补的盲区（补一条即可，或明确「接口方法文档由实现承担」并写进口径）。

## 6. 对第二轮回复的裁定

作者在回复里有一处**主动不采纳**（§3）：拒绝把「同名符号不同行为的文档不得逐字相同」做成**硬性门禁断言**，理由是「相同说明可能描述相同行为，不同文本也可能同时失实……单纯字符串比较不能证明它」。

**我的裁定：接受，且本轮我用他给的理由反向佐证了他。** §5-1 里 `storage` 的接口/实现三对文档**逐字相同却完全正当**——若真加了「重复文本 ⇒ 失败」的硬门禁，这里会**误报**。他的判断是对的：正确性对应关系需要人工核对，字符串相等既非充分也非必要。**工程规范里写「同名符号要分别说明各自的输入/空值/权限语义」，比加一条会误报的断言更成熟。**

其余口径（静态证据与运行证据分开、不把「门禁通过」当注释正确性的证明、不自行宣称评分、不改评审工具与冻结契约）我均**接受**，与第二轮裁定一致。
