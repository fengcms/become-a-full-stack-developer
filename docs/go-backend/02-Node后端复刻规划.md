# M6 Node 后端同契约复刻规划

> 日期：2026-10-07。状态：用户已确认，G0–G8 已完成；最终证据见 07、09 文档。技术结论见 [工程最佳实践](01-Go工程最佳实践.md)，操作范围见 [接口清单](03-接口与行为对照清单.md)。

## 1. 基线与完成定义

复刻意味着现有客户端能通过切换后端地址继续使用全部能力，而不是重新设计一套相似的 API。

| 基线 | 本次核查结果 |
| --- | --- |
| 契约 | `docs/api/openapi.v1.yaml`，OpenAPI 3.1.0，业务版本 1.12.0 |
| 契约规模 | 54 个路径条目、68 个操作；同一 URL 的不同方法分别计算 |
| 契约 SHA-256 | `7b252c7ca701b45fdfd2a1e9dc7650085ff36e4ee9644265ad3fb6c485a5e030` |
| Node 功能基线 | `node-backend-v1.0.4`，提交 `7effc0276ffdf2fbd8183ec2e60d544ed8998bec` |
| 当前仓库提交 | `e1eb18fa3e59cc106090a7b5b296588e1c170a62`；Node 与 API 文件相对上述 tag 无差异 |
| Node 实际数据层 | Drizzle + SQLite；本地 better-sqlite3，Cloudflare 使用 D1 |
| Go 拟选型 | Go 1.26 + 标准库 HTTP + GORM + PostgreSQL 17 |
| 其他数据库 | MySQL 8.4 LTS、SQLite，纳入完整业务验收 |
| 本机准备 | 已确认 Go 1.26.6、Docker CLI 存在；未确认 Docker daemon 和数据库服务可用 |

验收优先级：冻结契约 → 已确认的产品规则 → Node 行为样例。若 Node 与契约冲突，建立差异记录，Go 遵守契约；不得为了让差分测试变绿而复制违约行为，也不得自行改契约。如果冻结资料相互矛盾且无法判定，才需要单独提请确认。

完成时必须有：68 个操作的实现与测试证据；运行时 health 与文件直出；三数据库迁移和业务测试；四类既有客户端的本地回归；部署/迁移操作文档；测试、性能和已知限制报告。没有测试证据的数据库只能标注“适配中”，不能宣布支持。

## 3. 最容易遗漏的兼容规则

### 3.1 协议与查询

成功请求返回 HTTP 200、`code: 0` 和既有信封。错误码与 HTTP 状态必须对应：1001/1002/1003/1004/1005 → 401；2001 → 403；3001 → 404；3002/3003 → 409；4001 → 400；5000 → 500；5001 → 429。验证错误保留 `data.errors` 的字段与消息结构，限流保留 `Retry-After`。

逐操作核对请求必填性、未知字段策略、空值、枚举、返回字段、权限和错误优先级。一般性规则不能覆盖某个操作明确规定的例外。

列表默认 page=1、pageSize=20，上限 100；Node 当前解析有边界钳制和回退，契约未覆盖的非法输入建立样例记录。文章排序使用允许字段，`publishedAt` 空值用 createdAt 替代，最后追加 id DESC；总页数最小为 1。经实际冻结资料核查，未定义 `fields` 或括号过滤 DSL，不增加新查询协议。搜索、点赞列表、通知列表单独声明默认 pageSize=10、上限50，优先于通用默认20/100；其余非法分页保持有界回退。

Node 搜索关键词查询有 2000 条计数扫描护栏。G0 核对契约中的对应定义和现有输出，在固定数据量边界上做差分；未证明契约要求之前不把“全部精确计数”当作升级。大小写、`%/_`、中文和 Unicode 是跨数据库搜索的专项测试。

### 3.2 认证与账号

保持 bcrypt cost 12 与历史哈希可验证；超 72 UTF-8 字节兼容必须由跨语言向量确认。JWT 保持 HS256、字符串 sub、role 与现有 exp；冻结时钟验证过期边界，不要求新 claims。

刷新令牌仅存摘要，按现有生命周期与 Cookie/body 优先级消费。旋转、重放撤销、登出、禁用、修改密码、管理员重置密码的撤销范围都有独立用例。未知令牌、已撤销/过期令牌、缺失令牌和禁用用户不能合并成一种错误。

微信外部请求固定官方域名并设置超时，不把 AppSecret 或带密钥 URL 写日志。身份唯一约束为 appId + openId；并发首次登录只创建一个用户。旧用户默认已配置本地凭据，微信新用户未配置；首次设密使用条件更新和唯一约束，不能只先查再写。设密失败不撤销已有会话，成功撤销旧刷新令牌并签发新认证结果。微信服务故障和缺失配置必须与原错误映射一致，开发测试通过替身验证，不依赖真实 code 可重复使用。

### 3.3 权限与状态机

角色 member/editor/admin 与 `ownerOverride` 按操作执行。不能把“编辑人员可以编辑文章”推广为“编辑人员可以代作者投稿”：submit 的规则是 admin 或本人。`/me` 始终按当前用户限制，不接受客户端指定其他 userId。

文章 draft → pending → published；会员编辑已发布文章的回待审行为、审核重复请求、软删除释放 slug、未发布文章的可见性单独验证。匿名访问不可见对象保持 404，避免泄露存在性。

分类最大深度是 4；改父节点需防循环并检查整棵子树深度。标签使用 article_tags 精确关系，改名/删除同时维护既有 JSON/显示投影。评论保持接口的平面展开与 parentId，客户端负责盖楼；不得改成嵌套响应。父评论可见性、跨文章回复、整支删除、审核后通知去重都在验收范围。

敏感词比例、星号替换长度与 Markdown 目录锚点存在 JavaScript UTF-16 和 Go rune 差异。准备中文、emoji、重复标题、代码围栏等固定向量；不能直接换一个 Markdown 库然后假设锚点相同。

### 3.4 互动与存储

重复点赞/收藏不能重复增加计数；取消重复操作不产生负数；关系表与计数在事务中保持一致。阅读去重以契约和冻结时钟样例确认时间窗口、匿名身份与登录身份组合，不能把时间桶误称为滚动窗口。历史进度未提交、0、100、null 的更新语义分别验证。

上传保持 sha256 内容 key 加原扩展名，响应 URL 保持 `/files/{key}`，storage 仍为 local/r2。文件直出保持 Content-Type、Content-Disposition 与 nosniff。相同文件多个引用、最后一个引用删除、数据库写失败、远端删除失败及上传/删除并发必须有验证，不能假定 ORM 事务能原子提交文件操作。

## 4. 多数据库与迁移设计

逻辑表来自当前 Node schema，共 15 张：users、refresh_tokens、wechat_identities、articles、article_view_dedup、categories、tags、article_tags、comments、attachments、favorites、view_history、likes、notifications、site_settings。

保留业务关系，不要求物理 DDL 完全相同。三个方言统一迁移编号和逻辑变更，显式定义外键、唯一键、索引、时间、布尔和 JSON。PostgreSQL 是日常默认；MySQL 与 SQLite 不通过降级权限、删除微信能力或禁用事务来换取兼容。

数据库级门禁：空库迁移 → seed → 全部 HTTP 场景 → 并发/回滚用例 → 上一版升级 → 数据核查。每个驱动独立数据实例；SQLite 使用临时文件库、WAL、外键及单写连接，验证实际并发请求及持久化，不以单连接内存库代替文件数据库。PostgreSQL/MySQL 在真实服务上测试，不用 SQLite 替身代表通过。版本选择依据见 [PostgreSQL 支持策略](https://www.postgresql.org/support/versioning/) 和 [MySQL 8.4 官方说明](https://dev.mysql.com/doc/relnotes/mysql/8.4/en/)。

模式迁移属于开发必需；生产数据迁移属于以后单独批准的切换任务。本阶段可完成本地导出/导入工具及演练，不写现有线上数据库、不切换域名。

未来切换预案：一致性快照导出 SQLite/D1 → 校验中间格式 → 导入新数据库 → 校验用户、身份、文章、关系、计数及文件引用 → 修正序列 → 只读核验 → 小范围切换 → 观察与回退。保持用户 ID、bcrypt 哈希、credentialsConfigured、微信身份、日期与对象 key；不能通过重新注册“迁移”用户。

刷新令牌是否迁移、JWT 密钥是否沿用决定旧会话行为；默认演练不复制活跃刷新令牌，正式切换时明确统一重新登录及短时 AccessToken 处理策略。不能宣称只迁移用户表就能无感延续会话。数据冻结期间的增量写入、附件新增和双后端写入禁止规则必须在切换方案中落实；不做没有一致性保障的双写。

Node 在 Cloudflare Workers/D1 的部署方式不能直接搬给 Go + PostgreSQL。Go 拟用 Linux/容器服务，反向代理继续暴露 `/api/v1` 与 `/files`；R2 可继续使用。具体主机、数据库托管和凭据在实际部署节点落实，当前不购买、不部署。

## 6. 契约一致性验证方法

搭建独立测试执行器，针对固定 Node tag 和 Go 实例运行同一组请求。两边使用隔离测试库、相同 seed、受控时钟、微信/存储替身；不向线上发送写入测试。公共场景记录 method/path、身份、前置数据、请求、响应 schema、业务断言与后置数据库状态。

差分允许规范化随机 token、生成 ID、受控时间值和测试主机名，但必须使用明确白名单与 ID 映射。不能忽略状态码、业务码、null/省略、数组顺序、计数、字段类型、Cookie 属性或权限失败。每个操作至少验证成功、适用的鉴权失败与业务边界；重复、并发、撤销和状态迁移跨操作组成场景。

三条证据链同时成立才通过：OpenAPI schema 校验；权限/状态机/数据库后置断言；Node 与 Go 可观察结果对照。仅生成 Swagger 或返回相同字段不代表同契约。

现有 Node 测试为样例来源，包括 auth-flow、wechat、articles、articles-admin、article-tag-sync、categories、comments、interactions、users、attachment 与 storage.r2；移植其业务意图，不机械翻译测试实现。错误码测试、时间控制和条件更新回滚是重点。

四客户端 smoke 覆盖：首页/搜索/详情/分类；注册登录刷新与会员资料；投稿上传审核；点赞收藏历史；评论回复与通知；小程序微信建号及设密后 APP 登录。通过本地地址配置切换验证，保留原默认线上配置。模拟器、微信开发工具及 R2 实测凭据缺失属于环境待办，报告中不能把替身通过当作真实服务联调通过。

## 7. 当前差异与开发前风险登记

| 编号 | 已核查事实 | 处理与关闭依据 |
| --- | --- | --- |
| D01 | 路线图写 GORM/Prisma 对比，Node 当前实际使用 Drizzle | 教学文章准备时修正为 GORM/Drizzle，解释历史选型；本轮不修改路线图 |
| D02 | health、files 运行时存在，未列入当前 OpenAPI 68 操作 | 单列运行时兼容测试，不擅自给冻结契约增加路径 |
| D03 | 契约规定公开端点限流；Node 应用源码未发现统一进程内实现 | 核查网关规则；Go 显式实现本地限流；差分场景配置等效网关，不能按 Node 本地无限流放宽契约 |
| D04 | bcryptjs 与 Go bcrypt 超长输入行为不同 | 成本12、历史哈希与 UTF-8 边界跨语言验证后封装兼容策略 |
| D05 | 文档部分历史表述与源码不一致，例如“无限级”分类 | 使用契约最大4级与测试；记录差异，不凭概括性表述增加层级 |
| D06 | oapi-codegen 主分支支持声明未证明锁定发行版可处理本契约 | G0 生成/编译/schema 验证，不通过则显式 DTO |
| D07 | weibo/github 当前明确返回 HTTP500/code5000、尚未实现 | 保留扩展点的未实现行为，不开发新供应商，按当前500错误行为验收 |
| D08 | ORM、CGO、排序规则、RowsAffected 与 DDL 事务各库不同 | G1 迁移和后续真实库用例共同关闭，禁止只测连接 |
| D09 | Node 本地 CORS 与生产配置策略需逐项核查 | 记录 origin/credentials 样例；生产不允许通配凭据组合，配置加严格校验 |

风险等级以数据安全、鉴权和协议兼容为优先，不按“能跑起来”降低标准。开发中每发现一个差异都写入事实、契约依据、决策、对应测试与关闭状态；本表当前是待验证清单，不是全部问题已经解决。

## 8. 性能与教学输出

先正确，再比较。Node 使用 SQLite/D1，Go 主数据库 PostgreSQL，直接比较两个默认部署栈不能证明语言速度差异。语言实现对照优先选两边同一 SQLite、相同数据/查询/机器/连接与并发；默认部署栈对照另列并明确数据库与托管因素。

记录预热、样本量、吞吐、p50/p95/p99、错误率、CPU、RSS、数据库耗时及 fixture 规模。接口选择公开列表/详情、搜索、登录和互动写入，避免把 bcrypt成本差异或缓存命中误当 Go 性能。所有结果实测后再写，不预设 Go 必然更快。

M6 现有十篇路线可继续使用：Go 最小知识、Web 选型、分层、GORM/Drizzle、中间件认证、并发模型、性能比较、选型建议、契约验证、阶段复盘。三数据库兼容、微信复刻、迁移与 CGO 可成为对应文章的深入案例，是否拆成新增篇章在实际开发经验形成后再调整。

## 9. 本轮确认边界

需要确认的是：标准库 HTTP + GORM 的选择；PostgreSQL 主库与两种可选库的完整验证范围；68 操作及运行时能力的复刻边界；以上分阶段与迁移策略。确认后创建独立 `go-backend/` 并开展开发。当前既有后端、线上服务、客户端和冻结契约保持原样。
