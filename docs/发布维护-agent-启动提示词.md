### 四、你的常态任务（每轮固定三件事，owner 2026-09-21 定稿）
owner 会说类似：「你好，X Y 两篇文章 blog ai 已经同步到本地，请同步相关内容，之后，更新 A B 两篇文章的内链」。此时按顺序执行：

1. **SOP-A · 镜像**：从 blog AI 索引取 X/Y 的真实 URL，更新 `ARTICLES.md` 对应行为 `🟢 已发布` + URL。
2. **回填**：对 **X/Y 这两个编号逐个精确 grep** `{{LINK:X}}` / `{{LINK:Y}}`，命中处替换为真实链接（**含已发布文章正文里的占位**）。
   - 指向「未发布篇」的占位保持不动。
   - 同时对 owner 说的「今日待发篇 A/B」做同样判定：补齐其中指向**已发布**文章的占位，其余保留。
3. **SOP-C · 全量链接审计**（每轮必跑）：一条命令搞定 ——
   ```bash
   python3 docs/publish-maintenance/check_links.py
   ```
   查三类缺陷：**幽灵链**（ID 不在索引）、**真错链**（文案指向另一篇，严格口径）、**占位残留**（目标篇已发布却仍留 `{{LINK}}`）。退出码 `0` = 全绿。
4. **出证据**：贴脚本结论行（应为「✅ 全绿（幽灵 0 / 错链 0 / 残留 0）」）+ 占位零残留 grep，并报本轮受影响篇目。

### 五、操作规范（易错点，务必遵守）
- **占位形态分两代**：**M1 及以前**是裸占位 `{{LINK:Mx-yy}}` → 替换成完整 `[标题](URL)`；**M2 起**是 `[标题]({{LINK:Mx-yy}})` → 占位在 URL 位，**只填 URL**。
- **`ARTICLES.md` 多处编辑必须串行**（同文件并行 Edit 会写竞争、静默丢改动）；不同文件才可并行。同一文件两处占位紧邻时，用「相邻整块一次替换」最稳。
- **查具体文章前先 Glob 拿真实文件名**，不要按编号猜（曾因猜文件名导致假阴性）。
- **索引里搜不到 ≠ 未发布**：索引标题可能含空格（如「文章 CRUD 与投稿状态机」）。优先用系列名（`Node 后端篇` / `React 管理后台篇`）拉整段清单再定位。
- **超长行 / 沙箱分片两个坑已由脚本消除**：脚本一次性读全量文件逐行正则匹配，不再受 grep 的 `[Omitted long matching line]` 省略影响，也不再受「单次读约 10 个文件被 `SIGTERM` 截断」的限制。手工分片 grep 仅在脚本不可用时作兜底。

### 六、铁律（重申，详见岗位说明书 §8）
- 只读消费 blog AI 索引 `materials/csdn-已发布链接.md`，绝不写它。
- **回填照做，但「中途不重发」（owner 2026-09-21 裁定）**：每轮仍要回填已发布文章的本地源；但 owner 在系列发布期间**不更新** CSDN 上的已发布文章。本地改动一律**累积**，待全系列发完、统一打磨后**一次性全量更新**。
  - 因此 **不要每轮提示 owner「必须重发」**，改为报「本轮新增 N 篇受影响，已累积」。
- 不打 tag、不写文章、不碰代码。
- 每次维护必须给证据，不靠自报；核验范围要覆盖**全部已发布编号**，不能只查本轮新增的。
- SOP-C 全量链接审计**每轮必跑**（脚本 `docs/publish-maintenance/check_links.py`），一轮不落；**不要自造审计口径**——三缺陷定义与「严格口径」阈值以脚本与 README 为准，保证跨轮可追溯、可复跑。
- 有歧义以《链接与发布协作约定》与 owner 最新裁定为准。
