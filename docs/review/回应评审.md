## 四、两处重点说明

### 1. R4 认证方案定稿（关键决策）

评审指出「登录返回 refresh 与契约无 refreshToken」「refresh 端点无载体」自相矛盾。定稿方案：

- **access token**：短时效（默认 15 min），`Bearer` 头，前端存内存（非 localStorage，防 XSS）。
- **refresh token**：双载体覆盖所有端——
  - 浏览器：`Set-Cookie` 写 `HttpOnly; SameSite=None; Secure`，刷新时自动携带；
  - 移动端（Flutter/Taro）：响应体返回 `refreshToken`，存系统安全存储，刷新时置请求体。
- `POST /auth/refresh` 读取优先级：Cookie 优先，缺则取体；皆无 → 401（code 1003）。

此方案同时回答了 R4（载体）与 R8（CORS：跨站 Cookie 须 `SameSite=None` + 前端 `credentials:'include'`），并在 02 §三具名指向 M1-12/M1-13/M2-07，使高价值文章的依赖关系清晰。

### 2. R3 编号一致性

M3-15 原为「会员公开主页」，因后期补篇插在 M3-10 与 M3-11 之间造成编号断档。整改保留编号 `M3-15`、将其位置顺移至 M3-14 之后，恢复 01→15 连续，避免污染 `article/M3-15` 的 git tag 语义。M1-25~27 升 P0，使「功能已确认必做」与「文章必讲」一致。

## 五、R19 部分反驳理由

评审建议登录失败返回 `200 + code 1001` 或 `400`，以免触发前端拦截器的「401 自动跳登录」。

我的判断：**401 在此处语义正确，不应为绕过前端实现缺陷而改协议。**

- `401 Unauthorized` 正是「凭证无效」的标准语义；`400 Bad Request` 语义是「请求体格式错」，`200 + 业务码` 则模糊了传输层与业务层，反例是评审自身在 02 §四 强调的「HTTP 状态码只表达传输层结果」。
- 真正的问题是「拦截器对 401 一律跳登录」这一**前端实现陋习**，而非状态码本身。正确教学是：**登录/注册等鉴权端点必须加入拦截器白名单，其 401 不触发跳转**。这本身是一个值得写的真实坑（M2-03 / M1-13），比「为了省事改协议」更有教育价值。
- 因此保留 401，在 02 / 回应文档中固化「拦截器白名单」约定。若评审坚持协议层规避，可让步为 `400`，但本系列选择把它讲透而非绕开。
