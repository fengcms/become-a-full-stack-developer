## 一、复审方法

本轮不是"看回应文字"，而是**逐文件重新读取 + 程序化校验契约**：

- 用 PyYAML 解析 `openapi.v1.yaml`，扫描所有 `responses` 中是否存在"状态码键被错误塞进 schema 内部"的类错误；
- 用脚本枚举全部 33 个操作的响应码，核对 404/403 一致性；
- 逐段比对回应文档的 21 项处置声明与 00/01/02/OpenAPI 实际落点。

> **关键发现**：回应文档声称"契约通过机器校验、所有 200 响应均含 content.schema、无缺失 $ref"。程序化校验证实 22 个 schema、响应结构大体完整——**但漏检了 `POST /articles/{id}/view` 的 `404` 响应被错误嵌套进 `200` 的 `schema` 内部这一结构性缺陷**。宽松 YAML 解析器会"忽略"这个非法键，使校验"假通过"，但后果是**该端点的 404 响应在契约中彻底丢失**（详见 N1）。这说明"机器校验通过"的验收证据不完整。

## 三、🔴 新发现严重问题（必须修，否则"无逻辑漏洞"不成立）

### 🔴 N1 · `POST /articles/{id}/view` 的 404 响应被错误嵌套，契约该端点失效

**证据**（程序化解析 `openapi.v1.yaml` 的 `/articles/{id}/view` 响应结构）：

```json
"responses": {
  "200": {
    "content": { "application/json": { "schema": {
      "allOf": [ {"$ref":".../ApiResponse"}, {"properties":{"data":{"type":"object","properties":{"viewCount":{"type":"integer"}}}}} ],
      "404": { "description": "不存在" }   // ← 错！404 成了 schema 的子键
    }}}
  }
}
// responses 实际只有 "200" 一个键，"404" 不是响应
```

**问题**：`404` 的缩进层级落在 `200.schema` 内部，而非 `responses` 下与 `200` 并列。结果：
1. `responses` 下实际只有 `200`，**该端点的 404 响应在契约中完全丢失**；
2. Schema 对象多出非法键 `404`，严格 OpenAPI 校验器会判无效；
3. 类型生成器拿不到 404 分支，且"文章不存在"场景无契约依据。

**影响**：这是地基级缺陷。回应文档称"所有 200 响应含 content.schema、无缺失 $ref"——该描述虽真，却**掩盖了 404 丢失**。宽松校验器（如大多数 JS 解析器）会静默忽略非法键，造成"假通过"。后续七端照此契约生成代码，view 端点无 404 处理。

**建议**：将 `404` 提到与 `200` 并列（同属 `responses`）；并补 `403`/`401` 视需要。修后用严格校验器（Spectral / openapi-spec-validator）复验，而非仅 YAML 解析。

### 🔴 N2 · 公开接口可泄漏未发布内容（安全 + 正确性漏洞）

**证据**：
- `GET /api/v1/articles`：`security: []`（公开），且 `?status=` 参数 enum 含 `draft` / `pending`（OpenAPI L477-479）；02 §五 标注其鉴权为「否（公开已发布）」。
- `GET /api/v1/articles/{idOrSlug}`：`security: []`（公开，OpenAPI L521），详情端点未做任何"未发布仅作者/管理员可见"的约束。
- `GET /api/v1/articles/{idOrSlug}/comments`：同样公开（OpenAPI L805）。

**问题**：契约允许**匿名**请求携带 `?status=draft` 或 `?status=pending` 拉取草稿/待审文章；且匿名用户凭 id 或 slug 可直接读取未发布文章详情。02 §五 的"公开已发布"只是**文字标签**，机器契约并未强制——任何照 OpenAPI 实现的后端都会把草稿公开。

**影响**：这是真实的数据泄露漏洞，而本项目把"Web 安全基础（B-11：XSS/CSRF/SQL 注入）"列为必发支线。读者若照当前契约实现，恰好写出被 B-11 批评的反例。与"契约即单一事实来源、代码由契约生成"直接冲突。

**建议（二选一，写进契约）**：
- 方案 A（推荐）：公开列表**忽略 `status` 参数、强制只返回 `published`**；`status` 过滤仅对鉴权用户（作者/admin）生效，用于后台管理列表。详情端点：未发布文章对匿名返回 `404`，仅作者/admin 可见。评论列表同理（未发布文章返回 404）。
- 方案 B：列表/详情端点对匿名强制 published，并在 02 §三 显式写明"公开 = 仅 published"的服务端铁律。

无论哪种，必须在契约层面落地，不能只靠 02 的一句标签。

### 🔴 N3 · `view` 端点 `security: []` 使 §2.4 的"登录用户按 user_id 去重"不可达

**证据**：
- 02 §2.4（L226）："**登录用户按 `user_id` 去重**；匿名用户按 `ip+ua` 哈希去重。"
- OpenAPI `POST /articles/{id}/view`：`security: []`（L611），描述仅"阅读量 +1（带防刷去重）"，**未提可选 Bearer**。

**问题**：要用 `user_id` 去重，请求必须携带用户身份（Bearer）。但端点标记为"无需鉴权"，类型生成器不会为它附加令牌，照契约实现的客户端/服务端都不会读取 `user_id` 分支。结果：§2.4 承诺的"登录用户去重"在契约层面**无法触发**，实际全部退化为匿名 `ip+ua` 去重。

**影响**：设计文档与机器契约自相矛盾；读者实现后发现自己写的 user_id 去重永远不生效，却找不到原因。

**建议**：在 view 端点显式声明"可选携带 Bearer；携带则按 user_id 去重，否则按 ip+ua"。保留 `security: []` 以保证匿名可调用，但描述必须点明可选令牌。

## 四、🟠 新发现重要问题（功能不可实现 / 一致性 / 文档漂移）

### 🟠 N4 · `ReadingLog`（阅读历史）无任何写入路径，功能不可实现

**证据**：02 §2.2 定义 `ReadingLog`（last_read_at / progress），01 将"会员中心：收藏、阅读历史"（M3-10）列为功能；但契约中 `GET /api/v1/me/history` **只有读**，无 `POST /me/history`；`POST /articles/{id}/view`（N3）描述仅"阅读量 +1"，未提写入 ReadingLog。

**问题**：领域模型承诺了阅读历史，会员中心文章要讲它，但**没有任何端点能创建/更新阅读历史**。view 端点又是公开无令牌（N3），即使想借 view 顺带写 ReadingLog 也拿不到 user_id。结论：阅读历史在当前契约下**永远写不进去**。

**建议**：二选一——新增 `POST /api/v1/me/history`（上报阅读进度，鉴权）；或显式规定"view 端点对鉴权用户 upsert ReadingLog"（需先解决 N3 的可选 Bearer）。并在 02 §2.2 / M3-10 对应说明。

### 🟠 N5 · 第三方登录无契约端点，M3-09 缺支撑

**证据**：01 §六 M3-09「第三方登录如何统一回同一套用户体系」（微信/微博等归并 User）；但契约 Auth 段只有 `register/login/refresh/logout/me`，**无 `POST /auth/{provider}/callback` 或等价端点**。02 §三 认证约定也未提第三方登录的契约形态。

**问题**：路线图承诺讲第三方登录统一，但"单一事实来源"没有任何落点。读者学到 M3-09 会发现契约里根本没有对应接口，要么自行扩展（偏离契约），要么文章空谈。

**建议**：要么在契约补"第三方登录回调/绑定"端点（哪怕标注为扩展/可选），要么在 M3-09 明确"本课讲设计模式，契约暂不实现，留作扩展点"并在 Non-goals/02 注明，避免读者误以为有现成端点。

### 🟠 N6 · 错误码 4001"附 errors 明细"未进入机器契约

**证据**：02 §六 错误表 L440：「4001 参数校验失败（**附 errors 明细**）| 400」；但 OpenAPI 所有 `400` 响应（`register`、`articles POST`）**均无 `content.schema`**，没有 `data.errors` 结构。

**问题**：02 承诺校验错误带字段级 `errors` 明细，但机器契约里 400 响应是空的。前端类型生成后无法获得 `errors` 结构，M1-10（参数校验）、M2-03（拦截器错误处理）要展示字段级错误时无契约可依。

**建议**：新增 `ValidationError`（含 `field` / `message`）与 `ErrorResponse`（code/message/data:ValidationError）schema，在 400 响应引用；与 02 错误表对齐。

### 🟠 N7 · 资源详情 404 / admin 写操作 403 不一致

**证据**（程序化枚举全部响应码）：
- `GET /api/v1/users/{id}` 仅有 `200`，**无 404**；而 `GET /articles/{idOrSlug}`、`GET /members/{id}` 都有 404；
- `PATCH /api/v1/users/{id}`（admin 改角色/状态）仅有 `200`，**无 403**；而 `POST /admin/articles/{id}/approve|status` 都有 403。

**问题**：同是"资源详情/管理员写操作"，鉴权与不存在响应却不一致。读者按契约实现会出现"用户不存在返回 200 + 业务码"而"文章不存在返回 404"的分裂；`PATCH /users/{id}` 无 403 则权限错误无契约表达。

**建议**：`GET /users/{id}` 补 `404`；`PATCH /users/{id}` 补 `403`（及 404）。保持与 articles/members/admin 端点一致。

### 🟠 N8 · 分类/标签删除的级联与关联处理未定义

**证据**：`DELETE /categories/{id}`（02 §2.2 分类是无限级树）、`DELETE /tags/{id}`（多对多 ArticleTag）在契约与 02 中均未说明删除时的行为。

**问题**：
- 删除有子分类的父分类：树会断（子节点 parent_id 悬空）还是禁止/级联？未定义；
- 删除被文章引用的标签：ArticleTag 关联行如何处理（孤儿关联）？未定义。

**影响**：读者实现时各凭想象，易产生悬空 parent_id 或孤儿中间表行；也是"树/多对多"专题（M1-16、M1-25）的踩坑点却无契约约束。

**建议**：在 02 §2.2 / 契约删除端点补规则——分类删除前须无子节点（或级联置顶/拒绝并返 409）；标签删除须先清理 ArticleTag 关联（或拒绝有引用的删除）。

### 🟠 N9 · 00 §10.2 第 6 条评论态仍写 `pending`（R18 跨文档漂移）

**证据**：00 §10.2 #6（L213）「评论内容安全……；`pending` 为管理员人工兜底态」。但 R18 已将评论人工态在 OpenAPI/02/01 改为 `reviewing`（OpenAPI `Comment.status` enum `[approved,rejected,reviewing]`；02 §2.5 L243；01 M1-27 L132 也写 `reviewing`）。

**问题**：00 文档忘记同步，仍用旧词 `pending`。读者先读 00 会看到与 02/契约矛盾的评论状态名，正好踩中 R18 想消除的"文章 pending 与评论 pending 同名异义"混乱。

**建议**：00 §10.2 #6 改为 `reviewing`，与 02/OpenAPI/01 对齐。

### 🟠 N10 · R19 的决议只写在回应文档，未落入持久规划文档

**证据**：回应文档第五节给出 R19 决议——"登录/注册端点须加入拦截器白名单，其 401 不触发跳转"。但通读 02 §三（认证与 CORS 约定）与 00，未找到"拦截器白名单"或"登录端点 401 不跳登录"的持久表述；02 仅泛提"CORS 是 401 泥潭头号原因，本系列不回避"。

**问题**：R19 是**被采纳的决议**（仅反驳了"改协议"、保留了"加白名单"的教法），但它只存在于回应文档。若读者只读 02/00，看不到这条关键约定，M2-03 / M1-13 照讲时可能漏掉"登录端点 401 白名单"这一真实坑。

**建议**：把"鉴权端点（login/register/refresh）须加入前端拦截器白名单，其 401 不触发跳登录"写进 02 §三（或 00 §九），让决议进入持久文档。

## 五、🟡 新发现建议项（边界 / 完备性）

### 🟡 N11 · 登出清除 Cookie 未体现
02 §三 规定登录/刷新用 `Set-Cookie` 写 refreshToken（浏览器载体），但 `POST /auth/logout` 的契约响应未表达"清除 Cookie"（应 `Set-Cookie: refreshToken=; Max-Age=0`）。双载体设计的登出闭环不完整，读者实现浏览器登出会漏清 Cookie。建议在 02 §三 + 契约 logout 响应注明。

### 🟡 N12 · refresh Cookie 用 `SameSite=None` 的 CSRF 风险未提
02 §三 采用 `SameSite=None; Secure` 让跨站刷新 Cookie 可用。但 `SameSite=None` 会随跨站请求发送，refresh/logout 端点因此面临 CSRF（虽影响有限，因主调用靠 Bearer 头而非 Cookie）。教学项目应点出此权衡或建议双重提交/自定义头防护。02 §三 未提及。

### 🟡 N13 · `level` 字段永不可变且无设置端点
02 User.level「仅展示用、无业务功能；默认 1」（L76）。全契约无任何端点能修改 level（admin `PATCH /users/{id}` 只改 role/status）。结果 level 恒为 1，是"永不变化的展示字段"。读者会问"会员等级怎么来"——要么补 admin 设 level 端点，要么在 02 明确"本期 level 恒为 1、纯占位"，避免读者误以为有升级逻辑。

### 🟡 N14 · `author` 与 `member` 权限边界未解释
角色 enum 含 `admin/author/member`；`POST /tags` 允许 `admin/author`，`POST /articles` 允许 `member/author/admin`。但"何时是 author、与 member 的能力差（可建标签）"未说明；注册默认角色也未写。建议 02 §2.2 User 补一句：注册默认 `member`，admin 经 `PATCH /users/{id}/role` 晋升 `author`；author 比 member 多"管理标签"权限。

### 🟡 N15 · `sort` 白名单字段未枚举
02 §三（L269）"排序 `?sort=publishedAt,desc` 形式，白名单字段"——但白名单具体含哪些字段未列。实现易漂移、且与 ArticleSummary/Article 字段需对应。建议列出允许排序的字段集合（如 `publishedAt, viewCount, createdAt`）。

### 🟡 N16 · 评论删除父级后的子评论处理未定义
`DELETE /comments/{id}` 删除一条评论时，其下回复（parent_id 指向它）应级联删除还是保留为孤儿？02 §2.2 未说明。建议明确（级联删除或拒绝有子节点的删除）。

### 🟡 N17 · 密码 / 邮箱修改端点缺失
会员中心（M3-10「个人设置」）通常含改密码；但契约 `PATCH /me/profile` 仅允许 `nickname/avatar`，无密码/邮箱修改端点。非致命，但"个人设置"功能在契约上不完整，读者实现时会发现改密码无处下手。建议补 `POST /me/change-password`（或明确本期不做并写入 Non-goals）。

### 🟡 N18 · 最小可交付集未含新升 P0 的 M1-25/26/27
01 §13 应急集（30 篇）不含 M1-25/26/27，但 R3 已将它们升 P0（"缺了就断链，必发"）。应急集本意是"精力不足时的可跳过集"，却跳过了 P0 文章，逻辑上矛盾——P0 不该被跳过。建议要么把 M1-25/26/27 纳入应急集，要么在 01 §13 注明"应急集仍须保留全部 P0"。

### 🟡 N19 · 02 端点目录用 `:id` 记号与 OpenAPI `{id}` 不一致
02 §五 端点目录用 Express 风格 `:idOrSlug`、`:id`，而 OpenAPI 用 `{idOrSlug}`、`{id}`。同一份"单一事实来源"的记号不统一，读者易混淆。建议 02 §五 统一为 OpenAPI 的 `{...}` 风格（或加一句说明两种记号等价）。

### 🟡 N20 · 注册默认角色未声明
`RegisterRequest` 无 `role` 字段，但系统有三角色。应显式声明"注册默认 `member`"（与 N14 关联），否则实现者不知新用户角色初值。

## 七、DX / 读者视角总体判断

站在"读者照着这份契约写七端代码，会不会踩坑/卡死"的本项目命脉上：

- **上轮整改合格**：R1/R4/R7/R12 等地基级问题确实补上了，契约从"不可用"变为"基本可用"，这是实打实的进步，应予肯定。
- **但"无逻辑漏洞"尚未达成**，有三道硬伤必须在 M1 开工前清零：
  1. **N1（契约无效点）**：view 端点 404 丢失——用**严格** OpenAPI 校验器复验（不能只靠 YAML 解析），确保所有响应码都在正确层级。
  2. **N2（安全漏洞）**：公开接口泄漏未发布内容——这是会写进七端代码的真漏洞，且与被本系列重点讲授的 Web 安全（B-11）直接打脸。
  3. **N3 / N4（功能不可实现）**：阅读量 user_id 去重不可达 + 阅读历史无写入路径，导致"阅读"相关两篇（M1-26、M3-10）照契约无法实现。
- **文档漂移（N9/N10）**虽不致命，但正是章程最警惕的"文档与契约脱节"——R18/R19 改了 02 与回应文档，却漏了 00 与持久化，必须回填。
- **N5–N8、N11–N20** 属"边界与完备性"，不影响开工，但建议在对应 M 系列 PRD（03–06）撰写时逐一消化，否则会在具体实现篇里暴露为"契约没说清"。

**结论**：建议做**第二轮小整改**，优先清零 N1/N2/N3/N4 与回填 N9/N10，再用严格校验器复验 OpenAPI，然后才进入 M0-03 定稿与 M1 PRD。这样"后续所有文章和代码围绕当前文档实现"才具备"无逻辑漏洞"的前提。
