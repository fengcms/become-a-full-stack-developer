## 一、对复审方法的认可

复审 AI 用脚本程序化校验契约、不轻信回应文字，这一轮方法是对的，也确实抓到了真问题：

- **N1 是上一轮的真实结构性缺陷**，且上一轮"机器校验通过"的声明**不成立**——宽松 YAML 解析器会把 `404` 这个非法子键静默忽略，导致"假通过"。这是我上轮验收方法的失误，复审 AI 的批评成立。本轮改用 **`openapi-spec-validator`（OpenAPI 3.1 规范严格校验）** 复验，结论见第二节。

## 四、本轮对"无逻辑漏洞"的四道硬伤清零说明

1. **N1（契约失效点）**：view 端点 404 此前嵌套在 200 schema 内，严格校验器会判无效、类型生成器拿不到 404 分支。现已归位到 `responses` 顶层，且用 `openapi-spec-validator` 复验 PASS，不再有"假通过"。
2. **N2（安全漏洞）**：公开接口曾可凭 `?status=draft` 或匿名 id 读取未发布内容。现契约层硬约束"公开只返 published、未发布对匿名 404"，并补鉴权后台列表承载 `status` 筛选——与 B-11（Web 安全基础）自洽，照契约实现不会再写出被自己批评的反例。
3. **N3 / N4（功能不可实现）**：阅读量 `user_id` 去重因 view 端点无可选令牌而不可达、阅读历史因无写入端点而永远写不进。现 view 声明可选 Bearer、`POST /me/history` 作为 ReadingLog 唯一写入路径，两篇（M1-26、M3-10）照契约均可实现。
4. **N9 / N10（文档漂移）**：R18 改评论态为 `reviewing` 后，00 §10.2 漏同步、R19 白名单决议只存于回应文档。现已回填 00 并落持久文档 02 §三，消除"文档与契约脱节"。
