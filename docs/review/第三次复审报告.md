## 三、第三轮问题清单（更严苛标准）

### 🔴 严重（必须 freeze 前清零）

#### P1 · 评论 `reviewing` 态是 100% 不可达的死胡同状态机
- **位置**：`openapi.v1.yaml` `Comment.status` enum = `[approved, rejected, reviewing]`（L255）；`02 §2.5`（L253）称"管理员可手动把某条 `approved`/`rejected` 评论置为 `reviewing` 进入人工复核"；但评论变更端点**仅** `DELETE /api/v1/comments/{id}`（L979–999）。
- **问题**：没有任何端点能（a）把评论**置为** reviewing，也（b）没有任何端点能把 reviewing **移出**为 approved/rejected；自动流又"正常不产生 reviewing"。因此 `reviewing` 在 API 层面完全不可触达——它既进不去、也出不来。
- **影响**：§2.5 与 M1-27（评论内容安全，P0）、M3-11（评论系统）都告诉读者"存在人工复核态"，但契约无任何端点支撑，读者照契约写不出"人工复核"，只能写出被自己文档批评的反例。状态机不自洽。
- **修复建议**：新增 `PATCH /api/v1/comments/{id}/status`（admin 专用），`requestBody.status` 枚举 `[approved, rejected, reviewing]`，并补 200 响应 schema（含 `Comment`）。同时明确：自动流只产出 approved/rejected，reviewing 仅由该端点人工置位。M1-27/M3-11 才讲得通。

#### P2 · `Attachment` 实体是孤儿——没有任何端点创建或返回它
- **位置**：`openapi.v1.yaml` `Attachment` schema 定义了 `id/user_id/article_id/url/storage/mimeType/size/createdAt`（L281–292）；`00 §10.2 #7`（L214）声称"Attachment 记录实际 `storage` 后端"；`M1-18 文件上传双实现`（L123）以它为素材。但 `POST /api/v1/upload` 的 `200.data` 是内联对象 `{ url, storage }`（L1014–1030），**不是** `Attachment`；全契约**无**任何端点返回 `Attachment`（脚本核验：引用 `Attachment` schema 的端点数 = 0）。
- **问题**：模型定义了完整 Attachment 实体，契约却永不产生、永不返回它。`mimeType/size/id/article_id` 等字段在契约里无处落地。
- **影响**：M1-18 读者必须自行猜测"要不要落 Attachment 表"——与契约返回 `{url}` 矛盾。要么上传端点应返回完整 `Attachment`（带 id、mimeType、size），要么 02/00 应明确"Attachment 仅为内部审计表、契约不对外部暴露"。当前是悬空矛盾。
- **修复建议**：二选一——（A）`upload` 的 `200.data` 改为 `$ref: Attachment`（填充 id/url/storage/mimeType/size），并视需要补 `GET /attachments/{id}`；（B）在 02 §2.6 与 00 §10.2 #7 明确"上传契约只返回 `{url, storage}`，Attachment 为可选内部表，不在 v1 对外暴露"，消除读者误解。

#### P3 · 普通 `member` 无法列举自己的文章
- **位置**：`GET /api/v1/articles` 公开且**仅返回 published**（L554–585）；`GET /api/v1/admin/articles` 鉴权且限 `author/admin`（L1054–1089，目录表 §五 L446 亦标 `author/admin`）；脚本核验 `GET /me/articles` **不存在**。可见性铁律（02 §三 L287）允许作者本人 `GET /articles/{idOrSlug}` 看自己的未发布详情——但**只解决单条详情，不解决列表**。
- **问题**：§2.3 状态机明确支持 `member` 创建 draft→submit→pending→admin approve。一个 member 必然持有 draft/pending 文章需要跟踪，但**没有任何集合端点能列出"我自己的文章"**。member 既不在 `admin/articles` 权限内，又无 `/me/articles`。
- **影响**：会员中心（M3-10）、投稿流（M1-15/M2-11）的"我的投稿"列表无契约支撑，前端只能逐条 `GET /articles/{id}` 遍历——不现实。核心投稿流在 member 侧断裂。
- **修复建议**：新增 `GET /api/v1/me/articles`（`security: bearer`，返回 `ArticlePage`，仅含当前用户自己的全部 status），或在 `GET /admin/articles` 放宽：member 可访问但只看见自己的文章。推荐前者，语义更清晰。

### 🟠 重要（强烈建议 freeze 前清零）

#### P4 · "view 可选携带 Bearer"不可机器表达，生成客户端永远走匿名分支；§2.4 的"可达"断言对生成客户端为假
- **位置**：`POST /articles/{id}/view` 的 `security: []`（公开，L723），"可选携带 Bearer"仅写于 `description`（L720–722）；`02 §2.4`（L236）断言"这保证 §2.4 承诺的登录用户去重在契约上**可达**"。
- **问题**：OpenAPI 没有"可选鉴权"的标准语义。`security: []` 在代码生成器（M2-04 从 OpenAPI 生成 TS、M4-04 生成 Dart、M6-09 对照）里被解读为"无需令牌"，**生成的客户端永远不会附带 Bearer** → `user_id` 去重分支在生成客户端下不可达。§2.4 的"可达"只对"手写 fetch 并手动加 Authorization 头"成立，对"契约驱动生成"不成立。
- **影响**：直接削弱项目核心承诺"各端由 OpenAPI 生成类型、避免手写漂移"。照生成代码跑，登录用户阅读量仍按 ip+ua 去重，§2.4 自陈的"保证可达"是**错误断言**。
- **修复建议**：要么（a）明确在 02 §2.4 改写为"user_id 去重仅对手写携带 Bearer 的调用可达，生成客户端默认走匿名分支，需在生成后手动补 Authorization"——去掉"契约上可达"的过度声明；要么（b）将该端点拆为公开 `POST /view`（匿名计数）与鉴权 `POST /me/view`（user_id 去重）两个端点，使语义机器可执行。

#### P5 · 列表过滤 `category`/`tag`/`keyword` 与 `sort` 方向语义未定义 → Node 与 Go 必然分歧
- **位置**：`GET /articles` 参数 `category`/`tag`/`keyword`（L566–574）均为裸 `{type: string}`，无说明"按 id / slug / name 哪种标识匹配"；`Sort` 参数（L50–54）描述写"白名单字段：publishedAt, viewCount, createdAt"，但**未定义方向枚举与默认值**（如 `publishedAt,desc` 的 `desc`/`asc`、默认升还是降）。
- **问题**：这些是"沉默即分歧"的典型。Node 实现者可能用 slug 匹配 category、用 name 匹配 tag；Go 实现者可能用 id。sort 方向一个默认 asc 一个默认 desc。契约未定，两个后端必不一致。
- **影响**：M6-09 要靠"同一份 OpenAPI 做对照测试"证明两实现一致——但对照测试只能验结构，验不了这些**未定义行为**；读者照两个后端跑会得到不同结果，动摇"同契约"根基。
- **修复建议**：在 02 §三 + OpenAPI 参数 `description` 中明确：`category`/`tag` 均按 **slug** 匹配；`keyword` 匹配 `title + summary`（不含 content 全文，或显式说明含）；`sort` 方向枚举 `[asc, desc]`，默认 `desc`，分隔符逗号，格式 `field,direction`。

#### P6 · 评论列表返回哪些 `status` 未定义
- **位置**：`GET /api/v1/articles/{idOrSlug}/comments` 返回 `CommentPage`（L921–946），描述只说"未发布文章对匿名 404"，**未说明返回哪些评论 status**。
- **问题**：公开列表应只含 `approved`？作者/管理员是否额外看见 `reviewing`？`rejected` 永不返回？契约沉默。
- **影响**：Node/Go 与前后端实现者各自理解，评论展示不一致；且与 P1 的 reviewing 死胡同叠加，reviewing 评论到底谁看得见也毫无定义。
- **修复建议**：在 02 §2.5 与端点 description 明确：公开与作者均只返回 `approved`；`reviewing`/`rejected` 不在列表返回（仅作者/管理员可在管理视图单独查看）——或直接随 P1 的 moderate 端点一并定义。

#### P7 · 多处"白名单/约束"仅存于散文，契约沉默 → 威胁"七端一致"承诺
- **位置**：`Sort` 白名单（L53，仅 description，schema 无 enum，脚本核验 `has enum? False`）；`category`/`tag` 标识类型（L566–571，无 enum）；view 可选 Bearer（P4）；评论列表 status（P6）。
- **问题**：凡是"白名单/约束"只写在描述文本、不进入 `enum`/`required`/`security` 等机器字段的，代码生成器都无法强制，等于契约对实现"无约束"。这与项目反复强调的"契约先行、避免手写漂移"自相矛盾。
- **影响**：约束的权威性从"机器保证"退化成"人读文档自觉遵守"，七个端各自走形。
- **修复建议**：把可枚举的约束（sort 字段、filter 标识类型、评论列表 status）尽量下沉到 schema 的 `enum` 或显式 `description` + 在 02 单列"机器强制约束清单"，并标注哪些只能靠实现遵守。

#### P8 · `ArticleCreate.slug` 的 member 权限未定义（与 `status` 处理不一致）
- **位置**：`ArticleCreate.slug` 描述"可选；仅管理员可手动指定唯一 slug"（L363–366）；而同 schema 的 `status`（L367–372）明确写了"member/author 传入 published 时后端忽略并降级为 pending"。
- **问题**：`status` 有"member 传入则忽略降级"的显式规则，但 `slug` 只说"仅管理员可指定"，**没说 member 传入时如何处理**——是忽略、拒绝、还是允许？契约沉默。
- **影响**：member 传 slug 时行为未定义，实现者随意，前后端可能冲突（前端若允许 member 填 slug，后端若不处理则静默丢弃或冲突）。
- **修复建议**：与 `status` 对齐，显式补"member/author 传入 slug 时后端忽略（slug 留空，前台用 id 路由）；仅 admin 可指定唯一 slug"。

#### P9 · 全契约 40 个操作无一 `operationId` → 七端生成的函数名可能不一致
- **位置**：脚本核验 40/40 操作均**无** `operationId`（L401 起全部路径）。
- **问题**：OpenAPI 生成器在缺 `operationId` 时，按各语言/工具的规则从 `method+path` 推导函数名（如 `getArticles`、`articlesGet`、`listArticles`），不同端（TS/Dart/Go）推导结果不同。
- **影响**：项目核心卖点"七端复用同一契约生成类型与请求函数"在**函数命名**层面无法保证一致，读者跨端对照时函数名对不上，增加认知负担。
- **修复建议**：为每个 operation 补稳定的 `operationId`（如 `listArticles`、`createArticle`、`viewArticle`、`reportReadingHistory`），命名全局唯一、语义稳定。这是一次性低成本高回报的修改。

### 🟡 建议（可登记为已知边界后冻结）

- **P10 · 邮箱修改 / 找回密码 / 邮箱验证缺失**：注册要求 `email`（唯一），但无 `POST /me/email`、无 forgot/reset password、无验证流程。`change-password` 需旧密码，遗忘即死锁。B-11（Web 安全基础）是 P0 支线，应至少显式将"密码找回/邮箱验证"列为 Non-goals 或后续扩展，避免读者误以为体系完整。
- **P11 · refresh 令牌轮换策略未定义**：`refresh` 返回新 `AuthResult`（含新 refreshToken），但是否**作废旧 refreshToken**（旋转）未说明。安全教程应明确旋转策略（尤其 Cookie 与移动端双载体下）。
- **P12 · `Sort` 白名单未进 `enum`**：同 P7，单列因其直接影响 M1-17（列表三件套）与 M6-09 一致性。建议把字段白名单直接写成 `enum: [publishedAt, viewCount, createdAt]`，方向另作 `enum: [asc, desc]`。
- **P13 · 应急集（33 篇）自洽性存疑**：含 `M1-15`（文章 CRUD 后端）与 `M3-05`（前台列表/详情），却**跳过 `M2-11` 文章管理全流程（创建/发布 UI）**——"上线全栈项目"无人经 UI 发文（只能 curl）。同时含 `M1-26/27`（阅读量/评论后端）却无 `M3-10/11`（前台消费）。应急集自陈"读完能真正建成上线全栈项目"，与缺管理员发布 UI、缺评论/历史前台存在张力。建议要么把 `M2-11`、要么把"经 API 发文"明确写进应急集前提。
- **P14 · `submit`/`approve` 在错误当前态下的行为未定义**：`published` 文章调 `submit`？`draft` 文章调 `approve`？状态机（§2.3）未列这些转移，端点也未声明返回 409/400。建议补"非合法前态则 409"。
- **P15 · `disabled` 会员的公开主页与其文章可见性未定义**：`GET /members/{id}` 对 `status=disabled` 用户返回 200 还是 404？其 `published` 文章是否仍公开？契约沉默。
- **P16 · `:id` / `{id}` 记号等价仅 02 §五声明**：00（如 §10.2 #5/#7）与 README 仍混用 `:id` 且无等价提示。读者只读 00 不会看到 02 的等价说明。建议 00 也加一句"`:param` ≡ `{param}`"。
- **P17 · 被拒评论"闪现后消失"的 UX 未说明**：`POST /comments` 对 rejected 返回 `status=rejected` + `rejectedReason`，但 `GET` 列表不返回 rejected → 用户提交后看到"被拒"一次，刷新即消失。建议 02 说明该交互预期。
- **P18 · 阅读历史无"清空/删除单条"端点**：`ReadingLog` 只能 upsert，无删除。小缺口，可显式列为 v1 不做。
