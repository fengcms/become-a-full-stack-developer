## 一、总体结论

产品 AI 的定位、读者分层、波次串行节奏、Non-goals 边界都相当清晰，是一份**高于平均水准**的开局规划。尤其"文章是产品、代码是素材"的主次关系定得很死，避免了这类项目最常见的"做系统顺手写文章"的失控。

但站在**开发者体验（DX）与教程读者**的立场上，有几处硬伤会直接反噬这个项目本身：

1. 被标榜为"七端唯一硬地基、单一事实来源"的 `openapi.v1.yaml`，**大量端点缺少响应结构定义**，所谓"由 OpenAPI 自动生成各端类型"的目标在当前契约下无法成立——而 M2-04 / M4-04 / M7-06 / M6-09 全都依赖它。
2. 三份 PRD 文档之间存在**数字与编号自相矛盾**（规模数、M3 篇数、M3 编号顺序），以及"已确认的产品功能"却对应"可选文章"的逻辑冲突。
3. 认证刷新令牌的传输方案在文档内部**自相矛盾**，且 `AuthResult` 契约缺少 `refreshToken` 字段。
4. 若干已写入 Non-goals 的约束（"不做消息队列"）与领域模型 §2.4 的设计表述直接冲突。

> **一句话判断**：定位与节奏可以打 85 分，但"契约即地基"这一核心承诺目前**尚未兑现**，需要先把它补成真正可机器消费、跨文档自洽的契约，再开工 M1。否则后面六个子项目会在"类型对不上、路径对不上、文档对不上"上反复返工——而这恰恰是章程最想避免的。

严重度分布：🔴 4 项 · 🟠 8 项 · 🟡 9 项。

## 二、严重问题（🔴 必须修复）

### 🔴 R1 · OpenAPI 作为"单一事实来源"却大面积缺失响应结构

**证据**：`openapi.v1.yaml` 中以下端点只写了 `description: 成功`，**没有 `content` / `schema`**：
- `GET /api/v1/me/favorites`、`POST /api/v1/me/favorites`、`DELETE /api/v1/me/favorites/{articleId}`
- `GET /api/v1/me/history`、`GET /api/v1/me/profile`、`PATCH /api/v1/me/profile`
- `GET /api/v1/users`、`GET /api/v1/users/{id}`、`PATCH /api/v1/users/{id}`
- `POST /api/v1/auth/refresh`、`POST /api/v1/auth/logout`
- `POST /api/v1/articles`（创建后返回什么？）、`POST /api/v1/articles/{id}/submit`、`POST /api/v1/articles/{id}/view`
- `PUT /api/v1/categories/{id}`、`DELETE /api/v1/categories/{id}`、多个 admin 端点等

此外 `PaginatedData.list` 的 `items` 被定义为空 schema `{}`，导致列表项（文章等）的具体字段类型完全未知。

**问题**：文档反复强调"各端请求层类型尽量由 OpenAPI 自动生成，避免手写漂移"（00 §六、02 §一、07 §七）。但类型生成的**输入就是响应 schema**。当前契约下，代码生成器要么拿到 `any`、要么直接报错，与"单一事实来源"的承诺完全不符。

**影响**：M2-04「从 OpenAPI 自动生成前端类型」、M4-04「从 OpenAPI 生成 Dart 模型」、M6-09「契约一致性校验」这三篇高价值文章，其前提条件不成立。读者跟着做会卡在"生成出来全是 any / 编译不过"。

**建议**：
- 补齐所有 `200` 响应的 `content` 结构；列表类统一引用 `PaginatedData`（且其 `list.items` 明确引用 `Article` 或新建的 `ArticleSummary`）。
- 新增 `ArticleSummary`（不含 `content` 全文）供列表、收藏、会员主页复用。
- 生成前的契约应能通过 `openapi-generator` / `openapi-typescript` 跑通一次，作为"契约已就绪"的验收门槛。

---

### 🔴 R2 · 跨文档规模数字与篇数自相矛盾

**证据**：
- `README.md` 第 31 行「核心结论速查」写：**主线 100 篇 + 支线 14 篇（总计 114 篇）**。
- `01-内容路线图.md` 第二节表格与第十三节均写：**主线 103 篇 + 支线 14 篇 = 117 篇**（v1.3 变更记录也明确"主线 100→103、总计 114→117"）。
- `01` 第六节标题写「M3 · Next.js 网站前台（含会员中心）（**14 篇**）」，但同文档第二节表格写 M3 = **15 篇**，且实际列出 15 行（M3-01…M3-15）。

**问题**：同一仓库、同一版本（v1.3）下的数字互相打架。README 的速查区停留在 v1.2 之前的 114 篇，未随 v1.3 同步更新。

**影响**：读者/协作者第一眼在 README 看到的规模就是错的；M3 篇数两处不一致会让"按编号排期"的人困惑到底发 14 还是 15 篇。

**建议**：以 `01-内容路线图.md` 的 103/117 为真值，统一修正 README 速查区与所有"100/114"残留表述；把 M3 第六节标题的"14 篇"改为"15 篇"。

### 🔴 R3 · M3 编号顺序错乱 + "已确认功能"对应"可选文章"的逻辑冲突

**证据**：
- `01` 第六节 M3 表格行序为：`…M3-09、M3-10、M3-15、M3-11、M3-12、M3-13、M3-14`。**M3-15 插在 M3-10 与 M3-11 之间**，编号断档（跳 11–14 又折回）。
- `02` 文档状态为 v1.2「已确认」的功能：§2.2 分类无限级树、§2.4 阅读量防刷、§2.5 评论敏感词过滤、§2.6 附件双存储。
- 但 `01` 路线图中对应实现篇 **M1-25 / M1-26 / M1-27 全部标为 P1（可合并/可选）**。

**问题（两处）**：
1. M3-15（会员公开主页）编号与位置不符，读者看到 `M3-10 → M3-15 → M3-11` 会以为是跳读或遗漏。
2. 已经作为"已定稿产品决策"落进 02 文档的功能，其讲解文章却是 P1 可选——等于"功能必做、文章可发可不发"，自相矛盾。若文章不发，读者就看不到这些"已确认功能"的实现讲解，与"文章是产品"定位冲突。

**影响**：编号错乱会污染 git tag（`article/M3-15` 实际内容在 M3-11 之前），破坏"编号↔tag↔文章"三方绑定（00 §七）的严谨性；P1 与"已确认"的冲突会让排期决策无所适从。

**建议**：
- 将 M3-15 顺移到 M3-11 之后（即保持 01–15 连续）；或确认 M3-15 确为后期补篇并显式说明"插号"。
- 将 M1-25 / M1-26 / M1-27 由 P1 升为 **P0**（功能已确认必做，文章也应必讲）；或反过来把 02 中对应小节标注为"规划中"——二者必须一致。

### 🔴 R4 · 认证刷新令牌设计自相矛盾

**证据**：
- `02` §三 认证原则写：「刷新令牌用 HttpOnly Cookie **或**随登录返回」。
- `02` §五 Auth 表：`POST /api/v1/auth/login` 摘要为「登录，返回 access + refresh」。
- 但 `openapi.v1.yaml` 的 `AuthResult` schema 只含 `accessToken / expiresIn / user`，**没有 `refreshToken` 字段**。
- `POST /api/v1/auth/refresh` 端点 `security: []` 且无 `requestBody` schema，即刷新凭据从何而来未定义。

**问题**：登录"返回 refresh"与契约"AuthResult 无 refreshToken"矛盾；refresh 端点无鉴权却又无请求体，刷新令牌的载体（Cookie？Body？）处于未定义状态。

**影响**：M1-12（JWT 还是 Session）、M1-13（注册登录全流程）、M2-07（前端鉴权/无感刷新）、M3-08（C 端登录态）都会建立在悬空的设计上；读者无法照做一个自洽的刷新流程，且极易写出"refreshToken 存 localStorage 被 XSS 窃取"或"跨域 Cookie 取不到"的漏洞版。

**建议**：二选一并写死：
- **方案 A（Cookie）**：`AuthResult` 不含 refreshToken，refresh 走 HttpOnly+SameSite Cookie；需同步补充 CORS `credentials` 约定（见 R8）。
- **方案 B（Body）**：`AuthResult` 增加 `refreshToken` 字段，前端存内存（非 localStorage），refresh 端点用 `requestBody` 接收。
两方案对"无感刷新竞态"（M2-07 主题）的影响不同，应在 M0-03 / M1-12 明确。

## 三、重要问题（🟠 应修复）

### 🟠 R5 · 路径参数不一致：详情/评论用 `idOrSlug`，写入/计数只认 `id`

**证据**：`openapi.v1.yaml` 中
- `GET /api/v1/articles/{idOrSlug}`（详情）、`GET|POST /api/v1/articles/{idOrSlug}/comments`（评论）支持 slug；
- 但 `PUT /api/v1/articles/{id}`、`POST /api/v1/articles/{id}/submit`、`POST /api/v1/articles/{id}/view` 只接受 `{id}`（整数）。

**问题**：公开前台按 slug 路由（`/articles/{slug}`，章程 §2 与 02 §九均确认"slug 可选、id 为主"）。但"阅读量+1"（view）和"投稿提交"（submit）端点只认数字 id。前台用 slug 渲染时，上报阅读量还得额外持有 id，或后端偷偷兜底——契约与实现会在这里互相迁就。

**影响**：前端请求层封装（M2-03）会出现"同一个文章资源，有的接口传 slug 有的传 id"的分裂，类型生成后调用方容易传错；也是读者高频提问点。

**建议**：`submit` / `view` / `PUT` / `DELETE` 统一改为 `{idOrSlug}`，与详情、评论保持一致；或显式约定"写操作一律用 id，前端从详情响应里拿 id"。二选一并贯穿全文。

---

### 🟠 R6 · `idOrSlug` 静态路径吞噬风险

**证据**：`GET /api/v1/articles/{idOrSlug}` 是参数路径，会匹配任意字符串段。当前无冲突（无 `/articles/tree` 之类静态子路径），但 `slug` 是用户可填字符串（02 §九"slug 可选"）。

**问题**：若未来新增静态子资源（如 `/articles/featured`、`/articles/recommend`），或某文章 slug 恰为 `tree`/`view`/`submit`，会与现有路径冲突。这是 REST「静态路由 vs 参数路由」的经典坑。

**影响**：扩张 API 时被迫改名或加版本，破坏 v1 稳定性承诺（02 §八）。

**建议**：在 02 §三 明确路由优先级约定（静态路径优先于 `{idOrSlug}`）；slug 生成时禁止与预留子路径名冲突（校验白名单）。

---

### 🟠 R7 · 时间格式不统一

**证据**：`02` §三 传输约定「时间用 ISO 8601 字符串」；但 `openapi.v1.yaml` 中 `ApiResponse.timestamp` 的类型是 `integer`（Unix 时间戳），而 `Article.createdAt` 等实体字段是 `string, format: date-time`（ISO 8601）。

**问题**：同一 API 的 envelope 用 Unix 整数、业务字段用 ISO 8601 字符串，违反"时间统一"的自身约定。

**影响**：前端/移动端要写两套时间解析逻辑；Flutter/Dart（M4）对整数时间戳与字符串的解析差异尤其容易踩坑。

**建议**：`ApiResponse.timestamp` 也改为 ISO 8601 字符串，或文档显式声明"envelope 用 Unix、业务用 ISO"并说明原因。

---

### 🟠 R8 · CORS 与跨域凭证完全缺位

**证据**：七端（React SPA `manage-frontend/`、Vue、Next.js、Flutter、Taro）都调同一套 API，但 `00 / 01 / 02 / openapi` 均未提及 CORS、凭据模式（credentials）、同源策略。

**问题**：R4 的 refresh Cookie 方案在"API 与前端不同域"时直接受 CORS 限制（需 `Access-Control-Allow-Credentials` + `SameSite=None; Secure`）。React/Vue 管理后台若是独立部署域，Bearer + Cookie 组合必踩坑。

**影响**：这是全栈教学里**最高频的真实坑**之一，规划却完全没有，等于把读者推向"本地能跑、上线 401/CORS 报错"的泥潭。

**建议**：在 02 或 M0-03 增一节「CORS 与凭证策略」，明确各端部署拓扑下的跨域方案（同源代理 / 跨域带凭据 / 移动端无 CORS）。

---

### 🟠 R9 · §2.4 "消息队列/异步聚合" 与 Non-goals "不做消息队列"冲突

**证据**：`02` §2.4 写「写入独立计数表 / **消息队列**后**异步聚合**」；但 `00` §四 Non-goals 明确「**不做消息队列**……除非某篇文章专门讲它」。

**问题**：同一文档群内，领域模型引用了被 Non-goals 禁止的机制。后文又补一句"不引入 Redis……用唯一约束+冷却时间戳即可"——**"异步聚合"和"唯一约束+冷却时间戳"是两套机制**，混写会让"阅读量防刷"专题（M1-26）讲不清主线。

**影响**：M1-26 作者会纠结到底讲哪条路；读者学到的是矛盾方案。

**建议**：§2.4 删除"消息队列/异步聚合"表述，明确走"唯一约束 + 冷却时间戳"同步写去重表（与 Non-goals 一致）；若想保留异步视角，单独列为可选进阶篇，不与主方案混谈。

---

### 🟠 R10 · 软删除与 slug 唯一约束冲突

**证据**：`02` §2.3 文章删除为**软删除**；`Article.slug`「手动填写则需唯一」（02 §2.2）；但软删除不物理移除行。

**问题**：软删除后，被删文章的 slug 仍占唯一约束，同 slug 无法重建；会员投稿被拒/下架后再发同标题也会撞 slug。这是"软删除 + 唯一 slug"的经典冲突。

**影响**：读者照做会在"删除后再发布"时遇到唯一键报错，且文章（M1-15）未给解法。

**建议**：在 02 §2.2 / M1-15 给出方案：软删除行 slug 加墓碑前缀（如 `deleted_<id>_<slug>`），或将 `slug` 唯一约束改为 `(slug, deleted_at)` 联合（deleted_at 非空时放行）。

---

### 🟠 R11 · `ArticleCreate.status` 对 member 无权限约束

**证据**：`openapi.v1.yaml` `ArticleCreate.status` enum 为 `[draft, pending, published]`；`02` §2.3 说"**会员无法直接创建 published**"。

**问题**：契约允许 member 传 `published`，但权限规则禁止——契约未在任何地方声明"member 传 published 时后端忽略/拒绝"。代码生成器与前端都不会知道要拦截。

**影响**：实现者容易漏掉这层校验，造成越权直接发布；或前端展示了"发布"按钮给会员。

**建议**：在 `ArticleCreate` 的 `status` 字段 `description` 中写明权限约束，或在 02 §2.3 补一段"member 传入 published 的处理（忽略/报错）"，让实现与生成代码有依据。

---

### 🟠 R12 · `MemberProfile.articles` 与列表返回 `content` 全文

**证据**：`openapi.v1.yaml` `MemberProfile.articles` 直接 `$ref: Article`（含 `content` 全文 Markdown）；`PaginatedData.list.items` 当前为空 schema（见 R1），若补成 `Article` 也会带全文。

**问题**：会员公开主页聚合"其 published 文章"，返回每篇全文体积爆炸且无必要；列表接口同理。

**影响**：公开 API 带宽浪费、首屏变慢（与 M3-12 Core Web Vitals 主题冲突）；也是不合理的 API 设计示范。

**建议**：新增 `ArticleSummary`（含 id/title/slug/summary/coverImage/authorName/categoryName/tags/viewCount/publishedAt，不含 `content`），供列表、收藏、会员主页复用。

## 四、一般建议（🟡）

### 🟡 R13 · 主键类型文档与契约不一致
`02` User.id 写「bigint / uuid」，Article/Category.id 写 bigint；`openapi` 一律 `integer`。建议统一口径（如"整数主键，SQLite 下 integer、PG 下 bigint；uuid 选项本期不选"），避免实现者在 D1 与 PG 间摇摆。

### 🟡 R14 · 仓库组织（monorepo vs 多 repo）未明确
`00` §七 的 git tag 机制（`article/M1-05` 全局 checkout）隐含单一 git 历史，但当前目录 `node-backend/ go-backend/ …` 看起来像 monorepo。需显式声明是单仓多目录还是每端独立仓库——否则"读者 checkout 任意文章代码状态"的前提不清，且 M6 写 go-backend 时旧 tag 下该目录为空。

### 🟡 R15 · B 支线被 P0 主线依赖却"允许滞后"
`01` 第十二节 B-07(TS) 被 M1-01 依赖、B-03(Git) 被全系列依赖，但 B 系列"允许滞后于主线"。建议至少把被 P0 依赖的支线（B-02/B-03/B-05/B-07/B-11 等）前置发布，避免主线一开工读者就卡在缺前置知识。

### 🟡 R16 · 文章状态机图缺 `pending→draft`
`02` §2.3 状态机图未画"管理员退回：pending→draft"，但 `POST /admin/articles/{id}/status` 允许置位 draft。建议在图与文中补齐该转移，保持与端点的完全对应。

### 🟡 R17 · M0 / M8 非实现段套用"一个 M 一件实现"
`00` §五 定义"一个 M 只讲一件实现（一个独立代码库）"，但 M0（规划）与 M8（收官）均无对应代码库，却计入主线 103 篇。建议在 01 编号规则里说明 M0/M8 为"非实现的特殊段"，避免读者问"M0 的实现在哪"。

### 🟡 R18 · 评论与文章都用 `pending` 语义不同易混
文章 `pending`=待审，评论 `pending`=人工复核中，同名异义。`02` §2.5 评论状态用 `pending/approved/rejected`，建议评论人工态改名 `reviewing` 以区分，降低读者混淆。

### 🟡 R19 · 登录失败返回 HTTP 401 可能误触前端拦截器
`02` 错误码表 1001→401。多数前端拦截器对 401 有"跳登录"默认行为，会导致密码错误也跳登录。建议登录失败返回 `200 + code 1001`（或 400），仅鉴权过期用 401；在 M1-13 明确。

### 🟡 R20 · "脱敏/通用命名"与契约真实命名的边界
章程 §九"文章只讲通用技术命题，命名改通用"，但 02 / OpenAPI 用的是真实业务命名（Article/Member/Comment）。建议明确：契约与代码是真实素材，文章中讲解时再抽象为通用命名；否则读者会看到"代码叫 Member、文章叫某资源"的割裂。

### 🟡 R21 · M1-18 / M1-24 / §2.6 内容可能重叠
文件上传双实现（M1-18）、双部署适配层（M1-24）、附件双存储（§2.6）三者高度相关，提示在撰文时明确切分（M1-18 讲上传机制、M1-24 讲抽象适配层），避免读者觉得重复。

## 六、DX / 读者视角总体判断

作为 Developer Evangelist，我最后落到"读者跟着这份规划走，会不会顺"这个本项目的核心指标上：

- **最该先修的是 R1（契约完整性）**。它是七端共同的"地基中的地基"。地基没铺好就开工，后面六个子项目每个都会在"类型对不上"上返工——而这恰是章程最想用"契约先行"避免的。建议把"OpenAPI 能跑通类型生成"设为 M1 开工前的硬验收门槛。
- **R2/R3 是可信度问题**。一个连自己文档数字都对不上的系列，读者会先疑三分。修起来成本低、收益高，应第一时间同步。
- **R4/R8/R9/R10/R11 是"教程正确性"问题**。这几处若带病成文，读者复制代码会直接踩到认证漏洞、CORS 报错、软删除唯一键崩溃——本系列"每段代码必须能跑"的承诺（Developer Advocate 内容铁律）会被打破。
- 其余 🟡 项不影响开工，可在对应 M 系列 PRD 撰写时顺手消化。

**结论**：规划方向值得肯定，建议**先完成一轮"契约补全 + 跨文档一致性对齐"再启动 M1 实践**，把上面 🔴 4 项与 🟠 中 R5/R7/R9/R10/R11 作为 M1 开工前必清项。这与 README「下一步待决策」第 1–2 条（路线图评审、M0-03 选型定稿）的节奏是一致的。
