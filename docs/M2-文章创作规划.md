## 一、最终规模与编号原则

M2 由 17 篇调整为 22 篇。旧编号尚未发布，因此本次直接按教学依赖重排；从 M2-01 到 M2-22 就是发布顺序，不再让读者在复盘之后回头补业务模块。

- OpenAPI 只生成 TypeScript 类型，请求函数仍由人工维护；不写成“自动生成整套请求 SDK”。

全项目主线由 115 篇增至 120 篇，总计由 130 篇增至 135 篇。按每周两篇，M2 需要约 11 周。

## 五、写作批次

每批先出逐篇纲要，再写正文；同一批写完后统一复审内链和重复内容。

| 批次 | 篇目 | 预计产出 | 批次复审重点 |
| --- | --- | --- | --- |
| A | M2-01～04 | 4 篇 | 技术栈、工程配置、请求层和契约之间没有重复讲解 |
| B | M2-05～07 | 3 篇 | 三类状态边界清楚，认证文章不重复 M1 后端实现 |
| C | M2-08～10 | 3 篇 | 每篇都从具体交互问题进入，不写组件 API 说明书 |
| D | M2-11～14 | 4 篇 | 用界面解释状态机、权限与关系数据，业务细节能抽象迁移 |
| E | M2-15～18 | 4 篇 | 异步与失败场景有真实证据，账号中心和管理权限不混淆 |
| F | M2-19～22 | 4 篇 | 构建数据真实、部署边界明确、复盘不重复前文小结 |

M2-01～04 完成后先交 owner 阅读一次，以最早四篇校准声音；确认无偏差后再批量推进。这样可以尽早发现“像技术文，但不像 FungLeo”的问题。

## 六、文章统一规格

- 默认篇幅约 2500 中文字（±300）；论证链较长的文章可到 3200 字，但不能靠扩写概念凑字数。
- 固定骨架：前言 → 本文目标/前置 → 真实问题 → 方案比较 → 实现与证据 → 边界/代价 → 小结 → 延伸阅读与订阅。
- 每篇只证明一个核心命题，至少给出一个失败方案或反例、一段真实可运行代码、一项验证证据。
- 每篇配置 2～4 张图：架构/时序/状态图优先，其次是真实界面截图；不放纯装饰图。
- 代码路径来自最终仓库，引用时不写易漂移的行号；代码片段保留中文注释，并交代删掉了哪些无关上下文。
- 内链先用 `{{LINK:M2-xx}}`，并回链对应 M1 文章；不在正文中高频插链接打断阅读。
- 文件名、H1、路线图和 `ARTICLES.md` 标题完全一致。
- 每篇文末带可整段删除的发布辅助区：5～6 个 Tag、250 字以内文章简介、封面及正文配图 AI 提示词、发布核对项。

文风与质量门槛详见 [M2-写作风格与质量标准](./M2-写作风格与质量标准.md)，草稿格式使用 [M2 文章 Markdown 模板](./M2-文章模板.md)。
